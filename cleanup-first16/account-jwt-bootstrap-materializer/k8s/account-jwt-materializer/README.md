# Account JWT signer materializer

This is an opt-in, one-shot infrastructure custodian for the interim Account-only mounted-key fallback in [ADR 0014](../../design/architecture/decisions/adr-0014-phased-jwt-signing-key-rotation-and-readiness.md). It is not included in the ordinary Kubernetes base or Helm deployment. The checked-in assets create no workload, signing Secret, JWKS resource, key, or activation path.

Account remains the only JWT lifecycle, signer-selector, promotion/commit, and JWKS authority. This process may generate one RS256 RSA-3072 key only for Account's exact `GENERATE_PENDING` request and may apply one `PROMOTE_PENDING` private-slot transition only after Account returns its exact PREPARED request. It never signs tokens, writes JWKS, prunes outside that Account-authorized slot transition, or commits Account lifecycle state. A private-promotion receipt is not an Account commit or readiness result.

Build the distribution with `bash dev-tools/validation/run-locked-gradle.sh :account-jwt-materializer:installDist`, then build from the module directory with `(cd k8s/account-jwt-materializer && docker build -t account-jwt-materializer:local .)`. The module-local `.dockerignore` admits only the Dockerfile and generated application distribution, so repository-local credentials cannot enter the image build context. The default image entry point accepts no arguments, reads one protected binding at `/etc/firemud/account-jwt-materializer/binding.json`, performs one bounded reconciliation pass, prints one sanitized public outcome, and exits. The trusted Account bootstrap source also invokes the same packaged entrypoint once with the fixed `--observe-only` argument before its ordinary pass. That mode enrolls or obtains Account's exact generation request, rejects an existing/mixed signer state, observes the fixed Secret through the existing Account RPC, and stops before generating a pending key or attempting promotion. No alternate owner API or success inferred from process output is introduced. Neither mode sleeps, polls, watches Kubernetes, activates a daemon, or selects credentials from environment variables, kubeconfig, or service-discovery metadata.

## Required pre-provisioned state

An operator must separately provide the protected binding and credential files, the Account materializer trust binding, the authenticated Account gRPC endpoint, and the fixed `jwt-signing-keys` Secret. The Secret must already exist in the pinned namespace and be `Opaque`; this process has no create, list, or delete operation. The Account application remains the only application workload that mounts its private projection.

The binding is closed-schema JSON, root-owned, non-writable, and mounted as a regular file. Its parent directory must also be root-owned and non-writable. Every referenced CA, client certificate/private key, and Kubernetes token file has the same ownership and read-only requirements; use read-only file mounts that resolve to regular files rather than projected-volume symlinks. The configuration is reread and its full trust/credential snapshot is checked before and after each external operation. A changed or unreadable binding denies the pass.

Required top-level fields are:

| Field | Meaning |
| --- | --- |
| `schemaVersion`, `enabled`, `configRevision` | Exact enabled binding version and immutable configuration revision. |
| `environmentId`, `clusterId`, `namespace` | Account-selected environment and cluster labels plus the exact namespace. |
| `expectedClusterIncarnationUid`, `expectedNamespaceUid`, `expectedKubeSystemNamespaceUid` | Canonical UUID pins; cluster incarnation must equal the live `kube-system` namespace UID. |
| `expectedServiceAccountName`, `expectedServiceAccountUid` | Exact materializer service account identity. The token subject/claims are checked locally and the same bearer token is used for an authenticated read of this service-account object and every API operation. |
| `expectedMaterializerSpiffeUri`, `materializerSpkiSha256`, `materializerSpkiSha256Pins` | Exact client certificate URI SAN and SPKI digest/pin set; the canonical subset is used to compute the Account trust-binding digest. |
| `accountTarget`, `accountServerDnsName`, `expectedAccountSpiffeUri`, `accountServerSpkiSha256Pins`, `accountCaPath` | Exact Account gRPC TLS endpoint, DNS/SPIFFE identity, SPKI pin set, and server CA. `accountTarget` is `dns-name:port` and its host must equal `accountServerDnsName`. |
| `clientCertificatePath`, `clientPrivateKeyPath` | Materializer mTLS identity presented only to Account. |
| `kubernetesApiServerUri`, `kubernetesApiCaPath`, `kubernetesTokenPath` | Fixed HTTPS API endpoint, API CA, and the scoped projected token. The endpoint has no URL path, query, or fragment. |

All digest pins are lowercase SHA-256 hex. Account server TLS validates the CA chain, exact server URI SAN, SPKI pin, and DNS name. Kubernetes HTTP uses the pinned HTTPS endpoint and API CA, no proxy selector, no redirects, bounded response sizes, and finite connect/request deadlines. The API client performs only GETs for the pinned namespace, `kube-system`, its exact service account, and `jwt-signing-keys`, plus a resourceVersion/UID-guarded merge PATCH to that fixed Secret.

## Reconciliation and ambiguity

The observation-only pass reads the exact Account request, checks that no current, pending, or previous signer slot or lifecycle marker exists, reports the fixed Secret's UID/resourceVersion through `RecordSecretObservation`, validates Account's exact resulting `GENERATE_PENDING` response, and exits without writing the Secret. Before starting the ordinary pass, the trusted fixture performs one bounded PostgreSQL statement against its run-owned Account database. It reads only Account-owned desired-state, generation-operation, and Secret-observation identity/digest fields and proves their namespace, cluster, trust-binding, API-binding, operation, and fixed Secret UID/resourceVersion correspondence. Missing state is denial, not proof of no signer. The ordinary first generation pass then reads that same operation, writes only `pending.key` with an operation ID, request digest, and expected prior resourceVersion annotation, reads back the exact fixed Secret, and submits only the public JWK and Secret fence to Account. The bundle uses `AccountMountedJwtSignerBundle` v1 fields and canonical unpadded URL-base64 PKCS#8 bytes.

If a write response is ambiguous, this process never retries the PATCH in that pass. It performs read-only reconciliation. A later invocation may reuse stored `pending.key` only when the exact authenticated Account operation/request/prior-resourceVersion annotation and key identity read back. A different, partial, or malformed marker, a stale resourceVersion, or a missing stored key is denied; there is no overwrite, key regeneration, or invented receipt for an ambiguous operation.

Promotion is handled only from Account's exact PREPARED response. The request must name `PROMOTE_PENDING`, the fixed Secret UID/resourceVersion, the generated key identity, and exactly `current.key`, `pending.key`, and `previous.key` as allowed slots. The process verifies the pending key and Account's expected prior-current identity, moves only those authorized slots, reads the transition back, then reports public key identities and resulting slot names. Account decides whether to commit its lifecycle. Conflicts, mismatches, malformed responses, unavailable dependencies, and missing Account preconditions remain denied.

The process prints only one of `secret_observation_recorded`, `generation_recorded`, `generation_already_recorded`, `private_promotion_receipt_recorded`, or `denied`. Private key bytes and private-bundle JSON are never included in logs, status, RPCs, source fixtures, or tests.

## Trusted disposable bootstrap fixture

[`prove-account-jwt-bootstrap.sh`](../../dev-tools/hosted/account-bootstrap/prove-account-jwt-bootstrap.sh) is a trusted GitHub-hosted Linux runner-only source lifecycle for a uniquely run-owned, disposable kind cluster. It verifies the protected `develop` run, repository, commit, run ID and attempt, uses the exact kind, Kubernetes node-image, and kubectl pins in [`workflow-tool-versions.env`](../../config/workflow-tool-versions.env), records the observed API address, context, and `kube-system` UID, and deletes only the cluster whose recorded identities still match. Existing kubeconfig contexts, kind clusters/nodes, Docker containers or kind network are refused; failed or ambiguous ownership checks retain resources and report an explicit denial. The cluster uses a private run-and-attempt kubeconfig and does not join an existing cluster.

The pins currently pair kind v0.33.0 with its publisher-listed Kubernetes v1.35.8 node image digest and kubectl 1.35.9 from the same Kubernetes minor. Sources: [kind v0.33.0 release metadata](https://github.com/kubernetes-sigs/kind/releases/tag/v0.33.0) and its [Linux amd64 release checksum](https://github.com/kubernetes-sigs/kind/releases/download/v0.33.0/kind-linux-amd64.sha256sum). Renovate updates kind with its release checksum and updates the node-image tag with its digest as one repository authority block.

This entrypoint deliberately reports `fixture_ready` only as disposable-cluster evidence and then returns `incomplete_proof_flow`; it never reports login success, `COMMITTED`, or an open Account readiness gate. Its trusted-runner lifecycle composes two run-owned TLS-only Redis Pods from the repository-pinned Redis image, isolated AOF volumes, the `account_coord_app` boundary for token, issuer, account, selected-tenant, and membership key families, and a same-connection write/readback plus `WAITAOF 1 1 1000` proof. The primary and replica mount distinct immutable ACL Secrets: the Account user and password are primary-only, while replication and fixture-inspection roles retain separate needs. The fixture records replica/AOF/config evidence and requires plaintext and mismatched-CA probes to fail.

The Account source helper builds the Boot JAR from the exact claimed checkout, builds a run-tagged image from the pinned Account Dockerfile/base image, verifies its source revision and image ID, and imports that image into every node of the run-owned kind cluster. It starts the pinned PostgreSQL 16 image with a run-only credential Secret, ephemeral storage, a private ClusterIP Service, and a bounded readiness probe. After PostgreSQL readback, it copies the exact run-owned Redis binding, CA, and ACL credential from the Redis fixture's immutable owner Secret into regular files on the selected kind control-plane node. The per-run mount directory is `root:root` mode `0700`; each file is `root:65532` mode `0440`, and only the Account Pod receives supplementary GID `65532`. Every copied file's bytes, owner, group, mode, and regular-file type are read back before Pod creation and again before teardown.

The trusted Account source composes `account-inputs/` only after rechecking the protected `develop` run identity and the live run namespace UID/ownership. It derives the Account API binding from the API-server issuer/audience arguments and the exact CA in the run kubeconfig; it creates short-lived Account-server and materializer-client TLS leaves from a run-owned CA, validates their SAN/SPIFFE identities, chain purposes, and private-key/public-key correspondence, and removes the CA signing key. It also creates response-envelope and LOGIN-digest keyrings in the exact Account reader formats and builds the run/namespace/UID-bound materializer trust binding pinned to that client leaf. The bundle is root-of-trust-local to the owner-only runner directory (`0700` directories, `0600` regular files), accompanied by a run-identity/file-digest owner record, and rechecked before staging. Symlinks, missing or changed files, stale namespace identity, malformed material, and cleanup identity drift deny progress; cleanup removes only exact owner-recorded files after the run-owned cluster is torn down. The materializer client private key remains confined to its one-shot owner Job. PostgreSQL credentials are passed only by Secret key reference. The runner creates the exact fixed `jwt-signing-keys` Opaque Secret initially without data and mounts that Secret directly, read-only and without aliases, into only the Account container; it never generates or injects a JWT signing key. Subsequent signing-key bytes can only be produced by the existing Account-owned materializer lifecycle.

The Account workload is a run-owned, single-replica Deployment with an unset readiness condition and an internal ClusterIP Service; its explicit `firemud.account.gameplay-canonical-login.security.enabled=true` composition retains mandatory gRPC mTLS and serves the protected JWKS route over HTTPS using the existing `firemud-grpc` server certificate bundle. The source verifies that the bound leaf certificate carries both the canonical service DNS SAN and the Account service-account SPIFFE URI before wiring HTTPS. It runs on the node holding its protected files, keeps service-account automount disabled, and uses read-only regular-file mounts for static inputs. The original Pod spec projects a 600-second service-account token at the fixed API path, with an audience sourced from live API-server issuer/audience arguments, mode `0440`, and the restricted `fsGroup` needed by the non-root Account process. The projection remains kubelet-managed with its versioned symlink layout; the runner checks only link and target metadata, never token contents. A run-scoped namespaced Role is derived from the protected validator inventory and limited to JWKS ConfigMap reads, exact validator Deployment/ReplicaSet reads, and Pod listing in the run namespace; a ClusterRole is limited to namespace reads and SelfSubjectReview creation. Exact Role/RoleBinding/ClusterRole/ClusterRoleBinding UIDs and rules are read back. The receiver Deployment is created first; only after Kubernetes allocates the real Account Pod UID does the fixture bind the inventory to the actual Deployment/ReplicaSet/Pod UID, Pod IP, image, and TLS leaf SPKI. It atomically publishes the protected inventory into a root-owned directory mounted by that same Pod, rechecks that the receiver identity did not change, and then installs the inventory-derived read-only RBAC. Missing, stale, or replacement receiver identity denies the remaining steps; restarting the Pod requires a fresh inventory binding. Secret-derived digests stay in the owner-only receipt and are not included in public fixture output. The Account container receives the fixed Secret and the public JWKS ConfigMap at their canonical reader paths. The Account Pod remains non-ready and the Service retains normal endpoint semantics throughout the owner calls.

The response-envelope and LOGIN-digest keyring readers each take a protected directory root and resolve its literal `keyring` regular-file child. The Account Pod therefore mounts those files at `/etc/firemud/account-response-envelope/keyring` and `/etc/firemud/account-login-digest/keyring`, while the corresponding environment settings name the parent directories.

After live Deployment/ReplicaSet/Pod UID and IP inventory are read back and the exact API RBAC is installed, the source composes the existing packaged owner lifecycle in four finite, run-owned Jobs: an observation-only `MaterializerMain`, an ordinary `MaterializerMain`, one `ReadinessHarnessMain` call, and a follow-up `MaterializerMain`. Each materializer Job uses the protected Account/server and client TLS binding, its own 600-second projected API token with the observed audience, and only the exact Secret/RBAC permissions. Each Job is pinned to the Account node and maps only the canonical Account Service DNS name to the current inventory-bound Pod IP with per-job `hostAliases`; pre- and post-call readbacks reject Pod UID/IP, Deployment, Secret, ConfigMap, mount, token-audience, or image drift. The harness has a distinct mTLS identity and no Kubernetes token. Job output is accepted only as the packaged owner's bounded outcome and never as a durable operation, receipt, ACK, or commit. After the initial observation pass, the fixture reads desired state, generation operation, and persisted Secret observation together in one PostgreSQL statement snapshot and correlates the exact live Secret UID/resourceVersion, protected trust/API bindings, fixed resource identities, and mounted receiver-inventory digest before invoking the ordinary generation pass. It then reads back the existing Account generation result and, after readiness and follow-up reconciliation, the Account promotion `COMMITTED` state, Secret/JWKS resource versions, readiness plan, inventory snapshot binding, and complete persisted probe/Pod-receipt counts. These are reads of existing Account-owned rows; no new owner table, signer endpoint, or parallel status API is added. The fixture retains these digests and operation identities only in its private receipt and rechecks the committed snapshot before teardown. This is source preparation only: no such SQL or Job was executed during source preparation, and the fixture continues to return `incomplete_proof_flow`; no readiness, signer activation/promotion, or player-login success is claimed. Deployment and key generation require coherent independent review and separate trusted-run authorization.

## One-shot readiness harness caller

The same distribution contains a separate `account-jwt-readiness-harness` launcher at `build/install/account-jwt-materializer/bin/account-jwt-readiness-harness`. The default `account-jwt-materializer` entrypoint is unchanged. This opt-in caller reads only `/etc/firemud/account-jwt-readiness-harness/binding.json`; it does not consult environment variables, kubeconfig, command-line endpoint overrides, the Kubernetes API, the materializer binding, or the JWT signing Secret. Its only private key is the distinct readiness-harness mTLS client identity.

The closed schema contains exactly `schemaVersion`, `enabled`, `configRevision`, `environmentId`, `clusterId`, `namespace`, `expectedClusterIncarnationUid`, `expectedNamespaceUid`, `validUntilEpochSecond`, `accountTarget`, `accountServerDnsName`, `expectedAccountSpiffeUri`, `accountServerSpkiSha256`, `accountServerSpkiSha256Pins`, `accountCaPath`, `expectedHarnessSpiffeUri`, `harnessClientSpkiSha256`, `harnessClientSpkiSha256Pins`, `clientCaPath`, `clientCertificatePath`, and `clientPrivateKeyPath`. It binds the namespace and expected UIDs, short-lived configuration revision, exact Account DNS target and port, Account server DNS/SPIFFE identities and SPKI digest/pins, exact readiness-harness SPIFFE identity and client SPKI digest/pins, and protected paths for the Account CA, harness client CA, client certificate, and client key. The cluster/namespace UID values are protected run metadata only: this caller has no Kubernetes client and does not independently compare them with live objects; the trusted runner must source those values from its exact disposable resources. All files and their immediate parent must be root-owned, regular, and non-writable; credential paths must be direct children of the protected directory so projected-volume symlinks are rejected. Credentials are reread and compared as one snapshot before and after the call. The harness client certificate must have the exact role URI SAN, be currently valid, permit client authentication and digital signatures, chain to the bound client CA, match the pinned SPKI, and correspond to its protected private key. Account's peer must chain to the bound CA and match the exact DNS name, SPIFFE URI, and SPKI pin. The channel has no proxy detector or retries and uses a fixed finite RPC deadline.

The caller makes exactly one schema-version-1 `AccountJwtReadinessValidationService/IssueReadinessProbes` request. It never calls `ValidateReadinessProbe` and never interprets a response as validator convergence, a readiness receipt, signer promotion, or `COMMITTED` proof. It checks only the response's known-field/schema boundary and nonempty complete inventory-plan shape, then prints the bounded outcome `readiness_batch_requested`; any invalid or unavailable state prints `denied`. The Account owner remains responsible for the durable plan, actual probe delivery, per-Pod production-validator calls, receipts, and promotion proof. A successful caller outcome alone does not prove those receipts were committed or that a player can log in.

## Opt-in RBAC

`rbac.yaml` is a separate operator-applied asset. Replace `ACCOUNT_NAMESPACE` with the exact namespace before applying it. Its namespaced Role grants only get/update/patch on `jwt-signing-keys` and get on the exact materializer ServiceAccount. Its ClusterRole grants only get on that namespace and `kube-system`, bound to the materializer identity. It grants no JWKS access and no Secret list/create/delete permission. This RBAC does not provision or activate a workload, token, binding, key, Secret, or JWKS resource.
