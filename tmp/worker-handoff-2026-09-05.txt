4. What repeated review is revealing

- Distinct plugin bindings could be coalesced because durable work/audit identity omitted stable binding identity. That can silently drop legitimate plugin commands.

- Real PostgreSQL partial-index, reclaim/renewal, and FK-retention behavior lacked executable concurrency proof.
- Parallel fixes themselves introduced a proto field-number collision and initially incomplete timer/binding propagation; verification caught those before integration.
Classification:
- Pre-existing defects: missing binding identity, missing ingress digest, incomplete handoff pin fence, weak database concurrency proof.
- Defects introduced by fixes: field-number collision, partial propagation, initially timing-dependent integration proof, and earlier over-coupling of independent diagnostic filters.
- Newly made explicit requirements: durable stable binding identity and exact source/target pin evidence were already latent in canonical contracts but had not been translated into all schemas and services.
- Boundary-expansion findings: Game Session owner enforcement, scheduler propagation, and downstream admission appeared because reviewers correctly followed Automation evidence into consumers.
Continued findings are driven by four things:
- 5B invariants are inherently cross-service and cross-layer.
- The original code implemented fragments of target contracts without one closed end-to-end slice.
- Every legitimate fix exposes adjacent identity/persistence consumers.
- Repeated splitting and long-lived branches create integration drift and cause reviewers to rediscover stale or partially propagated facts.
Evidence supported continued depth: the latest broad Luna checks found real command-loss and idempotency defects, the last CLI returned 15 raw/11 accepted, and hosted at 16:10 returned 13 threads, many useful. That is not genuine taper.

A finish boundary is justified when new findings are duplicate, already fixed, transient status-only, cosmetic, or owned by a clearly separate implementation slice—and especially after two stable-head reviews find zero genuinely useful contract defects. Process changes I recommend:
- Keep semantic domains smaller than the original 5B, not merely under a file cap.
- Stop broad new discovery while a large known-finding backlog is unconsumed.
- Integrate correction branches frequently; do not let parallel branches diverge for hours.
- Treat CodeRabbit’s 100-file ceiling purely as packaging, never as a reason to omit a fix.
- Refresh the live tracker at each merge/split; stale status caused real orchestration errors.
- Collapse and remove verified-contained worktrees immediately after each merge.
- Separate “stable contract defect” from “current status maintenance” in review counts.
- Preserve the strongest parts of the process: independent verification, hosted-first scheduling, full-section reviews that may follow seams, canonical-owner dedup, and explicit current-versus-target honesty.
Candid revision: I previously treated 5B as if sufficient review could make one expanding surface terminal. That was wrong. The review depth found important defects, but the unit became too broad and too implementation-heavy to remain a useful single corpus section. The right response is not to reduce correctness; it is to finish the current coherent chain, then manage future discoveries as smaller semantic implementation slices alongside the remaining corpus review.

7. Deployment-gate applicability update (2026-09-07)
The current `develop` dev-demo workflow deletes and recreates namespace `dev` before deployment. Its PostgreSQL, Redis coordination/cache, and MinIO state are namespaced PVCs using the cluster-provided `local-path` StorageClass; service configuration names only those in-cluster endpoints, and no external database or Redis owner is configured. The seed hook therefore targets a fresh deployment. Old Game Session `STAGED` rows and Automation owner/epoch/pin state do not enter this deployment through the configured path after successful namespace deletion. A merely retained orphan PV would require an actual reattachment/reuse path before its bytes could become upgrade input. Consequently the inherited live-row drain checklist is not a merge gate for this disposable dev-demo path; post-merge evidence should instead confirm namespace reset, rollout, bootstrap, and smoke. This bounded applicability check did not inventory live data or change deployment tooling.
