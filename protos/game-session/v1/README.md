# Game-session Service Proto (v1)

This directory contains version 1 protocol buffer definitions for the game session service.
They describe the gRPC API exposed by the service.

Generate Java stubs with `./gradlew generateProto` from the repository root.

- `GetPinnedScriptPatchVersion`, `GetGameSessionPinConvergence`, and `GetGameInstanceRuntimeState` now all expose linked Game Design script-patch publication metadata alongside the persisted Game Session pin/runtime truth, so operator tooling can inspect current pin state without a second join.
For details see the [design docs](../../../design/architecture/microservices/game-session-service/README.md).

## Control Plane APIs

This proto now includes a separate `GameSessionControlPlaneService` for operator-driven actions (script patch pinning/rollback, pin-convergence/runtime-state reads, scoped tick pause/resume, queue purge hooks for rollback safety, and internal remote-followup scheduling over the durable cross-region substrate) as specified in `design/architecture/system-architecture-scripting-control-plane-api.md`. The Game Session pin reads now also return linked Game Design script-patch publication metadata alongside the persisted `controlPlaneRequestId`, actor, timestamp, and runtime-state fields instead of exposing only raw patch version strings. The command-status read accepts either `commandId` or the automation tuple `(tenantId, gameInstanceId, regionId, regionEpoch, automationDispatchId)` so operator tooling can correlate Automation handoff history with the Game Session command ledger, and it now exposes the current-boundary comparable `enqueueSeq`, plugin provenance, linked plugin publication metadata, carried automation origin-source metadata, and structured remote-result command/error/message summaries too. The runtime ownership status read returns the explicit stored `regionId` plus the current `lastCommittedTickId` from the same durable ownership row used for `regionEpoch` and executor fencing, and it now also exposes current remote follow-up backlog lag directly as `remoteFollowupDrainLagMs`; callers may resolve that ownership row by `regionId` directly, with `gameInstanceId` retained as the current-boundary fallback while true region partitioning remains future work. That same stored scope is also the tick progress value Game Session publishes to Automation's scheduler feed. Game Session control-plane reads now also expose the first durable remote-runtime substrate directly: remote command coordinators, their explicit `followupId` links, remote follow-up rows, and origin-addressed remote result rows now all cross-link plugin publication metadata alongside script-patch publication metadata, the linked target-side gameplay command row for remote-admitted work, and the internal schedule surface that returns durable coordinator/followup ids plus created-vs-reused truth for remote follow-up submissions. That internal schedule surface now also carries origin-source metadata as first-class request fields instead of forcing callers to smuggle that tuple through payload JSON. `ListRemoteFollowupResults` now carries the target command's execution/gameplay status too when the result payload references a concrete command id, so result reads no longer stop at payload parsing. The first shipped remote payload/result summaries now also prefer durable row authority: follow-up rows persist `payloadKind`, requested command text, `requiresSoloTick`, and remote origin-source metadata, result rows persist `resultCommandId`, `resultErrorCode`, and `resultMessage`, and target-side execution plus control-plane/gameplay status reads only fall back to reparsing JSON for older rows that predate those first-class columns. The sealed `REMOTE_FOLLOWUP_QUEUE` manifest now carries that same persisted origin-source tuple beside routing/provenance/payload summaries, so replay and operator reads no longer need payload JSON to reconstruct target-side automation admission origin. The new remote-runtime service layer also makes that substrate executable on the origin side for schedule, result-recording, and timeout-reconciliation paths, and target-side remote execution now supports both automation-command and gameplay-command enqueue payloads using persisted remote-row provenance rather than payload-only identity. The internal `EnqueueAutomationCommandIfAbsent` handoff surface now also allows immediate event-driven automation to omit `dueTickId`; scheduler/timer producers still carry it when a real due point exists, and the handoff preserves scripting-side origin-source metadata so later ledger and manifest reads can distinguish gameplay-triggered work from scheduler-triggered work. New automation handoffs are fenced by Game Session's current runtime ownership row and reject missing ownership, paused ownership, or stale `regionEpoch` before Redis tick-queue mutation. Automation handoff carries script-patch and plugin-version provenance so Game Session can purge queued commands by either rollback scope.

The existing `PauseTicks` / `ResumeTicks` RPCs on `GameSessionService` remain the minimal, backup-oriented APIs; the control-plane service is the normative surface for per-tenant/game/region operations.
