# Game-session Service Proto (v1)

This directory contains version 1 protocol buffer definitions for the game session service.
They describe the gRPC API exposed by the service.

Generate Java stubs with `./gradlew generateProto` from the repository root.

- `GetPinnedScriptPatchVersion`, `GetGameSessionPinConvergence`, and `GetGameInstanceRuntimeState` now all expose linked Game Design script-patch publication metadata alongside the persisted Game Session pin/runtime truth, so operator tooling can inspect current pin state without a second join.
For details see the [design docs](../../../design/architecture/microservices/game-session-service/README.md).

## Control Plane APIs

This proto now includes a separate `GameSessionControlPlaneService` for operator-driven actions (script patch pinning/rollback, pin-convergence/runtime-state reads, scoped tick pause/resume, queue purge hooks for rollback safety, and internal remote-followup scheduling over the durable cross-region substrate) as specified in `design/architecture/system-architecture-scripting-control-plane-api.md`. The Game Session pin reads now also return linked Game Design script-patch publication metadata alongside the persisted `controlPlaneRequestId`, actor, timestamp, and runtime-state fields instead of exposing only raw patch version strings. The command-status read accepts either `commandId` or the automation tuple `(tenantId, gameInstanceId, regionId, regionEpoch, automationDispatchId)` so operator tooling can correlate Automation handoff history with the Game Session command ledger, and it now exposes the current-boundary comparable `enqueueSeq`, plugin provenance, linked plugin publication metadata, carried automation origin-source metadata, structured remote-result command/error/message summaries, the remote origin/target game-instance and region scope plus deadline policy, and the linked target command's execution/gameplay outcome when the command is in the cross-region follow-up path. The runtime ownership status read returns the explicit stored `regionId` plus the current `lastCommittedTickId` from the same durable ownership row used for `regionEpoch` and executor fencing, and it now also exposes current remote follow-up backlog lag directly as `remoteFollowupDrainLagMs`; callers may resolve that ownership row by `regionId` directly, with `gameInstanceId` retained as the current-boundary fallback while true region partitioning remains future work. That same stored scope is also the tick progress value Game Session publishes to Automation's scheduler feed. Game Session control-plane reads now also expose the first durable remote-runtime substrate directly: remote command coordinators, their explicit `followupId` links, remote follow-up rows, and origin-addressed remote result rows now all cross-link plugin publication metadata alongside script-patch publication metadata, the linked target-side gameplay command row for remote-admitted work, and the internal schedule surface that returns durable coordinator/followup ids plus created-vs-reused truth for remote follow-up submissions. Remote coordinator reads are no longer point-lookup only either: `ListRemoteCommandCoordinators` now provides the same bounded filterable view over persisted origin/target game-instance and region scope, linked `followupId`, script/plugin/dispatch/command provenance, admitted routing-bundle fields, and followup target-leg traits (`targetEntityId`, `effectKey`, `payloadKind`, `originSourceKind`, `automationWorkItemId`) that operators actually need when pivoting into one remote execution family. Those standalone followup/result reads now also carry the coordinator's origin deadline and late-result policy, and all three remote list surfaces now accept the full persisted current-boundary scope they already store: game-instance ids, region ids, relevant region epochs, script-patch/plugin-version provenance, admitted routing-bundle fields (`playableStateScope`, `worldSlug`, `realmSlug`, `pointerVersion`), and the current live payload/result classifier fields (`payloadKind`, `originSourceKind`, `resultErrorCode`, `resultCommandId`) instead of forcing operators to recover that truth client-side after a broader scan. Followup/result lists now also support direct identity filtering over `automationWorkItemId`, and followup lists can now pivot by target-leg identity and terminal followup truth (`targetEntityId`, `effectKey`, `failureCode`, `requiresSoloTick`) instead of stopping at broader scope/provenance filters. The new control-plane query indexes now preserve that same contract at the storage boundary too, so epoch-aware, routing-aware, and identity-aware remote followup/result/coordinator reads stay aligned with the stronger operator filter surface instead of regressing into broader scans. That internal schedule surface now also carries origin-source metadata, `payloadKind`, requested command text, and `requiresSoloTick` as first-class request fields instead of forcing callers to smuggle remote execution authority through payload JSON. `payloadJson` is now optional enrichment on that surface, but if it is provided it must still parse and agree with the explicit payload contract. Schedule-time remote admission is fail-closed for the current live payload families: invalid JSON, missing `kind`, unsupported payload kinds, command-less enqueue payloads, and script-event trigger payloads that omit required event identity, snapshot-token, or event-body fields are all rejected before durable coordinator/follow-up rows are written. The target-side result contract now follows the same pattern: explicit `resultCommandId`, `resultErrorCode`, and `resultMessage` are first-class authority, while optional `resultPayloadJson` only survives as enrichment and must agree if present. `ListRemoteFollowupResults` now carries the target command's execution/gameplay status too when the result payload references a concrete command id, so result reads no longer stop at payload parsing. The first shipped remote payload/result summaries now also prefer durable row authority: follow-up rows persist `payloadKind`, requested command text, `requiresSoloTick`, and remote origin-source metadata, result rows persist `resultCommandId`, `resultErrorCode`, `resultMessage`, and full origin/target game-instance scope, and target-side execution plus control-plane/gameplay status reads only fall back to reparsing JSON for older rows that predate those first-class columns. The sealed `REMOTE_FOLLOWUP_QUEUE` manifest now carries that same persisted origin-source tuple beside routing/provenance/payload summaries, so replay and operator reads no longer need payload JSON to reconstruct target-side automation admission origin. The new remote-runtime service layer also makes that substrate executable on the origin side for schedule, result-recording, and timeout-reconciliation paths, and target-side remote execution now supports automation-command enqueue, gameplay-command enqueue, and target-region script-event trigger payloads using persisted remote-row provenance rather than payload-only identity. The internal `EnqueueAutomationCommandIfAbsent` handoff surface now also allows immediate event-driven automation to omit `dueTickId`; scheduler/timer producers still carry it when a real due point exists, and the handoff preserves scripting-side origin-source metadata so later ledger and manifest reads can distinguish gameplay-triggered work from scheduler-triggered work. New automation handoffs are fenced by Game Session's current runtime ownership row and reject missing ownership, paused ownership, or stale `regionEpoch` before Redis tick-queue mutation. Automation handoff carries script-patch and plugin-version provenance so Game Session can purge queued commands by either rollback scope.

The existing `PauseTicks` / `ResumeTicks` RPCs on `GameSessionService` remain the minimal, backup-oriented APIs; the control-plane service is the normative surface for per-tenant/game/region operations.
