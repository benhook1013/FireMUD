# Development Certificates

This directory contains the helper scripts for local development TLS material.

Generated certificate outputs in this directory are ignored by Git and should not be committed.

## Script Map

- `dev-tools/certs/generate-dev-certs.sh` writes into `dev-tools/certs/` when no explicit target or `CERT_DIR` is provided. A complete retained bundle is validated for certificate/key/CA agreement and reused without changing bytes or permissions. Incomplete or invalid retained material fails closed; preserve it and select a fresh dedicated directory for replacement material. The implicit script-local default resolves its directory physically. Explicit caller paths and all managed certificate entries and their directory ancestors are checked before writes; symlinks, nonregular files, and hardlinked files are refused. Generation changes only its named outputs, leaving unrelated entries untouched.
- `dev-tools/certs/generate-dev-certs.sh --workload` signs a local development or test-only gRPC workload leaf for any of the eleven Java application workload identities, with the exact SPIFFE URI and service DNS SANs. This mode requires fresh output paths; callers stage replacement leaves before installing them. Ordinary local development uses the dedicated per-workload helper described below; run-owned smoke uses the qualified fixture described below. Hosted preview and dev-demo do not use this signing mode; their standalone workload leaves come from the protected `firemud-ca-issuer` through the scoped certificate writer.
- Standalone hosted runs retain the legacy shared bundle for other gRPC workloads and consume eight cert-manager-issued runtime-facing `firemud-grpc-<workload>` leaf Secrets: five publication workloads, Account, Game Session, and Social Groups. They do not create or retain a CA private key in a runtime namespace; a missing or invalid issuer-projected leaf fails closed.
- `dev-tools/certs/ensure-local-compose-mtls.sh` owns ordinary local development certificates for all eleven application workloads. See [ordinary local Compose setup and retained-certificate recovery](../../docker/README.md#local-compose-mtls-certificate-recovery); this authority remains separate from run-owned smoke fixtures.
- `dev-tools/certs/ensure-dev-certs.sh` guarantees the canonical local smoke entrypoints have the required cert/key set in place before Compose boots.
- `dev-tools/certs/ensure-dev-certs.sh --compose-mtls <run-owned-fixture-root>` creates the dedicated canonical smoke fixture beneath the active run-owned Compose state directory. The authority and CA private key remain in a host-only mode-0700 directory; each of the eleven Java application containers receives a read-only `/app/certs` mount containing only that service's leaf key, certificate, and public CA certificate. Account, Game Session, Entity Management, World Management, and Game Design receive distinct `dev`-namespace SPIFFE leaves; World Management's leaf supports its authenticated Game Session owner-read path for the initial admission bind. This is local Compose wiring only; hosted deployments continue to use their separate certificate issuer. The remaining services use the shared local development leaf. The fixture is intentionally retained while its Compose project may be restarted and should be removed only after that exact project is torn down.
- The three canonical runtime-proof entrypoints layer `docker/docker-compose.grpc-mtls.override.yml` last. Ordinary local development layers `docker/docker-compose.local-mtls.override.yml` over its base local settings; see the [Docker guide](../../docker/README.md). Hosted certificate provisioning is separate: hosted runtime namespaces receive cert-manager-issued standalone workload leaves and never mount the local CA private key.
- `dev-tools/certs/clean-dev-certs.sh` removes only recognized generated regular files without hardlinks from `dev-tools/certs/` unless a target directory or `CERT_DIR` override is provided. It refuses a symlinked directory or ancestor, never recurses, and reports preserved entries, including foreign files, directories, and symlinks. Symlink targets are untouched.
