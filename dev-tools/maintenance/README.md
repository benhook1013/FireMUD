# Maintenance Tools

Detail for maintenance workflows and helpers in this folder. The agent-facing rules stay in [validation and runtime proof](../../design/developer-workflows/validation-and-runtime-proof.md).

## Local Renovate Extraction

When changing Renovate configuration or dependency declaration forms, optionally use the official CLI's [local platform](https://docs.renovatebot.com/modules/platform/local/) and [extract-only dry run](https://docs.renovatebot.com/self-hosted-configuration/#dryrun) alongside the repository authority checks (`bash dev-tools/tests/workflow-version-authority-contract.sh`). This temporary tool does not require a global installation, a service, or a new wrapper, and is not a required step for every PR. From the repository root, select the exact Renovate version being verified and run:

```bash
LOG_LEVEL=debug npm exec --yes \
  --package="renovate@${FIREMUD_RENOVATE_VERSION:?select the Renovate version being verified}" \
  -- renovate --platform=local --dry-run=extract --force-cli=true
```

Use a Node runtime supported by both the selected Renovate version and its optional RE2 dependency. RE2 must actually load for the repository's regex patterns; invoking npm exec or npx alone does not prove native optional dependencies installed successfully. If initialization skips because of the environment, report that limitation rather than treating exit zero as success.

Confirm the logs show actual repository initialization and dependency extraction with the expected package names, tags, and digests and no configuration skip. Extract-only proof does not check available-release compatibility or replace required CI and container execution proof.

## Daemon JDK Artifact Maintenance

[Refresh Gradle Daemon JDK](../../.github/workflows/refresh-gradle-daemon-jvm.yml) runs weekly from the default branch and can be dispatched from `develop`. Its [bounded helper](./refresh-gradle-daemon-jvm.py) enters the existing `run-locked-gradle.sh --resource-session` before snapshotting outside edits, reading daemon criteria, or querying release metadata; nested Gradle generation reuses the verified resource lease. In `--check-only` mode, the helper derives one exact approved release from the five existing daemon criteria URLs, fetches official Java 25 GA metadata for that release on each supported platform, and validates the same full release/build, platform, vendor, and immutable URL constraints before generation. Exact-release queries request Adoptium's `DEFAULT`/`DESC` ordering in deterministic zero-based pages of at most 20 records; they stop at the first exact match, treat HTTP 404 as pagination exhaustion, and fail after ten pages or exhaustion. Each response remains limited to 8 MiB. An explicit refresh without `--check-only` uses official latest-per-platform metadata and fails closed when those latest artifacts do not share one release/build; it never selects an older common release automatically. Both modes require exactly Linux and macOS on x64 and AArch64 plus Windows on x64, and pass all five validated URLs to Gradle's native `UpdateDaemonJvm.toolchainDownloadUrls`; Gradle generates the criteria file, and the helper verifies exact Java 25/Adoptium criteria and a one-file change boundary. The outside-artifact snapshot retains tracked changes and records contents/modes for Git-enumerated untracked regular files plus targets for Git-enumerated symlinks; it refuses an unsupported special file if Git enumerates one. Check-only validates the committed Java 25 pin during a staggered upstream rollout, while an explicit refresh waits for all supported platform latests to converge. Unsupported FreeBSD and generic Unix aliases, missing-platform URLs, signed redirect URLs, and mixed-release substitutions are not synthesized or accepted. This maintenance path uses immutable official release artifacts rather than resolver-generated download aliases; the configured resolver remains available for other Gradle toolchain uses. Renovate maintains the Gradle wrapper and resolver plugin; it does not maintain the generated daemon artifact IDs. Changing `toolchainVersion` alone does not refresh JDK patch artifacts.

**Platform limit:** Windows ARM (AArch64) automatic daemon provisioning is explicitly excluded because official Temurin 25 metadata lacks a matching artifact. The helper neither synthesizes that URL nor accepts it in generated criteria; adding the platform requires a matching official artifact and explicit qualification. This is an automatic-provisioning limitation, not a blanket claim that Java 25 cannot run on Windows ARM with an independently supplied compatible JDK. The [daemon criteria](../../gradle/gradle-daemon-jvm.properties) pin the five supported immutable artifacts; mocked metadata tests do not establish publisher availability or execution on all five platforms. Native generation and check-only validate the pin, while actual compilation/tests and fresh-image runtime proof establish their separately named execution boundaries.

**Setup required:** install a dedicated GitHub App on this repository with only repository Contents and Pull requests write access, store its private key first in repository secret `DEPENDENCY_MAINTENANCE_APP_PRIVATE_KEY`, then set repository variable `DEPENDENCY_MAINTENANCE_APP_CLIENT_ID` to its client ID. Setting the client ID deliberately enables scheduled publication; without it the scheduled publishing job skips. A manual dispatch from `develop` still runs the setup check and fails visibly if either field is missing, and enabled scheduled publication also fails on incomplete configuration. Keep private-key material in GitHub Secrets, never in chat or source. Its ordinary `GITHUB_TOKEN` has Contents and Pull requests read access; a short-lived, current-repository-only App token is minted only after successful generation for publication. The App-backed PR events trigger the existing exact-head Validation, Security, License, CodeQL, and Smoke gates. A `GITHUB_TOKEN` publisher would suppress those ordinary events; manual CI activation is not this workflow's maintenance contract. Credential provisioning and live hosted execution remain separate setup/proof steps. A separate path-filtered pull-request job in the same workflow runs the real generator and criteria guard with read-only permissions and no App credentials or publication steps; fork PRs cannot select the publishing job. `--check-only` generates and validates the candidate artifact without remote writes and preserves existing edits outside that artifact; publication requires a clean checkout.

The workflow proposes only `gradle/gradle-daemon-jvm.properties` to `develop` on `codex/gradle-daemon-jdk-refresh`, never merges, and skips publication when a PR on that branch is open either before generation or at the final check immediately before publication. The final API read and Git push are not atomic: a PR reopened after that read can still receive the update. Cancel an in-flight refresh before reopening the maintenance PR to preserve its review head. Merge or explicitly dispose of that pending proposal before another weekly refresh can advance. Unchanged generator output creates no PR. Generator, credential, or publication failures fail the run; inspect the failed step and rerun after correcting the cause. Cancel the run in Actions to stop an unwanted refresh; cancellation does not retract an already-created PR. Human review and merge remain required.
