# Validation Tools

Internals of the canonical local Gradle wrapper, `run-locked-gradle.sh`. How to use it and what to report are in [local Gradle execution](../../design/developer-workflows/validation-and-runtime-proof.md#local-gradle-execution).

## Local Gradle Wrapper Internals

The wrapper also accepts `--resource-session <command> [args...]` for a complete local runtime proof or proof chain. Runtime wrappers enter this mode automatically and retain the resource slot across jar/image builds, startup, transport probes, and authenticated teardown. Intermediate continuation uses explicit `--keep-running` within that same session; see the [Docker proof lifecycle](../../docker/README.md#canonical-commands). Nested Gradle retains its output guards and local daemon/cancellation policy while reusing only a verified inherited resource lease. Admission checks the live owning process identity, canonical lock inode, inherited open-file-description exclusive lock, and private owner metadata; a boolean or a fabricated descriptor cannot authorize bypass. Metadata encodes arbitrary command and working-directory text as JSON strings on single lines, while retaining well-formed prior owner records and exact runtime project identities. Nested Gradle keeps a distinct cancellation marker for its own processes; a separately inherited root-session process marker keeps those workers visible to the outer owner even when they close their resource descriptors or start separate process sessions. Outer cancellation therefore drains them before releasing admission, while nested cancellation does not target parent or sibling work. Nested completion closes its descriptor without unlocking the parent lease, and an inherited lease forces local policy even if a child sets `CI=true`. Before stack work, a runtime session durably records its exact Compose project IDs in the existing user-wide resource metadata. Completion or abrupt owner death retains those identities until the next local admission checks their exact project labels under the resource lock. Each read-only Docker check has a five-second timeout; running, restarting, paused, unknown, or uninspectable containers block admission with a scoped teardown/retry reason. Known stopped or absent containers release the resource hold even if volumes/networks remain: this does not release the smoke ownership marker or turn unsuccessful cleanup into successful proof. Concurrent contenders cannot replace an unresolved identity. Original-capability teardown or verified scoped recovery followed by an ordinary retry resolves the hold; there is no blind override, secret recovery path, or permanent lock-owning process.

The wrapper acquires a user-wide exclusive resource lock across worktrees before its existing worktree output locks. Service-scoped tasks retain a service lock and shared repository guard; unscoped or mixed tasks retain the exclusive repository guard. Output-lock metadata remains under `.gradle/firemud-validation-locks/`. The resource lock defaults to `${XDG_CACHE_HOME:-$HOME/.cache}/firemud/gradle-validation`, using the home cache when `XDG_CACHE_HOME` is unset or empty, independently of `GRADLE_USER_HOME`; separate Gradle caches do not create extra local build slots. Serialization limits concurrent admitted builds, not the memory usage of one build.

The shared local Gradle daemon has a 3 GiB maximum heap while heavy local work is serialized. This is a daemon heap limit, not a total-process memory guarantee: worker, test, and code-generation JVMs can use additional memory. The hosted module runner retains its explicit 2500m heap setting.

Local runs force `--no-daemon` and reject explicit `--daemon`. Gradle may still start a single-use daemon to satisfy JVM settings; reusable dependency and task caches remain available, with a JVM startup cost on each run. The repository's ten-minute reusable-daemon idle expiry applies to direct Gradle launches. Under `CI=true`, the wrapper bypasses the local resource guard, retains the existing daemon policy and output locks, and keeps bounded lock acquisition. CI runs have no finite local run budget and do not parse `FIREMUD_LOCK_GRADLE_RUN_SECONDS` or `FIREMUD_LOCK_GRADLE_CANCEL_SECONDS`; this local policy does not serialize hosted jobs.

A supervisor retains the locks during execution and cancellation. For runtime sessions, it sends TERM once so the proof shell can finish its authenticated cleanup; the existing cancellation grace still bounds escalation to KILL. SIGKILL, WSL shutdown, unresponsive Docker, and cleanup exceeding that grace do not establish successful stack disposal. These limitations must remain explicit in proof reporting. A random per-run environment marker admits owned processes after their UID/start identity and marker are validated against a still-live Linux pidfd. Retained pidfds bind signals to the original process even if its PID is later reused or an exec changes its environment. The wrapper itself is tracked by exact PID/start identity. Wrapper termination or disappearance triggers cancellation of the owned client, daemon, and workers; the run budget bounds the start of cancellation when the app disappears but the wrapper remains alive. App death is not immediate cancellation in that case. Diagnostics use a bounded asynchronous writer, so closed, failing, or full unread output pipes cannot block cancellation or bypass cleanup. Cancellation does not stop unrelated Gradle daemons or builds.

If an owned process survives KILL, for example because of uninterruptible kernel I/O, the supervisor keeps the locks while contenders fail immediately or exhaust their acquisition budget. The run budget bounds cancellation start, not guaranteed kernel process termination. Native or escaped processes outside the ownership evidence are not an established cleanup guarantee; focused proof must state the actual process boundary tested before claiming complete orphan cleanup.
