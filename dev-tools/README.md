# Dev Tools

This directory contains repository-owned operator, CI, and local-development tooling.

Keep the root of `dev-tools/` small. Only canonical human-facing entrypoints and shared runtime helpers should live directly here. Category-specific helpers belong in a subfolder.

## Canonical root entrypoints

- `firemud-cli.sh` – simple local stack shortcuts built on top of Gradle tasks.
- `verify-fresh-bootstrap.sh` – canonical source-built Docker smoke proof from a clean state. It establishes a new claim when the expected project is empty, or reuses the exact matching claim/capability for the exact per-run ID/project binding defined in [Testing: player-flow smoke and reset boundaries](../design/architecture/system-architecture-testing.md#player-flow-smoke-and-reset-boundaries) before destructive teardown, and defaults to the read-only `LOGIN -> PLAY -> LOOK` baseline over both transports. Defaults to a per-service serial build path for local reliability; set `FIREMUD_SMOKE_SERIAL_BUILD=0` to use a normal compose build and default `COMPOSE_PARALLEL_LIMIT=4`. Set `FIREMUD_SMOKE_NO_CACHE_SERVICES="service-a service-b"` when a smoke proof must force a fresh compose rebuild for specific Docker Compose service ids without turning the whole stack into a cold no-cache build; use `gateway`, not the Gradle module name `spring-cloud-gateway`. When running from WSL, keep Docker on a native Linux CLI pointed at `unix:///var/run/docker.sock`; Windows `docker.exe` wrappers can look healthy but break the bind mounts this proof depends on.
- `verify-restart-state.sh` – canonical source-built Docker smoke proof with preserved local state. It requires/reuses an already-existing matching claim/capability for the exact per-run ID/project binding defined in [Testing: player-flow smoke and reset boundaries](../design/architecture/system-architecture-testing.md#player-flow-smoke-and-reset-boundaries) before running.
- `verify-smoke-images.sh` – canonical GHCR/image-tag Docker smoke proof. Invoke it as `SMOKE_IMAGE_TAG=<published-full-commit-SHA> dev-tools/verify-smoke-images.sh`; see the [Docker guide](../docker/README.md#canonical-commands) for tag semantics and local-only mode. It establishes a new claim when the expected project is empty, or reuses the exact matching claim/capability for the exact per-run ID/project binding defined in [Testing: player-flow smoke and reset boundaries](../design/architecture/system-architecture-testing.md#player-flow-smoke-and-reset-boundaries) before running; it defaults to the baseline and rejects shared-state mutation parity.
- `build-compose-service-jars.sh` – rebuilds the service boot jars consumed by the source-built Compose stack.
- `ensure-local-compose-env.sh` – creates or completes the local root `.env` from `.env.sample` and synchronizes `docker/.env` for Compose-based smoke commands.
- `build-local-smoke-images.sh` – builds the pinned local base and service images for a 40-character commit tag after rebuilding the service boot jars.
- `verify-compose-health.sh` – shared health gate used by the smoke entrypoints.
- `validation/run-locked-gradle.sh` – canonical local Gradle wrapper that serializes heavy builds across worktrees, protects shared output trees, and bounds lock acquisition and cancellation start. Use it for local proof and service boot-jar builds; [Local Gradle execution](../design/developer-workflows/validation-and-runtime-proof.md#local-gradle-execution) owns configuration and cancellation limits. For example: `bash dev-tools/validation/run-locked-gradle.sh :account-service:test`.
- `validation/inspect-test-results.sh` – read-only JUnit XML helper for diagnosing quiet post-suite Gradle tails without guessing at process state. For example: `bash dev-tools/validation/inspect-test-results.sh account-service`. Default mode is diagnostic only and does not prove that Gradle completed cleanly. CI may use `--strict` with repeated `--require-suite <fully-qualified-suite>` and `--require-case <fully-qualified-suite#test-case>` arguments to fail closed on missing, duplicate, malformed, empty, skipped, or failing JUnit proof; strict output contains only counts, requested names, and outcomes.
- `pr-review` – the sole review controller. Use `dev-tools/pr-review stack set <pr>...` and `stack show` for the repository review stack, `status [--pr <pr>]` for fail-closed live state, `run hosted|cli [--expect-pr <pr>] [--force [--reason <context>]]` for a complete checkpoint, `evidence [<pr>]` for anchored evidence, and `decide ...` for explicit judgments. `--force` records acknowledgment of a known candidate-quality warning with the attempt; it does not bypass PR/candidate identity or admission-time rechecks, provider ceilings or quota, active-request exclusion, channel caps, stopped/completed channels, or accepted-finding obligations. A completed result counts normally for its PR and channel. The complete review, status, checkpoint, and disposition policy is owned by [PR lifecycle: Review and Status](../design/developer-workflows/pr-lifecycle.md#review-and-status). Until an explicitly validated JSON-to-SQLite cutover, controller decisions remain in the locked private common-directory JSON state file; do not assume cutover has occurred. Live shared cutover waits until the controller change is merged and its version-matched tooling is installed. Select the trusted promoted `dev-tools/pr-review` entrypoint and inspect `dev-tools/pr-review --version` before migration or shared writes. Follow [PR-review SQLite operations](pr_review/README.md) for the atomic JSON migration and old-writer fence, separate records bootstrap, provider-checkpoint imports, curated manual/subagent batch imports, and read-only history/route queries. Existing controller-era routes remain available through `routes` and `status`; full provider captures remain separate audit evidence outside SQLite. Provider imports and independent records do not affect CodeRabbit taper. Live PR, CI, checkpoint, and review evidence is derived when requested. For hands-on acceptance, pass the paired global options `--acceptance-fixture <json>` and `--state-path <isolated-file>`; these use synthetic fixture adapters in a dedicated private directory and never contact GitHub or consume review quota. The implementation and focused contracts live in `pr_review/` and `tests/pr-review-controller-contract.sh`.

  An acceptance fixture is a JSON object containing `repository`, `default_base_ref`, `default_base_tip`, `branch_heads`, `pull_requests`, `ancestors`, `merge_bases`, `test_merge_trees`, `patch_ids`, and optional `ordered_prs` and `evidence`. `test_merge_trees` maps each exact `base...head` pair to its synthetic full tree SHA; every direct default-base PR needs a matching fact. Pull requests provide exact `base_ref`, `base_tip`, `head`, and `head_repository` identities; `head_repository` must explicitly match the fixture's `repository`. They may also provide `head_ref`, state, mergeability, and merge flags; Git relationships, merge trees, and patch identities are explicit so missing or stale facts fail closed. Create a dedicated private directory with `review_acceptance_dir=$(mktemp -d)`, place the fixture there, then run `dev-tools/pr-review --acceptance-fixture "$review_acceptance_dir/fixture.json" --state-path "$review_acceptance_dir/state.json" status --json`. The state directory must already exist, be owned by the caller, and have mode `0700`; the canonical state directory is forbidden.

  By default, `dev-tools/pr-review status [--json]` batches current identity/state for the configured stack, deeply checks the first four unmerged PRs and active Hosted/CLI targets, and leaves later rows informational as `unknown` or `stale`; an identity-only row never claims review completion. In JSON, each Hosted/CLI `review_activity.recent` item includes a UTC `completed_at` checkpoint time, or `null` when no valid time is available. Use `status --full-scan [--json]` for the explicit full-stack evidence scan. `status --pr <number>` independently refreshes that PR and deeply verifies its configured ancestors and CI without deep-scanning unrelated later PRs.
- `validation/validate-jacoco-combined-report.py` – checks that the exact JaCoCo XML selected for Codecov contains covered representative production classes from the unit and PostgreSQL integration paths. CI applies it to `common-saga` after the combined report is generated and before upload; its focused proof is [the validator test](validation/test_validate_jacoco_combined_report.py).
- `validation/report-worktree-pr-topology.sh` – read-only local worktree, branch, and open-PR inventory. Use `bash dev-tools/validation/report-worktree-pr-topology.sh --json` for a machine-readable inventory, or `bash dev-tools/validation/report-worktree-pr-topology.sh --pr N --include-renovate --json` for a bounded exact branch/SHA selected-stack report that includes Renovate heads. Renovate heads are excluded from selected stacks unless `--include-renovate` is supplied; default selected-stack output exposes exact linked exclusions in `omitted_renovate` (and a corresponding text note) without including those heads. Ambiguous branch or PR identities fail closed. Its focused proof is [worktree-topology-contract.sh](tests/worktree-topology-contract.sh).
- `evidence_digest.py` – shared canonical RFC 8785-subset evidence digest helper imported by deployment and validation gates.
- `wait-for-it.sh` – shared Docker image/runtime helper.

The `pr-review`, `report-worktree-pr-topology.sh`, and `maintenance/cloc-report.py pr` entrypoints require GitHub CLI `gh` >= 2.63.0 because they request the `baseRefOid` field. The repository workflow pin is sourced from `config/workflow-tool-versions.env` as `GH_VERSION`.

## FireController

[`fire-controller`](fire_controller/README.md) is the reusable project-configured entrance for independent SQLite jobs and delegated review commands. Project-specific WSL wrappers select reviewed checkouts and explicit contexts; the existing `pr-review` entrance remains during rollout. The separately maintained private status site reads FireController's public job and workstream projections and serves private detail routes locally. Its source and privacy proof are owned by [the native site handoff](fire_controller/integration/README.md); private links and details stay out of static public artifacts.

## Folder map

- `backups/` – local and operator backup helpers; see `backups/README.md` for the script map.
- `certs/` – tracked certificate helper scripts plus ignored generated local TLS material.
- `deploy/` – deployment preflight and overlay validation; see `deploy/README.md` for the script map.
- `hosted/` – hosted Kubernetes environment tooling; see `hosted/README.md` for the lane split.
- `hosted/account-bootstrap/` – disposable fixture ownership and review-only factory inventory tooling; see the [manual qualification workflow](../.github/workflows/game-session-factory-qualification.yml) and [focused contract](tests/game-session-factory-qualification-contract.sh).
- `docs/` – documentation generation and validation helpers; see `docs/README.md` for the script map.
- `kreya/` – Kreya gRPC client assets.
- `load-testing/` – Gatling load-testing module.
- `maintenance/` – maintenance and analysis utilities, including `maintenance/cloc-report.py` for repository summaries and PR impact snippets. Report generation is read-only by default; `pr ... --update-pr` performs the guarded marked PR-body update defined by the [PR lifecycle](../design/developer-workflows/pr-lifecycle.md). Generated PR LOC blocks carry exact base, merge-base, and head metadata for freshness checks. Use `python3 dev-tools/maintenance/cloc-report.py --help` for invocation details; its focused proof is [cloc-report-contract.sh](tests/cloc-report-contract.sh).
- `maintenance/update-workflow-tool.py` – updates repository-frozen checksum tuples for GitHub CLI, Buf, Kubeconform, Trivy, and Lychee. Kubectl, Helm, and the Velero CLI instead keep one exact version in the repository and fetch the publisher's checksum for that exact version during installation; `maintenance/verify-publisher-checksum.sh` validates the sidecar format, exact asset filename where the publisher supplies one, and downloaded bytes before installation. This detects corruption and publisher-side mismatches but deliberately trusts the publisher's current HTTPS artifact and checksum together rather than retaining a separately reviewed hash. The Kubernetes 1.34 hosted cluster constrains Renovate's kubectl proposals to `<1.36.0`; advance that cap only with the corresponding cluster-version upgrade. Renovate groups the Velero CLI version with the digest-pinned verifier Dockerfile image, digest-pinned Terraform server image, and Terraform Helm chart. The independently promoted backup-verifier CronJob digest remains outside that group.

- `observability/` – observability contract and evidence validators.
- `release/` – release/notice generation utilities.
- `restores/` – restore, state-reset, and external-credential validation helpers; see `restores/README.md` for the script map.
- `smoke/` – shared smoke defaults and the run-owned Compose claim/capability helper.
- `seed/` – local and test data seeding helpers.
- `tests/` – contract tests for repo-owned tooling.
- `validation/` – repo policy and static validation scripts used by Gradle and CI.

The focused [Account jOOQ projection contract](tests/account-jooq-projection-contract.sh) executes the registered projection task with original and forward-versioned inventory migration fixtures. It checks byte-preserving projection and rejects missing or ambiguous semantic migration identities before touching existing output; it is not PostgreSQL migration proof.

The documentation lock is sourced from the unpinned direct roots in `config/docs/requirements.in` and generated into `config/docs/requirements.txt` with the repository Python version and `pip-compile --allow-unsafe --generate-hashes --index-url=https://pypi.org/simple --output-file=config/docs/requirements.txt config/docs/requirements.in`. The existing lock seeds compilation and preserves satisfying package pins unless you explicitly request an upgrade. When the installed pip-tools version mis-serializes its default index options into an unsupported header, set `CUSTOM_COMPILE_COMMAND` to that exact command so the generated header remains parseable. Keep the source roots and lock hashes in sync; do not edit lock hashes manually.

## Placement guidance

- Put a tool in `validation/` when its main job is enforcing a repo policy or static contract in CI/Gradle.
- Put a tool in `deploy/`, `hosted/shared/`, `hosted/preview/`, `hosted/dev-demo/`, `backups/`, or `restores/` when it owns a real operational lane.
- Keep root-level scripts only when they are canonical entrypoints contributors are expected to run directly.
- Avoid placing personal or AI-host-specific maintenance scripts at the root. If they remain in the repo at all, keep them under `maintenance/`.
