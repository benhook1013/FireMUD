# Microservice Consequential Decision Inventory

Status: Complete and independently coverage/fidelity-audited. This artifact is non-normative.

This inventory is the service-documentation companion to [decision-inventory-cross-cutting.md](./decision-inventory-cross-cutting.md). It records consequential product and architecture choices found in the microservice documentation scan. It does not create, accept, supersede, or amend canonical design.

The completed scan considered all 76 Markdown paths under `design/architecture/microservices/`: 73 service-directory documents and the three root documents. The exact per-service path set is recorded in [the coverage ledger](#exact-microservice-path-set-coverage). No path was omitted. Routine configuration, deployment values, implementation mechanics, and ordinary endpoint details are not decision rows unless they establish authority, lifecycle, externally observable behavior, security or durability semantics, creator/player/operator policy, or an expensive-to-reverse constraint.

The current ledger contains 40 cross-cutting evidence rows and 23 service-source rows, for 63 service/source rows total. Of the 23 service-source rows, 21 are active service-only canonical decisions, `MS-GR-EQUIPMENT-BODY-LAYOUT` is one formal reviewed decision now superseded by `EQUIP-01`, and `MS-AA-TOKEN-REVOCATION` is one excluded historical service-scan alias retained only for traceability/navigation. The 40 evidence rows intentionally reference existing keys and do not add canonical decisions. Across the source-scoped ledgers, the established universe is 182 distinct decision keys plus that one historical alias, or 183 key/navigation rows.

The taxonomy IDs below are the exact child IDs from [capability-taxonomy.md](../../product/capability-taxonomy.md). A parent capability is not used as a scope. Existing keys in the cross-cutting ledger are referenced rather than reissued; their complete question/current choice, status, importance/reversibility, strongest alternative, ADR recommendation, and consultation gap remain in that ledger. This file adds the stronger service-local evidence, exact service headings, and any distinct service decision not already represented by an existing key.

## Status And Review Notation

| Status | Meaning |
| --- | --- |
| `accepted-explicit` | An accepted ADR or explicit canonical service prose establishes the choice; this does not prove adequate human consultation. |
| `accepted-implicit` | Canonical service prose consistently implies the choice, but an accepted rationale or dedicated ADR was not found. |
| `proposed/deferred` | The target choice is stated but incomplete, gated, or deferred. |
| `conflicting` | Accepted ADRs or canonical sources imply incompatible current or target choices. |
| `needs-human-review` | Product, security, operational, or architectural consequences require explicit discussion. |
| `superseded` | The row is retained for traceability, but its decision is replaced by the referenced current decision set and must not be treated as an active choice. |
| `navigation-only` | A historical service-scan row is retained for navigation and does not add a distinct decision. |

`I/R` means importance/reversibility. `H/hard`, `H/med`, `M/med`, `M/easy`, and `C/L` are the same shorthand used by the cross-cutting ledger. `ADR: yes` means a dedicated or superseding ADR is warranted; `ADR: no` means the existing canonical contract is sufficient unless the boundary changes. “Consultation gap” is a suspicion based on the reviewed repository, not a claim that consultation did not occur elsewhere.
