# Player Access and Session

## Target-State Authority

This is a non-normative implementation tracker for player access and session. Canonical target-state authentication, admission, session, and reconnection contracts remain authoritative in [design/architecture](../../architecture/README.md) and the linked design sources below; this tracker owns current implementation status, proof evidence, gaps, and handoffs, and does not redefine those contracts.

## Current Status

Implemented seams currently span Account, Common Security, TCP Proxy, Gateway, Game Session, and the gameplay runtime services, including account-first tenantless bootstrap, global-only registration, explicit public-production JOIN, durable Account audit outbox and Logging receipt handling, tenant-bound discovery/admission, shared Telnet/WebSocket text handling, and bounded Gateway-bridge continuity. Current `PLAY` and connect-token issuance remain partial; Account-owned membership and realm-grant authorities remain separately modeled and read. Account now has a bounded readback-only worker for abandoned JOIN `PENDING` intents, but PostgreSQL lost-acknowledgement/concurrency and direct text-client end-to-end proof are not claimed. Expiry and absent evidence do not create terminal outcomes. The membership-authority-generation reread, namespace-aware binding enforcement, resume-window enforcement, exactly-one-prompt proof, and first-party post-logout replay suppression remain incomplete. Generic paths distinguish fresh entry, resume, takeover, and logout; current per-instance binding remains drift against the namespace-aware takeover contract. The current TCP Proxy keeps bounded ordered input in connection-local memory while an edge bridge is rebindable; that buffer is delivered only on the same retained connection and is never durable replay of input, bytes, or frames. Account lifecycle, Stripe hosting-billing follow-through, entitlement enforcement, safety restriction/appeal workflows, generic prompt login, and full control-plane revocation/logout remain partial. Focused automated proofs cover principal implemented paths; manual end-to-end QA and broader continuity/validation follow-ups remain. Canonical target behavior is linked below rather than restated in this tracker.

Official-hosted creator-content acceptance remains an unimplemented target gap; see [ADR 0180](../../architecture/decisions/adr-0180-account-owned-hosted-terms-acceptance-gate.md) and [ADR 0181](../../architecture/decisions/adr-0181-changed-hosted-terms-decline-and-existing-content-continuity.md). It is outside player-admission and session authority. Future managed creator commerce remains outside player access and session authority; its canonical boundary is [ADR 0179](../../architecture/decisions/adr-0179-firemud-managed-creator-commerce-boundary.md); no marketplace or purchase-entitlement implementation is present.

Account runtime admission reads remain a capability/proof blocker. `GetTenantMembershipForRuntime` and `GetTenantEntitlementsForRuntime` are no longer on the public bearer-bypass list, and these two methods plus `GetRealmAccessGrantForRuntime` now deny even the exact Game Session peer with `FAILED_PRECONDITION` before Account data reads because the current requests lack a verified player/tenant or lifecycle target. Missing or wrong peers are denied separately. Unit 1B must implement the typed caller/target contract and consumer propagation before these reads can be enabled; the target boundary is canonical in [Account Runtime and Data](../../architecture/microservices/account-service/runtime-and-data.md) and the [authorization route matrix](../../architecture/system-architecture-authz-route-matrix.md).

Account's credential-granting gameplay gRPC methods enforce the exact Game Session mTLS peer before authentication or email-code work, with local negative proof. Legacy profile GET/PUT now require the exact Social Groups peer and matching non-internal caller-account subject; presence-policy batch reads require the exact Social Groups peer and remain scoped to tenant profiles. Direct account-ID export, external-link, and verification gRPC methods deny before reads or mutation because no authorized internal caller is configured. These guards do not make the broader target method/caller authority complete or restore the disabled runtime reads. Deferred virtual-currency `GetBalance`, `AddCurrency`, and `SpendCurrency` gRPC calls fail with `FAILED_PRECONDITION` before stored balance access or mutation; this does not implement a supported economy or marketplace.

PLAYER-01 ownership and the target `CHARS`/`PLAY` actor-entry rules are canonical in [ADR 0140](../../architecture/decisions/adr-0140-realm-authored-controllable-actor-entry.md) and the [Entity Management API/runtime](../../architecture/microservices/entity-management-service/api-contracts.md), not this tracker. The Unit 1B child removes `PLAY`'s synthetic account/name/hash fallback and requires a persisted account-roster actor after admission checks, with focused foreign-owner, malformed-row, absent/ambiguous roster, and no-mutation negatives. That Entity list is not yet namespace/policy-qualified, and Account's runtime reads still deny before data access; `CHARS` now returns unavailable before Entity access. These are safety corrections, not a working complete actor-entry path. Typed Account caller/target authority, stable namespace and policy snapshot, descriptor/template resolution, zero/one/many entry behavior, and fork-local copy proof remain ordered pre-v1 work and do not upgrade AA-2.1 status.

Smoke identity consequence: the current demo-credential `LOGIN -> PLAY -> LOOK` path provides read-only baseline evidence only. Namespace-aware shared-versus-isolated playable-state persistence exists for current state families, but the Account-owned restricted-synthetic identity/isolation verifier and corresponding persistent/shared mutation proof remain unavailable; independent two-transport mutation parity remains unimplemented and unproved. Run-owned Compose mutation and teardown remain implemented and proved at their bounded scope. See the [canonical testing owner](../../architecture/system-architecture-testing.md#player-flow-smoke-and-reset-boundaries).

SEC-04 does not move player session ownership into Logging & Admin. Game Session `/sessions*` lifecycle routes remain current owner-local hooks with direct owner edge exposure denied; the target external operator path forwards from Logging & Admin to Game Session after Account issues the authorization reference and the receiving Game Session redeems that same reference. That target lifecycle family, and other operator mutation families gated by action schemas, shared `mutationDigest/v1` vectors, and the authorization-reference flow, are not currently available to players or operators.

## Consolidated Implementation Record

### Account, Tenant, and Realm Authority

Platform accounts are global identities. Tenant membership, tenant-scoped authorization, purchased/runtime entitlements, and non-public realm grants are distinct Account-owned authorities. The canonical tenant roles are `player`, `designer`, `tenantAdmin`, and `moderator`; global elevated roles such as `god`/platform admin are handled separately. Runtime consumers reuse Account and Common Security authority rather than deriving local equivalents.

`POST /auth/player-bootstrap` now authenticates the account before tenant selection, accepts the account's configured password or verified-email OTP mode, and records only account-scoped bootstrap session state. Current non-public discovery requires both an admitting Account membership and the separately stored Account-owned realm grant; `PLAY` evaluates the same authorities independently. Current connect-token issuance revalidates the selected tenant/realm, admission pointer, entitlement availability, membership, and runtime target but does not revalidate the applicable non-public grant. Target issuance grant validation and its focused proof remain gaps. Canonical admission behavior remains in [Authentication and authorization](../../architecture/system-architecture-authentication.md).

The obsolete implicit public-production membership-writer RPC/client/service seam has been removed. Connect-token issuance requires existing membership and never creates it. Explicit `JOIN`/`Join & Play` is implemented locally through the canonical `JoinPublicProductionMembership` Account writer, including a policy-bound v1 digest and membership/audit outbox transaction. Its bounded `PENDING` readback worker is local, but PostgreSQL recovery/concurrency and direct text-client proof remain open, so ADR 0025 is not complete. The membership-authority-generation reread at connect-token issuance remains unimplemented under [ADR 0025](../../architecture/decisions/adr-0025-explicit-open-enrollment-membership.md) and [Authentication and authorization](../../architecture/system-architecture-authentication.md).

Account export, deletion, recovery, password reset, username reminder, email verification, and profile operations are account-scoped. Public reset, reminder, and verification initiation resolve normalized email and return neutral success for unknown accounts without creating tokens or deliveries; public verification no longer accepts a numeric account selector. The broader trusted-source and distributed abuse controls remain absent. The target `ExportTenantData` contract is the separate tenant-admin route for a tenant-wide export of tenant-owned records and minimum stable subject references; it has no account subject selector and does not redefine full account export or deletion. The current Account Service route remains account-targeted implementation drift until that contract is implemented. Account deletion observes active subscription/billing preconditions without collapsing global account ownership into tenant ownership.

The Account-authorized request flow forwarded to Game Session remains target-state, not live or proved; affected operator paths remain gated. Current Game Session `/sessions*` lifecycle routes are owner-local/internal, with direct owner edge exposure denied. The canonical authorization-reference and durable owner-execution contracts are owned by [Authentication and authorization](../../architecture/system-architecture-authentication.md), [ADR 0047](../../architecture/decisions/adr-0047-logging-admin-as-external-operator-write-ingress.md), and [ADR 0048](../../architecture/decisions/adr-0048-durable-idempotent-operator-write-execution.md).

Live Account authentication hashes and verifies passwords with `argon2-jvm` Argon2 using `iterations=2`, `memory=65536 KiB`, and `parallelism=1`, with character-array handling and post-use wiping. Profile, external-account persistence/service scaffolds, recovery and verification, notification, payment, subscription, and virtual-currency surfaces have live foundations; the unsupported caller-asserted external-link REST route is removed and denied at the public edge. The broader account lifecycle state machine, server-verified provider linking, purchased-entitlement fulfillment, and complete billing/subscription follow-through remain partial or unavailable as tracked below.

### Text Protocol and Credential Policy

Telnet and generic WebSocket clients share one Game Session line-oriented parser/interpreter and gameplay queue. The parser trims input, accepts case-insensitive command names, handles empty or malformed lines, and maps unknown commands to `UNKNOWN`; Telnet performs no separate gameplay parsing. The current canonical flow is optional `WORLDS`, `LOGIN`, `PLAY`, and gameplay commands such as `LOOK` and `SAY`, with built-in `LOGOUT`. `LOGON` remains an accepted login spelling where the protocol documents it. The old typed `SESSION` attach flow is not part of the canonical initial-development protocol; future smart-client metadata, if revived, is transport metadata rather than a player command and is never authoritative.

TCP Proxy bootstrap metadata is proxy-owned hidden transport context, not a player-visible attach command. `TelnetSessionContext` and `TelnetServerHandler` validate the envelope before forwarding it, record connect events with session/tenant/client identity, reconnect with bounded backoff, preserve ordered buffered input, and close once `MAX_BUFFER_DEPTH` is exhausted while metering discarded input. Telnet logging redacts `LOGIN` arguments. `NotifyDisconnect` validates supplied instance ownership, meters duplicate and missing-context hints, and returns application-level `ErrorDetail` results; it currently makes no presence, region-exit, or instance-suspension mutation because the proxy hint lacks proved current binding/generation authority. Redis sequence dedupe still fails open on Redis errors and is reset-loss-vulnerable. A current-connection/generation compare and stale-hint/Redis-loss proof are required before target lifecycle effects can be enabled.

`LOGIN` is available in parameterized text form as `LOGIN <email> <secret>` and in challenge-initiation form as `LOGIN <email>`. The supplied secret is one opaque value forwarded to Account Service. Account Service interprets it from the account's enabled modes rather than guessing from its shape: live policy tries a valid active email code before password fallback when both are enabled, and rejects modes that do not permit email OTP. Successful Account authentication is required before Game Session creates authenticated session state or accepts gameplay commands. Failures map to canonical `ErrorDetail` and text `ERROR <CODE> <message>` responses, including invalid credentials, locked accounts, upstream unavailability, and unauthenticated gameplay.

The live account mode set is `PASSWORD` and `EMAIL_OTP`, exposed through global account-settings reads and replacements. New accounts default to `PASSWORD,EMAIL_OTP`; the requested set must be nonempty and supported, and enabling `EMAIL_OTP` requires a verified email. Email challenges are account-specific, short-lived, hashed, single-use, invalidated when replaced, resend-rate-limited, and bounded for failed attempts. Generic login challenge responses remain neutral for account-enumeration resistance. Signup-time mode selection, authenticator-app TOTP enrollment, and any dormant TOTP credential/field are not live. Secrets and OTP values are redacted from transport logs. Prompt/help text describes the optional-secret grammar without making text clients a separate authentication system.

Account Service publishes `/.well-known/jwks.json` from the configured mounted JWKS file with a classpath fallback. Common Security can hot-reload a configured JWT secret through `ReloadableJwtUtil` and `JwtSecretWatcher` when `FIREMUD_AUTH_JWT_SECRET_PATH` is present; this conditional mechanism is not deployment-wide proof of validator convergence or automated signing-key rotation.

The maintained integration path uses the real Account/Redis/GameInstance/downstream-service topology. Historical optimistic-success, dependency-light, proxy-only echo, GHCR placeholder, and fake-session shortcuts are not part of normal smoke or integration workflows; any remaining developer stub must be explicit and narrowly scoped.

### Admission and Gameplay Binding

Trusted proxy, first-party, bootstrap, and connect-token inputs fail closed before they can establish or preserve routing state. Signed actor identity requires positive, matching `sub` and `accountId` claims. Gameplay routing requires a complete positive bundle of `tenantId`, `gameInstanceId`, `worldSlug`, `realmSlug`, and `pointerVersion`; blank slugs, partial bundles, stale pointers, mismatched world/realm targets, and malformed claims are rejected before routing reuse or persistence.

Game Session owns the canonical admitted-runtime normalization through `GameplayAdmissionPointerSnapshots`. `LoginCommandHandler` and `SessionRoutingNormalizationService` validate strict runtime identity while remaining scope-agnostic about `playableStateScope`; command-routing-authoritative seams such as `CommandServiceImpl` enforce scope-aware durable routing metadata. Game Logic and Entity Management receive a complete-or-absent admitted routing bundle and fail rather than consuming a partial one. Room identifiers are opaque text routing identities such as `R-*`, not positive numeric IDs.

First-party selector state used as connect or admission authority is also complete-or-absent. A pre-`PLAY` session shell may retain a normalized `{worldSlug, realmSlug, pointerVersion}` trio only as a non-authoritative lobby selection hint while `playableStateScope=UNSPECIFIED`; that hint cannot establish or preserve a runtime route, authorize `PLAY`, or become downstream gameplay metadata. A missing registry entry combined with any other partial persisted selector fails as `CONNECT_CONTEXT_INVALID` rather than degrading into ordinary realm selection, and malformed or incomplete bootstrap/connect authority is rejected before route preservation. Gateway trust-boundary failures and handshake scope failures remain distinct (`403`/trust rejection versus `CONNECT_SCOPE_MISMATCH`), while invalid first-party signed context is `CONNECT_CONTEXT_INVALID` or `CONNECT_TOKEN_REJECTED` according to the owning seam.

`PLAY` is the gameplay-binding step after authentication or verified first-party bootstrap identity. Its canonical admission semantics and outcome mappings are owned by [Authentication and authorization](../../architecture/system-architecture-authentication.md); current implementation and proof status are recorded under `AA-2.1`. First-party `PLAY` uses the same runtime authority as generic reconnect.

The canonical gRPC `GameSessionGrpcService.startSession` path preflights IP admission before replacing an existing session. Replacement transfers/reserves the IP slot safely, leaves the existing session alive until the new session and reservation succeed, and on failed admission stops only the tentative session. The shared `GameInstanceService.startSession` default is non-destructive; replacement is explicit. Once replacement is admitted, failure to tear down the old session is warning/cleanup follow-up rather than grounds to revoke the newly accepted session. REST `/sessions` is explicitly noncanonical operator/bootstrap behavior.

### Session Lifecycle and Logout

Redis-backed session context carries the authenticated account/tenant identity and gameplay binding, including character and game-instance context. Namespace-aware takeover/transfer remains unimplemented and unproved: current implementation remains keyed by `{tenantId, gameInstanceId, characterId}` and supports explicit replacement at that scope, but current proof does not establish the target namespace/replacement boundary from [ADR 0122](../../architecture/decisions/adr-0122-stable-playable-state-namespaces-for-runtime-replacement.md) or the binding-generation transfer, old-source input fencing, and preservation of admitted-work identity owned by [ADR 0132](../../architecture/decisions/adr-0132-namespace-scoped-single-character-controller.md). An unexpected transport loss can preserve the underlying session and queues for resume. Resume and takeover emit structured identity-bearing logs and bounded metrics such as `gamesession.session.resume`, `gamesession.session.takeover`, `gamesession.session.resume_denied`, and `gamesession.session.fresh_entry_fallback`.

The lifecycle classes are deliberately distinct:

- Unexpected disconnect may mark the session suspended/reconnect-eligible, preserve bounded replay state, and allow later `PLAY` to request recovery.
- Takeover invalidates the losing gameplay binding and does not leave it in control; close/reason classification identifies takeover.
- Deliberate `LOGOUT` is termination, not suspension. It deletes authenticated/gameplay session context, clears first-party connect context registration, removes gameplay presence, invokes the current World Management termination seam and downstream Entity cleanup, returns one canonical result, and closes the transport with a deliberate logout reason. A fresh first-party `PLAY` no longer replays retained context after logout, but the durable terminal `resumeContextGeneration` fence and race/retry proof are still absent. Logout does not delete bounded durable `resume_transcript_entry`/screen-buffer rows merely to emulate that fence. Logout before login is a bounded in-band failure.

Replay projection is separate from retained transcript storage. Generic fresh `LOGIN` plus `PLAY` after logout is not reconnect and does not replay retained output; unexpected transport loss remains reconnect-eligible. The Unit 1B WebSocket correction no longer treats a first-party connect-context token alone as replay authority, while every successful first-party `PLAY` still requests a fresh `LOOK`, even without a retained buffer. This is a local replay-trigger correction, not durable terminal-episode or `resumeContextGeneration` proof; retained rows are not deleted merely to simulate logout authority. Partial gameplay shells are not authoritative: `hasGameplayBinding` may identify a shell requiring cleanup/normalization, but full gameplay identity requires positive game-instance and character identity, and gameplay-region readiness additionally requires a room. Logout cleanup and reconnect replay therefore skip partial identity shells rather than trusting them.

### Reconnect and Continuity

For generic Telnet and WebSocket, reconnect uses current identity and current Account runtime membership/entitlement authority, not only a prior backend token. Revoked membership, removed realm access, unavailable tenant gameplay, stale runtime target, and failed authority reads fail closed as appropriate. Current implementation resolves the effective disconnected-resume window but does not enforce it in `PLAY`; backend authority unavailability remains retryable temporary-unavailable behavior. A fresh `LOOK` redraw is the current-state authority after successful resume or fresh fallback. Reconnect target behavior and proof requirements remain canonical in [Reconnection](../../architecture/system-architecture-reconnection.md).

Current durable reconnect rows remain game-instance-keyed, so namespace-key migration is partial. Redis may cache them but is not authoritative gameplay state. The connection-local TCP Proxy input buffer is distinct from durable context and supports only a still-established edge rebind; it is never durable replay of input, transport bytes, frames, or unsent transient output. Current implementation/proof of the bounded reconnect context and prompt behavior remains partial; the canonical continuity contract is [Reconnection](../../architecture/system-architecture-reconnection.md).

First-party `/ws/game/**` has a separate but partial authority path. Account exposes player bootstrap and connect-token issuance; Gateway validates and forwards signed connect context; Game Session consumes verified identity at bare first-party `LOGIN` and keeps `PLAY` as the binding step. The current screen-buffer projection restores retained context and fresh redraw, but resume-window enforcement, prompt proof, and post-logout suppression remain incomplete. The authority and reconnect contracts remain linked in [Reconnection](../../architecture/system-architecture-reconnection.md) and [Authentication and authorization](../../architecture/system-architecture-authentication.md).

Gateway owns the downstream `/ws/game/**` socket and a stable edge transport session id. Its custom bridge can rebind an upstream Game Session socket after bounded loss without immediately dropping the player socket, reusing that edge id. Focused proofs cover abrupt upstream loss, a Game Session-like process bounce with isolated Reactor resources, and post-restart Game Logic commands (`LOOK`, movement-derived room context, and communication inputs) against shared state. Edge-visible retry taxonomy is reserved for actual edge-route loss or exhausted rebind windows; this does not guarantee in-flight command or byte replay.

Shared coordination state now carries reconnect/connect-context tracking, disconnect deduplication, gameplay-identity screen-buffer access, and bounded takeover information, while the in-process socket remains local. Shipped proof is limited to the close-metadata fallbacks: missing or unattributed metadata on a public WebSocket emits close `1011`/`internal_error`, and missing or invalid top-level metadata on an established authenticated TCP Proxy bridge renders `DISCONNECT backend_unavailable ...`. Focused Gateway/bridge and Telnet-handler tests cover those classifications; they do not prove command/byte replay, the broader handler taxonomy, or the complete continuity contract. Those remaining gaps are tracked in [TCP Proxy Operations](../../architecture/microservices/tcp-proxy-service/operations.md#implementation-status); duplicate and missing disconnect hints remain separately metered.

### Fail-Closed Boundary Convergence

The auth/session/routing guardrail family is complete at its current bounded seams and is now a standing regression boundary, not a claim that every future ingress path has been audited. Shared helpers and direct adopters cover:

- `JwtClaims`, `SessionClaims`, current-account access, tenant-scoped gameplay presence classification, and downstream gRPC bearer creation. The current Common Security seam still uses legacy session attestation and service-identity handling; the target replaces that with certificate-derived mTLS workload identity plus allowlists and typed `PlayerExecutionContext` for player scope;
- bootstrap/connect-scope/runtime membership/grant/entitlement claim readers, account-subject coherence, replay readers/writers, and account REST/gRPC request readers in Account Service;
- `GameplayAdmissionPointerSnapshots`, `ControlPlaneRequestParser`, `SessionIdParsing`, positive-ID readers, gameplay-character parsing, partial-shell classification, IP counter parsing, and command/control-plane routing normalization in Game Session;
- signed first-party handshake/connect-context checks and `TrustedTcpProxyIdentity` at Gateway, plus `TelnetRoutingBundle` and hidden bootstrap envelope handling at TCP Proxy;
- the corresponding positive-ID, room-scope, actor-scope, replay-payload, current-account, routing-bundle, and REST error-envelope readers in World Management, Entity Management, Social Groups, Automation, Logging & Admin, Game Design, and Game Logic.

The current numeric-reader guardrail is: numeric identifiers still used by an implemented seam must be present, well-formed, and positive; opaque room ids remain textual. This is not the durable cross-boundary target. [ADR 0020](../../architecture/decisions/adr-0020-scoped-domain-and-operational-identifiers.md) makes durable cross-boundary account, tenant, game-instance, character, and version identities scoped UUIDs, so replacing current numeric forms and proving scope-qualified comparison remains tracked migration work. Malformed or contradictory JWT/signed-token claims reject before identity comparison; partial routing bundles are absent or rejected, never completed by fallback; malformed persisted replay state is ignored/rejected or terminalizes only its affected durable work item; and request validation occurs before replay lookup when malformed shape could otherwise be masked by a stored effect. Malformed persisted Automation tenant identity terminalizes only that work item rather than aborting the batch. Unexpected parser/runtime bugs are not mislabeled as auth failures.

This includes positive readers for account, tenant, session, game-instance, character, version, item/container, payment, report, formation, and control-plane identities across the participating services; current-account claims that are present but malformed count as authenticated caller context and therefore fail tenant access rather than silently becoming anonymous; and invalid session JWTs used only for presence classification consistently degrade to the ordinary `PLAYER` presence role. The Game Session classifier and shared gameplay-specific claim helpers now ignore global roles and require an explicit tenant-scoped role for in-game elevation; this focused correction does not make the disabled Account runtime reads live. Automation schedule due-point identities reject fractional JSON numbers as `invalid_built_in_payload` before handler, pin, quota, or durable-queue work. Runtime-version, work-item, tenant, and gameplay routing readers reject malformed/non-positive values before lookups or mutation. Entity replay-backed mutations validate expiry, required text, optional container identity, and positive quantity before replay execution so a replay hit cannot hide malformed request shape.

Replay boundaries validate both read and write sides. Account connect-token and public-production membership replays require valid success/created flags, nonblank required text, and payload identity matching cache-key inputs; otherwise the replay is treated as unavailable rather than as authoritative success. Prepared upgrade and remote-control-plane replays likewise compare request/execution payloads before reuse. Shared control-plane response readers reject malformed or non-positive returned ids instead of projecting them into apparently valid DTOs.

Equivalent HTTP, WebSocket, and gRPC failures use stable boundary semantics. The [gRPC owner contract](../../architecture/system-architecture-grpc.md#outcome-and-transport-classification) uses typed result unions for successfully produced expected domain outcomes and canonical non-OK status with bounded details when a domain result cannot be produced. Current Game Session/peer handlers still return many response-level `ErrorDetail` payloads, while transport failures cover infrastructure and some pre-domain cases; exact per-RPC migration and proof remain gaps. Shared REST exception handling continues to produce `ApiResponse<ErrorDetail>` envelopes and field-specific `INVALID_ARGUMENT` responses instead of framework-default JSON. These seams log application warnings, meter `grpc.app_error` where applicable, and preserve span/error-code classification.

## Validation and Proof

The evidence records focused unit, controller, gRPC, WebSocket, cross-service, and restart/rebind proofs for text parsing and Telnet parity; real Account-backed login and authenticated `PLAY`; takeover, resume, logout, and replay cleanup; public-production membership idempotency; first-party handshake/reconnect; session-start IP ordering; malformed claim and positive-ID rejection; replay identity/payload mismatch; current REST/gRPC error envelopes; and Gateway upstream/process restart continuity. It does not yet prove the owner gRPC typed-result/non-OK classification across every adopter. The Telnet cross-service harness uses a lightweight Gateway stub only as a test fixture and has a successful `TelnetGatewayGameSessionCrossServiceIntegrationTest`; the maintained runtime path is not the stub.

The focused admission proofs cover fresh acceptance, same-IP replacement reservation transfer, rejection without destroying the old session, and the non-destructive operator path. Telnet proofs cover envelope parsing, event metadata, reconnect backoff, bounded connection-local ordered input buffering during edge rebind, buffer exhaustion, sensitive logging, and Telnet/WebSocket `LOOK` parity; they do not prove durable replay of client input or transport bytes. Game Session gRPC proofs cover `Ping`, `NotifyDisconnect`, session lifecycle/control-plane parsing, application-error payloads, and `grpc.app_error` classification. First-party proofs cover fresh-token enforcement, bare verified-identity login, `PLAY` scope binding, replay/expiry/context/scope failures, screen-buffer restore, and fresh redraw.

Account authority proof covers account-first tenantless bootstrap authentication and account-scoped session state, the current membership seam, Account-owned non-public realm grant denial, cross-tenant membership enforcement, and the contained export/deletion/recovery boundaries. `DeleteAccount` now denies before account or financial-row mutation rather than relying on a partial active-subscription guard. Explicit `JOIN`/`Join & Play` and its bounded readback worker are local, while PostgreSQL lost-acknowledgement/concurrency, the connect-token membership-authority-generation reread, and canonical tenant-role, lifecycle-state, and authority-generation follow-through remain partial or unproved.

- **Validation record:** Required current documentation, contract, settings-generation, allocation, ADR, and `git diff --check` gates are recorded in the canonical [Validation And Proof References](../design-alignment/design-capability-allocation.md#validation-and-proof-references). Runtime proof is not applicable to this documentation-only change.

## Active Gaps

- Account authentication has no stable attempt identity or replayable result contract. Game Session now avoids automatically retrying an ambiguous credential-consuming transport failure, but Account still needs durable request identity and idempotent result lookup before authentication itself is safely retryable.
- Signup-time login-mode selection and authenticator-app TOTP enrollment/management are not implemented; the live credential contract remains password plus email OTP. Richer MFA policy for elevated users is also future work.
- Tenant membership currently persists admission permission rather than the designed tenant-role set; Account JWT issuance does not emit tenant `scopedRoles`, and realm grants have no expiry or tenant-admin management surface.
- The canonical runtime entitlement response still lacks subscription status, explicit free/trial state, `allowNewInstanceStarts`, quota fields, authoritative evaluation freshness, and real monotonic version/sequence fields. Game Session does not implement per-tenant caching, event invalidation, strict new-commitment checks, bounded last-known-good reconnect/recovery, or hard-cutoff propagation; Current `past_due` gameplay/public-join eligibility matches the accepted policy; the missing snapshot fields and freshness gates above, not this allowance, are the gaps. Durable `purchase_entitlement` fulfillment/revocation is also absent.
- Prompt-based `LOGIN` remains unsupported on credential-bearing transports. Telnet and the direct internal/test WebSocket seam currently accept parameterized credentials, while public non-proxy `/ws/game/**` requires a verified connect-token context and bare `LOGIN`.
- Manual QA remains for generic Telnet/WebSocket reconnect, takeover and failed resume, first-party reconnect, shared-state replacement, abrupt upstream rebind, Game Session restart, and Game Logic restart while the edge client remains connected.
- The first-party fresh-`PLAY` replay trigger no longer reads retained context solely because a connect token exists, but durable logout-episode/generation fencing and race/retry proof remain. Retained transcript storage is not reconnect eligibility and is not deleted merely to simulate a terminal fence.
- Broader discovery parity (`WORLDS`/`REALMS`/`CHARS`), richer admission-pointer/discovery behavior, and any later public/non-public realm product expansion remain outside the current bounded implementation.
- Account switching, multi-session controls, global sign-out, and richer first-party logout UX are not implemented. The designed Account Service `/auth/logout` and `/auth/logout-all` control-plane routes and issuer/account/tenant/membership authority-generation workflows are also absent from production code.
- Gameplay presence and shared gameplay-role predicates now ignore global roles and derive elevation only from explicit tenant-scoped grants, with focused claim/classifier/WHO unit proof. Account's actual tenant-role issuance and full admission handoff remain incomplete; no staff impersonation or hidden-observer mode is part of the target.
- New Game Session Redis session-context aliases and movement-effect replay writes strip the raw Account delegation JWT, and their readers do not return legacy raw values. Existing untouched Redis values still require a fenced inventory/cleanup and readback before this new-write containment may be deployed as a complete at-rest correction. The ADR 0031 Account-issued opaque rebind handle, non-secret token metadata, refresh/revocation, and tenant-scoped presence evidence remain ordered pre-v1 work; a token hash alone is not restart authority.
- Every current Account deletion entry now denies before account and financial-row mutation. The full ADR 0043 pending-deletion and `DATA-01` retention workflow, with provider/transfer clearance and approved finite schedules, is the named pre-v1 Account successor required before deletion is enabled.
- Account security-lock, ban, suspension, operator recovery, and appeal handling are not a complete end-to-end cross-service flow. The current `AUTH_ACCOUNT_LOCKED`, moderation, and lifecycle boundaries must converge without making Logging & Admin the owner of Account enforcement.
- Automated signing-key rotation, overlap/pruning, and deployment-wide validator-convergence proof remain deferred even though JWKS publication and conditional file watching are live.
- The continuity boundary intentionally excludes generalized chaos testing, arbitrary command replay, transport-byte replay, and reconstruction of queue/tick ownership if Game Logic later owns durable execution.
- The guardrail family should reopen only for a new concrete auth/session/routing regression; it is not a completed audit of every future service ingress.

## To Discuss

No competing target state is currently recorded. Future design discussion is required before changing credential modes or introducing the shared OTP/TOTP enrollment model, changing Account-owned admission authority or the account-versus-tenant ownership split, expanding reconnect guarantees beyond bounded redraw, or making non-edge restart continuity depend on durable queue/tick ownership. Future smart-client attach metadata must remain non-authoritative if revived.
