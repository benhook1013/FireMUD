# Player Experience, Commands, and Communication

## Target-State Authority

This is a non-normative implementation tracker for player-facing commands, communication, presence, and client behavior. Canonical target-state player-experience and cross-service contracts remain authoritative in [design/architecture](../../architecture/README.md) and the linked design sources below; this tracker owns current capability status, proof evidence, gaps, and handoffs, not normative design.

## Current Status

This tracker is the permanent reader-facing implementation record for player-facing commands, admission, presentation, communication, presence, and client behavior. Most bounded capabilities are live, including the stored game-authored HELP path; broader command interpretation, rich help authoring/discovery, elevated staff behavior, richer communication, and the dedicated browser-service boundary remain explicitly incomplete. The output/reconnect lane remains partial where explicit structured schema versioning, strict complete-byte context bounds, first-party post-logout suppression, and broader client consumption are not yet proven.

## Current Gaps

- Gameplay presence role classification still maps global `platformAdmin` and legacy global `god` into in-game `ADMIN` and `GOD`; reconcile this against [ADR 0026](../../architecture/decisions/adr-0026-global-roles-do-not-grant-gameplay-authority.md).
- Profile-policy surfaces still accept `HIDDEN_STAFF` and fail closed to `PRIVATE` during projection; reconcile the vocabulary against [ADR 0046](../../architecture/decisions/adr-0046-bounded-friend-presence-with-private-by-failure-redaction.md).
- Player-facing presence responses still expose disconnect disposition; reconcile the response shape against [ADR 0046](../../architecture/decisions/adr-0046-bounded-friend-presence-with-private-by-failure-redaction.md).

## Consolidated Implementation Record

This section records implementation and proof status only. The target command, presentation, reconnection, settings, presence, privacy, and frontend contracts remain in the canonical sources listed above, including [ADR 0026](../../architecture/decisions/adr-0026-global-roles-do-not-grant-gameplay-authority.md) and [ADR 0046](../../architecture/decisions/adr-0046-bounded-friend-presence-with-private-by-failure-redaction.md).

### Admission, Commands, and Capabilities

Current text behavior exposes `WORLDS` as an optional pre-login public browse, then `LOGIN` followed by `PLAY <world> [character]` as the direct gameplay-binding path for existing members. Realm and character discovery helpers are currently not required ceremony. Text `PLAY` and connect-token issuance return `JOIN_REQUIRED` only when fresh authority confirms a publicly visible target with an allowed public-production join policy and the caller's membership is absent; policy denial remains `PUBLIC_PRODUCTION_ADMISSION_DENIED`, while unavailable or invalid authority remains the applicable unavailable/invalid-authority outcome. An unambiguous eligible `PLAY` enters directly; ambiguous or inaccessible selections return selection-oriented or explicit bounded errors rather than low-level gameplay failures. Wrong-stage input produces guidance such as `LOGIN_REQUIRED` or `PLAY_REQUIRED`.

The current admission gaps are explicit `JOIN`, realm-scoped discovery/character ceremony, and the connect-token membership-authority-generation reread. The `PLAY`-side `JOIN_REQUIRED` behavior and connect-token missing-membership rejection are implemented; canonical admission behavior remains in [Authentication and authorization](../../architecture/system-architecture-authentication.md) and [ADR 0025](../../architecture/decisions/adr-0025-explicit-open-enrollment-membership.md).

### HELP, Settings, and Presentation

- Current behavior: built-in `HELP` is filtered by effective optional command capability. A bounded game-authored topic path supports tenant/template-scoped published topics, normalized exact lookup, and platform fallback. `FEATURE_UNAVAILABLE` is returned for disabled direct optional commands. Communication, prompt, presentation, and reconnect settings have typed metadata and effective-settings readback across their owning services.
- Current proof and gap: parser, registry, capability, HELP/history, rendering, prompt, WebSocket/Telnet parity, and settings tests cover these seams. Rich authoring UI, localization-aware help, fuzzy/semantic search, related-topic and stage-aware discovery, richer prompt composition, and broader smart-client presentation remain incomplete.
- Current behavior: `PlayerOutput` remains structured until rendering; Telnet and generic WebSocket receive renderer-owned text, while first-party WebSocket responses and recipient pushes use structured envelopes. `LOOK`, movement refresh, communication, prompt, and reconnect paths use typed output metadata. The current `web-client` only generically JSON-parses the WebSocket envelope as `unknown`, so semantic structured `PlayerOutput` consumption and compatibility proof remain absent. Fresh room reads are authoritative and prompts are excluded from replay; schema/projection contract status is linked in [Input, Output, and Presentation](../../architecture/system-architecture-input-output-and-presentation.md).

### Transcript, History, and Room Views

- Current behavior: durable semantic recent-context rows are the bounded source of recent output and Redis is a best-effort hot cache. Structured entries preserve identity, ordering, payload metadata, and compatibility text. `HISTORY` is a separate accepted-command store. `LOGOUT` clears live presence and reconnect eligibility in storage, but the first-party connect-context replay handler currently ignores that eligibility and may replay retained rows; durable retained rows are distinct from reconnect eligibility. Complete-entry byte bounds and omission behavior remain implementation/proof gaps tracked by [Reconnection](../../architecture/system-architecture-reconnection.md) and [ADR 0134](../../architecture/decisions/adr-0134-bounded-durable-semantic-reconnect-context.md).
- Current proof and gap: focused transcript, repository-ordering, retention, Redis, settings, and HISTORY tests cover the storage boundary. ## Active Gaps

- The normalized command envelope is still text-command-first: stage and client metadata are outside the richer envelope. NPC targeting, explicit ambiguity outcomes, localized aliases, active-registry discovery, richer schema-driven definitions, and broader action-metadata policy consumers remain incomplete. Stable item references are live, but the broader duplicate-NPC and action-family resolution model is not.
- The bounded stored game-authored HELP path is live, but rich authoring UI, localization-aware content, fuzzy or semantic search, related-topic behavior, stage-aware indexes, moderation/versioning, and broader dynamic command-discovery integration are not implemented.
- Structured recent transcript retention is bounded and is not a complete player archive/export facility. Player-controlled export, long-term history/search, and final raw-versus-normalized speech storage policy remain separate work.
- Communication has no offline `TELL`, `SHOUT`, configurable topology propagation, richer partial/full interception, game-configurable observer policy, distinct observer moderation ledger, or first-party/MCP-aware recipient presentation.
- Localization is live for active built-in renderer outputs and room/exit prose, but item, lore, and broader world-content adoption and locale-specific speech policy remain incomplete. Stored authored variants follow exact locale -> explicitly stored base language -> source locale; arbitrary regional sibling fallback and live provider translation remain out of scope, and no broader creator workflow/provider has been selected.
- Presentation still lacks combat-state-driven brief-on-move behavior, richer configurable prompt composition, broader prompt scheduling, and broader smart-client presentation policy.
- Presence and social surfaces have a bounded canonical runtime/read model, but broader activity-engine consumers, richer recent-presence policy, broader social consumers, and operator visibility and staff-capability enforcement remain incomplete.
- The dedicated first-party web application service, permanent browser asset-hosting boundary, and richer browser product surface remain planned.
- Manual QA still needs to confirm that normal Telnet and generic WebSocket clients follow the same optional-browse, `LOGIN`, `PLAY`, in-game progression and that the first-party browser reaches the same gameplay binding semantics.

| Owner | Current responsibility | Primary contract boundary |
| --- | --- | --- |
| TCP Proxy and Gateway | Transport bridge, public edge, authentication/bootstrap propagation | Telnet bridge, gameplay WebSocket route, trusted ingress |
| Game Session | Command parsing/registry, stage and capability checks, canonical gameplay presence, structured output, rendering, prompt/replay, recipient push, account-presence query | Text command interpreter, WebSocket ingress, Game Session gRPC |

| World Management | Current room snapshots and localized room/exit source content | LOOK/world-read contracts |
| Game Design and settings authority | Effective command capability, presentation, communication, and prompt policy; tenant/game overrides | Shared settings precedence and Game Session effective-settings readback |
| Logging & Admin | Privileged built-in alias validation and operator diagnostics | Canonical control-plane readback |
| First-party frontend | Current generic WebSocket envelope/JSON consumer (`unknown`) and server-state baseline | Web client; dedicated web-app service remains planned |

The service boundaries above are the current ownership contract. Game Session is the player-facing policy/rendering and runtime-presence owner; Game Logic is the gameplay/action and communication-resolution owner; Social Groups is the social policy/history/fanout owner; World Management is the authoritative room-content owner; Account is the profile-policy source; and Logging & Admin consumes canonical control-plane diagnostics.
