# Gameplay Rules, Entities, and Effects

## Target-State Authority

This is a non-normative implementation tracker for gameplay rules, entities, and effects. Canonical target-state behavior and cross-service contracts remain authoritative in [design/architecture](../../architecture/README.md) and the linked design sources below; this tracker owns current capability status, implementation and proof evidence, gaps, and handoffs for this domain.

## Current Status

The live implementation is strongest in item containment and transfer, durable effect replay, and the first evaluated actor-state/effect seams. Entity Management also has crafting-oriented query structures and version-scoped recipe rows, but there is no complete player crafting/material-consumption flow yet. The broader authored-action, generic actor, targeting, resource-cost, and combat models remain incomplete. Cross-service proof is strongest on the bounded item, LOOK, movement, and replay paths; broader gameplay orchestration is still represented more by service-level tests and slice-oriented fixtures than by full production integration.

PLAYER-01 remains a target ownership contract, not a capability completion. Detailed persisted actor, policy, descriptor/template, and fork-copy rules are owned by [Entity Management](../../architecture/microservices/entity-management-service/runtime-and-data.md). Gameplay tracking retains only the consequence that actor-state/effect work must use Entity's persisted realm-valid identity; current synthetic-ID, fixed-schema, policy-resolution, provisioning, and fork-copy proof gaps remain.

## Consolidated Implementation Record

### Ownership and Visible World

World Management is authoritative for room identity, location, exits, and occupancy. Entity Management owns room-ground items through room-attached containers and exposes a bounded LOOK-oriented visible-entity listing keyed at minimum by tenant and room instance. That listing is structured for rendering with stable display names and player/NPC/item classification, without exposing internal stats. Game Logic combines those authorities for the player-facing room projection; Game Session owns command/protocol delivery rather than reconstructing entity state.

The live command distinction is intentional: ordinary `LOOK` is room-context prose, while `INV HERE` is the explicit room-ground management view. A room-ground container is shown as one room item, and nested contents are revealed only through `CONTAINER`; they are not expanded into ordinary room prose. Deterministic fixture rooms contain the minimal player/NPC/item data used by the current tests and transcripts. Rich prose, combat/effect annotations, NPC response, localized listening, and broader non-fixture room/entity context are not implemented.

### Item Commands and Service Boundaries

The authenticated live item command surface is `INVENTORY`, `INV HERE`, `GET`, `DROP`, `CONTAINER`, `PUT`, `TAKE`, `EQUIPMENT`, `WEAR`, and `REMOVE`. Game Session routes these through one bounded `ItemCommandHandler` seam to Game Logic; Game Logic performs gameplay-facing query, visibility, selector, and context validation; Entity Management remains authoritative for item, holder, equipment, and container persistence. Hidden inventory containers are implementation-owned rather than directly player-addressable. The current flow carries tenant/game/session/character and room context, and uses World Management room identity where required.

`GET` and `DROP` resolve names, visible refs, container refs, stack refs, and quantities against the appropriate holder surface in Game Logic before delegating a concrete mutation. Successful pickup/drop responses refresh both affected holder views. Structured first-party WebSocket payloads include typed item entries, refs, quantities, descriptions, slots, container context, and an `item_mutation_result` containing the action, mutated item, and source/destination holder context. Telnet and generic WebSocket retain the shared canonical transcript renderer.

Game Session records central `gamesession.command.item.*` invocation/failure metrics tagged by item command type and error, distinguishing player errors such as `ITEM_NOT_FOUND` and `SLOT_INCOMPATIBLE` from backend or validation failures. Inventory command availability is tenant/game policy; slot, body, compatibility, and stackability facts are versioned DML-backed design data rather than a second settings domain.

### Containers, Equipment, and Item Identity

Container contents are keyed by durable `container_instance_id`, not by the current character and container definition. The container instance moves across carried, equipped, and room-ground holders without losing contents, and access is derived from its current holder/location. Container-capable query rows expose the container instance identity. Nested containers remain out of scope.

All live holder classes use persisted `item_instances` as their physical-item truth: carried inventory, equipment, room ground, and container contents. A container instance is linked to its corresponding item instance. The canonical runtime holder representation is direct item-instance fields for character, equipment slot, game instance, room instance, and container instance, with one authoritative location/binding; an equipped item is not simultaneously an ordinary inventory member. Same-definition non-stackable items remain separate and can be selected independently.

Equipment uses versioned game-configured slot definitions, slot groups, body-layout membership, character body-layout keys, and item compatibility data. Familiar slot names are data, not universal platform enums. Slot/body-layout incompatibility and inaccessible/missing/mismatched item or container state are validated at the gameplay and owning-service boundaries.

### Visible References and Stack Semantics

Concrete item instances persist `visible_ref_token`, `visible_ref_sequence`, and canonical compact refs such as `satchel12`, allocated by Entity Management through a shared per-token counter. Refs are stable for the lifetime of the item and do not change when it moves among inventory, equipment, room ground, and containers. Inventory, equipment, container, room-ground, and room-entity management surfaces expose eligible refs; exact-item matching uses the persisted ref. Ordinary room prose and ordinary action transcripts hide refs by default. Player characters remain name-targeted rather than receiving item-style refs.

Stackability is explicit authored data and defaults to `false`. Eligible stackable items use eager holder-local `item_stacks` records, not overloaded non-stackable item identity. The current authored fields are `stackable`, `stackCompatibilityMode` (`DEFINITION_ONLY` or `DEFINITION_AND_FAMILY`), and optional `stackVariantKey`; runtime stack rows carry `stackFamilyKey`. Compatible items require the same definition, mode, and canonical compatibility fingerprint. Transfers preserve the source family. Query views return merged quantity-bearing stack rows, while non-stackable items retain concrete refs. If multiple families share a definition in one holder, a selector must identify the family or the action rejects as ambiguous; `GET`, `DROP`, `PUT`, and `TAKE` have explicit stack-family selection support.

Quantity belongs to the holder-local stack record. Exact item-instance refs are used for non-stackable physical items, and stack refs/family keys are used when a fungible holder has multiple compatible families. Ordinary prose may collapse identical names for presentation, but storage and mutation truth preserve non-stackable identity and stack-family distinctions.

### Guarded Transfer and Audit

All live inventory, room-ground, equipment, and container mutations use one shared guarded transfer helper and holder-policy validation. The mutation is a single expected-source-to-destination holder transition on an item instance or stack family, not unrelated remove/add operations. It checks tenant and expected source ownership at mutation time; stale, missing, incompatible, or already-at-destination state fails before holder fields are rewritten. Scheduler or tick serialization is not the duplication defense.

Transfer failures emit canonical warning context including item instance/item identity, expected and current holder, destination, verb/cause, and actor character when available. Successful item-instance and stack-backed transfers write `item_transfer_audits` in the same local transaction boundary as the mutation; failed transfers commit neither the holder change nor an audit row. The target audit and durable-reconciliation contract requires the complete `{tenantId, playableStateNamespaceId, playableStateScope, gameInstanceId}` scope tuple. That complete namespace/scope transfer/effect tuple is a target gap: current `item_transfer_audits` and `EntityMutationEffect` records do not carry it, so the current local transfer/audit implementation does not prove live cross-scope replay or reconciliation. Durable item/equipment/container mutation requests carry attested `sessionId` and durable `effectId`; when present, `effectId` is the explicit audit correlation key. A deterministic fallback correlation key is derived from verb, actor, item, quantity/family, and holder endpoints, but this is not broader replay semantics. Operators use the audit trail for item-duplication investigations, suspicious-transfer analysis, and later invariant checks.

The live transfer contract deliberately rejects an already-moved item by default. It does not infer idempotent success; a caller that needs replay/no-op behavior must provide an explicit replay contract.

### Durable Effects and Replay Guards

The live Game Session gameplay-command path persists a stable same-batch `effectKey` and derives `effectId` from `tickBatchId` plus that key (`command:<commandId>`); durable tick staging and replay reject missing or blank command IDs before effect selection, so the private helper's defensive `command-text:<hash>:slot:<index>` branch is unreachable in the live tick path and is not a no-commandId recovery identity. Same-batch duplicate keys are rejected. This command-linked effect identity does not establish the target command-plan root binding, which remains unimplemented and unproved here. Durable drained effects resume after restart and, after an ownership-fence check, converge to `APPLIED`, `REPLAY_NOOP`, or `REJECTED`; stale executors abandon and requeue rather than applying under the wrong fence. See [ADR 0069](../../architecture/decisions/adr-0069-at-least-once-effect-execution-with-one-logical-terminal-outcome.md) and [Transaction Strategies](../../architecture/system-architecture-transactions.md#command-atomicity-and-outcome-aggregation) for the canonical plan/root, participant, and replay contracts.

Owning domains provide the duplicate-application boundary rather than relying on one global guard table. Movement uses an `effectId`-keyed idempotency service tied to session-context mutation. Entity Management stores one mutation replay row per `{tenantId,effectId}` with the applied protobuf response for item/equipment/container mutations and `ApplyActorCondition`; duplicate delivery returns the stored response. Game Session has local replay records per `{tenantId,sessionId,effectId}` for `SAY`, `WHISPER`, `TELL`, `AFK`, `BLOCK`, and the bounded authored-action path, re-delivering actor-facing output without re-invoking the mutation handler. Social Groups persists `effect_id` with a `{tenantId,effectId}` uniqueness boundary and returns the stored chat DTO on duplicate delivery.

The shared execution helper also keeps Game Session communication, AFK, action-state, and authored-action replay lookup/save/delivery behavior aligned. Metrics distinguish first apply and replay/no-op outcomes through `gamesession.durable.effect.execution{command,effect_status,gameplay_result}` and Entity Management mutation execution metrics. This is a bounded adoption set, not a universal cross-service guard table; broader participant-guard propagation and cross-service replay proof remain incomplete.

### Actor State and Typed Effects

Entity Management owns persisted actor resource and active-condition state in `actor_resource_states` and `actor_active_conditions`, keyed by tenant, derived playable-state namespace, and character id. Runtime game-instance identifiers remain opaque strings. `QueryActorState` is a gameplay-attested, playable-scope-aware read that overlays baseline character stats, persisted resource rows, active non-expired conditions, equipped-item payloads, and replay-guarded transient action state. `STATUS` and its `STAT` alias expose typed resources and visible conditions through Game Session -> Game Logic -> Entity Management without exposing internal effect payloads or source provenance.

The first `EffectEvaluationService`/`DefaultEffectEvaluationService` is in-process and deterministic. It supports additive and multiplicative numeric modifiers, min/max clamps, granted flags, granted conditions, scoped metadata, and source provenance. Modifiers are ordered by priority and source metadata; numeric evaluation runs base, additive, multiplicative, minimum clamp, maximum clamp, then granted-state projection. Persisted effect payloads require a `modifiers` array, registered operation, identifier `target_key`, numeric `value`, optional identifier scopes, and optional integer priority; legacy aliases and implicit values are rejected.

Equipped item payloads and active condition payloads contribute through this evaluator. `ApplyActorCondition` is gameplay-attested, validates nonblank source identity and canonical effect JSON before replay lookup, and is routed by Game Logic. Its current request has no dedicated `effectId`: the current temporary adapter writes the durable effect id into `sourceId`, Game Logic forwards it, and Entity Management interprets that same `sourceId` as the `{tenantId, effectId}` replay key while also persisting it as source provenance. This overloaded `sourceId` behavior is an implementation adapter, not the canonical replay contract, and its tests must preserve that limitation explicitly. Separating replay identity into a dedicated `effectId` from authored/source provenance remains a contract gap before other condition producers can safely reuse one source across multiple applications. Entity Management removes elapsed transient states through its scheduled expiry job. Game Session no longer infers state mutation from broad tags such as `COMBAT`; only explicitly declared behavior routes to a concrete mutation.

The first equipment proof covers passive contributions such as `armour_value` or resistances. The first actor-state proof covers an effective resource composed from a persisted override, a non-expired condition, and an equipped-item contribution in Entity Management. A separate transport proof covers `STATUS` through the live Game Session and Game Logic applications to the Entity Management gRPC contract; its fixture controls the Entity Management response and is not evaluator proof.

### Authored Action Admission and Execution

The live authored-action path resolves aliases, direct HELP topics, dispatch validation, and command-result action metadata from the release bundle admitted for the game instance. Before enqueue, the durable command snapshots the admitted release-bundle id, version id, canonical command id, declared effects, and gameplay tenant/game/character identity. Execution validates that immutable declaration and current gameplay identity before replay lookup.

The bounded v1 executor accepts only a self-targeted `APPLY_ACTION_STATE` declaration. Runtime admission queues only definitions with that single supported effect; effectless or future multi-effect definitions remain discoverable but return the canonical execution-unavailable result without durable enqueue. Missing, mismatched, malformed, or unsupported snapshots fail closed before replay or script publication. The action-state adapter forwards the declared effect payload to Game Logic rather than substituting a built-in `BLOCK` payload. Authored-action replay participates in the durable command `effectId` contract and duplicate execution returns the stored/replay outcome without invoking the handler twice.

### Unified Actor and Combat Boundary

No general persisted actor runtime model is implemented. `WHO` remains player-presence oriented; gods/admins are role and presentation overlays on player presence. The locked implementation direction is one persisted opaque actor core shared by `PLAYER` and `NPC`, with Entity Management owning actor identity and durable actor state, World Management owning location and occupancy, Game Session owning ephemeral session attachment and player-facing presence projection, Game Logic resolving gameplay targets and effects against actor identity, and Account Service owning account identity and authorization inputs. Presence and disposition are separate; disconnect does not defeat an actor. The future core has no universal targetability or visibility fields: release-pinned observation and targeting policies evaluate optional authored facts. Its DML-authored disposition owns base action admission; conditions and equipment can add restrictions but cannot grant behavior that the disposition denies or become competing lifecycle owners.

Damage, mitigation, resistances, combat timing, body-region resolution, defeat, corpses, loot, respawn, and revival are not implemented. Resource adjustment has no implicit death, victory, corpse, loot, respawn, or revival meaning. Future combat must consume the shared actor/state/effect model and keep combat authority out of Game Session.

## Active Gaps

- Accepted TICK-03 requires command-level required/optional effect classification and invariant-sensitive routing; current gameplay families do not yet provide complete classification or terminal-outcome proof. See [ADR 0053](../../architecture/decisions/adr-0053-command-atomicity-by-invariant-class.md) and its [tick failure/operations owner](../../architecture/system-architecture-tick-failures-and-operations.md).
- Accepted TICK-04 requires one durable root `EffectId` with operation/target/request-digest-bound participant guards and causal read composition. Existing replay proof is domain-bounded and does not prove the cross-service guard, stale-precondition, or mixed-floor cases. See [ADR 0054](../../architecture/decisions/adr-0054-split-spatial-authority-with-causal-read-composition.md) and its [identifier-glossary owner](../../architecture/system-architecture-identifier-glossary.md).
- [ADR 0059](../../architecture/decisions/adr-0059-causal-floor-cross-service-presentation-reads.md) accepts a causal floor plus actual opaque World/Entity component versions; current LOOK composition still has scope-marker compatibility behavior, bounded stale-floor retry, and final read-fence error mapping gaps. This tracker does not claim the accepted presentation identity is implemented.
- [ADR 0060](../../architecture/decisions/adr-0060-world-owned-ambient-facts-and-logic-owned-consequences.md) and [ADR 0061](../../architecture/decisions/adr-0061-single-owner-spatial-mutations-across-split-authority.md) keep ambient/location facts in World, item holders in Entity, and root outcomes/reconciliation in Game Session. Current gameplay has no complete cross-owner mutation/targeting proof; the accepted ownership direction does not promote current item or movement seams.
- Broader gameplay families remain unimplemented or unproved against the target contracts owned by [ADR 0056](../../architecture/decisions/adr-0056-one-hot-path-fan-out-owner.md), [ADR 0069](../../architecture/decisions/adr-0069-at-least-once-effect-execution-with-one-logical-terminal-outcome.md), [ADR 0075](../../architecture/decisions/adr-0075-depth-cost-and-count-bounds-for-generated-effect-chains.md), and the canonical [Transactions generated-effect-chain contract](../../architecture/system-architecture-transactions.md#tick-effects-are-at-least-once-idempotency-is-mandatory).

- The parent inventory slice remains partially implemented as a domain: manual happy-path verification over both WebSocket and Telnet is still unchecked, and later nested-container UX, crafting/material flows, banking/vendor/mail/trade, loot generation, scripted item behavior, durability, and richer client filtering are not implemented.
- Broader holder families must reuse the direct-holder and guarded-handoff model. Cross-domain transfer replay is not implicit; it needs an explicit caller-owned contract. Stronger audit invariant/alert tooling is also future work.
- Broader character ownership and publish-copy/version synchronization across services remain incomplete; the current item and effect seams do not establish a complete cross-service ownership handoff for later gameplay domains.
- Stack compatibility currently has only the bounded `DEFINITION_ONLY` and `DEFINITION_AND_FAMILY`/`stackVariantKey` seam. Richer authored compatibility sources and a non-merging escape hatch are deferred until a real consumer exists.
- Generic authored stat/condition definitions, release-catalog enforcement as a full authoring system, broader effect kinds, generic resource-cost mutation, cooldown lifecycle, multi-effect action execution, and combat-facing effect consumption remain future work. The intended catalog is versioned DML frozen into a release bundle; Entity Management must reject unknown or stale keys rather than invent defaults, and starter profiles must materialize ordinary editable DML rather than hidden runtime fallback. The current typed payload is still a transitional continuous-source contract. The locked `EffectDeclaration` model distinguishes `CONTINUOUS` read-time sources, which never persist derived resource values, from idempotent `INSTANT` mutations under a resolved plan; future condition application uses authored `REPLACE`, `REFRESH`, `STACK`, or `PARALLEL` and duration policy, while cooldowns remain a sibling timed-state type.
- The future actor-state contract keeps capacity-change policy, floor transitions, disposition, conditions/equipment overlays, action-admission tags, command capability policy, costs, and cooldowns as separate concerns. Resource floors have no implicit `health`, death, victory, corpse, loot, respawn, or revival meaning; continuous sources cannot override disposition admission, and durable instant mutations must own explicit lifecycle transitions.
- The future action-admission contract uses a release-pinned DML `ActionAdmissionTag` catalog and ordered required `admissionTags`. Command-capability and login/play stage gates run first; disposition and continuous overlays may deny but never grant forbidden behavior, and unknown, stale, or omitted required tags fail closed.
- The broad authored target-resolution and structured-outcome capability remains unimplemented and unproved beyond the self-targeted v1 path: cross-actor target sets, multi-effect composition, cross-region outcomes, and the wider typed primitive catalogue remain gaps. Canonical ownership is defined by [ADR 0112](../../architecture/decisions/adr-0112-typed-bounded-gameplay-effect-extension.md), with target-plan resolution in the [Game Logic API contracts](../../architecture/microservices/game-logic-service/api-contracts.md) and validated actor/effect mutation in the [Entity Management API contracts](../../architecture/microservices/entity-management-service/api-contracts.md); this tracker records the current capability and proof gap only.
- Reusable DML observation, targeting, and selection policies define `SOURCE` plus keyed target sets, `EXACTLY_ONE`, bounded `UP_TO_N`, or `ALL_ELIGIBLE` cardinality, and player-selected, canonical-order, ranked, or effect-id-seeded selection. Resolution records candidates, fact snapshots, policy identity, ranking or seed, selected targets, and owner fence/version tokens. Missing or stale facts fail closed; token mismatch re-resolves under the same effect id before mutation.
- Resource costs and cooldowns remain future actor-state execution work. Game Design declarations carry typed costs, cooldowns, and `ON_EXECUTION` or `ON_EFFECT_SUCCESS` commit policy; Entity Management must atomically validate and consume resources, create durable cooldown records, and apply same-region effects under one idempotent effect id. Game Session timers are reconstructible wake-up projections, concurrent actions serialize at the authoritative mutation, queue acceptance consumes nothing, and cross-region failure has no implicit refund. Capacity changes use authored preserve/shift/clamp policy, and floor transitions are explicit one-shot lifecycle events rather than implicit death or victory semantics.
- No unified persisted actor runtime, NPC runtime actors, generic actor targeting/communication, or actor-state linkage exists. The locked core is an opaque `actorId` with tenant/game-instance context, `actorKind`, display name, presence state, and disposition, linking player actors to account/character and NPC actors to runtime instances; `PLAYER` and `NPC` are first kinds, with later `PET`/`SUMMON`, and gods/admins remain player overlays.
- Damage and mitigation implementation is absent, including typed damage packets, hit/mitigation ordering, resistances, action-gated defenses, combat timing, defeat/revival, corpse/loot, respawn, and victory policy.
