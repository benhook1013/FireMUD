# Gameplay Rules, Entities, and Effects

## Target-State Authority

This is a non-normative implementation tracker for gameplay rules, entities, and effects. Canonical target-state behavior and cross-service contracts remain authoritative in [design/architecture](../../architecture/README.md) and the linked design sources below; this tracker owns current capability status, implementation and proof evidence, gaps, and handoffs for this domain.

## Current Status

The live implementation is strongest in item containment and transfer, durable effect replay for requests carrying a nonblank `effectId`, and the first evaluated actor-state/effect seams. Entity mutation requests with a blank `effectId` still execute directly without the replay ledger; this compatibility path is not safe gameplay-admission proof, and focused replay/readiness remains blocked until ingress rejects blank IDs or supplies a valid trusted ID. Entity Management also has crafting-oriented query structures and version-scoped recipe rows, but there is no complete player crafting/material-consumption flow yet. The broader authored-action, generic actor, targeting, resource-cost, and combat models remain incomplete. Cross-service proof is strongest on the bounded item, LOOK, movement, and nonblank-effect replay paths; broader gameplay orchestration is still represented more by service-level tests and slice-oriented fixtures than by full production integration.

Current residual: the crafting handlers remain runtime-reachable legacy implementation drift, but their paths and schemas are omitted from the authoritative Entity OpenAPI; the REST adapter is therefore unsupported/nonconformant rather than a public contract. The deployed Entity HTTP layer still requires only an `AUTHENTICATED` bearer and does not authorize that caller to the supplied tenant. It trusts caller-supplied tenant, recipe, and item identifiers. The existing crafting proof is happy-path only; tenant-qualified recipe lookup/update, same-tenant result/ingredient ownership, and cross-tenant negative proof remain open.

The capability-table CRUD entry below refers only to this legacy persistence/service-controller seam; it is not a supported public REST API or gameplay crafting flow.

PLAYER-01 remains a target ownership contract, not a capability completion. Detailed persisted actor, policy, descriptor/template, and fork-copy rules are owned by [Entity Management](../../architecture/microservices/entity-management-service/runtime-and-data.md). The preparation adds opaque UUID/quarantine metadata, canonical assignment/receipt/roster storage, and manually composed unregistered source services. Existing legacy consumers retain develop behavior. Authenticated owner provenance, real caller/controller/execution replacement, runtime quarantine enforcement, and gameplay activation remain later work; storage fixtures do not close those gaps.

Passive `CHARACTER_CREATE/1` receiving support is now present in common-platform-core: [the family codec](../../../services/common-platform-core/src/main/java/net/firedevops/firemud/common/operator/CharacterCreateOperatorActionCodec.java) composes the existing `MutationDigestV1` grammar with schema-three `RealmEntryPolicy`; its bounded [authored-source projection parser](../../../services/common-platform-core/src/main/java/net/firedevops/firemud/common/gamedesign/AuthoredInitialActorCoreProjection.java) checks the retained `GameplayRuleManifest` and `PlayerCreationDescriptor` inputs. The [shared vector resource](../../../services/common-platform-core/src/test/resources/operator/character-create-v1-vectors.json) retains four literal positive preimages and now includes required negative cases; the [focused codec test](../../../services/common-platform-core/src/test/java/net/firedevops/firemud/common/operator/CharacterCreateOperatorActionCodecTest.java) exercises the production decoder against those fixtures and checks additional source contradictions. The current local run and its limits are recorded under [Validation and Proof](#validation-and-proof). This remains local-only receiver support: it does not establish a Game Session producer, authenticated source readback, Entity terminal or owner protections, or route activation, so GR-3.1 remains partial. The [canonical family schema](../../architecture/microservices/entity-management-service/character-create-action-schema.md) owns the contract details.

## Consolidated Implementation Record

### Ownership and Visible World

World Management is authoritative for room identity, location, exits, and occupancy. Entity Management owns room-ground items through room-attached containers and exposes a bounded LOOK-oriented visible-entity listing keyed at minimum by tenant and room instance. That listing is structured for rendering with stable display names and player/NPC/item classification, without exposing internal stats. Game Logic combines those authorities for the player-facing room projection; Game Session owns command/protocol delivery rather than reconstructing entity state.

The live command distinction is intentional: ordinary `LOOK` is room-context prose, while `INV HERE` is the explicit room-ground management view. A room-ground container is shown as one room item, and nested contents are revealed only through `CONTAINER`; they are not expanded into ordinary room prose. Deterministic fixture rooms contain the minimal player/NPC/item data used by the current tests and transcripts. Rich prose, combat/effect annotations, NPC response, localized listening, and broader non-fixture room/entity context are not implemented.

### Item Commands and Service Boundaries

The authenticated live item command surface is `INVENTORY`, `INV HERE`, `GET`, `DROP`, `CONTAINER`, `PUT`, `TAKE`, `EQUIPMENT`, `WEAR`, and `REMOVE`. Game Session routes these through one bounded `ItemCommandHandler` seam to Game Logic; Game Logic performs gameplay-facing query, visibility, selector, and context validation; Entity Management remains authoritative for item, holder, equipment, and container persistence. Hidden inventory containers are implementation-owned rather than directly player-addressable. The current flow carries tenant/game/session/character and room context, and uses World Management room identity where required.

`GET` and `DROP` resolve names, visible refs, container refs, stack refs, and quantities against the appropriate holder surface in Game Logic before delegating a concrete mutation. Successful pickup/drop responses refresh both affected holder views. Structured first-party WebSocket payloads include typed item entries, refs, quantities, descriptions, slots, container context, and an `item_mutation_result` containing the action, mutated item, and source/destination holder context. Telnet and generic WebSocket retain the shared canonical transcript renderer.

Game Session records central `gamesession.command.item.*` invocation/failure metrics tagged by item command type and error, distinguishing player errors such as `ITEM_NOT_FOUND` and `SLOT_INCOMPATIBLE` from backend or validation failures. Inventory command availability is tenant/game policy; slot, body, compatibility, and stackability facts are versioned DML-backed design data rather than a second settings domain.

### Containers, Equipment, and Item Identity

Current status/evidence: Entity Management implements durable container, item-instance, stack, and equipment bindings, with focused transfer, container, stack, and equipment tests. The canonical container-first storage, holder, stack, and body-layout contracts are owned by [Entity Management Runtime and Data](../../architecture/microservices/entity-management-service/runtime-and-data.md#containment-and-equipment-model); this tracker records only the current partial capability and its proof gaps. Nested-container behavior, complete published body-layout vocabulary, fail-closed publication/runtime validation, and cutover remapping remain unproved.

### Visible References and Stack Semantics

Current status/evidence: stable visible references and holder-local stack behavior are exercised by the focused inventory, container, transfer, and stack tests linked in the capability table above. ### Guarded Transfer and Audit

All live inventory, room-ground, equipment, and container mutations use one shared guarded transfer helper and holder-policy validation. The mutation is a single expected-source-to-destination holder transition on an item instance or stack family, not unrelated remove/add operations. It checks tenant and expected source ownership at mutation time; stale, missing, incompatible, or already-at-destination state fails before holder fields are rewritten. Scheduler or tick serialization is not the duplication defense.

Transfer failures emit canonical warning context including item instance/item identity, expected and current holder, destination, verb/cause, and actor character when available. Successful item-instance and stack-backed transfers write `item_transfer_audits` in the same local transaction boundary as the mutation; failed transfers commit neither the holder change nor an audit row. The target audit and durable-reconciliation contract requires the complete `{tenantId, playableStateNamespaceId, playableStateScope, gameInstanceId}` scope tuple. That complete namespace/scope transfer/effect tuple is a target gap: current `item_transfer_audits` and `EntityMutationEffect` records do not carry it, so the current local transfer/audit implementation does not prove live cross-scope replay or reconciliation. Durable item/equipment/container mutation requests carry attested `sessionId` and durable `effectId`; when present, `effectId` is the explicit audit correlation key. A deterministic fallback correlation key is derived from verb, actor, item, quantity/family, and holder endpoints, but this is not broader replay semantics. Operators use the audit trail for item-duplication investigations, suspicious-transfer analysis, and later invariant checks.

The live transfer contract deliberately rejects an already-moved item by default. It does not infer idempotent success; a caller that needs replay/no-op behavior must provide an explicit replay contract.

### Durable Effects and Replay Guards

Current Game Session implementation persists a stable same-batch `effectKey` and derives `effectId` from `tickBatchId` plus that key (`command:<commandId>`); durable tick staging/replay rejects missing or blank command IDs before effect selection, so the private helper's defensive `command-text:<hash>:slot:<index>` branch is unreachable in the live tick path and is not a no-commandId recovery identity. Same-batch duplicate keys are rejected. Focused replay tests exercise restart drain, ownership-fence checks, stale-executor requeue, and local result mappings (`APPLIED`, `REPLAY_NOOP`, and `REJECTED`); they do not establish canonical cross-service participant-guard identity, effect terminalization, or proof that an ambiguous or rejected attempt cannot be reapplied. The command-linked identity does not establish the accepted effect identity/replay contract, which remains unimplemented and unproved here. Accepted command-plan and root-allocation requirements are defined in [ADR 0183](../../architecture/decisions/adr-0183-deterministic-effect-id-allocation-and-replay-binding.md); implementation and focused proof remain incomplete. See [ADR 0069](../../architecture/decisions/adr-0069-at-least-once-effect-execution-with-one-logical-terminal-outcome.md) for the accepted effect rules and [Transaction Strategies](../../architecture/system-architecture-transactions.md#command-atomicity-and-outcome-aggregation) for participant-guard behavior.

The bounded owner-local replay implementations are: Movement's `effectId`-keyed idempotency service tied to session-context mutation; Entity Management's one mutation replay row per `{tenantId,effectId}` for validated, nonblank effect IDs, with the applied protobuf response for item, equipment, and container mutations, plus a separate `ApplyActorCondition` path that uses the temporary `sourceId` adapter. The focused Entity proof is limited to those nonblank-ID item/equipment/container and actor-condition paths: Entity mutation paths that accept blank effect IDs can bypass the replay table, while `ApplyActorCondition` rejects blank source identity before replay lookup. The Entity replay record also does not bind canonical target/scope/fence/request-digest evidence, so operation-only reuse is not proven fail-closed. Game Session has local replay records per `{tenantId,sessionId,effectId}` for `SAY`, `WHISPER`, `TELL`, `AFK`, `BLOCK`, and the bounded authored-action path, re-delivering actor-facing output without re-invoking the mutation handler. Social Groups persists `effect_id` with a `{tenantId,effectId}` uniqueness boundary and can return the stored chat DTO for a sequential duplicate whose first row was already committed; concurrent first-apply replay remains unproved. These are implementation boundaries and proof status, not the target participant-guard contract.

The shared execution helper currently keeps Game Session communication, AFK, action-state, and authored-action replay lookup/save/delivery behavior aligned. Existing metrics distinguish first-apply and replay/no-op outcomes through `gamesession.durable.effect.execution{command,effect_status,gameplay_result}` and Entity Management mutation execution metrics. This remains a bounded adoption set rather than a universal cross-service guard table; broader participant-guard propagation and cross-service replay proof remain incomplete. The target root/participant binding and outcome aggregation are owned by [ADR 0069](../../architecture/decisions/adr-0069-at-least-once-effect-execution-with-one-logical-terminal-outcome.md) and [Transaction Strategies](../../architecture/system-architecture-transactions.md#command-atomicity-and-outcome-aggregation).

Replay-status qualification: the GR-3.2 implementation and verification entries below describe the nonblank-`effectId` item/equipment/container replay-ledger path only. Those mutation requests still have a blank-ID compatibility direct-execution path that bypasses the Entity replay ledger. `ApplyActorCondition` is a separate exception: it has no dedicated `effectId`; its temporary adapter carries the durable ID in `sourceId`, which Entity uses as the replay key and source provenance. Existing replay tests therefore do not establish safe replay protection for every mutation ingress; focused proof and full-ingress replay readiness remain blocked until each ingress has a valid trusted replay identity.

### Actor State and Typed Effects

Current actor-state status/evidence: Entity Management provides the bounded evaluator and `STATUS` transport path, with focused tests covering evaluator composition, actor-condition mutation, and Game Session/Game Logic transport. Namespace-qualified actor-state persistence and isolation remain unproved because the live schema uses legacy `playable_state_key`; the current `QueryActorState` adapter also retains flat fields and legacy `session_attestation` carriage, so it does not prove the target delegated-context boundary. The canonical actor-state and execution-context contracts remain in [Entity Runtime and Data](../../architecture/microservices/entity-management-service/runtime-and-data.md#implementation-status) and [Gameplay Player Execution Context](../../architecture/system-architecture-authentication.md#gameplay-player-execution-context-contract-normative); this tracker records status and proof gaps only.

The first `EffectEvaluationService`/`DefaultEffectEvaluationService` is in-process and deterministic. It supports additive and multiplicative numeric modifiers, min/max clamps, granted flags, granted conditions, scoped metadata, and source provenance. Modifiers are ordered by priority and source metadata; numeric evaluation runs base, additive, multiplicative, minimum clamp, maximum clamp, then granted-state projection. Persisted effect payloads require a `modifiers` array, registered operation, identifier `target_key`, numeric `value`, optional identifier scopes, and optional integer priority; legacy aliases and implicit values are rejected.

Equipped item payloads and active condition payloads contribute through this evaluator. `ApplyActorCondition` is gameplay-attested, validates nonblank source identity and canonical effect JSON before replay lookup, and is routed by Game Logic. Its current request has no dedicated `effectId`: the current temporary adapter writes the durable effect id into `sourceId`, Game Logic forwards it, and Entity Management interprets that same `sourceId` as the `{tenantId, effectId}` replay key while also persisting it as source provenance. This overloaded `sourceId` behavior is an implementation adapter, not the canonical replay contract, and its tests must preserve that limitation explicitly. Separating replay identity into a dedicated `effectId` from authored/source provenance remains a contract gap before other condition producers can safely reuse one source across multiple applications. Entity Management removes elapsed transient states through its scheduled expiry job. Game Session no longer infers state mutation from broad tags such as `COMBAT`; only explicitly declared behavior routes to a concrete mutation.

The first equipment proof covers passive contributions such as `armour_value` or resistances. The first actor-state proof covers an effective resource composed from a persisted override, a non-expired condition, and an equipped-item contribution in Entity Management. A separate transport proof covers `STATUS` through the live Game Session and Game Logic applications to the Entity Management gRPC contract; its fixture controls the Entity Management response and is not evaluator proof.

### Authored Action Admission and Execution

The live authored-action path resolves aliases, direct HELP topics, dispatch validation, and command-result action metadata from the release bundle admitted for the game instance. Before enqueue, the durable command snapshots the admitted release-bundle id, version id, canonical command id, declared effects, and gameplay tenant/game/character identity. Execution validates that immutable declaration and current gameplay identity before replay lookup.

The bounded v1 executor accepts only a self-targeted `APPLY_ACTION_STATE` declaration. Runtime admission queues only definitions with that single supported effect; effectless or future multi-effect definitions remain discoverable but return the canonical execution-unavailable result without durable enqueue. Missing, mismatched, malformed, or unsupported snapshots fail closed before replay or script publication. The action-state adapter forwards the declared effect payload to Game Logic rather than substituting a built-in `BLOCK` payload. Authored-action replay participates in the durable command `effectId` contract and duplicate execution returns the stored/replay outcome without invoking the handler twice.

### Unified Actor and Combat Boundary

No general persisted actor runtime model is implemented. `WHO` remains player-presence oriented; gods/admins are role and presentation overlays on player presence. The locked implementation direction is one persisted opaque actor core shared by `PLAYER` and `NPC`, with Entity Management owning actor identity and durable actor state, World Management owning location and occupancy, Game Session owning ephemeral session attachment and player-facing presence projection, Game Logic resolving gameplay targets and effects against actor identity, and Account Service owning account identity and authorization inputs. Presence and disposition are separate; disconnect does not defeat an actor. The future core has no universal targetability or visibility fields: release-pinned observation and targeting policies evaluate optional authored facts. Its DML-authored disposition owns base action admission; conditions and equipment can add restrictions but cannot grant behavior that the disposition denies or become competing lifecycle owners.

Damage, mitigation, resistances, combat timing, body-region resolution, defeat, corpses, loot, respawn, and revival are not implemented. Resource adjustment has no implicit death, victory, corpse, loot, respawn, or revival meaning. Future combat must consume the shared actor/state/effect model and keep combat authority out of Game Session.
