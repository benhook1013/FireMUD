# Automation and Scheduler Runtime

## Target-State Authority

This is a non-normative implementation tracker for automation and scheduler runtime. Canonical target-state automation, scheduling, execution, handoff, readiness, and runtime/operator contracts remain authoritative in [design/architecture](../../architecture/README.md) and the linked design sources below; this tracker owns current implementation status, proof evidence, gaps, and handoffs, not normative design.

## Current Status

The bounded implementation slices recorded here are complete at their stated boundaries. This tracker is the permanent reader-facing implementation record for the live automation ingress, scheduling, execution, handoff, readiness, and runtime/operator projection contracts.

Current residual: the live NPC formation REST family is public/unauthenticated and accepts caller-supplied tenant selectors without proving leader/member NPC ownership. Formation behavior remains `partial`; existing controller/service tests are happy-path proof only. Route removal or exact internal/admin tenant binding, Entity-owned NPC ownership checks, and unauthenticated/cross-tenant negative proof remain open.

The current Automation queue reset/rebuild/resume path is unavailable and must fail closed regardless of the observed status mix; a non-atomic status preflight cannot authorize the target PENDING-only workflow. The owner-reconciled target recovery and its proof remain outstanding.

Terminal cleanup now disposes aged child audit and handoff evidence before deleting each parent `script_work_items` row in the same transaction; the non-cascading foreign keys therefore cannot strand the parent cleanup on a constraint violation. The configured parent retention windows remain the live evidence horizon, and repository proof covers the child-first SQL order; a real PostgreSQL migration/retention run remains unclaimed.

The `xmax = 0` insert discriminator used by the `ScriptWorkItem` and `ScriptEventAudit` repositories remains without PostgreSQL integration proof; current unit/mock evidence does not establish INSERT-versus-conflict-update behavior against PostgreSQL.

### Script-transition reconciliation

The accepted transition family does not promote the current implementation to complete. Exact patch/epoch propagation is present through the live instance-bound admission, schedule, replay, and timer/audit paths; focused exact-pin rollout proof is carried by the immediate stacked proof follow-up. Remote handoff source/target dual-tuple propagation and binding, projection freshness, complete command identity, and final-effect fencing remain implementation/proof gaps; current Automation pin projections and rollout rows are diagnostic/read-model state and cannot authorize an operation. Automation-owned plugin activation/lifecycle fences are not yet persisted and propagated through current plugin work, status, scheduler, handoff, retry, replay, and recovery surfaces, and same-version re-enable/same-epoch lifecycle proof remains open. In particular, the current scheduler `TimerFiringCandidate` has no captured `pluginActivationEpoch`, so plugin-owned `scheduleCandidateId` and derived `scriptEventId` cannot yet change on disable/re-enable; the scheduler/service model must add and persist that captured epoch before the target identity rule is live. Automation's target `failureGeneration` is likewise not yet persisted or propagated through dead-letter readback, recovery results, claims, and success evidence. Current properties still lack the target upper-bound validation for `SCRIPT_PIN_PROJECTION_STALE_THRESHOLD_MS`; the [Automation & Scripting configuration contract](../../architecture/microservices/automation-scripting-service/configuration.md#service-specific-variables) owns the numeric range and freshness-SLO relationship. These gaps remain separate from the region/region-epoch and plugin-binding fences tracked below; those fences do not substitute for final exact-epoch enforcement.

The target local consequences are tracked against [ADR 0103](../../architecture/decisions/adr-0103-single-authority-script-pins-with-exact-version-execution.md), [ADR 0106](../../architecture/decisions/adr-0106-epoch-fenced-script-rollback-without-routine-gameplay-pause.md), [ADR 0107](../../architecture/decisions/adr-0107-stage-aware-script-dead-letter-recovery.md), [ADR 0108](../../architecture/decisions/adr-0108-no-degraded-script-admission-without-authoritative-pin.md), [ADR 0109](../../architecture/decisions/adr-0109-game-session-owned-script-rollout-history.md), [ADR 0110](../../architecture/decisions/adr-0110-explicit-opt-in-schedule-continuity-across-script-transitions.md), [ADR 0111](../../architecture/decisions/adr-0111-unified-dsl-with-distinct-embedded-script-and-plugin-lifecycles.md), and [ADR 0173](../../architecture/decisions/adr-0173-registry-classified-reload-admission-policy.md). Stage-aware dead-letter recovery and no-degraded-admission behavior remain canonical system-contract obligations without a claim that the current aggregate replay or every admission boundary proves them.

### Packet 4 accepted-decision consequences

- [ADR 0114](../../architecture/decisions/adr-0114-command-plan-preview-dry-run-isolation.md) makes the initial dry-run a non-committing command-plan preview with explicit fenced inputs or fixtures. This is distinct from the current `TriggerScriptEvent(isDryRun=true)` execution, which has separate live-test rate, capacity, and bounded lease-TTL controls described below; those controls do not establish the ADR 0114 preview boundary. ADR 0114 defines no numeric capacity, concurrency, or TTL, and isolated preview capacity remains unproved, so `AS-1.2`/`AS-1.6` remain partial until live work-item/queue exclusion and exact result provenance are also proven.
- [ADR 0115](../../architecture/decisions/adr-0115-manifest-complete-onload-readiness-without-durable-game-initialization.md) makes the immutable expected handler set, including empty sets, and monotonic publication sequence part of readiness. Manifest completeness, late-completion fencing, and durable-init separation remain `AS-1.1`/`AS-1.2` gaps.
- [ADR 0116](../../architecture/decisions/adr-0116-routine-component-migration-and-explicit-emergency-revocation.md) separates routine `UNSAFE` migration blocking from explicit emergency containment. Component policy/dependency discovery, security authority, worker fencing, scoped pause, and focused proof remain `AS-1.2`/`AS-1.6` gaps.
- [ADR 0117](../../architecture/decisions/adr-0117-producer-owned-event-schemas-with-one-materialized-catalogue.md) keeps event meaning with producers while Automation materializes one complete catalogue. Producer-manifest discovery, revision/digest materialization, compatibility, retention, and convergence proof remain `AS-1.1` gaps.
- [ADR 0118](../../architecture/decisions/adr-0118-preselected-exclusive-handlers-and-durable-fanout-ordering.md) requires complete-set preselection, explicit exclusive selection, durable handler sequence, and ordered application. The current `AS-1.1`/`AS-1.5` implementation and proof do not yet carry or enforce that sequence.

[ADR 0119](../../architecture/decisions/adr-0119-epoch-fenced-per-instance-plugin-activation.md) and [ADR 0120](../../architecture/decisions/adr-0120-owner-read-first-control-plane-notifications.md) now record accepted target authority for per-instance activation fencing and owner-read-first control-plane notifications; activation epochs, lifecycle revisions, lexicographic projections/final fences, owner histories/cursors, durable acknowledgements, recovery, and focused proof remain gaps. They do not upgrade capability states.

Existing scheduler/plugin cleanup and recovery evidence remains partial; no all-owner acknowledgement proof is claimed.
- `AS-1.6`: [ADR 0128](../../architecture/decisions/adr-0128-game-design-plugin-trust-provenance.md) is limited to Game Design's service-local accepted provenance record under [ADR 0111](../../architecture/decisions/adr-0111-unified-dsl-with-distinct-embedded-script-and-plugin-lifecycles.md). Existing signed intake and activation caveats remain, and this record is not platform trust or runtime authorization proof.

These links add decision provenance only; they do not upgrade Automation implementation or verification state.

## Final Reviewed-Import Status and Proof Gaps

- `AS-1.6`: [ADR 0166](../../architecture/decisions/adr-0166-attributable-script-breakers-and-tenant-first-fairness.md) is applied as decision provenance. Current quota and tier budgets are partial foundations; breaker authority, audited reset, general priority scheduling, priority-sensitive queue-delay/starvation emission, the ADR 0166 cluster-ceiling capability (distinct from the current dry-run `SCRIPT_TEST_MAX_CLUSTER_CONCURRENCY` capacity), concurrency policy, and focused fairness proof remain gaps.
- `AS-1.1`: [ADR 0172](../../architecture/decisions/adr-0172-parent-event-and-frozen-handler-execution-identity.md) supersedes ADR 0001. Current ingress, storage, retry, scheduler, audit, and handoff convergence and focused proof remain incomplete.
- `AS-1.5`: Human review retained [ADR 0002](../../architecture/decisions/adr-0002-automation-handoff-reliability-and-success-semantics.md). Current duplicate recovery and child-dispatch/readback proof remain incomplete, so this capability stays partial.
- `AS-1.6`: [ADR 0173](../../architecture/decisions/adr-0173-registry-classified-reload-admission-policy.md) supersedes ADR 0003. Current implementation lacks the registry-classified `RELOADING`/`retryAfterMs` behavior, null-safe policy identity and atomic first-claim convergence, and `REJECT_VISIBLE`/`DURABLE_RETRY`/`SKIP_RECONCILE` producer behavior; existing readiness/plugin/admission tests do not prove the transient-denial retry lifecycle. These are implementation and proof gaps; ADR 0173 owns the normative reload policy semantics.

This records implementation and proof gaps; it does not upgrade the runtime slice.

## Consolidated Implementation Record

### Domain Boundary and Ownership

The `10.x` family is the canonical implementation home for runtime event ingress, scheduler/timer ownership, execution policy, Automation-to-Game-Session handoff, and operator visibility. Its child slices are complete at their current bounded boundaries; the parent remains a taxonomy, not a claim that every future scripting capability exists. Design-time publication, versioning, asset attestation, and publication compatibility remain Game Design/`08.4` concerns, while runtime readiness, activation, execution, and convergence remain separate facts.

Automation Scripting owns the event manifest and ingress, durable bindings/work items/audits, schedules, runtime activation, quotas, readiness, handoff orchestration, and runtime control-plane reads. Game Session owns admitted gameplay command execution, current runtime ownership, local command targets, durable remote follow-ups, and the canonical pin/runtime-state reads. Game Design owns script definitions and publication truth. Logging & Admin exposes tenant-guarded operator reads over those canonical service contracts. Temporal owns long-lived publish and script-patch readiness workflow execution; it is not a second operator state model. Resulting gameplay effects remain owned by Game Session and other domain services rather than by a scripting-owned mutation shortcut.

### Manifest-Backed Event Ingress

Script event ingress is one application-level runtime contract. The checked-in built-in event manifest is the current implementation source for producer, Trigger Identity, `payloadSchemaRef`, owner-specific input requirements, `quotaClass`, and allowed binding scopes; target semantic authority belongs to producer-owned manifests, with the Automation catalogue as the one materialized enforcement authority. Registry read APIs expose the definitions used by current admission. Script-definition writes reject unknown built-in events and illegal binding scopes before runtime work exists. Ingress admission, ingress audit, handler resolution, handler audit, durable work-item state, and the sealed handler input manifest are separate truths; one admitted event may produce mixed handler outcomes without making the ingress response ambiguous.

The target contract returns successfully produced ingress decisions, retry hints, and handler outcomes as typed application-level results; a failure that prevents the RPC from producing a domain result uses canonical non-`OK` transport status under the shared gRPC outcome/transport classification. Current per-RPC handlers may still use response-level `ErrorDetail`, and migration plus focused proof against that target classification remain incomplete.

Ingress enforces the registry producer, identity, and owner-input requirements before durable handler work is created. Automation must seal the target owner-versioned input manifest per resolved handler; the current token-bearing request is narrower and does not establish that proof.

The live built-in producer surface is broad and explicit. `onCommand` is published for session-enqueued durable commands, durable `SAY`/`WHISPER`/`TELL`/`AFK`, successful direct `INVENTORY`/`EQUIPMENT`/`CONTAINER`, `WHO`, `FRIENDS`, gameplay-scoped `HELP`, gameplay-scoped `WORLDS`/`REALMS`/`CHARS`, gameplay-scoped authored actions, direct `PLAY` and `LOGOUT`, Automation handoff, and remote target-side gameplay execution. `onSpawn` is emitted for fresh `PLAY`; `onEnterRegion` and `onLeaveRegion` are emitted for movement and for deliberate logout, transport loss, and takeover; scheduler-owned `onInterval` and wall-clock `onTimerExpire` are live; tenant-readiness `onLoad` is materialized from `NotifyScriptVersionUpdate`. Disconnect lifecycle ids preserve `logout:<sessionId>:<gameInstanceId>:<characterId>` for deliberate logout and use deterministic `disconnect:<reason>:<sessionId>:<gameInstanceId>:<characterId>` ids for forced exits, with producer-owned `exitReason` metadata.

Built-in payload parity is enforced for the already-live `onCommand`, `onSpawn`, `onEnterRegion`, `onLeaveRegion`, `onTimerExpire`, and `onInterval` families. Malformed, missing, or contradictory required fields fail closed. `onCommand` may carry additive `actionCategory` and `actionTags[]` enrichment resolved from the canonical command registry, while ingress requires the documented minimum identity fields. Gameplay-originated events carry `worldSlug`, `realmSlug`, `pointerVersion`, and `playableStateScope` as first-class routing identity together with `regionId` and `regionEpoch`; Game Session-sourced events fail closed if that admitted bundle is incomplete or if the region scope is stale (`runtime_region_scope_advanced`) before durable work is materialized.

Handler resolution supports real `COMMAND_ALIAS`, `ACTION_CATEGORY`, and `ACTION_TAG` binding scopes using normalized command-classification truth. Plugin-owned handlers resolve from the enabled plugin-version map for the current runtime scope, not optional request `pluginId`/`pluginVersionId` or publication-shaped assumptions. Resolved plugin ownership is persisted on work items and handler-audit rows; dead-letter replay prefers that per-handler ownership and only uses ingress-audit plugin metadata for older rows.

Queued player commands persist `targetEntityId`, `regionId`, `regionEpoch`, and the admitted routing bundle on the staged `GameplayCommand` row. `publishCommandEvent(...)` prefers that persisted authority, and live durable execution can republish `onCommand` after replay gates; replay/no-op execution stays silent and does not recalculate a newer trigger identity from drifted runtime state.

### Durable Work and Runtime Activation

Matched handlers materialize durable `script_work_items` with event, handler, source, plugin, routing, scope, quota, and admission provenance. Ordinary work can be claimed through the explicit `PENDING_EVALUATION` to `EVALUATING` transition, evaluated from persisted script definitions, canceled durably for patch/plugin rollback or drain, and dead-lettered/replayed under compatibility gates. Tenant-readiness `onLoad` instead follows readiness-owner terminalization and is not supported through generic replay. Handler-scoped `script_event_audit` rows remain distinct from ingress audit and record cancellation and terminal outcomes.

Current status: `VersionServiceImpl.publishScriptPatchVersion` in Game Design calls `AutomationScriptingClient.notifyScriptVersionUpdate`, which sends `NotifyScriptVersionUpdate` with an empty `affectedScripts` list. Automation's `ScriptVersionServiceImpl.notifyUpdate` returns before creating readiness state and skips the conditional `script-patch-readiness` Temporal tracking hook, so normal script-patch publication currently establishes neither a readiness candidate nor a workflow. Focused unit coverage proves the direct non-empty notification delegation/hook path and separately proves that an empty list skips that hook; it does not prove end-to-end readiness for normal publication. The non-empty path resolves only definitions found by name, can mark readiness from that subset, swallows notification/response failures, and can reuse/latest-select across changed base or release identities; these gaps remain. Target ownership and the expected-handler/terminal-outcome contract are canonical in [ADR 0115](../../architecture/decisions/adr-0115-manifest-complete-onload-readiness-without-durable-game-initialization.md).

Current gaps remain: `ReplayDeadLetteredWorkItems` can requeue `onLoad`, stale `ONLOAD_RUNNING` work remains unreclaimed, and focused proof for readiness-owner recovery is missing. Target ownership, recovery, terminalization, and identity rules are defined by [ADR 0115](../../architecture/decisions/adr-0115-manifest-complete-onload-readiness-without-durable-game-initialization.md) and the [scripting normative contract tables](../../architecture/system-architecture-scripting-normative-contract-tables.md#table-2-script_event_audit-stages-and-outcomes).

Publish workflow state is also exposed through canonical control-plane reads; Temporal workflow identity does not create a parallel operator state model.

Publication truth, readiness truth, activation truth, and append-only runtime chronology remain separately readable. Plugin runtime state is Automation-owned and records activation, disable, drain, policy reconciliation, request/actor visibility, policy-check time/staleness, and observed Game Session runtime scope. Activation preflight consults Game Design publication and Game Session instance metadata and fails closed for revoked signer evidence, blocked or missing component policy, unsupported built-in command-alias bindings, instance-scoped binding conflicts, stale publication/policy evidence, or stale observed region/epoch. Report-only policy decisions remain activatable. Enabled states are rechecked by scheduled policy reconciliation and disabled when evidence becomes fail-closed; append-only plugin runtime events retain previous/active publication cross-links.

Game Design plugin publication reads expose tenant-scoped version statuses, durable `SIGNATURE_VERIFIED` and `VALIDATION_FAILED_DESIGN` states with `statusReason`, base-version attestation, signer/component-policy gates, and distribution-manifest export. Publication and runtime activation currently compare `abilitySchemaDigest` against Automation's aggregate participant digest rather than a dedicated Game Logic-owned release-attested ability-schema digest, so exact ability-schema enforcement remains unproved; `baseVersionId` enforcement is live.

Plugin runtime status retains the last observed Game Session runtime scope and reuses its stored `runtimeRegionId` for later region-aware runtime-state reads rather than collapsing the selector to `{tenantId, gameInstanceId}`.

### Scheduler and Timer Ownership

The first scheduler ownership model is live, instance-aware, durable, and fenced. `NotifyScriptVersionUpdate` persists patch-scoped `script_schedule_definitions` from compiled script payloads, keyed by `scheduleDefinitionId` with cadence/unit metadata and duplicate detection. Observed pinned patches materialize `script_schedule_instances` keyed by tenant, game instance, plugin ownership metadata, binding target identity, and schedule definition; plugin-owned schedules retain only the currently enabled plugin version from the runtime registry.

Game Session advances durable `lastCommittedTickId` after successful tick cycles and publishes `ObserveRuntimeTickProgress` with `(tenantId, gameInstanceId, regionId, regionEpoch, tickId)`. Scheduler rows and timer work preserve the admitted routing bundle, pin, runtime progress, current owned runtime scope, and schedule identity. Due tick candidates and wall-clock timers use deterministic mixed ordering; catch-up selection is round-robin across schedule identities, capped by `script.scheduler.max-catch-up-firings-per-observation`. Truncated candidates produce bounded `catch_up_truncated` audit rows, while due work enters the same durable outbox/audit/queue path as other events. The accepted `lane` (`actor_action` or `passive_effect`) and bounded `cost_class` fields are target-state gaps: current scheduler rows and timer work do not yet preserve or enforce them. A timer or automation source that emits a gameplay command remains `actor_action`; actor-generated consequences, passive pulses, inbound/remote effects, and retries of already-admitted effects use `passive_effect` and avoid consuming the target actor slot.

Runtime-scope changes fence tick and wall-clock due points before work is minted. Stale due points are dropped with `runtime_scope_changed`, the `automation_script_timer_runtime_fence_dropped_total` metric, and old-scope audit identity rather than being re-emitted under a new region epoch. Emitted and skipped rows retain the current routing bundle. Timer audit reads expose due-point identity, plugin provenance, routing, and persisted-versus-skipped outcomes. The ownership model is explicitly best effort and does not imply stronger timer guarantees; richer scheduler dashboards and a later leader-checkpoint substrate are outside this first model.

Tick-aligned materialization derives the next future `nextDueTickId`. Scheduler materialization and plugin activation preflight ignore enabled plugin rows whose persisted observed runtime scope differs from current Game Session ownership, with exact `runtimeRegionId` and `runtimeRegionEpoch` checks; scoped plugin-policy convergence uses the same fence.

### Execution Budgets, Quotas, and Isolation

The current execution policy has bounded terminal cleanup, serialized-work-item rejection, total and per-target command ceilings, live `STANDARD_RUNTIME` quota/budget enforcement from persisted work-item source fields, and separate `PUBLISH_READINESS` capacity. The implementation and proof anchors for those claims are recorded in the `AS-1.2` and `AS-1.6` rows in [Capability Status](#capability-status). Artifact-pinned serialized-byte/data-dependent cost metering, deterministic scheduler reservation and deferral, durable full-Trigger-Identity charge records with separate exactly-once markers, fenced/reclaimable capacity leases, and end-to-end lane/cost metadata enforcement remain named gaps. Canonical charge points, reservation behavior, identity fields, lane/cost semantics, metrics, and retention rules remain owned by [Scripting Quotas and Operations](../../architecture/system-architecture-scripting-quotas-and-operations.md), [Scripting Scheduler and Timer Lifecycle](../../architecture/system-architecture-scripting-scheduler-and-timers.md), the [normative contract tables](../../architecture/system-architecture-scripting-normative-contract-tables.md), and [Automation Scripting Service configuration](../../architecture/microservices/automation-scripting-service/configuration.md); this tracker does not restate them.

Quota-denied handlers are audited without creating work items, and budget-denied live work uses `tenant_budget_exceeded`.

For this readiness path, the target `EXECUTING` transition is the execution state of `script_work_items`; the separate patch-readiness projection remains `ONLOAD_RUNNING` until it reaches `READY` or `FAILED`.
For target behavior, this readiness-projection gate is separate from generic dead-letter replay: tenant-readiness `onLoad` is at-most-once, the readiness owner terminalizes stale identities under their original Trigger Identity, and such work is ineligible for target `ReplayDeadLetteredWorkItems`; retry requires a newly published immutable patch. The current generic live replay path can still requeue such rows under its narrower implementation, which is noncanonical drift rather than supported target readiness recovery.
The manifest classifies `onLoad` as `PUBLISH_READINESS`, and every live work item persists its resolved `quotaClass`: `PUBLISH_READINESS` for `onLoad` and `STANDARD_RUNTIME` for ordinary runtime and scheduler work. Ordinary live per-script quota and tenant runtime budget charge only `STANDARD_RUNTIME` work; execution no longer infers readiness policy from `eventType`. Readiness-specific event semantics, including command prohibition, remain event-type semantics. Live `PUBLISH_READINESS` work instead uses a separate readiness capacity reservation/lease under `script.readiness.*` after the persisted work item is claimed and before DSL evaluation; ordinary live script quota and tenant budget are not charged. When that reservation is exhausted, the existing work item has already moved from `PENDING_EVALUATION` to `EVALUATING`, then is durably set to `CANCELED` with `cancelReason=onload_budget_exceeded` and its handler audit updated to `finalStage=ADMISSION`, `finalOutcome=quota_denied`, and `finalReason=onload_budget_exceeded`; no definition evaluation, command, or Game Session handoff occurs. This current sequence is stage/state drift against the normative stage table: the live projection maps that canceled `onLoad` row to `ROLLED_BACK` with the concrete `onload_budget_exceeded` reason, even though readiness has no `ROLLED_BACK` lifecycle state. Target convergence must acquire and deny readiness capacity before the target `EXECUTING` transition so `ADMISSION` remains valid and must record `FAILED` with the concrete `onload_budget_exceeded` reason; the current mapping remains an implementation gap. For instance-bound runtime work items, the live ingress/work-item/audit path now persists and deduplicates the exact `scriptPatchVersion`/`scriptPinEpoch` tuple with paired `scriptPinControlPlaneRequestId` evidence, and resolved plugin handlers include their applicable plugin/binding identity; same-version/different-epoch work cannot reuse an admitted work item. A deliberate new `scriptEventId`/Trigger Identity is for a new business attempt only; stale recovery preserves the original Trigger Identity and `scriptEventId`, records `finalStage=DSL_EVAL`, `finalOutcome=canceled`, and `finalReason=stale_execution_fenced` under the [scripting normative contract tables](../../architecture/system-architecture-scripting-normative-contract-tables.md#table-2-script_event_audit-stages-and-outcomes), and does not re-enter the DSL or create a new step or command-child identity. For tenant-readiness `onLoad`, the pre-instance canonical identity is `<tenantId, scriptId, eventSchemaVersion, scriptPatchVersion, eventType=onLoad, isDryRun, scriptEventId>` and intentionally omits `gameInstanceId`, `playableStateScope`, `regionId`, `regionEpoch`, `entityId`, and `scriptPinEpoch`; instance-bound work instead uses the full applicable Trigger Identity. The remaining target identity gaps are scheduler candidate/timer lifecycle evidence (including plugin activation evidence), remote source/target tuple binding, and final-effect fencing; the target path must retain exact epoch/plugin/binding fields where applicable as those gaps converge. The canceled outbox row remains for the configured terminal-cleanup policy. This current capacity path is not yet the target durable full-identity marker/lease contract.

Dry-run execution has separate tenant/principal per-minute admission limits (`SCRIPT_TEST_MAX_RUNS_PER_MINUTE` and `SCRIPT_TEST_MAX_RUNS_PER_MINUTE_PER_PRINCIPAL`) and separate tenant-local and cluster-wide capacity (`SCRIPT_TEST_MAX_CONCURRENCY` and `SCRIPT_TEST_MAX_CLUSTER_CONCURRENCY`). Dry runs skip live per-script and tenant-budget charging and never hand commands to Game Session. Capacity and policy denials remain distinct from quota and tenant-budget denials. Plugin-trigger admission fails closed when signer/component-policy evidence exceeds `SCRIPT_PLUGIN_POLICY_STALE_THRESHOLD_SECONDS`; pin/rollout projection staleness uses `SCRIPT_PIN_PROJECTION_STALE_THRESHOLD_MS`.

Dry-run capacity exhaustion uses `dry_run_capacity_exhausted` as its durable cancellation and audit reason. Its metric consequence is defined by [normative Table 4](../../architecture/system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix); it is not a live work-item metric outcome. Bounded sandbox execution-policy paths are live, while a broader arbitrary-code sandbox architecture is not.

The evaluator's `recordOutcome` producer now conforms to [normative Table 4](../../architecture/system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix): live terminal work-item outcomes use only `service`, `stage`, `outcome`, `priority`, and bounded `source_class` labels, while dry-run/test executions are excluded from this live family. Existing quota, tenant-budget, and dry-run capacity counter paths are instrumented. Repo-owned alert snippets cover tenant-budget denial spikes, quota-denial ratio, the test-capacity saturation family, and elevated live work-item outcomes; focused metric-schema proof covers the evaluator's producer.

### Canonical Gameplay Handoff

The queue status below is an implementation description, not a recovery authorization: current reset/rebuild/resume is unavailable and must fail closed for every status mix because no atomic PENDING-only/CAS gate exists. The target owner-reconciled workflow remains target-only.

Automation never writes Game Session tick keys directly. The live queue uses instance-aware `automation:queue:{tenantInstanceTag}:*` pointers containing a documented outbox-pointer envelope (`schemaVersion`, `outboxWorkItemId`, and bounded identity metadata); the retired `automation:tick:*` staging path is not part of the live design. Quota counters use `automation:quota:<tenantId>:<scriptId>`. Queue pointers are derived coordination indexes, not work truth: Redis drain deduplicates by `outboxWorkItemId`. Current `rebuildPendingWorkItemIndex` unconditionally selects both statuses and has no stale, owner, or compare-and-set gate, so current queue reset/resume is unavailable and must fail closed; a non-atomic status preflight cannot authorize the safe PENDING-only path. Live scheduled-rebuild containment and bounded duplicate-pointer recovery remain the owner-controlled gap defined in the [scripting runtime rebuild contract](../../architecture/system-architecture-scripting-runtime-execution.md#current-queue-rebuild-concurrency-gap). Health inspection reports `automation_queue_orphaned_entries_total` and `automation_queue_oldest_entry_age_seconds`, and the executor drains pointers for discovery before claiming PostgreSQL work, falling back to durable scanning if Redis discovery fails.

Game Session exposes idempotent `EnqueueAutomationCommandIfAbsent`, persists automation dispatch/work-item correlation on the gameplay command ledger before tick staging, and rejects new handoff when runtime ownership is missing, paused, or on another `regionEpoch`; an already-recorded dispatch still returns duplicate/no-op. Numeric gameplay `targetEntityId` is captured as `characterId` so durable execution can resolve an active session without a caller-owned `sessionId`. Automation assigns a per-command `automationDispatchId`, preserves the full routing bundle, and either uses the local admitted command path or creates a durable remote follow-up for a different target runtime scope. Local scripting commands therefore enter the same Game Session actor-action safety and fairness path as player commands; the durable remote-follow-up delivery envelope is passive at the target and does not consume its actor slot, but if its payload enqueues a gameplay/automation command, that resulting command remains an actor action and cannot receive a same-tick extra root action. The live Game Session enqueue proto remains narrower than the target automation handoff contract: it does not yet carry the full Trigger Identity, `commandOrdinal`, immutable `lane`, or `cost_class`; therefore target dispatch-plus-ordinal identity, lane/cost conflict and digest checks, readback, retry, recovery preservation, and enforcement are not implemented or proven.

The target remote-follow-up contract is owned by [Scripting & Automation: Cross-Service Contracts](../../architecture/system-architecture-scripting-contracts.md#3-version-fencing-rollback-safety). Current `ScriptHandoffEvent` persistence and readback now carry the source `scriptPinEpoch`, but they do not yet bind the source tuple to the target tuple or prove downstream target admission against that binding. Same-instance cross-region work and semantic target `UNPINNED` handling remain subject to that owner contract.

For plugin-originated remote follow-ups, the exact `(pluginId, pluginVersionId, bindingId)` plus captured Automation-owned `(pluginActivationEpoch, lifecycleRevision)` and fresh lifecycle/publication/policy evidence remain independent fences across Automation persistence/handoff and Game Session final execution, separate from Command-Handoff child identity and dedupe. Unavailable, displaced, disabled, revoked, activation-epoch-mismatched, or lifecycle-revision-mismatched evidence fails closed; current plugin-originated follow-up persistence and proof remain partial.

The bounded evaluator supports command-specific `targetEntityId`, structured `commandAlias` plus templated `arguments`, `when`/`unless` conditions, and multi-target `targetEntityIds[]` fan-out with stable command ordinals. **Target state:** durable handoff history is per command and preserves rendered command text, script/plugin/source/dispatch identity, captured plugin `(pluginActivationEpoch, lifecycleRevision)` when applicable, target scope, remote coordinator/follow-up ids, and later Game Session gameplay execution/outcome plus remote-state tail. Target `ListScriptHandoffEvents` directly filters by remote scope, remote ids, origin identity, command id, target entity, routing bundle, and source/state instead of reconstructing history from payloads; its exhaustive plugin-backed output retains the captured lifecycle revision beside the activation epoch. The current handoff storage/proto remains narrower and does not yet prove this target projection.

Handoff contracts fail closed before queue mutation or remote scheduling when payload kind, command text, solo-tick mode, target scope, routing bundle, provenance, dispatch/work-item identity, or source tuple is blank, incomplete, malformed, or contradictory. New handoff/follow-up rows are execution and read authority; payload JSON is only a compatibility fallback for older rows where intentionally required. The same rule applies to remote `trigger_script_event`: the current Game Session event-scope request/row carries `eventType`, `eventSchemaVersion`, `scriptEventId`, `triggerMode`, the owner-specific selector/token required before handler resolution (including `readSnapshotToken` where present), and payload identity; it does not carry a sealed handler-scoped input-manifest reference/digest. In the target flow, Automation must seal and persist that handler-scoped manifest after handler resolution, and downstream command handoff and replay from Automation to Game Session must carry its reference/digest as evaluation provenance. Neither target manifest step is live in the current cross-service payload/storage; `readSnapshotToken` remains owner-scoped only. Execution rejects contradictory row-versus-payload identity, and command status, coordinator, follow-up, and result reads expose/filter those first-class fields directly.

### Runtime and Operator Projection

Automation control-plane reads expose durable patch readiness, dead letters, schedules, timer audit, handoff events, pins, plugin activation/policy, drain status, rollout projections/events, and execution outcomes. Reads cross-link stable Game Design script-patch and plugin publication metadata without collapsing publication, readiness, activation, and runtime chronology into one lifecycle row. Dead-letter listing and controlled replay preserve plugin provenance, gameplay-versus-scheduler source, routing, current owned runtime scope, stale-scope/routing signals, and concrete terminal reasons. Schedule, timer, dead-letter, and handoff reads expose current owned `gameInstanceId`/`regionId`/`regionEpoch` and the current `playableStateScope`, `worldSlug`, `realmSlug`, and `pointerVersion` bundle.

Durable projections include `script_patch_readiness_projections`, `script_patch_pin_projections`, and per-instance `script_patch_instance_rollout_projections`. Patch status preserves legacy/runtime-only rows, publication metadata, projection freshness, and concrete reasons such as `rollback_epoch_advanced`, `runtime_region_scope_advanced`, `onload_commands_not_allowed`, and `tenant_readiness_canceled`. Current rollout reads expose the local non-authoritative projection's observed exact `{scriptPatchVersion, scriptPinEpoch, lastObservedControlPlaneRequestId}` when present, projection age/staleness, publication links, and local `PINNED`, `REPINNED`, and `ROLLED_BACK` statuses/events derived from observed pin/work-item state; these rows/events are implementation drift/diagnostics and do not constitute rollout history. Target rollout reads expose only exact-tuple observed projection state, while Game Session owns append-only transition history. Drain reads expose active execution count, oldest active start, pending cancelable count, read timestamp, and stale status. `SetAutomationAdmissionMode` persists a rollback barrier, advances `admissionEpoch` on rollback pause, rejects new runtime-scoped admissions, and cancels/fences late handoff from older admitted work.
The current Automation admission proto and implementation support optional regional selection but do not deduplicate or fingerprint `SetAutomationAdmissionMode` requests: each call can overwrite `controlPlaneRequestId` metadata, and Set/Get do not expose request identity or outcome for durable successful-acknowledgement readback; the current Get `findOrCreate` path can also persist missing state during a read. Recovery cannot validate current-success identity and must fail closed rather than proceed on drain counts alone; implementation of the owner idempotency/readback contract remains outstanding.

Game Session pin reads remain distinct: `GetPinnedScriptPatchVersion` reports pinned patch provenance, while `GetGameSessionPinConvergence` reports persisted convergence observation and stale signaling; `GetGameInstanceRuntimeState` supplies current ownership and routing. Logging & Admin exposes those canonical reads through tenant-guarded `GET /game-session-pins/{tenantId}/{gameInstanceId}` and `/convergence` routes, with fail-closed tenant/game-instance convergence identity validation. `GetGameplayCommandStatus` and remote runtime reads cross-link script-patch/plugin publication metadata while preserving runtime command and follow-up truth. Operator surfaces consume durable reads and append-only events rather than inferring state from raw tables, logs, or a second scripting state machine.

`GetAutomationPinConvergence` exposes the live observed patch, owner-projected `observed_script_pin_epoch` (`observedScriptPinEpoch`), publication metadata, `last_observed_control_plane_request_id`, observation time, and projection freshness (`projection_as_of_ms`, `projection_lag_ms`, `is_projection_stale`). This is Automation's non-authoritative projection; Game Session remains canonical pin authority. Instance-bound Automation admission, scheduling, runtime replay, and handoff persistence on that path require positive epoch evidence alongside the patch version, so same-version epoch-only repins cannot reuse stale Automation evidence. The distinct-instance remote handoff/follow-up path still lacks retained source epoch and source/target tuple binding, so it remains a downstream implementation/proof gap. Schedule reads distinguish `isPinStale` from `isRuntimeProgressStale`. `GetPluginStatus` exposes `lastPolicyCheckedAtMs`, stale policy evidence, active/pending publication links, and lookup failures; target status additionally exposes Automation's current `pluginActivationEpoch` and `lifecycleRevision` as separate lifecycle-fence evidence, but the live status/work projection and event/readback path do not yet persist or expose either field. `GetPluginPolicyConvergence` currently inspects enabled plugin states with an active version, optionally narrows them to one game instance, filters them against the current runtime region/region-epoch scope when that scope is available, and evaluates current publication, signer, and component-policy metadata. Its response does not carry `pluginActivationEpoch` or `lifecycleRevision` and therefore cannot serve as ADR 0119 lifecycle-fence proof. Game Session also exposes purge controls for not-yet-drained script-patch and plugin-version queue entries.

## Active Gaps

- The evaluator is intentionally bounded to persisted script definitions, structured command emission, simple conditions, and target fan-out. Richer graph/runtime evaluation, compiled artifacts, and a broader sandbox execution seam are not implemented and require a separate runtime slice.
- Script-driven generation and richer procedural population are not established gameplay slices; the current runtime does not provide the broader procedural-population flow described by the target architecture.
- The first scheduler ownership model is complete, but richer scheduler dashboards and a later explicit leader-checkpoint substrate are not part of it. TICK-01 lane declaration, actor-versus-passive selection, cost-class enforcement, and focused proof remain unimplemented; any future timer, retry, remote, or script-generated source must declare its lane and cost class and use the existing selected-work, region-fence, routing, quota, and durable-result contracts.
- The accepted [ADR 0072](../../architecture/decisions/adr-0072-class-specific-timer-durability-and-recovery.md) timer classes, durable resume-window identity, and `SKIP_MISSED`/`COALESCE_ONE` outcomes do not promote the current best-effort scheduler to complete recovery; durable correctness-bearing timer intent and focused recovery proof remain gaps.
- [ADR 0063](../../architecture/decisions/adr-0063-durable-per-dispatch-script-handoff.md) and [ADR 0064](../../architecture/decisions/adr-0064-stage-qualified-script-outcomes.md) require one durable child dispatch per emitted command and separate ingress, handler, and command outcome authorities. Current handoff paths remain bounded/partial where downstream execution-disposition readback and stage-qualified proof are absent.
- [ADR 0075](../../architecture/decisions/adr-0075-depth-cost-and-count-bounds-for-generated-effect-chains.md), [ADR 0076](../../architecture/decisions/adr-0076-failure-class-specific-durable-tick-retries.md), and [ADR 0078](../../architecture/decisions/adr-0078-digest-bound-workflow-and-step-retry-identities.md) are target contracts only: generated-chain budgets, class-specific durable retry owners, and adopter-side digest-conflict guards remain unimplemented or unproved in this runtime.
- Additional publish-adjacent or script-patch rollout Temporalization is not implemented by this tracker. It is justified only by a concrete long-lived workflow need; surviving short synchronous saga seams remain explicitly scoped for the later boundary cleanup.
- Custom event families and future gameplay lifecycle producers do not yet exist as additional implementation families. They must extend the manifest-backed ingress and payload contract rather than create local semantics.
- Cross-service UI composition and broader hosted-observability product work are outside this implementation boundary; the canonical gRPC/control-plane reads, bounded Logging & Admin routes, and repo-owned alert snippets are the implemented operator surfaces.

## To Discuss

No competing target state is currently recorded for manifest-backed ingress, runtime activation, durable work identity, source-aware quotas, readiness capacity, or Game Session handoff. Design discussion is required before choosing a new sandbox/compiled-artifact model, a new persistent workflow family, a custom event class, an adaptive scheduler or leader-checkpoint policy, a new cross-scope producer, or a composed cross-service UI. Those decisions must preserve the existing durable authority, fail-closed provenance, routing-bundle, and separate publication/readiness/activation truths.
