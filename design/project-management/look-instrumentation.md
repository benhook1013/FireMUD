# LOOK Instrumentation and Monitoring

This reference describes the metrics/logs generated by the data-driven `LOOK` pipeline so operators can trace a Telnet/WebSocket request end-to-end.

## Metrics

- `gamesession.command.look.invocations{tenantId="…"}` – incremented every time Game Session receives an authenticated `LOOK`. Tag `tenantId` with the current tenant. Emitted in `LookCommandHandler`.
- `gamesession.command.look.failures{tenantId="…",error="CODE"}` – incremented when Game Session translates a gRPC failure into an `ERROR CODE` response. Supported codes: `ROOM_NOT_FOUND`, `WORLD_UNAVAILABLE`, `ENTITY_UNAVAILABLE`, `LOOK_UNAVAILABLE`, `UNEXPECTED`.
- `game_logic.look.response_time` (histogram/gauge) – measured around `LookAggregationService` so downstream latency is visible.
- Upstream World/Entity metrics (e.g., `worldservice.grpc.calls`, `entityservice.grpc.calls`) should carry the same trace IDs so Prometheus can correlate spikes with the `LOOK` flow.

Define alerts for sustained drops in `gamesession.command.look.invocations` or spikes in failure counts.

## Logs

- **Game Session**: `LookCommandHandler` logs `redis.session.lookup` entries at DEBUG and emits warnings such as `LOG WARN LOOK failed for tenantId=… error=…` whenever it maps a gRPC error to a protocol response.
- **Game Logic**: `LookAggregationService` logs `Rendered LOOK text` at DEBUG with the canonical text produced by `LookResultRenderer`. When downstream calls fail, the `StatusRuntimeException` message is rewritten to include `WorldManagement` or `EntityManagement` so it is human-readable.
- Additional INFO-level logs from Game Logic should correlate `LookResult` objects with their rendered text so smoke transcripts can be reproduced manually.

## Correlation & Tracing

- Use the shared tracing context (trace ID/meter tags) emitted by the Micrometer interceptors to connect drops in `gamesession.command.look.*` with issues in Game Logic or World/Entity services.
- For Telnet smoke tests, capture the Redis `SessionContext` identifiers and use them as log filters to group repeated `LOOK` invocations across replays.

## Operational Guidance

- When a `LOOK` request fails, consult `gamesession.command.look.failures` to determine the tenant and error code, then follow the log chain: Game Session warning → Game Logic warning → downstream stack trace.
- Use the transcripts stored under `design/project-management/smoke-tests/look/` to validate manual runs match the automation and to tune `LookResultRenderer` formatting.

## Regression verification

- Run `./gradlew crossServiceTest` to exercise the WebSocket and Telnet regression suites; they emit the `gamesession.command.look.*` meters and `Rendered LOOK text` logs described above so the automation also validates instrumentation coverage.
- The cross-service target captures the same metrics/log tags documented here, making it easy to trace automation failures back to the dashboards or transcripts referenced earlier.
