# LOOK Instrumentation and Monitoring

This reference describes the metrics/logs generated by the data-driven `LOOK` pipeline so operators can trace a Telnet/WebSocket request end-to-end.

## Target-State Ownership

Game Session owns the player-facing `LOOK` outcome, bounded `gamesession.command.look.*` metrics, and the correlation fields needed to investigate a failure. Game Logic owns the structured `LookResult` and typed failure boundary; World and Entity remain the sources of their participant facts and failure attribution. Cross-service diagnostics may enrich the investigation but do not replace the player-visible response or metric/error-code fallback.

## Implementation Status

The metrics and logs below describe the current bounded implementation. Structured Game Logic and Game Session diagnostics are optional best-effort enrichment; the guaranteed failure fallback is the Game Session error response plus the bounded `gamesession.command.look.failures{error="<CODE>"}` metric and its request correlation context. No cross-service proof claim depends on an optional diagnostic record.

## Metrics

- `gamesession.command.look.invocations` — incremented every time Game Session receives an authenticated `LOOK`. Emitted in `LookCommandHandler`.
- `gamesession.command.look.failures{error="<CODE>"}` — incremented when Game Session translates a gRPC failure into an `ERROR CODE` response. Supported codes: `ROOM_NOT_FOUND`, `WORLD_UNAVAILABLE`, `ENTITY_UNAVAILABLE`, `LOOK_UNAVAILABLE`, `UNEXPECTED`.
- `game_logic.look.response_time` (histogram/gauge) — measured around `LookAggregationService` so downstream latency is visible.
- `gamesession.command.communication.invocations{type="<type>"}` — incremented when Game Session routes a communication command through `CommunicationCommandHandler`, with `type` drawn from bounded command types such as `say`, `whisper`, and `tell`.
- `gamesession.command.communication.failures{type="<type>",error="<CODE>"}` — incremented when Game Logic or Social/Groups reports a delivery failure (`PERMISSION_DENIED`, `UNAVAILABLE`, etc.) so telemetry can diagnose why clients see `ERROR COMMUNICATION_NOT_DELIVERED`.
- `gamesession.command.say.invocations`, `gamesession.command.whisper.invocations`, and `gamesession.command.tell.invocations` — bounded per-command compatibility counters for the current communication capability.

Define alerts for sustained drops in `gamesession.command.look.invocations` or spikes in failure counts.

## Logs and proof

- **Game Logic**: `LookAggregationService` is the structured-result boundary. Optional diagnostics may record the composed `LookResult` and typed failure outcomes, while downstream gRPC failures retain `WorldManagement` or `EntityManagement` source labels. The current `LookResultRenderer` `Rendered LOOK text` DEBUG/fixture path remains local diagnostic evidence only; it does not transfer player-facing renderer ownership to Game Logic or constitute automated cross-service proof.
- **Game Session**: `LookCommandHandler` logs `redis.session.lookup` entries at DEBUG, maps accepted outcomes to compact versioned `PlayerOutput`, and emits warnings such as `LOG WARN LOOK failed for tenantId=<tenantId> error=<ERROR>` whenever it maps a gRPC error to a protocol response. Optional diagnostics may record the `PlayerOutput` and deterministic text projection before delivery; automated cross-service proof remains the player-visible response and transport continuity assertions.

## Correlation & Tracing

- Use the shared tracing context and structured log fields emitted by the request/gRPC interceptors to connect drops in `gamesession.command.look.*` with issues in Game Logic or World/Entity services.
- For Telnet smoke tests, capture Redis `SessionContext` identifiers and use them as log filters to group repeated `LOOK` invocations across replays.

## Operational Guidance

- When a `LOOK` request fails, use the player-visible error and `gamesession.command.look.failures` as the guaranteed classification, then use structured logs with `tenantId`, `gameInstanceId`, `characterId`, and `traceId` when available to enrich the investigation. The optional chain is Game Session warning -> Game Logic typed failure diagnostic -> downstream stack trace; absence of those diagnostics does not remove the metric/error-code fallback.
- Use local or PR-attached transcripts from manual runs to validate that current behavior matches the documented `LOOK` contract and to tune the Game Session deterministic text projection. The local Game Logic `LookResultRenderer` remains useful for fixture/diagnostic comparison only.

## Regression verification

- Run `./gradlew crossServiceTest` to exercise the WebSocket and Telnet regression suites; they emit the `gamesession.command.look.*` meters and retain the canonical player-visible transcript proof for both transports. The controlled transport-continuity assertion is currently WebSocket-only; Telnet continuity/failure proof remains future coverage. Optional structured-result/`PlayerOutput` diagnostics may be collected during those runs but are not automated cross-service proof.
- The cross-service target captures the same metrics/log tags documented here for operational diagnosis, while its end-to-end assertions retain the canonical player-visible text projection for both transports.
