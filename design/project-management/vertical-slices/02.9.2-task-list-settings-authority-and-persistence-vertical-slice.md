# Settings Authority and Persistence Vertical Slice Task List

## Goal and Status

Goal: implement the first shared persisted settings authority for the already-surfaced pre-`06` domains so tenant/game behavior settings stop living only as service-local property seams and ad hoc file/env overrides. Status: planned.

This slice follows `02.9`. It should stay bounded: one authoritative read/write ownership model for the current surfaced domains, not a general distributed config platform.

## Scope

- Shared persisted settings ownership for:
  - `reconnection`
  - `communication`
  - `presentation`
  - `movement`
  - `worldTopology`
- Database storage for tenant/game-scoped overrides
- Canonical service/API ownership for settings reads and writes
- Migration path away from service-local-only gameplay settings

## Key Tasks

- [ ] Decide the owning authority for tenant/game behavioral settings, likely Game Design or an equivalent settings authority surface.
- [ ] Define the persisted settings data model for the currently surfaced domains.
- [ ] Add the first storage and service/API contract for reading and writing tenant/game settings overrides.
- [ ] Keep operator/bootstrap settings separate from tenant/game behavioral settings rather than collapsing them into one table or blob.
- [ ] Ensure settings domains remain domain-oriented rather than action-specific.
- [ ] Wire the first bounded runtime consumers to read persisted overrides through that authority instead of only from service-local config.

## Tests

- [ ] Add persistence/API tests for the first shared settings authority.
- [ ] Add focused cross-service tests proving one surfaced domain resolves tenant/game overrides through the shared authority.

## Notes

- This slice is about ownership and persistence first.
- It does not need to solve every cache or hot-reload concern before the authority exists.
