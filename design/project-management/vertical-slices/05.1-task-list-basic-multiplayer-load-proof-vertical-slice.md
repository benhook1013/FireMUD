# Basic Multiplayer Load Proof Vertical Slice Task List

## Goal and Status

Goal: add the first small but real multiplayer/load proof so FireMUD demonstrates that multiple players can log in, enter the game, and perform basic gameplay actions concurrently against the real service stack instead of only through single-user happy-path tests. Status: planned.

This slice is intentionally narrow. It is not a full performance program and it is not meant to prove final scalability. It exists to validate the first meaningful concurrent gameplay path with real services, real Redis/database state, and multiple simultaneous clients.

The initial target is deliberately small:

- around 10 concurrent players;
- real `LOGIN` -> `PLAY` -> `LOOK`;
- optional bounded follow-up actions such as one `SAY` burst or one movement step;
- enough assertions to prove multiplayer correctness and expose obvious coordination or shared-state bugs early.

## 1. Test Scope and Success Criteria

- [ ] Define one canonical first-pass multiplayer scenario using approximately 10 concurrent clients.
- [ ] Keep the first proof bounded to the already-live core path:
  - `LOGIN`
  - `PLAY`
  - `LOOK`
  - and optionally one additional lightweight gameplay action such as `SAY` or one movement command.
- [ ] Define the minimum success criteria, including at least:
  - all clients authenticate and enter gameplay successfully;
  - no unexpected disconnects or forced reconnect cycles;
  - bounded latency expectations are recorded, even if they are loose at first;
  - and the resulting room view / communication behavior is sane for multiple simultaneous players.

## 2. Data Setup Strategy

- [ ] Decide and document the first-pass setup model for accounts/characters needed by the load proof.
- [ ] Prefer generated test data over large static fixture packs where feasible, for example:
  - create accounts programmatically during setup;
  - create characters programmatically during setup;
  - and bind them to the test tenant/game world as part of the harness.
- [ ] Keep the setup pragmatic for test environments: avoid turning this slice into a full synthetic-world generator if a bounded test fixture helper will do.
- [ ] Document whether cleanup is required after each run or whether isolated test databases/tenants make coarse cleanup acceptable.

## 3. Client Harness Choice

- [ ] Decide whether the first load proof should use:
  - raw WebSocket clients;
  - raw TCP/Telnet clients;
  - or both in separate bounded scenarios.
- [ ] Keep the first version simple and close to real client behavior rather than inventing a specialized fake protocol.
- [ ] Document the chosen harness clearly enough that later higher-scale tests can reuse it instead of starting over.

## 4. Execution Environment

- [ ] Decide where the first multiplayer proof lives operationally:
  - `load-testing` module;
  - cross-service integration harness;
  - or another bounded home.
- [ ] Keep it runnable in a repeatable local/CI-friendly way for the initial 10-client scenario.
- [ ] Document which parts of the stack are expected to be real for the proof:
  - real Game Session / Game Logic / Gateway / TCP Proxy as relevant;
  - real Redis/database;
  - and any acceptable stubbing boundaries if they are truly necessary.

## 5. Initial Assertions

- [ ] Add baseline assertions for concurrent `LOGIN` / `PLAY` / `LOOK`.
- [ ] Add at least one multiplayer-facing assertion beyond simple connection success, for example:
  - multiple players in the same room see sane occupant counts;
  - or a `SAY` from one client is delivered to the other connected clients in the room.
- [ ] Ensure failures are diagnosable enough that the slice is useful for concurrency debugging rather than only producing “timed out” noise.

## 6. Observability and Metrics

- [ ] Record the minimum metrics/logging needed to make the first load proof useful, such as:
  - connection count;
  - login/play success rate;
  - simple latency summaries;
  - and disconnect/error counts.
- [ ] Keep the first pass lightweight; this slice is proving basic multiplayer viability, not building a full performance dashboard.

## 7. Follow-On Scope Boundary

- [ ] Explicitly defer larger-scale or more complex scenarios, such as:
  - hundreds of clients;
  - combat-heavy concurrency;
  - inventory-heavy concurrency;
  - and long-running soak tests.
- [ ] Capture the likely next increments after the initial 10-client proof, for example:
  - mixed WebSocket/Telnet clients;
  - burst `SAY` fanout;
  - move + `LOOK` churn;
  - or later inventory/equipment concurrency after `06`.

## 8. Final QA Checklist

- [ ] Verify the first multiplayer proof runs repeatably and demonstrates real concurrent player entry into gameplay.
- [ ] Confirm the slice uses generated or otherwise maintainable test data rather than requiring a growing hand-maintained account/character fixture set.
- [ ] Confirm the result is useful as a long-lived regression/validation asset rather than a one-off script.
