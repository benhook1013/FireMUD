# Temporal Workflow Foundation and Common Contracts Vertical Slice

## Goal and Status

Goal: establish only the shared FireMUD Temporal foundation that the first real adopters need, so durable control-plane workflows can use one canonical runtime, identity model, retry/timer policy, operator-read surface, and service-integration pattern without turning the repo into a speculative workflow platform project. Status: planned.

## Scope

- choose the Temporal deployment and service-runtime integration pattern for FireMUD;
- define canonical workflow identity, business-step idempotency, signal/query/update contracts, and operator-read integration;
- define how Temporal workflow state maps onto FireMUD’s current control-plane status/read surfaces;
- define the boundary between short synchronous `common-saga` usage and durable Temporal workflow usage;
- update high-level docs and tooling guidance for the new workflow substrate.

This slice should not build generic platform machinery that the first adopters will not consume immediately.

## Acceptance Criteria

- at least one service can host Temporal workflows with one documented shared integration pattern;
- workflow identity and business-step idempotency rules are documented canonically;
- later adoption slices can use one shared operator/read integration model instead of inventing per-workflow status semantics.

## Checklist

- [ ] Choose and document the canonical FireMUD Temporal deployment/runtime integration pattern.
- [ ] Define canonical workflow identity, business-step idempotency, and retry/timer conventions.
- [ ] Define canonical signal/query/update and operator-read conventions.
- [ ] Define the durable-workflow boundary versus short synchronous `common-saga` usage.
- [ ] Update developer and architecture docs for the shared Temporal workflow model.
