# Automation Scripting jOOQ Migration Vertical Slice

## Goal and Status

Goal: make `automation-scripting-service` the first full `jOOQ + Flyway` service migration so the repo’s new SQL house style is proven on a queue/projection-heavy control-plane service rather than on a low-signal CRUD seam. Status: in progress.

## Implementation Notes

- The first migration pass now covers the highest-leverage queue/projection/runtime-state cluster rather than every repository in the service at once.
- `script_work_items`, readiness/pin/rollout projections, script event ingress/audit plus handoff history, rollout/runtime event history, plugin runtime state, and automation admission state are now backed by explicit `jOOQ` repositories.
- Remaining JPA surface in this service is still real and intentionally explicit: schedules, definitions/bindings, NPC formations/memory, and faction state are the next bounded seams.
- This means the service is not yet free of JPA/Hibernate runtime/config, but the first meaningful product-code control-plane seam is now on the canonical SQL path.

## Why This Service Goes First

`automation-scripting-service` is the strongest early proving ground:

- it is SQL-heavy;
- it owns work-item, schedule, rollout, readiness, and control-plane query seams where explicit SQL is valuable;
- it is central enough to prove the pattern, but less risky than `game-session-service` as the first migration.

## Scope

- replace the service’s JPA repositories/entities with `jOOQ`-backed persistence seams;
- keep the current Flyway baseline as the schema authority;
- migrate the control-plane list/query surfaces, work-item reads/writes, and rollout/readiness projections onto explicit SQL ownership;
- update tests and local proof so no JPA/Hibernate runtime dependency remains in the service.
