# Reconnect and Session Recovery Semantics Vertical Slice Task List

## Goal and Status

Goal: align the implemented reconnect/takeover path with the explicit recovery model described in the design docs so Telnet, generic WebSocket, and first-party web clients all recover consistently and observably after disconnects, restarts, revocations, and stale-session loss. Status: planned; baseline takeover/resume works today, but the richer recovery contract remains only partially implemented and partially documented.

This slice is a follow-up to **Login and Session** and **Login and Session Hardening**. It does not rework the basic gameplay loop. It focuses on making reconnect behavior trustworthy, explicit, and testable.

## 1. Canonical Recovery Model Review

- [ ] Re-read the [Reconnection Strategy](../../architecture/system-architecture-reconnection.md), [Authentication & Authorization](../../architecture/system-architecture-authentication.md), [Game Session protocols](../../architecture/microservices/game-session-service/protocols.md), [TCP Proxy protocols](../../architecture/microservices/tcp-proxy-service/protocols.md), and [Spring Cloud Gateway client behavior](../../architecture/microservices/spring-cloud-gateway/client-behavior.md) docs and identify the parts that are currently design-only versus implemented.
- [ ] Make one canonical recovery sequence explicit for each transport class:
  - Telnet
  - generic WebSocket
  - first-party `/ws/game/**`
- [ ] Ensure every flow states clearly:
  - when a fresh `LOGIN` is required
  - when a fresh `PLAY` is required
  - when a fresh first-party connect token is required
  - what constitutes resume vs fresh session start

## 2. Session Resume and Takeover Semantics in Game Session

- [ ] Before changing this service for the slice, run `./gradlew :game-session-service:test` and stabilize the baseline if necessary.
- [ ] Tighten the implementation around the canonical gameplay uniqueness key `{tenantId, gameInstanceId, characterId}` so takeover and resume behavior is consistently keyed there rather than on weaker socket/session hints.
- [ ] Ensure resume is authorized from current identity and current membership/revocation state, not from the prior backend token alone.
- [ ] Add or refine explicit failure paths for:
  - expired gameplay session
  - revoked membership
  - changed tenant/world access
  - stale or missing room/game-instance context
- [ ] Document and test exactly what session state is reconstructed after resume:
  - room snapshot replay or rerun
  - command queue expectations
  - what is intentionally not replayed

## 3. Edge-Restart and Disconnect Classification

- [ ] Add or refine tests and docs for reconnect behavior after:
  - TCP Proxy restart
  - Gateway restart / planned drain
  - Game Session restart
  - upstream unavailability
- [ ] Ensure WebSocket close-code and Telnet disconnect-category mapping is stable, bounded, and documented enough for first-party and reference clients to implement retry policy correctly.
- [ ] Ensure missing close metadata and abnormal transport loss still map into a deterministic retry class.
- [ ] Add cross-service tests that prove the intended disconnect classification rather than only asserting eventual reconnect success.

## 4. Telnet Reconnect and `SESSION` Hint Behavior

- [ ] Make explicit whether advanced Telnet attach hints remain useful during reconnect and, if so, how they interact with the resumed gameplay binding without becoming authoritative.
- [ ] Add focused Telnet reconnect coverage for:
  - reconnect without `SESSION`
  - reconnect with `SESSION`
  - duplicate or late disconnect hints
  - stale-session expiry
- [ ] Ensure Telnet clients never appear to get a hidden transport-preserving recovery on the same TCP socket; reconnect must remain explicit and player-visible.

## 5. First-Party Web Reconnect Semantics

- [ ] Add or refine first-party web reconnect coverage proving that:
  - a fresh connect token is required after disconnect;
  - bare `LOGIN` still consumes verified bootstrap/connect identity;
  - `PLAY` is still the gameplay-binding step after reconnect;
  - stale or mismatched connect scope fails deterministically.
- [ ] Document how much of this recovery is automated by the first-party client versus what remains the canonical protocol-visible contract.

## 6. Recovery UX and Player-Facing Feedback

- [ ] Define the bounded player-facing outputs for:
  - resume succeeded
  - resumed session was stale and a fresh session was created
  - membership/access changed so resume was denied
  - backend unavailable during reconnect
- [ ] Ensure these outputs are player-helpful rather than backend-internal, while still preserving enough structure for clients to act on them.
- [ ] Update transcripts/examples to show at least one successful resume and one failed resume that falls back to explicit recovery steps.

## 7. Observability and Operator Confidence

- [ ] Audit and, if needed, add metrics/logs for:
  - successful resume
  - takeover
  - failed resume due to revocation/expiry
  - reconnect after edge restart
  - dropped or duplicate disconnect hints
- [ ] Ensure the logs and metrics are enough for operators to distinguish:
  - real player disconnects
  - edge instability
  - session-staleness cleanup
  - revocation/authorization failures

## 8. Cross-Service End-to-End Tests

- [ ] Add or refresh WebSocket and Telnet cross-service tests for:
  - reconnect after voluntary disconnect
  - reconnect after Gateway/Game Session restart
  - takeover from a second client
  - failed resume after revocation or stale-session expiry
- [ ] Keep the tests bounded and representative; do not grow this slice into a full chaos/recovery matrix.

## 9. Final QA Checklist

- [ ] Manually verify one happy-path reconnect over Telnet and one over WebSocket.
- [ ] Manually verify one takeover flow and one failed-resume flow.
- [ ] Confirm that the implemented behavior now matches the documented recovery model rather than only a subset of it.
