# `02.18.9` Region Epoch, Fencing, and Runtime Ownership

## Goal and Status

Goal: introduce durable region ownership, epoch, and fencing semantics so stale executors cannot safely continue acting after failover/reset and runtime coordination has one canonical owner-of-record model. Status: planned.

## Checklist

- [x] Define target-state behavior and scope.
- [ ] Discussion pass with user before implementation.
- [ ] Implement the slice end-to-end.
- [ ] Verify and close any follow-ups.

## Why This Slice Exists

The tick architecture already assumes stronger region ownership than the runtime currently enforces:

- one authoritative executor per region;
- region epochs that advance on reset/recovery;
- fencing tokens so stale workers cannot commit after ownership changes.

Today, that model is still more documented than implemented. Some pause/resume and runtime ownership behavior is still local or intentionally incomplete, which is acceptable for the current bounded runtime but not yet at the intended SaaS/operator bar.

## Discussion Gate

Do not implement this slice before a discussion pass with the user confirms:

- first concrete region ownership model;
- minimum durable `RegionStatus` shape;
- whether executor fencing should be per region, per batch, or both in the first pass;
- how much of the documented reset/epoch model should land in the first implementation boundary.

## Suggested Direction

The first implementation should add one durable `RegionStatus` or equivalent table/record in `game-session-service` with:

- `tenantId`
- `regionId`
- `regionEpoch`
- `lastCommittedTickId`
- current executor ownership marker
- ownership/fence token
- paused / draining / recovering state as needed

Redis remains useful for:

- live leases
- scheduling
- hot-path coordination

But durable region ownership must live in PostgreSQL so:

- reset/recovery can bump epoch safely;
- stale executors can be fenced off;
- operators do not infer ownership from volatile keys alone.

## Scope

- Define one durable region ownership/status record.
- Define epoch advancement rules for reset/recovery.
- Define executor fencing semantics for stale workers.
- Define how tick batches verify ownership before apply/commit.
- Define the minimum operator/runtime status surfaces for ownership and recovery.

## Out of Scope

- Full cluster-scheduler redesign.
- Full observer/heartbeat consumer redesign.
- Full operator UI.

## Target State

- Each region has one durable region status record.
- Epoch changes are explicit, durable, and monotonic.
- Stale executors cannot successfully commit after fencing changes.
- Reset/recovery tooling advances region epochs deliberately rather than rebuilding ambiguous mixed-epoch state in place.
- Tick-batch execution checks fence/epoch before finalizing work.

## Recommended First Model

The first pass should likely include:

- durable region status row per `(tenantId, regionId)`
- explicit `regionEpoch`
- explicit `executorFence`
- explicit `lastCommittedTickId`
- explicit paused/recovering state

The key principle is:

- Redis lease presence alone is not authoritative enough for recovery-critical ownership decisions.

## Recommended Implementation Order

1. Land durable command status and tick-batch/effect ledger first or in parallel if already grounded.
2. Add durable region status.
3. Thread `regionEpoch` and `executorFence` through tick-batch creation/commit.
4. Make reset/recovery bump epoch durably before resuming work.
5. Reject stale batch finalization attempts when epoch/fence no longer match.
