# 02.18.10.1 Task List: Authored-Action and Resource Effect Replay Guards Vertical Slice

## Goal and Status

Goal: extend the now-live durable `effectId` replay/no-op contract into the next higher-level gameplay mutation seams so later actor/resource or authored-action families do not become a second duplicate-application path outside `02.18.10`. Status: complete at the current bounded boundary for the first richer actor-state mutation seam.

## Why This Slice Exists

`02.18.10` already proved the first replay/idempotency substrate across movement, item mutations, communication, action-state mutation, and downstream social-message persistence. The next bounded follow-through was to move the first later owning mutation seam onto that same durable replay contract instead of leaving it on local duplicate heuristics.

The audit found that:

- configured authored actions are still a non-mutating command-success stub at the current boundary, so they are not yet an owning mutation family worth carrying onto a downstream replay substrate;
- the first real later owning seam is the Entity Management actor-condition mutation path behind durable `BLOCK` / transient action-state application;
- that path already deduped by active-condition source identity, but it still bypassed the canonical durable `EntityMutationEffectReplayService` that the item/equipment/container mutation families already use.

## Scope

- the first real later owning mutation seam above the current `02.18.10` boundary;
- durable `effectId` propagation, replay/no-op storage, and owning-service duplicate application behavior for that touched family;
- focused proof that duplicate delivery replays the stored response instead of reinvoking the owning mutation service.

## Out of Scope

- broader tick-batch or queue-source work already owned by `02.18.8` and siblings;
- full combat/effect-engine design;
- migrating every future mutation family in one batch.

## Locked Direction

- later mutation families should reuse the same durable `effectId` replay/no-op contract instead of introducing family-local duplicate semantics;
- duplicate application should remain an owning-service no-op/replay truth, not an accidental second mutation;
- this slice should converge one real next family set, not broaden into a generic architecture pass.

## What Landed

### 1. Next Owning-Family Audit

- [x] Enumerated the still-live gameplay mutation seams that remained outside the current `02.18.10` replay guard coverage.
- [x] Prioritized the first real richer actor/resource mutation family.
- [x] Skipped authored-action follow-through because authored actions are not yet a downstream owning mutation seam.

### 2. Replay-Guard Follow-Through

- [x] `EntityManagementGrpcService.applyActorCondition(...)` now routes through `EntityMutationEffectReplayService.execute(...)` using the same durable `{tenantId, effectId}` replay substrate as the existing item/equipment/container mutation RPCs, with the current actor-condition wire contract carrying that durable effect id in `sourceId`.
- [x] Duplicate durable `effectId` delivery now replays the stored `ApplyActorConditionResponse` instead of reinvoking `ActorConditionMutationService`.
- [x] The actor-condition path now inherits the same `entitymanagement.mutation.effect.execution{operation,effect_status}` observability as the other Entity Management replay-guarded mutation families.

### 3. Focused Proof and Docs

- [x] Added focused gRPC proof that the live `ApplyActorCondition` path executes through the durable replay helper and replays stored responses without reinvoking the mutation service.
- [x] Updated `02.18.10` docs/status so the next remaining adoption tail is explicit after this cut.
- [ ] Re-run touched validation and Markdown/link proof.

## Acceptance Shape

- the first later owning mutation seam no longer sits outside the canonical `effectId` replay/no-op contract;
- duplicate delivery converges safely to replay/no-op instead of double application for that seam;
- focused proof covers owning-service replay behavior for `ApplyActorCondition`.

## Completion Notes

- `ActorConditionMutationServiceImpl` still keeps its local source-identity dedupe, but it is no longer the only replay fence for the public mutation RPC.
- Later authored-action or broader actor/resource follow-through should start only once those families own real downstream mutation behavior instead of command-local stubs.
