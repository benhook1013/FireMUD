# Gameplay Admission UX Alignment Vertical Slice Task List

## Goal and Status

Goal: align the implemented login and lobby flow with the intended player-facing MUD experience so normal clients can move from connection to gameplay with minimal ceremony while preserving the current security and gameplay-binding model. Status: planned; the design direction is now agreed, but implementation has not started.

This slice is a follow-up to **Telnet to Gameplay**, **Login and Session**, and **Login and Session Hardening**. It does not replace the current security model. Instead, it reshapes the user-facing command flow so the system behaves more like a conventional MUD front door:

```text
WORLDS        # optional public browse
LOGIN user pass
PLAY gamename [character]
```

Optional helper commands such as `REALMS` and `CHARS` remain available, but they should no longer feel like required ceremony before entry.

## 1. Protocol and UX Canonicalization

- [ ] Re-read the [Game Session protocols](../../architecture/microservices/game-session-service/protocols.md), [Authentication & Authorization](../../architecture/system-architecture-authentication.md), [TCP Proxy protocols](../../architecture/microservices/tcp-proxy-service/protocols.md), and [Reconnection Strategy](../../architecture/system-architecture-reconnection.md) docs and reconcile any remaining contradictions around `WORLDS`, `LOGIN`, `PLAY`, and `SESSION`.
- [ ] Make one command-stage model canonical in the design docs:
  - connected but not logged in;
  - logged in but not yet playing;
  - in game.
- [ ] Document `WORLDS` as available before `LOGIN` for public browsing/discovery, while clarifying that authenticated callers may see a richer personalized result set after login.
- [ ] Explicitly document that `LOGIN` authenticates account identity and `PLAY` binds gameplay identity/scope; these commands are sequential in the player experience but semantically distinct.
- [ ] Add at least one canonical Telnet transcript and one canonical WebSocket transcript for the ordinary human flow:
  - `WORLDS`
  - `LOGIN user pass`
  - `PLAY gamename [character]`
  - first gameplay command

## 2. Stage-Aware Command Handling in Game Session

- [ ] Before changing this service for the slice, run `./gradlew :game-session-service:test` and stabilize the baseline if necessary.
- [ ] Replace the current player-facing wrong-stage behavior so pre-login gameplay-like input does not surface as `NOT_AUTHENTICATED` and post-login/pre-`PLAY` gameplay-like input does not surface as `WORLD_NOT_SELECTED`.
- [ ] Introduce or refine explicit stage-aware protocol errors such as:
  - `LOGIN_REQUIRED`
  - `PLAY_REQUIRED`
  - and any bounded ambiguity/help responses needed for `PLAY`
- [ ] Ensure the interpreter can distinguish:
  - public/discovery commands available before login;
  - authenticated lobby commands available after login but before gameplay binding;
  - true in-game gameplay commands.
- [ ] Add unit/integration tests showing that wrong-stage input produces menu/help guidance instead of backend-shaped or gameplay-mechanics-shaped errors.

## 3. Simplified `PLAY` Resolution Rules

- [ ] Define and implement the normal happy-path `PLAY` contract as `PLAY <world> [character]`, with realm optional in the ordinary case.
- [ ] If `PLAY <world>` resolves to exactly one admissible gameplay target and one visible character choice, enter directly.
- [ ] If `PLAY <world>` is ambiguous, return a selection-oriented response that guides the player toward `REALMS`, `CHARS`, or a more specific `PLAY` form rather than returning a low-level failure.
- [ ] Decide and document whether `PLAY <world>` with exactly one admissible realm but multiple characters should:
  - prompt/select;
  - return a bounded ambiguity response;
  - or require `PLAY <world> <character>` explicitly.
- [ ] Add tests for:
  - direct unambiguous `PLAY`
  - ambiguous `PLAY` needing more selection
  - inaccessible world/realm/character
  - default public production realm entry

## 4. First-Party Web Alignment

- [ ] Update the first-party `/ws/game/**` design docs so the web client still maps cleanly onto the same player-facing model even though it uses bootstrap, connect-token, and connect-context machinery under the hood.
- [ ] Make explicit that first-party bare `LOGIN` is an identity-consumption/binding step using already-verified bootstrap identity, not a second credential-entry step.
- [ ] Ensure first-party UI/discovery flows still conceptually terminate in the same `PLAY` semantics as Telnet/generic WebSocket clients rather than inventing a second gameplay-admission model.
- [ ] Add or refresh tests/documented examples showing the first-party path results in the same effective gameplay state machine even if the UI hides some of the lobby commands.

## 5. `SESSION` Demotion and Smart-Client Scope

- [ ] Rework docs and examples so `SESSION` is no longer presented as part of the normal human-facing Telnet flow.
- [ ] Keep `SESSION` only as advanced/smart-client metadata if it remains justified.
- [ ] Decide whether the preferred long-term transport for smart-client attach hints should be:
  - the existing typed `SESSION` line;
  - hidden MCP metadata;
  - or another explicit advanced-client channel.
- [ ] Ensure the chosen attach-hint path remains strictly advisory and cannot bypass `LOGIN` + `PLAY`.
- [ ] Update Telnet examples and tests so normal parity coverage does not rely on `SESSION` unless the specific test is intentionally exercising advanced-client attach behavior.

## 6. Cross-Service and Transport-Parity Coverage

- [ ] Add or refresh a Telnet cross-service test for the normal human flow without `SESSION`:
  - connect
  - optional `WORLDS`
  - `LOGIN`
  - `PLAY`
  - `LOOK`
- [ ] Add or refresh a direct WebSocket / Gateway parity test for the same flow.
- [ ] Add focused coverage for:
  - pre-login public `WORLDS`
  - wrong-stage command guidance
  - unambiguous vs ambiguous `PLAY`
  - advanced-client `SESSION` hints where still supported

## 7. Developer Workflows, Docs, and Cleanup

- [ ] Update smoke/manual verification guidance so the normal example path is `LOGIN` -> `PLAY` instead of `LOGIN` -> `WORLDS` -> `REALMS` -> `CHARS` -> `PLAY`.
- [ ] Refresh service-status docs so they describe the simplified admission UX and stage-aware error model rather than the older implementation-shaped behavior.
- [ ] Remove or rewrite examples that imply all pre-`PLAY` mistakes are gameplay-auth failures.

## 8. Final QA Checklist

- [ ] Manually verify the normal Telnet flow and generic WebSocket flow both feel like:
  - connect
  - optional browse
  - `LOGIN`
  - `PLAY`
  - in game
- [ ] Confirm the first-party web flow still lands on the same gameplay binding semantics.
- [ ] Confirm normal players are never expected to type `SESSION`.
