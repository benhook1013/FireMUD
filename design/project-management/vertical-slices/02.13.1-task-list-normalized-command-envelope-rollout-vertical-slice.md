# Normalized Command Envelope Rollout Vertical Slice Task List

## Goal and Status

Goal: carry the canonical input model from architecture into code by introducing a normalized command envelope with typed payload shapes through the active Game Session command path, without attempting a one-shot rewrite of every parser and handler. Status: planned.

## Scope

- Replace ad hoc raw-string command handling where it matters most with a normalized command envelope.
- Keep menu/lobby and gameplay-stage intents distinct.
- Avoid one-class-per-command; use a small set of payload shapes and normalized verb metadata.

## Key Tasks

- [ ] Define the first runtime command-envelope shape in code, including:
  - normalized verb;
  - alias used;
  - raw line;
  - stage;
  - typed payload;
  - client metadata.
- [ ] Identify the first bounded payload shapes needed for the current live command set, such as:
  - credentials payload;
  - selection payload;
  - targeted-message payload;
  - directional payload;
  - gameplay-view request payload.
- [ ] Refactor the active Game Session parser path so it produces the normalized envelope rather than only ad hoc command objects or raw text.
- [ ] Keep stage legality in the interpreter/session gate rather than moving it into payload parsing.
- [ ] Convert the highest-value current commands first:
  - `LOGIN`
  - `PLAY`
  - `LOOK`
  - `SAY`
  - `WHISPER`
  - `TELL`
  - movement
- [ ] Leave room for later schema/registry-driven command definitions without requiring them in this slice.

## Tests

- [ ] Add focused parser/interpreter tests proving normalized envelope production for the first bounded command set.
- [ ] Add regression coverage showing aliases and stage legality still behave correctly after the normalization step.

## Notes

- This slice is about input normalization, not about adding new gameplay verbs.
- Avoid inventing a large command class hierarchy; the goal is a small stable envelope with typed payloads.
