# Authored Action Definition and Execution Model Vertical Slice

## Goal and Status

Goal: define the canonical game-authored action model so later custom actions share one typed definition, validation, targeting, cost/cooldown, and execution path instead of bypassing the built-in command and effect architecture. Status: partially implemented.

## Implementation Notes

The runtime does not support true game-authored actions yet, but the first canonical insertion seam now exists:

- `TextCommandInterpreter` resolves through a general `TextCommandRegistry` rather than a built-in-only branch tree;
- the active runtime registry is now provider-backed, so later authored-command definition providers can register through the same seam as built-ins;
- command definitions already carry the shared metadata authored commands will need later:
  - dispatch group;
  - stage requirement;
  - prompt policy;
  - primary action category;
  - source/ownership metadata;
- duplicate command-definition ownership is rejected when providers are aggregated, which prevents later authored providers from silently shadowing built-in definitions.

Still future work under this slice:

- define the canonical authored action definition shape itself;
- define how authored commands map to action identity, targeting, costs, cooldowns, and execution hooks;
- add the first non-built-in command-definition provider and prove it executes through the same dispatch architecture;
- carry authored execution into the later effect/timing substrate rather than inventing a second action path.

## Why This Slice Exists

FireMUD already has slices for command interpretation and action classification, but the platform still needs a dedicated model for authored actions themselves. Without that, future game-defined verbs risk becoming one-off scripts or handler-local exceptions.

## Scope

- Define one canonical authored action model, including:
  - action identity;
  - command linkage;
  - classification/category;
  - requirements;
  - targeting rules;
  - costs/cooldowns;
  - execution/effect hooks.
- Define how authored actions plug into the built-in command registry/dispatcher architecture.
- Define how authored actions consume the future shared stats/effects foundation.
- Define how player-visible help/command discovery relates to authored actions.

## Out of Scope

- A full authoring UI.
- Full scripting language design.
- Combat-specific balance data.

## Known Design Considerations

- Built-in and authored commands should share one registry concept, not parallel dispatch paths.
- Action classification should provide the primary category and optional tags for activity/AFK semantics.
- Costs, cooldowns, and durations should align with the later shared timing model.
- Effects should eventually flow through the shared effect engine rather than action-local math.

## Locked Direction

- Built-in and authored command definitions use one provider-backed registry seam.
- Authored commands should register definitions as data first, then dispatch through the same family-handler or later authored-action executor seam rather than bypassing interpretation.
- Command-definition ownership collisions are configuration/programming errors and should fail fast.
- The first authored-action model should define one canonical typed action shape rather than per-command script-local execution rules.
- Costs, cooldowns, durations, and effects remain consumers of the later shared timing/effect substrate instead of being reinvented here.

## Current Remaining Work

- Define the canonical authored action definition record and its required typed fields.
- Decide how authored command phrases/aliases map to action identity without creating a parallel parser architecture.
- Add the first non-built-in provider using the existing registry seam.
- Define the first authored execution adapter so later actions do not bypass dispatch, activity classification, or prompt policy.
