# Design Area Slice Coverage

This document is the repo-wide planning map from architecture domains to vertical slices and current implementation maturity.

It is intentionally different from [00-slice-progress.md](./00-slice-progress.md):

- `00-slice-progress.md` is the active near-term queue.
- this file is the broader design review artifact used to answer:
  - which first-class architecture domains already have coherent slice families;
  - which domains are implemented but still under-sliced;
  - which domains are heavily designed but still mostly waiting for slice decomposition and delivery.

## How To Read This File

- `Slice coverage` answers: “how well is this design area translated into explicit slice planning?”
- `Implementation maturity` answers: “how much of the area is actually present in repo services and service-status docs?”
- These are separate axes on purpose. A domain can be implemented but poorly sliced, or well sliced but still mostly future work.

### Rating Scale

| Rating | Meaning for slice coverage | Meaning for implementation maturity |
| --- | --- | --- |
| `Strong` | The domain has a coherent slice family or a clearly sufficient spread of slices. | The core target behavior is already live across the current repo/services, with remaining work mostly follow-through or hardening. |
| `Moderate` | Important parts are sliced, but major subdomains still live mainly in architecture docs or scattered slices. | Significant working substrate exists, but important target-state behavior is still partial, uneven, or not yet proven end to end. |
| `Weak` | Only partial, indirect, or placeholder slice coverage exists for the domain. | Implementation is early, heavily partial, or mostly design-led rather than live. |
| `None` | No meaningful slice family exists yet. | No meaningful implementation evidence was found beyond stubs or architectural intent. |

## Biggest Coverage Corrections From The Previous Version

- Account/auth/JWT/tenant authorization/billing entitlements are now called out as a first-class design domain instead of being treated as mostly “login/session”.
- Multi-tenancy and realm modeling are now called out separately from gameplay admission and reconnect work.
- Game design/publishing/assets/version/runtime activation are now explicitly marked as under-sliced even though the design set is large and the Game Design service is not empty.
- Security/compliance/operator control plane are now treated as a major design-heavy domain rather than disappearing into generic “hardening”.
- Scripting/automation has been reassessed upward on implementation maturity but still marked weak on slice coverage because the repo has real service/runtime code without a comparable vertical-slice family.
- Frontend/first-party web has been reassessed from actual repo evidence: there is a live `web-client` module, but slice coverage for the broader product surface is still weak.
