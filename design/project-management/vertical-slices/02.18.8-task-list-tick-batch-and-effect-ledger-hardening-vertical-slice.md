# `02.18.8` Tick Batch and Effect Ledger Hardening

## Goal and Status

Goal: add the first durable tick-batch and effect-ledger substrate so Redis tick staging becomes hot-path coordination over durable execution truth instead of the only real record of in-flight gameplay work. Status: planned.

## Checklist

- [x] Define target-state behavior and scope.
- [ ] Discussion pass with user before implementation.
- [ ] Implement the slice end-to-end.
- [ ] Verify and close any follow-ups.

## Why This Slice Exists

The current runtime has tokened locks, pending queues, and rollback scripts, but it does not yet have the durable batch/effect ledger the architecture docs assume:

- there is no `tick_batch` durable execution record in the current service schema;
- Redis `pending`/`queue` state is still doing more than the intended coordination role;
- crash recovery cannot yet answer "which batch/effects were durably committed, which were abandoned, and which need replay?" from durable truth alone.

This matters because the intended hosted-runtime model relies on:

- replay-safe execution;
- bounded live repair burden;
- one durable execution trail per tick/batch/effect rather than reconstructing state from logs and Redis residue.

## Discussion Gate

Do not implement this slice before a discussion pass with the user confirms:

- exact tick-batch granularity;
- minimum durable fields required on batch and effect rows;
- whether the first effect ledger should be generic or only cover gameplay-state mutations;
- the first acceptable replay/abandon semantics.

The direction below is a suggested first implementation, not a locked contract.

## Suggested Direction

The first implementation should add two durable layers in `game-session-service`:

- `tick_batch`
  - one row per staged/owned tick batch
- `tick_effect`
  - one row per effect/application attempt within a batch

Redis remains:

- lease/lock/queue coordination
- fast staging metadata
- wake-up / backpressure / scheduling mechanics

PostgreSQL becomes:

- durable batch identity
- durable effect identity/outcome
- replay/reconciliation source of truth

## Scope

- Define one durable tick-batch identity model.
- Define one durable effect/application ledger tied to batch and command identity.
- Define the minimum status vocabulary for batches and effects.
- Define how Redis staging correlates to durable batch/effect rows.
- Define how replay and abandonment read from the ledger instead of guessing from Redis.

## Out of Scope

- Full region-fencing rollout.
- Full command-ingress implementation if not already landed.
- Migrating every gameplay command onto the path in the same slice.

## Target State

- Every staged gameplay batch has a durable `tickBatchId`.
- Every effect/application inside that batch has a durable row keyed by `effectId`.
- Redis `pending` and `queue` state can be discarded and rebuilt because durable execution truth remains.
- Batch status and effect status converge independently but consistently.
- Replay/rollback tools consult the ledger, not only transient Redis keys.

## Suggested First Data Model

The first implementation likely needs:

- `tick_batch`
  - `tick_batch_id`
  - `tenant_id`
  - `game_instance_id`
  - `region_id`
  - `region_epoch`
  - `tick_id`
  - `command_id`
  - `status`
  - `executor_id` / runtime ownership marker
  - timestamps
- `tick_effect`
  - `effect_id`
  - `tick_batch_id`
  - `effect_type`
  - `target_aggregate`
  - `participant_service`
  - `status`
  - idempotency/replay metadata
  - failure code/message
  - timestamps

## Suggested Status Model

The first pass should stay simple:

- batch states:
  - `SCHEDULED`
  - `STAGED`
  - `APPLIED`
  - `ABANDONED`
  - `FAILED`
- effect states:
  - `PENDING`
  - `APPLIED`
  - `NO_OP`
  - `FAILED`
  - `ABANDONED`

The exact vocabulary can change in discussion, but the important part is:

- durable terminal/non-terminal distinction;
- ability to reconcile from durable state after Redis loss.

## Recommended Implementation Order

1. Confirm the command-ingress/status substrate or land it first.
2. Add durable `tick_batch`.
3. Correlate Redis staging with `tick_batch_id`.
4. Add durable `tick_effect`.
5. Update replay/recovery logic to read durable batch/effect state.
6. Only then grow more advanced fencing or cross-region follow-up behavior.
