# Script Timer, Scheduler, and Runtime Ownership Vertical Slice

## Goal and Status

Goal: lock the first canonical scheduler/timer ownership model for scripting so interval and timer triggers, leader catch-up, region fencing, and plugin-owned schedules all follow one explicit runtime contract. Status: partially implemented, with durable patch-scoped schedule-definition catalog, first instance-scoped schedule materialization, first live plugin-version schedule filtering, Game Session runtime-progress publication, deterministic timer-derived work-item emission, and bounded round-robin catch-up from observed tick progress now live, but richer leader checkpointing and broader scheduler observability still pending.

## Why This Slice Exists

Timers and scheduler coordination are among the highest-risk scripting seams, but they are still easy to treat as internal service detail. This slice isolates the runtime ownership model before more scripting behavior accumulates on top of it.

## Implementation Notes

The human direction for this slice is no longer the blocker: scheduler ownership should be instance-aware, fenced, and backed by durable timer identity. Automation now persists a patch-scoped `script_schedule_definitions` catalog from compiled script payloads during `NotifyScriptVersionUpdate`, keyed by `scheduleDefinitionId` with cadence/unit metadata and duplicate detection per patch scope. It also materializes observed pinned patches into durable `script_schedule_instances` rows keyed by `(tenantId, gameInstanceId, plugin owner metadata, binding target identity, scheduleDefinitionId)`, and plugin-owned schedules are filtered through the live `(tenantId, gameInstanceId, pluginId)` runtime registry so only the currently enabled `pluginVersionId` keeps schedule ownership. Game Session advances durable `lastCommittedTickId` on its runtime ownership row after successful tick cycles, exposes that progress through runtime ownership status, and publishes `ObserveRuntimeTickProgress` to Automation with `(tenantId, gameInstanceId, regionId, regionEpoch, tickId)`. Automation records those runtime progress fields on tick-aligned schedule rows, derives the next future `nextDueTickId`, and now emits deterministic timer-derived work items into the same outbox/audit/queue path used by other script events when due ticks are reached. Catch-up candidates are selected in round-robin passes across schedule identities, capped by `script.scheduler.max-catch-up-firings-per-observation`, and surfaced in the progress response plus `script_timer_fired_total` / `script_timer_catchup_truncated_total` metrics. Automation has event ingress, handler resolution, durable work items, quota/budget enforcement, plugin-policy fencing, durable schedule-definition storage, first instance schedule materialization, first plugin-timer reconciliation via runtime version filtering, first binding-target-aware timer identity substrate, heartbeat-derived due-point advancement, timer trigger emission, and bounded catch-up from observed tick progress. What remains is richer leader checkpointing, audit-level truncation detail, and runtime-change proof around the new substrate.

## Scope

- script timers versus tick timers
- scheduler leadership and catch-up rules
- durable timer identity and ownership across `tenantId`, `gameInstanceId`, and `regionEpoch`
- plugin-owned timer reconciliation during activation/rollback/disablement

## Out of Scope

- general runtime durability hardening outside scripting-owned scheduler truth
- event ingress API shape beyond what timer-derived triggers require
- design-time plugin publication metadata

## Locked Direction

- scheduler ownership is instance-scoped and fenced; stale executors must not mint new timer-derived triggers.
- timer identities must be explicit enough for rollback, catch-up, and plugin-version changes to converge safely.
- plugin-owned schedules are runtime state and must be reconciled explicitly during activation changes.
- best-effort timer semantics remain explicit; the system must not imply stronger guarantees than documented.

## Current Remaining Work

- add audit-level truncation detail beyond the current response counts and aggregate metrics.
- carry the new plugin-version-aware schedule materialization forward into richer disable/drain/rollback observability.
- prove stale-scheduler fencing and region/instance isolation under runtime changes.
- keep scheduler leadership derived from documented runtime/region ownership unless a later Redis design update explicitly introduces a first-class `script-leader:*` prefix.
