# Script Timer, Scheduler, and Runtime Ownership Vertical Slice

## Goal and Status

Goal: lock the first canonical scheduler/timer ownership model for scripting so interval and timer triggers, leader catch-up, region fencing, and plugin-owned schedules all follow one explicit runtime contract. Status: partially implemented, with durable patch-scoped schedule-definition catalog now live but heartbeat- and instance-timer-runtime work still pending.

## Why This Slice Exists

Timers and scheduler coordination are among the highest-risk scripting seams, but they are still easy to treat as internal service detail. This slice isolates the runtime ownership model before more scripting behavior accumulates on top of it.

## Implementation Notes

The human direction for this slice is no longer the blocker: scheduler ownership should be instance-aware, fenced, and backed by durable timer identity. Automation now persists a first patch-scoped `script_schedule_definitions` catalog from compiled script payloads during `NotifyScriptVersionUpdate`, keyed by `scheduleDefinitionId` with cadence/unit metadata and duplicate detection per patch scope. That gives the service a real durable schedule-definition substrate instead of re-parsing arbitrary script JSON later. The remaining implementation blocker is still the missing live input that safely drives timer firings. Automation has event ingress, handler resolution, durable work items, quota/budget enforcement, plugin-policy fencing, and now durable schedule-definition storage, but it does not yet have a real Game Session heartbeat or a schedule-instantiation path that can supply `(tenantId, gameInstanceId, regionId, regionEpoch, tickId)` and turn those patch-owned definitions into durable instance/region timer rows without inventing synthetic timer authority inside Automation.

## Scope

- script timers versus tick timers
- scheduler leadership and catch-up rules
- durable timer identity and ownership across `tenantId`, `gameInstanceId`, and `regionEpoch`
- plugin-owned timer reconciliation during activation/rollback/disablement

## Out of Scope

- general runtime durability hardening outside scripting-owned scheduler truth
- event ingress API shape beyond what timer-derived triggers require
- design-time plugin publication metadata

## Locked Direction

- scheduler ownership is instance-scoped and fenced; stale executors must not mint new timer-derived triggers.
- timer identities must be explicit enough for rollback, catch-up, and plugin-version changes to converge safely.
- plugin-owned schedules are runtime state and must be reconciled explicitly during activation changes.
- best-effort timer semantics remain explicit; the system must not imply stronger guarantees than documented.

## Current Remaining Work

- add the Game Session heartbeat or equivalent runtime progress feed Automation can consume without owning tick progression.
- extend the now-live patch-scoped schedule-definition catalog into a schedule-instantiation path that turns compiled schedule definitions into durable instance/region-scoped timer rows with explicit `scheduleDefinitionId`, owner patch/plugin metadata, cadence, and next due point.
- implement bounded catch-up from durable schedule rows using the documented round-robin truncation rule and deterministic `scriptEventId` derivation.
- connect plugin-owned timer reconciliation to existing plugin lifecycle APIs.
- prove stale-scheduler fencing and region/instance isolation under runtime changes.
- keep scheduler leadership derived from documented runtime/region ownership unless a later Redis design update explicitly introduces a first-class `script-leader:*` prefix.
