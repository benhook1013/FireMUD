# Kubernetes Deployment-Contract Convergence Vertical Slice

## Goal and Status

Converge the checked-in Kubernetes deployment surfaces on one coherent contract by making the player-facing Kustomize path either genuinely canonical or explicitly non-canonical, aligning support assets with that decision, and documenting any intentional hosted preview/dev-demo exceptions. Status: planned.

## Why This Slice Exists

The repository now has one real hosted Helm deployment path for preview/dev-demo and one nominally canonical Kustomize path for staging/production, but the two surfaces do not yet read as one coherent deployment story:

- the Kustomize overlays are still thin includes over `base/`
- `base/` still carries placeholder credentials and TLS material
- some support assets still assume older secret names
- hosted preview/dev-demo do not yet share every checked-in infrastructure posture, especially around network policy

This is no longer a small doc-tidy problem. It is a deployment-contract convergence problem that needs deliberate ownership.

## Scope

- Decide whether `k8s/overlays/stage` and `k8s/overlays/prod` are truly the canonical player-facing deployment path now.
- If they are canonical, make that path operationally coherent:
  - environment-specific image/digest control
  - no placeholder player-facing credentials or TLS material in the canonical path
  - support assets that use the same secret/config contracts as the rest of the path
- If they are not yet canonical, demote them in docs until the contract is real.
- Reconcile the checked-in player-facing path with the backup/restore support assets under `k8s/postgres` and `k8s/velero`.
- Decide whether hosted preview/dev-demo should have checked-in `NetworkPolicy` parity with the player-facing path, or whether the exception is intentional and documented.
- Keep the preview/dev-demo lifecycle and exception model explicit without treating hosted-preview behavior as the player-facing production contract by accident.

## Out of Scope

- Replacing Helm with Kustomize or vice versa.
- Reworking unrelated service internals.
- General cluster-capacity or preview-topology redesign.
- Secret-manager migration beyond the current checked-in Kubernetes contract.

## Acceptance Shape

- The repo states one clear truth about the player-facing Kustomize path: canonical and current, or intentionally incomplete.
- Checked-in player-facing manifests no longer rely on placeholder credentials/TLS resources in the canonical path.
- Supporting backup assets use the same secret/config contract as the rest of the player-facing path.
- Hosted preview/dev-demo network-policy posture is either implemented or explicitly documented as a deliberate exception.
- A reviewer can understand the Kubernetes deployment families from docs without reopening multiple contradictory folders and workflows.
