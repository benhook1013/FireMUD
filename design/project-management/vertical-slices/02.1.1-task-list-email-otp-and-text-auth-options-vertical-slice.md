# Email OTP and Text-Client Auth Options Vertical Slice

## Goal and Status

Goal: add a text-client-friendly passwordless login path where `LOGIN <email>` initiates an email-delivered one-time code flow, then capture the bounded follow-up design for optional stronger MFA paths over Telnet and generic text clients. Status: planned.

This slice is a follow-up to the existing login/session work. The current `LOGIN <email> <password>` flow is functional, but text clients are a poor fit for modern password-heavy auth UX, especially when account creation, password storage, and recovery friction are considered. FireMUD should have one deliberate text-first authentication story rather than inheriting web-login assumptions.

## Why This Slice Exists

Text clients and Telnet clients have different constraints than browser UI:

- no native clickable auth UI;
- no strong expectation of password-manager integration;
- awkward multi-step secret entry flows;
- strong value in minimizing sensitive text entry over plain command lines.

For these clients, a passwordless email OTP flow is a better baseline:

- `LOGIN <email>` starts the flow;
- the player receives a short code by email;
- a follow-up command completes login using that code.

This should become the primary text-client login path unless a game or operator explicitly needs a different default.

## Target State

- `LOGIN <email>` initiates an email OTP challenge instead of requiring an immediate password.
- The player receives a bounded response such as:
  - `OK LOGIN Code sent to <email>. Use OTP <code>.`
- A follow-up command such as `OTP <code>` or `LOGIN <email> <code>` completes authentication.
- The text protocol remains concise and transport-neutral across Telnet and generic WebSocket.
- Sensitive secrets should remain redacted in logs exactly as current `LOGIN` handling already does for passwords.
- The Account Service remains authoritative for challenge creation, code verification, rate limits, expiry, and delivery policy.

## Scope

- Define the canonical text-client email OTP login flow.
- Define the minimum Game Session protocol updates needed for challenge initiation and challenge completion.
- Define the Account Service contract for:
  - creating an email OTP challenge;
  - verifying the code;
  - returning identity/session-binding details on success;
  - returning bounded application errors on failure.
- Define the transport-facing UX for:
  - code sent;
  - invalid code;
  - expired code;
  - rate-limited / locked-out attempts.
- Record the follow-up design space for optional stronger MFA over text clients without blocking the OTP-first baseline.

## Out of Scope

- Browser-first OAuth or social login flows.
- TOTP authenticator-app enrollment UX.
- Full account-recovery and account-management UI.
- Rich mail-provider abstraction design beyond what the first OTP delivery path needs.

## Canonical Text-Client Flow

Recommended baseline:

1. Player enters:
   - `LOGIN player@example.com`
2. Game Session calls Account Service to create an email OTP challenge.
3. Account Service sends a short-lived code to the email address.
4. Player sees:
   - `OK LOGIN Code sent to player@example.com. Use OTP <code>.`
5. Player enters:
   - `OTP 482193`
6. Game Session verifies the code through Account Service.
7. On success, the existing authenticated session path continues as normal.

The completion command could also be supported as a shaped `LOGIN` form later, but the baseline text UX should prefer a dedicated follow-up command because it is easier to explain, easier to gate, and cleaner to parse.

## Error and Guardrail Expectations

The first OTP slice should define bounded application errors for:

- unknown or unregistered email when the product policy allows user-facing distinction;
- `OTP_REQUIRED`;
- `OTP_INVALID`;
- `OTP_EXPIRED`;
- `RATE_LIMITED`;
- `ACCOUNT_LOCKED`;
- upstream mail delivery or Account Service failure.

Gameplay commands should remain blocked until the OTP challenge is successfully completed.

## Optional Stronger MFA Follow-Up

The branch should explicitly record but not prematurely implement stronger text-client MFA options.

Platform-level and game-level security policy may still require stronger login assurance than the baseline text-client OTP flow. The important distinction is that this stronger requirement does not need to be enforced through the classic Telnet/TCP command UX by default if a richer first-party client path exists.

Recommended policy direction:

- keep email OTP as the baseline text-client authentication path;
- allow platform admins or game creators to require stronger auth for selected surfaces;
- prefer enforcing richer MFA requirements such as authenticator-app OTP inside the web UI or other first-party GUI flows where the UX cost is much lower;
- avoid making the default Telnet/TCP path carry unnecessary multi-secret friction unless a deployment explicitly chooses that tradeoff.

Possible future options:

- optional password + OTP for users who explicitly enable it;
- optional TOTP-like second factor for advanced users;
- first-party web handoff or connect-token assist for clients that can open a browser.

But these should remain follow-up options, not the baseline text-client default, because:

- password + OTP is higher-friction;
- Telnet UX for multi-secret login is awkward;
- the number of users who truly need strong second-factor flow in classic text clients is likely small;
- the OTP-by-email flow delivers the biggest usability improvement first.

So the intended layered model is:

- baseline text-client auth: email OTP;
- optional stronger policy: platform-admin or game-level requirement;
- preferred richer MFA surface: first-party web or comparable GUI client, not plain Telnet by default.

## Testing Expectations

- Unit coverage for challenge-initiation and challenge-completion command handling.
- Integration coverage for Game Session <-> Account Service challenge creation and verification.
- Cross-service Telnet and generic WebSocket proof for:
  - `LOGIN <email>`
  - `OTP <code>`
  - `PLAY`
  - `LOOK`
- Logging tests proving OTP codes are redacted like passwords.

## Follow-On

- Optional stronger MFA slice for text clients.
- Optional first-party web assist/handoff for authentication bootstrap.
- Account creation and recovery UX aligned to the same passwordless text-client default.
