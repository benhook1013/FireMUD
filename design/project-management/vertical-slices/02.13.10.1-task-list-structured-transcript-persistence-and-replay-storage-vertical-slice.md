# Structured Transcript Persistence and Replay Storage Vertical Slice

## Goal and Status

Goal: narrow the remaining transcript/replay design into one concrete persistence and replay-storage model so reconnect, transcript history, and richer client playback do not remain split between structured live output and text-oriented replay buffers. Status: planned follow-up; discussion is required before implementation.

## Why This Slice Exists

The broader transcript slice is now clear at a high level:

- structured live output already exists;
- reconnect replay still persists text-oriented chunks;
- the final persistence/replay model is still not settled.

This follow-up exists so the exact storage decision is discussed before transcript end-state implementation resumes.

## Scope

- Define the canonical persisted transcript unit.
- Define whether reconnect replay stores structured output, rendered text, or both.
- Define the relationship between raw spoken text, normalized spoken text, and rendered transcript text.
- Define how richer clients consume replay without inventing a separate transcript contract.

## Out of Scope

- Full long-term archival retention policy.
- Search, moderation analytics, or mail history.

## Required Follow-Up Discussion

- Should replay persist canonical structured `PlayerOutput`-like envelopes or rendered text chunks?
- Should transcript storage preserve raw speech, normalized speech, or both?
- Where should color/style policy live once replay is no longer text-only?
