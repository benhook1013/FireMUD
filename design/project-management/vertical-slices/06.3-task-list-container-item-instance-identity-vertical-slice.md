# `06.3` Replace Aggregated Container Items With Distinct Item Instances

Goal: stop collapsing container-capable items by item definition so two identical satchels, backpacks, or chests can exist as distinct physical things with different contents and different locations.

## Implementation Notes

Current branch state after `06.2` is materially better:

- container contents are keyed by `container_instance_id`;
- container instances now move across carried, equipped, and room-ground states;
- room-ground interactions can now carry `container_instance_id` through the gameplay path.

The remaining hard limitation is that container-capable items themselves are still aggregated by `item_id` in inventory and room-ground state. That means the branch still treats "two identical backpacks" as one stack in places where the game should treat them as two separate things.

## Why This Follow-Up Exists

`06.2` fixed the identity of container contents and holder transitions, but it did not fully fix the identity of container items themselves.

Current remaining behavior still collapses by item definition in places like:

- `inventory` rows keyed by `(character_id, item_id)`;
- `room_ground_inventory` rows keyed by `(tenant_id, game_instance_id, room_instance_id, item_id)`;
- room-facing command matching that still assumes one actionable container target per item definition per location.

That means these cases are still not modeled correctly:

- two identical satchels carried by the same character;
- two identical chests dropped into the same room with different contents;
- picking up or dropping one matching container without affecting the other;
- later transfer flows that need to refer to one concrete container item, not an aggregate stack.

## Target State

- Every container-capable item is a first-class item instance with its own stable id.
- `container_instance_id` and container-item identity converge, or are explicitly and canonically linked one-to-one.
- Carried inventory, equipment, and room-ground storage stop aggregating container-capable items by `item_id`.
- Player-facing commands can resolve one concrete matching container even when multiple identical names exist.
- Generic references such as `get satchel from pouch` should use deterministic resolution rules when multiple matching containers are available.
- Specific references such as `satchel12345` should allow the player to bypass ambiguity and target one concrete container item directly.
- The platform should choose one canonical displayed/tab-completed explicit instance format, and the default should strongly favor compact text-client tab completion over readability punctuation.
- The visible ref for a concrete container item should be stable for the lifetime of that item instance, not renumbered per room or per current holder.
- The visible suffix should come from a stable monotonic per-type sequence, not a random GUID-like token.
- Non-container items may remain aggregated by `item_id + quantity` until a broader item-instance rollout is justified.

## Required Changes

- [ ] Introduce a first-class persisted identity for each container-capable item instance.
- [ ] Replace aggregated inventory and room-ground keys for container-capable items with that instance identity.
- [ ] Surface concrete item-instance identity through the entity-management API where Game Session must disambiguate one container from another.
- [ ] Update command resolution so repeated names produce deterministic disambiguation behavior instead of hidden stack collapse.
- [ ] Surface one canonical compact explicit container-reference form for output/help/tab completion while keeping the interpreter free to accept bounded equivalent readability aliases if they remain cheap and unambiguous.
- [ ] Allocate stable lifetime-visible refs for container item instances using a monotonic per-type sequence in the game/world namespace.
- [ ] Keep non-container item aggregation in place for the first pass unless the implementation proves that broader item-instance identity is cheaper and cleaner.

## Explicitly Out Of Scope

- full item-instance identity for every item in the game;
- nested containers;
- general mail, vendor, auction, or trade flows;
- creator-authored container naming or labelling systems.

## Validation

- [ ] Prove that two identical carried containers can hold different contents simultaneously.
- [ ] Prove that two identical room-ground containers can be dropped, listed, and picked up independently.
- [ ] Prove that `CONTAINER`, `PUT`, `TAKE`, `DROP`, `GET`, `WEAR`, and `REMOVE` continue to act on the correct concrete container item when duplicates exist.
