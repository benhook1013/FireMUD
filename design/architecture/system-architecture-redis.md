## Implementation Status

The target authenticated gameplay-session contract below is not fully implemented. Current pre-auth bootstrap and reconnect context remains in the implementation-local `sessionctx:*` family, and current Account sessions still use the legacy `session:auth:account:*` and `session:auth:tenant:*` projections. Canonical gameplay bindings belong under `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>`, with bounded gameplay lookup indexes under `session:game:index:*`; the target controller-uniqueness index is keyed by `{tenantId, playableStateNamespaceId, characterId}` and its value/evidence retains `{sessionId, gameInstanceId, bindingGeneration}` while `playableStateScope` remains binding context. The target binding owner and atomic monotonic takeover semantics are defined in [Session Behavior](./system-architecture-session-behavior.md#namespace-scoped-controller-transfer-session-02); this document records the Redis key and CAS consequences. That complete binding schema, its index obligations, session-only CAS, region-binding bridge, and cross-slot account/issuer-index repair and acknowledgement proof have not yet converged end-to-end. The current runtime still uses transitional session-context and tenant/identity lookup records, including the old `{tenantId, gameInstanceId, characterId}` character index shape, rather than the canonical global account and partitioned issuer index projections. This is implementation drift, not a transfer of ownership. The current runtime also derives Redis session TTL directly from `FIREMUD_AUTH_SESSION_EXPIRATION_MS`, with a `3,600,000` ms default, and does not enforce the target five-minute cap.

The three Account-owned target families are separate and incomplete: (1) the exact-token registry `session:auth:token:<tokenHash>`, (2) issuer/account/tenant/membership authority-generation projections under `session:auth:generation:*`, and (3) exact-input `session:connect-token:*` issuance-result projections. None of these target families, their freshness fences, or their fail-closed consumers may be treated as live merely because the target key names and validation rules are documented. Current runtime coverage and focused proof remain separate implementation gaps; current Account sessions use legacy projections and the current connect-token path uses its legacy result map as documented by the Account owner. The guarantees below are target-state contracts, not claims about the current runtime, until each family and its proof converge.

Gateway connect-token replay readiness is also not live: the current helper/configuration path does not consume `FIREMUD_GATEWAY_REPLAY_DOMAIN` or emit the tagged replay-domain keys, and the current writer emits only the untagged `gateway:connect-token:jti:<jti>` marker through the generic Cache-bound client. There is no current deny-marker, readiness, or `replayAdmissionFence` writer. Consequently, the target replay domain remains quarantined; the required migration inventory/readback, named Coordination client/ACL cutover, target-key readback, and cluster-reset/reopen proof are not implemented. These are current implementation-status facts; the target key, ownership, reset, and reopen contract is defined in [Gateway Architecture](./system-architecture-gateway.md#tenant-aware-edge-connect-token-gameplay-handshake) and [ADR 0029](./decisions/adr-0029-single-use-gameplay-connect-token-carriage.md).

## Redis Coordination Invariants

FireMUD uses Redis as a **transient, high‑performance coordination layer**, not as a primary source of truth. The following invariants apply to all coordination designs:

### Log of Record vs Coordination Buffer

Redis coordination keys form a long-running, measured-exposure **coordination buffer**, not the durable log of record for gameplay effects:

- Durable history for tick-driven outcomes (for example, “which effects were applied or abandoned for a given `(tenantId, gameInstanceId, playableStateScope, regionId, region_epoch, tickId, effectKey, targetAggregateType, targetAggregateId)`”) lives in PostgreSQL via the tick effect ledger and domain idempotency tables described in `system-architecture-tick-failures-and-operations.md` and `system-architecture-transactions.md`; `APPLIED`/`ABANDONED` are recorded only when that existing evidence policy permits terminalization, while inconclusive old-epoch work remains reconciliation-required under its original root `EffectId`.
- Coordination Redis holds volatile structures such as tick queues, `pending` sets, timers, region leases, tick event streams, and scheduler offsets; these structures are subject to measured unreplicated-write exposure and scoped resets as defined in this document and the Redis reset/runbook docs.
- Application and ops designs must not treat AOF contents or Redis key history as the primary log for audits, analytics, or long-term effect replay; those concerns belong in PostgreSQL-backed ledgers and domain stores.
- Redis Streams, lists, queue pointers, and wake signals are not durable event authority. Durable event capture, per-consumer delivery state, replay/reconstruction, retention, and backpressure remain owned by each flow's PostgreSQL outbox and worker/API contract; this hub records only the volatile Redis consequence.
- Target-state invariant, not a current runtime guarantee: `session:auth:token:<tokenHash>` is a narrow security exception whose exact-token registry record is authoritative for runtime protected admission and per-token revocation. A cryptographically valid JWT is denied and requires fresh authentication when its exact active, permitted registry record is reachable but absent, deleted, expired, or revoked; an unavailable registry is retryable `AUTH_UNAVAILABLE` and never permits reconstruction from the JWT or another local representation. This token family is distinct from Account's durable issuer, account, tenant, and membership generation family; those generations remain Account-owned. Redis and non-Account consumers cannot advance or recreate either family. Account may physically delete a record before its natural expiry only after the durable Account `PENDING_LOGOUT`/revocation fence or equivalent tombstone intent has committed; deletion is cleanup and never the revocation proof. For a destructive wipe, Account must durably invalidate old token authority before the wipe; cleanup may delete only old or stale projections, and replacement registry records are registered afterward and remain after registration. During reset recovery, Account alone may rebuild or re-project only its Account-owned `session:auth:token:<tokenHash>` values from durable token authority under the documented scope, cutover, and verification gates.
- Target-state invariant, not a current runtime guarantee: Account-owned exact-input `session:connect-token:*` issuance-result projections are a separate reset-sensitive projection family. Region- and tenant-scoped resets preserve exact records. A planned cluster reset that can drop them requires Account's durable operation/authority cutover and immutable pre-wipe handoff evidence before the wipe, then exact Account repair and readback before protected admission or the corresponding handshake reopens. An unexpected cold start or observed Redis loss has no pre-wipe gate to satisfy retroactively: protected admission and the handshake remain fail-closed while the affected projection is treated as untrusted and Account performs the owner-defined post-loss repair and exact readback under fenced recovery. Account alone may rebuild them from the durable issuance-result operation; consumers must not reconstruct one from a JWT, request fields, or Redis key presence. A missing, stale, changed, or ambiguous projection fails closed. This family is intentionally not a gameplay/session aggregate and is not covered by `--preserve-sessions` beyond its required preservation under narrower resets.
- Target-state invariant, not a current runtime guarantee: Account issuer, account, tenant, and membership generation projections are an approved global/account exception to ordinary Coordination Redis reset handling. Account durable authority remains the sole writer and source of truth; Redis is only a required projection. Region- and tenant-scoped resets preserve these projections and re-project/verify exact generations, while a cluster reset may discard them only after the Account repair/reset cutover, then must rebuild and verify them before protected admission reopens. The implementation limitations near the top of this document remain controlling until the projection and reset workflows are implemented and proved end to end.
- Every issuer-generation projection, including the canonical `session:auth:generation:issuer:<issuerId>` projection and the Game Session `session:game:auth:issuer-generation:v1:<issuerId>` consumer projection, atomically stores `lastAppliedSourceOutboxSequence` (the accepted source `outboxSequence`) and `lastAppliedIssuerGeneration` for its exact canonical `outboxStreamKey`, plus `lastAppliedSourceEventId` and `lastAppliedSourceEventDigest` as derived source-checkpoint evidence for every nonzero sequence. These `lastAppliedSource*` fields are projection evidence associated with the canonical `outboxStreamKey`/`outboxSequence` and the applicable `outboxCheckpoints`; they are not authority-tuple fields or JWT claims. For sequence `0`, the two source-event fields are omitted from the projection, not serialized as JSON `null`, an empty string, a zero digest, or another sentinel; the Account-owned zero-sequence checkpoint is the only evidence. For every positive sequence, both source-event fields are required non-null values in their canonical formats. Ordinary delivered events may apply only the next contiguous sequence. A higher delivered sequence is a gap and must quarantine the affected projection and reconcile from Account before advancing the watermark or generation. The sole exception is one Account-owned authoritative snapshot/reconciliation installation, which may atomically install the exact Account checkpoint and generation at its latest sequence without consuming skipped events; that installation must carry the exact snapshot/checkpoint evidence and operation identity, and the next delivered event must be exactly one greater than the installed sequence. For each stream, the projection also retains bounded duplicate evidence for the most recent accepted sequences, at minimum `{outboxStreamKey, outboxSequence, eventId, eventDigest}`; each evidence entry has a required non-null `eventDigest`, and no entry represents the zero-sequence baseline. An equal or lower sequence is a no-op only when that bounded evidence matches or an authoritative Account lookup for the exact `(outboxStreamKey, outboxSequence)` proves the same event identity and digest; a high-water mark alone is never duplicate proof. If the evidence has aged out, the lookup is unavailable, or same-sequence evidence conflicts, the projection is quarantined. A valid next event advances the complete persisted checkpoint even when set-if-greater generation semantics leave the generation unchanged. The gameplay binding's separate `{outboxStreamKey, outboxSequence}` freshness set does not replace this projection-local replay evidence. Projection recovery fails closed while the checkpoint is missing, stale, regressed, ambiguous, or quarantined, including any invalid omitted/null/sentinel representation.
- An empty Game Session issuer projection is an uninstalled and quarantined state, not an implicit zero-authority state and not permission to consume live events. Game Session, not Account, must install `session:game:auth:issuer-generation:v1:<issuerId>` from one Account-owned authoritative snapshot/reconciliation transaction for the exact `issuer/<issuerId>` scope and read back that installed derived projection. That transaction returns the exact checkpoint: `outboxStreamKey = account:auth-authority:v1:issuer/<issuerId>`, `lastAppliedSourceOutboxSequence` equal to the Account checkpoint's exact latest `outboxSequence`, and source `issuerAuthGeneration` from the same snapshot. For a nonzero sequence it also returns the exact source `eventId` and `eventDigest`; for sequence `0`, permitted only when the stream has no committed event, `lastAppliedSourceEventId` and `lastAppliedSourceEventDigest` are absent, and the Account-owned zero-sequence checkpoint itself is the evidence. The result also carries the source transaction or immutable bundle version, the exact checkpoint evidence, and the reconciliation operation identity; Game Session must not invent bootstrap event IDs, digests, sequences, or authority values locally. Before consuming events, Game Session atomically persists that complete checkpoint with the exact `issuerAuthGeneration` mapped to canonical persisted `lastAppliedIssuerGeneration`, stores matching `{outboxStreamKey, outboxSequence, eventId, eventDigest}` duplicate evidence only for a nonzero checkpoint, and reads back the installed projection. For a zero-sequence baseline, duplicate evidence is empty and the first consumable event must be sequence `1`; for a nonzero baseline, the next consumable event must be exactly `lastAppliedSourceOutboxSequence + 1`. Until the atomic installation and exact readback succeed, or if any applicable snapshot, source-checkpoint, event-identity/digest, or authority value is missing, stale, regressed, contradictory, or ambiguous, the projection remains quarantined and issuer-gated admission, reconnect, and revocation consumption fail closed.
- Canonical issuer snapshot mapping is exact across bootstrap, persistence, readback, replay, and recovery: Account's authoritative snapshot field `issuerAuthGeneration` maps one-to-one to the projection field `lastAppliedIssuerGeneration`. The latter is the only persisted projection field used for comparison and replay advancement; `issuerAuthGeneration` is the source snapshot/authority name and is not a second persisted alias or a local fallback. Every bootstrap install, event replay, exact readback, set-if-greater repair decision, and recovery acknowledgement must compare the mapped value together with the exact `outboxStreamKey`, `lastAppliedSourceOutboxSequence`, source event evidence, and operation/checkpoint evidence.
- Spring Cloud Gateway has one narrow Coordination Redis authority: one-use connect-token replay consumption under `gateway:connect-token:{gateway-connect-token-replay-v1}:jti:*`, browser-revocation deny markers under `gateway:connect-token:{gateway-connect-token-replay-v1}:deny:jti:*`, and the shared replay-readiness record under `gateway:connect-token:{gateway-connect-token-replay-v1}:readiness`. The readiness value carries the shared `replayAdmissionFence`. The Gateway fails closed when that replay authority is unavailable, owns the marker TTLs and reset contract, and must not expand this exception into ownership of gameplay sessions, Account auth state, or general coordination policy.

### Canonical Grant Authority-Stream Scope Codec

Account's non-public-grant authority stream uses one versioned codec for the grant `scopeId`, `outboxStreamKey`, and event `sourceScope`. The semantic five-field grant identity is owned by [Account API Contracts](./microservices/account-service/api-contracts.md#account-owned-playtest-grant-contract) and [ADR 0138](./decisions/adr-0138-expiring-playtest-grants-with-bounded-active-revocation.md); this subsection owns the shared byte encoding and parsing mechanics. Every non-public grant, including ordinary private and playtest grants, uses this lifecycle-bound identity; v1 has no ordinary-private four-field variant.

```text
segment(bytes) = ascii(canonical_decimal_count(byte_length(bytes))) + ":" + bytes
grantScopeBytes =
  segment(utf8("grantScope/v1"))
  + segment(utf8(accountId))
  + segment(utf8(tenantId))
  + segment(utf8(worldSlug))
  + segment(utf8(realmSlug))
  + segment(utf8(playtestLifecycleId))
scopeId = "grant/v1/" + base64url_without_padding(grantScopeBytes)
outboxStreamKey = "account:auth-authority:v1:" + scopeId
sourceScope = scopeId
```

`canonical_decimal_count(n)` is the existing unsigned ASCII base-10 byte-length grammar: zero is `0`, positive values have no leading zero, and no sign, decimal point, exponent, or whitespace. Every encoded and decoded field must be a non-empty valid UTF-8 byte sequence and must match the exact owner-issued canonical bytes for that field. `accountId`, `tenantId`, and `playtestLifecycleId` must be lowercase hyphenated canonical UUID text of exactly 36 ASCII bytes. `worldSlug` and `realmSlug` must be lowercase ASCII hyphenated slugs matching `[a-z0-9]+(?:-[a-z0-9]+)*` and measuring 1-120 bytes. The codec performs no trimming, case-folding, Unicode normalization (including NFC), mutation-digest/input normalization, or alternate serialization. Byte-distinct owner-issued identifiers remain distinct scope identities.

The maximum v1 owner-bound vector, measured in UTF-8 bytes and ordered as the tuple fields, is `(accountId=36, tenantId=36, worldSlug=120, realmSlug=120, playtestLifecycleId=36)`. The canonical identifier glossary and semantic grant owners publish these maxima; Redis consumes this maximum owner-bound vector as fixed input to every `grant/v1` codec operation and does not redistribute field ownership. A missing, zero, negative, unbounded, malformed, contradictory, alternate, or arithmetic-overflowing bound set fails closed. Redis does not invent slug or lifecycle limits, copy the semantic grant tuple into a second schema, or become the authority for any field.

For each member of this maximum owner-bound vector, the checked encoded maximum for its length-prefixed segment is `segmentMax(M) = digits(M) + 1 + M`. The marker segment remains the exact fixed UTF-8 `grantScope/v1` value. Checked arithmetic derives the maximum `grantScopeBytes` from that marker plus the five field segment maxima, then derives the maximum unpadded base64url payload using `base64urlMax(n) = 4 * ceil(n / 3) - ((3 - (n mod 3)) mod 3)`, the maximum `scopeId` by adding the fixed `grant/v1/` prefix, and the maximum `outboxStreamKey` by adding the fixed `account:auth-authority:v1:` prefix. Any intermediate or final overflow, including base64 expansion, is rejected before allocation.

The scope parser accepts only the exact `grant/v1/` prefix and canonical unpadded base64url payload. Before base64 decoding or allocating decoded storage it rejects an encoded payload, `scopeId`, or `outboxStreamKey` above its checked derived maximum. Its bounded decoder accepts only the exact `grantScope/v1` marker followed by exactly five field segments, consumes every encoded byte, and requires the re-encoded value to be byte-for-byte canonical. It parses each declared segment length and rejects a value above that field owner's maximum before reading or allocating the segment bytes. The encoder measures each actual field's UTF-8 bytes and rejects an over-limit field before constructing its segment or the complete payload. It rejects unknown versions, malformed or noncanonical lengths, invalid UTF-8, empty fields, truncated or trailing bytes, missing fields, a missing lifecycle ID, transformed or noncanonical field bytes, noncanonical or padded/base64-standard encodings, and the legacy four-field form. `sourceScope` must equal the codec-derived `scopeId`, and `outboxStreamKey` must equal the fixed prefix plus that same `scopeId`; grant-stream producers and consumers, stream-key projections and watermark ledgers, and reconciliation use the same helper rather than raw concatenation.

The Game Session lifecycle-qualified realm-grant index key builder consumes that exact codec result and emits `session:game:index:realm-grant:{tenantGameplayTag}:<grantScopeId>`, where `grantScopeId` is the complete five-field `scopeId`. Its callers supply the owner-issued tuple to the shared helper and never normalize, encode, concatenate, or parse `worldSlug`, `realmSlug`, lifecycle, tenant, or account fields independently. Session writers/readers, shard-local Lua callers, reconciliation, and reset tooling all reuse the same builder; the tenant hash tag selects the Redis Cluster slot but neither replaces nor changes the complete grant identity encoded in `grantScopeId`.

Pre-v1 activation is a versioned direct cutover, not a dual-read migration. Before any producer, consumer, or realm-grant index reader enables `grant/v1`, Account fences mutation and admission for every affected non-public grant scope and inventories the complete retained grant set in an immutable Account v1 grant inventory/checkpoint. A fenced migration adapter may transform a retained legacy four-field record into the canonical five-field v1 tuple only after objective evidence establishes one unambiguous current lifecycle; the v1 codec itself always rejects an untransformed four-field grant. It materializes the five-field Account record and its exact current grant version, and creates the new v1 stream snapshot/checkpoint under the codec-derived key; missing, ambiguous, or contradictory lifecycle evidence fails closed, is invalidated or quarantined, and requires deliberate regrant. Mapping retained grant data never upgrades legacy grant-bearing JWTs, issued-token registry records, authority tuples, or other authority artifacts: Account invalidates those artifacts before activation, and restored access requires a fresh lifecycle-bound grant read and token reissue. Each consumer carries no authority or sequence from an old key into the new key: while still fenced, it bootstraps the new stream and watermark from the exact Account v1 snapshot, rebuilds the lifecycle-qualified realm-grant index from that same complete inventory, and reads back the exact expected set and checkpoint. Throughout enumeration, build, and exact readback, the migration operation is the sole grant-index writer: every affected non-migration writer, including bind/takeover session-index updates, revocation/termination, reconciliation, and legacy producers, remains fenced or quiesced unless one atomic switch of all those writers to the versioned layout is proven. The activation gate switches all affected producers/readers only after Account and every required consumer prove complete v1 inventory, checkpoint, and index convergence. A crash, gap, mismatch, incomplete consumer, active legacy producer/consumer/index reader, runtime fallback, mixed-format path, or concurrent non-migration write keeps the affected scopes fenced and resumes the same migration operation. A migration or audit inventory may read retained legacy rows solely as non-authoritative evidence; that intentional read is not an active legacy consumer and does not itself block activation. Legacy stream, watermark, and index records remain non-authoritative audit/migration evidence and are removed only after v1 activation and replay-idempotency proof complete; no runtime fallback or mixed-format processing is permitted.

The codec invariants are `decode(encode(tuple)) == tuple` and distinct canonical tuples produce distinct `scopeId` values and distinct stream keys. Changing any tuple field therefore changes the scope, stream, and per-stream watermark identity; no consumer may merge or fall back across those identities. Focused proof must include the maximum owner-bound vector `(36, 36, 120, 120, 36)`, each UUID at exactly 36 bytes and at 35/37 bytes, each slug at 1 and 120 bytes and at 121 bytes, an over-limit declared segment length rejected before segment read/allocation, an encoded payload one byte above its derived maximum rejected before base64 decode/allocation, and scope/key values above their derived maxima. It must also cover invalid UUID/slug grammar, invalid UTF-8, noncanonical lengths, marker/trailing-byte failures, lifecycle omission, legacy four-field input, tuple distinctness, direct-cutover restart and exact retry, complete v1 snapshot/index readback before activation, preserved admission fencing on incomplete or contradictory migration evidence, and no duplicate or falsely gapped authority processing after activation. Numeric legacy IDs, four-field grants, and noncanonical/over-limit slugs are migration inputs that fail closed before codec use, not alternate codec forms. Select and report this focused validation through the [validation and runtime-proof workflow](../developer-workflows/validation-and-runtime-proof.md); this paragraph states proof obligations only and does not claim execution results.

Legacy inventory/readback is permitted only as a bounded, read-only evidence operation while the affected scopes are fenced and quarantined. It must not write either legacy or target keys, act as a runtime fallback, or mix legacy and v1 processing; only the fenced migration operation may materialize the canonical v1 snapshot and index.

- **Coordination timeline = epoch-scoped `(region_epoch, tickId)`**
- The identity definitions, ownership protocol, takeover reconciliation, outage behavior, and reset-versus-handoff rules are owned by [Tick System: Region Authority and Tick Executor](./system-architecture-ticks.md#region-authority-and-tick-executor). This Redis document records only the local key, token, script, and reset consequences.
- For each `<tenantId, gameInstanceId, regionId>` the canonical coordination timeline is the pair `(region_epoch, tickId)`. Tick IDs are scoped to `region_epoch`, not globally continuous across a reset; each new epoch starts its real tick sequence at `tickId=0`.
  - `region_epoch` lives in PostgreSQL and is advanced by the tick control plane when a scoped coordination reset occurs (or when explicitly performing topology/maintenance operations that intentionally sever the old timeline for a region).
  - `tickId` is monotonic per `<tenantId, gameInstanceId, regionId>` within a given `region_epoch`, starts at `0` for the first real tick in that epoch, and is carried on all tick-driven calls and ledger entries.
- **Bootstrap vs stream**
  - The authoritative **baseline** for `(region_epoch, tickId)` comes from the active Game Session owner surface described in [Tick System: Region Authority and Tick Executor](./system-architecture-ticks.md#region-authority-and-tick-executor): target state uses `GetRegionTickStatus` backed by a PostgreSQL `RegionStatus`-style table, while current live uses its instance-scoped ownership/status surface. A reset durably establishes the new epoch baseline before Redis `tick:{tenantRegionTag}:meta` is initialized for normal progress. New consumers and operational tooling must obtain their initial view from the owner surface rather than inferring it from Redis keys.
  - Long‑lived consumers then follow `StreamTickHeartbeats` as the authoritative progression of the timeline after that baseline; if a heartbeat disconnects or an epoch bump is observed, they reconcile using the control API plus durable domain state before resuming.
  - Redis coordination structures (including `tick:{tenantRegionTag}:*`, timers, retries, tick event streams, and scheduler offsets) are treated purely as volatile buffers; their measured unreplicated-write exposure is documented as `redis_unreplicated_write_window_slo_ms` in `system-architecture-redis-operations.md` and they are never considered the primary source of truth for epoch or tick counters. Class-specific outcomes remain governed by [ADR 0058](./decisions/adr-0058-class-specific-redis-loss-outcomes.md), including when that SLO is breached.
  - Tick-scoped Redis staging state (for example `tick:{tenantRegionTag}:pending`, effect batches, and other data created for one in-flight tick) and all corresponding PostgreSQL tick ledger rows conceptually belong to exactly one `(region_epoch, tickId)` on this timeline.
  - Region-scoped source structures such as `tick:{tenantRegionTag}:queue:*`, `timer:{tenantRegionTag}`, `retry:{tenantRegionTag}`, `tick-executor-lease:{tenantRegionTag}`, tick event streams, and scheduler offsets are primarily epoch-scoped coordination state:
    - They belong to the current `region_epoch`.
    - They carry eligibility/order metadata that may later be materialized into a specific `(region_epoch, tickId)` when a batch is staged.
    - Reset/replay tooling and Lua validation must therefore distinguish epoch-scoped source state from tick-scoped staged state.
  - A single **per-region metadata key** captures the Redis-side view of this timeline for coordination scripts:
    - `tick:{tenantRegionTag}:meta` is a hash that stores at least:
      - `region_epoch` – the epoch currently considered valid for this `<tenantId, gameInstanceId, regionId>` in Redis.
      - `current_tick_id` – the highest **staged** `tickId` for this region as observed by the tick executor’s coordination scripts. A fenced recovery baseline may use `-1` with `current_tick_state = APPLIED` before the first tick is staged. It is a monotonic guard for Redis writes only; it is **not** the source of truth for “last committed tick”, and the durable PostgreSQL `lastCommittedTickId = -1` remains a separate value.
      - `current_tick_state` – the Redis-side execution state for `current_tick_id`. Allowed values are:
        - `STAGED` – Redis `pending`/queue state exists for this tick and hot-path scripts may continue to add idempotent entries for the same tick.
        - `RESOLVING` – durable domain/application work for this tick is in progress or being reconciled; no newer tick may be staged yet.
        - `APPLIED` – every required participant for this tick has explicit durable terminal evidence: its participant outcome is `APPLIED` or `ABANDONED` in the PostgreSQL-backed ledger or an equivalent durable terminal record, and the existing evidence policy permits the tick to be terminal. The fenced recovery baseline uses `current_tick_id = -1` with `APPLIED` as its terminal no-prior-tick marker before the first tick is staged. An inconclusive old-epoch participant keeps the tick non-terminal and reconciliation-required. The mere presence of a reconciliation-backlog item is not evidence of a terminal outcome. Handler-level replay/no-op results are recorded separately as `replay_ok` attempt outcomes and do not satisfy this requirement by themselves.
        - `ABANDONED` – the tick was intentionally terminated for the current epoch only after the owner/fenced recovery decision and evidence policy permit that terminal state (for example due to reset/recovery); no more work for that `(region_epoch, tickId)` may be staged through hot-path scripts. Reset scope alone does not authorize bulk terminalization.
      - `current_tick_terminal_at_ms` – absent/NULL while `current_tick_state` is `STAGED` or `RESOLVING`; set exactly once when the current tick first terminalizes as `APPLIED` or `ABANDONED`, and cleared/absent again when a newer tick is staged. Exact retries of that same terminal transition preserve the stored value, while a conflicting caller value is a non-mutating idempotency conflict. It is used for observability and bounded cleanup only, never for correctness decisions inside Lua.
    - Illustrative Redis hash contents:

      ```text
      HGETALL tick:{tenantRegionTag}:meta
      region_epoch               14
      current_tick_id            9285
      current_tick_state         RESOLVING
      current_tick_terminal_at_ms <absent/NULL>
      ```

    - `tick-executor-lease:{tenantRegionTag}` is separate from this metadata: its value is only the opaque Redis liveness token and its TTL. It never stores or encodes `region_epoch`. The epoch is semantic timeline state, sourced by the tick owner from the durable reset/RegionStatus contract and carried separately to Lua; Lua compares that expected epoch with the `region_epoch` in `tick:{tenantRegionTag}:meta`. Possessing the token proves only Redis liveness possession, while matching the epoch proves that the operation belongs to the current semantic timeline.
    - Lease acquisition is the sole exception to the active-token precondition: the acquire operation supplies no expected active token and atomically claims only an absent or expired lease key with a unique opaque token and bounded TTL, returning bounded `ACQUIRED` or `BUSY`. This liveness result does not establish `region_epoch`; all post-acquisition scripts supply and validate both the token and the separate epoch.

    - The canonical Redis-side state machine for a region is:
      - During reset recovery, the fenced recovery owner initializes and verifies `tick:{tenantRegionTag}:meta` with `current_tick_id = -1` and `current_tick_state = APPLIED`. This metadata-only baseline does not authorize hot-path recovery or staging, and it remains distinct from durable PostgreSQL `lastCommittedTickId = -1`.
      - After the owner-defined recovery release, the first fenced staging CAS must accept only `requestedTickId = 0` and atomically advance exactly `-1 → 0` and `APPLIED → STAGED`. No other requested tick may treat `-1` as an ordinary terminal prior tick; subsequent ticks follow the ordinary immediate-next-tick transition.
      - A genuinely missing `meta` key, outside reset recovery, may be initialized only when the caller presents the authoritative scheduler/RegionStatus baseline, proves recovery is inactive, and explicitly proves that the exact environment and deployment are a documented non-reset profile. `requestedTickId` must equal the durable authority's first eligible tick: target-state `RegionStatus.lastCommittedTickId + 1`, or the current-live committed-tick equivalent from the ownership/progress authority, with the existing epoch/fence and unfinished durable batch, ledger, or source-claim guards. In addition, durable evidence must explicitly prove that all prior batches, effects, and commands are evidence-qualified terminal or that no unresolved work exists. Without that proof, the region remains fenced and the metadata is not initialized. The write then sets `current_tick_id = requestedTickId` and `current_tick_state = STAGED`.
      - An existing `meta` key must contain a valid `region_epoch`, `current_tick_id`, and recognized `current_tick_state`. If `current_tick_id` is unset while any other metadata is present—including a nonterminal, unknown, or contradictory state—the staging request returns non-mutating `INVALID_ARGS`; it does not repair or mutate the record, and the region remains fenced.
      - For an ordinary terminal tick with `current_tick_id >= 0`, `current_tick_state in {APPLIED, ABANDONED}` with no newer tick staged:
        - The next winning executor may initialize or advance the meta record to `current_tick_id = requestedTickId`, `current_tick_state = STAGED` only when `requestedTickId = current_tick_id + 1` and is exactly the immediate next scheduler/control-plane tick derived from PostgreSQL RegionStatus for that region.
      - `STAGED -> RESOLVING`:
        - The first script or caller that hands staged effects to durable domain/application processing flips the state to `RESOLVING`.
        - Replays for the same tick must treat `STAGED` and `RESOLVING` as the same logical in-flight tick and may only add idempotent effect entries for that same `current_tick_id`.
      - `RESOLVING -> APPLIED`:
        - Only after the durable tick ledger or equivalent durable terminal records for `(tenantId, gameInstanceId, playableStateScope, regionId, region_epoch, tickId)` contain explicit `APPLIED` or `ABANDONED` evidence for every required participant and the existing evidence policy permits terminalization. An inconclusive old-epoch participant keeps the tick non-terminal. A reconciliation-backlog item may identify work still needing reconciliation, but its presence alone cannot establish `APPLIED`; replay/no-op is a handler attempt outcome, recorded as `replay_ok`, not a ledger status.
      - `RESOLVING -> ABANDONED`:
        - Only after the control plane or recovery tooling has made an explicit, evidence-qualified terminal decision to abandon the tick for the current epoch; reset scope alone is insufficient.
      - `APPLIED` or `ABANDONED` for tick `T`:
        - Cleanup may delete `pending`, retry markers, and other Redis-only remnants for tick `T`.
        - `APPLIED`/`ABANDONED` marks the durable terminal state only; it does not by itself prove the region is no longer in flight for scheduler purposes.
        - Staging for tick `T+1` is allowed only after tick `T` is both terminal in Redis meta and `coordination_cleared` under the scheduler/runtime rules in `system-architecture-ticks.md`.
    - Tick- and epoch-aware Lua scripts:
      - Read `region_epoch` (and when needed `current_tick_id`) from this key and compare it to the expected epoch/tick supplied from PostgreSQL/lease context.
      - Apply the canonical lease-renewal and staging result mapping in [Redis Lua Patterns](./system-architecture-redis-lua-patterns.md#canonical-region-lease-and-tick-staging-result-mapping). Only `STALE_LEASE`, `STALE_EPOCH`, `STALE_LOCK`, and `OUT_OF_DATE_TICK` authorize abandoning stale work, reacquiring under the resulting epoch/lease, and re-bootstrapping from the authoritative timeline. `INVALID_ARGS` remains fenced and must be alerted for owner/configuration repair; it must not trigger stale retry.
      - Treat `current_tick_state` as the gate for hot-path progress:
        - Staging scripts may create or extend `pending` only when `requestedTickId == current_tick_id` and `current_tick_state in {STAGED, RESOLVING}`, or when they are initializing an ordinary next tick from a nonnegative terminal prior state; the recovery `-1` baseline uses only the explicit `-1 → 0` CAS above.
        - Hot-path scripts must never advance directly from `STAGED`/`RESOLVING` to a newer `current_tick_id`; only a terminal `APPLIED` or `ABANDONED` state plus separate scheduler-observed `coordination_cleared` unlocks the next tick.
    - Schedulers and operators:
      - Obtain their authoritative baseline for `(region_epoch, tickId)` from PostgreSQL RegionStatus/tick effect ledger and heartbeats, not from `current_tick_id`.
      - On a normal cold start with empty Coordination Redis and no active recovery, the next winning tick executor initializes `tick:{tenantRegionTag}:meta` during hot-path staging from PostgreSQL `RegionStatus` only when `requestedTickId` is the durable first-eligible tick, the caller explicitly proves that the exact environment and deployment are a documented non-reset profile, and the caller presents durable proof that all prior batches, effects, and commands are evidence-qualified terminal or that no unresolved work exists; without any of those guards or that proof, the region remains fenced. Schedulers and operators do not treat missing `meta` as a manual pre‑seeding task. While reset recovery is active, missing metadata keeps the scope fenced and hot-path staging must not create or recreate it until the canonical recovery release in [Redis Reset & Recovery](./system-architecture-redis-reset-and-recovery.md).
      - During reset recovery, the reset owner first establishes the durable new epoch, then initializes and verifies `tick:{tenantRegionTag}:meta` from that same authoritative baseline while the scope remains fenced. Only after that readback and the owner-defined recovery gates complete may the scope be released. The reset lifecycle and release prerequisites remain canonical in [Redis Reset & Recovery](./system-architecture-redis-reset-and-recovery.md#canonical-reset-sequence-boundary); this hub records only the local metadata and stale-key consequences.
      - Treat Redis `pending` contents as an implementation detail of the hot path, not as proof of durable convergence. The durable proof that a tick is safe to move past is explicit terminal `APPLIED` or `ABANDONED` evidence for every required participant in the PostgreSQL ledger or equivalent durable terminal records; reconciliation-backlog presence and `replay_ok` attempt outcomes are insufficient by themselves. An inconclusive old-epoch row remains non-terminal under its original root `EffectId`; it cannot mutate current `tick:{tenantRegionTag}:meta` or block an otherwise evidence-permitted current-epoch terminalization, though it may still block unsafe next-tick progression, reset-scope convergence, or reopening. A terminal outcome for older or historical work remains in the durable ledger/reconciliation records under its original epoch and root effect identity; it must never overwrite or regress the current `tick:{tenantRegionTag}:meta`. Tick metadata updates remain limited to the current epoch's scheduler timeline; only a terminal outcome for that timeline may set `APPLIED` or `ABANDONED`.
      - Recovery after coordination loss or reset does **not** reconstruct old ticks by silently restaging them through normal hot-path scripts. Recovery completes or abandons older work from durable manifests, ledger rows, and reconciliation backlog state only where the evidence policy permits; those historical terminal outcomes remain durable reconciliation state and do not update the current Redis tick metadata. Inconclusive old-epoch work remains non-terminal reconciliation work under its original root `EffectId`; it may prevent newer ticks from staging when that progression is unsafe, but it is not a reason to mutate or regress the current metadata or to withhold an otherwise permitted current-epoch terminalization.
- Redis-local split-brain and reset consequences:
  - `tick-executor-lease:{tenantRegionTag}` stores only the opaque lease token; `region_epoch` is read from the separate `tick:{tenantRegionTag}:meta` view and/or the durable reset contract. Region lease and coordination Lua receives both values separately, compares them before mutation, and follows the canonical result mapping in [Redis Lua Patterns](./system-architecture-redis-lua-patterns.md#canonical-region-lease-and-tick-staging-result-mapping).
  - After a reset, keys carrying an older `region_epoch` are ignored or explicitly cleaned up by reset tooling; Redis does not choose the durable epoch or authorize a new owner.

- **Non‑authoritative for game data**
  - Canonical game state (accounts, entities, items, rooms, instances) lives in PostgreSQL and domain services.
  - Redis holds **volatile coordination state**: tick queues and locks, timers, session bindings, automation hints, retry metadata, and similar.
  - Losing coordination state within a bounded window must not create irreversible financial effects, cross‑tenant data leaks, or unfixable domain inconsistencies.

- **Measured coordination-write exposure and class-specific outcomes**
  - In production-like and other non-ephemeral profiles, Coordination Redis is configured with AOF and measured replication/failover evidence. An explicitly ephemeral single-node coordination stack may omit AOF and opts out of the measured exposure/replay guarantees; it must remain reset-tolerant and must not be used to claim those SLOs. `redis_unreplicated_write_window_slo_ms` is an environment exposure target, not a product RPO or permission to lose every write made during that window; `ticks_exposed = ceil(window_ms / tick_interval_ms)` is diagnostic only.
  - Accepted commands, staged effects/retries, correctness-bearing timers, sessions/leases/hints, and premium/financial/external operations follow the distinct durable outcomes in ADR 0058. Tick ledgers and domain guards drive correctness-bearing effects to `APPLIED` (with `REPLAY_NOOP` only as an outcome/reason) or evidence-qualified `ABANDONED`; inconclusive work remains nonterminal and reconciliation-required rather than being silently lost or duplicated.
  - A breach increases durable reconstruction, explicit terminalization, or operator-reconciliation scope and reports affected backlog counts. It never weakens financial, security, isolation, or no-resurrection invariants.
  - Flows that cannot tolerate Redis loss (for example, real-money purchases, cross-tenant transfers, or unique external side effects) use durable domain mechanisms and may use Redis only for optional coordination.

- **Idempotent replay and monotonic guards**
  - Tick and session scripts are designed so that:
    - AOF replay cannot double‑apply logical effects, and
    - Replays after failover respect monotonic guards such as `tickId`, `generation` counters, and lease/lock tokens.
  - Lua scripts must treat Redis as the single coordination state for their keys, re‑deriving their desired state from current contents and arguments rather than relying on in‑process history.

- **Region authority**
  - For each `<tenantId, gameInstanceId, regionId>` there is at most **one active tick executor** at a time, guarded by a region‑scoped lease key.
  - All tick queues, locks, timers, and pending sets for that region live in a single hash‑slot‑compatible keyspace (see [Key Naming and Shard Discipline](#key-naming-and-shard-discipline)).

- **Session binding**
  - Session keys in Redis bind player connections and tick participation to authenticated platform identities. They do not own actor cooldown state.
  - Session binding is monotonic: once a session is rebound or terminated, old bindings are not resurrected, even under replay or measured coordination loss.
- Session keys are **not** the authoritative runtime record for region-local gameplay participation. To preserve shard locality in Redis Cluster:
  - `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>` remains the authoritative record for connection identity, reconnect eligibility, auth/session CAS fields, and desired gameplay attachment generation.
  - Region-local gameplay attachment is authoritative under the region-scoped key family `tick:{tenantRegionTag}:session-binding:<entityId>`, owned by Game Session and mutated only by region-lease scripts.
  - Any region list or attachment summary mirrored inside `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>` is advisory/reconnect metadata only and must not be used as the sole authority for gameplay admission or command routing.
- Because the physical session-record address contains `gameInstanceId` while the controller identity does not, a replacement is a durable rekey/transition rather than an alias. The controller index keyed by `{tenantId, playableStateNamespaceId, characterId}` is the canonical uniqueness and lookup projection; the target `session:game:*` record and character-index transition carry the same desired `{sessionId, gameInstanceId, bindingGeneration}` plus a durable transition identity. An initial tenant-local session/index CAS may publish only a provisional, non-admissible candidate. That candidate reserves the target for the transition but never authorizes gameplay; readers continue to resolve the prior admitted binding until the final tenant-local CAS commits. Separate exact account-index, issuer-index/capacity, and region-lease bridge operations and readbacks durably acknowledge that same transition, session/runtime identity, and `bindingGeneration`; the final tenant-local session/index CAS exact-compares every required acknowledgement and target-record readback, then admits the candidate at the controller linearization point. Readers start from the controller index but require the canonical session and durable binding records plus exact runtime, generation, lease, acknowledgement, and readback evidence, so neither the index alone nor a stale old-instance record can authorize. On a definitive pre-commit abort, Game Session's fenced cleanup terminalizes or rolls back every transition-owned account/issuer repair obligation created before provisional publication and every corresponding Redis projection or reservation written before the abort only with exact transition identity, candidate `bindingGeneration`, and applicable account-index, issuer-reservation, and transfer-preparation fences; the prior admitted binding and any newer generation remain untouched. A terminal abort requires terminal evidence for every such state, while unavailable or mismatched cleanup remains ambiguous under the same operation rather than using blind cleanup. An ambiguous outcome keeps the candidate non-admissible and reconciles commit or complete rollback under the same durable transition identity. Old admitted records, index members, and region bindings are cleaned only after the final CAS succeeds; crash recovery resumes or reconciles the same durable transition while the target remains non-admissible, never by blind aliasing, delete/create, or wildcard scan. The complete protocol remains owned by [Session Behavior](./system-architecture-session-behavior.md#namespace-scoped-controller-transfer-session-02); these are its Redis storage consequences.
- [ADR 0122](./decisions/adr-0122-stable-playable-state-namespaces-for-runtime-replacement.md) does not turn these volatile Redis keys into durable playable-state identity. Runtime session and region keys remain scoped to `gameInstanceId`; durable character/progression state is resolved by `playableStateNamespaceId` with active-instance authorization, and Redis presence or an echoed remap identifier cannot authorize replacement or prove mapping application. [ADR 0123](./decisions/adr-0123-database-authoritative-temporal-coordinated-world-lifecycle.md) keeps lifecycle row/epoch and cleanup completion in the owning database.
- This split exists specifically so same-type non-edge workers can take over after restart. If a value is required to preserve gameplay binding, region participation, or resumable command eligibility across Game Session/Game Logic restart, it must be externalized through these authoritative Redis/PostgreSQL-backed structures rather than hidden in process memory.

The **Redis Design Checklist** (`system-architecture-redis-design-checklist.md`) turns these invariants into concrete review steps for new prefixes, scripts, and flows.

### Redis Availability, Consistency, and Safety Guarantees

From an application perspective:

- Coordination Redis is expected to be **highly available** within the limits of the chosen profile (for example, `production_clustered`).
- `redis_unreplicated_write_window_slo_ms` is defined at the Coordination Redis deployment, environment, and active configuration/ruleset scope. Tenant, game, and region are diagnostic dimensions in control-plane and structured-log evidence for affected work, not independent SLO values.
- Lua scripts and domain idempotency guarantees ensure that replay and partial loss of coordination keys do not:
  - Double-apply critical effects.
  - Violate cross-tenant isolation.
  - Break financial or security invariants.

## Atomicity and Concurrency Control

Multi-key coordination operations in FireMUD must remain **shard-local, idempotent, and lease-guarded**:

- All mutating operations on coordination prefixes (tick queues, `pending` sets, timers, retry structures, locks, leases, and session keys) always go through owned **typed key and mutation helpers**. Raw Redis commands are prohibited. Registered Lua is mandatory for atomic multi-key behavior and may be used for a single-key mutation only when an explicitly documented atomic guard or compare-and-set contract requires it; ordinary single-key mutations use typed helpers without Lua. Registered scripts:
  - Validate lease tokens, lock tokens, and monotonic guards (`tickId`, epochs) before writing.
  - Operate only on keys that share the same hash tag and cluster slot.
  - Are deterministic and idempotent with respect to their `KEYS`/`ARGV` arguments and current Redis state.
- Application code and maintenance tooling must **not** issue ad-hoc multi-key Redis commands (including `MULTI/EXEC`) over coordination prefixes.
- Cross-region workflows are implemented as per-region operations or higher-level sagas, not as cross-region Redis transactions.

The detailed scripting rules and categories (region-lease scripts, session-only scripts, automation scripts, maintenance scripts) are defined in `system-architecture-redis-lua-patterns.md`, and the concrete checks to apply during design review are captured in the Lua section of `system-architecture-redis-design-checklist.md`.

## Session Keys and Gameplay Binding

Game Session uses Redis for two related but distinct session concerns:

- **Bootstrap/pre-auth transport context** is created when a socket connects and before gameplay authentication completes. It contains only unauthenticated bootstrap scope such as tenant, locale, or initial game-instance hints. Gameplay commands must treat this context as unauthenticated until `LOGIN` succeeds.
- **Authenticated gameplay session state** is created or promoted after successful `LOGIN` and `PLAY`. The canonical target key family for this state is `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>`.

The authenticated gameplay key family is the canonical session-state contract.

Authenticated gameplay session keys capture:

- Socket binding metadata and transport details.
- Active `characterId` / `tenantId` context plus the target resolved `playableStateNamespaceId` and server-derived `playableStateScope` for the character binding. The target one-controller key is `{tenantId, playableStateNamespaceId, characterId}`; the binding value/evidence retains `sessionId`, `gameInstanceId`, and `bindingGeneration`.
- Target-state authenticated-session contract (not a current runtime guarantee): server-side auth token identity used for Account and other control-plane calls on behalf of this session (`authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, and `tokenGeneration`), so planned refresh, resume, and mid-session revocation checks can be performed without exposing JWTs to gameplay clients. For the exact active registry record, `authTokenIssuedAt == registry.iat`, `authTokenExpiresAt == registry.exp`, and `tokenGeneration == registry.tokenGeneration`; these are equality checks, not lower/upper-bound checks against Redis TTL or the current time.
- The protected `rebindHandle`, immutable continuity anchor `continuityBindingExpiresAt`, complete `membershipBaseline`, and complete `authorityTuple` are required to complete a restart or resume rotation and verify that gameplay admission authority still exists without exposing the private delegation JWT to gameplay clients. The baseline includes the exact one-tenant `membershipBaseline.membershipVersion` map `{tenantId: version}` from the same Account snapshot as its lifecycle state and membership authority generation. The exact nested tuple field is `authorityTuple.membershipAuthorityGeneration`; it is stored as part of the complete tuple and is never replaced by a standalone tuple member. A duplicate top-level `membershipAuthorityGeneration` field outside the baseline and tuple is forbidden; readers and CAS scripts reject it rather than merging it with or choosing precedence over the nested fields. The Account-issued handle binds the exact token hash, signed `jti` and `nbf`, token lineage, gameplay binding, unchanged complete `membershipBaseline`, complete canonical `outboxCheckpoints` set, authority tuple, and exact `issuanceFence` captured for that issuance; only Account may open and validate it, and Game Session treats it as opaque. Account's `GetTenantMembershipForRuntime` response remains scalar; only `membershipBaseline.membershipVersion` wraps that value in the exact one-tenant map for the persisted and cross-service gameplay carrier.
- The binding also stores the complete canonical `outboxCheckpoints` set: one exact `{outboxStreamKey, outboxSequence}` entry for every applicable authority stream, canonicalized in stream-key order. It is independent freshness evidence, not an aggregate maximum or an authority replacement. Binding refresh atomically replaces the complete `membershipBaseline`, `authorityTuple`, and complete checkpoint set from one Account-issued binding lease; rebind, token rotation, and their retry carriers carry the baseline unchanged and compare the complete object, including the exact tenant key, value, and map shape of `membershipBaseline.membershipVersion`, never a scalar, omitted map, merged value, or aggregate-only checkpoint. `membershipBaseline.membershipVersion` remains an independent predicate from both `membershipBaseline.membershipAuthorityGeneration` and `authorityTuple.membershipAuthorityGeneration`.
- Tick-region participation metadata (for example active region bindings and reconnect context). Per-entity command queues remain under `tick:{tenantRegionTag}:queue:<entityId>` and are reset-tolerant coordination state, not durable session payload.
- Session-local coordination metadata (for example reconnect state, transport-level pacing, and other per-connection ephemeral fields).

The authenticated gameplay payload is one complete canonical contract, not a compatibility family. Every authenticated gameplay binding must carry `schemaVersion=2`; a missing version, `schemaVersion=1`, or any other unsupported version fails closed before the record can be used for refresh, resume, rebind, takeover, admission, backend authorization, or recovery. There is no reduced authenticated payload for a non-resumable binding: terminal or cleanup state does not relax the schema or become retained admission evidence, and fresh `LOGIN`/`PLAY` is required to establish a new binding. Bootstrap/pre-auth context remains unauthenticated and is not an authenticated gameplay payload.

`schemaVersion=2` is the canonical authenticated-session contract and requires the same common fields plus exactly ten authentication-specific fields: `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, `tokenGeneration`, `issuanceFence`, `rebindHandle`, `continuityBindingExpiresAt`, the complete `membershipBaseline`, the complete `authorityTuple`, and the complete `outboxCheckpoints` set. Readers, refresh, resume, rebind, admission, recovery, and CAS scripts must reject any authenticated record whose version is not exactly `2` or whose required field is absent, malformed, or unavailable for its declared type. The authentication identity, time, generation, fence, handle, and continuity fields are canonical scalar fields; `membershipBaseline` must instead be one complete same-snapshot object whose nested `membershipBaseline.membershipVersion` is exactly the one-tenant map `{tenantId: version}`, while `authorityTuple` is the complete object and `outboxCheckpoints` is the complete set. A missing baseline member or a multi-tenant, differently keyed, aggregate, scalarized, or otherwise malformed nested map fails closed. `membershipBaseline.membershipAuthorityGeneration` and `authorityTuple.membershipAuthorityGeneration` are both required in their owning objects and are compared independently; a duplicate standalone top-level `membershipAuthorityGeneration` is an invalid extra field and is rejected even when its value matches.

The rotation `installationIdentity` is not an additional `schemaVersion=2` authenticated gameplay field. It is candidate-installation metadata carried by the lease-scoped acknowledgement and durable installation-attempt carriers, with the established shape `{rotationOperationId, leaseId, gameplayBindingId, installationFence}`. The durable installation attempt is keyed by the existing `rotationOperationId`; the first session-only CAS and the second fenced session-only CAS must carry and exact-compare that same linkage before the candidate can become admissible. No `installationIdentity` member, including `rotationOperationId`, is retained as an undeclared field in the final admissible gameplay binding. The `INSTALLING` candidate remains non-admissible until the matching acknowledgement and second fenced CAS complete.

Target-state token rotation contract (not a current runtime guarantee): Game Session may install a replacement only with a current token-identity fence covering the expected prior `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, `tokenGeneration`, and `issuanceFence`, the expected prior complete `membershipBaseline`, complete `authorityTuple`, exact `outboxCheckpoints` set, and the binding/rebind lineage. At the first session-only CAS linearization point, the prior token's `authTokenExpiresAt` must equal the active registry `exp` and be later than the trusted current time; the prior `authTokenIssuedAt` and `tokenGeneration` must equal the same registry record's `iat` and `tokenGeneration`. An elapsed prior JWT is rejected even if its Redis session record remains. That CAS writes the replacement as a non-admissible `INSTALLING` candidate and atomically carries the replacement `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, `tokenGeneration`, `issuanceFence`, `rebindHandle`, complete refreshed `membershipBaseline`, complete `authorityTuple`, exact `outboxCheckpoints`, and installation identity bound to the durable installation attempt's existing `rotationOperationId`. While the candidate is `INSTALLING`, Account may finish predecessor-authenticated calls admitted before the claim until `predecessorUsableUntil = min(registry.exp, deadlineForAlreadyStartedCalls)`, but rejects new predecessor-authenticated Account calls; Game Session issues no new Account calls and keeps the candidate non-admissible. After exact readback, the durable installation attempt may advance to `BINDING_INSTALLED`, but that state and the `INSTALLING` candidate remain non-admissible. Game Session then sends an acknowledgement bound to the same installation identity and stable idempotency tuple/digest. Only a durably committed matching acknowledgement, including an exact retry after timeout-after-commit, permits the second fenced session-only CAS to carry and exact-compare the same `rotationOperationId`, leaseId, gameplayBindingId, and installationFence, mark the candidate `INSTALLED`, and admit it for new backend calls. A stale, mismatched, unavailable, or ambiguous acknowledgement, or a failed second CAS, produces no admissible partial update and invokes the existing abort/retire path; rotation cannot extend `continuityBindingExpiresAt` or `resumeDeadline`. The predecessor record remains retained through `predecessorRetentionUntil = registry.exp + FIREMUD_AUTH_SESSION_SAFETY_MARGIN_MS`, but is unusable for new calls after `predecessorUsableUntil` even while retained. Account may delete it earlier only after committing a durable exact-token retirement fence or tombstone bound to the predecessor identity, replacement installation, and operation identity that blocks recreation; deletion is cleanup, never revocation or installation proof.

Token rotation membership-baseline and checkpoint preservation is mandatory at both session-only CAS stages and in every durable rotation and retry record. The `TOKEN_ROTATION` operation, replacement lease, pending/active registry postcondition, installation claim, acknowledgement request and digest, binding candidate, readback evidence, and second CAS must each carry the complete unchanged `membershipBaseline` and exact stream-key-ordered `outboxCheckpoints` set. The first CAS compares the expected prior baseline exactly and writes the replacement candidate with the complete baseline from the Account lease; a binding refresh may update the baseline only atomically with complete authority evidence from that lease. The post-swap acknowledgement request, canonical digest, and every exact timeout-after-commit retry include the complete baseline and checkpoint set; Account validates both independently against the exact lease, operation evidence, current authority snapshot, and binding metadata before committing installation. The second fenced CAS compares the same acknowledged baseline and checkpoint set before marking the candidate `INSTALLED`. A missing or extra baseline member, or a scalarized, multi-tenant, differently keyed, stale, regressed, or cross-scope `membershipBaseline.membershipVersion` map or checkpoint set, fails closed; scalar authentication fields remain valid in their declared scalar form. Neither CAS may merge baseline or authority fields, retain a separate or scalar membership version, or retain only the latest checkpoint or an aggregate maximum.

Pre-auth transport context is not region-local gameplay authority. It must not be used to admit commands, route tick participation, or bypass the authenticated `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>` / `tick:{tenantRegionTag}:session-binding:<entityId>` contract. Authenticated gameplay binding semantics begin only after successful authentication and gameplay admission.

### Global Account Active-Binding Index

Reset scope, session policy, and recovery release are canonical in [Redis Reset & Recovery](./system-architecture-redis-reset-and-recovery.md). The canonical member schema, repair obligations, account-wide child/standalone recovery carriers, acknowledgement lifecycle, durable inventory, and fail-closed coverage rules are defined in [Session Behavior](./system-architecture-session-behavior.md#global-account-active-binding-index). This Redis hub retains only the physical storage and atomicity consequences.

- `session:game:index:account:<accountId>` is the one intentionally untagged global Redis set used by Game Session to project active bindings across tenants. It is explicitly exempt from tenant-local selector rules because every member is a complete tenant-qualified `accountIndexMember`; it is not an authorization source and is never included in tenant-local Lua or session-only CAS.
- Index mutation is a separate fenced operation from the tenant-local binding CAS. Narrow region/tenant or break-glass cleanup may repair only affected members of tenant-owned `session:game:index:*` projections and must preserve unrelated members and tenants. Untagged global account and issuer indexes are not narrow cleanup targets; replacement or rebuild requires the complete account- or issuer-wide durable inventory, coverage proof, exact readback, and the maintenance-lock release gate. If break-glass mutates an untagged global account or issuer index, the affected index and dependent admission remain fenced while evidence is preserved and the owner-defined [global index-family recovery consequence](./system-architecture-redis-reset-and-recovery.md#global-index-family-recovery-consequence) is followed; a narrow reset cannot serve as local repair. Redis `SCAN`, key absence, or a projection alone cannot establish coverage.
- Every consumer validates each referenced tenant-qualified binding and current Account authority. The global key never authorizes cross-tenant gameplay or substitutes for membership, grant, or entitlement checks.

### Issuer Active-Binding Index

The issuer cutoff family is intentionally **global per Account environment issuer**, not tenant-scoped. `issuerId` identifies the Account issuer and its issuer-generation cutoff; the `issuer/<issuerId>` authority stream and this derived index cover active and provisional gameplay bindings across every tenant under that issuer. Account owns the durable issuer generation, cutoff event, and outbox/checkpoint authority. Game Session owns the gameplay binding records, issuer partitions, repair obligations, coverage evidence, and socket/admission termination. The index cannot advance issuer authority and is not an authority source.

Because this is a global Coordination Redis family, `session:game:index:issuer:{issuerIndexLayoutTag}:<issuerId>:<partitionId>` is an explicit exception to the general tenant/region key-prefix rule. `tenantId` remains in every value and in `bindingRef`, and every operation validates the referenced tenant-scoped binding identity. Tenant isolation is enforced by Game Session's owner-controlled access and binding validation; the global index is not a tenant-local read or mutation surface. Region- and tenant-scoped resets must not flush a whole global issuer partition: Game Session reconciles only affected binding references from the durable inventory and preserves or repairs global coverage. A cluster reset may discard the volatile index, but protected admission remains fenced until Game Session rebuilds every partition in the active layout and proves coverage; Account-owned issuer authority is rebuilt and verified under the reset contract.

The issuer cutoff family is a bounded active-binding index, not an authority source. Its exact Redis representation is:

```text
key:   session:game:index:issuer:{issuerIndexLayoutTag}:<issuerId>:<partitionId>
type:  HASH
field: <bindingRef>
value: {
  schemaVersion: 1,
  issuerId,
  accountId,
  tenantId,
  gameInstanceId,
  sessionId,
  bindingGeneration,
  issuerAuthGeneration,
  issuerIndexLayoutVersion
}
```

### Canonical Issuer Partition Mapping

The target `bindingRef` encoding is one exact versioned UTF-8 byte sequence, consistent with the repository's length-prefixed identity convention. For `segment(bytes) = ascii(canonical_decimal_count(byte_length(bytes))) + ":" + bytes`, where the count has no leading zero, the complete binding identity is encoded in this fixed order:

```text
bindingRefBytes = segment(utf8("bindingRef/v1"))
                + segment(utf8(tenantId))
                + segment(utf8(gameInstanceId))
                + segment(utf8(sessionId))
bindingRef = bindingRefBytes
```

The three identity values are their already-canonical identifier strings: no trimming, case folding, delimiter escaping, alternate textual UUID form, Unicode normalization, or JSON serialization is applied by this encoder. Invalid UTF-8 or an invalid identifier is rejected before encoding. The Redis hash field and every durable/wire carrier use these exact `bindingRef` bytes; the partition function never hashes a reserialized object, a delimiter-joined tuple, a hex rendering, or a decoded Redis value with a different representation.

The canonical partition function is `SHA-256(bindingRefBytes)`. The 32-byte digest is first normalized as one non-negative unsigned big-endian integer `normalizedHash`; only then is `partitionId = normalizedHash mod issuerIndexPartitionCount` evaluated. `issuerIndexPartitionCount` must be positive, `partitionId` is zero-based in `[0, issuerIndexPartitionCount)`, and a signed hash conversion, language-native overflow, absolute-value workaround, or modulo before unsigned normalization is invalid. `issuerIndexLayoutVersion` pins this mapping version, the immutable positive partition count, and the positive partition capacity. `{issuerIndexLayoutTag}` remains the opaque shared key-helper output derived from `(issuerIndexLayoutVersion, issuerId, partitionId)` and is not a second partition-selection algorithm.

The following vectors are published target-state conformance fixtures; the displayed ASCII `bindingRef` is also the exact byte sequence for these fixtures:

| Vector | `bindingRef` tuple | `issuerIndexPartitionCount` | SHA-256 of `bindingRefBytes` | `partitionId` |
| --- | --- | ---: | --- | ---: |
| `ascii-v1-count-1` | `{tenant-01, instance-01, session-01}` -> `13:bindingRef/v19:tenant-0111:instance-0110:session-01` | 1 | `43f08f503d85155c8bbc4501f14f496f7b35fa334b875382da86831251722565` | 0 |
| `ascii-v1-count-16` | `{tenant-01, instance-01, session-01}` -> `13:bindingRef/v19:tenant-0111:instance-0110:session-01` | 16 | `43f08f503d85155c8bbc4501f14f496f7b35fa334b875382da86831251722565` | 5 |
| `delimiter-v1-count-16` | `{tenant/01, game:01, session\|01}` -> `13:bindingRef/v19:tenant/017:game:0110:session\|01` | 16 | `89e8ba42d8f2fc0525c5b7ac2363528c1cbe7d00fc968b7ff95118da3443413a` | 10 |

In the delimiter fixture, `session\|01` is Markdown table-source escaping only. Its semantic tuple value and exact bytes are the literal ASCII `session|01` (`73 65 73 73 69 6f 6e 7c 30 31`); the backslash is not part of `bindingRefBytes`. The published tuple, SHA-256, and partition values therefore remain unchanged.

Every binding writer and removal, issuer cutoff reader, capacity reservation CAS, recovery rebuild, acknowledgement producer, and issuer-layout migration must call this same mapping helper. A migration applies the same `bindingRefBytes` and SHA-256 digest to each pinned old and new layout count; only the pinned layout's modulo differs, and only the migration may account for both layouts. No ordinary writer, cutoff, recovery parent, or acknowledgement consumer may infer a partition from a Redis key, field, tenant, or partial inventory. Implementations and recovery tooling must consume the published vectors before this mapping is considered proven.

Changing `issuerIndexPartitionCount` is a layout migration, not a configuration refresh. Game Session creates a durable layout-transition operation under one `operationId` and `operationFence`, captures the expected active pointer as the pinned old layout `{issuerIndexLayoutVersion, issuerIndexPartitionCount, issuerIndexPartitionCapacity}`, and records the complete new layout as a separate pinned target. New binding/reconnect/resume admission and issuer cutoffs are fenced for the affected issuer, the complete durable inventory and unresolved obligations are snapshotted, and every new partition is rebuilt from that snapshot. The transition record covers both old and new layout descriptors, but migration is the only workflow allowed to read the old layout as a source and the new layout as a target; player, cutoff, and recovery readers never combine partitions from both layouts. It records and applies terminal transitions under the migration fence, proves per-partition capacity and exact readback for the new layout, and publishes durable per-layout coverage acknowledgements. Only a compare-and-set that still matches the pinned old pointer and `operationFence` may advance the active pointer to the pinned new version/count/capacity. Before that CAS, all ordinary readers and writers use only the old pointer; after it, they use only the new pointer. A crash leaves the old pointer active and resumes or abandons the recorded transition; an absent, changed, ambiguous, or mixed pointer fails closed. The old layout is retained read-only until the post-cutover drain/reconciliation window proves zero in-flight old-layout operations, then is removed by a separate fenced cleanup. A modulo change without this versioned build, pointer cutover, and old-layout drain is unsupported.

Before enumeration, Game Session establishes one issuer-wide admission `coverageFence` and immutable `inventorySnapshotRevision` under the durable `operationId`/`operationFence`, and pins the active layout pointer as `{issuerIndexLayoutVersion, issuerIndexPartitionCount, issuerIndexPartitionCapacity}` for that operation. The snapshot contains the exact `issuer/<issuerId>` cutoff checkpoint, issuer generation, `issuanceFence`, complete applicable `outboxCheckpoints`, and the pinned layout identity. `coverageFence` is the immutable admission/creation fence for that inventory snapshot and is distinct from the maintenance `operationFence`; `coverageGeneration` is a later generation used to account for every post-fence transition. New binding, reconnect, and resume admission is blocked against that fence while coverage is open; a post-fence binding can become admissible only when it and its exact durable evidence carrier bind both the `operationFence` and `coverageFence` plus a later `coverageGeneration` to the same operation and `inventorySnapshotRevision`. Carrying only one fence or only the coverage generation is invalid. Any race that produces a non-admissible candidate, reservation, or repair obligation must be accounted for before acknowledgement. A standalone issuer-wide operation persists `parentRecoveryOperationId=NOT_APPLICABLE`, `parentLifecycle=NOT_APPLICABLE`, `parentOperationFence=NOT_APPLICABLE`, and `parentCoverageFence=NOT_APPLICABLE`, and self-binds `issuerCoverageOperationId=operationId`, `issuerCoverageLifecycle=lifecycle`, and `issuerCoverageOperationFence=operationFence`; a linked child instead associates the exact parent tuple only through its independent parent edge, while the child itself owns only its operation and coverage fences and never nests under the parent maintenance lock. Every linked child request, digest, transition, readback, acknowledgement, and retry carries only the child-owned tuple; the independent edge and parent's consumption record carry the exact parent tuple and validate the child result. Standalone records carry the four exact `NOT_APPLICABLE` parent markers. Game Session durably acknowledges each partition only with the parent-independent child issuer-partition acknowledgement tuple defined above: issuer operation identity/lifecycle/fence, `issuerId`, applicable child fences, snapshot revision, later coverage generation, pinned layout version/count/capacity, `partitionId`, exact cutoff, reservation lifecycle identities, and local plus aggregate capacity evidence. A missing HASH key is an empty partition only when the read succeeded and the matching acknowledgement proves coverage for that exact issuer-wide snapshot, operation attempt, layout, cutoff, and fences. A missing, stale, or mismatched acknowledgement, cross-snapshot or cross-attempt evidence, an unavailable read, malformed value, conflicting duplicate, unresolved reservation, or unresolved repair obligation is ambiguous coverage; the cutoff fails closed and requires reconciliation/rebuild rather than inferring empty coverage from key absence or an aggregate proof. The coverage generation is index-maintenance evidence, not a second authority generation.

For every partition `p`, `N_issuer_partition(p)` counts distinct non-terminal durable reservation entries, with each binding transition counted once even when its reservation is attached to an active, provisional, or unresolved binding. Each `IssuerPartitionReservation` is Game Session-owned durable evidence with `reservationId`, `owner` (the complete `bindingRef` and owning session identity), exact `transitionId`, `issuerId`, `partitionId`, `issuerIndexLayoutVersion`, lifecycle (`RESERVED`, `BOUND`, `RELEASE_PENDING`, or terminal `RELEASED`), `reservationFence`, and the exact coverage tuple `{issuerCoverageOperationId, operationFence, coverageFence, inventorySnapshotRevision}`. `inventorySnapshotRevision` is the complete immutable issuer-inventory revision; it is not a caller-selected or generic local revision. Before any tenant-local binding CAS publishes a binding, Game Session commits the reservation and any repair obligation in the same durable transaction, then atomically reserves one unit in the target issuer partition through a single-key capacity compare-and-set keyed by the exact reservation and transition. That CAS exact-compares the owner, transition, partition/layout, lifecycle, reservation fence, `issuerCoverageOperationId`, `operationFence`, `coverageFence`, and `inventorySnapshotRevision`, and is idempotent only for the same complete reservation tuple. It rejects or backpressures when the reservation would exceed `issuerIndexPartitionCapacity`. A binding cannot become admissible or a repair obligation be considered covered without the matching reservation. The reservation remains counted through `RESERVED`, `BOUND`, and `RELEASE_PENDING`; failed or ambiguous cleanup leaves it counted. Terminal cleanup first records `RELEASE_PENDING`, exact-compares the same coverage tuple while removing the binding field through the fenced CAS, removes/releases the capacity entry, reads back both absences and the exact terminal state with that tuple, and only then records `RELEASED`; terminal evidence remains available for idempotent reconciliation. Every CAS, readback, acknowledgement, and cleanup must exact-compare all four coverage-tuple fields; a binding-only, reservation-only, operation-only, or current-snapshot match cannot substitute. This reservation-before-binding protocol serializes concurrent admissions at the partition and prevents over-capacity races. At recovery, Game Session must enumerate the complete binding and reservation inventory, establish the same finite per-partition invariant for every `p`, and publish no coverage acknowledgement when any non-terminal reservation exceeds capacity. The aggregate proof is additionally required: `N_issuer = sum_p N_issuer_partition(p) <= issuerIndexPartitionCount * issuerIndexPartitionCapacity`. Aggregate capacity alone is insufficient.

Game Session writes and removes issuer fields through a single-key compare-and-set over the complete expected `bindingRef`, `bindingGeneration`, `issuerAuthGeneration`, and `issuerIndexLayoutVersion`, together with the exact reservation identity, owner, transition, partition/layout, lifecycle, reservation fence, and coverage tuple `{issuerCoverageOperationId, operationFence, coverageFence, inventorySnapshotRevision}`. An identical complete value is an idempotent success; a stale or conflicting value leaves a durable repair obligation and reservation unresolved. The tenant-local binding CAS records `issuerIndexState=REPAIR_REQUIRED` and keeps the binding non-admissible until the index CAS, reservation capacity CAS, and obligation acknowledgement complete; a follow-up binding CAS records `issuerIndexState=ACKNOWLEDGED` only when the same candidate generation/fence remains current and the binding or its exact linked durable carrier retains the matching operation and coverage tuple plus later `coverageGeneration`. Recovery rebuilds partitions from the complete durable active-binding and reservation inventory using the same expected-value compare-and-set, reads back every expected binding field and reservation entry, exact-compares the complete reservation coverage tuple, enforces the per-partition capacity before publishing coverage acknowledgements, and clears obligations only after all required acknowledgements carry the matching `issuerCoverageOperationId`, `operationFence`, `coverageFence`, `inventorySnapshotRevision`, and later `coverageGeneration` for the same operation, snapshot, and layout.

The canonical durable active-binding inventory is a Game Session-owned PostgreSQL `GameplayBindingInventory` (or an equivalent durable control-store record with the same transaction and snapshot guarantees). It contains one row for every `ACTIVE`, `PROVISIONAL`, or unresolved account/issuer repair binding, keyed by the exact `bindingRef`, and records the binding-owner `accountId`, tenant/game/session identity, `bindingGeneration`, issuer and layout identity, lifecycle state, index-obligation state, account-index transition identity and `accountIndexFence`, every matching `IssuerPartitionReservation` identity/owner/transition/lifecycle/fence/revision, and durable inventory revision. A reservation-only pre-binding row is also included until it reaches terminal `RELEASED`. It is the authority for inventory completeness, recovery enumeration, and cutoff capacity coverage; it is not a substitute for Account authority, the `session:game:*` reconnect record, or the region-local `tick:{tenantRegionTag}:session-binding:<entityId>` command-admission record.

For standalone issuer coverage, the durable operation record and every post-fence carrier, digest, readback, acknowledgement, retry, and completion record persist `parentRecoveryOperationId=NOT_APPLICABLE`, `parentLifecycle=NOT_APPLICABLE`, `parentOperationFence=NOT_APPLICABLE`, and `parentCoverageFence=NOT_APPLICABLE`; the operation self-binds `issuerCoverageOperationId=operationId`, `issuerCoverageLifecycle=lifecycle`, and `issuerCoverageOperationFence=operationFence`, plus its distinct `coverageFence`, complete issuer `inventorySnapshotRevision`, and later `coverageGeneration`. Linked-child coverage retains the exact parent tuple only on the independent parent edge and the parent's exact consumption record; child requests, digests, readbacks, acknowledgements, and retries remain parent-independent. The linked child is a globally shareable immutable coverage operation and does not nest under the parent maintenance lock; standalone evidence never fabricates a parent identity, lifecycle, or fence.

Before a tenant-local binding CAS can publish an active or provisional record, Game Session commits the corresponding inventory row, reservation entry, and account/issuer repair obligations in one durable transaction. Every activation, replacement, terminalization, and removal advances the row and reservation through a fenced compare-and-set; ambiguous cleanup leaves both unresolved rather than deleting either. An issuer-wide recovery or issuer-cutoff operation establishes its `operationId`, `operationFence`, distinct `coverageFence`, immutable `inventorySnapshotRevision`, and pinned active layout before reading all binding and reservation rows and unresolved obligations at or before that revision under a repeatable snapshot. When this work is required by preserved-session region- or tenant-scoped recovery, the linked issuer-wide child is the only operation that may map the immutable issuer-wide inventory, repair or remove issuer fields, perform reservation-capacity CAS, read back partitions and reservation entries, and record issuer-partition evidence; the scoped parent performs binding-local repair only and consumes the complete child result only after the child reaches its coverage-proven lifecycle. The child accounts for every later transition with its `issuerCoverageOperationFence`, distinct `coverageFence`, and later `coverageGeneration`, deterministically maps every returned binding and reservation to the pinned layout, and records the complete per-partition acknowledgement tuple. Missing rows, an unavailable snapshot, a post-fence transition not represented by both fences and a later `coverageGeneration` or by an exact linked durable carrier binding those same values to the snapshot and operation, duplicate identities, cross-snapshot/attempt evidence, excess capacity, or any unresolved obligation keeps the scope blocked; Redis `SCAN`, a partial index, or an empty partition cannot establish inventory or capacity coverage.

For preserved-session region- or tenant-scoped recovery, the scoped recovery operation is the durable parent and its issuer-wide coverage operation is a separate durable child per affected issuer. The singleton is keyed by coverage family, exact `issuerId`, and compatible immutable scope/layout/snapshot identity. The parent-child edge is an independent `recovery-parent-edge/v1` that binds the exact `parentRecoveryOperationId`, `issuerCoverageOperationId`, resolved scope, `issuerId`, parent `operationFence`, the parent's distinct `parentCoverageFence`, child lifecycle and `issuerCoverageOperationFence`, distinct child `coverageFence`, and link revision in one durable transaction or exact idempotent compare-and-set. The child becomes globally shareable only after coverage is proven; it does not own, transfer, or nest under the parent maintenance lock. One controller mutates the singleton, while an overlapping compatible parent waits for or attaches to the same child and never creates a second child. A parent-fence change invalidates only that parent's edge, not the immutable child. Each edge is consumed exactly once; exact retries replay the same edge, while a different parent, child, resolved issuer/scope, link revision, parent fence, parent coverage fence, child fence, lifecycle, layout, or snapshot is a conflict and fails closed. The parent remains fenced until its edge observes the coverage-proven child; a paused, superseded, aborted, or terminally mismatched child prevents publication or admission. The edge is the only authority for associating a child request, digest, readback, acknowledgement, retry, or result with a parent, and a child cannot authorize a parent by itself.

An issuer-partition acknowledgement is either a standalone issuer-operation artifact or a linked-child artifact, never a region/tenant parent artifact. A standalone publication transaction validates `parentRecoveryOperationId=NOT_APPLICABLE`, `parentLifecycle=NOT_APPLICABLE`, `parentOperationFence=NOT_APPLICABLE`, `parentCoverageFence=NOT_APPLICABLE`, and the self-bound `issuerCoverageOperationId=operationId`, `issuerCoverageLifecycle=lifecycle`, `issuerCoverageOperationFence=operationFence`, and distinct `coverageFence`. A linked-child publication transaction validates the child identity and current lifecycle, the child `issuerCoverageOperationFence`, and the child `coverageFence` before recording the pinned issuer snapshot/layout/cutoff, later `coverageGeneration`, reservation identities, and partition-local plus issuer-wide capacity tuple; every reservation identity includes and exact-compares `issuerCoverageOperationId`, `operationFence`, `coverageFence`, and `inventorySnapshotRevision`. The independent parent edge and parent's consumption CAS validate the parent identity/lifecycle/fences, linked child identity, and `linkRevision`. The same child-owned tuple is required in the linked request/digest, partition and reservation CAS/readback, acknowledgement, exact retry, and cleanup; the edge and parent-consumption CAS additionally carry the exact parent tuple and must revalidate the full snapshot/layout/cutoff/reservation/capacity tuple rather than trusting a previously complete readback. A stale, terminal, or mismatched parent, child, reservation, operation, snapshot, or fence fails closed even when the partition readback is complete; a parent may consume only the complete finite set of acknowledgements from its linked child, with every expected partition, and only after the child reaches its coverage-proven lifecycle. A standalone operation completes and validates its own finite acknowledgement set and has no parent-consumption path.

An issuer-generation replay at sequence `0` is a no-op only when the exact canonical `outboxStreamKey` matches, the received sequence is exactly zero, and an Account-owned zero-sequence checkpoint proves that the stream has no committed event. The source event fields `lastAppliedSourceEventId` and `lastAppliedSourceEventDigest` must be omitted in that baseline, never represented by null or sentinels; a sequence-0 value from another stream or a caller-supplied baseline is not a no-op. Positive sequences require the exact stream key, contiguous sequence proof, source event identity, event digest, and complete Account snapshot/checkpoint proof.

The issuer binding/index CAS must persist and exact-compare the complete binding fields together with reservation identity, owner, transition, partition and layout, lifecycle, fence, and revision in one atomic durable result, or use separate atomic binding and reservation CAS results joined in one durable acknowledgement. The acknowledgement must preserve and exact-compare all of those fields, and recovery must read back and reconcile the same complete joined result before clearing an obligation or publishing coverage; a binding-only or reservation-only success cannot authorize recovery.

For a linked issuer recovery edge, edge creation, update, every exact retry, child-result/readback association, and parent-consumption CAS must persist and exact-compare `parentRecoveryOperationId`, `parentLifecycle`, `parentOperationFence`, and `parentCoverageFence` together with the exact child identity, child lifecycle/fences, `linkRevision`, and complete snapshot/layout/cutoff/reservation/capacity proof. Child requests, digests, transitions, readbacks, acknowledgements, and retries remain parent-independent. A standalone issuer operation uses the four exact typed `NOT_APPLICABLE` parent markers and has no parent lifecycle or parent-consumption path.

### Recovery and Cutoff Scope Authority

The permitted scope is part of the evidence contract, not an operator hint. A region- or tenant-scoped preserved-session parent may enumerate only its binding-local snapshot, repair the region-local and tenant-scoped families it owns, and validate a linked child result. It may not map an issuer layout, perform issuer Redis field or reservation-capacity repair, read back issuer partitions for coverage, publish an issuer-partition acknowledgement, or claim global account-index coverage from its narrow snapshot. An issuer-wide child or standalone issuer operation must use a complete authoritative issuer inventory. A standalone operation carries `parentRecoveryOperationId=NOT_APPLICABLE`, `parentLifecycle=NOT_APPLICABLE`, `parentOperationFence=NOT_APPLICABLE`, and `parentCoverageFence=NOT_APPLICABLE`, then uses its own `issuerCoverageOperationId`, `issuerCoverageOperationFence`, distinct `coverageFence`, later `coverageGeneration`, pinned layout, and all finite partitions. A linked child retains the exact parent tuple through its independent edge but does not nest under the parent maintenance lock; the parent owns that lock and the child owns only its operation and coverage fences. An account-wide operation may cover only the untagged account family from a complete account inventory and its own account coverage evidence; it cannot substitute for issuer coverage. A cluster recovery must rebuild or consume complete per-account and per-issuer coverage for the deployment rather than treating a local region, tenant, or aggregate snapshot as global proof.

For every preserved region/tenant recovery, the independent parent edge and parent-consumption CAS validate `parentRecoveryOperationId`, the parent lifecycle, parent `operationFence`, and the parent's distinct `parentCoverageFence` together with the linked child identity and `linkRevision`; the child validates its own lifecycle, `issuerCoverageOperationFence`, distinct child `coverageFence`, snapshot, and coverage generation before each layout mapping, issuer Redis/capacity mutation, readback, acknowledgement, and retry. A standalone issuer operation validates the four exact `NOT_APPLICABLE` parent fields and its self-bound issuer-operation tuple before those same actions. The parent-consumption CAS validates the same exact parent/child identities and lifecycles, both operation fences, both coverage fences, the child's later `coverageGeneration`, the pinned layout/cutoff, and the complete parent-independent acknowledgement tuple including every expected partition, reservation, and local/aggregate capacity value. No global index-family acknowledgement is valid when it was assembled from a local snapshot: the unaffected portion of the global family remains untouched, a complete global family is rebuilt only from the complete authoritative inventory, or issuer coverage is supplied by the linked issuer-wide child under its own coverage fence and generation.

For account-wide coverage, releasing the live `accountAdmissionFence` at the single `ACTIVE -> HISTORICAL` coverage-proven transition does not erase its proof. The live field becomes typed `NOT_APPLICABLE`, while the child or standalone result retains the exact released value as `historicalAccountAdmissionFence`; linked edge creation/update, edge retries, child-result readback, and parent-consumption CAS exact-compare that historical value with the child result and complete snapshot. A flow that acquired account-wide fencing never changes to `NO_ACTIVE_ACCOUNT_WIDE_FLOW`, discards its historical value, or treats the post-release sentinel as a new acquisition; the pair of account-fence `NOT_APPLICABLE` values is reserved for flows that never acquired account-wide fencing.

### Session and Region-Binding Contract

Session and region participation updates are intentionally **two-phase and monotonic**, not a single cross-slot atomic Redis transaction:

1. A **session-only** script updates `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>`:
   - It validates the session CAS fields and logical expiry.
   - It increments or verifies a monotonic `binding_generation`.
   - It records reconnect/takeover intent plus any advisory region summary fields.
2. A **region-lease** script for each affected region updates `tick:{tenantRegionTag}:session-binding:<entityId>`:
   - It validates the active region lease and expected `binding_generation` from the session contract carried in `ARGV`.
   - It binds or unbinds the session for gameplay participation within that region.
   - It rejects stale generations with a non-mutating outcome such as `"STALE_SESSION_GENERATION"`.
3. Gameplay authority reads region-local binding keys, not `session:game:*`, when deciding whether an entity may enqueue commands or continue tick participation in that region.
4. Disconnect/takeover reconciliation is generation-based:
   - If `session:game:*` says a newer generation is active, any older `tick:{tenantRegionTag}:session-binding:<entityId>` entry is stale and must be ignored or cleaned up by the next region-lease script.
   - If a region binding survives after the session key is deleted or expires, the next lease-holder treats it as stale and removes it as part of region-local cleanup.
5. Region reset reconciliation is also generation-based:
   - Region-scoped reset policy is defined by [Redis Reset & Recovery](./system-architecture-redis-reset-and-recovery.md): the operation must carry exactly one explicit `--preserve-sessions` or `--invalidate-sessions` option, and no default is inferred. Locally, clearing the affected `tick:{tenantRegionTag}:*` binding family requires retained `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>` records to rebind before intake under `--preserve-sessions`, while `--invalidate-sessions` requires fresh admission; affected tenant-owned `session:game:index:*` projections reconcile and read back under either policy, and pre-auth transport context is always invalidated or rebuilt.
   - Before ordinary gameplay mutation intake resumes for the affected region, Game Session must run a bounded rebind phase for preserved sessions that still intend to participate in that region. The rebind phase evaluates the complete canonical preserved-session rebind predicate below, increments or verifies `binding_generation`, and invokes the same region-lease bridge script that normal `PLAY` / reconnect uses.
   - Until a non-security region rebind succeeds, ordinary gameplay mutation intake remains blocked. The only exception is a gameplay or admission command actually attempted after valid identity validation and command-record establishment: it must be durably terminal with `executionOutcome = REGION_REBIND_REQUIRED` and a non-applied gameplay result (the shared default is `NOT_APPLIED`), or the client must re-`PLAY`; no gameplay mutation may execute or be staged. A revoked or invalid token authority follows the socket-close and resume-episode termination transition below, not this command outcome. Missing, invalid, or unauthenticated requests are rejected before command-record creation and must not synthesize either a command record or `REGION_REBIND_REQUIRED`.
   - `REGION_REBIND_REQUIRED` terminalizes the command/admission attempt, not the connected socket or gameplay-session record, but only after all Account identity, token, authority, membership, lease, and delegation-JWT predicates have passed, with entitlement satisfied by either a fresh read or the qualifying bounded fallback above, and the remaining failure is solely a non-security region rebind gap. In that case, if the recorded policy preserves sessions, the session remains connected but region-blocked and cannot admit further commands until rebind succeeds or fresh `LOGIN` / `PLAY` establishes a new binding. A reachable token-registry or Account-authority result of `AUTH_SESSION_REVOKED` or an invalid-token outcome instead marks the session auth-revoked, closes the socket, and ends the current resume episode; it is not a region rebind gap.
   - If preserved session state has a solely non-security region rebind gap after the Account predicates pass, the session remains connected but is no longer admitted to that region until fresh `LOGIN` / `PLAY` succeeds. Unavailable or ambiguous Account evidence remains fenced under the outage policy and is not treated as a region rebind gap.

The canonical preserved-session rebind predicate requires all of the following before the region bridge may recreate a binding:

- A complete canonical `schemaVersion=2` authenticated gameplay session payload, including `issuanceFence`, `rebindHandle`, `continuityBindingExpiresAt`, the complete `membershipBaseline` with its exact one-tenant `membershipBaseline.membershipVersion` map and `membershipBaseline.membershipAuthorityGeneration`, the complete `authorityTuple` including its separate `authorityTuple.membershipAuthorityGeneration`, and the complete canonical `outboxCheckpoints` set; a missing, `schemaVersion=1`, unsupported, duplicate-field, or incomplete record fails closed and cannot be rebound.
- Target-state exact-token predicate (not a current runtime guarantee): an exact `session:auth:token:<tokenHash>` registry record addressed by the payload's `authTokenHash` that is present, active, unrevoked, and unexpired. The binding's `authTokenIssuedAt`, `authTokenExpiresAt`, and `tokenGeneration` must equal the registry record's `iat`, `exp`, and `tokenGeneration` exactly; Redis TTL, current time, or a newer/older value cannot satisfy any of those fields. Account must validate the payload's opaque `rebindHandle` and prove that its bound token hash, signed `jti` and `nbf`, token lineage, account identity, profile, audience, and exact `issuanceFence` match that registry record and the gameplay binding exactly. The registry is authoritative for `jti`, `tokenGeneration`, `iat`, and `exp`; the Account-validated handle is authoritative for the original signed `nbf`, exact issuance fence, and expected exact-token identity used for comparison. Neither source may substitute for or repair the other, and Game Session must not parse or invent those handle values locally.
- The Account-validated `rebindHandle` must also bind and match the gameplay binding's complete unchanged `membershipBaseline` and complete stream-key-ordered `outboxCheckpoints` set. The baseline comparison is exact over every member, including presence, one tenant key, the version value in `membershipBaseline.membershipVersion`, and `membershipBaseline.membershipAuthorityGeneration`, and is independent from the separate `authorityTuple.membershipAuthorityGeneration` predicate. A scalarized baseline map or checkpoint set, missing baseline member, extra-tenant, differently keyed, stale, regressed, contradictory, or aggregate-only membership value or checkpoint fails closed; scalar authentication fields retain their declared scalar types. Rebind must not merge handle and binding values or retain only a latest checkpoint. Account's `GetTenantMembershipForRuntime` response remains scalar and is not changed by this persisted/cross-service carrier requirement.
- Current Account authority for the exact account and tenant, including the applicable `issuerAuthGeneration`, `accountAuthorityGeneration`, `tenantAuthorityGeneration`, `authorityTuple.membershipAuthorityGeneration`, and non-public realm-grant identity (ordinary private or playtest, always lifecycle-bound) and `grantVersion` when applicable, plus the complete current `membershipBaseline` from one authoritative Account snapshot, public-production entitlement, revocation, authority-freshness lease, and the complete exact `outboxCheckpoints` set for every applicable authority stream. The scalar membership version from `GetTenantMembershipForRuntime` is wrapped only as the exact one-tenant `membershipBaseline.membershipVersion` map inside that complete gameplay carrier. Missing, extra, stale, regressed, or aggregate-only baseline or checkpoint evidence fails closed. For an entitlement read that is unavailable, only the same-binding public-production continuity fallback below may apply; it never supplies current authority evidence.
- A valid `continuityBindingExpiresAt` and either the immutable `resumeDeadline` for a disconnected binding or a trusted connected-session fallback proof when the binding remains connected and `resumeDeadline` is absent. The proof is bound to the exact session/binding identity, `binding_generation`, `authTokenHash`, `issuanceFence`, connection episode with `connectionState=CONNECTED`, and positive Account entitlement evaluation; it carries `connectedSessionDeadline = evaluatedAt + 5 minutes`, using the Account-stamped `evaluatedAt` and the same synchronized-clock/skew rules as the entitlement continuity window. Socket liveness, Redis key presence/TTL, current time, reconnect attempts, and token rotation cannot create or extend that proof. The rebind does not extend any deadline, together with the current operation/region epoch and lease-fence evidence.
- A successful invocation of the region-lease bridge with the validated identity and generation; the canonical session record, `session:game:index:*`, and `sessionctx:*` are not authority substitutes.

Entitlement fallback is deliberately non-circular and public-production-only. New `PLAY`, a new binding, a target change, expansion, or any capacity-creating operation requires a fresh Account-authenticated `account-auth-evidence-bundle/v1`; if an entitlement-only evaluation is unavailable without an eligible LKG, the operation fails closed with `ENTITLEMENT_UNAVAILABLE`; an unavailable, stale, contradictory, or gapped non-entitlement authority, lease, binding, or delegation dependency fails closed with `AUTH_UNAVAILABLE` or the applicable stale-admission error. Only resume/rebind of the same unchanged binding may use a previously accepted positive bundle retained in a protected binding-continuity record. The fallback is permitted only for an entitlement-read-only outage, while every other current Account predicate succeeds, the exact activation lease is committed, and a fresh Account-authenticated delegation JWT check succeeds; it never supplies authority, revocation, checkpoint, lease, or token evidence. That record must contain the exact target, session/binding identity, `binding_generation`, connection episode and state, `bundleVersion`, `snapshotIdentity`, `evaluationIdentity`, Account-stamped `evaluatedAt`, immutable `connectedSessionDeadline = evaluatedAt + 5 minutes` when the binding is connected, `entitlementVersion`, `tenantBillingSequence`, applicable `tenantBillingCutoff`, complete `authorityTuple`, and complete `outboxCheckpoints` from one Account evaluation. A disconnected binding is eligible only when its immutable `resumeDeadline` is present; a connected binding is eligible without `resumeDeadline` only when the exact connected-session proof is present and its deadline has not passed. At `fallbackAt`, define `effectiveContinuityDeadline = min(continuityBindingExpiresAt, resumeDeadline)` when `resumeDeadline` is present, otherwise `effectiveContinuityDeadline = min(continuityBindingExpiresAt, connectedSessionDeadline)`. Then define `entitlementFallbackDeadline = min(effectiveContinuityDeadline, fallbackAt + 5 minutes, fallbackAt + session_expiration_ms)`, where `session_expiration_ms = min(FIREMUD_AUTH_SESSION_EXPIRATION_MS, 300000)`. The fallback is usable only before that deadline and only for the unchanged binding; when Account is reachable for the entitlement read, the live bundle is required and must equal those stored identity/version/checkpoint fields. Non-public admission, whether ordinary private or playtest, never uses this fallback: it requires existing caller-bound membership and the exact current lifecycle-bound Account realm-grant identity and `grantVersion`; unavailable, stale, contradictory, missing, or mismatched grant evidence fails closed. An unavailable non-entitlement predicate, activation lease, or delegation-JWT check never qualifies for fallback. A missing fallback record or connected-session proof, missing `resumeDeadline` for a disconnected binding, known newer billing sequence or authority fence, expired grace window, target change, negative/revoked snapshot, or contradictory local evidence fails closed. The fallback never validates itself by treating its own version as current authority.

The `ENTITLEMENT_UNAVAILABLE` outcome in this fallback contract applies only when entitlement evaluation alone is unavailable; an unavailable non-entitlement authority, lease, binding, or delegation dependency is `AUTH_UNAVAILABLE`. An LKG entitlement record is eligible only when its Account-stamped `evaluatedAt` satisfies `evaluatedAt <= localNow + maxClockSkew` and `localNow - evaluatedAt + maxClockSkew` is strictly below the applicable freshness bound. A future timestamp beyond `maxClockSkew` is invalid and fails closed; a timestamp within the bound never widens the freshness window, and the exact boundary is expired. This entitlement fallback is distinct from ADR 0037 active-binding continuity: active-binding continuity does not authorize new admission, reconnect/resume/rebind, lease renewal, token issuance/refresh, scope expansion, or any extension or recreation of its stored lease.

The fallback's canonical `entitlementFallbackDeadline` is the only usable deadline; Redis TTL refresh, socket activity, reconnect attempts, or local retry cannot extend it.

Rebind consumption is linearized by the durable Account operation, not by Redis key presence. A new operation with a handle bound to an older `issuanceFence` is stale and fails closed without consuming the handle or issuing a replacement. An exact retry matches the durable request ID, digest, workload, binding, handle identity, and issuance fence and replays the stored result without another consumption or mint; if the fence advanced before a credential can be replayed, the retry returns stable stale/failure metadata instead. Redis CAS or recovery must not override that outcome.

A failed non-security preserved-session predicate never implicitly changes the recorded session policy. The operation remains paused and fenced under its existing `operationId` and `maintenanceLockToken`; an explicit audited preserve-to-invalidate transition may compare-and-set the policy under that same lock, recording actor, reason, and immutable evidence before invalidation. If that same-lock transition is unavailable, the operator must complete audited abandonment and start an explicit new recover operation with `--invalidate-sessions`. The invalidation proof is not inferred from a non-security rebind failure; a revoked or invalid token authority follows the explicit socket-close and resume-episode termination transition above.

### Canonical Pre-Wipe Gates

The post-startup challenge/result, separate observed-configuration digest, ACL privilege proof, and isolated destructive-probe contract are owned by the [canonical post-reset verification checklist](./system-architecture-redis-ops-access.md#canonical-post-reset-verification-checklist). A consumed challenge remains single-use and the operation remains fenced until the controller durably accepts the exact attestor result; reset scenarios and migrations must reference that complete checklist rather than copy probe subsets.

For whole-deployment `FLUSHALL`, use the complete [canonical pre-wipe gates](./system-architecture-redis-ops-access.md#canonical-pre-wipe-gates) and independently evidence the deployment blast radius as `cluster`; physical dedication is not required. A node-local AOF reset or replacement is a separate destructive action and uses the same complete pre-wipe gates with a fresh [canonical `physical-dedication-proof/v1` exact binding](./system-architecture-redis-reset-and-recovery.md#coordination-reset-model) for the exact operation, deployment, node set, and resolved scope. This Redis architecture hub does not restate that proof schema; its immutable handoff evidence must bind the exact resolved scope to the same operation and maintenance lock. A resolved scope value alone is insufficient and the external handoff is rejected when the applicable mode-specific evidence is absent or mismatched.

- `scope_paused_and_locked` proves canonical `PAUSED`, blocked command and batch intake, no in-flight executor work, and no old-epoch coordination writer.
- `account_authority_token_cutover` proves protected admission is closed and Account's durable authority/token identity cutover and required immutable evidence are complete for the operation's scope. When the operation can drop `session:connect-token:*`, the gate also binds Account's exact-input issuance-result operation identity and immutable pre-wipe inventory/handoff evidence; recovery cannot release until Account's post-wipe repair/readback exact-matches that operation and its result records, with missing or ambiguous results remaining fail-closed.
- `replay_domain_quarantine_fence` proves the shared replay domain is either verified untouched for a narrower reset or quarantined and fenced for the destructive reset, with its immutable fence evidence recorded.
- `immutable_external_handoff_evidence` contains only pre-wipe authorization and fencing facts: the old and intended new deployment, fenced endpoint, authorized operator and action, time, and tooling digest. It contains no post-wipe health or replacement observations.
- `post_reset_replacement_verification/v1` is a separate evidence group recorded after startup. The controller creates the single-use challenge; only the trusted deployment attestor consumes it and signs the result. `SAME_DEPLOYMENT` requires independent `postWipeEmptyStartupAttestation/v1`; `REPLACEMENT_DEPLOYMENT` requires distinct target-bound `replacementEmptyStartupAttestation/v1`. The signed target evidence must exact-bind target identity/generation, canonical node set, Redis build, Lua registry, startup state, challenge, operation fence, target, and scope, and the controller must pass the complete [canonical post-reset verification checklist](./system-architecture-redis-ops-access.md#canonical-post-reset-verification-checklist). Operator assertions, key absence, and raw key counts are insufficient.

The reset gate must pass the complete [canonical post-reset verification checklist](./system-architecture-redis-ops-access.md#canonical-post-reset-verification-checklist), which keeps the exact `coord_ops_ro/v2` ACL digest and exact `coord_redis_config/v1` observed-configuration digest separate and includes the mode-specific startup attestation, positive probes, destructive negative probes, and cleanup/readback evidence.

The canonical checklist includes isolated disposable-target probes for destructive commands and cleanup/readback proving no key, TTL, coordination, or script-cache mutation remains even if a forbidden command is unexpectedly allowed.

This contract keeps region-local correctness shard-safe while still letting reconnect and takeover flows carry session-wide intent. It also means the system tolerates brief mismatches between `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>` and region-local bindings: the region-local binding key is authoritative for gameplay, while the canonical session record remains authoritative for reconnect semantics. Affected tenant-owned `session:game:index:*` projections may be rebuilt after a reset, but release remains fenced until they reconcile with the durable binding inventory; untagged global account and issuer indexes require their complete owner-defined global inventory and coverage proof before replacement and exact readback.

Gameplay timers and cooldowns (combat cooldowns, regen ticks, delayed effects) are not “session state”: they are region/entity gameplay state. Durable actor timed-state records are authoritative; tick timer keys are reconstructible scheduling projections used to wake expiry or retry work. This lets cooldowns continue correctly in idle regions and across reconnects without treating Redis session keys as their source of truth.

Key properties:

- `sessionId` is an opaque, server-generated identifier (for example, a UUID or fixed-length hash) chosen so key length stays bounded and independent of the raw JWT or account token.
- Session entries use a **derived physical Redis TTL** computed from authentication settings (see `infrastructure/environment-and-secrets-catalog.md#authentication--jwt`):

  - **Target state:** `session_expiration_ms = min(FIREMUD_AUTH_SESSION_EXPIRATION_MS, 300000)`.
  - `session_expiration_ms` derives the initial gameplay continuity-retention and cleanup horizon. It is not a JWT validity period or a cutoff for healthy uninterrupted play.
  - On successful gameplay admission at `admissionAt`, the session value stores an immutable logical expiry anchor:

    `continuityBindingExpiresAt = admissionAt + session_expiration_ms`

  - The Redis TTL for `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>` is physical cleanup metadata. An active-binding refresh atomically preserves the earliest of its existing physical expiry, the requested refresh deadline, and `continuityBindingExpiresAt`; it must not recreate a missing/expired binding, extend an earlier cleanup deadline, or move `continuityBindingExpiresAt`.
- Continuity-binding expiry is authoritative for resumption but does not itself end a continuously connected, currently authorized session. Game Session rejects reconnect/resume once `continuityBindingExpiresAt` has passed, even if the Redis key remains after delayed expiration, AOF replay, or failover drift. Physical deletion can remove the key earlier; a missing key is also non-resumable. Key presence and physical TTL are never permission to resume.
- For a binding disconnected or suspended at `disconnectAt`, the effective resume deadline is:

  `resumeDeadline = min(continuityBindingExpiresAt, disconnectAt + effective firemud.reconnection.policy.resume-window-ms)`

  Resume also requires current account identity, membership authority, entitlement, and revocation checks. The pair is immutable for that disconnection episode: failed reconnects, takeover attempts, and server-token rotation cannot change it. Successful resume consumes the episode; a later connected-to-disconnected transition creates a new pair bounded by the original continuity anchor. A genuinely fresh `PLAY` admission creates a new binding and anchor only after ordinary admission succeeds.
- JWT validity remains bounded by each token's own `exp` claim. Game Session may atomically rotate the complete token identity and `rebindHandle` only after Account validates the current token-identity fence, token lineage generation, and current authority generations, but rotation cannot cross a blocking generation advance or extend continuity-binding expiry or resume eligibility. During the ADR 0037 token-authority-only outage exception, an already-admitted binding may continue only through its prior-positive, unexpired authority-freshness lease while live coordination health remains positive. That continuity does not authorize new admission, reconnect/resume/rebind, lease renewal, token issuance/refresh, or scope expansion, and no Redis refresh or retry may extend or recreate the stored lease deadline.

Session design assumes **reasonably synchronized clocks** on Game Session nodes (for example, via NTP); large clock skew is treated as an infrastructure misconfiguration, not a normal edge case of the session protocol. The effective disconnected-resume window is the stricter of the remaining continuity-binding lifetime and `firemud.reconnection.policy.resume-window-ms`.

### Operational Trade-Offs for Session and Resume Lifetimes

`session_expiration_ms` is an independent gameplay-continuity setting derived only from `FIREMUD_AUTH_SESSION_EXPIRATION_MS` and capped at five minutes. Active authorization, JWT validity, and disconnected resume remain separate policies:

- Each JWT remains unusable after its own `exp`, regardless of the Redis TTL or gameplay binding anchor.
- The immutable continuity anchor prevents token rotation from extending old-binding resume eligibility; it does not force a healthy connected player through fresh admission.
- Tenant/game continuity policy can choose a shorter resume window without changing credential or token validity semantics.

When changing authentication settings, keep these trade-offs in mind:

- **Shorter JWT lifetime**
  - Reducing `FIREMUD_AUTH_JWT_EXPIRATION_MS` changes the lifetime of newly issued `control-ui` and private player-delegation JWTs. `player-bootstrap` JWTs use the separate `firemud.account.tokens.player-bootstrap-expiration-ms` setting (default `300000` ms; production may override it with `FIREMUD_ACCOUNT_TOKENS_PLAYER_BOOTSTRAP_EXPIRATION_MS`), so changing the global JWT setting does not change their lifetime. None of these settings changes `session_expiration_ms`, an already issued token's signed `exp`, moves an existing continuity anchor, or shortens a healthy uninterrupted session by itself.
- **Different disconnected-resume policy**
  - Adjust `firemud.reconnection.policy.resume-window-ms` through the canonical effective-settings path. Increasing it never permits resume beyond the remaining logical gameplay binding lifetime.
- **Unsupported combinations**
  - Do not treat transcript retention, cache TTL, Redis key presence, or physical deletion timing as permission to resume.
  - Do not add another binding/session TTL outside the derived server-side ceiling and the canonical disconnected-resume policy.

For full details on how session keys integrate with reconnect and takeover flows, see:

- Authentication & Authorization (`system-architecture-authentication.md`)
- Reconnection Strategy (`system-architecture-reconnection.md`)
- Game Session Service Redis keys (`microservices/game-session-service/README.md#redis-keys`)

Session revocation actions (for example “kick all sessions for tenant X” on a billing suspension) must not be implemented by scanning the Redis keyspace in hot paths. Runtime revocation is performed by:

- Publishing a tenant-scoped billing/security event that Game Session consumes promptly, and
- Closing affected sockets and removing the corresponding per-session keys using in-memory registries and/or purpose-built, bounded indexes.

Target-state issued-token registry contract (not a current runtime guarantee): issued-token registry records (`session:auth:token:<tokenHash>`) use each record's actual JWT `exp` plus the cleanup margin rather than gameplay's global `session_expiration_ms` derivation. The exact-token record is authoritative for runtime admission and per-token revocation, but it is not the durable Account generation authority. A per-token logout or equivalent revocation may remove the Redis record before natural expiry only after the durable Account `PENDING_LOGOUT`/revocation fence or tombstone intent commits; the record deletion is not the fence, tombstone, or negative proof. A reachable missing record denies the JWT and requires reauthentication, while an unavailable registry remains `AUTH_UNAVAILABLE`. Their reset policy is independent of gameplay-session preservation: region- and tenant-scoped coordination resets preserve these Account-owned records, while a cluster reset must close protected admission, complete the Account repair/reset cutover and durable issuer-generation advance, drop the old records as physical cleanup, then rebuild and prove the current generation projection before any replacement records are issued or protected admission reopens. The Account token and generation families remain outside gameplay session policy. The separate Account-owned `session:connect-token:*` issuance-result projection family is likewise preserved by region/tenant resets and requires exact durable Account repair/readback after any cluster wipe or cold start that can lose the family; missing or ambiguous results deny the corresponding handshake and are never reconstructed from JWT or request fields. The `--preserve-sessions` option applies only to region- and tenant-scoped `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>` records; derived tenant-owned `session:game:index:*` projections are reconciled independently under either session policy, and cluster scope rejects `--preserve-sessions` in favor of explicit `--invalidate-sessions`. The records are documented in detail in `system-architecture-jwt-and-token-contracts.md` and the Account Service design, and live on Coordination Redis so a cluster reset can force re-authentication in a controlled way.

### Gateway Connect-Token Replay Markers

Gateway connect-token replay state is a narrow security-critical exception to the general Redis coordination model. The accepted carrier, validation, consumption, readiness, and quarantine contract is defined by [Gateway Architecture](./system-architecture-gateway.md#tenant-aware-edge-connect-token-gameplay-handshake) and [ADR 0029](./decisions/adr-0029-single-use-gameplay-connect-token-carriage.md). This section fixes its Redis lifetime and reset scope:

- **Canonical replay-domain pin:** Gateway owns the shared domain identity and carries it through the non-secret `FIREMUD_GATEWAY_REPLAY_DOMAIN` configuration value. The only accepted value is the versioned literal `gateway-connect-token-replay-v1`; it is not generated per pod, tenant, region, deployment attempt, or reset. This fixed literal is the complete shared replay namespace: tenant, game, and region identifiers are intentionally not additional key components. Target Gateway startup and deployment preflight must reject a missing, unknown, or mismatched value, and every target key helper, ACL/prefix declaration, migration, reset, and recovery tool must use the exact hash tag `{gateway-connect-token-replay-v1}`.

- The target key shapes are `gateway:connect-token:{gateway-connect-token-replay-v1}:readiness`, `gateway:connect-token:{gateway-connect-token-replay-v1}:jti:<jti>`, and `gateway:connect-token:{gateway-connect-token-replay-v1}:deny:jti:<jti>`. The readiness value carries `replayAdmissionFence`, state, cutoff, and quarantine fields. All three keys contain the same literal `{gateway-connect-token-replay-v1}` hash tag and therefore share one Redis Cluster slot; matching [ADR 0029](./decisions/adr-0029-single-use-gameplay-connect-token-carriage.md), the consume script receives `KEYS[1]=readiness`, `KEYS[2]=replay jti`, and `KEYS[3]=deny jti` and **must atomically validate readiness state, the signed fence and cutoff, and deny-marker absence, then create the replay marker in that same operation**. Replay and deny marker expiries are absolute at `token.exp + firemud.gateway.connectTokenClockSkewMs`; neither marker is refreshed, extended from consumption time, or replaced with a fixed 30-second TTL. The deployed clock-skew setting is the single `FIREMUD_GATEWAY_CONNECT_TOKEN_CLOCK_SKEW_MS` value, default `5000` ms and bounded to `0..5000` ms.
- The target deployment has one shared replay-continuity domain, so replay markers, deny markers, and the shared `replayAdmissionFence` are not tenant- or region-partitioned even though their physical keys use the fixed slot tag. Region- and tenant-scoped coordination resets must leave the Gateway replay and deny-marker prefixes and readiness record untouched and must not invalidate connect tokens solely because gameplay coordination in that narrower scope was reset. If either reset cannot prove that the shared replay domain was untouched and continuous, it escalates to the same shared quarantine rather than attempting a narrower fence. Migration and recovery use the owner-defined quarantine, exact old-prefix inventory/readback, named Coordination client/ACL cutover, target-key readback, and retention or explicit cleanup of old markers through their original acceptance window before reopening admission; see [Redis Reset & Recovery](./system-architecture-redis-reset-and-recovery.md#reset-policy-matrix-prefix-summary).
- A cluster-scoped Coordination Redis reset, loss of replay or deny-marker continuity, uncertain failover, eviction, capacity breach, or durability-acknowledgement failure invalidates the shared replay domain. The reset drops or makes untrusted all replay markers, deny markers, and readiness state, advances the shared fence, rejects new first-party handshakes for at least the maximum gameplay-connect lifetime (`30 seconds`) plus two configured clock-skew intervals after the recorded detection cutoff, and reopens only after the configured disposable-marker plus `WAITAOF` proof establishes `DURABLE_REPLAY_CONSUME_ACK`. Existing WebSockets are not closed by replay-state reset alone; the broader cluster reset separately requires explicit gameplay-session invalidation.
- A future partitioned replay deployment may narrow quarantine to a proven marker/fence domain only after its topology and reset contract establish that isolation. It must not be inferred from a tenant or region label in the current shared deployment.

## Redis Profiles

Redis deployments approximate one of a small set of **profiles**. These named profiles are non-ephemeral and describe the expected persistence, restart behavior, and SLO assumptions for Coordination Redis; only an explicitly labelled ephemeral single-node stack may omit AOF.

- **`dev_local`**
  - Used for individual developers and lightweight local stacks.
  - AOF enabled on Coordination Redis, primarily for debugging and replay during development.
  - Measured coordination-write SLOs are relaxed, but invariants and key naming rules still apply.

- **`hobby_self_hosted`**
  - For small/self‑hosted player‑facing deployments.
  - Coordination Redis runs with AOF enabled and memory sizing tuned so restarts typically complete within **30–60 seconds**.
  - Measured exposure and replay guarantees are expected to match production‑like behavior for a single tenant.

- **`production_clustered`**
  - For multi‑tenant or higher scale environments.
  - Coordination Redis runs as a cluster or carefully sized single‑node deployment with AOF, predictable restart times, and shard sizing aligned with tick workloads.
  - Measured coordination-write SLOs, availability SLOs, and incident playbooks are evaluated against this profile.

Environments (local, CI, staging, production) are mapped to these profiles and their concrete settings in **Redis Usage & Profiles** (`system-architecture-redis-usage-and-profiles.md`).

## Redis as a Volatile State Layer

Redis is used primarily for non‑authoritative, transient data. The target-state exact-token registry below is the narrow runtime security exception; it is not a current runtime guarantee until the implementation and proof gaps above are closed:

- In‑flight command queues and tick staging structures.
- Tick locks and executor leases.
- Reconstructible timer, cooldown-expiry, and retry scheduling metadata (stored in milliseconds).
- Gameplay session state and live coordination (session bindings, queue participation).
- Best‑effort caches for hot‑path aggregates and chat history in Cache/Rate‑Limit Redis.
- Automation queues and coordination hints that can be reconstructed from durable domain state.
- Target-state exact-token runtime admission and per-token revocation records under `session:auth:token:<tokenHash>`; these are authoritative for that token only, while Account's durable issuer/account/tenant/membership generations remain authoritative for generation advancement.

Implications:

- Losing ordinary coordination keys within the measured exposure must behave like lost/reordered messages or delayed timers, not permanent data corruption. In the target state, losing an exact-token registry record fails closed for that token's protected runtime admission; it does not advance or replace Account's durable generations.
- Designs must **never** put the only record of a critical effect (for example, a currency transfer) exclusively in Redis.
- Every new use of Redis must explicitly state:
  - Which role it targets (Coordination vs Cache/Rate‑Limit).
  - Whether it is reset‑tolerant, reset‑sensitive, or reset‑forbidden.
  - How it behaves under measured coordination-write exposure and during coordination resets.

The **Redis Usage & Profiles** and **Redis Cache & Rate Limiting** docs expand on role‑specific expectations, eviction behavior, and cache correctness classes.

## Key Naming and Shard Discipline

Redis keys follow strict naming conventions to ensure:

- Shard‑aware key locality and safe multi‑key Lua scripts.
- Clean separation between Coordination and Cache/Rate‑Limit workloads.
- Tenant and region isolation in shared clusters.

Key principles:

- **Tenant and region prefixes**
  - All coordination and cache keys include a `tenantId` component.
  - Region-scoped coordination keys include both `gameInstanceId` and `regionId` so tick workloads and timers are scoped to the complete tick-region identity.
  - Mutable or display-only human-readable values (character names, room titles) are **never** embedded directly in keys. Key components use canonical stable identifiers or stable owner-defined selectors; shared key helpers define any required encoding. For the realm-grant index, `grantScopeId` is the sole physical grant-identity component. `worldSlug` and `realmSlug` are owner-issued fields inside the tuple passed directly to the shared codec, without caller normalization or encoding, and are not independent physical key components.
  - Explicit exceptions: the shared Gateway replay domain (`gateway:connect-token:{gateway-connect-token-replay-v1}:jti:<jti>` replay markers, `gateway:connect-token:{gateway-connect-token-replay-v1}:deny:jti:<jti>` deny markers, and `gateway:connect-token:{gateway-connect-token-replay-v1}:readiness` carrying its `replayAdmissionFence`), Account-owned exact-token registry records (`session:auth:token:<tokenHash>`), Account-owned exact-input connect-token issuance-result projections (`session:connect-token:tenant:<tenantId>:account:<accountId>:scope:<scopeHash>:request:<requestHash>`), Account-owned global authority-generation projections (`session:auth:generation:*`), the Game Session issuer-generation consumer projection (`session:game:auth:issuer-generation:v1:<issuerId>`), the Game Session-owned global account active-binding index (`session:game:index:account:<accountId>`), and the Game Session-owned global issuer active-binding index (`session:game:index:issuer:{issuerIndexLayoutTag}:<issuerId>:<partitionId>`) are intentionally not tenant- or region-tagged. The connect-token family is a narrow Account-owned, single-key issuance-result projection keyed with tenant identity but not a gameplay/session or region aggregate; it is not used in shard-local multi-key Lua and is reset through Account's exact tenant/request inventory and owner recovery contract. The Gateway's fixed tag is a slot-locality tag, not tenant or region scope. These are explicit global authority or global coordination exceptions only; all ordinary tenant/region key families remain subject to the general tagging rules. Exact-token, connect-token issuance-result, and authority-generation projections remain outside tenant/region key-tagging rules and are untouched by region- or tenant-scoped coordination resets except through their owning authority/reprojection contracts. The global account index remains one full-key-hash-sharded key; narrower resets reconcile only affected references rather than deleting unrelated tenants. The global issuer index is also outside those tags, but narrower resets reconcile only their affected binding references rather than flushing a whole issuer partition.

- **`{tenantRegionTag}` hash tag**
  - Tick‑region coordination keys use a canonical hash tag placeholder `{tenantRegionTag}` derived from the complete `<tenantId, gameInstanceId, regionId>` scope. The projection must remain collision-safe; callers treat the concrete encoding as opaque.
  - Properties:
    - The concrete string format is an implementation detail of shared key helpers; callers treat it as opaque.
    - All region‑scoped keys for a given `<tenantId, gameInstanceId, regionId>` share the same full-scope `{tenantRegionTag}` and therefore land in the same Redis Cluster slot.
    - Multi‑key coordination scripts must only receive keys that share the same hash tag; CI and helpers enforce this.
  - Representative patterns:
    - `tick:{tenantRegionTag}:lock:<entityId>`
    - `tick:{tenantRegionTag}:pending`
    - `timer:{tenantRegionTag}`
    - `retry:{tenantRegionTag}`
    - `tick-executor-lease:{tenantRegionTag}`

- **`{tenantInstanceTag}` hash tag**
  - Instance-scoped coordination or automation projection keys use a canonical opaque hash tag placeholder `{tenantInstanceTag}` derived from `<tenantId, gameInstanceId>`.
  - The concrete string format is an implementation detail of shared key helpers; callers must not replace it with a tenant-only tag or append a second raw instance identifier.

- **`{tenantGameplayTag}` hash tag**
  - Session-only gameplay keys use a canonical hash tag placeholder `{tenantGameplayTag}` derived from `<tenantId>`.
  - Properties:
    - The concrete string format is an implementation detail of shared key helpers; callers treat it as opaque.
    - The session record plus its tenant-scoped uniqueness and reverse indexes for one tenant share the same `{tenantGameplayTag}` and therefore land in the same Redis Cluster slot.
    - Session-only Lua scripts may perform shard-local multi-key CAS/update flows across these tenant-scoped keys, but they must not include the untagged global account index, mix `{tenantGameplayTag}` session keys with `{tenantRegionTag}` tick-region keys, or claim cross-slot account-index atomicity in the same invocation.
  - Representative patterns:
    - `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>`
    - `session:game:index:character:{tenantGameplayTag}:<playableStateNamespaceId>:<characterId>`
    - `session:game:index:account-tenant:{tenantGameplayTag}:<accountId>`
    - `session:game:index:tenant:{tenantGameplayTag}`
    - `session:game:index:realm-grant:{tenantGameplayTag}:<grantScopeId>`

- **`{issuerIndexLayoutTag}` hash tag**
  - Issuer active-binding index partitions use the canonical opaque hash tag `{issuerIndexLayoutTag}` derived from `(issuerIndexLayoutVersion, issuerId, partitionId)`. Each partition is independently readable and writable; issuer partitions are not mixed with `{tenantGameplayTag}` keys in a shard-local Lua invocation.
  - Representative pattern: `session:game:index:issuer:{issuerIndexLayoutTag}:<issuerId>:<partitionId>`.

- **Coordination vs cache prefixes**
  - Canonical coordination prefixes (for example `tick:*`, `timer:*`, `retry:*`, `session:game:*`, `session:auth:token:*`, `session:auth:generation:*`, `session:connect-token:*`, `gateway:connect-token:{gateway-connect-token-replay-v1}:jti:*`, `gateway:connect-token:{gateway-connect-token-replay-v1}:deny:jti:*`, `gateway:connect-token:{gateway-connect-token-replay-v1}:readiness`, and `tick-executor-lease:*`) live **only** on Coordination Redis. The shared `replayAdmissionFence` is a field in `gateway:connect-token:{gateway-connect-token-replay-v1}:readiness`, not a physical prefix. The current generic Cache-bound writer's untagged `gateway:connect-token:*` replay marker is migration-only implementation drift, not a current canonical Coordination Redis prefix or authority.
  - Cache and rate‑limit prefixes (for example `inventory:*`, `view:room-look:*`, `ratelimit:*`) live **only** on Cache/Rate‑Limit Redis.
- Coordination prefix ownership is normative: Account owns the live legacy `session:auth:account:*` and `session:auth:tenant:*` projections, the target `session:auth:token:*` exact-token registry, the target `session:auth:generation:*` authority-generation projections, and the target `session:connect-token:*` exact-input issuance-result projections. Gateway owns only the shared replay-domain exception: `gateway:connect-token:{gateway-connect-token-replay-v1}:jti:*`, `gateway:connect-token:{gateway-connect-token-replay-v1}:deny:jti:*`, and `gateway:connect-token:{gateway-connect-token-replay-v1}:readiness` carrying `replayAdmissionFence`; this does not grant gameplay-session, Account-auth, or general coordination ownership. Game Session owns the separately approved gameplay families under `session:game:*`, including `session:game:auth:issuer-generation:v1:<issuerId>`; it never owns the Account auth prefixes, and no wildcard `session:auth:*` grant is implied. Game Session also owns `tick:*`, `timer:*`, `retry:*`, and `tick-executor-lease:*`; it does not own or mutate the target-only, unimplemented Automation & Scripting families `automation:timer:*` or `script-scheduler:*`. The retired `automation:tick:*` staging path is not part of the live design or active prefix inventory. Automation & Scripting owns its current automation prefixes and the reserved target families once implemented; non-owner participation is contract-bound through approved helpers. See `design/architecture/decisions/adr-0009-coordination-redis-ownership-boundary.md`, with later canonical owner contracts including ADR 0029 defining the Gateway replay carrier.
  - New prefixes must be registered in the canonical catalogs:
    - Coordination prefixes and their reset policies belong in the reset policy matrix and any extended catalogs in `system-architecture-redis-reset-and-recovery.md`.
    - Cache/rate-limit prefix details belong in the [Cache/Rate-Limit Key Catalog](./system-architecture-redis-cache-reference.md#cacherate-limit-key-catalog), including their correctness class and reset tolerance; cache policy remains in [Redis Cache & Rate Limiting](./system-architecture-redis-cache.md).
  - For each new or changed prefix, designs must record:
    - Role (Coordination vs Cache/Rate‑Limit).
    - Measured coordination-write exposure and reset behavior (reset‑tolerant, reset‑sensitive, or reset‑forbidden).
    - Expected owners and usage patterns, and links to the relevant service README sections.

The **Redis Cheat Sheet** maintains a representative prefix → role/owner mapping. The **Redis Design Checklist** includes concrete checks to run before adding or changing any prefix.

### Shard-Local Design Checklist (Quick Reference)

When designing or reviewing coordination flows, use this shard-local checklist:

- In normal application and routine runbook paths, all coordination mutations use owned typed key and mutation helpers; raw Redis commands are prohibited. The external infrastructure step of a fenced recovery/reset is permitted only after the durable operation and maintenance lock, protected Account authority/token and replay-domain cutover/fence, and the complete [canonical pre-wipe gates](./system-architecture-redis-ops-access.md#canonical-pre-wipe-gates) are complete. Whole-deployment `FLUSHALL` and node-local AOF reset/replacement are separate destructive actions; the former requires the canonical deployment blast-radius evidence, while the latter requires the fresh [canonical `physical-dedication-proof/v1` exact binding](./system-architecture-redis-reset-and-recovery.md#coordination-reset-model), and a resolved scope value alone is insufficient. After startup, immutable `post_reset_replacement_verification/v1` must be accepted through the complete [canonical post-reset verification checklist](./system-architecture-redis-ops-access.md#canonical-post-reset-verification-checklist) before `continueRecovery` or protected admission can reopen. Incident break-glass writes remain incident-only and must follow the documented reset and verification lifecycle; none of these exceptions authorize ordinary raw commands or bypass the lifecycle. Registered Lua is mandatory for atomic multi-key behavior and may be used for a single-key mutation only when an explicitly documented atomic guard or compare-and-set contract requires it; ordinary single-key mutations use typed helpers without Lua. Any Lua multi-key operation must be shard-local, with all `KEYS` sharing the same `{tenantRegionTag}`, `{tenantInstanceTag}`, `{tenantGameplayTag}`, `{issuerIndexLayoutTag}`, or fixed `{gateway-connect-token-replay-v1}` hash tag and Redis Cluster slot. The Gateway replay consume invocation must use exactly the fixed `{gateway-connect-token-replay-v1}` tag for its readiness, replay-marker, and deny-marker keys; it must not mix those keys with tenant, instance, region, or issuer keys. An issuer-index invocation may contain only keys with one exact issuer layout/partition tag and must not mix issuer-index keys with tenant, instance, region, or Gateway replay keys.
- Cross-region behavior is implemented via per-region operations and durable follow-up records in PostgreSQL, **not** via cross-region multi-key scripts.
- Callers always construct keys via shared key helpers (for example, builders in `firemud-common`) so `{tenantRegionTag}`, `{tenantInstanceTag}`, `{tenantGameplayTag}`, `{issuerIndexLayoutTag}`, fixed `{gateway-connect-token-replay-v1}`, prefixes, and slots remain consistent; scripts and callers must not hand-roll key strings with embedded hostnames, region names, or ad-hoc hash tags.
- CI and the Lua Script Registry:
  - Reject registry entries that claim shard-local multi-key semantics but declare keys that cannot share a hash tag.
  - Reject coordination scripts that reference cache/rate-limit prefixes or omit required reset and work-class loss-outcome metadata.

If a proposed coordination pattern cannot satisfy this checklist, it should be treated as an architectural change and captured first in design docs (Redis + tick) before any implementation work proceeds.

### Coordination Key Examples

This table lists representative coordination keys and their responsibilities. Full semantics live in service‑specific docs and Lua descriptors, but these examples provide a quick mental model:

| Redis Key | Description |
| --- | --- |
| `tick:{tenantRegionTag}:lock:<entityId>` | Lock for an entity during tick execution within a region. |
| `tick:{tenantRegionTag}:pending` | Staged results for a tick region (single in‑flight tick). |
| `tick:{tenantRegionTag}:queue:<entityId>` | Per‑entity command queue within a region. |
| `tick:{tenantRegionTag}:session-binding:<entityId>` | Region-authoritative gameplay session binding for an entity. Stores the currently admitted `sessionId` and `binding_generation` for region-local command admission and takeover cleanup. |
| `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>` | Authenticated gameplay session record holding reconnect eligibility, auth/session CAS fields, and the latest desired gameplay binding generation for one tenant-scoped session. |
| `session:game:index:character:{tenantGameplayTag}:<playableStateNamespaceId>:<characterId>` | Target tenant-scoped one-controller uniqueness index for `{tenantId, playableStateNamespaceId, characterId}`. Server-derived `playableStateScope` remains binding evidence. The value/evidence retains `sessionId`, `gameInstanceId`, and `bindingGeneration`; it is updated atomically with the session record inside the session-only CAS flow. The existing `<gameInstanceId>:<characterId>` index shape is current implementation drift, not the target key. |
| `session:game:index:account:<accountId>` | Untagged global account-wide set projected by Game Session. The index and its repair/reconciliation protocol are owned by [Session Behavior](./system-architecture-session-behavior.md#global-account-active-binding-index); it is a deliberate cross-tenant exception for account-wide revocation and repair, not an authorization source and never a tenant-local Lua/CAS key. |
| `session:game:index:account-tenant:{tenantGameplayTag}:<accountId>` | Tenant-scoped account reverse index used for bounded revocation, reconnect, and inspection without wildcard scans. |
| `session:game:index:tenant:{tenantGameplayTag}` | Tenant-scoped reverse index used for bounded revocation, reconnect, and inspection without wildcard scans. |
| `session:game:index:realm-grant:{tenantGameplayTag}:<grantScopeId>` | Tenant-scoped lifecycle-bound non-public grant index, covering ordinary private and playtest grants, used for bounded realm admission and revocation. `grantScopeId` is the exact shared-codec `grant/v1` scope ID for the complete Account-owned tuple; Account-owned grant state remains authoritative. Public-production and unscoped bindings have no entry. |
| `session:game:index:issuer:{issuerIndexLayoutTag}:<issuerId>:<partitionId>` | Global-per-issuer bounded hash of active/provisional binding references and captured issuer generations across tenants, maintained by Game Session through the versioned-layout repair/CAS and durable coverage-ack protocol and swept across the finite configured partition range for issuer cutoffs. |
| `retry:{tenantRegionTag}` | Retry queue for failed actions, keyed by `next_eligible_tick_id` on the target region timeline (not wall-clock due time). |
| `tick-executor-lease:{tenantRegionTag}` | Redis-local liveness key for the active tick executor. Its value is an opaque token checked by lease Lua; durable ownership and handoff semantics are owned by [Tick System: Region Authority and Tick Executor](./system-architecture-ticks.md#region-authority-and-tick-executor). |
| `timer:{tenantRegionTag}` | Sorted set of timers for a region; score is expiration timestamp (ms), members encode entity/effect metadata. |
| `remote:{tenantInstanceTag}:<entityId>` | Best‑effort, TTL-bounded hint marker scoped to the complete `<tenantId, gameInstanceId>` identity for cross‑region follow‑ups (durable follow‑ups live in PostgreSQL). Default `remote_hint_ttl_ms = 60_000`; expiry/missing keys affect latency only. Tenant/cluster reset tooling resolves game instances from the durable scope inventory and scans one `remote:{tenantInstanceTag}:*` pattern per instance; no tenant-only remote key family exists. |
| `route:{tenantRegionTag}:gamesession` | Reserved for a potential future gameplay routing view for `<tenantId, gameInstanceId, regionId> → shardTarget`. Per ADR 0007, lease-aware edge admission and a client-visible shard handoff signal are not part of the current edge contract; do not implement Gateway consumption of this mapping without a dedicated sharding/routing design update. |
| `tick-events:{tenantRegionTag}` and `tick-events-offset:{tenantRegionTag}:<consumerId>` | Best‑effort per-region tick event stream and per-consumer offset (typically Redis Stream entry ID). Each consumer's offset value must include `{tenantId, gameInstanceId, regionId, consumerId, region_epoch, latestTickId, streamOffset}`; consumers compare `region_epoch` with the current control-plane epoch and discard that consumer's value before reuse on mismatch. Streams are retention-capped (default `tick_events_maxlen = 2048` per region); consumers treat trimmed history as normal truncation and bootstrap from committed heartbeats/RegionStatus. |
| `tick-events-lease:{tenantRegionTag}` | Best-effort lease to avoid duplicate tick-event consumption work by observers. Safe to drop; consumers reacquire after restarts/resets. |
| `automation:timer:{tenantRegionTag}` | **Target-only, once implemented.** Reserved for the region-scoped Automation & Scripting timer index for `onInterval` and timer coordination. Stored entries must remain instance-aware in payload and durable identity (`gameInstanceId`, and plugin identifiers when applicable) even though the Redis key is region-scoped for slotting and reset targeting. No current key or reset operation is defined for this unimplemented target projection. |
| `script-scheduler:{tenantRegionTag}:lastTickId` | **Target-only, once implemented.** Reserved for the Automation & Scripting derived discovery hint for “every N ticks” triggers. Its value will contain `{regionEpoch, latestTickId}` and be rejected/rebuilt when the stored epoch differs from the authoritative epoch. It will not store or own `streamOffset`; `tick-events-offset:{tenantRegionTag}:<consumerId>` is the sole event-stream offset record for each consumer. Durable automation schedules, quotas, and trigger-instance de-duplication live in PostgreSQL; this unimplemented key is not the source of truth for which scripts should eventually run or whether a due trigger was already emitted. No current key or reset operation is defined. |

Region‑scoped coordination metadata keys share the same full-scope `{tenantRegionTag}` hash tag and therefore carry `<tenantId, gameInstanceId, regionId>` while landing in the same Redis Cluster slot. Instance-scoped projections use `{tenantInstanceTag}` for `<tenantId, gameInstanceId>`, and tenant-scoped gameplay session keys share `{tenantGameplayTag}` for session-only CAS/index updates. Pre-auth transport context and tenant-only auth/quotas are intentionally outside the runtime region scope and must retain their documented lifecycle scope.

## Topology Compatibility Overview

Redis features and assumptions in FireMUD must work across both single‑instance and clustered deployments. This table summarizes what is supported; operational details and exact configuration live in **Redis Usage & Profiles** and **Redis Operations & Migrations**.

| Topology | Coordination Usage | Cache/Rate‑Limit Usage | Notes |
| --- | --- | --- | --- |
| Single‑node with AOF (coordination) | **Supported.** All coordination prefixes (`tick:*`, `timer:*`, `retry:*`, `session:game:*`, `session:auth:token:*`, `session:auth:generation:*`, `tick-executor-lease:*`, etc.) and shard‑local Lua patterns apply. Measured unreplicated-write exposure and AOF replay guarantees assume this profile or better. | **Supported** on a separate Cache/Rate‑Limit deployment (distinct process or container). | Recommended baseline for `dev_local` and `hobby_self_hosted` profiles. |
| Single‑node without AOF (ephemeral coordination) | **Supported only for explicitly labelled one-shot test/CI stacks** (hosted `pr-preview` is excluded) that opt out of measured unreplicated-write SLOs and replay guarantees. Coordination keys are disposable and must be reset‑tolerant. | **Supported** on a separate Cache/Rate‑Limit deployment by default. An explicitly labelled one-shot test/CI stack may temporarily collapse both roles under ADR 0171's narrow exception. | Not appropriate for environments where role-isolation, tick replay, measured loss-window SLOs, or long‑lived coordination logs are required. |
| Redis Cluster (coordination) | **Supported** provided all coordination Lua scripts obey shard‑local rules using `{tenantRegionTag}` for region/tick flows, `{tenantInstanceTag}` for instance-scoped automation and remote-hint flows, `{tenantGameplayTag}` for tenant-scoped session flows, `{issuerIndexLayoutTag}` for one issuer-layout partition, and the fixed `{gateway-connect-token-replay-v1}` for Gateway replay-admission flows. Multi-key coordination scripts must only touch keys that share one hash tag and slot; the reserved Automation & Scripting families `automation:timer:*` and `script-scheduler:*` remain target-only and unimplemented, while the retired `automation:tick:*` path is not a current family. | **Supported** for cache/rate‑limit workloads; rate‑limit prefixes (`ratelimit:*`) are treated as single‑key operations without cross‑slot atomicity. | Cluster deployment requires strict adherence to the canonical family/tag rules in [Key Naming and Shard Discipline](#key-naming-and-shard-discipline), including the issuer-layout partition and instance-scoped automation families. |

In all non-ephemeral topologies:

- Coordination Redis and Cache/Rate‑Limit Redis are **separate deployments** (distinct processes/containers) even when they share the same host or Kubernetes node.
- Application and tooling configuration **must not** point `FIREMUD_REDIS_COORD_*` and `FIREMUD_REDIS_CACHE_*` to the same endpoint; endpoint overlap is an invalid topology.
- Shared configuration helpers must detect endpoint overlap (for example, by comparing resolved host/port pairs), fail health checks, and emit a clear failing health indicator when both roles resolve to the same target. This is a hard configuration/health failure in every non-ephemeral environment, including `dev_local`, staging, production, and long-lived hobby/self-hosted deployments.

Only an explicitly labelled one-shot test/CI environment may collapse both roles into one process and endpoint. In that narrow ephemeral exception, overlap produces warning/visibility in logs, metrics, and health output but does not fail health checks solely for that reason. The stack must be reset-tolerant and cannot provide coordination-isolation, replay, or SLO evidence; hosted `pr-preview` and every persistent or player-facing environment retain the normal split. See [ADR 0171](./decisions/adr-0171-separated-redis-role-processes-and-owned-keyspaces.md) and [Redis Usage & Profiles](./system-architecture-redis-usage-and-profiles.md#environment-mappings).

## External Invariants Redis Depends On

Redis designs in FireMUD assume several invariants that are defined and enforced in other parts of the system. This section summarizes the most important ones so Redis reviews do not have to repeatedly re-derive them:

- **Region lease key consequences**
  - The tick owner defines `regionEpoch`, durable `executorFence`, lease acquisition, revalidation, takeover, outage, and reset semantics in [Tick System: Region Authority and Tick Executor](./system-architecture-ticks.md#region-authority-and-tick-executor). Redis does not define or advance those durable identities.
  - `tick-executor-lease:{tenantRegionTag}` stores only the opaque lease token; `region_epoch` is read from the separate `tick:{tenantRegionTag}:meta` view and/or the durable reset contract. Region lease and coordination Lua receives both values separately, compares them before mutation, and follows the canonical result mapping in [Redis Lua Patterns](./system-architecture-redis-lua-patterns.md#canonical-region-lease-and-tick-staging-result-mapping).
  - Lease uncertainty, partition, or expiry must make Redis mutations fail closed. Redis key presence, token correlation, or a successful local script is not durable ownership proof and cannot authorize staging or effect dispatch.
  - Ordinary handoff retains the epoch while replacing the durable fence; for a reset, the reset owner establishes the durable new epoch, initializes and verifies local metadata while recovery remains fenced, and releases the scope only after the owner-defined gates complete, while old-epoch keys remain stale and are ignored or cleaned according to [Redis Reset & Recovery](./system-architecture-redis-reset-and-recovery.md#canonical-reset-sequence-boundary).
- **Idempotent domain effects**
  - Domain-level effects (damage application, currency transfers, quest progress, etc.) are recorded via idempotent identifiers or transaction rows in PostgreSQL (see `system-architecture-transactions.md`).
  - Coordination keys such as `pending` entries and retries rely on these idempotency guards: re-running ticks or retries must not double-apply or silently lose logical effects even if Redis state is replayed, partially lost, or exceeds the measured unreplicated-write-window SLO.
- **Transactional boundaries**
  - Services that participate in ticks and coordination flows encapsulate their durable writes in transactions with clear boundaries and conflict detection (for example, optimistic locking or explicit version checks).
  - Redis designs may assume that “commit vs abandon/cleanup” is visible in domain state and must not introduce coordination patterns that require peeking into in-flight, uncommitted work.
- **Authentication and session semantics**
  - Session TTLs and reconnect windows follow the authentication settings described in `system-architecture-authentication.md` and `system-architecture-reconnection.md`.
  - Session-related Redis keys (`session:game:*`) are expected to enforce those logical expiry rules; Redis designs must not introduce independent notions of “session lifetime” that diverge from the documented auth contracts.

When changing any of these external invariants, update this section and the referenced docs together so Redis designs and reset/runbook assumptions remain aligned.
