## Scope and Ownership

- The Automation & Scripting Service evaluates scripts, persists admitted work, and coordinates runtime reloads and queue projection.
- Game Session owns the authoritative tick queues, pin state, and execution-time version fence.
- Game Design owns authoring and publish-time validation, not runtime execution.
- Redis is a coordination and projection layer. Durable outbox rows remain the source of truth for admitted work.

When this document and the DSL reference appear to overlap, use the DSL reference for graph/model/determinism semantics and this document for runtime ownership, outbox, queue projection, and rollback behavior.

## Normative Target Contract

The target runtime uses one canonical two-layer lifecycle, not parallel state machines. The trigger lifecycle has pre-`EVALUATED_COMMITTED` states `PENDING_EVALUATION` and `EXECUTING`, followed by the committed post-evaluation state `EVALUATED_COMMITTED`; evaluated command descriptors use the existing `PENDING`, `INDEXED`, `HANDOFF_IN_FLIGHT`, `HANDED_OFF`, `CANCELED`, and `DEAD_LETTERED` statuses. The trigger and descriptor layers have separate roles and must not be collapsed into one command-outbox status.

`EVALUATED_COMMITTED` is the canonical target trigger state reached by the atomic descriptor commit. One transaction persists the immutable evaluated descriptor rows, parent outbox evidence, terminal evaluation outcome, and audit update, and compare-and-set transitions the pre-`EVALUATED_COMMITTED` trigger from `EXECUTING` to `EVALUATED_COMMITTED`. Recovery uses the committed descriptors and retained outcome as its only replay input and never re-enters the DSL. The trigger state itself contributes zero to `activeExecutionCount`; any unresolved child descriptors contribute through their descriptor status.

## Current Implementation Status

This section records current implementation boundaries, not target-state authority. The normative contracts below and the linked owning documents remain canonical. Metric names, labels, and increment units are owned by [Table 4](./system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix); audit fields and handoff diagnostics are owned by the [Scripting & Automation Observability Contract](./system-architecture-scripting-observability-contract.md). Normative audit stage/outcome semantics and final lifecycle statuses remain owned by the normative audit and scripting lifecycle/rollout documents.

The current runtime now includes a first durable work-item executor instead of stopping at ingress-only outbox materialization. During ingress, after handler resolution, Automation acquires per-script quota for live `STANDARD_RUNTIME` handlers before persisting `PENDING_EVALUATION` work. The executor claims `PENDING_EVALUATION` rows without re-charging that per-script quota; it separately applies tenant-budget, publish-readiness, or isolated dry-run capacity controls as applicable before loading the persisted script definition, evaluating a current-boundary command-emission format, and handing emitted commands to Game Session through `EnqueueAutomationCommandIfAbsent`. The target durable full-Trigger-Identity charge record and separate exactly-once admission/execution-start markers remain unimplemented. The replay and evaluated-descriptor layers described by the target lifecycle are target-only. The current implementation still uses one `script_work_items` row spanning the pre-DSL trigger and later handoff processing; it does not yet implement the target separation between durable trigger state and evaluated command descriptors or descriptor-only replay.

### Current evaluator boundary

The current evaluator supports a bounded emitted-command collection per work item, assigns deterministic local ordinals in emitted-command order, and attempts handoff for each emitted command. An actual configured output-count or per-entity limit is rejected before output/descriptor persistence or handoff; the pre-DSL parent work item was claimed from `PENDING_EVALUATION` and is `EVALUATING` at evaluation time, then its durable terminal transition and audit row record `finalStage=DSL_EVAL`, `finalOutcome=sandbox_error`, and the exact bounded limit reason (`command_count_exceeded` or `per_entity_command_limit_exceeded`). This local multi-command behavior does not establish the target end-to-end handoff contract: the live Game Session boundary still lacks `scriptPinEpoch`, `commandOrdinal`, and the complete Trigger/Command-Handoff Identity, so per-command deduplication, fence proof, and independent progress remain unproved. The target contract remains canonical in [Scripting & Automation: Cross-Service Contracts](./system-architecture-scripting-contracts.md#2-script-work-item-vs-tick-command-boundary), including deterministic identity under the complete [Command-Handoff Identity](./system-architecture-scripting-normative-contract-tables.md#command-handoff-identity-target-state).

That current-boundary execution format is intentionally narrow but no longer raw-text-only: script definitions may expose `emitCommands` at the top level or under `eventHandlers.<eventType>.emitCommands`, and each emitted command may currently carry either direct `commandText` or a structured `commandAlias` plus templated `arguments`, along with an optional target entity or bounded `targetEntityIds[]` list, optional explicit target runtime scope (`targetGameInstanceId`, `targetRegionId`, `targetRegionEpoch`), `requiresSoloTick`, and optional `dueTickId`. The evaluator may expand `targetEntityIds[]` locally and attempt one command per listed target. If no target is present, the command targets the triggering work item's entity; if explicit target runtime scope is absent, the command defaults to the triggering work item's owned gameplay scope. Each resulting command receives a local ordinal and is attempted through the handoff service, but this local expansion is not the target-state multi-target fan-out contract: the live wire does not carry the complete per-target identity or target `playableStateScope`, so complete handoff identity, scope validation, deduplication, and end-to-end progress remain unproved. Command nodes may also carry bounded `when` / `unless` predicate maps over durable work-item metadata and flat primitive payload fields; target-state command ordinals and optional `targetPlayableStateScope` distinguish emitted commands after handoff identity is widened. Template substitution is still limited to durable work-item metadata and flat primitive payload fields such as `{{payload.commandName}}`. Richer graph execution and broader DSL semantics remain target-state work above this first production evaluator path.

The current claim boundary is the atomic PostgreSQL transition from `PENDING_EVALUATION` to `EVALUATING`; the existing Game Session lease rules govern region-owned tick execution, not Automation work-item claims. The current implementation has no evaluation lease expiry, fencing generation, descriptor-commit marker, or recovery owner. While `PAUSED_FOR_ROLLBACK`, its `GetAutomationDrainStatus` implementation restricts the counted set to rows whose `workItem.admissionEpoch <= 0` or `workItem.admissionEpoch < current admissionEpoch`, excluding positive current-epoch rows; within that set `activeExecutionCount` counts `EVALUATING` and `HANDOFF_IN_FLIGHT`, including unresolved stale `EVALUATING`, and `pendingCancelableWorkItemCount` counts `PENDING_EVALUATION`. Normal mode counts the corresponding scoped rows without that epoch filter. These are current implementation gaps: the current runtime retains unresolved work and keeps the Automation admission barrier closed; ordinary gameplay ticks continue except within a separately declared unfenced-effect workflow. It cannot safely resume or promise terminal audit from lease age alone. The target mapping and recovery behavior are defined below, and current tooling must not infer reclaim, terminalization, or re-entry to the DSL.

The current `onLoad` implementation slice is tenant-readiness work limited to configuration/runtime metadata validation and warming recomputable in-process caches. It does not perform per-entity setup or create handler-owned durable shared state. Platform-owned execution, readiness, and `script_event_audit` metadata remains required bookkeeping and is not a handler-created effect. The current implementation also lacks stale-`ONLOAD_RUNNING` generation recovery; that gap must not be handled by re-entering the same DSL execution.

At the live Game Session handoff boundary, the current `EnqueueAutomationCommandIfAbsentRequest` wire fields are exactly `tenant_id`, `game_instance_id`, `region_id`, `region_epoch`, `due_tick_id` (logically optional for immediate event-driven work), `automation_dispatch_id`, `automation_work_item_id`, `script_id`, `script_patch_version`, `target_entity_id`, `command`, `requires_solo_tick`, `plugin_id`, `plugin_version_id`, `playable_state_scope`, `world_slug`, `realm_slug`, `pointer_version`, `origin_source_kind`, `origin_source_state`, `origin_source_ordinal`, `origin_source_due_tick_id`, and `origin_source_due_at_ms`. Its response fields are exactly `accepted`, `admission_outcome`, `command_id`, and `error`. The current `playable_state_scope` is the source/current admitted routing scope, not a distinct target scope; `automation_work_item_id` is the wire alias for parent `outboxWorkItemId`. The request does not carry `script_pin_epoch`, `command_ordinal`, `script_event_id`, `event_type`, `event_schema_version`, `is_dry_run`, `binding_id`, `target_game_instance_id`, `target_playable_state_scope`, `target_region_id`, or `target_region_epoch`; those fields, the complete Trigger Identity, and the complete Command-Handoff Identity are target-only for this direct enqueue boundary. A command with a distinct target runtime scope must not be sent through this local enqueue mutation; if no existing remote follow-up path handles it, the local request rejects before its persistence/handoff attempt. The existing remote follow-up path remains separate and continues to carry its target scope. The supported source/current scope remains admitted. The current executor may attempt multiple emitted commands with local ordinals, but this narrower wire does not prove target per-command identity, deduplication, fencing, or independent progress.

The exact `scriptPinEpoch` propagation and final same-version old-epoch rejection are therefore target-state only at this boundary. The live request carries `scriptPatchVersion` but not `scriptPinEpoch`, so live Game Session handoff cannot reject same-version work produced under an older script pin epoch today; this current limitation must not be presented as target enforcement.

Target local instance admission and replay use Automation's bounded-fresh exact `(scriptPatchVersion, scriptPinEpoch)` projection; when it is absent or stale, Automation performs a bounded refresh from an epoch-carrying authoritative Game Session read and fails closed if that refresh cannot prove the tuple. Direct Game Session reads remain the owner/final-fence source and are used to freeze a remote target tuple; neither path permits a patch-only local pointer or version-only fallback. See [ADR 0108](./decisions/adr-0108-no-degraded-script-admission-without-authoritative-pin.md) and the [cross-service version-fencing contract](./system-architecture-scripting-contracts.md#3-version-fencing-rollback-safety).

**Target-state remote-follow-up consequence:** When a follow-up crosses to a distinct target game instance, the source work retains the originating exact `(scriptPatchVersion, scriptPinEpoch)` as immutable provenance and source rollback-fence evidence. Before target-side Automation admission, Game Session revalidates that source tuple, reads and freezes the target instance's current exact tuple, and binds both tuples to the target delivery/claim and immutable request/dedupe evidence. Target event/handler Trigger Identity and target-side script admission/execution fences use the target tuple, not the source tuple. Retries reuse both frozen tuples; source or target displacement/conflict fails closed, authority unavailability remains retryable with no target admission, and target `UNPINNED` creates no target script work. A same-instance cross-region follow-up uses one exact tuple for both roles.
For semantic target `UNPINNED`, Game Session applies the owner-defined durable/replayable result encoding and exact-retry/conflict rules; the target creates no Automation event, work item, or command. See the [Game Session remote-follow-up result contract](./microservices/game-session-service/api-contracts.md#service-interactions). Authority unavailability remains retryable and non-admitted rather than becoming that finalized result.

Current dedupe, rejection, and status diagnostics use the available `outboxWorkItemId`/parent work-item correlation, persisted `automationDispatchId`, Game Session `commandId`/persisted `gameSessionCommandId`, command text, selected provenance, and `script_event_audit`. `outboxWorkItemId` is not a per-command discriminator. This is a live diagnostic and retry fallback only; it does not claim end-to-end complete Trigger Identity, `commandOrdinal`, independent per-command progress, or target command-level deduplication/fence proof.

## Pre-DSL Trigger and Evaluated Descriptor Boundary

The durable pre-DSL trigger state and the post-DSL evaluated command descriptor/outbox are separate durable roles:

- The target lifecycle for the **pre-DSL trigger record** is `PENDING_EVALUATION` -> `EXECUTING` -> `EVALUATED_COMMITTED`, with explicit terminal cancellation/dead-letter transitions only where the cancellation and stale-recovery rules below permit them. The record owns the complete applicable Trigger Identity, event payload, pinned script/configuration and artifact references, the immutable handler-scoped input manifest, admission epoch, evaluation lease, fencing generation, and the durable descriptor-commit marker/status. Before that descriptor commit, a command-capable gameplay/runtime evaluation has no `automationDispatchId` or command-child identity. It contains no evaluated gameplay command descriptors. The manifest is the deterministic read input; an owner-specific `read_snapshot_token`, when applicable, is one recorded manifest entry rather than universal authority.
- The **evaluated command descriptor/outbox** is created only after DSL evaluation. It contains the immutable evaluated descriptor for each emitted command, including `automationDispatchId` and `commandOrdinal`, plus parent `outboxWorkItemId` correlation, the applicable trigger/configuration inputs, and optional `targetGameInstanceId`, `targetPlayableStateScope`, `targetRegionId`, and `targetRegionEpoch` when the command has a distinct target runtime scope needed for handoff and replay.

**Target state only:** Before DSL evaluation, the worker acquires the separately fenced, reclaimable capacity lease and uses one Automation-owned durable executor-acceptance transaction to revalidate the current fence, durably accept/claim the run for the executor, persist the exactly-once execution-start marker, and compare-and-set the pre-DSL trigger to `EXECUTING` with a monotonically increasing fencing generation. Evaluation begins only after that transaction commits. Tenant-readiness `onLoad` is non-emitting and neither allocates nor exposes a command dispatch identity. The worker may commit evaluated descriptors only while that lease and generation are current. If commands are emitted, the descriptor rows, their parent outbox record, the persisted `automationDispatchId` and canonical ordinals, the terminal evaluation outcome, and the audit update are committed atomically with a compare-and-set transition from `EXECUTING` to `EVALUATED_COMMITTED` in one transaction; a valid zero-command evaluation creates no dispatch identity. A non-cancellation retry after that commit boundary loads the committed descriptors and replays handoff; it never re-enters the DSL. If executor acceptance cannot commit, the transition does not occur, the lease is released or reclaimed, and no execution charge is recorded.

The `EVALUATED_COMMITTED` state is the durable descriptor-commit marker/status. If the execution lease expires, Automation's recovery owner must first read that state. `EVALUATED_COMMITTED` makes the persisted descriptor rows and retained evaluation outcome the sole replay input, and recovery replays them without DSL re-entry. Only a stale `EXECUTING` state with no committed marker/status may be compare-and-set by the recovery owner to a terminal audited `DEAD_LETTERED` outcome with `finalStage=DSL_EVAL`, `finalOutcome=canceled`, and `finalReason=stale_execution_fenced`.

Target-state cancellation of pre-DSL trigger states is durable and fencing-aware:

- `PENDING_EVALUATION` transitions by compare-and-set to terminal `CANCELED` without entering the DSL. The same durable transition records `cancelReason` and updates `script_event_audit` to `finalStage=ADMISSION`, `finalOutcome=canceled`, and the applicable bounded reason, such as `operator_canceled` or `rollback_epoch_advanced`.
- `EXECUTING` cancellation first fences the claimed attempt and reads the descriptor-commit marker/status. If the state is or becomes `EVALUATED_COMMITTED`, cancellation never resumes or re-dispatches a committed child: evaluated `PENDING` and `INDEXED` children compare-and-set to `CANCELED` with durable `cancelReason`, `finalStage=WORK_ITEM_PERSIST`, and `finalOutcome=canceled`; `HANDOFF_IN_FLIGHT` fences further retry and reconciles the durable downstream outcome, remaining active/unresolved when that outcome is ambiguous; and `HANDED_OFF`, `CANCELED`, or `DEAD_LETTERED` children retain their outcome and no-op. Recovery of that committed state is a separate path owned by the control-plane recovery contract and may replay only the stored child ledger; cancellation itself does not dispatch. If no descriptor was committed, explicit cancellation compare-and-sets the trigger to terminal `CANCELED` and records `cancelReason`, `finalStage=DSL_EVAL`, `finalOutcome=canceled`, and the applicable bounded cancellation reason; this terminal cancellation is never replay-eligible. If the lease is instead expired and stale, only the distinct recovery-owner transition may make the row terminal `DEAD_LETTERED` with `finalStage=DSL_EVAL`, `finalOutcome=canceled`, and `finalReason=stale_execution_fenced`.

Cancellation and automatic stale-executor recovery never invoke or re-enter the DSL. Separately, control-plane evaluation-stage recovery may re-enter the DSL only when the persisted failure class is retryable under [Failure Modes and Error Handling](#failure-modes-and-error-handling), no descriptor has committed, and frozen manifest/graph evidence and the original work-item/Trigger Identity are present; non-retryable classes remain terminal/ineligible. Once a descriptor is committed, control-plane recovery replays the stored child ledger without DSL re-entry. These cancellation and automatic stale-recovery paths operate only on durable trigger state, descriptor-commit evidence, and already committed descriptors.

## Work Item Outbox Contract (Normative)

The Automation & Scripting Service must treat Redis automation queues (`automation:queue:*`) as derived indexes/pointers only. The authoritative record of admitted post-DSL work is the durable work item outbox. Queue ownership, command handoff, and cross-service retry invariants are defined in the [scripting cross-service contracts](./system-architecture-scripting-contracts.md); this section retains the local outbox schema and projection behavior.

This section defines the minimum contract that makes "persist -> index -> drain -> handoff" interoperable and rollback-safe across services and operational tooling.

### Minimum Outbox Record Fields

For plugin-backed work, every outbox/descriptor record also persists the captured owner `lifecycleRevision` alongside `pluginActivationEpoch`. Both values are fence evidence rather than Trigger Identity or Command-Handoff Identity. `ENABLED` execution and admission require the exact current lifecycle revision; same-version/same-epoch `DRAINING` may retain only the immediately preceding `ENABLED` revision when the work's winning admission CAS durably committed that revision before the durable Automation-owned `DRAINING` admission barrier was created. Mere capture or observation is insufficient, and arbitrary lower, non-executable, or epoch-advanced evidence fails closed.

Each evaluated descriptor/outbox record must include:

- Trigger Identity fields from [Table 1](./system-architecture-scripting-normative-contract-tables.md#table-1-trigger-identity-required-fields) (including `gameInstanceId` and, for gameplay/runtime triggers, `regionEpoch`).
- The exact `scriptPatchVersion` and `scriptPinEpoch` captured from the authoritative Game Session pin. A local active/latest pointer or version-only match is insufficient.
- `outboxWorkItemId` (stable parent correlation identifier; not descriptor identity).
- The unique child identity for each evaluated command descriptor: the complete Command-Handoff Identity, including optional `targetPlayableStateScope` and the other target runtime fields when a distinct target scope applies. `outboxWorkItemId` is parent correlation only and is excluded from command identity, uniqueness, and deduplication keys.
- `createdAt` and `updatedAt`.
- `workItemStatus` (per evaluated descriptor/command; see below, not a pre-DSL trigger or parent aggregate status).
- The immutable evaluated command descriptor (one descriptor per emitted command, stored durably), including immutable `lane`, bounded `cost_class`, and `handoffRequirement` (`REQUIRED` or `OPTIONAL`) metadata.
- `commandCount` (the immutable total number of committed descriptors for the parent `outboxWorkItemId`, for budgeting/inspection; it is not per-descriptor progress).
- `cancelReason` (nullable; required when canceled).

`outboxWorkItemId` is the Automation-owned parent correlation identifier. At the current Game Session boundary, Automation produces `EnqueueAutomationCommandIfAbsentRequest.automationWorkItemId` with this same value, and Game Session consumes/reports it under the wire field name `automationWorkItemId`; these are boundary-specific names for one parent identifier, not separate work-item records. It is not the per-command discriminator and must not be used as command-level dedupe.

Target-state per-command progress follows the [cross-service command boundary](./system-architecture-scripting-contracts.md#2-script-work-item-vs-tick-command-boundary): descriptor identity is the complete Command-Handoff Identity and is linked to the parent `outboxWorkItemId`. Each emitted command has independent durable progress, so a retry resumes only unresolved commands and cannot drop an unattempted command or replay a command already accepted or terminally rejected. A queue pointer may be deduplicated by parent `outboxWorkItemId` for index hygiene, but that does not deduplicate commands. The current live executor attempts each bounded emitted command, but the narrower handoff boundary above does not establish this target per-command identity or progress behavior end to end.

Each emitted command is also represented by one durable child dispatch row under the work item. At minimum it stores `outboxWorkItemId`, the persisted opaque `automationDispatchId` and deterministic `commandOrdinal`, immutable command digest, target scope, `lane`, bounded `cost_class`, `handoffRequirement`, handoff status/result, attempt metadata, and the returned Game Session `commandId` when accepted; a plugin-backed child additionally retains exact `(pluginId, pluginVersionId, bindingId)` provenance and the captured `(pluginActivationEpoch, lifecycleRevision)` pair, plus the durable winning pre-`DRAINING` admission/fence evidence when that narrow exception applies. The durable uniqueness key remains the complete Command-Handoff Identity defined by the [normative identity table](./system-architecture-scripting-normative-contract-tables.md#command-handoff-identity-target-state); it is not widened by evidence checks. Before duplicate evaluation or delivery reads or advances an existing child, it must compare all bound immutable descriptor and binding evidence, including command digest, exact `(scriptPatchVersion, scriptPinEpoch)`, source/target scope, `lane`, `cost_class`, `handoffRequirement`, and all applicable plugin, binding, activation-epoch, lifecycle-revision, manifest, and routing evidence. Any mismatch records a bounded conflict and fails closed; only an exact evidence match may reuse or advance the child rather than creating another logical command. Retries select only unfinished children. The dispatch identifier is allocated and persisted only in the atomic first durable evaluated-descriptor/outbox commit when evaluation emits commands; pre-commit evaluation retries preserve Trigger/work-item/frozen-input identity and allocate no command-child identity, while retries after a winning commit reuse the persisted dispatch ID and ordinals. A valid zero-command evaluation creates no dispatch identity.

**Target-state lane/cost contract:** The evaluated descriptor and each child dispatch retain the immutable `lane` and bounded `cost_class` unchanged through durable work, retry, readback, and recovery. Missing, changed, or contradictory values fail closed and cannot authorize handoff, replay, or application; recovery preserves the admitted values rather than inferring or reclassifying them.

**Target-state handoff-requirement contract:** Evaluation commits the `handoffRequirement=REQUIRED|OPTIONAL` classification required by the accepted [durable per-dispatch handoff decision](./decisions/adr-0063-durable-per-dispatch-script-handoff.md) and persists it on both the evaluated descriptor and child dispatch before handoff. The value is bound by the immutable command digest but is not part of Command-Handoff Identity. Every emitted command must carry exactly one recognized value; missing, unknown, or contradictory descriptor/child evidence fails closed, and retry, readback, and recovery preserve the committed value rather than defaulting or reclassifying it. A valid zero-command evaluation creates no synthetic child. Parent convergence and optional-child retry follow that decision.

When a work item is handed to Game Session, the local wire boundary is:

- `EnqueueAutomationCommandIfAbsent` carries the local handoff fields described in [Current Implementation Status](#current-implementation-status), and its response returns the live Game Session `commandId`/admission outcome. The target handoff identity and fenced acceptance rule are owned by the [cross-service scripting contracts](./system-architecture-scripting-contracts.md#2-script-work-item-vs-tick-command-boundary).

### Minimum Status Model

`PENDING` through `DEAD_LETTERED` are per evaluated descriptor/command statuses; pre-DSL trigger states and any parent-level aggregate are separate. Statuses are a target-state contract; implementations may use different internal names as long as they are mapped 1:1:

- `PENDING` - persisted, eligible for indexing and draining.
- `INDEXED` - a pointer/index has been published into `automation:queue:*` (best-effort; may be rederived).
- `HANDOFF_IN_FLIGHT` - being handed off to Game Session (idempotent retries allowed).
- `HANDED_OFF` - This evaluated descriptor/child was durably accepted by Game Session. The parent aggregate may become `HANDED_OFF`, making `script_event_audit.finalStage=TICK_HANDOFF` eligible for `finalOutcome=handoff_accepted`, once every required child is durably accepted. The parent aggregate remains `HANDOFF_IN_FLIGHT` only while an unfinished required child exists; once required children reach the accepted terminal condition, optional children may continue bounded post-handoff retry and do not block parent convergence to `HANDED_OFF` or `handoff_accepted`. A permanent required-child failure atomically moves the separate parent recovery aggregate to `DEAD_LETTERED` while retaining the `EVALUATED_COMMITTED` descriptor marker and complete output/child ledger, making the parent eligible for `resumed_dispatch` recovery and initializing or advancing `failureGeneration` exactly once.
- `CANCELED` - permanently canceled by control plane (for example rollback, disable, or operator purge). For a committed `EVALUATED_COMMITTED` parent, required-child cancellation is not a dead-letter transition: the fenced, idempotent cancellation operation compare-and-sets cancelable `PENDING`/`INDEXED` children and records the parent/audit consequence atomically once every child is terminal and no child can newly apply; it fences `HANDOFF_IN_FLIGHT` and reconciles its downstream outcome before that terminal commit. The terminal derived parent convergence outcome is `canceled`, represented by the terminal `script_event_audit` with `finalOutcome=canceled` and `finalStage=WORK_ITEM_PERSIST` when handoff was never attempted or `TICK_HANDOFF` when cancellation settled during handoff, while the durable trigger remains `EVALUATED_COMMITTED`. This is why required-child cancellation does not turn the parent handoff aggregate into `HANDED_OFF` and no separate stored parent cancellation status is introduced; the separate parent recovery aggregate remains non-`DEAD_LETTERED` and non-replayable, and exact retries no-op. A prior `handoff_accepted` audit result remains immutable.
- `DEAD_LETTERED` - permanently non-progressing after a fenced terminal decision; bounded retention and operator visibility are required.

### Pointer Payload Contract for `automation:queue:*`

Plugin queue pointers and their durable records retain the captured lifecycle revision as a non-identity fence checksum alongside the activation epoch. Queue rebuild, claim, handoff, retry, and recovery must preserve that evidence and must not treat a stale pointer or local lifecycle observation as authorization.

Entries in `automation:queue:{tenantInstanceTag}:<entityId>` must contain enough information to locate and safely process the durable outbox record:

- `outboxWorkItemId` - the stable parent pointer used to locate the evaluated descriptor set; it must not be replaced by Redis list position. It is not command-level dedupe, which uses the complete Command-Handoff Identity.
- A minimal identity checksum containing `gameInstanceId` and exact `scriptPatchVersion` plus `scriptPinEpoch`; a plugin-backed pointer additionally contains exact `(pluginId, pluginVersionId, bindingId)` provenance and the captured `(pluginActivationEpoch, lifecycleRevision)` pair. This derived checksum may reject stale projection work early but never authorizes execution without loading and revalidating the durable record and, for the narrow same-epoch `DRAINING` exception, its winning pre-barrier admission/fence evidence.

The pointer/index format must be forward-compatible (versioned envelope) so it can evolve without requiring out-of-band Redis migrations.

### Rebuild and Deduplication Rules

For plugin-owned schedule-derived work, rebuilding a due candidate or firing claim never mints a new candidate identity solely because its captured `lifecycleRevision` changed. The old candidate remains fenced under its original evidence; a target schedule reconciliation may derive a fresh candidate only when the scheduler identity tuple changes, including the tagged `pluginActivationEpoch` and excluding `lifecycleRevision`, after exact current admission checks. A lifecycle-revision-only change preserves the old candidate/firing identity and follows the applicable fence or terminalization contract; those identities are never rewritten or reused.

- Rebuilding `automation:queue:*` from the outbox must be safe to run repeatedly and concurrently (idempotent projection).
- Automation's queue-drain/rebuild path must dedupe repeated parent pointers by `outboxWorkItemId` (not by Redis list position) so queue resets and re-indexing do not multiply discovery. The durable executor and Game Session must dedupe each descriptor by the complete Command-Handoff Identity so parent-pointer retries do not cause double-handoff.
- `HANDOFF_IN_FLIGHT` rows are active evaluated descriptors during queue rebuild and recovery. Recovery must load the committed descriptor and retry or confirm handoff by the complete Command-Handoff Identity without re-entering the DSL; if the durable handoff-lease evidence is insufficient, retain the row active/unresolved rather than rebuilding it as fresh DSL work. Explicit cancellation does not use this recovery retry path and instead fences retry and reconciles the durable downstream outcome.
- `CancelPendingWorkItemsForPatch` and `CancelPendingWorkItemsForPluginVersion` must make durable transitions in both layers: `PENDING_EVALUATION` transitions to `CANCELED` at `ADMISSION`; target `EXECUTING` follows the fencing and descriptor-commit rules above; when committed, evaluated descriptors in `PENDING` or `INDEXED` compare-and-set to `workItemStatus=CANCELED` with durable `cancelReason`, `finalStage=WORK_ITEM_PERSIST`, and `finalOutcome=canceled`, `HANDOFF_IN_FLIGHT` fences retry and reconciles downstream outcome while retaining ambiguity active/unresolved, and terminal children no-op. Cancellation remains authoritative if Redis is reset and is reflected in the corresponding stage-aware `script_event_audit` outcome.

### Operational Constraints

- Outbox scanning for rebuild and cancellation must be bounded and backpressured (pagination, time windows, per-tenant limits) so it cannot become an unbounded full-table scan on large tenants.
- Outbox retention must be explicitly defined for `HANDED_OFF`, `CANCELED`, and `DEAD_LETTERED` records. Payload compaction or deletion waits until every child is terminal and the longest downstream replay, rollback-diagnosis, command-status, and audit horizon has elapsed; retained identity, digest, and disposition evidence must still prevent a duplicate logical dispatch.
- The canonical defaults are owned by [Automation & Scripting Service Configuration](./microservices/automation-scripting-service/configuration.md): `SCRIPT_OUTBOX_HANDED_OFF_RETENTION_DAYS`, `SCRIPT_OUTBOX_CANCELED_RETENTION_DAYS`, `SCRIPT_DEAD_LETTER_MAX_AGE_SECONDS`, `SCRIPT_OUTBOX_TERMINAL_CLEANUP_INTERVAL_SECONDS`, `SCRIPT_OUTBOX_QUEUE_REBUILD_INTERVAL_SECONDS`, `SCRIPT_OUTBOX_QUEUE_REBUILD_BATCH_SIZE`, `SCRIPT_OUTBOX_EXECUTION_INTERVAL_SECONDS`, and `SCRIPT_OUTBOX_EXECUTION_BATCH_SIZE`.
- The current Automation & Scripting implementation wires those retention knobs into a scheduled cleanup job for terminal `script_work_items`: `HANDED_OFF` and `CANCELED` rows expire by status-specific retention days, and `DEAD_LETTERED` rows expire by max age plus a row-count cap that removes the oldest excess rows first. The target retention policy also covers terminal dead-lettered records.
- **Target-state only:** The derived queue contract is a projection only: queue drains dedupe repeated parent pointer envelopes by `outboxWorkItemId`, and a bounded rebuild republishes missing queue pointers only from evaluated descriptors in `PENDING` or `INDEXED` status. Rebuild and handoff must apply an explicit status gate before treating a row as evaluated command work. Projection or Redis arrival order is not replay order: the executor selects durable rows by their canonical status and complete identity, and a rebuild must not advance, reorder, or replay a descriptor merely because its pointer was observed first. Pre-DSL `PENDING_EVALUATION` and `EXECUTING` rows are never published to or consumed from the evaluated-command queue; a separate pre-DSL projection may route evaluator work. Redis never becomes authoritative, and reindexing `EXECUTING` rows must not reclaim or replay them. The target descriptor rebuild and lease/fencing recovery contract above remain current implementation gaps.
- Current rebuild behavior is narrower and unsafe, and must not be described as the target descriptor rebuild: `ScriptOutboxQueueRebuildJob` invokes `rebuildPendingWorkItemIndex` on its configured schedule whenever service readiness is `ACCEPTING_TRAFFIC`; that readiness guard is not a queue-state safety or recovery gate. The method unconditionally selects current `script_work_items` rows in both `PENDING_EVALUATION` and `EVALUATING` and republishes missing pointers. It has no stale, owner, or compare-and-set reconciliation gate and cannot distinguish a safe from a stale `EVALUATING` row. The current executor catches queue-pointer discovery failures and falls back to a bounded durable `PENDING_EVALUATION` scan, and supplements a short queue batch with a durable scan when capacity remains; however, the Redis drain deletes an entire list before enforcing its pointer cap, so an over-cap list can lose its unreturned suffix and neither fallback nor rebuild immediately recovers those deleted pointers. Consequently the scheduled projection is a live scheduled unsafe rebuild, not a safe recovery operation; the safe owner-reconciled rebuild and any safe reset/recovery operation are unavailable. The executor fallback has the same unsafe implementation/proof gap, while current queue reset/resume is unavailable and must fail closed; a non-atomic status preflight cannot authorize the safe PENDING-only path. Until the unsafe scheduled rebuild is disabled during accepted traffic or runs under the same owner/serialization gate as enqueue, the service must not claim this readiness state as queue safety. If the queue projection is already known unsafe or requires reset/recovery, operational containment instead requires stopping/scaling the Automation deployment to zero (or making process readiness non-accepting with verified cessation of executor and rebuild invocations), recording the availability impact, and keeping it stopped until owner-reconciled recovery is available and proven. Target pre-DSL recovery permits `PENDING_EVALUATION` plus only owner-reconciled/reclaimed safe non-stale `EVALUATING`; target `PENDING`/`INDEXED` descriptor rebuild is unavailable because the separate evaluated descriptor status layer is not currently persisted. These current pointers are not evaluated-command queue entries and are not evidence of descriptor replay. This implementation and proof gap remains owned by the Automation queue owner.
- Target purge follows the [normative terminal descriptor evidence rule](./system-architecture-scripting-normative-contract-tables.md#terminal-descriptor-evidence-purge-target-state): under an `EVALUATED_COMMITTED` parent it may remove descriptor/outbox/evaluated-output evidence only after every child under that parent is terminal (`HANDED_OFF`, `CANCELED`, or `DEAD_LETTERED`) and every eligible evidence item is retention-eligible. A fully canceled required-child set therefore follows the same retention-gated purge path; purge does not create or transition a dead-letter recovery aggregate or create replay eligibility. The purge transaction atomically removes all eligible evidence and persists an explicit durable `descriptorEvidencePurgedAt` marker on the retained parent. If any sibling is `PENDING`, `INDEXED`, `HANDOFF_IN_FLIGHT`, otherwise nonterminal, or not retention-eligible, the entire parent purge is rejected and no marker is written. A marked parent is non-recoverable and non-replayable, and consumers reject it deterministically rather than treating missing children as recoverable. It preserves the trigger marker, corresponding `script_event_audit`, and replay-causation evidence, and rejects active/nonterminal trigger or descriptor work.
- Operator-facing replay, purge, and convergence tooling must treat those retention windows as the supported diagnosis horizon rather than inventing ad hoc cleanup timing.

## Current State Mapping, Drain, and Rebuild Rules

Target-state rule: stable schedule rows carry the mutable current reconciled `(pluginActivationEpoch, lifecycleRevision)` pair for their current owner; due candidates, firing claims, candidate audits, and timer-derived work retain the immutable captured pair as execution-fence evidence across every mapping below. New evaluator or firing admission requires the exact current `(pluginActivationEpoch, lifecycleRevision)` under `ENABLED`; work may use only the immediately preceding `ENABLED` revision during same-version/same-epoch `DRAINING` when its winning admission CAS durably committed that revision before the durable Automation-owned `DRAINING` admission barrier was created. A non-executable or epoch-advancing transition supplies no predecessor exception. The current implementation does not yet persist and propagate this complete plugin fence across these surfaces; see [Current Implementation Status](#current-implementation-status) and the [Automation and Scheduler Runtime tracker](../project-management/implementation-tracking/automation-and-scheduler-runtime.md#capability-status).

The current `script_work_items` statuses span two target layers. `workItemStatus` on an evaluated descriptor is per descriptor/command; pre-DSL trigger status and any parent aggregate are separate scopes. Tooling must not collapse them into one command-outbox state machine:

Current legacy single-row marker: when the current executor completes a live non-`onLoad` zero-command evaluation on the `completed_no_commands` path, it stores that work item with `status=HANDED_OFF` as a terminal storage marker even though no command dispatch or Game Session handoff occurred. The authoritative outcome remains `finalStage=DSL_EVAL` / `finalOutcome=completed_no_commands`, with no dispatch identity; `HANDED_OFF` in this legacy single-row context is not evidence of a command handoff or `handoff_accepted`. This is implementation drift from the target two-layer status model and must not be treated as the target descriptor meaning below.

| Current or target status | Canonical target meaning | Drain and rebuild treatment |
| --- | --- | --- |
| `PENDING_EVALUATION` | Pre-DSL trigger state pending evaluation; it is not an evaluated command outbox row. | Count as pending pre-DSL work. During asynchronous cancellation/cleanup, compare-and-set it to terminal `CANCELED`, persist `cancelReason`, and record `finalStage=ADMISSION` / `finalOutcome=canceled` with the bounded cancellation reason, without entering the DSL. Do not publish it as an evaluated command pointer. |
| `EXECUTING` (target) | Pre-DSL trigger accepted by the executor after the fenced capacity lease, executor-acceptance transaction, and exactly-once execution-start marker commit; DSL evaluation begins only after that commit. | Count as active. Cancellation/recovery first fences the attempt and reads the durable descriptor-commit marker/status. For cancellation, a committed descriptor is never resumed or re-dispatched: `PENDING`/`INDEXED` children compare-and-set to `CANCELED`, `HANDOFF_IN_FLIGHT` fences retry and reconciles downstream outcome while remaining active/unresolved when ambiguous, and terminal children no-op. A separate recovery path may replay the stored committed child ledger without DSL re-entry. With no committed descriptor, explicit cancellation transitions to terminal `CANCELED` with `finalStage=DSL_EVAL` / `finalOutcome=canceled` and the bounded cancellation reason; this terminal cancellation is never replay-eligible. Only expired stale recovery-owner handling transitions to terminal `DEAD_LETTERED` with `finalStage=DSL_EVAL`, `finalOutcome=canceled`, and `finalReason=stale_execution_fenced`. |

The live projection counts it as active, including unresolved stale rows; current recovery does not infer reclaim, terminalization, or safe resumption from lease age. |
| `EVALUATED_COMMITTED` | Retained trigger descriptor-commit marker whose evaluated descriptors, parent outbox evidence, terminal evaluation outcome, and audit update were committed atomically. Replay its descriptor children without DSL re-entry; any `PENDING`/`INDEXED` children remain pending and any `HANDOFF_IN_FLIGHT` children remain active. If a permanent required-child failure occurs, the separate parent recovery aggregate becomes `DEAD_LETTERED` while this marker and its output/child ledger remain retained for operator recovery. If required children are instead canceled, the aggregate stays non-`DEAD_LETTERED`, cancellation settles through the child ledger and stage-aware handler audit, and the parent is not eligible for `resumed_dispatch`. |
| `PENDING` | Evaluated descriptor/outbox pending handoff. | Count as pending post-DSL work and publish or rebuild its derived pointer. |
| `INDEXED` | Evaluated descriptor whose derived queue pointer has been published. | Count as pending post-DSL work; rebuilding is idempotent and may restore only the missing pointer. |
| `HANDOFF_IN_FLIGHT` | Evaluated descriptor currently being handed to Game Session. | Count as active; rebuild/recovery retries or confirms the committed descriptor by the complete Command-Handoff Identity, never by re-entering the DSL. **Target-state `GetAutomationDrainStatus` mapping:** for the current scope and `admissionEpoch`, `activeExecutionCount` is exactly the sum of `EXECUTING` pre-DSL triggers and `HANDOFF_IN_FLIGHT` evaluated descriptors; an `EVALUATED_COMMITTED` trigger itself contributes zero. `pendingCancelableWorkItemCount` is exactly the sum of `PENDING_EVALUATION` pre-DSL triggers and `PENDING`/`INDEXED` evaluated descriptors, including descriptors committed by an `EVALUATED_COMMITTED` trigger. Terminal states, including required `CANCELED` children and their settled parent audit, another scope or epoch, and derived queue pointers do not contribute. These counts expose asynchronous cleanup progress only; they do not gate Automation resumption or ordinary gameplay ticks, and no cleanup path enters or re-enters the DSL.

`PENDING` and `INDEXED` are target descriptor states; the current implementation does not persist them as separate statuses or persist `EVALUATED_COMMITTED`. **Current projection mapping:** while `PAUSED_FOR_ROLLBACK`, the live projection first restricts its counted set to rows whose `workItem.admissionEpoch <= 0` or `workItem.admissionEpoch < current admissionEpoch`, excluding positive current-epoch rows; within that set it counts `EVALUATING`, including unresolved stale rows, and `HANDOFF_IN_FLIGHT` as active and `PENDING_EVALUATION` as pending. Normal mode counts the corresponding scoped rows without that epoch filter. Until the implementation converges, drain and rebuild projections must report that gap rather than presenting `PENDING_EVALUATION` or `EVALUATING` as evaluated command work; unresolved counts remain diagnostic cleanup backlog and do not gate ordinary ticks or target Automation resumption.

### Operator Replay of DEAD_LETTERED Work

Replay preserves and revalidates the captured plugin lifecycle tuple at the stage boundary: `ENABLED` requires the exact current `lifecycleRevision`, while same-version/same-epoch `DRAINING` may resume only work whose winning admission CAS durably committed the immediately preceding `ENABLED` revision before the durable Automation-owned `DRAINING` admission barrier was created. It never refreshes a dead letter to an arbitrary lower revision, and a displaced item remains dead-lettered after a non-executable or epoch-advancing transition.

Recovery selection, eligibility, stage mapping, idempotency, and the atomic recovery claim/attempt owner are defined by [Control Plane Operations](./system-architecture-scripting-control-plane-operations.md#replaydeadletteredworkitems); that owner persists and revalidates the expected exact fence/binding and `controlPlaneRequestId`, including same-attempt claim reclaim. This runtime section records only local consequences: command-capable gameplay/runtime evaluation-stage recovery may invoke the DSL evaluator again only when the persisted failure class is retryable under [Failure Modes and Error Handling](#failure-modes-and-error-handling), using the original work-item and `scriptEventId`, original persisted payload, frozen manifest/graph evidence, exact admitted immutable graph and artifact references, and recorded digests, while remaining outside the normal admission path. Before its winning descriptor commit it allocates no dispatch or command-child identity; if commands are emitted, that first atomic evaluated-descriptor/outbox commit allocates and persists the `automationDispatchId` and ordinals, while retries after a winning commit reuse them. A valid zero-command evaluation creates no dispatch identity. Non-retryable classes remain terminal/ineligible, and recovery must never refresh to the latest/default payload, manifest, graph, or artifact. Post-evaluation recovery reads the immutable evaluated output and complete child-dispatch ledger keyed by the full Command-Handoff Identity, preserving original child identities, ordinals, downstream acknowledgements/outcomes, and per-child recovery state, and never invokes the DSL. A parent recovery aggregate marked `DEAD_LETTERED` because of a permanent required-child failure resumes this retained ledger as `resumed_dispatch`; a required-child cancellation does not mark that aggregate `DEAD_LETTERED`, so the canceled parent/children are not replay-eligible. Recovery never replaces or clears the `EVALUATED_COMMITTED` descriptor marker. Successful recovery clears only the separate parent recovery aggregate; purge may remove eligible descriptor evidence and writes `descriptorEvidencePurgedAt`, but retains the marker. `DRAINING` remains valid for recovery only when the work has ADR 0119's durable pre-`DRAINING` admission/fence evidence and exact plugin fences and policy evidence pass; a lifecycle state that invalidates admitted work fails closed. Evaluated-output and command digests are integrity evidence only, not substitutes for retained output or identity; `outboxWorkItemId`, the parent Trigger Identity, and `scriptEventId` remain correlation-only. Neither stage reopens the original audit row.

**Target-state only:** The control-plane recovery mutation accepts bounded explicit `workItemIds[]` only; descriptor references and filter selectors remain deferred until preview plus stable per-row proof. A `DEAD_LETTERED` evaluation-stage trigger with no committed descriptor may retry only when its persisted failure class is retryable under [Failure Modes and Error Handling](#failure-modes-and-error-handling), and its original work-item, `scriptEventId`, frozen manifest/graph evidence, and exact admitted immutable graph are present; a missing or contradictory stage record remains ineligible, and non-retryable classes remain terminal/ineligible. A parent recovery aggregate marked `DEAD_LETTERED` after a permanent required-child failure retains its `EVALUATED_COMMITTED` marker and may resume only the stored output/child ledger. The current mutation selects parent `workItemIds` and requeues eligible `script_work_items` rows, so it does not yet prove independent descriptor recovery. Command-capable gameplay/runtime evaluation-stage recovery may invoke the DSL evaluator again only for that retryable failure class, under the original identity and evidence, remains outside the normal admission path, allocates no dispatch or command-child identity before a winning descriptor commit, and must converge on the original work item. If commands are emitted, that first atomic descriptor commit allocates and persists the `automationDispatchId` and canonical ordinals; retries after a winning commit reuse them. A valid zero-command evaluation creates no dispatch identity. Post-evaluation recovery must resume only the stored output/child ledger and never invoke the DSL. Recovery must never move a dead-lettered item into a fresh admission path, regenerate output after the evaluation boundary, or append new history to the original audit row. Before recovery, the service must revalidate the current exact `(scriptPatchVersion, scriptPinEpoch)` tuple, runtime `regionId`/`regionEpoch`, and admitted routing bundle (`playableStateScope`, world/realm identity, and pointer version); for plugin work, it must also revalidate the immutable `(pluginId, pluginVersionId, bindingId)` tuple, the captured `(pluginActivationEpoch, lifecycleRevision)` pair against the current Automation-owned lifecycle evidence, and fresh applicable activation/lifecycle, publication, component-policy, capability-grant, and signer evidence against the same scoped `<tenantId, gameInstanceId, pluginId>`. `DRAINING` blocks new trigger admission; recovery requires ADR 0119's canonical durable pre-`DRAINING` admission-CAS/fence evidence and otherwise only remains eligible for a lifecycle state that does not invalidate admitted work. A captured-epoch mismatch returns `plugin_activation_epoch_mismatch`. A `DISABLED`, revoked, or policy-driven invalidation of admitted work returns `plugin_disabled`. If any authoritative fence or plugin-policy read is temporarily unavailable, return the applicable established bounded reason (`authority_unavailable`, `component_policy_unavailable`, or `signer_policy_unavailable`), leave the already-`DEAD_LETTERED` item unchanged with no recovery claim/attempt record, and persist the request-level rejected result so an exact retry of the same request replays it; only a later request with a new `controlPlaneRequestId` may retry after the evidence recovers. A proven fence, binding, publication, policy, or revocation mismatch remains terminal/ineligible, leaves the item `DEAD_LETTERED`, and produces no recovery claim/attempt record.

Target-state recovery is idempotent by stable `controlPlaneRequestId` for each original work item and Automation-owned `failureGeneration`. The first atomic parent recovery-aggregate transition into `DEAD_LETTERED` initializes generation `1`; a later re-entry advances it exactly once in that same transition, including a permanent required-child failure after the retained `EVALUATED_COMMITTED` marker, while an exact retry/no-op or failed recovery attempt that leaves the parent in the same generation does not advance it. Retrying the same operator request returns its stored per-work-item result and generation unchanged and creates no second recovery attempt or audit history. A new request resolves the current generation atomically: only same-generation successful-recovery evidence returns `outcome=already_recovered`; an older generation's success remains immutable and neither satisfies nor blocks recovery of a newer current generation. Claims are unique per current `(tenantId, outboxWorkItemId, failureGeneration)`, stale owners/generations fail CAS, and failure generation is not reused as a Trigger Identity or Command-Handoff Identity. Missing or contradictory stage evidence remains dead-lettered.

## Script Patch Lifecycle

The canonical patch lifecycle and readiness states remain owned by [Scripting DSL Reference & Event Lifecycle](./system-architecture-scripting-dsl-reference-and-lifecycle.md#script-patch-lifecycle). Runtime execution consumes that lifecycle by enforcing the [canonical version-fence contract](./system-architecture-scripting-contracts.md#3-version-fencing-rollback-safety) at its local admission boundary for instance-bound gameplay/runtime triggers. Tenant-readiness `onLoad` is explicitly excluded from these instance-pin checks because it uses its pre-instance readiness identity without `gameInstanceId` or `scriptPinEpoch`:

Exact-epoch admission in the following bullets is **target-state only**; the current live handoff carries the patch version but does not enforce same-version epoch rejection.

- For an instance-bound gameplay/runtime trigger, Runtime compares the supplied exact `(scriptPatchVersion, scriptPinEpoch)` to Automation's bounded-fresh observation of the authoritative Game Session tuple for `<tenantId, gameInstanceId>`. When that projection is absent or stale, Automation must perform a bounded owner refresh before admission; neither path permits a patch-only or version-only fallback.
- If the projection is absent or stale and authoritative refresh is unavailable beyond the configured freshness boundary, admission fails closed; no local, stale, or operator pin override is permitted.
- If either supplied field differs from the bounded-fresh observed tuple, admission is rejected at the exact execution fence.
- Tenant `READY` remains required for a new pin or pin progression. A newer publish supersedes only an unpinned candidate in `PENDING_VALIDATION` or `ONLOAD_RUNNING`. An already-pinned `READY` patch is not relabeled `SUPERSEDED` merely because a newer publish arrives; it remains admissible only under its exact current Game Session tuple until an explicit Game Session repin or rollback. An unknown or non-ready patch is rejected at admission.

## Runtime Execution Flow

Scripts do not execute inside the tick system. The Automation & Scripting Service evaluates scripts independently, on a schedule, via timers, or in response to events, and enqueues the resulting commands into each entity's command queue.

- These queued commands run during the next tick cycle via the normal Game Session and Game Logic flow.
- Script evaluation never blocks or interferes with tick execution.
- Script-generated commands may fail due to lock contention or target remote regions, and Game Session handles those cases via its normal tick rescheduling and cross-region routing logic.
- The Automation & Scripting Service only determines which commands to inject. It never mutates entity or world data directly.

For a non-exclusive multi-handler event, Automation assigns the resolved handlers a durable `handlerSequence` under [ADR 0118](./decisions/adr-0118-preselected-exclusive-handlers-and-durable-fanout-ordering.md). The event resolution record or equivalent durable manifest identifies the complete ordered set. That sequence and each handler's local command ordinal are preserved on work items, generated-command persistence, handoff records, Game Session command admission, retries, and final application. Consumers must not infer semantic order from enqueue time, database identity, Redis list position, worker claim order, scheduling priority, or arrival time.

This is target-state behavior. The current live Game Session handoff does not yet carry or prove the durable handler sequence and complete resolution evidence through handoff, Game Session admission, retry, and final application; it also lacks `commandOrdinal` and the complete Trigger/Command-Handoff Identity. Existing local ordinals and parent correlation are only current handoff bookkeeping and diagnostics, not semantic ordering authority or a fallback when target metadata is missing.

A handler's terminal failure or empty output closes its sequence position and allows later non-exclusive handler commands to proceed without canceling them. A delayed lower sequence is not equivalent to a terminal failure; downstream application must retain or reconstruct enough resolution state to avoid applying a higher sequence prematurely. Missing or contradictory sequence/completeness metadata fails explicitly rather than degrading to arrival order.

Automation first resolves and seals the complete applicable core/plugin binding set, rejecting missing or contradictory completeness evidence, multiple exclusive claims, or unauthorized exclusive claims. It then selects an authorized exclusive binding before work-item fan-out; that binding is the only handler materialized for the event scope. If it fails or is denied, no sibling fallback is created.

## Output Budgeting and Command Fan-Out

Admission and sandboxing must bound not only how often a handler runs, but also how much work a single admitted run can emit:

- Each DSL run must enforce explicit output budgets before a work item is persisted, including `maxCommandsPerRun`, `maxCommandsPerEntityPerTrigger`, and `maxSerializedWorkItemBytes`, plus any bounded payload ceilings needed for known large command families.
- Exceeding an output budget must fail deterministically with a non-success stage-aware outcome. A generated-output meter or cap violation discovered while evaluating a resolved handler is a handler-scoped `DSL_EVAL` outcome; an independent serialization or durable persistence transaction failure is a `WORK_ITEM_PERSIST` outcome. In either case, `finalReason` must use bounded canonical codes such as `command_count_exceeded`, `per_entity_command_limit_exceeded`, or `work_item_size_exceeded`.
- A non-exclusive handler failure closes only that handler's durable sequence position. It does not cancel sibling work or change their Trigger Identities and outcomes.
- Output budgets apply equally to core scripts and plugins.
- Publish-time validation in Game Design must perform conservative worst-case fan-out analysis for bounded loops and bulk action nodes using the same component cost metadata that Automation & Scripting uses for runtime revalidation.

### Static Output Cost Contract

Every compiled script artifact must carry enough normalized output-cost metadata for Game Design and Automation & Scripting to reach the same accept/reject decision before runtime. The metadata is a versioned, digested contract, not an implementation-local estimate:

- The shared component-cost registry publishes a `costMetadataSchemaVersion` and `componentCostRegistryDigest`. Each action/component definition must declare `maxCommandsEmitted`, optional per-entity command distribution rules, `maxSerializedBytesPerCommand`, an estimated millisecond cost, data-dependent input bounds, and whether its output cost is `STATIC`, `BOUNDED_BY_INPUT`, or `UNSUPPORTED_FOR_STATIC_BOUND`.
- `STATIC` components contribute a fixed cost. `BOUNDED_BY_INPUT` components must name the validated input bound that caps their fan-out, such as a maximum selected-entity count, bounded loop counter, or configured list length. `UNSUPPORTED_FOR_STATIC_BOUND` components are not eligible for publish in live scripts until they are redesigned or given a bounded contract.
- Branches are analyzed conservatively by taking the maximum cost of mutually exclusive branches and the sum of costs for paths that can both execute in one run.
- Bounded loops multiply the loop body cost by the validated finite iteration bound. Loops without a finite bound are rejected by loop-safety validation before output-cost analysis.
- Timer edges that create future triggers do not add same-run command cost beyond the timer-registration command itself, if any; the future trigger is analyzed as its own run.
- Bulk action nodes must expose an explicit validated maximum fan-out. Runtime-discovered collection sizes without a publish-time upper bound are treated as `UNSUPPORTED_FOR_STATIC_BOUND`.
- Game Design writes the normalized cost summary, the `costMetadataSchemaVersion`, `componentCostRegistryDigest`, and `artifactRuntimeCapDigest` into the immutable compiled artifact. Automation & Scripting recomputes and validates both exact embedded payload/digest pairs against the shared registry/cap contract and rejects ingress or readiness when metadata is missing, stale, contradictory, or exceeds the artifact-pinned runtime ceilings. It must not silently substitute newer registry metadata for an already-pinned artifact; the exact RFC 8785/UTF-8/SHA-256 subordinate digest contract is owned by [ADR 0088](./decisions/adr-0088-static-and-incremental-script-output-bounds.md).
- The immutable artifact also pins the estimated millisecond cost and scheduler ceiling used for target-state automation admission. Each live handler estimate must be a positive finite schema-bounded integer no greater than that ceiling; an artifact or handler that cannot fit one empty tick window is rejected before `READY`/pinning rather than deferred indefinitely. Runtime revalidates the pinned estimate/ceiling relation, and checked arithmetic makes overflow fail closed while forming cumulative ordered-prefix estimates. Actual runtime is calibration telemetry only and does not create a same-tick refund; a later operator/configuration ceiling reduction must be preflighted or rejected for incompatible `READY`/pinned artifacts until republish or reconfiguration.
- Runtime output budgeting remains mandatory even when static validation passes; the static contract prevents obviously oversized graphs from publishing, while runtime guards protect against registry bugs, corrupted artifacts, or future component changes.

### Incremental Runtime Metering and Atomic Persistence

Runtime metering is incremental and happens before constructing each generated command or data-dependent collection. The evaluator charges the artifact-pinned conservative prospective serialized-byte bound together with cumulative command count, per-entity count, payload/collection bounds, and every data-dependent cap declared by the pinned metadata before construction or allocation. After bounded descriptors are staged, their exact serialized size is checked against the pinned ceiling immediately before atomic persistence. A run that would exceed any cap stops with the stage-correct `DSL_EVAL` non-success outcome and bounded reason; an independent serializer or persistence transaction failure remains `WORK_ITEM_PERSIST`. It must not construct an unbounded intermediate result and discover a cap violation only at handoff.

Generated output is atomic per resolved handler: either every bounded descriptor for that handler is durably persisted with its parent evidence, or none of that handler's generated output is persisted or handed off. A failed output-meter check, serialization check, or persistence transaction discards all staged output for that handler; it must not leave a partial command set that a retry could interpret as successful work. Event-scope ingress may reject a missing or conflicting artifact-cost digest with its ingress `OUTPUT_BUDGET_EXCEEDED` outcome, while a handler that exceeds a runtime cap records the canonical handler-scoped `DSL_EVAL` outcome and reason from [Table 2](./system-architecture-scripting-normative-contract-tables.md#table-2-script_event_audit-stages-and-outcomes).

## Budget Charge Points

The canonical charge lifecycle is owned by [Scripting Quotas & Operations](./system-architecture-scripting-quotas-and-operations.md#budget-accounting-rules). Runtime execution consumes its result and must not introduce another charge point:

- The durable handler charge record is keyed by the full applicable Trigger Identity, including each resolved `onLoad` handler. Its exactly-once admission and execution-start markers are reused by duplicate and recovery attempts.
- A queued handler holds no sandbox capacity. Runtime acquires a separately fenced, reclaimable capacity lease only when execution is about to start, then in one Automation-owned durable executor-acceptance transaction revalidates the current fence, durably accepts/claims the run for the executor, persists the exactly-once execution-start marker, and transitions the work item to `EXECUTING`; DSL evaluation begins only after that commit. If the executor cannot accept the run, the transition does not commit, the lease is released or reclaimed, and no execution charge is recorded. A crash after commit recovers from the durable executor claim and may reacquire a lease but never creates a second marker.
- A failed run does not refund an already committed admission charge or execution-start charge. Lease reclamation is capacity recovery, not a quota refund, and cannot create a second charge record or execution-start marker.
- Runtime persists the resolved `quotaClass` on durable work so execution follows the admission decision. `PUBLISH_READINESS` remains isolated from ordinary live quota and capacity; its readiness lease and outcome are local runtime consequences, not a new live charge path.
- Target-state scheduler reservations are separate from the durable admission/execution charges and fenced occupancy lease described here; the current runtime does not implement that reservation.

## Ordering Between Player and Script Commands

Game Session owns the combined per-entity tick queue and its enqueue/order invariants as defined in the [cross-service scripting contracts](./system-architecture-scripting-contracts.md#1-tick-queue-ownership-tick). At this runtime boundary, the current handoff preserves `scriptId` and optional `dueTickId` when present. `commandOrdinal`, `triggerMode`, `scheduleDefinitionId`, and scheduler/ordinal propagation are target-only and are not current ordering guarantees. `scriptEventId` remains on the Automation-owned durable work item and `script_event_audit`; it is omitted from the current Game Session handoff. Target command identity and complete Trigger Identity propagation remain subject to the widened handoff contract.

## Failure Modes and Error Handling

At every plugin evaluation, persistence, handoff, staged/final-effect, retry, replay, and recovery boundary, the captured plugin version and `pluginActivationEpoch` must first match the authoritative current activation exactly; only then is the captured `lifecycleRevision` evaluated by state. `ENABLED` requires exact current revision; `DRAINING` admits no new work and grants only the bounded immediately preceding `ENABLED` exception when the work's winning admission/fence CAS durably committed that revision before the Automation-owned durable `DRAINING` admission barrier was created, under the same plugin version and activation epoch. Missing, stale, capture-only, contradictory, arbitrary-lower, non-executable, or epoch-advanced lifecycle evidence fails closed.

The canonical stage and outcome taxonomy is defined in the [normative audit table](./system-architecture-scripting-normative-contract-tables.md#table-2-script_event_audit-stages-and-outcomes). Runtime-specific failure behavior includes quota, sandbox, validation, version, signer-policy, and infrastructure failures; the executor does not re-enter the DSL for a persisted trigger when retrying an idempotent downstream operation.

Routine core-script component safety classification is fixed at validation and readiness time: `UNSAFE` is migration-required/new-use-blocked classification only, not a live runtime policy reevaluated on already-`READY` patches. This routine classification does not supersede an explicit emergency revocation under [ADR 0116](./decisions/adr-0116-routine-component-migration-and-explicit-emergency-revocation.md), whose live component-revocation fence remains applicable at final execution.

`handoff_accepted` is valid only after every required child dispatch is durably accepted by Game Session; it is not gameplay success. A valid live evaluation that intentionally emits no commands uses `completed_no_commands` at `DSL_EVAL`. The owner table defines the stage-aware audit fields and allowed outcomes, while later gameplay truth remains per dispatch.

Target-state retry behavior (see [Current Implementation Status](#current-implementation-status)):

- Logical failures are treated as final for a trigger. Before `EVALUATED_COMMITTED`, infrastructure retry, including admitted timer evaluation, may re-run evaluation only under the same full Trigger Identity and must converge on the same work-item and frozen inputs; it allocates no dispatch or command-child identity before the first durable descriptor commit. If commands are emitted, that winning commit allocates/persists the dispatch ID and canonical ordinals; retries after the commit reuse them. It must never create a duplicate logical command. After `EVALUATED_COMMITTED`, recovery replays the durable descriptors and never re-enters the DSL. The audit `finalStage` remains the last stage actually reached rather than being advanced by an attempted retry.
- **Pre-commit replay evidence:** For event and timer evaluation retries before `EVALUATED_COMMITTED`, the executor reloads the original durable trigger payload, frozen dependency/manifest snapshot, immutable graph and artifact references with recorded digests. For plugin-backed work it also compares the exact plugin provenance and captured `(pluginActivationEpoch, lifecycleRevision)` pair; for the same-version/same-epoch `DRAINING` predecessor exception, the durable winning pre-`DRAINING` admission/fence CAS evidence is part of the immutable comparison and must be present. Missing, changed, capture-only, or unreadable evidence fails closed before DSL evaluation; the retry preserves the full Trigger Identity and original work-item identity, allocates no command-child identity, and can only reuse dispatch/ordinal identities after a winning descriptor commit with the same lifecycle evidence.
- Any work referencing a revocable component, including embedded/core-script and plugin-backed work, carries the component-revocation security-policy fence through evaluation, persistence, dispatch, staged/final effects, retry, replay, and recovery and is checked immediately before gameplay effects. Missing, stale, unavailable, or mismatched evidence fails closed with the established bounded component/authority disposition. Plugin-backed work additionally carries and revalidates the independent `(pluginActivationEpoch, lifecycleRevision)` fence pair; neither lifecycle fence substitutes for the other or for component-revocation evidence. The captured plugin lifecycle pair and exact recovery fences are revalidated immediately before evaluation, before descriptor/outbox persistence, before each post-evaluation dispatch, and at every applicable boundary. Applicable current signer, component, capability, publication, and lifecycle policy evidence is revalidated at evaluation, each dispatch, final effect, and activation/resume/recovery as owned by ADR 0119, using the canonical durable pre-`DRAINING` admission-CAS evidence for the narrowly retained predecessor exception. Proven lifecycle, publication, component/capability, signer, tuple, or scope mismatches remain terminal/ineligible with their applicable bounded reason.
- For event ingress, pre-handler rollback pause is an ingress-audit backpressure outcome only. Timer candidates use the Table 3 candidate-audit rule instead. Post-resolution handler backpressure such as `skipped_reloading` and `rollback_paused` is not treated as final for low-rate external events.
- Infrastructure errors may be retried by lower layers following platform-wide retry policies and idempotency contracts.

When script components call other services over gRPC, target-state handoff calls must carry the complete Command-Handoff Identity for child-dispatch deduplication, fence reporting, replay selection, and correlation, and bind the stable root `EffectId` in the canonical transaction context to the typed operation, exact target aggregate, required participant context, sealed manifest, and immutable request digest before participant verification. The downstream owner stores and compares that binding under the effect guard and fails closed on a conflicting operation, target, participant context, sealed manifest, or digest, so downstream operations can retry without duplicating effects. The `(automationDispatchId, commandOrdinal)` pair alone is insufficient; current live calls remain subject to the narrower fallback described above.

## Version Fencing and Rollback Safety

Rollback of a script patch must not allow previously queued work from the displaced tuple to continue affecting gameplay. The version-and-epoch fence, rejection disposition, and diagnostic identity are owned by the [cross-service scripting contracts](./system-architecture-scripting-contracts.md#3-version-fencing-rollback-safety). Locally, script work items retain the effective `scriptPatchVersion` and `scriptPinEpoch`; current live handoff limitations and rejection/status diagnostic fallback are recorded in [Current Implementation Status](#current-implementation-status). A version or epoch/runtime-scope mismatch is not applied; temporary plugin-authority or binding-read unavailability returns bounded `authority_unavailable` and leaves the durable effect retryable under its original identity, while a proven tuple/binding mismatch or revocation remains terminal/ineligible. Cancellation/purge of queued work is bounded asynchronous cleanup rather than the correctness barrier. Ordinary gameplay continues through routine rollback.

## Timer Failure Semantics

Timer admission, due-point identity, catch-up, reload, and failure outcomes follow the [normative timer semantics](./system-architecture-scripting-normative-contract-tables.md#table-3-timer-semantics-matrix). In the target state, before `EVALUATED_COMMITTED`, an admitted timer evaluation may retry only under the same full Trigger Identity, allocates no dispatch or command-child identity before the first durable descriptor commit, and must converge on the same work-item and frozen inputs. If commands are emitted, that atomic commit allocates/persists the `automationDispatchId` and canonical ordinals; retries after the commit reuse them. After that commit boundary, recovery replays durable descriptors and never re-enters the DSL; independently idempotent downstream operations may still retry. Recurring/advisory firings remain bounded scheduling signals rather than guaranteed cadence ledgers, while correctness-bearing one-shot timers converge to one execution or an explicit terminal outcome.

## `onLoad` Semantics and Failure Handling

The `onLoad` lifecycle event is a tenant-readiness check for scripts in a given `<tenantId, scriptPatchVersion>` before that patch becomes eligible for an instance-scoped exact pin. Its lifecycle and identity are defined by the [DSL lifecycle](./system-architecture-scripting-dsl-reference-and-lifecycle.md#onload-semantics) and [normative readiness contract](./system-architecture-scripting-normative-contract-tables.md#table-1-trigger-identity-required-fields):

- `onLoad` handlers run after static validation and compilation succeed, but before the patch is marked `READY` for a tenant.
- Allowed uses are limited to configuration/runtime metadata validation and ephemeral or trivially recomputable in-process initialization.
- `onLoad` handlers may not emit gameplay commands, tick commands, or durable shared effects, and may not create durable or semi-durable artifacts in databases, Redis, object storage, or other shared stores. Platform-owned execution, readiness, fencing/recovery, and `script_event_audit` metadata remain allowed and are not handler-created artifacts.
- There is no compensating `onUnload` / `onDeactivate` lifecycle in the current architecture.
- If future requirements demand durable patch-managed shared state, the platform must add a symmetric deactivation/cleanup lifecycle first.

Failure handling:

- `onLoad` admission uses a dedicated publish-time initialization budget, not the normal live-trigger quota windows enforced by `ScriptQuotaService`.
- If every required per-script `onLoad` execution completes successfully for a tenant, the Automation & Scripting Service may attempt the readiness transition for that tenant.
- If `onLoad` fails with a logical or sandbox-level error, the patch is marked `FAILED` for that tenant and events that reference the failed patch are rejected at admission with `version_unavailable` or a more specific bounded variant such as `onload_failed`.
- If the dedicated `onLoad` initialization budget is exhausted before completion, the patch must fail deterministically with an explicit bounded reason.
- If `onLoad` encounters `infrastructure_error`, the service must not re-enter the DSL for that readiness identity. Only an external infrastructure operation that is independently idempotent may be retried; if the required step cannot be retried safely, readiness fails rather than executing the DSL again.
- **Target state only:** A stale `ONLOAD_RUNNING` execution is fenced by its readiness publication/generation and compare-and-set transitioned by Automation's recovery owner to a terminal audited `finalStage=DSL_EVAL`, `finalOutcome=canceled`, and `finalReason=stale_execution_fenced`. It blocks `READY`; the same canonical readiness identity is never re-entered. Readiness/publication generations are fences, not execution identity. After the stale fencing and terminal audit are durable, retry requires republishing as a new immutable `scriptPatchVersion`; a new execution identity must not be minted for the stale patch.

All `onLoad` runs are recorded in `script_event_audit` with `eventType=onLoad` and the target `scriptPatchVersion`; stage/outcome fields follow the [normative audit table](./system-architecture-scripting-normative-contract-tables.md#table-2-script_event_audit-stages-and-outcomes). **Target state only:** Patch-level readiness for `<tenantId, scriptPatchVersion>` is derived from the aggregate of all required per-script runs and becomes `READY` only after every required readiness execution succeeds and no fenced stale run remains unresolved. The recovery transition from `ONLOAD_RUNNING` to `READY` must be one atomic conditional durable update whose write predicate revalidates the complete required `onLoad` aggregate for the current readiness identity, the expected readiness generation, and the current publication/readiness row still being current, `ONLOAD_RUNNING`, and not `SUPERSEDED`; a concurrent supersession or stale-run terminalization must win and a partial or stale aggregate must not produce `READY`.

## Current Queue-Rebuild Concurrency Gap

The current `rebuildPendingWorkItemIndex` implementation checks Redis for an existing pointer and then appends when absent in separate operations. Concurrent rebuilds, or a rebuild racing normal enqueue, can therefore publish duplicate pointers. Drain-time deduplication limits duplicate processing in one batch but does not make the projection idempotent or bound queue growth. Until atomic uniqueness or serialized owner coordination is implemented and proved, the scheduled `ScriptOutboxQueueRebuildJob` must be disabled while normal automation traffic is accepted, or must run only under the same owner/serialization gate as enqueue; readiness alone is not that gate. If duplicate pointers are observed, keep rebuild/reset/resume fail-closed, continue bounded drain-time deduplication by `outboxWorkItemId`, and use an owner-controlled, bounded cleanup/rebuild of only the affected queue projection while preserving PostgreSQL outbox rows as authority. The target atomic uniqueness and concurrency proof remain unavailable.
