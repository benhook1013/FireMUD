# Account Service API Contracts

This document defines the Account Service REST and gRPC contracts, authentication classes, subject-binding rules, and runtime membership and entitlement response semantics.

The authoritative REST schema source lives in [../../../../services/account-service/src/main/resources/openapi.yaml](../../../../services/account-service/src/main/resources/openapi.yaml). Proto definitions are the authoritative gRPC source.

## Private Current Public-JWKS Read

The default-off `AccountPublicJwksReadService.GetCurrentPublicJwks` is a private read for the exact same-namespace Game Session mTLS workload. Its closed request and response use `schema_version=2`; the request still accepts no key, issuer, path, URI, or rotation selector. Response fields 1–3 retain the existing exact nine-field Account source identity and bounded public-snapshot semantics. Closed field 4 is the disposition: `UNSPECIFIED` is invalid, and the only valid values are `SNAPSHOT` and `PREPARED_DENY`. A `SNAPSHOT` carries the exact Account public snapshot, at most 256 KiB, and requires optional bool field 5, `committed_recovery_eligible`, to be present. `PREPARED_DENY` carries the canonical exact nine-field identity with zero JWKS bytes and omits field 5. The complete frame remains bounded to 256 KiB plus 2 KiB; unknown fields and other schema versions are refused. The nine-field identity and source provenance are defined by the [JWT verification provenance contract](../../system-architecture-jwt-and-token-contracts.md#signing-key-rotation-contract-normative), not by a raw JWKS controller or a finite readiness-plan read.

Account returns `PREPARED_DENY` only for one coherent current durable `PREPARED` promotion linked to the exact operation and trusted owner identity, with the live ConfigMap UID, both complete Account-owned JWKS/marker values, public-data digest, and applicable prior receipt and mounted-proof evidence matching across stable owner reads. A live `ACTIVE` marker with a completed `ActiveJwksPromotionReceipt` must match its exact operation, UID, resulting `resourceVersion` and data-marker digest. During that same writer's proven CAS-before-receipt window, a missing ACTIVE receipt may instead support denial only: the exact prior prepublication receipt and mount, dispatched private promotion and full canonical `PrivatePromotionReceipt.fromStored` preimage/linkage/digest must validate, both live owned values must equal this operation's complete intended ACTIVE projection, and the valid opaque observed `resourceVersion` must differ from the exact prior version. A digest-shaped string alone is insufficient; versions are never numerically ordered. Partial, corrupt or mismatched receipt evidence remains terminal. This exception produces zero JWKS bytes and no recovery eligibility, creates no receipt, and grants no publication, promotion, pruning, readiness or admission authority. Serving keys after PREPARED denial and clearing that latch still require the exact completed current ACTIVE receipt, durable COMMITTED owner and protected coherent same-pin mounted bytes. `committed_recovery_eligible` may be true only when the returned projection itself meets that committed receipt-backed boundary. An older committed ACTIVE cannot qualify a newer PREPUBLISHED projection; ordinary receipt-backed PREPUBLISHED bootstrap returns a noneligible snapshot.

Before PREPARED, a missing prepublication receipt has a separate temporary classification only when the exact current generation and immutable intent plus trusted enrollment or the exact prior committed receipt prove the predecessor. The live UID and complete owned values must prove either that exact prior projection or this operation's exact additive PREPUBLISHED projection, with its closed marker bound to the pending generation, operation, request/receipt digests, trust/API identity and both expected active identities. The supported initial predecessor has canonical empty JWKS and no marker; its full snapshot commitment must match enrollment and intent, including reconstructed unchanged unowned data after CAS. Unknown or unprovable predecessor shapes remain terminal. Additive qualification retains the exact prior keys and adds only the current target. A qualified window returns ordinary unavailable with no snapshot, new keys, repin or cache-age renewal; already cached prior keys remain usable only to their original expiry. It does not install a PREPARED-until-COMMITTED latch before pending-key readiness. The exact publication receipt and mounted correspondence remain prerequisites for normal readiness progression.

The owner reads through `AccountJwtJwksTrustedSource`, retaining its protected binding, coherent owner projection, and exact live ConfigMap checks. The peer and protected Account binding are checked before and after the read. A public read begins with a locked enrollment row and retains one immutable protected materializer/API/source-UID/pin anchor. Proven owner movement permits at most three complete internal qualification trials under the same incoming deadline and cancellation, without sleeps or a reset. Before retrying, the intervening live bytes must qualify against a complete coherent bracket at that original anchor, including exact UID and complete owned bytes with resource-version-only drift; this justifies only another full bounded trial, never a response from moving brackets. Genuine UID, trust, owned-byte or marker tamper is terminal and is not retried. Only a fully stable trial may return evidence or install the initial pin. Repeated unresolved movement remains terminal and never becomes an ordinary outage or key-serving fallback. Once a call observes owner movement, later API/SQL unavailability, missing resources, cancellation or deadline exhaustion is terminal too; an ordinary first-trial outage retains its existing unavailable behavior. A later fully coherent trial that proves the existing prepublication temporary window or exact-UID and exact-owned-byte resource-version-only drift resolves movement into the existing unavailable classification, after checking the original cancellation/deadline budget. It returns no snapshot, installs no pin and renews no cache age; dependency failure is not that qualification. Established-pin reads do not hold the first-install monitor across remote work; first installation remains synchronized and cannot replace a pin. The ordinary issuance adapter retains its existing retry behavior. A valid `PREPARED_DENY` is a method-response disposition, distinct from transport failure. Missing or wrong workload authority returns `PERMISSION_DENIED`, malformed request frames return `INVALID_ARGUMENT`, temporary source unavailability or an unclassified handler fault returns `UNAVAILABLE`, and typed custody/publication rejection (including failure to encode Account's produced snapshot) returns `FAILED_PRECONDITION`. The private trusted-source rejection category remains terminal; a generic handler exception is not custody evidence. A coherent owner projection with the exact ConfigMap UID and Account-owned JWKS/marker bytes but a different `resourceVersion` remains unavailable: no unreceipted snapshot is returned and the immutable receipt is not rewritten. Recovery requires a later exact owner-receipted publication. This preserves ordinary resource-version-only, transport, and issuance behavior; unproved pruning and ambiguous, unqualified unreceipted, tampered, or unsupported lifecycle evidence remain terminal. Consumers do not infer retryability from generic transport status codes without exact authenticated peer and server-origin proof. No private keys or credentials are returned, and no signing, registry, readiness, promotion, or admission authority is granted. Composition and the exact bearer-exempt method classification are recorded in [configuration](./configuration.md#private-current-public-jwks-read); Game Session's cache and deny-latch consequences are defined in its [JWKS consumer contract](../game-session-service/api-contracts.md#steady-state-account-public-jwks-provenance), while focused proof and deployed prerequisites belong to [Player Access and Session](../../../project-management/implementation-tracking/player-access-and-session.md#account-and-game-session-steady-state-jwks-deny-gate).

Public pruning is not implemented by this receiving boundary: it supplies no authorized Account public-pruning producer, pruning receipt, or current-read pruning projection. Same-UID removal of an owned public key without matching owner evidence remains terminal; restored bytes cannot clear an already terminal consumer. The [writer-window inventory and proof](../../../project-management/implementation-tracking/player-access-and-session.md#actual-public-jwks-writer-windows-and-pruning-limit) record supported writer-window qualification and retained limitations. No receipt-less snapshot, pruning fallback, or runtime activation is defined here.

## Normative Target Contract

Account is the API boundary for platform identity, durable membership, entitlement authority, and Account-owned authentication mutations. This document retains endpoint and transport consequences; gameplay admission and JOIN identity binding are defined by [Authentication](../../system-architecture-authentication.md), while token refresh, replacement, generation, revocation, fencing, and logout are defined by [JWT and Token Contracts](../../system-architecture-jwt-and-token-contracts.md).

### Account-Owned Hosted Terms and Creator Party

Account is the sole target authority for the identified hosted Creator Party, operator/legal-party and terms-version catalog, and acceptance/currentness evidence under [ADR 0180](../../decisions/adr-0180-account-owned-hosted-terms-acceptance-gate.md). Acceptance is an explicit party-level decision for an identified operator and hosted-terms scope; tenant roles, billing ownership, payment, caller-supplied fields, or a copied Game Design flag do not establish party, signer, or acceptance authority. Organization and other unsupported party/signer paths remain disabled until their target contract is implemented and reviewed.

Changing a tenant's Creator Party is a distinct target-only Account transfer operation with its own authority and evidence; ordinary tenant, membership, billing, or content updates cannot substitute for it. No transfer route or schema is selected here.

For official hosted deployments, Game Design owns creator content and must obtain a bounded Account currentness/evidence result before each creator-intent content-bearing write, including the first Draft. The exact party, evidence, and material-acceptance-generation authority must remain valid through Game Design's commit linearization point; a preflight read alone is insufficient, so the boundary requires commit-bound Account authorization/fence or equivalent validation without selecting its mechanism. Each committed covered mutation records `tenantId`, exact `creatorPartyId`, `acceptanceEvidenceId`, and material-acceptance `generation`; Game Design stores only this local binding and does not duplicate Account's party or terms catalogs. Missing, stale, mismatched, ambiguous, unavailable, or uncertain authority aborts the Game Design local transaction before any mutation or staged artifact becomes authoritative or externally reachable; staged bytes are cleanup/quarantine state, not success. Exact durably committed retries replay their stored result and evidence. An uncertain or not-durably-committed attempt first reconciles the original stable identity and obtains durable no-commit proof; it is not blindly redispatched or mutated while indeterminate. Only a permitted fresh attempt performs a fresh commit-bound currentness check. Reusing the same identity with changed normalized payload returns the target application outcome `IDEMPOTENCY_CONFLICT` before mutation. Account does not select a distributed transaction, public route, or future schema here.

Account owns the changed-hosted-terms technical contract. It classifies each proposed terms change as material or nonmaterial through audited operator/legal review. A material change classified under [ADR 0181](../../decisions/adr-0181-changed-hosted-terms-decline-and-existing-content-continuity.md) advances the monotonic material-acceptance generation and requires affirmative reacceptance; only a nonmaterial change may leave that generation unchanged. Account keeps operative and proposed versions distinct, gives reasonable notice through disclosed durable channels with a disclosed effective date, and records sufficient notice evidence. An explicit decline during the notice period records nonacceptance but does not end the previously accepted terms or freeze writes early. At the effective date, a declined or non-reaccepted material generation is stale; Account currentness fails closed and Game Design blocks each covered new content-bearing mutation before side effects.

Until the disclosed effective date, the previously accepted terms remain operative. After currentness becomes stale, narrow prior-terms continuity may support reads of persisted Draft/history content, unchanged published or active delivery, and technically necessary caching, replication, backup, restart, repair, security, or moderation. It must not create a new creator-content side effect, version, or publication, expand reachability or audience, or grant a new right.

Supported reads and downloads, including any controlled export the product supports, remain separate from lifecycle reduction and use their applicable authorization and audit boundaries. A controlled export uses its own authorization, audit, and [ADR 0050](../../decisions/adr-0050-versioned-export-retention-and-erasure-policy.md) retention requirements and does not promise whole-game portability. Only unpublish, retire, removal, deletion, and account-closure requests are lifecycle-reducing operations; each must be narrowly authorized, audited, idempotent, and reducing-only, with no new creator-content payload, reachability expansion, or new version.

Decline or missing reacceptance does not itself cancel a subscription, delete content, decide a refund, or change billing or entitlement state. Subscription and billing consequences remain independent under [ADR 0143](../../decisions/adr-0143-stripe-v1-hosting-billing-and-deferred-creator-monetization.md) and the Account subscription lifecycle; payment or continued hosting never implies hosted-terms acceptance or marketplace enrollment. Future creator commerce remains separately gated by [ADR 0179](../../decisions/adr-0179-firemud-managed-creator-commerce-boundary.md).

### Original Creator Callback Authorization

For fresh current-actor callbacks, Account observes its existing clock after the final blocking owner operations and immediately before invoking the callback. The original ControlUI issuance must have whole-second `issuedAt = iat = nbf`, with zero skew, and one clock observation must satisfy `issuedAt <= now < expiresAt`. Account does not rewrite the token, registry cleanup deadline, source evidence, or retained order. Exact historical recovery of an already-held original order remains separate and may proceed after creator expiry. Global token profile, signature, and key contracts remain defined by [JWT and Token Contracts](../../system-architecture-jwt-and-token-contracts.md).

For each fresh current-actor path, Account loads the existing trusted public JWKS source outside SQL transactions and synchronization. The protected snapshot must contain the immutable original signer receipt’s exact key ID and RFC 7638 fingerprint. An accepted original key may coexist with other current public keys and need not be the newest active signer. The snapshot belongs to one invocation and does not guarantee acceptance through later locks, callback, or commit. Signature/profile, active registry, historical signer provenance, and current Account source checks remain independent; the source remains unregistered.

The original Draft claim transport delegates to Account’s existing creator and retained-fence owners; a claim uses the exact same-namespace Game Design workload and protected creator credential, while the separate held-order read is restricted to the exact World workload. The [original-order proto](../../../../protos/account/v1/original_draft_order_service.proto) carries only the original operation and transport correlation; it supplies neither environment authority nor a creator credential in its body. The credential is carried in the protected binary metadata header and retains Account’s 16 KiB maximum compact creator-token bound. The shared transport codec permits 22,872 bytes of inbound metadata and a 4 MiB + 1 KiB inbound request message. Before registering `AccountOriginalDraftOrderGrpcService`, the Account receiving server must allow inbound metadata of at least `AccountOriginalDraftOrderGrpcCodec.MAX_METADATA_BYTES` and inbound request messages of at least `AccountOriginalDraftOrderGrpcCodec.MAX_WIRE_BYTES`; binding the service configures neither server limit. Held replay preserves the original binding and pending settlement rather than issuing fresh creator authority. These adapters remain unregistered, and both application profiles continue to omit permission for the RPCs. Controlled issuer, environment and PKI inputs are component proof only; caller qualification and remaining genuine authority are tracked in [Game Authoring](../../../project-management/implementation-tracking/game-authoring-publishing-and-activation.md#original-account-ordered-world-source-caller).

The selected-publication order adapter accepts only the exact same-namespace Game Design workload without authenticated end-user caller context, and carries the original creator credential only in protected binary metadata with an unchanged 16 KiB maximum. Its `AccountSelectedPublicationOrderGrpcCodec.MAX_METADATA_BYTES` allowance is 22,872 bytes, including base64 wire encoding and bounded metadata overhead. Any future Account receiving composition must allow that metadata size before registering `AccountSelectedDraftPublicationOrderGrpcService`; binding the service does not configure the server limit. The service remains unregistered, so this prerequisite does not configure or claim a deployed receiver.

The unregistered Draft terminal reconciler consumes the exact required Game Design and World owner readbacks outside Account transactions, then retains missing evidence through the existing Account fence repository after rechecking the original binding and ordering. Additional required v2 owners without a supported reader remain pending. It creates no new authorization or runtime access; its qualification and source-provenance limits belong to [the authoring tracker](../../../project-management/implementation-tracking/game-authoring-publishing-and-activation.md#account-terminal-settlement-continuation).

Both terminal-read transports retain the complete original binding and complete owner readback. Their shared bounds are 4 MiB for the binding, 16 MiB for the complete framed owner readback (including its repeated binding and result), and 1 KiB for protobuf/request metadata. The response allowance is therefore 20 MiB plus 1 KiB; both Account clients set that inbound limit, and both owner codecs enforce the same field and wire bounds on production and consumption. Receiving-server composition must allow the request bound of 4 MiB plus 1 KiB before these currently unregistered adapters are enabled. These limits change no original bytes, outcome, owner authorization or settlement rule.

### Account-Owned Playtest Grant Contract

Account is the sole writer and read authority for non-public realm grants under [ADR 0138 (PLAYTEST-01)](../../decisions/adr-0138-expiring-playtest-grants-with-bounded-active-revocation.md). The canonical grant identity is `{accountId, tenantId, worldSlug, realmSlug, playtestLifecycleId}`, with `playtestLifecycleId` immutable for the lifecycle; the record carries active/revoked state, monotonic `grantRevision`, `grantExpiresAt`, grantor/audit metadata, and the stable `requestId` outcome. `tenantAdmin` may create, extend, list, and revoke grants only within the exact tenant it administers. Authenticated `platformAdmin` may create, extend, revoke, or deliberately re-grant only through a distinct reasoned and audited `privileged_control`/break-glass grant-mutation branch governed by [Operator Authorization References](#operator-authorization-references) and [operator delegation](../../system-architecture-authz-route-matrix.md#operator-delegation). The branch requires an Account-issued authorization reference bound to the typed grant action, exact target and current playtest lifecycle, canonical `mutationDigest/v1` digest, live `platformAdmin` role, exact target-tenant generation, and `privileged_control` evidence. The grant's stable `requestId` remains the domain idempotency identity; the operator flow's `controlPlaneRequestId` is a separate correlation identity, and the reference binds both. The branch carries an explicit reason and audit attribution, is distinct from `tenantAdmin`, and is not tenant impersonation or a gameplay grant. Both paths validate the exact tenant, world, realm, account, and current playtest lifecycle; a slug or caller-supplied tenant identifier is not proof.

The unregistered `AccountCurrentLifecycleRealmGrantReadOwner` composes a read through the exact Game Session workload with Account's five-field grant storage. The finite peer-qualified source call runs outside Account SQL; a separate bounded Account read transaction evaluates its retained grant or tombstone against the exact selected lifecycle and minimum grant/fork expiry. Missing source, a different current lifecycle, revocation and expiry do not fall back to legacy grants. Its result is explicitly as-of: even an active grant has `admissionAllowed=false` while preparation remains incomplete, and this read supplies neither mutation authorization nor a cross-owner commit hold. The source transport and preparation limits belong to [Game Session API Contracts](../game-session-service/api-contracts.md#initial-fresh-playtest-lifecycle-source-preparation).

The grant `scopeId`, `outboxStreamKey`, and event `sourceScope` use the shared [canonical grant authority-stream scope codec](../../system-architecture-redis.md#canonical-grant-authority-stream-scope-codec). This API contract owns the five-field semantic identity and lifecycle rules; it does not define a second stream encoding or permit a legacy scope fallback.

#### Realm-grant action-family schema

The closed action-family schema is `firemud.account.realm-grant`, version `1`. Its typed digest schema contains exactly the seven ADR 0047 fields in this canonical order: `actionFamilySchemaId`, `actionFamilySchemaVersion`, `scope`, `target`, `expectedVersion`, `mutation`, and `auditReason`. Nested object values use their declared schema order below when constructing the binary digest preimage, rather than lexicographic sorting. A future raw-token decoder must reject duplicate, unknown, missing-required, wrong-type, malformed-Unicode, trailing, or over-limit input and construct this exact typed schema; this definition does not make raw JSON property order authoritative.

| Field | Required shape and constraint |
| --- | --- |
| `actionFamilySchemaId` | String exactly `firemud.account.realm-grant`. |
| `actionFamilySchemaVersion` | String exactly `1`. |
| `scope` | Object with exactly `tenantId`, then `targetNamespace`. |
| `scope.tenantId` | Canonical lowercase, hyphenated, non-nil UUID. |
| `scope.targetNamespace` | One lowercase ASCII workload namespace label: 1–63 letters or digits, with internal hyphens allowed and no leading or trailing hyphen. |
| `target` | Object with exactly `accountId`, `worldSlug`, `realmSlug`, then `playtestLifecycleId`. |
| `target.accountId` | Canonical lowercase, hyphenated, non-nil Account UUID. |
| `target.worldSlug`, `target.realmSlug` | Lowercase ASCII slug matching `[a-z0-9]+(?:-[a-z0-9]+)*`, 1–120 bytes. |
| `target.playtestLifecycleId` | Canonical lowercase, hyphenated, non-nil UUID for the exact playtest lifecycle. |
| `expectedVersion` | Absent for `CREATE`; a positive canonical JSON integer within signed `long` range for `EXTEND`, `REVOKE`, and `REGRANT`. It is the expected grant revision, with absence retained as an explicit digest value. |
| `mutation` | Object with exactly `operation`, then the conditionally present `grantExpiresAt` member. |
| `mutation.operation` | String exactly `CREATE`, `EXTEND`, `REVOKE`, or `REGRANT`. |
| `mutation.grantExpiresAt` | Absent for `REVOKE`; required for the other operations as a UTC instant in the canonical `Instant.toString()` form. The expiry must not exceed the current fork expiry; the immutable action digest does not establish that current value. |
| `auditReason` | Required NFC-normalized string, nonblank, without U+0000 (NUL), at most 4,096 normalized UTF-8 bytes. The shared blank set is U+0009–U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000–U+200A, U+2028, U+2029, U+202F, U+205F, and U+3000; U+200B does not make a reason blank. |

`expectedVersion` and `mutation.grantExpiresAt` are absent from the request object in their absent cases, including no `null` substitute, but remain in their declared positions in the digest grammar. The operation-specific expiry and revision constraints apply equally to all four operations. The action target includes the exact five-field grant identity; stream identifiers are derived separately by the shared Redis codec linked above. Stable `requestId`, actor identity, transport credentials, authorization references, reservation data, and Account authority evidence are outside these seven digest fields.

The family retains ADR 0047's default bounded-parser and digest limits below. The typed model implements digest construction; the required raw-token decoder remains unimplemented. Arrays and additional nested values are not part of this schema.

| Limit | Maximum |
| --- | ---: |
| Raw UTF-8 JSON input | 16 KiB |
| Composite nesting depth | 8 |
| Members in one object | 16 |
| Elements in one array | 64 |
| NFC-normalized string or object-key bytes | 4,096 |
| Raw or canonical numeric bytes | 128 |
| Numeric scale | 128 |
| Canonical segment payload | 8,192 bytes |
| Complete `mutationDigest/v1` preimage | 32 KiB |

The digest is lowercase hexadecimal SHA-256 over ADR 0047's exact seven-field `mutationDigest/v1` preimage; it has no family-specific prefix. A fixed `CREATE` vector uses namespace `prod`, account `11111111-1111-4111-8111-111111111111`, tenant `22222222-2222-4222-8222-222222222222`, world `world`, realm `private-realm`, lifecycle `33333333-3333-4333-8333-333333333333`, absent `expectedVersion`, expiry `2026-11-03T01:00:00.123456789Z`, and reason `invite`; its canonical preimage is 623 bytes and its digest is `02b15bc519f034f7e70ba1a4acef87564d0eb1881555b21272db9d6cc59ae6bc`.

Publishing this digest shape does not make the family executable or supported. The local typed mutation model is not a raw-token decoder, authorization-reference issuer or redeemer, or actor-qualification source. No route is enabled by constructing the data; current lifecycle/fork-expiry authority, caller authorization, required cross-language vectors, and complete owner composition remain prerequisites. Operator/global ingress remains unsupported, and no actor or lifecycle authority may be inferred from this action data.

Every grant has an explicit expiry no later than the fork's current `forkExpiresAt`; effective access is `min(grantExpiresAt, forkExpiresAt)`. The existing target tenant-admin `POST /tenant-admin/tenants/{tenantId}/realm-access-grants/{worldSlug}/{realmSlug}/{playtestLifecycleId}` is the duplicate-safe create-or-extend command: it carries the exact account/lifecycle target, `operation`, requested `grantExpiresAt`, stable `requestId`, and conditional `expectedGrantRevision`. `expectedGrantRevision` is absent for `CREATE`, which is an explicit absent-grant-and-tombstone precondition, and is required for `EXTEND` against the current active-grant revision. Its action-family schema maps that revision presence/value to ADR 0047's typed `expectedVersion`, maps normalized operation and requested-expiry presence/value into typed `mutation`, and uses the exact seven-field `mutationDigest/v1` grammar; an exact request identity with the same digest replays that stored outcome, while changed operation, target, lifecycle, expiry, expected revision, or normalized payload returns `IDEMPOTENCY_CONFLICT` before mutation. Fork extension does not extend grants implicitly, and each grant extension revalidates the current fork expiry and advances the revision. Create, extend, revoke, and deliberate re-grant operations are ordered by the grant revision. Reordered or conflicting requests return the stored outcome or `IDEMPOTENCY_CONFLICT`; revocation retains a tombstone so delayed create/extend retries cannot resurrect access. A later intentional re-grant observes that tombstone and advances beyond it.

Account atomically compares the expected revision with the current grant or retained tombstone, then commits the next revision, any tombstone, the durable request result, and the authority event. A mismatched existing revision, or a failed absent-grant precondition for `CREATE`, returns deterministic `GRANT_REVISION_CONFLICT` with no grant, tombstone, result, or event mutation. Concurrent operations with different request IDs and the same expected revision therefore have exactly one winner; an exact retry is resolved by request identity and `mutationDigest/v1` and replays the stored result without another revision or event.

The target `DELETE /tenant-admin/tenants/{tenantId}/realm-access-grants/{worldSlug}/{realmSlug}/{playtestLifecycleId}/{accountId}` revocation carries the same stable `requestId` contract as grant mutations and requires `expectedGrantRevision` for the current active grant. The canonical action-family schema uses the same ADR 0047 mapping and exact seven-field `mutationDigest/v1`, returns the stored outcome for an exact retry, and rejects a changed target, lifecycle, expected revision, or payload with `IDEMPOTENCY_CONFLICT` before mutation.

The distinct platform-admin break-glass owner transport is `POST /internal/operator/realm-access-grants/{tenantId}/{worldSlug}/{realmSlug}/{playtestLifecycleId}/{accountId}` with the typed `PlatformAdminRealmAccessGrantMutationRequest` body. It is internal-workload-only and accepts only the exact Logging & Admin mTLS identity after the canonical external Gateway → Logging & Admin ingress has durably recorded and authorized the operator intent. The body carries the exact target `{accountId, tenantId, worldSlug, realmSlug, playtestLifecycleId}` (which must equal the path), stable domain `requestId`, original `operatorAuthorizationReference`, Account-returned `authorizationReferenceFingerprint`, `controlPlaneRequestId`, reservation owner/fence, the canonical complete `postAuthorizationExecutionTuple`, closed `action` (`CREATE`, `EXTEND`, `REVOKE`, or `REGRANT`), conditional `expectedGrantRevision` (absent only for `CREATE`, required for `EXTEND` and `REVOKE` against an active grant, and required for `REGRANT` against the current grant or tombstone), canonical `mutationDigest/v1`, explicit `reason`, and `grantExpiresAt` when applicable. Account redeems the reference, exact-compares the complete tuple including the expected revision, revalidates the live `platformAdmin`/`privileged_control` evidence and current lifecycle, and then applies the same atomic grant revision, tombstone, result, event, and domain-idempotency rules. No public `/platform-admin/**` Account route exists, and this owner transport never reuses or implicitly aliases the tenant-admin surface.

At effective expiry or revocation, Account publishes the monotonic grant-authority change. The grant becomes invalid for discovery, connect-token issuance, `PLAY`, reconnect, and continued gameplay authority; Game Session consumes that change through bounded indexes/reconciliation and terminates affected active bindings under the session contract. A planned friendly ending is separate: close admission, complete bounded drain, then revoke/expire grants. Grant revocation is never a request to drain indefinitely. This contract is target state; the registered legacy four-field `AccountRealmAccessGrant` persistence and internal reads do not provide expiry, exact request replay, or retained tombstones. Local lifecycle-bound storage retains those capabilities, while its management and consumer entry points remain unregistered; tenant-admin mutation, qualified actor authorization, and end-to-end active-binding ejection remain unproved.

### Public bootstrap WORLDS discovery

Each visible world returns its stable `tenantSlug` and tenant-scoped `worldSlug` with its display name. Different tenants may expose the same world slug; clients retain both selectors and pass `tenantSlug` as the required query parameter to `GET /auth/bootstrap/worlds/{worldSlug}/realms`. Account resolves the pair against one complete current discovery collection. A bare or globally inferred world selector is not a supported browser request. The resulting opaque `connectScopeId` binds the exact tenant and realm for subsequent character discovery and admission; the character route still verifies its world/realm path against that scope.

`ListBootstrapWorlds` returns the complete set of visible public-production tenant-qualified world selectors whose current Account entitlement says gameplay is available. The whole request fails if the collection represents one canonical tenant more than once; shared world slugs across different tenants remain valid. Account verifies the existing browser-bootstrap credential against its persisted account identity, obtains the complete canonical target collection from Game Session, evaluates current entitlement once for each represented canonical tenant, and revalidates the caller and checks each original entitlement observation deadline before returning a deterministic `worldSlug`, then `tenantSlug`, ordering. The Account owner fails the whole request when the target collection changes, is ambiguous, or cannot be read completely, or when any required entitlement is unavailable or expired; it never returns a partial list. The canonical target collection contract and limits are owned by [Game Session's public-production target collection read](../game-session-service/api-contracts.md#public-production-bootstrap-target-collection-read).

Independent tenant entitlement evaluations run outside ambient SQL with at most eight concurrent workers per discovery request. A shared fair eight-permit bound also limits active evaluations across all discovery requests and owner instances in the Account process. Waiting for a permit occurs outside SQL and lasts at most five seconds; contention expiry fails the whole discovery request as `ENTITLEMENT_UNAVAILABLE`. Success, source failure and interruption return acquired permits. This bounds this owner’s aggregate connection demand without resizing the Account pool or guaranteeing production capacity. Each tenant is evaluated once and retains its owner’s independent transaction/isolation checks; caller and SQL context are not propagated to workers. The owner waits for the complete set, validates every returned tenant identity and returns no partial result on failure or interruption. Original observation deadlines remain unchanged and are checked after the second complete target read and final caller check. This bound reduces serialized latency; it is not a production capacity guarantee or permission to extend expired evidence, and slow or large collections can still refuse when their original observations expire.

### Account-Owned Safety Restriction Contract

Account is the sole enforcement owner for the two global safety categories defined by [Moderation Policies](../logging-admin-service/moderation-policies.md): `account_security_lock` and `platform_access_ban`. They are separate durable lifecycles, not aliases or one combined account-ban state. Both apply to the global account subject across tenants; neither accepts a tenant, realm, or channel scope.

`account_security_lock` is protective compromise state. It revokes ordinary account and player-bootstrap authority and is cleared only by the Account-owned security-recovery workflow after its required identity/security evidence. `platform_access_ban` is punitive platform denial. Credential reset, password recovery, or successful security-lock recovery never clears it; only a later authorized punitive revision may remove, expire, or correct it. The two categories may stack, and clearing one never changes the other.

Every Account restriction transition (create, extend, expiry, removal, security recovery clearance, or correction) is an immutable monotonic revision keyed by exact `{accountId, category}`. The revision carries normalized scope, effective/expiry time, actor, case or security-event identity, source request, safe notice/reason, owner enforcement epoch, idempotency identity, and payload digest. Account atomically commits the revision, current projection, authority-generation effects, and idempotent result. Same-identity/same-digest retries replay; a changed digest conflicts; delayed or reordered revisions cannot resurrect older state.

For a moderation action or appeal outcome, Logging & Admin records durable intent first and sends one typed digest-bound command under [ADR 0048](../../decisions/adr-0048-durable-idempotent-operator-write-execution.md). Account independently validates current authorization and account facts, redeems its Account authorization reference when required, commits the local state and result, and returns the owner outcome. Logging & Admin does not own or mutate Account restriction tables and Account does not own the moderation appeal case. Account exposes only a safe denial category/next-step projection to players; protected evidence and moderator notes remain in Logging & Admin.

This target contract is not complete in the current service. The existing `security_locked` lifecycle and auth foundations do not prove the separate punitive platform-ban lifecycle, revision/tombstone ordering, generation propagation, owner command/idempotency, recovery-clearance isolation, or end-to-end player-safe outcomes.

Fresh-enrollment certification is internal Account owner work, not a public registration, login, or bootstrap response contract. Those API paths must not infer a clear category from a new account, absent restriction rows, or historical birth evidence; protected operations require readable current category-owner results and otherwise fail closed. The normative owner contract and partial implementation limit are recorded in [Account Runtime and Data](./runtime-and-data.md#account-lifecycle-state-model) and the [Player Access and Session tracker](../../../project-management/implementation-tracking/player-access-and-session.md#current-status).

### Current vs Target Export Lifecycle

The current `GET /accounts/{accountId}/export` route returns a synchronous Account/profile-local result. It has no cross-service required-owner fan-in and does not satisfy ADR 0050. The current local implementation is known drift from this target.

For `security_locked` accounts, Account's successful recovery authorization issues a single-use `security-lock-export` credential bound to the exact global `accountId`, caller `requestId`, and canonical `requestDigest` before export initiation. A retry with the same account, request ID, and digest reuses the attached `exportId` and stored operation, including after a lost response. A changed account, request ID, digest, export ID, or export scope is an idempotency conflict; the credential cannot initiate a second export, be rebound to another operation, or be used as general account or support authority.

### Runtime account identity owner read

`RuntimeAccountIdentityService/ResolveRuntimeAccountIdentity` reads Account's already-persisted canonical UUID and provenance for Account's own row. The protobuf in [`runtime_account_identity_service.proto`](../../../../protos/account/v1/runtime_account_identity_service.proto) is the wire authority; Account does not derive an identity from another owner's key or row.

The only permitted peers are verified Game Session and Entity Management workload identities in the exact configured `FIREMUD_GRPC_WORKLOAD_NAMESPACE`. The RPC is exempted by its exact full method name from bearer-token validation because it is workload-only; the listener remains mTLS-only, and the handler verifies the exact peer service and namespace. JWT claims and request metadata do not establish workload identity.

The request contains exactly `canonical_account_id` and `request_id`; both must be canonical, lower-case, nonnil UUID strings, and unknown fields or invalid/missing values are rejected. The schema-version-1 response contains the configured `target_namespace`, exact echoed `request_id` and `canonical_account_id`, `source_account_row_id`, and `account_uuid_provenance`. The returned source row and provenance must come from the same persisted Account row whose UUID exactly matches the request selector. The numeric row value is provenance only and must not be used as gameplay identity. Account independently verifies that its persisted `account_uuid_source_numeric_id` equals that row's `id` before returning evidence. Account returns no partial evidence when persisted UUID/provenance/source-row evidence is missing, ambiguous, malformed, or inconsistent.

This read is not an authentication, membership, entitlement, realm-grant, actor-owner, playable-state namespace, or admission decision. It creates no membership or grant and does not select or activate an actor. Game Session and Entity Management retain their respective runtime composition and admission contracts.

### Operator Authorization References

This public response addition does not change the five-field encrypted recovery plaintext or retained ciphertext. The additional tuple is bounded at 256 KiB; the existing authority-bundle and envelope limits remain separate. These source APIs remain default inactive; this carrier change does not register an executable ingress.

`IssueHumanOperatorAuthorizationReferenceRequest` contains the forwarded `control-ui` evidence, target owner service, typed target scope, action family, action-family schema identifier/version, the applicable mutation identity, correlation-only `controlPlaneRequestId`, and canonical digest. Its branch selector is `action_category_or_absence`: published moderation schemas must validate a closed `action_category` before branch selection, while published non-moderation schemas must explicitly omit `action_category` and select `non_moderation`; omission cannot downgrade a moderation family. For moderation action families, the typed request carries exactly one dedicated identity: `policyIntentRequestId` with the local policy-intent digest, or `ownerEnforcementRequestId` with the owner-enforcement digest. Neither dedicated identity may be omitted, replaced, or aliased by `controlPlaneRequestId`; the separate appeal-submission identity is not carried by operator issuance. For non-moderation families, the typed mutation identity remains `controlPlaneRequestId` with `mutationDigest/v1`. The typed scope is branch-specific: `non_moderation` and `tenant_restriction` require `tenant_scope`, while `platform_access_ban` requires explicit `target_account_id` and has no tenant scope or membership fields. Actor identity is not a request field: Account derives it from the validated token forwarded by the exact Logging & Admin mTLS workload. Account chooses a short expiry, stores a keyed hash for lookup, and retains the original high-entropy opaque reference only in protected encrypted authority storage or a bounded encrypted response envelope for the reference lifetime plus the documented retry and read-only recovery window. The exact authenticated internal response contains `operatorAuthorizationReference`, Account-calculated `authorizationReferenceFingerprint`, `expiresAt`, the immutable `authorityEvidenceBundle/v1`, and `authenticatedLoggingWorkloadIdentity`, which is copied from the verified same-namespace Logging/Admin TLS peer after successful issue or recovery; Logging checks the returned identity against the action target namespace before accepting the response. Account never exposes that evidence through an external route, logs, audit text, or client-visible response.

`IssueAutomationOperatorAuthorizationReferenceRequest` contains no workload identity field: Account derives `workloadIdentity` from the authenticated mTLS transport peer and rejects any serialized or caller-supplied substitute. It contains `automation_policy_id`, `automation_policy_version`, target owner service, typed target scope, action family, action-family schema identifier/version, `controlPlaneRequestId`, and canonical `mutationDigest`, with no account, end-user token, or human identity. The target request is `non_moderation`-only: published schema pairs must select the branch with `action_category` absent, moderation schema pairs are rejected before issuance, and no concrete schema pairs are published while the route remains target-not-routable. For the supported tenant-scoped branch, Account binds the exact `tenant_generation`; global-role or `privileged_control` authority is rejected rather than inferred. The exact authenticated internal response has the same opaque reference, fingerprint, expiry, and immutable authority-evidence shape; its stored binding includes the authenticated workload and policy evidence plus the applicable generation predicate. `controlPlaneRequestId` and `mutationDigest/v1` cannot be reused for moderation; any future moderation automation contract must declare dedicated request identity, digest, and idempotency semantics with `controlPlaneRequestId` correlation-only.
Both issuance requests are typed by the published action-family schema pair and contain the target owner, typed scope, action family, typed target, typed expected version, typed mutation, typed audit reason, the applicable mutation identity, correlation-only `controlPlaneRequestId`, canonical digest, the exact authenticated workload binding, the validated actor or automation-policy input, `reservationOwnerId`, and positive `reservationClaimFence`, including every schema-declared bound presence/absence value. `preAuthorizationReservationTuple` is limited to those request, target, mutation, identity, digest, and reservation-claim inputs; it explicitly excludes `issuanceKind`, `authorityTuple`, `membershipVersion`, and `issuanceFence`. For non-moderation families, the mutation identity is `controlPlaneRequestId`; for moderation, the tuple contains exactly `policyIntentRequestId` or `ownerEnforcementRequestId` according to the action-family contract, while `controlPlaneRequestId` remains correlation-only. The appeal-submission identity is not added to this operator tuple. Human actor identity is not a request assertion: Account derives it from the validated `control-ui` evidence forwarded by the exact Logging & Admin mTLS workload. Automation carries no user identity and is authorized only by the exact workload plus versioned automation policy. Account rejects malformed, unsupported, over-limit, missing, aliased, or digest-mismatched identity input before authorization issuance. Account derives `issuanceKind`, the complete applicable `authorityTuple`, independent applicable `membershipVersion`, and positive `issuanceFence` after authorization issuance as post-issuance enrichment. If a transport carries copies of those fields, they are non-authoritative echoes and are excluded from `preAuthorizationReservationTuple` and its digest; Account verifies the current reservation owner and claim fence before issuing. The human and automation requests therefore share the typed pre-authorization tuple while retaining distinct actor-versus-policy authority paths.

Account creates one durable bounded issuance record keyed by the applicable mutation identity and its complete immutable tuple: `controlPlaneRequestId` is the sole unique mutation key only for non-moderation families, while moderation uses the dedicated `policyIntentRequestId` or `ownerEnforcementRequestId` and keeps `controlPlaneRequestId` correlation-only. The complete immutable `preAuthorizationReservationTuple` is comparison data for conflict detection in addition to that applicable identity key, not a substitute or alias for it, and is stored together with Account-derived post-issuance enrichment. It owns the original high-entropy opaque reference and retains it only in protected, encrypted authority storage or a bounded encrypted response envelope for the reference lifetime plus the documented retry and read-only recovery window; a keyed hash may support lookup, but the original response remains Account-owned. The issuance response contains the original `operatorAuthorizationReference`, Account-calculated `authorizationReferenceFingerprint`, `expiresAt`, and immutable `authorityEvidenceBundle`.

An exact retry of either typed issuance RPC with the same applicable mutation identity and the same `preAuthorizationReservationTuple` returns the original issuance response and never creates a replacement reference. For non-moderation families, a changed `controlPlaneRequestId` names a distinct operation; for moderation, changing correlation-only `controlPlaneRequestId` never changes or replaces the dedicated mutation identity. `IDEMPOTENCY_CONFLICT` is returned when the applicable mutation identity resolves an existing durable record and any immutable request, target, mutation, digest, workload/actor or automation-policy input, reservation owner, reservation claim fence, or other pre-authorization tuple field differs. Account compares the dedicated moderation identity and its digest as part of that tuple, and rejects any attempt to supply both dedicated identities or to use `controlPlaneRequestId` as their alias. Account-derived post-issuance fields (`issuanceKind`, `authorityTuple`, `membershipVersion`, and `issuanceFence`) are output evidence, not caller-controlled idempotency inputs; any echoed copies must match Account's stored result but cannot authorize issuance. Returning an already consumed issuance response does not restore redemption authority.

Pre-authorization identity is exactly [ADR 0048](../../decisions/adr-0048-durable-idempotent-operator-write-execution.md)'s stored `preAuthorizationReservationTuple/v1`; Account and callers do not define a local variant. Account-authenticated or reference-derived fields are not request authority assertions: after authenticating the exact mTLS caller as an allowed owner/redeemer workload, Account validates the syntax and presence of the applicable mutation identity, validates correlation-only `controlPlaneRequestId` only when the action-family/transport requires or carries it, and validates `reservationClaimFence`, then looks up the opaque reference in its durable issuance record, compares that caller with the stored redeemer/workload binding, and only then derives and compares the recorded target owner, workload/actor or automation-policy binding, current authority state, reservation owner, and claim fence. The disabled `ExportAccount`, `ExportTenantData`, `LinkExternalAccount`, `RequestEmailVerification`, `GetBalance`, `AddCurrency`, and `SpendCurrency` adapters fail before domain execution with non-OK gRPC `FAILED_PRECONDITION` and one bounded `ErrorDetail` in status trailers. They emit no response body or successful completion. This follows the shared [outcome and transport classification](../../system-architecture-grpc.md#outcome-and-transport-classification); the retained response schemas do not make these operations available.

### Control-Plane Tenant Selection

`/auth/login` accepts account credentials, not a `tenantId`. The target `control-ui` token identifies the global account and may carry global roles plus roles scoped to multiple tenants; current issuance provides global roles only, as recorded in the implementation status. A first-party UI may remember a selected tenant for navigation, but that state is not authorization evidence and switching it does not require a new token.

Every tenant-targeted request identifies its tenant in the route or request contract and independently enforces the `control-ui` profile, account subject, route class, scoped role, current membership generation, and applicable account or tenant authority generation. Global-role operations use explicit global or cross-tenant route classes and never derive authority from the UI's selected tenant. Gameplay discovery and admission continue to use the separate `player-bootstrap` profile.

## Subject-Binding Rules (Normative)

- `GET /tenants/{tenantId}/profiles/{accountId}` and `PUT /tenants/{tenantId}/profiles/{accountId}` are tenant-qualified, caller-subject-bound profile routes. They require live membership and the path `accountId` must equal the authenticated account; global roles do not broaden these routes. Cross-account moderation/support views require separate minimized contracts.
- The portable-data `/accounts/{accountId}/exports/**` lifecycle is state-dependent, while `DELETE /accounts/{accountId}` is an ordinary subject-bound account route. Pending-deletion export uses that same canonical asynchronous lifecycle:
  - While the account is active and eligible for ordinary authority, export requests use the ordinary authenticated account subject and the path `accountId` must match that subject.
  - Once the account is `deactivated_pending_delete`, export initiation, status, and content use the same `/accounts/{accountId}/exports` resources with the dedicated pending-deletion credential and `pending_deletion_scoped` classification. There is no separate `/accounts/{accountId}/deletion/export` route.
  - Default rule: `path accountId` must equal authenticated `accountId` from JWT (`sub`/`accountId` claim).
  - Exception: cross-account access is allowed only for explicitly authorized global roles (`platformAdmin`) on routes that explicitly document this override.
  - On mismatch without eligible role, return canonical authorization failure (`AUTH_FORBIDDEN_SUBJECT_MISMATCH` or service-equivalent).
- The target `/accounts/{accountId}/exports/**` lifecycle is the portable-data export contract within the defined account scope. It must not require a caller-selected `tenantId`, and it must not be treated as the billing-safe recovery export for a billing-blocked tenant. The current singular `/accounts/{accountId}/export` route is Account/profile-local drift.
- Account-scoped portable-data export is asynchronous and versioned. Its manifest names every required owning-service contribution and schema version, exposes partial/retryable owner failures, and explicitly records redacted, omitted, unavailable, and separately retained categories rather than silently dropping them; it is not a promise to return every account-related record, secret, retained evidence, or provider object.
- `GET /tenant-admin/tenants/{tenantId}/export` is the canonical tenant-wide billing-safe export route. It requires the exact `control-ui` profile plus the caller's live `tenantAdmin` membership for the path `tenantId`, remains reachable when that tenant is `grace`, `suspended`, or `canceled`, and returns only tenant-owned exportable records with minimum stable subject references. It has no `accountId` selector and is not subject-bound to one account.
- `DELETE /accounts/{accountId}` requests global account deletion after recent authentication and explicit confirmation and must offer a clear portable-data export path within the defined account scope. It rejects with canonical error `ACCOUNT_DELETE_ACTIVE_BILLING_OWNER` until Account can prove that billing authority has no nonterminal work for the account: no owned subscription in `pending`, `provisioning`, `trialing`, `active`, `past_due`, `grace`, or `suspended`; no nonterminal billing-owner transfer naming the account as old or proposed owner; and no unresolved customer, subscription, webhook, outbox, cancellation, or provider-reconciliation work. The response returns every affected tenant ID and blocker category when safe to disclose. An eligible request enters `deactivated_pending_delete`; it does not synchronously hard-delete the account or claim terminal erasure. Platform-admin deletion uses the same billing-owner precondition unless an explicit break-glass compliance workflow is documented separately.
- A billing-owner transfer is not cleared merely because its effective date passed: deletion requires terminal reconciliation as completed, or terminal cancellation with provider absence or old-subscription cancellation, plus clearance of every related customer, subscription, webhook, outbox, cleanup, cancellation, and provider-reconciliation blocker.
- Pending-deletion status, the canonical account export lifecycle, cancel, and necessary billing-settlement access use only the separate Account-owned pending-deletion credential and remain unavailable to ordinary `control-ui`/`player-bootstrap` login paths while pending. The credential is revoked on cancel, terminal completion, or expiry; a dedicated recovery challenge can issue a replacement pending credential only.
- `POST /auth/login` and `POST /auth/player-bootstrap` perform live account-state eligibility checks and reject `deactivated_pending_delete`; pending-deletion access cannot be upgraded into normal `control-ui` or `player-bootstrap` authority.
- `GET /tenants/{tenantId}/memberships/me` must ignore any caller-supplied account identifier and always bind subject from authenticated caller context.
- `GET /tenants/{tenantId}/memberships/{accountId}` is cross-subject by design and is restricted to `billingAdmin`/`platformAdmin`; every call must be audit-logged with caller identity and target `{tenantId, accountId}`.

## Billing and Support Variant Contract (Normative)

Billing, entitlement, and subscription APIs must expose distinct route/method variants per authorization class. A single endpoint must not multiplex tenant-safe, support-safe, and cross-tenant billing-safe behavior via optional flags or query parameters.

- Tenant-scoped billing-safe variants (`billing_safe_tenant`) are caller-bound and require live `GetCallerTenantMembership(tenantId)` checks.
- Cross-tenant support-safe variants (`cross_tenant_support_safe`) are separate methods/routes and return only high-level response profiles (status/plan/derived entitlement summaries).
- Cross-tenant billing-safe variants (`cross_tenant_billing_safe`) are separate methods/routes restricted to `billingAdmin`/`platformAdmin` and may include billing-reporting fields.
- Shared response-profile identifiers (`high_level_only`, `billing_reporting`, `membership_self_only`, `membership_reporting`) must be declared in the auth route matrix YAML entry for each variant so CI can enforce redaction tests by class.

## Login Modes

Account Service supports `PASSWORD` and verified-email `EMAIL_OTP` as account-enabled ordinary primary-login mechanisms. Both mechanisms must also be accepted by first-party player bootstrap when enabled for the account. `/auth/login` and internal `Authenticate` accept one login secret: when both mechanisms are enabled, either one valid supplied password or valid email-login code authenticates, rather than requiring sequential multi-factor authentication. Account Service may recognize an active eligible email-login code or verify a password according to the supplied secret and enabled mechanism; no `BOTH` enum is introduced. Authenticator TOTP and a separate `otp` field are not ordinary gameplay contracts; TOTP is target-state only for entering bounded `platformAdmin` or cross-tenant `billingAdmin` elevation.

Current implementation status: `GET /accounts/{accountId}/login-auth-modes` is available to the current account or a global privileged role. `PUT /accounts/{accountId}/login-auth-modes` is deliberately unavailable and returns HTTP `501 NOT_IMPLEMENTED` before Account service mutation, including for the current account and `platformAdmin`. Account has purpose-specific, unregistered recent-reauthentication evidence preparation and pending-creation validation for `SELF_SERVICE_GAME_CREATION`; this owner is not composed into factor changes, which remain unavailable until their Account-owned evidence and mutation boundary is implemented. Receiving proof remains pending in [Player Access and Session](../../../project-management/implementation-tracking/player-access-and-session.md#account-initial-billing-owner-preparation). The target `PUT` contract continues to require recent ordinary reauthentication under ADR 0045.

The private self-service game-creation reauthentication owner binds exact original request, Account, purpose and creation-operation identities to retained credential-MAC evidence. A wrong credential replay appends one immutable failed-attempt record and commits it before returning a credential denial. Five failures exhaust that original request; later attempts are denied before credential-MAC access. Successful replay preserves the original evidence and freshness deadline and never resets the budget or consumes another OTP. Missing custody or replay-proof dependencies remain unavailable and are not counted as bad credentials. This owner remains unregistered and supplies no factor-change or general billing authority.

### Hosting First-Invoice Checkout

The isolated receiving login is public `POST /api/account/auth/login` at Gateway. Its bounded JSON body is `{requestId, callerContextId, email, secret}`, with non-nil request/context UUIDs and one enabled ordinary primary secret. Gateway authenticates Account's exact same-namespace URI SAN before releasing credentials over the narrow mTLS `AccountControlUiAuthenticationService/AuthLogin` RPC. Account permits only the exact same-namespace Gateway workload and delegates to its durable Account-only issuer and current-actor owners. Gateway's existing header-trust WebFilter supplies a process-private canonical source proof; the controller does not interpret public source headers as proof. The closed RPC requires one canonical literal client address and the fixed HTTP transport class, and Account carries that transient source into the sign-in owner. Missing Gateway proof returns no-store HTTP 503 before credential forwarding; absent, duplicate, malformed or unsupported wire source fields are rejected before issuance. Source metadata does not change the retained v1 credential-request MAC or reset its replay budget. Success is `{status: SUCCESS, data: {accountId, authToken, expiresAt}}`, with no-store headers. Exact retries retain the same issuance; changed input conflicts. Credential-bearing replay uses a constant-time MAC comparison and an Account-owned, serialized five-failure budget bound to the immutable original issuance operation and request. Failed comparisons commit independent immutable attempt records before returning the conflict; after five failures, that request is denied before credential-MAC access. Exact retries below the budget recover the original credential without primary reauthentication or another OTP consumption, and never reset the budget. Scope, caller or context conflicts and unavailable custody are not counted as credential failures. This short recovery-request budget changes neither Account security state nor other requests and does not replace the broader credential-abuse policy in [ADR 0034](../../decisions/adr-0034-layered-abuse-controls-without-attacker-triggered-account-locks.md). The direct legacy Account HTTP login is rejected in this isolated mode and cannot provide a checkout fallback. Production legacy-login drift elsewhere remains unchanged.

The first-party `/account/subscriptions/{subscriptionId}/checkout` route obtains its bearer only from that login, holds it in memory, restricts authenticated requests to the exact owner endpoints, and unmounts checkout on expiry, local sign-out, session replacement or route departure. Local sign-out clears this UI's credentials; it does not claim server-side token revocation. Navigation, Back/Forward, reload and remount never authorize a provider command.

The Account-owned HTTPS owner surface is `/billing/hosting/subscriptions/{subscriptionId}/first-invoice`, externally prefixed by `/api/account`. It is an account-scoped billing-owner operation, not tenant-role authority: the exact current `control-ui` Account subject must own the subscription and selected instrument. Billing suspension does not remove this recovery surface. The controller is registered only by the explicitly isolated, default-off receiving composition; the [Stripe owner contract](./stripe-integration.md#first-invoice-confirmation-and-completion) and existing retention, deletion, backup, custody and registration gates remain binding.

- `GET` returns the exact existing invoice, PaymentIntent, selected instrument, amount, currency, immutable `tupleDigest`, expected current subscription row version, expiry, nullable retained `confirmationRequestId`, nullable server-verified `preRowOriginalRequestId`, current `authorizationVersion` (zero before first consent) and `AWAITING_PAYMENT` or `COMMITTED` state. `amount` is a positive decimal integer string in Stripe minor units, not a floating-point or major-unit amount. No client secret appears in status, URLs, logs or audit. A null `confirmationRequestId` means only that no confirmation row is currently committed; it does not prove that an original operation has stopped. That absence does not authorize a replacement request or charge. Before a confirmation row exists, `preRowOriginalRequestId` exposes only the original operation identity from an exact owner/subscription/tuple/row-version/expiry-verified durable fence at authorization version zero; inconsistent retained evidence refuses the read instead of appearing absent. A committed confirmation takes precedence and makes this pre-row reference null. Navigation or replacement login may recover this identity through a fresh authenticated owner read, never earlier consent or proof. Resumption requires a separate explicit renewal action, fresh unchanged charge consent and primary authentication bound to `PRE_ROW_RENEWAL` with a distinct authorization request. Expired status is observational and never extends renewal eligibility. Recovery semantics remain owned by the [Stripe contract](./stripe-integration.md#first-invoice-confirmation-and-completion).
- `POST /reauthenticate` takes distinct stable evidence `requestId` and `confirmationRequestId` plus one enabled ordinary login secret over HTTPS. A proof usable for new billing consent requires `billingBinding` with `originalRequestId`, `expectedRowVersion`, `expectedAuthorizationVersion`, `acceptedTupleDigest`, `invoiceExpiresAt`, and `authorizationPurpose`; `confirmationRequestId` names that binding's authorization request. Use `INITIAL_CONFIRMATION` with the original request ID and version zero for opening proof, `PRE_ROW_RENEWAL` with the retained original ID and a distinct authorization request at version zero for pre-row recovery, or `FOLLOWUP_RENEWAL` for a later retained authorization version. Account returns a newly bound proof only after actual primary authentication and exact owner binding. A replayed unbound historical `evidenceId` remains non-authorizing for new consent. `SELF_SERVICE_GAME_CREATION` evidence is rejected for payment. The [Stripe owner contract](./stripe-integration.md#durable-opening-proof-and-explicit-pre-row-renewal) defines the binding and recovery behavior.
- `POST /confirm` takes the immutable confirmation `requestId`, `expectedRowVersion`, `reauthenticationEvidenceId`, exact `acceptedTupleDigest` and explicit `acceptCharge=true`. The server resolves the retained commercial tuple; client amounts, instrument substitutions and provider defaults cannot change it. An exact retry retains the original operation and provider idempotency identity. Changed request fields conflict.
- `POST /renew` takes the original confirmation `requestId`, distinct fresh `authorizationRequestId`, `expectedAuthorizationVersion`, original `expectedRowVersion`, fresh `reauthenticationEvidenceId`, unchanged `acceptedTupleDigest` and explicit `acceptCharge=true`. For pre-row renewal, use expected authorization version zero and `PRE_ROW_RENEWAL` proof from `/reauthenticate`; after a retained first consent, use the exact current version and `FOLLOWUP_RENEWAL` proof. Exact renewal replay is read-only; changed evidence, consent, payment identity or losing authorization version conflicts. Renewal never resets invoice expiry or provider command history. The [Stripe owner contract](./stripe-integration.md#durable-opening-proof-and-explicit-pre-row-renewal) owns the recovery behavior and single-command boundary.
- The narrowly authorized owner response returns provider status and a client secret only for `requires_action`, with `Cache-Control: no-store`. Stripe.js `handleNextAction` completes provider authentication for that existing intent. A browser result never completes Account fulfillment; the owner polls status until the signed server completion has committed and independently read back.
- Transport or provider failures are uncertain, not evidence that no payment occurred. `FIRST_INVOICE_PROVIDER_UNCERTAIN` and `FIRST_INVOICE_EVIDENCE_REFUSED` preserve the original operation; clients must not create a replacement request or charge to escape an unknown result.

The separate `POST /billing/hosting/webhook` adapter accepts only a single bounded `Stripe-Signature` header and the exact raw UTF-8 JSON body, at most 256 KiB, over actual HTTPS. It accepts no browser bearer as provider authority. Signature validation, immutable intake, retained invoice linkage, fresh provider observations and Account completion remain independent predicates. Only independently read-back `COMMITTED` completion is acknowledged with HTTP 200; retained `RECONCILING` state returns 503 so the same signed event can be redelivered without another payment command. Gateway forwards only this exact signed-event path and the four owner operations over verified HTTPS without automatic retries or redirects; forwarded scheme or identity headers cannot establish transport security.

### Sensitive Actions and Gameplay Handoff

- Account identity/factor changes, new real-money charges, saved payment-instrument changes, global deletion, billing-owner transfer, and global administration are HTTPS-only account/control operations. Clients may be web, native, or CLI, but a Telnet gameplay connection cannot complete them or receive elevated authority.
- Sensitive personal and billing mutations require recent ordinary reauthentication. Global privileged elevation additionally requires independent TOTP once per bounded elevated window, not once per action.
- A gameplay client may explicitly initiate an eligible action and receive an opaque, short-lived, single-use HTTPS URL. Its server-side intent binds the initiating account, gameplay session, tenant when applicable, exact action, product and immutable amount/currency when applicable, and `requestId`. The URL contains no account, payment, or factor secret and grants no completion authority without independent HTTPS authentication and any required provider flow.
- Account records only a verified, idempotent completion. Gameplay may poll or receive the resulting success, failure, expiry, or cancellation but cannot approve it.
- Existing non-withdrawable premium-balance spending remains a confirmed, capped, idempotent gameplay mutation rather than a new real-money charge. Cash redemption, withdrawal, or cash-equivalent transfer is outside this contract.

## Login Error Codes

The `/auth/login` REST endpoint and the gRPC `Authenticate` method currently expose structured `shared.v1.ErrorDetail` responses for the authentication failure cases below. Those codes remain Account-local expected credential-decision semantics where the service produces its declared result; the [gRPC owner contract](../../system-architecture-grpc.md#outcome-and-transport-classification) governs failures that prevent producing that result. The current gRPC blanket response shape is implementation drift pending exact classification and proof, and this document does not decide per-RPC status mappings:

- `AUTH_INVALID_CREDENTIALS` - wrong username or unsupported/invalid login secret
- `AUTH_RETRY_LATER` - a graduated credential-abuse throttle rejected the attempt; bounded retry metadata is supplied without confirming account existence
- `AUTH_ACCOUNT_LOCKED` - an active durable Account security lock denies authentication; its public outcome is disclosed only after sufficient identity proof or through the recovery path. The lock may be entered from verified or high-confidence compromise evidence, explicit Account security policy, or audited operator action; arbitrary failed attempts must not use this as an account-existence oracle
- `AUTH_ABUSE_CONTROL_UNAVAILABLE` - shared credential-abuse enforcement is unavailable, so new player-facing authentication fails closed and may be retried
- `AUTH_UNAVAILABLE` - the required authentication authority is unreachable or times out before authentication can complete; reachable stale, regressed, malformed, or mismatched authority evidence is a denial/revocation, not an availability result

The Game Session Service translates Account application errors into the text-protocol namespace: `AUTH_INVALID_CREDENTIALS`, `AUTH_RETRY_LATER`, `AUTH_ACCOUNT_LOCKED`, `AUTH_ABUSE_CONTROL_UNAVAILABLE`, and `AUTH_UNAVAILABLE` become `ERROR INVALID_CREDENTIALS`, `ERROR RETRY_LATER`, `ERROR ACCOUNT_LOCKED`, `ERROR ABUSE_CONTROL_UNAVAILABLE`, and `ERROR AUTH_UNAVAILABLE` respectively. Telnet and WebSocket clients therefore receive stable protocol codes without collapsing distinct retry throttling, abuse-control outage, account-state, and general availability failures.

Canonical non-login authorization/entitlement errors:

- `ADMISSION_POINTER_UNAVAILABLE` - reachable routing/catalog evidence is missing, malformed, ambiguous, stale, or otherwise contract-invalid before a valid scope comparison. A valid scope whose exact `catalogRevision`/`pointerVersion` pair differs from the fresh authoritative snapshot returns `CONNECT_SCOPE_MISMATCH`; an unreachable or timed-out Account or routing authority is `AUTH_UNAVAILABLE`, not this pointer-evidence failure.
- `AUTH_UNAVAILABLE` - required current authentication, membership, registry, role, grant, or routing authority is unreachable or times out; entitlement authority remains separately classified as `ENTITLEMENT_UNAVAILABLE`. Callers retain authentication state, fail closed, and may retry. Reachable stale, regressed, malformed, scope-mismatched, or otherwise conflicting evidence returns the applicable denial, revocation, or invalid-routing outcome instead and must not be reinterpreted as missing/`INACTIVE` membership.
- `ENTITLEMENT_UNAVAILABLE` - authoritative entitlement snapshot could not be produced at required freshness/sequence guarantees; it is never a billing denial or `AUTH_UNAVAILABLE`.
- `ACCOUNT_DELETE_ACTIVE_BILLING_OWNER` - billing authority cannot yet prove that the account has no owned nonterminal tenant subscription, transfer responsibility, or unresolved provider/durable work; callers must finish terminal cancellation or transfer and allow related work to reconcile before retrying deletion.

For authenticated direct-text `REALMS`, `JOIN`, and `PLAY`, Game Session passes `ADMISSION_POINTER_UNAVAILABLE` through as `ERROR ADMISSION_POINTER_UNAVAILABLE` and preserves login state while requiring fresh routing discovery. It maps an unreachable or timed-out routing authority's `AUTH_UNAVAILABLE` to retryable `ERROR AUTH_UNAVAILABLE`; neither case permits cached-selector fallback.
