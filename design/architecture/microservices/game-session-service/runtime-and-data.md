# Game Session Service Runtime and Data

## Runtime Model

Game Session coordinates with Redis to store volatile session state and command queues and with PostgreSQL to persist durable game-instance control-plane metadata. It provides a single point of truth for current tick and world time while exposing gameplay-session state to the protocol front door.

The service runtime model assumes replaceable workers, not authoritative in-process state.

## Implementation Status

The sections below define the target-state runtime contract. Current implementation and proof status is:

- The current effective-settings HTTP read is admitted by the service-wide `PRIVILEGED` role requirement, whose shared classifier accepts any global privileged role or any tenant-scoped `tenantAdmin`/`moderator` claim. `EffectiveSettingsController` then trusts query tenant/game selectors and session ids: it can synthesize a requested tenant scope without binding it to the caller's scoped role, or resolve a persisted session without checking that its tenant is authorized by the caller. The current controller/integration tests do not prove denial of a tenant-A caller reading tenant-B settings.
- **Target effective-settings boundary:** keep this as a read-only operator surface but make authorization route-aware. Bind a tenant-scoped role to the exact target tenant and require persisted session tenant ownership/equality; allow a global `platformAdmin` branch to select a tenant only with current operator authorization, target-tenant generation, and `privileged_control`. Reject ambiguous/missing target authority, tenant/session mismatches, and unavailable owner/session evidence before invoking any resolver. The negative proof must cover scoped cross-tenant synthetic and persisted-session reads and the global branch without privileged control.
- Script pin/epoch rollout remains partial: the authoritative `{scriptPatchVersion, scriptPinEpoch, controlPlaneRequestId}` owner read, CAS-backed pin transition, and instance-bound Automation admission epoch validation are live. Local instance-scoped Automation admission, duplicate replay, and final Game Session execution now compare the complete tuple; the live ledger is still limited to current atomic request/result rows, and bounded rollout-history readback plus complete source/target remote command identity and final-effect fencing remain gaps. See the [canonical runtime-execution owner](../../system-architecture-scripting-runtime-execution.md#normative-target-contract) and the [Game Session runtime and tick coordination tracker](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md#active-gaps).
- Current Game Session does not yet persist or propagate the complete Automation-owned plugin lifecycle projection, activation epoch, or owner lifecycle revision, or prove lifecycle-time fence acknowledgement and final execution enforcement.
- Canonical mode-aware tick telemetry (`tick_execution_time_ms_bucket/p95/p99{scope_class,tick_mode}`, `tick_lock_ttl_ms{scope_class}`, `solo_lock_ttl_ms{scope_class}`, and the derived safety ratio) is target-only and currently unavailable: the live `TickService` records `game_session_tick_duration_ms` without bounded `scope_class` or `tick_mode` labels, so the Prometheus/Grafana rules are templates until Game Session emits and proves the required families.
- Hidden same-type Game Session recovery within ADR 0013's qualifying conditions remains an implementation or proof gap; the target is to preserve the session through upstream rebind rather than require a player-visible re-`LOGIN` / re-`PLAY` cycle.
- The live `startSession` path keeps the Game Session row and runtime projection `STARTING` until World confirms its fenced `PREPARING -> ACTIVE` transition, then records `RUNNING`; failures before an activation attempt use the existing pre-activation cleanup. Once activation may have been issued or committed, an activation error or ambiguous result, or a later local runtime-state save/finalization failure, retains both the runtime projection and local owner row as `STARTING`, and never calls stale-epoch `failPrepared` or deletes either record. A failure proven before any World termination request is issued may restore the prior `RUNNING` row and runtime state while the World remains `ACTIVE`; once a termination request may have been issued, an error or ambiguous result leaves the local row `STOPPING` and runtime projection absent. Confirmed World termination retries local `STOPPED` finalization and never restores `RUNNING`. Durable stable lifecycle-operation identity and lifecycle readback/reconciliation remain unimplemented, so these local fail-closed quarantines are not a replacement for the target durable lifecycle cleanup workflow.
- Current `onCommand` ingress uses the live `{tenantId, gameInstanceId}` boundary as a region surrogate until true region partitioning is shipped; it carries the current `regionEpoch` and a producer-supplied `readSnapshotToken` derived from the command and ownership fence. That token is retained only as an owner-specific manifest input or correlation value, not universal evaluation authority. The target handler-scoped input manifest is owned by the [DSL lifecycle contract](../../system-architecture-scripting-dsl-reference-and-lifecycle.md#read-consistency-contract); current producer/storage behavior is narrower and does not yet seal the complete manifest.
- Durable command/effect execution currently covers movement and `PUT`, `TAKE`, `WEAR`, and `REMOVE` fully at the existing boundary. Current `GET` is the command spelling for the target `PICKUP`/`PickupVisibleRoomItem` family, and `GET` plus `DROP` also enqueue and execute on that durable command path, but their ADR 0054 spatial correctness remains incomplete until World `TargetingFactSnapshot` attestation/location-version propagation, the shared actor-lock/executor-fence critical section and durable barrier/handoff path, and stale-race proof are implemented. Current movement/item replay rows do not yet prove the ADR 0054 participant guard bound to root `EffectId`, typed operation, target, and request digest, or fail-closed changed reuse.
- `BLOCK` is also on the current durable effect replay/no-op seam; other state-changing command families still need to migrate onto it.
- Current Game Session code still defaults `FIREMUD_AUTH_SESSION_EXPIRATION_MS` to one hour and does not enforce the target five-minute continuity cap.
- Current Game Session code has not converged on the canonical bounded `session:game:*` index families or proved their repair protocol: it still uses transitional `sessionctx:*` and tenant/identity lookup records and does not implement/prove the generation-safe global `accountIndexMember` set, the partitioned global issuer index, or their cross-slot repair/acknowledgement flows. This is implementation/proof drift, not a transfer of ownership or a different member shape.
- Current Game Session Redis-backed per-session rate limiting under the legacy `ratelimit:<sessionId>` key remains implementation drift from ADR 0034's target in-process ordinary gameplay limiter; its Cache/Rate-Limit role isolation, eviction behavior, and loss semantics are not yet proved. Migration must stop legacy writers and drain the maximum key TTL before unversioned target helpers consume `ratelimit:*`, or use a distinct versioned namespace.
- Bounded durable semantic reconnect-context persistence is partial: ordered `resume_transcript_entry` rows and best-effort Redis caching are live, while namespace-key migration to `{tenantId, playableStateNamespaceId, characterId}`, the distinct durable `resumeContextGeneration` episode fence and termination protocol, complete-envelope hard-bound accounting and omission-marker convergence, and post-logout replay suppression remain implementation/proof gaps.

## Runtime Details

- Redis and PostgreSQL hold the meaningful gameplay-session, tick-coordination, and control-plane state needed for takeover.
- A Game Session instance may cache or buffer transient transport-local details while it is healthy, but those details must never be the sole source of truth for reconnect, tick ownership, or gameplay admission.
- Ordinary qualifying Game Session restarts use the bounded upstream rebind contract in [Reconnection Strategy](../../system-architecture-reconnection.md#bounded-non-edge-restart-recovery); this service retains the local replacement-worker and shared-state consequences rather than redefining the elapsed-time or authority contract.

- PostgreSQL stores `game_instances`, the legacy `game_manifest` table, the exact pinned runtime-version/script-patch selections plus `scriptPinEpoch`, active runtime feature-flag overrides, and audit-relevant disconnect/remediation metadata. `game_instances` retains the active `gameInstanceId` execution target and its durable `{tenantId, playableStateNamespaceId, playableStateScope}` binding; that namespace/scope identity remains stable across replacement while instance-scoped routing/session state follows the active pointer, and stale instance or region evidence is fenced by the current lifecycle and runtime/region fence. The live `script_pin_operation` immutable request/result ledger supplies current atomic mutation-history rows within the Game Session-owned pin boundary; bounded rollout-history readback, complete history fields, and focused proof remain gaps. Automation readiness/projection rows do not compete with it. The current `game_manifest` schema has only `id`, unqualified `version_id`, description, and timestamps; it has no tenant column, tenant-qualified constraints, or canonical version-lineage fields, and its repository exposes global `count`/`findAll` operations. It is therefore unsupported legacy/current implementation drift, not tenant/version namespace authority and not a launch or admission source. Its retained rows require an inventory and explicit disposition (verified empty/no-data boundary or mapped migration) before removal or replacement; proof must establish tenant-qualified canonical version references and owner-readback through the Game Design authority.
- Redis stores gameplay session bindings, tick queues, timers, retries, and region leases.
- Game Session uses PostgreSQL for durable control-plane metadata and Redis as the coordination plane for gameplay-session bindings, tick queues, timers, retries, and region leases.
- Bootstrap session-context records are created as soon as a client connects. They remain unauthenticated until Account Service verifies credentials and issues a token, and gameplay commands must reject them as `LOGIN_REQUIRED` until `LOGIN` promotes the context to authenticated account scope.
- Game Session relies on the shared libraries for DTO definitions, logging interceptors, Micrometer metrics, and shared saga helpers rather than reimplementing those surfaces locally.
- Credential brute-force defense remains delegated to Account Service, which owns one login-attempt policy across transport paths using trusted source context. Game Session consumes the resulting auth outcomes when binding gameplay sessions but does not implement separate credential-abuse logic. The target ordinary gameplay limiter is an in-process session-front-end token bucket under [ADR 0034](../../decisions/adr-0034-layered-abuse-controls-without-attacker-triggered-account-locks.md); the current implementation still uses a Redis-backed per-session limiter and does not yet prove the target role isolation or loss behavior. Before a restart or takeover initializes a replacement bucket, the target owner atomically reserves from the binding's shared bounded cumulative handoff budget, so retries or concurrent replacements cannot reset or double-consume the remaining allowance. Optional coarse shared abuse windows remain outside the per-command fast path.
- No single Game Session process may become the hidden source of truth for reconnectable gameplay state. If the service needs a value to survive non-edge restart or permit same-type takeover, that value must live in Redis or PostgreSQL-backed coordination rather than only in process memory. Realm admission additionally requires a fresh World lifecycle row/epoch read under [ADR 0123](../../decisions/adr-0123-database-authoritative-temporal-coordinated-world-lifecycle.md); Temporal status is coordination evidence, not admission authority.

### Persisted actor admission boundary

Game Session does not persist or allocate the primary actor. It resolves the realm target, asks Entity Management for the valid roster/policy result, and keeps `CHARS` as discovery before `PLAY`. A normal binding requires one persisted `characterId`; controller uniqueness is `{tenantId, playableStateNamespaceId, characterId}`, with `accountId` owner evidence and `playableStateScope`, `gameInstanceId`, and region/epoch as routing/fence evidence. See [Entity Runtime and Data](../entity-management-service/runtime-and-data.md) for allocation, policy, descriptor/template, and fork-copy rules.

The local runtime stores only active attachment, protocol state, presence, and controller-fence data. A playtest copy is selected by its new fork-local `characterId`; `sourceCharacterId` is not used as authority. Current per-instance lookup, unresolved-character fallback, and complete cross-service proof remain gaps.

## Owner-Local Gameplay Restrictions

Game Session is the sole runtime enforcement owner for `gameplay_ban`, while Logging & Admin owns fixed-category policy intent, cases, appeals, and audit. The complete category and command contract is [Moderation Policies](../logging-admin-service/moderation-policies.md); this section records Game Session's local state and decision consequences.

Game Session persists an indexed restriction projection keyed by the exact subject, `tenantId`, optional `realmId`, category, monotonic owner revision/enforcement epoch, effective/expiry times, source case/request identity, payload digest, and player-safe notice. Each create, extension, expiry, removal, correction, or appeal outcome is a new digest-bound owner command. The owner atomically commits the revision, current projection, and idempotent result; same identity/same digest replays, conflicting digest is rejected, and delayed or reordered commands cannot resurrect older state. A verified result is either one or more applicable restrictions or the explicit `NO_APPLICABLE_RESTRICTION` outcome; only unreadable, unknown, or otherwise unverifiable applicable-state evidence fails closed.

At `PLAY`, Game Session evaluates all applicable Account authority and local `gameplay_ban` records for the exact tenant/realm scope; a verified `NO_APPLICABLE_RESTRICTION` is the positive no-ban outcome. A newly effective ban denies `PLAY`, fences new gameplay command admission, and closes active covered bindings. Work already durably admitted before the effective transition may finish idempotently; it is not partially unwound. A broader tenant ban may dominate a realm request without deleting a narrower realm record. Routine `PLAY` and command admission never synchronously query Logging & Admin.

Player responses expose only the safe category/scope and permitted next step. A modified or overturned moderation appeal arrives as a newer owner command and cannot erase a later unrelated restriction. Current code does not yet provide the complete local restriction table, owner command/idempotency path, active-binding containment, expiry/reordering behavior, safe notices, or focused proof; existing synchronous `EvaluateModerationPolicy` consumption remains an implementation seam rather than completion evidence.

## Registered Durable Families and Lifecycle Participation

Multi-Tenancy owns the realm catalog, the canonical durable `{tenantId, realmId}` pointer identity and its routing/admission semantics, and the stable `playableStateNamespaceId` contract. It is the contract and identity owner, not a second persistence writer. Game Session is the sole runtime resolver, persister, and compare-and-set orchestrator for the resolved realm catalog and admission pointer, including the durable pointer record, audit, and admission-pointer state; no other service may independently write that state. Game Session does not become the owner of the cross-cutting realm or namespace policy. World Management remains the sole owner of the database lifecycle row, lifecycle epoch, and Temporal lifecycle coordination. Game Session consumes that lifecycle authority and participates in registered cleanup; it does not infer lifecycle authority from Temporal status or own the lifecycle epoch.

Game Session's registered durable families are classified as follows:

- **Namespace-backed durable state:** the resolved realm-catalog/admission-pointer facts identify the stable playable realm and survive replacement of its runtime instance. The legacy `game_manifest` row is not part of this authority: because it lacks tenant qualification and canonical version lineage, it must be treated as unsupported drift pending the retained-data disposition and tenant-qualified replacement proof described in Implementation Status. The canonical namespace identity is not copied into a new namespace, and it is not deleted as cleanup for the replaced `gameInstanceId`.
- **Bounded durable semantic recent context:** Game Session owns persistence of replay-eligible `PlayerOutput` context as ordered `resume_transcript_entry` rows, rebuilding the Redis cache from those rows and orchestrating authorized restoration. The shared [Input, Output, and Presentation contract](../../system-architecture-input-output-and-presentation.md#canonical-resume-context-model) owns the `PlayerOutput` schema and reconnect-context retention, namespace scope, resource bounds, and non-authority semantics. The rows are keyed by the durable `{tenantId, playableStateNamespaceId, characterId}` identity and follow that stable namespace across replaceable `gameInstanceId` values, so replacement cleanup must not delete or reassign them. Game Session owns a distinct positive, monotonic durable `resumeContextGeneration` for each private semantic-context episode under that stable identity; `bindingGeneration` remains the independent controller-ownership and concurrency fence. Authorized reconnect, takeover, or runtime replacement carries the current `resumeContextGeneration` unchanged even when `bindingGeneration` advances. Every durable row and cache envelope carries the exact current `resumeContextGeneration`; PostgreSQL append/read/restore and Redis cache fill/rebuild/mutation require that exact generation and durable proof that the episode remains unterminated rather than deriving authority from a prior `bindingGeneration` read or copying rows into another generation. Explicit logout, character ownership transfer, or loss of replay authority durably terminates the episode before acknowledgement, and any later authorized episode receives a newer `resumeContextGeneration`; physical deletion may complete asynchronously. Restoration is authorized only after fresh `LOGIN`/`PLAY` validates current binding and episode evidence; Game Session then renders retained entries in ordering-token order before a fresh authoritative `LOOK` and applicable prompt policy. See [ADR 0134](../../decisions/adr-0134-bounded-durable-semantic-reconnect-context.md) and the [canonical Input, Output, and Presentation contract](../../system-architecture-input-output-and-presentation.md#canonical-resume-context-model); current stable-scope, generation, termination, and no-replay proof remains incomplete.
- **Instance-scoped runtime/control state:** the active `game_instances` runtime record and its instance-bound runtime metadata, active feature-flag overrides, disconnect/remediation metadata, session records, live-presence projections, and instance/region coordination state are registered against the concrete `gameInstanceId`. Game Session flushes or retires these families idempotently and acknowledges their cleanup only after the old instance is fenced and no longer admissible. The namespace/scope/character uniqueness projection is the exception: it survives runtime replacement and is rebound from the source to the target through the existing `bindingGeneration` CAS rather than retired with the source instance. The `game_instances` row itself retains terminal lifecycle evidence; cleanup does not silently delete it, and its `playableStateNamespaceId` field is a stable namespace reference rather than an instance-owned replacement of that identity.
- **Instance-bound pin and history state:** the active current-pin projection is bound to the concrete runtime instance and is cleaned up or retired with that instance's active execution state, but retirement retains the final exact `{scriptPatchVersion, scriptPinEpoch}` tuple and append-only pin/repin/rollback history for a previously pinned instance. Semantic `UNPINNED` is reserved for a never-pinned instance whose three owner fields—`scriptPatchVersion`, `scriptPinEpoch`, and `controlPlaneRequestId`—are all absent; partial or unavailable state fails closed and is not `UNPINNED`. A cleanup acknowledgement means no active instance work or binding remains, not that retained final tuple/history evidence is erased.

These families are Game Session's local registration and acknowledgement boundary under [ADR 0122](../../decisions/adr-0122-stable-playable-state-namespaces-for-runtime-replacement.md) and [ADR 0123](../../decisions/adr-0123-database-authoritative-temporal-coordinated-world-lifecycle.md). The current implementation has the listed PostgreSQL/Redis seams and partial cleanup paths, but does not yet prove exhaustive owner registration, namespace-aware replacement fencing, or all-owner cleanup convergence. World Management records the lifecycle transition to `TERMINATED` only after every owner in the frozen required-owner snapshot captured for that `terminationRequestId` acknowledges its own obligation against that same snapshot and frozen ownership-registry revision; Logging & Admin may read and diagnose those records but is not a lifecycle or cleanup owner, and Game Logic is not a lifecycle workflow owner.

## Redis Ownership and Coordination Rules

Game Session uses the gameplay layer’s session front-end plus lease-owner execution model:

- Connected sockets bind to a stable session front-end pod, while region-scoped tick execution remains fenced to the current `<tenantId, gameInstanceId, regionId>` lease owner.
- In the target-state forwarding model, session front-ends may forward work to lease owners over internal gRPC, but only lease owners may mutate region-scoped coordination state.
- In that target-state model, owner-directory state and the front-end's execution-region pointer are routing projections, not mutation authority. The receiving executor revalidates its fence before execution and, after the authoritative durable spatial/effect result returns, revalidates its current owner fence and atomically updates the pointer only with the expected generation/CAS guard; a stale post-result fence must not update it.
- The current live `EnqueueCommand` path resolves the session's current `{tenantId, gameInstanceId}` queue target and uses the local Game Session tick-queue path; it does not expose the dedicated forwarding RPC. Accordingly, the forwarding, stale-owner validation, post-result CAS, and generation-targeted delivery rules above remain target-state implementation/proof gaps under [ADR 0170](../../decisions/adr-0170-fenced-command-forwarding-and-authoritative-region-transition.md).
- In the target-state model, connection-local FIFO uses `sessionSequence`, while retry and duplicate protection use stable command/effect/request identities. Asynchronous results address one active `{sessionId, frontEndGeneration}` so a replaced front end cannot receive them; this check is scoped to result delivery.
- Tick-related multi-key operations, including locks, pending state, queues, timers, and retry metadata, are performed exclusively via the shared Lua scripts described in [Redis Architecture](../../system-architecture-redis.md#atomicity-and-concurrency-control). Ad-hoc multi-key sequences against tick keys are not allowed outside these scripts.
- Because session bindings, leases, queues, timers, and retry markers are externalized, another Game Session instance of the same type must be able to assume session-front-end or lease-owner responsibility after an ordinary qualifying failure. Exhausted recovery, unavailable shared authority, unsafe ownership ambiguity, terminal session policy, or edge transport loss uses explicit fallback instead.
- Lease ownership and session front-end routing are deliberately takeover-ready. Another same-type Game Session instance must be able to acquire the relevant lease or front-end responsibility from shared state after restart. Replacement continues the current server-side session authority using the stable edge transport identity rather than requiring the original connect token to remain valid as fresh admission; current membership, entitlement, revocation, authorization, tenant/game scope, and fencing still apply. An exact same-binding, non-expanding reconnect or retained-edge continuation may use bounded last-known-good entitlement only for an unchanged public-production binding during an entitlement-only outage, after Account validates every other current security and authority predicate and commits the resume lease under ADR 0028. Missing, unavailable, stale, contradictory, or mismatched non-entitlement security or authority evidence fails closed; private/playtest bindings require the exact current Account-owned realm grant and `grantVersion`, with no entitlement fallback. A fresh gameplay binding remains a strict fresh-entitlement operation; retained-edge is the form that preserves the established edge without a new client transport.
- Closure of only the Gateway-to-Game-Session upstream is not authoritative player transport loss. Presence removal, disconnect lifecycle events, and gameplay-binding teardown must account for retained edge liveness and replacement registration so a successful hidden rebind neither publishes a false disconnect nor leaves the resumed player absent.

Game Session treats Redis Coordination and Cache/Rate-Limit roles as separate concerns:

- All tick, lock, timer, retry, and session coordination keys live on Coordination Redis and are accessed only via the Lua Script Registry and shared key builders.
- Game Session code that runs inside the tick engine, including the tick scheduler, staging/commit flows, and lease management, never reads or writes Cache/Rate-Limit Redis directly.
- Cache lookups and invalidations remain encapsulated inside domain services, which own correctness and treat caches as performance hints only.

### Redis role and prefix details

- Coordination prefixes are reset-tolerant in line with [Redis Reset & Recovery](../../system-architecture-redis-reset-and-recovery.md), except for reset-sensitive gameplay session bindings under `session:game:*`. That document owns reset lifecycle and session policy; Game Session retains only local consequences: the canonical session record is the policy-selected binding, while derived gameplay indexes reconcile independently under either policy. Account token and generation authority remains outside session policy. Game Session’s coordination design must therefore remain safe under the documented Redis tail-loss envelope rather than assuming perfect recovery of every transient coordination key.
- The canonical opaque `{tenantRegionTag}` is derived by the shared key builders from the full `<tenantId, gameInstanceId, regionId>` tuple. It is the region scope for lease, queue, timer, retry, pending, and lock keys below; key examples must retain `{tenantRegionTag}` rather than substituting a differently named or partial tag.
- Coordination ownership includes registered Lua-script access to prefixes such as:
  - `tick:{tenantRegionTag}:queue:<entityId>`
  - `tick:{tenantRegionTag}:pending`
  - `tick:{tenantRegionTag}:lock:<entityId>`
  - `timer:{tenantRegionTag}`
  - `retry:{tenantRegionTag}`
  - `tick-executor-lease:{tenantRegionTag}`
  - `remote:{tenantInstanceTag}:<entityId>` and related coordination prefixes listed in the [Redis Cheat Sheet](../../system-architecture-redis-cheatsheet.md)
- `remote:{tenantInstanceTag}:<entityId>` derives `{tenantInstanceTag}` from `<tenantId, gameInstanceId>` and remains a best-effort hint marker for cross-region follow-ups; durable follow-up state lives in PostgreSQL via the tick effect ledger and follow-up tables.
- During a cold start, Game Session must not recreate `tick:{tenantRegionTag}:meta` from the hot path unless the recovery boundary supplies explicit proof that the exact environment and deployment are a documented non-reset profile. Otherwise the scope remains fenced under [Redis Reset & Recovery](../../system-architecture-redis-reset-and-recovery.md#failover-vs-cold-start-vs-reset).
- Coordination keys must be constructed through the shared key builders and script-registry contracts rather than ad-hoc string concatenation in service code.
- Changes to Game Session Redis usage must also be reviewed against the [Redis Design Checklist](../../system-architecture-redis-design-checklist.md) in addition to the core Redis architecture docs.
- Game Session may rely on Cache/Rate-Limit Redis for read-side caches that help serve hot-path session views, most notably pre-rendered room LOOK aggregates under `view:room-look:<tenantId>:<gameInstanceId>:<roomInstanceId>:<sessionId>:<viewerContextHash>:<policyContextHash>:<readFenceHash>` as defined in [Redis Cache & Rate Limiting](../../system-architecture-redis-cache.md#key-naming-and-overwrite-expectations).
- `view:room-look:*` entries are Class B, TTL-only caches. They may become stale briefly, but gameplay correctness still comes from authoritative reads and tick execution rather than cache contents. The key must remain bound to the exact room, viewer/session, policy context, and applicable read-fence context; use the [canonical Class-B contract](../../system-architecture-redis-cache.md#canonical-viewroom-look-class-b-contract) for the fence-hash derivation and the uncached fallback when the complete fence is unavailable. Underlying world or entity changes do not require synchronous invalidation of these keys; recomputation happens on cache miss or TTL expiry, and correctness-critical flows must not treat the cache as authoritative.
- Cache prefixes must never be silently repurposed onto Coordination Redis, and new cache usage should be introduced only through the central cache-key catalog rather than ad-hoc per-service naming.
- Game Session must not read or write Social & Groups history caches such as `chat:say:*`, `chat:tell:*`, `chat:guild:*`, or `chat:account:*`. Chat history ownership stays behind Social & Groups APIs.

Crash recovery replays ticks stored in Redis using AOF persistence and the idempotent replay rules described in [Tick System and Runtime Design](../../system-architecture-ticks.md#crash-recovery-and-replay). Replication remains asynchronous, and Redis is treated as a volatile coordination layer rather than a durable source of truth.

When Redis becomes slow or unavailable, Game Session applies the graceful degradation and halt behavior defined in [Redis Architecture – Graceful Degradation & Redis Outage Policy](../../system-architecture-redis.md#graceful-degradation--redis-outage-policy) instead of buffering authoritative commands only in memory. If coordination state must be cleared or repaired, operators follow the scoped reset flows in [Redis Operations & Migrations](../../system-architecture-redis-operations.md) rather than issuing ad-hoc key deletions.

## Session Keys and Indexes

Every gameplay session record includes a `tenantId` identifying the owning tenant. At target, controller uniqueness resolves by `{tenantId, playableStateNamespaceId, characterId}`; the authenticated `accountId` is separately verified as binding-owner evidence for resumable admission. Server-derived `playableStateScope` is immutable for the playable-state namespace lifecycle; only the current `{gameInstanceId, regionId, regionEpoch}` runtime fence may change during replacement, and a scope change requires a new `playableStateNamespaceId`. Redis keys and database tables prefix the tenant value so sessions from different games remain isolated: tenant-scoped keys use the canonical `{tenantGameplayTag}`, while intentionally global account and issuer indexes use tenant-qualified members and their owner-defined account-wide or issuer-wide fences. The platform may enforce per-tenant resource quotas at this level so one tenant cannot exhaust cluster capacity. See [Multi-Tenancy](../../system-architecture-multi-tenancy.md).

Session state needed for reconnect recovery is stored under the physical key `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>`; that addressability does not make `gameInstanceId` part of the durable/resumable identity. Replacement rekeys or reads the target-instance record under the existing binding transition and separately validates the current runtime/region fence. This expiring record is not the sole liveness authority for a continuously connected player: the live transport plus its fenced region-local gameplay binding remain active while current authorization and the active-session lease remain valid. Passing `continuityBindingExpiresAt` atomically retires only reconnect eligibility and the expiring recovery record; it does not remove the live region binding or close an otherwise authorized socket. A later disconnect cannot recreate or resume that expired continuity episode. Every reconnect-record create/update/heartbeat/refresh uses an absolute, server-side expiry that preserves the earliest existing physical deadline and never exceeds `continuityBindingExpiresAt`; when the anchor has passed, the operation retires reconnect state and fails any resume attempt closed rather than issuing a zero-TTL success. The target split between active gameplay liveness and expiring reconnect state remains incomplete while current `sessionctx:*` storage conflates those concerns.

Current Game Session code also maintains a `sessionctx:*` Redis-backed session-context family for bootstrap and implementation-local lookup indexes:

- `sessionctx:session:<sessionId>:context` maps a transport session id to its current context.
- `sessionctx:<tenantId>:<sessionId>:context` stores tenant-scoped session context.
- `sessionctx:<tenantId>:identity:<gameInstanceId>:<characterId>:context` and `sessionctx:<tenantId>:identity:<gameInstanceId>:name:<characterName>:context` support current takeover and reconnect lookups.

Unauthenticated `sessionctx:*` entries may exist before `LOGIN`; they are bootstrap context only and must not authorize gameplay commands. Authenticated gameplay semantics still follow the `session:game:*` / region-binding contract in the Redis architecture docs. If this implementation-local key family is renamed or collapsed into `session:game:*`, the pre-auth vs authenticated distinction remains mandatory.

Game Session owns the live `sessionctx:*` family and applies only its local reset consequence: reset invalidates or rebuilds this bootstrap/lookup context and never preserves it. The canonical reset lifecycle and session-policy choice remain in [Redis Reset & Recovery](../../system-architecture-redis-reset-and-recovery.md#coordination-reset-model). Account owns the live legacy `session:auth:account:*` and `session:auth:tenant:*` projections; Game Session does not reset or repair them, and gameplay session policy does not change their Account-owned behavior.

Target-state Game Session maintains the bounded active-binding index families owned by [Session Behavior](../../system-architecture-session-behavior.md#session-and-identity-management). The local Redis key shapes are:

- `session:game:index:character:{tenantGameplayTag}:<playableStateNamespaceId>:<characterId>` -> `{sessionId, gameInstanceId, bindingGeneration}`; `playableStateScope` is binding evidence and is not part of the controller-uniqueness index key.
- `session:game:index:account:<accountId>` -> one intentionally global, account-wide generation-safe set of tenant-qualified `accountIndexMember` values across all tenants; each target member contains the complete `bindingRef`, positive `bindingGeneration`, and `accountIndexFence` defined by [Session Behavior](../../system-architecture-session-behavior.md#global-account-active-binding-index)
- `session:game:index:account-tenant:{tenantGameplayTag}:<accountId>` -> active `sessionId` set
- `session:game:index:tenant:{tenantGameplayTag}` -> active `sessionId` set
- `session:game:index:realm-grant:{tenantGameplayTag}:<grantScopeId>` -> active `sessionId` set for lifecycle-bound private/playtest grant-gated realms, where `grantScopeId` is the exact canonical `grant/v1` scope ID for the complete Account-owned tuple; public-production and unscoped bindings have no entry
- `session:game:index:issuer:{issuerIndexLayoutTag}:<issuerId>:<partitionId>` -> partitioned global issuer active-binding hash, using the immutable layout and `bindingRef` fields defined by the [Redis issuer-index contract](../../system-architecture-redis.md#issuer-active-binding-index) across all tenants

These indexes are derived gameplay projections, not preserved-session state or Account authority. Game Session is the target-state local writer and reconciler for them under the reset consequences in [Redis Reset & Recovery](../../system-architecture-redis-reset-and-recovery.md); affected tenant-owned indexes may be dropped and rebuilt under either explicit session policy, while the global account index and partitioned global issuer index require their separate account-wide or issuer-wide owner-defined coverage before replacement. A region/tenant parent may repair only its local binding consequences and consume a complete issuer-wide child or standalone issuer-wide recovery result; it may not claim issuer coverage from a local snapshot. Binding transitions use the owner-defined generation/fence and repair protocol; this service must not use wildcard scans or treat index presence as authorization. Missing or ambiguous index/coordination state fails closed for admission and reconnect, while local cleanup remains idempotent.

Gameplay session bindings persist the local identity and receiver-validation fields required by the owner contract:

- Controller binding identity is exactly `{tenantId, playableStateNamespaceId, characterId}`. The authenticated `accountId` is retained separately as binding-owner evidence; server-derived `playableStateScope`, the current `gameInstanceId`, applicable `regionId`/`regionEpoch` fence, session identity, binding generation, membership/grant freshness, and revocation/lease evidence are separately retained runtime and receiver-validation fields.
- Every authenticated gameplay binding must persist the complete canonical `schemaVersion=2` payload from [Session Behavior](../../system-architecture-session-behavior.md#session-and-identity-management), including exact token identity/times/generation, `issuanceFence`, the protected single-use Account `rebindHandle`, immutable continuity deadline, membership baseline, authority tuple, and complete outbox checkpoints. Shape validation is field-specific: scalar authentication fields retain their canonical scalar forms, while the membership baseline/maps, authority tuple, and checkpoint set require their exact object/collection shapes. A binding made non-resumable does not gain a reduced authenticated schema or become reusable evidence; fresh `LOGIN`/`PLAY` establishes a new complete binding.
- The raw `game-session-account-delegation` JWT remains process-local and is never persisted in a binding, log, metric, or trace. Gameplay-domain RPCs use concrete workload identity and typed `PlayerExecutionContext`, not a per-call player JWT.

Before restoring a binding, Game Session resolves the authoritative realm/pointer snapshot and looks up the durable controller identity `{tenantId, playableStateNamespaceId, characterId}`, retaining `playableStateScope` as server-derived binding context. It separately compares the stored authenticated `accountId` with current binding-owner evidence and validates the fresh current `{gameInstanceId, regionId, regionEpoch}` runtime fence where applicable; every controller-key component must match exactly, and a stale or caller-replayed namespace is rejected rather than used as a fallback. For same-character replacement takeover, Game Session first applies transfer-identity-bound temporary fences to new source input and affected region admission and reconciles already-admitted source effects under those fences. These preparation fences do not transfer controller authority: a definitive pre-CAS abort unwinds them idempotently before failure is reported, while an ambiguous result remains under same-operation reconciliation until commit or complete rollback is proven. Because canonical `session:game:*` physical addressability includes `gameInstanceId`, an initial tenant-local session/index CAS may publish the target-instance record and character-index candidate only as a provisional, non-admissible transition. Separate exact account-index, issuer-index/capacity, and region-lease bridge operations and readbacks durably acknowledge the same transition, session/runtime identity, and `bindingGeneration`; the final tenant-local session/index CAS exact-compares every required acknowledgement and is the controller switch, linearization, and admission point. Target commands remain blocked and old session/index/region state is not cleaned up until that final CAS succeeds; other source bindings retain the ordinary bounded drain, and missing proof waits or fails closed. Game Session also validates the immediate Account response, membership/grant scope, authority evidence, lease fence, and current routing/ownership before accepting or restoring the binding. Current `sessionctx:*` payloads and per-instance identity indexes omit the namespace components and do not prove this replacement handoff, so the complete persisted binding, lookup, and CAS remain implementation gaps. The exact controller-transfer protocol is canonical in [Session Behavior](../../system-architecture-session-behavior.md#namespace-scoped-controller-transfer-session-02); a failed or ambiguous replacement remains non-admissible and is reconciled or cleaned up idempotently.

This controller-transfer gate does not itself authorize private semantic-context restoration on a new client transport: that path still requires fresh `LOGIN`/`PLAY`, the exact current `resumeContextGeneration`, and durable proof that its context episode remains unterminated, as defined by [ADR 0134](../../decisions/adr-0134-bounded-durable-semantic-reconnect-context.md). Hidden same-type upstream rebind behind a retained healthy edge socket remains the separate bounded recovery path and does not repeat client `LOGIN`/`PLAY`.

The target transition's durable identity spans the target session record and character-index repair. A positive, monotonic `bindingGeneration` is established durably before the transition is admitted; the durable transition identity and `bindingGeneration` together form the crash-safe idempotency/version fence for reconciliation. After final admission, readers begin with the controller index and exact-match `{sessionId, gameInstanceId, bindingGeneration}` and refuse stale old-instance records. Recovery resumes or reconciles the existing transition by that durable transition identity and generation while its candidate remains non-admissible, rather than using an alias, blind delete/create, or scan. This is target behavior; current `sessionctx:*` and per-instance indexes do not yet prove it.

## Tick Coordination and Lease Ownership

Game Session acts as the authoritative tick executor for each `<tenantId, gameInstanceId, regionId>` region scope it owns:

- It participates in region leadership using the Redis lease key `tick-executor-lease:{tenantRegionTag}` described in [Redis Architecture](../../system-architecture-redis.md#region-leadership-and-tick-executor-lease).
- While it holds the lease for a region, it is the only instance allowed to consume commands from that region’s queues and timers, drive `tick:{tenantRegionTag}:pending`, and issue tick-scoped gRPC calls on behalf of that region’s commands.
- On crash or deliberate handoff, another instance acquires the lease and resumes tick processing from Redis using the epoch-scoped `(regionEpoch, tickId)` timeline and EffectId/effect-guard rules from the tick-system design.
- Tick execution correctness must not depend on process-local executor memory surviving restart. Lease acquisition, staged tick state, retry metadata, and resumable session bindings are all externalized specifically so another Game Session instance can continue work from shared state.
- **Target state:** The executor monitors mode-aware `tick_execution_time_ms_p99{scope_class,tick_mode}` and selects `tick_lock_ttl_ms{scope_class}` for `tick_mode="normal"` or `solo_lock_ttl_ms{scope_class}` for `tick_mode="solo"`. A repeated over-TTL class-level signal is for detection and escalation only; it does not identify or classify an individual region. The executor resolves the exact region and current health from authoritative runtime-health/control-plane records before reducing tick fan-out, marking a region degraded, halting new ticks, or rejecting new commands for that region until operators intervene.
- Changing `tick_interval_ms` is not part of this in-place degradation path. Any live cadence change that alters timer ordering must run as an epoch-bumped maintenance operation with pause, timer re-derivation, and resume on the new `regionEpoch`, as defined in the tick and scaling docs.
- The staging Lua script only moves a bounded number of commands each tick, governed by `GAME_TICK_MAX_COMMANDS`, so one player cannot starve others. Commands marked `requiresSoloTick: true` are dequeued into isolated ticks so expensive operations such as runtime procedural generation do not share time with normal actions.
- Each tick-staging or entity-lock-acquiring Lua invocation uses a registered script governed by [ADR 0074](../../decisions/adr-0074-one-entity-lock-per-redis-script.md), acquires at most one entity lock, and fails closed if the operation would require more. Multi-entity correctness is enforced by one owning PostgreSQL transaction when the invariant is co-located, or by durable effect/workflow legs with [ADR 0076](../../decisions/adr-0076-failure-class-specific-durable-tick-retries.md) retry and reconciliation when authority is split. Redis locks are coordination only: Game Session does not assemble entity lock sets or use Redis rollback as a transaction boundary. Each retryable outcome maps to ADR 0076's declared failure class, whose policy owns its deterministic cadence, attempt and age bounds, and exhaustion disposition; only authoritative pre-dispatch lock contention uses capped exponential tick backoff. An unstaged command may surface an explicit retry-budget failure, while a staged or ambiguously dispatched effect remains unresolved for owner reconciliation, dead-letter, quarantine, or verified terminal evidence rather than being logged as permanently unapplied merely because automation exhausted.

These degraded and halt transitions follow the same thresholds and policies captured under [Redis Architecture – Operational SLOs & Alert Thresholds](../../system-architecture-redis.md#operational-slos--alert-thresholds) so operators and implementations share a single set of red lines for coordination health.

For `DROP` and `PICKUP`, Game Session acquires the actor lock keyed by the complete gameplay scope, including `regionId`, and `actorEntityId`, captures the current `(regionId, regionEpoch, executorFence)` from its durable region-status snapshot after authority validation, and durably records an in-flight barrier keyed by the existing scoped root identity `(tenantId, gameInstanceId, EffectId)` and bound to the actor, `regionId`, `RoomInstanceRef`, epoch, fence, and canonical immutable `requestDigest` before World validation. `regionId` propagates unchanged through World validation and any Game Logic re-resolution and is checked with the same root `EffectId` and unchanged `requestDigest` at Entity commit. It owns lock/retry orchestration, renews the actor-lock lease through Entity commit acknowledgement, and invokes Game Logic to re-resolve stale evidence under the same root `EffectId`, preserving that `requestDigest`; Entity verifies the attestation, guard, and `requestDigest` at local commit. A changed request is rejected rather than reusing the root. Lock-renewal failure, owner crash, or fence change fences the old orchestrator and leaves the barrier reconciliation-required. Handoff/recovery may reconcile the exact root but MOVE admission must pass the same actor lock/barrier gate and cannot authorize a conflicting move merely because Redis lock state expired; a later valid `MOVE` is allowed only after terminal barrier evidence. The detailed local-transaction and proof contract is in [Transaction Strategies](../../system-architecture-transactions.md#drop-pickup-targeting-and-actor-fence-critical-section).

Tick coordination is region-scoped, not session-scoped. Tick queues, locks, timers, retry metadata, and `tick:{tenantRegionTag}:pending` use the `tick:{tenantRegionTag}:...` prefix described in [Redis Architecture](../../system-architecture-redis.md#tick-integration-resilience-locking-staging). Region keys follow region lifecycle and crash-recovery rules:

- `tick:{tenantRegionTag}:pending` is created without a TTL so it survives process crashes and failover.
- It is cleared only when the tick is successfully committed or an operator-driven recovery flow explicitly marks the tick as skipped/failed and removes the key.

Session shutdown therefore cleans up session keys but does not implicitly delete region-level tick coordination keys.

## Reconnection and Disconnect Handling

Game Session restores player sessions after disconnects and enforces single-session control as outlined in the [Reconnection Strategy](../../system-architecture-reconnection.md). For Telnet clients, it also consumes best-effort, at-least-once `NotifyDisconnect` events emitted by the TCP Proxy Service over an internal gRPC link and treats them as idempotent hints keyed by `<proxyConnectionId, disconnectSequence>` rather than a guaranteed source of truth.

Game Session persists the latest processed `disconnectSequence` per `<proxyConnectionId>` and ignores older or duplicate events so retry behavior at the proxy can remain simple while consumption stays idempotent. Any `{tenantId, gameInstanceId}` values coming from proxy-owned bootstrap metadata or future hidden MCP-carried smart-client hints remain advisory context that may be used for logging and audit, but they are not trusted as authorization claims or binding directives. Game Session still validates any game-instance ownership claims against Redis and its authenticated session state before rebinding the transport. **Current implementation gap:** the live Redis sequence-dedupe path fails open on Redis errors and is reset-loss-vulnerable; no current connection/generation binding guard runs before `NotifyDisconnect` presence or region-exit effects or `GameInstance` suspension. The live path therefore does not yet satisfy the target advisory safety contract; the eventual binding design remains unspecified.

Recent/offline account-presence state should preserve the last admitted routing bundle too. In target state, when live presence drops to recent presence after transport loss, takeover, or logout, the bounded recent-presence record keeps the last admitted `tenantId`, `gameInstanceId`, `realmId`, `worldSlug`, `realmSlug`, and `pointerVersion` so account-presence and friend-presence reads can continue to describe the last resolved durable realm target directly instead of collapsing immediately to a routing-less timestamp. The current selector-based record does not yet prove durable `{tenantId, realmId}` propagation.

Deliberate logout remains a different lifecycle from transport loss. `LOGOUT` must not be acknowledged until durable termination of the current private semantic-context episode and its exact `resumeContextGeneration` evidence are committed; that evidence immediately makes the episode non-replayable and removes the session's reconnect-oriented replay and restore eligibility. Restoration and cache rebuild check that durable episode evidence while physical context deletion may complete asynchronously. It retires the live gameplay presence row, records bounded recent-presence disconnect disposition as deliberate logout, and routes gameplay-bound runtime shutdown through the shared termination seam instead of preserving a reconnect-suspended gameplay shell.

Game Session also owns the canonical live gameplay-presence substrate rather than treating authenticated session context as an online-presence proxy. The bounded live presence record contains tenant/game-instance/account/character identity, current role bucket for `WHO`, explicit-AFK state, accepted-command activity, meaningful-gameplay activity, and the admitted routing bundle used by later account/friend presence reads. It does not resolve, cache, or transport profile visibility policy. Player-facing `WHO` is scoped to the current game instance and reads this presence substrate directly, while later social consumers use the same substrate plus bounded recent-presence handoff and Account-owned policy instead of rebuilding online/offline truth from raw Redis session shells.

## Script Patch Version Pinning and Rollback (target-state contract)

Each running game instance has durable pin state alongside its `runtimeVersion`, represented by the nullable `{scriptPatchVersion, scriptPinEpoch}` pair and owner-bound `controlPlaneRequestId`. The pair is exact when present; semantic `UNPINNED` requires all three owner fields—`scriptPatchVersion`, `scriptPinEpoch`, and `controlPlaneRequestId`—to be absent for a never-pinned instance, while partial or unavailable state fails closed and is never `UNPINNED` or represented by a sentinel. Game Session is the sole authority for this current-pin state and the live `script_pin_operation` immutable request/result ledger supplies current atomic mutation-history rows for pin and rollback mutations. Bounded rollout-history readback, complete history fields, and focused proof remain gaps. Both requests require an explicit tagged `expectedCurrentPin` precondition: exactly `UNCONDITIONAL`, `EXPECT_UNPINNED`, or `EXPECT_EPOCH(scriptPinEpoch)`; a missing or unknown tag, or a missing epoch value for `EXPECT_EPOCH`, fails validation. `UNCONDITIONAL` performs no current-pin comparison only on the explicit `platformAdmin` break-glass repair branch, which requires the matrix's `privileged_control` authorization and still must satisfy coherent owner state, readiness, and every other validation; `EXPECT_UNPINNED` atomically requires all three current owner fields absent, and `EXPECT_EPOCH(scriptPinEpoch)` requires the exact current epoch. See [Rollout and Rollback](../../system-architecture-scripting-rollout-and-rollback.md#pin-compare-and-set-preconditions) for the owner semantics. Every control-plane request digest is scoped to the composite owner identity `(tenantId, gameInstanceId)`—with `tenantId` retained as the typed scope—and durably binds its request ID to a normalized digest covering every schema-bound input: operation kind, target game instance, exact script patch, actor/reason, complete expected-pin tag/value, and any preparation-attestation reference presence and identity. The server-derived resulting `scriptPinEpoch` and the idempotency key itself are excluded from the digest. Reusing the request ID with a different digest is an idempotency conflict with no pin mutation or epoch advance, while an exact retry returns the stored result. A valid expected-pin mismatch is a deterministic, non-mutating stored failure; concurrent callers are serialized by the authoritative `game_instances` row lock and row-version CAS. The committed result returns both previous and resulting exact epochs.

- Instance-bound gameplay/runtime event ingress to Automation includes the exact current patch and epoch so script evaluation is tied to the authority selected for the instance. Tenant-readiness `onLoad` runs before an instance pin exists and instead carries only its candidate `scriptPatchVersion` and declared pre-pin readiness identity; it omits `gameInstanceId`, `scriptPinEpoch`, and other instance/runtime tuple fields, and cannot emit gameplay work or effects.
- For local instance-scoped Automation commands, Game Session persists the complete captured `(scriptPatchVersion, scriptPinEpoch, controlPlaneRequestId)` tuple with the `gameplay_command` admission row and compares it with current authoritative `GameInstance` state before admission or duplicate replay and immediately before final gameplay mutation; displaced work is a fenced no-op/rejection without substituting a newer or locally cached patch. Tenant-readiness `onLoad` remains on its pre-instance-pin readiness path. The [canonical runtime-execution owner](../../system-architecture-scripting-runtime-execution.md#normative-target-contract) owns the tuple semantics; the [canonical cross-service scripting contract](../../system-architecture-scripting-contracts.md#2-script-work-item-vs-tick-command-boundary) owns the complete propagation artifact list and distinct-instance remote-follow-up source/target tuple rule.
- For target remote-follow-up delivery, Game Session revalidates source authority and race-safely captures the target instance's current exact tuple in the durable target delivery/claim. For an authoritative target semantic `UNPINNED`, the existing Game Session result transaction owns exactly one terminal `remote_followup_result` row under `resultId=remote-result:<followupId>`, with `outcome=ABANDONED`, `resultErrorCode=REMOTE_TARGET_UNPINNED`, canonical empty `resultPayloadJson={}`, and no result command or Automation event/work/command; it updates the existing follow-up/coordinator identities atomically. Exact retries return that row without work, while a changed scope, tuple/identity, outcome, or normalized result-authority fingerprint conflicts without overwrite. This uses existing persisted fields and identities, with no new digest column or outcome family. `authority_unavailable` persists no terminal result and remains non-admitted/retryable under the same follow-up identity after authority recovers. When source and target are the same game instance, including a cross-region follow-up, one authoritative tuple serves both roles.
- For each recognized player command, durable staging validates the required gameplay session and current runtime ownership row and reads the exact Game Session-owned current pin state, including `{scriptPatchVersion, scriptPinEpoch, controlPlaneRequestId}`, in that same staging transaction. Only an authoritative instance row with all three owner fields absent (`UNPINNED`) means that no script is configured: in that case the transaction creates no `onCommand` outbox/event record and no later tuple is synthesized. When an exact pin exists, it creates one retryable/idempotent `onCommand` outbox/event record keyed by the durable command/event identity; same-identity retries reuse that record, and the post-commit tick kick is only a wake-up/retry hint, not the durability proof. A missing, unreadable, partial, or ambiguous pin-authority result is not `UNPINNED`; staging must retain/retry the command or reject it with bounded `pin_state_unavailable`, never silently suppressing the `onCommand` record.
- Scripting availability is not a gameplay admission dependency beyond the normal session and runtime-ownership checks: a scripting outage leaves the staged `onCommand` record retryable while ordinary gameplay and tick processing continue.
- Script-generated commands enter only through the canonical handoff contract. For plugin-originated binding-scoped work, final validation uses the exact tuple `(pluginId, pluginVersionId, bindingId, pluginActivationEpoch, lifecycleRevision)`. The activation epoch and lifecycle revision are execution-fence evidence, not child identity; Game Session enforces them at its owned boundaries and fails closed when any field or its authoritative lifecycle/policy evidence is missing, unavailable, stale, changed, or mismatched. Automation remains the plugin lifecycle and policy authority, and plugin-only changes do not advance `scriptPinEpoch` but do advance the independent lifecycle fence as defined by ADR 0119.
- At final execution, any command/work referencing a revocable component, including embedded/core-script and plugin-backed work, carries the applicable component-revocation security-policy fence. Game Session validates current applicable evidence immediately before gameplay effects; missing, stale, unavailable, or mismatched evidence fails closed and records the established bounded component/authority disposition. Plugin-backed work additionally carries the independent `pluginActivationEpoch` and `lifecycleRevision` fences; neither lifecycle fence substitutes for the other or for component policy.

For the plugin lifecycle, Game Session maintains a local versioned projection of Automation-owned `(tenantId, gameInstanceId, pluginId, pluginVersionId, pluginActivationEpoch, pluginState, lifecycleRevision)` state and, while one exists, its pending-transition evidence including nullable `pendingVersionId`, target state/epoch, reserved `targetLifecycleRevision`, request identity/digest, and exact fence-install acknowledgement. Projection updates use an atomic lexicographic compare-and-set by `(pluginActivationEpoch, lifecycleRevision)` only for projection-write ordering; that ordering is not an admission or recovery comparison. Projection evidence is usable only within the owner-defined bounded freshness/expiry window; missing or expired evidence fails closed and triggers owner reread/reconciliation outside the tick path. Automation admission and recovery validate current Automation-owned lifecycle/policy evidence together with a bounded-fresh observation of the authoritative Game Session script-pin tuple; missing, stale, or contradictory evidence fails closed. The Game Session tick path uses only its latest accepted local Automation projection and never makes a synchronous Automation call. Admission and recovery first require exact `pluginActivationEpoch` equality with authoritative current state, then apply the state-specific revision rule: final `ENABLED` execution requires the exact current lifecycle revision, while a same-version/same-epoch `DRAINING` projection may allow only already-admitted work whose winning admission/fence CAS durably committed the immediately preceding `ENABLED` revision before the Automation-owned durable `DRAINING` admission barrier was created. The projection/admission evidence must bind that durable barrier's Automation-owned identity and the ordering evidence that the winning CAS preceded its creation; missing, contradictory, or unverifiable barrier identity/order evidence fails closed. The evidence must bind the same exact plugin version and activation epoch; mere observation or capture, or a winning CAS after barrier creation, is insufficient. Lower or reordered tuples cannot overwrite newer projection state, and contradictory equal tuples are rejected. Each successful lifecycle transition that changes the executable activation or containment state must first install the exact target state and tuple through an idempotent Game Session fence-install control command and durably acknowledge it before Automation admits the new activation or reports containment complete. It never accepts an arbitrary lower revision, and non-executable or epoch-advancing transitions provide no predecessor exception. `PluginVersionRuntimeStateChanged` is an advisory owner-committed notification and is never this barrier; consumers reread the owning service after loss, delay, duplication, or contradiction.

Control-plane operations that change the pinned patch are admin-only and idempotent. Their required request/response fields are specified in [Scripting Control Plane API](../../system-architecture-scripting-control-plane-api.md), the associated event contracts are specified in [Scripting Control Plane Events](../../system-architecture-scripting-control-plane-events.md), and the Game Session API surface is represented in `protos/game-session/v1/game_session_service.proto` under `GameSessionControlPlaneService`. The live ledger supplies current atomic mutation-history rows; bounded paginated rollout-history readback and complete history fields remain gaps. Automation projections and notifications are accelerators/diagnostics only.

The shared Game Session-owned promotion/rollback workflow is an epoch-fenced pin transition. Game Session owns its durable workflow, immutable `operationKind`, convergence deadline, and `PIN_CONVERGENCE_TIMEOUT` transition/event; the complete ordering and recovery contract is defined in [Rollout and Rollback](../../system-architecture-scripting-rollout-and-rollback.md#pin-transition-orchestration-state-machine-required). Candidate preparation occurs while the current tuple remains active. Before the serialized commit boundary, Automation must pause new script admission for the affected scope and keep it paused through exact-artifact observation, schedule reconciliation, and convergence; at that boundary, Game Session advances the epoch. Routine pin transitions do not pause unrelated player commands or gameplay ticks. Cancellation and purge of old work are bounded asynchronous cleanup, not the correctness barrier. A full tick pause is reserved for a declared unfenced effect family, migration, or compatibility transition that cannot enforce the final `scriptPinEpoch` fence; the exceptional workflow identifies the smallest complete gameplay scope and proves quiescence before mutation.

For cross-service invariants, see [Scripting Contracts](../../system-architecture-scripting-contracts.md).

## Durable Command and Effect Execution

Game Session now has a real current-boundary durable gameplay execution seam instead of stopping at queue staging:

- accepted gameplay commands persist a durable command ledger row with both a human-safe sanitized text projection and the canonical raw command payload used for later execution;
- the tick runtime stages Redis queue work into durable `tick_batch` / `tick_effect` rows before drain commit, including the current-boundary selected-work manifest, expected effect count, and manifest digest on the batch row;
- after drain commit, Game Session resumes from any durable `DRAINED` effects for that queue boundary and executes the supported command families from the ledger itself rather than assuming Redis drain already implies terminal gameplay work;
- drained effects re-check the durable runtime owner row before application. If the batch fence is stale, unapplied drained effects are marked `ABANDONED`, their durable commands are requeued for a fresh fenced batch, and the old executor does not invoke the effect handler.

The live ledger does not yet prove the target retention boundary. Game Session owns cleanup for its command receipts, batches, effects, manifests, and its `tick_effect` ledger/projection. Each domain service owns its participant guards and local cleanup; Game Session retains cross-service blocker references and safe-watermark consequences until those owners provide the evidence that permits ledger cleanup. The family-specific application of [ADR 0163](../../decisions/adr-0163-service-owned-retention-classes-with-cross-service-safety.md) is:

- `gameplay_command` is the retry/idempotency receipt keyed by `(tenantId, gameInstanceId, commandId)`. Its compact target receipt preserves the stable command identity, request fingerprint/digest, terminal outcome, and required lineage through every supported client and internal retry/reconnect/replay/restore/reconciliation horizon. It is eligible only after the target command status is terminal (`ingressStatus=TERMINAL`, as defined by the [Ingress Deduplication Store](../../system-architecture-tick-execution-flows.md#ingress-deduplication-store-required), with its `executionOutcome`/`gameplayResult` and applicable failure pair), no tick, remote-follow-up, or reconciliation path can reference or resurrect it, and the applicable safe watermark covers those horizons. The current table has `command_id`, execution/result fields, timestamps, and source-lineage columns, but does not yet expose the complete target ingress-status/request-fingerprint shape.
- `tick_batch` is recovery/reconciliation lineage keyed by `tickBatchId` and, in target state, the unique coordinates `(tenantId, gameInstanceId, regionId, regionEpoch, tickId)`. It is terminal only at the batch's terminal outcome after every related effect and source claim is terminal or reconciled. Any nonterminal, inconsistent, quarantined, or inconclusive effect/source claim, or any supported replay/restore/reconciliation reference, blocks deletion; the safe watermark must cover the batch's remaining recovery horizon. The current table persists `tick_batch_id`, scope/fence, status, expected-effect count, and manifest digest/payload, but does not yet enforce the target coordinate uniqueness.
- `tick_effect` is Game Session-owned recovery lineage and the target ledger projection for participant evidence. Its target identity includes the root effect, typed operation, exact runtime scope, tick coordinates, and target aggregate; the target terminal set is the closed `APPLIED`/`ABANDONED` set defined by the [Tick Effect Ledger and Replay Guarantees](../../system-architecture-tick-failures-and-operations.md#tick-effect-ledger-and-replay-guarantees), with `ABANDONED` requiring durable proof that the effect was unapplied. Missing, extra, partial, conflicting, or inconclusive participant evidence blocks cleanup, as does any producer retry/replay/restore/reconciliation reference; the safe watermark applies only after each domain owner’s guard/recovery horizon closes. The current table has `effect_id`, batch/command references, operation/target descriptors, status, and timestamps, but does not yet prove the complete target participant projection.
- The selected-work manifest is batch-bound recovery lineage, identified by its `tickBatchId` and sealed manifest digest. It remains required until the batch, all selected source claims, and related effects are terminal and no supported replay or restore can use it; unresolved source claims or effects block cleanup regardless of age. The current `tick_batch` row stores `selected_work_manifest_digest` and `selected_work_manifest_json`; payload minimization may occur earlier only after replay, investigation, and governance no longer require the content.
- Participant guards are target-state evidence owned and cleaned up by each domain service, not a claim that a dedicated current Game Session guard table exists. Each expected owner-local guard projection must retain the complete root-effect/typed-operation/runtime-scope/target identity until all producer retry, duplicate-delivery, replay, restore, and reconciliation paths are beyond its safe watermark. Any missing or contradictory projection, nonterminal effect, or still-addressable logical action blocks cleanup; Game Session retains the linked blocker/reference and does not make its `tick_effect` ledger eligible until the owning service's evidence and watermark permit cleanup.

Across all five families, age or a terminal-looking timestamp is insufficient: deletion requires the family-specific terminality predicate, no blocking reference, and the applicable safe watermark. Exact durations and cleanup mechanics remain deployment policy owned by the [Scaling Runbook](../../system-architecture-scaling-runbook.md#data-retention-and-high-churn-tables); implementation and proof status remains tracked in [Shared Runtime Contracts and Persistence](../../../project-management/implementation-tracking/shared-runtime-contracts-and-persistence.md).

The first migrated command families are movement plus the first item/equipment/container mutation surface:

- built-in movement input now enqueues durably instead of performing the current Game Session room-binding/projection update directly in the dispatch handler; World-authoritative character location and occupancy mutation remains unimplemented;
- movement execution reuses the shared move-planning logic to preserve player-visible semantics, but `MoveCommandHandler` no longer exposes a public synchronous session-write path and the current Game Session room-binding/projection update now flows through one dedicated domain-local replay seam keyed by `effectId`; this is not the World-authoritative location/occupancy mutation and does not prove the ADR 0054 operation/target/request-digest participant guard;
- duplicate movement application at this current seam converges to replay/no-op rather than a second room-binding update; changed reuse of an `effectId` is not proven fail-closed;
- player-visible movement output is delivered asynchronously through the same active-websocket plus screen-buffer-aware delivery path used for runtime recipient delivery;
- item/equipment/container mutation commands, including `GET`, `DROP`, `PUT`, `TAKE`, `WEAR`, and `REMOVE`, enqueue durably from the player-facing command path and execute from the durable post-drain effect executor before their player-visible outputs are delivered; `PUT`, `TAKE`, `WEAR`, and `REMOVE` are current domain coverage, while `GET` and `DROP` remain partial/blocked for ADR 0054 spatial correctness pending World `TargetingFactSnapshot` attestation/location-version propagation, the shared actor-lock/executor-fence critical section and durable barrier/handoff path, and stale-race proof;
- Game Session passes the durable `tick_effect.effectId` to Entity Management for those item/equipment/container mutations so duplicate downstream delivery can replay the stored domain response instead of applying the mutation again. This current `{tenantId,effectId}` identity is domain-local replay only, not the ADR 0054 participant guard bound to root effect, typed operation, target, and request digest; changed reuse is not proven fail-closed;
- `BLOCK` is the first transient action-state command on the same durable execution seam: Game Session stores/replays the durable effect, Game Logic routes `ApplyActorCondition`, and Entity Management persists the short-lived `blocking` active condition.
- read-only item views such as `INVENTORY`, `EQUIPMENT`, and `CONTAINER` remain direct view commands because they do not mutate authoritative gameplay state.

Pure view/meta commands may remain direct until there is a concrete reason to queue them, but state-changing gameplay families should not introduce new synchronous bypasses.

### Automation Command Admission

Fairness-critical automation enters gameplay through the same durable command/admission boundary as player commands, not through direct Automation & Scripting writes to `tick:*` Redis keys.

The current live `EnqueueAutomationCommandIfAbsent` implementation compares the complete set of immutable fields carried by its request against an existing `gameplay_command` row before returning a duplicate outcome. This includes the command payload and derived name/sanitized text, target, solo-tick and due fields, current routing bundle and region fence, all currently carried source/provenance fields, and the local Automation tuple `(scriptPatchVersion, scriptPinEpoch, scriptPinControlPlaneRequestId)`. The same comparison runs after an atomic insert loses an `ON CONFLICT` race; an exact match may return the existing bounded outcome, while any mismatch—including same-patch epoch drift or owner-request mismatch—returns `REJECTED` with `IDEMPOTENCY_CONFLICT` and does not enqueue. The persisted local tuple is compared again at final execution. Non-script player commands retain their existing admission path and do not acquire these Automation-only fields. Remote Automation follow-ups retain their separate legacy source/target path; this local boundary does not widen remote tuple behavior. See [Scripting Runtime Execution](../../system-architecture-scripting-runtime-execution.md#normative-target-contract) for the owner contract.

- Target-state handoff uses one complete Command-Handoff Identity for each emitted command: source `(tenantId, gameInstanceId, playableStateScope, regionId, regionEpoch)`, optional distinct target `(targetGameInstanceId, targetPlayableStateScope, targetRegionId, targetRegionEpoch)`, the `automationDispatchId` allocated and persisted at the first durable evaluated-descriptor/outbox commit when commands are emitted (not reserved before DSL evaluation), and deterministic `commandOrdinal` in canonical emitted-command order starting at `0`. Optional target fields are present only when the command is routed to a distinct runtime scope, including its own `targetPlayableStateScope` when applicable; same-instance handoffs keep every optional target field absent. Replay selection and child uniqueness use only the complete source runtime scope, any applicable distinct target runtime scope, `automationDispatchId`, and `commandOrdinal`; the parent Trigger Identity, `outboxWorkItemId`, and `scriptEventId` are correlation-only and are excluded from child uniqueness, deduplication, and replay selection.
- For a non-exclusive multi-handler event, each emitted child also retains, as non-identity evidence, the already-assigned `handlerSequence` and the event resolution record (or equivalent durable manifest) that identifies the complete ordered handler set, together with that handler's local command order. Game Session preserves and reuses those facts through durable admission, Redis materialization/recovery, retries, and final application; missing or contradictory sequence/completeness evidence fails closed rather than permitting higher-sequence application or arrival-order fallback. An authorized exclusive event carries Automation's sealed complete-resolution proof and sole-handler selection and creates no sibling admission or application; Game Session validates that sealed proof but does not independently resolve bindings or select the handler.
- In target state, Game Session records or reads a durable `gameplay_command` admission row through `EnqueueAutomationCommandIfAbsent` using that complete child identity before mutating Redis. Existing child dispatches are classified by durable state: only rows with proven Redis staging or downstream application return duplicate/no-op from the durable key; matching pre-Redis `ACCEPTED` rows enter materialization recovery and may converge to terminal non-applied only after durable proof that neither staging nor application occurred. Without a durable materialization marker or authoritative downstream evidence, the row remains indeterminate and retryable under the same identity. Same-scope dispatches validate and persist one current durable owner/epoch fence; dispatches with a distinct target read and lock the source and target owner rows in one stable canonical owner-identity order, validate each row against its source or target role, and persist both owner/epoch fences before Redis mutation. Missing or paused source/target ownership, or a mismatched source/target `regionEpoch`, returns a non-mutating rejection. The admission row retains the validated source and, when distinct, target owner/epoch fences so retry, Redis materialization, and final execution recheck the stored fences and fail closed on displacement. The row stores optional `dueTickId`, target entity, parent/work-item correlation fields, command payload, and current execution outcome. Target-state action execution persists a structured `GameplayActionOutcome` rather than relying on one free-form result string; Game Session renders its separate semantic presentation events without interpreting target-leg state itself.
- Conflicting payloads for the same key are validation failures and must not enqueue.
- Only after durable admission succeeds does Game Session invoke the region-lease Redis script that materializes the command into `tick:{tenantRegionTag}:queue:<entityId>`.
- If Redis enqueue times out or returns an unknown outcome after durable admission, a missing acknowledgement is not terminal evidence: Game Session reconciles materialization under the same durable child identity using a durable materialization marker or equivalent authoritative staging/downstream-application evidence before choosing an outcome. Only a proven pre-materialization failure with proof that no staging or application occurred may converge to terminal non-applied; otherwise the retry/idempotency path remains active. Redis queue contents are never the sole proof that the automation action existed.
- The complete source/target identity, `commandOrdinal`, and parent-correlation distinction remain target-state at the current boundary; the live request is narrower and must not be presented as proof of the canonical handoff contract. See [Scripting Runtime Execution](../../system-architecture-scripting-runtime-execution.md#current-implementation-status) for the current field gap and fallback diagnostics.

Current implementation/proof gap: the live recovery path still terminalizes stale `ACCEPTED` rows selected by `stagedAt IS NULL` as `LOST_BEFORE_STAGING`; `stagedAt IS NULL` is only absence of that marker and never proves that no Redis materialization or downstream application occurred. The current path has no durable materialization marker or authoritative downstream evidence for that decision. This ADR parcel does not change that code; target recovery must keep the row indeterminate/retryable under its original identity unless such evidence proves no staging or application, and target compliance and proof remain incomplete.

## Saga Participation

Game Session includes the `common-saga` module and its migrations as a normal service dependency; the optional element is the `SagaRunner` bean and the dependency check that uses it. The current start hook uses that check only to ping Entity Management and Game Logic when those clients and the `SagaRunner` are available; when the optional bean is unavailable, the check is skipped. The saga runner is not the authority for game startup or shutdown, does not coordinate World Management's lifecycle, and is not the cross-service lifecycle-compensation mechanism. Target start-failure cleanup follows Game Session's explicit local cleanup and fenced World lifecycle calls; current implementation status is that the failed-preparation call stops at the World `FAILED_PRE_ACTIVATION` state and does not yet initiate the durable termination and owner-cleanup flow. World Management's durable lifecycle row and epoch remain authoritative, with Temporal coordinating the restart-safe lifecycle workflow; Game Session consumes that evidence and performs its owner-local session-state consequences. See [Transaction Strategies](../../system-architecture-transactions.md) and [Database-Authoritative, Temporal-Coordinated World Lifecycle](../../decisions/adr-0123-database-authoritative-temporal-coordinated-world-lifecycle.md).
