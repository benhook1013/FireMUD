# Game Session Service API Contracts

## Target Control-Plane Summary

Target state makes Game Session the authoritative owner of region/tick coordination, each instance's exact `(scriptPatchVersion, scriptPinEpoch)`, and append-only script rollout history. Owner mutations are fenced and idempotent; Logging & Admin is the external operator ingress, and session front ends forward region work without writing lease-owned state directly. Authoritative owner reads gate script admission and convergence. See [Scripting Control-Plane API](../../system-architecture-scripting-control-plane-api.md#game-session-patch-pinning).

## Implementation Status

This document mixes live and target-state control-plane surfaces. Current live behavior is narrower:

- the shipped pause/resume control path is `PauseTicksForScope` / `ResumeTicksForScope` at the current `{tenantId, gameInstanceId}` runtime boundary;
- the shipped owner/status read is `GetRuntimeOwnershipStatus`, not yet the fuller target-state `GetRegionTickStatus` surface described below;
- canonical region pause/status remains incomplete for maintenance, reset, migration, and future scoped recovery. Any target region- or tenant-scoped reset must select exactly one explicit gameplay-session policy, `--preserve-sessions` or `--invalidate-sessions`; no preserve default is permitted. Cluster-scoped reset is invalidate-only, and pre-auth transport context is always invalidated or rebuilt. Routine online PostgreSQL backup does not depend on this control; player-facing restore remains blocked instead on the environment-wide cold-start quarantine, convergence, hardening, and proof gaps. See [Redis Reset & Recovery](../../system-architecture-redis-reset-and-recovery.md#coordination-reset-model) for the canonical reset policy.
- the live script-transition proto/runtime lacks the target tagged `expectedCurrentPin` precondition on pin/rollback requests, lacks `scriptPinEpoch` on `GetPinnedScriptPatchVersion`, lacks `observedScriptPinEpoch` on `GetGameSessionPinConvergence`, and does not expose target `GetScriptPinTransitionWorkflowStatus`; exact pinned-tuple convergence is unavailable until the epoch fields exist, and a missing epoch never matches a pinned target tuple. Semantic `UNPINNED` matching is defined separately below. Patch/request convergence, workflow-status, and epoch/history proof remain implementation gaps tracked in the [Game Session runtime and tick coordination tracker](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md);

Read the pause/status/recovery APIs below as the target-state contract unless the [Game Session runtime and tick coordination tracker](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md) explicitly records them as live.

For script transitions, the exact `scriptPinEpoch`, atomic pin/history commit, and bounded authoritative history read are target-state consequences. Target pin and rollback requests require the explicit tagged `expectedCurrentPin` precondition defined in the [Scripting Control Plane API](../../system-architecture-scripting-control-plane-api.md): exactly `UNCONDITIONAL`, `EXPECT_UNPINNED`, or `EXPECT_EPOCH(scriptPinEpoch)`, with the complete tag/value included in the normalized digest. Missing/unknown tags fail validation; a both-absent tuple for a never-pinned instance is valid semantic `UNPINNED` and matches only `EXPECT_UNPINNED`; a partial tuple is invalid owner state, cannot satisfy `EXPECT_UNPINNED` or `EXPECT_EPOCH`, and is rejected/fails closed even for an `UNCONDITIONAL` request. Missing or unreadable authority is not `UNPINNED` and remains unavailable. `UNCONDITIONAL` is only the explicit `platformAdmin` break-glass repair branch with the matrix's `privileged_control` authorization; it skips only current-pin comparison and does not bypass coherent owner state, readiness, or other validation. See [Rollout and Rollback](../../system-architecture-scripting-rollout-and-rollback.md#pin-compare-and-set-preconditions) for the owner semantics. A valid precondition mismatch is deterministic and non-mutating and follows the existing idempotency/history semantics.

## Service Interactions

Game Session communicates with other platform services exclusively via gRPC for gameplay-domain work. Player-delegated calls carry the typed unsigned `PlayerExecutionContext` defined in the authentication architecture, including the required gameplay scope for admission. Downstream services authenticate the concrete mTLS caller, enforce an exact RPC caller allowlist, validate context/request equality and domain scope, and reject client-supplied identity metadata. Routine gameplay calls do not use signed per-action attestations or a generic replay cache; mutations retain their owning command/effect/request idempotency.

For target gameplay forwarding, `PlayerExecutionContext` carries the server-resolved `{tenantId, playableStateNamespaceId, playableStateScope, gameInstanceId}` binding and, for region-scoped work, its `{regionId, regionEpoch}` fence as one context. Game Session forwards the namespace and scope unchanged and validates exact context/request equality on every downstream response or mutation result; it never accepts a caller-selected namespace or substitutes a current one after admission. The current context/forwarding wire is narrower in places and does not yet carry or prove this complete namespace-plus-fence tuple, so that path remains an implementation/proof gap and must fail closed on missing authority.

It also communicates game lifecycle changes to other microservices over gRPC so they can react to game instances starting, stopping, or changing runtime configuration.

## World Lifecycle and Admission Boundary

The World Management database row and monotonic lifecycle epoch are the admission authority under [ADR 0123](../../decisions/adr-0123-database-authoritative-temporal-coordinated-world-lifecycle.md). Game Session reads that owner state and epoch at lifecycle-sensitive boundaries; it does not use Temporal workflow status, worker memory, or a projection to admit an instance. `PREPARING` is non-admissible, `ACTIVE` is admissible only after the final version-state and owner checks, `FAILED_PRE_ACTIVATION` is terminal for admission, `TERMINATING` rejects new and reconnected bindings, and `TERMINATED` remains closed.

Game Session owns the realm admission pointer and cutover orchestration, not World lifecycle state. Replacement preparation and pointer swap carry the stable `playableStateNamespaceId` from [ADR 0122](../../decisions/adr-0122-stable-playable-state-namespaces-for-runtime-replacement.md); changing `gameInstanceId` does not authorize a new namespace or copy durable state. Cutover remains closed unless every owner reports fresh compatible state and the fenced pointer CAS succeeds. After a source swap, Game Session drains and closes source bindings, then asks World to progress termination; it reports a stopped runtime only after authoritative `TERMINATED` readback.

The prepared compatibility proof captures the target `gameInstanceId` at exact World lifecycle state `PREPARING` and its exact epoch as the activation precondition. Game Session then asks World to perform the owner-database `PREPARING -> ACTIVE` lifecycle CAS against that precondition; World returns the resulting exact `ACTIVE` state/epoch, which Game Session persists in the durable cutover execution/result. Before the admission-pointer CAS, Game Session rereads World authority and requires that same `ACTIVE` state/epoch. A changed state/epoch invalidates execution and preserves the prior pointer. The pointer CAS binds that durable `ACTIVE` proof and expected pointer version without making Game Session a lifecycle owner. The existing ordering remains: register source cleanup and its binding in the pointer-CAS transaction, then obtain authoritative post-swap pointer/readback confirmation of that registration and source binding before requesting World’s `TERMINATING` transition. This confirmation is not the all-owner terminal cleanup acknowledgement; World obtains those owner acknowledgements during its `TERMINATING` workflow before the final `TERMINATED` CAS.

## Session Front-End and Lease-Owner Routing

Game Session deliberately separates socket ownership from region execution ownership:

- The pod holding a player's WebSocket or proxied Telnet bridge is the session front-end for that gameplay session.
- Region-scoped command execution belongs to the current lease owner for the target `<tenantId, gameInstanceId, regionId>`.
- Session front-ends may authenticate, normalize input, manage connection-local state, and stream results to the client.
- Session front-ends must not directly stage or commit tick-owned Redis mutations for regions they do not lease.
- In the target-state model, when a command or follow-up targets a region owned by another pod, the session front-end forwards the request over internal gRPC to the lease owner and returns the resulting output to the client.
- Current-live fallback: the existing `EnqueueCommand` path resolves the session's current `{tenantId, gameInstanceId}` queue target and runtime ownership, persists the command, and uses the local Game Session tick-queue path. It does not expose a dedicated cross-pod forwarding RPC; if runtime ownership is missing or paused, admission rejects the command rather than performing an unfenced handoff.

### Forwarding contract

The internal front-end to lease-owner path is a **target-state** fenced gameplay contract, not a best-effort proxy hop. The live proto and Game Session implementation do not yet expose this forwarding RPC; the current-live fallback is the existing local `EnqueueCommand` admission path described above. [GR-1.1](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md) tracks that gap.

- Forwarded requests include the server-resolved `tenantId`, `playableStateNamespaceId`, `playableStateScope`, and `gameInstanceId`, plus `sessionId`, `characterId`, target `regionId`, command/action identifier, and a monotonic per-session sequencing token; the namespace and scope are forwarded unchanged from `PlayerExecutionContext`.
- Forwarded requests include the current region lease/epoch fence. Lease owners reject stale or missing fences with an application-level stale-lease response rather than silently executing.
- The session front-end preserves per-connection FIFO when emitting forwarded work. Cross-connection ordering remains undefined during takeovers as described in the reconnection and protocol-bridging docs.
- If the lease owner rejects a stale fence before execution, the front-end refreshes ownership and may retry the request once against the new lease owner when the request is still valid.
- If forwarding fails after the executor may already have started, the front-end must treat the result as ambiguous and use the normal structured command-failure or reconnect path; it must not re-issue potentially mutating work without an idempotency guarantee.
- All forwarded execution attempts and stale-lease rejections must emit dedicated metrics and traces so operators can distinguish edge socket health from region-executor health.

## gRPC APIs

- `Ping` – basic connectivity check.
- `StartSession` – spins up a game instance from a template-driven launch descriptor. Despite the name, this operates on game instances, not player gameplay sessions; gameplay sessions are per-player contexts backed by `session:game:*` keys.
- `StopSession` – stops a running game instance.
- `RestartSession` – restarts a stopped game instance.
- `EnqueueCommand` – adds a player action to the next tick's queue.
- `QueryState` – retrieves condensed session or player state for monitoring.
- `ToggleFeatureFlag` – updates runtime flags for a tenant.
- `PauseTicksForScope` – current scoped control-plane RPC for halting tick execution at the `{tenantId, gameInstanceId}` runtime boundary. The legacy unscoped `PauseTicks` method is not the canonical operator path.
- `ResumeTicksForScope` – current scoped control-plane RPC for resuming tick execution at the `{tenantId, gameInstanceId}` runtime boundary. The legacy unscoped `ResumeTicks` method is not the canonical operator path.
- `GetRuntimeOwnershipStatus` – current owner/status read for the shipped runtime boundary. `GetRegionTickStatus` is the fuller target-state per-region surface for maintenance, reset tooling, topology changes, and future scoped-recovery gates.
- `ValidateInstanceCutoverCompatibility` – resolves the target replacement launch descriptor, carries the stable `playableStateNamespaceId`, freezes any approved `remapSetId`, checks target Game Design proof, and returns the canonical multi-participant cutover-preflight report for a source instance and target version. The exhaustive classification and fail-closed unknown/mapping rules belong to ADR 0122 and the owner participant contracts.
- `PrepareVersionUpgrade` – persists one `prepared_version_upgrade` control-plane artifact for the target replacement attempt. At target state the artifact is bound to `{tenantId, playableStateNamespaceId, sourceGameInstanceId, sourceVersionId, targetGameInstanceId, targetVersionId}` and carries the namespace-bound durable summary required by [ADR 0122](../../decisions/adr-0122-stable-playable-state-namespaces-for-runtime-replacement.md): exhaustive owner family/classification/count/unknown evidence, the exact common state-family/owner-registry revision or complete owner-scoped catalog epochs, owner-validated and applied mapping state, participant freshness epochs, and the exact target World `PREPARING` lifecycle state/epoch captured by the compatibility proof as World’s later activation-CAS precondition. Game Session accepts a World `COMPATIBLE` result only when the report declares a supported capability and completeness, exactly matches that namespace/source/target tuple including the optional target instance when supplied, contains exhaustive family evidence bound to that registry revision or every applicable owner catalog epoch, carries current freshness and target-lifecycle evidence, and proves every required mapping was validated and applied; missing, unsupported, incomplete, stale, or mismatched reports fail closed. The normalized preparation request and its canonical `mutationDigest` bind only the known request and preparation inputs; the stored idempotent preparation result additionally binds the captured `PREPARING` proof. An exact retry reuses that artifact/result rather than recapturing a newer epoch under the same request identity. The current request/response fields are narrower and remain target-state where not live. `controlPlaneRequestId` makes retries reuse the same durable preparation instead of creating duplicates.
- `ExecutePreparedVersionCutover` – executes the prepared cutover workflow for one realm pointer. Game Session first revalidates the prepared summary's exact tenant, namespace, source/target instances and versions, every participant's owner evidence and freshness epochs, the exact state-family/owner-registry revision or complete owner-scoped catalog epochs, the owner-validated/applied mapping state, and the captured target World `PREPARING` state/epoch. Any family registration, ownership, or classification change since preflight invalidates completeness; stale, missing, contradictory, or changed evidence preserves the prior pointer and fails closed. Game Session then asks World to CAS that exact `PREPARING` state/epoch to `ACTIVE`; World remains the sole lifecycle owner. The durable execution/result captures World’s resulting exact `ACTIVE` state/epoch. Immediately before the pointer CAS, Game Session rereads World authority and requires the same `ACTIVE` proof; any state/epoch change fails closed. The execution request and canonical `mutationDigest` bind the known inputs, including `preparedVersionUpgradeId` and expected pointer version, but do not claim to contain the not-yet-issued `ACTIVE` epoch; that proof is bound by the durable execution result and its idempotent readback. The pointer-CAS transaction must also register the idempotent source cleanup work and its source binding before it can commit the pointer swap. The request identifies the realm, replacement `gameInstanceId`, durable `preparedVersionUpgradeId`, and expected pointer version; the remaining drain identity, deadline, fence, audit, and work-item fields are target-state unless noted as live below. After the pointer swap, the source-drain reconciler must obtain authoritative post-swap pointer/readback confirmation that the cleanup work and source binding were registered before requesting World `TERMINATING`; a sent or in-memory termination request is not sufficient. This readback is not the all-owner terminal cleanup acknowledgement, which follows through World’s `TERMINATING` workflow and is required before `TERMINATED`. The pointer CAS and cleanup-work registration commit atomically at the existing target boundary.
- `GetPreparedVersionUpgrade` returns preparation and execution state. Its target readback includes the namespace-bound durable summary, exact source/target instance and version pairs, participant family/classification/count/unknown evidence, the exact common state-family/owner-registry revision or complete owner-scoped catalog epochs, mapping validation/application state, freshness epochs, the prepared target World `PREPARING` proof, the execution result’s exact `ACTIVE` proof once issued, resulting pointer version, execution timestamp/request id, the normalized request digest, and source-drain evidence. An exact retry reuses the stored execution result and requires its same `ACTIVE` state/epoch for an unfinished pointer CAS; it does not substitute a later World epoch under the same request identity. Current readback is narrower and must not be treated as proof of the full ADR 0122/0123 summary. Command-rejection readback uses the persisted fence and authoritative clock and does not wait for reconciliation.
- The prepared-version cutover commit must also persist one idempotent drain-enforcement outbox/work item, keyed by `{tenantId, sourceGameInstanceId, sourceDrainId}`, in the same atomic database outcome as the pointer swap and deadline-armed source command-fence identity. The fence's `effectiveAt` is `sourceDrainDeadlineAt`; every acknowledgement and authoritative readback must carry and exactly match that same `sourceGameInstanceId`, and a missing, changed, or ambiguous source binding is not a successful reconciliation. A zero-duration cutover sets `effectiveAt` to the cutover commit and makes the work item immediately due; a non-zero drain leaves it pending until early-empty completion or its deadline. At or after the deadline, command handling rejects source commands from the persisted fence even if the reconciler is late. The Game Session reconciler records and reads back fence activation, confirms the authoritative post-swap pointer/readback evidence for cleanup-work registration and source binding, and then requests the source transition; only after that confirmation does it attempt one bounded update notice before closing sockets. Game Session owns that reconciliation, notice delivery, socket closure, and request delivery, but not the lifecycle transition. World alone owns the lifecycle epoch compare-and-swap, the transition through `TERMINATING` to `TERMINATED`, the all-owner cleanup gate, and the terminal lifecycle result. The bounded notice attempt cannot hold sockets open indefinitely.
- A dispatcher reconciles the durable work item after commit and retries delivery until source cleanup-work dispatch and the World lifecycle request are acknowledged by their authoritative readbacks. Lost responses, dispatcher restarts, and duplicate deliveries are recovered by the stable work-item identity, source instance binding, and acknowledgement state; delayed reconciliation does not delay deadline-based command rejection, and the cutover result is not reported as fully completed merely because an in-memory termination request was sent. Final `TERMINATED` readback is World’s authoritative all-owner cleanup result.
- `EnqueueAutomationCommandIfAbsent` – internal Automation & Scripting handoff API that records or replays a durable automation dispatch row keyed by the complete [Command-Handoff Identity](../../system-architecture-scripting-normative-contract-tables.md#command-handoff-identity-target-state) before staging the generated command into the normal Game Session tick queue. For non-exclusive fan-out, the target handoff also retains, as non-identity evidence, the already-assigned `handlerSequence` and the event resolution record (or equivalent durable manifest) identifying the complete ordered handler set, plus the handler-local command order; Game Session carries and reuses those facts through admission, retry/recovery, and final application, and fails closed on missing or contradictory sequence/completeness evidence rather than falling back to arrival order. An authorized exclusive event has only its selected handler and no sibling admission. The target `EnqueueAutomationCommandIfAbsentRequest` includes required `script_patch_version` and `script_pin_epoch` fields for the exact script tuple; the current proto/runtime carries `script_patch_version` but not `script_pin_epoch`, so this remains target-only. Only an already-staged or downstream-confirmed dispatch returns `DUPLICATE_NOOP` with the existing `commandId`; a matching pre-Redis `ACCEPTED` row is not a duplicate. Target behavior retries materialization from that durable row or converges it to a terminal non-applied outcome under the command-status rules. The current implementation returns `UNAVAILABLE` for an existing `ACCEPTED` row, and later recovery may mark stale accepted-but-unstaged work `LOST_BEFORE_STAGING`; it does not introduce a separate staging state. New same-scope dispatches validate and persist one current durable owner/epoch fence, while a dispatch with a distinct target reads and locks the source and target owner rows in one stable canonical owner-identity order, validates each against its source or target role, and persists both owner/epoch fences before Redis mutation. Missing source/target ownership returns `OWNERSHIP_UNAVAILABLE`, a stale source/target `regionEpoch` returns `STALE_TIMELINE`, and paused ownership returns `RUNTIME_PAUSED` without staging into Redis. `dueTickId` is still carried for scheduler/timer-derived automation, but immediate event-driven automation may omit it and rely on immediate enqueue semantics.
- At the Game Session-to-Automation handoff, Game Session first resolves `playableStateNamespaceId` and `playableStateScope` from the authoritative admission-pointer/world-lifecycle snapshot; neither Automation nor the caller supplies namespace authority. The owner-side admission/CAS validates the exact `{tenantId, playableStateNamespaceId, playableStateScope, gameInstanceId, regionId, regionEpoch}` tuple atomically before staging. The current handoff wire carries only a narrower tenant/instance/region fence in some paths and lacks complete namespace/scope plus active-instance proof, so this is an explicit current wire/implementation gap rather than a claim that the target handoff is live.
- `GetGameplayCommandStatus` – returns the durable command status by `commandId`, including accepted/staged/completed timestamps, attempt count, failure code/message, source type, automation dispatch/work-item ids, script/plugin provenance, target entity, `regionId`, `regionEpoch`, `dueTickId`, and the full remote origin/target game-instance plus region scope when the command has entered the cross-region follow-up path. That same status read now also exposes the durable remote follow-up contract itself when present: follow-up status, payload kind, requested command, solo-tick requirement, origin-source tuple, target entity/effect/failure summary, and trigger-script-event identity. The automation handoff fields `(tenantId, gameInstanceId, regionId, regionEpoch, automationDispatchId)` are a current correlation/filter-only subset, not a standalone target lookup identity. Target-state lookup, deduplication, replay, and fence diagnostics use the complete [Command-Handoff Identity](../../system-architecture-scripting-normative-contract-tables.md#command-handoff-identity-target-state), including `playableStateScope`, optional distinct target-scope fields, and `commandOrdinal`. The tuple is carried by the proto, but the live status resolver remains command-ID-based and does not implement complete target-identity lookup.
- `ListRemoteCommandCoordinators` – returns bounded remote coordinator rows for a tenant, filterable by persisted origin/target game-instance and region scope, state, linked `followupId`, script/plugin/dispatch/command provenance, the admitted routing bundle (`playableStateScope`, `worldSlug`, `realmSlug`, `pointerVersion`), linked follow-up target-leg traits (`targetEntityId`, `effectKey`, `payloadKind`, `originSourceKind`, `automationWorkItemId`), and first-class trigger-event identity (`eventType`, `scriptEventId`) instead of requiring point lookup by one coordinator id.
- `ListRemoteFollowups` – returns bounded remote target-leg rows for a tenant, filterable by persisted target scope, origin scope, follow-up status/id, script/plugin/dispatch/command provenance, the admitted routing bundle, current live payload/source classifiers (`payloadKind`, `originSourceKind`), direct target-leg identity/terminal fields (`automationWorkItemId`, `targetEntityId`, `effectKey`, `failureCode`, `requiresSoloTick`), and first-class trigger-event identity (`eventType`, `scriptEventId`) instead of requiring operators to scrape one entire target-region stream.
- `ListRemoteFollowupResults` – returns bounded origin-addressed remote result rows for a tenant, filterable by coordinator/follow-up identity, origin/target game-instance and region scope, outcome, script/plugin/dispatch/command provenance, the admitted routing bundle, and durable result identity/failure fields (`resultErrorCode`, `resultCommandId`, `automationWorkItemId`) instead of requiring operators to know one exact coordinator id up front.
- `ScheduleRemoteFollowup` – the `trigger_script_event` payload is a pre-handler event transport, not a request to persist a post-resolution handler Trigger Identity. The target `ScheduleRemoteFollowupRequest` preserves the separately named source exact pinned tuple as `source_script_patch_version` and `source_script_pin_epoch`; the current proto uses generic `script_patch_version` and lacks the epoch and source/target dual-tuple boundary. At target admission, Game Session revalidates source authority, race-safely reads and freezes the target instance's current exact tuple, and durably binds the source/target tuples and applicable event-scope evidence to the target delivery/claim. Retries reuse the stable delivery identity and both tuples; source or target displacement/conflict fails closed, unavailable authority remains non-admitted/retryable, and a target semantic `UNPINNED` result records a durable/replayable no-script delivery result without invoking Automation or creating an Automation event/work. When source and target are the same game instance, including a cross-region follow-up, one authoritative tuple serves both roles. Game Session persists and forwards the applicable event-scope ingress identity and owner selector/token evidence in its durable coordinator/follow-up row. For an entity-scoped follow-up, `targetEntityId` is part of that identity and target durable lookup/uniqueness; the current implementation lookup/index omits it, so this remains a target gap. Game Session retries and deduplicates delivery by its stable coordinator/follow-up identity; duplicate delivery preserves/reuses the existing Game Session local target-command/result consequences and coordinator↔follow-up/result links. It forwards that event-scope identity to Automation and does not require or fabricate handler-only `scriptId`, `pluginId`, `pluginVersionId`, or `bindingId`. The current proto/storage and status-consumer surfaces remain narrower than the canonical event-scope and handler-manifest contract, while `readSnapshotToken` remains an owner-specific manifest input or correlation value rather than universal evaluation authority. The shared tuple-binding, event-scope identity, and handler input-manifest rules are canonical in [Scripting Contracts version-fencing rules](../../system-architecture-scripting-contracts.md#3-version-fencing-rollback-safety), the [normative tuple-binding rules](../../system-architecture-scripting-normative-contract-tables.md#remote-follow-up-tuple-binding-normative), and the [handler input manifest boundary](../../system-architecture-scripting-contracts.md#4a-handler-input-manifest-boundary).
- For an authoritative target semantic `UNPINNED`, Game Session's existing result transaction persists exactly one terminal `remote_followup_result` row with `resultId=remote-result:<followupId>`, `outcome=ABANDONED`, stable `resultErrorCode=REMOTE_TARGET_UNPINNED`, canonical empty `resultPayloadJson={}`, and no `resultCommandId`; it updates the existing follow-up/coordinator identities in that transaction and creates no Automation event, work item, or command. An exact retry returns the stored row without work. A retry whose existing scope, source/target tuple or identity, outcome, or normalized result-authority fingerprint differs conflicts and cannot overwrite the row; the contract reuses those existing fields and adds no digest column or outcome family. `authority_unavailable` writes no terminal result and does not terminalize delivery, remaining non-admitted/retryable under the same follow-up identity after authority recovers.
- `GetPinnedScriptPatchVersion` returns the authoritative nullable `{scriptPatchVersion, scriptPinEpoch}` pair for `(tenantId, gameInstanceId)`, together with last-change metadata `controlPlaneRequestId`, `pinnedAt`, and `pinnedBy`, each nullable/inapplicable before the first pin for semantic `UNPINNED`. Both fields are present for a pin or both absent only for a never-pinned semantic `UNPINNED`; no sentinel represents an unpinned instance. It does not promise same-request retry snapshot semantics unless a future explicit snapshot contract is added.
- `GetGameSessionPinConvergence` – reports the persisted Game Session-side pin observation for `(tenantId, gameInstanceId)`: nullable `observedPinnedScriptPatchVersion` and `observedScriptPinEpoch` (both absent together only for a never-pinned semantic `UNPINNED`), `lastObservedControlPlaneRequestId` (absent/inapplicable only before the first pin), and `observedAt` (present for the observation). An unavailable or incomplete authority read is not `UNPINNED`. Automation treats its own convergence read as a projection and must not use it as a substitute for this owner read.
- `GetScriptPinTransitionWorkflowStatus` is the target-state authoritative, read-only Game Session workflow read selected by exact `(tenantId, gameInstanceId, controlPlaneRequestId)`; it returns the workflow operation, exact target tuple, state, current attempt generation/deadline, and applicable terminal timeout outcome/evidence. The current proto/runtime does not expose this read; the canonical contract is [Scripting Control Plane API](../../system-architecture-scripting-control-plane-api.md#getscriptpintransitionworkflowstatus).
- The Game Session control-plane read surface also exposes a bounded, stable-order, paginated rollout history for `(tenantId, gameInstanceId)`. Each immutable entry records the request identity, operation kind, nullable previous and resulting exact pin tuples, nullable `rolloutStatus`, actor/reason where applicable, outcome, and commit time; each tuple is either fully present or fully absent, with both absent meaning semantic `UNPINNED` only for a never-pinned instance. Once a syntactically valid request is accepted and its `controlPlaneRequestId` is bound to the normalized digest, a deterministic validation or preparation failure persists one immutable unsuccessful history attempt with equal tuples, including absent -> absent for an unpinned first-pin failure and no epoch advance; its `rolloutStatus` remains unset and the failure is represented by `outcome` and `reason`. A successful first pin may record absent -> present. An exact retry returns the stored result, while a different digest conflicts. A repeated request identity does not append another logical history entry. This history is authoritative even when Automation projections or notifications are unavailable. The canonical request/response, bounded `limit`, opaque `pageToken`, stable ordering, and first-pin tuple rules are defined by [`ListScriptPatchInstanceRolloutEvents`](../../system-architecture-scripting-control-plane-api.md#listscriptpatchinstancerolloutevents).
- The existing Game Session pin mutation may consume optional immutable Automation-owned candidate-preparation evidence bound to the exact `(tenantId, gameInstanceId, controlPlaneRequestId, targetScriptPatchVersion, tenant-READY artifact digest, current readiness revision, applicable policy revisions)`, but only as evidence. When preparation is selected or required, missing, mismatched, or stale evidence rejects; the commit revalidates the current tenant-`READY` state, artifact digest, readiness revision, and applicable policy revisions. A no-preparation request performs the equivalent commit-time checks. Game Session remains the sole pin/history authority, and deterministic failure leaves the previous and resulting tuples equal with no `scriptPinEpoch` advance under the history/idempotency rules above.
- `GetGameInstanceRuntimeState` now exposes the explicit `currentAdmissionPointers[]` list for the current runtime target. The legacy singular runtime routing fields (`playableStateScope`, `worldSlug`, `realmSlug`, `pointerVersion`) remain populated only when exactly one current admission pointer targets that runtime; when multiple pointers do, those singular fields intentionally fail closed to blank/unspecified values instead of implying one canonical reverse-mapped realm identity.
- `SetAdmissionPointer` represents `OPEN(gameInstanceId)` or `CLOSED`. Existing records require `expectedPointerVersion`; creation uses the equivalent of version `0`. Its transition matrix is: initial/no-record or `CLOSED -> OPEN(new)` uses fresh launch/activation proof and does not use `preparedVersionUpgradeId`; `OPEN(old) -> OPEN(new)` is the replacement cutover and requires `preparedVersionUpgradeId` plus namespace-bound `COMPATIBLE` preparation; `OPEN(old) -> CLOSED` closes admission without a version-upgrade artifact; `CLOSED -> CLOSED` and `OPEN(old) -> OPEN(old)` are exact idempotent/no-op cases and do not manufacture a preparation. For `OPEN(old) -> OPEN(new)`, Game Session rejects the swap unless the preparation still matches the current source and target instance/version pair and `playableStateNamespaceId`, contains fresh owner family/classification/count/unknown, mapping-validation/application, and participant-epoch evidence required by ADR 0122, and the durable execution result’s exact target World `ACTIVE` state/epoch matches a fresh authoritative World read. The prepared `PREPARING` proof authorizes World’s activation CAS; it does not by itself authorize the pointer swap. Initial and closed-to-open transitions have their own current lifecycle/version/owner proof and must not be treated as replacement compatibility proof.
- Admission-pointer requests and read/audit responses carry the runtime route version separately from catalog/policy revision. Public-production admission and first-join membership creation consume current catalog visibility/public-production facts with entitlement checks instead of inferring behavior from `realmSlug`; display-only changes do not become runtime cutovers.
- Admission-pointer audit/list responses now also expose the `preparedVersionUpgradeId` used by a cutover write so operator history preserves the same proof identity that the mutation validated.

Gameplay admission uses `JOIN_REQUIRED` only as a next-step response when fresh authority confirms that the selected target is publicly visible and public-production joining is allowed, while the caller's membership is absent. A public-production policy denial remains `PUBLIC_PRODUCTION_ADMISSION_DENIED`; unavailable, stale, malformed, or ambiguous authority uses the applicable unavailable or invalid-authority outcome instead. Private/playtest admission always requires an existing caller-bound membership, the current membership authority generation, and the applicable Account-owned realm grant; a grant never replaces membership. Current implementation is narrower: text `PLAY` enforces the current non-public realm grant, while current connect-token issuance does not validate that grant; target connect-token issuance adds the same fresh grant gate.

### ADR-0048 operator-write contract

**Target state:** every mutating operator RPC listed above (`StartSession`, `StopSession`, `RestartSession`, `ToggleFeatureFlag`, `PauseTicksForScope`, `ResumeTicksForScope`, `SetAdmissionPointer`, `ExecutePreparedVersionCutover`, and `PrepareVersionUpgrade`) requires the same durable request identity: `controlPlaneRequestId` plus the canonical `mutationDigest`. Account binds both values into the bounded operator authorization reference, and Game Session recomputes and validates the digest before execution. The owner durably records the request before execution and records a terminal result only after owner-specific commit proof; PostgreSQL-owned mutations commit domain state and result atomically, while Redis-backed projections use the durable claim, fenced mutation marker, and reconciliation contract in ADR 0048. A duplicate request carrying the same digest returns the previously committed result, while the same request identifier with a different digest returns `IDEMPOTENCY_CONFLICT` without applying either payload. A timeout must not create a new request identifier; Logging & Admin may use that identifier only for owner result lookup until the exact operation is reconciled. `FENCE_REJECTED` is non-rearmable and prohibits mutation redelivery. A retry against a current owner or fence is permitted only after the owner has durably recorded terminal `NOT_EXECUTED` proof for the original attempt; it uses a new `ownerMutationId` and a newly fenced attempt while retaining the external request tuple. After authorization expiry, reconciliation is read-only.

The current proto and admission-pointer mutation flow remain incomplete against this target. `StartSessionRequest`, `PauseTicksForScopeRequest`, `ResumeTicksForScopeRequest`, and `GameplayAdmissionPointerMutation` for `SetAdmissionPointer` carry `controlPlaneRequestId` but not `mutationDigest`; those operations must not be reported as ADR-0048-complete until the missing request-field propagation, authorization binding, owner-side digest verification, replay persistence, and focused proof converge together.

### gRPC Outcome Handling

Game Session follows the [canonical gRPC outcome and transport classification](../../system-architecture-grpc.md#outcome-and-transport-classification). A successfully produced command, control-plane, or read outcome uses its typed response contract; a failure that prevents producing that domain result uses canonical non-OK status with bounded structured details. Game Session preserves stable mutation request identities and reconciles ambiguous timeouts or transport failures before replaying work. Current handlers use a mixture of response-level `ErrorDetail` and transport failures, so exact per-RPC classifications and focused migration proof remain implementation gaps rather than a new service contract.

### External Operator Lifecycle Contract

**Target state:** External operator mutations enter through the Logging & Admin Service via Gateway. Logging & Admin authenticates the `control-ui` session, records the durable intent and audit context, and calls Account's canonical [`IssueHumanOperatorAuthorizationReference`](../account-service/api-contracts.md#operator-authorization-references) RPC; unattended automation uses the separately typed `IssueAutomationOperatorAuthorizationReference` branch under the restrictions that Account contract defines. Logging & Admin then forwards the opaque bounded reference unchanged with the exact typed action-family request, `actionFamilySchemaId`, `actionFamilySchemaVersion`, same `controlPlaneRequestId`, canonical `mutationDigest/v1` digest, and every scope, target, expected-version, mutation, and audit-reason field declared by that schema to the Game Session owner RPC over its exact mTLS workload identity. Only transport credentials and the authorization reference are excluded from the digest. If generation or privileged-predicate fields are copied outside the Account reference, they are non-authoritative context: Game Session must exclude those forwarded copies from authorization decisions and the mutation digest, or omit them entirely. Logging & Admin may forward the end-user `control-ui` JWT to Account only for reference issuance; it must never forward an end-user JWT or caller-asserted actor identity to Game Session. Game Session recomputes the digest from the exact schema pair and every declared digest input, then calls Account's `RedeemOperatorAuthorization` contract with the exact owner, action family and schema pair, scope, request identity, and digest. Account's returned bounded actor or automation-policy authorization projection is the sole authorization source; Game Session uses that Account-derived projection for audit while independently validating target-domain ownership, runtime fences, and owner-side idempotency. This target path is not currently routable and has no fallback external mutation route.

**Current implementation status:** The current OpenAPI surface exposes an owner-local `/sessions*` HTTP family. It uses the service-local control-plane auth boundary, direct edge exposure is denied, and no Logging & Admin external `/sessions*` family is currently available. These owner-local routes are not the canonical external operator ingress or player-admission contract.

### Service-Local HTTP Surface

Game Session owns the `/api/session/**` Gateway family, but the public gateway inventory exposes only `GET /api/session/ping`. The service-local endpoint inventory is:

- `GET /ping` – basic health check returning `"pong"`.
- `POST /sessions` – `target_not_currently_routable`; a current owner-local OpenAPI scaffold creates a game instance from a template-driven launch attempt, but it is not the player gameplay-admission seam and is not supported external operator ingress.
- `POST /sessions/{sessionId}/stop` – `target_not_currently_routable`; a current owner-local OpenAPI scaffold stops a running session, but supported external operator ingress remains unavailable.
- `POST /sessions/{sessionId}/restart` – `target_not_currently_routable`; a current owner-local OpenAPI scaffold restarts a stopped session, but supported external operator ingress remains unavailable.
- `POST /sessions/{sessionId}/refresh-roles` – `current_openapi_operator_surface`; this owner-local workload-authenticated route refreshes roles for an active session and is not an Account-authorization-reference mutation.

Use `/sessions/{sessionId}/refresh-roles` after updating an account's privileges so the session reflects the latest role assignments.

Direct external operator exposure of a mutating `/sessions*` route is forbidden unless the owning contract explicitly marks that exact route as bypass-safe and defines its auth class, audit behavior, and lease-owner forwarding rules in the same change.

#### Owner-side operator RPC classification

The gRPC owner methods `StartSession`, `RestartSession`, `StopSession`, `ToggleFeatureFlag`, `PauseTicksForScope`, `ResumeTicksForScope`, `SetAdmissionPointer`, `ExecutePreparedVersionCutover`, and `PrepareVersionUpgrade` are the target `internal_workload` operator RPC family. They accept the exact Logging & Admin mTLS workload identity and one opaque, short-lived Account-issued operator authorization reference for the bounded request, redeemed with Account; they accept no end-user JWT or caller-asserted actor authority. Once converged, every method uses the ADR-0048 request identity and result-replay rules above. `StartSession`, `RestartSession`, and `StopSession` additionally require reason and their target scope; each other mutating method requires the equivalent method-specific scope and precondition fields. Every owner obtains the authoritative actor projection from Account redemption and uses it for audit. Game Session still validates current domain ownership, admission/CAS or runtime-fence facts, and durable request idempotency before committing the owner result. `RefreshRoles` is also `internal_workload`, but uses only its exact allowlisted workload identity plus current session and Account role state because it is a role-refresh operation rather than delegated operator authority.

## Command Front Door Ownership

Game Session owns the gameplay session front door and the split between protocol-level system commands and queued gameplay work:

- System commands such as `LOGIN`, `LOGON`, `PING`, and lightweight state queries are fully owned by Game Session and may complete synchronously without enqueuing gameplay work.
- Gameplay commands such as `LOOK`, `SAY`, movement, and combat are validated and normalized by Game Session, then forwarded to the tick/gameplay path. Game Session does not re-implement gameplay rules for these commands.
- If a command would produce both immediate text and enqueue metadata, enqueue failure wins. Game Session returns a single `ERROR` response instead of reporting success and silently dropping gameplay work.

For the [ADR 0112](../../decisions/adr-0112-typed-bounded-gameplay-effect-extension.md) boundary, the wider typed command and target-plan behavior is target-state. Game Session is the single semantic admission point: it resolves the release-pinned command declaration, validates the player/session context, and admits the typed command into the appropriate tick. It does not resolve actor targets, evaluate effect predicates, or mutate actor state; those remain Game Logic and Entity Management responsibilities. Current implementation and proof remain narrow and incomplete; see the [Game Session Runtime and Tick Coordination tracker](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md).

For the player-visible line protocol and examples, see [`protocols.md`](./protocols.md).
