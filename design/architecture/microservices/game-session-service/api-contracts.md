# Game Session Service API Contracts

Player-facing controller binding and takeover are owned by [Session Behavior](../../system-architecture-session-behavior.md#namespace-scoped-controller-transfer-session-02), fresh-edge reconstruction is owned by [Reconnection](../../system-architecture-reconnection.md#client-reconnection-behaviour), and versioned output/late rendering are owned by [Input, Output, and Presentation](../../system-architecture-input-output-and-presentation.md#output-model). The APIs below record only Game Session's local control-plane and forwarding consequences; they do not duplicate those player-facing contracts.

## Target Control-Plane Summary

Target state makes Game Session the authoritative owner of region/tick coordination, each instance's exact owner tuple `(scriptPatchVersion, scriptPinEpoch, controlPlaneRequestId)`, and append-only script rollout history. The request ID is owner-grounded transition/readback evidence; the patch and epoch remain the execution fence. Owner mutations are fenced and idempotent; Logging & Admin is the external operator ingress, and session front ends forward region work without writing lease-owned state directly. Authoritative owner reads gate script admission and convergence. See [Scripting Control-Plane API](../../system-architecture-scripting-control-plane-api.md#game-session-patch-pinning).

## Implementation Status

`EnqueueAutomationCommandIfAbsent` and `ScheduleRemoteFollowup` currently fail closed at their authenticated internal receiving boundary with `FAILED_PRECONDITION` / `automation_admission_receiver_fence_unavailable`, before command, coordinator, follow-up, or queue mutation. The retained lower-level admission implementation does not prove the cross-service Automation admission-epoch fence required by [ADR 0106](../../decisions/adr-0106-epoch-fenced-script-rollback-without-routine-gameplay-pause.md). A separate receiver-fence successor must durably serialize installation against receiving admission, preserve exact retry outcomes, and prove that a handoff whose intent committed before an Automation pause cannot create live work under the displaced admission epoch afterward. This gate preserves ordinary gameplay APIs and does not claim the successor implemented.

Realm-catalog identity status: Game Session pointer and audit rows persist a separately advancing positive `catalogRevision` and stable UUID `realmId`/`playableStateNamespaceId`; player-facing catalog and runtime pointer projections fail closed when identity is incomplete or a tenant catalog is ambiguous. The control-plane `SetAdmissionPointer` and `ExecutePreparedVersionCutover` paths remain closed pending catalog-revision and durable-identity preconditions. The configuration-driven pointer initializer validates seed shape but does not write authority rows while World-owned lifecycle proof is unavailable; raw seed inputs do not establish that proof or an owner-validated initial bind. Current implementation and proof gaps are tracked in the [Game Session runtime tracker](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md).

Missing or unreadable authority is not `UNPINNED` and remains unavailable. `UNCONDITIONAL` is only the explicit `platformAdmin` break-glass repair branch with the matrix's `privileged_control` authorization; it skips only current-pin comparison and does not bypass coherent owner state, readiness, or other validation. See [Rollout and Rollback](../../system-architecture-scripting-rollout-and-rollback.md#pin-compare-and-set-preconditions) for the owner semantics. A valid precondition mismatch is deterministic and non-mutating and follows the existing idempotency/history semantics.

## Service Interactions

Game Session communicates with other platform services exclusively via gRPC for gameplay-domain work. Player-delegated calls carry the typed unsigned `PlayerExecutionContext` defined in the authentication architecture, including the required gameplay scope for admission. Downstream services authenticate the concrete mTLS caller, enforce an exact RPC caller allowlist, validate context/request equality and domain scope, and reject client-supplied identity metadata. Routine gameplay calls do not use signed per-action attestations or a generic replay cache; mutations retain their owning command/effect/request idempotency.

For target gameplay forwarding, `PlayerExecutionContext` carries the server-resolved `{tenantId, playableStateNamespaceId, playableStateScope, gameInstanceId}` binding and, for region-scoped work, its `{regionId, regionEpoch}` fence as one context. Game Session forwards the namespace and scope unchanged and validates exact context/request equality on every downstream response or mutation result; it never accepts a caller-selected namespace or substitutes a current one after admission. The current context/forwarding wire is narrower in places and does not yet carry or prove this complete namespace-plus-fence tuple, so that path remains an implementation/proof gap and must fail closed on missing authority.

It also communicates game lifecycle changes to other microservices over gRPC so they can react to game instances starting, stopping, or changing runtime configuration.

## World Lifecycle and Admission Boundary

Game Session consumes the exact authenticated authored-world receipt defined by [Game Design's source contract](../game-design-service/api-contracts.md#authored-world-source-registration-and-game-session-readback) before its own runtime catalog intake. The source client validates the separate read identity, complete tenant/world scope and both immutable digests; it does not create or update a catalog, select a runtime, or grant admission. Game Session alone persists the runtime association and must prove exact owner readback. A retained numeric Game Session tenant key requires its separately audited source association and current retained-row evidence, never Account's migration manifest or a guessed selector. Normal fresh intake is an automated owner handoff, while this candidate stays unwired until producer, receiver, creator authorization and catalog proof exist. Remaining implementation and execution limits are recorded in [Player Access and Session](../../../project-management/implementation-tracking/player-access-and-session.md).

### Authored-world source intake and durable readback

The separate [audited retained-tenant association](../game-design-service/api-contracts.md#audited-retained-game-session-tenant-association) uses this same Game Design-authenticated client channel but a distinct closed manifest and read method. The client checks the independent request echo, exact namespace/operation/tenant/key binding, complete evidence, canonical signature shape and recomputed digest. It does not persist a local retained association or prove the captured Game Session rows; that owner-fenced snapshot and durable receiver remain required before catalog use. The source digest and historical approval are never gameplay authorization.

The owner-local source intake, retained association, and command UUID schema slots are assigned to Game Session migrations V7.1, V8.1, and V9.1, after distinct parent migrations V7, V8, and V9. This source-tree ordering does not prove a prior deployment's Flyway history or retained-data readback. Before dependent paths activate, exact deployed history and owner-readback of retained rows/evidence must be established; unknown provenance remains unresolved, with no Flyway repair, out-of-order execution, identity casting, or data cleanup. See [runtime and data](./runtime-and-data.md#implementation-status) for the current gate.

Game Session's source intake binds its own stable non-nil UUID `intakeRequestId` to the complete immutable Game Design source receipt under the exact workload namespace. The intake service obtains that receipt through the authenticated Game Design source client using a separate read-attempt identity and verifies the requested source operation, tenant UUID and world selector. Before delivering response headers or content, the source client also checks the authenticated TLS leaf's single exact `spiffe://firemud/ns/<namespace>/sa/game-design-service` URI; a trusted CA or matching DNS name alone cannot substitute for workload identity. Missing, ambiguous, another-service or cross-namespace peers fail closed. A caller-constructed receipt, digest alone, Account migration manifest or unchecked transport is not a source authorization. Game Design remains the normative source owner; Game Session's stored copy is the exact consumed evidence, not a new authored selector issuer.

The owner transaction atomically persists the local non-nil UUID operation, immutable source evidence and tenant selector claim. Within a namespace, one tenant UUID has one `tenantSlug`, one `tenantSlug` has one tenant UUID, and each `(tenantId, worldSlug)` has one exact consumed source. Compatible additional worlds reuse the same tenant source claim; a conflicting tenant/world/source or changed request fails without partial claims. Exact retries return the original local operation and receipt without changing rows. The transient read-attempt ID is an authenticated response echo, not a replacement intake request or persisted registration field. Exact committed readback is non-mutating and checks the complete stored source and selector binding; it cannot allocate missing state or choose another candidate.

`game-session-authored-world-intake-request/v1` hashes, in order, the domain, canonical `intakeRequestId` and Game Design `evidenceDigest`. `game-session-authored-world-intake-receipt/v1` hashes the domain, canonical local operation UUID, exact local request digest and exact Game Design evidence digest. Each value is encoded in UTF-8 as its decimal byte length, a colon, then those bytes; results are lowercase `sha256:` SHA-256 values. Game Design's closed source codec independently verifies all source fields and both owner digests before either local digest is calculated. A local digest never replaces the authenticated source read or its exact scope checks.

This source intake records no numeric tenant alias, instance, realm, pointer, lease, membership, authority generation or admission. It does not attach a retained Game Session runtime row: that requires the separately audited association and exact retained-row proof. The normal authorized creation workflow may invoke intake automatically after its Game Design commit; the primitive is not a public creator API and cannot bypass Account-owned creator/terms authorization. Source receipts and selector claims remain immutable survivor evidence; cleanup or release requires its owner retention proof rather than an invented TTL. Runtime catalog and credential activation stay denied until their complete producer, consumer and live proof gates pass.

### Retained tenant identity snapshot and local association

Game Session owns the evidence behind `gameSessionEvidenceDigest` in [Game Design's audited association](../game-design-service/api-contracts.md#audited-retained-game-session-tenant-association). It captures an exact, declared identity projection of its retained rows, not a complete runtime backup or proof of historical lifecycle, effects or admission. The closed version-2 snapshot contains `schemaVersion=2`, the exact `targetNamespace`, canonical positive BIGINT decimal-string `legacyGameSessionTenantId`, and all six arrays below. Each array includes every row for that tenant, in ascending numeric primary-key order; the shared namespace uses its tenant primary key. Row objects contain exactly their listed SQL field names. SQL integer values are canonical decimal strings, UUIDs are canonical lowercase strings, booleans are JSON booleans, text is exact valid Unicode, and absent nullable fields are explicit JSON null. Each instance binds both its nullable retained numeric `owner_account_id` and nullable canonical `owner_account_uuid`; at least one must be present. Capturing those exact slots does not prove an association between them, authorize a guessed mapping, or make a retained numeric owner a canonical Account identity. No timestamp, display label, actor/reason or participant-result payload is reconstructed or asserted by this projection.

The owner encodes this closed object using RFC 8785 canonical JSON. The SHA-256 preimage consists of two UTF-8 segments, the exact domain `game-session/retained-tenant-identity-snapshot/v2` and that canonical JSON, each prefixed by its decimal UTF-8 byte length and a colon. The digest is lowercase `sha256:` plus 64 hexadecimal digits. Unknown fields, noncanonical values, duplicate or out-of-order rows, changed scope or digest, unsupported schema versions, and empty retained evidence deny use. There is no fallback to the unmerged version-1 snapshot. The separately versioned association request and receipt bind this exact snapshot digest without changing their own identity or retry contract. Every current pointer must refer to a captured instance of that same tenant, have complete realm/namespace UUIDs and an exact `SHARED` or `ISOLATED` scope; a SHARED pointer must match the captured tenant-shared namespace. Historical pointer events can survive their former runtime instance; they do not acquire missing realm, namespace, catalog revision or World lifecycle evidence through this capture.

Capture requires a non-read-only Game Session owner transaction at PostgreSQL READ COMMITTED. Before any source read it acquires one fixed-order `SHARE MODE NOWAIT` relation-lock statement for all six source tables. Those locks prevent concurrent insertion, mutation, deletion and truncation, including empty-range phantom inserts, and remain held through the local association commit or rollback. Ordinary reads remain possible. An existing writer causes immediate retryable capture failure, not a durable terminal receipt or an assertion of absence. This short, global source-write barrier is limited to the one-time retained-data association; it is not a per-request gameplay lock or an automated runtime quiescence policy. Operational and live use remain gated until the complete capture/receiver proof passes. A prior unlocked preview may prepare approval evidence, but only the receiver's fenced recapture can authorize first commit.

The local receiver authenticates and validates the exact Game Design receipt before entering the source-lock transaction; no source locks are held across a network call. It then recaptures the declared projection and requires its exact namespace, retained key and digest to match the approval. It atomically stores the complete immutable approval, snapshot and local operation with namespace-qualified one-to-one canonical UUID and retained-key claims, and reads back that exact result before returning. Changed input under the same operation or a conflicting claim denies without partial state. Exact retry and committed readback return the original evidence without recapturing or rewriting later source state; they are historical association proof only. Missing or contradictory readback remains unavailable. This owner-local primitive does not create a realm, pointer, lease, membership, grant or credential, and cannot activate a catalog or gameplay path.

The local stable non-nil UUID `associationRequestId` is distinct from Game Design's approval `operationId` and the transient authenticated read attempt. Its request digest frames the domain `game-session/retained-tenant-association-request/v1`, exact namespace, local request UUID, complete Game Design manifest digest and exact canonical signature, in that order. The local receipt digest frames `game-session/retained-tenant-association-receipt/v1`, the persisted non-nil local operation UUID, request digest, approval manifest digest and snapshot evidence digest. Both use the same UTF-8 byte-length framing and lowercase SHA-256 rendering above. Committed readback requires the exact local operation, request, namespace, canonical tenant UUID and retained key, and validates the complete stored approval and snapshot before returning; a transient read echo is never stored as either owner operation.

The World Management database row and monotonic lifecycle epoch are the admission authority under [ADR 0123](../../decisions/adr-0123-database-authoritative-temporal-coordinated-world-lifecycle.md). Game Session reads that owner state and epoch at lifecycle-sensitive boundaries; it does not use Temporal workflow status, worker memory, or a projection to admit an instance. `PREPARING` is non-admissible, `ACTIVE` is admissible only after the final version-state and owner checks, `FAILED_PRE_ACTIVATION` is terminal for admission, `TERMINATING` rejects new and reconnected bindings, and `TERMINATED` remains closed.

Multi-Tenancy owns the realm catalog, the canonical durable `{tenantId, realmId}` pointer identity and its routing/admission semantics, while Game Session is the sole runtime resolver, persister, and compare-and-set orchestrator for that resolved catalog and admission-pointer state; neither service owns World lifecycle state. Replacement preparation and pointer swap carry the catalog-bound `worldSlug`/`realmSlug` selectors, stable `playableStateNamespaceId`/`playableStateScope`, and, for private/playtest targets, the canonical lifecycle proof tuple `{playtestLifecycleId, playtestStateGeneration}` from [ADR 0122](../../decisions/adr-0122-stable-playable-state-namespaces-for-runtime-replacement.md); changing `gameInstanceId` does not authorize a new realm identity, namespace, or durable-state copy. Cutover remains closed unless every owner reports fresh compatible state and the fenced pointer CAS succeeds. After a source swap, Game Session drains and closes source bindings, then asks World to progress termination; it reports a stopped runtime only after authoritative `TERMINATED` readback. Public-production requests omit both playtest fields and reject supplied values.

The prepared compatibility proof captures the target `gameInstanceId` at exact World lifecycle state `PREPARING` and its exact epoch as the activation precondition, together with the applicable canonical lifecycle proof tuple. Game Session then asks World to perform the owner-database `PREPARING -> ACTIVE` lifecycle CAS against that precondition; World returns the resulting exact `ACTIVE` state/epoch and the same tuple, which Game Session persists in the durable cutover execution/result. Before the admission-pointer CAS, Game Session rereads World authority and requires that same `ACTIVE` state/epoch and exact tuple. A changed state/epoch or tuple invalidates execution and preserves the prior pointer. The pointer CAS binds that durable `ACTIVE` proof and expected pointer version without making Game Session a lifecycle owner. The existing ordering remains: register source cleanup and its binding in the pointer-CAS transaction, then obtain authoritative post-swap pointer/readback confirmation of that registration and source binding before asking World to finalize the cutover hold and request the source `TERMINATING` transition. This confirmation is not the all-owner terminal cleanup acknowledgement; World obtains those owner acknowledgements during its `TERMINATING` workflow before the final `TERMINATED` CAS.

### World-owned cutover hold binding

After World proves the target `ACTIVE`, it acquires one durable, opaque cutover hold for the execution. Game Session treats `cutoverHoldId` and `cutoverHoldFence` as equality-only World authority: it does not allocate, renew, release, or reinterpret the hold. The local pointer transaction must bind that identity/fence, the exact source/target lifecycle proofs, and the applicable canonical lifecycle proof tuple atomically with the pointer update, audit event, prepared execution/result, source-cleanup registration, and drain-fence identity. The post-swap readback must prove that exact lifecycle-proof-bound local transaction before Game Session asks World to finalize the hold or progress source termination. Public production omits both playtest fields and rejects supplied values.

Lost responses reconcile through the exact hold identity and authoritative World/Game Session reads. Game Session may request an abort only when owner evidence proves that its pointer transaction did not commit and the prior pointer remains authoritative; contradictory or unavailable evidence remains `RECONCILIATION_REQUIRED` and cannot be treated as a failed cutover or permit termination. The hold's World-owned `expiresAt` is diagnostic/repair input only and never auto-releases it. The current Game Session wire, durable transaction, and focused proof do not yet carry or prove this hold binding; see the [World cutover hold contract](../world-management-service/api-contracts.md#replacement-cutover-hold-contract).

### Initial admission bind

The first admission-pointer bind for a realm is a separate owner transaction from replacement cutover. Game Session owns a durable attempt ledger with one stable request identity and canonical digest, plus the terminal outcome `COMMITTED` or `ABORTED`. Its initial pointer transaction must prove that no pointer exists for the exact `{tenantId, realmId}` and atomically bind the World-issued initial-bind hold identity/fence, the same request identity/digest, `{tenantId, realmId, playableStateNamespaceId, playableStateScope}`, target `gameInstanceId`/`versionId` and exact `ACTIVE` lifecycle epoch, and `catalogRevision` with the new pointer and matching append-only audit event. The durable `COMMITTED` attempt outcome commits in that same transaction. This owner-side no-prior-pointer check is not replaced by a bootstrap snapshot, startup configuration, public raw-pointer RPC, or external operator write bypass.

An exact retry or post-restart recovery reuses the same attempt and hold identities and reconciles the durable attempt, pointer, and audit. Game Session may record `ABORTED` only as a durable terminal outcome that prevents any later commit for that same attempt. World may accept that exact, authenticated owner-readback outcome bound to the same hold and tuple as abort proof; pointer absence, `NOT_FOUND`, `PENDING`, unavailable reads, mismatched tuple/audit, or contradictory evidence is not proof. World finalization requires an authenticated exact Game Session owner readback of the same hold and request identity/digest, tuple, committed pointer, matching audit, and `COMMITTED` outcome. Ambiguous results remain termination-fenced while automatic reconciliation retries; elapsed time does not release the World hold. See the World-owned [initial admission bind hold contract](../world-management-service/api-contracts.md#initial-admission-bind-hold-contract).

This path is a local Compose fixture bootstrap, not the accepted Account `JOIN` transaction or a production activation path; realm identity and admission-pointer authority remain defined by the [Multi-Tenancy contract](../../system-architecture-multi-tenancy.md#realm-catalog-and-admission-pointer-contract), and explicit join remains owned by [ADR 0025](../../decisions/adr-0025-explicit-open-enrollment-membership.md). ## Session Front-End and Lease-Owner Routing

Game Session deliberately separates socket ownership from region execution ownership:

- The pod holding a player's WebSocket or proxied Telnet bridge is the session front-end for that gameplay session.
- Region-scoped command execution belongs to the current lease owner for the target `<tenantId, gameInstanceId, regionId>`.
- Session front-ends may authenticate, normalize input, manage connection-local state, and stream results to the client.
- Session front-ends must not directly stage or commit tick-owned Redis mutations for regions they do not lease.
- In the target-state model, when a command or follow-up targets a region owned by another pod, the session front-end forwards the request over internal gRPC to the lease owner and returns the resulting output to the client.
- Current-live fallback: the existing `EnqueueCommand` path resolves the session's current `{tenantId, gameInstanceId}` queue target and runtime ownership, persists the command, and uses the local Game Session tick-queue path. It does not expose a dedicated cross-pod forwarding RPC; if runtime ownership is missing or paused, admission rejects the command rather than performing an unfenced handoff.

### Forwarding contract

The internal front-end to lease-owner path is a **target-state** fenced gameplay contract, not a best-effort proxy hop. The live proto and Game Session implementation do not yet expose this forwarding RPC; the current-live fallback is the existing local `EnqueueCommand` admission path described above. [GR-1.1](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md) tracks that gap.

- Forwarded requests include the server-resolved `tenantId`, `playableStateNamespaceId`, `playableStateScope`, and `gameInstanceId`, plus `sessionId`, active `frontEndGeneration`, `characterId`, target `regionId`, stable `commandId`, `sessionSequence`, and the expected executor fence; namespace and scope are forwarded unchanged from `PlayerExecutionContext`.
- Owner-directory or lease-projection data is a routing hint. The receiving executor validates current ownership and fence at admission and rejects stale or missing authority rather than silently executing.
- `sessionSequence` preserves FIFO within one live connection generation only. `commandId` and effect/request identities provide dedupe and retry safety; sequencing is not an idempotency key or distributed transaction fence.
- A stale-owner rejection before admission may refresh routing and retry the same logical identity. If execution may have started, the front-end reconciles that same `commandId` through `GetGameplayCommandStatus` and never invents a replacement identity.
- Cross-region movement converges through the authoritative spatial/effect result. The front-end updates its execution-region pointer only after that durable result; it does not coordinate a separate source-release/destination-accept transaction.
- Asynchronous output targets the active `{sessionId, frontEndGeneration}` registration. Superseded generations cannot deliver to the replacement controller.
- Forwarding, in-flight work, retries, output buffering, and route refresh are bounded and expose saturation, timeout, stale-fence, ambiguous-result, and generation-mismatch metrics.

The reset pointer, audit, digest, CAS/readback, owner fences, and exact retry compare the applicable lifecycle ID, positive generation, namespace, pointer fence/version, and owner-registry revision/epochs together. A reset must not carry or use `preparedVersionUpgradeId`; version-upgrade compatibility or remap evidence cannot authorize it. Its transition matrix is: initial/no-record or `CLOSED -> OPEN(new)` uses fresh launch/activation proof and does not use `preparedVersionUpgradeId`; version replacement `OPEN(old) -> OPEN(new)` outside the reset branch is the replacement cutover and requires `preparedVersionUpgradeId` plus namespace/scope-bound `COMPATIBLE` preparation; `OPEN(old) -> CLOSED` closes admission without a version-upgrade artifact; `CLOSED -> CLOSED` and `OPEN(old) -> OPEN(old)` are exact idempotent/no-op cases and do not manufacture a preparation. For version replacement `OPEN(old) -> OPEN(new)`, this method routes through or reuses `ExecutePreparedVersionCutover` rather than being an independent replacement commit. Game Session rejects the swap unless the preparation still matches the current catalog-derived `{playableStateNamespaceId, playableStateScope}` and source/target instance/version pair, contains fresh owner family/classification/count/unknown, mapping-validation/application, and participant-epoch evidence required by ADR 0122, and the same pointer-CAS transaction binds World’s one-shot `cutoverHoldId`/`cutoverHoldFence` plus the exact source/target lifecycle proofs and durable execution result, all matching fresh authoritative World reads including the exact target `ACTIVE` state/epoch. The prepared `PREPARING` proof authorizes World’s activation CAS; it does not by itself authorize the pointer swap. Initial and closed-to-open transitions have their own current lifecycle/version/owner proof and must not be treated as replacement compatibility proof.
- Admission-pointer requests identify the durable `{tenantId, realmId}` route after selector resolution; read/audit responses carry `worldSlug`/`realmSlug` from the referenced catalog snapshot, the runtime route version separately from catalog/policy revision, and, for private/playtest targets, the positive `playtestStateGeneration`. Public-production admission and first-join membership creation consume current catalog visibility/public-production facts with entitlement checks instead of inferring behavior from `realmSlug`; display-only changes do not become runtime cutovers.
- Admission-pointer audit/list responses now also expose the `preparedVersionUpgradeId` used by a cutover write so operator history preserves the same proof identity that the mutation validated; private/playtest audit/readback retains the applicable lifecycle ID and generation, while public-production responses omit them.

**Target state:** Gameplay admission uses `JOIN_REQUIRED` only as a next-step response when fresh authority confirms that the selected target is publicly visible and public-production joining is allowed, while the caller's membership is absent or `INACTIVE` under [Account's explicit membership lifecycle](../../decisions/adr-0025-explicit-open-enrollment-membership.md#decision). A public-production policy denial remains `PUBLIC_PRODUCTION_ADMISSION_DENIED`; unavailable, stale, malformed, or ambiguous authority uses the applicable unavailable or invalid-authority outcome instead. Private/playtest admission always requires an existing caller-bound membership, the current membership authority generation, and the applicable Account-owned realm grant; a grant never replaces membership. **Current implementation:** text `PLAY` returns `JOIN_REQUIRED` only for a complete, fresh `MISSING` or `INACTIVE` membership snapshot on an eligible public-production target after public joining is allowed. A complete `ACTIVE` snapshot with `gameplayAdmissionAllowed=false` returns `WORLD_ACCESS_DENIED` without binding. Unavailable or malformed authority remains unavailable. It enforces the current non-public realm grant, while current connect-token issuance does not validate that grant; target connect-token issuance adds the same fresh grant gate.

- **Admission-pointer CAS inputs:** existing-row writes compare the exact `expectedPointerVersion` and `expectedCatalogRevision` pair. The current owner-local no-record insert requires `0/0` as its expected-absent precondition; because no row exists to version-check, insert-race safety comes from runtime-target locking and database uniqueness constraints, not a row-version CAS. Neither condition is proof of realm/catalog initialization or permission to create a pointer. The `SetAdmissionPointer` and `ExecutePreparedVersionCutover` control-plane RPCs remain fail-closed until their complete owner contracts are supported. Initial admission still requires the separate World lifecycle, canonical realm/catalog identity, pointer/audit transaction, and exact owner-readback proof described in [Initial admission bind](#initial-admission-bind).

### ADR-0048 operator-write contract

**Target state:** every mutating operator RPC listed above (`StartSession`, `StopSession`, `RestartSession`, `ToggleFeatureFlag`, `PauseTicksForScope`, `ResumeTicksForScope`, `SetAdmissionPointer`, `ExecutePreparedVersionCutover`, and `PrepareVersionUpgrade`) requires the same durable request identity: `controlPlaneRequestId` plus the canonical `mutationDigest`. Account binds both values into the bounded operator authorization reference, and Game Session recomputes and validates the digest before execution. The owner durably records the request before execution and records a terminal result only after owner-specific commit proof; PostgreSQL-owned mutations commit domain state and result atomically, while Redis-backed projections use the durable claim, fenced mutation marker, and reconciliation contract in ADR 0048. A duplicate request carrying the same digest returns the previously committed result, while the same request identifier with a different digest returns `IDEMPOTENCY_CONFLICT` without applying either payload. A timeout must not create a new request identifier; Logging & Admin may use that identifier only for owner result lookup until the exact operation is reconciled. `FENCE_REJECTED` is non-rearmable and prohibits mutation redelivery. A retry against a current owner or fence is permitted only after the owner has durably recorded terminal `NOT_EXECUTED` proof for the original attempt; it uses a new `ownerMutationId` and a newly fenced attempt while retaining the external request tuple. After authorization expiry, reconciliation is read-only.

The current proto and admission-pointer mutation flow remain incomplete against this target. `SetAdmissionPointerRequest` and `ExecutePreparedVersionCutoverRequest` still identify routes by `worldSlug`/`realmSlug` and do not carry durable `realmId`; the persisted/read models and callers have not proved migration to `{tenantId, realmId}`. `StartSessionRequest`, `PauseTicksForScopeRequest`, `ResumeTicksForScopeRequest`, and `GameplayAdmissionPointerMutation` for `SetAdmissionPointer` carry `controlPlaneRequestId` but not `mutationDigest`; those operations must not be reported as ADR-0048-complete until the missing request-field propagation, authorization binding, owner-side digest verification, replay persistence, and focused proof converge together.

Game Session follows the [canonical gRPC outcome and transport classification](../../system-architecture-grpc.md#outcome-and-transport-classification). A successfully produced command, control-plane, or read outcome uses its typed response contract; a failure that prevents producing that domain result uses canonical non-OK status with bounded structured details. Game Session preserves stable mutation request identities and reconciles ambiguous timeouts or transport failures before replaying work. Current handlers use a mixture of response-level `ErrorDetail` and transport failures, so exact per-RPC classifications and focused migration proof remain implementation gaps rather than a new service contract.

### External Operator Lifecycle Contract

**Target state:** External operator mutations enter through the Logging & Admin Service via Gateway. Logging & Admin authenticates the `control-ui` session, records the durable intent and audit context, and calls Account's canonical [`IssueHumanOperatorAuthorizationReference`](../account-service/api-contracts.md#operator-authorization-references) RPC; unattended automation uses the separately typed `IssueAutomationOperatorAuthorizationReference` branch under the restrictions that Account contract defines. Logging & Admin then forwards the opaque bounded reference unchanged with the exact typed action-family request, `actionFamilySchemaId`, `actionFamilySchemaVersion`, same `controlPlaneRequestId`, canonical `mutationDigest/v1` digest, and every scope, target, expected-version, mutation, and audit-reason field declared by that schema to the Game Session owner RPC over its exact mTLS workload identity. Only transport credentials and the authorization reference are excluded from the digest. If generation or privileged-predicate fields are copied outside the Account reference, they are non-authoritative context: Game Session must exclude those forwarded copies from authorization decisions and the mutation digest, or omit them entirely. Logging & Admin may forward the end-user `control-ui` JWT to Account only for reference issuance; it must never forward an end-user JWT or caller-asserted actor identity to Game Session. Game Session recomputes the digest from the exact schema pair and every declared digest input, then calls Account's `RedeemOperatorAuthorization` contract with the exact owner, action family and schema pair, scope, request identity, and digest. Account's returned bounded actor or automation-policy authorization projection is the sole authorization source; Game Session uses that Account-derived projection for audit while independently validating target-domain ownership, runtime fences, and owner-side idempotency. This target path is not currently routable and has no fallback external mutation route.

**Current implementation status:** The current OpenAPI surface exposes an owner-local `/sessions*` HTTP family. It uses the service-local control-plane auth boundary, direct edge exposure is denied, and no Logging & Admin external `/sessions*` family is currently available. These owner-local routes are not the canonical external operator ingress or player-admission contract.

### Service-Local HTTP Surface

Game Session owns the `/api/session/**` Gateway family, but the public gateway inventory exposes only `GET /api/session/ping`. The service-local endpoint inventory is:

- `GET /ping` – basic health check returning `"pong"`.
- `POST /sessions` – `target_not_currently_routable`; a current owner-local OpenAPI scaffold creates a game instance from a template-driven launch attempt, but it is not the player gameplay-admission seam and is not supported external operator ingress.
- `POST /sessions/{sessionId}/stop` – `target_not_currently_routable`; a current owner-local OpenAPI scaffold stops a running session, but supported external operator ingress remains unavailable.
- `POST /sessions/{sessionId}/restart` – `target_not_currently_routable`; a current owner-local OpenAPI scaffold restarts a stopped session, but supported external operator ingress remains unavailable.
- `POST /sessions/{sessionId}/refresh-roles` – `current_openapi_operator_surface`; this owner-local workload-authenticated route refreshes roles for an active session and is not an Account-authorization-reference mutation.

Use `/sessions/{sessionId}/refresh-roles` after updating an account's privileges so the session reflects the latest role assignments.

Direct external operator exposure of a mutating `/sessions*` route is forbidden unless the owning contract explicitly marks that exact route as bypass-safe and defines its auth class, audit behavior, and lease-owner forwarding rules in the same change.

#### Owner-side operator RPC classification

The gRPC owner methods `StartSession`, `RestartSession`, `StopSession`, `ToggleFeatureFlag`, `PauseTicksForScope`, `ResumeTicksForScope`, `SetAdmissionPointer`, `ExecutePreparedVersionCutover`, and `PrepareVersionUpgrade` are the target `internal_workload` operator RPC family. They accept the exact Logging & Admin mTLS workload identity and one opaque, short-lived Account-issued operator authorization reference for the bounded request, redeemed with Account; they accept no end-user JWT or caller-asserted actor authority. ## Command Front Door Ownership

Game Session owns the gameplay session front door and the split between protocol-level system commands and queued gameplay work:

- System commands such as `LOGIN`, `LOGON`, `PING`, and lightweight state queries are fully owned by Game Session and may complete synchronously without enqueuing gameplay work.
- Gameplay commands such as `LOOK`, `SAY`, movement, and combat are validated and normalized by Game Session, then forwarded to the tick/gameplay path. Game Session does not re-implement gameplay rules or resolve domain-owned facts for these commands.
- At target state, line input and future structured-client input are adapters onto the same pinned registry, stage, capability, history, idempotency, and durable-admission boundary. A structured client may submit typed intention directly and need not round-trip through text.
- At target state, a verified empty authored registry is distinct from a required registry that is unavailable, corrupt, mismatched, colliding, or unsupported. The latter fails closed; it never activates a process-local built-in fallback.
- At target state, the immutable verified registry may be cached by admitted release identity. Downstream production services receive typed intentions and do not maintain another raw-text command authority.
- If a command would produce both immediate text and enqueue metadata, enqueue failure wins. Game Session returns a single `ERROR` response instead of reporting success and silently dropping gameplay work.

For the [ADR 0112](../../decisions/adr-0112-typed-bounded-gameplay-effect-extension.md) boundary, the wider typed command and target-plan behavior is target-state. Game Session is the single semantic admission point: it resolves the release-pinned command declaration, validates the player/session context, and admits the typed command into the appropriate tick. It does not resolve actor targets, evaluate effect predicates, or mutate actor state; those remain Game Logic and Entity Management responsibilities. Current implementation and proof remain narrow and incomplete; see the [Game Session Runtime and Tick Coordination tracker](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md).

For the player-visible line protocol and examples, see [`protocols.md`](./protocols.md).
