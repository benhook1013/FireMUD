# Game Design Service API Contracts

## Overview

The protobuf service definitions under [../../../../protos/game-design/v1](../../../../protos/game-design/v1) are the authoritative wire-contract source for Game Design gRPC APIs. Architecture-doc JSON examples are normative for semantics and invariants, but field names and enums must ultimately converge on the proto definitions.

For REST endpoints, the authoritative request/response schema source is [openapi.yaml](../../../../services/game-design-service/src/main/resources/openapi.yaml). Design-doc examples should be updated to match when those schemas evolve.

## Tenant Identity Source and Selector

Game Design is the canonical issuer of opaque UUID `tenantId` values and the owner of stable `tenantSlug` selectors under [Multi-Tenancy](../../system-architecture-multi-tenancy.md#canonical-identity-and-retained-key-bridge). A retained Game Design game row may receive a UUID with exact owner-local provenance naming its row and former `game.tenant_id`; that binding is immutable and read back exactly. A newly created tenant receives a fresh persisted UUID rather than a numeric-key conversion. Selector assignment is explicit and unique; a game name, row key, former tenant string, or guessed slug is not a selector. Resolving a selector requires the current authoritative binding and does not authorize the caller by itself.

The fresh-tenant Account handoff is distinct from both retained-key reads below. Game Design must durably bind the exact creation request to its issued UUID and return authenticated operation-bound creation/readback evidence to Account under the [canonical identity contract](../../system-architecture-multi-tenancy.md#canonical-identity-and-retained-key-bridge). The smoke seeder and a legacy-manifest read do not supply this handoff. The owner-local operation/readback contract is specified below; executed database component proof and the remaining product-caller and live handoff gates are recorded in [Player Access and Session](../../../project-management/implementation-tracking/player-access-and-session.md). No production creation caller or Account handoff is enabled.

The separate `TenantIdentityService.ResolveLegacyGameTenantIdentity` read is limited to the verified Account workload peer. It accepts only an exact former Game Design tenant key and returns the persisted UUID, source key, source game row, and provenance kind together. A missing source returns `NOT_FOUND`; malformed input, missing peer, changed provenance, and ambiguous owner data fail closed before returning content. This read does **not** attest that an Account-retained numeric tenant key has the same identity as a numerically similar Game Design key. The separate `ResolveLegacyAccountTenantAssociation` read returns that cross-owner association only when a signed, owner-approved migration manifest has been applied and its exact source tuple still reads back. It is limited to the verified, same-namespace `account-tenant-migrator` workload identity; ordinary Account and other service peers are denied. It returns the immutable operation, approval, signature, digest, and retained-source evidence with the mapping, and denies absent or contradictory rows. Account's own retained-row verification and mapping readback are still required before it may use the UUID, and neither read itself grants membership admission. The [multi-tenancy identity bridge](../../system-architecture-multi-tenancy.md#canonical-identity-and-retained-key-bridge) owns the target contract; [Game Design operations](./operations.md#legacy-tenant-association-migration) records the controlled migration sequence and current proof limits.

**Implementation status:** Authored-world selector registration is an owner-local candidate with authenticated source readback, not a protected product creator or deployed runtime catalog intake; no current player-facing selector resolution is claimed. The fresh-creation and Account-association components have executed PostgreSQL proof, separately scoped in [Player Access and Session](../../../project-management/implementation-tracking/player-access-and-session.md); that does not prove a live product caller or deployed handoff. Source and selector components do not establish a proved deployed cross-owner legacy-key association, catalog enrollment or admission. Retained-row migration, mounted-certificate acceptance, full Account/Game Session authority and live caller/consumer proof remain separate gates; the membership RPC and credential paths remain disabled.

### Runtime tenant identity read for Game Session

`TenantIdentityService.ResolveRuntimeTenantIdentity` supplies Game Design's persisted tenant identity to Game Session, which remains the [sole runtime realm-catalog and admission-pointer resolver/persister](../game-session-service/api-contracts.md#world-lifecycle-and-admission-boundary). This read neither creates a tenant nor allocates or changes a realm, namespace, catalog or pointer. It does not replace Account's creation-operation readback or the approved retained Account association.

The request carries canonical non-nil UUIDs `canonical_tenant_id` and `request_id`. The closed version-1 response carries `schema_version`, `target_namespace`, the exact `request_id` and `canonical_tenant_id`, positive `source_game_row_id`, exact `source_game_tenant_key` and `provenance_kind` (`NEW_GAME_ROW` or `RETAINED_GAME_V30`). The source key and row are private Game Design provenance, not selectors or assertions about any Account or Game Session numeric key. The repository uniquely reads the actual canonical-UUID row and verifies its provenance against that same row and source key; missing, ambiguous, changed or contradictory identity fails closed without mutation.

Only the verified peer `spiffe://firemud/ns/{configured_namespace}/sa/game-session-service` may read this method. The exact peer check precedes data access, and any bearer bypass is limited to this method; a JWT service claim, another workload or another namespace cannot substitute. Existing Account-only creation and migration method guards are unchanged. The Game Session consumer requires file-backed workload mTLS, validates the closed evidence and exact namespace/request/tenant echoes, and rejects aliases or incomplete evidence before using it. This proves owner identity provenance only, not a membership grant, Account authority, World lifecycle, selected-target readiness or admission. Runtime catalog intake must separately persist and read back the association at Game Session's owner boundary; missing provenance and unmapped retained runtime rows remain denied rather than deriving UUIDs from numeric IDs.

This is owner database proof, not a deployed Game Session client, retained Game Session association, authored-world enrollment or catalog activation; remaining proof belongs to [Player Access and Session](../../../project-management/implementation-tracking/player-access-and-session.md).

### Authored-world source registration and Game Session readback

Game Design owns a persisted authored-world selector source; Game Session consumes its authenticated readback and remains the sole runtime catalog writer. World consumes the same source authority for its separate [automatic authored-content intake and local association](../world-management-service/api-contracts.md#authenticated-authored-content-intake-and-tenant-association); only the exact same-namespace Game Session and World workloads may read this source, while the other tenant-identity methods retain their own caller restrictions. A Game Design owner transaction binds the existing canonical tenant identity and exact source-game provenance to separately supplied stable `tenantSlug` and tenant-scoped `worldSlug` values. Neither selector is inferred from a display name, template, numeric key, realm slug or runtime instance. A template or launch descriptor is not itself an authored-world identity. This source is selector provenance, not a content-version release, realm policy, membership grant, selected runtime or admission permission.

The closed `game-design-authored-world-source/v1` evidence contains `schemaVersion=1`, `targetNamespace`, canonical non-nil `registrationRequestId`, canonical non-nil owner `operationId`, `requestDigest`, canonical non-nil `canonicalTenantId`, `tenantSlug`, `worldSlug`, `worldDisplayName`, positive private `sourceGameRowId`, exact private `sourceGameTenantKey`, `provenanceKind` (`NEW_GAME_ROW` or `RETAINED_GAME_V30`) and `evidenceDigest`. Slugs use the existing canonical lower-case routing-selector grammar `[a-z0-9]+(?:-[a-z0-9]+)*`, bounded to 120 UTF-8 bytes; no case folding, trimming or inference changes a signed or stored selector. The display name is explicitly supplied, nonblank valid Unicode and at most 100 code points. Source-key bounds and actual game-row provenance retain the tenant-identity rules above. Private source row/key fields are provenance only, not public logical identifiers or a Game Session numeric tenant association.

The owner claims `(targetNamespace, registrationRequestId)` and commits the tenant-selector binding and complete world-source receipt atomically under the actual Game Design tenant row fence; no claim-only or partial source is authoritative. `tenantSlug` is unique within that namespace's tenant authority, one tenant has one stable slug, and `worldSlug` is unique only within the exact tenant. An exact registration retry returns the same operation, source tuple, metadata and digests. Changed input under the same request, rebinding a tenant slug, slug ownership collision, another request claiming an existing world, absent/contradictory source or failed commit denies without leaving a partial assignment. Reads do not allocate selectors or repair mappings. Ordinary creation and its eventual handoff are automated owner work, not a routine operator import.

Both digests are SHA-256 rendered as `sha256:` plus 64 lowercase hexadecimal digits over fixed-order UTF-8 segments with decimal byte-length `:` framing, as in the fresh-creation contract. The request preimage is `game-design-authored-world-source-request/v1`, namespace, registration request UUID, canonical tenant UUID, tenant slug, world slug and world display name. The evidence preimage is `game-design-authored-world-source-receipt/v1`, namespace, registration request UUID, operation UUID, request digest, canonical tenant UUID, tenant slug, world slug, world display name, canonical decimal source row ID, exact source game tenant key and provenance kind. No field, implicit normalization or unframed concatenation is omitted. Producer and consumer recompute both digests and share positive/changed-field vectors.

The readback request binds a distinct canonical non-nil read `requestId` to the exact source `operationId`, canonical tenant UUID and world slug; the closed response echoes that read identity separately from the original registration identity and carries the complete source evidence. Only the verified same-namespace Game Session and World workloads may read it for their respective catalog and [World intake](../world-management-service/api-contracts.md#authenticated-authored-content-intake-and-tenant-association) consequences. The guard precedes owner data access, and the receiver authenticates Game Design rather than accepting a JWT service claim or digest alone. The consuming client proves the exact same-namespace Game Design workload from the negotiated TLS transport before releasing request metadata or body; response-only verification is insufficient. Missing or changed source, digest/echo/scope mismatch, wrong workload or namespace, and unknown wire fields fail closed. Exact committed readback returns the same source receipt without mutation; it is not a catalog enrollment, released-content or admission result.

**Implementation and activation boundary:** The source repository/codec/readback is a prerequisite candidate, not a protected product creator or a live catalog handoff. Normal official-hosted authoring remains subject to the Account-owned commit-bound creator/terms gate below, which cannot be replaced by the source transaction or a caller-supplied authorization flag. No new public creation route or catalog admission is enabled before its producer, receiver, owner authorization and negative proof pass. Retained Game Session tenant keys need a separate audited, Game Design-authenticated association and Game Session's own exact retained-row readback; Account's manifest and numeric/slug similarity cannot establish it. The [Player Access tracker](../../../project-management/implementation-tracking/player-access-and-session.md) owns the remaining implementation and proof.

#### Durable fresh-source delivery to World

Game Design commits a new fresh `NEW_GAME_ROW` source operation and its World delivery intent in the same owner transaction. The intent binds the complete immutable source evidence to one separately allocated, durable World `intakeRequestId`; process restart, an exact source retry or an uncertain acknowledgement must not allocate a replacement intake identity. Retained source registration does not create this fresh delivery intent or infer a World association. The migration installs storage without backfilling retained or historical associations. Exact replay of a historical source-only operation still returns its original source receipt; an absent delivery intent neither fabricates a delivery result nor invalidates that source receipt, and its delivery remains denied until separately proved.

Delivery uses the authenticated [World intake and readback contract](../world-management-service/api-contracts.md#authenticated-authored-content-intake-and-tenant-association), outside the Game Design database transaction. Before acknowledging delivery, Game Design obtains independent authenticated World readback and compares the complete original public receipt and intake binding. A short local transaction retains that first complete receipt against the original intent, followed by independent durable readback; concurrent identical acknowledgements return the same stored outcome and conflicting receipts fail closed. An exact completed retry reads that outcome before contacting World. Unavailable, mismatched or ambiguous outcomes remain pending for exact retry, not terminal failure or expiry-based deletion. This is source delivery only: neither its intent nor World receipt supplies Account creator authorization, content materialization, release evidence, lifecycle readiness or admission. Normal protected creator and delivery wiring still require their own implementation and proof under the [authoring tracker](../../../project-management/implementation-tracking/game-authoring-publishing-and-activation.md#current-status).

### Authored-source-bound launch descriptor and exact readback

The descriptor's `publishedReleaseBundleRef` uses the exact persisted [Game Design release identity](version-control.md#launch-and-attestation-read-authorization-target-state), not a reference reconstructed from its source tenant or private row identifiers. A new source-bound resolution rejects a bundle without that owner reference. This storage prerequisite does not complete the separately required release-attestation response or authorize launch.

Game Design's existing immutable launch-descriptor boundary binds selector provenance to a resolved release; it does not turn selector registration into publication. Game Session remains the launch orchestrator. A canonical launch request names the exact authored-source operation and evidence digest, canonical tenant UUID and tenant-scoped `worldSlug`, together with its stable request identity and requested template/version inputs. Game Design reads and verifies its actual persisted source and template/version ownership before resolving. A private Game Design source key is usable only inside that proved owner association, never as a World or Game Session tenant alias.

The committed descriptor retains those source fields and the exact resolved template, version, release bundle reference and Game Design version-state epoch, plus every other resolved launch field and the original request identity/digest. New canonical request and result digests use distinct versioned domains, fixed exhaustive field order, strict UTF-8 byte-length framing and explicit optional presence/value encoding as in [ADR 0047](../../decisions/adr-0047-logging-admin-as-external-operator-write-ingress.md). A digest excludes only its own derived value, not an applicable source, request or result field. Source identity, release attestation and the launch result remain independently verified evidence; none substitutes for another.

The complete immutable resolved launch binding consists of this unchanged closed descriptor and a separately authenticated full release attestation produced through Game Design's normal owner workflow. The attestation binds the exact descriptor and authored-source identity, plus the canonical UUID version identity, to the resolved release and its required participant, ability-schema, artifact and manifest evidence under the [version-resolution predicate](../../system-architecture-versioning-runtime.md#launch-descriptor-version-resolution-rules). The descriptor alone is not full release evidence, and a caller-supplied or operator-maintained sidecar is not an attestation. Consumers authenticate and verify the exact attestation against the descriptor before retaining or using the pair. The separate representation below does not extend or reinterpret signed descriptor v1 or its digests.

### Audited retained Game Session tenant association

This is a distinct, one-time retained-data association, not the Account migration manifest or the normal fresh-creation path. Game Design's approved tenant owner must explicitly attest that one retained Game Session tenant key denotes its persisted canonical tenant. Existing source rows on either side, similar selectors or numeric values do not establish that relation. With no such attestation, the association remains absent and denied. Normal new creation and source intake remain automated owner work; this retained-data approval does not introduce a routine creation-time operator step.

The closed `game-design/game-session-retained-tenant-association/v1` manifest binds, in fixed order: `schemaVersion=1`, canonical non-nil `operationId`, `targetNamespace`, `signerKeyId`, `approvedBy`, `approvalReference`, canonical UTC `signedAt`, positive decimal-string `legacyGameSessionTenantId`, canonical non-nil `canonicalTenantId`, positive decimal-string `sourceGameRowId`, exact `sourceGameTenantKey`, `provenanceKind`, and `gameSessionEvidenceDigest`. The namespace, source key and provenance retain the runtime-tenant identity bounds above. Signer key IDs are bounded to 128 UTF-8 bytes, approval actors to 256 and references to 512; these strings must be nonblank valid Unicode without control characters and are not trimmed or case-folded. Approval labels alone are not authorization.

The signature and digest preimage starts with the exact domain string above, followed by every manifest field in that order, represented as UTF-8 segments with decimal byte-length `:` framing. An Account manifest cannot be reinterpreted as this type. Unknown fields, invalid signature, untrusted signer, missing source, changed provenance or ambiguous association fail without mutation.

### Fresh tenant creation operation and Account readback

This owner-local prerequisite binds a fresh Game Design-issued UUID to a stable creation request and exposes only authenticated readback to Account. It is not a tenant-creation API, product caller, selector-registration path, membership grant, or runtime activation. The internal producer candidate is not a protected product creator; it must not change smoke-seeder behavior or bypass the official-hosted creator gate in [ADR 0180](../../decisions/adr-0180-account-owned-hosted-terms-acceptance-gate.md). Any official-hosted creator-intent mutation remains subject to that gate and its current missing implementation/proof.

The owner transaction claims a unique `(target_namespace, creation_request_id)` using a canonical non-nil UUID request identity, computes `request_digest`, creates the row through the existing Game Design repository UUID issuer, and commits one immutable `game_tenant_creation_operations` record with the source row/key and receipt evidence. Migration V32 introduces this storage; the evidence schema version is `1`. There is no committed `PENDING` operation: the game row and complete operation evidence commit atomically. An exact retry returns the same persisted receipt; reuse of the same namespace/request UUID with changed input or source key conflicts without mutation. The operation record retains the immutable creation inputs needed to recompute the request digest; later edits to mutable game name/description do not rewrite creation identity.

The request digest is `sha256:` followed by 64 lowercase hexadecimal digits over fixed-order, length-framed UTF-8 byte segments. Each segment is encoded as its decimal byte length, `:`, then its bytes; the decimal length has no leading zero except for the single digit `0`. Before digest framing or database work, validate cheap input bounds: source key at most 36 Unicode code points, name at most 100 Unicode code points, and description at most 255 Unicode code points. These bounds match the owner columns, including the existing `game.description VARCHAR(255)`; do not expand that owner column for this candidate. Then strictly encode each exact string as UTF-8, rejecting unpaired surrogates; encoding does not replace, trim, or Unicode-normalize input. In order, the request preimage segments are `game-design-tenant-creation-request/v1`, target namespace, canonical creation-request UUID, exact source game tenant key, name, description-presence (`absent` for null and `present` otherwise), and description bytes (empty when absent). Thus absent and present-empty descriptions differ. Length framing counts UTF-8 bytes, not Unicode code points.

The receipt digest uses the same framing and encoding rules, with ordered preimage segments `game-design-tenant-creation-receipt/v1`, target namespace, creation-request UUID, owner-issued operation UUID, request digest, issued canonical tenant UUID, positive decimal Game Design row ID, exact source game tenant key, and `NEW_GAME_ROW`. Persisted source key and numeric row ID are private owner provenance, not selectors and not assertions about any Account key.

The candidate read-only method is `TenantIdentityService.ResolveFreshTenantCreation`. Its request carries a canonical non-nil `creation_request_id` and mandatory canonical `expected_request_digest`; unknown protobuf fields are rejected before owner access. The response carries exactly `schema_version=1`, `target_namespace`, `creation_request_id`, `operation_id`, `request_digest`, `canonical_tenant_id`, `source_game_row_id`, `source_game_tenant_key`, `provenance_kind=NEW_GAME_ROW`, and `evidence_digest` (the receipt digest). The receiver requires the verified mTLS peer `spiffe://firemud/ns/{target_namespace}/sa/account-service` for the same configured namespace and denies an authenticated forwarded caller context; the mTLS workload identity is the sole caller identity for this read. The bearer/JWT bypass, if needed for this method, is scoped only to this exact RPC and does not relax the peer guard or authorize another method/caller. Missing, ambiguous, changed, or digest-mismatched operation evidence fails closed using standard shared gRPC status errors; no new error enum is introduced.

The focused proof boundary is an owner database producer/readback test that verifies atomic row+operation commit, exact retry, changed-input/source conflict with no second row or mutation, persisted digest recomputation, immutable operation/source/receipt readback, plus RPC positive exact-Account-peer and negative wrong/missing-peer tests. [Player Access and Session](../../../project-management/implementation-tracking/player-access-and-session.md) owns exact-head execution evidence and incident history. Account must separately persist its UUID-keyed identity association before membership work, as required by [Multi-Tenancy](../../system-architecture-multi-tenancy.md#canonical-identity-and-retained-key-bridge); this owner proof creates no numeric alias. Neither unit tests nor database component execution substitutes for live workload authentication, a protected product creator, or a complete runtime admission handoff.

### Fresh tenant creation initiator qualification

The original `FreshTenantCreationEvidence/v1` and both creation digests above establish tenant identity, not creator authority. Preserve their exact bytes and digests. A fresh creator-qualified operation additionally records a distinct `FreshTenantCreatorEvidence/v1`: the complete original creation evidence, canonical initiating Account UUID, exact Account-owned creation-authorization operation UUID and digest, and its own qualification digest. Game Design stores both evidence classes atomically with the newly issued tenant; an unqualified existing operation cannot acquire a creator qualification afterward. Changed creator, authorization identity/digest or original creation input conflicts before mutation. Exact retries independently read back the original source and qualification. Private source keys remain provenance, never Account identity or permission.

The qualification digest uses the same strict UTF-8 decimal-byte-length framing as the original creation digests. Its fixed-order segments are `game-design-tenant-creator-qualification/v1`, qualification schema version `1`, original creation schema version, namespace, creation-request UUID, original operation UUID, original request digest, canonical tenant UUID, positive decimal source game row ID, exact source tenant key, provenance kind, original evidence digest, initiating Account UUID, Account authorization operation UUID and Account authorization digest. All fields are mandatory; a valid digest binds evidence but does not authenticate its producer or authorize a creator.

`TenantIdentityService.ResolveFreshTenantCreatorQualification` is a separate Account-only, same-namespace verified-mTLS read. Its closed request binds a distinct canonical `read_request_id`, the original creation request and expected request/evidence digests, the initiating Account, authorization operation/digest and expected qualification digest. Its closed response echoes the read identity and returns the complete unchanged creation evidence and distinct qualification. The receiver rejects unknown fields and authenticated forwarded caller context before owner access, compares every requested binding and both recomputed digests, and denies missing or contradictory qualification. The Account consumer authenticates Game Design and repeats those complete checks. Only this exact method is exempted from JWT interception; the workload guard remains mandatory. Existing source-only creation and authored-world source reads retain their contracts.

The [Account tenant-role owner contract](../account-service/api-contracts.md#account-owned-tenant-role-administration) governs the resulting control-only first-administrator transition. Qualification storage or successful readback is not the protected Account creation-authorization producer, role bootstrap, hosted-terms acceptance or gameplay admission. These implementation and proof gaps remain in [Player Access and Session](../../../project-management/implementation-tracking/player-access-and-session.md); public creation and creator authorization remain unavailable until their owner prerequisites are proved.

## Official Hosted Creator Mutation Gate

For official hosted deployments, every creator-intent content-bearing mutation enters the Game Design boundary only after the Account-owned currentness/evidence authority in [Account Service API Contracts](../account-service/api-contracts.md#account-owned-hosted-terms-and-creator-party) has been evaluated for the tenant's Creator Party, identified operator, and hosted-terms scope under [ADR 0180](../../decisions/adr-0180-account-owned-hosted-terms-acceptance-gate.md). This applies before the first persisted Draft and before later authoring/revision, asset, template, plugin, and publication writes. The acting account's current tenant authorization is a separate conjunct; Gateway/UI checks are advisory.

Game Design records only the local committed evidence-binding tuple `{tenantId, creatorPartyId, acceptanceEvidenceId, generation}` for a covered operation, where `generation` is Account's material-acceptance generation; it does not copy the Account terms/party catalog. The exact Account party, evidence, and generation authority must remain valid through Game Design's commit linearization point; a preflight read alone is insufficient, and the boundary requires commit-bound authority/fence or equivalent validation without selecting its mechanism. Missing, stale, mismatched, ambiguous, unavailable, or uncertain authority fails closed by aborting the local transaction before any creator mutation or staged artifact becomes authoritative or externally reachable; staged bytes are cleanup/quarantine state, not success. An exact durably committed retry replays its stored outcome and local evidence. An uncertain or not-durably-committed attempt first reconciles the original stable identity and obtains durable no-commit proof; it is not blindly redispatched or mutated while indeterminate. Only a permitted fresh attempt performs a fresh commit-bound currentness check. Reusing the same identity with changed normalized payload returns the target application outcome `IDEMPOTENCY_CONFLICT` before mutation. Game Design does not infer signer authority or materiality.

Changed-term stale acceptance and the separate non-authoring continuity/lifecycle-reduction paths are target-only under [ADR 0181](../../decisions/adr-0181-changed-hosted-terms-decline-and-existing-content-continuity.md). Current proto/OpenAPI, routes, storage, UI/status, and focused proof do not implement this gate; no future route or schema is selected here. **Current route consequence:** the implemented Gateway exposes only `GET /api/design/ping` and `GET /api/design/templates`, not the service-local `POST /assets` or `POST /templates` controllers. Those creator writes currently check only privileged JWT/tenant access and do not evaluate Account hosted-terms/currentness authority. Official-hosted creator-write readiness remains blocked until the exact Account-owned gate is implemented and proved; the Gateway restriction is containment, not a substitute for the owner-side gate.

## Draft Commit and Proposal Semantics (Target State)

The eventual creator-facing proto/OpenAPI shape must expose these semantics without treating a private frontend endpoint as a stable public API by accident:

- submitting or accepting a commit/proposal binds its stable identity to the target `tenantId` and `versionId`, exact `baseCommitId`, canonical digest of the complete diff, canonical revision order, and complete affected `(tenantId, versionId, owner, aggregateId, scopeId, epoch)` set;
- exact replay returns the existing result only when every ADR 0129 binding matches: target tenant/version, canonical input/mutation, exact `baseCommitId`, canonical revision order, canonical digest, and the complete affected set. Reusing the identity with any changed or omitted binding field is rejected deterministically as changed-request reuse, even when the digest happens to match;
- a creator-visible status read reports the overall coordination state and each required owner's durable apply outcome for the exact commit/digest;
- normal Draft reads return or require the fully synchronized commit fence and do not expose a partial owner application as current Draft truth;
- stale affected epochs return a typed conflict containing enough current fence/epoch identity to construct a new proposal, but the service never silently rebases or merges it; and
- AI-assisted and external clients use the same proposal acceptance, concurrency, status, and error semantics as ordinary creator tools.

Concrete RPC names, message fields, enums, pagination, and transport exposure remain deferred until the proto/OpenAPI contract is implemented. Whatever shape is selected must preserve the authority and visibility rules in ADR 0129.

Full-version publication selects an existing authored Draft through `PublishVersionRequest`: canonical `tenant_id` and `version_id`, stable `publish_request_id`, positive canonical decimal `expected_version_state_epoch`, `notes`, and the exact `selected_commit_request_id`, `selected_commit_id` and `selected_commit_digest`. The first durable selection binds all of those fields to the synchronized commit and its complete owner evidence. A tenant/request identity cannot select a second Version. Changed or omitted selection input conflicts before a new attempt or attachment to a workflow; an exact retry retains the original selection instead of substituting the current Draft. Game Design resolves private storage keys from its persisted canonical association. Private tenant or Version keys do not replace the canonical target or publication-workflow identity.

The [Account-owned exact-operation authorization fence](../account-service/api-contracts.md#account-owned-authored-draft-authorization-fence) covers both World's owner commit and Game Design's final authoritative commit. Game Design preserves the original operation and complete binding during automatic recovery and supplies immutable, authenticated final commit or no-commit readback. It must not treat an Account capture or finalization result as permission for a later commit, or expose a partial World outcome as a synchronized Draft. Source changes remain subject to the Account-owned ordering until both participant outcomes are definitive; this producer/consumer integration is not established by the coordinator storage alone.

For every creator-intent `SaveRevision`, including revision-only requests, the exact Account party, acceptance-evidence, and material-acceptance-generation authorization must remain valid through Game Design's authoritative commit boundary. A preflight Account read alone is insufficient. If the authority is stale, mismatched, unavailable, or uncertain at that boundary, Game Design aborts the local transaction; no creator mutation or staged artifact becomes authoritative or externally reachable, and any staged artifact is cleanup/quarantine state, not success. The implementation must use commit-bound Account authorization/fence or equivalent validation without this contract selecting its mechanism.

For a `SaveRevision` request carrying `worldDesignMutation`, the same authorization invariant applies to every participating authoritative mutation. Game Design carries the current Account authorization with the exact mutation descriptor to World, whose owner contract defines the [canonical Draft commit authorization boundary](../world-management-service/api-contracts.md#canonical-draft-commit-authorization). Until World can verify that authorization at its commit boundary, no participating owner commits and `SaveRevision` must not report success for a partial cross-owner commit; any staging remains non-authoritative. A source receipt, forwarded JWT, workload identity, or preflight-only check does not satisfy this producer obligation.

The request must include `controlPlaneRequestId`, and repeated calls for the same launch attempt must return the same descriptor values without re-resolving to newer attestation or patch state. The resolved descriptor now carries the real version-state CAS epoch rather than a derived release-bundle surrogate, and deterministic launch-preflight failures such as `RELEASE_BUNDLE_NOT_FOUND` and `LAUNCH_REMAP_REQUIRED` are returned as normal app errors rather than generic invalid-input collapse. When a cross-version replacement launch is valid, the descriptor now freezes the approved persisted `remapSetId` for the source/target version pair.
- `CreateTemplateRemapSet` / `ApproveTemplateRemapSet` / `GetTemplateRemapSet` – authoritative control-plane APIs for persisted version-to-version remap identities and their audit history. Game Design owns the `remapSetId` namespace consumed by replacement launch resolution and later cutover preflight.
- `CanDeleteVersionAssets` – deletion-eligibility oracle for version-scoped asset prefixes.
- `BeginPurgeVersionAssets` – **Target state:** CAS-guarded purge start that atomically re-checks deletion eligibility and transitions `version_asset_artifact` into purge-in-progress state. The current implementation has no database CAS or shared idempotency ledger.

When request/response schemas evolve, the proto contract and those architecture sections must be updated in the same change so launch-resolution and template-phase semantics do not drift.

#### `AppendPluginVersionSignatureEvidence` (target only)

This target mutation belongs to Game Design and is separate from runtime plugin activation. It is a signed-intake-only supplement to `UploadPluginBundle`: the target row must have entered the lifecycle through the allowlisted Ed25519 signed-intake path, and an unsigned package cannot use this RPC to manufacture signature evidence. Unsigned operator-permitted intake, when implemented under ADR 0111, needs its own platform-acceptance/approval evidence path and is not represented by this signature ledger. For signed intake, the mutation appends to an immutable evidence ledger; it never rewrites the uploaded bundle, signed payload, `pluginVersionId`, `bundleDigest`, publication status, or publication content. It is allowed only while the design-time status is `SIGNATURE_VERIFIED` or `PUBLISHED`; other statuses fail deterministically without mutation. A successful append on a `PUBLISHED` version does not republish or change its status, and an append on `SIGNATURE_VERIFIED` leaves that status unchanged.

The owner first resolves `controlPlaneRequestId` and the normalized request digest: an exact terminal retry returns its stored result before current status/evidence validation, while changed-digest reuse returns `IDEMPOTENCY_CONFLICT` without mutation. Only a new request evaluates current `SIGNATURE_VERIFIED`/`PUBLISHED` eligibility. The owner serializes this mutation with `RevokePluginVersion` status transitions and `PublishPluginVersion` supersession of older versions. Under one owner-row/status-revision transaction, it rechecks status eligibility and commits the duplicate/conflict decision, the ledger append when applicable, the idempotency result, and exactly one `PluginVersionSignatureEvidenceAppended` outbox event if and only if the outcome is `APPENDED`; an identical no-op or conflict has no ledger append or event. Revoke, supersede, and evidence append therefore resolve as one ordered owner decision, never as a partially applied combination.

Signature verification uses the canonical [Signing and Key Lifecycle](modding-framework.md#signing-and-key-lifecycle-required) owner contract: resolve the exact stored immutable `bundleDigest` for `(tenantId, pluginId, pluginVersionId)`, require it to equal the expected `bundleDigest`, and verify the appended Ed25519 entry against the signed-intake-v1 envelope and preimage. The resulting canonical `verifiedSignatures[]` is the complete ordered set of the immutable initial signed-intake evidence plus append-only evidence and retains the owner-defined key metadata; this API defines no separate algorithm, schema, or domain-separator scheme.

Inputs:

- exact `(tenantId, pluginId, pluginVersionId)`;
- expected `bundleDigest`;
- one bounded Ed25519 signed-intake-v1 evidence entry containing the signer identity, signature bytes, and optional creation metadata; and
- a stable `controlPlaneRequestId`.

The normalized request digest includes the complete plugin identity, expected digest, and canonical evidence entry. Outputs return the exact plugin identity, unchanged publication status, immutable `bundleDigest`, the canonical ordered complete `verifiedSignatures[]` set composed from the immutable initial signed-intake evidence plus the append-only ledger, and an `appendOutcome` of `APPENDED` or `IDENTICAL_EVIDENCE_NOOP`. Only `APPENDED` creates one durable `PluginVersionSignatureEvidenceAppended` event; exact retries return the stored result without another append or event. Reusing a request ID with a changed normalized digest is an idempotency conflict. A request carrying identical existing signer evidence is an idempotent no-op; conflicting same-signer evidence, digest mismatch, malformed or over-limit evidence, invalid cryptographic verification, no allowlisted signer, or any revoked signer fails deterministically without mutation.

### Script-patch and plugin transition consequences

`PublishScriptPatchVersion` and `PublishPluginVersion` are design-time publication operations. They persist immutable authoring metadata and compatibility evidence but do not activate a running instance, allocate a script pin epoch, or write rollout history. A patch must pass the normal publication boundary before Automation can perform tenant readiness; readiness still does not imply an instance pin. **Target-state ownership:** Game Session owns the exact instance pin, epoch, and committed append-only rollout/rollback history, while Automation owns readiness, artifact loading, and observed convergence. The current Game Session implementation does not yet prove complete epoch propagation or Game-Session-owned append-only rollout history; see [Game Session API implementation notes](../game-session-service/api-contracts.md#implementation-notes). This document does not claim those target-state consequences are live.

Creator/operator read models must therefore distinguish:

- design-time publication (`PUBLISHED`, or a design-time failure);
- tenant runtime readiness (`READY`, `FAILED`, or an intermediate state) from Automation; and
- the authoritative instance pin/epoch and rollout history from Game Session.

Game Design must not infer a rollback or repin from event arrival, readiness rows, or plugin activation state. Plugin publication and instance activation remain separate API lifecycles, and plugin graphs use the same DSL/sandbox as embedded scripts while retaining independent immutable plugin identity.
