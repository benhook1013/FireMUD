# Game Design Service API Contracts

## Overview

The protobuf service definitions under [../../../../protos/game-design/v1](../../../../protos/game-design/v1) are the authoritative wire-contract source for Game Design gRPC APIs. Architecture-doc JSON examples are normative for semantics and invariants, but field names and enums must ultimately converge on the proto definitions.

For REST endpoints, the authoritative request/response schema source is [openapi.yaml](../../../../services/game-design-service/src/main/resources/openapi.yaml). Design-doc examples should be updated to match when those schemas evolve.

## Fresh-Tenant Prerequisite Implementation Status

The owner-local fresh-creation repository and exact Account/Game Session mTLS receipt read are implemented; authenticated creator authorization, Account enrollment, runtime admission, and playable proof remain unavailable. No creation RPC or activation is introduced. Current validation evidence and remaining gaps are recorded in the [implementation tracker](../../../project-management/implementation-tracking/game-authoring-publishing-and-activation.md#fresh-tenant-identity-prerequisite).

## Canonical Tenant Identity and Fresh-Creation Readback

Game Design issues each new game row an opaque canonical tenant UUID and keeps exact row/key provenance in that owner row. V29 preserves only well-shaped retained source keys with `RETAINED_GAME_V29` provenance; new rows receive `NEW_GAME_ROW` provenance. V30 adds the immutable operation receipt for an exact fresh-creation request. Neither a legacy tenant string nor this owner evidence is an Account identity association, membership grant, JOIN decision, or caller authorization.

`TenantIdentityService.ResolveFreshTenantCreation` is a read-only receipt lookup for the exact same-namespace `account-service` or `game-session-service` mTLS peer. It accepts a canonical non-nil `creation_request_id` plus `expected_request_digest` and returns the exact persisted operation, request, UUID, source-row/key, provenance, and evidence digest, including the stored `request_digest`. The bearer-token bypass is limited to this read RPC and does not replace that peer check; an authenticated player caller context is rejected even on an otherwise permitted peer. Unknown request fields, absent or inconsistent evidence, and digest mismatches fail closed.

`GameTenantCreationDigest` binds request and receipt fields using domain-separated, length-prefixed UTF-8 segments before SHA-256. Optional descriptions have an explicit presence marker. Malformed Unicode, including unpaired surrogates, is rejected before digesting rather than replaced; changed fields change the digest, and values are not normalized into a guessed selector.

`GameTenantCreationRepository.createCandidate` is an owner-local transaction primitive, not a tenant-creation API. There is no creation RPC or authenticated creator authority in this slice, so normal creator-facing tenant creation remains unavailable. This boundary must not be used as an admin shortcut, an Account JOIN substitute, or proof that any Account association or runtime admission is enabled.

## Official Hosted Creator Mutation Gate

For official hosted deployments, every creator-intent content-bearing mutation enters the Game Design boundary only after the Account-owned currentness/evidence authority in [Account Service API Contracts](../account-service/api-contracts.md#account-owned-hosted-terms-and-creator-party) has been evaluated for the tenant's Creator Party, identified operator, and hosted-terms scope under [ADR 0180](../../decisions/adr-0180-account-owned-hosted-terms-acceptance-gate.md). This applies before the first persisted Draft and before later authoring/revision, asset, template, plugin, and publication writes. The acting account's current tenant authorization is a separate conjunct; Gateway/UI checks are advisory.

Game Design records only the local committed evidence-binding tuple `{tenantId, creatorPartyId, acceptanceEvidenceId, generation}` for a covered operation, where `generation` is Account's material-acceptance generation; it does not copy the Account terms/party catalog. The exact Account party, evidence, and generation authority must remain valid through Game Design's commit linearization point; a preflight read alone is insufficient, and the boundary requires commit-bound authority/fence or equivalent validation without selecting its mechanism. Missing, stale, mismatched, ambiguous, unavailable, or uncertain authority fails closed by aborting the local transaction before any creator mutation or staged artifact becomes authoritative or externally reachable; staged bytes are cleanup/quarantine state, not success. An exact durably committed retry replays its stored outcome and local evidence. An uncertain or not-durably-committed attempt first reconciles the original stable identity and obtains durable no-commit proof; it is not blindly redispatched or mutated while indeterminate. Only a permitted fresh attempt performs a fresh commit-bound currentness check. Reusing the same identity with changed normalized payload returns the target application outcome `IDEMPOTENCY_CONFLICT` before mutation. Game Design does not infer signer authority or materiality.

Changed-term stale acceptance and the separate non-authoring continuity/lifecycle-reduction paths are target-only under [ADR 0181](../../decisions/adr-0181-changed-hosted-terms-decline-and-existing-content-continuity.md). Current proto/OpenAPI, routes, storage, UI/status, and focused proof do not implement this gate; no future route or schema is selected here. **Current route consequence:** the implemented Gateway still publishes a coarse `/api/design/**` family, so `/api/design/assets` is forwarded through `StripPrefix=2` to the live `POST /assets` controller. The service now returns a structured owner-proof refusal before accessing the multipart file or persistence because Account commit-bound authority is unavailable. This deny-only containment does not evaluate Account currentness or record its evidence binding; official-hosted asset-upload readiness remains blocked until the exact Account-owned gate and its required proof are implemented.

## Draft Commit and Proposal Semantics (Target State)

The eventual creator-facing proto/OpenAPI shape must expose these semantics without treating a private frontend endpoint as a stable public API by accident:

- submitting or accepting a commit/proposal binds its stable identity to the target `tenantId` and `versionId`, exact `baseCommitId`, canonical digest of the complete diff, canonical revision order, and complete affected `(tenantId, versionId, owner, aggregateId, scopeId, epoch)` set;
- exact replay returns the existing result only when every ADR 0129 binding matches: target tenant/version, canonical input/mutation, exact `baseCommitId`, canonical revision order, canonical digest, and the complete affected set. Reusing the identity with any changed or omitted binding field is rejected deterministically as changed-request reuse, even when the digest happens to match;
- a creator-visible status read reports the overall coordination state and each required owner's durable apply outcome for the exact commit/digest;
- normal Draft reads return or require the fully synchronized commit fence and do not expose a partial owner application as current Draft truth;
- stale affected epochs return a typed conflict containing enough current fence/epoch identity to construct a new proposal, but the service never silently rebases or merges it; and
- AI-assisted and external clients use the same proposal acceptance, concurrency, status, and error semantics as ordinary creator tools.

Concrete RPC names, message fields, enums, pagination, and transport exposure remain deferred until the proto/OpenAPI contract is implemented. Whatever shape is selected must preserve the authority and visibility rules in ADR 0129.

For every creator-intent `SaveRevision`, including revision-only requests, the exact Account party, acceptance-evidence, and material-acceptance-generation authorization must remain valid through Game Design's authoritative commit boundary. A preflight Account read alone is insufficient. If the authority is stale, mismatched, unavailable, or uncertain at that boundary, Game Design aborts the local transaction; no creator mutation or staged artifact becomes authoritative or externally reachable, and any staged artifact is cleanup/quarantine state, not success. The implementation must use commit-bound Account authorization/fence or equivalent validation without this contract selecting its mechanism.

For a `SaveRevision` request carrying `worldDesignMutation`, the same authorization invariant additionally applies to every participating authoritative mutation. Participating owners may use prepare or other non-authoritative staging before the authoritative commit boundary, but this contract selects no transaction, lease, fence, saga, route, or schema mechanism. If the boundary cannot be satisfied, no participating owner commits, and SaveRevision must not report success for a partial cross-owner commit.

## Implementation Status

The fresh-tenant owner source includes V29 canonical UUID/provenance storage, V30 exact creation-operation persistence, the owner-local transaction producer and source readback, and the exact Account/Game Session peer receipt read RPC. Validation evidence and remaining gaps belong to the linked implementation tracker. No creator RPC or authenticated creator authority is wired, and no Account association, membership, JOIN, or runtime admission is enabled by this source.

The release-attestation, launch-resolution, version-state, settings, asset-purge, script-patch publication read APIs, and the first plugin publication workflow (`UploadPluginBundle`, `PublishPluginVersion`, `GetPublishedPluginVersion`, and `ListPluginVersionStatuses`) are live in the current proto/service path. The full-version proto carries the exact selected existing Version, expected state epoch, and synchronized commit request/commit/digest. A selected request fails closed before reservation because current Account authorization and an authenticated World owner-freeze producer are unavailable. Independently, the shared command guard denies every fresh and PENDING full-version request before mutation because no production source creates a genuine version-to-Draft association; the configured Temporal orchestrator does not start a new workflow and registered activities propagate the same refusal without writes or synthetic terminal outcomes. The no-selection legacy shape is limited to exact retained terminal replay: FAILED returns the stored attempt result, and SUCCEEDED requires exact immutable release readback. Selected-operation source, staging, export, finalization, and sealing mechanics are private and exercised only through a narrowly named reflective unit harness; they prove conditional mechanics, not current Account authority, World freeze, public capability, or reachable publication success. The four owner-to-owner digest read handlers use the distinct Game Design workload identity, exact method guards, and complete tenant/scope/request binding; this does not establish end-to-end publication authority. Full-version publication remains blocked because Game Logic owner manifest and provenance for rule inputs are absent, Automation's content mapping remains broader than the requested version, and live mounted-certificate, Temporal-activity, and multi-version owner proof remain outstanding (see [Game Logic API Contracts](../game-logic-service/api-contracts.md#implementation-status)). The selected finalizer requires a captured publication operation and same-transaction terminal seal; the legacy five-argument release-bundle entrypoint rejects mutable-revision synthesis. Release storage retains canonical Version identity, an opaque owner reference, manifest schema, artifact digests, and exact persisted readback, but these fields do not establish selected commit provenance or a public tenant projection. `UploadPluginBundle` now parses signed plugin bundles, enforces bounded ZIP intake limits, verifies allowlisted Ed25519 signatures, extracts immutable manifest metadata, persists the raw bundle in Game Design storage, and records a durable `SIGNATURE_VERIFIED` publication row. The live intake currently selects, persists, and exposes one allowlisted `signerKeyId`, not the complete target `verifiedSignatures[]` set; current proto/storage also expose no append-only signature-evidence ledger or append RPC. `PublishPluginVersion` validates the uploaded bundle and requires a published base-version release, applies component policy, exports plugin assets into a version-scoped distribution manifest, and makes a best-effort attempt to supersede older published versions. Its current `abilitySchemaDigest` comparison incorrectly uses the attested `AUTOMATION_SCRIPTING` aggregate participant digest; the target contract requires the dedicated Game Logic-owned ability-schema attestation for the same base version, so exact ability-schema compatibility remains unproved until the release bundle and validator converge. Explicit design-time revoke transitions and a durable append-only plugin publication-event read surface are live too through `RevokePluginVersion` and `ListPluginVersionStatusEvents`; the main remaining follow-through includes the dedicated ability-schema proof and broader activation-time alias/binding validation in owning runtime services. The official-hosted Account currentness evaluation and durable tenant/evidence binding required by [ADR 0180](../../decisions/adr-0180-account-owned-hosted-terms-acceptance-gate.md) are not implemented for any creator mutation class.

The shared deny-only owner-proof boundary also refuses `POST /assets` before multipart access or persistence and refuses state-changing `CompareAndSetVersionState` requests before a Version write. Reads and an exact same-state no-op remain available. These refusals do not implement Account authorization, the legal lifecycle transition matrix, release evidence, or retirement predicates; full-version fresh/PENDING denial and exact terminal replay retain their existing behavior.

The following implementation and proof gaps remain in these live paths:

- Automation's full-version `GetDraftDesignDigest` receives `versionId` but queries tenant-wide script definitions and event bindings, then hashes that entire set alongside the requested identifier. It therefore does not attest the version-scoped script/binding set required by the [version-control digest contract](version-control.md#digest-participants-by-publish-type); until exact mapping exists, the participant must fail closed. Cross-version isolation and wrong-scope digest proof are absent.
- `GetPublishedReleaseBundle` now requires an exact same-namespace Game Session, World Management, or Automation workload identity through its dedicated read guard. This is a workload allowlist only; caller-to-tenant binding and wrong-workload/cross-tenant negative proof remain absent. `ResolveLaunchDescriptor` fails closed pending authored-world source binding; legacy numeric tenant/template/version fields do not authorize launch. `GetVersionState` and `GetVersionAssetArtifactState` still use `requireLaunchAttestationReadAccess`, which accepts any `isInternalService` caller, so their per-RPC workload allowlists, caller-to-tenant binding, and wrong-workload/cross-tenant negative proof remain absent. The target matrix is recorded in [version control](version-control.md#launch-and-attestation-read-authorization-target-state).
- `PublishPluginVersion` has no stable request identity or normalized request digest, serializes neither publication nor supersession, and has no database CAS/one-active constraint. Concurrent publication attempts can therefore both report `PUBLISHED`; deterministic winner/loser and retry proof remain absent. The target contract makes supersession one serialized owner decision, but it is a normal-path attempt attached to the winning publication, not a guarantee that every competing publication attempt supersedes another version.
- `VersionServiceImpl` rejects an uploaded plugin row in terminal `SUPERSEDED` or `REVOKED_DESIGN` state before export or status mutation, so it cannot return to `PUBLISHED` under the same immutable `pluginVersionId`. Rollback/replacement still requires a new `pluginVersionId`, while the prior terminal row remains an immutable audit record; focused `VersionServiceImplTest` proof covers terminal-state rejection, but new-version rollback proof remains absent.
- The live `PublishPluginVersionRequest` carries `distribution_manifest_hash` and `distribution_manifest_path`, but the idempotent comparison self-compares stored values and the normal path replaces both with newly exported values. Those inputs are neither removed nor bound as exact expected values, so a changed retry can replay success. The target write contract must choose one path explicitly: remove generated manifest fields from the request, or include them in the request identity/digest and exact validation.
- Plugin bundle intake validates referenced paths and byte digests but does not reject duplicate signed `assetId` values within one `assetRefs[]` list. Export iterates the list verbatim, so `plugin-distribution-manifest.json` can contain duplicate asset keys. The target boundary rejects duplicate `assetId` values deterministically before publication persistence or object-store export; focused duplicate-intake and duplicate-export proof is absent.
- `PublishedReleaseBundle` retains `tenantId` in the entity/DTO but the current proto has no tenant field and the gRPC mapper does not emit it. Consumers cannot exact-compare the requested `(tenantId, versionId)` against the returned attestation; the target deterministic tenant/version response and fail-closed consumer comparison remain unimplemented.
- `UploadPluginBundle` parses and verifies bytes before it creates a durable publication row or status event. Parse, malformed-manifest, archive-limit, and signature failures therefore cannot produce the target `UPLOAD_REJECTED` row/event, and the request has no stable retry identity or pre-parse raw-upload digest. The target intake boundary must durably record an attempt/rejection before or alongside parsing and compute `rawUploadDigest` as `sha256:<64 lowercase hexadecimal characters>` (SHA-256 over the exact received bytes, with no archive normalization, decompression, or transport metadata) under positive `rawUploadDigestSchemaVersion=1` before archive parsing; the normalized request binds that digest and schema version to the tenant and stable request identity. This raw-upload digest is distinct from the post-parse `bundleDigest` over canonical extracted entries. An identifiable plugin version may receive `UPLOAD_REJECTED`, while malformed or unidentifiable input must remain a tenant/request-scoped durable rejection without inventing plugin identity; exact retries replay only when the complete binding, including the raw-upload digest and schema version, matches, and changed request digests conflict. Focused proof for both identifiable and unidentifiable rejection is absent.

The current script-patch publication/read path is also narrower than the target contract: publication accepts an unvalidated caller-supplied `baseVersionId`, and publication reuse must preserve the effective `(tenantId, baseVersionId, scriptPatchVersion)` identity. Tenant readiness remains keyed by `(tenantId, scriptPatchVersion)` while separately validating immutable `baseVersionId` context, as defined in [Version Control](version-control.md#script-patch-versions-and-runtime-behavior); a separate script-only publication `versionId` is metadata/history and must not be substituted for `baseVersionId`. Game Design now rejects a new publish request when a retained script-only row already owns the effective tenant/base/patch tuple; V27 fails closed on retained incomplete or duplicate tuples and installs partial uniqueness without selecting or deleting a winner. Exact same-request replay still resolves its durable attempt first. Launch resolution and `StartSession` do not prove same-base published patch identity or Automation `READY`. `GetPublishedScriptPatchVersion` requires the complete tuple and its service/digest lookups require exactly one script-only row in retained `PUBLISHED`, `ACTIVE`, or `RETIRED` state for publication metadata; new Game Session pin admission remains independently `PUBLISHED`-only. Callers without authoritative base context fail closed. Notification transport and response failures are swallowed without a durable redrive. The remaining publication, projection, and readiness gaps mean the live APIs must not be treated as complete patch publication or launch-readiness authorities.

The target tenant-scoped `GetTemplateReferencePhase` surface is not implemented: it has no current proto RPC, handler, or durable tenant phase authority. The live launch path checks only each `game_templates.template_reference_phase` value (`ENFORCED` or legacy `LEGACY`), not the target monotonic `BACKFILLING`/`VALIDATED`/`ENFORCED` cutover phase consumed by launch and retirement tooling. The API index below marks this surface target-only; no current launch or retirement proof may treat the per-template field as the target tenant phase.

The live `CompareAndSetVersionState` path now preserves tenant/version lookup, expected-epoch validation, and an exact same-state no-op, but refuses every state-changing request before updating the Version. The deny-only boundary does not implement the target legal transition matrix, require a committed release bundle/artifact for `DRAFT -> PUBLISHED`, or apply retirement predicates for active instances, templates, and in-flight activation. Therefore the live API must not be treated as an activation- or retirement-safe transition authority; transition validation and focused proof remain blocked.

The current `SaveRevision` path is not the complete target Draft-concurrency contract from [ADR 0129](../../decisions/adr-0129-durable-fenced-multi-owner-draft-commits.md). It lacks a Game Design-owned durable commit/proposal record bound to exact base and canonical digest, complete affected-scope capture, per-owner apply status, and a creator-visible synchronized read fence. Owner storage-level compare-and-swap and partial-application isolation also remain implementation and proof gaps.

Asset lifecycle API status requires the same distinction: the target `CompareAndSetVersionState`, `TombstoneVersionAssets`, `BeginPurgeVersionAssets`, `FinalizePurgeVersionAssets`, and `RepairPublishedVersionAssets` contracts require database epoch predicates/locks, affected-row proof, and the shared ADR 0048 operation envelope with caller-supplied identity, canonical digest, exact replay, and conflict outcomes. State-changing `CompareAndSetVersionState` requests now fail closed before Version mutation; its legal transition and database-CAS proof remain unimplemented. Other lifecycle writes still lack the complete operation ledger, and `BeginPurgeVersionAssets` mints a random workflow ID. The target asset upload guardrails (25 MiB file limit, 2 GiB tenant quota, and streaming/chunked transfer) are likewise not implemented or proved: the live upload service now refuses before multipart access or storage because Account commit-bound owner proof is unavailable, so this containment does not establish upload readiness. The API entries below describe target semantics and must not be read as current race-safe or idempotent proof. See [Asset Storage](asset-storage.md#implementation-status) for the current upload, repair, release-bundle, and purge boundaries.

The current SaveRevision ordering is verified in `RevisionServiceImpl` and its focused tests: after Draft/version and payload validation, an optional `worldDesignMutation` is sent to World Management before the Game Design revision entity is mapped and saved. World Management applies the mutation, advances its owner epochs, and writes its revision ledger in its own transaction. A World Management validation or Draft-epoch failure therefore reaches no Game Design revision save; the focused tests verify invalid Game Design payloads and published-version rejection before the client call, while World Management tests verify stale-epoch failure without an aggregate write. If World Management applies successfully but the later Game Design revision save fails, the World mutation, epochs, and ledger can remain committed while the Game Design revision is absent: the separate service transactions provide no cross-owner rollback. This is a current partial-application gap, not an atomicity guarantee.

For retries, World Management's ledger lookup makes the same mutation identity (`tenantId`, version, commit, revision, operation, aggregate type, and requested aggregate) return `NO_OP_ALREADY_APPLIED` without reapplying the world rows; the focused World Management test verifies that replay. SaveRevision then proceeds to its Game Design revision save, which has no matching deduplication lookup or uniqueness constraint (only an index on tenant/version/kind/logical revision), so a completed request retried with the same mutation can create another Game Design revision even though World converges to the existing mutation. A World failure before apply leaves no Game Design revision and retry repeats the failure until its cause is corrected. The repository does not contain focused proof for a Game Design repository failure or an indeterminate transport result after a remote World commit, so those outcomes are not promoted beyond this ordering analysis. Exact retry convergence and synchronized multi-owner visibility remain gaps under ADR 0129.

The live `FinalizePurgeVersionAssets` failure handler also saves `PURGE_FAILED`/failed-workflow markers and then rethrows inside its `@Transactional` method. Spring transaction rollback can therefore discard those markers; if object deletion already succeeded, the durable row may remain `PURGE_IN_PROGRESS` without resumable failure evidence. This is not current retry/resume proof and remains blocked pending an independent durable failure/reconciliation boundary (or equivalent non-rollback record) plus focused proof for deletion and post-delete database-save failures.

When Temporal is disabled or its beans are absent, `PublishVersion` has no synchronous full-version fallback. Fresh and PENDING full-version publication is denied before mutation regardless of Temporal configuration because the command boundary lacks a production version-to-Draft association; the selected public route also lacks current Account authorization and authenticated World owner-freeze evidence. The configured orchestrator does not start a workflow for these requests, and registered activities propagate the refusal without writes or synthetic terminal outcomes. The no-selection legacy shape permits only exact terminal replay: FAILED returns the stored attempt result and SUCCEEDED requires exact immutable release readback. The captured-operation mechanics remain private conditional proof through a reflective unit harness, not evidence of authorization or reachable publication. Legacy replay establishes no Temporal restart durability, workflow run ID, or independent workflow status metadata.

The Temporal owner-authorization seam is implemented at the receiver boundary: each owner digest handler now requires the authenticated Game Design workload peer and exact method allowlist, while the request carries and validates tenant, typed scope, stable publish request, derived workflow identity, and canonical request digest. Temporal activities still do not propagate the initiating operator JWT, and the owner handlers reject JWT-only or user/admin substitution. This closes the former empty-role/admin-guard authorization failure, but does not by itself prove end-to-end Temporal publication: mounted certificate material, the real activity path, and multi-version/cross-tenant owner proof remain required, as do the content-scope gaps recorded above. The canonical authorization and proof requirements are defined in [version control](version-control.md#owner-to-owner-digest-authorization-and-tenant-identity) and [Automation API contracts](../automation-scripting-service/api-contracts.md#game-design-owner-to-owner-digest-authorization).

The published realm-policy owner read is present behind the default-off `firemud.game-design.published-realm-entry-policy-read.enabled` provider. This slice adds only the two `PublishedRealmEntryPolicyService` methods to the base and production bearer-exemption lists; each handler still requires the verified same-namespace Game Session mTLS identity before decoding or owner access. Source and focused test fixtures are present, but final A-dependent compilation, physical PostgreSQL execution, and runtime consumer/activation proof remain unestablished.

It is an implementation seam, not proof that a multi-owner commit is synchronized.
- `ResolvePublishedRealmEntryPolicy` – returns immutable Game Design policy and provenance for one exact canonical tenant/version and world/realm selector pair; it does not compose runtime catalog or admission state.
- `ListPublishedRealmEntryPolicies` – returns the complete bounded policy set and owner-bound count/digest for one exact canonical tenant/version; it does not activate runtime state.
- `PublishVersion` – carries the exact selected existing Version, expected state epoch, and synchronized commit request/commit/digest identity, but fails closed before reservation because current Account authorization and authenticated World owner-freeze evidence are unavailable. The shared command boundary also denies fresh/PENDING requests before mutation until a production Version-to-Draft association exists; configured Temporal ingress uses the same guard, while no-selection requests are limited to exact terminal replay.
- `PublishScriptPatchVersion` – creates a script-only patch version referencing a base version.
- `GetPublishedScriptPatchVersion` – target-authoritative design-time read API for script-patch publication lifecycle and digest identity; current reads reject non-script-only rows and rows outside retained `PUBLISHED`, `ACTIVE`, or `RETIRED` states, while new Game Session pin admission remains independently `PUBLISHED`-only and the remaining publication/readiness gaps are recorded in Implementation Status.
- `UploadPluginBundle` – signed bundle ingestion, archive verification, object-store persistence, and indexed manifest extraction flow.
- `PublishPluginVersion` – promotes a previously uploaded verified bundle into immutable design-time publication after compatibility and policy validation, exporting a plugin distribution manifest when the signed bundle declares `assetRefs[]`.
- `RevokePluginVersion` – transitions a design-time plugin publication to `REVOKED_DESIGN`.
- `ListPluginVersionStatusEvents` – returns bounded, filtered append-only plugin publication status-event history.
- `AppendPluginVersionSignatureEvidence` (target only, signed-intake-only) – appends one verified Ed25519 signature-evidence entry to the Game Design-owned append-only evidence ledger for an existing signed-intake plugin version without changing immutable payload, publication content, status, or `bundleDigest`; it is not an unsigned-intake attestation path.
- `GetPublishedPluginVersion` – authoritative design-time read API for plugin publication lifecycle and compatibility metadata.
- `ListPluginVersionStatuses` – authoritative broader plugin publication listing surface for operator and authoring tooling.
- `ListVersions` – enumerates published versions for selection when creating a game instance.
- `GetVersionState` / `CompareAndSetVersionState` – authoritative control-plane version lifecycle reads and target CAS transitions. These APIs are live in the proto/service path and are the canonical owner for `versionStateEpoch`; state-changing `CompareAndSetVersionState` requests currently fail closed before mutation, and current Version saves do not provide the target database epoch predicate/affected-row fence.
- `GetVersionAssetArtifactState` – live authoritative read of the persisted version-asset artifact lifecycle/proof row; the target read authorization and complete frozen proof remain unimplemented or unproved.
- `AbandonFailedVersionAssets` / `GetFailedVersionAssetAbandonment` – **Target state only; absent from the current proto and implementation:** illustrative owner-local operation/read names for recording and reading durable failed-candidate abandonment proof; see [Asset Storage](asset-storage.md#api).
- `TombstoneVersionAssets` – live lifecycle mutation endpoint, but the current implementation supports only the `FAILED`/`PURGE_FAILED` cases and lacks the target retired-`PUBLISHED` authority checks, durable abandonment proof, and database CAS fence.
- `RepairPublishedVersionAssets` – live lifecycle mutation endpoint, but the current repair path does not yet provide exact durable snapshot/readback proof and can write current version-prefix objects before completing target attestation checks.
- `GetVersionAssetPurgeStatus` – live operator-visible read of persisted purge workflow status; it reports the current workflow surface but does not by itself provide the target destructive-operation replay or reconciliation proof.
- `GetDesignControlPlaneDigest` – digest surface for publish gating over normalized metadata.
- `GetTemplateReferencePhase` – **Target state only; absent from the current proto and implementation:** returns the persisted normalized-reference enforcement phase (`BACKFILLING`, `VALIDATED`, `ENFORCED`) used by instance-creation and retirement workflows.
- `GetPublishedReleaseBundle` – authoritative read surface for immutable release attestation used by activation, cutover preflight, and repair workflows. It also carries the canonical publish workflow identity and workflow-runtime status for operators. `NOT_FOUND` means the target version is not publish-complete; `SCHEMA_VERSION_UNSUPPORTED` means callers must fail closed until they understand the attestation schema.
- `ResolveLaunchDescriptor` – resolves template metadata and control-plane inputs into one immutable launch descriptor for a game-instance creation attempt. The request must include `controlPlaneRequestId`, and repeated calls for the same launch attempt must return the same descriptor values without re-resolving to newer attestation or patch state. The resolved descriptor now carries the real version-state CAS epoch rather than a derived release-bundle surrogate, and deterministic launch-preflight failures such as `RELEASE_BUNDLE_NOT_FOUND` and `LAUNCH_REMAP_REQUIRED` are returned as normal app errors rather than generic invalid-input collapse. When a cross-version replacement launch is valid, the descriptor now freezes the approved persisted `remapSetId` for the source/target version pair.
- `CreateTemplateRemapSet` / `ApproveTemplateRemapSet` / `GetTemplateRemapSet` – authoritative control-plane APIs for persisted version-to-version remap identities and their audit history. Game Design owns the `remapSetId` namespace consumed by replacement launch resolution and later cutover preflight.
- `CanDeleteVersionAssets` – deletion-eligibility oracle for version-scoped asset prefixes.
- `BeginPurgeVersionAssets` – **Target state:** CAS-guarded purge start that atomically re-checks deletion eligibility and transitions `version_asset_artifact` into purge-in-progress state. The current implementation has no database CAS or shared idempotency ledger.
- `FinalizePurgeVersionAssets` – **Target state:** CAS-guarded purge completion that transitions purge-in-progress artifacts to `PURGED` after byte-deletion confirmation. The current implementation has no database CAS or shared idempotency ledger.

When request/response schemas evolve, the proto contract and those architecture sections must be updated in the same change so launch-resolution and template-phase semantics do not drift.

### Authored source genesis and deterministic replay

Game Design records an explicit immutable empty genesis only as part of genuinely new Draft creation. A missing source row is never evidence of empty content. Retained Drafts require a separate audited, authoritative baseline bound to their exact owner target and retained content; unknown or contradictory legacy lineage remains denied. Genesis and retained enrollment are owner evidence, not caller declarations, and neither substitutes for the creator authorization or exact affected-owner fencing required by [ADR 0129](../../decisions/adr-0129-durable-fenced-multi-owner-draft-commits.md).

The closed `game-design-draft-base-reference/v1` grammar admits exactly two forms in the immutable reviewed proposal's `baseCommitId`: `genesis:<canonical receipt UUID>` for the genuinely new Draft's first authored base, or the exact canonical UUID of a retained authored commit. UUIDs are non-nil lower-case canonical text; other prefixes, opaque labels, missing values and ambiguous references deny. The genesis form names the separately persisted shared command/policy receipt, not an authored commit. It never populates actual `commitId`, `sourceCommitId` or `inheritedCommitId` UUID fields.

Before accepting the reviewed proposal, Game Design resolves that exact reference against its own persisted canonical target and Draft. Genesis resolution proves the original shared receipt UUID, creation lineage, receipt kind and version, complete stored policy/command evidence and evidence digest. Authored-base resolution proves the exact retained synchronized commit, complete owner result and source evidence for that target. The complete resolved evidence and digest are frozen with the exact reviewed binding, base, complete diff and affected epochs; retry preserves them byte-for-byte. Wrong-Draft, unknown, mismatched or contradictory receipt, digest or retained commit fails before a new application. Retained Drafts do not acquire inferred empty genesis. A later synchronized change confined to disjoint scopes does not rewrite the reviewed base or itself create a conflict; freshness remains the complete affected-owner epoch check in ADR 0129, not equality with the latest visible commit.

Effective command and policy source is reconstructed deterministically from that proved baseline and the canonical commit/revision order. Each typed upsert or explicit deletion names its stable authored key and preserves the original immutable base, complete diff, revision identity, input digest and affected scope epochs. An omitted row is not a deletion. Partial owner applications remain invisible; only the exact fully synchronized owner fence advances the effective snapshot. Publication freezes the complete effective selected snapshot under the same owner serialization boundary, rather than selecting mutable latest rows or treating the last commit's diff as the full source. Exact retry and readback preserve the original source and capture bytes. No source enrollment or capture grants publication, launch or gameplay authority.

### Published realm-entry policy owner read

Game Design owns typed `REALM_ENTRY_POLICY` source and immutable published policy evidence. The policy data is one closed v1 JSON object with exactly `schemaVersion`, `worldSlug`, `worldDisplayName`, `realmSlug`, `realmDisplayName`, `visible`, `publicProduction`, `stateScope`, and `entryPolicy`. The schema version is integer `1`; all fields are required and typed, without boolean defaults. Slugs are canonical lower-case ASCII selectors of at most 64 characters; display names are trimmed, control-free text of at most 128 Unicode code points. The UTF-8 policy document is bounded to 4096 bytes. Unknown or duplicate JSON fields, malformed values, and unsupported policies deny. V1 supports only `entryPolicy=PRESEEDED_ONLY` with `stateScope=SHARED|ISOLATED`; descriptor and template fields do not belong to this policy.

The [durable Draft coordinator](./version-control.md#design-time-synchronization) owns application and visibility. Source changes bind the complete canonical target, original authored revision and logical identity, exact input/commit digest, and affected policy scope epoch. A selected commit's diff is not the complete effective policy set: Game Design retains the complete synchronized effective snapshot, including unchanged policy provenance inherited from earlier owner applications. Partial owner writes remain invisible. A missing or contradictory owner baseline is denied, not reconstructed from the latest mutable revision, missing rows, slugs or numeric equality. Retained history never acquires inferred source authority.

Publication freezes that exact selected synchronized source and the complete original publication operation once. Source mutation and freeze share the owning Version serialization boundary. The effective published set has at most 128 policies, unique `(worldSlug, realmSlug)` selectors, tenant/version-wide `realmSlug` uniqueness, and exactly one `visible=true && publicProduction=true` policy. Game Design persists separate immutable policy rows and allocates each policy UUID once. Exact retry returns the original identities and bytes; conflicting evidence cannot silently select another source or bundle. Policy evidence binds canonical tenant/version and owner provenance, original source commit/revision/logical identity, the selected source capture, and the genuine sealed publication's workflow, manifest and release-content identity/digest. A source capture alone is not `PUBLISHED`. These separate rows and digests do not rewrite the closed release, terminal, launch-descriptor or release-attestation bytes.

`ResolvePublishedRealmEntryPolicy` proves one exact selector; `ListPublishedRealmEntryPolicies` proves the complete ordered set, exact count and set digest. Both authenticate the same-namespace Game Session workload before decoding or owner access, independently read the exact canonical owner target and its full Version in `PUBLISHED` or `ACTIVE`, and verify the frozen source against the actual sealed publication and immutable release. Missing, contradictory, wrong-operation or mismatched digest evidence denies the complete response. No policy is inferred from a bundle, current mutable revisions or a caller's publication claim. The set read is complete-or-error: a bounded read detects an oversized set instead of returning a truncated prefix, and individual-selector proof cannot substitute for complete-set cardinality. Private owner row keys remain provenance, not public tenant/version identity.

The [published-policy read proto](../../../../protos/game-design/v1/published_realm_entry_policy_service.proto) owns the closed schema-1 wire shape. Each read binds the configured namespace, a distinct non-nil canonical read-request UUID and canonical tenant/Version UUIDs; Resolve additionally binds the exact world and realm selectors. The response echoes that complete read request and carries the complete canonical `game-design-published-realm-policy-evidence/v1` set, not a selector-only fragment. This separate carrier retains the original operation, captured selected source and PUBLISHED terminal bytes, actual immutable release reference/content digest, workflow, manifest and original publication epoch, together with the ordered policy identities, source provenance, count and policy/set digests. It does not extend the closed release or terminal representation. Receivers authenticate Game Design, reject unknown fields, unsupported schemas or changed echoes, and verify every original evidence binding and digest before consuming content; digest integrity alone is not workload authentication.

Published policy evidence alone establishes no runtime catalog, realm UUID, pointer, namespace resolution, lifecycle readiness, Entity assignment or admission. Game Session remains the runtime catalog owner and must compose the policy with its other owner evidence. Missing policy evidence denies that intake without enabling a fallback; [implementation status and proof](../../../project-management/implementation-tracking/game-authoring-publishing-and-activation.md#current-status) remain separate from this target contract.

## REST & gRPC Endpoints

Default ports: REST on `8080`, gRPC on `6565`.

### REST

- `GET /ping` – basic health check returning `"pong"`.
- `POST /assets` – the route remains exposed to the service, but the current service returns a structured owner-proof refusal before accessing the multipart file or persistence. Previously retained asset rows store bytes in `game_assets.data`; publication later exports those bytes to version-scoped object-storage prefixes, while direct content-addressed object-storage upload is target-only. The Gateway-exposed `/api/design/assets` route is not readiness-approved for official-hosted use: this refusal does not evaluate Account currentness or record its evidence binding. Once readiness is established, it is a bypass-safe Game Design creator write when routed externally through Gateway because it is tenant-scoped, domain-local to Game Design, guarded by tenant access checks, and does not depend on Logging & Admin-owned policy or cross-domain write orchestration. Bypass-safe bypasses Logging & Admin only: before any byte or metadata side effect, Game Design must obtain current Account hosted-terms/currentness authority and record `{tenantId, creatorPartyId, acceptanceEvidenceId, generation}` locally.
- `POST /templates` – create a new game template. Its external official-hosted exposure is target-only and must remain unavailable until the hosted-content gate is implemented and its required proof is validated. Once enabled there, it is a bypass-safe Game Design creator write when routed externally through Gateway because it is tenant-scoped, domain-local to Game Design, guarded by tenant access checks, and does not depend on Logging & Admin-owned policy or cross-domain write orchestration. Bypass-safe bypasses Logging & Admin only: before any persistence side effect, Game Design must obtain current Account hosted-terms/currentness authority and record `{tenantId, creatorPartyId, acceptanceEvidenceId, generation}` locally.
- `GET /templates` – list templates for a tenant.

Externally routed Game Design REST paths use the Gateway allowlist prefix (for example `/api/design/assets` and `/api/design/templates`) and are stripped to the service-local paths above before reaching Game Design. #### `AppendPluginVersionSignatureEvidence` (target only)

This target mutation belongs to Game Design and is separate from runtime plugin activation. It is a signed-intake-only supplement to `UploadPluginBundle`: the target row must have entered the lifecycle through the allowlisted Ed25519 signed-intake path, and an unsigned package cannot use this RPC to manufacture signature evidence. Unsigned operator-permitted intake, when implemented under ADR 0111, needs its own platform-acceptance/approval evidence path and is not represented by this signature ledger. For signed intake, the mutation appends to an immutable evidence ledger; it never rewrites the uploaded bundle, signed payload, `pluginVersionId`, `bundleDigest`, publication status, or publication content. It is allowed only while the design-time status is `SIGNATURE_VERIFIED` or `PUBLISHED`; other statuses fail deterministically without mutation. A successful append on a `PUBLISHED` version does not republish or change its status, and an append on `SIGNATURE_VERIFIED` leaves that status unchanged.

The owner first resolves `controlPlaneRequestId` and the normalized request digest: an exact terminal retry returns its stored result before current status/evidence validation, while changed-digest reuse returns `IDEMPOTENCY_CONFLICT` without mutation. Only a new request evaluates current `SIGNATURE_VERIFIED`/`PUBLISHED` eligibility. The owner serializes this mutation with `RevokePluginVersion` status transitions and `PublishPluginVersion` supersession of older versions. Under one owner-row/status-revision transaction, it rechecks status eligibility and commits the duplicate/conflict decision, the ledger append when applicable, the idempotency result, and exactly one `PluginVersionSignatureEvidenceAppended` outbox event if and only if the outcome is `APPENDED`; an identical no-op or conflict has no ledger append or event. Revoke, supersede, and evidence append therefore resolve as one ordered owner decision, never as a partially applied combination.

Signature verification uses the canonical [Signing and Key Lifecycle](modding-framework.md#signing-and-key-lifecycle-required) owner contract: resolve the exact stored immutable `bundleDigest` for `(tenantId, pluginId, pluginVersionId)`, require it to equal the expected `bundleDigest`, and verify the appended Ed25519 entry against the signed-intake-v1 envelope and preimage. The resulting canonical `verifiedSignatures[]` is the complete ordered set of the immutable initial signed-intake evidence plus append-only evidence and retains the owner-defined key metadata; this API defines no separate algorithm, schema, or domain-separator scheme.

Inputs:

- exact `(tenantId, pluginId, pluginVersionId)`;
- expected `bundleDigest`;
- one bounded Ed25519 signed-intake-v1 evidence entry containing the signer identity, signature bytes, and optional creation metadata; and
- a stable `controlPlaneRequestId`.

The normalized request digest includes the complete plugin identity, expected digest, and canonical evidence entry. Outputs return the exact plugin identity, unchanged publication status, immutable `bundleDigest`, the canonical ordered complete `verifiedSignatures[]` set composed from the immutable initial signed-intake evidence plus the append-only ledger, and an `appendOutcome` of `APPENDED` or `IDENTICAL_EVIDENCE_NOOP`. Only `APPENDED` creates one durable `PluginVersionSignatureEvidenceAppended` event; exact retries return the stored result without another append or event. Reusing a request ID with a changed normalized digest is an idempotency conflict. A request carrying identical existing signer evidence is an idempotent no-op; conflicting same-signer evidence, digest mismatch, malformed or over-limit evidence, invalid cryptographic verification, no allowlisted signer, or any revoked signer fails deterministically without mutation.

### Script-patch and plugin transition consequences

`PublishScriptPatchVersion` and `PublishPluginVersion` are design-time publication operations. They persist immutable authoring metadata and compatibility evidence but do not activate a running instance, allocate a script pin epoch, or write rollout history. A patch must pass the normal publication boundary before Automation can perform tenant readiness; readiness still does not imply an instance pin. **Target-state ownership:** Game Session owns the exact instance pin, epoch, and committed append-only rollout/rollback history, while Automation owns readiness, artifact loading, and observed convergence. The current Game Session implementation does not yet prove complete epoch propagation or Game-Session-owned append-only rollout history; see [Game Session API implementation notes](../game-session-service/api-contracts.md#implementation-notes). This document does not claim those target-state consequences are live.

Creator/operator read models must therefore distinguish:

- design-time publication (`PUBLISHED`, or a design-time failure);
- tenant runtime readiness (`READY`, `FAILED`, or an intermediate state) from Automation; and
- the authoritative instance pin/epoch and rollout history from Game Session.

Game Design must not infer a rollback or repin from event arrival, readiness rows, or plugin activation state. Plugin publication and instance activation remain separate API lifecycles, and plugin graphs use the same DSL/sandbox as embedded scripts while retaining independent immutable plugin identity.

The plaintext `Ping` example below is only a local connectivity diagnostic. Published-bundle, launch, and attestation RPCs that require workload identity must use the mTLS profile and their exact same-namespace peer allowlist; plaintext does not establish that identity.

```bash
grpcurl -plaintext localhost:6565 game_design.v1.GameDesignService/Ping
```
