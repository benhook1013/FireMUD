# Game Design Service Operations

## Operational Notes

- Runs as a Kubernetes Deployment (Docker Compose for local dev) with `/actuator/health/readiness` and `/actuator/health/liveness` probes. See [Deployment Environments](../../infrastructure/deployment-environments.md).
- Logging, metrics, and tracing follow the standard [Logging & Monitoring](../../system-architecture-logging-monitoring.md) pipeline.
- Full-version publication of an existing authored Draft is coordinated through the Temporal-backed `publish` workflow family. `PublishVersion` requires a stable `publish_request_id`; the durable workflow gates the selected Draft, commits release evidence, and reconciles the outcome under one caller-visible workflow identity. See [Versioning & Runtime Configuration](../../system-architecture-versioning-runtime.md) for the overall flow.

### Publish request identity and digest binding

Full-version `PublishVersion` selects an existing authored Draft. The immutable `AuthoredDraftPublishSelection` is the canonical binding for the complete caller selection and the synchronized Draft evidence; its `versionId` is supplied at request admission, and reservation does not allocate a replacement Version. Exact retries retain that first selection, while changed or omitted selection input conflicts before workflow attachment. The [Game Design API contract](./api-contracts.md#draft-commit-and-proposal-semantics-target-state) owns the selection fields and evidence. The separate, approved Account publication authorization and complete publication-operation identity must bind to that selection without replacing it; Account's [hosted-terms and creator-party contract](../account-service/api-contracts.md#account-owned-hosted-terms-and-creator-party) owns currentness authority, and World Management's [publication freeze and terminal handoff](../world-management-service/api-contracts.md#publication-freeze-and-terminal-handoff-target-state) owns the World fence. These publication-level bindings remain unimplemented. This adopter behavior follows [ADR 0078](../../decisions/adr-0078-digest-bound-workflow-and-step-retry-identities.md).

**Current implementation status:** the selected full-version `publish_attempt` stores and exact-validates `AuthoredDraftPublishSelection.digest()`, which binds the complete caller selection together with its retained target and synchronized-Draft evidence. The selection and its canonical bytes are stored separately and immutably. This is distinct from `publicationDigestRequest/v1`, which remains the owner-to-owner digest-read request binding and does not replace the selected attempt digest. Public full-version publication still denies before workflow dispatch when Account authorization is unavailable; the separate Account publication operation and complete publication-operation identity are not implemented.

### Publication terminality and attempt ownership

The publication artifact/release-bundle state, allocated version state, participant/release evidence, and publish-attempt terminal state must commit atomically in one Game Design owner-local transaction. If the workflow boundary cannot provide that transaction, the adopter must use an explicit durable state machine with readback reconciliation; it must never expose `SUCCEEDED` until the artifact and version commit is durably readable and bound to the same immutable request and attempt evidence. A terminal attempt is therefore not an acknowledgement that a separate transaction was started: it is the commit/readback proof of the publication state.

**Current implementation status:** full-version publication reserves the selected existing Draft and PENDING attempt in one owner-local transaction. After participant reads and object export, its final owner-local transaction records participant evidence, artifact state, release bundle, Published version, verified digests, and the SUCCEEDED attempt together. An ambiguous final commit is resolved by exact attempt/version/bundle/artifact readback rather than an independent terminal-success transaction. This success path is behind the required participant digest gate: ordinary full-version requests currently cannot reach it because Game Logic rejects the required full-version participant request without an owner-local manifest/provenance digest. The canonical participant gate and current availability are documented in [Version Control](./version-control.md#owner-to-owner-digest-authorization-and-tenant-identity); script-patch publication does not require the Game Logic participant. The ordinary-byte exporter now commits and independently reads its exact private candidate before conditional content-addressed writes and byte readback. This does not prove complete publication-attempt ownership, authenticated terminal settlement, abandonment or cleanup; those gates remain separately open in [Asset Storage](./asset-storage.md#implementation-status).

The existing attempt `FAILED` status and a read showing no release evidence are not immutable publication no-publication proof. Game Design has no publication-specific authenticated terminal readback that fences a delayed finalizer; its [authored-Draft terminal readback](./api-contracts.md#exact-authored-draft-terminal-readback) covers Draft commits, not publication. A missing row or artifact, a `FAILED` status, or a Temporal timeout must therefore remain pending/reconciliation evidence and must not authorize World Management's `ABORTED` handoff. The required publication-specific readback and full-operation binding remain owner-contract and implementation gaps; see the [World publication handoff](../world-management-service/api-contracts.md#publication-freeze-and-terminal-handoff-target-state) and the [Account hosted-creator authority contract](../account-service/api-contracts.md#account-owned-hosted-terms-and-creator-party).

The target publication operation must retain the exact selected-Draft binding and keep its Account authorization and World freeze identity bound to the same stable workflow/request. Allocated artifact/release identity, participant evidence, and the final owner outcome are result evidence for that operation, not replacement caller-input digests; the selected existing Version remains part of the original input. Every attempt transition must CAS the expected status and monotonic attempt revision; only the still-current attempt owner may publish a terminal result. Failure cleanup must conditionally own the same nonterminal attempt and prove the target has not been won or published. Every transition must prevent a delayed finalizer from publishing after an immutable no-publication outcome is recorded. That outcome requires authenticated Game Design owner evidence for the exact operation and World fence; failed status, absent evidence, or timeout alone is never terminal. Same-identity exact retries read back the original selection and operation outcome; changed binding, stale attempt status/revision or contradictory release/Version readback fails closed. Focused proof must cover crashes before and after each commit/readback boundary, concurrent exact retries, changed selection, a losing failure cleanup racing a winning publisher, and a no-publication outcome racing a delayed finalizer.

### External artifact recovery

The target publication boundary treats object-store export as a durable candidate operation: persist `STAGED` export intent before any write, retain a deterministic candidate manifest or incremental durable key evidence, make writes and deletes idempotent, and use a durable cleanup retry/outbox with exact object/readback verification. An ambiguous external result remains nonterminal and reconciliation-required until the candidate and release state are proven; it must not be reported as terminal `FAILED` merely because a storage call timed out. `version_asset_artifact` and the immutable release attestation remain the Game Design authorities; object-store listings alone cannot authorize publication or purge.

**Current implementation boundary:** `AssetExportServiceImpl` selects owner-retained ordinary bytes, records and reads the durable candidate, then uses conditional immutable object puts and exact byte readback. Uncertain export outcomes remain PENDING for reconciliation; final publication readback is separate. A no-publication seal must exclude a delayed release finalizer, but it is not cancellation or deletion proof for an already-running private candidate put. Late private objects remain quarantine/cleanup work and cannot establish release reachability, abandonment or purge eligibility. The [Asset Storage owner contract](./asset-storage.md) and [publishing tracker](../../../project-management/implementation-tracking/game-authoring-publishing-and-activation.md#current-status) retain the distinct current producer boundary and remaining gates.

## Local Development Notes

### One-shot migration startup prerequisites

The Entity baseline and legacy tenant-association Jobs are mutually exclusive one-shot modes. Set only the intended `FIREMUD_ENTITY_BASELINE_MIGRATION_ENABLED` or `FIREMUD_TENANT_ASSOCIATION_MIGRATION_ENABLED` flag. Each Job requires the effective `spring.flyway.enabled` property to be explicitly `false`; startup rejects a missing, true, or invalid value before the Spring context is refreshed. Ordinary Game Design service startup retains its normal Flyway behavior.

Before deploying a Game Design image that includes the canonical tenant identity migration, the Game Design operator must inventory and read back Flyway history for any previously applied draft canonical-identity V30. The identity migration now runs as V30.1 after the retained V30 baseline-lock migration and before V31 associations. A history row whose version or checksum conflicts with the reviewed migration remains blocked pending an explicit database recovery decision; do not rewrite Flyway history, enable out-of-order or baseline repair, infer data, or bypass migration validation automatically.

### Legacy tenant association migration

**Current implementation status:** V31 and the opt-in `TenantAssociationManifestJobRunner` can verify a trusted Ed25519 owner signature over a versioned, byte-length-framed manifest, compare every former Game Design key and canonical UUID with its persisted V30.1 source row, and store/read back the immutable operation and one-to-one associations. The job requires an exact deployment namespace, dedicated `game-design-tenant-migrator` service account and certificate, with listeners and Temporal disabled. It is not a public mutation route and ordinary startup does not import any association. Local focused verifier/gRPC/identity and startup-mode tests execute, and the Docker-free V30/V30.1/V31 uniqueness/order test passes against the service migration resources. The V31 PostgreSQL test executed and passed in hosted CI on a preceding head, but the newly composed migration sequence has not executed against PostgreSQL locally. No real signed manifest, Job deployment, retained-row set, or live readback has been proved.

For an approved operation, first obtain Account's exact retained-source evidence digest from its [Account owner migration mode](../account-service/operations.md#legacy-tenant-association-import). The Game Design owner then reviews the explicit numeric Account key, former Game Design key, V30.1 game row, canonical UUID, namespace, stable operation identity, and Account evidence digest; records the approval reference; and signs the canonical manifest preimage using an owner-controlled key already trusted by the migration job. A preflight verifies the signed bytes and exact namespace without writing. Only an operator-invoked `apply` with that same signed manifest and trusted public-key set writes V31; an exact retry must return the same readback and a conflicting pair fails. Account then imports from the authenticated owner read and checks its retained evidence before the membership consumer can be considered. This order does not enable the disabled runtime membership RPC.

Separately deploy the reviewed V31 schema migration and independently verify its readback before `apply`; missing required storage fails application rather than triggering automatic schema repair. Neither `preflight` nor `apply` runs Flyway; the rendered Job explicitly disables it for every mode. A successful signature-and-namespace-only `preflight` does not verify database schema readiness or replace that separate readback prerequisite.

Each mode requires its own fixed database Secret and authenticated PostgreSQL role: `preflight` uses `firemud-game-design-tenant-preflight-db` as `firemud_game_design_tenant_preflight`, and `apply` uses `firemud-game-design-tenant-apply-db` as `firemud_game_design_tenant_apply`. Both roles may connect only to the selected database; only `apply` may use `game_design_service`. `preflight` verifies the signature and exact namespace only; it performs no owner-table SQL and must not receive schema or table grants. `apply` receives only `SELECT` on the required identity/provenance columns of the Game Design `game` source table and `SELECT`/`INSERT` on the required operation and association fields in `legacy_account_tenant_association_operations` and `legacy_account_tenant_associations`. Neither mode needs `UPDATE`, `DELETE`, sequence, DDL, or lock-function privileges. These credentials are separately provisioned operator inputs, not shared bootstrap, application, or baseline credentials; a missing mode Secret must fail closed, with no optional fallback or chart-created credential. This follows the [Secret Delivery Boundary](../../system-architecture-security.md#secret-delivery-boundary) and [per-service migration ownership](../../system-architecture-database-migrations.md#per-service-organization).

Before enabling the ordinary-disabled Job, the trusted database operator must provision each role without `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION`, or `BYPASSRLS`, ensure it is not `INHERIT` and has no inherited role memberships, and grant no application-object ownership or unrelated-schema access. Independently read back effective memberships, required grants and prohibited grants, and verify that each Secret-authenticated connection is the exact expected role. Retire the scoped role and Secret after the operation and its recovery window. A rendered Job, Helm check, or role-name assertion is not live grant, Secret-authentication, or PostgreSQL readback proof.

The chart's `previewStack.tenantAssociationMigration.gameDesign` values are disabled by default. A trusted operator supplies an immutable Game Design image digest, exact namespace, stable run ID, mode, signed-manifest Secret and trusted-key Secret. Explicitly issue and verify the stable `firemud-grpc-game-design-tenant-migrator` identity using `ensure-standalone-transport-certificates.sh --game-design-tenant-migrator` and `--verify-game-design-tenant-migrator` before enabling the Job; the ordinary Game Design certificate is not a fallback. This dedicated certificate is a workload attestation guard, not an outbound owner-read credential. The Job has no Kubernetes API token or ingress and only DNS/Postgres egress; no ordinary Helm release creates it. Disable the Job after use and retire its exact certificate and Secret through the trusted operator boundary. A rendered Job is not executed migration proof: the live certificate, trusted Secrets, actual manifest, PostgreSQL readback and Account import still require deployment proof. Do not describe this path as an applied data migration until those checks execute.

### Historical Entity digest baseline migration

Enumeration reports retained Entity full-version v1 baselines that resolve to a script-only Version as `BLOCKED_SCRIPT_ONLY`, not as migratable full versions. Exact preflight and migration continue to reject those scopes with `VERSION_SCOPE_MISMATCH`; enumeration neither repairs the anomalous row nor changes its provenance.

**Current implementation status:** The one-shot Game Design maintenance Job and guarded owner-local v1→v2 baseline transition are implemented, but no retained row set or live certificate/consumer/readback outcome has been verified by this document. A retained v1 scope whose authoritative Version is `DRAFT` is reported as `BLOCKED_DRAFT`; migrate rejects it before the Entity digest read and locks/rechecks Version state at the baseline-and-audit write boundary. A no-data scope, existing v2 row, ambiguous scope, or unsupported schema retains its separate preflight classification. This does not freeze live authoring. Publication quiescence drains publication work only and must not be treated as an authoring freeze or proof that DRAFT content cannot change. The Job is disabled in ordinary Helm releases and must be invoked only from a trusted operator context, using a reviewed immutable Game Design image digest. It is not a public API, a general admin role, or a PR-controlled executor. Its dedicated `game-design-baseline-migrator` Kubernetes service account has no Kubernetes API verbs, and its separate client certificate may read only Entity Management's bound `GetDraftDesignDigest` RPC. No Game Design, Account, or Game Session mutation API is delegated to that identity. The Job only writes Game Design's own baseline and audit tables through its guarded service operation; it never accesses Entity's database.

Use a controlled pre-v1 publication window for the affected Entity v1 full-version scopes. Drain in-flight publication and prevent new publication on those scopes before comparing rows or deploying the writer. Deploy the migration-capable Game Design reader/reconciler image first so retained stored v1 and v2 baseline shapes can be inspected; its publish gate still requires v2 and never compares v1 content with v2 content. Then deploy Entity's v2 producer image. Because #2872 already has a v2-only gate, deploying it alone may temporarily block affected v1 publication; this is an accepted fail-closed maintenance window, not seamless dual-reader availability. Verify actual service image digests and deployment order before proceeding; if the image topology cannot maintain that sequence, stop instead of relaxing the gate. The current Entity applied-commit token is synthetic `version:<versionId>` and does not prove durable applied-revision convergence.

Before invoking a Job, verify the exact Kubernetes context and namespace, the authorized operator identity and approved maintenance window, both current service image digests, database backup/recovery posture, completed in-flight publication drain, and the dedicated migrator certificate's issuer, `Ready` state, URI SAN, trust chain, projected Secret, and actual mTLS acceptance at Entity. The hosted trust/controller admission policy includes a narrow runtime-namespace exception for this identity; it does not make the migrator one of the controller's permanent certificate consumers. A trusted certificate writer must explicitly invoke `ensure-standalone-transport-certificates.sh --migrator <runtime-namespace>`; a separately authorized Secret-read operator then invokes `--verify-migrator <runtime-namespace>` before the Job is enabled. The certificate writer's service account has no Secret-read permission. These opt-in operations do not alter ordinary preview transport-certificate rollout. A rendered Certificate or Secret name alone is not issuance or served-identity proof. The trusted operator must create an immutable expected-source ConfigMap or Secret from a read-only exact database row, including baseline ID, tenant, `FULL_VERSION`, `ENTITY_MANAGEMENT`, null base version, version scope, applied commit, digest, schema `1`, and both workflow IDs and timestamps. Do not place this manifest, credentials, or raw retained row values in a PR or CI artifact. Check that the source object is immutable before applying the Job. The Job's `targetNamespace`, tenant/version, operation ID, actor identity, and expected-source object are all fixed for that invocation; a changed command gets a new operation ID, never a reinterpretation of the old one. `actorIdentity` is an operator-supplied audit claim, not an identity attested by the Job's workload certificate. Preserve the trusted deployment audit identifying the authenticated human operator and correlate its Job UID, operation ID, values/image revision, and time with the Game Design before/after audit row; do not use that row alone as proof of the human operator's identity.

The chart's `previewStack.entityDigestBaselineMigration` values are disabled by default. From the trusted operator revision, supply an image pinned as `repository@sha256:<digest>`, exact `targetNamespace`, the dedicated `firemud-grpc-game-design-baseline-migrator` Secret, and `mode`. The chart requires the separately provisioned `firemud-game-design-baseline-reader-db` Secret for `enumerate` and `preflight`, and `firemud-game-design-baseline-writer-db` for `migrate`; both must provide `FIREMUD_POSTGRES_USER` and `FIREMUD_POSTGRES_PASSWORD`. A trusted database operator provisions these least-privilege credentials; the chart does not create them, and the Job never consumes the shared `firemud-secret` bootstrap credentials. The migration Job disables Flyway. `enumerate` returns at most 500 Entity schema-v1 full-version rows after one baseline ID and reports each scope's migration status, including `BLOCKED_DRAFT`; repeat with its returned keyset cursor until an empty page proves no more rows at the quiesced snapshot. `preflight` classifies one exact tenant/version as v1, v2, absent, ambiguous, unsupported, or `BLOCKED_DRAFT`, and refuses a missing or script-only Version. `migrate` requires one stable operation ID, exact tenant/version, actor identity, and the immutable expected-source object. It rejects a DRAFT Version before reading the Entity digest, captures the non-DRAFT Version's state epoch, then locks the Version row and requires both non-DRAFT state and the same epoch in the transaction that performs the guarded baseline update and audit insertion. A lifecycle transition during the external digest read therefore fails closed before either write, even if the Version returns to Published. This guard does not freeze authoring while the external digest is read. The Java runner verifies its namespace, dedicated service account, and certificate URI identity before reading or writing. A missing identity, policy, input, row, version, exact-old match, or v2 Entity response fails closed. Render and inspect the operator overlay before installation; do not leave `enabled: true` in the ordinary chart values or an unattended release upgrade. Completed Jobs are deliberately not Helm hooks, so an unchanged upgrade does not rerun them; a changed immutable Job spec is rejected and needs an explicit trusted disposition.

Before enabling the Job, a trusted database operator provisions `firemud_game_design_baseline_reader` and `firemud_game_design_baseline_writer` as separate login roles with no superuser, database/role-creation, replication, bypass-RLS, inherited-role, or application-object ownership powers. Both may connect to the selected database, use `game_design_service`, and select only Game Design `version` and `publish_recorded_participant_digest`; the writer additionally needs audit-table select/insert, usage/select on `entity_digest_baseline_migration_audit_id_seq`, and column-limited update of only `applied_commit_id`, `content_digest`, and `digest_schema_version` on the baseline table. Neither role gets Entity or another service's schema access, Version or Flyway-history writes, baseline insert/delete, broad table grants, or DDL. V30 creates a Game Design-owned `SECURITY DEFINER` function that locks and reads only the exact tenant/version row for the guarded migration transaction, with public execute revoked. After V30 is applied and the restricted roles exist, the trusted database operator grants `EXECUTE` on `game_design_service.lock_version_for_entity_digest_baseline_migration(VARCHAR(36), BIGINT)` only to the writer; the reader and public roles must remain denied. This narrow call replaces direct `SELECT ... FOR UPDATE`, which requires Version UPDATE privilege even when the Job changes no Version column. Revoke broader/default grants first, then read back effective role attributes, memberships, ownership, table/column/sequence/function grants, and denied direct Version lock/update operations as the restricted users. Verify the mode-specific Secret's exact username/password authentication and V29, V30, and V30.1 presence before live activation; a rendered Secret reference is not proof of those facts. Retire both Secrets and roles after final database readback and the approved rollback window.

For each affected scope, retain the preflight row ID and complete source tuple privately, run `migrate`, and require its reported operation/audit/baseline IDs and disposition. The Game Design transaction conditionally replaces the exact old row and inserts an immutable before/after audit atomically. The live row retains its original and last real publish-workflow IDs and timestamps; only the audit's operation ID and committed time describe the maintenance transition.
