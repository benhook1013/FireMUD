# Game Design Service Operations

## Operational Notes

- Runs as a Kubernetes Deployment (Docker Compose for local dev) with `/actuator/health/readiness` and `/actuator/health/liveness` probes. See [Deployment Environments](../../infrastructure/deployment-environments.md).
- Logging, metrics, and tracing follow the standard [Logging & Monitoring](../../system-architecture-logging-monitoring.md) pipeline.
- Publishing a game version is coordinated through the Temporal-backed `publish` workflow family. The synchronous `PublishVersion` API now requires a stable `publish_request_id`, while the durable workflow performs version metadata creation, participant digest gating, release attestation, and publish reconciliation under one caller-visible workflow identity. See [Versioning & Runtime Configuration](../../system-architecture-versioning-runtime.md) for the overall flow.

### Publish request identity and digest binding

The target publish contract binds the stable `publish_request_id` to one canonical request digest. Game Design normalizes the complete preallocation caller intent, including `tenantId`, publish type, `notes`, and any other actual request inputs, before computing and durably recording that digest with the workflow/attempt identity. The owner-allocated `versionId` is not an input to that original digest because it does not exist at request admission; after allocation, it is immutable attempt/result evidence bound durably to the same workflow identity and exact replay/readback. A retry with the same `publish_request_id` and the same preallocation-intent digest may attach to or replay the existing workflow and recorded outcome. Reuse of that identity with a different digest is an identity conflict: it must fail closed without executing the new request or returning the prior outcome as though the requests matched. This is the Game Design adopter mapping of [ADR 0078](../../decisions/adr-0078-digest-bound-workflow-and-step-retry-identities.md).

**Current implementation gap:** `PublishWorkflowRequest` and the `publish_attempt` persistence currently carry no immutable normalized preallocation-intent digest or exact comparison. Temporal `AlreadyStarted` handling and existing-attempt reconciliation therefore reuse `publishWorkflowId` without comparing normalized caller intent; although the attempt stores the allocated `versionId`, it does not bind that result evidence to a request digest. The current implementation must not be treated as proof of the target different-digest conflict behavior; code and focused proof remain a future implementation gap tracked with the shared runtime contract.

### Publication terminality and attempt ownership

The publication artifact/release-bundle state, allocated version state, participant/release evidence, and publish-attempt terminal state must commit atomically in one Game Design owner-local transaction. If the workflow boundary cannot provide that transaction, the adopter must use an explicit durable state machine with readback reconciliation; it must never expose `SUCCEEDED` until the artifact and version commit is durably readable and bound to the same immutable request and attempt evidence. A terminal attempt is therefore not an acknowledgement that a separate transaction was started: it is the commit/readback proof of the publication state.

**Current implementation gap:** `VersionPublishCommandServiceImpl` writes publication state and then calls `PublishAttemptServiceImpl.markSucceeded`, whose `REQUIRES_NEW` transaction can commit the attempt terminal state independently of the outer artifact/version transaction. The same `REQUIRES_NEW` boundary is used by `createAttempt` and `recordParticipantDigests`: an outer version rollback can therefore leave an attempt and participant rows committed with no committed version (the script-patch path has the same ordering). `publish_attempt.version_id` has no referential constraint to prevent that orphan. `PublishAttemptRepository` updates attempts by id without status/revision compare-and-set (CAS), and the failure path can mark failure and clean up while a concurrent publisher has already won. The current path consequently does not prove that `SUCCEEDED` is coupled to the artifact/version commit, that a failed preallocation can be recovered, or that losing cleanup cannot delete a winning publication.

The target attempt record must immutably bind the normalized preallocation request digest, workflow/request identity, allocated version, artifact/release identity, and owner evidence. Every attempt transition must CAS both the expected status and monotonic attempt revision; only the still-current attempt owner may publish a terminal result. Failure cleanup may delete or mark provisional state only when it conditionally owns the same still-current nonterminal attempt and the target has not been won or published. Same-identity/same-digest retries must read back and replay the existing state; a different digest, stale revision/status, or contradictory artifact/version readback fails closed. Focused proof must cover crashes before and after each commit/readback boundary, concurrent exact retries, different-digest reuse, and a losing failure cleanup racing a winning publisher.

### External artifact recovery

The target publication boundary treats object-store export as a durable candidate operation: persist `STAGED` export intent before any write, retain a deterministic candidate manifest or incremental durable key evidence, make writes and deletes idempotent, and use a durable cleanup retry/outbox with exact object/readback verification. An ambiguous external result remains nonterminal and reconciliation-required until the candidate and release state are proven; it must not be reported as terminal `FAILED` merely because a storage call timed out. `version_asset_artifact` and the immutable release attestation remain the Game Design authorities; object-store listings alone cannot authorize publication or purge.

**Current implementation gap:** `AssetExportServiceImpl` writes directly to S3-compatible storage before the artifact row receives the exported manifest. If an asset or manifest write fails, `VersionPublishCommandServiceImpl` has no manifest to record or clean up; if later cleanup fails, it is only logged. The Temporal activity catches these failures and returns terminal `FAILED`, so ambiguous partial exports have no durable recovery authority. The current direct-prefix implementation is therefore not proof of the target `STAGED`/candidate/reconciliation contract described in [Asset Storage](./asset-storage.md).

## Local Development Notes

`TestDataSeeder` populates a demo game, template, revision and version only when explicit smoke/runtime seeding is enabled through deployment config (`FIREMUD_SMOKE_SEED_DEMO_RUNTIME_ENABLED=true` in the local Compose smoke stack). Run `services/game-design-service/smoke-test.sh` to verify both REST and gRPC endpoints. The lightweight maintained application smoke now lives under `src/test/java/integration`; the old disabled GHCR-based cross-service placeholder was removed because it did not prove a meaningful current contract.
