# Game Design Service Operations

## Operational Notes

- Runs as a Kubernetes Deployment (Docker Compose for local dev) with `/actuator/health/readiness` and `/actuator/health/liveness` probes. See [Deployment Environments](../../infrastructure/deployment-environments.md).
- Logging, metrics, and tracing follow the standard [Logging & Monitoring](../../system-architecture-logging-monitoring.md) pipeline.
- Publishing a game version is coordinated through the Temporal-backed `publish` workflow family. The synchronous `PublishVersion` API now requires a stable `publish_request_id`, while the durable workflow performs version metadata creation, participant digest gating, release attestation, and publish reconciliation under one caller-visible workflow identity. See [Versioning & Runtime Configuration](../../system-architecture-versioning-runtime.md) for the overall flow.

### Publish request identity and digest binding

The target publish contract binds the stable `publish_request_id` to one canonical request digest. Game Design normalizes the complete preallocation caller intent, including `tenantId`, publish type, `notes`, and any other actual request inputs, before computing and durably recording that digest with the workflow/attempt identity. The owner-allocated `versionId` is not an input to that original digest because it does not exist at request admission; after allocation, it is immutable attempt/result evidence bound durably to the same workflow identity and exact replay/readback. A retry with the same `publish_request_id` and the same preallocation-intent digest may attach to or replay the existing workflow and recorded outcome. Reuse of that identity with a different digest is an identity conflict: it must fail closed without executing the new request or returning the prior outcome as though the requests matched. This is the Game Design adopter mapping of [ADR 0078](../../decisions/adr-0078-digest-bound-workflow-and-step-retry-identities.md).

**Current implementation status:** the full-version `publish_attempt` stores and exact-validates `publicationDigestRequest/v1`, binding tenant, allocated version scope, stable publish request, and derived workflow identity. That is the owner-to-owner publication-read binding and intentionally excludes notes and content. Game Design does not yet persist and compare the separate preallocation control-plane content digest that binds notes and every other caller input before version allocation. Temporal `AlreadyStarted` handling can therefore attach a changed-notes request to the same workflow identity even though its publication-read digest still matches. The current implementation proves the scoped owner-read binding, not the target different-control-plane-content conflict behavior.

### Publication terminality and attempt ownership

The publication artifact/release-bundle state, allocated version state, participant/release evidence, and publish-attempt terminal state must commit atomically in one Game Design owner-local transaction. If the workflow boundary cannot provide that transaction, the adopter must use an explicit durable state machine with readback reconciliation; it must never expose `SUCCEEDED` until the artifact and version commit is durably readable and bound to the same immutable request and attempt evidence. A terminal attempt is therefore not an acknowledgement that a separate transaction was started: it is the commit/readback proof of the publication state.

**Current implementation status:** full-version publication reserves its Draft version and PENDING attempt in one owner-local transaction. After participant reads and object export, its final owner-local transaction records participant evidence, artifact state, release bundle, Published version, verified digests, and the SUCCEEDED attempt together. An ambiguous final commit is resolved by exact attempt/version/bundle/artifact readback rather than an independent terminal-success transaction. This implemented success path is behind the required participant digest gate: ordinary full-version requests currently cannot reach it because Game Logic rejects the required full-version participant request without an owner-local manifest/provenance digest. The canonical participant gate and current availability are documented in [Version Control](./version-control.md#owner-to-owner-digest-authorization-and-tenant-identity); script-patch publication does not require the Game Logic participant. The remaining gap is the external phase: participant collection and mutable object-key export occur before that final transaction without a durable external-phase owner, private candidate namespace, or export deduplication. Same-request retries can therefore race before the final Game row lock; a late exporter can overwrite bytes after another attempt's release attestation, while definite-failure cleanup can race an active exporter. The final local transaction does not prove safe external-write ownership, cleanup, or ambiguous object-store recovery.

The target attempt record must immutably bind the normalized preallocation request digest, workflow/request identity, allocated version, artifact/release identity, and owner evidence. Every attempt transition must CAS both the expected status and monotonic attempt revision; only the still-current attempt owner may publish a terminal result. Failure cleanup may delete or mark provisional state only when it conditionally owns the same still-current nonterminal attempt and the target has not been won or published. Same-identity/same-digest retries must read back and replay the existing state; a different digest, stale revision/status, or contradictory artifact/version readback fails closed. Focused proof must cover crashes before and after each commit/readback boundary, concurrent exact retries, different-digest reuse, and a losing failure cleanup racing a winning publisher.

### External artifact recovery

The target publication boundary treats object-store export as a durable candidate operation: persist `STAGED` export intent before any write, retain a deterministic candidate manifest or incremental durable key evidence, make writes and deletes idempotent, and use a durable cleanup retry/outbox with exact object/readback verification. An ambiguous external result remains nonterminal and reconciliation-required until the candidate and release state are proven; it must not be reported as terminal `FAILED` merely because a storage call timed out. `version_asset_artifact` and the immutable release attestation remain the Game Design authorities; object-store listings alone cannot authorize publication or purge.

**Current implementation gap:** `AssetExportServiceImpl` writes directly to S3-compatible storage before the artifact row receives the exported manifest. If an asset or manifest write fails, `VersionPublishCommandServiceImpl` has no manifest to record or clean up; if later cleanup fails, it is only logged. `VersionPublishCommandServiceImpl` normally records terminal `FAILED` and returns the attempt snapshot for publication failures; `TemporalVersionPublishActivitiesImpl` catches only `PendingReconciliationException` and returns `PENDING`. A partial export before manifest persistence can therefore lack durable cleanup and failure evidence. The current direct-prefix implementation is not proof of the target `STAGED`/candidate/reconciliation contract described in [Asset Storage](./asset-storage.md).

## Local Development Notes

### Historical Entity digest baseline migration

Enumeration reports retained Entity full-version v1 baselines that resolve to a script-only Version as `BLOCKED_SCRIPT_ONLY`, not as migratable full versions. Exact preflight and migration continue to reject those scopes with `VERSION_SCOPE_MISMATCH`; enumeration neither repairs the anomalous row nor changes its provenance.

**Current implementation status:** The one-shot Game Design maintenance Job and guarded owner-local v1→v2 baseline transition are implemented, but no retained row set or live certificate/consumer/readback outcome has been verified by this document. A retained v1 scope whose authoritative Version is `DRAFT` is reported as `BLOCKED_DRAFT`; migrate rejects it before the Entity digest read and locks/rechecks Version state at the baseline-and-audit write boundary. A no-data scope, existing v2 row, ambiguous scope, or unsupported schema retains its separate preflight classification. This does not freeze live authoring. Publication quiescence drains publication work only and must not be treated as an authoring freeze or proof that DRAFT content cannot change. The Job is disabled in ordinary Helm releases and must be invoked only from a trusted operator context, using a reviewed immutable Game Design image digest. It is not a public API, a general admin role, or a PR-controlled executor. Its dedicated `game-design-baseline-migrator` Kubernetes service account has no Kubernetes API verbs, and its separate client certificate may read only Entity Management's bound `GetDraftDesignDigest` RPC. No Game Design, Account, or Game Session mutation API is delegated to that identity. The Job only writes Game Design's own baseline and audit tables through its guarded service operation; it never accesses Entity's database.

Use a controlled pre-v1 publication window for the affected Entity v1 full-version scopes. Drain in-flight publication and prevent new publication on those scopes before comparing rows or deploying the writer. Deploy the migration-capable Game Design reader/reconciler image first so retained stored v1 and v2 baseline shapes can be inspected; its publish gate still requires v2 and never compares v1 content with v2 content. Then deploy Entity's v2 producer image. Because #2872 already has a v2-only gate, deploying it alone may temporarily block affected v1 publication; this is an accepted fail-closed maintenance window, not seamless dual-reader availability. Verify actual service image digests and deployment order before proceeding; if the image topology cannot maintain that sequence, stop instead of relaxing the gate. The current Entity applied-commit token is synthetic `version:<versionId>` and does not prove durable applied-revision convergence.

Before invoking a Job, verify the exact Kubernetes context and namespace, the authorized operator identity and approved maintenance window, both current service image digests, database backup/recovery posture, completed in-flight publication drain, and the dedicated migrator certificate's issuer, `Ready` state, URI SAN, trust chain, projected Secret, and actual mTLS acceptance at Entity. The hosted trust/controller admission policy includes a narrow runtime-namespace exception for this identity; it does not make the migrator one of the controller's permanent certificate consumers. A trusted certificate writer must explicitly invoke `ensure-standalone-transport-certificates.sh --migrator <runtime-namespace>`; a separately authorized Secret-read operator then invokes `--verify-migrator <runtime-namespace>` before the Job is enabled. The certificate writer's service account has no Secret-read permission. These opt-in operations do not alter ordinary preview transport-certificate rollout. A rendered Certificate or Secret name alone is not issuance or served-identity proof. The trusted operator must create an immutable expected-source ConfigMap or Secret from a read-only exact database row, including baseline ID, tenant, `FULL_VERSION`, `ENTITY_MANAGEMENT`, null base version, version scope, applied commit, digest, schema `1`, and both workflow IDs and timestamps. Do not place this manifest, credentials, or raw retained row values in a PR or CI artifact. Check that the source object is immutable before applying the Job. The Job's `targetNamespace`, tenant/version, operation ID, actor identity, and expected-source object are all fixed for that invocation; a changed command gets a new operation ID, never a reinterpretation of the old one. `actorIdentity` is an operator-supplied audit claim, not an identity attested by the Job's workload certificate. Preserve the trusted deployment audit identifying the authenticated human operator and correlate its Job UID, operation ID, values/image revision, and time with the Game Design before/after audit row; do not use that row alone as proof of the human operator's identity.

The chart's `previewStack.entityDigestBaselineMigration` values are disabled by default. From the trusted operator revision, supply an image pinned as `repository@sha256:<digest>`, exact `targetNamespace`, the dedicated `firemud-grpc-game-design-baseline-migrator` Secret, and `mode`. The chart requires the separately provisioned `firemud-game-design-baseline-reader-db` Secret for `enumerate` and `preflight`, and `firemud-game-design-baseline-writer-db` for `migrate`; both must provide `FIREMUD_POSTGRES_USER` and `FIREMUD_POSTGRES_PASSWORD`. A trusted database operator provisions these least-privilege credentials; the chart does not create them, and the Job never consumes the shared `firemud-secret` bootstrap credentials. The migration Job disables Flyway. `enumerate` returns at most 500 Entity schema-v1 full-version rows after one baseline ID and reports each scope's migration status, including `BLOCKED_DRAFT`; repeat with its returned keyset cursor until an empty page proves no more rows at the quiesced snapshot. `preflight` classifies one exact tenant/version as v1, v2, absent, ambiguous, unsupported, or `BLOCKED_DRAFT`, and refuses a missing or script-only Version. `migrate` requires one stable operation ID, exact tenant/version, actor identity, and the immutable expected-source object. It rejects a DRAFT Version before reading the Entity digest, captures the non-DRAFT Version's state epoch, then locks the Version row and requires both non-DRAFT state and the same epoch in the transaction that performs the guarded baseline update and audit insertion. A lifecycle transition during the external digest read therefore fails closed before either write, even if the Version returns to Published. This guard does not freeze authoring while the external digest is read. The Java runner verifies its namespace, dedicated service account, and certificate URI identity before reading or writing. A missing identity, policy, input, row, version, exact-old match, or v2 Entity response fails closed. Render and inspect the operator overlay before installation; do not leave `enabled: true` in the ordinary chart values or an unattended release upgrade. Completed Jobs are deliberately not Helm hooks, so an unchanged upgrade does not rerun them; a changed immutable Job spec is rejected and needs an explicit trusted disposition.

Before enabling the Job, a trusted database operator provisions `firemud_game_design_baseline_reader` and `firemud_game_design_baseline_writer` as separate login roles with no superuser, database/role-creation, replication, bypass-RLS, inherited-role, or application-object ownership powers. Both may connect to the selected database, use `game_design_service`, and select only Game Design `version` and `publish_recorded_participant_digest`; the writer additionally needs audit-table select/insert, usage/select on `entity_digest_baseline_migration_audit_id_seq`, and column-limited update of only `applied_commit_id`, `content_digest`, and `digest_schema_version` on the baseline table. Neither role gets Entity or another service's schema access, Version or Flyway-history writes, baseline insert/delete, broad table grants, or DDL. V30 creates a Game Design-owned `SECURITY DEFINER` function that locks and reads only the exact tenant/version row for the guarded migration transaction, with public execute revoked. After V30 is applied and the restricted roles exist, the trusted database operator grants `EXECUTE` on `game_design_service.lock_version_for_entity_digest_baseline_migration(VARCHAR(36), BIGINT)` only to the writer; the reader and public roles must remain denied. This narrow call replaces direct `SELECT ... FOR UPDATE`, which requires Version UPDATE privilege even when the Job changes no Version column. Revoke broader/default grants first, then read back effective role attributes, memberships, ownership, table/column/sequence/function grants, and denied direct Version lock/update operations as the restricted users. Verify the mode-specific Secret's exact username/password authentication and both V29 and V30 presence before live activation; a rendered Secret reference is not proof of those facts. Retire both Secrets and roles after final database readback and the approved rollback window.

For each affected scope, retain the preflight row ID and complete source tuple privately, run `migrate`, and require its reported operation/audit/baseline IDs and disposition. The Game Design transaction conditionally replaces the exact old row and inserts an immutable before/after audit atomically. The live row retains its original and last real publish-workflow IDs and timestamps; only the audit's operation ID and committed time describe the maintenance transition. An exact retry of the same operation reads the existing audit and baseline rather than writing again; a lost acknowledgement is resolved by that same operation identity and exact readback. A changed source, ambiguous scope, different actor/workload binding, mismatched Entity v2 schema/scope/digest/commit, or unproved write outcome is a stop condition. Independently read back `publish_recorded_participant_digest` by baseline ID and `entity_digest_baseline_migration_audit` by operation ID from Game Design's PostgreSQL schema; compare the new schema/digest/commit and preserved publish provenance, complete old tuple, observed v2 tuple, migration operation, actor/workload, outcome, and timestamp exactly. Never count Job completion alone as database proof. Keep the before/after records with the private migration log, excluding secrets and certificate keys.

If no retained Entity v1 rows exist, record the exact namespace, database/schema, query time, quiescence evidence, and an empty bounded enumeration through its terminal page; separately preflight every affected known tenant/version scope and record its state. This is a no-data boundary, not a claim that migration ran. If a migration fails or proof is incomplete, leave affected publication closed and retain the old row/audit evidence; do not restore a v1 hash over an audited v2 row or weaken the v2 publish gate. Resume only after an exact retry/readback or an explicit database recovery decision with equivalent provenance. After the approved work and readback are complete, disable the Helm migration Job and have an authorized `system:masters` operator explicitly retire its exact dedicated Certificate and Secret; the scoped writer cannot delete them. Retain the database audit and private operation evidence. Do not leave the one-shot workload identity provisioned as an ordinary Game Design credential.
