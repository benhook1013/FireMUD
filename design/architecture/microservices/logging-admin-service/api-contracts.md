# Logging & Admin Service API Contracts

This document defines the Logging & Admin Service REST and gRPC surfaces, authentication classes, and endpoint availability expectations.

## Implementation Status

- Feature-flag toggles and scoped tick-remediation pause/resume forwarding have implementation paths but are unavailable as supported operator mutations until all three parts of the mutation gate exist: their action-family schemas, shared cross-language `mutationDigest/v1` golden vectors, and Account-issued authorization-reference issuance plus redemption by the receiving authoritative owner. Admission-pointer reads, audit, and prepared-upgrade proof reads remain live. Public POST/operator mutation routes under `/admission-pointers`, `/cutover`, or `/version-upgrades` are target-only absent: no public HTTP handlers or Gateway write forwarding exist. Internal preparation/cutover service and control-plane implementation remains behind internal trust boundaries, and there is no current UI control.
- Availability vocabulary is explicit: **implemented-but-externally-gated** means an executable public controller/owner path exists but the shared mutation gate is incomplete; **target-only absent** means no executable public route exists. Admission-pointer mutation, version-upgrade preparation, and prepared cutover use the latter classification at public HTTP ingress even though internal preparation/cutover implementation remains. Quota-override ingress and broader tick-remediation `remediate` are also target-only absent families.
- No forwarded owner mutation is currently supported as a live Logging & Admin capability until its action-family schema, shared cross-language `mutationDigest/v1` golden vectors, and Account-issued authorization-reference issuance plus redemption by the receiving authoritative owner exist. The service-local `POST /moderation/actions` endpoint is an unavailable/gated human mutation owned by Logging & Admin for persistence and audit; it is not Gateway-forwarded and is not supported at external ingress. `ApplyModerationAction` is its corresponding unavailable/gated gRPC path until its action-family schema, shared vectors, Account authorization-reference issuance, and Logging & Admin receiving-boundary validation/redemption exist. That persistence path does not use owner forwarding, separate domain-owner redemption, or domain-owner enforcement. Game Session and Social & Groups synchronously consume the live `EvaluateModerationPolicy` read at the `GAMEPLAY_ADMISSION` and `CHAT_SEND` enforcement boundaries, but that evaluation does not make the gated action route live. Versioned snapshot/event propagation and broader policy coverage are not implemented. Existing Game Session `/sessions*` lifecycle routes are current owner-local hooks, not a complete external Logging & Admin route family. These distinctions do not mean that read, audit, log-search, saga, metrics, or dashboard/observability endpoints are absent; those are separate live read and investigation surfaces.
- Live admission-pointer reads, audit, and prepared-upgrade proof reads are part of the core operator/control-plane availability model and must not depend on observability backends. Admission-pointer mutation and preparation handlers are absent from public HTTP ingress and OpenAPI; their internal service/control-plane implementation must not be described as current live operator mutation support.
- The internal `SetAdmissionPointerRequest` DTO omits `actorPrincipal`. `AdmissionPointerServiceImpl` derives the actor from the authenticated internal caller context and writes that derived value to the control-plane request; `actorPrincipal` is response/audit data, not client-supplied write authority.
- Public administrative report persistence is currently unavailable. The unsafe controller that formerly occupied `POST /reports` and its `/api/admin/reports/**` Gateway exposure have been removed because the canonical role- and purpose-scoped authorization and live reference-validation checks are not implemented. Any restored administrative surface uses the distinct `POST /admin/reports` service path. `POST /reports` is reserved for the separate player-bootstrap submission contract and must bind the `player-bootstrap` subject and live tenant membership; it must not be inferred from or share the unavailable administrative route. The internal `CreateReport` gRPC contract remains behind the existing internal mTLS/workload boundary; caller-supplied tenant, reporter, and optional target identities are data references only.
- `ApplyModerationAction` has an implementation path for moderation policy input/audit, but `/moderation/actions` and the gRPC action remain unavailable/gated until the action-family schema, shared cross-language `mutationDigest/v1` vectors, Account authorization-reference issuance, and Logging & Admin receiving-service validation/redemption exist. The separate live `EvaluateModerationPolicy` contract supplies synchronous decisions consumed by Game Session at `GAMEPLAY_ADMISSION` and Social & Groups at `CHAT_SEND`; that evaluation is not operator mutation support and the action is not a currently supported forwarded enforcement mutation. Versioned snapshot/event propagation and broader enforcement remain target coverage.
- Quota-override ingress is a hypothetical target family until Account exposes the canonical owner-side override mutation contract; no executable route exists today.
- Broader tick-remediation `remediate` is a hypothetical target family until Game Session exposes the canonical owner-side remediation RPC; no executable route exists today.

### Script-transition read and audit consequences (target state; complete composition unavailable)

Target state only: for script and plugin operations, Logging & Admin is a composition and audit surface only. The complete joined composition is currently unavailable; current implementation status is recorded in the [Automation runtime/operator projection](../../../project-management/implementation-tracking/automation-and-scheduler-runtime.md#runtime-and-operator-projection) and [Game Session operator readback](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md#operator-readback-and-facade-boundaries) tracker sections.

- Target composition reads current-pin and rollout-history evidence from Game Session, including the exact patch/epoch, request identity, operation, outcome, and commit time. Owner-backed rollout history is target-only and currently unavailable through Logging & Admin. The current facade exposes only two bounded Game Session reads: `GetPinnedScriptPatchVersion` (authoritative current-pin version/request read; the current wire omits `scriptPinEpoch`, so it is not complete exact-tuple proof) and `GetGameSessionPinConvergence` (Game Session-side observed version/request read; the current wire omits `observedScriptPinEpoch`); direct Game Session bounded history remains the target owner source. `GetAutomationPinConvergence` is the Automation-owned, non-authoritative convergence projection and is not a substitute for either Game Session owner read. The joined history/readiness composition therefore remains unavailable, and no separate Logging & Admin history facade is implied. Game Session owner reads/history supply the exact tuple and owner result; if that owner-read dependency fails, the composition call returns the canonical non-OK gRPC status `UNAVAILABLE`.
- Target composition reads readiness, observed-pin freshness/convergence, plugin policy, timer reconciliation, and stage-aware dead-letter outcomes from Automation. An Automation dependency timeout, transport failure, or read failure returns the canonical non-OK gRPC status `UNAVAILABLE`; a successful response with stale or missing Automation data is instead reported explicitly as convergence/projection lag and never promoted to a pin or history decision or presented as owner truth.
- Target audit records retain `tenantId`, `gameInstanceId`, `scriptPatchVersion`, `scriptPinEpoch`, `controlPlaneRequestId`, `actor`, `reason`, `ownerResult`, and `projectionFreshness` (plus target scope). For plugin-scoped operations, the target audit record must also retain `pluginId`, `pluginVersionId`, `bindingId`, and the applicable Automation `runtimeStateFence` or authoritative Automation runtime-history reference; those fields are absent or inapplicable only for script-only operations, supplement the Game Session script tuple, and plugin-only changes do not advance `scriptPinEpoch`. Logging & Admin does not mutate Game Session pin state, Automation work, timer rows, plugin runtime rows, or Redis coordination directly. Any future mutating route must use the canonical owner-forwarding and authorization gates already required for other operator writes.

Routine rollback is expected to leave ordinary gameplay available while scoped Automation admission drains and reconciles; operator views must not describe cleanup or projection lag as a gameplay pause. Dead-letter recovery and purge remain separate, explicit, per-row owner operations. These read and audit consequences follow the [scripting contracts](../../system-architecture-scripting-contracts.md), [scripting control-plane API](../../system-architecture-scripting-control-plane-api.md), and [scripting rollout and rollback](../../system-architecture-scripting-rollout-and-rollback.md) owners.

- `POST /feature-flags/toggle` – implemented forwarding ingress but unavailable pending its action-family schema, shared `mutationDigest/v1` golden-vector conformance, and Account authorization-reference issuance plus redemption by the authoritative Game Session owner. Logging & Admin records/forwards the operator intent; it does not own or mutate the feature-flag state.
- `POST /logs/query` – search stored logs.
- The service-local route `/moderation/actions` is an unavailable/gated human mutation and is not Gateway-forwarded or supported at external ingress until its action-family schema, shared cross-language `mutationDigest/v1` golden vectors, Account authorization-reference issuance, and Logging & Admin receiving-service validation/redemption exist. No current live operator mutation support is claimed. Runtime owners separately consume the synchronous `EvaluateModerationPolicy` result at `GAMEPLAY_ADMISSION` and `CHAT_SEND`; versioned propagation remains target work.
- `GET /sagas` – list saga instances.
- `GET /sagas/{id}/steps` – inspect steps for a saga instance.
- `GET /admission-pointers` – list the caller-visible Game Session route records joined with their separately revisioned catalog/policy projection, including `OPEN`/`CLOSED`, the route version, and the explicit public-production policy used by admission and first-join membership creation.
- `GET /admission-pointers/{tenantId}/{worldSlug}/{realmSlug}/audit` – read the append-only cutover audit history for one gameplay realm pointer, using the same canonical `{tenantId, worldSlug, realmSlug}` key as admission authority itself instead of inferring tenant ownership from world/realm selectors after the read.

- Admission-pointer mutation, version-upgrade preparation, and prepared-cutover execution are target-only absent public HTTP/operator capabilities under `/admission-pointers`, `/cutover`, and `/version-upgrades`: they have no public HTTP handlers or Gateway write forwarding. Internal preparation/cutover service and control-plane implementation remains available only behind internal trust boundaries, and there is no current UI control.
- `GET /admission-pointers/version-upgrades/{tenantId}/{preparationId}` – read one durable prepared-version-upgrade proof, including participant attestations and execution state after a cutover has consumed the preparation.
- `POST /tick-remediation/pause` – implemented forwarding ingress but unavailable pending its action-family schema, shared `mutationDigest/v1` golden-vector conformance, and Account authorization-reference issuance plus redemption by the authoritative Game Session owner. Tick state is Game Session-owned; Logging & Admin audits and forwards the request rather than defining a competing remediation mutation.

Tick state is Game Session-owned; Logging & Admin audits and forwards the request rather than defining a competing remediation mutation.

### Administrative Report Contract (Unavailable HTTP Surface: `POST /admin/reports`)

The removed administrative controller previously occupied `POST /reports`; that route identity is now reserved for the separate player-bootstrap contract. A restored tenant-scoped operator surface uses `POST /admin/reports` and is not currently routable. Its canonical access policy is `tenant_regular`: a human request requires the exact `control-ui` token, the current route-allowed operator role (`moderator`, `tenantAdmin`, or an explicitly declared `platformAdmin` override), role-appropriate assurance, and an Account-issued `IssueHumanOperatorAuthorizationReference` bound to the `report_persistence` action family, explicit target tenant, and `controlPlaneRequestId`. Tenant-role alternatives additionally require live membership and the caller-bound `tenant_generation` check for the explicit target tenant. A `platformAdmin` override follows the explicit-target and `target_tenant_generation` branch rules in [ADR 0040](../../decisions/adr-0040-account-global-control-login-and-explicit-tenant-selection.md), requires the bounded `privileged_control` predicate, does not require target-tenant membership or membership-generation authority, and does not obtain authority from the supplied reporter or target references. Unattended automation instead uses Account's `IssueAutomationOperatorAuthorizationReference` with the exact Logging & Admin workload mTLS identity and versioned automation policy, but is restricted to the tenant-scoped branch and must carry the exact target `tenant_generation`; it carries no human identity, end-user token, or `privileged_control` authority.

Before creating the durable report record, the service must validate all request references against live authoritative data and fail closed on missing, unavailable, or ambiguous evidence:

- `tenantId` must identify an existing tenant within the operator authorization reference's permitted tenant scope.
- `reporterAccountId` must identify an existing account with the report-policy-required relationship to that tenant; it is report data, not the authenticated operator subject.
- If `targetAccountId` is supplied, it must identify an existing account valid for the same tenant and report policy; omission is allowed only when the report type permits no target.
- The report type and description must satisfy the applicable moderation/report policy before persistence, and the audit record must retain the authenticated operator or automation actor separately from the supplied references.

The implementation gap is fail-closed: the HTTP controller and Gateway route are removed rather than persisting caller-supplied references without the checks above. The internal `CreateReport` gRPC contract remains an internal report-ingress seam behind the existing workload boundary and must not be described as public or player-facing. The canonical checks above are required before `POST /admin/reports` is restored; `POST /reports` remains a separate player-bootstrap contract.

### Hypothetical/Target Coverage

- Quota override is hypothetical target coverage: it has no current OpenAPI route and no current Account owner mutation contract. Do not add `/quota-overrides*` until the owner contract exists.
- Versioned moderation propagation and broader enforcement are target coverage. Current Game Session and Social & Groups enforcement synchronously consumes Logging & Admin `EvaluateModerationPolicy`; `POST /moderation/actions` is unavailable/gated pending its action-family schema, shared `mutationDigest/v1` vectors, Account authorization-reference issuance, and Logging & Admin receiving-service validation/redemption, and is not current operator mutation support or an enforcement mutation.
- Game instance session lifecycle remains a current Game Session owner-local route family (`/sessions*`), not current Logging & Admin ingress. Its target external operator path is Logging & Admin to Game Session owner RPCs with Account-issued authorization references; no complete current Logging & Admin `/sessions*` route family exists.
- Scoped remediation beyond pause/resume is hypothetical target coverage: it has no current OpenAPI route and no current Game Session owner RPC. Do not add `/tick-remediation/remediate` or a direct Redis mutation path.

**Target ADR 0048 owner-forwarding path:** supported executable operator mutations use Account's canonical [`IssueHumanOperatorAuthorizationReference`](../account-service/api-contracts.md#operator-authorization-references) issuance RPC after Logging & Admin authenticates the current `control-ui` actor and records durable intent. Logging & Admin forwards the opaque bounded reference and unchanged request/generation binding; the authoritative receiving owner recomputes the canonical digest and is the only service that calls Account's `RedeemOperatorAuthorization` RPC. Unattended automation uses Account's `IssueAutomationOperatorAuthorizationReference` with `exact_mtls_workload_plus_versioned_automation_policy`, bound to the exact Logging and Admin workload mTLS identity and current `automation_policy_id`/`automation_policy_version`; the currently supported automation branch is tenant-scoped only and carries the exact target `tenant_generation` through issuance, forwarding, redemption, and owner commit. It carries no human identity, end-user token, or `privileged_control` authority. For each owner contract, predicate evidence comes exclusively from Account's redemption response; any copy forwarded by Logging & Admin is unchanged audit/context evidence, not authority. The moderation route remains unavailable/gated until the action-family schema, shared `mutationDigest/v1` vectors, Account authorization-reference issuance, and Logging & Admin receiving-service validation/redemption exist; if enabled, Logging & Admin redeems the operation/tenant-bound reference at its own receiving boundary before persistence. That persistence-only path has no forwarded domain owner and therefore no separate domain-owner redemption or enforcement step. The request identity is the exact `controlPlaneRequestId` plus digest pair, and Logging & Admin never becomes a second authorization authority. Current feature-flag and tick forwarding paths, plus internal admission control-plane implementations, are not evidence that this ADR 0048 target contract is complete.

For every forwarded owner mutation, the authoritative owner calls Account's `RedeemOperatorAuthorization` with the opaque reference and its independently derived request binding. Authorization predicates and generation authority come exclusively from that Account response. The moderation policy-input/audit path is the sole exception: it has no forwarded domain owner, so Logging & Admin validates and redeems the reference at its receiving boundary before persistence and does not perform owner-side redemption or enforcement. Any predicate, generation, checkpoint, or assurance copies forwarded by Logging & Admin are unchanged audit/context evidence only; the owner must not authorize or mutate from those copies, and they are excluded from the canonical `mutationDigest/v1`, which covers the normalized action request rather than ingress assertions.

### Internal Admission State Operations

The internal admission-pointer service/owner paths represent exactly one of two same-target Game Session control-plane operations for `{tenantId, worldSlug, realmSlug}`. These CAS operations and version-upgrade preparation are not public HTTP or OpenAPI capabilities; the supported public boundary is limited to admission-pointer reads, audit, and prepared-upgrade proof reads.

- `OpenAdmissionPointer` performs `CLOSED -> OPEN(target)`. The target must exist, belong to `tenantId`, and be the prepared/active runtime for the same world and realm. It must pass current runtime lifecycle and entitlement/admission checks; display names, slugs, or a caller-supplied instance id are not proof of that relationship. If validation is unavailable or ambiguous, the operation fails closed. `preparedVersionUpgradeId` is forbidden because this operation cannot replace an already open target.
- `CloseAdmissionPointer` performs `OPEN(target) -> CLOSED`. Game Session first checks the idempotency record for `controlPlaneRequestId`: an exact completed duplicate replays its original successful response and audit identity before current pointer-state validation. For a new request ID, the request must identify the exact currently open `gameInstanceId`; a missing pointer, already closed pointer, or different current target fails without mutation. Reusing a completed request ID with a different digest conflicts. Closing is a safety operation and therefore does not require the target to remain lifecycle- or entitlement-admissible. It cannot select a replacement target, and `preparedVersionUpgradeId` is forbidden. The resulting pointer makes no `gameInstanceId` gameplay-admissible while preserving the former target in audit evidence.
- Both requests carry the complete routing identity, target `gameInstanceId`, expected route version (`expectedPointerVersion`), reason, and idempotent `controlPlaneRequestId`. The schema does not accept a client-supplied actor: the actor is derived server-side from the authenticated operator session or workload. The response and audit record expose that actor and the resulting monotonic `pointerVersion`. `pointerVersion` is the route version and CAS token for exactly `{tenantId, worldSlug, realmSlug}`. The write succeeds only when the stored version equals the expected version; otherwise it returns a conflict and leaves the route unchanged. An absent route record uses `expectedPointerVersion=0` for the first open rather than an unscoped blind write.
- Replacing or rolling back `OPEN(old)` to `OPEN(new)` is a prepared cutover, not a generic open. It must use the internal `ExecutePreparedVersionCutover` control-plane operation with one durable `preparedVersionUpgradeId`; that operation revalidates the preparation, source and target identities, and CAS version before atomically swapping the route. Preparation is proof for cutover, not a substitute for route-version concurrency control.
- Game Session remains the sole routing-state writer and audits the transition under the same identity and CAS result. Internal callers must not maintain a competing pointer or infer `tenantId` from `worldSlug` or `realmSlug`; Logging & Admin's public REST surface reads the resulting state and audit evidence only.

## gRPC

- `Ping(PingRequest) returns (PingResponse)` – connectivity check defined in [`logging_admin_service.proto`](../../../../protos/logging-admin/v1/logging_admin_service.proto).
- `QueryLogs(QueryLogsRequest) returns (QueryLogsResponse)` – searches collected logs.
- `ApplyModerationAction(ApplyModerationActionRequest) returns (ApplyModerationActionResponse)` – unavailable/gated implementation contract for moderation policy input/audit until the action-family schema, shared cross-language `mutationDigest/v1` golden vectors, Account authorization-reference issuance, and Logging & Admin receiving-service validation/redemption exist; it does not currently persist or enforce moderation actions and is not current supported external operator mutation. `EvaluateModerationPolicy` remains the live read contract used at owner enforcement boundaries.
- `EvaluateModerationPolicy(EvaluateModerationPolicyRequest) returns (EvaluateModerationPolicyResponse)` – live internal owner-boundary read, not external operator or admin-UI availability. The current proto inventory is:

  ```protobuf
  rpc EvaluateModerationPolicy(EvaluateModerationPolicyRequest)
      returns (EvaluateModerationPolicyResponse);

  message EvaluateModerationPolicyRequest {
    string tenant_id = 1;
    string account_id = 2;
    string scope = 3;
  }

  message EvaluateModerationPolicyResponse {
    bool allowed = 1;
    string action = 2;
    string reason = 3;
    int64 expires_at_epoch_seconds = 4;
    shared.v1.ErrorDetail error = 5;
  }
  ```

  Game Session calls it with `GAMEPLAY_ADMISSION`; Social & Groups calls it with `CHAT_SEND`. It is an `internal_workload` RPC available only to the exact allowlisted Game Session and Social & Groups workload identities over internal mTLS; it accepts no end-user JWT, `control-ui` token, or operator authorization reference. The read remains live independently of observability backends, and applicable high-risk enforcement fails closed when the result is unavailable or not fresh.
- `logging_admin.v1.ReportService/CreateReport` – internal report persistence behind the existing mTLS/workload boundary. Its `CreateReportRequest` and `CreateReportResponse` messages carry caller-supplied tenant, reporter, and optional target identities as data references only; they do not authorize a caller. This gRPC contract is not public HTTP or player submission ingress.
- `ToggleFeatureFlag(ToggleFeatureFlagRequest) returns (ToggleFeatureFlagResponse)` – target owner-forwarding contract, unavailable until the action-family schema, shared cross-language `mutationDigest/v1` vectors, and Account authorization-reference issuance plus redemption by the authoritative Game Session owner exist. Logging & Admin is the audited forwarding ingress; Game Session owns the feature-flag mutation and its durable result.
- Tick-remediation is not a Logging & Admin-owned state-mutation gRPC surface. The pause/resume forwarding contracts are implemented but externally unavailable until their mutation gates pass; Logging & Admin audits and forwards them to Game Session, which owns tick state, fencing, idempotency, and the durable result. Broader `remediate` remains target-only absent.
