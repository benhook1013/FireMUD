# Logging & Admin Service API Contracts

This document defines the Logging & Admin Service REST and gRPC surfaces, authentication classes, and endpoint availability expectations.

## Script-transition read and audit consequences (target state; complete composition unavailable)

Target state only: for script and plugin operations, Logging & Admin is a composition and audit surface only. The complete joined composition is currently unavailable; current implementation status is recorded in the [Automation runtime/operator projection](../../../project-management/implementation-tracking/automation-and-scheduler-runtime.md#runtime-and-operator-projection) and [Game Session operator readback](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md#operator-readback-and-facade-boundaries) tracker sections.

- Target composition joins Game Session owner current-pin/rollout-history evidence with Automation readiness and convergence projections. The shared tuple, history, plugin-fence, projection, and audit-evidence fields are canonical in the [Scripting Contracts](../../system-architecture-scripting-contracts.md), [Control Plane API](../../system-architecture-scripting-control-plane-api.md), and [Observability Contract](../../system-architecture-scripting-observability-contract.md); this document retains only the local composition and availability consequences. Owner-backed rollout history is target-only and currently unavailable through Logging & Admin. The current facade exposes only two bounded Game Session reads: `GetPinnedScriptPatchVersion` (authoritative current-pin version/request read; the current wire omits `scriptPinEpoch`, so it is not complete exact-tuple proof) and `GetGameSessionPinConvergence` (Game Session-side observed version/request read; the current wire omits `observedScriptPinEpoch`); direct Game Session bounded history remains the target owner source. `GetAutomationPinConvergence` is the Automation-owned, non-authoritative convergence projection and is not a substitute for either Game Session owner read. The joined history/readiness composition therefore remains unavailable, and no separate Logging & Admin history facade is implied. If the Game Session owner-read dependency fails, the composition call returns the canonical non-OK gRPC status `UNAVAILABLE`.
- Target composition reads readiness, observed-pin freshness/convergence, plugin policy, timer reconciliation, and stage-aware dead-letter outcomes from Automation. An Automation dependency timeout, transport failure, or read failure returns the canonical non-OK gRPC status `UNAVAILABLE`; a successful response with stale or missing Automation data is instead reported explicitly as convergence/projection lag and never promoted to a pin or history decision or presented as owner truth.
- Logging & Admin audit retains `tenantId`, `gameInstanceId`, applicable target scope, the exact `scriptPatchVersion`/`scriptPinEpoch` tuple, `controlPlaneRequestId`, `actor`, `reason`, `ownerResult`, `projectionFreshness`, and, for plugin operations, applicable `pluginId`, `pluginVersionId`, `bindingId`, and captured `(pluginActivationEpoch, lifecycleRevision)` evidence; the pair is fence evidence, not identity, and the canonical tuple, history, and evidence schema remain defined by the linked owner contracts. Plugin-only changes do not advance the Game Session `scriptPinEpoch`. Logging & Admin does not mutate Game Session pin state, Automation work, timer rows, plugin runtime rows, or Redis coordination directly. Any future mutating route must use the canonical owner-forwarding and authorization gates already required for other operator writes.

Routine rollback is expected to leave ordinary gameplay available while scoped Automation admission drains and reconciles; operator views must not describe cleanup or projection lag as a gameplay pause. Dead-letter recovery and purge remain separate, explicit, per-row owner operations. These read and audit consequences follow the [scripting contracts](../../system-architecture-scripting-contracts.md), [scripting control-plane API](../../system-architecture-scripting-control-plane-api.md), and [scripting rollout and rollback](../../system-architecture-scripting-rollout-and-rollback.md) owners.

## Implementation Status

- Feature-flag toggles and scoped tick-remediation pause/resume forwarding have implementation paths but are unavailable as supported operator mutations until all three parts of the mutation gate exist: their action-family schemas, shared cross-language `mutationDigest/v1` golden vectors, and Account-issued authorization-reference issuance plus redemption by the receiving authoritative owner. Admission-pointer reads, audit, and prepared-upgrade proof reads remain live. Public POST/operator mutation routes under `/admission-pointers`, `/cutover`, or `/version-upgrades` are target-only absent: no public HTTP handlers or Gateway write forwarding exist. Internal preparation/cutover service and control-plane implementation remains behind internal trust boundaries, and there is no current UI control.
- Availability vocabulary is explicit: **implemented-but-externally-gated** means an executable public controller/owner path exists but the shared mutation gate is incomplete; **target-only absent** means no executable public route exists. Admission-pointer mutation, version-upgrade preparation, and prepared cutover use the latter classification at public HTTP ingress even though internal preparation/cutover implementation remains. Quota-override ingress and broader tick-remediation `remediate` are also target-only absent families.
- No forwarded owner mutation is currently supported as a live Logging & Admin capability until its action-family schema, shared cross-language `mutationDigest/v1` golden vectors, and Account-issued authorization-reference issuance plus redemption by the receiving authoritative owner exist. The service-local `POST /moderation/actions` endpoint and `ApplyModerationAction` gRPC path are gated/unavailable: they currently persist only the generic legacy `moderation_actions` row; separate fixed-category policy/audit evidence and owner enforcement state are absent, and they are not Gateway-forwarded or supported at external ingress. In the target local workflow, once the gate exists, Logging & Admin records durable intent/case/audit evidence and redeems its one Account reference exactly once; it never forwards that reference or performs owner enforcement. A future typed owner-enforcement command uses a separately issued reference redeemed by its receiving owner. Game Session and Social & Groups synchronously consume the live `EvaluateModerationPolicy` read at the `GAMEPLAY_ADMISSION` and `CHAT_SEND` enforcement boundaries, but that evaluation does not make the gated action route live. Fixed-category owner commands, monotonic owner state, bounded appeals, and broader policy coverage are not implemented. Existing Game Session `/sessions*` lifecycle routes are current owner-local hooks, not a complete external Logging & Admin route family. These distinctions do not mean that read, audit, log-search, saga, metrics, or dashboard/observability endpoints are absent; those are separate live read and investigation surfaces.
- The current moderation proto's `scope` and `action` fields are unrestricted strings, which is drift from ADR 0141's closed typed target rather than permission to accept arbitrary categories. Converged moderation ingress must validate the closed-category, typed-scope vocabulary and reject unknown values, `account_security_lock`, and its aliases before persistence. Only Account-owned security policy and recovery may create, extend, expire, remove, or clear `account_security_lock`; the moderation action route cannot create or clear it. `EvaluateModerationPolicy` remains a live read and carries no mutation authorization reference.
- Live admission-pointer reads, audit, and prepared-upgrade proof reads are part of the core operator/control-plane availability model and must not depend on observability backends. Admission-pointer mutation and preparation handlers are absent from public HTTP ingress and OpenAPI; their internal service/control-plane implementation must not be described as current live operator mutation support.
- The internal `SetAdmissionPointerRequest` DTO omits `actorPrincipal`. `AdmissionPointerServiceImpl` derives the actor from the authenticated internal caller context and writes that derived value to the control-plane request; `actorPrincipal` is response/audit data, not client-supplied write authority.
- Public administrative report persistence is currently unavailable. The unsafe controller that formerly occupied `POST /reports` and its `/api/admin/reports/**` Gateway exposure have been removed because the canonical role- and purpose-scoped authorization and live reference-validation checks are not implemented. Any restored administrative surface uses the distinct `POST /admin/reports` service path. `POST /reports` is reserved for the separate player-bootstrap submission contract and must bind the `player-bootstrap` subject and live tenant membership; it must not be inferred from or share the unavailable administrative route. The internal `CreateReport` gRPC contract remains behind the existing internal mTLS/workload boundary; caller-supplied tenant, reporter, and optional target identities are data references only.
- `ApplyModerationAction` has an implementation path but `/moderation/actions` and the gRPC action remain unavailable/gated until the action-family schema, shared cross-language `mutationDigest/v1` vectors, Account authorization-reference issuance, and receiving-boundary validation/redemption exist. Current behavior persists only the generic legacy `moderation_actions` row; separate fixed-category policy/audit evidence and owner enforcement are absent, and no forwarding occurs. Target behavior is Logging & Admin intent/case/audit persistence followed by exactly-once redemption of its local Account reference; that reference is never forwarded. A separate future owner-enforcement command has its own Account reference and receiving-owner redemption. The separate live `EvaluateModerationPolicy` contract supplies synchronous decisions consumed by Game Session at `GAMEPLAY_ADMISSION` and Social & Groups at `CHAT_SEND`; that evaluation is not operator mutation support. Fixed-category owner-local enforcement, bounded appeals, and broader coverage remain target work under [Moderation Policies](./moderation-policies.md).
- Quota-override ingress is a hypothetical target family until Account exposes the canonical owner-side override mutation contract; no executable route exists today.
- Broader tick-remediation `remediate` is a hypothetical target family until Game Session exposes the canonical owner-side remediation RPC; no executable route exists today.

## Moderation and Appeal API Consequences

The local API surface retains only Logging & Admin consequences of the owner contract in [Moderation Policies](./moderation-policies.md):

- `POST /moderation/actions` remains a service-local, unavailable/gated policy-input and audit mutation. Current behavior persists only the generic legacy `moderation_actions` row; separate fixed-category policy/audit evidence and owner enforcement are absent and no forwarding occurs. When enabled, the gated Logging & Admin intent/audit mutation uses one Account-issued reference bound to its exact dedicated `policyIntentRequestId`/digest and redeemed exactly once by Logging & Admin at its receiving boundary. A future typed owner-enforcement command has a distinct dedicated `ownerEnforcementRequestId`/digest and separately issued command-bound Account reference redeemed exactly once by the receiving owner; the local identity/reference is never forwarded or reused. `controlPlaneRequestId` remains a separate correlation-only field on these moderation transports and must not carry, replace, alias, or serve as either mutation identity. Logging & Admin never writes an owner table, and `EvaluateModerationPolicy` is a live read with no mutation authorization reference.
- `POST /moderation/appeals` and `GET /moderation/appeals/{appealCaseId}` are target-only caller-bound case submission/status surfaces. Eligibility, jurisdiction, exact restriction revision, one-active-case idempotency, safe response projection, rate limits, and finite evidence lifecycle are owned by [Moderation Policies](./moderation-policies.md); no current route or OpenAPI implementation proves them.
- An appeal may be initiated from gameplay only through an opaque short-lived HTTPS handoff whose Account-authenticated intent binds the appellant, case/restriction revision, action, expiry, and stable dedicated appeal-submission request identity. That identity is persisted and correlated with `appealCaseId` for status and is distinct from any later dedicated `ownerEnforcementRequestId`; `controlPlaneRequestId` remains correlation-only on both moderation transports and cannot carry or alias either identity. The gameplay API cannot collect evidence or decide an appeal.
- `UPHELD` has no owner mutation. `MODIFIED` and `OVERTURNED` retain the appeal linkage and forward a new digest-bound command to the existing enforcement owner; Logging & Admin does not directly clear or rewrite owner state. `DECIDED` is the terminal case fact, distinct from the subsequent owner-command outcome, which uses ADR 0048's phase-qualified states. Caller-facing status may report phase-qualified pending, committed, failed, or not-executed owner execution, or `RETRYABLE` guidance to poll/retry reconciliation for the same dedicated `ownerEnforcementRequestId`/digest; `RETRYABLE` is not a persisted or rearm state, and lost acknowledgement is reconciled with that same dedicated command identity/digest.

The target REST mapping is explicit per operation:

Both OpenAPI operations must declare that `503` response alongside `200`. The current convergence DTO still emits Java `long` values as JSON numbers and accepts values above JavaScript's exact integer range of `9,007,199,254,740,991`; clients cannot treat those out-of-range values as exact. Canonical UUID-string identifiers remain the target migration state, so this decimal-string representation is an explicitly tracked migration contract, not a competing identifier rule. The code and OpenAPI schema have not yet converged; no safe-integer rejection policy is claimed.

### Administrative Report Contract (Unavailable HTTP Surface: `POST /admin/reports`)

The removed administrative controller previously occupied `POST /reports`; that route identity is now reserved for the separate player-bootstrap contract. A restored tenant-scoped operator surface uses `POST /admin/reports` and is not currently routable. Its canonical access policy is `tenant_regular`: a human request requires the exact `control-ui` token, the current route-allowed operator role (`moderator`, `tenantAdmin`, or an explicitly declared `platformAdmin` override), role-appropriate assurance, and an Account-issued `IssueHumanOperatorAuthorizationReference` bound to the `report_persistence` action family, explicit target tenant, and `controlPlaneRequestId`. Tenant-role alternatives additionally require live membership and the caller-bound `tenant_generation` check for the explicit target tenant. A `platformAdmin` override follows the explicit-target and `target_tenant_generation` branch rules in [ADR 0040](../../decisions/adr-0040-account-global-control-login-and-explicit-tenant-selection.md), requires the bounded `privileged_control` predicate, does not require target-tenant membership or membership-generation authority, and does not obtain authority from the supplied reporter or target references. Unattended automation instead uses Account's `IssueAutomationOperatorAuthorizationReference` with the exact Logging & Admin workload mTLS identity and versioned automation policy, but is restricted to the tenant-scoped branch and must carry the exact target `tenant_generation`; it carries no human identity, end-user token, or `privileged_control` authority.

Before creating the durable report record, the service must validate all request references against live authoritative data and fail closed on missing, unavailable, or ambiguous evidence:

- `tenantId` must identify an existing tenant within the operator authorization reference's permitted tenant scope.
- `reporterAccountId` must identify an existing account with the report-policy-required relationship to that tenant; it is report data, not the authenticated operator subject.
- If `targetAccountId` is supplied, it must identify an existing account valid for the same tenant and report policy; omission is allowed only when the report type permits no target.
- The report type and description must satisfy the applicable moderation/report policy before persistence, and the audit record must retain the authenticated operator or automation actor separately from the supplied references.

The implementation gap is fail-closed: the HTTP controller and Gateway route are removed rather than persisting caller-supplied references without the checks above. The internal `CreateReport` gRPC contract remains an internal report-ingress seam behind the existing workload boundary and must not be described as public or player-facing. The canonical checks above are required before `POST /admin/reports` is restored; `POST /reports` remains a separate player-bootstrap contract.

### Internal Admission State Operations

The internal admission-pointer service/owner paths represent exactly one of two same-target Game Session control-plane operations for `{tenantId, worldSlug, realmSlug}`. These CAS operations and version-upgrade preparation are not public HTTP or OpenAPI capabilities; the supported public boundary is limited to admission-pointer reads, audit, and prepared-upgrade proof reads.

- `OpenAdmissionPointer` performs `CLOSED -> OPEN(target)`. The target must exist, belong to `tenantId`, and be the prepared/active runtime for the same world and realm. It must pass current runtime lifecycle and entitlement/admission checks; display names, slugs, or a caller-supplied instance id are not proof of that relationship. If validation is unavailable or ambiguous, the operation fails closed. `preparedVersionUpgradeId` is forbidden because this operation cannot replace an already open target.
- `CloseAdmissionPointer` performs `OPEN(target) -> CLOSED`. Game Session first checks the idempotency record for `controlPlaneRequestId`: an exact completed duplicate replays its original successful response and audit identity before current pointer-state validation. For a new request ID, the request must identify the exact currently open `gameInstanceId`; a missing pointer, already closed pointer, or different current target fails without mutation. Reusing a completed request ID with a different digest conflicts. Closing is a safety operation and therefore does not require the target to remain lifecycle- or entitlement-admissible. It cannot select a replacement target, and `preparedVersionUpgradeId` is forbidden. The resulting pointer makes no `gameInstanceId` gameplay-admissible while preserving the former target in audit evidence.
- Both requests carry the complete routing identity, target `gameInstanceId`, expected route version (`expectedPointerVersion`), reason, and idempotent `controlPlaneRequestId`. The schema does not accept a client-supplied actor: the actor is derived server-side from the authenticated operator session or workload. The response and audit record expose that actor and the resulting monotonic `pointerVersion`. `pointerVersion` is the route version and CAS token for exactly `{tenantId, worldSlug, realmSlug}`. The write succeeds only when the stored version equals the expected version; otherwise it returns a conflict and leaves the route unchanged. An absent route record uses `expectedPointerVersion=0` for the first open rather than an unscoped blind write.
- Replacing or rolling back `OPEN(old)` to `OPEN(new)` is a prepared cutover, not a generic open. It must use the internal `ExecutePreparedVersionCutover` control-plane operation with one durable `preparedVersionUpgradeId`; that operation revalidates the preparation, source and target identities, and CAS version before atomically swapping the route. Preparation is proof for cutover, not a substitute for route-version concurrency control.
- Game Session remains the sole routing-state writer and audits the transition under the same identity and CAS result. Internal callers must not maintain a competing pointer or infer `tenantId` from `worldSlug` or `realmSlug`; Logging & Admin's public REST surface reads the resulting state and audit evidence only.

## Endpoint Authentication Classes

Operator authentication and receiving-boundary rules are canonical in the [Authorization Route Matrix](../../system-architecture-authz-route-matrix.md#operator-delegation). The table below retains Logging & Admin's local endpoint availability and forwarding consequences. Every gated human or implemented mutation remains unavailable until its action-family schema, shared `mutationDigest/v1` golden vectors, Account authorization-reference issuance, and receiving-boundary validation or redemption are implemented; route authentication alone does not establish mutation support.

| Surface | Examples | Required auth path | Notes |
| --- | --- | --- | --- |
| Public/infra health | `GET /ping`, `Ping` | Internal network + platform health policy | Not a user-authenticated business operation. |
| Administrative report persistence (HTTP) | Unavailable; the unsafe former `POST /reports` controller and `/api/admin/reports/**` exposure were removed, and any restored administrative route uses `POST /admin/reports` | [Operator route authentication](../../system-architecture-authz-route-matrix.md#operator-delegation) | The administrative route remains unavailable until tenant scope, reporter relationship, optional target relationship, report policy, and authorization-reference checks are implemented. This is not player ingress. `POST /reports` is reserved for a separate player-bootstrap contract and must bind `player-bootstrap` authority independently. |
| Read/investigation APIs (HTTP) | `/logs/query`, `/sagas*`, `GET /admission-pointers`, `GET /admission-pointers/{tenantId}/{worldSlug}/{realmSlug}/audit`, `GET /admission-pointers/version-upgrades/{tenantId}/{preparationId}`, `GET /game-session-pins/{tenantId}/{gameInstanceId}`, `GET /game-session-pins/{tenantId}/{gameInstanceId}/convergence` | The exact route-declared read auth path, normally `control-ui` plus current role and route classification | These surfaces do not mutate domain or policy state and do not receive an operator mutation reference. The two game-session-pin reads are current tenant-scoped controller routes: the REST path variables are positive decimal numeric text parsed to `long`; the controller validates positive decimal numeric `tenantId`/`gameInstanceId` values and authorized tenant scope before the internal Game Session RPC. The internal proto fields are strings carrying the same decimal numeric text, and `GameSessionPinConvergenceDto` currently emits the identifiers as JSON integer values; exact client round-trip above JavaScript's safe-integer limit is an explicit implementation gap, not a supported contract. Canonical UUID strings remain the target migration state per the [Identifier Glossary](../../system-architecture-identifier-glossary.md). They are not currently Gateway-forwarded. The other listed routes are the live admission-pointer read/audit/proof-read boundary; admission-pointer and preparation writes have no public HTTP route. |
| Gated human mutation (HTTP) | Service-local `/moderation/actions` | [Operator route authentication](../../system-architecture-authz-route-matrix.md#operator-delegation) plus the action-family schema, shared `mutationDigest/v1` vectors, Account-issued authorization reference, and Logging & Admin validation/redemption | Unavailable at external Gateway ingress until the complete gate is implemented. The current service-local controller's tenant-access check is not canonical mutation authority and its path persists only the generic legacy `moderation_actions` row, with no separate fixed-category audit evidence or owner enforcement. Once conformant, Logging & Admin redeems the intent reference and records durable policy intent/case/audit evidence locally; it does not forward that reference. A future owner-enforcement command is a separate contract with a separately issued reference redeemed by the receiving owner. |
| Gated implemented mutations (HTTP) | `/feature-flags/toggle`, `/tick-remediation/pause`, `/tick-remediation/resume` | [Operator route authentication](../../system-architecture-authz-route-matrix.md#operator-delegation) plus the action-family schema, shared `mutationDigest/v1` vectors, Account-issued authorization reference, and authoritative-owner validation/redemption | Unavailable until the complete gate is implemented. Logging & Admin forwards the opaque reference and unchanged binding; the authoritative owner redeems it. Existing implementation paths do not establish canonical support. Admission-pointer mutation, preparation, and cutover have no public HTTP handlers; their internal service/control-plane code does not establish public route availability. |
| Target operator mutations (HTTP) | Future `/quota-overrides*` and broader remediation | [Operator route authentication](../../system-architecture-authz-route-matrix.md#operator-delegation) | These route families are target-only absent and must not be treated as current route availability. The owning service validates domain facts, fencing, and idempotency. |
| Owner mutation calls (gRPC internal) | Target feature-flag and tick owner RPCs; target session-lifecycle forwarding calls Game Session owner RPCs; current session-lifecycle hooks remain Game Session owner-local; target admission, quota, and broader-remediation mutations are forwarded to their authoritative owner services | [Operator delegation boundary](../../system-architecture-authz-route-matrix.md#operator-delegation) plus the receiving owner's exact mTLS identity | Public mutation support is unavailable until the three-part mutation gate is complete. Implemented internal feature-flag and tick owner paths remain gated; target-only owner RPCs remain absent. The authoritative owner validates domain facts, fencing, and idempotency. Logging & Admin forwards the opaque reference and unchanged request/generation binding; it does not redeem the owner reference, supply authority, or become a second authorization authority. |
| Service-to-service control/ingest (gRPC internal) | Internal lifecycle/event ingestion and trusted backend calls | mTLS caller identity + explicit service authorization checks | Never exposed at public ingress; use an exact receiver-specific private delegation profile only where the route declares one. |

## Availability Classes by Endpoint Family

| Endpoint family | Availability class | Required behavior during observability outage |
| --- | --- | --- |
| `/sagas*`, `GET /admission-pointers`, `GET /admission-pointers/{tenantId}/{worldSlug}/{realmSlug}/audit`, `GET /admission-pointers/version-upgrades/{tenantId}/{preparationId}` | Core operator/control plane | Remain available; may use local/PostgreSQL-backed audit state and downstream domain-service APIs only |
| `GET /game-session-pins/{tenantId}/{gameInstanceId}`, `GET /game-session-pins/{tenantId}/{gameInstanceId}/convergence` | Core operator/control plane | Remain available when the Game Session owner is available, independent of observability backends. Validate positive decimal numeric identifiers and authorized tenant scope before authoritative Game Session reads. These reads are not currently Gateway-forwarded and must never use Logging & Admin local/PostgreSQL composition as current pin/history authority; if the owner read is unavailable, return canonical `UNAVAILABLE`. |
| `/moderation/actions` | Gated operator mutation | Unavailable until its action-family schema, shared `mutationDigest/v1` golden vectors, Account authorization-reference issuance, and Logging & Admin validation/redemption exist; when enabled, it must remain independent of observability backends |
| `/feature-flags/toggle`, `/tick-remediation/pause`, `/tick-remediation/resume` | Gated implemented operator mutations | Unavailable pending action-schema, shared digest-vector, and Account authorization-reference issuance plus redemption-by-receiving-owner conformance; when enabled, must remain independent of observability backends. Admission-pointer mutation, preparation, and cutover have no public HTTP handlers or Gateway write forwarding |
| Future `/quota-overrides*` and broader remediation | Target-only absent operator mutations | No live route exists; when implemented, these families must use the canonical Account authorization-reference and authoritative-owner validation contracts |
| Current public report persistence | Unavailable | The unsafe former `POST /reports` administrative controller and Gateway exposure remain removed; any restored administrative route uses `POST /admin/reports`. The role/purpose authorization and live reference-validation checks in the canonical administrative contract must exist before administrative persistence is restored; reserved player-bootstrap `POST /reports` remains unavailable until its own caller-bound checks exist. |
| `/logs/query`, embedded Kibana/Grafana/Jaeger/Alertmanager views | Observability-backed | May degrade, return explicit unavailable/read-only states, or be hidden behind degraded-state messaging |
