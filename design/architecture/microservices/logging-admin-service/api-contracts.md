# Logging & Admin Service API Contracts

This document defines the Logging & Admin Service REST and gRPC surfaces, authentication classes, and endpoint availability expectations.

## Account Audit Ingress and Receipt

The canonical Account-to-Logging & Admin audit ingress is the existing `logging_admin.v1.LoggingAdminService/CreateLogEvent` RPC, converged in place rather than duplicated as a parallel ingress. It is a non-destructive internal service RPC, not an operator/admin mutation. Account is the producer and source authority for account state; Logging & Admin owns the receiver-side audit envelope, durable receipt/readback, deduplication, and audit projection. The audit ingress follows only shared envelope fundamentals (stable identity, event type/schema, producer occurrence time, and at-least-once/idempotent delivery) from [Session Behavior](../../system-architecture-session-behavior.md); it does **not** inherit that document's membership-specific field set or `eventDigest` grammar. Internal workload identity and method authorization follow [Authentication](../../system-architecture-authentication.md) and [gRPC](../../system-architecture-grpc.md#tls-requirements).

Target `CreateLogEventRequest` carries `scope` (`platform` or `tenant`), `tenantId` only for `tenant` scope and never for `platform` scope, stable `auditEventId` generated and persisted by Account, `producerService`, `eventType`, producer `occurredAt`, positive `schemaVersion`, exact UTF-8 `payload`, `payloadDigestVersion` exactly `1` until a later canonical digest-version registry is accepted, and `payloadDigest`. Global registration, `account_security_lock`, `platform_access_ban`, recovery, and suspicious-activity events use `platform` scope with no `tenantId`; tenant profile and JOIN events use `tenant` scope with the exact committed `tenantId`. Unsupported digest versions fail before deduplication or persistence. `producerService` is derived from the authenticated Account workload identity and a mismatching request value is rejected. An upstream producer domain-event digest, when present inside `payload`, remains opaque payload evidence and is distinct from the receiver's `payloadDigest`. `payloadDigest` is `sha256:` followed by 64 lowercase hexadecimal characters over the exact UTF-8 payload bytes under `payloadDigestVersion=1`; no JSON reserialization or alternate canonicalization is permitted. Retry equivalence is the complete immutable `(scope, tenantId-if-tenant, auditEventId, producerService, eventType, occurredAt, schemaVersion, payloadDigestVersion, payloadDigest, exact payload bytes)` tuple: while exact payload bytes remain retained, an exact match returns the original receipt, while any changed field or payload bytes fails closed as `IDEMPOTENCY_CONFLICT`. After the safe watermark permits payload minimization, the retained identity and metadata may still detect a changed non-payload field, but the receiver must not claim exact payload equality or replay; a matching late request is a terminal non-replayable result. Timeout, transport failure, or an ambiguous response is not success; the producer retries or reconciles with the same identity and digest and never mints a replacement event.

`CreateLogEventResponse` returns `scope`, the matching `tenantId` only for tenant scope, `auditEventId`, stable receiver-generated `receiptId`, receiver `logEventId`, `schemaVersion`, `payloadDigestVersion`, `payloadDigest`, `status`, and `outcome`. The durable envelope/receipt stores and exact-compares the complete immutable tuple and exact payload bytes defined above while they are retained, and exposes the receipt fields for readback. Its status/outcome vocabulary is `COMMITTED/ACCEPTED` for the first durable write, `COMMITTED/DUPLICATE` for an exact retry before minimization, `MINIMIZED/NON_REPLAYABLE` for a matching request after payload minimization, and `CONFLICT/IDEMPOTENCY_CONFLICT` for a mismatch proven by retained metadata. `MINIMIZED/NON_REPLAYABLE` is a successful typed domain result, so both `CreateLogEvent` and `ReadLogEventReceipt` return gRPC status `OK` with only the bounded digest-only receipt metadata; they do not return payload bytes, claim exact payload equality, or create a replacement identity. The concrete readback is `logging_admin.v1.LoggingAdminService/ReadLogEventReceipt`, whose request carries the same complete tuple and whose response is `ReadLogEventReceiptResponse` with the same receipt fields. Before minimization, an exact readback returns `OK` with `COMMITTED/DUPLICATE` or the original terminal result; after minimization, an exact identity/digest read returns `OK` with `MINIMIZED/NON_REPLAYABLE`. A missing receipt returns canonical non-OK gRPC status `NOT_FOUND`; receiver/dependency unavailability returns canonical non-OK gRPC status `UNAVAILABLE`; neither is an empty typed success. Authorization is a workload-only method: the receiver derives the exact `account-service` mTLS identity, requires the `CreateLogEvent` or `ReadLogEventReceipt` method-specific allowlist entry, and accepts no bearer token or `AdminRole` in that path. The current proto and receiver instead expose only the legacy `CreateLogEvent` shape and `AdminRoleGuard`; this is explicitly current drift pending the target convergence.

The receipt retention class and cleanup owner are defined in [Logging & Admin Runtime and Data](./runtime-and-data.md#audit-envelope-and-receipt-retention).

## Script-transition read and audit consequences (target state; complete composition unavailable)

Target state only: for script and plugin operations, Logging & Admin is a composition and audit surface only. The complete joined composition is currently unavailable; current implementation status is recorded in the [Automation runtime/operator projection](../../../project-management/implementation-tracking/automation-and-scheduler-runtime.md#runtime-and-operator-projection) and [Game Session operator readback](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md#operator-readback-and-facade-boundaries) tracker sections.

- Target composition joins Game Session owner current-pin/rollout-history evidence with Automation readiness and convergence projections. The shared tuple, history, plugin-fence, projection, and audit-evidence fields are canonical in the [Scripting Contracts](../../system-architecture-scripting-contracts.md), [Control Plane API](../../system-architecture-scripting-control-plane-api.md), and [Observability Contract](../../system-architecture-scripting-observability-contract.md); this document retains only the local composition and availability consequences. Owner-backed rollout history is target-only and currently unavailable through Logging & Admin. The current facade exposes only two bounded Game Session reads: `GetPinnedScriptPatchVersion` (authoritative current-pin version/request read; the current wire omits `scriptPinEpoch`, so it is not complete exact-tuple proof) and `GetGameSessionPinConvergence` (Game Session-side observed version/request read; the current wire omits `observedScriptPinEpoch`); direct Game Session bounded history remains the target owner source. `GetAutomationPinConvergence` is the Automation-owned, non-authoritative convergence projection and is not a substitute for either Game Session owner read. The joined history/readiness composition therefore remains unavailable, and no separate Logging & Admin history facade is implied. If the Game Session owner-read dependency fails, the composition call returns the canonical non-OK gRPC status `UNAVAILABLE`.
- Target composition reads readiness, observed-pin freshness/convergence, plugin policy, timer reconciliation, and stage-aware dead-letter outcomes from Automation. An Automation dependency timeout, transport failure, or read failure returns the canonical non-OK gRPC status `UNAVAILABLE`; a successful response with stale or missing Automation data is instead reported explicitly as convergence/projection lag and never promoted to a pin or history decision or presented as owner truth.
- Logging & Admin audit retains `tenantId`, `gameInstanceId`, applicable target scope, the exact `scriptPatchVersion`/`scriptPinEpoch` tuple, `controlPlaneRequestId`, `actor`, `reason`, `ownerResult`, `projectionFreshness`, and, for plugin operations, applicable `pluginId`, `pluginVersionId`, `bindingId`, and captured `(pluginActivationEpoch, lifecycleRevision)` evidence; the pair is fence evidence, not identity, and the canonical tuple, history, and evidence schema remain defined by the linked owner contracts. Plugin-only changes do not advance the Game Session `scriptPinEpoch`. Logging & Admin does not mutate Game Session pin state, Automation work, timer rows, plugin runtime rows, or Redis coordination directly. Any future mutating route must use the canonical owner-forwarding and authorization gates already required for other operator writes.

Routine rollback is expected to leave ordinary gameplay available while scoped Automation admission drains and reconciles; operator views must not describe cleanup or projection lag as a gameplay pause. Dead-letter recovery and purge remain separate, explicit, per-row owner operations. These read and audit consequences follow the [scripting contracts](../../system-architecture-scripting-contracts.md), [scripting control-plane API](../../system-architecture-scripting-control-plane-api.md), and [scripting rollout and rollback](../../system-architecture-scripting-rollout-and-rollback.md) owners.

## Implementation Status

- Feature-flag toggles and scoped tick-remediation pause/resume ingress routes now hard fail closed as unavailable operator mutations until the minimum three-part schema/authorization gate exists: their action-family schemas, shared cross-language `mutationDigest/v1` golden vectors, and Account-issued authorization-reference issuance plus redemption by the receiving authoritative owner. This minimum gate is necessary but not sufficient for live-success support; supported execution also requires the complete durable, idempotent, fenced owner-mutation contract in [ADR 0048](../../decisions/adr-0048-durable-idempotent-operator-write-execution.md), including durable intent/audit, stable digest-bound request identity, authoritative-owner state, safety/recovery gates, and durable acknowledgement. The HTTP entrypoints preserve authentication, authorization, and basic request validation, then return `503 Service Unavailable` with stable action-specific unavailable error codes (`FEATURE_FLAG_TOGGLE_UNAVAILABLE` or `TICK_REMEDIATION_UNAVAILABLE`) without invoking a service, owner, or audit dependency. The internal `ToggleFeatureFlag` gRPC entrypoint preserves admin-role, positive-tenant, and feature-name validation, then returns an application-level `UNAVAILABLE` error without dispatch. No Logging & Admin feature-flag or tick forwarding method remains callable internally. Admission-pointer reads, audit, and prepared-upgrade proof reads remain live. Public POST/operator mutation routes under `/admission-pointers`, `/cutover`, or `/version-upgrades` are target-only absent: no public HTTP handlers or Gateway write forwarding exist. Internal preparation/cutover service and control-plane implementation remains behind internal trust boundaries, and there is no current UI control.
- Availability vocabulary is explicit: **implemented-but-externally-gated** means an executable public controller/owner path exists but the shared mutation gate is incomplete; **target-only absent** means no executable public route exists. Admission-pointer mutation, version-upgrade preparation, and prepared cutover use the latter classification at public HTTP ingress even though internal preparation/cutover implementation remains. Quota-override ingress is also target-only absent. No generic tick-remediation payload or reserved `remediate` route is part of the target; each future recovery operation requires a named typed contract implemented by its authoritative workflow owner.
- No forwarded owner mutation is currently supported as a live Logging & Admin capability until its minimum schema/authorization gate and the complete durable, idempotent, fenced owner-execution contract in [ADR 0048](../../decisions/adr-0048-durable-idempotent-operator-write-execution.md) are implemented and proved. The service-local `POST /moderation/actions` endpoint and `ApplyModerationAction` gRPC path now hard fail closed after their narrow tenant/admin checks: HTTP returns `503 Service Unavailable`, gRPC returns an application-level `UNAVAILABLE` error, and neither path dispatches or persists the generic legacy `moderation_actions` row. They remain unsupported, nonconformant implementation drift and must not be wired or called as available mutations; separate fixed-category policy/audit evidence and owner enforcement state are absent, and they are not Gateway-forwarded or supported at external ingress. In the target local workflow, once its applicable schema/authorization and local durable intent/audit requirements are implemented, Logging & Admin records durable intent/case/audit evidence and redeems its one Account reference exactly once; it never forwards that reference or performs owner enforcement. A future typed owner-enforcement command uses a separately issued reference redeemed by its receiving owner. Game Session and Social & Groups synchronously consume the live `EvaluateModerationPolicy` read at the `GAMEPLAY_ADMISSION` and `CHAT_SEND` enforcement boundaries, but that evaluation does not make the legacy action route live. Fixed-category owner commands, monotonic owner state, bounded appeals, and broader policy coverage are not implemented. Existing Game Session `/sessions*` lifecycle routes are current owner-local hooks, not a complete external Logging & Admin route family. Separate current read and investigation surfaces include the PostgreSQL-backed log query, saga reads, metrics, and owner/control-plane reads; profile-aware indexed or console/journal query integration and embedded dashboard endpoints remain target-only and unimplemented.
- Current `POST /logs/query` and `QueryLogs` read only the service-owned PostgreSQL `log_events` table. They require an exact tenant and apply case-insensitive containment to the stored message, returning the matching messages. They do not query deployed structured logs, mirror data to Elasticsearch, prove the ADR 0162 emitter-to-query path, implement a compatible indexed or console/journal profile, or expose Kibana/Grafana embedding.
- The current moderation proto's `scope` and `action` fields are unrestricted strings, which is drift from ADR 0141's closed typed target rather than permission to accept arbitrary categories. Converged moderation ingress must validate the closed-category, typed-scope vocabulary and reject unknown values, `account_security_lock`, and its aliases before persistence. Only Account-owned security policy and recovery may create, extend, expire, remove, or clear `account_security_lock`; the moderation action route cannot create or clear it. `EvaluateModerationPolicy` remains a live read and carries no mutation authorization reference.
- Live admission-pointer reads, audit, and prepared-upgrade proof reads are part of the core operator/control-plane availability model and must not depend on observability backends. Admission-pointer mutation and preparation handlers are absent from public HTTP ingress and OpenAPI; their internal service/control-plane implementation must not be described as current live operator mutation support.
- The internal `SetAdmissionPointerRequest` DTO omits `actorPrincipal`. `AdmissionPointerServiceImpl` derives the actor from the authenticated internal caller context and writes that derived value to the control-plane request; `actorPrincipal` is response/audit data, not client-supplied write authority.
- Public administrative report persistence is currently unavailable. The unsafe controller that formerly occupied `POST /reports` and its `/api/admin/reports/**` Gateway exposure have been removed because the canonical role- and purpose-scoped authorization and live reference-validation checks are not implemented. Any restored administrative surface uses the distinct `POST /admin/reports` service path. `POST /reports` is reserved for the separate player-bootstrap submission contract and must bind the `player-bootstrap` subject and live tenant membership; it must not be inferred from or share the unavailable administrative route. The internal `CreateReport` gRPC contract is not public HTTP or player ingress, but its target exact workload/method authorization is unproved: current transport mTLS alone does not establish an allowlisted receiver identity. The interim receiver requires an internal-service JWT naming `social-groups-service`, while certificate-derived exact workload/method authorization remains unproved. Caller-supplied tenant, reporter, and optional target identities are data references only.
- `ApplyModerationAction` has an implementation path, but `/moderation/actions` plus the gRPC action now hard fail closed after narrow tenant/admin checks. HTTP returns `503 Service Unavailable`, gRPC returns an application-level `UNAVAILABLE` error, and neither path dispatches or persists the generic legacy `moderation_actions` row. They remain unsupported/nonconformant drift, not available mutation support. The target gate requires the action-family schema, shared cross-language `mutationDigest/v1` vectors, Account authorization-reference issuance, and receiving-boundary validation/redemption. Separate fixed-category policy/audit evidence and owner enforcement are absent, and no forwarding occurs. Target behavior is Logging & Admin intent/case/audit persistence followed by exactly-once redemption of its local Account reference; that reference is never forwarded. A separate future owner-enforcement command has its own Account reference and receiving-owner redemption. The separate live `EvaluateModerationPolicy` contract supplies synchronous decisions consumed by Game Session at `GAMEPLAY_ADMISSION` and Social & Groups at `CHAT_SEND`; that compatibility read is a legacy, deny-only lookup over generic action rows ordered by recency, is nonconformant with ADR 0141's broadest-effect response precedence (`platform_access_ban` over `account_security_lock`, `chat_ban` over `chat_mute`), and does not implement or prove all five fixed categories or their independent lifecycles. It is not operator mutation support. Fixed-category owner-local enforcement, bounded appeals, and broader coverage remain target work under [Moderation Policies](./moderation-policies.md).
- Quota-override ingress is a hypothetical target family until Account exposes the canonical owner-side override mutation contract; no executable route exists today.
- Future coordination and tick recovery operations use a closed catalog of named typed actions owned by their authoritative workflow owner. Logging & Admin does not expose a generic `remediate(action, payload)` endpoint, reveal internal recovery phases as public verbs, or hold Redis write credentials.

## Moderation and Appeal API Consequences

The local API surface retains only Logging & Admin consequences of the owner contract in [Moderation Policies](./moderation-policies.md):

- `POST /moderation/actions` remains a service-local, unsupported/nonconformant legacy policy-input and audit mutation path. Its handler now hard fails closed after narrow tenant checks: it returns HTTP `503 Service Unavailable` and does not dispatch or persist the generic legacy `moderation_actions` row. It must not be wired or called as available. When enabled, the target Logging & Admin intent/audit mutation uses one Account-issued reference bound to its exact dedicated `policyIntentRequestId`/digest and redeemed exactly once by Logging & Admin at its receiving boundary. A future typed owner-enforcement command has a distinct dedicated `ownerEnforcementRequestId`/digest and separately issued command-bound Account reference redeemed exactly once by the receiving owner; the local identity/reference is never forwarded or reused. `controlPlaneRequestId` remains a separate correlation-only field on these moderation transports and must not carry, replace, alias, or serve as either mutation identity. Logging & Admin never writes an owner table, and `EvaluateModerationPolicy` is a live compatibility read with no mutation authorization reference.
- `POST /moderation/appeals` and `GET /moderation/appeals/{appealCaseId}` are target-only caller-bound case submission/status surfaces. Eligibility, jurisdiction, exact restriction revision, one-active-case idempotency, safe response projection, rate limits, and finite evidence lifecycle are owned by [Moderation Policies](./moderation-policies.md); no current route or OpenAPI implementation proves them.
- An appeal may be initiated from gameplay only through an opaque short-lived HTTPS handoff whose Account-authenticated intent binds the appellant, case/restriction revision, action, expiry, and stable dedicated appeal-submission request identity. That identity is persisted and correlated with `appealCaseId` for status and is distinct from any later dedicated `ownerEnforcementRequestId`; `controlPlaneRequestId` remains correlation-only on both moderation transports and cannot carry or alias either identity. The gameplay API cannot collect evidence or decide an appeal.
- `UPHELD` has no owner mutation. `MODIFIED` and `OVERTURNED` retain the appeal linkage and forward a new digest-bound command to the existing enforcement owner; Logging & Admin does not directly clear or rewrite owner state. `DECIDED` is the terminal case fact, distinct from the subsequent owner-command outcome, which uses ADR 0048's phase-qualified states. Caller-facing status may report phase-qualified pending, committed, failed, or not-executed owner execution, or `RETRYABLE` guidance to poll/retry reconciliation for the same dedicated `ownerEnforcementRequestId`/digest; `RETRYABLE` is not a persisted or rearm state, and lost acknowledgement is reconciled with that same dedicated command identity/digest.

## REST

- `GET /ping` – basic health check returning `"pong"`.
- `GET /game-session-pins/{tenantId}/{gameInstanceId}` (`getPinnedScriptPatchVersion`) – live tenant-scoped bounded read returning `PinnedScriptPatchVersionDto` through the internal Game Session `GetPinnedScriptPatchVersion` RPC; it is not a Logging & Admin gRPC operation, and the current DTO omits `scriptPinEpoch`.
- `GET /game-session-pins/{tenantId}/{gameInstanceId}/convergence` (`getGameSessionPinConvergence`) – live tenant-scoped bounded read returning `GameSessionPinConvergenceDto` through the internal Game Session `GetGameSessionPinConvergence` RPC; it is not a Logging & Admin gRPC operation, and the current DTO omits `observedScriptPinEpoch`.

The target REST mapping is explicit per operation:

- `getPinnedScriptPatchVersion` returns HTTP `503 Service Unavailable` when the internal Game Session `GetPinnedScriptPatchVersion` owner read returns gRPC `UNAVAILABLE`, before constructing a success DTO.
- `getGameSessionPinConvergence` returns HTTP `503 Service Unavailable` when the internal Game Session `GetGameSessionPinConvergence` owner read returns gRPC `UNAVAILABLE`, before constructing a success DTO.

Both OpenAPI operations must declare that `503` response alongside `200`. The current `GameSessionPinServiceImpl` leaves `UNAVAILABLE` on its default HTTP 500 branch, and `openapi.yaml` declares only `200` for both operations; this is an implementation and proof gap rather than an alternate target contract. The owning Game Session read/status boundary and its implementation gaps are tracked in the [Game Session runtime tracker](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md#operator-readback-and-facade-boundaries).

The interim legacy numeric pin-read contract must also remain exact across JavaScript clients: `GameSessionPinConvergenceDto.tenantId` and `gameInstanceId` are to be serialized as decimal strings, and both matching OpenAPI properties must be `string`, not JSON `number`. The current convergence DTO still emits Java `long` values as JSON numbers and accepts values above JavaScript's exact integer range of `9,007,199,254,740,991`; clients cannot treat those out-of-range values as exact. Canonical UUID-string identifiers remain the target migration state, so this decimal-string representation is an explicitly tracked migration contract, not a competing identifier rule. The code and OpenAPI schema have not yet converged; no safe-integer rejection policy is claimed.

### Administrative Report Contract (Unavailable HTTP Surface: `POST /admin/reports`)

The removed administrative controller previously occupied `POST /reports`; that route identity is now reserved for the separate player-bootstrap contract. A restored tenant-scoped operator surface uses `POST /admin/reports` and is not currently routable. Its canonical access policy is `tenant_regular`: a human request requires the exact `control-ui` token, the current route-allowed operator role (`moderator`, `tenantAdmin`, or an explicitly declared `platformAdmin` override), role-appropriate assurance, and an Account-issued `IssueHumanOperatorAuthorizationReference` bound to the `report_persistence` action family, explicit target tenant, and `controlPlaneRequestId`. Tenant-role alternatives additionally require live membership and the caller-bound `tenant_generation` check for the explicit target tenant. A `platformAdmin` override follows the explicit-target and `target_tenant_generation` branch rules in [ADR 0040](../../decisions/adr-0040-account-global-control-login-and-explicit-tenant-selection.md), requires the bounded `privileged_control` predicate, does not require target-tenant membership or membership-generation authority, and does not obtain authority from the supplied reporter or target references. Unattended automation instead uses Account's `IssueAutomationOperatorAuthorizationReference` with the exact Logging & Admin workload mTLS identity and versioned automation policy, but is restricted to the tenant-scoped branch and must carry the exact target `tenant_generation`; it carries no human identity, end-user token, or `privileged_control` authority.

Before creating the durable report record, the service must validate all request references against live authoritative data and fail closed on missing, unavailable, or ambiguous evidence:

- `tenantId` must identify an existing tenant within the operator authorization reference's permitted tenant scope.
- `reporterAccountId` must identify an existing account with the report-policy-required relationship to that tenant; it is report data, not the authenticated operator subject.
- If `targetAccountId` is supplied, it must identify an existing account valid for the same tenant and report policy; omission is allowed only when the report type permits no target.
- The report type and description must satisfy the applicable moderation/report policy before persistence, and the audit record must retain the authenticated operator or automation actor separately from the supplied references.

The implementation gap is fail-closed: the HTTP controller and Gateway route are removed rather than persisting caller-supplied references without the checks above. The internal `CreateReport` gRPC contract remains an internal report-ingress seam behind the existing workload boundary and must not be described as public or player-facing. The canonical checks above are required before `POST /admin/reports` is restored; `POST /reports` remains a separate player-bootstrap contract.

### Hypothetical/Target Coverage

- Digest-bound moderation owner-command delivery and broader enforcement are target coverage. Its target external operator path is Logging & Admin to Game Session owner RPCs with Account-issued authorization references; no complete current Logging & Admin `/sessions*` route family exists.
- Recovery actions beyond pause/resume are hypothetical target coverage until a named typed authoritative-owner contract exists. Do not add `/tick-remediation/remediate`, an open-ended payload language, or a direct Redis mutation path.

**Target ADR 0047/0048 owner-forwarding path:** [ADR 0047](../../decisions/adr-0047-logging-admin-as-external-operator-write-ingress.md) owns the Logging & Admin ingress and Account-reference issuance boundary; [ADR 0048](../../decisions/adr-0048-durable-idempotent-operator-write-execution.md) owns the phase-qualified execution, redemption, and reconciliation contract. Supported executable operator mutations use Account's canonical [`IssueHumanOperatorAuthorizationReference`](../account-service/api-contracts.md#operator-authorization-references) issuance RPC after Logging & Admin authenticates the current `control-ui` actor and records durable intent. Logging & Admin forwards the opaque bounded reference and unchanged request/generation binding; the authoritative receiving owner recomputes the canonical digest and is the only service that calls Account's `RedeemOperatorAuthorization` RPC. Unattended automation uses Account's `IssueAutomationOperatorAuthorizationReference` with `exact_mtls_workload_plus_versioned_automation_policy`, bound to the exact Logging and Admin workload mTLS identity and current `automation_policy_id`/`automation_policy_version`; the currently supported automation branch is tenant-scoped only and carries the exact target `tenant_generation` through issuance, forwarding, redemption, and owner commit. It carries no human identity, end-user token, or `privileged_control` authority. For each owner contract, predicate evidence comes exclusively from Account's redemption response; any copy forwarded by Logging & Admin is unchanged audit/context evidence, not authority. The local `/moderation/actions` policy-input/audit mutation is a separate receiving-service path: after its gate exists, Logging & Admin redeems its one Account reference exactly once for local persistence and never forwards or reuses that reference. Any future moderation owner-enforcement command uses a separately issued command-bound reference redeemed exactly once by the receiving owner. The moderation route is currently gated/unavailable; it hard fails closed without dispatch or persistence and performs no target fixed-category policy/audit persistence or forwarding. `EvaluateModerationPolicy` is a live read and carries no mutation authorization reference. For non-moderation action families, the request identity is the exact `controlPlaneRequestId` plus digest pair. Moderation and appeal transports instead use dedicated `policyIntentRequestId`, `ownerEnforcementRequestId`, and stable appeal-submission request identities end-to-end; `controlPlaneRequestId` remains a separate correlation-only field and must not carry, replace, alias, or serve as any of those mutation identities. The dedicated identities are never shared or reused. Logging & Admin never becomes a second authorization authority. Current feature-flag and tick forwarding paths, plus internal admission control-plane implementations, are not evidence that this ADR 0048 target contract is complete.

For every forwarded owner mutation, excluding the separate local `/moderation/actions` policy-input/audit path, the authoritative owner calls Account's `RedeemOperatorAuthorization` with the separately issued opaque reference and its independently derived request binding. Authorization predicates and generation authority come exclusively from that Account response. Any predicate, generation, checkpoint, or assurance copies forwarded by Logging & Admin are unchanged audit/context evidence only; the owner must not authorize or mutate from those copies, and they are excluded from the canonical `mutationDigest/v1`, which covers the normalized action request rather than ingress assertions. The local moderation route is gated/unavailable; it hard fails closed without dispatch or persistence and does not persist target fixed-category policy/audit evidence, redeem, forward, or enforce.

### Internal Admission State Operations

The internal admission-pointer service/owner paths represent exactly one of two same-target Game Session control-plane operations for `{tenantId, worldSlug, realmSlug}`. These CAS operations and version-upgrade preparation are not public HTTP or OpenAPI capabilities; the supported public boundary is limited to admission-pointer reads, audit, and prepared-upgrade proof reads.

- `OpenAdmissionPointer` performs `CLOSED -> OPEN(target)`. The target must exist, belong to `tenantId`, and be the prepared/active runtime for the same world and realm. It must pass current runtime lifecycle and entitlement/admission checks; display names, slugs, or a caller-supplied instance id are not proof of that relationship. If validation is unavailable or ambiguous, the operation fails closed. `preparedVersionUpgradeId` is forbidden because this operation cannot replace an already open target.
- `CloseAdmissionPointer` performs `OPEN(target) -> CLOSED`. Game Session first checks the idempotency record for `controlPlaneRequestId`: an exact completed duplicate replays its original successful response and audit identity before current pointer-state validation. For a new request ID, the request must identify the exact currently open `gameInstanceId`; a missing pointer, already closed pointer, or different current target fails without mutation. Reusing a completed request ID with a different digest conflicts. Closing is a safety operation and therefore does not require the target to remain lifecycle- or entitlement-admissible. It cannot select a replacement target, and `preparedVersionUpgradeId` is forbidden. The resulting pointer makes no `gameInstanceId` gameplay-admissible while preserving the former target in audit evidence.
- Both requests carry the complete routing identity, target `gameInstanceId`, expected route version (`expectedPointerVersion`), reason, and idempotent `controlPlaneRequestId`. The schema does not accept a client-supplied actor: the actor is derived server-side from the authenticated operator session or workload. The response and audit record expose that actor and the resulting monotonic `pointerVersion`. `pointerVersion` is the route version and CAS token for exactly `{tenantId, worldSlug, realmSlug}`. The write succeeds only when the stored version equals the expected version; otherwise it returns a conflict and leaves the route unchanged. An absent route record uses `expectedPointerVersion=0` for the first open rather than an unscoped blind write.
- Replacing or rolling back `OPEN(old)` to `OPEN(new)` is a prepared cutover, not a generic open. It must use the internal `ExecutePreparedVersionCutover` control-plane operation with one durable `preparedVersionUpgradeId`; that operation revalidates the preparation, source and target identities, and CAS version before atomically swapping the route. Preparation is proof for cutover, not a substitute for route-version concurrency control.
- Game Session remains the sole routing-state writer and audits the transition under the same identity and CAS result. Internal callers must not maintain a competing pointer or infer `tenantId` from `worldSlug` or `realmSlug`; Logging & Admin's public REST surface reads the resulting state and audit evidence only.
