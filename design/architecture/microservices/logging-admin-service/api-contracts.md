# Logging & Admin Service API Contracts

This document defines the Logging & Admin Service REST and gRPC surfaces, authentication classes, and endpoint availability expectations.

## Implementation Status

- Feature-flag toggles, version-upgrade preparation mutations, and scoped tick-remediation pause/resume forwarding have implementation paths but are unavailable as supported operator mutations until their action-family schemas and shared cross-language `mutationDigest/v1` golden vectors exist. Admission-pointer reads, audit, and prepared-upgrade reads remain live; admission-pointer CAS open/close and prepared cutover are target-state mutations, not current implementation claims.
- The current supported Logging & Admin mutation surface is limited to moderation policy persistence/audit. Game Session and Social & Groups synchronously consume the live policy evaluation at the `GAMEPLAY_ADMISSION` and `CHAT_SEND` enforcement boundaries. Versioned snapshot/event propagation and broader policy coverage are not implemented. Existing Game Session `/sessions*` lifecycle routes are current owner-local hooks, not a complete external Logging & Admin route family. These distinctions do not mean that read, audit, log-search, saga, metrics, or dashboard/observability endpoints are absent; those are separate live read and investigation surfaces.
- Live admission-pointer reads, audit, and prepared-upgrade reads, plus the gated preparation and target-state CAS/cutover mutations when conformant, are part of the core operator/control-plane availability model and must not depend on observability backends.
- The canonical `SetAdmissionPointerRequest` REST schema omits `actorPrincipal`. `AdmissionPointerServiceImpl` derives the actor from the authenticated operator session or internal workload and writes that derived value to the internal control-plane request; `actorPrincipal` is response/audit data, not client-supplied write authority.
- Public administrative report persistence is currently unavailable. The unsafe HTTP controller and `/api/admin/reports/**` Gateway route have been removed because the canonical role- and purpose-scoped authorization and live reference-validation checks are not implemented. The internal `CreateReport` gRPC contract remains behind the existing internal mTLS/workload boundary; caller-supplied tenant, reporter, and optional target identities are data references only. A separate player submission contract, if introduced, must bind the `player-bootstrap` subject and live tenant membership and must not be inferred from the unavailable administrative route.
- `ApplyModerationAction` currently persists moderation policy input and audit in Logging & Admin. The separate live `EvaluateModerationPolicy` contract supplies synchronous decisions consumed by Game Session at `GAMEPLAY_ADMISSION` and Social & Groups at `CHAT_SEND`; the operator action is not itself a forwarded enforcement mutation. Versioned snapshot/event propagation and broader enforcement remain target coverage.
- Quota-override ingress is a hypothetical target family until Account exposes the canonical owner-side override mutation contract; no executable route exists today.
- Broader tick-remediation `remediate` is a hypothetical target family until Game Session exposes the canonical owner-side remediation RPC; no executable route exists today.

## REST

- `GET /ping` – basic health check returning `"pong"`.
- `POST /reports` – unavailable. The public administrative controller and Gateway exposure are removed until the canonical administrative authorization and pre-persistence reference-validation checks exist. Do not treat the internal `CreateReport` gRPC contract as a public or player submission route.
- `POST /feature-flags/toggle` – implemented but unavailable pending its action-family schema and shared `mutationDigest/v1` golden-vector conformance.
- `POST /logs/query` – search stored logs.
- `POST /moderation/actions` – persist moderation policy input and audit (current); it does not forward an enforcement mutation. Runtime owners enforce the current synchronous `EvaluateModerationPolicy` result at `GAMEPLAY_ADMISSION` and `CHAT_SEND`; versioned propagation remains separate target work.
- `GET /sagas` – list saga instances.
- `GET /sagas/{id}/steps` – inspect steps for a saga instance.
- `GET /admission-pointers` – list the caller-visible Game Session route records joined with their separately revisioned catalog/policy projection, including `OPEN`/`CLOSED`, the route version, and the explicit public-production policy used by admission and first-join membership creation.
- `GET /admission-pointers/{tenantId}/{worldSlug}/{realmSlug}/audit` – read the append-only cutover audit history for one gameplay realm pointer, using the same canonical `{tenantId, worldSlug, realmSlug}` key as admission authority itself instead of inferring tenant ownership from world/realm selectors after the read.
- `POST /admission-pointers` – target-state same-target route mutation that would open the existing `gameInstanceId` or move it to `CLOSED`, forwarding the required expected route version to Game Session's atomic compare-and-set control plane. It is not a current live capability. Retargeting an open `gameInstanceId` to another instance is not a generic mutation and is accepted only through the target-state `/admission-pointers/cutover` operation.
- Realm display, visibility, and public-production policy mutations use a separately revisioned catalog/policy control-plane surface; they must not be smuggled through a route mutation or invalidate active gameplay merely by changing presentation metadata.
- `POST /admission-pointers/cutover` – target-state canonical prepared retarget/cutover operation that would forward one prepared-upgrade id, replacement instance id, and pointer CAS guard to Game Session so proof revalidation and pointer swap happen in one control-plane call. It is not a current live capability.
- `POST /admission-pointers/version-upgrades` – implemented operator-facing preparation mutation, but unavailable pending its action-family schema and shared `mutationDigest/v1` golden-vector conformance. When enabled, it persists the Game Session `PrepareVersionUpgrade` compatibility proof for a source instance and target version under the caller-supplied `controlPlaneRequestId` and canonical digest; exact retries reuse that pair and a changed digest conflicts.
- `GET /admission-pointers/version-upgrades/{tenantId}/{preparationId}` – read one durable prepared-version-upgrade proof, including participant attestations and execution state after a cutover has consumed the preparation.
- `POST /tick-remediation/pause` – implemented forwarding path, but unavailable pending its action-family schema and shared `mutationDigest/v1` golden-vector conformance.
- `POST /tick-remediation/resume` – implemented forwarding path, but unavailable under the same conformance gate.

### Administrative Report Contract (Unavailable HTTP Surface)

The former `POST /reports` administrative route was a tenant-scoped operator surface, not a player submission route. It is not currently routable. If reintroduced, its canonical access policy is `tenant_regular`: a human request requires the exact `control-ui` token, the current route-allowed operator role (`moderator`, `tenantAdmin`, or an explicitly declared `platformAdmin` override), role-appropriate assurance, and an Account-issued operator authorization reference bound to the `report_persistence` action family, explicit target tenant, and `controlPlaneRequestId`. Tenant-role alternatives additionally require live membership and the caller-bound membership-generation check for the explicit target tenant. A `platformAdmin` override follows the explicit-target and target-generation branch rules in [ADR 0040](../../decisions/adr-0040-account-global-control-login-and-explicit-tenant-selection.md), does not require target-tenant membership or membership-generation authority, and does not obtain authority from the supplied reporter or target references. Unattended automation instead requires the exact Logging & Admin workload mTLS identity and Account's versioned automation-policy authorization reference bound to the same action family and tenant scope; it carries no human identity or end-user token.

Before creating the durable report record, the service must validate all request references against live authoritative data and fail closed on missing, unavailable, or ambiguous evidence:

- `tenantId` must identify an existing tenant within the operator authorization reference's permitted tenant scope.
- `reporterAccountId` must identify an existing account with the report-policy-required relationship to that tenant; it is report data, not the authenticated operator subject.
- If `targetAccountId` is supplied, it must identify an existing account valid for the same tenant and report policy; omission is allowed only when the report type permits no target.
- The report type and description must satisfy the applicable moderation/report policy before persistence, and the audit record must retain the authenticated operator or automation actor separately from the supplied references.

The implementation gap is fail-closed: the HTTP controller and Gateway route are removed rather than persisting caller-supplied references without the checks above. The internal `CreateReport` gRPC contract remains an internal report-ingress seam behind the existing workload boundary and must not be described as public or player-facing. The canonical checks above are required before any public administrative route is restored.

### Hypothetical/Target Coverage

- Quota override is hypothetical target coverage: it has no current OpenAPI route and no current Account owner mutation contract. Do not add `/quota-overrides*` until the owner contract exists.
- Versioned moderation propagation and broader enforcement are target coverage. Current Game Session and Social & Groups enforcement synchronously consumes Logging & Admin `EvaluateModerationPolicy`; `POST /moderation/actions` only persists policy input and audit and is not an enforcement mutation.
- Game instance session lifecycle remains a current Game Session owner-local route family (`/sessions*`), not current Logging & Admin ingress. Its target external operator path is Logging & Admin to Game Session owner RPCs; no complete current Logging & Admin `/sessions*` route family exists.
- Scoped remediation beyond pause/resume is hypothetical target coverage: it has no current OpenAPI route and no current Game Session owner RPC. Do not add `/tick-remediation/remediate` or a direct Redis mutation path.

**Target ADR 0048 owner-forwarding path:** supported executable operator mutations use Account's canonical [`IssueHumanOperatorAuthorizationReference`](../account-service/api-contracts.md#operator-authorization-references) contract after Logging & Admin authenticates the current `control-ui` actor and records durable intent. Unattended automation uses the typed Account `IssueAutomationOperatorAuthorizationReference` path with `exact_mtls_workload_plus_versioned_automation_policy`, bound to the exact Logging and Admin workload mTLS identity and current `automation_policy_id`/`automation_policy_version`; it carries no human identity or end-user token. Logging & Admin forwards the opaque bounded reference to the owning service only for those supported executable mutations. The persistence-only moderation route still requires the Account-issued operation/tenant-bound human reference before persistence, but does not use owner forwarding because Logging & Admin owns that record. The owner recomputes the canonical digest of the normalized request and redeems the reference directly with Account; the request identity is the exact `controlPlaneRequestId` plus digest pair, and Logging & Admin never becomes a second authorization authority. Current feature-flag, tick, and admission-pointer forwarding paths are not evidence that this ADR 0048 target contract is complete.

### Target-State Canonical Admission State Operations

When implemented, `POST /admission-pointers` will represent exactly one of two same-target Game Session control-plane operations for `{tenantId, worldSlug, realmSlug}`. These CAS operations are target-state only; the live boundary is limited to admission-pointer reads, audit, and version-upgrade preparation/read.

- `OpenAdmissionPointer` performs `CLOSED -> OPEN(target)`. The target must exist, belong to `tenantId`, and be the prepared/active runtime for the same world and realm. It must pass current runtime lifecycle and entitlement/admission checks; display names, slugs, or a caller-supplied instance id are not proof of that relationship. If validation is unavailable or ambiguous, the operation fails closed. `preparedVersionUpgradeId` is forbidden because this operation cannot replace an already open target.
- `CloseAdmissionPointer` performs `OPEN(target) -> CLOSED`. Game Session first checks the idempotency record for `controlPlaneRequestId`: an exact completed duplicate replays its original successful response and audit identity before current pointer-state validation. For a new request ID, the request must identify the exact currently open `gameInstanceId`; a missing pointer, already closed pointer, or different current target fails without mutation. Reusing a completed request ID with a different digest conflicts. Closing is a safety operation and therefore does not require the target to remain lifecycle- or entitlement-admissible. It cannot select a replacement target, and `preparedVersionUpgradeId` is forbidden. The resulting pointer makes no `gameInstanceId` gameplay-admissible while preserving the former target in audit evidence.
- Both requests carry the complete routing identity, target `gameInstanceId`, expected route version (`expectedPointerVersion`), reason, and idempotent `controlPlaneRequestId`. The schema does not accept a client-supplied actor: the actor is derived server-side from the authenticated operator session or workload. The response and audit record expose that actor and the resulting monotonic `pointerVersion`. `pointerVersion` is the route version and CAS token for exactly `{tenantId, worldSlug, realmSlug}`. The write succeeds only when the stored version equals the expected version; otherwise it returns a conflict and leaves the route unchanged. An absent route record uses `expectedPointerVersion=0` for the first open rather than an unscoped blind write.
- Replacing or rolling back `OPEN(old)` to `OPEN(new)` is a prepared cutover, not a generic open. It must use `/admission-pointers/cutover` / `ExecutePreparedVersionCutover` with one durable `preparedVersionUpgradeId`; that operation revalidates the preparation, source and target identities, and CAS version before atomically swapping the route. Preparation is proof for cutover, not a substitute for route-version concurrency control.
- Game Session remains the sole routing-state writer and audits the transition under the same identity and CAS result. Logging & Admin authenticates and records operator intent but must not maintain a competing pointer or infer `tenantId` from `worldSlug` or `realmSlug`.

## gRPC

- `Ping(PingRequest) returns (PingResponse)` – connectivity check defined in [`logging_admin_service.proto`](../../../../protos/logging-admin/v1/logging_admin_service.proto).
- `QueryLogs(QueryLogsRequest) returns (QueryLogsResponse)` – searches collected logs.
- `ApplyModerationAction(ApplyModerationActionRequest) returns (ApplyModerationActionResponse)` – records a moderation event.
- `CreateReport(CreateReportRequest) returns (CreateReportResponse)` – internal report persistence behind the existing mTLS/workload boundary. Caller-supplied tenant, reporter, and optional target identities are data references only; they do not authorize a caller. This gRPC contract is not public HTTP or player submission ingress.
- `ToggleFeatureFlag(ToggleFeatureFlagRequest) returns (ToggleFeatureFlagResponse)` – enable or disable a feature flag.
- Tick-remediation is not a Logging & Admin-owned state-mutation gRPC surface; this service audits and forwards those operator actions to Game Session control-plane APIs instead of defining a competing remediation RPC.

## Endpoint Authentication Classes

| Surface | Examples | Required auth path | Notes |
| --- | --- | --- | --- |
| Public/infra health | `GET /ping`, `Ping` | Internal network + platform health policy | Not a user-authenticated business operation. |
| Administrative report persistence (HTTP) | Unavailable; the former `POST /reports` and `/api/admin/reports/**` route were removed | Canonical target: exact `control-ui` plus current route-allowed role, role-appropriate assurance, and Account operator authorization reference bound to `report_persistence`; unattended automation uses exact workload mTLS plus the versioned automation-policy reference | The public route remains unavailable until tenant scope, reporter relationship, optional target relationship, report policy, and authorization-reference checks are implemented. This is not player ingress; any separate player route must bind `player-bootstrap` authority independently. |
| Read/investigation APIs (HTTP) | `/logs/query`, `/sagas*`, `GET /admission-pointers`, `GET /admission-pointers/{tenantId}/{worldSlug}/{realmSlug}/audit`, `GET /admission-pointers/version-upgrades/{tenantId}/{preparationId}` | The exact route-declared read auth path, normally `control-ui` plus current role and route classification | These surfaces do not mutate domain or policy state and do not receive an operator mutation reference. |
| Supported human mutation (HTTP) | `/moderation/actions` | Exact `control-ui` profile, current route-allowed role, role-appropriate assurance, and an Account-issued operator authorization reference | Persists policy input/audit in Logging & Admin; it is not a forwarded enforcement mutation. |
| Gated implemented mutations (HTTP) | `/feature-flags/toggle`, `POST /admission-pointers/version-upgrades`, `/tick-remediation/pause`, `/tick-remediation/resume` | Unavailable until the family schema and shared `mutationDigest/v1` vectors exist; then exact `control-ui` plus current role, assurance, and Account operator authorization reference | Implementation paths do not establish canonical support. Once conformant, the owner redeems the bound reference and validates domain facts, fencing, and idempotency. |
| Target operator mutations (HTTP) | `POST /admission-pointers` for open/close, `POST /admission-pointers/cutover` for prepared retarget, future `/quota-overrides*`, and broader remediation | Target: the same `control-ui`/Account authorization model after the owning contracts exist | These routes are documented target capability only and must not be treated as current route availability. The owning service validates domain facts, fencing, and idempotency. |
| Owner mutation calls (gRPC internal) | Current feature-flag and tick owner RPCs; current session-lifecycle hooks remain Game Session owner-local; target admission, moderation, quota, broader-remediation, and Logging & Admin session-lifecycle owner RPCs | Exact Logging & Admin mTLS identity plus Account redemption of the matching human or versioned automation authorization reference | The owner validates domain facts, fencing, and idempotency. Logging & Admin assertions alone are not authority. |
| Service-to-service control/ingest (gRPC internal) | Internal lifecycle/event ingestion and trusted backend calls | mTLS caller identity + explicit service authorization checks | Never exposed at public ingress; use an exact receiver-specific private delegation profile only where the route declares one. |
