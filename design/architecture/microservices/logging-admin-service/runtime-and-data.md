# Logging & Admin Service Runtime and Data

This document defines the Logging & Admin Service runtime model, availability partitioning, control-plane responsibilities, and persistent data ownership.

## Architecture and Design Notes

Logging & Admin uses the common stack outlined in [Logging & Monitoring](../../system-architecture-logging-monitoring.md) and exposes admin endpoints for reviewing logs, managing coordination health, and coordinating gated moderation actions. Its current log-query implementation reads only the service-owned PostgreSQL `log_events` table for an exact tenant plus case-insensitive message containment. Profile-aware indexed or console/journal query integration, Kibana/Grafana clients, embedded dashboards, and a separate admin UI remain target-state and unimplemented; the linked logging owner defines the canonical profile contract.

## Target-State Runtime Contract

Logging & Admin is the operator-facing policy, audit, and observability coordination plane. It owns moderation policy definitions, operator intent, audit history, the target/hypothetical quota and limit override UX, control-plane inspection, and the availability boundary between core operator actions and observability-backed experiences. It does not own gameplay coordination state, runtime feature-flag truth, entity state, or another service's persistence, and it must invoke those owning services through their canonical contracts.

The target service preserves two independently degradable partitions:

- core control-plane actions remain usable when search, metrics, tracing, dashboards, or alerting backends are unavailable;
- observability-backed searches, dashboards, traces, and alert investigations degrade explicitly without taking the core control plane down.

Moderation policy, case, appeal, and audit records carry one explicit normalized jurisdiction scope. Tenant-scoped records carry the exact `tenantId` and any narrower realm/channel scope and remain visible only through tenant-authorized query paths. A `platform_access_ban` record instead carries platform scope plus the global target account principal and never fabricates a `tenantId`; its reads and actions require a separately authorized platform-jurisdiction path. Tenant query paths exclude platform rows and reject cross-tenant or mixed-scope selectors. Platform-jurisdiction audit records retain the authenticated actor, global target account, platform scope, request identity and digest, and terminal outcome. Account's separate enforcement projection remains the global `{accountId, category}` owner-local record rather than a Logging & Admin runtime-enforcement copy.

Tick and coordination recovery remains a Game Session responsibility. Logging & Admin may display health, choose a named allowed operation, invoke its authoritative owner, and record audit evidence, but Game Session remains the authority for region leases, pause/resume, reset, and coordination mutation. The live pause/resume target is exactly one gameplay instance, identified by `<tenantId, gameInstanceId>`; regional pause/resume and named regional recovery actions are target-only contracts, not live broad-scope controls. Any regional or aggregate operation must carry the owning service's explicit scope and fencing evidence rather than being inferred from an operator UI selection.

Target external session-lifecycle operator requests enter through Gateway and Logging & Admin under [ADR 0047](../../decisions/adr-0047-logging-admin-as-external-operator-write-ingress.md); phase-qualified owner execution and reconciliation follow [ADR 0048](../../decisions/adr-0048-durable-idempotent-operator-write-execution.md). Logging & Admin authenticates the operator, records durable intent, and forwards the opaque Account authorization reference and exact operation identity unchanged to Game Session owner RPCs. Game Session validates domain facts and redeems the reference at its receiving owner boundary; direct external exposure of Game Session's owner-local `/sessions*` hooks is not a substitute for this ingress family. The moderation policy-input/audit path is the sole receiving-boundary exception: it uses one separate Account-issued intent-persistence reference bound to the exact request/digest, which Logging & Admin validates and redeems exactly once before persistence. That local reference is never forwarded or reused. A future moderation owner-enforcement command receives a separately issued command-bound reference redeemed exactly once by its receiving owner. `EvaluateModerationPolicy` is a live read and carries no mutation authorization reference.

## Implementation Status

The current shipped scope is narrower than this target contract:

- The service exposes core admin investigation reads, saga inspection, coordination-health reads, and the narrow PostgreSQL-backed log query described above. Moderation policy-input and report-persistence paths are only unsupported legacy transport/internal seams that hard fail closed or remain authorization-unproved; they are not exposed current capabilities. The service does not implement the target profile-aware log-query/dashboard integrations or the complete target control-plane workflow for every recovery, regional, or aggregate operation.
- The moderation policy-input and audit persistence mutation has present legacy transport stubs through `POST /moderation/actions` and the internal `ApplyModerationAction` gRPC ingress; after narrow tenant/admin checks they hard fail closed with HTTP `503 Service Unavailable` or an application-level gRPC `UNAVAILABLE` error, without dispatch or persistence. They are unsupported, nonconformant implementation drift and must not be wired or called as available mutations. They do not provide the target fixed-category policy-input/audit record or Account, Game Session, or Social & Groups enforcement state. Current execution performs no Account authorization-reference issuance or redemption, owner forwarding, or owner enforcement. Once its action-family schema, shared cross-language `mutationDigest/v1` golden vectors, Account authorization-reference issuance, and Logging & Admin receiving-boundary validation/redemption are complete, Logging & Admin redeems the separate intent-persistence reference exactly once at its receiving boundary; that reference is never forwarded or reused and the path does not require owner-side authorization-reference redemption or enforcement. Any future owner-enforcement command uses a separately issued reference redeemed once by its receiving owner. The separate `EvaluateModerationPolicy` compatibility read remains live at the owner enforcement boundaries and carries no mutation authorization reference. Public administrative report persistence at `POST /admin/reports` is unavailable: the HTTP controller and Gateway route were removed because canonical authorization and live reference validation are not implemented. The internal `CreateReport` gRPC ingress is not public; its interim receiver guard requires an internal-service JWT naming `social-groups-service`, which the Social & Groups client emits, while certificate-derived exact workload/method authorization remains unproved. The reserved player-bootstrap `POST /reports` submission route is separate and also unavailable until its caller-bound subject and live tenant-membership checks exist.
- Admission-pointer reads, audit, and prepared-upgrade proof reads are implemented and live. Internal admission-pointer mutation, version-upgrade preparation, and prepared-cutover owner paths have implementation-participating surfaces, but the current pointer writer is read-then-write/nonconformant; the target atomic open/close CAS and prepared cutover remain unimplemented and externally unavailable behind internal trust boundaries, with public HTTP/Gateway write support unavailable and no current UI control. Target-only absent is reserved for operations with no executable owner path at all, such as quota-override mutations or future named typed recovery actions whose owner contracts do not yet exist.
- **Implemented but externally gated:** The per-instance tick pause/resume ingress is declared at the `<tenantId, gameInstanceId>` boundary, not a claim of live admin UI or automation, and no Logging & Admin forwarding method is callable. Its minimum schema/authorization gate is the action-family schema, shared cross-language `mutationDigest/v1` golden vectors, Account authorization-reference issuance, and exact owner-side redemption/authentication and scope binding. That minimum gate only establishes that a typed request can be authorized for admission; it is not the complete execution contract. A forwarded tick mutation also remains unavailable until ADR 0048's complete durable, phase-qualified intent and authorization record, canonical `postAuthorizationExecutionTuple`, owner durable idempotency/result record, current owner/gameplay fence, and fenced no-accept/no-commit reconciliation proof are implemented and proved. Regional pause/resume and named regional recovery actions remain target-only behavior, with no claim that the target instance contract implicitly expands to a region or aggregate scope; they are tracked in [Game Session runtime and tick coordination](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md#capability-status).
- Logging & Admin consumes Game Session health and requests Game Session-owned control APIs; it does not directly mutate Redis or runtime coordination state.
- Moderation policy intent, fixed-category case/audit data, bounded appeal cases/evidence, and operator history remain owned here, while Account, Game Session, and Social & Groups enforce their respective local restriction state. Active [ADR 0146](../../decisions/adr-0146-owner-local-moderation-enforcement.md) (mapped from reviewed archive record `archive-ADR-0133`) is the owner-local authority outcome: one typed digest-bound command reaches the enforcement owner, which commits monotonic local state, and routine boundary reads do not call Logging & Admin. Quota/limit override is hypothetical target UX only; no current Account owner mutation route exists. The legacy policy-input/audit transport stubs now hard fail closed before dispatch or persistence; they do not persist target fixed-category policy input or audit evidence, represent a domain-owner enforcement mutation, or provide target proof. Current execution performs no Account authorization-reference redemption. The current `EvaluateModerationPolicy` read is an implementation compatibility seam, not target authority; target owner commands and bounded appeal outcomes follow [Moderation Policies](./moderation-policies.md). Once the target persistence gate is complete, Logging & Admin validates and redeems its one separate intent-persistence reference exactly once for its own persistence path; it never forwards or reuses that reference. Future receiving enforcement owners redeem separately issued command-bound Account references and retain their own state.
- The core/observability availability split is a design contract; exact independent deployment and pool isolation remain implementation obligations rather than a claim that every backend integration is already isolated in production.
- The current composed plugin epoch/fence readback remains incomplete and unproved; missing or stale owner evidence must remain non-success and must not authorize admission or cleanup completion.
- World-lifecycle and replacement composition described below remains target-state; current operator readback does not prove complete owner acknowledgement or cleanup convergence.

Non-moderation operator write requests use one canonical logical `controlPlaneRequestId` across HTTP, Java/domain contracts, ADRs, and audit records. Protobuf contracts may use the wire spelling `control_plane_request_id`, which maps directly to that same identifier. Moderation policy intent uses `policyIntentRequestId`, owner enforcement uses `ownerEnforcementRequestId`, and appeals use their defined stable identity; `controlPlaneRequestId` is correlation-only for those flows. Human requests use the typed Account `IssueHumanOperatorAuthorizationReference` path and require the current `control-ui` identity, the applicable tenant or target-tenant generation, and any required `privileged_control` predicate. Unattended automation uses the typed Account `IssueAutomationOperatorAuthorizationReference` path with `exact_mtls_workload_plus_versioned_automation_policy`, bound to the exact Logging and Admin workload mTLS identity, its `automation_policy_id`/`automation_policy_version`, and the exact tenant generation; the current automation branch is tenant-scoped and cannot authorize a global-role or `privileged_control` action family. Unattended authorization contains no user account, end-user token, or human identity, and neither path may substitute the other's identity.

Owner reconciliation for an expired `PENDING` claim or missing owner record is bounded and read-only: the current owner inspects the original request ID, digest, durable effect/outcome evidence, owner mutation marker, lease/fence, and target version/state within a fixed attempt and deadline. It does not call a business mutator, create new authorization, or replay a payload. A proven terminal commit may be recorded as committed; durable proof of no mutation may be `NOT_EXECUTED`; missing or conflicting evidence, including an absent Redis marker and absent terminal result, remains `PENDING`/indeterminate and non-replayable so recovery cannot double-apply a write.

In addition to log and moderation tooling, the service acts as a control-plane coordinator for tick and coordination health:

- Consumes metrics and health information published by the Game Session Service (for example, per-region status such as `HEALTHY`, `DEGRADED`, or `COORDINATION_UNTRUSTWORTHY`).
- Describes target-state admin APIs and UI controls for:
  - targeting pause or resume tick execution for the `<tenantId, gameInstanceId>` boundary only after the minimum schema/authorization gate and the complete ADR 0048 owner-execution contract described above are complete; regional pause/resume controls remain target-state behavior and are tracked against the current Game Session implementation status in [Game Session runtime and tick coordination](../../../project-management/implementation-tracking/game-session-runtime-and-tick-coordination.md#capability-status); and
  - requesting the scoped tick pause/resume operation through Game Session control APIs; future reset or recovery actions require separate named typed owner contracts and remain unavailable until those contracts exist.
- Describes target-state guarded automation that would:
  - enumerate affected game instances from coordination-health signals and, after the minimum schema/authorization gate and complete ADR 0048 owner-execution contract pass, call Game Session `PauseTicksForScope`/`ResumeTicksForScope` for each exact `<tenantId, gameInstanceId>` scope; regional pause/resume and other regional mutations remain target-state only; and
  - issue conformant per-instance requests without requiring an operator to be present, while still emitting audit events for every action. A closed, typed, risk-reducing unattended action is allowed only when the durable request identifies the service principal, policy or rule version, trigger evidence, exact scope, and idempotent payload digest. Any broader named owner operation remains target-state only. Unattended requests use the typed Account authorization path with the exact Logging and Admin mTLS identity plus the current versioned automation policy; they never synthesize a human `control-ui` token or operator identity.

Game Session remains the only service allowed to mutate gameplay coordination state or execute tick pause/resume behavior. Logging & Admin owns operator UX, automation policy, and audit only; it does not become the runtime state owner for remediation.

There is no generic remediation command language. Ordinary actions use named owner contracts. Composed recovery exposes only a small high-level vocabulary such as pause, status, recover or reset, and resume through one durable workflow owner. Exceptional direct Redis maintenance remains separate version-matched break-glass tooling with dedicated narrow credentials, forced verification, and recovery evidence; Logging & Admin may invoke that owner or tool but never receives those credentials itself.

Operator and support diagnostics do not impersonate a player, attach to a live player session, or observe gameplay through a hidden actor. They use purpose-built, minimized support-safe reads, logs, dashboards, reports, moderation records, and explicit control-plane operations. Break-glass controls remain separately authorized and audited and must not create a player actor, gameplay session, or tenant-scoped gameplay capability.

- External operator REST endpoints exposed through Gateway require the declared `control-ui` JWT and route-specific authorization. The target internal gRPC contract requires concrete mTLS workload identity plus exact service/method authorization; the interim `EvaluateModerationPolicy` and `CreateReport` receiver guards reject non-internal JWTs and unallowlisted service names, and Social & Groups emits internal-service JWTs for those calls. Certificate-derived exact workload/method authorization remains unproved.
- The target security model uses the `control-ui` JWT and route policy for external operator REST, plus workload mTLS and method allowlists for internal gRPC; Gateway/internal management surfaces and namespace/network-policy controls prevent direct public exposure. The certificate-derived exact workload/method boundary remains an implementation gap even where the interim JWT receiver guard is present.
- Canonical target-state admin APIs use role-based access control integrated with Account Service. Human operator writes require the current `control-ui` identity and Account's human authorization reference; unattended automation uses the exact Logging and Admin mTLS identity and Account's typed, versioned automation-policy authorization reference rather than a human token or identity. Current mutation paths that do not yet implement the applicable action-family/scope/digest and reference-redemption contract remain unsupported/nonconformant; the legacy moderation transport stubs hard fail closed after narrow tenant/admin checks and must not be treated as available or conformant merely because they perform those checks.
- Tenant-scoped moderation data and current `log_events` rows include `tenantId` so administrators see only information for games they manage. Target indexed profiles preserve that tenant scope in their mapped records and query paths. Platform-scoped `platform_access_ban` policy/case/audit records use the explicit platform jurisdiction described above and carry no fabricated tenant. Tenant queries exclude platform rows and reject cross-tenant or mixed-scope selectors; platform reads require the separately authorized platform-jurisdiction path. See [Multi-Tenancy](../../system-architecture-multi-tenancy.md).
- The service utilizes the [Shared Libraries](../../system-architecture-shared-libraries.md) for DTO definitions, logging interceptors, and Micrometer metrics.

## Availability Partitioning

This service has two intentionally different availability classes:

- Core operator control plane: security-sensitive operator APIs whose availability must not depend on observability backends.
- Target observability-backed experiences: selected-profile log search, embedded dashboards, metric exploration, traces, and alert-centric investigations.

The core operator control plane must remain available when Elasticsearch, Prometheus, Jaeger, Grafana, Kibana, or Alertmanager are degraded, but observability loss does not waive ordinary authorization, authority, fencing, audit, idempotency, or action-specific safety gates. Implementations preserve this with independent readiness/degradation behavior, resource isolation, and defensive timeouts or circuit breakers around observability backends.

The architecture treats these as two runtime partitions even when they are delivered from one deployable:

- Core control-plane availability and route classifications follow [Implementation Status](#implementation-status) above and the [API contracts](./api-contracts.md#implementation-status). This partitioning section defines only the operational rule: live core reads and future gated control-plane paths must not depend on observability backends, while observability-backed experiences may degrade independently.
- A target owner-forwarded core write proceeds only while its owner-side mutation-support gates and inputs remain available: the action-family schema, shared `mutationDigest/v1` golden vectors, Account authorization-reference issuance plus redemption by the authoritative receiving owner, authentication and tenant or jurisdiction binding, required durable audit or intent persistence, authoritative owner state and fences, stable request identity, and durable owner acknowledgement. The target local `/moderation/actions` receiving-service path uses a separate gate: the action-family schema, shared digest vectors, Account authorization-reference issuance plus exactly-once local receiving-boundary redemption, authentication and tenant or jurisdiction binding, stable request identity, durable local intent/audit commit, and local acknowledgement. It does not require downstream owner-side reference redemption, authoritative downstream owner state or fences, or downstream owner acknowledgement because it does not mutate downstream owner state. If any mandatory input for the selected target path is unavailable, that action fails closed; the current legacy moderation transport stubs fail closed before those target inputs are evaluated and remain unsupported/nonconformant.
- Risk-reducing actions such as close admission, pause ticks, disable features, lower quotas, and add restrictions remain available when the applicable path's prerequisites hold. Exposure-increasing and recovery actions retain their normal compatibility, recovery, freshness, fence, and owner-state gates as well as the action-schema, digest-vector, and Account-reference gates; missing telemetry alone is neither permission nor prohibition.
- Target observability-backed endpoints include the selected profile's log search, embedded dashboards, traces, metric exploration, and alert investigation views. Once implemented, these paths may degrade independently or return the profile's explicit backend-unavailable or `not_applicable` state; the current PostgreSQL `log_events` query remains the narrower service-local read documented above.
- Stale or cached telemetry is time-labelled and cannot be presented as current authority. Unavailable current state is reported as unavailable or `unknown`.
- Readiness and degradation reporting must distinguish these partitions so an observability outage does not mark the entire operator service unavailable.
- Thread pools, connection pools, and timeout budgets for observability integrations must be isolated from the core control plane so expensive search/dashboard failures cannot starve moderation or remediation requests.
- If a future implementation cannot preserve those guarantees inside one service boundary, the architecture should split the deployable into separate operator-control and observability surfaces rather than weakening the availability rule.

See [ADR 0165](../../decisions/adr-0165-authoritative-control-actions-during-observability-loss.md).

## World Lifecycle and Replacement Diagnostics

Logging & Admin may present World Management's lifecycle state and epoch for operator diagnosis, together with the stable playable-state namespace, source and target runtime evidence, Temporal workflow progress, cleanup requests, and durable-data-owner acknowledgements. These are composed owner reads: Logging & Admin does not decide admission, infer lifecycle truth from Temporal status alone, or declare termination from a partial projection. A failed pre-activation instance can be admission-terminal while cleanup remains outstanding, and terminal cleanup is evaluated against the exact required-owner-set and ownership-registry-revision snapshot frozen when `terminationRequestId` began, rather than every currently registered owner; `TERMINATED` is reported only after World Management has durable acknowledgement from every owner in that snapshot. See [Instance Termination and Cleanup](../../microservices/world-management-service/world-creation-workflow.md#instance-termination-and-cleanup), [ADR 0122](../../decisions/adr-0122-stable-playable-state-namespaces-for-runtime-replacement.md), and [ADR 0123](../../decisions/adr-0123-database-authoritative-temporal-coordinated-world-lifecycle.md).

## Script Patch and Plugin Control-Plane Coordination

Logging & Admin provides the operator-facing audit and coordination layer around script patch and plugin changes:

- operators review automation or plugin state here and then invoke the owning control-plane APIs exposed by Game Design, Automation & Scripting, and Game Session;
- audit trails and operator intent for those changes are recorded here; and
- runtime mutation authority remains with the owning domain services rather than with Logging & Admin itself.

Logging & Admin does not write to Redis directly and does not define a competing script/plugin state-mutation API. It coordinates operator UX and audit around the documented service-owned APIs so operators can explain why automation behavior changed.

For script transitions, the complete owner-read composition is target-state and currently unavailable; current operator routes expose only bounded Game Session current-pin and convergence reads, as described by the [API/current-status boundary](./api-contracts.md#script-transition-read-and-audit-consequences-target-state-complete-composition-unavailable) and linked implementation trackers. Target-state operator responses compose owner reads at response time: Game Session supplies authoritative pin/history evidence and its owner-side convergence observation, while Automation supplies readiness, its non-authoritative observed-pin/convergence projection, plugin policy/runtime, schedule, and work/dead-letter diagnostics. The canonical shared tuple, plugin, projection, and audit-evidence schema is defined by the [scripting contracts](../../system-architecture-scripting-contracts.md), [scripting control-plane API](../../system-architecture-scripting-control-plane-api.md), and [scripting observability contract](../../system-architecture-scripting-observability-contract.md). A successful Game Session result is semantic `UNPINNED` only when `scriptPatchVersion`, `scriptPinEpoch`, and the current-pin `controlPlaneRequestId` are all absent, regardless of whether bounded history is empty or contains unsuccessful attempts; empty history is a valid `UNPINNED` result, not `UNAVAILABLE`. Any partial presence or absence of those three fields is `UNAVAILABLE`, as are owner/dependency failures, missing reads, or other ambiguous/incomplete evidence. Successful Automation responses with stale or missing observations are reported as projection lag/convergence. Logging & Admin does not persist a separate composed state/read model, pin/history copy, or rollback state machine, and never resolves disagreement by writing a projection or by choosing Automation history over Game Session history.

The observability plane must make these distinctions queryable without making search, metrics, or tracing a prerequisite for owner mutation success. A missing Game Session pin/history read is an authority-unavailable condition; a successful Automation response with stale or missing observations is projection-lag/convergence, while an Automation timeout, transport failure, or read failure is dependency-unavailable and returns non-OK gRPC `UNAVAILABLE`; neither is an operator permission to admit work. Rollback dashboards should show that ordinary gameplay continues while scoped Automation admission and asynchronous cleanup converge. A full gameplay pause is valid only for a declared unfenced effect family, migration, or compatibility transition that cannot enforce the final `scriptPinEpoch` fence; the exceptional workflow identifies the smallest complete gameplay scope and proves quiescence before mutation. The composed evidence follows the [scripting contracts](../../system-architecture-scripting-contracts.md), [scripting control-plane API](../../system-architecture-scripting-control-plane-api.md), and [scripting rollout and rollback](../../system-architecture-scripting-rollout-and-rollback.md) owners.

### Owner-read recovery and plugin notification consequences

Logging & Admin treats `ScriptPatchPinChanged`, `PluginVersionRuntimeStateChanged`, and related scripting control-plane messages as advisory refresh wake-ups. It does not persist a competing pin, plugin lifecycle, or notification-derived projection. After a lost, delayed, duplicated, reordered, or contradictory wake-up, operator reads reread Game Session or Automation owner APIs and report freshness or dependency-unavailable state rather than inferring committed state from arrival order. `eventId` is notification occurrence identity; `controlPlaneRequestId` correlates an operator request and is not a universal event deduplication key.

For plugin operations, Automation remains the activation/lifecycle owner and Game Session remains the final gameplay-execution-fence owner. Logging & Admin records operator intent and audit context, forwards the exact operation identity, and composes owner reads; it does not install the Game Session fence, declare activation or containment complete, or substitute notification delivery for the required durable acknowledgement.

## Data Model

- `log_events` is the current service-owned PostgreSQL domain table. `LogQueryServiceImpl` queries it by exact `tenantId` and case-insensitive message containment and returns only stored messages. No current implementation mirrors this table into Elasticsearch or proves the profile-aware emitter-to-query path; selected-profile indexed, compatible-backend, or console/journal querying remains target-state under [Logging & Monitoring](../../system-architecture-logging-monitoring.md#log-pipeline-queryability-contract).
- `moderation_actions` is the target durable record for accepted moderation policy intent and audit evidence, with the fixed category, normalized explicit scope, actor/case/source request, safe notice/reason, local intent-reference redemption outcome, separate owner command/result linkage when a later enforcement command exists, and the idempotency identity, digest, and timestamps. A linked owner-result revision is recorded only when that result supplies it; the local policy-intent commit never synthesizes owner revision or enforcement epoch. Raw authorization references are never persisted. The legacy `POST /moderation/actions` and `ApplyModerationAction` transport stubs now hard fail closed after narrow checks without persisting their generic legacy row; they are unsupported/nonconformant and not target fixed-category proof. Owner restriction tables and owner-command redemption are separate; Logging & Admin does not mutate them.
- `moderation_appeal_cases` and bounded `moderation_appeal_evidence_refs` are target Logging & Admin records for the `SUBMITTED -> UNDER_REVIEW -> DECIDED` lifecycle, exact appealed owner revision/digest, jurisdiction, eligibility policy, safe submission/decision, bounded evidence references, retention/legal-hold/export state, and resulting owner command identity. No complete appeal table or workflow is currently implemented.
- `player_reports` stores abuse and bug reports submitted through the internal report-persistence seam, with a `tenant_id` column; public administrative and target caller-bound external/player submission remain unavailable.
- Runtime feature-flag truth is owned by Game Session. After the action-family schema, shared cross-language `mutationDigest/v1` golden vectors, and Account-issued authorization-reference issuance plus owner-side redemption gate passes, Logging & Admin records operator intent and audit context for feature-flag requests, then forwards the mutation to Game Session rather than maintaining a competing `feature_flag` runtime table.

## Moderation Workflow

- Target state: once the administrative web UI is implemented, operators will review flagged logs and reports through that UI. The current service has no web UI; operators use the documented backend/API surfaces, and its log query implementation remains PostgreSQL-only.
- The current availability of `POST /moderation/actions` and the separate live `EvaluateModerationPolicy` read is defined in [API Contracts](./api-contracts.md#implementation-status). The target workflow first redeems one local intent-persistence reference and records policy intent/audit under its exact request identity/digest; a later owner-enforcement command uses a distinct linked request identity/digest, separately issued reference, and owner redemption. The local identity/reference is never forwarded or reused, and this service never becomes a foreign owner-table mutation.
- The fixed categories, independent revisions, safe notices, and owner-local boundaries are canonical in [Moderation Policies](./moderation-policies.md). Account owns `account_security_lock` and `platform_access_ban`, Game Session owns `gameplay_ban`, and Social & Groups owns `chat_mute` and `chat_ban`.
- Appeal cases are Logging & Admin-owned. Account provides authentication/handoff and security recovery; a modified or overturned appeal forwards a newer command to the original enforcement owner. `DECIDED` is the terminal case fact, distinct from the subsequent ADR 0048 phase-qualified owner-command outcome; `RETRYABLE` is guidance to poll/retry reconciliation for the same command identity/digest only. Filing an appeal never changes enforcement.

When enabled, policy intent, case, appeal, owner-result, and audit records are retained according to their declared lifecycle; observability is not part of write success.

## Saga Dashboard

The service exposes `/sagas` and `/sagas/{id}/steps` endpoints for operators to inspect short synchronous orchestration coordinated via the shared Saga library. Durable long-running workflow inspection belongs on the corresponding Temporal adopter read surfaces, not on the shared saga dashboard. The dashboard reads from the `saga_instance` and `saga_step` tables and publishes a `sagas.active` Prometheus gauge.

See [Transaction Strategies](../../system-architecture-transactions.md) for an overview of Saga usage across FireMUD.
