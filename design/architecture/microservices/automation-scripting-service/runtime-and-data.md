# Automation & Scripting Service Runtime and Data

This document defines the Automation & Scripting Service runtime model, persistence boundaries, reload semantics, Redis usage, and script work-item lifecycle.

## Implementation Status

The current service validates and resolves handlers during admission, persists each admitted handler as pre-DSL `PENDING_EVALUATION` work, and later lets a scheduled executor claim the work and evaluate the sandboxed DSL; it carries only the narrower read-snapshot token field, does not yet seal the complete handler input manifest, and does not persist the separate evaluated-descriptor layer. Current admission, runtime projection, schedule rows, and handoff also do not propagate `scriptPinEpoch` end to end, so exact-epoch persistence and final fencing remain target-state gaps. The target Automation-owned `pluginActivationEpoch` and owner `lifecycleRevision` are likewise not yet persisted in plugin runtime/status/work records or propagated through handoff, retry, replay, and recovery, so same-version re-enable and same-epoch lifecycle fencing remain implementation and proof gaps. These are implementation and proof gaps; the target lifecycle and manifest contracts below remain normative.

The command-plan preview boundary in [ADR 0114](../../decisions/adr-0114-command-plan-preview-dry-run-isolation.md) is non-committing: a preview must not persist live `script_work_items`, populate the live automation queue, hand off commands, or perform external side effects. It may persist isolated audit/result evidence containing the exact input identity, fenced snapshot/fixture reference, and ordered plan. The current materialized dry-run path may use the internal pre-DSL work-item/queue shape and persists that dry-run work item, but its live implementation records `finalStage=DSL_EVAL`, `finalOutcome=dry_run_completed`, and `finalReason=dry_run_no_handoff`; the shared terminal-success helper marks its internal `script_work_items.status=HANDED_OFF` even though no Game Session handoff or gameplay-work acceptance occurs. It has not converged on target `DRY_RUN_RESULT` terminology; that internal marker is not target live-work persistence or downstream-handoff evidence, and complete plan-result/input proof is still absent. This is an implementation handoff, not a competing contract.

## Architecture and Design Notes

- Executes scripts in response to world or player events received via gRPC callbacks from Game Session and other domain services. Standard lifecycle events (`onSpawn`, `onEnterRegion`, `onCommand`, and similar) are delivered as unary gRPC calls via `TriggerScriptEvent`, while tick-derived scheduling signals are driven by a gRPC streaming tick heartbeat originating from Game Session.
- Scripts run inside a sandboxed engine to prevent malicious behavior.
- Scripts are authored in a component-based DSL using a visual editor so designers can build behaviors without coding.
- AI computations are optimized for large worlds by evaluating scripts on a separate schedule and batching the resulting commands before handing them to the tick system.
- Script definitions are versioned and can be hot reloaded without downtime as described in [System Architecture: Scripting & Automation](../../system-architecture-scripting.md). Detailed sandbox and loop-safety rules live in [Script Sandbox & Resource Limits](./sandbox-runtime-design.md).
- The service listens for `NotifyScriptVersionUpdate` and reloads the specified patch into tenant-readiness state, validating compatibility and running `onLoad` before any running instance is allowed to switch to it. Tenant readiness is single-pending per tenant: if a newer publish arrives before the current pending patch reaches a terminal state, the older pending patch becomes `SUPERSEDED` and cannot later advance to `READY`.
- **Target state:** Runtime execution is instance-aware even when patch readiness is tenant-scoped: a tenant-level `READY` patch is only eligible for pinning, while admission, timer scheduling, and scoped Automation admission pause are evaluated per `<tenantId, gameInstanceId>`, and plugin activation is evaluated per `<tenantId, gameInstanceId, pluginId>`. Plugin-backed work captures the Automation-owned `pluginActivationEpoch` and owner `lifecycleRevision` and preserves and revalidates both through evaluation, persistence, handoff, staged/final effects, retry, replay, and recovery. Game Session remains the sole authority for the exact `{scriptPatchVersion, scriptPinEpoch}` and committed rollout history.
- Automation is also a lifecycle owner for these instance-scoped work, schedule, and plugin-runtime families: each family must be registered with World Management's durable cleanup-owner inventory, expose idempotent cleanup and acknowledgement, and retain namespace-backed durable state according to its S1/S2/S3 classification. A missing owner registration or cleanup acknowledgement blocks termination; local queue/drain state and workflow history are diagnostic only.
- **Target plugin lifecycle state:** Automation persists the current `(pluginVersionId, pluginActivationEpoch, pluginState, lifecycleRevision)` and at most one pending transition with the captured current tuple and fixed target values. The same runtime row separately persists `breakerState` (`CLOSED` or `DISABLED_DUE_TO_ERRORS`), bounded `breakerReason`, monotonic `breakerRevision`, and monotonic `breakerSampleGeneration` for the exact active version/runtime scope; a new active version starts at sample generation `0`, and each reset advances that generation exactly once. Breaker trip transactions compare-and-set the exact active version, observed closed-state revision, and sample generation while atomically appending immutable sample/transition evidence and advancing `breakerRevision` once. Reset transactions compare-and-set the expected disabled state/revision, clear the breaker, advance both `breakerRevision` and `breakerSampleGeneration` once, and atomically append immutable reset evidence; prior-generation samples remain history-only. Breaker transitions do not mutate lifecycle state or counters. Every state-changing lifecycle transition persists/reserves `targetLifecycleRevision = current lifecycleRevision + 1`; epoch-advancing transitions additionally persist/reserve `targetPluginActivationEpoch = current pluginActivationEpoch + 1`. Same-epoch entry to `DRAINING` retains the current `pluginActivationEpoch` while advancing/reserving the next lifecycle revision. The fixed target epoch/revision are bound into the canonical request digest, initiation and completion compare-and-set, idempotent Game Session fence-install command and durable acknowledgement, exact retry, and commit; they are never recomputed after initiation and become current exactly once on commit.
- Patch reload now also persists a first durable `script_schedule_definitions` catalog for scheduler-owned handlers such as `onInterval` / `onTimerExpire`. Its current live uniqueness key is `(tenantId, scriptPatchVersion, pluginId, pluginVersionId, scheduleDefinitionId)` with cadence/unit metadata and normalized schedule hash; because core scripts use empty plugin fields, their `scheduleDefinitionId` values are currently patch-wide unique. Observed Game Session pins create durable `script_schedule_instances` rows for the matching `(tenantId, gameInstanceId)` scope, retaining the current patch version, schedule identity, binding target, and mutable due-point state; they do not yet retain `scriptPinEpoch`. `ObserveRuntimeTickProgress` updates the runtime region and due-point fields for tick-aligned schedules, including the next future due tick; wall-clock schedules currently expose `nextDueAt`, which maps to target durable `dueAt` plus projected `nextRunAt`, not to independent deadlines. Current live schedule rows retain `playableStateScope` but not the stable `playableStateNamespaceId`; target rows must retain both, and a missing namespace fails closed rather than being inferred. Target schedule rows also retain the exact pin tuple, and target scheduler identity is scoped by stable owner kind/id as defined by [Scripting Scheduler and Timer Lifecycle](../../system-architecture-scripting-scheduler-and-timers.md#stable-schedule-instance-row-identity), while live region ownership remains a transitional non-empty scope marker and core-script owner identity remains narrower than that target. Richer recovery guarantees and their proof remain implementation gaps.
- Authoritative gameplay reads use the durable handler-scoped input manifest owned by the [DSL lifecycle contract](../../system-architecture-scripting-dsl-reference-and-lifecycle.md#read-consistency-contract). The manifest records bounded trigger facts, pinned artifacts, owner versions/values, causal floor, and seed version for each resolved handler. A `readSnapshotToken` may remain as one owner-specific manifest input or correlation value where the owner contract requires it; it is not universal authority, and retries/recovery must never fetch a fresher value.
- For gameplay-originated events, ingress and durable runtime state now also persist the resolved `playableStateScope` and stable `playableStateNamespaceId` alongside `tenantId`, `gameInstanceId`, `regionId`, `regionEpoch`, and `entityId`, so shared-state and isolated-state realms remain distinct through work-item identity, timer/schedule materialization, replay checks, dead letters, and operator reads even when they share the same tenant. `playableStateNamespaceId` is durable playable-state identity; `gameInstanceId` remains the active runtime fence and S3 scope. At the Game Session-to-Automation handoff, Game Session resolves `playableStateNamespaceId` and `playableStateScope` from the scoped runtime context and the receiving owner validates the exact `{tenantId, playableStateNamespaceId, playableStateScope, gameInstanceId, regionId, regionEpoch}` atomically with the enqueue/claim transition before enqueue or execution. This namespace/scope evidence is separate from the canonical Command-Handoff Identity and does not redefine that identity. The current live ingress/handoff wire does not yet guarantee the namespace/scope fields or their owner proof, so missing or mismatched authority remains an implementation gap and must fail closed. `regionEpoch` is an explicit Trigger Identity dimension and replay fence, not metadata that may be refreshed from the current region later. A retry is the same trigger only when it carries the same epoch. Admission, ownership transfer, handoff, and execution must not rely on a detached compare-then-apply check: the owner that durably claims or applies the work must validate the supplied epoch atomically with that transition, or the handoff must carry an authoritative fence token that the downstream execution owner validates immediately before application. A stale or mismatched event is rejected or made a fenced no-op under its original identity, recorded with a bounded `runtime_scope_changed` reason where an admitted run is canceled, and is never evaluated or reminted under the newer epoch. A producer must emit a new identity against the current epoch when the event is still valid.
- Each game’s scripts live in tables keyed by `tenantId`, ensuring automation for one game cannot access another’s data. Derived Redis coordination and index keys must preserve runtime instance isolation as well, not just tenant isolation.
- Utilizes the [Shared Libraries](../../system-architecture-shared-libraries.md) for DTO definitions, logging interceptors, and Micrometer metrics.

## Workflow Participation

The Automation & Scripting Service uses the shared workflow substrates as follows:

- Script patch consumption: when a script-only patch version is published, Game Design drives the durable publish workflow and this service participates as a consumer via `NotifyScriptVersionUpdate`, ingesting the patch for tenant readiness without coordinating its own publish-workflow steps. Running instances reload only after a later pin change to that tenant-`READY` patch.
- Bootstrap and dev-only upload path: if `UpdateScript` exists in an environment, it must be explicitly marked non-production and must not bypass patch lifecycle gates, readiness checks, or control-plane events.

Tick-driven automation and event handling never use synchronous sagas or Temporal; they follow the Redis and tick contracts described in [System Architecture: Scripting & Automation](../../system-architecture-scripting.md) and [Tick System and Runtime Design](../../system-architecture-ticks.md).

## Runtime Data Model

- `script` holds compiled component definitions and version metadata.
- `npc_memory` stores persistent state for NPC behaviors.
- **Target-state:** Admitted script work items are persisted durably in a PostgreSQL-backed outbox in `PENDING_EVALUATION`, keyed only by the full canonical Trigger Identity plus sequencing fields as needed, including `playableStateScope` and `regionEpoch`; the exact observed `(scriptPatchVersion, scriptPinEpoch)` tuple, captured plugin `pluginActivationEpoch` and owner `lifecycleRevision` where applicable, resolved binding `priorityTag`/`quotaClass`, immutable `lane`, and bounded `cost_class` are execution evidence used for the canonical charge lifecycle. The owner-committed `controlPlaneRequestId` is persisted separately as owner-grounded projection/correlation evidence and retained through reload, convergence, handoff, and recovery; it is not part of Trigger Identity, sequencing, uniqueness, or deduplication. Pre-DSL records retain the sealed immutable handler input manifest, including `priorityTag`, `quotaClass`, `lane`, `cost_class`, `componentCostRegistryDigest`, and `artifactRuntimeCapDigest` where applicable. Gameplay/runtime persistence, handoff, retry/replay, and recovery preserve these values unchanged; missing, changed, or contradictory lane/cost or plugin lifecycle-fence evidence fails closed rather than being inferred or refreshed.
- For scheduler-derived plugin work, the captured `pluginActivationEpoch` is also a tagged input to the durable schedule-candidate/firing-claim identity and therefore transitively to the derived event-scope `scriptEventId`; it remains excluded from handler Trigger Identity and Command-Handoff Identity, while `lifecycleRevision` remains fence-only. Ordinary producer ingress must not fabricate either scheduler-owned field.
- `automation:queue:{tenantInstanceTag}:<entityId>` keys in Redis buffer indexes or pointers for admitted handler work after its durable `PENDING_EVALUATION` work item is persisted. Each entry includes enough identity to locate the durable work item and must not be treated as an authoritative log of commands.
- Queue activity must be surfaced through the canonical observability contract metric families rather than through an unsupported parallel metric surface.
- Player reputation data is stored in the Social & Groups Service; this service reads those scores to drive NPC morale and aggression behavior.

## Script Lifecycle

- Scripts reside in the service database and are versioned along with other game data as described in the design-service versioning process.
- **Target-state lifecycle:** Events from Game Session and other domain services trigger script admission via gRPC. Event/handler admission seals the handler input manifest and durably creates each admitted handler's `PENDING_EVALUATION` work item, then queues its rebuildable pointer; DSL evaluation is later, only after the executor claims the work and the lease/executor-acceptance transaction advances it to `EXECUTING`.
- The sandboxed engine limits CPU time and memory for each script to prevent runaway behavior.
- After evaluation, bounded command descriptors are staged into the already admitted durable handler work item and handed off for tick enqueue; the `automation:queue:{tenantInstanceTag}:<entityId>` entry remains a rebuildable pointer rather than a post-evaluation source of truth.
- A scheduled durable executor claims persisted `PENDING_EVALUATION` work items, evaluates the current command-emission format, and hands off commands to Game Session for tick enqueue. `automation:queue:*` remains a rebuildable pointer projection rather than the driver of authoritative execution state. In the current legacy materialized dry-run path, the work-item storage status is nevertheless set to `HANDED_OFF` as a terminal compatibility marker even though no Game Session handoff occurs; the authoritative audit remains `finalStage=DSL_EVAL`, `finalOutcome=dry_run_completed`, and `finalReason=dry_run_no_handoff`. This is current implementation drift, not target `TICK_HANDOFF`/`handoff_accepted` semantics; target ADR 0114 previews use an isolated preview result and do not create a live work item.
- Target execution start is one Automation-owned durable executor-acceptance transition: after acquiring a fenced capacity lease, the worker revalidates the current fence, durably accepts/claims the run for the executor, persists the exactly-once execution-start marker, and advances the work item to `EXECUTING` before DSL evaluation. If executor acceptance fails, the transition does not commit, the lease is released or reclaimed, and no execution charge is recorded; a crash after commit recovers from the durable executor claim and may reacquire a lease but never creates a second marker.
- **Target state:** The runtime applies the ADR 0088 owner contract: conservative artifact-pinned prospective serialized-byte and data-dependent bounds are enforced before constructing output, then exact bounded serialized size is checked before atomic per-handler persistence. A cap or serialization failure discards all staged output and cannot leave a partial work item or handoff. See [ADR 0088](../../decisions/adr-0088-static-and-incremental-script-output-bounds.md) for the owner contract.
- **Current behavior:** Configurable command-count, per-entity, and ingress-payload byte limits exist, but generated collections are built before total/per-entity checks, complete generated-output serialized-byte enforcement is absent, and handler output is not yet persisted atomically; see the current-status boundary in [ADR 0088](../../decisions/adr-0088-static-and-incremental-script-output-bounds.md).
- Script ticks never hold game tick locks (`tick:{tenantRegionTag}:lock:<entityId>`); they only batch and stage automation work before handing it to Game Session, which applies commands under its own tick and locking model.

## Hot Reload and Failure Handling

`NotifyScriptVersionUpdate` starts tenant-scoped readiness ingestion for `<tenantId, scriptPatchVersion>`. Instance-scoped reload happens later only when Game Session pins an already-`READY` patch for a specific runtime scope:

- `NotifyScriptVersionUpdate` is a tenant-readiness ingestion signal, not an instance activation signal. It causes the service to ingest compiled graphs and bindings for `<tenantId, scriptPatchVersion>`, then run tenant-scoped readiness checks and `onLoad` before any running instance is allowed to pin that patch.
- Tenant readiness uses the patch lifecycle `PENDING_VALIDATION -> ONLOAD_RUNNING -> READY/FAILED`, plus terminal `SUPERSEDED` when a newer publish displaces an older pending patch for the same tenant.
- **Target state:** Runtime scopes track the exact patch and pin epoch observed from Game Session for `<tenantId, gameInstanceId>` plus the owner-committed `controlPlaneRequestId` that produced that observation, alongside instance-scoped admission state such as `reloadState` and a scoped Automation admission pause. The Automation projection persists and retains that request ID through reload/convergence and relevant handoff/recovery evidence, exposing it as `lastObservedControlPlaneRequestId`; it remains projection evidence, not pin or rollout-history authority. A notification or stale/gapped projection starts a bounded owner reread; it does not advance the projection or authorize reload by arrival order, and lower, reordered, or contradictory producer tuples/cursors are rejected.
- **Target state:** When Game Session later commits a tenant-`READY` patch for a specific runtime scope, leaders set runtime-scope `pendingPatchVersion`/`pendingPinEpoch` and the committed pin-mutation `controlPlaneRequestId`, with `reloadState=RELOADING` while retaining the captured tuple and request identity of already-admitted work. New script/plugin triggers pause for that scope; ordinary Game Session gameplay ticks continue. In-flight evaluation may finish computation against its immutable captured graph, but every persistence, handoff, and final gameplay boundary enforces the captured patch and epoch plus any captured plugin activation epoch/lifecycle revision; reload/convergence and recovery evidence retain the owner request ID rather than a locally invented correlation.
- **Target state:** Instance reload does not rerun tenant `onLoad`. Leaders first reread the authoritative Game Session tuple/history when notification or projection state is stale or incomplete, then load the already validated exact artifact for the newly observed tuple, reconcile version-scoped timers and other derived scheduler state, and atomically publish the observed projection and clear `reloadState=IDLE` only after evidence is complete. The advisory notification is published after the owner commit but may be observed before or after this consumer projection; it is never the lifecycle-completion barrier.
- **Target state:** If tenant readiness fails, the patch remains `FAILED` for that tenant and never becomes eligible for pinning. If instance reload of an already-`READY` patch fails or reconciliation evidence is stale, the service marks the runtime scope `reloadState=FAILED`, discards partially loaded derived state, and fails closed: no new trigger or timer work is admitted until the authoritative pin, schedule ownership, scope, epoch, and due state are durably reconciled. Recovery uses one idempotent recovery identity to transition `FAILED -> RELOADING`; the prior observed patch remains diagnostic state only and is never an execution fallback. Game Session may explicitly repin to a prior `READY` patch, producing a new epoch and history entry.
- Triggers pinned to a failed or unknown `scriptPatchVersion` are rejected explicitly with audit visibility and bounded failure reasons rather than falling back silently.

This behavior ensures that a script patch either becomes the new active version for the targeted runtime scope or fails cleanly without affecting unrelated live automation behavior.

**Target-state recovery evidence:** Automation owns a monotonic `failureGeneration` per `(tenantId, outboxWorkItemId)` and initializes/advances it exactly once in the same atomic transition that enters `DEAD_LETTERED`; exact transition retries/no-ops do not advance it. Dead-letter rows retain the immutable failure stage and current `failureGeneration`, original Trigger Identity, exact patch/epoch, immutable `lane` and bounded `cost_class`, owner-committed `controlPlaneRequestId`, plugin provenance and captured `pluginActivationEpoch`/`lifecycleRevision` where applicable, frozen manifest, immutable evaluated output, and a complete descriptor/child-dispatch ledger keyed by the full Command-Handoff Identity. Per-item request results, recovery claims/attempts, successful-recovery evidence, and `already_recovered` readback bind `(tenantId, outboxWorkItemId, failureGeneration)`; one active claim exists per current generation and stale owners/generations fail CAS. A new request resolves the current failure generation atomically, so older-generation evidence remains immutable and cannot satisfy or block a newer current generation. Per-child recovery state records each child status, its persisted `handoffRequirement`, attempt/claim information, and durable downstream acknowledgement or outcome. The evaluated output and complete ledger are replay input; an evaluated-output or command digest is integrity evidence only and cannot substitute for the retained output or descriptor identity. `outboxWorkItemId`, the parent Trigger Identity, and `scriptEventId` remain correlation-only identifiers and are not child identity. The frozen manifest retains `priorityTag`, `quotaClass`, `lane`, `cost_class`, `componentCostRegistryDigest`, and `artifactRuntimeCapDigest` where applicable; evaluation-stage and post-evaluation recovery reuse that evidence verbatim without recomputing mutable registry, cap, scheduler-policy, or required/optional classification values. Evaluation-stage recovery may retry the original graph; post-evaluation recovery only resumes unfinished children. Missing or contradictory evidence, including missing or changed lane/cost, plugin lifecycle-fence, or handoff-requirement values at handoff, replay, or recovery, remains dead-lettered and fails closed. Schedule reconciliation defaults to cancel-and-recreate, with continuity only when the authored stable identity and compatibility declaration explicitly match.

## Redis Roles and Prefixes

- **Coordination Redis participation**
  - Uses Automation-owned cache/rate-limit prefixes such as `automation:queue:{tenantInstanceTag}:*`, `automation:quota:<tenantId>:<scriptId>`, `automation:tenant-budget:<tenantId>:tier:<tier>`, and dry-run capacity keys. Game Session remains the only owner of `tick:{tenantRegionTag}:*` gameplay coordination prefixes.
- **Cache/Rate-Limit Redis usage**
  - Stores script quota counters and similar best-effort aggregates in Cache/Rate-Limit Redis using prefixes such as `automation:quota:<tenantId>:<scriptId>`, `automation:tenant-budget:<tenantId>:tier:<tier>`, `automation:test:capacity:<tenantId>:*`, `automation:test:capacity:cluster*`, and `automation:queue:{tenantInstanceTag}:*`.
  - Treats these keys as transient operational data; PostgreSQL remains authoritative for script definitions and long-lived automation state.
  - Quota and queue-oriented prefixes are best-effort TTL-only caches unless explicitly documented as strongly validated caches with versioned payloads and stricter invalidation semantics.

Ownership and durability expectations for Automation & Scripting prefixes:

| Prefix | Redis role | Durability / reset tolerance |
| --- | --- | --- |
| `automation:queue:{tenantInstanceTag}:*` | Cache/Rate-Limit | Reset-tolerant, best-effort cache or queue of automation work-item indexes. Loss is acceptable because admitted work items are persisted durably in PostgreSQL and can be re-driven. |
| `automation:quota:<tenantId>:<scriptId>` | Cache/Rate-Limit | Reset-tolerant, best-effort quota counters. Dropping these keys temporarily resets budgets but does not affect script correctness or long-term state. |
| `automation:tenant-budget:<tenantId>:tier:<tier>` | Cache/Rate-Limit | Reset-tolerant, best-effort tenant budget counters for live automation execution reservations. Dropping these keys temporarily relaxes tenant fairness but does not affect durable work truth. |
| `automation:test:capacity:<tenantId>:tenant`, `automation:test:capacity:<tenantId>:lease:<workItemId>`, `automation:test:capacity:cluster*` | Cache/Rate-Limit | Reset-tolerant tenant-local and cluster-wide dry-run capacity counters and leases. Leases have bounded TTLs and are released on normal completion; dropping them temporarily relaxes test-capacity fairness without affecting live work. |

Any new Automation & Scripting-specific prefixes must be added here and to the central Redis key catalogs, with a clear statement of Redis role and reset behavior.

Quota and queue-related caches are best-effort TTL-only caches unless this service doc set states otherwise. `automation:queue:*` must never be the sole source of truth for whether work has been enqueued or processed; exactly-once or at-least-once semantics are provided by durable trigger tables and idempotent domain logic, not Redis queue contents.

## Durable Script Work-Item Outbox

To avoid “DSL evaluated successfully but effects were silently dropped”, the service must durably persist and queue each admitted handler's `PENDING_EVALUATION` work item before DSL evaluation or execution acceptance:

- **Target state:** Admitted triggers seal the handler input manifest and produce `PENDING_EVALUATION` script work items written to a PostgreSQL-backed outbox table keyed by Trigger Identity plus sequencing fields as needed.
- Target materialized `script_schedule_instances`, resume windows, due candidates, firing claims/audits, timer-generated work items, handoff events, and dead-letter rows preserve the same stable `playableStateNamespaceId` and gameplay `playableStateScope` evidence so scheduler-driven follow-up work stays in the same shared-versus-isolated state namespace as the original admitted event. Namespace evidence remains separate from canonical schedule, Trigger, and Command-Handoff identities; missing or mismatched evidence fails closed rather than being inferred or refreshed. Current schedule rows still lack `playableStateNamespaceId`, as recorded in the implementation-status boundary above.
- `automation:queue:*` keys are derived coordination indexes that accelerate draining and batching, not the authoritative record of pending work.
- On restart, failover, or Cache/Rate-Limit Redis resets, the service can rebuild `automation:queue:*` indexes by scanning the outbox for pending items and re-projecting them.

This enables stage-aware outcomes in `script_event_audit`: the system can distinguish “DSL evaluation succeeded” from “handoff or enqueue succeeded”, and can re-drive delivery where appropriate without re-executing the DSL body for the same trigger.

## Redis Cluster Slotting Rules

- Automation Redis usage must never perform multi-key operations that span both `automation:*` and `tick:*` keys in a single invocation.
- Allowed examples:
  - A Redis operation that touches only `automation:queue:{tenantInstanceTag}:*` keys for one runtime scope.
  - A Redis operation that touches only Automation-owned quota or dry-run-capacity keys for one documented scope.
- Disallowed examples:
  - Any script or transaction that reads or writes both `automation:*` and `tick:{tenantRegionTag}:*` keys in one atomic Redis call.
  - Any Automation-owned key family that attempts to mirror or stage authoritative gameplay queue state outside Game Session.
- Automation work is projected under `automation:queue:*` and then handed off to Game Session via gRPC; only Game Session scripts mutate `tick:*` prefixes.

Any change to automation Redis usage or Lua scripts must follow the [Redis Design Checklist](../../system-architecture-redis-design-checklist.md) and the slotting rules above.

## PvE, Faction, and Reputation Behavior

Random encounters and environmental hazards are generated by `PveEncounterService`. Encounters are seeded so results can be reproduced during testing. The service includes an `NpcMoraleService` which adjusts an NPC’s `AggressionState` based on current health, morale, and reputation. When those values fall below configurable thresholds the NPC may become `FLEEING` or `SURRENDERED`, allowing encounters to end without a kill.
