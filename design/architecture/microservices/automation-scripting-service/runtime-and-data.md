# Automation & Scripting Service Runtime and Data

This document defines the Automation & Scripting Service runtime model, persistence boundaries, reload semantics, Redis usage, and pre-DSL trigger/evaluated script work-item lifecycle.

## Implementation Status

The unsupported NPC formation REST handlers and OpenAPI paths have been removed. Formation operations remain on the authenticated internal gRPC control-plane path, whose existing global admin guard is not the target tenant-bound `tenantAdmin` authorization or proof that referenced leader and member NPCs belong to the requested tenant and gameplay namespace. The service still checks formation-row tenant on member operations but does not obtain Entity-owned NPC ownership evidence. Removing the REST route closes its unauthenticated public reachability; internal authorization/ownership checks and focused cross-tenant NPC proof remain open.

**Target formation boundary:** keep the external public route absent, require exact tenant-bound internal `tenantAdmin` authorization without a global-role override, derive the tenant from that authority, and validate formation plus leader/member NPC ownership against the Entity Management owner read before every mutation/read. A missing or unavailable owner read, tenant/namespace mismatch, or caller-selected cross-tenant identifier fails closed before persistence or disclosure. Negative proof must cover unauthenticated access, tenant A selecting tenant B, and tenant A attaching tenant B's NPC to an otherwise tenant-A formation. The owning [API contract](./api-contracts.md#normative-target-contract) defines the complete target rule.

The current service validates and resolves handlers during admission, persists each admitted handler as pre-DSL `PENDING_EVALUATION` work, and later lets a scheduled executor claim the work and evaluate the sandboxed DSL; it carries only the narrower read-snapshot token field, does not yet seal the complete handler input manifest, and does not persist the separate evaluated-descriptor layer. For evaluated child commands, Automation commits a deterministic `HANDOFF_IN_FLIGHT` intent in a short local transaction before invoking Game Session with no Automation transaction active, then records a definitive response in a separate local transaction guarded by the work-item version. A dispatch or post-dispatch persistence ambiguity retains the intent for recovery, while a failure before the intent commits performs no RPC and returns a retryable rejection rather than falsely claiming an in-flight dispatch. Each child intent also reacquires the local admission lock and rereads the current admission state before it becomes dispatchable. The service still lacks the durable evaluated descriptor and reconciliation owner needed to resume every ambiguous handoff without re-evaluating the DSL, so the complete crash/restart contract remains unimplemented.

Admission, runtime projection, schedule rows, and runtime replay now carry the authoritative exact `(scriptPatchVersion, scriptPinEpoch)` pair plus associated owner `controlPlaneRequestId` evidence, compare that captured evidence with owner and observed state, and fail closed on absent, stale, partial, or mismatched evidence. Automation now persists `pluginActivationEpoch` and `lifecycleRevision` in plugin runtime state and captures them on plugin-backed ingress, work, audit, schedule, and handoff rows. Admission and downstream evaluation reject absent or stale captured fence evidence, including same-version re-enable and same-epoch lifecycle changes. Pending-transition ownership, Game Session fence-install acknowledgement, complete retry/replay/recovery propagation, and final gameplay-effect enforcement remain implementation and proof gaps; the target lifecycle and manifest contracts below remain normative.

Plugin lifecycle mutations use immutable request history keyed by `(tenantId, gameInstanceId, pluginId, controlPlaneRequestId)`, with the operation and canonical request fingerprint stored as bound payload. An exact retry returns the recorded result, while reuse for another operation or changed input fails before state, epoch, revision, lifecycle history, schedule, or notification mutation. Fresh same-target activation, already-`DRAINING`, already-`DISABLED`, and never-active `DISABLE` no-ops store one immutable successful request receipt while leaving runtime state, lifecycle event history, notifications, schedules, and counters unchanged. A new `DRAIN` against a plugin with no active `ENABLED` lifecycle records one immutable `FAILED_PRECONDITION` receipt without changing plugin state. Transient transition or fence-install failures are not terminalized by this receipt slice. V3 assigns a founding `(pluginActivationEpoch, lifecycleRevision)=(1,1)` only to retained runtime rows with a nonblank active version and to retained schedules whose tenant, instance, plugin, version, runtime region, and region epoch match exactly; contradictory executable rows fail migration, and schema/repository guards reject incoherent pairs or an active version at `0/0`, while historical work/audit/handoff evidence remains `0/0` and fenced because its winning admission cannot be reconstructed. Generic plugin-owned ingress also requires the later fence read to remain `ENABLED` before persisting work. Focused service and migration-shape proof executes locally; PostgreSQL receipt/concurrency and retained-data cases require Docker/Testcontainers.

The plugin lifecycle histories are separate ADR 0163 retained families. `plugin_runtime_request_history` is a retry/idempotency-receipt family: its immutable canonical request digest and terminal result must survive every supported client retry, reconnect, replay, restore, and lifecycle-transition recovery horizon. `plugin_runtime_events` is recovery/reconciliation lineage and purpose-bound lifecycle audit evidence: an event is immutable history, but it is not cleanup-eligible while a lifecycle transition, owner reconciliation, rollback diagnosis, supported restore, or related retained runtime evidence may still depend on it. Automation owns both families. Neither family currently has a declared measured minimum horizon, retention-hold mechanism, archive/compaction policy, bounded garbage-collection cadence, safe watermark, or cleanup-lag/oldest-blocker metrics, so both remain retained and ineligible for automatic deletion. A future cleanup slice must establish those fields and dependency inequalities from measured retry/recovery/governance horizons; age alone is never eligibility, and archive storage cannot replace an online receipt needed for exact retry.

The current admission barrier supports the optional regional selector and now implements the durable acknowledgement slice: boundary normalization preserves exact scope/mode/request identity, a length-delimited SHA-256 fingerprint binds the request, and immutable `APPLIED`/`ALREADY_APPLIED` history supports exact retry readback and changed-input conflict. The operator Get path performs a read-only exact-scope lookup, returns `NOT_FOUND` for an absent state and `ACKNOWLEDGEMENT_UNAVAILABLE` when durable successful history is missing, and never reconstructs missing history from mutable state. Response fields expose the successful acknowledgement identity, target mode, fingerprint, outcome, and timestamp. Direct V1 schema and focused unit proof cover this slice. Exact-head hosted CI, Automation service checks, and generic full-stack smoke passed. Hosted `integrationTest` executed against Docker/PostgreSQL and passed, but the hosted logs/artifact do not expose a trustworthy exact test count; the local exact-head integration run discovered 33 tests and skipped all 33 because Docker/Testcontainers was unavailable. Generic full-stack smoke did not exercise admission behavior and is not claimed as admission proof. The separate preview endpoint was unavailable at capacity. The target owner contract is [SetAutomationAdmissionMode](../../system-architecture-scripting-control-plane-api.md#setautomationadmissionmode); the [local API contract](./api-contracts.md#script-patch-and-plugin-visibility-apis) records this service's consequence.
Immutable admission request history currently has no cleanup and remains retained; safe pruning and production launch require a future ADR 0163/ADR 0123 owner, horizon, and tombstone design, so this boundary adds no arbitrary TTL.

Tenant-readiness mutation now serializes per tenant, preserves admitted identities on retry, and fails duplicate or unresolved script names before admission. The V2 unique active-tenant index fails closed on retained duplicates. PostgreSQL proof and the remaining manifest, notification, generation-fence, and recovery gaps are recorded in the [Automation implementation tracker](../../../project-management/implementation-tracking/automation-and-scheduler-runtime.md#current-status); this bounded correction is not complete publication readiness.

The same V2 migration replaces handler work-item and audit identities so authenticated `sourceService` participates in both pinned and unpinned uniqueness. Ingress now supplies that owner-derived value to repository duplicate checks, conflict targets, and exact readback, so equal producer-local event identities from different services remain independent while an exact same-source retry deduplicates. Migration-shape and focused repository tests execute locally; the PostgreSQL same-source/different-source integration case compiles but was skipped because Docker was unavailable. This does not close the separate namespace, sealed-manifest, lifecycle-fence, replay, or retention gaps.

The current `script_event_ingress_audit` event-scope claim uses branch-specific `INSERT ... ON CONFLICT` claims: instance-scoped rows include their exact runtime identity and positive pin tuple, while pre-instance tenant-readiness `onLoad` rows use the nullable branch without inventing absent optional identity fields. The V5 indexes provide the corresponding positive-epoch instance and pre-instance uniqueness branches. Retained pre-fencing instance rows may keep a null epoch as historical evidence, but no live repository claim can create that shape; duplicate retained identities fail migration preflight for operator reconciliation rather than being deleted. The claim row carries a row-version/lease token. Before quota acquisition, work-item or projection fan-out, and handler-audit persistence, the owner renews that token with an atomic row-version/state check; stale reclaim advances the same fence, so a reclaimed slow owner fails before those effects. The implementation has unit and deterministic mocked concurrency proof for claim/reclaim fencing, but does not yet provide a full database-backed slow-owner/reclaim proof or rollback compensation for external quota counters; those remain implementation and proof gaps.

The live `faction`/`faction_standing` schema and `FactionServiceImpl` currently make Automation the player-reputation writer and derive isolated standing identity from `gameInstanceId`. The target owner is Social & Groups under a stable playable-state namespace; Automation remains a consumer for NPC behavior. Owner migration, retained-row disposition, namespace-stable identity, and focused owner-read proof remain unimplemented.

The live `script_event_audit` and `script_work_items` schema uniqueness constraints omit plugin provenance, and neither current row shape nor repository identity lookup carries the required resolved `bindingId`. Distinct plugin handlers can therefore alias or collide even though the target full Trigger Identity requires `pluginId`, `pluginVersionId`, and `bindingId` where applicable. A new owner-local migration, aligned jOOQ/repository identity, and focused multi-handler retry/concurrency proof are required; this is current implementation drift, not a change to Trigger Identity authority.

The command-plan preview boundary in [ADR 0114](../../decisions/adr-0114-command-plan-preview-dry-run-isolation.md) is non-committing: a preview must not persist live evaluated script work items, populate the live automation queue, hand off commands, or perform external side effects. It may persist isolated audit/result evidence containing the exact input identity, fenced snapshot/fixture reference, and ordered plan. The current materialized dry-run path may use the internal pre-DSL trigger-record/queue shape and persists that current pre-DSL trigger record, but its live implementation records `finalStage=DSL_EVAL`, `finalOutcome=dry_run_completed`, and `finalReason=dry_run_no_handoff`; the shared terminal-success helper marks its internal `script_work_items.status=HANDED_OFF` even though no Game Session handoff or gameplay-work acceptance occurs. It has not converged on target `DRY_RUN_RESULT` terminology; that internal marker is not target live-work persistence or downstream-handoff evidence, and complete plan-result/input proof is still absent. This is an implementation handoff, not a competing contract.

Redis adoption has separate current gaps: the live `automation:test:quota:*`, `automation:test:capacity:*`, and `automation:readiness:capacity:*` builders are named in the cache catalog but are not yet all represented in the central reset/ACL ownership inventory. Readiness and dry-run capacity reservations invoke the shared two-key counter/lease script with one documented hash tag shared by each pair, so the current pairs are not inherently cross-slot; central ownership registration, canonical key encoding, durable charge/admission, reset, retention, and idempotent lease-accounting proof remain incomplete. The live `automation:queue:{tenantInstanceTag}:*` projection also appends to lists without a pointer TTL or maximum-length bound, so it is not yet proven TTL-only; its current `AutomationRedisKeys` builder accepts raw nonblank IDs and does not prove canonical opaque tuple encoding, delimiter/brace rejection, or collision safety. These are current implementation/proof gaps, not new authority. In the target state, PostgreSQL owns durable automation work, definitions, and persisted charge/admission truth, but the current implementation has no durable charge/admission markers or charge record: `ScriptQuotaServiceImpl`, `ScriptTenantBudgetServiceImpl`, and the readiness/dry-run capacity services make best-effort Redis counter/lease decisions. Current quota, tenant-budget, readiness, capacity, and queue-pointer decisions are therefore Redis best-effort and reset-sensitive; their loss may relax or tighten admission fairness or delay discovery, but cannot change the durable work and definition rows that currently exist. Before claiming the target boundary, register each family with its owner/class/reset behavior, define and enforce the queue retention policy, and either use one canonical encoded tuple builder for every key or prove canonical UUID parsing at every boundary, then add focused retention, collision/brace, same-scope slot, cluster, reset, and durable charge/admission proof.

The current dry-run and readiness capacity reservations also are not idempotent by work item: each retry generates a new lease token, increments the same counter, and overwrites the prior `(tenantId, workItemId)` lease. Releasing the earlier reservation then fails its token check and leaves one count occupied until expiry. The counters remain heuristic and reset-tolerant, but lease accounting must not leak on repeated reservation attempts; duplicate/retry and release-order proof is absent.

The current queue consumer has an additional bounded-drain limitation that must remain explicit: `drainWorkItems` and `drainIndexedWorkItemPointers` consume pointers with atomic Redis `LPOP`, so a producer's concurrent `RPUSH` is not discarded by a range/read followed by deletion. The indexed path still uses database-wide `KEYS("automation:queue:*")`, and the current lists have no pointer TTL or maximum-length bound, so the path is not a cluster-safe discovery or retention proof. Durable claim fallback can process pending PostgreSQL rows independently, but it does not establish a reset/rebuild recovery gate. Target enqueue/rebuild must atomically apply `SCRIPT_OUTBOX_QUEUE_POINTER_TTL_SECONDS` and `SCRIPT_OUTBOX_QUEUE_MAX_POINTERS_PER_KEY`, preserve or durably account for unreturned tails and concurrent appends, use an owner-maintained/cursor-based cluster-safe queue index rather than database-wide `KEYS`, and trigger bounded durable re-drive with exact identity/readback before reset-gate release. The two settings remain environment/service configuration (currently `TBD`); no target support claim is valid until each environment supplies validated positive bounds and focused concurrent-drain, truncation/expiry, cluster, and re-drive proof.

## Architecture and Design Notes

- Executes scripts in response to world or player events received via gRPC callbacks from Game Session and other domain services. Standard lifecycle events (`onSpawn`, `onEnterRegion`, `onCommand`, and similar) are delivered as unary gRPC calls via `TriggerScriptEvent`, while tick-derived scheduling signals are driven by a gRPC streaming tick heartbeat originating from Game Session.
- Scripts run inside a sandboxed engine to prevent malicious behavior.
- Scripts are authored in a component-based DSL using a visual editor so designers can build behaviors without coding.
- AI computations are optimized for large worlds by evaluating scripts on a separate schedule and batching the resulting commands before handing them to the tick system.
- Script definitions are versioned and can be hot reloaded without downtime as described in [System Architecture: Scripting & Automation](../../system-architecture-scripting.md). Detailed sandbox and loop-safety rules live in [Script Sandbox & Resource Limits](./sandbox-runtime-design.md).
- For a non-empty `NotifyScriptVersionUpdate` notification, the service reloads the specified patch into tenant-readiness state, validating compatibility and running `onLoad` before any running instance is allowed to switch to it. Tenant readiness is single-pending per tenant: if a newer publish arrives before the current pending patch reaches a terminal state, the older pending patch becomes `SUPERSEDED` and cannot later advance to `READY`.
- In the current normal Game Design integration, `affectedScripts` is empty, so the notification handler returns before creating readiness state and no readiness row or Temporal workflow is created. An empty list is valid only when an immutable patch manifest proves that zero `onLoad` handlers are expected; for an identifiable tenant/patch notification without that proof, the readiness owner must durably record `FAILED` with bounded reason `zero_handler_manifest_unverifiable` and normal status/audit evidence, and may not advance the patch to `READY` or bypass the mandatory `onLoad` gate. An unidentifiable malformed notification may fail at transport/validation without fabricating a readiness identity. The lifecycle above describes target/non-empty behavior rather than every notification.
- **Target state:** Runtime execution is instance-aware even when patch readiness is tenant-scoped: a tenant-level `READY` patch is only eligible for pinning, while admission, timer scheduling, and scoped Automation admission pause are evaluated per `<tenantId, gameInstanceId>`, and plugin activation is evaluated per `<tenantId, gameInstanceId, pluginId>`. Plugin-backed work captures the Automation-owned `pluginActivationEpoch` and owner `lifecycleRevision` and preserves and revalidates both through evaluation, persistence, handoff, staged/final effects, retry, replay, and recovery. Game Session remains the sole authority for the exact `(scriptPatchVersion, scriptPinEpoch)` execution tuple and its owner-grounded `controlPlaneRequestId` evidence; runtime surfaces carry and compare the request ID with the patch and epoch, and absent or mismatched evidence fails closed. The request ID is correlation/readback evidence, not a third pin-identity component.
- Automation is also a lifecycle owner for these instance-scoped work, schedule, and plugin-runtime families: each family must be registered with World Management's durable cleanup-owner inventory, expose idempotent cleanup and acknowledgement, and retain namespace-backed durable state according to its S1/S2/S3 classification. A missing owner registration or cleanup acknowledgement blocks termination; local queue/drain state and workflow history are diagnostic only.
- **Current cleanup behavior:** `ScriptWorkItemServiceImpl.cleanupTerminalWorkItems` selects eligible `HANDED_OFF` and `CANCELED` `script_work_items` rows under lock and, within the caller transaction, detaches nullable `script_event_audit.work_item_id` links, deletes associated `script_handoff_events` children, and then deletes the eligible parent rows. Retained audit rows remain under their independent retention policy, while handoff children are disposed with the parent. Automatic age- and row-cap cleanup of `DEAD_LETTERED` parents now fails closed and deletes nothing: the live schema does not yet retain the recovery aggregate, failure generation/claim state, expected-child ledger, or evidence-retention horizons needed to prove whole-bundle eligibility and completed `resumed_dispatch`. Focused unit proof covers this fail-closed branch; PostgreSQL integration cases exercise unfinished-child retention but require Docker/Testcontainers at execution time. Target cleanup must retain or explicitly dispose each child handoff/audit record under its owning retention, safety-evidence, replay, and lifecycle contracts, and only delete a parent when those child dispositions and required audit evidence are durably settled. The target retention rules remain owned by the scripting normative contracts and applicable lifecycle/operations documents.
- **Target plugin lifecycle state:** Automation persists the current `(pluginVersionId, pluginActivationEpoch, pluginState, lifecycleRevision)` and at most one pending transition with the captured current tuple and fixed target values. The same runtime row separately persists `breakerState` (`CLOSED` or `DISABLED_DUE_TO_ERRORS`), bounded `breakerReason`, monotonic `breakerRevision`, and monotonic `breakerSampleGeneration` for the exact active version/runtime scope; a new active version starts at sample generation `0`, and each reset advances that generation exactly once. Breaker trip transactions compare-and-set the exact active version, observed closed-state revision, and sample generation while atomically appending immutable sample/transition evidence and advancing `breakerRevision` once. Reset transactions compare-and-set the expected disabled state/revision, clear the breaker, advance both `breakerRevision` and `breakerSampleGeneration` once, and atomically append immutable reset evidence; prior-generation samples remain history-only. Breaker transitions do not mutate lifecycle state or counters. Every state-changing lifecycle transition persists/reserves `targetLifecycleRevision = current lifecycleRevision + 1`; epoch-advancing transitions additionally persist/reserve `targetPluginActivationEpoch = current pluginActivationEpoch + 1`. Same-epoch entry to `DRAINING` retains the current `pluginActivationEpoch` while advancing/reserving the next lifecycle revision. The fixed target epoch/revision are bound into the canonical request digest, initiation and completion compare-and-set, idempotent Game Session fence-install command and durable acknowledgement, exact retry, and commit; they are never recomputed after initiation and become current exactly once on commit.
- Patch reload now also persists a first durable `script_schedule_definitions` catalog for scheduler-owned handlers such as `onInterval` / `onTimerExpire`. Its current live uniqueness key is `(tenantId, scriptPatchVersion, pluginId, pluginVersionId, scheduleDefinitionId)` with cadence/unit metadata and normalized schedule hash; because core scripts use empty plugin fields, their `scheduleDefinitionId` values are currently patch-wide unique. Observed Game Session pins create durable `script_schedule_instances` rows for the matching `(tenantId, gameInstanceId)` scope, retaining the current exact owner tuple `(scriptPatchVersion, scriptPinEpoch, scriptPinControlPlaneRequestId)`, schedule identity, binding target, and mutable due-point state; schedule reconciliation and firing fail closed on absent or mismatched pin/owner evidence. The pin-owner request ID is retained as owner evidence/correlation and is distinct from any reconciliation operation request ID. `ObserveRuntimeTickProgress` updates the runtime region and due-point fields for tick-aligned schedules, including the next future due tick; wall-clock schedules currently expose `nextDueAt`, which maps to target durable `dueAt` plus projected `nextRunAt`, not to independent deadlines. Current live schedule rows retain `playableStateScope` but not the stable `playableStateNamespaceId`; target rows must retain both, and a missing namespace fails closed rather than being inferred. Target schedule rows also retain the exact pin tuple, and target scheduler identity is scoped by stable owner kind/id as defined by [Scripting Scheduler and Timer Lifecycle](../../system-architecture-scripting-scheduler-and-timers.md#stable-schedule-instance-row-identity), while live region ownership remains a transitional non-empty scope marker and core-script owner identity remains narrower than that target. Richer recovery guarantees and their proof remain implementation gaps.
- Authoritative gameplay reads use the durable handler-scoped input manifest owned by the [DSL lifecycle contract](../../system-architecture-scripting-dsl-reference-and-lifecycle.md#read-consistency-contract). The manifest records bounded trigger facts, pinned artifacts, owner versions/values, causal floor, and seed version for each resolved handler. A `readSnapshotToken` may remain as one owner-specific manifest input or correlation value where the owner contract requires it; it is not universal authority, and retries/recovery must never fetch a fresher value.
- **Target state:** For gameplay-originated events, ingress and durable runtime state persist the resolved `playableStateScope` and stable `playableStateNamespaceId` alongside `tenantId`, `gameInstanceId`, `regionId`, `regionEpoch`, and `entityId`, so shared-state and isolated-state realms remain distinct through trigger/descriptor identity, timer/schedule materialization, replay checks, dead letters, and operator reads even when they share the same tenant. `playableStateNamespaceId` is the durable playable-state uniqueness component; `playableStateScope` is separately retained and exact-validated policy/routing/authorization/migration-fence evidence. `gameInstanceId` remains the active runtime fence and S3 scope. At the Game Session-to-Automation handoff, Game Session resolves `playableStateNamespaceId` and `playableStateScope` from the scoped runtime context and the receiving owner validates the exact `{tenantId, playableStateNamespaceId, playableStateScope, gameInstanceId, regionId, regionEpoch}` atomically with the enqueue/claim transition before enqueue or execution. The namespace participates in the canonical Trigger and Command-Handoff identities; scope evidence is separate from those uniqueness keys and does not redefine them. **Current implementation gap:** The live ingress/handoff wire does not yet guarantee the namespace/scope fields or their owner proof, so missing or mismatched authority must fail closed. `regionEpoch` is an explicit Trigger Identity dimension and replay fence, not metadata that may be refreshed from the current region later. A retry is the same trigger only when it carries the same epoch. Admission, ownership transfer, handoff, and execution must not rely on a detached compare-then-apply check: the owner that durably claims or applies the work must validate the supplied epoch atomically with that transition, or the handoff must carry an authoritative fence token that the downstream execution owner validates immediately before application. A stale or mismatched event is rejected or made a fenced no-op under its original identity, recorded with a bounded `runtime_scope_changed` reason where an admitted run is canceled, and is never evaluated or reminted under the newer epoch. A producer must emit a new identity against the current epoch when the event is still valid.
- Each game’s scripts live in tables keyed by `tenantId`, ensuring automation for one game cannot access another’s data. Derived Redis coordination and index keys must preserve runtime instance isolation as well, not just tenant isolation.
- Utilizes the [Shared Libraries](../../system-architecture-shared-libraries.md) for DTO definitions, logging interceptors, and Micrometer metrics.

## Workflow Participation

The Automation & Scripting Service uses the shared workflow substrates as follows:

- Script patch consumption: when a script-only patch version is published, Game Design drives the durable publish workflow and this service participates as a consumer via `NotifyScriptVersionUpdate`, ingesting the patch for tenant readiness without coordinating its own publish-workflow steps. Running instances reload only after a later pin change to that tenant-`READY` patch.
- Bootstrap and dev-only upload path: if `UpdateScript` exists in an environment, it must be explicitly marked non-production and must not bypass patch lifecycle gates, readiness checks, or control-plane events.

Tick-driven automation and event handling never use synchronous sagas or Temporal; they follow the Redis and tick contracts described in [System Architecture: Scripting & Automation](../../system-architecture-scripting.md) and [Tick System and Runtime Design](../../system-architecture-ticks.md).

## Runtime Data Model

- `script` holds compiled component definitions and version metadata.
- `npc_memory` is a live but latent NPC-behavior state family. The baseline schema and repository key it only by `tenantId`, `npcId`, and `key`; they do not carry a stable playable-state namespace or a typed runtime-actor identity. Owner classification and any required mapping/application evidence are not established, so no S1/S2/S3 selection is made. The path is non-admissible for replacement until its owner classification, identity mapping, and focused proof exist; this is not a claim that it is S3 or disposable.
- **Target-state:** Admitted pre-DSL trigger records are persisted durably in a PostgreSQL-backed outbox in `PENDING_EVALUATION`, keyed only by the full canonical Trigger Identity plus sequencing fields as needed, including `playableStateNamespaceId` and `regionEpoch`; the exact observed `(scriptPatchVersion, scriptPinEpoch)` tuple, captured plugin `pluginActivationEpoch` and owner `lifecycleRevision` where applicable, resolved binding `priorityTag`/`quotaClass`, immutable `lane`, and bounded `cost_class` are execution evidence used for the canonical charge lifecycle. The owner-committed `controlPlaneRequestId` is persisted separately as owner-grounded projection/correlation evidence and retained through reload, convergence, handoff, and recovery; it is not part of Trigger Identity, sequencing, uniqueness, or deduplication. `playableStateScope` is persisted and exact-validated alongside the namespace as policy/routing/authorization/migration-fence evidence, but is excluded from Trigger Identity, schedule, and Command-Handoff uniqueness. Where the current repository/schema includes scope in uniqueness, that is current implementation drift and not target identity authority. Pre-DSL records retain the sealed immutable handler input manifest, including `priorityTag`, `quotaClass`, `lane`, `cost_class`, `componentCostRegistryDigest`, and `artifactRuntimeCapDigest` where applicable. Gameplay/runtime persistence, handoff, retry/replay, and recovery preserve these values unchanged; missing, changed, or contradictory lane/cost or plugin lifecycle-fence evidence fails closed rather than being inferred or refreshed.
- For scheduler-derived plugin work, the captured `pluginActivationEpoch` is also a tagged input to the durable schedule-candidate/firing-claim identity and therefore transitively to the derived event-scope `scriptEventId`; it remains excluded from handler Trigger Identity and Command-Handoff Identity, while `lifecycleRevision` remains fence-only. Ordinary producer ingress must not fabricate either scheduler-owned field.
- `automation:queue:{tenantInstanceTag}:<entityId>` keys in Redis buffer indexes or pointers for admitted handler work after its durable `PENDING_EVALUATION` pre-DSL trigger record is persisted. Each entry includes enough identity to locate the durable trigger record and must not be treated as an authoritative log of commands.
- Queue activity must be surfaced through the canonical observability contract metric families rather than through an unsupported parallel metric surface.
- **Current migration drift:** The unauthenticated `PATCH /factions/{id}/reputation` route has been removed from the service-local HTTP port and OpenAPI. The remaining `FactionServiceImpl` is not an exposed route, but it still contains an Automation-owned `faction_standing` writer keyed from `gameInstanceId`; its faction lookup is now tenant-qualified. Removal of the public route does not prove Social ownership, character binding, a null-safe unique standing identity for `{tenantId, playableStateNamespaceId, characterId, factionId}`, or concurrent first-write safety. Before any new caller reaches this service method, the owner migration must converge it on an authenticated, caller-bound Social contract rather than resume Automation standing writes. **Target state:** Social owns durable player faction standing under `{tenantId, playableStateNamespaceId, characterId, factionId}`; see the [Social & Groups runtime/data owner contract](../social-groups-service/runtime-and-data.md#data-model). Automation is read-only for standing and consumes Social's owner read contract to drive NPC morale and aggression behavior.

## Script Lifecycle

- Scripts reside in the service database and are versioned along with other game data as described in the design-service versioning process.
- **Target-state lifecycle:** Events from Game Session and other domain services trigger script admission via gRPC. Event/handler admission seals the handler input manifest and durably creates each admitted handler's `PENDING_EVALUATION` pre-DSL trigger record, then queues its rebuildable pointer; DSL evaluation is later, only after the executor claims the record and the lease/executor-acceptance transaction advances it to `EXECUTING`.
- The sandboxed engine limits CPU time and memory for each script to prevent runaway behavior.
- After evaluation, bounded command descriptors are staged into the already admitted durable handler work item and handed off for tick enqueue; the `automation:queue:{tenantInstanceTag}:<entityId>` entry remains a rebuildable pointer rather than a post-evaluation source of truth.
- A scheduled durable executor claims persisted `PENDING_EVALUATION` work items, evaluates the current command-emission format, and hands off commands to Game Session for tick enqueue. `automation:queue:*` remains a rebuildable pointer projection rather than the driver of authoritative execution state. In the current legacy materialized dry-run path, the work-item storage status is nevertheless set to `HANDED_OFF` as a terminal compatibility marker even though no Game Session handoff occurs; the authoritative audit remains `finalStage=DSL_EVAL`, `finalOutcome=dry_run_completed`, and `finalReason=dry_run_no_handoff`. This is current implementation drift, not target `TICK_HANDOFF`/`handoff_accepted` semantics; target ADR 0114 previews use an isolated preview result and do not create a live work item.
- Target execution start is one Automation-owned durable executor-acceptance transition: after acquiring a fenced capacity lease, the worker revalidates the current fence, durably accepts/claims the run for the executor, persists the exactly-once execution-start marker, and advances the work item to `EXECUTING` before DSL evaluation. If executor acceptance fails, the transition does not commit, the lease is released or reclaimed, and no execution charge is recorded; a crash after commit recovers from the durable executor claim and may reacquire a lease but never creates a second marker.
- **Target state:** The runtime applies the ADR 0088 owner contract: conservative artifact-pinned prospective serialized-byte and data-dependent bounds are enforced before constructing output, then exact bounded serialized size is checked before atomic per-handler persistence. A cap or serialization failure discards all staged output and cannot leave a partial work item or handoff. See [ADR 0088](../../decisions/adr-0088-static-and-incremental-script-output-bounds.md) for the owner contract.
- **Current behavior:** Configurable command-count, per-entity, and ingress-payload byte limits exist, and the evaluator enforces command-count and per-entity ceilings incrementally while expanding its legacy emitted-command output. Complete generated-output serialized-byte enforcement, artifact-cost validation, and atomic handler-output persistence remain absent; see the current-status boundary in [ADR 0088](../../decisions/adr-0088-static-and-incremental-script-output-bounds.md).
- Script ticks never hold game tick locks (`tick:{tenantRegionTag}:lock:<entityId>`); they only batch and stage automation work before handing it to Game Session, which applies commands under its own tick and locking model.

## Hot Reload and Failure Handling

For a non-empty `NotifyScriptVersionUpdate` notification, tenant-scoped readiness ingestion is intended for `<tenantId, scriptPatchVersion>`. Instance-scoped reload happens later only when Game Session pins an already-`READY` patch for a specific runtime scope. In the current normal Game Design integration, `affectedScripts` is empty; the handler returns before creating a readiness row and the conditional Temporal tracking hook does not run:

- `NotifyScriptVersionUpdate` is a tenant-readiness ingestion signal, not an instance activation signal. It causes the service to ingest compiled graphs and bindings for `<tenantId, scriptPatchVersion>`, then run tenant-scoped readiness checks and `onLoad` before any running instance is allowed to pin that patch.
- Tenant readiness uses the patch lifecycle `PENDING_VALIDATION -> ONLOAD_RUNNING -> READY/FAILED`, plus terminal `SUPERSEDED` when a newer publish displaces an older pending patch for the same tenant.
- **Target state:** Runtime scopes track the exact patch and pin epoch observed from Game Session for `<tenantId, gameInstanceId>` plus the owner-committed `controlPlaneRequestId` that produced that observation, alongside instance-scoped admission state such as `reloadState` and a scoped Automation admission pause. The Automation projection persists and retains that request ID through reload/convergence and relevant handoff/recovery evidence, exposing it as `lastObservedControlPlaneRequestId`; it remains projection evidence, not pin or rollout-history authority. A notification or stale/gapped projection starts a bounded owner reread; it does not advance the projection or authorize reload by arrival order, and lower, reordered, or contradictory producer tuples/cursors are rejected.
- **Target state:** When Game Session later commits a tenant-`READY` patch for a specific runtime scope, leaders set runtime-scope `pendingPatchVersion`/`pendingPinEpoch` and the committed pin-mutation `controlPlaneRequestId`, with `reloadState=RELOADING` while retaining the captured tuple and request identity of already-admitted work. New script/plugin triggers pause for that scope; ordinary Game Session gameplay ticks continue. In-flight evaluation may finish computation against its immutable captured graph, but every persistence, handoff, and final gameplay boundary enforces the captured patch and epoch plus any captured plugin activation epoch/lifecycle revision; reload/convergence and recovery evidence retain the owner request ID rather than a locally invented correlation.
- **Target state:** Instance reload does not rerun tenant `onLoad`. Leaders first reread the authoritative Game Session tuple/history when notification or projection state is stale or incomplete, then load the already validated exact artifact for the newly observed tuple, reconcile version-scoped timers and other derived scheduler state, and atomically publish the observed projection and clear `reloadState=IDLE` only after evidence is complete. The advisory notification is published after the owner commit but may be observed before or after this consumer projection; it is never the lifecycle-completion barrier.
- **Target state:** If tenant readiness fails, the patch remains `FAILED` for that tenant and never becomes eligible for pinning. If instance reload of an already-`READY` patch fails or reconciliation evidence is stale, the service marks the runtime scope `reloadState=FAILED`, discards partially loaded derived state, and fails closed: no new trigger or timer work is admitted until the authoritative pin, schedule ownership, scope, epoch, and due state are durably reconciled. Recovery uses one idempotent recovery identity to transition `FAILED -> RELOADING`; the prior observed patch remains diagnostic state only and is never an execution fallback. Game Session may explicitly repin to a prior `READY` patch, producing a new epoch and history entry.
- Triggers pinned to a failed or unknown `scriptPatchVersion` are rejected explicitly with audit visibility and bounded failure reasons rather than falling back silently.

This behavior ensures that a script patch either becomes the new active version for the targeted runtime scope or fails cleanly without affecting unrelated live automation behavior.

**Target-state recovery evidence:** Automation owns a monotonic `failureGeneration` per `(tenantId, outboxWorkItemId)` and initializes/advances it exactly once in the same atomic transition that enters `DEAD_LETTERED`; exact transition retries/no-ops do not advance it. Dead-letter rows retain the immutable failure stage and current `failureGeneration`, original Trigger Identity, exact patch/epoch, immutable `lane` and bounded `cost_class`, owner-committed `controlPlaneRequestId`, plugin provenance and captured `pluginActivationEpoch`/`lifecycleRevision` where applicable, frozen manifest, immutable evaluated output, and a complete descriptor/child-dispatch ledger keyed by the full Command-Handoff Identity. Per-item request results, recovery claims/attempts, successful-recovery evidence, and `already_recovered` readback bind `(tenantId, outboxWorkItemId, failureGeneration)`; one active claim exists per current generation and stale owners/generations fail CAS. A new request resolves the current failure generation atomically, so older-generation evidence remains immutable and cannot satisfy or block a newer current generation. Per-child recovery state records each child status, its persisted `handoffRequirement`, attempt/claim information, and durable downstream acknowledgement or outcome. The evaluated output and complete ledger are replay input; an evaluated-output or command digest is integrity evidence only and cannot substitute for the retained output or descriptor identity. `outboxWorkItemId`, the parent Trigger Identity, and `scriptEventId` remain correlation-only identifiers and are not child identity. The frozen manifest retains `priorityTag`, `quotaClass`, `lane`, `cost_class`, `componentCostRegistryDigest`, and `artifactRuntimeCapDigest` where applicable; evaluation-stage and post-evaluation recovery reuse that evidence verbatim without recomputing mutable registry, cap, scheduler-policy, or required/optional classification values. Evaluation-stage recovery may retry the original graph; post-evaluation recovery only resumes unfinished children. Missing or contradictory evidence, including missing or changed lane/cost, plugin lifecycle-fence, or handoff-requirement values at handoff, replay, or recovery, remains dead-lettered and fails closed. Schedule reconciliation defaults to cancel-and-recreate, with continuity only when the authored stable identity and compatibility declaration explicitly match.

Ordinary owner-local dead-letter recovery/retry remains non-conflicting routine replay when it only replays the owner’s existing durable PostgreSQL work-item truth. Target `automation:queue:*` queue-pointer rebuild is non-conflicting routine reprojection only through the owner-reconciled `PENDING_EVALUATION` status/owner/CAS gate; current reset/rebuild/resume remains unavailable and must fail closed because the implementation cannot distinguish safe from stale claims. Automation records the owner classification and the evidence for that exemption, including the exact durable identity, source snapshot/cursor, request or output digest, and affected scope; this does not grant maintenance authority. Any maintenance or reset mutation, including one reached from dead-letter recovery or pointer rebuild, must instead carry the unchanged ADR-0085 external maintenance handoff with its exact `operationId`, external maintenance fence/lock binding, classifier, immutable evidence digest, and complete affected scope, or fail closed.

## Redis Roles and Prefixes

- **Coordination Redis participation**
  - Target scheduler participation uses the registered Automation-owned coordination families `script-scheduler:{tenantRegionTag}:lastTickId`, `automation:timer:{tenantRegionTag}`, and (once implemented) `tick-events-offset:{tenantRegionTag}:<consumerId>` / `tick-events-lease:{tenantRegionTag}`. These are timeline/progress projections tied to Game Session's tick contracts; their target projections and reset/rebuild proof remain unimplemented. Game Session remains the owner of `tick:{tenantRegionTag}:*`, gameplay `timer:*`, `retry:*`, and executor-lease prefixes, and Automation reaches them only through the documented handoff/API contracts.
  - `automation:queue:{tenantInstanceTag}:*`, quota and tenant-budget counters, and dry-run/readiness capacity families are Cache/Rate-Limit Redis data, not Coordination Redis participation. Their eviction, expiry, or reset affects only best-effort queue acceleration and fairness/capacity admission; PostgreSQL work/readiness state remains authoritative. Their owner-local prefix and reset contracts are listed below and in the shared Redis catalogs.
- **Cache/Rate-Limit Redis usage**
  - Stores script quota counters and similar best-effort aggregates in Cache/Rate-Limit Redis using prefixes such as `automation:quota:<tenantId>:<scriptId>`, `automation:tenant-budget:<tenantId>:tier:<tier>`, the dry-run/test quota families `automation:test:quota:<tenantId>:script:<scriptId>:tenant` and `automation:test:quota:<tenantId>:script:<scriptId>:principal:<principalKey>`, the dry-run capacity families `automation:test:capacity:{<tenant-id>}:tenant`, `automation:test:capacity:{<tenant-id>}:lease:<workItemId>`, `automation:test:capacity:{automation-test-capacity}:cluster`, and `automation:test:capacity:{automation-test-capacity}:cluster:lease:<tenant-id>:<workItemId>`, the readiness capacity families `automation:readiness:capacity:{<tenant-id>}:tenant`, `automation:readiness:capacity:{<tenant-id>}:lease:<workItemId>`, `automation:readiness:capacity:{automation-readiness-capacity}:cluster`, and `automation:readiness:capacity:{automation-readiness-capacity}:cluster:lease:<tenant-id>:<workItemId>`, and `automation:queue:{tenantInstanceTag}:*`.
  - Treats these keys as transient operational data; PostgreSQL remains authoritative for script definitions and long-lived automation state.
  - Quota and queue-oriented prefixes are best-effort TTL-only caches unless explicitly documented as strongly validated caches with versioned payloads and stricter invalidation semantics.

### Capacity-key rollout compatibility

The tenant and cluster capacity counter/lease pairs use Redis hash tags so each pair can be updated atomically in one cluster slot. This physical key-shape change is incompatible with legacy untagged-key binaries: old and new binaries would maintain separate best-effort counters and could temporarily admit more work than either configured limit. The current key builders and capacity services have no dual-read or dual-write migration path, so releases changing these key shapes are coordinated/recreate (or roll-forward-only) changes rather than rolling-compatible changes. The V3 plugin lifecycle-fence migration has the same boundary: it is a coordinated/recreate, roll-forward-only migration, and a pre-V3 binary must not be rolled back after V3 has migrated the database. The Kubernetes base manifest and hosted Helm values set the Automation deployment strategy to `Recreate`; any other deployment must apply the same stop-before-start boundary. Capacity keys are reset-tolerant and disposable, so a stopped legacy deployment's residual keys do not authorize new work; the new binary starts from its tagged key family after the deployment boundary.

Quota and queue-related caches are best-effort TTL-only caches unless this service doc set states otherwise. `automation:queue:*` must never be the sole source of truth for whether work has been enqueued or processed; exactly-once or at-least-once semantics are provided by durable trigger tables and idempotent domain logic, not Redis queue contents.

## Durable Script Work-Item Outbox

To avoid “DSL evaluated successfully but effects were silently dropped”, the service must durably persist and queue each admitted handler's `PENDING_EVALUATION` pre-DSL trigger record before DSL evaluation or execution acceptance:

- **Target state:** Admitted triggers seal the handler input manifest and produce `PENDING_EVALUATION` pre-DSL trigger records written to a PostgreSQL-backed outbox table keyed by the canonical Trigger Identity plus sequencing fields as needed. `playableStateNamespaceId` is the playable-state uniqueness dimension; `playableStateScope` is separately persisted and exact-validated policy/routing/authorization/migration-fence evidence and is excluded from Trigger Identity, schedule, and Command-Handoff uniqueness. Where the current repository/schema includes scope in uniqueness, that is current implementation drift and not target identity authority.
- Target materialized `script_schedule_instances`, resume windows, due candidates, firing claims/audits, timer-generated pre-DSL trigger records, evaluated script work items, handoff events, and dead-letter rows preserve the same stable `playableStateNamespaceId` and gameplay `playableStateScope` evidence so scheduler-driven follow-up work stays in the same shared-versus-isolated state namespace as the original admitted event. The namespace participates in canonical schedule, Trigger, and Command-Handoff identities; `playableStateScope` evidence remains separate from those identities. Missing or mismatched evidence fails closed rather than being inferred or refreshed. Current schedule rows still lack `playableStateNamespaceId`, as recorded in the implementation-status boundary above.
- `automation:queue:*` keys are derived coordination indexes that accelerate draining and batching, not the authoritative record of pending work.
- On restart, failover, or Cache/Rate-Limit Redis resets, the target service rebuilds `automation:queue:*` indexes from durable eligible work under the [Redis Operations owner/CAS gate](../../system-architecture-redis-operations.md#cacherate-limit-redis-reset). The current `rebuildPendingWorkItemIndex` selects only `PENDING_EVALUATION` rows, but has no owner or compare-and-set gate; its Redis-existence check and append are separate operations. Queue reset/rebuild and resume are therefore unavailable and must fail closed, and a status preflight cannot establish a safe disposition for `EVALUATING` rows. The helper also uses `PageRequest.of(0, maxItems)` for each rebuild batch, so later eligible rows with missing pointers can be starved when earlier rows already have pointers; this bounded page-0 scan is not completeness or readback proof. The durable claim fallback can process pending PostgreSQL rows independently. Target reset/rebuild requires a cursor- or owner-maintained index with complete eligible-row coverage and the atomic status/owner/CAS gate before the external maintenance gate is released. This gap is recorded in the [scripting runtime rebuild contract](../../system-architecture-scripting-runtime-execution.md#rebuild-and-deduplication-rules).

This enables stage-aware outcomes in `script_event_audit`: the system can distinguish “DSL evaluation succeeded” from “handoff or enqueue succeeded”, and can re-drive delivery where appropriate without re-executing the DSL body for the same trigger.

## Redis Cluster Slotting Rules

- Every Automation-owned multi-key operation must use keys carrying one canonical scope hash tag and therefore resolve to one Redis Cluster slot. Key families without a canonical shared tag are unsupported for atomic multi-key operations. Queue discovery must also avoid database-wide `KEYS`; it must use an owner-maintained index or bounded cursor/read path whose completeness and per-scope coverage are proven across cluster nodes.
- The target `tenantInstanceTag` is an opaque, collision-safe encoding of the complete `(tenantId, gameInstanceId)` tuple. The live builder concatenates raw nonblank strings, so it must not be described as canonical until it either uses the shared encoded/length-prefixed tuple helper or proves canonical lowercase UUID parsing and rejection of separators/braces at every boundary. Focused tests must cover delimiter/brace inputs, collision vectors, and same-scope slot equality.
- The current `automation:test:quota:*`, `automation:test:capacity:*`, and `automation:readiness:capacity:*` capacity families are unsupported until their central ownership/reset/ACL registration is complete and their keys use one canonical scope hash tag/Redis Cluster slot, or the cross-key reservation is replaced with a single-key design.
- Automation Redis usage must never perform multi-key operations that span both `automation:*` and `tick:*` keys in a single invocation.
- Allowed examples:
  - A Redis operation that touches only `automation:queue:{tenantInstanceTag}:*` keys for one runtime scope.
  - A Redis operation that touches only Automation-owned quota or dry-run-capacity keys for one documented scope.
- Disallowed examples:
  - Any script or transaction that reads or writes both `automation:*` and `tick:{tenantRegionTag}:*` keys in one atomic Redis call.
  - Any Automation-owned key family that attempts to mirror or stage authoritative gameplay queue state outside Game Session.
- Automation work is projected under `automation:queue:*` and then handed off to Game Session via gRPC; only Game Session scripts mutate `tick:*` prefixes.

Any change to automation Redis usage or Lua scripts must follow the [Redis Design Checklist](../../system-architecture-redis-design-checklist.md) and the slotting rules above.

## PvE, Faction, and Reputation Behavior

Random encounters and environmental hazards are generated by `PveEncounterService`. Encounters are seeded so results can be reproduced during testing. The service includes an `NpcMoraleService` which adjusts an NPC’s `AggressionState` based on current health, morale, and reputation. When those values fall below configurable thresholds the NPC may become `FLEEING` or `SURRENDERED`, allowing encounters to end without a kill.
