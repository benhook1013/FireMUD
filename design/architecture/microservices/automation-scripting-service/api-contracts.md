# Automation & Scripting Service API Contracts

This document defines the Automation & Scripting Service REST and gRPC surfaces, event-ingress contract, patch and plugin control-plane visibility APIs, and publish-gating digest contract.

## Normative Target Contract

The API sections below define the target Automation & Scripting contract. The target runtime separates pre-DSL trigger state from evaluated descriptor/outbox evidence; an atomic evaluation commit reaches trigger state `EVALUATED_COMMITTED`, retains the committed evaluation outcome, and permits descriptor replay without DSL re-entry. That trigger state is excluded from active evaluation counts; descriptor children continue to determine pending or handoff activity. A row advertised as recoverable and all of its stage, manifest, evaluated-output, and child-dispatch evidence form one coherent retention bundle. Age/capacity cleanup and explicit purge share the same evaluated-evidence whole-bundle eligibility: under an `EVALUATED_COMMITTED` parent, descriptor/outbox/evaluated-output evidence may be removed only after every child is terminal (`HANDED_OFF`, `CANCELED`, or `DEAD_LETTERED`) and every eligible evidence item is retention-eligible, with eligible evidence purged atomically; if any sibling is `PENDING`, `INDEXED`, `HANDOFF_IN_FLIGHT`, otherwise nonterminal, or not retention-eligible, the bundle remains unchanged (and an explicit purge is rejected) and no `descriptorEvidencePurgedAt` marker is written. Supporting evidence must not be removed independently while leaving the row recoverable; incoherent evidence fails closed. A successful purge preserves the trigger marker, corresponding `script_event_audit`, and replay-causation evidence under their owning retention contracts, and the same transaction persists an explicit durable `descriptorEvidencePurgedAt` marker on the retained parent. A marked parent is non-recoverable and non-replayable, and consumers reject it deterministically rather than treating missing children as recoverable. It rejects active/nonterminal trigger or descriptor work.

For handler execution, the target API boundary seals one durable input manifest per resolved handler. An instance-scoped gameplay/runtime handler's manifest includes complete applicable owner/runtime scope, tenant/script identity, the exact `(scriptPatchVersion, scriptPinEpoch)` tuple, exact plugin provenance `(pluginId, pluginVersionId, bindingId)` when applicable, and, for plugin-backed work, captured `(pluginActivationEpoch, lifecycleRevision)` as separate Automation runtime-fence evidence rather than Trigger Identity. Neither lifecycle value is a separate handler Trigger Identity or Command-Handoff Identity field; for plugin-owned schedules, `pluginActivationEpoch` remains the tagged input to scheduler candidate, firing-claim, candidate-audit, and derived event-scope `scriptEventId` identity, while `lifecycleRevision` remains fence-only. The durable handler execution child identity is `{parentEventId, scriptId}` for core work and `{parentEventId, pluginId, pluginVersionId, bindingId, pluginActivationEpoch}` for plugin work, as defined by ADR 0172; handler Trigger Identity dedupe omits the epoch, while child work, audit lineage, retry, and recovery reuse the captured execution identity. Scheduler epoch changes derive a fresh parent event ID transitively, whereas ordinary producer retries reuse the frozen parent and fail closed on an epoch mismatch, so the two identity layers cannot alias across activation ABA. The manifest also includes bounded trigger facts, owner-versioned inputs, pinned artifact references/digests, causal floor, and seed version. Tenant-readiness `onLoad` is the explicit pre-instance-pin exception: its manifest carries tenant/script identity and candidate `scriptPatchVersion` but omits `gameInstanceId`, runtime scope, and `scriptPinEpoch`; it cannot emit gameplay work or effects. Retries and recovery reuse the manifest's deterministic inputs and artifact references rather than fetching newer semantic inputs; captured authority and policy fields remain provenance, while the captured plugin activation fence and current patch/epoch, runtime, plugin, component, signer, and policy fences are revalidated at every applicable evaluation, dispatch, and final side-effect boundary. A `readSnapshotToken` may appear only as an owner-specific recorded input/correlation. The live request may still carry the narrower token field for current producers, but that field is not proof of the target manifest contract.

For `ListScriptHandoffEvents`, the target command identity is the complete Command-Handoff Identity defined in the [normative contract tables](../../system-architecture-scripting-normative-contract-tables.md#command-handoff-identity-target-state), ending in `(automationDispatchId, commandOrdinal)` within the complete scope. `automationDispatchId` is not assumed globally unique, and the parent Trigger Identity is correlation data rather than a command-child uniqueness key. The target evaluated-descriptor response includes the complete command/trigger context. Those identity and descriptor semantics are target-only end-to-end. The current API remains a handoff-history read over `outboxWorkItemId`/`workItemId`, `gameSessionCommandId`, and the dispatch, scope, remote, provenance, routing, and source fields currently supported by the proto/client.

## Implementation Status

This section records the current implementation boundary only. The API sections below remain normative target contracts; a current implementation note does not relax those contracts, and a target-only surface must not be inferred as shipped.

The live NPC formation REST family is an unauthenticated public surface: the source OpenAPI declares `security: []`, and `NpcFormationController` has no `SessionContext` or tenant authorization guard. `POST /formations` trusts the request `tenantId`, while member add/list trust query `tenantId`; the service checks only that a looked-up formation's stored tenant equals the supplied selector and does not verify the leader/member NPC belongs to that tenant. These routes are not a safe proof of tenant isolation: there is no focused unauthenticated denial, caller-tenant binding, or cross-tenant NPC ownership proof.

Target formation REST behavior removes this public reachability and retains the family only as an exact internal/admin tenant operation. An authenticated admin caller must be bound to the requested tenant (or an explicitly authorized global operator branch); request tenant selectors are not authority. Automation must verify formation ownership before every read or mutation, including member listing, and must verify through Entity Management's NPC owner contract that the leader and every referenced member belong to the same tenant and applicable gameplay namespace before create, membership mutation, or returning the formation. Missing auth/context, tenant mismatch, formation mismatch, and cross-tenant NPC references fail closed; focused negative proof must cover unauthenticated calls, tenant A selecting tenant B, and tenant A adding/listing tenant B NPCs.

- `UpdateScript` is limited to bootstrap/dev tooling and is not the production runtime publish path; production rollout uses `PublishScriptPatchVersion` and `NotifyScriptVersionUpdate`.
- `GetScriptStatus` is backed by the shared durable `script_work_items` pre-DSL states: runtime workers claim `PENDING_EVALUATION` rows by transitioning them to `EVALUATING` before DSL execution. These are the current work-item statuses and are not evaluated-command queue entries. The target trigger state `EVALUATED_COMMITTED` and separate evaluated-descriptor flow using `PENDING` and `INDEXED` are not currently persisted as that separate status layer, while a separate pre-DSL projection may route evaluator work.
- `GetScriptBreakerStatus` and `ListScriptBreakerEvents` are target-state reads for the exact `(tenantId, gameInstanceId, scriptPatchVersion, scriptPinEpoch, scriptId)` core-script breaker identity, and `ResetScriptBreaker` is its target operator mutation. The current proto/implementation has no authoritative breaker status/history surface, monotonic breaker revision, reset mutation, stored request result, or reset evidence. They are distinct from `GetScriptPatchStatus` tenant readiness and `GetScriptStatus` pre-DSL work states; do not introduce or infer a `scriptVersionId`.
- Target pre-DSL recovery permits rebuilding `PENDING_EVALUATION` and only a non-stale `EVALUATING` row whose owner has reconciled/reclaimed it and proved re-projection safe; stale or unresolved `EVALUATING` rows remain excluded. The current `rebuildPendingWorkItemIndex` instead unconditionally selects both statuses and republishes missing pointers, with no stale, owner, or compare-and-set reconciliation gate. Because it cannot distinguish safe from stale `EVALUATING`, current queue reset/resume is unavailable and must fail closed; a non-atomic status preflight cannot authorize a PENDING-only rebuild. It does not implement target `PENDING`/`INDEXED` evaluated-descriptor rebuild because the separate descriptor status layer is not currently persisted; these pointers are not evaluated-command queue entries or descriptor replay evidence.
- For a non-empty `NotifyScriptVersionUpdate` notification, the current path validates and stages patches through `PENDING_VALIDATION -> ONLOAD_RUNNING -> READY/FAILED/SUPERSEDED`; running instances reload only after a later pin change to that tenant-`READY` patch.
- In the current normal Game Design integration, `affectedScripts` is empty. Automation returns before creating readiness state, and the conditional Temporal start is skipped, so publication does not establish a readiness row or workflow; this is a current implementation gap, not readiness proof. An empty list is valid only when an immutable patch manifest proves that zero `onLoad` handlers are expected. For an identifiable tenant/patch notification without that proof, the canonical target outcome is a durable `FAILED` readiness record with bounded reason `zero_handler_manifest_unverifiable`, normal status/audit evidence, no synthetic handler work, and no DSL retry; it may not advance the patch to `READY`. An unidentifiable malformed notification may fail at transport/validation without fabricating a patch identity. The lifecycle above is therefore target/non-empty behavior, not an outcome guaranteed after every notification.
- The current `ListScriptHandoffEvents` proto/client reads handoff rows using `workItemId`/persisted `outboxWorkItemId`, `gameSessionCommandId`, `automationDispatchId`, and the currently supported scope, remote, provenance, routing, target, and source fields. The target complete Command-Handoff Identity and complete evaluated-descriptor semantics remain target-only end-to-end; locally stored ordinal/text/target values do not establish that target contract. The current proto/client exposes no `bindingId` request filter, and target response metadata remains target-state follow-through rather than a claimed live field.
- `GetAutomationPinConvergence` is currently served from a durable Automation-owned `script_patch_pin_projections` view keyed by `(tenantId, gameInstanceId)` and returns freshness flags (`projectionAsOfMs`, `projectionLagMs`, `isProjectionStale`) so temporary Game Session read failures do not collapse operator visibility into raw pass-through coupling.
- Signer/component-policy enforcement is live on the Automation runtime side. The current control-plane surface exposes `GetPluginStatus`, `ListPluginRuntimeEvents`, and `GetPluginPolicyConvergence`, and scheduled reconciliation disables enabled plugins when current publication metadata becomes fail-closed. The separate propagation-event families `SignerPolicyVersionObserved` and `SignerRevocationApplied` remain target-state follow-through rather than a shipped API family.
- Script-patch digesting already attests the patch-scoped script graph for `scriptPatchVersion`. The current full-version digest attests the tenant's draft script graph using the existing schema and returns synthetic `appliedCommitId = "version:<versionId>"` until script definitions are modeled as fully version-scoped draft data.
- The current executor supports bounded multiple emitted commands with local ordinals and per-command handoff attempts; the complete Command-Handoff Identity and end-to-end per-command progress remain target-only. See [Scripting & Automation: Cross-Service Contracts](../../system-architecture-scripting-contracts.md#implementation-status) for the owner contract and current wire consequence. `command_count_exceeded` applies only to an actual configured output-count limit.
- The current ingress/remote payload may carry `readSnapshotToken`, but Automation does not yet persist the complete handler-scoped input manifest with owner versions, artifacts, causal floor, and seed version; manifest sealing and descriptor replay remain target-state gaps.
- Durable parent-event identity, canonical request-digest conflict handling, an atomically frozen ordered handler manifest, binding-scoped plugin execution identity, and activation-epoch fencing under ADR 0172 are not implemented. Current retries can still re-resolve mutable handler state.
- Registry-classified `REJECT_VISIBLE`, `DURABLE_RETRY`, and `SKIP_RECONCILE` reload handling, transient attempt state, producer-specific expiry/backoff, and policy-specific proof under ADR 0173 are not implemented. Current denial memoization and producer behavior do not establish that target.

## Script-transition API consequences

The service-local control-plane and event-ingress surfaces apply the canonical script-transition authority as follows:

- `GetAutomationPinConvergence` is an observed, freshness-bounded projection of Game Session's exact `{scriptPatchVersion, scriptPinEpoch}` for an instance. A bounded-fresh projection may satisfy admission and diagnostics during a temporary Game Session read outage; it cannot commit a pin, mint rollout history, or authorize work when the projection is absent or stale and a bounded owner refresh is unavailable. A bounded refresh is required only for absent or stale projection state, and an operator override is not permitted.
- Every instance-scoped admission, scheduler firing, retry/replay, durable work item, plugin trigger, and Game Session handoff carries the exact patch and pin epoch under which it was admitted. Tenant-readiness `onLoad` remains pre-instance-pin work: it omits `gameInstanceId` and `scriptPinEpoch`, and cannot emit gameplay work or effects. Automation rejects a mismatch at each local durable boundary and reports a bounded pin-state outcome rather than substituting a different ready artifact. Ordinary non-script gameplay is outside this admission failure boundary.
- Rollback participation is a scoped Automation admission pause, exact-artifact preload/reconciliation, and asynchronous cancellation/purge. Game Session owns the authority transition, epoch, deadline, and rollout history; this service does not pause ordinary gameplay ticks or emit a competing timeout or history record.
- Dead-letter recovery accepts bounded explicit work-item identifiers and returns a per-row deterministic result. Evaluation-stage rows may re-enter the DSL only with the original work-item/scriptEventId, immutable graph, frozen payload/manifest, and exact fence; they preserve the original logical trigger/work-item identity and allocate no `automationDispatchId` or command-child identity before a winning descriptor/outbox commit. If commands emit, that winning commit allocates and persists one `automationDispatchId` and deterministic child ordinals; a valid zero-command evaluation creates no dispatch identity. Rows with committed evaluated output resume the stored child ledger without re-entering the DSL or generic admission, reusing its existing command identities and creating no replacement dispatch identity. Incomplete stage/fence evidence leaves the row dead-lettered. The current aggregate requeue behavior remains an implementation/proof gap.
- Interval schedules use cancel-and-recreate unless both sides explicitly declare continuity for the same stable logical key, `source.isDryRun == target.isDryRun`, and the cadence, target, playable scope, owner/binding, and exact-fence compatibility predicates all pass unambiguously. `pluginId` is the stable plugin owner while `pluginVersionId` and `scriptPatchVersion` remain provenance and execution-fence metadata. One-shot timers always remain on their own cancel-and-recreate/terminal-outcome path and are not transferred by this interval rule.

The shared DSL and sandbox serve embedded scripts and linked plugins, but this service receives immutable exact-version artifacts and runtime plugin state; Game Design remains responsible for authored revision/plugin publication and does not become a runtime pin or activation authority.

The canonical decision links for these local consequences are [ADR 0103](../../decisions/adr-0103-single-authority-script-pins-with-exact-version-execution.md), [ADR 0106](../../decisions/adr-0106-epoch-fenced-script-rollback-without-routine-gameplay-pause.md), [ADR 0107](../../decisions/adr-0107-stage-aware-script-dead-letter-recovery.md), [ADR 0108](../../decisions/adr-0108-no-degraded-script-admission-without-authoritative-pin.md), [ADR 0109](../../decisions/adr-0109-game-session-owned-script-rollout-history.md), [ADR 0110](../../decisions/adr-0110-explicit-opt-in-schedule-continuity-across-script-transitions.md), and [ADR 0111](../../decisions/adr-0111-unified-dsl-with-distinct-embedded-script-and-plugin-lifecycles.md).

### Work-Item Identifier Naming

On the current public Automation & Scripting API, `workItemId` and `workItemIds` are aliases for the canonical persisted `outboxWorkItemId` parent identifiers. The aliases carry the same identifier values and do not define a second work-item identity. `automationWorkItemId` remains the current Game Session wire name for that same parent identifier at the handoff boundary. **Target-state mutation contract:** Replay and purge mutations are bounded to explicit work-item IDs; descriptor references carrying the complete Command-Handoff Identity remain deferred until a separate accepted contract. **Current replay gap:** `ReplayDeadLetteredWorkItems` still exposes optional scope fields, permits an empty ID list, falls back to tenant-wide dead-letter selection, and applies filters both with and without explicit IDs, as detailed in the endpoint entry below.

## Event Ingress Contract

Domain services such as Game Session and Game Logic deliver automation events through event-ingress RPCs (for example `TriggerScriptEvent`). The required identity fields, endpoint ownership, and audit behavior are defined in the [normative scripting contract tables](../../system-architecture-scripting-normative-contract-tables.md#table-1-trigger-identity-required-fields); the following list describes the service-local wire envelope:

- `tenantId`, `gameInstanceId`, `regionId`, and `entityId` for the target runtime context.
- resolved `playableStateScope` for gameplay-originated events so shared versus isolated realm state stays explicit through durable trigger identity, timer follow-up work, and operator read models.
- `regionEpoch` for gameplay/runtime triggers and scheduler triggers so Trigger Identity is fenced across scoped coordination resets.
- `scriptEventId` in the normalized applicable Trigger Identity. Its wire requirement follows the [ingress ownership matrix](../../system-architecture-scripting-normative-contract-tables.md#table-1a-event-ingress-scripteventid-ownership-matrix), and it is not a complete idempotency key by itself.
- `isDryRun` so live and dry-run/test traffic are always in separate idempotency namespaces.
- `eventType` and versioning metadata such as `scriptPatchVersion`.
- `scriptPinEpoch` for instance-scoped gameplay/runtime triggers, paired with `scriptPatchVersion`; tenant-readiness `onLoad` is the pre-instance-pin exception and carries only its tenant/script identity plus candidate `scriptPatchVersion`, omitting `gameInstanceId`, runtime scope fields, and `scriptPinEpoch`.
- `eventSchemaVersion` for custom or service-specific events governed by the event registry.
- For custom or service-specific events, `sourceService` is derived from the authenticated producer/workload identity and event-registry authorization, not supplied as an untrusted payload field. The same derived value participates in event-scope dedupe and is persisted unchanged in ingress and handler audit records.
- An owner-specific read selector (which may be a `readSnapshotToken`) when the canonical event-registry entry requires one. Automation seals the durable handler-scoped input manifest after handler resolution; callers must not treat one universal token as the authority for every downstream read. The selector is absent for events whose registry entry explicitly marks snapshot authority as `NONE`.
- An envelope for the event payload, including any domain-specific fields.

Event ingress uses two-stage deduplication. Before handler resolution, incoming request dedupe uses event-scope identity; `scriptId` and `bindingId` are unavailable at ingress and must not be invented. The first accepted event-scope claim binds that parent identity to one canonical request digest and freezes the complete ordered handler manifest plus applicable activation fences. A retry reuses that manifest rather than resolving the current binding set, and changed-input reuse of the parent identity is an idempotency conflict. After binding resolution, each resolved handler dedupes by the full applicable Trigger Identity and produces its own handler-scoped outcome. Core scripts coalesce by `scriptId` and execute once per parent event, while plugin handlers remain distinct by stable `bindingId` under that parent; captured `pluginActivationEpoch` is activation-fence and handler execution-identity evidence, not a Handler Trigger Identity field, so retries and activation-fenced recovery reuse the same parent-and-binding outcome. The identity, ownership, and audit uniqueness rules are defined in [ADR 0172](../../decisions/adr-0172-parent-event-and-frozen-handler-execution-identity.md), the [normative scripting contracts](../../system-architecture-scripting-normative-contract-tables.md#table-1-trigger-identity-required-fields), and the [cross-service deduplication contract](../../system-architecture-scripting-contracts.md#4-scripteventid-identity-and-at-most-once-dedupe).

Admission must also enforce pin consistency for `<tenantId, gameInstanceId>`:

For instance-scoped gameplay/runtime ingress, Automation admits against a bounded-fresh observation of the exact Game Session `(scriptPatchVersion, scriptPinEpoch)` tuple. A bounded-fresh local projection may satisfy admission during a temporary Game Session read outage; only absent or stale projection state requires a bounded owner refresh, whose failure yields `pin_state_unavailable`. That observation supplies both fields; Automation persists them with the normalized Trigger Identity and event-scope claim in one local durable transaction before evaluation. This preserves ADR 0108's bounded-fresh projection model and does not introduce a globally atomic refresh-and-admit RPC. Same-version work from a different epoch is a distinct claim and an older epoch cannot be treated as current.

For ordinary Game Session-originated events, Game Session finalizes an authoritative semantic `UNPINNED` result before Automation ingress and therefore creates no Automation ingress RPC, event, or work; missing or unreadable authority remains non-admitted/retryable as `pin_state_unavailable` rather than `UNPINNED`.

For remote follow-up ingress, Automation owns only target-side admission and durable target work after Game Session has resolved the target outcome. It must preserve the supplied target fence on admitted work and must not create an event or work item for Game Session's final semantic `UNPINNED` result. The complete distinct-instance source/target tuple, retry, displacement, and same-instance rules are canonical in the [cross-service version-fencing contract](../../system-architecture-scripting-contracts.md#3-version-fencing-rollback-safety). The current `ScheduleRemoteFollowup` wire/storage path does not yet provide that contract; see the current gap in the [Game Session ScheduleRemoteFollowup contract](../game-session-service/api-contracts.md).

These are event-scope ingress decisions: return the same `admissionOutcome` and `admissionReason` values in the ingress response and `script_event_ingress_audit`; they are not handler-scoped `finalOutcome` or `finalReason` values.

- `READY` is required for readiness completion and a new instance pin or pin progression. Tenant-readiness `SUPERSEDED` applies only to an unpinned `PENDING_VALIDATION` or `ONLOAD_RUNNING` candidate. An already-pinned `READY` patch retains `READY` and remains admissible only under its exact Game Session tuple until explicit repin or rollback. Unknown or non-`READY` patches are rejected with `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE` and bounded `admissionReason=version_unavailable`.
- If local pin state is stale beyond max age and cannot be refreshed, reject with `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_PIN_STATE_UNAVAILABLE` and bounded `admissionReason=pin_state_unavailable`.
- If the request's exact `(scriptPatchVersion, scriptPinEpoch)` differs from the bounded-fresh observed Game Session tuple for the instance, reject with `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE` and bounded `admissionReason=pin_state_mismatch_requested_vs_observed` rather than silently substituting a version or epoch.
- Custom and service-specific events must additionally be validated against a canonical event registry so only authorized producer services can emit a given `eventType` and schema version.

Canonical event-registry contract for ingress:

- Each registry entry is keyed by `eventType` plus `eventSchemaVersion`.
- Producer services own the versioned event semantics and schema manifests. Automation mechanically validates and deterministically materializes those manifests into the one complete catalogue used by ingress and read APIs; manually copied producer definitions are not a second authority. The canonical producer-activation fence is owned by the [event-registry contract](../../system-architecture-scripting-event-registry.md#publication-and-update-flow).
- Each accepted catalogue exposes an immutable revision identity and canonical digest over its validated manifest inputs and ordered entries. Ingress authorizes a key/version only from that accepted revision/digest; failed or partial materialization retains the prior complete accepted catalogue and cannot authorize a new key/version.
- The registry entry must define the owning producer service, allowed producer principal classes, payload schema/version, payload schema reference, replay semantics, quota class, snapshot authority, consistency class, and whether `GLOBAL` bindings are legal.
- For authoritative gameplay-affecting events, the registry entry must state the owner-versioned inputs, causal floor, and consistency class required in the handler manifest. An owner-specific `readSnapshotToken`, when used, is one bounded manifest input and its scope must be defined by that owner.
- For non-authoritative or synthetic events, the registry entry must explicitly mark gameplay input authority absent so callers cannot imply stronger consistency than the event contract provides.
- Registry rejection is an event-scope ingress failure and must use `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_EVENT_REGISTRY_REJECTED` with a bounded `admissionReason` such as `unknown_event_type`, `schema_version_unsupported`, `producer_not_authorized`, `owner_input_required`, or `owner_input_forbidden`.
- Breaking contract or policy changes require a new `eventSchemaVersion`. Deprecated schema versions stop new authoring before removal, and definitions referenced by supported patches remain readable and enforceable until the authoritative patch-support lifecycle releases them.

### Production script-patch publication and rollout

`PublishScriptPatchVersion` is owned by the Game Design Service. Its canonical design-time publication contract is defined in the [Game Design Service API contracts](../game-design-service/api-contracts.md#grpc-apis) and the [Game Design gRPC proto](../../../../protos/game-design/v1/game_design_service.proto): it publishes an immutable script-only patch referencing a base version. The [Scripting Control Plane API](../../system-architecture-scripting-control-plane-api.md#game-design-design-time-publication-visibility) is canonical for the boundary between that `PUBLISHED` design status and Automation & Scripting runtime readiness.

Production rollout therefore uses `PublishScriptPatchVersion` followed by Automation & Scripting's `NotifyScriptVersionUpdate`, which validates and stages the published patch for tenant readiness. Game Session remains the owner of the instance `scriptPatchVersion` pin; a notification does not repin a running instance by itself. `UpdateScript` remains limited to bootstrap/dev tooling and must not be used as either the production publication or rollout path.

Direct script upload and update APIs such as `UpdateScript` are limited to bootstrap/dev tooling and must not be used as a production runtime publish path.

## Idempotency and Retry Rules

The canonical Trigger Identity, endpoint-specific `scriptEventId` ownership, deduplication, and downstream command retry rules are defined in the [normative contract tables](../../system-architecture-scripting-normative-contract-tables.md#table-1a-event-ingress-scripteventid-ownership-matrix) and [cross-service scripting contracts](../../system-architecture-scripting-contracts.md#4-scripteventid-identity-and-at-most-once-dedupe).

At this API boundary:

- Unary event-ingress calls may be retried at the gRPC transport layer only when the caller follows that canonical identity and retry contract.
- Timer and scheduler internals may retry idempotent infrastructure operations such as Redis writes, but do not re-execute the DSL body for the same trigger.
- Handler-level outcomes remain represented by the service's durable `script_event_audit` rows and handoff/status APIs rather than by treating transport acknowledgement as execution success.

## Dry-Run and Test Execution Contract

The shared dry-run safety, namespace, authorization, budget, and capacity rules are defined in the [cross-service scripting contracts](../../system-architecture-scripting-contracts.md#6-dry-run--test-traffic-safety). The ADR 0114 command-plan preview is a separate target endpoint for Game Design and Logging & Admin tools; the currently exposed `TriggerScriptEvent(isDryRun=true)` path is legacy/incomplete and must not be described as that preview surface:

- The existing `TriggerScriptEvent` proto/runtime path is not the [ADR 0114](../../decisions/adr-0114-command-plan-preview-dry-run-isolation.md) command-plan preview surface. Its current request/response contract does not yet prove the required no-live-work exclusion or expose the preview command plan, exact command provenance, authorized fixture or fenced-input reference, and `DRY_RUN_RESULT` fields as one isolated result. A caller must not infer ADR 0114 preview guarantees from `isDryRun=true` on the existing event-ingress path.
- The target preview uses the production sandbox and loop-safety/resource limits, but returns would-be commands to the caller instead of persisting/indexing live work or handing off to tick queues. The current `TriggerScriptEvent(isDryRun=true)` path may still follow the legacy materialized work-item shape and remains an implementation gap.
- Target preview audit evidence is isolated and uses `finalStage=DRY_RUN_RESULT` with `finalOutcome=dry_run_success`; legacy materialized handler-scoped test executions are recorded in `script_event_audit` with `isDryRun=true`, while pre-handler rejection remains in `script_event_ingress_audit`. Persisted, queryable handler audit evidence also carries the semantic execution-surface discriminator `executionSurface=LEGACY_TRIGGER_DRY_RUN | COMMAND_PLAN_PREVIEW`, so the shared stage/outcome pair cannot make the legacy path appear to satisfy ADR 0114. Current audit rows that expose only `isDryRun` and the shared result pair remain an implementation gap. Neither path establishes the ADR 0114 no-live-work proof until the separate endpoint is implemented.
- A successful materialized handler dry-run on the legacy `TriggerScriptEvent(isDryRun=true)` path, distinct from the ADR 0114 target preview endpoint, uses `finalStage=DSL_EVAL`, `finalOutcome=dry_run_completed`, and `finalReason=dry_run_no_handoff`. If handler resolution succeeds but capacity is denied before DSL evaluation, use the handler-scoped pair `finalStage=ADMISSION`, `finalOutcome=quota_denied` with bounded `finalReason=dry_run_capacity_exhausted`. Pre-resolution dry-run budget denial is an expected event-scope typed result `TRIGGER_ADMISSION_OUTCOME_QUOTA_DENIED` / `admissionReason=dry_run_budget_exceeded` and creates no handler row. Transport/pre-domain authorization or validation failures, resource exhaustion, dependency failures, and internal failures use canonical non-OK gRPC status with bounded details under the [gRPC outcome classification](../../system-architecture-grpc.md#outcome-and-transport-classification), rather than being relabeled as scripting admission outcomes. When authoritative resource/capacity exhaustion prevents the declared decision, use non-OK `RESOURCE_EXHAUSTED`; when route/lease, worker, dependency, or capacity-policy infrastructure is unavailable and cannot produce the decision, use non-OK `UNAVAILABLE`, rather than `quota_denied`.

## Reload Backpressure Contract

Reload admission and retry semantics follow [ADR 0173](../../decisions/adr-0173-registry-classified-reload-admission-policy.md) and the canonical [Scripting & Automation Cross-Service Contracts](../../system-architecture-scripting-contracts.md#7-reload-backpressure-contract). During `reloadState=RELOADING`, each event registry entry selects exactly one policy:

- `REJECT_VISIBLE` returns an explicit visible rejection for the current intent such as `onCommand`; the platform does not queue it for delayed automatic execution.
- `DURABLE_RETRY` requires the named owning producer to retain and retry the same parent identity with bounded expiry or elapsed time, exponential backoff, and jitter.
- `SKIP_RECONCILE` records the skipped attempt and applies the event's declared reconciliation or catch-up behavior. Best-effort timer events are not generally backfilled.
- Reload backpressure is policy-specific: only a `DURABLE_RETRY` entry may retain a retry-eligible attempt or perform a monotonic `BACKPRESSURED -> ADMITTED` transition with the same request digest and version/fence. `REJECT_VISIBLE` finalizes the current intent without delayed execution; a new intent uses a new parent event identity. `SKIP_RECONCILE` follows its declared reconciliation or catch-up rule and does not reclaim stale intent.

At this API boundary, a reload rejection returns explicit backpressure signals consistent with that selected policy:

- `TriggerScriptEventResponse.admitted=false`
- `TriggerScriptEventResponse.admissionOutcome=TRIGGER_ADMISSION_OUTCOME_BACKPRESSURE_RELOADING`
- `TriggerScriptEventResponse.admissionReason="reloading"` or equivalent
- `TriggerScriptEventResponse.retryAfterMs` is populated only where the selected producer policy permits retry; it is absent for visible rejection or skip/reconcile behavior

The service must also record the event-scope ingress decision in the ingress audit/logging surface with `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_BACKPRESSURE_RELOADING` and bounded reason `reloading`. A handler-scoped `script_event_audit` row is written only if handler resolution has already produced a concrete Trigger Identity.

When the runtime scope is `reloadState=FAILED`, ingress is fail-closed rather than backpressure:

- `TriggerScriptEventResponse.admitted=false`
- `TriggerScriptEventResponse.admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE`
- `TriggerScriptEventResponse.admissionReason=reload_failed`
- `retryAfterMs` is absent; recovery is not an automatic caller retry contract.

The same event-scope decision is recorded in `script_event_ingress_audit`, with no handler row or handler Trigger Identity. Timer due candidates record their event-scope `scheduleCandidateId` audit instead and create no firing claim or `scriptEventId`. Recovery durably reconciles the current pin, schedule ownership, runtime scope/epoch, and due evidence, transitions `FAILED -> RELOADING` under one idempotent recovery identity, and reaches `IDLE` only through one successful atomic reconciliation; the previous patch remains diagnostic state only.

During operator rollback pause (`PAUSED_FOR_ROLLBACK`), ingress must return an explicit rollback backpressure outcome and ingress audit record:

- `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_BACKPRESSURE_ROLLBACK`
- `admissionReason=rollback_pause`
- event-scope identity fields from the request, without inventing synthetic `scriptId` or `bindingId` fields

While terminal `PIN_CONVERGENCE_TIMEOUT` is active for either promotion or rollback, pre-handler ingress remains rejected using the terminal version-unavailable response; no `retryAfterMs` is returned because terminal convergence has no bounded retry horizon:

- `TriggerScriptEventResponse.admitted=false`
- `TriggerScriptEventResponse.admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE`
- `TriggerScriptEventResponse.admissionReason=pin_convergence_timeout`
- `script_event_ingress_audit` records the same event-scope admission outcome and `admissionReason=pin_convergence_timeout`, with no `retryAfterMs`
- Each rejected ingress increments the existing `automation_script_triggers_dropped_total` family with the bounded `pin_convergence_timeout` reason and pre-handler dimensions owned by [normative Table 4](../../system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix). `automation_pin_convergence_timeout_total` increments only when the owner workflow enters the terminal state, not for each rejected ingress.

This is an event-scope decision. It must not create or relabel a handler-scoped `script_event_audit` row with `finalOutcome=pin_convergence_timeout`.

The current ingress implementation looks up an existing ingress-audit result before handler resolution, then performs validation and handler fan-out before writing the audit result. It does not yet provide the target durable `IN_PROGRESS` claim that fences resolution/fan-out and makes concurrent retries wait or return a retryable signal without an admission result; that target retry behavior remains defined by the normative event-scope contract.

These ingress response fields are event-scope only. A successful ingress admission means the request was accepted for handler resolution; it does not mean every resolved script or plugin handler later succeeded. `resolvedHandlerCount` reports the number of enabled bindings matched and resolved for the admitted event scope, including dry-run/test ingress. It is not a persisted work-item, command, successful-handler, or handler-audit-row count; a resolved handler may have no work item after handler-scoped admission denial. Zero handlers remains a normal admitted response with count zero and is metric-only, not an ingress or handler-audit outcome. This metric-only live-event case is distinct from a tenant-readiness notification whose zero-handler manifest proof is missing or unverifiable; that readiness case must produce the durable `FAILED` status/audit outcome defined by the lifecycle contract. Per-handler outcomes remain authoritative in `script_event_audit`.

Event-scope admission outcomes are intentionally limited to ingress-time fences such as reload/rollback backpressure, version visibility, pin visibility, explicit-plugin signer-policy visibility, dry-run rejection, and event-registry validation. These pre-resolution outcomes are recorded in `script_event_ingress_audit`; handler-scoped outcomes such as `quota_denied`, `script_disabled`, `plugin_disabled`, `plugin_component_blocked`, and generic-ingress signer/publication-policy rejection are recorded only after binding resolution in `script_event_audit`. Pre-handler dry-run rejection, explicit-plugin signer-policy unavailability, and rollback backpressure do not create handler audit rows; an admitted live event with zero handlers is metric-only. This does not weaken the separate readiness requirement: an identifiable zero-handler readiness notification without immutable proof is durably `FAILED` with status/audit evidence and cannot be silently rejected or marked `READY`.

Retry identity and timer catch-up behavior follow the linked scripting contract. The event-ingress response fields (`admitted`, `admissionOutcome`, `admissionReason`, `retryAfterMs`) and enum values are normative API contract and must align with [Scripting Control Plane API](../../system-architecture-scripting-control-plane-api.md).

Same-request retries return persisted per-row outcomes under the canonical [operator replay contract](../../system-architecture-scripting-control-plane-operations.md#replaydeadletteredworkitems).

Target-state replay claim and scope rules for `ReplayDeadLetteredWorkItems`:

- Reusing a `controlPlaneRequestId` with a different canonical request fingerprint returns an idempotency conflict and cannot alter an existing result. An exact retry of the same `controlPlaneRequestId` and canonical request fingerprint returns the identical stored per-row outcomes and `failureGeneration`, including `recovery_failed` with its stored `failureReason` or `rejected`, without repeating evaluation or dispatch or relabeling the result; `already_recovered` is emitted only for a new recovery request with immutable prior successful-recovery evidence for the same current generation, while any other non-`DEAD_LETTERED` row is rejected with `work_item_not_dead_lettered`. A different request targeting a `DEAD_LETTERED` row with an active `IN_PROGRESS` claim for the current generation stores `outcome=rejected` with `rejectionReason=recovery_in_progress` and creates no new claim, evaluation, or dispatch. An older generation's evidence remains immutable and cannot satisfy or block a new current-generation request.
- The initial mutation accepts only bounded explicit work-item IDs; descriptor references and descriptor filters remain deferred. Each requested ID is checked and claimed at its owning durable work-item boundary; recovery preserves the original work-item, `scriptEventId`, and logical trigger identity. Evaluation-stage dispatch allocation follows the pre-commit/command-emission rule above; committed-descriptor recovery reuses its existing dispatch and child identities without replacement.
- Explicitly selecting tenant-readiness `onLoad` work does not override its replay exclusion: the row remains `DEAD_LETTERED`, returns `outcome=rejected`, creates no recovery claim or fabricated runtime identity fields, and requires a newly published immutable patch before readiness can run again.
- Automation owns a monotonic `failureGeneration` per `(tenantId, outboxWorkItemId)` on the separate parent recovery aggregate. The first atomic transition of that aggregate into `DEAD_LETTERED` initializes it to `1`; a later transition, including a permanent required-child failure after an `EVALUATED_COMMITTED` evaluation or a failure after successful recovery, advances it exactly once in that same transition, while an exact retry/no-op does not advance it. The parent work-item retains its `EVALUATED_COMMITTED` descriptor marker and complete output/child ledger when post-evaluation failure moves the recovery aggregate to `DEAD_LETTERED`. The `DEAD_LETTERED` recovery claim/attempt is persisted atomically with the aggregate status claim and records `(tenantId, outboxWorkItemId, failureGeneration)`, the expected exact `(scriptPatchVersion, scriptPinEpoch)`, runtime scope, applicable plugin binding tuple, captured plugin `(pluginActivationEpoch, lifecycleRevision)` when applicable, and `controlPlaneRequestId`. The canonical recovery-attempt fence applies to every recovery write: reclamation reuses the same attempt while advancing its owner fence, and the prior owner or stale generation then fails closed. Recovery also revalidates the exact pin/runtime fences, exact plugin binding identity, and captured plugin `(pluginActivationEpoch, lifecycleRevision)` lifecycle-fence evidence immediately before evaluation and each post-evaluation dispatch. A terminal failed attempt stores `outcome=recovery_failed` with its required `failureReason` and leaves the aggregate `DEAD_LETTERED` in the same generation; an exact retry returns that stored result without a new attempt, while a later new request may create one new attempt only after the prior attempt is terminal `FAILED` and fresh eligibility/fence checks pass. Failed attempts that leave the aggregate in the same generation do not advance it. Selectors remain explicit work-item IDs, and the mutation resolves the current failure generation rather than accepting it as a selector.
- A successful recovery durably stores the original work-item/script-event identity, stage, outcome/result, winning `controlPlaneRequestId`, and canonical request fingerprint. Evaluation-stage recovery uses the original frozen evidence; post-evaluation recovery resumes only unfinished child dispatches from the stored ledger and never re-enters generic admission.
- Every selected row is checked against its own stored `tenantId` and `gameInstanceId`. The request tenant must match that row, and the row's own instance must be used to resolve the current pinned patch and current plugin binding. Tenant-wide selection is not a target mutation; each explicit ID is evaluated at its owning durable instance boundary.
- Each requested ID returns exactly one canonical per-row `failureGeneration` when a generation is resolved and `outcome`: `retried_evaluation`, `resumed_dispatch`, `already_recovered`, `recovery_failed`, or `rejected`. Only `outcome=rejected` carries `rejectionReason`; `recovery_failed` carries required `failureReason` and no `rejectionReason`. Both use the established bounded failure vocabulary, with `failureReason` describing the terminal failed attempt rather than introducing a parallel taxonomy. Eligible rows advance independently and an ineligible `DEAD_LETTERED` row remains unchanged. `recoveryStage` is optional/nullable and is `null` when the row is `not_found_or_not_owned` or `stage_evidence_unavailable` because no trustworthy stage is available.
- Local replay consequence: the Automation surface reports the canonical per-item rejection outcomes and leaves an ineligible parent recovery aggregate `DEAD_LETTERED`; detailed stage, generation, claim, and fence rules remain owned by [Scripting Control Plane Operations](../../system-architecture-scripting-control-plane-operations.md#replaydeadletteredworkitems). `DRAINING` is non-admitting for new triggers but permits recovery of already-admitted work only under [ADR 0119's exact lifecycle fence](../../decisions/adr-0119-epoch-fenced-per-instance-plugin-activation.md): `ENABLED` requires the exact current `lifecycleRevision`, while same-version, same-epoch `DRAINING` may use only work whose winning admission/fence CAS durably committed the immediately preceding `ENABLED` revision before the `DRAINING` transition; capture or observation alone is insufficient. `plugin_disabled` applies only when the lifecycle transition invalidates admitted work, such as `DISABLED`, revocation, or policy-driven disablement; committed-descriptor recovery reuses existing dispatch/child identities without replacement, while evaluation-stage recovery allocates no dispatch or command-child identity before a winning descriptor/outbox commit that emits commands.

Target schedule rows, due candidates and claims, timer-audit rows, and any derived scheduler work/dead-letter/replay evidence additionally retain and expose stable `playableStateNamespaceId` as non-identity evidence, revalidate it with the exact namespace/scope and active-instance/region owner binding on materialization, claim, replay, and readback, and fail closed on missing or mismatched evidence. The current schema, proto, implementation, and dead-letter/replay path do not persist or expose that namespace field.
- `GetPluginStatus(tenantId, gameInstanceId, pluginId)` – **target-state read:** returns plugin runtime state (`ENABLED`, `DISABLED`, `DRAINING`, `RELOADING`, `FAILED`), active and pending version IDs, the current committed `pluginActivationEpoch` and `lifecycleRevision`, the last control-plane request id, the last recorded actor principal for the runtime row, separate failure-rate breaker outputs (`breakerState`, bounded `breakerReason`, monotonic `breakerRevision`, and monotonic `breakerSampleGeneration`) for the exact active version/runtime scope, nullable current breaker-reset evidence including bounded immutable `lastResetReason` distinct from lifecycle `statusReason`, and current policy-check freshness (`lastPolicyCheckedAtMs`, `policyCheckStale`). The current proto/implementation returns the state/version and policy/publication fields but does not persist or expose the target activation epoch/lifecycle revision or breaker/reset outputs.
- `ListPluginRuntimeEvents(tenantId, gameInstanceId?, pluginId?, pluginState?, breakerState?, activePluginVersionId?, changedAfterMs?, changedBeforeMs?, limit?)` – **target-state read:** returns append-only instance-scoped plugin lifecycle history for activation, drain, disable, policy-reconcile fail-closed transitions, and breaker trip/reset transitions. Breaker trip rows retain exact active-version, policy/window/threshold/count/sample evidence; reset rows retain actor, bounded immutable `resetReason`, request, validation, and sample-generation evidence; lifecycle rows omit those transition-only fields and use separate lifecycle `statusReason`. The current event proto/implementation has no epoch/revision or breaker/reset evidence and remains a narrower history projection.
- `GetPluginPolicyConvergence(tenantId, gameInstanceId?, maxResults?)` – the current read inspects enabled plugin runtime states with an active version, optionally narrows them to one game instance, filters them against the current runtime region/region-epoch scope when that scope is available, and reports publication, signer, or component-policy violations plus freshness. The response has no `pluginActivationEpoch` or `lifecycleRevision` fields and cannot serve as ADR 0119 lifecycle-fence proof.
- Plugin runtime reads and history also expose the separate failure-rate breaker state: `GetPluginStatus` returns `breakerState`, bounded `breakerReason`, `breakerRevision`, and `breakerSampleGeneration` for the exact active version/runtime scope, while `ListPluginRuntimeEvents` uses a bounded `transitionKind` and transition-specific evidence to distinguish lifecycle, breaker trip, and breaker reset rows. `ResetPluginBreaker` is the target operator mutation for the exact active `(tenantId, gameInstanceId, pluginId, pluginVersionId)` breaker aggregate; it is digest-bound, expected-state/revision fenced, advances the sample generation so prior samples remain history-only, and atomically appends its immutable reset evidence without changing lifecycle counters. Breaker notifications carry that exact unchanged active version. `breakerState=DISABLED_DUE_TO_ERRORS` blocks newly resolved plugin handlers with `finalOutcome=disabled_due_to_errors` / `finalReason=failure_rate_breaker` without changing lifecycle `pluginState`; a new active version starts `CLOSED`, and there is no half-open loop. The current proto/implementation does not expose the breaker read/history fields or reset mutation.
- `SetPluginActiveVersion`, `DisablePlugin`, and `DrainPlugin` – **target-state operations:** idempotent plugin lifecycle operations used by Logging & Admin to promote, disable, or drain plugin versions per runtime scope. Automation owns one pending-transition slot per `(tenantId, gameInstanceId, pluginId)`: initiation CASes the captured current `(pluginVersionId, pluginActivationEpoch, pluginState, lifecycleRevision)` tuple only when no transition is pending, reserves `targetLifecycleRevision = current + 1` for every state-changing transition, exact retries resume, and different activation/switch/drain/disable/revocation/reactivation/policy requests fail closed as `transition_in_progress`. Completion CAS requires the unchanged tuple, pending request identity/digest, target epoch when applicable, and target lifecycle revision; stale completion cannot overwrite newer state. The idempotent Game Session install and durable acknowledgement precede reporting a new activation or completed containment. The current operations do not yet persist/propagate the complete epoch/revision/acknowledgement fence across the API and runtime surfaces; this remains an implementation/proof gap. Security, component, and signer-policy fences remain independent immediate fail-closed checks.

Consumption rules:

- Use `ScriptPatchTenantStatusChanged` for tenant readiness gates and publish-validation UX.
- Use `ScriptPatchPinChanged` only to accelerate observed convergence and projection refresh; use Game Session's direct current-pin and history reads for committed rollout progression and rollback history.
- Read-model ownership for Automation status is a bounded, idempotent projection keyed by `(tenantId, gameInstanceId)`; `controlPlaneRequestId` is retained only as last-applied/idempotency evidence. `ScriptPatchPinChanged` is an advisory wake-up: the consumer rereads Game Session's authoritative current-pin and bounded history APIs, uses the producer-owned `scriptPinEpoch` and owner-history cursor/version to ignore stale observations, and treats duplicate or lost notifications as refresh-latency only. An epoch-only `REPIN` is applied when the owner read reports a newer epoch even when the patch version is unchanged. The projection remains replaceable, non-authoritative, and never derives rollout history locally; it does not consume a generic `instanceSequence` or allocate a cross-service sequence.

Game Session and Logging & Admin use script patch visibility APIs and events to decide which `scriptPatchVersion` values may be passed to runtime. Mutating operations that change the pinned patch for a running game instance are defined on the Game Session control-plane surface and must follow the contracts in [Scripting Control Plane API](../../system-architecture-scripting-control-plane-api.md). The Automation & Scripting Service uses the shared Game Session runtime-state read as the authoritative refresh source for its local pin projection and for admission alignment, but it is not the source of truth for the pin. Pinning must also satisfy base-version cohesion (`patch.baseVersionId == runtimeVersionId` for the instance).

## Pinned Version Visibility Consistency

Admission and scheduler decisions use the bounded-staleness and fail-closed rules in the [cross-service version-fencing contract](../../system-architecture-scripting-contracts.md#3-version-fencing-rollback-safety). This service-local projection exposes the latest observed pin and freshness flags only; it does not return an admission `finalStage`, `finalOutcome`, or `finalReason`. Event-scope admission outcomes and reasons are produced on the [normative event-ingress decision path](../../system-architecture-scripting-control-plane-api.md#automation--scripting-event-ingress-admission-contract-normative), while handler-scoped final outcomes remain in `script_event_audit` after binding resolution.

Plugin signer-policy admission follows the same fail-closed principle, with the audit stage determined by when plugin ownership is known. For requests carrying explicit plugin identity, if signer policy for a scope is stale beyond max age and cannot be refreshed, current event ingress is rejected before handler work is materialized; no handler-scoped `finalOutcome` or `script_event_audit` row is produced. For generic ingress, target behavior revalidates current signer/publication policy immediately after resolving and durably claiming the plugin-owned handler identity, but before quota charging or work-item materialization; a rejection commits that handler's `script_event_audit` row with `finalStage=ADMISSION` and the applicable bounded handler-scoped outcome. The current generic path does not yet implement that check and remains an implementation gap. The canonical admission fields, ingress-audit mapping, and metric are owned by the [normative scripting contract tables](../../system-architecture-scripting-normative-contract-tables.md#table-1-trigger-identity-required-fields) and [observability contract](../../system-architecture-scripting-observability-contract.md#ingress-audit-vs-handler-audit).

## Digest Contract

This service is a required digest participant for full publishes and script-patch publishes. It must expose `GetDraftDesignDigest` with a typed scope selector `oneof { versionId, scriptPatchVersion }` and maintain a service-local digest input manifest with:

- Included objects such as version- or patch-scoped script graphs, bindings, and publish-critical metadata that affect runtime execution for the scoped publish type.
- Excluded objects such as runtime queues, audit and event logs, quota counters, and other non-launchability operational state.
- Canonicalization rules covering stable ordering, normalized serialization, and deterministic default and null handling before hashing.
- `digestSchemaVersion` bump criteria: any include, exclude, or canonicalization change requires an explicit schema bump and digest migration or re-record workflow.

Publish gating must fail closed when the service cannot attest a digest under its documented manifest for the reported `digestSchemaVersion`.

### Game Design owner-to-owner digest authorization

For publication-gate calls, `GetDraftDesignDigest` is not an admin or user operation. The target receiver authorization is a method-level allowlist for the authenticated Game Design workload identity, under the shared [Security Architecture](../../system-architecture-security.md) and [Authentication & Authorization](../../system-architecture-authentication.md) owner rules. The call must carry and validate the exact `{tenantId, scope}` (`versionId` or `scriptPatchVersion`) together with the stable caller `publishRequestId`, derived workflow identity, and canonical `requestDigest`; omitted or changed binding fails closed. This context is authorization and replay evidence, not a digest input. Other internal workloads are denied, and no user/admin JWT is accepted as a substitute. Game Design's Temporal activities must never forward the initiating human operator JWT; operator authority terminates at workflow admission.

**Current status:** Temporal activities run without an incoming `SessionContext`, so the Game Design client falls back to an internal JWT with empty `globalRoles`. `AutomationScriptingGrpcService.GetDraftDesignDigest` currently calls `AdminRoleGuard.requireAdminRole()`, which only accepts a global privileged role. The call therefore returns `PERMISSION_DENIED`, blocking full publish when Temporal is enabled. The current `GetDraftDesignDigestRequest` proto carries only `tenant_id` plus a `oneof` `version_id`/`script_patch_version`; neither the proto nor handler carries or validates the target `publishRequestId`, derived workflow identity, or canonical `requestDigest`, so the current path is neither owner-bound nor replay-proof.
