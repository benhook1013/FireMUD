# Automation & Scripting Service Operations

This document collects the service readiness model, quota and fairness behavior, rollback and convergence operational expectations, and operator-facing observability guidance.

## Implementation Status

The current service implementation still combines pre-DSL trigger state and later handoff processing in its work-item row, lacks evaluation lease/fencing-generation recovery, and does not carry stable per-command identity and dedupe through the live producer/consumer boundary. Bounded local multi-command and multi-target fan-out is live, and the evaluator now attempts every emitted sibling before finalizing the parent from the first rejection; the handoff owner records each attempted child, while complete durable child/target identity and end-to-end handoff/dedup proof remain incomplete, so current fan-out is not target-conformant. The target durable boundary, state mapping, and recovery behavior are owned by [Scripting Runtime Execution](../../system-architecture-scripting-runtime-execution.md#pre-dsl-trigger-and-evaluated-descriptor-boundary).

## Operational Notes

- Runs as a Kubernetes Deployment (Docker Compose for local dev) with `/actuator/health/readiness` and `/actuator/health/liveness` probes. See [Deployment Environments](../../infrastructure/deployment-environments.md).
- Logging, metrics, and tracing follow the standard [Logging & Monitoring](../../system-architecture-logging-monitoring.md) pipeline.
- Operators and SREs should pair this document with [Scripting Quotas and Operations](../../system-architecture-scripting-quotas-and-operations.md), [Scripting Operations Cookbook](../../system-architecture-scripting-operations-cookbook.md), [Scripting Observability Contract](../../system-architecture-scripting-observability-contract.md), and [Redis Architecture](../../system-architecture-redis.md).

## Readiness and Liveness

- `liveness` is local-only and indicates that the process is alive and the scheduler/runtime loops are not wedged.
- `readiness` is runtime-safety for the currently exposed automation slice. The service is ready only when its durable PostgreSQL state, required Redis coordination paths, and the script-patch readiness ingestion loop are able to accept and reconcile new work safely.
- A process that can answer `Ping` locally but cannot ingest tenant patch updates, persist automation work, or reconcile runtime-scope pin changes is not ready for new automation traffic.
- Readiness must reflect rollback and convergence safety as well as simple process health, so partially initialized runtimes or failed reload loops remain unready until they return to a safe state.

## Fairness Quotas and Budgets

`ScriptQuotaService` limits how many times a script may execute within a configurable window. Counters are stored in Redis using keys of the form `automation:quota:<tenantId>:<scriptId>`. When a quota is exceeded the event is denied under the owning admission and audit semantics. The metric family, labels, and increment unit for that decision are defined only by [Table 4](../../system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix). Saga orchestration emits separate Saga-specific metrics and must not be conflated with quota enforcement.

Dry-run and test executions use separate budgets and isolated capacity so privileged tooling cannot starve live automation.

The staging Lua script processes only a limited number of events each tick, controlled by `AUTOMATION_TICK_MAX_EVENTS`, to keep automation work predictable.

## Patch Rollout, Rollback, and Convergence

Game Session and Logging & Admin use the script patch visibility APIs and events described in [API Contracts](./api-contracts.md) to decide which `scriptPatchVersion` values may be passed to runtime. The Automation & Scripting Service does not own authoritative pin mutations, but it must expose enough convergence status for promotion and rollback orchestration to prove that runtime scopes observed the intended pin.

Pin-transition orchestration rules:

- Pinning must satisfy base-version cohesion (`patch.baseVersionId == runtimeVersionId` for the instance).
- Promotion and rollback target only a tenant-`READY` patch from Automation & Scripting; [Game Session owns](../../system-architecture-scripting-control-plane-api.md#game-session-patch-pinning) the per-instance pin/CAS. `EXPECT_UNPINNED` is valid only for a first pin. Semantic `UNPINNED` means no script is selected only for a never-pinned instance (both tuple fields are absent), never an active target or convergence branch.
- Promotion and rollback convergence waiting is bounded and delegates to the [Pin Convergence Acknowledgement Predicate](../../system-architecture-scripting-rollout-and-rollback.md#pin-convergence-acknowledgment-predicate). **Target state:** pinned promotion/rollback convergence is acknowledged only when the Game Session owner result and Automation's observed projection both report the requested target exact `{scriptPatchVersion, scriptPinEpoch}` tuple (the observed fields match the owner fields and requested target), the owner `controlPlaneRequestId` matches the admitted transition, Automation's `lastObservedControlPlaneRequestId` equals that same owner ID, both owners report the same exact `convergenceAttemptGeneration` for the admitted attempt, and projection freshness and lag bounds pass; the same patch under a new epoch remains non-converged. The current Automation convergence API does not expose `observedConvergenceAttemptGeneration`, so the current API cannot prove this attempt-bound predicate. A never-pinned semantic `UNPINNED` observation is the separate no-script-configured case, with both tuple fields and its request identity absent, and is not a pinned transition acknowledgement. This service must not declare convergence from its own acknowledgement; it consumes the owner workflow outcome and keeps new script admission for the affected scope paused when the canonical predicate has not succeeded. Routine pin transition does not pause ordinary Game Session gameplay ticks; a full gameplay pause is exceptional and belongs to the owner contract for an explicitly unfenced effect family.
- Game Session alone owns the convergence deadline, `PIN_CONVERGENCE_TIMEOUT` transition, immutable workflow `operationKind`, and terminal timeout signal. Automation consumes that durable workflow state through the authoritative [`GetScriptPinTransitionWorkflowStatus`](../../system-architecture-scripting-control-plane-api.md#getscriptpintransitionworkflowstatus) read and uses the signal only as an advisory wakeup; it must not run a competing timeout, emit the timeout signal, or define a local timeout metric. Any metric consequence follows [Table 4](../../system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix).
- Promotion and rollback orchestration follow the durable state machine in [Scripting Rollout and Rollback](../../system-architecture-scripting-rollout-and-rollback.md#pin-transition-orchestration-state-machine-required). This service must resume its idempotent participation from the last durable owner state rather than restarting or accidentally unpausing.
- **Current fresh-schema timer consequence:** runtime materialization creates missing unpinned `script_schedule_instances` rows via `ScriptScheduleInstanceServiceImpl`/`ScriptScheduleInstanceRepository.saveAll`, with `scriptPinEpoch=0` and no owner request identity. On the next runtime tick or wall-clock observation, the scheduler treats that incomplete tuple as fenced, sets `materializationStatus=FENCED`, clears the retained due point and runtime-progress fields, and emits no timer work or audit. A later complete Game Session pin/runtime reconciliation rematerializes the schedule; wall-clock timers are seeded from the pin-observation time, while tick-aligned timers wait for fresh runtime progress. Operators should reconcile the owner tuple before treating the timer as active.
- **Target-state drain mapping:** `GetAutomationDrainStatus` is diagnostic cleanup-progress evidence, not a resume gate. A fresh response for the current `{tenantId, gameInstanceId, regionId?}` scope, `admissionEpoch`, and exact `scriptPinEpoch` reports the current `activeExecutionCount` and `pendingCancelableWorkItemCount`; both counts being zero means counted cleanup is complete for that exact scope, `admissionEpoch`, and `scriptPinEpoch`, but remains diagnostic and is not a resume gate. `activeExecutionCount` is exactly current-epoch `EXECUTING` pre-DSL triggers plus `HANDOFF_IN_FLIGHT` evaluated descriptors, and `pendingCancelableWorkItemCount` is exactly current-epoch `PENDING_EVALUATION` pre-DSL triggers plus `PENDING`/`INDEXED` evaluated descriptors. Terminal states, rows from another scope or epoch, and derived queue pointers are excluded. Nonzero counts report current counted work, while Automation resume remains gated by exact target-artifact convergence and schedule reconciliation; missing, stale, or other-epoch pin evidence cannot prove cleanup completion.
- **Current fail-closed counts:** while `PAUSED_FOR_ROLLBACK`, the live projection restricts persisted current `script_work_items` to rows whose `workItem.admissionEpoch <= 0` or `workItem.admissionEpoch < current admissionEpoch`, excluding positive current-epoch rows; within that set it counts `EVALUATING`, including unresolved stale rows, and `HANDOFF_IN_FLIGHT` as active and `PENDING_EVALUATION` as pending. In normal mode it counts the corresponding scoped rows without that admission-epoch filter. The current query does not filter or group by `scriptPinEpoch`, so a response can aggregate mixed pin epochs and cannot prove cleanup for one exact epoch. The current work-item model now persists the exact positive `scriptPinEpoch` captured at admission; the separate `PENDING`/`INDEXED` descriptor layer and its richer recovery semantics remain target-only. These counts are diagnostic only, not authoritative target cleanup completion; any unresolved count, stale response, or mixed/earlier-epoch response cannot prove cleanup completion or authorize resume.
- During target-state `DRAINING`, `PENDING_EVALUATION` is durably canceled without entering the DSL. `EXECUTING` is resolved only after reading the descriptor-commit marker: if committed, cancellation never resumes or re-dispatches a child; `PENDING` and `INDEXED` children compare-and-set to `CANCELED` with durable `cancelReason`, `finalStage=WORK_ITEM_PERSIST`, and `finalOutcome=canceled`; `HANDOFF_IN_FLIGHT` fences further retry and reconciles the durable downstream outcome (remaining active/unresolved when ambiguous); and `HANDED_OFF`, `CANCELED`, or `DEAD_LETTERED` children retain their outcome and no-op. An explicitly canceled uncommitted trigger becomes terminal `CANCELED` with `finalStage=DSL_EVAL` and `finalOutcome=canceled`, while only the distinct expired-stale recovery-owner path makes an uncommitted trigger terminal `DEAD_LETTERED` with `finalReason=stale_execution_fenced`. The current live projection remains `EVALUATING` and retains unresolved stale rows as active; the status, reason, and audit mapping are defined in [Scripting Runtime Execution](../../system-architecture-scripting-runtime-execution.md#pre-dsl-trigger-and-evaluated-descriptor-boundary).

**Target-state exact-epoch admission:** For instance-scoped script admission, a bounded-fresh observed Game Session pin/epoch projection may admit work. If that projection is absent or stale, Automation must perform a bounded refresh from authoritative Game Session `GetPinnedScriptPatchVersion` before admission; refresh failure fails closed. A mismatched exact tuple also fails closed, and no stale or local projection override may admit work. Current ordinary instance-scoped gameplay/runtime ingress carries `scriptPinControlPlaneRequestId` with the patch and positive epoch, persists that owner evidence on the event claim and admitted handler work, and compares it with current owner/observed state; absent, partial, or mismatched owner evidence fails closed. Tenant-readiness `onLoad` remains the explicit pre-instance exception and omits all instance pin-owner fields. The stronger target lifecycle carries the same evidence through every local and remote handoff, recovery, and final-effect boundary; remote source/target binding and complete final-effect proof remain gaps. Plugin-backed admission and final-execution fencing follow [ADR 0119](../../decisions/adr-0119-epoch-fenced-per-instance-plugin-activation.md). A successful semantic `UNPINNED` owner result remains the explicit no-script-configured case. The service may continue ordinary non-script runtime work while scoped script admission is unavailable. Cleanup of displaced work is bounded and asynchronous; cleanup completion is not the epoch-fence correctness barrier. Operators must use owner pin/history reads together with the Automation convergence projection and must not repair or purge rows by direct SQL.

Automation is a registered owner of instance-scoped script work, schedules, plugin runtime projections, and cleanup records for the world lifecycle. Each registered family must identify its exact `{tenantId, gameInstanceId, playableStateNamespaceId?, playableStateScope?, regionId?}` scope and its `S1`, `S2`, or `S3` classification. Termination cleanup may delete only records classified as instance-owned `S3`; namespace-backed `S1`/`S2` records are retained or mapped under the replacement contract and must report their retention/mapping disposition separately. Automation must report idempotent cleanup progress and acknowledgement for the old instance and every required cleanup family in the frozen required-owner snapshot captured for that `terminationRequestId`, at its frozen ownership-registry revision, before World Management can mark termination complete; retries and repairs must match that snapshot and revision, and a missing, unknown, or unregistered cleanup family in that snapshot fails closed and blocks completion. A local drain projection or Temporal history is not a substitute for the database lifecycle row or owner acknowledgement. Plugin provenance remains service-local accepted evidence under [ADR 0128](../../decisions/adr-0128-game-design-plugin-trust-provenance.md), while [ADR 0111](../../decisions/adr-0111-unified-dsl-with-distinct-embedded-script-and-plugin-lifecycles.md) remains the trust/runtime authority.

## Plugin Activation Operations

**Target state:** [ADR 0119](../../decisions/adr-0119-epoch-fenced-per-instance-plugin-activation.md) owns the normative per-instance activation and final-execution fence contract.

**Current V3:** Automation persists `pluginActivationEpoch` and `lifecycleRevision` on runtime state and plugin-backed ingress, work, audit, schedule, and handoff rows. The local execution path validates the captured and current plugin state, version, epoch, and revision before quota/DSL evaluation and each gameplay handoff; tuple-wide lifecycle request history includes successful no-op results and the inactive `DRAIN` `FAILED_PRECONDITION` receipt. A timer due candidate snapshots `pluginId`, `pluginVersionId`, applicable `bindingId`, `pluginActivationEpoch`, and `lifecycleRevision`, then rechecks the snapshot against the schedule row and local plugin-owner state before emission. Durable winning-admission CAS/barrier ordering, retained firing claims, and the final Game Session effect fence remain gaps; candidate rechecking does not establish complete timer lifecycle-tuple validation. Pending-transition/admission-barrier ownership, Game Session fence-install acknowledgement/projection, final Game Session effect enforcement, replay/recovery, remote handoff, policy coordination, and complete cleanup remain implementation and proof gaps. Current lifecycle status, event, and mutation responses remain narrower where the proto lacks the pair.

At the Game Session-to-Automation handoff, Automation treats the namespace/scope and active-instance/region fence as owner-provided evidence, not as caller or script metadata. It rejects a missing or mismatched `{tenantId, playableStateNamespaceId, playableStateScope, gameInstanceId, regionId, regionEpoch}` binding and never resolves a replacement namespace locally. The current handoff path remains narrower in places, so this is a target receiver-side check and an explicit implementation/proof gap.

**Plugin cleanup batches:** `CancelPendingWorkItemsForPluginVersion` accepts only a nonempty, unique, nonblank explicit `workItemIds[]` batch of at most 100 parent IDs, validated before candidate reads or mutation. The normalized sorted ID set is part of the request digest and exact retries return the stored batch results; callers use a new request ID for each bounded batch and the service never truncates or pages an exact request. The exact `(tenantId, gameInstanceId, pluginId, pluginVersionId, pluginActivationEpoch, scriptPatchVersion, scriptPinEpoch)` tuple remains required; `lifecycleRevision` is deliberately not a request selector or digest field because cleanup is asynchronous and it is not the cleanup correctness barrier, although it remains required final-execution evidence. IDs may resolve rows from any binding; `bindingId` remains per-row evidence, not a selector. Each parent returns exactly one result: precondition failure is `not_found_or_not_owned`/`rejected`; any active or ambiguous parent/child (including `HANDOFF_IN_FLIGHT`) is `recovery_in_progress`; `canceled` requires this request to change at least one eligible row and every applicable child to be terminal; `already_terminal` requires no mutation and all applicable children already terminal. Bounded child-state counts/reasons may accompany the result, including the row's stored/revalidated `lifecycleRevision` beside the activation epoch when that evidence exists; omitting it from the selector and digest never permits cleanup to erase or rewrite this per-row final-execution fence evidence. `canceledCount` counts only parent results with `outcome=canceled`; cleanup is asynchronous and never the correctness barrier.

## Metrics and Audit Guidance

The authoritative metric-family names, labels, and increment units live only in [Table 4](../../system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix). The examples below are pointers to those definitions, not service-local metric schemas:

- `automation_script_triggers_total`, `automation_script_skips_total`, and `automation_script_triggers_dropped_total` for scheduler activity and drops.
- `automation_script_queue_delay_seconds` by its Table 4 bounded priority class for queue latency/starvation, and `automation_script_leadership_changes_total` for leader stability.
- `automation_script_timer_catchup_truncated_total` for each cap-excluded catch-up candidate settled by the resume-window limit; cap-excluded candidates create no firing.
- `automation_script_tenant_budget_allowed_total` / `automation_script_tenant_budget_denied_total` for bounded operator-facing automation budget pressure, with tenant-specific drilldown coming from audit rows and control-plane reads rather than raw metric labels.
- `script_quota_allowed_total`, `script_quota_denied_total`, and `automation_tick_events_enqueued_total` for quota enforcement and tick integration.
- `automation_script_sandbox_failures_total`, `automation_script_errors_total`, and `automation_script_runtime_seconds` for sandbox and runtime health.

Queue and quota behavior must be observable either through the canonical `cache.automation_queue_*` patterns in `system-architecture-redis-cache.md` or through the mapped automation metrics documented above.

## Operator Guidance

When diagnosing sandbox-related or automation-runtime issues in production, operators should:

- Check `script_event_ingress_audit` for event-scope admission outcomes, and `script_event_audit` records for `finalStage`, `finalOutcome`, `finalReason`, and associated scope fields such as `tenantId`, `scriptId`, `gameInstanceId`, `regionId`, `regionEpoch`, `tickId`, resolved `playableStateScope` (`shared` or `isolated`), and `sourceService` when present. For emitted-command diagnostics, the complete Command-Handoff Identity is target-state only because `commandOrdinal` and the full identity are not exposed at the current live boundary; `(automationDispatchId, commandOrdinal)` is only that identity's dispatch-group suffix. Current correlation uses `outboxWorkItemId`, `automationDispatchId`, `gameSessionCommandId`, and the exposed Game Session command/result/fence fields. Inspect target-state command-handoff records by the complete Command-Handoff Identity only after that boundary is widened, and inspect rendered command text/shape only when required by the canonical command-handoff schema, so shared-state and isolated-state work can be distinguished without treating one handler audit row as one command.
- Inspect sandbox and runtime metrics such as `automation_script_sandbox_failures_total` and `automation_script_runtime_seconds`; inspect `automation_script_queue_delay_seconds` by bounded priority. Sustained background delay without corresponding skips still indicates starvation pressure.
- Verify patch visibility using `GetScriptPatchStatus` and `GetScriptPatchInstanceRolloutStatus`; `GetPinnedScriptPatchVersion` remains an additional authoritative current-pin diagnostic. When a pinned promotion or rollback is active, the named [Pin Convergence Acknowledgement Predicate](../../system-architecture-scripting-rollout-and-rollback.md#pin-convergence-acknowledgment-predicate) requires fresh Game Session and Automation responses from `GetGameSessionPinConvergence` and `GetAutomationPinConvergence`, accepting convergence only when both expose and report the same target `{scriptPatchVersion, scriptPinEpoch}` tuple, the owner-committed `controlPlaneRequestId`, and an equal `convergenceAttemptGeneration`; the Automation projection must additionally have `isProjectionStale=false` and `projectionLagMs <= SCRIPT_PIN_PROJECTION_STALE_THRESHOLD_MS`. The current API cannot acknowledge this predicate and must fail closed until both responses expose matching attempt-generation evidence. Treat a never-pinned semantic `UNPINNED` result separately as the no-script-configured observation: both tuple fields and the associated request identity are absent, so it is not pinned transition convergence. The projection never substitutes for the owner response.
- Verify plugin policy/runtime convergence using `GetPluginStatus`, `ListPluginRuntimeEvents`, and `GetPluginPolicyConvergence` together with the design-time publication reads from Game Design.
