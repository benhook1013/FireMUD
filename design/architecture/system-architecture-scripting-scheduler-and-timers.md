# FireMUD System Architecture: Scripting Scheduler and Timer Lifecycle

This document defines the runtime scheduler, timer, and reload lifecycle for scripting and automation. It complements [Scripting DSL Reference & Event Lifecycle](./system-architecture-scripting-dsl-reference-and-lifecycle.md), which remains the canonical owner for DSL semantics, trigger identity, event fan-out, and determinism rules.

Schedule transition semantics are owned here under [ADR 0110](./decisions/adr-0110-explicit-opt-in-schedule-continuity-across-script-transitions.md). The exact Game Session pin/epoch fence and no-routine-gameplay-pause rollback boundary remain owned by [Scripting & Automation: Rollout and Rollback](./system-architecture-scripting-rollout-and-rollback.md) and [ADR 0106](./decisions/adr-0106-epoch-fenced-script-rollback-without-routine-gameplay-pause.md). Clocks and recovery remain linked to existing [ADR 0091](./decisions/adr-0091-class-specific-script-timer-clocks-and-recovery.md), not duplicated here.

## Target-State Authority

The scheduler target contract requires durable timer identity and due state, the exact applicable Game Session pin tuple, complete due-candidate and firing-claim identity, and deterministic recovery and fencing. The detailed target contract below is canonical; the implementation status that follows does not claim those target guarantees.

## Implementation Status

The current implementation provides the following substrate:

- `NotifyScriptVersionUpdate` persists the durable patch-scoped schedule-definition catalog in PostgreSQL (`script_schedule_definitions`), and each observed `(tenantId, gameInstanceId)` pin materializes durable `script_schedule_instances` rows. Current rows retain patch-only `scriptPatchVersion`, `scheduleDefinitionId`, patch/plugin ownership, cadence/unit, priority, binding target identity and priority/exclusivity, `scheduleSemanticsHash`, the pin operation's `controlPlaneRequestId`, and mutable due-point state; `scriptPinEpoch` persistence and end-to-end fencing remain target-state incomplete. See the [Automation and Scheduler Runtime tracker](../project-management/implementation-tracking/automation-and-scheduler-runtime.md#capability-status).
- Wall-clock timers persist `nextDueAt`; in the live schema/entity, `next_due_at`/`nextDueAt` is the current equivalent of target canonical `dueAt`, while `nextRunAt` is only a derived projection, not the canonical persisted due point. Tick-aligned schedules remain `PENDING_RUNTIME_PROGRESS` until Game Session reports `(tenantId, gameInstanceId, regionId, regionEpoch, tickId)` through `ObserveRuntimeTickProgress`; Automation then stores `runtimeRegionId`, `runtimeRegionEpoch`, `lastObservedTickId`, `lastRuntimeProgressObservedAt`, and the next future `nextDueTickId`.
- Game Session advances durable `lastCommittedTickId` on the runtime-ownership row that also carries `regionId`, `regionEpoch`, and `executorFence`, exposes that state through runtime ownership status, and publishes it after successful tick cycles. True region partitioning remains target-state; the live ownership row currently carries a transitional non-empty `regionId` scope marker, but consumers must not derive or reconstruct that value from `gameInstanceId`.
- Runtime observations stamp the fenced region scope onto wall-clock timers as well as tick schedules. Due tick and wall-clock candidates emit deterministic timer-derived `ScriptWorkItem` rows through the normal durable work-item, audit, and `automation:queue:*` projection path, then advance or clear the consumed due point.
- A newer observation that proves the runtime scope changed fences the stale due point instead of reminting it under the new epoch. The service records `runtime_scope_changed` against the old Trigger Identity and increments `automation_script_timer_runtime_fence_dropped_total`.
- Due candidates are selected in round-robin passes across complete stable schedule-instance identities and capped by `script.scheduler.max-catch-up-firings-per-observation`; this current per-observation behavior does not yet prove the accepted one-per-schedule-instance durable resume-window cap across repeated observations. `ObserveRuntimeTickProgress` reports updated rows, fired work items, and truncated candidates; timer-fired, catch-up-truncated, and runtime-fence metrics expose aggregate outcomes.
- Control-plane timer audit reads expose scheduler-owned `script_event_audit` rows, including plugin ownership, admitted routing, due-point coordinates, and skipped-versus-persisted outcomes. Plugin-owned definitions retain `pluginId`/`pluginVersionId`/`bindingId`, and materialization admits only the enabled runtime plugin version and resolved signed-bundle binding.
- The richer Redis leader/checkpoint model remains target-state.

## Target-State Design

The sections below define the target-state scheduler contract. Current behavior remains limited to the implementation facts listed in the dedicated status section above unless a bullet explicitly identifies a target-state requirement.

### Script Timers vs Tick Timers

Plugin timer admission carries the owner lifecycle fence as evidence separate from schedule identity: the stable schedule row carries the mutable current reconciled `(pluginActivationEpoch, lifecycleRevision)` pair, while each due candidate and firing claim captures the pair as immutable evidence; a new firing requires the exact current tuple. `DRAINING` cannot authorize a new firing; only same-version/same-epoch work whose winning admission CAS durably committed the immediately preceding `ENABLED` revision before the durable Automation-owned `DRAINING` admission barrier was created may retain it under ADR 0119. A revision change alone does not create a new candidate identity.

Every authored timer declares both its clock unit and recovery class. Tick/game time is the default for gameplay timers; wall clock must be explicit and is a scheduler-eligibility clock only. Timers remain layered on the authoritative runtime timeline, but not every deadline is a tick deadline:

- **Wall clock** timers use a persisted absolute due time such as `dueAt`; changing tick cadence does not rescale an already persisted deadline. `dueAt` remains only in internal durable scheduling, identity, seed, fencing, and audit metadata; it is excluded from DSL-visible trigger facts and gameplay inputs. Wall-clock eligibility enters the next canonical tick, and scripts can observe only that canonical tick/game-time context rather than a wall-clock value.
- **Tick/game time** timers use committed tick identifiers for eligibility and cadence; changing tick cadence changes the real-world duration of future intervals while preserving their game-time cadence.
- Time scaling is applied explicitly when a new duration or due point is calculated. A later cadence or time-scale change does not silently rewrite an already persisted due point.
- Recovery classes are:
  - **Correctness-bearing one-shot**: durable intent exists outside Redis before acknowledgement and converges to one logical execution or explicit terminal outcome; retries preserve identity.
  - **Durable recurring**: the schedule declares exactly one missed-occurrence policy, `SKIP_MISSED` or `COALESCE_ONE`. The latter may create at most one synthetic firing for the complete stable schedule-instance identity in one durable resume-window identity.
  - **Advisory or cosmetic**: missed occurrences may drop and the timer resumes with a future occurrence under its declared cadence.
- Redis timer indexes, due indexes, leader checkpoints, and wake-up hints are rebuildable coordination projections. Durable timer identity, due state, recovery policy, resume-window identity, and required terminal or skipped outcomes live outside Redis.
- A correctness-bearing one-shot must durably terminalize under its original identity with one of the accepted outcomes: `applied`, `canceled`, `superseded`, `expired`, or a feature-defined terminal outcome. A scheduler or worker crash may reclaim a fenced lease, but an inconclusive one-shot remains nonterminal; it must not be silently marked skipped or reminted under a newer scope.
- For timer catch-up, Automation owns one durable timer-recovery resume-window record per `<tenantId, gameInstanceId, playableStateScope, regionId, regionEpoch, isDryRun>`. Including `isDryRun` in this key keeps live and dry-run/test catch-up candidates in separate windows and caps. A durable compare-and-set creates or returns the one `OPEN` record; its `resumeWindowId` is `<tenantId, gameInstanceId, playableStateScope, regionId, regionEpoch, isDryRun, resumeGeneration>`. At creation, the record freezes recovery start and through observations, the effective numeric tenant-local cap, and the selection-policy revision that defines grouping, ordering, round-robin passes, and tie breaks; it also retains the authoritative `playableStateNamespaceId` as immutable non-identity scope evidence. Creation, reuse, retry, observation, and takeover revalidate the same `isDryRun` mode and namespace/binding evidence, then reuse the frozen cap and selection-policy revision unchanged. A policy or configured-cap change applies only to a later window allocated after this one reaches `COMPLETE`; it cannot alter selection or cap-excluded outcomes within the existing `resumeWindowId`. Missing or mismatched mode or namespace evidence fails closed and cannot be refreshed, inferred, or added to `resumeWindowId`. Leader, worker, takeover, and attempt IDs are not identity inputs; retries and takeovers reuse the same mode-specific `resumeWindowId`, and only a later recovery episode after completion allocates the next generation.
- An epoch transition atomically moves each prior epoch's `OPEN` resume window for each `isDryRun` mode out of `OPEN` before creating the corresponding new-epoch `OPEN` window; prior claims remain fenced and reconciled under their original epoch and resume-window identity and cannot enter the new window, as owned by [ADR 0072](./decisions/adr-0072-class-specific-timer-durability-and-recovery.md).
- `playableStateNamespaceId` is intentionally separate non-identity scope evidence, but a namespace transition is a new playable-state lifecycle under [ADR 0122](./decisions/adr-0122-stable-playable-state-namespaces-for-runtime-replacement.md). If target materialization were allowed to update or reuse the prior schedule row, due point, or `OPEN` resume window before fencing the old namespace, the canonical candidate identity could collide—especially when the replacement has the same due point—and uniqueness could suppress the target firing. Namespace transitions therefore use a retire-before-materialize fence, which takes precedence over ordinary playable-scope replacement ordering: one atomic durable operation, or a resumable idempotent operation under the same `controlPlaneRequestId`, first fences and retires/tombstones every prior-namespace schedule row, moves its mode-specific `OPEN` resume windows out of `OPEN`, and preserves prior due candidates, firing claims, and candidate audits with their immutable old namespace evidence and original identities for settlement. No target-namespace schedule row or `OPEN` window may be materialized until that retirement barrier is durable. Target rows then receive fresh due state (the next future tick boundary or a transition-seeded wall-clock due point), never the old due point; namespace remains excluded from candidate, firing-claim, and `scriptEventId` identity, and the fresh due point ensures a same-due-point replacement cannot be suppressed by prior uniqueness. A crash or ambiguous retry leaves target admission fenced until this same operation converges; prior evidence is never rewritten or refreshed.
- Missed firings are handled in a bounded, deterministic way:
  - `COALESCE_ONE` schedule instances may enqueue at most one synthetic firing for that complete stable schedule-instance identity within one `resumeWindowId` (and therefore one `isDryRun` mode); `SKIP_MISSED` schedule instances enqueue none. The window's frozen tenant-local cap and selection-policy revision govern every scan, retry, takeover, deterministic selection, and cap-excluded outcome across independent schedule instances within that same full runtime-scope-and-mode ID. Tenant-local identifies the window's tenant owner and does not create a tenant-wide pool, so another runtime scope cannot consume this window's cap. Excluded candidates are dropped rather than deferred as backlog.
  - Tenant-local catch-up selection is not shared scheduler admission. A selected candidate still passes through ADR 0166 tenant-first scheduling and the applicable tenant and cluster ceilings. Capacity denial there terminally skips that due candidate within the same `resumeWindowId`: a tenant-ceiling denial records candidate-audit `finalStage=ADMISSION`, `finalOutcome=tenant_budget_exceeded`, and `finalReason=tenant_budget_exceeded`; a cluster-ceiling denial records candidate-audit `finalStage=ADMISSION`, `finalOutcome=quota_denied`, and `finalReason=cluster_limit_reached`. Either denial consumes its deterministic catch-up selection slot, creates no firing claim, handler Trigger Identity, or `scriptEventId`, and is not deferred, retried, backfilled, or reminted as catch-up. The terminal candidate audit, advance of the recurring schedule's canonical due state to its next ordinary future occurrence, and resume-window denial outcome are one atomic owner transaction; when one storage transaction is unavailable, a resumable idempotent reconciliation keyed by `(scheduleCandidateId, resumeWindowId)` must complete all three before the denial is settled or the window can complete. A partial or crashed denial therefore remains fenced and cannot be rediscovered from the unchanged overdue due point. That durable denial counts toward resume-window completion and does not suppress the schedule's next ordinary future occurrence. For live candidates (`isDryRun=false`), emit `automation_script_skips_total` with `scope="tenant"` and `reason="tenant_budget_exceeded"` for a tenant-ceiling denial, or `automation_script_skips_total` with `scope="cluster"` and `reason="cluster_limit_reached"` for a cluster-ceiling denial, using every other required bounded label from [normative Table 4](./system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix). For dry-run/test candidates (`isDryRun=true`), neither live-only family is emitted: no dedicated test-only candidate-ceiling metric is currently defined, so the settled candidate audit and mode-specific resume-window outcome are the complete observability surface. The handler-scoped test families are not used because the denial occurs before handler materialization. These candidate-level outcomes do not invoke `ScriptTenantBudgetService` or increment `automation_script_tenant_budget_denied_total`; do not increment the catch-up-truncation family for either shared-admission denial. Retryable authority, reload, or reconciliation fences remain governed by the separate nonterminal candidate lifecycle below and are not capacity denials.
  - After a due candidate passes admission, and before enqueueing that firing, the scheduler must claim or insert a durable trigger-instance row keyed by an instance-aware uniqueness projection. For `triggerMode=CATCH_UP`, the firing claim uniqueness and comparison include `resumeWindowId`, and the candidate-audit record carries the same ID, so failover or duplicate consumers cannot create duplicate logical triggers or consume a later window's cap.

  - The projection must define the event-scope due-candidate identity, including `tenantId`, `gameInstanceId`, `playableStateScope`, mandatory `stableOwnerKind` and `stableOwnerId`, `regionId`, `regionEpoch`, `eventType`, `eventSchemaVersion`, the exact `scriptPatchVersion` and `scriptPinEpoch`, `isDryRun`, `scheduleDefinitionId`, the persisted due point (`dueTickId` or `dueAt`), and `triggerMode`; include `entityId` only when the schedule target scope is entity-scoped, and `resumeWindowId` for catch-up claims. Each durable row, candidate, claim, and candidate audit also retains and revalidates the authoritative `playableStateNamespaceId` as immutable non-identity scope evidence; it does not participate in `scheduleCandidateId`, firing-claim, `scriptEventId`, Trigger Identity, or Command-Handoff Identity derivation. A core-script schedule must carry its durable `scriptId`; a plugin-owned schedule must carry `pluginId`, `pluginVersionId`, its schedule-owned `bindingId`, and the captured `(pluginActivationEpoch, lifecycleRevision)` pair. `pluginActivationEpoch` is the tagged candidate/firing-claim field; `lifecycleRevision` is required non-identity fence evidence. Core-script candidates omit both plugin lifecycle fields. Missing applicable namespace, durable owner, provenance, or either plugin lifecycle field, or namespace evidence that mismatches the authoritative namespace/scope and active-instance/region binding, rejects the candidate before deriving `scheduleCandidateId`, the firing claim, or `scriptEventId`; a legacy or corrupt row missing any applicable required field is not a candidate: record one deterministic non-candidate schedule-reconciliation outcome keyed by the existing durable `scheduleInstanceId` (the natural key or surrogate row ID defined below) plus the originating `controlPlaneRequestId` from its pin operation or Automation runtime transition, with bounded missing-field reason codes; quarantine or tombstone it, create no `scheduleCandidateId`, `scriptEventId`, ingress audit, firing claim, or handler audit, and never replay it. A handler-only binding field not present on the schedule remains absent until handler resolution. The firing claim derives one event-scope `scriptEventId` from this complete due-candidate identity and propagates that ID unchanged into every resolved handler's full Trigger Identity. Globally unique schedule IDs do not replace runtime scope, exact pin tuple, explicit `isDryRun`, or timeline fencing.
  - Candidates denied by a permanent or declared-skip cadence, reload, version, or event-policy outcome before handler binding are terminally consumed; they are recorded as event-scope `scheduleCandidateId` audits with no firing claim or `scriptEventId` and are not replayed later. A transient retryable reload, reconciliation, or authority fence instead retains a durable due-candidate state/claim keyed by `scheduleCandidateId` and the canonical due point under its original exact tuple and captured `(pluginActivationEpoch, lifecycleRevision)` pair, when applicable, as fenced/nonterminal evidence; this transient state is not a terminal candidate audit and carries no `finalStage`, `finalOutcome`, firing claim, handler Trigger Identity, or `scriptEventId` while fenced. Same-epoch retries reuse the candidate identity only while its complete captured fence evidence remains current. A lifecycle-revision mismatch fences the candidate under its original captured pair; reconciliation never refreshes or rebinds that candidate evidence. Unavailable, contradictory, or ambiguous owner evidence keeps it nonterminal. Once authoritative evidence proves that the captured revision is displaced and the ADR 0119 pre-`DRAINING` admission exception cannot apply, reconciliation terminalizes the candidate once under its original identity; it advances or retires a recurring/advisory row's canonical due state in the same durable reconciliation before any later candidate is admitted, while a correctness-bearing one-shot retains its original durable intent until an explicit terminal outcome and is never reminted. `DRAINING` cannot create a new firing; only already-admitted same-version/same-epoch work with the pre-barrier winning admission/fence CAS remains eligible under ADR 0119. A displaced old scope, region epoch, exact pin tuple, or plugin activation epoch remains fenced under its original candidate identity and is never reused on the new timeline; target reconciliation derives a fresh candidate identity for the changed identity tuple before admission. The candidate ID is derived from the complete event-scope due-candidate identity: tenant/instance/playable scope, stable schedule-owned script/plugin/binding identity when present, region and region epoch, exact script patch and pin epoch, event type and schema version, explicit `isDryRun`, schedule definition, trigger mode, target selector when applicable, and, for plugin-owned schedules, the tagged captured `pluginActivationEpoch`, and, when `triggerMode=CATCH_UP`, `resumeWindowId`, and the tagged due point. A candidate that passes those gates creates at most one event-scope firing claim and deterministic event-scope `scriptEventId` for that due candidate, with the tagged plugin activation epoch included in that derivation, resolves handlers, and fans out zero or more handler work items, each with its own full Trigger Identity containing that same propagated ID; a pre-materialization handler quota denial is recorded per resolved handler with no handler work item, while an ordinary post-executor-claim `ScriptTenantBudgetService` denial records the existing handler identity and terminally cancels its already materialized work item before DSL evaluation.

  For plugin-owned candidates, the transient candidate state, reconciliation evidence, and retry/reload state retain the captured `(pluginActivationEpoch, lifecycleRevision)` pair. Reconciliation and retry revalidate both values against the current owner pair; `lifecycleRevision` is fence evidence only and is not added to `scheduleCandidateId`, firing-claim, or `scriptEventId` identity.

  Legacy-row migration is reconciliation evidence, not candidate recovery: retain the original `scheduleInstanceId` and source `controlPlaneRequestId`, record the bounded missing-field or migration reason, and never synthesize a missing activation epoch, lifecycle revision, due-candidate identity, or `scriptEventId`. Only a later validated target schedule reconciliation may create fresh state. Use `plugin_activation_epoch_mismatch` only when a present captured epoch differs from authoritative current epoch evidence; use `plugin_binding_mismatch` for a present plugin/lifecycle provenance mismatch, and `authority_unavailable`, `component_policy_unavailable`, or `signer_policy_unavailable` when the applicable evidence is unavailable or unverifiable.

Within that model:

- The Game Session Service owns authoritative tick progression and tick timers, as described in [Tick System and Runtime Design](./system-architecture-ticks.md).
- The Automation & Scripting Service owns script timers and intervals, which are scheduled against tick heartbeat information but do not own ticks themselves.
- Scheduler data structures such as `automation:timer:{tenantRegionTag}` are used to track when script timers should fire relative to tick progression. `{tenantRegionTag}` is the opaque shared-key-builder tag derived from the full `<tenantId, gameInstanceId, regionId>` scope; it is not a competing schedule identity. Durable script schedules and quotas live in the Automation & Scripting Service’s PostgreSQL schema, while Redis indexes are coordination structures that can be rebuilt or reset without changing which scripts should eventually run.

From the tick system’s perspective, script timers are a source of work that ultimately enters the tick scheduler. Every scheduler and timer source must declare immutable `lane` (`actor_action` or `passive_effect`) and bounded `cost_class` before admission, and must carry those fields unchanged through durable schedule state, firing claims, work items, retries, and recovery. Missing or changed values reject timer firing, admission, retry, or recovery rather than being inferred or reclassified. Under ADR 0051, `passive_effect` is bounded non-actor work governed by the passive lane’s budgets: status pulses, environmental changes, passive inbound or remote envelopes, actor-generated consequences, and retries of already-admitted passive effects. Root intentional player, AI, automation, movement, or other gameplay commands remain `actor_action`; a timer is `actor_action` when it makes an actor act. If a passive inbound envelope emits a gameplay command, that resulting command is `actor_action` and cannot grant another same-tick root action. The determinism rules in the DSL reference apply equally to timer-driven triggers, while lane selection and budgets remain owned by the tick contract.

#### Automation Command Admission (Target-State)

The target `EnqueueAutomationCommandIfAbsent` contract carries the complete applicable parent Trigger Identity and complete child Command-Handoff Identity (with `(automationDispatchId, commandOrdinal)` as only its final discriminator), the target runtime timeline and due point, immutable `lane` and bounded `cost_class` values, an immutable request digest, and the deterministic evaluated command descriptor/payload. The durable admission row uses the complete child Command-Handoff Identity for uniqueness, deduplication, and replay selection and stores the other values before any tick-queue mutation as immutable correlation and conflict/readback evidence. Duplicate admission is a replay/no-op only when the child key matches and all stored comparison evidence matches; any missing, changed, or contradictory value is a non-mutating validation rejection and must remain fenced. Field ownership and canonical replay rules remain in the [Command-Handoff Identity](./system-architecture-scripting-normative-contract-tables.md#command-handoff-identity-target-state) and [tick-effect idempotency](./system-architecture-transactions.md#tick-effects-are-at-least-once-idempotency-is-mandatory) contracts.

The complete identity, target timeline/due point, request digest, deterministic command descriptor/payload, lane, and cost class are part of every target conflict, request-digest, readback, retry, and recovery comparison. A readback or retry with any missing, changed, or contradictory value rejects and remains fenced; recovery preserves the originally admitted values rather than deriving new scheduling metadata. This contract is target-state and does not make the current live wire or durable rows claim these fields: the live `EnqueueAutomationCommandIfAbsent` boundary remains narrower and does not yet carry the full Trigger Identity, `commandOrdinal`, `lane`, or `cost_class`, so live enforcement and focused proof remain outstanding as tracked in [Automation and Scheduler Runtime](../project-management/implementation-tracking/automation-and-scheduler-runtime.md).

#### Timer Resume Rule (Normative)

When an explicitly preserved tick-aligned interval keeps a logical timer alive across a version transition, the scheduler must recalculate its next due point using the explicit rule below. The default transition is cancel-and-recreate; the formula does not itself grant continuity.

- Inputs:
  - `resumeTickId` = the latest committed tick known for the timer's region when scheduling resumes for the runtime scope.
  - `previousDueTickId` = the durable due point stored before pause or reconciliation.
  - `intervalTicks` = the preserved schedule cadence in ticks.
- Preconditions:
  - Apply the preserved-due-point formula only when the preserved row's `runtimeRegionId`, runtime scope (`gameInstanceId` and `playableStateScope`), and `runtimeRegionEpoch` match the resumed runtime's corresponding region, scope, and `regionEpoch`.
  - If the runtime region, runtime scope, or region epoch differs, fence the old due point and derive a new due point on the new timeline after the replacement/new-scope schedule entry is durable; do not feed the stale `previousDueTickId` into this formula.
- Rule:
  - `intervalTicks` must be a positive integer. A schedule with `intervalTicks <= 0` is invalid and must be rejected before any modulo or due-point calculation.
  - if `previousDueTickId >= resumeTickId`, keep `nextTick = previousDueTickId`;
  - otherwise calculate `remainder = (resumeTickId - previousDueTickId) % intervalTicks`; set `nextTick = resumeTickId` when `remainder = 0`, and permit exactly one firing at that boundary under the durable schedule-instance plus resume-window identity; otherwise set `nextTick = resumeTickId + intervalTicks - remainder`, the first cadence boundary strictly after resume.
- Consequences:
  - the scheduler resumes on the next valid cadence boundary at or after resume, never by replaying every missed firing from the paused window;
  - a preserved schedule may fire immediately after resume only when its next valid cadence boundary is exactly `resumeTickId`;
  - reload and rollback preservation and downtime recovery remain distinct behaviors. The resume rule governs preserved timers after a version transition on the same runtime region, scope, and epoch; a scope or epoch migration fences the old due point and starts from the new timeline. The declared recovery class and durable resume-window policy govern missed firings after scheduler downtime within the same logical schedule instance and version.
  - Reset, incompatible, or newly materialized replacement rows do not use this rule and start with fresh due state; a preserved wall-clock timer does not use the tick formula, and compatible continuity retains its persisted absolute `dueAt` and regenerates `nextRunAt`.

### End-to-End `onInterval` Timer Lifecycle

This section summarizes how a single `onInterval` timer behaves across normal operation, leader changes, and script reloads, and which Redis keys are authoritative at each step.

All durable timer identity and scheduler checkpoints must be instance-aware even when Redis keys are region-scoped for slotting and locality:

- `gameInstanceId` is a required part of timer identity, deterministic scheduler `scriptEventId` derivation, catch-up deduplication, and checkpoint projection state.
- If a Redis key name omits `gameInstanceId`, the stored timer or checkpoint payload must still include it, and rebuild logic must treat instance mismatches as corruption rather than as reusable timer state.
- Plugin timers must additionally carry `pluginId`, `pluginVersionId`, and `bindingId` in their durable identity so sibling bindings and plugin rollback, disablement, or revocation cannot cross-contaminate interval state.

#### Interval-Entry Identity and Due-Point Persistence

A durable interval has two identities that must not be conflated.

Stable schedule-instance row identity:

The stable durable row identity retains tenant, instance, playable-scope, stable-owner, definition, target-scope, and dry-run separation. Replaceable pin/provenance metadata remains on the row as mutable execution-fence evidence:

`<tenantId, gameInstanceId, playableStateScope, stableOwnerKind, stableOwnerId, isDryRun, scheduleDefinitionId, targetScopeType, targetScopeId>`

This row identity is distinct from the stable logical continuity key:

`{stableOwnerKind, stableOwnerId, scheduleDefinitionId, targetScopeType, targetScopeId}`

For a core script, `stableOwnerId` is the durable script identity. For a plugin, it is `pluginId`; `pluginVersionId` remains provenance and an execution fence, not continuity identity. `scriptPatchVersion` and `scriptPinEpoch` are exact pin metadata and execution-fence fields, not continuity identity.

- `scheduleInstanceId` is an immutable surrogate row-generation identity allocated idempotently under the materializing `controlPlaneRequestId`; it is not the stable logical continuity key. Within one `(tenantId, gameInstanceId, isDryRun)` runtime scope, the natural continuity key above identifies at most one admitting, non-tombstoned row. A compatible continuity transition retains the same `scheduleInstanceId`; a reset or incompatible transition that still has a replacement target allocates a fresh one. Immutable non-identity namespace evidence (`playableStateNamespaceId`), mutable pin/provenance metadata, mutable runtime-region metadata (`runtimeRegionId`, `runtimeRegionEpoch`), and due point remain outside both the continuity key and the surrogate identity. `playableStateNamespaceId` remains persisted and exact-matched with `playableStateScope` and the active-instance/region owner binding on materialization, readback, due-candidate creation, claim, retry, and reconciliation; it is never inferred or refreshed onto an existing row. `pluginVersionId`, `bindingId`, `scriptPatchVersion`, and `scriptPinEpoch` remain persisted on the row as exact provenance and execution-fence fields; `runtimeRegionId`, `runtimeRegionEpoch`, `nextDueTickId`/`nextDueAt`, and last-observed progress are schedule state. Ordinary matching heartbeat evidence may advance those mutable fields on the active generation, but a namespace or active-instance/region binding transition creates a replacement generation rather than rewriting that evidence in place.
- `scheduleDefinitionId` participates in the stable logical continuity key and is one component of the complete due-candidate/firing claim identity; it is never sufficient alone and does not replace that complete identity. `scriptPatchVersion` and `scriptPinEpoch` identify the exact Game Session pin under which the row may execute; plugin-owned entries additionally carry `pluginId`, `pluginVersionId`, and `bindingId`, and `isDryRun` separates test execution from live scheduling. Live durable interval entries persist `isDryRun=false`.
- `duePoint` is exactly one mutable persisted value: `dueTickId` for tick-aligned schedules or `dueAt` for wall-clock timers. `nextTick` and `nextRunAt` are projections of that stored due point, not substitutes for it.
- Each due candidate has at most one event-scope durable firing claim and one deterministic event-scope `scriptEventId`, keyed by the complete event-scope due-candidate identity defined above, including `scheduleDefinitionId`, `eventType`/`eventSchemaVersion`, the tagged captured `pluginActivationEpoch` for plugin-owned schedules, and, for catch-up claims and candidate audits, `resumeWindowId`. Same-epoch retries reuse that candidate identity; for plugin-owned schedules, a same-version disable/re-enable derives a fresh candidate identity from the newer `pluginActivationEpoch`. Core schedule transition identity changes only through the accepted exact patch/pin epoch contract; no separate core generation is implied. The claim and candidate audit persist/expose that same exact identity; handler-only identity fields are added only after resolution. Advancing the schedule due point must never rewrite a prior claim or mint a second ID.

Every durable schedule-instance row, resume window, due candidate, firing claim, candidate audit, and scheduler list/read output must persist and expose `isDryRun` as an identity dimension, `playableStateNamespaceId` as separate non-identity scope evidence, and `scriptPinEpoch` alongside `scriptPatchVersion`. Namespace evidence must exact-match the authoritative namespace/scope and active-instance/region owner binding at each materialization, claim, retry, and reconciliation boundary; missing or mismatched evidence fails closed without changing any canonical identity tuple. The pin epoch is exact execution/fence metadata and is deliberately excluded from the stable logical continuity key above. A same-version repin creates a new exact tuple: before Automation admission resumes, reconciliation may rewrite or retire only mutable schedule state. It must never rewrite an old-epoch firing claim or candidate/audit identity or outcome; pending claims may be fenced or terminal-marked when required while preserving their original exact tuples. Same-version repin retries must remain idempotent and replay-safe by reusing existing claim/candidate identities rather than duplicating them.

On every exact script pin selection change, including a same-patch/new-epoch repin, reconciliation moves each prior `OPEN` resume window (independently for each `isDryRun` mode) out of `OPEN` before target timer admission resumes. Existing firing claims and candidate/audit records retain their original mode-specific `resumeWindowId` and exact pin, remain fenced for settlement under those original identities, and cannot consume the next window's cap. Only after the new exact `(scriptPatchVersion, scriptPinEpoch)` and schedules reconcile may a still-required catch-up episode allocate the next `resumeGeneration` window for the candidate's mode; retries are idempotent under the reconciliation `controlPlaneRequestId`.

#### Normal Operation

The schedule-row requirement to persist and expose `scriptPinEpoch` alongside `scriptPatchVersion` is target state. The current live handoff/projection path does not yet persist and expose the complete pin-epoch contract, so this persistence and its proof remain implementation gaps. The artifact-estimate ordered-prefix reservation up to `AUTOMATION_TICK_BUDGET_MS` is likewise target-state scheduler behavior; the current runtime does not yet implement that reservation.

The interval admission, durable-claim, artifact-estimate reservation, and retry/deferral behavior described below is target-state unless explicitly identified as current. It must not be read as evidence that the current runtime already implements those guarantees; the current-state gaps above and in the quotas document remain authoritative.

- When an instance first observes an exact pinned tuple, Automation materializes the patch-owned schedules for that `(tenantId, gameInstanceId)` scope into durable `script_schedule_instances` rows keyed by the stable schedule-instance identity above, with plugin owner metadata and binding target identity. Each row stores the authoritative `playableStateNamespaceId` as immutable non-identity scope evidence, the exact `scriptPatchVersion` and `scriptPinEpoch`, `isDryRun`, `scheduleDefinitionId`, cadence, unit, scheduler priority tag, normalized schedule metadata hash, the initiating pin or runtime-transition `controlPlaneRequestId`, and exactly one mutable due-point field (`dueTickId` or `dueAt`). Missing or mismatched namespace evidence rejects materialization without creating or updating a row. For an initially materialized or reset wall-clock row with an absent durable `dueAt`, Automation derives it once from the transition's immutable seed plus the schedule's authored wall-clock cadence (`cadence`/`unit`) after any explicit time scaling. A Game Session pin or rollback uses Game Session `pinnedAt` bound to that pin request ID; a schedule-creating or resetting plugin activation/enable or other non-pin replacement instead uses an immutable Automation transition commit timestamp durably bound to that same `controlPlaneRequestId` (the runtime transition's committed `lastChangedAt` may supply the seed) and must never look up Game Session `pinnedAt` using a non-pin request ID. Automation persists and reuses that seed and derived `dueAt` across retries and reconciliation; projection refresh or observation time is diagnostic only. Disablement or revocation without a replacement tombstones the displaced row and creates no replacement row or fresh due point. Compatible continuity retains an existing `dueAt`; ordinary reload or repin does not overwrite it except through the transition branch below, while reset, incompatible, or newly materialized replacement rows receive fresh due state. Tick-aligned schedules remain persisted but `PENDING_RUNTIME_PROGRESS` until Game Session's `ObserveRuntimeTickProgress` input supplies the current runtime region epoch and tick id from Game Session's durable runtime ownership row. At that point Automation exact-matches the stored namespace/scope evidence with current owner scope, records the runtime region fields, and derives the first future `dueTickId` as `observedTickId + cadenceValue`; later observations that reach or pass it revalidate the complete namespace/scope and active-instance/region binding before admitting the due candidate, creating at most one event-scope firing claim, and deriving one deterministic event-scope `scriptEventId` for that due candidate, then use the same durable work-item, audit, and queue projection path as other admitted script events. Plugin-owned schedules are materialized only for the plugin version currently enabled in Automation's runtime registry for that instance; other published or displaced plugin versions must not keep durable schedule ownership. Region-scoped Redis indexes such as `automation:timer:{tenantRegionTag}` remain a derived coordination layer above those durable rows rather than the first source of schedule identity.
- Leaders track these interval entries alongside other automation timers using bounded scans. Event scope applies cadence, reload, version, and event-policy gates, then creates at most one event-scope firing claim and one event-scope `scriptEventId` per due candidate before resolving handlers. Handlers admitted by all pre-materialization handler-scoped gates, including quota, become durable queued work, each with its own full Trigger Identity containing that same propagated ID; every resolved handler still receives an audit row, while a handler denied by a pre-materialization handler-scoped gate receives no work item, queue projection, lease, or execution marker. The later execution scheduler considers queued handler work in canonical order and reserves the artifact-estimate ordered prefix up to `AUTOMATION_TICK_BUDGET_MS`, leaving the remainder durably queued/deferred under unchanged handler identity. An ordinary post-executor-claim `ScriptTenantBudgetService` denial instead acts on an existing durable work item, terminally cancels it before DSL evaluation, and follows the handler-level budget outcome route. The reservation is not actual execution time, a per-run timeout, or a lease debit; actual runtime never changes the selected prefix or creates a same-tick refund, and the quota owner separately governs fenced capacity lease acquisition and recovery.
  - When an interval becomes due, the scheduler derives a deterministic `scheduleCandidateId` from the complete event-scope due-candidate identity defined above, including the captured `pluginActivationEpoch` for plugin-owned schedules. It applies cadence, reload, version, and event-policy gates at event scope before handler binding. A permanent or declared-skip gate failure is durably consumed with its `scheduleCandidateId`-keyed audit outcome: advance the canonical due point according to the cadence, or quarantine/tombstone the schedule when safe advancement is impossible; it creates no firing claim or `scriptEventId`. A transient retryable reload, reconciliation, or authority fence instead retains a durable due-candidate state/claim keyed by `scheduleCandidateId` and the canonical due point under its original exact tuple and captured `(pluginActivationEpoch, lifecycleRevision)` pair, when applicable, as fenced/nonterminal evidence without creating a firing claim or `scriptEventId`; this transient state is not a terminal candidate audit and carries no `finalStage` or `finalOutcome` while fenced. It may retry the same candidate only while the captured lifecycle pair remains current and after the exact pin tuple, runtime scope, and owner evidence reconcile, then compare-and-set once into the one firing path or one immutable terminal candidate audit. A displaced old scope, epoch, or plugin activation epoch remains fenced under its original candidate identity and is never reused; a plugin-owned same-version disable/re-enable derives a fresh candidate identity from the newer `pluginActivationEpoch` before admission. Core schedule transition identity changes only through the accepted exact patch/pin epoch contract. Once the candidate passes those event gates, the scheduler creates at most one event-scope durable firing claim and one event-scope `scriptEventId`, resolves handlers, and applies all pre-materialization handler-scoped gates. Handlers admitted by those gates, including quota, create durable queued work, each with its own full Trigger Identity containing that same propagated ID; every resolved handler receives an audit row, while a handler denied by a pre-materialization handler-scoped gate, including quota denial as `ADMISSION/quota_denied`, creates no work item, queue projection, lease, or execution marker. An ordinary post-executor-claim `ScriptTenantBudgetService` denial instead terminally cancels the already materialized and claimed handler work item before DSL evaluation with `ADMISSION/tenant_budget_exceeded`; it is not a pre-materialization denial. Before `EVALUATED_COMMITTED`, a failed handler evaluation may retry under that same full Trigger Identity and same propagated `scriptEventId` only for a retryable infrastructure or fencing failure; deterministic logical, validation, and sandbox outcomes are final. After the boundary, recovery replays its durable descriptors without re-entering the DSL. The later execution scheduler applies the artifact-estimate ordered-prefix reservation to queued handler work and defers the remainder without changing identity.

  An admitted firing must use one crash-safe durable transition. The transition atomically creates or claims the firing, records one handler-scoped `script_event_audit` row for every resolved handler's pre-materialization admission outcome, including quota-denied handlers with `finalOutcome=quota_denied`, persists work items and rebuildable `automation:queue:*` projections only for handlers admitted by all pre-materialization handler-scoped gates, including quota, and advances the canonical due point. Leases and execution-start markers remain later execution-stage artifacts; an ordinary post-executor-claim `ScriptTenantBudgetService` denial is handled against the existing claimed work item and is not part of this pre-materialization transition. If the storage boundary cannot provide one transaction, it must persist a resumable idempotent reconciliation keyed by the firing claim and `scheduleCandidateId`; recovery must link or complete every missing audit, work-item, queue-projection, and due-point update before the firing is considered committed, without re-running the DSL or minting a second `scriptEventId`. This admission transition creates no `automationDispatchId` or command-child identity; dispatch identity is allocated only by a later winning evaluated-descriptor/outbox commit when evaluation emits commands. A crash may leave the operation resumable, but must not leave a durable claim that can be rediscovered as new work or a due point advanced without the corresponding durable handler outcomes and admitted work evidence.

#### Leader Changes

- Leaders advance a per-region notion of time by consuming the tick heartbeat stream and tracking how far they have progressed. In addition to the current heartbeat `(tenantId, gameInstanceId, regionId, regionEpoch, tickId)`, schedulers maintain a derived discovery hint such as `script-scheduler:{tenantRegionTag}:lastTickId`. The opaque `{tenantRegionTag}` physically carries the full `<tenantId, gameInstanceId, regionId>` scope, while the payload stores `regionEpoch` and `latestTickId`. Consumers must compare the stored epoch with the authoritative current epoch before reusing the progress value. The separate per-consumer `tick-events-offset:{tenantRegionTag}:<consumerId>` record is the sole owner of that consumer's `streamOffset`.
- When leadership changes, the new leader:
  - reads the scheduler hint and canonical event-offset record for the current `regionEpoch`;
  - rejects either value when its stored `regionEpoch` does not match the current heartbeat/status epoch. It must not walk old-epoch ticks, reuse an old stream offset, or reuse old-epoch due points. The mismatch is recorded in scheduler audit with `reason=checkpoint_region_epoch_mismatch`; this stale coordination projection does not drop or terminalize a due point and does not increment `automation_script_timer_runtime_fence_dropped_total`;
  - discards each stale value, rebuilds the current-epoch scheduler hint and event-offset record from the authoritative durable status/heartbeat, and then reconciles durable due points under the bounded catch-up policy; and
  - enumerates the authoritative PostgreSQL `script_schedule_instances` rows for the current runtime scope to determine which current-epoch "every N ticks" boundaries were crossed during the gap. The Redis region index `automation:timer:{tenantRegionTag}` may accelerate this scan, but it is rebuildable and must not be the source of truth; if it is missing or stale, rebuild it from the durable rows before admitting candidates. It obtains or creates the one `OPEN` durable resume-window record for the candidate's `isDryRun` mode by CAS, freezes that record's recovery start and through observations, and admits each due candidate before claiming or inserting a durable firing claim. Every firing-claim insert, lookup, and conflict comparison uses the complete event-scope due-candidate identity defined above, including the exact pin tuple, event/schema, explicit `isDryRun`, trigger mode, applicable target selector, schedule definition, tagged due point, and `resumeWindowId` for catch-up; only then may it enqueue an `onInterval` trigger.
  - Each `COALESCE_ONE` schedule instance may enqueue at most one missed `onInterval` trigger before normal scheduling resumes; `SKIP_MISSED` schedule instances enqueue none. `SCRIPT_TIMER_CATCH_UP_MAX_FIRINGS_PER_RESUME` is evaluated as a tenant-local cap across complete stable schedule-instance identities within one durable, mode-specific `resumeWindowId`; the cap's boundary is that ID's full runtime scope and `isDryRun` mode, while tenant-local identifies the window's tenant owner rather than a tenant-wide pool. Live and dry-run/test windows apply the cap independently, and a schedule in another game instance, playable-state scope, region, or epoch cannot consume this window's cap. Candidates beyond this cap are dropped, not deferred, and surfaced through candidate audit plus exactly one `automation_script_timer_catchup_truncated_total{reason="resume_window_cap"}` increment when each candidate's durable settlement completes; they create no firing claim or firing. The window is marked `COMPLETE` only after selected candidates' firing or durable shared-admission-denial outcomes and all cap-excluded candidate outcomes are durable; only a later recovery episode then allocates the next generation. These are target-state recovery guarantees; the current runtime's bounded per-observation catch-up does not yet prove the durable resume-window enforcement described here.
- Leader changes and takeover reconciliation preserve each firing's declared lane and cost class and validate the current runtime epoch/fence before admitting it; stale or ambiguous claims are fenced and reconciled rather than reclassified or replayed as new work.
- Catch-up truncation must use one stable fairness algorithm when due candidates exceed `SCRIPT_TIMER_CATCH_UP_MAX_FIRINGS_PER_RESUME`:
  - Collapse each overdue schedule instance to its earliest missed tagged due point in its declared clock domain (`dueTickId` for tick/game time or `dueAt` for wall clock). Do not numerically compare tick IDs with wall-clock timestamps. Because each `resumeWindowId` is already scoped to one `<tenantId, gameInstanceId, playableStateScope, regionId, regionEpoch, isDryRun>` record, this cap is evaluated only within that full runtime-scope-and-mode window: tenant-local identifies its tenant owner and does not make it a tenant-wide pool, so candidates from another game instance, playable-state scope, region, or epoch never join this set. It is mode-isolated and does not arbitrate across tenants. Within that window's candidate set, order by bounded `priorityTag` (`high`, `normal`, `background`), then complete stable schedule-instance identity ASC.
  - Admit catch-up firings in round-robin passes across distinct complete stable schedule-instance identities within that resume-window candidate set (the stable row identity defined above, including target scope and `isDryRun`), not merely `scheduleDefinitionId`, so independently materialized instances sharing one definition each receive an opportunity and one noisy instance cannot consume the entire resume window. `pluginVersionId` and `bindingId` remain due-candidate provenance, fence, and deduplication dimensions; they do not split stable fairness groups. Priority and every tie break retain stable schedule-instance identity ordering. Candidates admitted by tenant-local catch-up still enter the shared scheduler/cluster admission layer, where [ADR 0166](./decisions/adr-0166-attributable-script-breakers-and-tenant-first-fairness.md) tenant-first fairness precedes priority; catch-up cannot bypass per-tenant or cluster ceilings.
  - Admit at most one missed firing for any logical schedule instance in the complete `resumeWindowId`, using its earliest missed tagged due point as the coalesced identity.
  - Once the resume cap is reached, remaining overdue firings are truncated rather than deferred into an unbounded backlog; emit audit/metrics that distinguish how many were coalesced or dropped.
- If a per-script index is used, it is reconciled against the region index as needed; discrepancies are treated as projection bugs and corrected, not as new timers.
- Because the authoritative schedule configuration lives in PostgreSQL and Redis holds only coordination state (timer indexes and checkpoints), leader changes do not reset cadences; they only introduce a bounded delay before the new leader catches up.

#### Script Reload

- During reload, leaders set `reloadState=RELOADING` for the affected runtime scope after observing that Game Session has pinned a tenant-`READY` patch for that instance. `onLoad` is not part of this instance reload path; it has already completed as part of tenant patch readiness. Existing timer entries in the region index `automation:timer:{tenantRegionTag}` and any derived per-script projections remain in Redis but are treated as pending until reconciliation completes.
- Once the exact Game Session `(scriptPatchVersion, scriptPinEpoch)` is committed and reconciliation succeeds, the leader:
  - re-reads its heartbeat checkpoint and the current `tickId`;
  - reconciles durable schedule definitions for the newly pinned exact `(scriptPatchVersion, scriptPinEpoch)` tuple before any timer is allowed to fire again, updating the instance-scoped `script_schedule_instances` rows first;
  - updates each explicitly preserved interval entry's authoritative due point (`dueTickId` or `dueAt`) after typed continuity compatibility checks: it applies the normative tick resume formula only to preserved tick timers, while compatible wall-clock continuity retains persisted `dueAt` and regenerates `nextRunAt`; reset, incompatible, or newly materialized replacement rows retain fresh due state; and
  - resumes normal scheduling for `onInterval` using the exact committed patch and pin epoch. No interval runs against a partially loaded script definition or a local active/latest pointer.
- If reload fails or durable reconciliation evidence is unavailable, the pending exact `(scriptPatchVersion, scriptPinEpoch)` tuple is retained with failed/fenced diagnostic state and any partially loaded schedule state is discarded. The affected runtime scope admits no new timer firing until reconciliation confirms the current exact pin tuple, schedule owner, scope, epoch, due state, and, for plugin-owned schedules, the captured `(pluginActivationEpoch, lifecycleRevision)` pair. Transient retryable reload, reconciliation, or authority-fence conditions retain each due candidate as durable nonterminal state/claim under the same `scheduleCandidateId` and canonical due point from the original exact tuple; while fenced, that state has no `finalStage`, `finalOutcome`, firing claim, or `scriptEventId`. If the captured exact tuple remains current when evidence reconciles, the same state may compare-and-set once into the firing path or one immutable terminal candidate audit; a lifecycle-revision mismatch fences that candidate under its captured pair, and reconciliation never refreshes or rebinds its historical evidence. `DRAINING` permits this only for already-admitted work whose winning admission/fence CAS committed before the durable drain barrier; a merely fenced candidate without that proof cannot create a firing. Only a changed identity tuple—such as patch, pin epoch, runtime region epoch, or `pluginActivationEpoch` (including a same-version plugin disable/re-enable)—displaces the old candidate, which remains fenced under its original identity and captured lifecycle pair (and may be terminal-marked as required), while target reconciliation derives a fresh, non-reused candidate identity only after durable reconciliation and before admission. Explicit continuity may carry stable schedule-row/due state but never rewrites candidate identity, and no `scriptEventId` is minted before the target candidate passes admission. A prior observed tuple may remain observable for diagnosis, but the scheduler must not use a "last known good" fallback to mint or execute new timer work.

During reload, plugin-owned due candidates retain and revalidate the captured `(pluginActivationEpoch, lifecycleRevision)` pair alongside the exact script pin and runtime scope. A same-version/same-epoch `DRAINING` predecessor is usable only with ADR 0119's durable pre-`DRAINING` admission-CAS evidence; lifecycle revision remains non-identity evidence and does not authorize a new candidate.

### Explicit Continuity Across Script Transitions

The default for an authored interval at a script-patch, plugin-version, activation, disablement, rollback, or repin transition is cancel-and-recreate. Continuity is an explicit opt-in on both sides of the transition, keyed by `{stableOwnerKind, stableOwnerId, scheduleDefinitionId, targetScopeType, targetScopeId}` and accepted only after typed interval/cadence/target compatibility checks. `pluginId` is the stable plugin owner; `pluginVersionId` and `scriptPatchVersion` remain exact provenance and execution-fence metadata. One-shot timers are outside this rule and must not be silently migrated or recreated because a `scheduleDefinitionId` matches. The full recovery clock and downtime contract remains in [ADR 0091](./decisions/adr-0091-class-specific-script-timer-clocks-and-recovery.md).

Timer reconciliation on patch or plugin change is a required part of reload and rollback safety:

For plugin-owned schedules, the stable schedule row carries the mutable current reconciled lifecycle pair for its current owner; due candidates, firing claims, candidate audits, and timer-derived work retain the captured owner `lifecycleRevision` alongside `pluginActivationEpoch` as immutable fence evidence. Before a new firing or handler admission, the scheduler must compare the exact current `(pluginActivationEpoch, lifecycleRevision)` and require the current revision under `ENABLED`; a same-version/same-epoch `DRAINING` predecessor exception is reserved only for work carrying the exact immediately preceding `ENABLED` revision whose winning admission CAS durably committed it before the durable Automation-owned `DRAINING` admission barrier was created. Capture or observation alone, an arbitrary lower or non-predecessor revision, a changed plugin version or activation epoch, a post-barrier admission CAS, or unavailable/contradictory evidence fails closed. A lifecycle-revision mismatch fences the existing candidate and firing claim under their captured evidence; reconciliation never refreshes or rebinds historical or candidate evidence. Only an epoch-advancing or other identity-tuple change displaces work, and non-executable transitions keep the original identity fenced rather than minting a replacement.

- Durable timer execution and firing identities must carry the exact schedule pin that created them, including `scriptPatchVersion`, `scriptPinEpoch`, and, for plugin-owned schedules, `pluginId`, `pluginVersionId`, and `bindingId`; the stable schedule row must not be keyed just by entity and cadence or by those mutable pin/provenance fields.
- The stable plugin-owned schedule row carries the mutable current reconciled `(pluginActivationEpoch, lifecycleRevision)` pair for its current owner; due candidates, firing claims, candidate audits, and timer-derived work capture the immutable pair as execution-fence evidence. Revalidate both values against that current pair before timer firing or handler admission and at later evaluation, persistence, handoff, staging/final-effect, retry, replay, and recovery boundaries as required by [Scripting Contracts](./system-architecture-scripting-contracts.md#8-plugin-version-fencing-and-control-plane-scope). The pair is not part of stable schedule-row or continuity identity. For plugin-owned due candidates, only the captured `pluginActivationEpoch` is a tagged input to candidate/firing identity so same-epoch retries reuse `scheduleCandidateId` while an epoch transition fences old records under their original evidence and derives a fresh candidate identity; `lifecycleRevision` travels alongside it as non-identity evidence and remains separate from handler Trigger Identity and Command-Handoff Identity. When that transition displaces a due candidate, including a same-version plugin disable/re-enable, the old candidate remains fenced under its captured pair and target reconciliation derives a fresh, non-reused candidate before admission.
- Every compiled timer or interval definition must carry a stable `scheduleDefinitionId` generated by the Game Design compilation pipeline and persisted with the schedule metadata. This identifier represents one logical schedule definition within a patch or plugin version.
- A patch or plugin version must not contain duplicate `scheduleDefinitionId` values within the same owning scope; compilation and publish must fail deterministically if duplicates are present. Materialization through sibling bindings must also remain unique for each complete target-scope schedule identity; an ambiguous duplicate is rejected before it can share row or due-point state. `bindingId` remains compatibility and fencing metadata rather than changing ADR 0110's stable continuity key.
- Implementations must persist a `scheduleSemanticsHash` or equivalent canonical normalized fingerprint with each compiled definition as diagnostic evidence. Hash equality cannot grant continuity and hash inequality alone cannot deny an otherwise valid explicit declaration.
- When an instance observes a newly pinned exact `(scriptPatchVersion, scriptPinEpoch)` tuple, the scheduler must compare the durable schedules for the previously observed tuple with those for the newly pinned tuple before resuming timer admission. Plugin activation, disablement, rollback, and revocation perform the same comparison for `(pluginId, pluginVersionId, bindingId)`.
- Schedules that do not exist in the newly pinned patch must be tombstoned so they can no longer generate triggers. When there is no replacement owner, disablement or revocation must fence admission and tombstone the displaced row atomically under the same control-plane operation; it must not fabricate a replacement schedule.
- For the default or incompatible path, a patch, plugin-version, activation, disablement, rollback, or repin transition uses cancel-and-recreate: when a replacement owner exists, reconciliation creates or confirms the target schedule generation with fresh due state before retiring or tombstoning the displaced row; when no replacement owner exists, it fences and tombstones the displaced row without fabricating a replacement. Continuity is preserved only when both source and target explicitly declare compatible continuity for the same stable logical key `{stableOwnerKind, stableOwnerId, scheduleDefinitionId, targetScopeType, targetScopeId}`, `source.isDryRun` equals `target.isDryRun`, and interval kind, cadence unit/value, target binding, playable-state scope, and runtime fencing are compatible, with exact equality of the authoritative `playableStateNamespaceId` and active-instance/region binding (including `gameInstanceId`, `regionId`, and `regionEpoch`); an ordinary executor-fence handoff that preserves that instance/region binding is not itself a transition. A namespace or active-instance/region binding transition is therefore incompatible with in-place continuity and routes to a fresh `scheduleInstanceId` under the applicable reset ordering. Namespace transitions follow the retire-before-materialize barrier above; other replacement-owner resets may prepare a fresh non-admitting generation before the atomic retirement/activation step below. Only when all continuity conditions hold is the existing generation updated in place with the target ownership/pin metadata and recalculated due point. A missing declaration, dry-run mode mismatch, changed key/cadence/target, explicit reset, absent target, disabled/revoked owner, namespace or active-instance/region binding mismatch, or ambiguity forces the reset path. A same-version repin is still a new epoch transition: for a continuity-preserved row, reconciliation adopts the target exact `(scriptPatchVersion, scriptPinEpoch)` and associated mutable current pin/owner/provenance metadata on the active row before admission resumes; for the reset path, it creates or confirms the target row with that exact metadata before retiring the displaced row. Only the active row and pending mutable schedule state may be retired or rewritten; old-epoch firing claims and candidate/audit identities and outcomes retain their original tuple and may only be fenced or terminal-marked, never rewritten. Rollback follows the same rule and never infers continuity from history or hash similarity.
- `controlPlaneRequestId` is the reconciliation idempotency key. The same nonblank value from the initiating patch pin, plugin activation, disable, rollback, or signer-revocation request must be persisted on and carried through every schedule-reconciliation step, including preserved-schedule updates, reset replacement, retirement, and retry; a sub-step must not mint a new reconciliation key.
- When explicit continuity is valid, reconciliation updates the existing stable row in place, adopting the exact target `(scriptPatchVersion, scriptPinEpoch)` and associated mutable current pin/owner/provenance metadata before admission resumes, while retaining immutable namespace evidence, and branches due-point recalculation by clock unit: preserved tick timers use the normative tick resume formula, while compatible wall-clock timers retain persisted `dueAt` and regenerate `nextRunAt` strictly as its projection. Target resume time does not alter the persisted deadline, and any wall-clock overdue state remains governed by its declared recovery/catch-up policy. Both branches retain the exact target metadata and reconciliation idempotency under `controlPlaneRequestId`; the tick branch must not retain an overdue point, neither branch restarts from deployment time nor replays every missed interval. The in-place update must be atomic or a resumable idempotent operation keyed by `controlPlaneRequestId`; it creates no replacement row, tombstone, firing claim, or `scriptEventId`. Previously captured candidate, firing-claim, audit, and work evidence remains immutable under its original tuple and identity; the scheduler mints firing claims and `scriptEventId` only after a due candidate passes admission.
- For the reset or incompatible path when a replacement owner exists, replacement-before-retirement applies to plugin activation, repin, rollback, region/epoch changes, and other transitions except the namespace barrier above: reconciliation creates or confirms a fresh target `scheduleInstanceId` in a non-admitting prepared state with the target owner/binding and fresh due state, then one atomic durable transition, or resumable idempotent operation under the same `controlPlaneRequestId`, retires the displaced generation and makes the target the sole admitting row for its natural continuity key. The active-row uniqueness rule therefore never permits two generations to admit, and a prepared target cannot mint a candidate, firing claim, or `scriptEventId`. Namespace changes instead retire the source before any target row is materialized as required above. Disablement or signer revocation without a replacement fences admission and atomically tombstones the displaced row under the same `controlPlaneRequestId`.
- Canceling outbox work items alone is insufficient for rollback safety; old-version timer schedules must also be reconciled so they cannot mint new `scriptEventId` values after the version has been displaced.

Plugin example:

- If plugin version `combat-helper@v4` and `combat-helper@v5` both compile a "reapply guard aura every 20 ticks" timer with `scheduleDefinitionId=combat-helper.guard-aura.v1`, explicit compatible continuity updates the existing stable schedule row from `v4` to `v5` ownership/pin metadata in place and recalculates its next due point before scheduling resumes; it does not create a replacement row. If continuity is absent or incompatible, the default reset path instead creates or confirms `v5` before retiring `v4`. The `v5` entry receives a firing claim and `scriptEventId` only after a due candidate passes admission.
- If `combat-helper@v5` replaces that timer with a different logical schedule such as "pulse only while threat > 0" compiled to a different `scheduleDefinitionId`, reconciliation must create the new timer for `v5` before retiring the old `v4` timer under the same atomic-or-resumable rule.

Under this model, durable script schedules, quotas, and firing-claim de-duplication live in PostgreSQL, while `automation:timer:{tenantRegionTag}`, `script-scheduler:{tenantRegionTag}:lastTickId`, and related coordination keys form a reset-tolerant coordination layer for interval state. Stored entries and reconciliation logic remain instance-aware even though the Redis keys are region-scoped for slotting. The combination of tick heartbeat, durable firing claims, epoch-validated checkpoints, and script patch versioning preserves both correctness and determinism across failures and leader changes: losing or resetting these Redis keys may delay or slightly reshuffle timer firings within the tail-loss envelope but must not change which scripts are eventually scheduled according to their stored configurations or cause duplicate logical trigger creation.

### Scheduler Leadership & Coordination

Scheduler leadership and coordination ensure that script timers and Automation-owned scheduling windows are processed safely in a distributed environment:

- Leadership must remain explicit and bounded, but the canonical design does not currently require a separate first-class `script-leader:*` Redis prefix. Scheduler ownership should instead be documented through the same runtime and coordination surfaces used by the Redis and automation docs unless a later design update introduces a dedicated lease family.
- Only the current leader for a runtime scope processes that scope’s script timers and automation queues. Implementations may lease by tenant for operational simplicity only if the leased worker still preserves per-instance isolation in its timer, queue, and reload state.
- Automation scheduling coordinates with tick heartbeat streams to ensure that:
  - `onInterval` triggers fire on the correct tick boundaries;
  - per-tenant and per-script quotas are respected; and
  - work is sharded in a way that keeps multi-key operations hash-tag-local.

See [Tick System and Runtime Design](./system-architecture-ticks.md) and [`automation-scripting-service/README.md`](./microservices/automation-scripting-service/README.md) for the current leadership and sharding model.

### Hot Reload & Resume Behavior

- Scripts are versioned and published via the Game Design Service; the Game Session Service pins an exact `(scriptPatchVersion, scriptPinEpoch)` tuple per game.
- When a new script patch is published, the Automation & Scripting Service:
  - ingests the new definitions and validates them for tenant readiness;
  - runs tenant-scoped `onLoad` handlers while the patch is still in `PENDING_VALIDATION` / `ONLOAD_RUNNING`;
  - marks the patch `READY` or `FAILED` for the tenant; and only then
  - uses instance-scoped reload state (for example, `reloadState=RELOADING`) when a running game pins that already-`READY` patch.
- During reloads, triggers are paused or skipped while in-flight runs drain under existing concurrency settings:
  - New triggers for the affected runtime scope are not admitted; attempts to schedule additional runs receive explicit backpressure outcomes (`skipped_reloading` during `RELOADING`, `rollback_paused` during rollback pause). For a low-rate runtime event denied before handler resolution by rollback pause, ingress records `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_BACKPRESSURE_ROLLBACK` and `admissionReason=rollback_pause` in `script_event_ingress_audit`; this is an event-scope outcome, not a handler `finalOutcome`. While that event-scope claim remains `IN_PROGRESS`, a concurrent retry may wait for the same claim to finalize or receive a retryable transport/application signal without an admission result; recovery resumes the same claim under fencing. Once finalized, a retry with the same event-scope identity replays permanent denials and successful final results exactly; an explicitly retryable transient backpressure denial stores retry eligibility and hint, and after that window the same identity may atomically reclaim and reopen the fenced claim for a new admission attempt, retaining the same `scriptEventId` and event identity. Once a handler has resolved, retries of that handler use its same full Trigger Identity and the same propagated `scriptEventId`; no separate handler ID is minted. A pre-handler `FAILED` reload is different: ingress records `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE` and `admissionReason=reload_failed` with no retry hint, while timer candidates use the terminal `reloadState=FAILED` candidate-audit behavior in [Table 3](./system-architecture-scripting-normative-contract-tables.md#table-3-timer-semantics-matrix), with no firing claim or `scriptEventId` until durable recovery returns the scope to `IDLE`. Resolved-handler failures continue to use `finalOutcome` in `script_event_audit`.
  - In-flight runs remain bounded by each script’s configured `maxConcurrent` and `concurrencyPolicy` (for example, `queue_until_free`); any short per-script waiting queues are allowed to drain, but no new entries are added while `reloadState=RELOADING`.
  - Pending timer-based triggers that became due during a transient retryable reload, reconciliation, or authority fence retain a durable due-candidate state/claim keyed by `scheduleCandidateId` and the canonical due point under the original exact tuple; scheduler timer indexes remain only rebuildable projections until exact version, epoch, and runtime-scope reconciliation completes. While fenced, this transient state has no `finalStage`, `finalOutcome`, firing claim, handler identity, or `scriptEventId`. If the captured exact tuple remains current when evidence reconciles, that state may compare-and-set once into the one firing path or one immutable terminal candidate audit; if a patch, plugin, or pin-epoch transition displaces the tuple, the old candidate remains fenced under its original identity (and may be terminal-marked as required), while the target schedule derives a new candidate identity only after durable reconciliation. Explicit continuity may carry stable schedule-row/due state but never rewrites candidate identity; the target candidate creates its firing claim and `scriptEventId` only after admission. Permanent or declared skips consume/drop their candidate under the declared policy, and an old scope or epoch remains fenced and is never reused.
- On success, the scheduler observes the newly committed Game Session `(scriptPatchVersion, scriptPinEpoch)` for future triggers; on failure:
  - `activePatchVersion` remains an observed diagnostic value, but it does not authorize new timer work while reconciliation is unresolved;
  - the pending exact `(scriptPatchVersion, scriptPinEpoch)` tuple is marked failed/fenced along with an error reason, and leaders discard any partially loaded state for that tuple;
  - Ordinary pre-handler ingress referencing a failed or unknown patch, or a scope whose reconciliation evidence is stale, is rejected in `script_event_ingress_audit` with `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE` and the applicable `admissionReason`; it does not receive a handler `finalOutcome`. Timer due candidates under the same condition follow the transient/permanent split: a transient retryable condition retains nonterminal due-candidate state/claim under its `scheduleCandidateId` and canonical due point, while only a permanent or declared-skip outcome is recorded in candidate audit; neither path creates a firing claim or `scriptEventId` before exact admission. Only a resolved handler records `finalOutcome=version_unavailable` (or another applicable fail-closed outcome, with specific cause in `finalReason`) in `script_event_audit`; metrics such as `automation_script_triggers_dropped_total{reason="version_unavailable"}` must not change that stage split.

- New timer admissions select the exact currently pinned `(scriptPatchVersion, scriptPinEpoch)` for the game; work already admitted under a prior tuple retains its sealed exact tuple for retries and replays, and a stale apply is fenced and reconciled rather than applied.
- Older script versions remain in the Automation & Scripting Service database for auditing and potential rollback. A prior observed/local version is diagnostic evidence only and cannot authorize new admissions or mint new work.
