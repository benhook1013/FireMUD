# ADR 0031: Revocation-Safe Session-Token Rotation And Logout

## Status

Accepted

## Implementation Status

There is no complete periodic rotation or generation-bound refresh path. The role-refresh service is a placeholder, gameplay session state does not yet implement the complete token metadata and atomic replacement contract, and Account logout/logout-all authority-generation workflows are absent.

## Context

A gameplay connection may remain active longer than the private `game-session-account-delegation` JWT that Game Session uses for Account calls. Without planned rotation, healthy long-running sessions fail at token expiry. A refresh surface that trusts only Game Session's workload identity can create the opposite problem: logout-all, password reset, security lock, or membership revocation may invalidate the current token and then lose a race to a newly issued token with a later `iat`.

The current target already requires periodic refresh, atomic binding replacement, idempotent per-token logout, and generation-based logout-all. The review retains those boundaries and makes refresh lineage, authority generations, expiry scheduling, overlap, and logout scope explicit.

### Canonical Authority Tuple

Rotation, revocation, leases, bindings, refresh requests, rebind handles/proofs, and registry records use one exact `authorityTuple` and no aliases:

```text
authorityTuple: {
  issuerAuthGeneration,
  accountAuthorityGeneration,
  tenantAuthorityGeneration: { tenantId: generation },
  membershipAuthorityGeneration: { tenantId: generation },
  privateRealmGrantVersions: [
    { tenantId, worldSlug, realmSlug, grantVersion }
  ],
  accountSecurityCutoff: {
    accountAuthorityGeneration,
    outboxStreamKey,
    outboxSequence
  }?,
  tenantBillingCutoff: {
    tenantId: {
      tenantAuthorityGeneration,
      tenantBillingSequence,
      outboxStreamKey,
      outboxSequence
    }
  }
}
```

Tenant and membership maps contain only exact applicable tenant IDs. Their key sets are determined independently by token profile and route classification; the closed `billing_safe_tenant` exception can require a membership entry while deliberately omitting the target-tenant generation. Explicitly unscoped artifacts use empty maps. `privateRealmGrantVersions` is empty for public production and otherwise contains exact `{tenantId, worldSlug, realmSlug, grantVersion}` entries. `accountSecurityCutoff` and `tenantBillingCutoff` are optional cutoff evidence, not replacement authorities. `membershipVersion` is independent membership-data freshness and must always be compared separately from `membershipAuthorityGeneration`; neither field substitutes for the other. The same tuple is copied into every applicable JWT/registry snapshot, Account lease, gameplay binding, refresh request, rebind proof, installation acknowledgement, and outbox payload. `issuanceFence` is copied alongside it as the Account composite authority fence captured by the issuance transaction or CAS.

## Decision

### Private Player-Delegation Token Rotation

- The rotated JWT is the receiver-specific private player-delegation profile `game-session-account-delegation` with audience `account-service`. It is private backend material for Account calls; gameplay clients never receive it. Gameplay-domain services continue to authorize the concrete mTLS workload and typed `PlayerExecutionContext`; they do not gain a per-action player-JWT dependency.
- Game Session schedules planned refresh at approximately half of the current token lifetime with random jitter and always before `exp` by the configured safety margin.
- A 60-second minimum retry interval may prevent a refresh storm only while sufficient validity remains. It cannot postpone the final safe attempt beyond expiry.
- Concurrent refresh demand for one gameplay binding is single-flighted. Transient failure while the current token remains valid uses bounded jittered retry.
- `tokenGeneration` is the positive monotonic generation for one JWT issuance/refresh lineage and is distinct from every field in `authorityTuple`. The Account-owned refresh request presents the current token identity and lineage generation, exact gameplay binding identity, `issuanceFence`, complete applicable `authorityTuple`, and an idempotent request ID. Account validates the current issued-token registry lineage, Account state, membership/version, exact realm grants, and every tuple field. The authority-generation record shape and monotonic cutoff ordering are the accepted contract of [ADR 0036](./adr-0036-monotonic-authority-generations-for-bulk-token-revocation.md); this ADR defines the refresh and logout ordering that consumes that contract. The one-record issued-token registry shape is defined by [ADR 0035](./adr-0035-single-record-issued-token-registry.md).
- Refresh and every competing revocation writer use one serializable Account transaction or one composite Account CAS/fence that covers every applicable field in `authorityTuple`, `issuanceFence`, the token-lineage fence, and the predecessor token identity. The predicate reads and conditionally compares issuer, account, every tenant map entry, every membership map entry, every private-realm grant entry, `accountSecurityCutoff`, and every `tenantBillingCutoff` entry as one unit before committing replacement issuance or revocation. Independent locks or per-field CAS operations are not sufficient. If any field changes, the whole operation loses the fence and must not expose or install a replacement; a concurrent revocation therefore wins rather than allowing refresh to cross the cutoff.
- Game Session mTLS identity authorizes calling the refresh API but is not authority to mint for an arbitrary player or to cross a current authority generation.
- Account also issues a high-entropy, single-use rebind handle bound to the gameplay binding, token hash and generation, account/tenant scope, complete authority tuple, and continuity deadline. Game Session stores that handle only in its protected durable binding while keeping the raw delegation JWT process-local. On takeover or restart, the exact Game Session workload may exchange the handle through the Account-owned rebind surface; Account verifies and consumes it, revalidates the current registry lineage and authority tuple, and returns a fresh delegation token plus replacement handle. Workload identity, binding identifiers, or a token hash without the handle are insufficient. Rebind cannot cross revocation or extend gameplay continuity, and a missing, replayed, or ambiguous handle fails closed to fresh login.
- The protected gameplay binding stores the complete `authorityTuple`, `issuanceFence`, and separate `membershipVersion` without the raw delegation JWT. It stores the exact delegated `accountId`/`tenantId` scope, positive `tokenGeneration`, `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, binding generation, and the secret-valued single-use `rebindHandle` alongside that tuple. Tenant-bound bindings contain exactly the applicable map entries and grant records; explicitly unscoped bindings contain empty maps/lists and no fabricated tenant or realm values. The tuple and binding metadata are replaced atomically under the binding CAS generation, while the raw JWT remains process-local.
- An auth-expired response may trigger immediate refresh while the current lineage, authority generations, and applicable private-realm grant versions remain refresh-eligible. An auth-revoked response triggers authoritative reconciliation; logout-all, password reset, security lock, membership loss, or another blocking authority-generation advance cannot be bypassed by giving the replacement a newer `iat`.
- Account first commits an immutable durable `TOKEN_ROTATION` operation in `PENDING` state in Account state, together with the Account-owned replacement lease, before changing any replacement-registry state in Coordination Redis. The operation binds the refresh request, request digest, predecessor and replacement token identities, lineage, gameplay binding, `issuanceFence` and complete `authorityTuple`, and expected postconditions; it contains no raw JWT. The lease carries the same complete `authorityTuple` and `issuanceFence`, has state `ISSUED`, carries a monotonic `leaseVersion`, and sets a bounded `installBy` deadline. Account then idempotently creates a non-authorizing `pending` replacement record. After verifying that record and the lease evidence, Account commits the operation as `COMMITTED`; a token-fence-guarded Redis operation then atomically marks the replacement registry record `active` and moves the predecessor to `retiring` before Account exposes the replacement response. These Redis mutations are not part of a claimed global transaction. For a rotated private delegation, registry `active` is necessary but not sufficient authorization: every Account call also requires the exact Account-owned replacement lease and binding-installation fence to be durably `INSTALLED` for that token, lineage, and gameplay binding. Before finalization, the registry-active candidate remains inadmissible. `COMMITTED` is therefore a durable activation decision, not sufficient stored-success evidence on its own: every initial response and retry must verify the exact replacement registry state, predecessor cutoff, lease identity, and fence, while protected use additionally requires `INSTALLED`. A retry or reconciler resumes a matching `PENDING` operation, revoking or removing the pending candidate on terminal failure, while a `COMMITTED` operation interrupted before Redis activation is completed only toward its exact recorded replacement/predecessor transition. Every replacement-registry mutation and lease or binding CAS also revalidates the current Account-owned token-identity fence, so work captured before a logout fence cannot recreate or make the replacement admissible. That Account-owned operation and lease evidence records `predecessorUsableUntil = min(originalExp, replacementIssuedAt + maxInFlightRpcDeadline)`, so predecessor authority is independently bounded without pretending the later Game Session binding compare-and-set shares an Account transaction.
- Durable operation evidence never becomes a replay store for the raw replacement JWT. The general prohibition is on persisting a raw delegation JWT in gameplay bindings, Redis, token-registry records, operation evidence, logs, metrics, or traces. The sole accepted persistence exception is a separate, bounded response envelope encrypted under Account-owned application encryption and bound to the exact request ID, request digest, caller workload, gameplay binding, token lineage, replacement identity, and `issuanceFence`, complete `authorityTuple`, and lease fence. The envelope may contain the replacement JWT and rebind handle only until the earlier of `installBy`, token expiry, or the configured idempotency deadline; it is not registry state or authorization evidence and is never exposed to Game Session storage, logs, metrics, or traces as durable plaintext. Game Session may persist only the separately returned opaque next rebind handle in its protected gameplay binding; it never persists the encrypted response envelope or raw replacement JWT. A matching retry may recover the same issuance result only after reconciliation proves the exact registry, lease, binding, and current token-identity fence postconditions and the retry revalidates the immutable request binding; the envelope cannot bypass a pending or committed logout fence. If the envelope is missing, unreadable, expired, or mismatched, Account revokes the orphan candidate and records a stable fail-closed outcome rather than minting a substitute credential. Game Session may begin a new rotation with a new request ID only while the predecessor and current authority tuple remain valid; otherwise it requires fresh login.
- A `COMMITTED` `TOKEN_ROTATION` whose replacement is still pending is eligible for activation only while its recorded fence remains current. If a newer logout or applicable authority fence advances before activation, Account uses a fence-guarded CAS to record terminal operation state `SUPERSEDED` with stable fail-closed outcome `TOKEN_ROTATION_SUPERSEDED`, advances the replacement lease to `ABORTED`, and idempotently revokes or removes the pending candidate. The candidate must remain non-authorizing even if cleanup is uncertain; bounded reconciliation may remove a durable non-authorizing record but must not retry activation. A matching retry returns the same terminal failure and requires fresh login; it never reopens or exposes the replacement.
- Before changing the protected binding, Game Session calls an idempotent Account installation-claim operation. Account compare-and-sets the lease from unexpired `ISSUED` to `INSTALLING`, revalidating `tokenGeneration`, `issuanceFence`, complete `authorityTuple`, and the current token-identity fence, and returns the current `leaseVersion` and `installBy`. A pending or committed exact-token logout fence, or a newer valid fence for the same lineage, rejects the claim. Game Session must atomically replace `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, `tokenGeneration`, `issuanceFence`, `authorityTuple`, `membershipVersion`, `rebindHandle`, and the expected old binding generation with that lease fence. The candidate replacement is not admissible for new calls until Account durably finalizes the claim as `INSTALLED`. While the lease is `INSTALLING`, the predecessor credential remains usable for Account RPCs until `predecessorUsableUntil`; its retiring registry record remains present through that cutoff even after successful installation. A lease expiry, abort, reconciliation, logout, or authority-generation cutoff serializes through the same lease CAS, advances `leaseVersion`, and invalidates the claim. A stale Game Session CAS or late finalization therefore cannot be a successful installation after expiry, abort, or a logout-fence advance; Game Session terminates or removes any non-finalized candidate and fails closed to fresh login.
- The post-swap installation acknowledgement is a lease-scoped Account control-plane operation authorized by the exact Game Session workload mTLS identity and the recorded lease binding. It does not require either the predecessor or replacement gameplay JWT to remain admissible, and neither gameplay credential is accepted as authority for the acknowledgement. The request carries a stable high-entropy acknowledgement/retirement request ID and request digest, rotation operation ID, exact lease identity and `leaseVersion`, gameplay binding identity, predecessor and replacement token identities, refresh lineage, issuanceFence, complete `authorityTuple`, and the Account-owned token-identity fence observed by the installation claim. The binding swap durably records the same operation, lease, version, replacement identity, `issuanceFence`, and `authorityTuple`, and `AWAITING_ACCOUNT_FINALIZATION` state so a restart or takeover can retry the acknowledgement without recovering either raw JWT.
- Account accepts the acknowledgement only when the caller workload and every request identity match the exact unexpired lease in `INSTALLING`, the replacement is the lease's active candidate, the predecessor, lineage, `issuanceFence`, complete `authorityTuple`, and the presented token-identity fence still equals the authoritative current fence. In one Account durable transaction, it compare-and-sets that exact lease from `INSTALLING` to `INSTALLED` and records the immutable acknowledgement result and predecessor-retirement obligation; no success is visible unless those writes commit together. A retry with the same request ID and digest returns that stored `INSTALLED` result. A different digest, caller, binding, operation, lease/version, predecessor, replacement, lineage, or fence, and any expired, `ABORTED`, or superseded lease, is rejected without mutation. If acknowledgement wins before a racing logout or authority advance, that later writer observes the installed tuple/fence and revokes it through its normal fence advance; if the logout or authority advance wins, acknowledgement fails closed on the changed fence or lease state.
- From successful finalization, Game Session clears `AWAITING_ACCOUNT_FINALIZATION` and uses only the replacement for new calls. Account keeps the predecessor record in `retiring` until `predecessorUsableUntil`, then compare-and-sets it to terminal `revoked`, records the retirement outcome in durable operation evidence, and only then deletes it idempotently; installation acknowledgement is therefore immediate fenced evidence, while physical predecessor cleanup follows the independently bounded in-flight overlap. If Game Session crashes after the binding swap, the recovery owner first retries the exact acknowledgement with workload mTLS and the stored lease-scoped metadata. Stored `INSTALLED` success completes local convergence; an expired, `ABORTED`, `SUPERSEDED`, stale, or mismatched result causes a fence-guarded local transition that terminates or removes the pending candidate binding and an idempotent Account cleanup request. Account revokes or removes the exact replacement only while the operation, lease, identity, and fence still authorize that cleanup; a newer authority state returns a stable stale result and is not overwritten. The pending Game Session binding remains inadmissible throughout unresolved finalization or cleanup. An Account reconciler claims expired `ISSUED` or `INSTALLING` leases, idempotently revokes the orphan replacement, completes predecessor retirement no earlier than its safety cutoff, and records the terminal result. It may commit a logout operation only when the matching `PENDING` logout fence still owns the current fence version; if a newer valid installation or other lineage operation has advanced that fence, it records a stale/no-op outcome and cannot overwrite or commit over the newer state. The reconciler never reactivates the predecessor; an unfinalized gameplay binding fails closed to fresh login. Lease recovery is bounded independently of arbitrary JWT expiry and serializes with abort, acknowledgement, logout, and authority-generation cutoff through the same lineage state. An absent record without matching durable operation evidence is not sufficient authority.
- Rotation never changes `continuityBindingExpiresAt` or `resumeDeadline`. If refresh cannot establish authority before expiry, backend-authenticated actions fail closed and the player must complete fresh login.

### Per-Token Logout

- `POST /auth/logout` revokes only the presented `control-ui` JWT or `player-bootstrap` token. A completed per-token logout is idempotent only when Account has durable `COMMITTED` tombstone evidence for that exact token; an absent issued-token registry record alone is not proof of a completed logout.
- The first logout attempt uses normal registry-backed authorization. In the same Account transaction as the operation record, Account advances the exact-token, Account-owned monotonic fence to a new `PENDING_LOGOUT` version bound to the request ID, request digest, and exact token identity (`tokenHash`, `jti`, profile, and subject/account). That durable fence is authoritative before Account touches Redis. Only after the transaction commits does Account idempotently delete that token's registry record, then advance the matching operation and fence to `COMMITTED` with its `token_logout` audit evidence before reporting success; any account-security outbox/message is emitted or retried after that commit. A bounded reconciler may complete matching `PENDING` work when the intended absent-record postcondition is established, but it must first compare-and-set that it still owns the same fence version and must not commit if a newer valid installation or other lineage operation has advanced the fence. Bare registry absence without that durable intent remains denied. A retry may return no-op success after full local signature, profile, time, and subject validation only when the matching durable `COMMITTED` tombstone proves that exact token was revoked. Pending, failed, or mismatched evidence is not reported as success; the fence creates no authorization context or new authority. Invalid, expired, wrong-profile, or ambiguous tokens remain denied.
- The exact-token `PENDING_LOGOUT`/`COMMITTED` tombstone is an Account-owned monotonic token-identity fence. The fence records the token identity and lineage metadata (`tokenHash`, `jti`, profile, subject/account, and fence version) without persisting the raw JWT. Every refresh, rebind, installation, or reconciliation compare-and-set that could recreate or mutate an issued-token registry record or gameplay binding must present and validate the current fence before changing Coordination Redis or making the replacement binding admissible. A pending or committed logout fence therefore rejects stale work captured before the fence and prevents it from recreating logged-out registry state. A later valid operation may advance the lineage only through the same Account-owned fence CAS; it cannot restore the logged-out token identity. These are ordered idempotent operations across Account and Coordination Redis, not a cross-store transaction.
- Other devices and unrelated gameplay bindings for the account remain active.
- A first-party player UI performs its local/device logout sequence separately: stop reconnect, gameplay `LOGOUT`, close the socket, revoke the current bootstrap token, and clear local state. Account does not locate gameplay sockets from the per-token endpoint.
- The audit action is explicitly `token_logout` and records bounded actor, account, token-profile/hash identifier, request, and outcome metadata without the raw token.

### Account-Wide Logout

- `POST /auth/logout-all` atomically advances the durable account authority generation and applicable `authorityTuple`/`accountSecurityCutoff` fields with its account-wide logout event, distinct `account_logout_all` audit record, and outbox record, then idempotently projects `session:auth:generation:account:<accountId>` set-if-greater. The new account authority generation invalidates earlier account-scoped authority without comparing it to JWT `iat`.
- Logout-all and every equivalent account-wide security cutoff serialize against private-token refresh through the same account generation row or compare-and-set. A refresh validated against the previous generation cannot commit after the cutoff advances it.
- The current account authority generation, not deletion of every token record, is immediate correctness authority. Bounded background cleanup may remove older token records.
- Logout-all is not successful merely because no live tokens remain. The first attempt uses normal registry-backed authorization and succeeds only after the authorized account-generation/event operation commits. A retry whose registry record or account-generation check no longer passes may return no-op success only when durable Account authority proves that a prior logout-all generation/event already superseded the presented token. It must not advance authority or mutate state from this retry path; current or ambiguous tokens remain denied.
- The event terminates all control-plane tokens, player-bootstrap tokens, and active gameplay bindings for the account across tenants through ADR 0030. A later deliberate login with fresh credentials starts a new generation normally.
- The same account-wide authority event invalidates every prior `game-session-account-delegation` token and its Account-issued registry lineage for the account, regardless of tenant, game instance, or token `iat`. Account publishes the event through the account-wide gameplay-session index/reconciliation contract; Game Session marks the indexed gameplay bindings disconnected and inadmissible, while Account remains the authority for invalidation. Missing, stale, or ambiguous index evidence fails closed for affected admission and cannot be reported as complete merely because a bounded token-record scan found nothing. Cleanup is best effort after the authority generation has become invalidating; a later fresh login creates a new generation.
- Password reset, security lock, and other account-wide revocations use distinct audit/event action types even when they advance the same account authority generation.

## Consequences

- Healthy long-running gameplay does not fail merely because a private control-plane token reaches its ordinary expiry.
- A trusted Game Session cannot use automatic refresh to resurrect a generation invalidated by logout-all or another security event.
- Planned refresh adds one bounded Account interaction per active session per fraction of token lifetime, with jitter and single-flight to avoid synchronized load. It is not on the gameplay command hot path.
- Atomic swap plus bounded overlap prevents new calls from using the old token while allowing already-started RPCs to finish.
- Logout current device no longer unexpectedly signs out every device; logout-all deliberately terminates gameplay as well as control-plane sessions.
- The model requires a lineage- and authority-generation-bound refresh API, expiry-aware scheduler, token-entry lifecycle, durable account-wide events, authority-generation projection, and cross-device/gameplay proof.

## Alternatives Considered

### Refresh Only At Expiry Or First Failure

This removes scheduled work but creates synchronized expiry failures, adds user-visible latency, and makes recovery dependent on an already-expired credential.

### Long-Lived Tokens Without Rotation

Long lifetimes reduce refresh traffic but extend stale-role and stolen-token exposure and make revocation machinery carry more risk.

### Workload-Identity-Only Refresh

Allowing Game Session to mint a fresh player token from mTLS plus an account ID is simple, but can cross logout-all and security authority-generation advances. The current `tokenGeneration`, complete applicable `authorityTuple`, separate `membershipVersion`, and `issuanceFence` must remain part of refresh authority.

### Delete Every Token For Logout-All

Enumerating and deleting all token keys creates race, indexing, and partial-failure problems. A monotonic account authority generation gives one correctness decision while cleanup remains bounded background work.

### Make Per-Token Logout Global

This has one simpler logout meaning but unexpectedly terminates other devices and gameplay sessions when a user only intended to sign out the current browser.

## Implementation and Proof Obligations

- Define and implement `RefreshGameplayServiceToken` with current-lineage subject binding, idempotency, live membership/account validation, complete `authorityTuple`, separate `membershipVersion`, positive `issuanceFence`, and exact `privateRealmGrantVersions` comparison.
- Persist `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, `tokenGeneration`, `issuanceFence`, the secret-valued single-use `rebindHandle`, complete `authorityTuple`, refreshed `membershipVersion`, and rotation CAS generation in the protected authenticated gameplay binding; never persist the raw delegation JWT outside the sole accepted bounded Account-encrypted response-envelope exception described above.
- Implement half-life scheduling, jitter, single-flight, expiry safety margin, bounded retry, the durable pre-mutation `TOKEN_ROTATION` `PENDING`/`COMMITTED`/`SUPERSEDED`/`FAILED` operation state machine, the bounded Account-encrypted response envelope, idempotent replacement/predecessor registry mutations and reconciliation, the Account-owned replacement lease/CAS reconciler, idempotent old-entry retirement acknowledgement, and failure-to-fresh-login behavior. Prove `COMMITTED` cannot replay success until the active-replacement/retiring-predecessor and lease/fence postconditions are revalidated. The envelope may be used only for same-request recovery after current-state validation; it must never become registry, operation, authorization, or Game Session storage. Do not implement rotation as a cross-store transaction.
- The `TOKEN_ROTATION` proof must cover `PENDING`/`COMMITTED`/`SUPERSEDED`/`FAILED`, including a newer logout or authority fence racing a committed-but-not-activated replacement. It must prove the fence-guarded `SUPERSEDED`/`ABORTED` terminalization revokes/removes or durably non-authorizes the pending candidate, returns stable `TOKEN_ROTATION_SUPERSEDED`, and does not retry activation indefinitely.
- Prove installation acknowledgement succeeds using only the exact workload mTLS and lease-scoped identities, without requiring either gameplay JWT to be admissible; atomically finalizes only the matching `INSTALLING` lease and current fence; returns stored success for identical retries; and rejects stale or mismatched retries without mutation. Cover loss of the acknowledgement response and a crash after the binding swap, including takeover retry from persisted non-secret metadata and fail-closed candidate-binding removal plus Account cleanup when finalization cannot succeed.
- Prove refresh cannot cross any applicable `authorityTuple` field, `accountSecurityCutoff`, `tenantBillingCutoff`, `issuanceFence`, or separate `membershipVersion` advance, including races with logout-all, password reset, security lock, membership removal, and `privateRealmGrantVersions` revocation.
- Prove restart and takeover recover the exact persisted authority tuple and binding scope, compare every tuple member and the current token lineage with fresh Account authority, and fail closed on any missing, unavailable, malformed, regressed, or mismatched value. Prove the binding stores no raw delegation JWT and that a token hash, workload identity, binding identifier, or stale tuple cannot authorize rebind or replacement issuance without the single-use handle and current fence.
- Implement idempotent `/auth/logout` for `control-ui` and `player-bootstrap` profiles with bounded scoped-key lookup, a durable exact-token `PENDING_LOGOUT` fence established before Redis deletion, `COMMITTED` tombstones, an Account-owned monotonic token-identity fence that refresh/rebind/install/reconciliation CAS operations must validate, and distinct audit events.
- Implement logout-all durable event/audit, Account-owned `authorityTuple.accountAuthorityGeneration` and applicable `accountSecurityCutoff`/`issuanceFence` advancement, active-gameplay termination, idempotency, and background token cleanup.
- Prove per-token logout leaves other devices and unrelated gameplay active, while logout-all terminates every active account binding and permits later deliberate reauthentication.
- Prove gameplay-domain routine actions acquire no private player-delegation JWT refresh or authority-generation lookup.
- Prove restart/takeover can recover only through the binding-scoped single-use rebind handle, rejects handle replay or cross-binding use, and cannot extend continuity or cross a current authority cutoff.

## Reversibility and Revisit Triggers

Refresh timing, retry, and overlap are centralized policy that can be tuned without changing logout scope or authority ownership. Revisit if measured refresh load is material, token lifetimes become shorter than safe scheduled rotation permits, cross-device UX requires a durable device/session management surface, or gameplay services no longer need the `game-session-account-delegation` profile for Account calls.
