# ADR 0031: Revocation-Safe Session-Token Rotation And Logout

## Status

Accepted

## Implementation Status

There is no complete periodic rotation or generation-bound refresh path. The role-refresh service is a placeholder, gameplay session state does not yet implement the complete token metadata and atomic replacement contract, and Account logout/logout-all authority-generation workflows are absent.

## Context

A gameplay connection may remain active longer than the private `game-session-account-delegation` JWT that Game Session uses for Account calls. Without planned rotation, healthy long-running sessions fail at token expiry. A refresh surface that trusts only Game Session's workload identity can create the opposite problem: logout-all, password reset, security lock, or membership revocation may invalidate the current token and then lose a race to a newly issued token with a later `iat`.

The current target already requires periodic refresh, atomic binding replacement, idempotent per-token logout, and generation-based logout-all. The review retains those boundaries and makes refresh lineage, authority generations, expiry scheduling, overlap, and logout scope explicit.

### Canonical Authority Tuple Boundary

[ADR 0035](./adr-0035-single-record-issued-token-registry.md) owns the single normative `authorityTuple` schema and exact field names. This ADR references that schema without redefining it. Rotation-local requirements copy the unchanged tuple into every applicable JWT/registry snapshot, Account lease, gameplay binding, refresh request, rebind proof, installation acknowledgement, and outbox payload; `issuanceFence` is copied alongside it as the Account composite authority fence captured by the issuance transaction or CAS. `membershipVersion` is the complete canonical exact one-tenant map `{tenantId: version}` for a tenant-bound gameplay binding, remains independent membership-data freshness, and is always compared separately from `authorityTuple.membershipAuthorityGeneration`.
Alongside the tuple, `outboxCheckpoints` is the complete set of one exact `{outboxStreamKey, outboxSequence}` checkpoint for every applicable authority stream in the operation scope, with no aggregate maximum or omitted stream. It is canonicalized in stream-key order and copied unchanged through protected binding metadata, the installation claim and acknowledgement, binding CAS payloads, replacement leases, `TOKEN_ROTATION` operation evidence, retries, reconciliation records, and rotation proofs. Any missing, extra, stale, regressed, or mismatched checkpoint fails closed; checkpoints prove source position but never become an alternate authority. An authenticated Account event may update only a derived consumer-local projection after its checkpoint is validated, never the Account authority or source evidence.

The `membershipVersion` map is a first-class carrier, not a scalar alias. For the tenant-bound rotation scope its key set is exactly `{tenantId}`, its value is a JSON string in the canonical grammar `0` or `[1-9][0-9]*`, and only a process-local arbitrary-precision extraction may use that value as a scalar. The complete map is carried and exact-compared independently through every rotation boundary: the Account refresh request and serializable predicate; `TOKEN_ROTATION` operation stages; replacement lease; pending, active, and retiring registry postconditions; `rebindHandle`; `PENDING` rebind attempt and response envelope; first binding CAS and readback; installation claim, `BINDING_INSTALLED` attempt, acknowledgement request, acknowledgement digest, and Account `INSTALLED` postcondition; second binding CAS; every retry, abort/retire path, and reconciler; and every durable rotation record and proof. A missing, extra, differently keyed, scalarized, stale, regressed, or cross-snapshot map fails closed. No stage may reconstruct it from a tuple member, a high-water mark, or a latest-only membership value.

The complete checkpoint set is part of the canonical installation request and acknowledgement digest, the binding metadata and CAS comparison, the lease and operation-evidence identity, and every retry or reconciliation comparison. A record that carries only the checkpoint for the latest cutoff or only an aggregate maximum is incomplete and cannot authorize installation, activation, replacement use, or replayed success. Consumers also retain bounded per-stream duplicate evidence; an event below a high-water mark is a no-op only when that evidence matches or an authoritative Account lookup for the exact stream and sequence proves the same event identity and digest. A high-water mark without bounded evidence or authoritative lookup is insufficient and fails closed.

Rotation uses three distinct fence/version concepts. `leaseVersion` is the positive CAS revision of the Account-owned replacement lease. `installationFence` is the positive Account-owned monotonic fence for the exact replacement installation and is the canonical fence carried by the rotation lease, replacement registry record, Game Session binding CAS, response envelope, and installation acknowledgement. The admission `leaseFence` defined by ADR 0030 is a separate exact-binding admission fence and is not a rotation alias. A stale `leaseVersion` or `installationFence` rejects the operation; a lease transition that invalidates the candidate advances the applicable fence state. These fields are never renamed or substituted for one another.

Installation state is scoped explicitly. The protected binding is first an inadmissible `INSTALLING` candidate. `BINDING_INSTALLED` is the one canonical durable Game Session attempt state proving that the first binding CAS and exact readback completed; it is not a protected-binding state and does not permit replacement use. There is no separate `AWAITING_ACCOUNT_FINALIZATION` persisted state. The Account replacement lease has its own `INSTALLED` state after acknowledgement. Only then may the second fenced binding CAS transition the protected binding from `INSTALLING` to final `INSTALLED`, which is the sole admissible replacement-binding state.

## Decision

### Private Player-Delegation Token Rotation

`outboxCheckpoints` is preserved as an exact set throughout both replacement binding CAS stages. The first session-only CAS compares the expected prior set and writes the replacement candidate with the unchanged canonical set from the Account lease; after the durable attempt reaches `BINDING_INSTALLED` and Account commits the matching acknowledgement, the second fenced CAS compares that same set before marking the candidate binding `INSTALLED`. Neither stage may derive a new set, retain only the latest checkpoint, or substitute an aggregate maximum. The installation acknowledgement request and its canonical digest include the complete stream-key-ordered set and complete canonical `membershipVersion` map, and Account validates both against the exact lease, operation evidence, current authority snapshot, and binding metadata before committing the lease `INSTALLED` postcondition. A missing, extra, reordered-with-different-content, stale, regressed, or cross-scope checkpoint or membership map fails closed, including on an exact retry after timeout-after-commit.

Rotation record completeness is normative at every boundary: the `TOKEN_ROTATION` operation record, replacement lease, non-authorizing pending replacement, `ACTIVATING`/`ACTIVATED` registry postcondition, installation claim, first binding CAS candidate, binding readback, durable `BINDING_INSTALLED` attempt checkpoint, acknowledgement request and digest, Account replacement-lease `INSTALLED` postcondition, and second binding CAS each carry the exact stream-key-ordered `outboxCheckpoints` set and complete canonical `membershipVersion` map alongside the same token identities, `authorityTuple`, `issuanceFence`, `leaseVersion`, and `installationFence`. Account compares both carriers when it verifies the active replacement and retiring predecessor; Game Session compares both before it marks the protected binding `INSTALLED`. A record or postcondition that omits either carrier, keeps only the latest checkpoint or membership value, or uses an aggregate maximum is incomplete and cannot advance the operation or authorize replacement use.

- The rotated JWT is the receiver-specific private player-delegation profile `game-session-account-delegation` with audience `account-service`. It is private backend material for Account calls; gameplay clients never receive it. Gameplay-domain services continue to authorize the concrete mTLS workload and typed `PlayerExecutionContext`; they do not gain a per-action player-JWT dependency.
- Game Session schedules planned refresh at approximately half of the current token lifetime with random jitter and always before `exp` by the configured safety margin.
- A 60-second minimum retry interval may prevent a refresh storm only while sufficient validity remains. It cannot postpone the final safe attempt beyond expiry.
- Concurrent refresh demand for one gameplay binding is single-flighted. Transient failure while the current token remains valid uses bounded jittered retry.
- `tokenGeneration` is the positive monotonic generation for one JWT issuance/refresh lineage and is distinct from every field in `authorityTuple`. For the exact active registry record, `authTokenIssuedAt == registry.iat`, `authTokenExpiresAt == registry.exp`, and `tokenGeneration == registry.tokenGeneration`; these are exact equality checks for the same token identity, not ordering checks against Redis TTL, current time, or another registry record. The Account-owned refresh authority request presents the current token identity and lineage generation, exact gameplay binding identity, the complete canonical `membershipVersion` map, `issuanceFence`, complete applicable `authorityTuple`, exact `outboxCheckpoints` set, and an idempotent request ID. Account validates the current issued-token registry lineage, exact token-field equality, Account state, the authoritative membership snapshot and its source version, exact realm grants, and every tuple field. `membershipVersion` is independent of `authorityTuple.membershipAuthorityGeneration`; a missing, stale, malformed, unavailable, or mismatched map fails closed. The authority-generation record shape and monotonic cutoff ordering are the accepted contract of [ADR 0036](./adr-0036-monotonic-authority-generations-for-bulk-token-revocation.md); this ADR defines the refresh and logout ordering that consumes that contract. The one-record issued-token registry shape is defined by [ADR 0035](./adr-0035-single-record-issued-token-registry.md).
- Refresh and every competing revocation writer use one serializable Account transaction or one composite Account CAS/fence that covers every applicable field in `authorityTuple`, the complete canonical `membershipVersion` map, `issuanceFence`, the token-lineage fence, and the predecessor token identity. The predicate reads and conditionally compares issuer, account, every tenant map entry, every membership map entry, every private-realm grant entry, `accountSecurityCutoff`, every applicable `tenantBillingCutoff` entry, and the complete requested membership map against the current authoritative membership source version as one unit before committing replacement issuance or revocation. Missing, stale, regressed, unavailable, or mismatched map or membership source/freshness evidence loses the same fence as any other authority mismatch; independent locks or per-field CAS operations are not sufficient. If any field changes, the whole operation loses the fence and must not expose or install a replacement; a concurrent revocation therefore wins rather than allowing refresh to cross the cutoff.
- Game Session mTLS identity authorizes calling the refresh API but is not authority to mint for an arbitrary player or to cross a current authority generation.

#### Canonical `rebindHandle`

`rebindHandle` is a high-entropy, opaque, Account-issued signed handle, not a gameplay JWT or locally parseable authority. Its signed content includes the required `jti`, `nbf`, `lineage`, `account`, `profile`, `audience`, `issuanceFence`, and exact gameplay binding identity. Account also binds it to the exact token hash and generation, applicable account/tenant scope, complete `authorityTuple`, complete canonical `membershipVersion` map, canonical stream-key-ordered `outboxCheckpoints` set, and the binding's immutable `continuityBindingExpiresAt` and applicable `resumeDeadline`; Game Session stores only the opaque value in the protected durable binding and keeps the raw delegation JWT process-local.

Account is the sole verifier and must validate the signature and required claims, expected rebind profile and audience, signed `jti`/`nbf`/lineage, account and binding identity, exact token hash/generation, complete authority tuple and checkpoint set, and current `issuanceFence` against Account's authoritative token registry, binding, current authority, and token-identity fence. The signed `jti` and token identity must match the active, unrevoked, unexpired registry record exactly, including `authTokenIssuedAt == registry.iat` and `authTokenExpiresAt == registry.exp`; Redis TTL or current time cannot repair a missing or mismatched record. It must reject missing, malformed, unavailable, stale, expired, replayed, ambiguous, or mismatched evidence; workload identity, binding identifiers, or a token hash without the handle cannot substitute for it. A new operation is accepted only while the signed `nbf` and the immutable continuity/reconnect deadlines are valid, and rebind or rotation never extends `continuityBindingExpiresAt` or `resumeDeadline` or crosses a current authority cutoff.

The handle is single-use for a new operation: the client supplies a stable `rebindRequestId`, and Account atomically records the exact request and consumes the current handle identity once only after the current `issuanceFence` and all other evidence validate. An exact retry with the same request ID, canonical digest, workload, binding identity, handle identity, authority evidence, and fence replays the stored bounded Account result without minting another token or consuming another handle. A fence race returns stable stale/failure metadata; an expired response envelope returns only durable completion/failure metadata and never a raw token. A later operation requires the newly returned handle and a new request ID; any changed request identity or digest is rejected without mutation.

- The protected gameplay binding stores the complete `authorityTuple`, exact `outboxCheckpoints` set, complete canonical `membershipVersion` map, `issuanceFence`, and no raw delegation JWT. It stores the exact delegated `accountId`/`tenantId` scope, positive `tokenGeneration`, `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, binding generation, and the canonical opaque `rebindHandle` defined above alongside that tuple. Tenant-bound bindings contain exactly the applicable map entries and grant records; explicitly unscoped bindings contain empty maps/lists and no fabricated tenant or realm values. The tuple, membership map, checkpoint set, and binding metadata are replaced atomically under the binding CAS generation, while the raw JWT remains process-local.
- Rebind-handle consumption follows the canonical single-use and exact-replay contract above and is a durable, bounded, replayable Account operation. Before calling Account, Game Session records a `PENDING` attempt containing the client-supplied `rebindRequestId`, canonical request digest, exact workload, gameplay-binding identity, current handle identity, `authorityTuple`, complete canonical `membershipVersion` map, exact `outboxCheckpoints` set, `issuanceFence`, and token-identity fence. Account atomically records the matching operation and response envelope under that contract; a new operation with a stale exact `issuanceFence` is rejected without consuming the handle or issuing a replacement. A retry with the same request ID, exact digest, workload, binding, handle identity, complete membership map, exact checkpoint set, `issuanceFence`, and authority evidence returns the stored result without minting another token or consuming another handle. If the fence advanced before a credential result can be replayed, the same-operation retry returns stable stale/failure metadata rather than a replacement credential. A conflicting request ID, mismatched binding, membership map, checkpoint set, or digest, expired request/envelope, expired continuity deadline, or changed authority fence for a new operation is rejected without mutation. After installation acknowledgement or envelope expiry, replay returns only durable completion/failure metadata and never a raw token; unavailable or ambiguous result state fails closed.
- An auth-expired response may trigger immediate refresh while the current lineage, authority generations, and applicable private-realm grant versions remain refresh-eligible. An auth-revoked response triggers authoritative reconciliation; logout-all, password reset, security lock, membership loss, or another blocking authority-generation advance cannot be bypassed by giving the replacement a newer `iat`.
- `TOKEN_ROTATION` has separate durable operation stages and lease stages. `PENDING` is the immutable Account intent committed before any replacement-registry mutation; `COMMITTED` is the durable Account decision to attempt the recorded activation after the non-authorizing pending replacement and lease evidence are verified; `ACTIVATING` records a fenced, replayable attempt to perform the exact Redis transition; and `ACTIVATED` is recorded only after the replacement is verified `active` and the predecessor is verified `retiring` with the recorded cutoff. `SUPERSEDED` and `FAILED` are terminal failure states. The replacement lease is independent and transitions `ISSUED` to `INSTALLING` to `INSTALLED`; `ACTIVATED` is not installation completion, and neither state may be treated as protected-use success without the required postconditions. This is one no-global-transaction issuance protocol: the Account transaction writes the authority snapshot and durable issuance evidence, while the Redis registry and Game Session binding CAS are separately fenced, idempotent postconditions reconciled by exact operation identity. The operation binds the refresh request, request digest, predecessor and replacement token identities, lineage, gameplay binding, `issuanceFence`, complete `authorityTuple`, complete canonical `membershipVersion` map, canonical stream-key-ordered `outboxCheckpoints`, and expected postconditions; it contains no raw JWT. The lease carries the same complete tuple, membership map, exact checkpoint set, and `issuanceFence`, has state `ISSUED`, carries a positive `leaseVersion` and positive `installationFence`, and sets a bounded `installBy` deadline. Account then idempotently creates a non-authorizing `pending` replacement record carrying the exact `rotationOperationId`, `leaseId`, `leaseVersion`, `gameplayBindingId`, `installationFence`, `issuanceFence`, complete `authorityTuple`, complete membership map, and exact checkpoint set. After verifying that record and the lease evidence, Account advances the operation to `COMMITTED`; a token-identity-fence-guarded Redis operation advances it through `ACTIVATING` and atomically marks the replacement registry record `active` and the predecessor `retiring`, then records `ACTIVATED` only after both exact postconditions are verified before Account exposes the replacement response. These Redis mutations and the later binding CAS are not part of a claimed global transaction. For a rotated private delegation, registry `active` is necessary but not sufficient authorization: every Account call also requires the exact Account-owned replacement lease and `installationFence` to be durably `INSTALLED` for that token, lineage, and gameplay binding. A retry or reconciler resumes matching `PENDING` intent toward its recorded decision or matching `COMMITTED`/`ACTIVATING` operation toward activation, verifies all recorded activation, membership-map, and lease postconditions, and never reports success from durable intent or decision evidence alone. Every replacement-registry mutation and lease or binding CAS also revalidates the current Account-owned token-identity fence and complete membership map, so work captured before a logout fence or membership change cannot recreate or make the replacement admissible. That Account-owned operation and lease evidence records `predecessorUsableUntilMs = min(predecessorExp * 1000, replacementIssuedAtMs + maxInFlightRpcDeadlineMs)` and `predecessorRetentionUntilMs = predecessorExp * 1000 + FIREMUD_AUTH_SESSION_SAFETY_MARGIN_MS`, so predecessor authority and physical retention are independently bounded without pretending the later Game Session binding compare-and-set shares an Account transaction.
- Durable operation evidence never becomes a replay store for the raw replacement JWT. The general prohibition is on persisting a raw delegation JWT in gameplay bindings, Redis, token-registry records, operation evidence, logs, metrics, or traces. The sole accepted persistence exception is a separate, bounded response envelope encrypted under Account-owned application encryption and bound to the exact request ID, request digest, caller workload, gameplay binding, token lineage, replacement identity, `issuanceFence`, complete `authorityTuple`, complete canonical `membershipVersion` map, `leaseVersion`, and `installationFence`. The envelope may contain the replacement JWT and canonical opaque `rebindHandle` only until the earlier of `installBy`, token expiry, or the configured idempotency deadline; it is not registry state or authorization evidence and is never exposed to Game Session storage, logs, metrics, or traces as durable plaintext. Game Session may persist only the separately returned opaque next rebind handle in its protected gameplay binding; it never persists the encrypted response envelope or raw replacement JWT. A matching retry may recover the same issuance result only after reconciliation proves the exact registry, lease, binding, `leaseVersion`, `installationFence`, `issuanceFence`, complete membership map, and current token-identity fence postconditions and the retry revalidates the immutable request binding; the envelope cannot bypass a pending or committed logout fence. If the envelope is missing, unreadable, expired, or mismatched, Account revokes the orphan candidate and records a stable fail-closed outcome rather than minting a substitute credential. Game Session may begin a new rotation with a new request ID only while the predecessor and current authority tuple and membership map remain valid; otherwise it requires fresh login.
- A `COMMITTED` or `ACTIVATING` `TOKEN_ROTATION` whose `ACTIVATED` postconditions are not yet verified is eligible for activation only while its recorded `installationFence` and `issuanceFence` remain current. If a newer logout or applicable authority fence advances before activation, Account uses a fence-guarded CAS to record terminal operation state `SUPERSEDED` with stable fail-closed outcome `TOKEN_ROTATION_SUPERSEDED`, advances the replacement lease to `ABORTED`, and idempotently revokes or removes the pending candidate. The candidate must remain non-authorizing even if cleanup is uncertain; bounded reconciliation may remove a durable non-authorizing record but must not retry activation. A matching retry returns the same terminal failure and requires fresh login; it never reopens or exposes the replacement.
- Before changing the protected binding, Game Session calls an idempotent Account installation-claim operation. Account compare-and-sets the lease from unexpired `ISSUED` to `INSTALLING`, revalidating `tokenGeneration`, `issuanceFence`, `installationFence`, complete `authorityTuple`, complete canonical `membershipVersion` map, canonical stream-key-ordered `outboxCheckpoints`, and the current token-identity fence, and returns the current `leaseVersion`, `installationFence`, and `installBy`. A pending or committed exact-token logout fence, or a newer valid fence for the same lineage, rejects the claim. Game Session must atomically replace `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, `tokenGeneration`, `issuanceFence`, `authorityTuple`, the complete canonical `membershipVersion` map, the exact checkpoint set, `rebindHandle`, and the expected old binding generation with the exact lease ID, `leaseVersion`, and `installationFence`. The candidate replacement is not admissible for new calls until Account durably finalizes the claim as lease `INSTALLED` and the second fenced CAS marks the binding `INSTALLED`. While the lease is `INSTALLING`, Account may finish predecessor-authenticated RPCs that were admitted before the claim, bounded by `predecessorUsableUntil`, but rejects new predecessor-authenticated Account calls. Game Session issues no new predecessor-authenticated business RPCs during this interval; it may issue only the lease-scoped workload-mTLS acknowledgement and finalization control-plane calls defined below, then waits for the replacement lease acknowledgement and final binding `INSTALLED` postcondition before resuming business calls. The predecessor's retiring registry record remains present through that cutoff even after successful installation. A lease expiry, abort, reconciliation, logout, or authority-generation cutoff serializes through the same lease CAS, advances `leaseVersion` and invalidates `installationFence`, and invalidates the claim. A stale Game Session CAS or late finalization therefore cannot be a successful installation after expiry, abort, or a logout-fence advance; Game Session terminates or removes any non-finalized candidate and fails closed to fresh login.
- The post-swap installation acknowledgement is a lease-scoped Account control-plane operation authorized by the exact Game Session workload mTLS identity and the recorded lease binding. It does not require either the predecessor or replacement gameplay JWT to remain admissible, and neither gameplay credential is accepted as authority for the acknowledgement. The request carries an installation identity `{rotationOperationId, leaseId, gameplayBindingId, installationFence}`, a stable high-entropy acknowledgement/retirement request ID, and a canonical request digest over that identity plus `leaseVersion`, predecessor and replacement token identities, refresh lineage, `issuanceFence`, complete `authorityTuple`, complete canonical `membershipVersion` map, canonical stream-key-ordered `outboxCheckpoints`, and the Account-owned token-identity fence observed by the installation claim. The binding swap durably advances the attempt to `BINDING_INSTALLED` with that same operation, lease, `leaseVersion`, `installationFence`, replacement identity, `issuanceFence`, `authorityTuple`, complete membership map, and exact checkpoint set so a restart or takeover can retry the acknowledgement without recovering either raw JWT.
- Account accepts the acknowledgement only when the caller workload and every request identity match the exact unexpired lease in `INSTALLING`, the replacement is the lease's active candidate, the predecessor, lineage, `leaseVersion`, `installationFence`, `issuanceFence`, complete `authorityTuple`, complete canonical `membershipVersion` map, canonical stream-key-ordered `outboxCheckpoints`, and the presented token-identity fence still equal the authoritative current evidence. The stable idempotency tuple is `(installationIdentity, acknowledgementRequestId, requestDigest)`. In one Account durable transaction, Account may compare-and-set that exact lease from `INSTALLING` to lease `INSTALLED` only when the same durable `TOKEN_ROTATION` operation is already `ACTIVATED` and its exact active-replacement/retiring-predecessor postconditions are recorded and verified. `COMMITTED`, `ACTIVATING`, a merely observed active Redis record, or a merely observed binding swap is insufficient proof for `INSTALLED`. The transaction records the immutable acknowledgement result and predecessor-retirement obligation; no success is visible unless those writes commit together. A retry with the same tuple, including a timeout-after-commit retry, returns that stored committed result. A different digest, caller, installation identity, binding, operation, lease/version, predecessor, replacement, lineage, membership map, checkpoint set, or fence, and any expired, `ABORTED`, or superseded lease, is rejected without mutation. Only that committed acknowledgement permits Game Session's second fenced binding CAS to mark the candidate binding `INSTALLED` using that same membership map and checkpoint set; an uncommitted, ambiguous, or merely observed swap never does. If acknowledgement wins before a racing logout or authority advance, that later writer observes the installed tuple/fences and revokes it through its normal fence advance; if the logout or authority advance wins, acknowledgement fails closed on the changed fence or lease state.
- From successful replacement-lease `INSTALLED` finalization of a durably `ACTIVATED` operation with its exact verified activation evidence, Game Session performs the second fenced CAS, marks the binding `INSTALLED`, completes the durable attempt, and uses only the replacement for new calls. The predecessor is unusable for new calls after `predecessorUsableUntilMs`, but Account retains its `retiring` record until `predecessorRetentionUntilMs`, then compare-and-sets it to terminal `revoked`, records the retirement outcome in durable operation evidence, and deletes it idempotently. Earlier physical deletion is permitted only after `predecessorUsableUntilMs` when Account commits a durable exact-token retirement fence or tombstone bound to the predecessor, replacement installation, and operation identity that prevents recreation; installation acknowledgement alone is not deletion authority. If Game Session crashes after the first binding swap, the recovery owner first retries the exact acknowledgement with workload mTLS and the stored lease-scoped metadata. Stored `ACTIVATED`, durable attempt `BINDING_INSTALLED`, replacement-lease `INSTALLED`, and protected binding `INSTALLED` postconditions complete local convergence; an expired, `ABORTED`, `SUPERSEDED`, stale, or mismatched result causes a fence-guarded local transition that terminates or removes the pending candidate binding and an idempotent Account cleanup request. Account revokes or removes the exact replacement only while the operation, `leaseVersion`, `installationFence`, identity, and `issuanceFence` still authorize that cleanup; a newer authority state returns a stable stale result and is not overwritten. The pending Game Session binding remains inadmissible throughout unresolved finalization or cleanup. An Account reconciler claims expired `ISSUED` or `INSTALLING` leases, idempotently revokes the orphan replacement, completes predecessor retirement no earlier than `predecessorUsableUntilMs`, and retains or deletes the record according to `predecessorRetentionUntilMs` and the exact-token retirement tombstone rule. It may commit a logout operation only when the matching `PENDING` logout fence still owns the current fence version; if a newer valid installation or other lineage operation has advanced that fence, it records a stale/no-op outcome and cannot overwrite or commit over the newer state. The reconciler never reactivates the predecessor; an unfinalized gameplay binding fails closed to fresh login. Lease recovery is bounded independently of arbitrary JWT expiry and serializes with abort, acknowledgement, logout, and authority-generation cutoff through the same lineage state. An absent record without matching durable operation evidence is not sufficient authority.
- Rotation never changes `continuityBindingExpiresAt` or `resumeDeadline`. If refresh cannot establish authority before expiry, backend-authenticated actions fail closed and the player must complete fresh login.

### Per-Token Logout

- `POST /auth/logout` revokes only the presented `control-ui` JWT or `player-bootstrap` token. A completed per-token logout is idempotent only when Account has durable `COMMITTED` tombstone evidence for that exact token; an absent issued-token registry record alone is not proof of a completed logout.
- Per-token logout also covers every associated unexpired `gameplay-connect` credential, not only the presented ordinary JWT. Account commits the exact-token `PENDING_LOGOUT` fence before any Gateway deny processing, enumerates every associated unexpired connect-token issuance/replay record, and requires one exact committed Gateway deny-marker/clear acknowledgement for each credential's `jti`; if enumeration proves that none remains, it requires a retained current fence-bound negative proof. Account cannot report success while any credential acknowledgement or the exact negative proof is missing, stale, conflicting, or ambiguous.
- The first logout attempt uses normal registry-backed authorization. In the same Account transaction as the operation record, Account advances the exact-token, Account-owned monotonic fence to a new `PENDING_LOGOUT` version bound to the request ID, request digest, and exact token identity (`tokenHash`, `jti`, profile, and subject/account). That durable fence is authoritative before Account touches Redis. Only after the transaction commits does Account idempotently delete that token's registry record, then advance the matching operation and fence to `COMMITTED` with its `token_logout` audit evidence and the Account-committed `issuanceFence` snapshot before reporting success; any account-security outbox/message carries that same applicable `issuanceFence` and is emitted or retried after that commit. A bounded reconciler may complete matching `PENDING` work when the intended absent-record postcondition is established, but it must first compare-and-set that it still owns the same fence version and must not commit if a newer valid installation or other lineage operation has advanced the fence. Bare registry absence without that durable intent remains denied. A retry may return no-op success after full local signature, profile, time, and subject validation only when the matching durable `COMMITTED` tombstone proves that exact token was revoked. Pending, failed, or mismatched evidence is not reported as success; the fence creates no authorization context or new authority. Invalid, expired, wrong-profile, or ambiguous tokens remain denied.
- The exact-token `PENDING_LOGOUT`/`COMMITTED` tombstone is an Account-owned monotonic token-identity fence. The fence records the token identity and lineage metadata (`tokenHash`, `jti`, profile, subject/account, and fence version) without persisting the raw JWT, together with the applicable Account `issuanceFence` evidence. Every refresh, rebind, installation, or reconciliation compare-and-set that could recreate or mutate an issued-token registry record or gameplay binding must present and validate the current fence before changing Coordination Redis or making the replacement binding admissible. A pending or committed logout fence therefore rejects stale work captured before the fence and prevents it from recreating logged-out registry state. A later valid operation may advance the lineage only through the same Account-owned fence CAS; it cannot restore the logged-out token identity. These are ordered idempotent operations across Account and Coordination Redis, not a cross-store transaction.
- Other devices and unrelated gameplay bindings for the account remain active.
- A first-party player UI performs its local/device logout sequence separately: stop reconnect, gameplay `LOGOUT`, close the socket, revoke the current bootstrap token, and clear local state. Account does not locate gameplay sockets from the per-token endpoint.
- The audit action is explicitly `token_logout` and records bounded actor, account, token-profile/hash identifier, request, and outcome metadata without the raw token.

### Account-Wide Logout

- `POST /auth/logout-all` atomically advances the durable account authority generation, applicable `authorityTuple`/`accountSecurityCutoff` fields, and the applicable Account `issuanceFence` with its account-wide logout event, distinct `account_logout_all` audit record, and outbox record, then idempotently projects `session:auth:generation:account:<accountId>` set-if-greater. The event and every downstream logout/revocation evidence record carry that same committed `issuanceFence`. The new account authority generation invalidates earlier account-scoped authority without comparing it to JWT `iat`.
- Logout-all and every equivalent account-wide security cutoff serialize against private-token refresh through the same account generation row or compare-and-set. A refresh validated against the previous generation cannot commit after the cutoff advances it.
- The current account authority generation, not deletion of every token record, is immediate correctness authority. Bounded background cleanup may remove older token records.
- Logout-all is not successful merely because no live tokens remain. The first attempt uses normal registry-backed authorization and succeeds only after the authorized account-generation/event operation commits. A retry whose registry record or account-generation check no longer passes may return no-op success only when durable Account authority proves that a prior logout-all generation/event already superseded the presented token. It must not advance authority or mutate state from this retry path; current or ambiguous tokens remain denied.
- The event terminates all control-plane tokens, player-bootstrap tokens, and active gameplay bindings for the account across tenants through ADR 0030. A later deliberate login with fresh credentials starts a new generation normally.
- The same account-wide authority event invalidates every prior `game-session-account-delegation` token and its Account-issued registry lineage for the account, regardless of tenant, game instance, or token `iat`. Account publishes the event, including the committed `issuanceFence`, through the account-wide gameplay-session index/reconciliation contract; Game Session marks the indexed gameplay bindings disconnected and inadmissible, while Account remains the authority for invalidation. Missing, stale, or ambiguous index evidence fails closed for affected admission and cannot be reported as complete merely because a bounded token-record scan found nothing. Cleanup is best effort after the authority generation has become invalidating; a later fresh login creates a new generation.
- Logout-all uses a dedicated account-scoped Gateway gameplay-connect deny fence/index, distinct from `replayAdmissionFence`; it must not reuse the per-credential replay-admission fence. Account reports completion only after Gateway acknowledges or reconciles every affected unexpired gameplay-connect credential and Game Session acknowledges or reconciles every affected gameplay binding and binding index. Any missing, stale, unavailable, or ambiguous credential or binding evidence leaves logout-all pending; local cleanup, token expiry, or the Account generation advance alone is not success.
- Password reset, security lock, and other account-wide revocations use distinct audit/event action types even when they advance the same account authority generation.

## Consequences

- Healthy long-running gameplay does not fail merely because a private control-plane token reaches its ordinary expiry.
- A trusted Game Session cannot use automatic refresh to resurrect a generation invalidated by logout-all or another security event.
- Planned refresh adds one bounded Account interaction per active session per fraction of token lifetime, with jitter and single-flight to avoid synchronized load. It is not on the gameplay command hot path.
- Atomic swap plus bounded overlap prevents new calls from using the old token while allowing already-started RPCs to finish.
- Logout current device no longer unexpectedly signs out every device; logout-all deliberately terminates gameplay as well as control-plane sessions.
- The model requires a lineage- and authority-generation-bound refresh API, expiry-aware scheduler, token-entry lifecycle, durable account-wide events, authority-generation projection, and cross-device/gameplay proof.

## Alternatives Considered

### Refresh Only At Expiry Or First Failure

This removes scheduled work but creates synchronized expiry failures, adds user-visible latency, and makes recovery dependent on an already-expired credential.

### Long-Lived Tokens Without Rotation

Long lifetimes reduce refresh traffic but extend stale-role and stolen-token exposure and make revocation machinery carry more risk.

### Workload-Identity-Only Refresh

Allowing Game Session to mint a fresh player token from mTLS plus an account ID is simple, but can cross logout-all and security authority-generation advances. The current `tokenGeneration`, complete applicable `authorityTuple`, separate `membershipVersion`, and `issuanceFence` must remain part of refresh authority.

### Delete Every Token For Logout-All

Enumerating and deleting all token keys creates race, indexing, and partial-failure problems. A monotonic account authority generation gives one correctness decision while cleanup remains bounded background work.

### Make Per-Token Logout Global

This has one simpler logout meaning but unexpectedly terminates other devices and gameplay sessions when a user only intended to sign out the current browser.

- Define and implement `RefreshGameplayServiceToken` with current-lineage subject binding, idempotency, live membership/account validation, complete `authorityTuple`, complete canonical `membershipVersion` map, positive `issuanceFence`, and exact `privateRealmGrantVersions` comparison.
- Persist `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, `tokenGeneration`, `issuanceFence`, the canonical opaque `rebindHandle` defined above, complete `authorityTuple`, complete canonical `membershipVersion` map, and rotation CAS generation in the protected authenticated gameplay binding; never persist the raw delegation JWT outside the sole accepted bounded Account-encrypted response-envelope exception described above.
- Carry and compare the complete canonical `membershipVersion` map and complete per-stream `outboxCheckpoints` set through binding metadata, installation claim and acknowledgement, binding CAS, lease and operation evidence, retries, reconciliation, and every rotation proof; do not substitute one scalar membership value, latest checkpoint, aggregate maximum, or a value from another authority scope.
- Implement half-life scheduling, jitter, single-flight, expiry safety margin, bounded retry, the durable pre-mutation `TOKEN_ROTATION` `PENDING`/`COMMITTED`/`ACTIVATING`/`ACTIVATED`/`SUPERSEDED`/`FAILED` operation state machine, the bounded Account-encrypted response envelope, idempotent replacement/predecessor registry mutations and reconciliation, the Account-owned replacement lease/CAS reconciler, idempotent old-entry retirement acknowledgement, and failure-to-fresh-login behavior. Prove no retry or reconciler reports success from `PENDING`, `COMMITTED`, or `ACTIVATING` evidence; `ACTIVATED` is recorded only after active-replacement/retiring-predecessor postconditions, and lease `INSTALLED` plus protected-use success require durable proof of that exact `ACTIVATED` operation and its postconditions, followed by exact `leaseVersion`/`installationFence`/`issuanceFence` and complete membership-map revalidation. A merely observed Redis active record or binding swap cannot satisfy the `ACTIVATED` gate. The envelope may be used only for same-request recovery after current-state validation; it must never become registry, operation, authorization, or Game Session storage. - Prove installation acknowledgement succeeds using only the exact workload mTLS and lease-scoped identities, without requiring either gameplay JWT to be admissible; atomically finalizes only the matching `INSTALLING` lease when the durable `TOKEN_ROTATION` operation is already `ACTIVATED` with exact active-replacement/retiring-predecessor proof and current `leaseVersion`, `installationFence`, and `issuanceFence`; returns stored success for identical retries; and rejects stale or mismatched retries without mutation. Prove the binding stores no raw delegation JWT and that the canonical `rebindHandle` verification, single-use, continuity, and exact-replay rules prevent a token hash, workload identity, binding identifier, stale tuple, scalarized membership value, or stale `issuanceFence` from authorizing rebind or replacement issuance without the current fence.

## Reversibility and Revisit Triggers

Refresh timing, retry, and overlap are centralized policy that can be tuned without changing logout scope or authority ownership. Revisit if measured refresh load is material, token lifetimes become shorter than safe scheduled rotation permits, cross-device UX requires a durable device/session management surface, or gameplay services no longer need the `game-session-account-delegation` profile for Account calls.
