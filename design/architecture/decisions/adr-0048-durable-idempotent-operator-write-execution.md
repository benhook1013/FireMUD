# ADR 0048: Durable Idempotent Operator-Write Execution

## Status

Accepted

## Implementation Status

This ADR is partially implemented. Existing operator intent and forwarding paths do not yet prove durable owner idempotency, owner-result recovery, or lease-fenced reconciliation for every supported action family. The separate moderation policy-input/audit path is an unavailable/gated implementation path: Account authorization-reference issuance and Logging & Admin receiving-boundary validation/redemption are not complete, it is not a shipped operator mutation, and domain-owner moderation enforcement remains target-state work. The WorldLifecycle path has deterministic workflow identity and bounded lifecycle state handling, but does not yet prove this ADR's full request-tuple idempotency, durable outcome recovery, or domain-snapshot/Temporal-status equivalence.

## Context

[ADR 0047](./adr-0047-logging-admin-as-external-operator-write-ingress.md) makes Logging and Admin the external ingress for operator writes while preserving domain mutation authority. That routing choice does not by itself settle which durable record proves execution, how timeouts and retries avoid duplicate effects, or how a stable Game Session front end reaches region-owned state.

Operator writes are low-volume control-plane operations, so one durable intent record and owner-side idempotency are justified. They must not become a distributed transaction, depend on an observability backend, or allow an ingress process to bypass current domain authority and gameplay fencing.

## Decision

### One Correlated Execution

Logging and Admin assigns one `controlPlaneRequestId`, computes ADR 0047's versioned canonical `mutationDigest`, and atomically reserves that identifier before issuing an Account authorization reference or forwarding any mutation. `mutationDigest` is only the SHA-256 digest of the normalized action-family schema pair and typed scope, target, expected-version, mutation, and audit-reason values defined by ADR 0047; it is not the owner idempotency identity. The owner idempotency tuple is the larger immutable tuple containing `controlPlaneRequestId`, `mutationDigest`, authorization-reference fingerprint, identities, schema pair, all typed request fields, authority evidence, fences, and every schema-declared bound presence/absence value. The reservation stores the immutable pre-authorization request tuple: `controlPlaneRequestId`, `mutationDigest`, requested actor or workload identity, applicable automation-policy identity or explicit human no-policy value, exact typed `scope`, normalized `actionFamily`, `actionFamilySchemaId`, `actionFamilySchemaVersion`, typed `target`, typed `expectedVersion`, typed `mutation`, typed `auditReason`, and every schema-declared bound presence/absence value. The canonical digest is persisted and recomputed as an integrity check and never substitutes for those stored fields or for the owner tuple. Reservation is a durable compare-and-set: exactly one caller becomes the reservation owner, and the owner token is required for every later tuple-completion write. The reservation is not authorization and does not permit forwarding.

The reservation-owner claim is itself a durable bounded lease. The record stores `reservationOwnerId`, `reservationClaimFence`, `reservationClaimExpiresAt`, and claim state. `CAS acquire` creates the `RESERVED` record and assigns one owner with a new monotonic claim fence; `CAS renew` may extend only that bounded claim when the exact owner and fence are still current and unexpired; `CAS completion` of authorization, forwarding, or a terminal no-mutation result requires the same owner and fence; and `CAS expiry` advances the claim fence and prevents the expired owner from authorizing, forwarding, or completing. A stale owner cannot issue or redeem an Account authorization reference, forward a mutation, or write any terminal result. A recovery CAS may complete an expired `RESERVED` claim only when durable evidence proves that no Account authorization or owner-forward call can still occur; if a call was dispatched or its outcome is ambiguous, the record remains `PENDING`/indeterminate and non-replayable. An active claim is never transferred while a call may still be in flight.

An exact duplicate of an existing reservation observes the same durable record and waits for the reservation owner to complete it or for the bounded reservation attempt to reach its terminal no-mutation outcome; it must not issue another authorization reference or forward another request. A request with the same `controlPlaneRequestId` but any difference in the owner idempotency tuple returns canonical `IDEMPOTENCY_CONFLICT` without mutation. Only the current reservation owner with an unexpired matching claim fence may complete the record with the post-authorization tuple. Reservation state transitions are explicit: `RESERVED -> PENDING` is the owner/fence-protected transition required before dispatching the Account authorization request; `PENDING -> AUTHORIZED` is the owner/fence-protected completion after Account issues the reference and the full post-authorization tuple is durably stored; `RESERVED -> NOT_EXECUTED` is allowed only when durable evidence proves that no Account authorization or owner-forward call can still occur; `AUTHORIZED -> NOT_EXECUTED` is allowed only when durable evidence proves that no owner call can still occur; `AUTHORIZED -> PENDING` is the durable owner-side idempotency transition written before the exact reference or mutation is dispatched to the owner; and `PENDING -> NOT_EXECUTED` is allowed only when the currently pending phase is durably known and the owner commits an explicit terminal no-mutation result before invoking the corresponding business mutator, with no applicable `FENCE_REJECTED` or `IDEMPOTENCY_CONFLICT` outcome. A stale owner/fence first produces `FENCE_REJECTED`; only that rejecting owner may later record `FENCE_REJECTED -> NOT_EXECUTED`, and only after durable no-accept/no-commit proof. A tuple mismatch is `IDEMPOTENCY_CONFLICT`; neither wire outcome is itself rearmable. An expired claim, lost response, missing record after dispatch, or any other ambiguous state remains `PENDING`/indeterminate and is never converted to `NOT_EXECUTED`. Recovery may not transfer an active reservation claim or issue another reference while a call may still be in flight. After the claim expires, a recovery CAS may assign a new fenced recovery owner solely to call ADR 0047's read-only `RecoverOperatorAuthorizationReference` with the complete pre-authorization tuple. That read either returns the original durable Account response or durable absence; it cannot create or replace a reference. A recovered original response permits normal tuple completion, while durable absence permits `NOT_EXECUTED` only when the record also proves that no owner forwarding occurred.

The canonical same-identifier rearm is limited to an owner-side terminal `NOT_EXECUTED` record whose complete post-authorization authority-bound tuple still matches. A pre-authorization `RESERVED -> NOT_EXECUTED` record has no opaque reference and is never rearmed; repeating that business intent requires a new explicit operator request with a new `controlPlaneRequestId` unless a later accepted Account recovery decision defines a different contract. Before any owner-side rearm CAS allocation, the current owner must freshly call `RedeemOperatorAuthorization` for the original opaque Account reference and validate current authority, membership, any applicable privilege predicate, the exact tuple, and the current owner/gameplay fence. A failed, expired, revoked, mismatched, or stale redemption prevents rearm and prevents allocation of a new attempt. Only after that validation succeeds may the same owner atomically compare-and-set that exact record back to `PENDING` as a new attempt with only a new attempt number, high-entropy `ownerMutationId`, and fenced execution token. It reuses the original operator request and reference without issuing a new authorization request or reference, does not widen scope or transfer reservation ownership, and retains the prior attempt evidence. A terminal `NOT_EXECUTED` record is not permission to replay an indeterminate dispatch.

For a forwarded owner-mutation family, after the reservation owner receives the Account authorization reference, it completes the durable operation record with the full authority-bound idempotency tuple: `controlPlaneRequestId`, `mutationDigest`, the `authorizationReferenceFingerprint` returned unchanged by Account for the exact opaque reference, exact typed `scope`, normalized `actionFamily`, `actionFamilySchemaId`, `actionFamilySchemaVersion`, typed `target`, typed `expectedVersion`, typed `mutation`, typed `auditReason`, exact authenticated workload identity, applicable workload/policy identity, the exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, immutable `authorityEvidenceBundle` with authority scope, source transaction/outbox or event version, projection status/freshness, and issuance-operation identity, and every bound presence/absence value. Logging and Admin never derives or recomputes the fingerprint or any authority evidence. The workload identity is the exact authenticated Logging and Admin mTLS identity; an automated request also binds `automation_policy_id` and `automation_policy_version`, while a human request has an explicit no-automation-policy value. Schema-bound absent or null values represented by the digest are stored as bound values rather than omitted during tuple completion. If the reservation, initial durable record, or tuple completion cannot be written, the mutation is not attempted. `controlPlaneRequestId` is the canonical logical request name across HTTP, Java/domain contracts, ADRs, and audit records. Protobuf contracts may use the language-standard wire spelling `control_plane_request_id`, which maps directly to that same identifier; it is not a second idempotency key.

For a forwarded owner-mutation family, Account first issues the applicable opaque bounded operator authorization reference defined by ADR 0047. A human request uses the typed Account `IssueHumanOperatorAuthorizationReference` path and requires the current `control-ui` identity; its reference is bound to the current token `jti`, account generation, role-assurance result, applicable `tenant_generation` or `target_tenant_generation`, any required `privileged_control` predicate, complete applicable authority tuple, independent applicable `membershipVersion`, positive `issuanceFence`, exact tenant/scope, action family, `actionFamilySchemaId`, `actionFamilySchemaVersion`, actor, `controlPlaneRequestId`, `mutationDigest`, issue time, and expiry. An unattended request uses the typed Account `IssueAutomationOperatorAuthorizationReference` path with `exact_mtls_workload_plus_versioned_automation_policy`; the current automation branch is restricted to tenant-scoped action families that require no `privileged_control`, and its reference is bound to the exact Logging and Admin workload mTLS identity, `automation_policy_id`, `automation_policy_version`, exact `tenant_generation`, complete applicable authority tuple, independent applicable `membershipVersion` when applicable, positive `issuanceFence`, exact tenant/scope, action family, `actionFamilySchemaId`, `actionFamilySchemaVersion`, `controlPlaneRequestId`, `mutationDigest`, issue time, and expiry. It carries no user account, end-user token, `control-ui` identity, global-role authority, or human elevation. Logging and Admin forwards that reference and its unchanged generation, evidence-bundle, and predicate evidence with the typed request, digest, schema pair, exact scope, and same request identifier to the authoritative domain owner. The owner:

- authenticates the immediate caller with the exact Logging and Admin workload mTLS identity and redeems the matching human or unattended reference with Account;
- authorizes the current actor or automation policy and scope rather than trusting ingress-derived domain conclusions or Logging and Admin assertions, and requires Account redemption to confirm the exact current generation and any required privileged predicate before commit;
- validates current domain preconditions and, where applicable, the current authority generation or gameplay fence;
- recomputes the canonical mutation digest and requires it to match the Account reference;
- treats the full authority-bound tuple (`controlPlaneRequestId`, `mutationDigest`, Account-returned `authorizationReferenceFingerprint`, exact typed `scope`, normalized `actionFamily`, `actionFamilySchemaId`, `actionFamilySchemaVersion`, typed `target`, typed `expectedVersion`, typed `mutation`, typed `auditReason`, exact `workloadIdentity`, applicable workload/policy identity, exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, immutable `authorityEvidenceBundle` with authority scope, source transaction/outbox or event version, projection status/freshness, and issuance-operation identity, and every bound presence/absence value) as its idempotency identity, using `controlPlaneRequestId` only to locate a candidate record and storing every tuple member on the durable request record;
- atomically persists or claims the owner request as `PENDING` before dispatching any owner call or business execution, with a durable owner claim lease and monotonic fenced execution token that prevents a superseded claimant from authorizing, forwarding, mutating, or committing;
- durably commits the authoritative owner mutation and terminal result together when both reside in the same owner store, or records a terminal `NOT_EXECUTED` result when it can prove that no owner mutation committed; and
- returns the previously committed result only when a duplicate `controlPlaneRequestId` carries an exact match for the full authority-bound tuple, including `mutationDigest` integrity, normalized `actionFamily`, schema identifier/version, typed scope, target, expected version, mutation, audit reason, bound presence/absence values, `authorityTuple`, `membershipVersion`, `issuanceFence`, and immutable authority evidence/source versions. The initial attempt has its own immutable `ownerMutationId`; a permitted `NOT_EXECUTED` rearm allocates a new attempt and never reuses that identity. The durable record retains every prior attempt's identity, terminal evidence, claim/fence, and timestamps so later reconciliation cannot attribute an old response or effect to the current attempt. A same-identifier request with any difference in digest, authorization-reference fingerprint, typed scope, normalized action family, schema identifier/version, target, expected version, mutation, audit reason, workload identity, applicable automation-policy identity, `authorityTuple`, `membershipVersion`, `issuanceFence`, authority evidence/source version, or bound presence/absence value fails with canonical `IDEMPOTENCY_CONFLICT` and never applies either payload again. A stale owner, expired lease, or fencing-token mismatch is a distinct `FENCE_REJECTED` outcome when durable evidence proves that this attempt did not mutate the owner state; it is never reported as `IDEMPOTENCY_CONFLICT`.

Logging and Admin then records the correlated outcome. It reports success only after the owner confirms its durable commit.

### Failure and Reconciliation Semantics

For every owner identity, durable request record, result lookup, and reconciliation path, the complete idempotency tuple includes `controlPlaneRequestId`, `mutationDigest` integrity, normalized `actionFamily`, schema identifier/version, typed scope/target/expected-version/mutation/audit-reason fields, bound presence/absence values, the exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, and immutable `authorityEvidenceBundle` with authority scope, source transaction/outbox or event version, projection status/freshness, and issuance-operation identity. The authority evidence fields are immutable evidence from Account's authority decision, while the typed request fields are immutable request data; all are compared exactly and none is reconstructed from caller assertions or a later authority read.

A failed final audit-outcome update does not roll back an already committed domain mutation. Each owner exposes an internal, read-only request-result lookup callable only by the allowlisted Logging and Admin workload. The lookup request carries the complete authority tuple: `controlPlaneRequestId`, `mutationDigest`, Account-returned `authorizationReferenceFingerprint`, exact typed `scope`, normalized `actionFamily`, `actionFamilySchemaId`, `actionFamilySchemaVersion`, typed `target`, typed `expectedVersion`, typed `mutation`, typed `auditReason`, the exact authenticated `workloadIdentity`, the applicable automation-policy identity, exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, immutable `authorityEvidenceBundle` with authority scope, source transaction/outbox or event version, projection status/freshness, and issuance-operation identity, and the exact bound presence/absence values, including the explicit no-policy value for a human request and any schema-bound absent or null values represented by the digest. The owner may use `controlPlaneRequestId` only to locate a candidate durable idempotency/result record; it then validates `mutationDigest` integrity and every typed tuple member, including normalized action family, schema pair, scope, target, expected version, mutation, audit reason, workload/policy identity, `authorityTuple`, `membershipVersion`, `issuanceFence`, authority evidence/source versions, and bound presence/absence values, before returning the result. Any mismatch returns canonical `IDEMPOTENCY_CONFLICT` without exposing the stored result or mutating state. The lookup cannot execute or reauthorize the mutation, so it remains safe after the original human or automation authorization reference expires or is revoked.

Logging and Admin retains the original durable intent and reconciles through that result lookup until the owner result can be recorded. The canonical same-identifier rearm is allowed only after a durable terminal owner-side result `NOT_EXECUTED` proves either that forwarding never occurred after authorization or that owner handling ended with that explicit no-mutation result before the business mutator was invoked, without a `FENCE_REJECTED` or `IDEMPOTENCY_CONFLICT` outcome, and the complete post-authorization authority-bound tuple still matches. A pre-authorization `RESERVED -> NOT_EXECUTED` record is terminal and requires a new explicit operator request rather than rearm. Before the owner-side rearm CAS allocation, the current owner must freshly call `RedeemOperatorAuthorization` for the original opaque Account reference and validate current authority, membership, any applicable privilege predicate, the exact tuple, and the current owner/gameplay fence; any redemption failure, expiry, revocation, mismatch, or stale fence prevents rearm. The owner may then atomically rearm that exact result record as one new attempt, allocating only a fresh attempt number, `ownerMutationId`, and fenced execution token while retaining the completed attempt history; it issues no new authorization request or reference. Any other terminal result is replay-only through the read-only lookup. An expired `PENDING` claim, missing owner record after dispatch, or any other indeterminate state remains read-only and non-replayable and retains its existing `ownerMutationId`; it never allocates a successor attempt. Durable absence cannot prove that an already dispatched mutation will not commit later, and authority revocation or expiry prevents rearm rather than creating a fresh reference to replay the old write.

`FENCE_REJECTED` is the initial wire/status outcome for a stale owner or fence and is non-rearmable. Only the owner that issued that rejection may transition its own record to terminal `NOT_EXECUTED`, and only after durable proof that the request was not accepted and no mutation committed; Logging and Admin, a caller, a recovery reader, or a different owner may not synthesize or advance that transition. Until the rejecting owner records that proof and terminal outcome, the request remains `FENCE_REJECTED` and cannot be rearmed.

Operator-visible states must distinguish at least:

- **not executed** — the reservation owner or recovery CAS durably proves that no Account authorization or owner-forward call can still occur, or the owner durably records an explicit `NOT_EXECUTED` no-mutation result before invoking the business mutator; `FENCE_REJECTED` and `IDEMPOTENCY_CONFLICT` are separate non-rearmable outcomes. The record is rearmable only by the exact owner after fresh `RedeemOperatorAuthorization` validates the unchanged tuple, current authority, membership, applicable privilege, and current fence;
- **pending or indeterminate, non-replayable** — dispatch may have reached the owner but no terminal result or durable effect evidence proves its outcome; reconciliation remains read-only and the mutation is never replayed;
- **committed, response lost or outcome pending** — execution may have committed and the same identifier must be queried through the owner result-read contract rather than replaced;
- **failed** — the owner received or claimed the request and a terminal, durable owner result proves execution ended without a successful mutation. A terminal `NOT_EXECUTED` result is not `FAILED`; these outcomes are mutually exclusive; and
- **fence rejected** — the owner returned the canonical `FENCE_REJECTED` wire/status outcome with reason `STALE_OWNER` or `STALE_FENCE` because its owner lease or gameplay fence was stale, and durable no-commit evidence exists. The reason is not an alternate outcome name. Audit records, contract tests, and metrics use `FENCE_REJECTED` as the outcome and the stale-owner or stale-fence value as its reason. This is distinct from `IDEMPOTENCY_CONFLICT`, which is reserved for a mismatch in the authority-bound idempotency tuple.

Clients and operators must not create a fresh request identifier merely because a response timed out. Retention of idempotency results must cover the documented retry and reconciliation window for that action family.

### Bounded Owner Reconciliation

When a `PENDING` owner claim expires or the owner request record is missing, the current owner performs a bounded, non-mutating reconciliation before considering any new request. It uses the original full authority-bound idempotency tuple, including `mutationDigest` integrity, normalized `actionFamily`, schema identifier/version, typed scope, target, expected version, mutation, audit reason, bound presence/absence values, the exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, immutable `authorityEvidenceBundle`, and its source transaction/outbox or event version and projection status/freshness, the prior `ownerMutationId` and its originating lease/fence when one exists, current lease/fencing evidence, and a fixed attempt and deadline to inspect the durable request record, durable effect/outcome evidence, mutation marker, and target version/state. Read-only reconciliation may validate the prior mutation marker and originating fence after lease ownership changes; the current fence is required only for a new Redis write or a durable terminal commit. It never calls a business mutator, creates a replacement authorization reference, or replays the payload as part of reconciliation.

If durable owner-store effect/outcome evidence bound to the prior `ownerMutationId`, originating fence, exact marker identity, and target-state digest proves that the mutation committed, the owner records or returns `COMMITTED`. A Redis marker plus target state may corroborate that evidence but cannot replace it. This read/validation remains allowed after lease ownership changes; only a new Redis write or durable terminal commit requires the current fence. If a durable terminal record explicitly proves that forwarding never occurred or that owner handling ended with `NOT_EXECUTED` before the business mutator was invoked, and no `FENCE_REJECTED` or `IDEMPOTENCY_CONFLICT` applies, it may return `NOT_EXECUTED`; the original reference remains the only possible rearm authority until its normal expiry or revocation. An expired `PENDING` claim, missing owner record after dispatch, absent Redis projection/marker with no terminal result, or conflicting evidence remains `PENDING`/indeterminate and non-replayable; it is never converted to `NOT_EXECUTED` and never silently applied again. The bounded read-only result is the no-double-apply rule for owner recovery. A later mutation requires a new explicit operator request and authorization unless the exact original request has terminal `NOT_EXECUTED` and satisfies the narrowly bounded same-identifier rearm rule above.

### Region-Scoped Game Session Writes

A Game Session request that mutates region-scoped tick or coordination state executes at the current lease owner under the current gameplay fence. A stable front end locates and forwards to that owner; it does not mutate region-owned state itself. A stale owner or stale fence returns `FENCE_REJECTED` only when durable evidence proves that no owner mutation committed; it does not authorize same-identifier redelivery. A later mutation requires a new request identifier unless the general reconciliation rule has produced terminal `NOT_EXECUTED`. An ambiguous timeout follows read-only reconciliation and is not replayed.

Owner-side admission, feature-flag, and tick control RPCs are `internal_workload` calls under this contract. Scopes or action families that cannot yet satisfy this durable, idempotent, fenced contract are rejected as unsupported rather than implemented through a weaker direct-write path. Forwarded owner-mutation families such as `ToggleFeatureFlag` and per-instance tick mutations remain unavailable/gated until their action-family schema, shared cross-language `mutationDigest/v1` golden vectors, and Account authorization-reference issuance/redemption flow exist. The separate `/moderation/actions` and `ApplyModerationAction` policy-input/audit path remains unavailable/gated until its action-family schema, shared cross-language `mutationDigest/v1` golden vectors, Account authorization-reference issuance, and Logging & Admin receiving-boundary validation/redemption exist. It is not an owner-side enforcement mutation, and the live `EvaluateModerationPolicy` read remains separate owner enforcement input; moderation enforcement and quota override owner contracts remain hypothetical target coverage until their routes and owner APIs exist.

### Moderation Policy-Input/Audit Boundary

`/moderation/actions` and `ApplyModerationAction` are a Logging & Admin-owned policy-input/audit path, not a forwarded domain mutation. Account owns issuance of the Account authorization reference, and Logging & Admin validates and redeems it at the receiving boundary before the path can persist policy input and audit evidence. This path does not require or perform domain-owner redemption or enforcement. The separate live `EvaluateModerationPolicy` read remains input at the current Account, Game Session, and Social & Groups enforcement boundaries; versioned propagation and domain enforcement remain target-state work.

### Redis-Backed Owner Mutations

The Redis-backed owner record uses the same complete authority-bound tuple defined above; Redis markers, key presence, and command responses never replace its `authorityTuple`, `membershipVersion`, `issuanceFence`, or immutable authority evidence/source versions.

Coordination Redis is a volatile projection, not the durable owner of an operator mutation. Any supported action that materializes state in Redis must first create or claim a durable owner request record containing the full authority-bound idempotency tuple (`controlPlaneRequestId`, `mutationDigest`, Account-returned `authorizationReferenceFingerprint`, exact typed `scope`, normalized `actionFamily`, `actionFamilySchemaId`, `actionFamilySchemaVersion`, typed `target`, typed `expectedVersion`, typed `mutation`, typed `auditReason`, exact `workloadIdentity`, applicable workload/policy identity, exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, immutable `authorityEvidenceBundle` with authority scope, source transaction/outbox or event version, projection status/freshness, and issuance-operation identity, and every bound presence/absence value), desired mutation, `ownerMutationId`, current owner/lease identity, fencing token, lease expiry, state, and terminal result, together with durable execution/effect evidence sufficient to distinguish a committed effect from an unstarted attempt. Atomic mutation-plus-result commit applies within the authoritative durable owner store; it does not imply a distributed transaction with Redis. The durable record and effect evidence are the source of truth for `PENDING`, `COMMITTED`, `FAILED`, `FENCE_REJECTED`, and `NOT_EXECUTED`; Redis key presence or a Redis command response alone is never a terminal result.

The current lease owner applies the projection through one registered Lua script that validates the current lease/fencing token, the persisted typed `target` and `expectedVersion`, and `ownerMutationId`, then atomically writes the desired Redis state and its mutation marker. A duplicate with an exact match for the full authority-bound tuple, including normalized `actionFamily`, schema identifier/version, typed target, expected version, mutation, audit, and presence/absence fields plus `mutationDigest` integrity, returns the existing marker/result; any tuple difference is rejected with canonical `IDEMPOTENCY_CONFLICT` without mutation, while a stale owner or fence is rejected with `FENCE_REJECTED` only when the owner can prove no mutation occurred. This creates an explicit cross-store reconciliation window: the durable owner record remains `PENDING` while the Redis projection may already contain the fenced marker and desired state. Read-only reconciliation validates the marker and desired state against the prior `ownerMutationId`, originating fence, and persisted typed tuple, even after lease transfer; the current fence is required only when issuing a new Redis write or durably committing the terminal owner result. `NOT_EXECUTED` is allowed only when a durable terminal outcome proves that no mutation marker or target-state change committed under this request; an absent or ambiguous marker without terminal evidence remains `PENDING`/indeterminate and non-replayable.

Crash and ownership recovery use the same durable record and request identity. A crash before the Redis script is `NOT_EXECUTED` only when durable execution/effect evidence proves that the script could not have committed; otherwise the claim is indeterminate and non-replayable. A crash after the script but before terminal-result persistence is reconciled by the current lease owner from durable effect evidence, the mutation marker, the prior `ownerMutationId`, its originating fence, target version, and the unchanged normalized typed tuple plus `mutationDigest` integrity, not by issuing a new mutation. Lease loss fences the old owner from both the Redis script and durable terminal commit; after lease expiry, the new owner must perform the bounded read-only reconciliation above and may not replay the same `ownerMutationId`. A Redis reset or lost projection is repaired from durable effect/outcome evidence when available; if that evidence is absent, recovery remains indeterminate and does not recreate the operator effect. No terminal result may claim `NOT_EXECUTED` while an old owner could still commit, and no `COMMITTED` result may depend on an unreconciled Redis mutation.

### Availability Boundary

Elasticsearch, Prometheus, Jaeger, Grafana, Kibana, Alertmanager, and similar observability systems may assist investigation, but are not part of write success, owner durability, idempotency, or reconciliation. The required durable records remain in Logging and Admin PostgreSQL and the owning domain's authoritative store.

## Consequences

- An accepted operator request is auditable before execution and can be reconciled after crashes or lost responses.
- Each owner needs a durable request-result record or equivalent atomic idempotency mechanism for supported operator actions.
- Logging and Admin remains a coordinator and audit owner, not a second owner of domain state.
- The protocol adds durable writes and coordination latency to low-volume operator actions, not to ordinary gameplay processing.
- Cross-service atomic rollback is deliberately absent: a committed owner mutation remains valid while a missing final audit outcome is repaired.
- Region-scoped remediation cannot bypass lease ownership even when invoked through an externally stable endpoint.

## Alternatives Considered

### Best-Effort Forwarding with Audit Afterward

Rejected because an audit outage could allow unaudited mutation and a lost response could encourage a duplicate effect.

### Distributed Transaction Across Logging and Admin and the Owner

Rejected because it would couple availability and storage protocols across services without eliminating the need for idempotent recovery.

### Logging and Admin Owns the Authoritative Mutation

Rejected because it duplicates domain state and bypasses owner-side invariants, current authority, and gameplay fencing.

### Let the Stable Game Session Front End Mutate Region State

Rejected because the front end is not the lease owner and cannot safely serialize a write with region tick execution.

## Implementation and Proof Obligations

The current implementation is partial. Each supported operator-action family must demonstrate:

- Wherever the proof refers to a full or complete authority-bound identity, it must name and compare the exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, and immutable authority evidence/source versions, in addition to `controlPlaneRequestId`, `mutationDigest` integrity, normalized `actionFamily`, schema identifier/version, typed scope/target/expected-version/mutation/audit-reason fields, bound presence/absence values, and the existing identity and audit fields.

- Current WorldLifecycle evidence is not full support for this ADR. `WorldLifecycleCommandServiceImpl.prepareWorldInstance` looks up by `(tenantId, gameInstanceId)` and compares the prepared fields, including `controlPlaneRequestId`; an exact prepared duplicate returns the existing snapshot, while a mismatch currently returns `INVALID_ARGUMENT`, not request-keyed `IDEMPOTENCY_CONFLICT`. Activation and failure are guarded by lifecycle epoch/state but have no complete request-tuple record. Termination uses `terminationRequestId` for state transitions and repeated terminal reads, but does not yet provide a durable terminal result/fingerprint for every retry or prove that a same-request retry cannot repeat cleanup. `TemporalWorldLifecycleOrchestrator` uses a deterministic tenant/game-instance workflow ID and queries an existing workflow after `WorkflowExecutionAlreadyStarted`, but does not compare a full request digest on prepare; its lifecycle read attaches Temporal describe metadata to a fallback domain snapshot rather than proving domain-state and workflow-status equivalence. The workflow signals also do not enforce a durable request identity/digest. These paths remain partial and must not be reported as satisfying the target idempotency contract.
- For WorldLifecycle to satisfy this ADR, each lifecycle command must use a stable request identity and canonical digest for the complete typed request tuple, with durable same-tuple replay and `IDEMPOTENCY_CONFLICT` on mismatch; deterministic workflow identity alone is insufficient. A status response must separately identify the authoritative domain snapshot and Temporal execution metadata, and may claim convergence only after proof that both represent the same lifecycle state and epoch.
- durable intent before forwarding, including trusted actor, reason, exact scope, mutation, and the full authority-bound idempotency tuple: exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, and immutable authority evidence/source versions in addition to the request, digest, scope, schema, workload/policy, and bound-presence fields;
- for forwarded owner-mutation families, authorization and domain validation at the owner;
- for `/moderation/actions` and `ApplyModerationAction`, Account authorization-reference issuance plus Logging & Admin receiving-boundary validation/redemption, without treating domain-owner redemption or enforcement as part of the policy-input/audit path;
- atomic owner mutation and result persistence with duplicate delivery returning the original result only on a full tuple match, and every mismatch returning canonical `IDEMPOTENCY_CONFLICT` without mutation;
- for Redis-backed owner state, a durable reservation-owner claim lease with CAS acquire/renew/expiry/completion and a monotonic fence, durable claim/state/result and effect-evidence records, marker-based Lua mutation, lease-owner fencing for new writes and terminal commits, and non-replayable read-only reconciliation that validates the prior `ownerMutationId` and originating fence after a crash or lease transfer;
- an allowlisted read-only owner result lookup that locates by `controlPlaneRequestId` but validates the complete authority tuple, including `mutationDigest` integrity, normalized `actionFamily`, typed scope/target/expected-version/mutation/audit-reason fields, the exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, immutable authority evidence/source versions, Account-returned authorization-reference fingerprint, schema identifier/version, exact workload/policy identity, and bound presence/absence values, returning `IDEMPOTENCY_CONFLICT` for any mismatch and recovering the durable outcome after authorization expiry or revocation without executing the mutation;
- recovery from crashes before forwarding, during owner execution, after owner commit, and before final outcome recording;
- truthful operator outcomes for rejection, timeout, lost response, duplicate delivery, authorization expiry, and reconciliation;
- no successful mutation when the initial intent store is unavailable;
- successful execution and reconciliation while observability dependencies are unavailable; and
- read-only recovery of a lost Account issuance response through the same request ID, complete typed tuple, and current reservation-claim fence, returning only the original reference response or durable absence and never creating a replacement reference; and
- for region-scoped Game Session actions, current-owner forwarding, durable stale-fence/no-commit rejection, and canonical same-identifier rearm only for a post-authorization owner-side terminal `NOT_EXECUTED` record, then fresh `RedeemOperatorAuthorization` validates current authority, membership, applicable privilege, the unchanged tuple, and the current fence before CAS allocation; a pre-authorization `RESERVED -> NOT_EXECUTED` record requires a new explicit operator request, while a valid owner-side rearm may allocate only a new attempt, `ownerMutationId`, and fenced execution token, and any validation failure prevents rearm.

## Reversibility and Revisit Triggers

Individual action families can migrate to another durable command mechanism while preserving their request identifiers and result history. Revisit this decision if write volume makes synchronous intent-and-forward coordination material, a durable command bus supplies equivalent authorization and outcome semantics, or an action genuinely requires atomic mutation across multiple domain owners rather than one authoritative owner plus correlated audit.
