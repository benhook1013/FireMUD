# ADR 0048: Durable Idempotent Operator-Write Execution

## Status

Accepted

## Implementation Status

This ADR is partially implemented. Existing operator intent and forwarding paths do not yet prove durable owner idempotency, owner-result recovery, or lease-fenced reconciliation for every supported action family. The separate moderation policy-input/audit path is an unavailable/gated implementation path: Account authorization-reference issuance and Logging & Admin receiving-boundary validation/redemption are not complete, it is not a shipped operator mutation, and domain-owner moderation enforcement remains target-state work. The WorldLifecycle path has deterministic workflow identity and bounded lifecycle state handling, but does not yet prove this ADR's full request-tuple idempotency, durable outcome recovery, or domain-snapshot/Temporal-status equivalence.

## Context

[ADR 0047](./adr-0047-logging-admin-as-external-operator-write-ingress.md) makes Logging and Admin the external ingress for operator writes while preserving domain mutation authority. That routing choice does not by itself settle which durable record proves execution, how timeouts and retries avoid duplicate effects, or how a stable Game Session front end reaches region-owned state.

Operator writes are low-volume control-plane operations, so one durable intent record and owner-side idempotency are justified. They must not become a distributed transaction, depend on an observability backend, or allow an ingress process to bypass current domain authority and gameplay fencing.

## Decision

### One Correlated Execution

ADR 0048 is the sole owning definition of `preAuthorizationReservationTuple/v1`; ADR 0047 and the Account issuance API reference this tuple exactly and must not define a variant. Logging and Admin assigns one `controlPlaneRequestId`, computes ADR 0047's versioned canonical `mutationDigest`, and atomically reserves that identifier before issuing an Account authorization reference or forwarding any mutation. `mutationDigest` is only the SHA-256 digest of the normalized action-family schema pair and typed scope, target, expected-version, mutation, and audit-reason values defined by ADR 0047; it is not the idempotency identity. The reservation actor is authority-derived and never caller supplied: a human reservation uses the Account-derived human actor from validated `control-ui` evidence, while automation uses the exact authenticated workload identity paired with its versioned automation-policy identity. Logging and Admin may carry that validated evidence but may not invent, override, or accept a caller-supplied actor. The immutable `preAuthorizationReservationTuple/v1` contains `controlPlaneRequestId`, this reservation actor identity, applicable automation-policy identity or explicit human no-policy value, exact typed `scope`, normalized `actionFamily`, `actionFamilySchemaId`, `actionFamilySchemaVersion`, typed `target`, immutable typed `targetOwner`, typed `expectedVersion`, typed `mutation`, typed `auditReason`, and every schema-declared bound presence/absence value. `targetOwner` is a schema-bound typed owner-selection value, distinct from `target`; it is immutable after reservation and is not recomputed from current routing or lease ownership. It contains only values known before Account authorization: it does not contain or fabricate an `issuanceKind`, `issuanceOperationId`, authorization-reference fingerprint, authenticated authority tuple, `membershipVersion`, `issuanceFence`, authority scope, source transaction/outbox or event version, projection status/freshness, or issuance-operation identity. The canonical digest is persisted and recomputed as an integrity check and never substitutes for those stored fields. Reservation is a durable compare-and-set: exactly one caller becomes the reservation owner, and the owner token is required for every later tuple-completion write. The reservation is not authorization and does not permit forwarding.

The canonical complete `postAuthorizationExecutionTuple` is the immutable tuple created only after Account authorization. It contains the complete pre-authorization tuple plus `issuanceKind`, Account-returned `authorizationReferenceFingerprint`, exact authenticated workload and actor binding, applicable workload/policy identity, exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, `reservationOwnerId`, positive `reservationClaimFence`, and the exact immutable `authorityEvidenceBundle/v1` defined in ADR 0047. That bundle includes authority scope, source evidence/version, projection status/freshness, issuance-operation identity, `authorityTuple`, `membershipVersion`, `issuanceFence`, and exactly the applicable human or automation evidence; it does not contain the execution tuple. The post-authorization tuple explicitly includes the immutable typed `targetOwner` and every schema-bound typed presence/absence value; only a value whose absence is declared by the action-family schema may be absent. Every tuple completion, recovery lookup, owner idempotency record, terminal or no-accept/no-commit proof, and conflict comparison carries and compares this exact tuple. No participant may omit, infer, or replace one of these fields from current ownership, routing, caller assertions, or a later authority read.

The pre-authorization recovery lookup carries the immutable typed `targetOwner` and its schema-bound presence/absence value as part of `preAuthorizationReservationTuple`; post-authorization same-identifier rearm carries it as part of the exact canonical complete `postAuthorizationExecutionTuple`. Rearm is not a pre-authorization recovery lookup, and neither path can substitute current routing or lease ownership for that value.

The reservation-owner claim is itself a durable bounded lease. The record stores `reservationOwnerId`, `reservationClaimFence`, `reservationClaimExpiresAt`, and claim state. `CAS acquire` creates the `RESERVED` record and assigns one owner with a new monotonic claim fence; `CAS renew` may extend only that bounded claim when the exact owner and fence are still current and unexpired; `CAS completion` of authorization, forwarding, or a terminal no-mutation result requires the same owner and fence; and `CAS expiry` advances the claim fence and prevents the expired owner from authorizing, forwarding, or completing. A stale owner cannot issue or redeem an Account authorization reference, forward a mutation, or write any terminal result. A recovery CAS may complete an expired `ACCOUNT_AUTHORIZATION/RESERVED` claim only when durable evidence proves that no Account authorization or owner-forward call can still occur; if a call was dispatched or its outcome is ambiguous, the record remains in the applicable phase-specific pending state and is non-replayable. An active claim is never transferred while a call may still be in flight.

The durable record has an explicit `phase` and `state`; `PENDING` is never persisted or returned without its phase. `phase=ACCOUNT_AUTHORIZATION` covers `RESERVED`, `AUTHORIZATION_PENDING`, `AUTHORIZED`, and `NOT_EXECUTED_BEFORE_AUTHORIZATION`; `phase=OWNER_EXECUTION` covers `OWNER_EXECUTION_PENDING`, `FENCE_REJECTED`, `COMMITTED`, `FAILED`, and `NOT_EXECUTED_AFTER_AUTHORIZATION`. Every acquire, renew, expiry, completion, rejection, recovery, lookup, and rearm CAS compares the expected phase and state together with the phase-appropriate tuple, attempt identity, owner identity, and applicable claim/fencing token. Pre-authorization operations compare `preAuthorizationReservationTuple`; the transition to `AUTHORIZED` atomically enriches that tuple into `postAuthorizationExecutionTuple`, and every later owner execution, result lookup, rearm, and reconciliation operation compares the post-authorization tuple. A phase mismatch is an idempotency conflict or stale-fence rejection as applicable; it is never treated as an interchangeable `PENDING` state.

An exact pre-authorization duplicate has the same `preAuthorizationReservationTuple` and reservation claim metadata; it observes the same durable record and waits for the reservation owner to complete it or for the bounded reservation attempt to reach its terminal no-mutation outcome. It must not issue another authorization reference or forward another request. A request with the same `controlPlaneRequestId` but any difference in the phase-appropriate tuple returns canonical `IDEMPOTENCY_CONFLICT` without mutation. Only the current reservation owner with an unexpired matching claim fence may atomically enrich the record with the Account-returned `postAuthorizationExecutionTuple`. Reservation state transitions are explicit and phase-qualified: `ACCOUNT_AUTHORIZATION/RESERVED -> ACCOUNT_AUTHORIZATION/AUTHORIZATION_PENDING` is the owner/fence-protected transition required before dispatching the Account authorization request; `ACCOUNT_AUTHORIZATION/AUTHORIZATION_PENDING -> ACCOUNT_AUTHORIZATION/AUTHORIZED` is the owner/fence-protected completion after Account issues the reference and the full post-authorization tuple is durably stored; `ACCOUNT_AUTHORIZATION/RESERVED` or `ACCOUNT_AUTHORIZATION/AUTHORIZATION_PENDING -> ACCOUNT_AUTHORIZATION/NOT_EXECUTED_BEFORE_AUTHORIZATION` is allowed only when durable phase evidence records that Account authorization cannot complete and durable dispatch evidence proves that no owner-forward call occurred and no owner-forward call can still occur. A `NOT_FOUND` returned by the read-only `RecoverOperatorAuthorizationReference` lookup is only read-only lookup evidence and never satisfies either proof. If either proof is absent or an Account or owner-forward call is in flight or ambiguous, the record remains `ACCOUNT_AUTHORIZATION/AUTHORIZATION_PENDING`, non-replayable and non-rearmable. `ACCOUNT_AUTHORIZATION/AUTHORIZED -> OWNER_EXECUTION/OWNER_EXECUTION_PENDING` is the durable owner-side idempotency transition written before the exact reference or mutation is dispatched to the owner; and `OWNER_EXECUTION/OWNER_EXECUTION_PENDING -> OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` is allowed only when durable evidence proves that no owner call or mutation committed and no `FENCE_REJECTED` or `IDEMPOTENCY_CONFLICT` applies. A stale owner/fence may produce `OWNER_EXECUTION/FENCE_REJECTED` only after the rejecting owner atomically persists its no-accept/no-commit proof; absent or inconsistent proof leaves the request in `OWNER_EXECUTION/OWNER_EXECUTION_PENDING`, non-replayable and non-rearmable. The rejecting owner or one fenced recovery owner may transition a valid `FENCE_REJECTED` to `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` only after validating that proof. A tuple mismatch is `IDEMPOTENCY_CONFLICT`; neither wire outcome is itself rearmable. An expired claim, lost response, missing record after dispatch, or any other ambiguous phase-specific state remains `ACCOUNT_AUTHORIZATION/AUTHORIZATION_PENDING` or `OWNER_EXECUTION/OWNER_EXECUTION_PENDING`, as applicable, and is never converted to a phase-inappropriate `NOT_EXECUTED` result. Recovery may not transfer an active reservation claim or issue another reference while a call may still be in flight. After the claim expires, a recovery CAS may assign a new fenced recovery owner solely to call ADR 0047's read-only `RecoverOperatorAuthorizationReference` for `ACCOUNT_AUTHORIZATION/AUTHORIZATION_PENDING`, with `preAuthorizationReservationTuple`. That read either returns the original durable Account response or durable absence; it cannot create or replace a reference. A recovered original response permits normal tuple enrichment, while durable absence permits `ACCOUNT_AUTHORIZATION/NOT_EXECUTED_BEFORE_AUTHORIZATION` only after the independent durable phase and dispatch evidence above is present.

The canonical same-identifier rearm is limited to an owner-side terminal `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` record whose complete post-authorization authority-bound tuple still matches. A pre-authorization `ACCOUNT_AUTHORIZATION/RESERVED -> ACCOUNT_AUTHORIZATION/NOT_EXECUTED_BEFORE_AUTHORIZATION` record has no opaque reference and is never rearmed; repeating that business intent requires a new explicit operator request with a new `controlPlaneRequestId`. Before any owner-side rearm CAS allocation, the current owner must obtain the original opaque Account reference through the fenced handoff below, then freshly call `RedeemOperatorAuthorization` and validate current authority, membership, any applicable privilege predicate, the exact tuple, and the current owner/gameplay fence. A failed, expired, revoked, mismatched, or stale handoff or redemption prevents rearm and prevents allocation of a new attempt. Only after that validation succeeds may the same owner atomically compare-and-set that exact record from `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` to `OWNER_EXECUTION/OWNER_EXECUTION_PENDING` as a new attempt with only a new attempt number, high-entropy `ownerMutationId`, and fenced execution token. The prior terminal result remains immutable and is never replayed as the new attempt's result. The external `controlPlaneRequestId` and complete request tuple remain the same, reservation ownership is not transferred, and the same still-unredeemed original reference is delivered under the bounded handoff without issuing a new authorization request or reference. The original reference is never reused after successful redemption, expiry, revocation, or zeroization. A terminal `NOT_EXECUTED` record is not permission to replay an indeterminate dispatch.

### Fenced Same-Identifier Rearm And Reference Handoff

The original opaque reference is never stored durably by Logging and Admin, the domain owner, or the owner-result record. Account remains the source-of-truth provider and retains the reference in its protected authority record. For a post-authorization owner-side terminal `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` result, the current domain owner requests one bounded rearm handoff from the exact Logging and Admin reservation owner. The request carries the unchanged canonical complete `postAuthorizationExecutionTuple`, including immutable typed `targetOwner`, Account-returned `authorizationReferenceFingerprint`, `controlPlaneRequestId`, `reservationOwnerId`, current positive `reservationClaimFence`, the current domain `ownerId` and owner/gameplay fence, and a fresh high-entropy `rearmHandoffId`.

Logging and Admin is the delivery provider, not a second authority: it must hold the exact unexpired reservation owner and claim fence. Only a separately fenced replacement owner of the exact authenticated Logging and Admin mTLS workload may call Account's read-only `RecoverOperatorAuthorizationReference` with `preAuthorizationReservationTuple/v1` and that fence during pre-authorization recovery. The domain owner's `recoveryOwnerId` never calls `RecoverOperatorAuthorizationReference`; it receives the original opaque reference only through this post-authorization handoff after the owner-side claim is current and fenced. Account checks `issuanceKind`, immutable typed `targetOwner`, authenticated workload/actor binding, automation-policy identity, authority tuple, membership version, issuance fence, all existing immutable fields, and the reservation owner/fence before returning the original reference. Logging and Admin delivers that reference only over the exact allowlisted mTLS channel to the current domain owner in a bounded, non-durable envelope bound to the handoff identity, full tuple, reference fingerprint, reservation owner/fence, current owner/fence, and an expiry no later than the Account reference expiry. The raw reference is held only in protected in-flight memory and is zeroized after redemption, expiry, or failed delivery; no durable recovery copy is created. Post-authorization same-identifier rearm is a separate handoff and redemption path using the canonical complete `postAuthorizationExecutionTuple`; it does not use `RecoverOperatorAuthorizationReference`, which remains pre-authorization only.

If that Logging and Admin reservation claim has expired, the terminal result is not eligible for same-identifier rearm. A recovery owner may retain and reconcile the historical result read-only, but it cannot transfer reservation ownership, recover or deliver the original reference, redeem it for execution, or allocate a successor owner attempt. Repeating the business intent requires a new explicit operator request with a new `controlPlaneRequestId`; claim expiry never turns the old reference or terminal result into authorization for another actor.

The current domain owner authenticates the delivery provider, rechecks its own current owner/gameplay fence and the unchanged reservation claim fence, and redeems the exact reference with Account before allocating the new attempt. Account redemption must still validate the exact caller workload, tuple, current authority, membership, applicable privilege, and issuance fence. Only then may the owner CAS allocate the new attempt number, `ownerMutationId`, and fenced execution token from the original `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` record. Handoff timeout, provider/owner fence loss, tuple or fingerprint mismatch, expired or revoked reference, Account `NOT_FOUND`, delivery failure, or redemption failure leaves the original terminal result unchanged, allocates no attempt, issues no replacement reference, and requires a new explicit operator request if the reference cannot be recovered. An ambiguous handoff is read-only and non-replayable; it never authorizes business execution.

For a forwarded owner-mutation family, after the reservation owner receives the Account authorization reference, it atomically enriches the exact `preAuthorizationReservationTuple/v1` into the canonical complete `postAuthorizationExecutionTuple`. The latter contains the complete pre-authorization tuple plus `issuanceKind`, the `authorizationReferenceFingerprint` returned unchanged by Account for the exact opaque reference, exact authenticated workload and actor binding, applicable workload/policy identity, the exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, `reservationOwnerId`, positive `reservationClaimFence`, and the exact immutable `authorityEvidenceBundle/v1` defined in ADR 0047. It explicitly retains the immutable typed `targetOwner` from the reservation and every schema-bound typed presence/absence value; no declared value may be dropped during tuple completion. Logging and Admin never derives or recomputes the fingerprint or any authority evidence. Its durable record may retain the operator intent and Account-returned fingerprint; any opaque reference held by Logging and Admin is protected, bounded in-flight delivery material only, not a recovery authority record or competing copy of Account's authority. The workload identity is the exact authenticated Logging and Admin mTLS identity; an automated request also binds `automation_policy_id` and `automation_policy_version`, while a human request has an explicit no-automation-policy value. Schema-bound absent or null values represented by the digest are stored as bound values rather than omitted during tuple completion. If the reservation, initial durable record, or tuple completion cannot be written, the mutation is not attempted. `controlPlaneRequestId` is the canonical logical request name across HTTP, Java/domain contracts, ADRs, and audit records. Protobuf contracts may use the language-standard wire spelling `control_plane_request_id`, which maps directly to that same identifier; it is not a second idempotency key.

For a forwarded owner-mutation family, Account first issues the applicable opaque bounded operator authorization reference defined by ADR 0047. A human request uses the typed Account `IssueHumanOperatorAuthorizationReference` path and requires the current `control-ui` identity; its reference is bound to the `human_operator` issuance kind, current token `jti`, account generation, role-assurance result, applicable `tenant_generation` or `target_tenant_generation`, any required `privileged_control` predicate, exact authenticated workload and actor binding, complete applicable authority tuple, independent applicable `membershipVersion`, positive `issuanceFence`, `reservationOwnerId`, positive `reservationClaimFence`, exact tenant/scope, immutable typed `targetOwner`, action family, `actionFamilySchemaId`, `actionFamilySchemaVersion`, actor, `controlPlaneRequestId`, `mutationDigest`, issue time, and expiry. An unattended request uses the typed Account `IssueAutomationOperatorAuthorizationReference` path with `exact_mtls_workload_plus_versioned_automation_policy`; the current automation branch is restricted to tenant-scoped action families that require no `privileged_control`, and its reference is bound to the `automation_operator` issuance kind, exact Logging and Admin workload mTLS identity, `automation_policy_id`, `automation_policy_version`, exact `tenant_generation`, complete applicable authority tuple, independent applicable `membershipVersion` when applicable, positive `issuanceFence`, `reservationOwnerId`, positive `reservationClaimFence`, exact tenant/scope, immutable typed `targetOwner`, action family, `actionFamilySchemaId`, `actionFamilySchemaVersion`, `controlPlaneRequestId`, `mutationDigest`, issue time, and expiry. It carries no user account, end-user token, `control-ui` identity, global-role authority, or human elevation. Logging and Admin forwards that reference and its unchanged generation, evidence-bundle, predicate evidence, reservation owner, claim fence, immutable typed `targetOwner`, and every schema-bound typed presence/absence value with the typed request, digest, schema pair, exact scope, and same request identifier to the authoritative domain owner. The owner:

- authenticates the immediate caller with the exact Logging and Admin workload mTLS identity, redeems the matching human or unattended reference with Account, and recomputes the canonical mutation digest before any new execution;
- compares the canonical complete `postAuthorizationExecutionTuple` (`controlPlaneRequestId`, `mutationDigest`, `issuanceKind`, Account-returned `authorizationReferenceFingerprint`, exact authenticated workload and actor binding, applicable workload/policy identity, exact typed `scope`, normalized `actionFamily`, `actionFamilySchemaId`, `actionFamilySchemaVersion`, typed `target`, immutable typed `targetOwner`, typed `expectedVersion`, typed `mutation`, typed `auditReason`, exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, `reservationOwnerId`, positive `reservationClaimFence`, immutable `authorityEvidenceBundle` with authority scope, source transaction/outbox or event version, projection status/freshness, and issuance-operation identity, and every schema-bound typed presence/absence value) using `controlPlaneRequestId` only to locate a candidate record. An exact tuple match with a terminal result returns the stored result without new validation or mutation, and any mismatch returns `IDEMPOTENCY_CONFLICT`. An expired or revoked reference permits only the allowlisted read-only result lookup against this exact tuple: an exact terminal result may be returned, but if none exists the request remains non-replayable with no forward, owner mutation, or other continuation and requires a new explicit operator request plus fresh Account authorization; it never continues as a new non-replayable attempt;
- authorizes the current actor or automation policy and scope rather than trusting ingress-derived domain conclusions or Logging and Admin assertions, requires Account redemption to confirm the exact current generation and any required privileged predicate, and only then validates current domain preconditions and, where applicable, the current authority generation or gameplay fence;
- atomically persists or claims the owner request as `OWNER_EXECUTION/OWNER_EXECUTION_PENDING` before dispatching any owner call or business execution, with a durable owner claim lease and monotonic fenced execution token that prevents a superseded claimant from authorizing, forwarding, mutating, or committing;
- durably commits the authoritative owner mutation and terminal result together when both reside in the same owner store, or records `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` when it can prove that no owner mutation committed; `ACCOUNT_AUTHORIZATION/NOT_EXECUTED_BEFORE_AUTHORIZATION` is reserved for the pre-authorization phase and cannot be emitted by owner execution; and
- returns the previously committed result only when a duplicate `controlPlaneRequestId` carries an exact match for the canonical complete `postAuthorizationExecutionTuple`, including `mutationDigest` integrity, `issuanceKind`, normalized `actionFamily`, schema identifier/version, typed scope, target, immutable typed `targetOwner`, expected version, mutation, audit reason, every schema-bound typed presence/absence value, `authorityTuple`, `membershipVersion`, `issuanceFence`, `reservationOwnerId`, `reservationClaimFence`, and immutable authority evidence/source versions. The same comparison includes authenticated workload/actor binding and applicable automation-policy identity. The initial attempt has its own immutable `ownerMutationId`; a permitted `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` rearm allocates a new attempt and never reuses that identity. The durable record retains every prior attempt's identity, terminal evidence, claim/fence, and timestamps so later reconciliation cannot attribute an old response or effect to the current attempt. A same-identifier request with any difference in digest, authorization-reference fingerprint, issuance kind, typed scope, normalized action family, schema identifier/version, target, immutable typed `targetOwner`, expected version, mutation, audit reason, workload identity, applicable automation-policy identity, `authorityTuple`, `membershipVersion`, `issuanceFence`, `reservationOwnerId`, `reservationClaimFence`, authority evidence/source version, or any bound presence/absence value fails with canonical `IDEMPOTENCY_CONFLICT` and never applies either payload again. A stale owner, expired lease, or fencing-token mismatch may produce `FENCE_REJECTED` only after the owner atomically persists durable no-accept/no-commit evidence proving that this attempt did not mutate the owner state; absent or inconsistent proof leaves `OWNER_EXECUTION/OWNER_EXECUTION_PENDING` and is never reported as `IDEMPOTENCY_CONFLICT` or replayed.

Logging and Admin then records the correlated outcome. It reports success only after the owner confirms its durable commit.

### Canonical Evidence Reference

ADR 0048 uses the exact `authorityEvidenceBundle/v1` shape owned by ADR 0047. Any compact tuple or result-lookup list below that names only authority scope, source evidence/version, projection status/freshness, or issuance-operation identity is not a reduced bundle: it refers to the same complete bundle, including `issuanceKind`, `authorityTuple`, `membershipVersion`, `issuanceFence`, and exactly the applicable human or automation evidence. The bundle never contains `reservationOwnerId`, `reservationClaimFence`, `targetOwner`, or other execution-tuple fields; those remain separately bound by `postAuthorizationExecutionTuple`.

### Failure and Reconciliation Semantics

Before authorization, the reservation and authorization-recovery paths compare only `preAuthorizationReservationTuple` plus the applicable claim metadata. After the atomic `AUTHORIZED` enrichment, every owner identity, durable owner request, result lookup, rearm, and reconciliation path compares `postAuthorizationExecutionTuple`. Result lookup is therefore a post-authorization owner operation; no pre-authorization path may use it or fabricate the authority fields it requires. The Account-returned authorization and authority-evidence fields are immutable additions to the pre-authorization request data; all members are compared exactly and none is reconstructed from caller assertions, fabricated before issuance, or replaced by a later authority read.

A failed final audit-outcome update does not roll back an already committed domain mutation. Each owner exposes an internal, read-only request-result lookup callable only by the allowlisted Logging and Admin workload. The lookup request carries the canonical complete `postAuthorizationExecutionTuple`: `controlPlaneRequestId`, `mutationDigest`, `issuanceKind`, Account-returned `authorizationReferenceFingerprint`, exact typed `scope`, normalized `actionFamily`, `actionFamilySchemaId`, `actionFamilySchemaVersion`, typed `target`, immutable typed `targetOwner`, typed `expectedVersion`, typed `mutation`, typed `auditReason`, the exact authenticated `workloadIdentity` and actor binding, the applicable automation-policy identity, `reservationOwnerId`, positive `reservationClaimFence`, exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, immutable `authorityEvidenceBundle` containing only authority scope, source transaction/outbox or event version, projection status/freshness, and issuance-operation identity, and every schema-bound typed presence/absence value, including the explicit no-policy value for a human request and any schema-bound absent or null values represented by the digest. The owner may use `controlPlaneRequestId` only to locate a candidate durable idempotency/result record; it then validates `mutationDigest` integrity and every typed tuple member, including normalized action family, schema pair, scope, target, immutable typed `targetOwner`, expected version, mutation, audit reason, workload/actor and policy identity, reservation owner/fence, `authorityTuple`, `membershipVersion`, `issuanceFence`, authority evidence/source versions, and every bound presence/absence value, before returning the result. Any mismatch returns canonical `IDEMPOTENCY_CONFLICT` without exposing the stored result or mutating state. The lookup cannot execute or reauthorize the mutation, so it remains safe after the original human or automation authorization reference expires or is revoked.

Every owner result lookup carries the expected phase and state in addition to the complete authority-bound tuple. An exact tuple with the wrong phase/state is not an existing result for that request: it returns `IDEMPOTENCY_CONFLICT` or the applicable stale-fence outcome and cannot authorize a phase transition.

Logging and Admin retains the original durable intent and reconciles through that result lookup until the owner result can be recorded. The canonical same-identifier rearm is allowed only after a durable terminal `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` result proves either that forwarding never occurred after authorization, that owner handling ended with that explicit no-mutation result before the business mutator was invoked, or that a prior `FENCE_REJECTED` was converted through the fenced proof-validation transition below. An `IDEMPOTENCY_CONFLICT`, an unconverted `FENCE_REJECTED`, or any mismatch in the complete post-authorization authority-bound tuple is not rearmable. A pre-authorization `ACCOUNT_AUTHORIZATION/NOT_EXECUTED_BEFORE_AUTHORIZATION` record is terminal and requires a new explicit operator request rather than rearm. Before the owner-side rearm CAS allocation, the current owner must complete the fenced same-identifier reference handoff, freshly call `RedeemOperatorAuthorization` for the original opaque Account reference, and validate current authority, membership, any applicable privilege predicate, the exact tuple, and the current owner/gameplay fence; any handoff or redemption failure, expiry, revocation, mismatch, or stale fence prevents rearm. The owner may then atomically rearm that exact result record as one new attempt, allocating only a fresh attempt number, `ownerMutationId`, and fenced execution token while retaining the completed attempt history; it issues no new authorization request or reference. Any other terminal result is replay-only through the read-only lookup. An expired `AUTHORIZATION_PENDING` or `OWNER_EXECUTION_PENDING` claim, missing owner record after owner dispatch, or any other indeterminate phase remains read-only and non-replayable and retains its existing `ownerMutationId`; it never allocates a successor attempt. Durable absence cannot prove that an already dispatched mutation will not commit later, and authority revocation or expiry prevents rearm rather than creating a fresh reference to replay the old write.

`FENCE_REJECTED` is the initial wire/status outcome for a stale owner or fence and is non-rearmable only after the rejecting owner atomically persists that outcome with immutable no-accept/no-commit proof for the exact owner attempt, observed owner/gameplay fence, and complete tuple. The owner must not emit `FENCE_REJECTED` before that durable proof exists. If the proof is absent, incomplete, or inconsistent, the durable request remains `OWNER_EXECUTION/OWNER_EXECUTION_PENDING`; it cannot be replayed, converted to `NOT_EXECUTED`, or rearmed. If the owner loses its lease afterward, exactly one CAS-selected recovery owner with a newer owner fence may validate the persisted proof, confirm that the rejecting owner can no longer commit, and transition `OWNER_EXECUTION/FENCE_REJECTED` to terminal `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION`. Logging and Admin, a caller, or a recovery reader without the fenced owner-recovery CAS may not synthesize or advance that transition. Until the rejecting owner or qualifying recovery owner records the terminal outcome, a valid `FENCE_REJECTED` remains non-rearmable.

Operator-visible states must distinguish at least:

- **not executed before authorization** — `ACCOUNT_AUTHORIZATION/NOT_EXECUTED_BEFORE_AUTHORIZATION` is a terminal reservation outcome proving that no opaque Account authorization reference exists and no owner-forward call can still occur. It is not eligible for rearm; a new explicit operator request is required;
- **not executed after authorization** — `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` proves that forwarding or owner handling ended without invoking the business mutator, either directly or through the fenced validation of an atomically persisted `FENCE_REJECTED` no-accept/no-commit proof. An `IDEMPOTENCY_CONFLICT` or unconverted `FENCE_REJECTED` cannot produce this state. This is the only `NOT_EXECUTED` form eligible for rearm, after the current owner completes the fenced reference handoff and fresh `RedeemOperatorAuthorization` validation for the unchanged tuple, current authority, membership, applicable privilege, and current fence;
- **authorization pending, non-replayable** — `ACCOUNT_AUTHORIZATION/AUTHORIZATION_PENDING` means Account issuance was dispatched or may be in flight and no durable Account response or phase-specific terminal no-mutation proof exists. Recovery is limited to the read-only Account reference lookup;
- **owner execution pending, non-replayable** — `OWNER_EXECUTION/OWNER_EXECUTION_PENDING` means the owner call was dispatched or may be in flight and no terminal result or durable effect evidence proves its outcome. Recovery remains read-only and the mutation is never replayed;
- **committed, response lost or outcome pending** — execution may have committed and the same identifier must be queried through the owner result-read contract rather than replaced;
- **failed** — the owner received or claimed the request and a terminal, durable owner result proves execution ended without a successful mutation. A terminal phase-qualified `NOT_EXECUTED` result is not `FAILED`; these outcomes are mutually exclusive; and
- **fence rejected** — `OWNER_EXECUTION/FENCE_REJECTED` is the canonical wire/status outcome with reason `STALE_OWNER` or `STALE_FENCE` because its owner lease or gameplay fence was stale, but only after its immutable no-accept/no-commit proof is persisted atomically with the rejection. If that proof is absent or inconsistent, the request remains `OWNER_EXECUTION/OWNER_EXECUTION_PENDING`, non-replayable, and non-rearmable; it cannot be treated as `FENCE_REJECTED` or either `NOT_EXECUTED` outcome. A newer fenced recovery owner may validate a valid persisted proof and complete `NOT_EXECUTED_AFTER_AUTHORIZATION`, but neither outcome authorizes rearm by itself. The reason is not an alternate outcome name. Audit records, contract tests, and metrics use `FENCE_REJECTED` as the outcome and the stale-owner or stale-fence value as its reason only when the proof exists. This is distinct from `IDEMPOTENCY_CONFLICT`, which is reserved for a mismatch in the authority-bound idempotency tuple.

Clients and operators must not create a fresh request identifier merely because a response timed out. Retention of idempotency results must cover the documented retry and reconciliation window for that action family.

### Bounded Owner Reconciliation

The bounded recovery owner is explicit. For an owner-side execution record, `recoveryOwnerId` is the current domain lease owner; after that lease expires, exactly one CAS-selected replacement owner may receive a fresh owner fence and bounded recovery deadline. That recovery owner may perform only the read-only reconciliation below until durable evidence permits a terminal result or a separately authorized fresh attempt. It cannot transfer the Logging and Admin reservation owner, issue another Account reference, or replay an ambiguous owner call. For pre-authorization Account-reference recovery, `reservationOwnerId` remains the Logging and Admin reservation owner; after its claim expires, only a separately fenced replacement owner of the exact authenticated Logging and Admin workload may call `RecoverOperatorAuthorizationReference` for `ACCOUNT_AUTHORIZATION/AUTHORIZATION_PENDING` with the complete tuple. The domain-owner `recoveryOwnerId` is explicitly forbidden from that pre-authorization call; it may receive the original opaque reference only through the post-authorization fenced handoff and may not issue or replace a reference. For `OWNER_EXECUTION/FENCE_REJECTED`, the domain recovery owner may additionally validate the immutable no-accept/no-commit proof stored by the rejecting owner and perform only the phase-qualified terminal transition to `NOT_EXECUTED_AFTER_AUTHORIZATION`.

When an `AUTHORIZATION_PENDING` or `OWNER_EXECUTION_PENDING` claim expires, or the owner request record is missing, recovery branches on the persisted phase and state before doing anything else. For `ACCOUNT_AUTHORIZATION/AUTHORIZATION_PENDING`, the recovery owner may perform only the bounded, read-only `RecoverOperatorAuthorizationReference` lookup with the complete pre-authorization tuple. For `OWNER_EXECUTION/OWNER_EXECUTION_PENDING`, it may perform only bounded, non-mutating reconciliation of the durable owner record, effect/outcome evidence, mutation marker, and target version/state; it may not call Account issuance/recovery or replay the owner payload. Every recovery CAS and lookup includes the expected phase/state, complete authority-bound idempotency tuple, prior `ownerMutationId` and originating lease/fence when one exists, current lease/fencing evidence, and a fixed attempt and deadline. Read-only reconciliation may validate the prior mutation marker and originating fence after lease ownership changes; the current fence is required only for a new Redis write or a durable phase-qualified terminal commit. It never calls a business mutator, creates a replacement authorization reference, or replays the payload as part of reconciliation.

If durable owner-store effect/outcome evidence bound to the prior `ownerMutationId`, originating fence, exact marker identity, and target-state digest proves that the mutation committed, the owner records or returns `OWNER_EXECUTION/COMMITTED`. A Redis marker plus target state may corroborate that evidence but cannot replace it. This read/validation remains allowed after lease ownership changes; only a new Redis write or durable phase-qualified terminal commit requires the current fence. If a durable terminal record explicitly proves that forwarding never occurred or that owner handling ended before the business mutator was invoked, it may return `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION`; the same result is permitted after the dedicated recovery owner validates an atomically persisted `FENCE_REJECTED` no-accept/no-commit proof and completes the explicit transition above. An `IDEMPOTENCY_CONFLICT`, unconverted `FENCE_REJECTED`, or ambiguous result cannot produce that state. The original reference remains the only possible rearm authority while its authorization is valid. After authorization expiry or revocation, the only permitted operation is the allowlisted read-only owner result lookup against the exact canonical `postAuthorizationExecutionTuple`; if no exact terminal result exists, the request remains non-replayable with no forward, owner mutation, or other continuation and requires a new explicit operator request plus fresh Account authorization. An expired `ACCOUNT_AUTHORIZATION/AUTHORIZATION_PENDING` or `OWNER_EXECUTION/OWNER_EXECUTION_PENDING` claim, missing owner record after dispatch, absent Redis projection/marker with no terminal result, or conflicting evidence remains in its persisted phase and is non-replayable; it is never converted to a phase-inappropriate `NOT_EXECUTED` result and never silently applied again. The bounded read-only result is the no-double-apply rule for owner recovery. A later mutation requires a new explicit operator request and authorization unless the exact original request has terminal `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION`, a still-valid authorization, and satisfies the narrowly bounded same-identifier rearm rule above.

### Region-Scoped Game Session Writes

A Game Session request that mutates region-scoped tick or coordination state executes at the current lease owner under the current gameplay fence. A stable front end locates and forwards to that owner; it does not mutate region-owned state itself. A stale owner or stale fence may atomically record `OWNER_EXECUTION/FENCE_REJECTED` only with durable no-accept/no-commit proof persisted in the same owner transaction; without complete consistent proof, the request remains `OWNER_EXECUTION/OWNER_EXECUTION_PENDING` and cannot replay or rearm. A rejecting or newer fenced recovery owner may complete `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` only after that proof is validated; it does not authorize same-identifier redelivery. A later mutation requires a new request identifier unless the general reconciliation rule has produced the phase-qualified terminal `NOT_EXECUTED_AFTER_AUTHORIZATION`. An ambiguous timeout follows read-only reconciliation and is not replayed.

Owner-side admission, feature-flag, and tick control RPCs are `internal_workload` calls under this contract. Scopes or action families that cannot yet satisfy this durable, idempotent, fenced contract are rejected as unsupported rather than implemented through a weaker direct-write path. Forwarded owner-mutation families such as `ToggleFeatureFlag` and per-instance tick mutations remain unavailable/gated until their action-family schema, shared cross-language `mutationDigest/v1` golden vectors, and Account authorization-reference issuance/redemption flow exist. The separate `/moderation/actions` and `ApplyModerationAction` policy-input/audit path remains unavailable/gated until its action-family schema, shared cross-language `mutationDigest/v1` golden vectors, Account authorization-reference issuance, and Logging & Admin receiving-boundary validation/redemption exist. It is not an owner-side enforcement mutation, and the live `EvaluateModerationPolicy` read remains separate owner enforcement input; moderation enforcement and quota override owner contracts remain hypothetical target coverage until their routes and owner APIs exist.

### Moderation Policy-Input/Audit Boundary

`/moderation/actions` and `ApplyModerationAction` are a Logging & Admin-owned policy-input/audit path, not a forwarded domain mutation. Account owns issuance of the Account authorization reference, and Logging & Admin validates and redeems it at the receiving boundary before the path can persist policy input and audit evidence. This path does not require or perform domain-owner redemption or enforcement. The separate live `EvaluateModerationPolicy` read remains input at the current Account, Game Session, and Social & Groups enforcement boundaries; versioned propagation and domain enforcement remain target-state work.

### Redis-Backed Owner Mutations

The Redis-backed owner record uses the same canonical complete `postAuthorizationExecutionTuple` defined above; Redis markers, key presence, and command responses never replace its `issuanceKind`, immutable typed `targetOwner`, `authorityTuple`, `membershipVersion`, `issuanceFence`, `reservationOwnerId`, `reservationClaimFence`, or immutable authority evidence/source versions.

Coordination Redis is a volatile projection, not the durable owner of an operator mutation. Any supported action that materializes state in Redis must first create or claim a durable owner request record containing the canonical complete `postAuthorizationExecutionTuple` (`controlPlaneRequestId`, `mutationDigest`, `issuanceKind`, Account-returned `authorizationReferenceFingerprint`, exact typed `scope`, normalized `actionFamily`, `actionFamilySchemaId`, `actionFamilySchemaVersion`, typed `target`, immutable typed `targetOwner`, typed `expectedVersion`, typed `mutation`, typed `auditReason`, exact `workloadIdentity`, applicable workload/policy identity, exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, `reservationOwnerId`, positive `reservationClaimFence`, immutable `authorityEvidenceBundle` containing only authority scope, source transaction/outbox or event version, projection status/freshness, and issuance-operation identity, and every schema-bound typed presence/absence value), desired mutation, `phase`, `state`, `ownerMutationId`, current owner/lease identity, fencing token, lease expiry, and terminal result, together with durable write-ahead and effect evidence sufficient to distinguish a committed effect, an unstarted attempt, and an indeterminate attempt. Atomic mutation-plus-result commit applies within the authoritative durable owner store; it does not imply a distributed transaction with Redis. The durable record and effect evidence are the source of truth for `ACCOUNT_AUTHORIZATION/AUTHORIZATION_PENDING`, `OWNER_EXECUTION/OWNER_EXECUTION_PENDING`, `COMMITTED`, `FAILED`, `FENCE_REJECTED`, and the two phase-qualified `NOT_EXECUTED` outcomes; Redis key presence or a Redis command response alone is never a terminal result.

The durable record is written ahead of Redis in this order: persist the exact `ownerMutationId`, originating owner fence, target-state digest, intended effect, and `dispatchState=NOT_DISPATCHED`; persist `dispatchState=DISPATCHED` before any call that could reach Redis; then, only after a successful script result or an exact read-only marker/state proof, persist effect evidence bound to that attempt, marker identity, originating fence, target version, and canonical tuple. A durable terminal result is written only from that evidence and with the current durable owner fence. A crash with `NOT_DISPATCHED` and durable proof that the old claimant can no longer dispatch reconciles to `UNSTARTED`; a crash after `DISPATCHED` and before a script result is `INDETERMINATE` unless exact durable evidence proves no dispatch could occur; a crash after an accepted script and before effect/terminal persistence reconciles to `COMMITTED` only when the marker and target state exactly match the attempt and tuple, after which the durable effect and result are recorded. If the Redis marker is lost, durable committed effect evidence still supports `COMMITTED`; a missing marker with only write-ahead or dispatch evidence is `INDETERMINATE`, never `UNSTARTED`, and is never replayed. These classifications are produced by read-only reconciliation of durable evidence and current Redis state; reconciliation does not call the business mutator or Lua script, and an indeterminate attempt remains non-replayable.

Before invoking Lua, the durable owner store validates the complete tuple, phase/state, current owner claim, effect identity, and authorization evidence. The registered Lua script validates only Redis-local inputs: the current Redis lease/fencing token, the Redis-resident marker identity, the target key's current version/state, the supplied `ownerMutationId`, and the supplied effect digest. It cannot read or infer durable tuple, authority, or phase evidence and cannot authorize the operation by itself. After those local checks it atomically writes the desired Redis state and its mutation marker. A duplicate with an exact match for the canonical complete `postAuthorizationExecutionTuple`, including `issuanceKind`, normalized `actionFamily`, schema identifier/version, typed target, immutable typed `targetOwner`, expected version, mutation, audit, every schema-bound presence/absence value, reservation owner/fence, and `mutationDigest` integrity, returns the existing marker/result; any tuple or phase difference is rejected with canonical `IDEMPOTENCY_CONFLICT` without mutation. A stale owner or fence may produce `FENCE_REJECTED` only when the owner atomically persists that rejection and its immutable no-accept/no-commit proof in the durable owner record; absent or inconsistent proof leaves `OWNER_EXECUTION/OWNER_EXECUTION_PENDING` and non-replayable. After lease loss, a newer fenced recovery owner may validate valid proof and transition only `OWNER_EXECUTION/FENCE_REJECTED` to `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION`. This creates an explicit cross-store reconciliation window: the durable owner record remains `OWNER_EXECUTION/OWNER_EXECUTION_PENDING` while the Redis projection may already contain the fenced marker and desired state. Read-only reconciliation validates the marker and desired state against the prior `ownerMutationId`, originating fence, immutable typed `targetOwner`, and the persisted canonical complete tuple, even after lease transfer; the current fence is required only when issuing a new Redis write or durably committing the terminal owner result. `OWNER_EXECUTION/NOT_EXECUTED_AFTER_AUTHORIZATION` is allowed only when a durable terminal outcome proves that no mutation marker or target-state change committed under this request; an absent or ambiguous marker without terminal evidence remains `OWNER_EXECUTION/OWNER_EXECUTION_PENDING` and non-replayable.

Crash and ownership recovery use the same durable record and request identity. A crash before the Account call is `ACCOUNT_AUTHORIZATION/NOT_EXECUTED_BEFORE_AUTHORIZATION` only when durable execution evidence proves that authorization could not have been issued; for Redis execution, a crash before the durable `DISPATCHED` write reconciles to `UNSTARTED` only when the old claimant is fenced and the write-ahead record proves no script call could occur. A crash after `DISPATCHED` but before the Redis script response is `INDETERMINATE` unless exact durable no-dispatch evidence exists. A crash after the script but before effect or terminal-result persistence is reconciled by the current lease owner from durable effect evidence, the mutation marker, the prior `ownerMutationId`, its originating fence, immutable typed `targetOwner`, target version, and the unchanged canonical complete `postAuthorizationExecutionTuple` plus `mutationDigest` integrity, not by issuing a new mutation; an exact marker/state match permits durable `COMMITTED`, while a lost or conflicting marker without durable committed-effect evidence remains `INDETERMINATE`. Lease loss fences the old owner from both the Redis script and durable terminal commit; after lease expiry, the new owner must perform the bounded read-only reconciliation above and may not replay the same `ownerMutationId`. A Redis reset or lost projection is repaired from durable effect/outcome evidence when available; if that evidence is absent, recovery remains indeterminate and does not recreate the operator effect. No terminal result may claim either phase-specific `NOT_EXECUTED` outcome while an old owner could still commit, and no `COMMITTED` result may depend on an unreconciled Redis mutation.

### Availability Boundary

Elasticsearch, Prometheus, Jaeger, Grafana, Kibana, Alertmanager, and similar observability systems may assist investigation, but are not part of write success, owner durability, idempotency, or reconciliation. For a forwarded owner mutation, successful authorization and execution require all three durable authorities: the Logging and Admin operation record, Account's protected authorization-reference and authority record, and the owning domain's authoritative request/result and effect store. None may be reconstructed from observability data or substituted by either of the other two. `/moderation/actions` and `ApplyModerationAction` are the distinct Logging & Admin-owned policy-input/audit path: it ends after Account authorization-reference validation/redemption plus Logging & Admin persistence of policy input and audit evidence, requires no domain-owner execution or domain-owner durable store, and cannot be described as a forwarded owner mutation.

## Consequences

- An accepted operator request is auditable before execution and can be reconciled after crashes or lost responses.
- Each owner needs a durable request-result record or equivalent atomic idempotency mechanism for supported operator actions.
- Logging and Admin remains a coordinator and audit owner, not a second owner of domain state.
- The protocol adds durable writes and coordination latency to low-volume operator actions, not to ordinary gameplay processing.
- Cross-service atomic rollback is deliberately absent: a committed owner mutation remains valid while a missing final audit outcome is repaired.
- Region-scoped remediation cannot bypass lease ownership even when invoked through an externally stable endpoint.

## Alternatives Considered

### Best-Effort Forwarding with Audit Afterward

Rejected because an audit outage could allow unaudited mutation and a lost response could encourage a duplicate effect.

### Distributed Transaction Across Logging and Admin and the Owner

Rejected because it would couple availability and storage protocols across services without eliminating the need for idempotent recovery.

### Logging and Admin Owns the Authoritative Mutation

Rejected because it duplicates domain state and bypasses owner-side invariants, current authority, and gameplay fencing.

### Let the Stable Game Session Front End Mutate Region State

Rejected because the front end is not the lease owner and cannot safely serialize a write with region tick execution.

## Implementation and Proof Obligations

The current implementation is partial. Each supported operator-action family must demonstrate:

No complete-authority proof may substitute a digest, current owner lookup, or partial identity for this tuple.

- Current WorldLifecycle evidence is not full support for this ADR. `WorldLifecycleCommandServiceImpl.prepareWorldInstance` looks up by `(tenantId, gameInstanceId)` and compares the prepared fields, including `controlPlaneRequestId`; an exact prepared duplicate returns the existing snapshot, while a mismatch currently returns `INVALID_ARGUMENT`, not request-keyed `IDEMPOTENCY_CONFLICT`. Activation and failure are guarded by lifecycle epoch/state but have no complete request-tuple record. Termination uses `terminationRequestId` for state transitions and repeated terminal reads, but does not yet provide a durable terminal result/fingerprint for every retry or prove that a same-request retry cannot repeat cleanup. `TemporalWorldLifecycleOrchestrator` uses a deterministic tenant/game-instance workflow ID and queries an existing workflow after `WorkflowExecutionAlreadyStarted`, but does not compare a full request digest on prepare; its lifecycle read attaches Temporal describe metadata to a fallback domain snapshot rather than proving domain-state and workflow-status equivalence. The workflow signals also do not enforce a durable request identity/digest. These paths remain partial and must not be reported as satisfying the target idempotency contract.
- For WorldLifecycle to satisfy this ADR, each lifecycle command must use a stable request identity and canonical digest for the complete typed request tuple, with durable same-tuple replay and `IDEMPOTENCY_CONFLICT` on mismatch; deterministic workflow identity alone is insufficient. A status response must separately identify the authoritative domain snapshot and Temporal execution metadata, and may claim convergence only after proof that both represent the same lifecycle state and epoch.
- durable intent before forwarding, including trusted actor, reason, exact scope, immutable typed `targetOwner`, mutation, and the phase-appropriate tuple, with the canonical complete `postAuthorizationExecutionTuple` required after authorization: exact applicable `authorityTuple`, independent applicable `membershipVersion`, positive `issuanceFence`, `reservationOwnerId`, positive `reservationClaimFence`, immutable authority evidence/source versions, and every schema-bound typed presence/absence value in addition to the request, digest, scope, schema, workload/policy, and other typed fields;

- for `/moderation/actions` and `ApplyModerationAction`, Account authorization-reference issuance plus Logging & Admin receiving-boundary validation/redemption, without treating domain-owner redemption or enforcement as part of the policy-input/audit path;

## Reversibility and Revisit Triggers

Individual action families can migrate to another durable command mechanism while preserving their request identifiers and result history. Revisit this decision if write volume makes synchronous intent-and-forward coordination material, a durable command bus supplies equivalent authorization and outcome semantics, or an action genuinely requires atomic mutation across multiple domain owners rather than one authoritative owner plus correlated audit.
