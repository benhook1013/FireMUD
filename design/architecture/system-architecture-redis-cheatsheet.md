# FireMUD Redis Cheat Sheet

This cheat sheet is the **front door** for Redis-related design and operations. It summarizes key prefixes, roles, and docs so contributors can quickly find the right reference.

Treat it as a **routing map and curated subset**:

- Canonical coordination/reset details (including reset-tolerance classes) live in the reset policy matrix and any extended catalogs in `system-architecture-redis-reset-and-recovery.md`.
- Canonical cache/rate-limit prefix details (including correctness class and reset behavior) live in the Cache/Rate-Limit Key Catalog in `system-architecture-redis-cache.md`.
- When adding new prefixes, always update the canonical catalog first, then reflect representative entries here as needed for discoverability.

## Implementation Status

The Account issuer, account, tenant, and membership generation projections and issued-token projections shown below are required target state; these equivalent Redis projections and their repair workflow are not currently implemented and proven end to end. Reset recovery must rebuild and verify these projections from Account durable authority before post-reset smoke gates and public `resume` authorization, and protected traffic remains closed when the projections are missing, stale, malformed, mismatched, or poisoned. Set-if-greater remains valid only for missing or lower projections; a projection greater than Account durable authority must be quarantined or replaced through an Account-owned audited workflow, recreated from durable authority, and accompanied by immutable per-scope evidence and verification before protected traffic reopens. The `sessionctx:*` row describes current implementation-local bootstrap/session-context keys, not gameplay authority.

The bounded public recovery contract is target state in the current repository. `continueRecovery(operationId, expectedPhase=ready_to_reopen, maintenanceLockToken, evidenceRef)` records `AWAITING_RESUME`; `resume(operationId, expectedPhase=awaiting_resume, maintenanceLockToken, evidenceRef)` records `RESUME_AUTHORIZED`. The controller then internally transitions `releasing -> finalized`; `SUCCEEDED` is recorded only after `finalized` and all release postconditions. No public recovery scope is currently implemented and proven; region, tenant, and cluster recovery scopes remain target-only until their runtime implementation and end-to-end proof exist.

Destructive reset evidence is split: immutable pre-wipe authorization/fencing evidence is available before the wipe, while `post_reset_replacement_verification` records the replacement endpoint, ACL/configuration, empty keyspace, and health after replacement starts. The controller validates both groups, bound to the same operation and maintenance lock, before protected traffic can reopen.

## Prefix & Role Overview

This table highlights representative prefixes and their intended Redis role. It is not an exhaustive key catalog but should be treated as the **first stop** when introducing new prefixes or reviewing existing ones.

| Prefix (pattern) | Redis Role | Primary Owner / Service | Reset / Lifecycle Notes |
| --- | --- | --- | --- |
| `tick:{tenantRegionTag}:*` | **Coordination Redis** | Game Session Service | Region-scoped tick queues, locks, pending sets, and the narrow `session-binding:<entityId>` bridge. Reset only via **coordination reset** tooling described in [Redis Operations & Migrations](./system-architecture-redis-operations.md) and [Coordination Reset Model](./system-architecture-redis-reset-and-recovery.md#coordination-reset-model); never via ad-hoc `FLUSHDB`/`DEL`. |
| `timer:{tenantRegionTag}` | **Coordination Redis** | Game Session Service | Tick-region timers and scheduled effects. Subject to the same reset and tail-loss envelopes as other tick coordination keys. |
| `retry:{tenantRegionTag}` | **Coordination Redis** | Game Session Service | Retry queues for tick effects. Uses idempotent Lua semantics; reset only through documented coordination reset flows. |
| `tick-executor-lease:{tenantRegionTag}` | **Coordination Redis** | Game Session Service | Region leadership and executor lease. Must obey shard-local Lua rules; coordination resets and failover must follow the patterns in [Tick System and Runtime Design](./system-architecture-ticks.md). |
| `session:game:{tenantGameplayTag}:<gameInstanceId>:<sessionId>` | **Coordination Redis** | Game Session Service | Gameplay session binding and reconnect state. Treated as volatile coordination data with derived expiry; removed when sessions end or expire. Recreated as part of normal login/reconnect flows, not by manual key edits. Every recovery request records either `--preserve-sessions` or `--invalidate-sessions`; no region-scoped reset policy is inferred. Tenant/cluster resets use the same explicit policy. |
| `session:game:index:character:{tenantGameplayTag}:<gameInstanceId>:<characterId>`, `session:game:index:account-tenant:{tenantGameplayTag}:<accountId>`, `session:game:index:tenant:{tenantGameplayTag}` | **Coordination Redis** | Game Session Service | Secondary gameplay-session indexes over the canonical `session:game:*` records. Reset and rebuild behavior follows the owning session keys; these indexes are not separate authority. |
| `sessionctx:*` | **Coordination Redis** | Game Session Service | Bootstrap/session-context keys for pre-auth transport context and authenticated session lookup indexes. Not region-local gameplay authority; gameplay commands still require authenticated `LOGIN` / `PLAY` state and region binding. |
| `session:auth:token:<tokenHash>` | **Coordination Redis** | Account Service | One versioned server-side issued-token record per revocable `control-ui`, player-bootstrap, or receiver-specific private player-delegation JWT as described in [JWT and Token Contracts](./system-architecture-jwt-and-token-contracts.md). Ownership is split from `session:game:*`. Region- and tenant-scoped resets preserve these records; a cluster reset closes protected admission, completes the Account repair/reset cutover, then drops them as physical cleanup and forces reauthentication/token re-issuance. |
| `session:auth:generation:issuer:<issuerId>`, `session:auth:generation:account:<accountId>`, `session:auth:generation:tenant:<tenantId>`, `session:auth:generation:membership:<accountId>:<tenantId>` | **Approved global/account exception: Account durable authority with required Coordination Redis projection** | Account Service | Account advances one positive monotonic `generation` per scope transactionally in its durable store and is the sole writer of the Redis projection. Idempotent set-if-greater is permitted for a missing or lower projection only. A projection greater than durable authority is poison: Account must quarantine or replace that exact scope through an audited workflow, recreate it from durable authority, and emit immutable per-scope evidence/verification; consumers fail closed until the evidence is accepted. Region- and tenant-scoped resets preserve unaffected projections but verify affected scopes; a cluster reset may discard projections only after the Account repair/reset cutover and must rebuild and verify every affected scope before reopening. |
| `gateway:connect-token:jti:<jti>` and the shared replay-readiness generation | **Coordination Redis** | Spring Cloud Gateway | Security-critical, non-evicting single-use connect-token state. Consumption requires the configured durability acknowledgement. Region- and tenant-scoped resets preserve the shared replay domain. A Coordination Redis replay-continuity loss trigger, including a cluster reset that invalidates this shared state, requires new gameplay handshakes to remain closed for the 30-second maximum connect-token lifetime plus two configured clock-skew intervals, followed by the required disposable-marker and durability-acknowledgement proof before a new readiness generation may admit tokens. This quarantine does not apply to unrelated tenant/region reset handling or Cache/Rate-Limit Redis. |
| `remote:{tenantInstanceTag}:<entityId>` | **Coordination Redis** | Game Session Service / Automation & Scripting | Best-effort, TTL-bounded hint marker for remote participation scoped to the complete `<tenantId, gameInstanceId>` identity (typically “this entity has remote follow-ups due”). Default `remote_hint_ttl_ms = 60_000`. Region-scoped resets leave instance-scoped hints intact; tenant/cluster resets resolve every game instance from the durable scope inventory and enumerate `remote:{tenantInstanceTag}:*` per instance before removal. No tenant-only remote key family exists. |
| `script-scheduler:{tenantRegionTag}:lastTickId` | **Coordination Redis** | Automation & Scripting Service | Tracks tick heartbeat consumption. Treated as coordination metadata; adjustments should go through documented automation tooling, not manual writes. |
| `tick-events:{tenantRegionTag}` and `tick-events-offset:{tenantRegionTag}:<consumerId>` | **Coordination Redis** | Game Session Service / Automation & Scripting | Best-effort tick event stream and per-consumer offsets used only as observer/wakeup hints. `tenantRegionTag` is the opaque encoding of the complete `<tenantId, gameInstanceId, regionId>` scope and must include `gameInstanceId`; no tenant-plus-region alias is valid. The key's `tenantRegionTag` and `<consumerId>` are authoritative for the event-offset scope; each offset payload stores `{tenantId, gameInstanceId, regionId, consumerId, regionEpoch, latestTickId, streamOffset}` and is not a standalone scope identifier. It is discarded before reuse when `regionEpoch` differs from the control-plane epoch. Stream retention is capped (default `tick_events_maxlen = 2048` per region). Correctness derives from committed heartbeats/RegionStatus plus durable schedules; missing/duplicated events must not change which schedules eventually fire. |
| `automation:queue:{tenantInstanceTag}:*` | **Cache/Rate-Limit Redis** (single-key ops) | Automation & Scripting Service | Treated as a non-authoritative, best-effort queue on Cache/Rate-Limit Redis that must not mix with coordination prefixes in a single Lua call. Reset via automation tooling or cache-level maintenance; see [Redis Cache & Rate Limiting](./system-architecture-redis-cache.md) and [Redis Architecture](./system-architecture-redis.md#redis-as-a-volatile-state-layer). |
| `automation:quota:<tenantId>:<scriptId>` | **Cache/Rate-Limit Redis** | Automation & Scripting Service | Best-effort per-script quota counters. Safe to drop; budgets are re-established from configuration and durable state. |
| `automation:tenant-budget:<tenantId>:tier:<tier>` | **Cache/Rate-Limit Redis** | Automation & Scripting Service | Best-effort per-tenant live execution budget counters. Safe to drop; counters are re-established from configuration and durable work state. |
| `automation:test:capacity:<tenantId>:*`, `automation:test:capacity:cluster*` | **Cache/Rate-Limit Redis** | Automation & Scripting Service | Best-effort dry-run/test capacity counters and leases. Safe to drop; leases are bounded and protect test traffic from starving live automation. |
| `inventory:<tenantId>:<containerId>` | **Cache/Rate-Limit Redis** | Entity Management Service (target-state) | Cached inventory/container aggregates. Safe to evict; writers must respect TTL and invalidation rules. Never stored on Coordination Redis. |
| `character-cache:<tenantId>:<characterId>` | **Cache/Rate-Limit Redis** | Entity Management Service (target-state) | Cached character graphs for hot reads. Versioned Class A cache; eviction/reset only affects latency. |
| `world-dynamic:<tenantId>:room-dynamic:<gameInstanceId>:<roomInstanceId>` | **Cache/Rate-Limit Redis** | World Management Service | Cached room-scoped dynamic world state. Versioned Class A cache validated against `roomDynamicVersion`; safe to drop but must be rebuilt from authoritative World Management state. |
| `room:<tenantId>:<gameInstanceId>:<roomInstanceId>` | **Cache/Rate-Limit Redis** | World Management Service | Cached room topology snapshots/navigation slices scoped to a running instance. Versioned Class A cache; safe to drop and recompute from PostgreSQL. |
| `view:room-look:<tenantId>:<gameInstanceId>:<roomInstanceId>` | **Cache/Rate-Limit Redis** | Game Session (LOOK aggregates) | HOT-path cached room views. Class B, TTL-only caches owned and accessed directly only by Game Session; non-authoritative and safe to recompute. Game Logic consumes LOOK results via gRPC and does not read this prefix directly. |
| `chat:say:<tenantId>:<characterId>`, `chat:tell:<tenantId>:<conversationId>`, `chat:guild:<tenantId>:<guildId>`, `chat:account:<tenantId>:<accountId>` | **Cache/Rate-Limit Redis** | Social & Groups Service | Short-lived chat history buffers. TTL-only, reset-tolerant caches; authoritative history (where required) lives in PostgreSQL and clients must tolerate gaps after resets/TTL truncation. |
| `ratelimit:<tenantId>:<bucket>:<timeWindow>[:<shard>]` | **Cache/Rate-Limit Redis** | Spring Cloud Gateway / edge services | Gateway and API rate-limit buckets. Reside only on Cache/Rate-Limit Redis; eviction is acceptable within documented behavior. |

When introducing **new prefixes**, update the owning service design doc and ensure the prefix is consistent with the role and reset expectations above.

The “shared replay-readiness generation” wording in the table is an explanatory alias for the canonical `replayAdmissionFence`; it is not a second key or field.
For tick prefixes, `tenantRegionTag` is a naming alias, not a reduced scope: it must encode `tenantId`, `gameInstanceId`, and `regionId` in a stable, collision-free form. The event stream and offset rows are especially sensitive because omitting `gameInstanceId` would merge wakeups and baselines for otherwise independent game instances.
