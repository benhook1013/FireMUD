# FireMUD Scripting & Automation: Cross-Service Contracts

This document defines the **non-negotiable contracts** that make the scripting DSL, Automation & Scripting Service, Game Session tick system, and operator tooling work as a single end-to-end system.

Document conflict resolution order is defined in `design/architecture/system-architecture-scripting-normative-contract-tables.md#document-precedence-normative`. This document defines the cross-service invariants layer in that precedence model.

The accepted script-transition decisions applied by this contract are [ADR 0103](./decisions/adr-0103-single-authority-script-pins-with-exact-version-execution.md), [ADR 0106](./decisions/adr-0106-epoch-fenced-script-rollback-without-routine-gameplay-pause.md), [ADR 0107](./decisions/adr-0107-stage-aware-script-dead-letter-recovery.md), [ADR 0108](./decisions/adr-0108-no-degraded-script-admission-without-authoritative-pin.md), [ADR 0109](./decisions/adr-0109-game-session-owned-script-rollout-history.md), [ADR 0110](./decisions/adr-0110-explicit-opt-in-schedule-continuity-across-script-transitions.md), [ADR 0111](./decisions/adr-0111-unified-dsl-with-distinct-embedded-script-and-plugin-lifecycles.md), [ADR 0114](./decisions/adr-0114-command-plan-preview-dry-run-isolation.md), [ADR 0116](./decisions/adr-0116-routine-component-migration-and-explicit-emergency-revocation.md), [ADR 0119](./decisions/adr-0119-epoch-fenced-per-instance-plugin-activation.md), and [ADR 0120](./decisions/adr-0120-owner-read-first-control-plane-notifications.md). Their implementation and proof gaps remain explicit below.

## Implementation Status

The current evaluator supports a bounded emitted-command collection per pre-DSL trigger record, assigns each emitted command a local ordinal, and attempts handoff for each command independently. `command_count_exceeded` is reserved for an actual configured output-count limit. The current evaluator path persists `command_count_exceeded` as both `finalOutcome` and `finalReason`; alignment with the canonical `finalStage=DSL_EVAL`, `finalOutcome=sandbox_error`, `finalReason=command_count_exceeded`, and Table 4 output-budget metric remains an implementation and focused-proof gap. The live Game Session handoff still omits `scriptPinEpoch`, `commandOrdinal`, and the complete Trigger/Command-Handoff Identity, so end-to-end per-command deduplication, fence proof, and independent progress remain unproved. The complete Command-Handoff Identity remains the target contract; `(automationDispatchId, commandOrdinal)` is only its final pair and is not a standalone identity.

## Contracts

### 1) Tick Queue Ownership (`tick:*`)

- The Game Session Service is the **only** service that writes to `tick:{tenantRegionTag}:*` coordination keys and per-entity tick queues.
- The Automation & Scripting Service never mutates `tick:*` keys directly (including via Redis Lua). It hands off script-generated commands to Game Session via internal gRPC. Game Session owns the executable tick-key builders, Lua, invocation boundary, and tick invariants; the ADR 0176 target shared foundation contributes only the common contract schema, outcome vocabulary, Redis-role/prefix-owner and compatibility metadata rules, aggregated registry, `KEYS`/`ARGV` and descriptor/slot validation, and repository aggregation of owner adapters and focused tests for that owner-local implementation. The current shared foundation and aggregated registry are not implemented, so this target validation must not be reported as current evidence.

### 2) Script Work Item vs Tick Command Boundary

- A **script work item** is the post-DSL output staged by Automation & Scripting (domain commands + metadata such as `scriptId`, `scriptPatchVersion`, and `scriptEventId`). It preserves the immutable source Trigger Identity, including the source `regionId` and `regionEpoch` when applicable; any enqueue or current-routing identity is carried separately and must not overwrite the source trigger fields.
- A **tick command** is a unit of work that has been accepted into an entity’s tick queue by Game Session and will be executed under tick locks and replay semantics.
- **Target-state command handoff:** Every script work item that emits gameplay commands receives one stable `automationDispatchId`, and each emitted command carries a deterministic `commandOrdinal` under that dispatch. The pair is only the final discriminator within the complete Command-Handoff Identity; one handler may fan out into multiple commands, and a pair without its complete source/target runtime identity, including playable-state namespace IDs, is not a command identity. Source and target scope evidence is retained and exact-validated alongside that identity but does not participate in identity or deduplication.
- **Target-state command handoff:** The complete Command-Handoff Identity is the canonical identity for evaluated child-dispatch handoff deduplication, execution-fence reporting, replay selection, and correlation. It is not the downstream effect guard: authoritative effect idempotency uses the root `EffectId`, typed operation, exact target aggregate, and stored/compared immutable request digest, with conflicts failing closed. The `(automationDispatchId, commandOrdinal)` pair is only a display suffix and is insufficient by itself; `automationDispatchId` identifies a dispatch group, and `scriptEventId` alone must never identify a fan-out command. See [Implementation Status](#implementation-status) for the current evaluator boundary.

Target-state handoff linkage uses the complete Command-Handoff Identity: complete source/target runtime identity, including playable-state namespace IDs, plus `automationDispatchId` and `commandOrdinal`. Separately persisted source/target scope evidence must exact-validate alongside the identity but is excluded from identity and deduplication. The current implementation is narrower than this target: because Trigger Identity and `commandOrdinal` are not carried end to end, current live linkage and retry diagnostics use the pre-DSL parent `outboxWorkItemId`, `gameSessionCommandId`, available `automationDispatchId`, and `script_event_audit`. This fallback is not complete command-level deduplication or replay evidence. The remaining gap is tracked under `AS-1.5` and its Game Session handoff dependency in the [automation and scheduler runtime tracker](../project-management/implementation-tracking/automation-and-scheduler-runtime.md#capability-status).

- **Remote follow-up tuple binding:** For a distinct target game instance, the originating exact `(scriptPatchVersion, scriptPinEpoch)` is retained as immutable source provenance and rollback-fence evidence. Before target-side Automation admission, Game Session revalidates that source tuple, freezes the target instance's current exact tuple, and binds both to the target delivery/claim and immutable request/dedupe evidence. The target tuple populates the target event/handler Trigger Identity and target-side script admission/execution fences; the source tuple never substitutes for it. Retries reuse both frozen tuples, with source or target displacement/conflict failing closed, unavailable authority remaining retryable and non-admitted, and target `UNPINNED` producing no target script work. A same-instance cross-region follow-up uses one exact tuple for both roles.
For semantic target `UNPINNED`, that no-script outcome is a durable/replayable delivery result with no Automation event or target script work. Game Session owns its result encoding, replay, and conflict rules; see the [Game Session remote-follow-up result contract](./microservices/game-session-service/api-contracts.md#service-interactions) and the [normative tuple-binding rules](./system-architecture-scripting-normative-contract-tables.md#remote-follow-up-tuple-binding-normative). It is distinct from unavailable authority, which remains retryable and non-admitted.

Audit and outcomes must distinguish between:

- “DSL evaluated successfully” vs
- “commands were accepted into the tick system”.

Live `script_event_audit.finalOutcome=handoff_accepted` means every required child dispatch was durably accepted by Game Session, not that the DSL merely evaluated or gameplay applied. A valid handler emitting no commands uses `finalStage=DSL_EVAL`, `finalOutcome=completed_no_commands`. Target ADR 0114 isolated preview success uses `finalStage=DRY_RUN_RESULT`, `finalOutcome=dry_run_success`, and creates no handler audit row; the current legacy materialized dry-run path uses `finalStage=DSL_EVAL`, `finalOutcome=dry_run_completed`, `finalReason=dry_run_no_handoff`. Per-command gameplay outcomes remain authoritative in Game Session and are linked through the complete Command-Handoff Identity comprising source/target runtime identity, `automationDispatchId`, and `commandOrdinal`; separately persisted source/target scope evidence is exact-validated alongside that identity but remains outside identity and deduplication, as specified in [ADR 0064](./decisions/adr-0064-stage-qualified-script-outcomes.md).

### 3) Version Fencing (Rollback Safety)

For plugin-backed work, the captured owner `lifecycleRevision` travels with the independent `pluginActivationEpoch` fence through durable persistence, handoff, staged/final effects, retry, replay, and recovery. `lifecycleRevision` is non-identity fence evidence. `pluginActivationEpoch` is not a separate handler Trigger Identity or Command-Handoff Identity field; for plugin-owned schedules, it is instead a tagged input to scheduler candidate, firing-claim, candidate-audit, and derived event-scope `scriptEventId` identity as defined by the [normative identity tables](./system-architecture-scripting-normative-contract-tables.md#table-1-trigger-identity-required-fields). Missing, stale, contradictory, or unavailable lifecycle evidence fails closed.

To make script patch rollback meaningful:

- Every script work item and tick command must carry the effective `scriptPatchVersion` used to produce it.
- Every admitted gameplay/runtime-derived trigger, pre-DSL trigger record, evaluated script work item, schedule/timer firing, emitted command, remote follow-up, staged tick effect, retry, replay, and tuple-bearing audit record must also carry the exact `scriptPinEpoch` captured from Game Session for the instance. A pre-admission fail-closed ingress audit may omit the tuple when authoritative state is unavailable; it records the unavailable reason and must not present a stale observation as exact evidence. Tenant-readiness `onLoad` is the explicit exception because it runs before an instance pin exists. The authoritative selection is the tuple `(scriptPatchVersion, scriptPinEpoch)`, not the version string alone.
- For a distinct-instance remote follow-up, the preceding rule defers to the dual source/target tuple binding: the source tuple remains immutable provenance/fence, while the target tuple governs target work; a same-instance cross-region follow-up retains one tuple for both roles.
- Game Session is the sole durable authority for `(scriptPatchVersion, scriptPinEpoch)` per `(tenantId, gameInstanceId)`. It advances `scriptPinEpoch` for every selection change, including rollback or repinning to a previously used version. Automation readiness, caches, projections, and local active-version observations are non-authoritative.
- On execution, Game Session must enforce a **version fence**:
  - If a command’s `scriptPatchVersion` does not match the game instance’s currently pinned `scriptPatchVersion`, Game Session must not execute it.
  - If a command’s `scriptPinEpoch` does not match the game instance’s current epoch, Game Session must not execute it, even when the patch version is identical.
  - **Target state:** rejection must retain the complete applicable Trigger Identity (`tenantId`, `gameInstanceId`, `playableStateNamespaceId`, `regionId`, `regionEpoch`, `entityId`, `scriptId`, `eventType`, `eventSchemaVersion`, `scriptPatchVersion`, `scriptPinEpoch`, `scriptEventId`, `isDryRun`, plus plugin/binding and scheduler fields when applicable), the parent `outboxWorkItemId` as correlation, and the complete Command-Handoff Identity, including optional distinct target fields (`targetGameInstanceId`, `targetPlayableStateNamespaceId`, `targetRegionId`, `targetRegionEpoch`), so operators can diagnose exactly which fan-out command was dropped. The source and target `playableStateScope` values remain separately retained and exact-validated policy/routing/authorization/migration-fence evidence; they are not Trigger Identity or child-uniqueness fields. A child rejection must not be reduced to one handler-level disposition. The live fallback records the narrower pre-DSL trigger-record, command, and available dispatch fields in the current handoff/audit surfaces until `AS-1.5` is complete.
  - Parent `outboxWorkItemId` and Trigger Identity fields are correlation-only; they are excluded from child uniqueness, deduplication, and replay selection (see the [normative identity tables](./system-architecture-scripting-normative-contract-tables.md#table-2-command-handoff-identity)).
  - Rejected entries must be removed or moved to a bounded dead-letter store with explicit `maxAge`/`maxRows` and alert-backed cleanup cadence.
- Before schedule admission resumes under a new `scriptPinEpoch`, durable or resumable-idempotent reconciliation must fence or terminalize pending old-epoch occurrences and claims, and every old-epoch enqueue attempt must fail. Rollback may still cancel or purge displaced rows asynchronously for bounded resource use, but that cleanup is not the admission or mutation correctness barrier. The epoch fence at each persistence, handoff, staging, replay, and final effect boundary remains authoritative; ordinary player commands and ticks continue unless an explicitly declared unfenced effect requires an exceptional pause.
- For instance-scoped gameplay/runtime ingress, Automation must obtain a bounded-fresh observation of the exact Game Session `(scriptPatchVersion, scriptPinEpoch)` tuple, refreshing its local projection from the authoritative read when required. It must persist both fields with the normalized Trigger Identity and event-scope claim in one Automation-owned local durable transaction before evaluation; a same-version different-epoch claim is distinct and an older epoch cannot be treated as current. This is the ADR 0108 bounded-fresh projection model, not a new globally atomic refresh-and-admit RPC. Tenant-readiness `onLoad` remains the explicit pre-pin exception.
- Any work that references a revocable component, including embedded/core-script and plugin-backed work, must carry and revalidate the applicable component-revocation security-policy fence through durable persistence, handoff, staged/final effects, retry, replay, and recovery boundaries, with an immediate check before gameplay effects. Missing, stale, unavailable, or mismatched fence evidence fails closed. The captured `(pluginActivationEpoch, lifecycleRevision)` pair is an additional independent fence only for plugin-backed work; neither lifecycle fence substitutes for the other or for component-revocation evidence.

### 4) `scriptEventId` Identity and At-Most-Once Dedupe

`scriptEventId` identifies the handler trigger, but it is not the complete idempotency token for “run a handler for this trigger”. Scripting idempotency must use every applicable field in the full Trigger Identity defined in the normative contract tables; `scriptEventId` alone is insufficient.

- **Entity-scoped events** (`onSpawn`, `onEnterRegion`, `onCommand`, custom events) must use every applicable field in the full Trigger Identity after handler resolution, including `tenantId`, `gameInstanceId`, `playableStateNamespaceId`, `regionId`, `regionEpoch` when gameplay/runtime-scoped, `entityId`, `scriptId`, `eventType`, `eventSchemaVersion`, the exact `scriptPatchVersion`/`scriptPinEpoch` pair for gameplay/runtime work, `scriptEventId`, and `isDryRun`. The resolved `playableStateScope` is retained and exact-validated as separate policy/routing/authorization/migration-fence evidence; it is not part of Trigger Identity uniqueness. Plugin handlers additionally require `pluginId`, `pluginVersionId`, and the signed-bundle `bindingId`. These identity fields, not `scriptEventId` alone, define the unique trigger identity; tenant-readiness `onLoad` retains its explicit pre-instance-pin exception.
- For custom or service-specific events, `sourceService` is derived from the authenticated producer/workload identity, participates in the event-scope dedupe identity, and is persisted unchanged in the ingress and handler audit records. It is not a caller-selected identity field; the canonical derivation and applicability rules are owned by the normative contract tables.
- **Scheduler events** (`onInterval`, `onTimerExpire`) must use every applicable Trigger Identity field plus the due point and `triggerMode` so leader catch-up and retries do not double-fire. For tick-cadence scheduling (for example `onInterval` configured in ticks), the due point must be expressed as `dueTickId` in the canonical tick timeline. For wall-clock timers, the due point must be expressed as absolute `dueAt` and still include `regionEpoch` to fence across coordination resets.
- Scheduler identities and durable timer state must also include `gameInstanceId` and `playableStateNamespaceId` for gameplay/runtime schedules. The resolved `playableStateScope` remains separately persisted and exact-validated as policy/routing/authorization/migration-fence evidence, and is not added to schedule or firing identity uniqueness. For plugin timers, `pluginId`, `pluginVersionId`, and the binding-scoped `bindingId` are additionally required so multiple bindings, instances, and plugin-version rollbacks cannot alias timer state.
- After event fan-out, each resolved handler is a separate dedupe and audit unit. A plugin handler is uniquely identified by the full applicable Trigger Identity plus `(pluginId, pluginVersionId, bindingId)`; `pluginId` or `pluginVersionId` alone is never sufficient when one plugin version contributes multiple bindings. The same handler-scoped identity governs `script_event_audit`, quota attribution, timer ownership, and binding-scoped cleanup.
- **Tenant-readiness `onLoad` events** apply only to embedded patch scripts; linked-plugin bindings are excluded from tenant-readiness `onLoad`. Plugin initialization, binding validation, and activation remain in the independently versioned, instance-scoped plugin lifecycle for `(tenantId, gameInstanceId, pluginId)`. These events intentionally omit `gameInstanceId`, `playableStateScope`, `regionId`, `regionEpoch`, and `entityId` because they run before any instance pins the patch. Automation & Scripting generates `scriptEventId` deterministically from the preimage `<tenantId, scriptId, eventSchemaVersion, scriptPatchVersion, eventType=onLoad, isDryRun=false>`. The persisted dedupe/audit Trigger Identity is then `<tenantId, scriptId, eventSchemaVersion, scriptPatchVersion, eventType=onLoad, scriptEventId, isDryRun=false>`.
- `onLoad` handler code may not create durable or semi-durable shared effects, including gameplay/tick commands or handler-owned records in shared stores. Platform-owned execution and readiness state, including required `script_event_audit` metadata, is permitted and required to claim, fence, record, and complete readiness; it is not a handler-created shared effect.
- A stale `onLoad` execution is terminalized under the DSL lifecycle's fencing rule and cannot transition its patch to `READY`. Readiness/publication generations are fences, not execution identity; retry after durable stale terminalization requires republishing a new immutable `scriptPatchVersion`, not minting another execution identity for the stale patch.

For live ingress, only a `DURABLE_RETRY` policy permits callers to reuse the same full applicable parent event identity, including the same `scriptEventId`, for a delayed pre-resolution retry. After handler resolution, a policy-allowed handler retry reuses that handler's full applicable Trigger Identity, including the same propagated `scriptEventId`. `REJECT_VISIBLE` finalizes the current intent and must not reuse that parent identity for delayed retry; `SKIP_RECONCILE` follows its declared reconciliation or catch-up rule and likewise does not reclaim stale intent. For downstream command-handoff retries, target state reuses the complete Command-Handoff Identity comprising the complete source/target runtime identity plus `automationDispatchId` and `commandOrdinal`; separately persisted source/target scope evidence must exact-match but remains outside identity and deduplication. The current live fallback reuses the available pre-DSL trigger-record/command identity and does not claim complete fan-out deduplication. For dry-run/test ingress, server-generated IDs are preferred by default; if caller-supplied IDs are accepted, they must be collision-validated in the dry-run namespace.

Ingress ownership is endpoint-specific and must follow the matrix in `design/architecture/system-architecture-scripting-normative-contract-tables.md#table-1a-event-ingress-scripteventid-ownership-matrix`.

### 4a) Handler Input Manifest Boundary

For a plugin-backed handler, the sealed manifest also retains the captured owner `lifecycleRevision` alongside `pluginActivationEpoch` as independent runtime-fence evidence. Recovery, downstream handoff, and final-effect replay preserve and revalidate both values rather than refreshing lifecycle state. Neither value is a separate handler Trigger Identity or Command-Handoff Identity field; the scheduler-owned candidate/claim/derived-`scriptEventId` use of `pluginActivationEpoch` remains the pre-handler exception defined by the normative identity tables.

The [DSL lifecycle](./system-architecture-scripting-dsl-reference-and-lifecycle.md#read-consistency-contract) owns deterministic evaluation/read consistency. Automation seals one bounded input manifest per resolved handler, including the one-time embedded-script tenant-readiness `onLoad` execution, with the complete applicable owner/runtime context, tenant/script identity, exact `(scriptPatchVersion, scriptPinEpoch)` tuple for instance-scoped work, the applicable component-revocation security-policy fence for any work referencing a revocable component (including embedded/core-script and plugin-backed work), plugin provenance `(pluginId, pluginVersionId, bindingId)` when applicable to instance-scoped linked-plugin work, and, only for plugin-backed work, captured `(pluginActivationEpoch, lifecycleRevision)` as additional independent Automation runtime-fence evidence rather than Trigger Identity, plus trigger facts, pinned artifacts, owner-versioned values, causal floor, and seed version. Tenant-readiness `onLoad` retains its declared pre-instance-pin identity exception. A `readSnapshotToken` is retained only when an individual owner contract uses it, as one manifest input or correlation value. Evaluation-stage recovery may invoke the DSL evaluator again only for eligible gameplay/runtime work under the original pre-DSL trigger record/`scriptEventId`, frozen manifest evidence, and exact admitted immutable graph, outside normal admission; it has no dispatch or child identity before its winning descriptor/outbox commit, which allocates and persists one `automationDispatchId` with canonical ordinals only when commands emit. Tenant-readiness `onLoad` is at-most-once and excluded from evaluation replay. Post-evaluation recovery, downstream handoff, and tick replay must carry the manifest digest/reference and reuse the sealed inputs; work referencing a revocable component carries the applicable component-revocation security-policy fence through evaluation, durable persistence, handoff, staged/final effects, retry, replay, and recovery and revalidates it at each applicable boundary, with an immediate check before gameplay effects. Plugin-backed work additionally carries and revalidates the independent `(pluginActivationEpoch, lifecycleRevision)` pair; neither lifecycle fence substitutes for the other or for component-revocation evidence. They must not fetch newer state or re-enter the DSL. The current cross-service payloads may still carry the narrower token field, which remains an implementation gap rather than universal read authority. Missing or stale required manifest, component-revocation, or plugin-lifecycle evidence fails closed.

Replay evidence also includes the original durable trigger payload, frozen dependency/manifest snapshot, immutable graph and artifact references with their recorded digests. Missing, changed, or unreadable evidence fails closed before DSL evaluation; pre-commit retries preserve the full Trigger Identity, original pre-DSL trigger-record identity, and frozen inputs but have no dispatch or child identity. If commands emit, the first atomic evaluated-descriptor/outbox commit allocates and persists one `automationDispatchId` with canonical ordinals; post-commit retries reuse those identities.

### 5) Metrics Cardinality Guardrails

- `scriptEventId` is for logs, traces, and `script_event_audit` queries.
- `scriptEventId` must not be used as a Prometheus metric label (or any other high-cardinality metric dimension).

### 6) Dry-Run / Test Traffic Safety

Dry-run executions are privileged and must not destabilize production:

- Dry-runs share the same sandbox and loop-safety guards as live traffic.
- Dry-runs do not consume live ScriptQuotaService windows or tenant automation budgets.
- Dry-runs must never contribute to failure-rate circuit breakers that can disable live scripts. Any dry-run/test safety gate must use an always-isolated test-only breaker or gate whose state cannot affect live breaker state or live-script admission; no environment, tenant, or request opt-in may cross that boundary.
- Dry-runs must use an idempotency/audit namespace that is distinct from live traffic (for example, include `isDryRun=true` in Trigger Identity) so test calls cannot dedupe, suppress, or overwrite live trigger records.
- Dry-run/test APIs should default to server-generated `scriptEventId` values to avoid cross-client collision and namespace drift. If a caller-supplied `scriptEventId` is accepted, the service must validate namespace rules and reject collisions with a deterministic application error.
- Dry-run/test ingress must enforce explicit authorization scopes/roles (for example `automation.dryrun.execute`) and must record principal identity in audit fields for privileged use.
- Dry-run/test budget ceilings use the bounded pre-handler admission pair defined in the [normative contract tables](./system-architecture-scripting-normative-contract-tables.md#table-1-trigger-identity-required-fields). After handler work is materialized, capacity denial uses handler-scoped `finalOutcome=quota_denied` with a bounded reason; no separate `DRY_RUN_*` outcome is introduced.
- If dry-run authorization context is missing or invalid, the call must fail with deterministic application error (for example `DRY_RUN_UNAUTHORIZED`) and must not execute DSL evaluation.
- Dry-run/test execution capacity must be isolated from live traffic with separate worker pools, reserved worker shares, or equivalent scheduling partitions so privileged tooling cannot consume the last available live automation capacity.

#### Command-plan preview boundary

[ADR 0114](./decisions/adr-0114-command-plan-preview-dry-run-isolation.md) defines the initial dry-run product as a command-plan preview. It uses the same evaluator and sandbox guards as live work, but accepts an explicit authorized fenced snapshot or fixture bundle and returns the exact handler/version/input identity, snapshot evidence, and ordered valid command descriptors. It performs no live gameplay mutation, live pre-DSL trigger-record or evaluated script work-item queueing, or external side effect. Preview results and audit records use an isolated preview namespace; the concrete endpoint and wire shape remain unspecified here. The legacy `TriggerScriptEvent(isDryRun=true)` path and its handler audit are not this preview contract. Preview identity, audit, quota/breaker accounting, and capacity are isolated from live traffic; any shared workers require a hard reservation or equivalent guarantee. Results must state their fidelity and limitations. The owner-defined schema and policy values for preview-evidence freshness remain pending; consumers must not choose competing local stale limits. This preview-evidence boundary is separate from settings freshness under [ADR 0113](./decisions/adr-0113-bounded-pull-settings-distribution-with-freshness-classes.md). The isolated preview surface and its proof are not yet implemented.

### 7) Reload Backpressure Contract

- During `reloadState=RELOADING`, the Automation & Scripting Service must return an explicit application-level backpressure outcome (not a silent drop).
- Each event-registry entry selects exactly one reload policy. Only `DURABLE_RETRY` low-rate external events may be retried with the same full applicable Trigger Identity, including the same `scriptEventId`, using bounded exponential backoff and jitter:
  - `maxAttempts` must be finite and documented per client.
  - `maxElapsedMs` must be finite and documented per client.
  - Jitter must be non-zero to avoid synchronized retry storms.
- `REJECT_VISIBLE` finalizes the current intent as an explicit rejection and never executes it later; a new business intent must use a new parent event identity. `SKIP_RECONCILE` records the skipped attempt and follows the event's declared reconciliation or catch-up rule; it does not reclaim stale intent.
- Only a `DURABLE_RETRY` response includes a server hint (`retryAfterMs`) and permits reclaiming the same retry-eligible parent claim. A rejected or skipped event has no automatic delayed admission.
- For timer-derived scheduler events, best-effort timer semantics apply; triggers not admitted during reload are not backfilled unless explicitly covered by a bounded catch-up rule.

### 7a) Runtime Scope Isolation

- Tenant-scoped patch readiness (`READY` / `FAILED`) is an eligibility signal, not a runtime execution scope.
- Admission pause, reload backpressure, timer ownership, pin convergence, and plugin lifecycle actions must preserve instance isolation at minimum scope `(tenantId, gameInstanceId)`.
- A deployment may intentionally couple all instances in a tenant only if that invariant is explicitly documented and enforced end-to-end; otherwise one instance's patch transition must not stall unrelated instances.

### 7b) Reload Failure Contract

- When a runtime scope is `reloadState=FAILED`, event ingress is rejected with `admitted=false`, `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE`, and bounded `admissionReason=reload_failed`.
- `reload_failed` is not automatic-retry backpressure: the response has no `retryAfterMs`, the event-scope decision is recorded in `script_event_ingress_audit`, and no handler row, firing claim, or handler Trigger Identity is created. Timer due candidates use their event-scope `scheduleCandidateId` audit instead and create no `scriptEventId`.
- Recovery must durably reconcile the current pin, schedule ownership, runtime scope/epoch, and due-point evidence, then transition `FAILED -> RELOADING` under one idempotent recovery identity. Only a successful atomic reconciliation may transition `RELOADING -> IDLE`; the prior observed patch is diagnostic evidence only and is never a last-known-good execution fallback.

### 8) Plugin Version Fencing and Control-Plane Scope

The canonical executable lifecycle state is `ENABLED`; `DRAINING` is non-admitting but may retain a bounded completion exception. Automation owns both monotonic `pluginActivationEpoch` and owner `lifecycleRevision` at `(tenantId, gameInstanceId, pluginId)`. Every plugin trigger, pre-DSL trigger record, evaluated script work item, schedule/timer row, due candidate, firing claim, remote follow-up, staged command, and gameplay command carries the captured lifecycle revision alongside the activation epoch as fence evidence. Game Session projects the tuple lexicographically by `(pluginActivationEpoch, lifecycleRevision)` and compares it before final execution: `ENABLED` requires the exact current revision, while `DRAINING` accepts only work whose winning admission CAS durably committed the immediately preceding `ENABLED` revision before the durable `DRAINING` admission barrier was created (and therefore before the `DRAINING` transition), under the same exact plugin version and activation epoch. Mere capture or observation of that revision is insufficient. Arbitrary lower revisions, non-executable states, and epoch-advanced transitions reject work. For plugin-owned schedules, `pluginActivationEpoch` is the tagged scheduler candidate, firing-claim, candidate-audit, and derived event-scope `scriptEventId` input, but it is not a separate handler Trigger Identity or Command-Handoff Identity field. `lifecycleRevision` is not Trigger Identity, Command-Handoff Identity, stable schedule identity, or candidate identity.

Plugins are executed by the same runtime engine as scripts and must not rely on weaker rollback semantics:

- Plugin enablement and selected `pluginVersionId` state are explicit per `(tenantId, gameInstanceId, pluginId)`; the executable lifecycle state is `ENABLED`, with `DRAINING` and non-executable states handled by the owner contract. These mutations are controlled by operator control-plane APIs (typically via Logging & Admin driving Automation & Scripting registry APIs).
- Automation owns a monotonic `pluginActivationEpoch` and `lifecycleRevision` per `(tenantId, gameInstanceId, pluginId)`. [ADR 0119](./decisions/adr-0119-epoch-fenced-per-instance-plugin-activation.md) owns the epoch/revision transition matrix, Game Session projection, acknowledgement, and final-execution fence. This local contract carries the captured `(pluginActivationEpoch, lifecycleRevision)` pair through plugin work, preserves and revalidates it at each applicable boundary, blocks new trigger admission on entry to `DRAINING` while allowing exact-fenced completion or recovery of already-admitted work, and rejects displaced work after an invalidating transition. The pair is Automation runtime-state evidence, not a Game Session-owned plugin identity.
- Plugin triggers must follow the same Trigger Identity rules, including `gameInstanceId` and (for gameplay/runtime triggers) `regionEpoch`. For plugin triggers, `pluginId`, `pluginVersionId`, and the contributing `bindingId` are required identity fields; the binding identity is stable within the signed plugin version and is resolved before handler-scoped audit/dedupe.
- Pre-DSL trigger records, evaluated script work items, and tick commands produced by plugins must carry `pluginId`, `pluginVersionId`, and `bindingId` in addition to `scriptPatchVersion`, the applicable component-revocation security-policy fence required for any work referencing a revocable component, and the additional captured `(pluginActivationEpoch, lifecycleRevision)` pair required only for plugin-backed work. These are independent fences: admitted plugin work preserves and revalidates both lifecycle values and the component-revocation fence through evaluation, durable persistence, handoff, staged/final effects, retry, replay, and recovery, with the component-revocation fence checked immediately before gameplay effects.
  - On execution, Game Session must enforce a **plugin version fence** analogous to the script patch fence:
  - Before final gameplay execution, `ENABLED` work must carry the exact current plugin provenance `(pluginId, pluginVersionId, bindingId)` and captured `(pluginActivationEpoch, lifecycleRevision)` pair. Same-version/same-epoch `DRAINING` may retain only already-admitted work whose winning admission/fence compare-and-set durably committed the immediately preceding `ENABLED` lifecycle revision before the durable drain admission barrier was created; mere capture or observation does not qualify. All other provenance or lifecycle-pair mismatches, including arbitrary lower revisions and non-executable or epoch-advanced states, must fail closed. Game Session also consumes fresh current scoped activation/lifecycle, component-policy, component-revocation security-policy, capability-grant, and signer/publication evidence; missing, stale, contradictory, or unavailable evidence fails closed with the applicable established bounded reason (`authority_unavailable`, `component_policy_unavailable`, or `signer_policy_unavailable`), while proven epoch, lifecycle, publication, binding, component/capability, or signer mismatches use the applicable existing reason such as `plugin_activation_epoch_mismatch`, `plugin_disabled`, `plugin_version_not_published`, `plugin_binding_mismatch`, `plugin_component_policy_blocked`, or `signer_revoked`. Game Session consumes the applicable current evidence and does not become the plugin lifecycle authority.
    - **Target state:** rejection must be recorded with `outboxWorkItemId` as explicit parent correlation, the complete applicable parent Trigger Identity (including plugin fields `pluginId`, `pluginVersionId`, and `bindingId`), the captured `(pluginActivationEpoch, lifecycleRevision)` pair as fence evidence, and the complete child Command-Handoff Identity (source/target runtime identity, `automationDispatchId`, and deterministic `commandOrdinal`, including optional distinct target fields) so operators can diagnose exactly which fan-out command was dropped. Source and target scope evidence is retained and exact-validated alongside the child identity but remains outside identity, deduplication, and replay selection. `outboxWorkItemId` and the complete parent Trigger Identity are correlation/diagnostic context only; they are excluded from child uniqueness, deduplication, and replay selection. The rejected queue entry must be removed or moved to a bounded dead-letter store with explicit `maxAge`/`maxRows` and alert-backed cleanup cadence. The live fallback uses the narrower plugin/work-item/command fields currently retained by Automation and Game Session; it must not be described as complete Trigger Identity proof. The remaining target gap is tracked under `AS-1.5` in the [automation and scheduler runtime tracker](../project-management/implementation-tracking/automation-and-scheduler-runtime.md#capability-status).

### 9) Pin Convergence Timeout Contract

- Promotion and rollback orchestration must enforce bounded convergence waiting across Automation and Game Session pin-convergence APIs through the same Game Session-owned workflow family, with immutable `operationKind` distinguishing the transition.
- If convergence is not observed before timeout, the pin-transition workflow enters terminal state `PIN_CONVERGENCE_TIMEOUT`.
- In that state, new Automation admission remains fail-closed for the affected instance until the named `RecoverScriptPinConvergence` timeout recovery path (`PIN_CONVERGENCE_TIMEOUT -> CONVERGING` with the same `controlPlaneRequestId` and the expected timed-out `convergenceAttemptGeneration`) in the [Scripting & Automation: Rollout and Rollback](./system-architecture-scripting-rollout-and-rollback.md#pin-transition-orchestration-state-machine-required), explicit repair, or another repin. Ordinary player-command admission and gameplay ticks continue when their own dependencies and fences are healthy; a full tick pause is exceptional and requires a named unfenced effect or migration boundary.
- For each durable convergence attempt generation that enters the terminal state, emit exactly once:
  - Control-plane event `ScriptPinConvergenceTimedOut` produced by Game Session as producer-of-record.
  - Metric `automation_pin_convergence_timeout_total{service="game-session-service", scope, operation, reason}`, with `service` identifying the Game Session producer and `operation` derived directly from the workflow's existing immutable rollout `operationKind`; a later recovery generation may produce its own event and metric increment, while retries of an existing generation produce neither, and no generation/attempt label is added.
- While that terminal state remains active, each rejected live ingress (`isDryRun=false`) must record event-scope outcome `admitted=false`, `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE`, `admissionReason=pin_convergence_timeout`, and no `retryAfterMs` in `script_event_ingress_audit` and increment the existing `automation_script_triggers_dropped_total` family with the bounded `pin_convergence_timeout` reason and pre-handler dimensions owned by [normative Table 4](./system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix). Dry-run/test ingress (`isDryRun=true`) remains event-scope audit-only in this state and emits no live metric family. This is terminal fail-closed state, not retryable backpressure. These rejected ingresses must not increment `automation_pin_convergence_timeout_total` and must not create a handler-scoped `finalOutcome`.
- Pin-transition Automation pause scope is instance-level: admission pause, convergence checks, and resume operations target `(tenantId, gameInstanceId)`. Region-only pause operations are operational tools and must not substitute for the script epoch fence. `PauseTicks`/`ResumeTicks` are reserved for the exceptional unfenced boundary documented by the rollout owner, not the routine promotion or rollback path.

### 10) Instance Rollout Read Model Ownership

- Game Session atomically owns the current `(scriptPatchVersion, scriptPinEpoch)` and append-only history of every accepted syntactically valid pin, rollback, and repin attempt for `(tenantId, gameInstanceId)`, including immutable unsuccessful validation/preparation attempts that leave the pin/epoch unchanged. Each history record includes `controlPlaneRequestId` bound to the normalized request digest, operation kind, previous/resulting exact tuples, actor/reason when operator-driven, outcome, and commit time. An exact retry returns the stored result and appends no duplicate logical entry; reusing the request ID with a changed digest conflicts before mutation or history append.
- Optional pre-pin candidate-preparation evidence is an immutable Automation-owned attestation bound to the exact `(tenantId, gameInstanceId, controlPlaneRequestId, targetScriptPatchVersion, tenant-READY artifact digest, current readiness revision, applicable policy revisions)`. The existing Game Session pin mutation consumes it only as evidence: when preparation is selected or required, missing, mismatched, or stale evidence rejects, and the commit revalidates the current tenant-`READY` state, artifact digest, readiness revision, and policy revisions. Omitting preparation follows an equivalent commit-time validation path. Game Session remains the sole pin and history authority; a deterministic validation or preparation failure retains equal previous/resulting tuples, does not advance `scriptPinEpoch`, and follows the history/idempotency rules above.
- Game Session exposes bounded authoritative current-pin and paginated rollout-history reads. Automation & Scripting may retain only observed-pin, convergence, and freshness projections for local admission and diagnostics; it must not author `PINNED`, `ROLLED_BACK`, or `REPINNED` history from pre-DSL trigger-record or evaluated script work-item presence or projection refresh.
- Logging & Admin composes Game Session history with Automation readiness/convergence state and presents disagreement as projection or convergence lag. `ScriptPatchPinChanged` is an advisory cache-refresh wake-up only: consumers recover by rereading Game Session's authoritative current-pin and rollout-history APIs, and loss or duplication affects freshness latency only, not Game Session history. The ordinary family has no transactional-outbox or guaranteed durable-delivery contract. A future outbox requires a separately named guaranteed asynchronous consequence or durable consumer adopting [ADR 0083](./decisions/adr-0083-no-general-event-broker-until-measured-adoption-gates.md); it must not silently upgrade this advisory family. The separately named same-transaction `ScriptPinConvergenceTimedOut` producer-capture exception remains governed by its rollout contract. A separate Automation rollout event family is not required for this contract.

### 11) Pin-State Degraded Override Governance

- Admission decisions must fail closed with `pin_state_unavailable` when bounded-staleness pin refresh cannot reach an authoritative source.
- There is no operator stale-pin override. A stale or unbounded local pin, TTL, audit record, or operator reason cannot authorize admission without a bounded-fresh observation ultimately sourced from the authoritative Game Session tuple. Recovery restores Game Session reads/projection delivery or performs an explicit repin after authority returns; ordinary non-script gameplay may continue when healthy.
- A future exception would require a new accepted contract for a short-lived Game Session-issued capability bound to the exact tenant, instance, version, and epoch; no generic flag or stale-cache grace path exists today.

### 12) Dead-Letter Replay Version-Fence Safety

Plugin recovery preserves the captured `pluginActivationEpoch` and `lifecycleRevision` through both evaluation-stage retry and stored-output dispatch. `ENABLED` recovery requires the exact current lifecycle revision; `DRAINING` may recover only work whose winning admission CAS durably committed the immediately preceding `ENABLED` revision before the durable `DRAINING` admission barrier was created (and therefore before the `DRAINING` transition), with the same plugin version and activation epoch. Mere capture or observation of that revision is insufficient. No arbitrary lower revision or work displaced by a non-executable or epoch-advancing transition is recoverable.

- Every recoverable dead letter records an immutable failure stage and the evidence required by that stage. Missing, contradictory, or unreadable stage evidence remains `DEAD_LETTERED`.
- Automation owns a monotonic `failureGeneration` per durable parent `(tenantId, outboxWorkItemId)`. The parent retains its `EVALUATED_COMMITTED` descriptor marker and complete output/child ledger, while a separate parent recovery aggregate records whether that evidence is currently dead-lettered. The first atomic transition of that parent recovery aggregate into `DEAD_LETTERED` initializes it to `1`; each later entry, including a permanent required-child failure after an `EVALUATED_COMMITTED` evaluation or a failure after successful recovery, advances it exactly once in the same transition, while an exact retry/no-op of that transition does not advance it. Dead-letter evidence, request per-item results, recovery claim/attempt identity, successful-recovery evidence, and `already_recovered` bind `(tenantId, outboxWorkItemId, failureGeneration)`. Selectors remain parent-record IDs and the mutation resolves the current generation atomically; `failureGeneration` is not `rowVersion` or `admissionEpoch` and does not extend Trigger Identity or Command-Handoff Identity.
- Evaluation-stage recovery may re-run the DSL only from the original persisted trigger identity and payload, frozen manifest/input evidence, and exact immutable compiled graph identified by the admitted `(scriptPatchVersion, scriptPinEpoch)`; it retains the original pre-DSL trigger-record and `scriptEventId` identity and never resolves `latest` or mutable defaults.
- Post-evaluation recovery never invokes the DSL. It resumes the stored output and child-dispatch ledger, preserving child identities, payload digests, ordinals, and acknowledgements; accepted or terminal children no-op and only unfinished children dispatch. A permanent required-child failure atomically moves the parent recovery aggregate to `DEAD_LETTERED` while retaining the `EVALUATED_COMMITTED` descriptor marker and ledger, making the parent-record selector eligible for `resumed_dispatch` recovery under the current `failureGeneration`.
- Both paths require an exact current match for the admitted patch/epoch, the applicable component-revocation security-policy fence whenever work references a revocable component (including embedded/core-script and plugin-backed work), runtime region/`regionEpoch`, and admitted routing bundle. Applicable plugin identity/version/binding and captured `(pluginActivationEpoch, lifecycleRevision)` are required only for plugin-backed work. Matching patch text under a different pin epoch is ineligible.
- Recovery revalidates those fences immediately before evaluation for the evaluation-stage path and immediately before each post-evaluation dispatch for the stored-output path, with the component-revocation fence checked immediately before gameplay effects. For plugin-backed work, it must additionally revalidate the independent captured `(pluginActivationEpoch, lifecycleRevision)` pair against current Automation-owned epoch/revision evidence, as well as fresh current activation/lifecycle, component-policy, capability-grant, and signer/publication evidence; neither lifecycle fence substitutes for the other. `DRAINING` blocks only new trigger admission; recovery remains eligible only when the work has ADR 0119's canonical durable pre-`DRAINING` admission-CAS/fence evidence and all exact fences and policy evidence pass. Missing, stale, or temporarily unavailable evidence fails closed with established bounded reasons such as `authority_unavailable`, `component_policy_unavailable`, or `signer_policy_unavailable`; a captured-epoch mismatch returns `plugin_activation_epoch_mismatch`; proven lifecycle invalidation such as `DISABLED`, revocation, or policy-driven disablement, publication, component/capability, signer, tuple, or scope mismatches use `plugin_disabled`, `plugin_version_not_published`, `plugin_component_policy_blocked`, `signer_revoked`, `plugin_binding_mismatch`, `script_pin_epoch_mismatch`, or `runtime_scope_mismatch` as applicable.
- `ReplayDeadLetteredWorkItems` accepts bounded explicit parent `workItemIds[]` only; descriptor references and filters remain deferred mutation selectors. Each row returns exactly one `outcome`: `retried_evaluation`, `resumed_dispatch`, `already_recovered`, `recovery_failed`, or `rejected`, together with its resolved `failureGeneration` when the parent is owned. Only a `rejected` row carries `rejectionReason`; `recovery_failed` carries required `failureReason` and no `rejectionReason`, using the established bounded failure vocabulary to describe the terminal failed attempt. `already_recovered` is permitted only when immutable prior successful-recovery evidence binds the same current generation; an older generation's success neither satisfies nor blocks a new current-generation request. An exact retry with the same `controlPlaneRequestId` and canonical request fingerprint returns its stored result, including any `recovery_failed`/`failureReason`, and generation without reevaluating current row status or creating a new attempt. Eligible rows progress independently; ineligible `DEAD_LETTERED` rows remain unchanged. A stable `controlPlaneRequestId`, actor, and reason make duplicate recovery requests idempotent.
- Replay request idempotency binds `controlPlaneRequestId` to the canonical normalized request fingerprint, including the bounded selected `workItemIds[]`, `actor`, and `reason`. An exact retry returns the stored per-row result without work; reusing the request ID with a changed fingerprint conflicts before evaluation or dispatch and cannot alter the stored result.
- Purge is a separate bounded, authorized, audited operation with its own request identity and per-row outcomes. Operators and automation never repair or delete dead-letter rows through direct SQL.

### 13) Output Budget Safety

- A successfully admitted trigger must still be prevented from emitting unbounded work. The canonical versioned/digested component-cost metadata, conservative publish analysis, artifact-pinned caps, and incremental metering contract are owned by [Scripting Runtime Execution](./system-architecture-scripting-runtime-execution.md#static-output-cost-contract).
- At this cross-service boundary, Automation must reject a missing/stale/contradictory artifact-cost digest at the correct ingress or readiness stage, enforce the owner-defined conservative prospective serialized-byte and data-dependent bounds before constructing each output descriptor, and check exact bounded serialized size before atomic persistence.
- Output-budget violations are non-success stage-aware outcomes. Generated output is atomic per resolved handler: no partial descriptor set may be persisted or handed off, and Game Session must never receive a partial handoff presented as successful work.
- Publish-time validation in Game Design must conservatively reject graphs whose bounded worst-case fan-out exceeds the artifact-pinned runtime ceilings. The owner document defines metadata shape and exact failure mapping; this contract only protects the persistence/handoff boundary.

### 14) Handler Charge and Capacity Boundary

The durable charge lifecycle is owned by [Scripting Quotas & Operations](./system-architecture-scripting-quotas-and-operations.md#budget-accounting-rules). Cross-service consumers must preserve its consequences:

- The same durable pre-DSL trigger-record/work-item row for the full Trigger Identity is the sole charge authority; its exactly-once admission and execution-start markers are persisted on that row, not in a separate handler charge record. Immediately before evaluation, Automation acquires the fenced lease and atomically revalidates its fence, durably accepts/claims the run for the executor, persists the execution-start marker, and transitions the pre-DSL row to `EXECUTING` in one executor-acceptance transaction; evaluation begins only after commit. If executor acceptance fails, the transition does not commit and no execution charge is recorded. Duplicate and recovery attempts reuse the durable executor claim, and recovery may reacquire a lease without creating another marker.
- Queued work holds no execution capacity. The capacity lease is separately fenced/reclaimable, and reclaiming an expired lease is not a refund or a new charge.
- `PUBLISH_READINESS`/`onLoad` uses isolated readiness capacity and must not consume ordinary live quota or capacity. Game Session handoff occurs only after Automation's admission/execution markers and capacity checks succeed; Game Session must not charge the handler again.
