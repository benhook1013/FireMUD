# FireMUD System Architecture: CI/CD Pipeline

This document describes the continuous integration strategy for FireMUD using **GitHub Actions**. Every service is built, tested, containerized, and images are pushed to the registry. Deployment to Kubernetes runs through separate workflows so both local and cloud-hosted clusters use the same pipeline but use different manifests per environment.

---

## Goals

- **Automate builds and tests** for all microservices whenever code changes are pushed by running the [`ci.yml`](../../.github/workflows/ci.yml) workflow.
- **Build Docker images** without registry credentials for pull-request smoke, then publish only successful PR artifacts through a trusted workflow; trusted branch workflows push directly to GitHub Container Registry (GHCR).
- **Deploy hosted Kubernetes development/demo environments** through the dedicated preview and dev-demo workflows. [`preview.yml`](../../.github/workflows/preview.yml) builds credential-free per-PR render artifacts, [`hosted-identity-request.yml`](../../.github/workflows/hosted-identity-request.yml) validates and deploys them from the trusted default branch, and [`dev-demo.yml`](../../.github/workflows/dev-demo.yml) manages the fixed `develop` dev-demo environment. Staging and production clusters use Kustomize overlays as described in the Deployment Runbook; the current production implementation applies them via `kubectl` from a secure admin environment, while the accepted steady-state target is an exact-plan-authorized protected executor.
- Treat `dev-demo-cluster` as validation-only infrastructure that is excluded from production promotion evidence.
- Keep the workflow configuration easy to maintain and extensible for additional security scans or nightly jobs.
- **Generate release notes automatically** whenever version tags are pushed.
- **Perform deep static code scanning** with CodeQL on pull requests targeting any base branch, including stacked feature branches, expose the dedicated CodeQL gate for every pull request, and continue running the full analysis on `main` pushes, scheduled runs, and manual dispatches.
- Route AI-assisted pull-request review through the supplied FireController connection according to [PR lifecycle](../developer-workflows/pr-lifecycle.md). CodeRabbit automatic reviews are disabled; operators request complete reviews only when the controller selects a stable target.
- **Benchmark repository hardening** with OSSF Scorecard on `develop` and `main` pushes plus the weekly scorecard schedule.
- **Scan for vulnerabilities** with Trivy during CI runs and scheduled security scans. The scanner step uses explicit Bash pipeline failure handling so saving a report with `tee` cannot mask a vulnerability or scanner error; report upload still runs after failures.
- **Publish coverage feedback** to Codecov from the service validation matrix so pull requests receive patch-coverage status and coverage comments.
- **Run OWASP ZAP baseline scans** against the built web client preview during CI.
- **Publish documentation** to GitHub Pages after successful builds.
- **Create release PRs automatically** using the `release-please` workflow.
- **Propose dependency updates automatically** with Renovate against the `develop` branch across the supported dependency managers.
- **Generate database ERD diagrams** as build artifacts after each run. The [`dev-tools/docs/generate-erd.sh`](../../dev-tools/docs/generate-erd.sh) script writes them to `design/erd/`, and the workflow uploads this directory as artifacts.
- **Cancel superseded substantive runs for the same branch** using a concurrency group so CI resources are conserved and deployment jobs do not race for the same environment. Metadata-only title/body edits skip every job and never replace a required check; see [Required Gates on Metadata Edits](#required-gates-on-metadata-edits).

## Implementation Status

The current executable unconditionally blocks every player-facing production promotion class, including `rollback-compatible`, until all required production evidence and validations are complete; incomplete evidence can never become promotion authority. Static CI validates checked-in evidence shape and available bindings, but it does not yet validate release-manifest presence, schema, or bindings (including the release tag where applicable, source commit, deployment ref, promotion attestation ref, staging deployment record ref, and exact `serviceDigests`). Production promotion remains blocked until that validator exists; target validation must reject missing, malformed, or mismatched manifests. Production preflight also does not yet execute the staging-lineage, expanded backup-readiness, nested candidate recovery-controller, `PREFLIGHT-JWT-INTERIM-001`, `PREFLIGHT-JWT-002`, or `PREFLIGHT-JWT-ROTATION-001` validations behind that block. No rollback classification becomes current promotion authority until those diagnostics, recovery inventory membership, immutable evidence dereferencing, participant, confidentiality, hardening, JWT/JWKS, and controlled-reopen validations are implemented. The [ADR 0177](./decisions/adr-0177-exact-plan-authorized-automated-production-deployment.md) protected executor, ADR 0156 automatic observation/pause, bounded-canary progression, and compatibility-bounded automatic restoration remain target-state-only; current staging and production rollout and rollback remain operator-controlled under the Deployment Runbook.

The manual [Game Session factory inventory qualification workflow](../../.github/workflows/game-session-factory-qualification.yml) and [focused contract](../../dev-tools/tests/game-session-factory-qualification-contract.sh) provide review-only status and proof; the workflow owns its execution and artifact rules.

## Required Gates on Metadata Edits

The Validation, Security, CodeQL, License, and Smoke gates keep their exact branch-protection names for every substantive pull-request event: open, new commits, reopen, and a base-branch change. Their workflows still listen to `edited`, because GitHub reports a retarget as an `edited` event and cannot filter it by field before starting a run.

A metadata-only edit is an `edited` event whose `changes.base` is absent, such as a title or description change. On that event every job in the five workflows is skipped, and each gate job is skipped under a non-required name. The name expression selects `PR Metadata Edit (<gate name>)`; GitHub does not evaluate a skipped job's name, so the check run shows the whole expression text instead, which is still not a required name. The edit produces no check run under a required name. The earlier substantive result keeps its effect only on the exact comparison it validated. If the base has moved and GitHub evaluates checks on a different test merge commit, the new comparison remains held until substantive CI reports the correctly issued required checks for that comparison. A metadata edit neither satisfies a required name nor transplants a result from another test merge. Independently valid runtime smoke retains proof only for the exact event tuple it tested. A failing or pending gate stays failing or pending, and an edit cannot turn a pull request green. A skipped job under a required name would count as passing, which is why the gate must never skip under its required name.

Metadata runs use their own concurrency namespace, so an edit cannot cancel or replace an in-progress substantive run. Completion callbacks that read gate results, such as the [runtime-image refresh](#pull-request-runtime-and-preview-chain), the detached Validation Summary and the Static Analysis Summary, ignore metadata runs: they require the required-name gate job, or exclude runs whose gate check name contains the metadata label.

For the detached Validation Summary, skipping publication is not the same as skipping queue admission. Its workflow enters a concurrency group keyed by the source head before inspecting the detector. A metadata callback can replace the pending summary for a retarget on that head, then skip publication; the retarget can lack a detached summary, but required checks are unchanged. Static Analysis Summary uses a separate per-PR publication queue with `queue: max`.

The Validation Gate temporarily retains one inert, unconditionally skipped native step named `Preserve successful required gate on metadata-only edit` for the default-branch runtime callback that still expects that marker. It does not execute the retired status-preservation machinery or change any check result. Metadata edits skip the entire gate under its non-required name, so the marker cannot qualify them. Remove this marker only after the default-branch callback no longer requires it.

The [required-gate contract](../../dev-tools/tests/pr-required-gate-context-contract.sh) checks the gate names, job conditions and concurrency namespaces for all five workflows.

Account Service and Game Session validation each use four independent matrix partitions. Account retains two test forks per partition. On Linux, Game Session caps `integrationTest` at two JVM forks, bounded by Gradle’s worker count; JUnit methods within each suite remain serial, and other platforms retain their existing single-fork behavior. Each runner compiles every current test source set, selects whole discovered classes with nested classes kept together, and runs the complete service check task graph with fullCheck and existing fork settings. Checked-in historical assignments seed the selectors; newly discovered classes are assigned deterministically so the module’s partitions are disjoint and cover the current compiled class inventory. Each runner publishes run-, tested-source-, attempt-, service-, and partition-qualified JUnit, JaCoCo execution-data, measured production class files, selector, and partial-report artifacts. For pull requests, the tested source SHA is the merge checkout while Actions API head identities refer to the PR head; the aggregate verifies both against the trusted event and canonical run title. Push and manual runs use one SHA for both identities. The read-only service aggregate queries the workflow run and every attempt’s job and artifact metadata with complete pagination, then binds each artifact to the latest effective successful job outcome for that exact run, tested source, native head, service, and partition. GitHub may clone carried jobs into a later attempt with new job IDs and a later raw `run_attempt` while retaining their original execution timestamps. The aggregate therefore keeps the latest effective outcome authoritative and correlates its exact run, native head, job name and execution window with the earliest matching successful attempt before selecting that attempt’s artifact and manifest. A retained earlier successful partition may support a partial retry only when its artifact remains available and its latest effective job outcome is successful; absent or ambiguous provenance, missing artifacts, and failed newer job outcomes hold aggregation, and a newer failure never falls back to an older success. The aggregate verifies both selector and JUnit report unions and requires identical complete production-class inventories and bytes from every measured partition. Missing, extra, symlinked or unequal class files refuse aggregation. The exact Spring annotation-processor sidecar `META-INF/spring-configuration-metadata.json` may accompany the measured class tree but is not bytecode and is not copied into the verified JaCoCo handoff; other non-class payloads remain rejected. It copies one verified measured tree into its fixed build handoff and generates the complete service JaCoCo report from those class bytes and every current test task’s execution data, without recompiling aggregate classes. World Management uses the same provenance and aggregation contract with two whole-class partitions balanced collectively across its unit, integration, and cross-service tasks. The existing Validation Gate requires every selected module matrix group and the corresponding coverage aggregate when any of the three slow services is affected. Ordinary local checks for all three services remain unpartitioned. The historical profiles and saved reports supply candidate grouping only; they do not establish a whole-run saving or available runner capacity.

## Workflow Structure

Workflows live in the `.github/workflows/` directory. A typical pipeline runs on every pull request and on pushes to the long-lived publication branches (`develop` today, and `main` for release-oriented publication paths).

The optional Validation Summary publishes from a trusted default-branch completion callback, outside the original Validation workflow, so comment scheduling cannot delay required-gate resolution. It reconstructs the existing summary from complete exact-attempt job evidence after checking the source workflow/repository and canonical title’s PR number, base SHA, and head SHA against the current PR. It recognizes source-qualified Build and Test module/partition inventories and requires the complete selected partition set and matching aggregate for each affected Account, Game Session, or World Management module. World requires its native two-partition declaration; historical World full-check jobs remain valid without an aggregate. Account and Game Session retain attributable older two-partition and unpartitioned source runs. This optional reporter accepts native empty PR-association arrays; absent, malformed, conflicting, or ambiguous associations cannot publish. With an empty array the historical source base ref remains unknown: the first fresh exact-SHA PR read instead pins the current base ref as a publication fence, rechecked before every write. An available association must agree with the title and current PR; required-gate provenance selectors remain unchanged. It executes no PR code or artifacts and retains only Actions read and PR comment-write permissions. Metadata-only, fork, bot, cancelled, closed, stale, and incomplete sources cannot publish; legacy sources retaining their inline Validation Summary remain solely owned by that inline job until their next normal base carry. The reporter bounds API time and pagination and rechecks the source and PR before each comment write. Native callback execution and timing improvement remain unproved until default-branch deployment and hosted proof.

The optional [Static Analysis Summary](../../.github/workflows/static-analysis-summary.yml) takes one bounded snapshot on each CodeQL or License completion, showing a pending counterpart honestly and updating the same bot comment when its completion arrives. A no-checkout resolver without write permissions validates the PR callback identity before publication enters a PR-number queue. CodeQL and License callbacks for the same PR serialize across heads; different PRs sharing a branch and skipped push callbacks cannot replace that PR’s pending work. An older-head callback for the same PR can join the queue without replacing a waiting publisher; GitHub cancels a new arrival if the queue is full. When it runs, publication snapshots the live PR tuple. An older-base callback for the same head is only a wake signal: it validates its source identity and selects exact current-base/head workflow and check proof before publishing. Current-PR fences and duplicate cleanup remain mandatory; callback cancellation, unavailable API evidence, and the non-atomic final read/write do not establish guaranteed delivery. Required gates are independent of this optional comment.

The optional [PR LOC Report](../../.github/workflows/pr-loc-report.yml) is also a trusted default-branch callback after `CI — Validation` completes. It takes the PR number, base, and head from the `ci.yml` run's canonical title and checks GitHub's native PR association, as Validation Summary does, and acts only on an open, same-repository, non-Renovate PR that still has that exact base and head and on a run that was not metadata-only. It rewrites only the marked LOC section of the PR body with `dev-tools/maintenance/cloc-report.py`, which rechecks that the PR is open on the same refs, base, head, and body and skips while CodeRabbit shows a review in progress (status, check run, or processing comment) immediately before the edit. It skips when metadata inside a complete marked section already matches the head and base. GitHub's body update has no atomic precondition, so the edit is best effort. Each source CI run has its own concurrency group, so callbacks for different runs never cancel each other; a rerun attempt of the same run may replace that run's still-pending callback. Its `GITHUB_TOKEN` edit starts no workflow runs, so it never creates metadata-only gate runs. It is not a gate and adds no check to the PR head.

### Pull Request Runtime And Preview Chain

| Workflow | Execution context | Responsibility | What its GitHub run means |
| --- | --- | --- | --- |
| [`runtime-images.yml`](../../.github/workflows/runtime-images.yml) (`Build Runtime Images`) | Untrusted PR merge commit with read-only repository permissions | Build the PR merge commit locally, run the explicit held-admission qualification, and upload the image archive named for the tested merge SHA and native run attempt | The recorded base/head/merge input was built without registry-write credentials. Successful smoke preserves direct backend `LOGIN` -> `PLAY` -> `LOOK` proof and verifies Gateway/Telnet fail closed; it does not establish successful public admission. The diagnostic exception below provides no passing `PLAY` or `LOOK` proof. See [player-flow smoke boundaries](system-architecture-testing.md#player-flow-smoke-and-reset-boundaries). |
| [`smoke.yml`](../../.github/workflows/smoke.yml) (`PR Smoke Gate`) | PR metadata and Actions API | Decide whether runtime smoke is required and expose the protected `Smoke Gate` by tracking the matching `Build Runtime Images` result | This is a controller and required gate; it does not run a second copy of the runtime qualification. Metadata-only edits skip it under a non-required name and do not dispatch or cancel runtime construction; see [Required Gates on Metadata Edits](#required-gates-on-metadata-edits). |
| [`publish-pr-runtime-images.yml`](../../.github/workflows/publish-pr-runtime-images.yml) (`Publish PR Runtime Images`) | Trusted default-branch `workflow_run` or typed `repository_dispatch` definition | Verify the current PR and exact source artifact identity, then publish immutable `pr-merge-<merge SHA>` tags in GHCR | GitHub displays the default branch because the trusted publisher runs there; its summary identifies the source PR run and base/head/merge SHAs. |
| [`preview.yml`](../../.github/workflows/preview.yml) (`PR Preview Environment`) | PR-scoped untrusted source run | Render and upload a sanitized full-stack chart artifact without deployment credentials | The artifact is bound to the PR head and recorded base/merge SHAs; PR-controlled code never receives cluster or registry credentials. |
| [`hosted-identity-request.yml`](../../.github/workflows/hosted-identity-request.yml) (`Hosted Identity Request`) | Trusted default-branch workflow | Validate the exact source run, current PR base/head/merge, and artifact, wait for the matching merge-scoped images or proven base images, then deploy or retire the PR namespace and report preview access | Only the trusted job receives protected deployment credentials; it never executes PR-controlled code. |

The trust split is deliberate: PR-controlled source can build and execute without package-write authority, while the trusted publisher never checks out or executes PR source. The current base branch ref and the test merge's ordered base/head parents establish the exact tuple for image publication and preview selection; a pull request event or API `base.sha` can lag the branch ref and is not current-base authority for those actions. The required Smoke Gate accepts a successful credential-free smoke run for its verified PR-event base/head/merge tuple. If GitHub supplies no usable event merge SHA or the event base SHA already lags the event merge's parents, the gate instead requires a successful trusted, typed refresh for the verified current base/head/merge tuple. An unrelated base advance after valid event-tuple smoke does not invalidate that tested merge or require the PR head to absorb new dependencies; a changed PR head or base branch requires new proof. The source run records the verified base, head, and merge SHAs, and the merge SHA keys the immutable PR image tag. Ordinary previews remain limited to same-repository, non-dependency-bot pull requests targeting `main` or `develop`. The credential-free runtime producer and required Smoke Gate cover every PR base, including same-repository feature branches, while retaining runtime path classification and an explicit no-op for irrelevant changes. Hosted preview and registry publication retain their separate eligibility policy: a stacked pull request requires the maintainer-controlled `preview:priority` label, an open mergeable state, and a current same-repository base. Completed Validation callbacks qualify long-lived branch pushes or substantive same-repository PR heads against the current branch ref before dispatching child-specific exact base/head/merge runtime refreshes. PR callbacks verify the current native CI attempt and its executed substantive Validation Gate enforcement before reconciling their source PR's current tuple, recovering retarget edits whose event merge cannot qualify. Metadata-only, superseded, or unclassifiable attempts do not reconstruct runtime. PR-completion reconciliation is isolated by source run ID and attempt, so a metadata completion cannot cancel a substantive refresh; protected branch publication retains its separate branch serialization. Dependent refresh for `main` and `develop` belongs only to their push callback; PR callbacks whose head is one of those branches still reconcile their own source PR. A stale parent callback cannot dispatch proof for an advanced branch, and the callback itself supplies no child smoke proof. Runtime producers group by exact PR/base/head/merge tuple. An old-head rerun uses a separate group, and a duplicate request cannot cancel an already-running producer. The shared GitHub concurrency queue retains up to 100 pending runs per group without replacing an already queued receiver. A new arrival can still be rejected if that queue is full; missing exact receiver evidence still holds the claim. Duplicate successful push deliveries for the same exact attempt wait rather than preempt an active producer, while the separate branch promotion queue and live-head fence remain unchanged. The two trusted observers submit an exact refresh request to one default-branch admission workflow. Admission serializes each PR/base/head/merge tuple, verifies the current comparison, and rechecks for a visible active producer. Before sending the trusted refresh, it creates an immutable annotated Git claim for the exact PR, base ref, merge, and send generation using the existing repository permissions. The annotation retains the digest of a one-time dispatch witness. The runtime receiver verifies the entire current tuple and that witness, then records the claim tag and execution attempt in the native metadata job. A retry can claim the next generation after the unique exact native terminal receiver proves the preceding claim in its current attempt. Carried evidence from an older attempt does not qualify. Missing or ambiguous receiver evidence holds the existing claim, including after an accepted dispatch whose response was lost. The claim persists across admission jobs and Actions run visibility delays. Preview reconciliation is dispatched only for independently eligible targets; scheduled preview reconciliation remains an additional recovery path. A failed branch CI run cannot publish branch images; the separately dispatched PR merge images can be published only after their own held-admission qualification succeeds and the trusted publisher validates their current eligibility and provenance. Preview selection fails closed until a successful image run for the new merge is published. An ordinary `main`/`develop` PR with no runtime-image change may instead reuse the proven base-commit service images. A stacked PR always uses its exact merge image because its feature-branch base SHA is not a trusted branch-image identity.

A typed runtime refresh hands off publication explicitly after its required credential-free image and smoke jobs succeed and its image artifact upload succeeds; an exception pass with no uploaded artifact cannot dispatch publication. Its separate trusted default-ref job checks out no source and receives only job-scoped `contents: write` to send `pr-runtime-image-publication` with the sole `source_run_id` field. PR build jobs retain read-only repository permissions. The publisher accepts this fixed repository-dispatch type and ordinary successful runtime workflow-run callbacks, both using the trusted default-branch definition. It exposes no branch-selectable manual publication entrypoint and requires no additional credential.

The publisher's no-checkout, Actions-read-only resolver verifies the owning runtime workflow and pins the current native attempt of the supplied exact source run. A completion callback must name that same attempt; a typed `source_run_id` dispatch can arrive before completion, so the resolver waits for actual terminal success of the pinned attempt within a two-minute budget. A changed attempt, malformed provenance, an API error, a failed or cancelled source, and an exhausted wait fail closed. Publication checks the successful producer job from that exact attempt, excludes the diagnostic exception, and rechecks the current successful attempt before registry login. The only eligible download is `pr-runtime-images-pr-merge-<merge SHA>-attempt-<attempt>` from the pinned run ID, with an integer `sourceRunAttempt` in its provenance matching the pinned attempt. An older merge-name-only archive cannot be published; recreating an eligible archive requires running the updated producer definition. If **Re-run failed jobs** leaves the latest successful source attempt without its own producer job and archive, use **Re-run all jobs** on that source workflow run when the PR comparison is still current. Then verify the new attempt produces its own exact-attempt evidence before retrying publication. Do not reuse the archive from the older attempt. This does not invalidate independently valid Smoke Gate proof. Both trigger paths retain the same exact source, current PR/base/head/merge, artifact provenance, and immutable-tag validation. Publishing jobs serialize on the verified merge-bound source title across both paths; duplicate publication preserves identical existing images and rejects conflicting image bytes. Explicit dispatch avoids relying on a workflow-run callback from a token-origin refresh without weakening the source or registry boundary.

The trusted publisher's retained exact-attempt publication receipt binds the original producer artifact ID and digest, PR comparison, and successful publisher attempt. The preview waiter compares producer metadata when Actions still lists that artifact, including an expired row. A successful, completely empty exact producer-artifact lookup lets the authenticated receipt carry the original artifact identity for its retention window. Unavailable or ambiguous inventory, changed attempts, and missing or invalid publisher receipts withhold publication proof.

Smoke Gate retains affirmative successful smoke-step evidence for earlier producers. When GitHub omits or delays step metadata, the canonical producer additionally qualifies through its native `PR Full-Stack Smoke (runtime-required=true)` job identity and successful terminal job outcome. This producer has stable smoke and cleanup step IDs and an unconditional terminal guard. Ordinary runtime qualification requires both Actions-native outcomes to be `success` and the transition-exception marker to be explicitly skipped. Missing marker metadata cannot use the native-job fallback: a successful job alone may instead represent the bounded exception described below. Skipped, missing, cancelled, or failed execution or authenticated cleanup cannot qualify as real runtime proof. Non-required image builds use a different evaluated job name. The gate verifies the exact successful run attempt, owning repository/workflow/event, native job ID/attempt/head/check URL, canonical PR/base/head/merge title, ordered merge parents, and current PR head/base branch before accepting this path. It also rechecks that no newer attempt superseded that source. Job success, logs, command-written outputs, and image artifacts alone are not smoke proof. The existing native job name does not widen the held-admission proof scope defined above. A separate, temporary diagnostic exception lets the required Smoke Gate succeed for a same-repository `benhook1013/FireMUD` pull request whose current live PR carries the `canonical-play-transition` label. A `pull_request` producer also requires the source event label and exact verified PR-event base/head/merge tuple. A typed `pr-runtime-base-refresh` producer instead derives label authority from its verified live same-repository PR, never dispatch payload labels, and requires the exact current base/head/merge tuple again at consumption. Both paths require the latest successful CI attempt with its explicit exception marker while the PR head and base branch remain current. During the default-branch workflow rollout, the exact previous fail-red producer fingerprint remains accepted only with its original failed smoke and terminal guard plus successful marker and cleanup; it supplies the same diagnostic exception and no runtime qualification. The smoke invocation retains its failed Actions-native outcome through step-level continuation; only the exact label, classifier and successful authenticated cleanup can make the mandatory final guard accept that failed probe. Every other probe failure still fails CI. GitHub reports the continued step conclusion as success, so the consumer verifies the immutable marker rather than treating that conclusion as runtime proof. The fingerprinted producer must attest the classified direct-backend `PLAY` `ERROR ENTITLEMENT_UNAVAILABLE` after successful held-admission qualification and backend `LOGIN`, with successful authenticated cleanup. The executing workflow is fingerprinted at the PR merge revision or typed refresh's native default-branch revision, respectively; classifiers, held-admission qualification, authenticated cleanup, certificate setup, and their checked-in environment and Compose inputs are always fingerprinted at the tested PR merge. Its original smoke failure remains visible in the probe logs, summary and Actions-native outcome; unrelated failures still block, and image export and upload must be skipped. The typed publication handoff also requires a real successful image upload. A trusted workflow-run publisher detects the exception marker before exposing a publication source and skips its privileged job; a successful CI conclusion under exception does not authorize registry access or preview images. This is gate acceptance for the nonproduction canonical cutover, not successful smoke, runtime qualification, branch-image promotion, hosted preview eligibility, or production activation. Trusted `main`/`develop` branch publication still requires real passing `LOGIN` → `PLAY` → `LOOK` smoke and cannot use this exception; after the cutover merges, branch images remain on hold until the Account entitlement path is repaired. Remove the label-based marker and consumer exception when fresh-image backend `LOGIN` → `PLAY` → `LOOK` passes, then remove this transitional contract. The [player access tracker](../project-management/implementation-tracking/player-access-and-session.md#temporary-canonical-play-transition-exception) records the current cutover proof gap.

When Smoke Gate considers an older exact successful attempt behind a newer pending producer, it revalidates the comparison and the observed newer candidates before accepting the older proof. A newer terminal failure or a changed pending attempt observed in those checks forces exact reselection. If both the trusted refresh and the native primary are pending, the final direct refresh check precedes the final direct native check. The last awaited fallback validation is the selected attempt's completed-success read. Those separate native reads are not an atomic snapshot; pending producers are authoritative through their last successful observation, not through a claimed simultaneous view at acceptance.

The producer guarantee, independent of smoke-step metadata but requiring an explicit skipped exception marker, is bound to a SHA-256 fingerprint of the entire immutable source workflow definition, including its surrounding YAML execution context. Pull-request attempts use the verified event test-merge revision, and typed refresh attempts use their native default-branch `head_sha`. Both can still use the immediately preceding merge-name-only producer definition as smoke proof, not as image publication proof. The older trusted-refresh fingerprint fallback remains available only to verified typed refreshes. Both paths keep the existing marker, attempt, and execution proof requirements. Missing, unavailable, altered, or unattributable definitions cannot use this guarantee. Every change to [runtime-images.yml](../../.github/workflows/runtime-images.yml) requires review of the producer guarantee and an update of `canonicalRuntimeWorkflowSha256` in [smoke.yml](../../.github/workflows/smoke.yml). The existing [required-gate contract](../../dev-tools/tests/pr-required-gate-context-contract.sh) computes the expected fingerprint and reports the exact update when it is stale; it also exercises native outcome rejection, immutable revision/attempt attribution, and the retained older step-proof path. Every change to a fingerprinted classifier, qualification or cleanup script, certificate setup, environment defaults, or Compose input also requires review and an update of `canonicalPlayClassifierSha256` in `smoke.yml`; the required-gate contract reports each stale value. These fingerprints remain part of the owning workflows, not a separate proof registry.

Branch-to-environment promotion contract:

| Source branch/event | Primary purpose | Deployment target |
| --- | --- | --- |
| Pull requests (every base branch) | Validation, applicable smoke and preview checks, and review evidence | No direct staging/production apply |
| `develop` merges | Integration and staging candidate flow | Staging overlay updates (operator apply after policy gates) |
| Release PR merged to `main` + release tag (for example `v1.2.3`) | Production release candidate artifacting | Production overlay updates (operator apply after attestation + policy gates) |

The workflow YAML files remain the source of truth for concrete triggers; this table is the architecture contract for promotion intent.

Pull-request change scope is classified once by [`.github/scripts/classify-change-scope.cjs`](../../.github/scripts/classify-change-scope.cjs). A pull request uses the lightweight path only when every changed file is documentation, documentation tooling, or non-runtime Python validation tooling. Mixed changes, workflow changes, operational Python, and runtime changes use the normal path. Required gate names remain stable on both paths: lightweight runs execute documentation checks and any applicable repository-wide Python or design-contract proof, while intentionally irrelevant service, infrastructure, `trivy-scan`, preview, and ZAP jobs are skipped; `secret-compliance` remains enabled. Push and manual runs always use the complete path.

The main [`ci.yml`](../../.github/workflows/ci.yml) workflow:

- Generates protobuf outputs to keep generated stubs aligned with the checked-in schemas.
- Runs formatting and lint steps (Spotless, markdownlint, link checks).
- On the complete CI path, executes a matrix of Gradle `check` tasks for affected microservices with SpotBugs, Checkstyle, and tests enabled. Account Service and Game Session each use four complete-check partitions, and World Management uses two; other modules remain one check per affected module. Lightweight documentation-only PR validation does not run these service checks.
- Gradle-based Validation and runtime builds, including affected-module checks, controller builds and the source-built Compose boot-jar command, can recover one exact pinned Gradle-wrapper distribution HTTP 429, 500, 502, 503 or 504 failure before any Gradle task starts. The recovery uses only the official Gradle GitHub release-asset API for the same stable version, requires the release asset digest and downloaded bytes to match the repository's SHA-256 pin, checks the exact asset size, and atomically seeds the ordinary wrapper cache without replacing existing bytes. Metadata and asset requests have bounded time/size limits. The unchanged wrapper command then retries once and still verifies/extracts its own archive. No alternate Gradle version, mirror, compiler/test retry or successful runtime claim is introduced; missing, inconsistent, custom-layout, mixed, interrupted or unrecognized evidence retains the original failure.
- Affected-module checks and the source-built Compose boot-jar command first use Gradle's restored dependency metadata without a forced refresh. The shared runner gives a fully recognized repository-resolution failure one retry of the same complete Gradle command. The retry normally refreshes dependencies. Exact buildSrc, Buf-generated Java and Checkstyle classpath JAR failures consisting entirely of Maven Central HTTP 429 responses keep cached dependency metadata for that retry. The same cached retry applies when a matching annotation-processor classpath fails before compilation because Maven Central returned HTTP 429 for the Spring Boot validation POM. ## Building and Pushing Images

Trusted branch images retain commit-SHA tags. Pull-request images are built locally without registry credentials; only the successful artifact for an exact base/head/merge crosses into the trusted publisher, which pushes immutable `pr-merge-<merge SHA>` tags to **GitHub Container Registry (GHCR)**. The candidate runtime and controller smoke jobs use GitHub-enforced read-only Actions cache tokens because a typed repository dispatch runs on the default branch while building candidate code. Trusted `develop` and `main` builds first publish unique candidate tags, run full-stack smoke against those candidates, then assign commit-SHA and branch aliases to the tested digests. Shared build-cache tags are not deployment evidence.

The `hosted-environment-identity-controller` image is a trusted infrastructure artifact published only by its dedicated job during trusted-source `develop` and `main` runs. That job builds the controller service from the checked-out branch commit against the exact registry-returned `firemud-base` digest produced by its prerequisite job, smokes the exact local controller image, pushes that same image to the dedicated `ghcr.io/benhook1013/firemud-hosted-identity-controller` package, and records SLSA provenance for the registry-returned controller digest. A pre-existing tag is overwritten by the exact smoke-tested build rather than accepted as trusted. Pull-request runs may build and smoke a clearly local controller image without registry credentials, but they exclude it from the exported PR runtime-image artifact, and the trusted PR artifact publisher never publishes it. Runtime deployment accepts only a digest-pinned reference from the dedicated controller package whose GitHub attestation verifies the `runtime-images.yml` signer workflow and a `develop` or `main` source ref.

Deployable artifact lineage, including the OCI index and platform-to-child mapping, is canonical in the [Promotion Attestation Contract](./system-architecture-promotion-attestation.md#artifact-format). This document retains the build and publication consequence: promotable artifacts come from the canonical reviewed build path, staging and production reuse exact digests, and any rebuild requires new staging evidence and a new attestation lineage. Runtime/service image lineage remains separate from tenant/game published-release-bundle attestation.

Production release digest manifest:

- Each production release must have one canonical release digest manifest under `design/operations/deployments/production/release-manifests/<deployment-ref>.json`, where `<deployment-ref>` is the stable production deployment reference.
- The manifest stores the final `releaseTag` as a field and binds it with the source commit, production deployment reference, production promotion attestation, staging deployment record, release-note/compliance asset refs, and exact service image digest set required by the [Promotion Attestation Contract](./system-architecture-promotion-attestation.md#artifact-format).
- Release-note workflows may publish metadata and compliance assets for a tag, but they do not select promotable runtime artifacts. The production overlay PR and release digest manifest are the authority for which staged digests belong to the release.
- If a release tag is created before production promotion completes, the manifest remains at the stable deployment-ref path and is updated with the final `releaseTag` before the release is treated as official.

The mutable `firemud-base:latest` tag is a branch-publication convenience tag for `develop` / `main`, not a promotable release artifact by itself:

- Rebuilding a service later against a moved base-image tag creates a new artifact lineage that must earn its own validation evidence before promotion.

### Rollback Strategy

The rollout and rollback owner contract is [ADR 0156: risk-tiered progressive rollout with compatibility-bounded rollback](./decisions/adr-0156-risk-tiered-progressive-rollout-with-compatibility-bounded-rollback.md).

Target state: multi-replica staging and production workloads use an explicit conservative Kubernetes `RollingUpdate` baseline, normally `maxUnavailable: 0` and `maxSurge: 1`. The canonical playbook introduces one candidate at a time, observes readiness, smoke checks, and applicable SLO evidence, and pauses or aborts on a hard failure; readiness alone is insufficient.

Target state: for a proved `rollback-compatible` release, automation may restore the exact predeclared known-good digest set when current compatibility evidence remains valid and the failure matches policy. A `roll-forward-only` release may pause automatically but never reapplies old binaries automatically. Higher-risk changes use a bounded canary when production has enough replicas and representative traffic; hobby and small deployments use a simple rolling or recreate strategy. No mandatory Argo/Flagger dependency is required until measured scale and policy complexity justify it. This automation is not currently available: current staging and production rollouts use the operator-controlled RollingUpdate and explicit known-good digest reapplication flow below. The `rollback-compatible`/`roll-forward-only` classification and its safety boundary remain in force for that operator path.

## PR Preview Environments

FireMUD's preview workflow is reserved for real reviewer-accessible PR environments, not CI-only stack boot validation. The [`.github/workflows/preview.yml`](../../.github/workflows/preview.yml) workflow targets a hosted single-node k3s cluster and follows this contract:

- Build and smoke-test PR merge images in the credential-free job, then publish the verified artifact to private GHCR under the immutable `pr-merge-<merge SHA>` tag from the trusted default-branch publisher.
- Deploy or upgrade Helm release `pr-<PR_NUMBER>` into namespace `pr-<PR_NUMBER>`.
- Expose the environment at `https://pr-<PR_NUMBER>.preview.<DOMAIN>` using cluster ingress/TLS.
- Expose a reviewer-usable TCP/Telnet entry path for the preview stack so manual gameplay proof can happen through the normal MUD client surface.
- Reset the preview namespace on each deploy, then seed the minimum bootstrap state needed for reviewer proof so the hosted environment remains reproducible across preview updates.
- Tear the preview down when the pull request closes or merges, is explicitly released, or its visible bounded renewable lease expires. Eligible same-repository pull requests allocate automatically; ordinary requests remain first-come at the serialized allocation boundary rather than relying on GitHub's raw job-scheduling order. A currently `preview:priority`-labelled request may reclaim the oldest ordinary allocation when the pool is full, but never another priority-labelled allocation; both labels are re-read at the destructive boundary, and the full allocation/deploy/proof/cleanup lifecycle uses one durable bounded non-cancelling queue. The displaced pull request retains ordinary CI and its historical hosted result while reporting no current preview.

For both `standalone` and explicit `hosted-controller` preview modes, automatic preview rendering uses `pull_request` with read-only permissions rather than `pull_request_target`. Typed `repository_dispatch` retains its default-branch-owned manual deploy/destroy route. The configured render checkout loads tools and local actions from the default branch, while the separate exact PR merge checkout supplies Helm chart data. A pull-request-owned workflow definition can change its own checkout steps, so that configured checkout is not itself a privilege boundary. Only the default-branch-owned privileged dispatch and lifecycle may exercise trusted authority; they never execute candidate scripts or actions. The write-capable runtime refresh in the source workflow is dispatch-only. A separate default-branch `preview-runtime-refresh.yml` observer handles automatic PR base refresh through `workflow_run`: it reads GitHub-owned source-run/PR metadata and current exact merge parents, checks out only the default branch to reuse its canonical image-selection policy, never checks out candidate code or downloads artifacts, and submits the typed runtime-image refresh request to the shared admission workflow. The PR preview producer preserves its existing run and job names, recording the event PR/base/head/merge tuple in a successful native step name. The refresh observer reads bounded exact-attempt job metadata and requires both the immutable event tuple and the eligible deployment plan’s resolved tuple. It binds them to the native run head and unique PR association, independently verifies the recorded and current merge parents, and uses the branch ref for current base authority. A failed render can still trigger repair after a successful eligible plan. Step metadata is not privilege authority: the PR-authored workflow can affect it, and every requested refresh still requires independent current-PR eligibility and exact current merge verification. Missing or malformed legacy tuple metadata explicitly requires a fresh render from the updated producer rather than inferring historical proof; the observer still downloads no artifacts. Unrelated native PR associations are tolerated only when exactly one association matches the selected target; duplicate matching associations fail closed. PR-controlled build and render work must have no cluster, registry-write, or hosted-identity requester credentials. This is a required credential-scope boundary, not proof supplied by a default-branch tools checkout; repository-level legacy credential removal remains a separate verified rollout prerequisite. The trusted default-branch lifecycle consumes its sanitized render artifact only after validating source-run provenance (including the GitHub-owned PR association and source head for `pull_request`), current head/base/merge binding, checksum, closed schema, exact image tags, and allowlisted Secret consumers. In `standalone` mode, the trusted lifecycle restores only the canonical cert-manager ingress issuer annotation after artifact validation; the PR render cannot choose it. A manual release publishes an unprivileged destroy intent for the trusted lifecycle. Once close cleanup is separately activated, the trusted close event handles PR close. Privileged preview maintenance and dev-demo operations run only from default-branch schedule, push, workflow-run, pull-request-target, or typed repository-dispatch events, never a branch-selectable privileged manual dispatch. Every secret-consuming hosted job selects the separately protected `trusted-hosted-cluster` GitHub Environment, whose deployment branch policy must allow only `develop`; the legacy GitHub Environments named `pr-preview` and `dev-demo-cluster` must not hold requester credentials. Before live activation, repository-scoped runtime, GHCR, and any remaining hosted-identity credentials must be migrated to the protected Environment or removed and rotated as appropriate. Cluster kubeconfigs are written only to job-temporary files and removed at job end; operators must clear any historical runner-home copy and rotate exposed credentials as needed.

This separation does not activate hosted deployment or cleanup workflows and does not change repository event-policy settings. The temporary path-specific `preview.yml` exception permits only `pull_request_target` and `repository_dispatch`, so it blocks the new `pull_request` event. At rollout, separately authorize and coordinate the additive path-specific policy update: retain `pull_request_target` and `repository_dispatch` and add `pull_request`. Verify fresh natural PR and manual-dispatch events against the merged code; the documentation change itself neither grants authorization nor changes that policy. Keep the `pull_request_target` allowance until the trusted-tools, read-only `pull_request` route is the effective default and fresh natural preview and runtime-refresh events prove the same exact PR/base/head/merge tuple. Removing the old allowance then requires separate review and approval at the time of the change; approval of the additive rollout does not authorize removal. Do not rename the workflow to evade that policy. Disabled close cleanup still uses its existing trusted `pull_request_target` route and requires a separate policy/activation decision before enabling it. A read-only token is not a secret-free execution guarantee; privileged consumers must keep treating every PR artifact as hostile data rather than executable configuration.

On the explicit `hosted-controller` target path, that lifecycle prepares the runtime namespace, capacity allocation, bounded allocated preview Telnet NodePort (or fixed dev-demo NodePort `32016`), and requested base/head/merge/image tuple annotations with the runtime credential before a requester-only credential applies `HostedEnvironmentIdentity` `Active`. The controller materializes the retained identity namespace and cert-manager Certificate resources; it does not create disposable runtime namespaces. Only successful runtime deployment writes the distinct deployed-head annotation consumed by controller readiness; the trusted workflow writes the separate proof-complete tuple and Namespace UID only after all verification checks and the exact Namespace UID fence succeed. Close/merge cleanup deletes runtime and waits for exact `NotFound` before requesting `Retired`. All uncertain lifecycle/API results fail closed and retain identity.

Hosted verification waits for the complete readiness tuple defined by the owning [deployment-environments contract](./infrastructure/deployment-environments.md) before running the existing gameplay smoke; this CI/CD overview does not duplicate that tuple. In `hosted-controller` mode, preparation creates the runtime Namespace, records its requested base/head/merge/image tuple and port annotations, submits the active identity request, and waits for the complete labeled, key-complete controller-projected Secret set—including the distinct Account, Game Session, and Social Groups workload leaves—before Helm installs or upgrades the runtime workloads. A deployed tuple alone is not reconciled health: after the verification checks and exact Namespace UID fence, the workflow records proof annotations containing the exact base/head/merge/image tuple and live Namespace UID, and the reconciler requires those annotations to match before it treats the preview as aligned. This ordering rule does not relax the separate bootstrap prerequisite: the fixed `firemud-system/firemud-grpc-ca` Secret must already exist before controller activation so the gRPC projection can be issued. `standalone` remains the default/current certificate-identity path until live controller activation and consumer-convergence proof exists; the `hosted-controller` target does not change stage or production deployment.

Main CI remains responsible for stack startup, smoke, and cross-service verification. Preview deployment is intentionally a separate concern focused on reviewer-accessible environments. Capacity exhaustion or infrastructure failure reports preview proof as unavailable; it never records a pass, and any claimed hosted proof is bound to the current pull-request base/head/merge/image tuple.

Before spending a preview proof retry, the reconciler checks for active work for that exact comparison. The trusted consumer records the validated PR/base/head/merge tuple in a successful step of its native validation job. The reconciler requires the default-branch consumer workflow identity and the current attempt's successful step before treating that consumer as an exact match. An inherited source run title can identify a candidate for lookup but cannot establish a match. When the lookup budget leaves candidates unexamined, the reconciler preserves the retry budget. It rechecks the live Namespace proof after candidate lookup so a consumer that finished during the lookup does not cause another render. A successful exact source completion during lookup defers one retry cycle while its trusted consumer may enter the queue. When GitHub caps the completed-source inventory, the reconciler checks disjoint creation ranges across the history. It still evaluates handoff freshness from completion evidence, including later attempts of older runs, and preserves the retry budget if any range cannot be verified. The [hosted identity lifecycle](./infrastructure/deployment-environments.md#hosted-identity-lifecycle) owns durable retry custody across Namespace recreation and the dispatch rejection boundary.

The initial Telnet-first hosted milestone is complete. Continuing preview acceptance follows [ADR 0178](decisions/adr-0178-disposable-transport-complete-pr-preview-proof.md): one shared semantic authenticated, admitted, `LOOK` assertion set is exercised through both the public Telnet path and the deployed first-party browser path. Telnet proves TCP Proxy and bridge/framing behavior. The bounded browser journey proves frontend delivery, HTTPS bootstrap and discovery, connect-token cookie and `/ws/game/**` admission, one reconnect, logout, and non-reuse. Direct backend WebSocket smoke remains CI or diagnostic evidence rather than a substitute or third required hosted path. Dedicated frontend delivery and the browser journey remain implementation gaps, so current TCP/Telnet preview proof is not yet transport-complete.

## Promotion & Rollback Model

FireMUD uses a simple promotion flow from pull requests through staging to production:

- Pull requests validate candidates, `develop` supplies staging candidates, and reviewed `main` releases target production. A merge or mutable branch reference never substitutes for explicit human authorization of the exact production plan.
- Feature branches are merged into `develop` after passing CI.
- Staging promotion is performed by updating the staging Kustomize overlay (for example `k8s/overlays/stage`) to the desired image digests (`image@sha256:...`) via a Git change, merging it, and applying it from a secure operator environment using `kubectl apply -k k8s/overlays/stage`. This keeps “what was deployed” traceable in Git history and removes mutable-tag drift.
- When a release is ready, `release-please` opens a release PR against `main`; after that PR is merged, the release tag (for example `v1.2.3`) is created. Release-tag workflows may publish metadata and additional tags for the already-validated digest set, but must not rebuild or choose the promotable production artifacts.
- Production promotion updates the production Kustomize overlay (for example `k8s/overlays/prod`) to exact image digests that have already passed staging validation. In the accepted target, a human authorizes the immutable generated plan and a protected executor applies and observes that exact plan; the current implementation still uses a secure operator environment and `kubectl apply -k k8s/overlays/prod` as tracked deployment debt.
- Production release PRs must include a release digest manifest at the stable production deployment-ref path; its `releaseTag` field (when a tag exists) and deployment reference bind the production attestation and exact staged digest set.
- Overlay PRs are validated by [`.github/workflows/validate-kustomize-overlays.yml`](../../.github/workflows/validate-kustomize-overlays.yml), which checks that referenced images exist in GHCR, enforces digest pinning for staging/production overlays, and blocks staging backup schedules unless the explicit marker `k8s/overlays/stage/STAGING_BACKUPS_ENABLED` is present.
- The standalone `k8s/velero` manifests are pre-release assets while FireMUD has no player-facing production deployment, so maintenance updates there do not require production promotion evidence today. Their checked-in production consumer is `k8s/terraform-production/main.tf`, through `kubernetes_manifest.velero_schedule` and `kubernetes_manifest.velero_verify`; no live player-facing production apply is proven. If that Terraform production stack is later applied live, the exact applied stack plan and its promotion evidence govern the deployment; this does not imply a currently implemented Terraform gate. The production Kustomize overlay and its attestation remain the authority for actual overlay resources.
- Overlay PRs run the canonical preflight entrypoint (`dev-tools/deploy/preflight.py`) in `ci-static` context so policy IDs and report shape match operator pre-apply validation. CI-static mode may mark production attestation policy as `not_applicable` when no production promotion is being executed.
- Production overlay PRs must include exactly one in-repo staging promotion attestation under `design/operations/deployments/production/attestations/<deployment-ref>.json` following the [Promotion Attestation Contract](./system-architecture-promotion-attestation.md#validation-rules). Production PRs are rejected if they reference digests that cannot be tied to that attestation, a successful staging deployment record with live-state verification, and a staging deployment record whose `secretComplianceStatus` is `pass` and whose `secretComplianceEvidenceRef` resolves to an existing immutable, digest-qualified evidence artifact under the canonical secret-compliance rule.
- A production overlay change without its required attestation fails validation; preflight must never be skipped because evidence is absent. Target promotion tooling should machine-generate routine lineage fields from observed staging state for operator review, but the current repository implementation validates checked-in/operator-authored evidence and does not yet prove that generator.
- Production overlay PR CI must evaluate the attestation and compact recovery-compatibility result for every promotion. `compatibilityStatus=incompatible` is unconditionally non-promotable. `compatibilityStatus=drill_required` remains non-promotable until the fresh drill is complete and the compatibility result is regenerated as `compatible`; attached backup-readiness evidence cannot make the stale result promotable. A `roll-forward-only` release requires matching full backup-readiness evidence in addition to a regenerated compatible result. Deferring those checks to operator-only preflight is non-compliant.
- Staging apply evidence must include the immutable in-repo deployment record `design/operations/deployments/staging/deployments/<stagingOverlayCommitSha>/<stagingDeploymentEventId>.json`; production promotion validation fails when the attestation does not select the exact event record or that record is missing, digest-mismatched, lacks live-state verification, or lacks passing secret-compliance evidence.
- Player-facing preflight and operator validation must also verify environment bootstrap completeness and external integration isolation before apply; these checks are not limited to restore events.
- `manual-backup-restore.yml` is limited to throwaway recovery drills. It may target only explicit non-player-facing restore namespaces or isolated drill clusters using dedicated low-privilege credentials and GitHub Environment approvals. It must not restore into live staging or production namespaces and must not hold credentials capable of modifying the currently player-facing cluster boundary.

Rollbacks are handled by resuming a previously known-good image digest set and re-applying the staging or production manifests with those digests. See the Deployment Runbook for the step-by-step operator flow.
Before approving a production promotion, deployment evidence must classify rollback mode as either:

- `rollback-compatible` (previous digest set remains safe to re-apply against the current database schema, secret/config contract, mounted file-path contract, and external-binding contract), or
- `roll-forward-only` (schema, secret/config, file-path, or external-binding change requires forward remediation and/or restore-point recovery rather than old-binary rollback).

Production promotions lacking this explicit rollback-mode classification are non-compliant.

Target-state production promotion evidence records a compact recovery-compatibility result against the current production-equivalent cold-start drill and consumes the current environment-bound reference and complete digest for the newest verified restorable point, proving the observed point is within the accepted 15-minute bound. A `drill_required` result blocks promotion until the required fresh drill is complete and a new `compatible` result replaces it. A compatible release may reference that live freshness proof without repeating the full selected-release record; the freshness gate does not itself require a full drill for every release. For releases classified as `roll-forward-only`, promotion evidence must also include fresh full backup-readiness evidence proving:

- a recent successful logical backup,
- recent backup-verification success, and
- a current environment-wide `cold_start_restore` record suitable for the release, including empty Redis, safe recovery-participant dispositions, hardening, and controlled reopen.

The canonical full-evidence path is `design/operations/deployments/production/backup-readiness/<deployment-ref>.json`. The compact result uses `compatibilityStatus` (`compatible`, `drill_required`, or `incompatible`) as the outcome and `newDrillRequired` as the machine-readable drill gate. `incompatible` is a terminal failed result. `drill_required` requires `newDrillRequired=true` and is also non-promotable: after the drill and full evidence are complete, the compatibility classifier must produce a new `compatible` result bound to that evidence. Every `roll-forward-only` release also sets `newDrillRequired=true`, carries matching full evidence, and must have a compatible regenerated result. Production CI/preflight rejects stale `drill_required` results and full evidence that is missing, stale, or not bound to the source production database lineage, candidate recovery tooling, exact candidate digests, migration path, config, bindings, and promotion attestation. Compatible rollback releases keep only the compact result or immutable reference in promotion/deployment evidence rather than copying the full recovery record. The current executable validates the implemented compact `rollback-compatible` result, but that result alone cannot authorize promotion while broader event-scoped player-facing gates remain unimplemented. The full `roll-forward-only` evidence lane remains fail-closed until its target checks are complete.

Target-state traffic-open readiness for production first-live or reopen events uses `design/operations/deployments/production/traffic-open/<first-live|reopen>-<deployment-ref>/<deploymentEventId>.json`, whose stored event identity matches the referenced preflight report, consumes the current environment-bound newest-verified-point reference and complete digest within the 15-minute bound, and references the canonical backup-readiness, recovery-controller, and confidentiality evidence. Upload existence alone is insufficient. Routine online backups cover the environment-wide PostgreSQL database and do not use Game Session pause/resume as readiness proof. The current executable has no controller-backed traffic-open result and therefore fails this gate closed; finalized checked-in projections are post-release evidence, not pre-release authority.

Pre-apply policy checks for staging and production must run through the canonical preflight contract in `system-architecture-deploy-preflight-policy.md`. Static checks run in overlay PR CI, and resolved-manifest/runtime checks run in operator preflight execution. Both use the same policy IDs and evidence shape.

## Canonical Deployment Evidence Lifecycle

FireMUD uses one deployment-evidence chain per deployment event so promotion, rollback, and incident review all answer from the same record set:

1. Preflight produces `design/operations/deployments/<environment>/preflight/<deployment-ref>/<deploymentEventId>.json`.
2. Secret-compliance validation produces or references `design/operations/secret-compliance/<environment>.yaml` plus immutable supporting evidence.
3. Operator apply produces one immutable environment deployment record:
   - staging: `design/operations/deployments/staging/deployments/<overlayCommitSha>/<deploymentEventId>.json`
   - production: `design/operations/deployments/production/deployments/<overlayCommitSha>/<deploymentEventId>.json`
   - hobby-self-hosted: `design/operations/deployments/hobby-self-hosted/deployments/<deployment-ref>/<deploymentEventId>.json`
4. After apply and live-state verification succeed, the operator updates the environment's one current-state index at `design/operations/deployments/<environment>/deployments/current.json`. The index identifies the exact immutable deployment record through `deploymentRef`, `deploymentEventId`, and `deploymentRecordRef`; it is the sole repository answer to what is currently deployed in that environment.
5. Production promotion references exactly one staging attestation at `design/operations/deployments/production/attestations/<deployment-ref>.json`. The attestation binds one exact staging deployment event and remains immutable even after the staging current-state index advances.
6. Production release publication references one release digest manifest at the stable path `design/operations/deployments/production/release-manifests/<deployment-ref>.json`; the final `releaseTag` is stored as a manifest field.
7. Every production release records its compact recovery-compatibility result; if that result requires a drill or the release is `roll-forward-only`, production also references `design/operations/deployments/production/backup-readiness/<deployment-ref>.json`.

Lifecycle rules:

- The environment's `deployments/current.json` index is the canonical answer to “what is currently deployed.” Promotion eligibility is a separate immutable claim: an attestation selects one exact successful deployment event and never performs a later “latest event” lookup.
- Preflight artifacts, secret-compliance snapshots, smoke evidence, and live-state verification are supporting evidence linked from the deployment record rather than parallel sources of truth. Promotion/staging `smokeEvidence` entries are closed `{ref, contentDigest}` objects; the digest covers the exact retained JSON bytes. Each retained smoke artifact preserves `deploymentRef` as the environment-agnostic deployment lineage (for Git-managed staging, the selected `stagingOverlayCommitSha`) and carries the selected `deploymentEventId` equal to the selected staging deployment event. Recovery-baseline smoke evidence uses the same closed `{ref, contentDigest}` shape, without promotion-only deployment-lineage binding.
- Current promotion trust is repository-reviewed evidence with immutable artifact references. Promotion attestation field selection and validation follow the [Promotion Attestation Contract](./system-architecture-promotion-attestation.md#validation-rules); this lifecycle retains the deployment consequence that static CI validates the authored in-repo deployment record contains and binds the required live-state and secret-compliance evidence, while operator preflight verifies observed live state before apply. Detached signatures are not required in the current single-admin/operator model.
- Re-applying the same overlay commit creates a new immutable event record and, after successful live-state verification, advances the current-state index. It never overwrites prior preflight, apply, or attestation evidence.
- A promotion attestation is valid only if `stagingOverlayCommitSha` plus `stagingDeploymentEventId` selects the exact successful promotable apply event it attests. A later apply does not invalidate or retarget that historical attestation.
- Rollback uses the deployment record and original attestation lineage for the digest set being restored.

Terminology note:

- `deployment evidence` answers what was checked, applied, and verified for a concrete deployment event in one environment.
- `promotion evidence` is the subset of evidence used to prove a staging deployment is eligible to be promoted into production, primarily the attestation plus its referenced deployment and compliance records.
- `traffic-open evidence` is the evidence family used to prove an environment may be opened or reopened to player traffic, for example the production traffic-open backup-readiness artifact or hobby traffic-open records.
- `promotion candidate` means a staging deployment record that is eligible to produce production promotion evidence; quarantined or detached staging drills can remain valid deployment evidence without becoming promotion candidates.
- `deployment-ref` is the canonical environment-agnostic identity for the reviewed deployment input lineage and is used by preflight, attestation, and backup-readiness artifacts. For Git-managed staging/production overlays, it is the same Git SHA recorded as `overlayCommitSha`. `deploymentEventId` is the distinct UUID for one concrete preflight/apply event, including a retry or later re-apply of the same deployment ref; a retained promotion/staging smoke artifact records both fields and never overloads `deploymentRef` with this event identity.

The following is non-promotable pseudodata showing deployment-record field shape only; its placeholder references and example values are not promotion evidence. In real promotion evidence, `secretComplianceEvidenceRef` must resolve to an existing immutable, digest-qualified secret-compliance evidence artifact under the canonical secret-compliance owner; `secretComplianceStatus: pass` alone is insufficient.

## Secret Compliance Gate

Promotion and DR-readiness reporting depend on environment secret-compliance records described in `infrastructure/environment-and-secrets-overview.md`.

- `production`: missing or stale secret-compliance records are a hard CI gate for production promotion, first-live/reopen, and disaster-recovery-readiness claims.
- `staging`: missing or stale records are a hard CI gate for staging promotion and any staging deployment intended to produce production-promotion or production-readiness evidence. Detached or quarantined staging playtests and drills may report warnings, but they remain non-promotable operational exercises rather than promotion candidates.
- `hobby-self-hosted`: operator tooling should validate records before opening traffic, but GitHub CI gating may be unavailable.

Promotion-evidence rule:

- Any staging deployment record used by production attestation must carry `secretComplianceStatus=pass` and a `secretComplianceEvidenceRef`; warning-only or note-only evidence is never promotion evidence.

Enforcement workflow contract:

- CI check name: `validate-secret-compliance`.
- Expected implementation location: `.github/workflows/validate-secret-compliance.yml`.
- Required validator behavior:
  - Load `design/operations/secret-compliance/<environment>.yaml` and apply the canonical record, evidence-payload, and bootstrap operation/generation contract in [Environment Variables & Secrets Overview](./infrastructure/environment-and-secrets-overview.md#secret-compliance-controls).
  - Fail when required records/classes, their exact parent-to-payload bindings, or a completed exact bootstrap generation are missing; partial or crashed bootstrap remains noncompliant and resumes its existing operation.
  - Fail when credential age exceeds the configured maximum age for hard-gated environments, regardless of whether age is measured from bootstrap provisioning or later rotation.
- Required record classes:
  - `jwt-signing-keys-jwks`
  - `postgres-application-credentials`
  - `backup-object-store-credentials`
  - `operator-credentials`

The `jwt-signing-keys-jwks` age record is necessary but not sufficient for JWT readiness. Every production first-live or reopen traffic-open event must itself carry exactly one authenticated custody proof selected by that event (`PREFLIGHT-JWT-INTERIM-001=pass` for `INTERIM_ACCOUNT_ONLY_MOUNTED_FALLBACK` or `PREFLIGHT-JWT-002=pass` for `TARGET_NON_EXPORTABLE_SIGNER`) and current `PREFLIGHT-JWT-ROTATION-001=pass` evidence for that selected custody mode. Separately, any staging deployment record used for production attestation or promotion must carry the matching selected custody and rotation evidence as an additional lineage check; staging lineage never substitutes for event-bound production proof. Interim evidence must prove Account-only asymmetric signing, Account authorization of the materialization controller's bounded private-slot generate/materialize/resource-version-CAS/prune operations, private/public projection correspondence, and validator convergence. Target signer evidence must prove Account-owned signing authority with signer-bound non-exportable custody, authenticated signer generation and health, challenge-signature correspondence with the Account-published JWK, validator convergence, Account-authorized signer retirement for planned rotation and hard cutover for compromise, and that no application workload mounts or receives private material. The two custody proofs are alternatives, not cumulative requirements. Recovery disposition remains event-scoped: `verified_not_restored` may retain the unchanged current key set when current binding, generation, keyset integrity, and validator acceptance are proved; it does not require a replacement `kid`, rejection of the still-current `kid`, or an issuer-generation advance solely for credential evidence. Replacement dispositions instead require the applicable replacement-key acceptance and old-key rejection evidence. The current executable preflight does not yet implement these checks, so mounted JWT/JWKS resources and a fresh credential-age record cannot be used to claim the player-facing JWT gate is satisfied.

## Deployment Credentials & Environments

CI workflows and operators use distinct credentials for each Kubernetes environment:

- **Hosted preview and dev-demo credential boundary**
  - All secret-consuming hosted deploy, verify, cleanup, janitor, reconciler, and dev-demo jobs select the protected GitHub Environment `trusted-hosted-cluster`. Its required deployment branch policy is `develop`, so a pull-request branch cannot authorize these credentials by changing workflow code.
  - `pr-preview` and `dev-demo-cluster` remain Kubernetes target classes; the legacy GitHub Environments of those names are not credential boundaries. The PR source/render path selects no GitHub Environment, and no requester kubeconfig may be stored in either legacy environment.
  - The protected Environment uses distinct secret names: `TRUSTED_HOSTED_PREVIEW_NAMESPACE_MANAGER_KUBECONFIG`, `TRUSTED_HOSTED_PREVIEW_RUNTIME_KUBECONFIG`, `TRUSTED_HOSTED_STANDALONE_CERTIFICATE_KUBECONFIG`, `TRUSTED_HOSTED_IDENTITY_REQUESTER_KUBECONFIG`, `TRUSTED_HOSTED_PREVIEW_GHCR_USERNAME`, and `TRUSTED_HOSTED_PREVIEW_GHCR_TOKEN`. Existing repository-scoped runtime and GHCR credentials must be migrated into those protected names, or removed and rotated, before live activation. Environment creation and static workflow checks do not themselves prove credential cleanup or a live hosted deployment.

- **Development clusters**
  - May use a kubeconfig or token that is available to a wider set of workflows (for example the hosted preview and dev-demo environments).
  - Intended for non-player-facing stacks where rapid iteration is more important than strict change control.
- **Staging cluster**
  - Uses credentials limited to operator `kubectl` access and, if introduced later, dedicated staging deployment workflows.
  - Credentials are not exposed to pull request workflows; only merges to `develop` and explicit operator actions (or approved staging workflows) can update the staging cluster.
- **Production cluster**
  - Uses credentials restricted to production deployment paths and operator break-glass `kubectl` access from approved workstations or bastion hosts.
  - The accepted target is a protected executor activated only after human approval of an exact immutable plan. It uses short-lived environment-specific credentials where supported, strict concurrency and live-state preconditions, reviewed immutable workflow code, and least-privilege deployment/observation RBAC unavailable to pull-request jobs.
  - No workflow currently proves this target; production apply remains manual implementation debt. A generic GitHub Environment approval of a mutable branch or free-form inputs is insufficient.

Registry credentials (for GHCR) are shared across environments but access to pull images into each cluster is controlled by Kubernetes secrets and RBAC within that environment.
