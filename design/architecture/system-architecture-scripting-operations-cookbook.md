# FireMUD Scripting Operations Cookbook

This document collects operator-facing procedures and examples for scripting and automation. [Scripting Quotas & Operations](./system-architecture-scripting-quotas-and-operations.md) owns steady-state quota and budget policy/status; the [normative contract tables](./system-architecture-scripting-normative-contract-tables.md) are the sole authority for metric names, labels, and increment units; the [Scripting & Automation Observability Contract](./system-architecture-scripting-observability-contract.md) owns audit fields and handoff diagnostics; [Scripting & Automation: Rollout and Rollback](./system-architecture-scripting-rollout-and-rollback.md) owns promotion and rollback semantics. The exact pin/epoch, stage-aware recovery, and rollout-history decisions are linked from [ADR 0103](./decisions/adr-0103-single-authority-script-pins-with-exact-version-execution.md), [ADR 0106](./decisions/adr-0106-epoch-fenced-script-rollback-without-routine-gameplay-pause.md), [ADR 0107](./decisions/adr-0107-stage-aware-script-dead-letter-recovery.md), and [ADR 0109](./decisions/adr-0109-game-session-owned-script-rollout-history.md). The cookbook demonstrates those contracts without redefining them.

## Implementation Status

This is a non-authoritative operator guide. Required rollout, rollback, convergence, and timeout behavior belongs to [Scripting & Automation: Rollout and Rollback](./system-architecture-scripting-rollout-and-rollback.md); the rollback section below is only a worked example. Current runtime limitations also remain canonical in [Scripting Runtime Execution](./system-architecture-scripting-runtime-execution.md#current-implementation-status): the live evaluator performs bounded local `targetEntityIds[]` expansion into individual attempts, while the live handoff supports one target entity per attempt; complete target-scope/child identity, deduplication, and handoff proof remain target-only, and the implementation has not yet converged on the target lease/fencing-generation recovery or separate evaluated descriptor/outbox boundary. Target-state recovery resumes a committed descriptor without DSL re-entry; only a stale uncommitted `EXECUTING` evaluation is terminalized as `DEAD_LETTERED` with `stale_execution_fenced`. Current live `EVALUATING` rows remain active/unresolved and fail closed. Tenant-readiness `ONLOAD_RUNNING` is a separate recovery path: current stale work remains unresolved/fail-closed, while target recovery terminalizes it as non-replayable `DEAD_LETTERED` with `stale_execution_fenced`, blocks `READY`, and requires a newer immutable publication/readiness identity. Ordinary gameplay ticks continue except in a separately declared unfenced-effect workflow.

## Operational Cookbook: Quotas, Budgets, and Metrics

Metric names, labels, and increment units in the examples below are illustrative query patterns only. The [normative Table 4](./system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix) is the sole authority for those metric definitions, while the [Observability Contract](./system-architecture-scripting-observability-contract.md) owns audit and handoff diagnostics; this cookbook records only local operator consequences and diagnostic usage.

Use the following patterns to answer common operational questions:

- **"Which events are being rejected before handler resolution by quotas or queues?"**
  - Look at `automation_script_triggers_dropped_total{reason="quota"}` for event-scope limiter rejections and `automation_script_triggers_dropped_total{reason="concurrency"}` / `automation_script_triggers_dropped_total{reason="concurrency_policy_drop_new"}` for pre-handler concurrency and queue-limit rejections. These are event-scope decisions, not per-script `ScriptQuotaService` charges.
  - For handler-level per-script `quota_denied` with `finalReason=script_quota_denied`, use `automation_script_triggers_total{outcome="quota_denied"}`, `script_quota_denied_total`, and the handler-scoped audit row as separate diagnostics; do not treat it as a dropped pre-handler event. For `finalReason=dry_run_capacity_exhausted`, use `automation_script_test_runs_total{result="quota_denied"}`, `automation_script_test_capacity_denied_total{scope=~"tenant|cluster"}`, and the audit row instead; it never increments the live `automation_script_triggers_total` family or `script_quota_denied_total`.

- **"Is a tenant being throttled by its own automation budget?"**
  - Check `automation_script_skips_total{scope="tenant",reason="tenant_budget_exceeded"}` only for pre-handler or catch-up candidate skips. A `ScriptTenantBudgetService` denial after durable work-item claim but before executor acceptance is handler-scoped: use `automation_script_triggers_total{outcome="tenant_budget_exceeded"}`, `automation_script_tenant_budget_denied_total{scope="tenant",tier=~"high|normal|background"}`, and the corresponding handler audit row; it has no execution-start marker or charge and must not increment `automation_script_skips_total`.
  - Use `automation_script_tenant_budget_allowed_total{scope="tenant",tier=~"high|normal|background"}` / `automation_script_tenant_budget_denied_total{scope="tenant",tier=~"high|normal|background"}` to see which priority tiers are consuming or exhausting bounded runtime budget. Use audit rows, Redis counters, and control-plane reads for tenant-specific drilldown instead of raw metric labels.

- **"Are cluster-wide ceilings causing drops?"**
  - Monitor `automation_script_skips_total{scope="cluster",reason="cluster_limit_reached"}` alongside `automation_tick_events_enqueued_total` and infrastructure-level CPU/time metrics for live catch-up candidates whose cluster-ceiling denial was durably settled after candidate selection. This combination indicates pressure at the cluster layer rather than within a single script or tenant. Use `automation_script_triggers_dropped_total{reason="cluster_limit_reached"}` only for a genuine pre-handler ingress rejection, not for a settled catch-up candidate.

- **"Are lower-priority scripts being throttled in favor of higher-priority ones?"**
  - Compare `automation_script_queue_delay_seconds` by Table 4's bounded `priority` to detect sustained background deferral, including work that remains queued, then correlate the pre-handler/catch-up-only `automation_script_skips_total{reason="tenant_budget_exceeded"}` with handler-level tenant-budget denials from `automation_script_triggers_total` and `automation_script_tenant_budget_denied_total`. Tenant/script drilldown remains in audit and control-plane records rather than metric labels.

- **"Are reloads or version issues causing skips?"**
  - For pre-handler denials, inspect the ingress response and `script_event_ingress_audit` for the bounded `admissionOutcome`/`admissionReason` pair, together with `automation_script_triggers_dropped_total{reason=...}`. Do not query handler `finalOutcome` for this path. For handler-scoped denials after resolution, use `automation_script_triggers_total{outcome=...}` and `script_event_audit.finalStage=ADMISSION`; do not treat the dropped metric as a handler audit join.
  - For a pre-handler stale control-plane pin, inspect the ingress response and `script_event_ingress_audit` for `admitted=false`, `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_PIN_STATE_UNAVAILABLE`, and `admissionReason=pin_state_unavailable`. Do not look for `script_event_audit.finalOutcome` for this pre-handler case; a pin failure after handler resolution remains handler-scoped.

### Tuning Playbook: Misbehaving Scripts

When a script or tenant consumes too many resources, adjust settings in this order:

1. **Per-script cadence and concurrency** – Start with the script’s own knobs in [Scripting Quotas & Operations](./system-architecture-scripting-quotas-and-operations.md#per-script-scheduling-policies): increase `intervalTicks`, reduce `maxConcurrent`, or switch `concurrencyPolicy` from `queue_until_free` to `drop_new` so the script enqueues less often and runs fewer overlapping instances.
2. **Per-script quota window** – If the script still runs too frequently, tighten `SCRIPT_QUOTA_LIMIT` / `SCRIPT_QUOTA_WINDOW_SECONDS` for that script so abusive patterns are capped before they hit the tick queues.
3. **Per-tenant tier budgets** – When one tenant’s background work threatens others, adjust that tenant’s budgets per tier (for example, reduce `background` capacity), watching pre-handler/catch-up `automation_script_skips_total{scope="tenant",reason="tenant_budget_exceeded"}` alongside the separate handler-level tenant-budget denial metrics.
4. **Cluster-wide ceilings and capacity** – Only after tuning the above should you raise or lower global ceilings such as `AUTOMATION_TICK_MAX_EVENTS` or cluster CPU budgets. Use the metric families and labels defined by [normative Table 4](./system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix), with the [Scripting & Automation Observability Contract](./system-architecture-scripting-observability-contract.md) for audit and handoff diagnostics, to confirm whether you are cluster-bound or script and tenant-bound.

### Worked Example: Noisy Background Script vs High-Priority Script

Consider two tenants sharing the same Automation & Scripting cluster:

- **Tenant A** – runs a noisy background script `npc-logger` tagged `priorityTag=background` that logs non-critical events frequently.
- **Tenant B** – runs a high-priority script `boss-ai` tagged `priorityTag=high` that drives a raid boss encounter.

Assumptions:

- Per-script quotas allow both scripts to run a reasonable number of times per window under normal conditions.
- Tenant budgets are configured so each tenant has its own automation budget per priority tier.
- Cluster-level ceilings cap total automation work per second across all tenants.

Under light load:

- `npc-logger` and `boss-ai` both operate within their per-script quotas.
- Tenant A and Tenant B remain within their per-tenant budgets.
- Cluster ceilings are not reached; both scripts run as expected.

Under heavy load from Tenant A:

1. **Event-scope limiter and per-script quota layers**: An event-scope limiter may reject incoming events before handler resolution, increasing `automation_script_triggers_dropped_total{reason="quota"}` and the event-scope ingress audit without charging per-script quota. After resolution, apply [normative Table 4's](./system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix) increment unit: `automation_script_triggers_total` counts once per resolved handler and adds no separate admitted-event increment; an admitted event with no handlers uses the table's single bounded event-scope `outcome="admitted_no_handlers"` consequence. `admitted_no_handlers` is metric-only: it is not an ingress response or an Automation audit `finalOutcome`/`finalReason`. `ScriptQuotaService` applies `npc-logger`'s per-script quota to each handler; a handler-level denial instead uses `automation_script_triggers_total{outcome="quota_denied"}` and its handler-scoped audit row. `boss-ai` remains within its own per-script quota and continues to run when triggered.
2. **Per-tenant budget layer**: If Tenant A continues to generate background triggers, it may exhaust its tenant-level budget for the `background` tier. When the applicable tenant ceiling denies a pre-handler or catch-up candidate, that candidate is skipped and the corresponding `automation_script_skips_total{scope="tenant",reason="tenant_budget_exceeded"}` bucket increases; this path does not invoke `ScriptTenantBudgetService`. If a durable handler work item has been claimed for evaluation, a `ScriptTenantBudgetService` denial before executor acceptance cancels that handler before DSL evaluation, acquires no execution lease, and records no execution-start marker or charge; use `automation_script_triggers_total{outcome="tenant_budget_exceeded"}` plus `automation_script_tenant_budget_denied_total{scope="tenant",tier="background"}` and its handler audit row, never `automation_script_skips_total`. Each `high`, `normal`, and `background` ceiling is an independent capacity; exhaustion of the applicable ceiling denies every candidate governed by it regardless of priority, while priority orders candidates only while capacity remains. Tenant B’s budgets are independent; its `high`-priority `boss-ai` script is unaffected by Tenant A’s exhaustion.
3. **Cluster-level ceilings**: If total automation work across all tenants (including other games) approaches the cluster ceiling, the scheduler allocates capacity across tenants fairly before applying priority preference. Within each tenant's allocated share, it may favor `high`-priority scripts like `boss-ai` and defer or reject `background` work such as `npc-logger`; no priority bypasses tenant or cluster ceilings. See [ADR 0166](./decisions/adr-0166-attributable-script-breakers-and-tenant-first-fairness.md) and [Scripting Quotas & Operations](./system-architecture-scripting-quotas-and-operations.md) for the authoritative ordering and ceiling rules. Genuine pre-handler ingress rejections are reflected in `automation_script_triggers_dropped_total` with bounded reasons such as `cluster_limit_reached`; a live catch-up candidate denied after durable settlement increments `automation_script_skips_total{scope="cluster",reason="cluster_limit_reached"}` instead.

This example illustrates how the layers interact:

- Per-script quotas prevent any single script from running unboundedly.
- Per-tenant budgets prevent one tenant’s background scripts from starving another tenant’s automation.
- Cluster ceilings ensure the entire cluster remains healthy under extreme load while preserving cross-tenant fairness; high-priority, latency-sensitive scripts may be favored only within each tenant's allocated share.

## Operational Disable / Throttle Flows

Operators can disable or throttle scripts to respond to failures or abuse:

- **Disable now (hard stop)**:
  - Mark a script as disabled via the Game Design or Logging & Admin tools.
  - The Automation & Scripting Service flips `runtimeStatus=DISABLED` in script metadata.
  - The scheduler stops accepting new triggers for that script immediately (recording `script_event_audit.finalStage=ADMISSION`, `finalOutcome=script_disabled`, and a suitable `finalReason`, such as `admin_hard_disable`), but does not preempt in-flight runs; they are allowed to complete under existing quotas.

- **Soft-disable after current run**:
  - For scripts that should drain gracefully, administrators can set `runtimeStatus=DISABLE_AFTER_DRAIN`.
  - The scheduler continues to run any currently queued triggers up to a small grace window, then transitions the script to `DISABLED` once its active and queued counts reach zero.
  - Subsequent triggers are skipped and logged with `finalStage=ADMISSION`, `finalOutcome=script_disabled`, and a `finalReason` that reflects the drain behavior.

- **Throttling**:
  - Throttling is modeled as a temporary adjustment of per-script and per-tenant budgets rather than a separate toggle.
  - Operators can reduce `SCRIPT_QUOTA_LIMIT`, increase `intervalTicks`, or change `priorityTag` to `background`; the scheduler immediately applies the new configuration when evaluating triggers.
  - In addition, the failure-rate circuit breaker may set the exact core-script `breakerState` aggregate to `DISABLED_DUE_TO_ERRORS`, which behaves like a hard admission block until an administrator explicitly resets that exact breaker after validation. `GetScriptBreakerStatus` / `ListScriptBreakerEvents` are target-state reads for authoritative core-script state and `TRIPPED`/`RESET` history; `GetPluginStatus` / `ListPluginRuntimeEvents` are target-state reads for plugin breaker state and explicit `BREAKER_TRIPPED`/`BREAKER_RESET` rows. Until those target surfaces are implemented, use `script_event_audit` and live breaker metrics for classified handler failures and denied attempts, plus existing administrative/pre-DSL status reads for lifecycle or readiness; this fallback cannot reconstruct authoritative breaker state, transition history, or reset evidence. If a read model exposes `runtimeStatus=DISABLED_DUE_TO_ERRORS`, treat it only as the read-only effective-admission projection for the queried exact tuple. `script_event_audit` remains handler evidence (`finalOutcome=disabled_due_to_errors`, `finalReason=failure_rate_breaker`), not the owner transition history.

All disable/enable and throttle actions are idempotent and recorded with the acting principal (where available) via the `actorPrincipal` field, so operators can trace when and why a script stopped executing.

## Rollback & Recovery Scenarios

This section summarizes common failure and rollback scenarios and how operators should respond. It complements the per-feature lifecycle details in the DSL reference and modding framework documents.

- **Tenant script-patch readiness `FAILED` before instance pinning**
  - Symptoms:
    - For a given `<tenantId, scriptPatchVersion>`, audit entries with `eventType=onLoad` and `finalStage=DSL_EVAL`, `finalOutcome=sandbox_error` (or other logical failures) so you can distinguish `onLoad` evaluation failures from downstream persistence/handoff problems.
    - Pre-handler triggers referencing that patch produce event-scope ingress records and drop metrics such as `automation_script_triggers_dropped_total{reason="version_unavailable"}`; handler-scoped denials are diagnosed separately through `script_event_audit`.
  - Behavior:
    - The Automation & Scripting Service marks the patch `FAILED` for that tenant; it is not eligible for pinning, and running instances continue on their current previously pinned patch. Tenant readiness failure does not itself change an existing instance pin or mean that an instance reload failed.
  - Operator actions:
    - Use Game Design tooling to inspect and fix the script configuration, then publish a new patch.
    - Optionally disable the faulty script entirely (`runtimeStatus=DISABLED`) to stop further admission attempts while iterating.

- **Instance reload or reconciliation failure after pinning**
  - Symptoms:
    - An instance that observed a tenant-`READY` pin reports runtime-scope `reloadState=FAILED`; inspect `GetScriptPatchInstanceRolloutStatus(...)` or the Game Session-owned rollout history, and retain the previously observed patch version and pin epoch as diagnostic state.
  - Behavior:
    - Automation & Scripting discards partially loaded derived state, keeps new Automation admission fail-closed, and admits no new trigger or timer work until the current Game Session pin tuple, schedule ownership, scope, epoch, and due state are durably reconciled. Ordinary gameplay continues; the previously observed patch is diagnostic state only, not an active last-known-good execution fallback.
  - Operator actions:
    - Follow the fenced reconciliation or operator-authorized rollback procedure to establish an admissible current pin and schedule state before resuming work.

- **Stale `onLoad` execution**
  - **Target state only:** A stale `ONLOAD_RUNNING` readiness execution is terminalized by the Automation recovery owner as an audited `finalStage=DSL_EVAL`, `finalOutcome=canceled`, and `finalReason=stale_execution_fenced` result with durable work status `DEAD_LETTERED`, distinct from ordinary cancellation status `CANCELED`, and is explicitly non-replayable. It blocks `READY` only for the affected `tenantId`/`scriptPatchVersion`/readiness generation. The affected unresolved work and Automation admission barrier remain in force until that fencing and audit result are durable; the barrier does not pause unrelated instance runtime triggers, and ordinary gameplay ticks continue.
  - **Current behavior:** Stale `ONLOAD_RUNNING` recovery is not implemented. Fail closed by retaining the unresolved work and Automation admission barrier only for the affected `tenantId`/`scriptPatchVersion`/readiness generation; do not infer a terminal audit record, reclaim, replay, or safe resumption from age alone. The barrier does not pause unrelated instance runtime triggers, and ordinary gameplay ticks continue.
  - Do not replay or replace the stale readiness identity for the superseded patch. A newer immutable publication may progress independently under its distinct readiness identity; a late completion of the old execution is audit-only and cannot restore the old patch to `READY` or advance the newer patch. The old execution still requires owner fencing and terminal audit; that fencing is not an implicit retry.

- **Plugin version failures or misbehavior**
  - Symptoms:
    - Plugin lifecycle state in the Automation & Scripting Service shows `pluginState=FAILED` or frequent `sandbox_error` outcomes for `pluginId` / `pluginVersionId`.
    - Audit entries in `script_event_audit` tagged with `pluginId` / `pluginVersionId` show repeated failures, and plugin-specific metrics spike.
  - Behavior:
    - The modding framework keeps `activeVersionId` unchanged when a new plugin version fails validation or initialization; triggers for the failed version are rejected.
  - Operator actions:
    - Use Logging & Admin APIs to set the plugin to a disabled or drain state for affected tenants.
    - If the desired rollback target is older logic, publish a new signed bundle `pluginVersionId` that reintroduces that logic, then promote the new published version to `activeVersionId`. Historical `SUPERSEDED` versions are not reactivated directly.

- **Heavy timer drops or throttled `onInterval` handlers**
  - Symptoms:
    - For `onInterval`, high counts for `automation_script_skips_total{scope="tenant",reason="tenant_budget_exceeded"}` indicate only pre-handler/catch-up candidate-ceiling skips, not ordinary recurring handler denials. After a durable handler work item is claimed, a live `ScriptTenantBudgetService` denial before executor acceptance is handler-scoped: increment `automation_script_triggers_total{outcome="tenant_budget_exceeded"}` and `automation_script_tenant_budget_denied_total{scope="tenant",tier=~"high|normal|background"}` with its handler audit row, and never `automation_script_skips_total`. A live catch-up candidate denied by the cluster ceiling after durable candidate settlement uses `automation_script_skips_total{scope="cluster",reason="cluster_limit_reached"}`. Use `automation_script_triggers_dropped_total` only when the timer request is rejected under genuine pre-handler ingress semantics, not for a settled catch-up candidate.
    - Handler-scoped `onInterval` denials are diagnosed separately through `automation_script_triggers_total` outcomes and `script_event_audit` entries with `finalStage=ADMISSION` and outcomes such as `quota_denied`, `tenant_budget_exceeded`, or `version_unavailable`.
  - Behavior:
    - Recurring timer triggers produce at most one logical durable firing per Trigger Identity; dropped or skipped intervals are not replayed, although future firings may still occur. **Target-state recovery:** a failed physical evaluation attempt before `EVALUATED_COMMITTED` may retry only under the same identity and must converge on that same logical firing; after that boundary, descriptor recovery replays durable descriptors without re-entering the DSL. **Current live behavior:** unresolved `EVALUATING` work remains fail-closed and active, and the runtime lacks `EVALUATED_COMMITTED` plus descriptor replay, so this target recovery is not yet available.
  - Operator actions:
    - Reduce cadence (increase `intervalTicks`) or lower priority for noisy timers.
    - Adjust per-tenant budgets or cluster ceilings if drops reflect legitimate load rather than misbehaving scripts.
    - For persistent version-related drops, inspect tenant readiness with `GetScriptPatchStatus`/`ScriptPatchTenantStatusChanged` and, when an instance has already observed a new pin, inspect rollout/reload state with `GetScriptPatchInstanceRolloutStatus` plus Game Session's authoritative `ScriptPatchPinChanged` history before fixing and republishing or explicitly disabling the affected scripts.

In all of these cases, `script_event_audit` remains the primary source of truth for Automation-owned handler lifecycle. For the current live diagnostic boundary and target per-command identity contract, use [Command Identity and Live Handoff Boundary](./system-architecture-scripting-rollout-and-rollback.md#command-identity-and-live-handoff-boundary). Metrics defined by [normative Table 4](./system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix), together with audit and handoff diagnostics from the [Scripting & Automation Observability Contract](./system-architecture-scripting-observability-contract.md), indicate whether the problem is localized to a script/plugin, a tenant budget, or cluster capacity.

Target-state note: exact `scriptPinEpoch` propagation and final same-version old-epoch rejection are required at runtime-derived boundaries. The live `EnqueueAutomationCommandIfAbsentRequest` carries `scriptPatchVersion` but not `scriptPinEpoch`, so the current boundary cannot reject same-version work from an older epoch; this is an implementation gap, not a relaxation of the target fence.

## Rollback & Recovery Cookbook

This section summarizes common rollback and recovery scenarios for scripting and automation. It complements the broader backup and recovery guidance in [Backup and Recovery](./system-architecture-backup-recovery.md) and the versioning rules in [Versioning & Runtime Configuration](./system-architecture-versioning-runtime.md).

### Rollback Protocol and Diagnostics

The required rollback sequencing, state transitions, convergence deadline, and timeout behavior are owned by [Scripting & Automation: Rollout and Rollback](./system-architecture-scripting-rollout-and-rollback.md#patch-rollback-operator-driven-required). The underlying RPC contracts, request fields, and mutable state boundaries are owned by [Scripting & Automation: Control Plane API](./system-architecture-scripting-control-plane-api.md). This cookbook does not define a second rollback sequence or state machine.

Game Session's committed exact pin and append-only rollout history are the sole rollback mutation/history authority; Automation owns tenant readiness and eligibility evidence, while its instance pin/convergence/rollout reads are non-authoritative projections/diagnostics and cannot select or authorize a rollback.

For local diagnosis during a rollback:

The current runtime does not prove target-state drain recovery from lease age: unresolved `EVALUATING` work remains active and `PENDING_EVALUATION` remains pending; target cancellation treats `PENDING_EVALUATION` as cancelable pre-DSL work. These are pre-DSL states, not evaluated descriptor `PENDING` or `INDEXED` work. Keep the Automation admission barrier in place until exact pin convergence and schedule reconciliation succeed; do not wait for asynchronous cancel/purge cleanup. Cleanup remains bounded and non-blocking, while **target-state exact `(scriptPatchVersion, scriptPinEpoch)` fencing** remains authoritative. **Current live gap:** `EnqueueAutomationCommandIfAbsentRequest` carries `scriptPatchVersion` but not `scriptPinEpoch`, so the current handoff cannot reject same-version old-epoch work; do not infer target rejection as shipped. Ordinary gameplay ticks and player commands continue, except within a separately declared unfenced-effect workflow. Do not infer reclaim, terminalization, or safe resumption locally.

For pending and dead-lettered work, use control-plane APIs rather than direct data-store edits:

- Current implementation: `ReplayDeadLetteredWorkItems(tenantId=11111111-1111-4111-8111-111111111111, workItemIds=[work-9], controlPlaneRequestId=RB-42, actor=operator:alice, reason="rollback RB-42")` uses `workItemIds` as the executable parent-row selector. It does not select independent command descriptors and must not be described as complete command-level replay.
- **Target-state only and capability-gated:** `ListOutboxWorkItems(tenantId=11111111-1111-4111-8111-111111111111, gameInstanceId=44444444-4444-4444-8444-444444444444, scriptPatchVersion=P22, scriptPinEpoch=42, pluginId=town-crier, pluginVersionId=town-crier-v22, workItemStatus=PENDING)` inspects evaluated descriptor/outbox work for the instance; omit both plugin filters only when the operation is not plugin-owned. This read is diagnostic only: `bindingId`, `pluginActivationEpoch`, and `lifecycleRevision` are not supported filters and the listing does not establish replay or execution fencing. The current diagnosis remains the `PENDING_EVALUATION` and `EVALUATING` state distinction above, without treating either state as evaluated-command `PENDING`.
- **Target-state only and capability-gated:** `ReplayDeadLetteredWorkItems(tenantId=11111111-1111-4111-8111-111111111111, workItemIds=[work-9], controlPlaneRequestId=RB-42, actor=operator:alice, reason="rollback RB-42")` accepts bounded explicit work-item IDs only; descriptor references and filters are listing/preview inputs, not mutation selectors. Recovery fences the stored exact `(scriptPatchVersion, scriptPinEpoch)` tuple, current runtime `regionId`/`regionEpoch`, and admitted routing bundle (`playableStateScope`, world/realm identity, and pointer version); plugin work additionally requires the immutable `(pluginId, pluginVersionId, bindingId)` tuple, carries the captured `(pluginActivationEpoch, lifecycleRevision)` pair as execution-fence evidence, compares both values with current scoped Automation evidence, and fails closed with existing bounded reasons when current evidence is present and differs: `plugin_activation_epoch_mismatch` for an activation-epoch mismatch, or `plugin_binding_mismatch` for a lifecycle-revision/lifecycle-evidence or plugin tuple/binding mismatch. Same-epoch `DRAINING` is eligible only for already-admitted work whose winning admission/fence compare-and-set durably committed the immediately preceding `ENABLED` lifecycle revision before the owner committed the transition; `DRAINING` does not admit new work. Evaluation-stage retry may re-enter the DSL only for retryable infrastructure or temporary authority/fencing failures before `EVALUATED_COMMITTED`; logical, validation, sandbox, and proven tuple/policy/scope mismatches remain terminal/ineligible. When eligible, it invokes the DSL evaluator again under the complete original Trigger Identity, preserving every field including the same `scriptEventId` for handler replay identity and deduplication; `scriptEventId` remains correlation-only for command-child identity. It reuses the work-item identity, frozen trigger/manifest/graph evidence, and exact admitted immutable graph, outside normal admission with no dispatch or child identity before the winning descriptor/outbox commit; if commands emit, that commit allocates and persists one `automationDispatchId` with canonical ordinals. Post-evaluation recovery skips the DSL and resumes the stored output/child ledger with original child identities. Tenant-readiness `onLoad` is not eligible for this replay path; a stale readiness identity must be terminalized by its readiness owner and retry requires republishing a new immutable `scriptPatchVersion`. Missing or contradictory stage evidence and proven permanent tuple/binding/policy/scope mismatches remain dead-lettered/ineligible; temporary authority or policy unavailability, including unavailable or unverifiable plugin lifecycle-fence evidence, leaves eligible instance-bound work dead-lettered with no recovery claim and a bounded `rejectionReason` such as `component_policy_unavailable`, `signer_policy_unavailable`, or `authority_unavailable`; a later request may retry after evidence recovers.
- Replay phase semantics are stage-aware. A pre-claim authority or policy-unavailability result is `outcome=rejected`, records the bounded `rejectionReason`, creates no recovery claim or attempt, and leaves the row `DEAD_LETTERED`. Once a recovery claim/attempt is durably created, any failed evaluation or dispatch attempt must terminalize that attempt as `FAILED` and return `outcome=recovery_failed` with its persisted bounded `failureReason`; it must not be relabeled as a pre-claim rejection. A new request may create another attempt only after the prior attempt is terminal `FAILED` and fresh eligibility/fence checks pass; an `IN_PROGRESS` or unreconciled claim remains ineligible. Each requested ID returns exactly one bounded result (`retried_evaluation`, `resumed_dispatch`, `already_recovered`, `recovery_failed`, or `rejected`) with the canonical `failureGeneration` when a generation is resolved, bound to `(tenantId, outboxWorkItemId, failureGeneration)`, plus its applicable reason. The recovery claim/attempt has its own persisted attempt identity; this API does not expose a separate recovery-attempt generation, so no second generation field should be inferred. One row's result never changes another row's outcome or aggregate count.
- **Target-state only and capability-gated:** `PurgeOutboxWorkItems(tenantId=11111111-1111-4111-8111-111111111111, scriptPatchVersion=P22, scriptPinEpoch=41, workItemIds=[work-9], controlPlaneRequestId=PURGE-42, actor=operator:alice, reason="rollback RB-42")` is auditable cleanup only when each selected work item matches the displaced exact tuple, is terminal (`HANDED_OFF`, `CANCELED`, or `DEAD_LETTERED`), and its configured retention horizon has elapsed. For evaluated descriptor/output evidence, the parent must be `EVALUATED_COMMITTED`, the parent and every child/evidence record must be retention-eligible, and every child must be terminal before that evidence is purged; a same-version repin with a newer epoch does not by itself make terminal rows from the displaced tuple ineligible, but the selector must remain the displaced exact tuple so current-epoch rows cannot be selected. For a pre-DSL `DEAD_LETTERED` row with no committed descriptor, purge may remove only terminal, retention-eligible trigger/failure payloads after the recovery eligibility window has expired, after resolving the current `failureGeneration` and atomically CASing recovery claim/attempt state. Any current-generation `IN_PROGRESS` claim, including an expired claim not yet canonically reclaimed, rejects with `recovery_in_progress` and deletes no evidence; only when no current-generation claim exists or its claim/attempt is terminal may purge proceed. For that pre-DSL path, no new schema marker is introduced: the retained purge audit/idempotency outcome is the durable evidence and makes the row permanently non-recoverable, so later replay rejects deterministically with `rejectionReason=stage_evidence_unavailable`; its immutable identity/digest, failure-stage, corresponding `script_event_audit`, and recovery-causation evidence remain retained under their owning retention contracts. When terminal descriptor/evaluated-output evidence is purged under the retained parent, the same transaction persists durable `descriptorEvidencePurgedAt`; that marked parent is non-recoverable and non-replayable, and consumers reject it deterministically rather than treating missing children as recoverable. The purge does not mutate active or nonterminal work.

For command-level diagnosis, use the [Scripting & Automation Observability Contract](./system-architecture-scripting-observability-contract.md) and [Command Identity and Live Handoff Boundary](./system-architecture-scripting-rollout-and-rollback.md#command-identity-and-live-handoff-boundary). The target query is `ListScriptHandoffEvents`; child replay and deduplication use the complete source runtime scope plus any distinct target runtime scope, the persisted `automationDispatchId`, and deterministic `commandOrdinal` from canonical output order. The full parent Trigger Identity (including `bindingId` where applicable), `outboxWorkItemId`, and `scriptEventId` are correlation only; bounded `workItemIds[]` are parent-row selectors only and cannot replace the child identity. When a distinct target runtime exists, its complete query/reference identity includes `targetGameInstanceId`, optional `targetPlayableStateScope`, `targetRegionId`, and `targetRegionEpoch`. The current live fallback is the correlation of `script_event_audit`, narrower Automation handoff/work-item rows, `outboxWorkItemId`, `automationDispatchId`, `gameSessionCommandId`, and the Game Session command/result/fence fields currently exposed. Do not infer complete Trigger Identity or downstream per-command disposition from that fallback.

For the canonical rollback and version-fence requirements, follow [Scripting & Automation: Rollout and Rollback](./system-architecture-scripting-rollout-and-rollback.md#patch-rollback-operator-driven-required) and [Scripting & Automation: Cross-Service Contracts](./system-architecture-scripting-contracts.md#3-version-fencing-rollback-safety).

### Misbehaving Script Patch After Activation

Symptoms:

- A script patch has already been marked `READY` for a tenant and selected in the exact Game Session `(scriptPatchVersion, scriptPinEpoch)` tuple, but automation metrics and `script_event_audit` show sustained `sandbox_error` or `infrastructure_error` outcomes for one or more scripts.
- Players or operators report regressions that correlate with the newly pinned tuple (for example, NPCs stuck in loops, missing timers, or over-aggressive automation).

Behavior:

- The Automation & Scripting Service continues to enforce quotas, budgets, and failure-rate circuit breakers for individual scripts; misbehaving handlers may transition the exact core-script `breakerState` aggregate to `DISABLED_DUE_TO_ERRORS`. Any `runtimeStatus=DISABLED_DUE_TO_ERRORS` display is only a read-only effective-admission projection for the queried exact tuple.
- Recurring timer and event triggers produce at most one logical durable firing per Trigger Identity; skipped firings are not automatically replayed even if the patch is later rolled back. **Target-state recovery:** a failed physical evaluation attempt before `EVALUATED_COMMITTED` may retry only under the same identity and must converge on the same logical firing; after that boundary, committed descriptors recover without re-entering the DSL. **Current live behavior:** unresolved `EVALUATING` work remains fail-closed and active, and the runtime lacks `EVALUATED_COMMITTED` plus descriptor replay, so this target recovery is not yet available.

Operator actions:

1. Identify the affected scripts and patch.
   - Use `script_event_audit` filtered by the complete applicable Trigger Identity defined in [Table 1](./system-architecture-scripting-normative-contract-tables.md#table-1-trigger-identity-required-fields)—including all applicable runtime-scope, entity, event/schema, patch/epoch, `scriptEventId`, and `isDryRun` fields—and, when plugin-owned, the applicable `(pluginId, pluginVersionId, bindingId)` tuple to confirm which handlers are failing.
   - Correlate with automation metrics such as `automation_script_sandbox_failures_total`, `automation_script_errors_total`, and `automation_script_triggers_dropped_total` to determine scope and severity.
   - Use `ScriptPatchTenantStatusChanged` for tenant readiness gates and Game Session's `ScriptPatchPinChanged` plus bounded rollout-history read for instance rollout history; do not infer one from the other.
2. Contain impact at the script level.
   - Use the normal disable/throttle flows in this document to set offending scripts to `runtimeStatus=DISABLED` or a drain state while you triage (for example, `DISABLE_AFTER_DRAIN`).
3. Roll back the currently pinned script tuple if necessary.
   - If regressions are widespread or difficult to isolate, use the Game Session-owned workflow to explicitly repin the affected game instance to the target `scriptPatchVersion`; Game Session atomically allocates and returns the resulting `scriptPinEpoch` for the exact convergence proof. Concretely:
     - Query the Automation & Scripting Service via read-only APIs such as `GetScriptPatchStatus(tenantId, scriptPatchVersion)` and `GetScriptPatchInstanceRolloutStatus(...)`, and consume Game Session's `ScriptPatchPinChanged`/bounded history where available, to confirm tenant readiness and instance rollout state.
     - Call the Game Session control-plane APIs to update the pin (for example `SetPinnedScriptPatchVersion` or `RollbackScriptPatchVersion`) following the request/response contracts in [Scripting & Automation: Control Plane API](./system-architecture-scripting-control-plane-api.md) and the sequencing rules in [Scripting & Automation: Control Plane Operations](./system-architecture-scripting-control-plane-operations.md).
   - Repinning does not backfill skipped logical firings or rewrite existing automation queues; Automation admission is fenced during the workflow while ordinary gameplay ticks and player commands continue. **Target-state requirement:** every new execution propagates and uses the exact Game Session `(scriptPatchVersion, scriptPinEpoch)` tuple, and the new epoch fences work carrying the prior tuple.
   - Repinning must also ensure rollback safety:
     - Automation admission should remain paused for the affected scope through repin and schedule reconciliation; **target-state cleanup** is asynchronous, bounded, and non-blocking and must not delay resumption. This is not a routine gameplay-tick pause.
     - **Target-state cleanup:** queued automation work items and staging entries that carry the displaced exact `(scriptPatchVersion, scriptPinEpoch)` tuple are drained/purged as bounded resource and diagnostic cleanup; cleanup completion is not the correctness barrier and must not be described as preventing execution after repin.
     - **Target-state cleanup:** if plugin versions are also being rolled back, disabled, or revoked, call `CancelPendingWorkItemsForPluginVersion(tenantId=11111111-1111-4111-8111-111111111111, gameInstanceId=44444444-4444-4444-8444-444444444444, pluginId=town-crier, pluginVersionId=town-crier-v22, pluginActivationEpoch=7, scriptPatchVersion=P22, scriptPinEpoch=41, workItemIds=[work-9,work-10], controlPlaneRequestId=RB-42-PLUGIN-01, actor=operator:alice, reason="rollback RB-42")` with a nonempty, unique batch of at most 100 parent IDs (and optional `regionId`) before queue purge. Callers group IDs by the exact tuple and repeat batches with new request IDs; an exact retry reuses the stored batch result. The operation covers all applicable bindings in that tuple; each bounded result retains its `workItemId` and `bindingId` evidence. `lifecycleRevision` is intentionally absent from this request example: it is not a selector or request-digest field, and is retained per row and in final-fence evidence for later revalidation beside `pluginActivationEpoch`. Cleanup remains asynchronous and non-blocking and is not the correctness barrier.
     - **Target-state only:** before handoff, Automation validates and carries the exact `(pluginId, pluginVersionId, bindingId)`, captured `(pluginActivationEpoch, lifecycleRevision)` pair, and current lifecycle/publication/policy evidence for plugin work. That independent fence survives evaluation, persistence, handoff, replay, final execution, and dead-letter recovery. Same-epoch `DRAINING` permits only the immediately preceding `ENABLED` revision whose winning admission/fence compare-and-set durably committed before the transition; it does not admit new work. Game Session revalidates the exact script tuple and captured plugin lifecycle pair and rejects stale applicable plugin tuple or fence evidence at execution time, including same-version work from an older script epoch or plugin activation epoch. **Current live gap:** `EnqueueAutomationCommandIfAbsentRequest` carries `scriptPatchVersion` but lacks `scriptPinEpoch` and the complete plugin fence, so the current handoff cannot make those rejections; do not present them as shipped.
     - Use the [Command Identity and Live Handoff Boundary](./system-architecture-scripting-rollout-and-rollback.md#command-identity-and-live-handoff-boundary) contract. For current live incidents, correlate `script_event_audit`, the narrower Automation handoff rows, and the Game Session command/result/fence fields currently exposed; do not infer a complete Trigger Identity or downstream per-command disposition.
4. Repair and republish.
   - Fix the underlying script configuration in the Game Design Service and publish a new script-only patch version.
   - Verify that the new patch completes the tenant-scoped pre-instance-pin readiness path (`PENDING_VALIDATION` -> `ONLOAD_RUNNING` -> `READY`) and that its tenant-readiness `onLoad` initialization succeeds. Only after that gate does Game Session explicitly pin the patch for an instance and allocate the new `scriptPinEpoch`; instance rollout and schedule reconciliation follow that pin rather than being prerequisites for tenant `READY`.
