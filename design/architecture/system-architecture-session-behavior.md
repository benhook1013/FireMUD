# FireMUD System Architecture: Session Behavior

This document defines gameplay takeover, reconnect, token refresh, membership-version handling, and control-plane logout behavior. It is the owner for the namespace-scoped controller and binding-generation contract (decision key `SESSION-02`) and the local session consequences of the canonical reconnect/authentication rules. It complements [Authentication & Authorization](./system-architecture-authentication.md), which defines the end-to-end authn/authz model and gameplay admission flow.

## Canonical Authority Tuple

The canonical `authorityTuple` schema, exact nested field names, profile requirements, and registry mapping are defined in [JWT and Token Contracts](./system-architecture-jwt-and-token-contracts.md#canonical-authority-tuple). This document does not duplicate that schema. Session behavior copies the canonical tuple unchanged into applicable events, leases, bindings, refresh requests, rebind proofs, registry records/claims, and installation acknowledgements; missing applicable evidence, extra scope, malformed values, or mismatches fail closed.

Session behavior uses one immutable `membershipBaseline` carrier for each admission or replacement operation:

```json
{
  "membershipLifecycleState": "<Account membership lifecycle state>",
  "membershipVersion": { "<exact tenantId>": "<canonical membership version>" },
  "membershipAuthorityGeneration": "<exact account/tenant membership authority generation>"
}
```

The object is captured from one Account snapshot and is carried unchanged, as one object rather than three independently sourced fields, through the admission lease, lease identity and request digest, Game Session binding CAS, Account finalization and `COMMITTED` comparison, and every exact retry/replay. Each boundary compares the complete object, including lifecycle state, the sole tenant key/value, and the exact membership authority generation; missing, extra, scalarized, null, stale, or differently keyed evidence fails closed. A new refresh or rebind operation may establish a new baseline only from its own Account snapshot; it must not mutate the baseline inside the operation being retried or finalized. The `billing_safe_tenant` exception omits the target-tenant generation only from route comparison, never from this required carrier or the canonical tuple shape. Account owns all canonical authority-generation projections; Game Session may maintain only the distinct derived issuer projection and schema defined by [ADR 0022](./decisions/adr-0022-account-authority-and-gameplay-session-ownership.md).

Target admission behavior carries the same unchanged `membershipBaseline` through admission lease state, lease identity/digest, the Game Session binding CAS, Account finalization and `COMMITTED` evidence, and all retries/replays. The separate `membershipVersion` map remains available wherever the canonical JWT or authority contract requires it, but it is never used as a substitute for the baseline object or for `membershipAuthorityGeneration`.

The canonical `outboxCheckpoints` entry schema remains the ADR 0030 `{outboxStreamKey, outboxSequence}` carrier; [ADR 0022](./decisions/adr-0022-account-authority-and-gameplay-session-ownership.md#canonical-checkpoint-and-source-evidence-binding) defines its bytewise ordering and the separate same-snapshot source-evidence binding. Session behavior carries the exact complete checkpoint array unchanged through authority-event delivery, admission and refresh leases, binding CAS, refresh, rebind, installation acknowledgement, retries/replays, and every request or response digest; it never reconstructs the set from a latest checkpoint, aggregate maximum, or separately read event evidence.

Retained per-sequence duplicate evidence is a separate same-snapshot carrier, not an expanded checkpoint entry. Its canonical schema is `{outboxStreamKey, outboxSequence, eventId, eventDigest, authorityTuple, issuanceFence, membershipBaseline, outboxCheckpoints}` when membership applies; a non-membership scope omits `membershipBaseline` rather than fabricating membership values. The complete evidence is retained for each bounded sequence window or proven by an authoritative Account lookup for the exact stream and sequence. A checkpoint array alone, an event ID/digest pair alone, a generation-only match, or evidence assembled from another Account snapshot is never duplicate proof.

## Canonical Monotonic Integer Strings

`outboxSequence` is a scalar JSON string containing a canonical non-negative base-10 integer. `membershipVersion` is not a scalar in this contract: it is the exact map `{tenantId: version}`, and the grammar below applies independently to each map value. The only accepted value grammar is `0` or a nonzero digit sequence with no leading zero (`[1-9][0-9]*`). Values must be JSON strings; empty values, signs, decimal points, exponents, nonfinite values such as `NaN` or `Infinity`, other numeric types, and any alternate spelling are rejected. Consumers validate the complete membership map and exact tenant key, then may parse a value as a process-local arbitrary-precision integer before high-water comparisons. They must never compare strings lexicographically or convert values through IEEE-754 numbers. For `outboxSequence`, the existing sequence-0 baseline and positive-sequence checkpoint rules still apply.

## Implementation Status

Membership-change event delivery and generation-aware session consumption are not yet live. The current `GetTenantMembershipForRuntimeResponse` and `AccountGrpcService` producer expose `accountId`, `tenantId`, `membershipExists`, `gameplayAdmissionAllowed`, `membershipVersion`, `evaluatedAt`, and `error`; the current Game Session `PLAY` path consumes that response, while roles, the target exact one-tenant `membershipVersion` map carrier, `membershipAuthorityGeneration`, `authorityTuple`, `outboxCheckpoints`, Account event delivery, generation-aware consumers, same-stream reconciliation, remaining player-facing legacy mapping, and focused proof across admission/reconnect paths remain gaps. The versioned Account-owned token-registry rules and binding schema below are target state, not current runtime behavior: the current fallback uses the legacy Account session key rather than the canonical issued-token registry. Game Session must not treat the contract below as fully implemented until those fields, consumers, and proofs converge. The target Account-durable-intent-before-Gateway-marker logout ordering and final Account token-fence invalidation are also not currently proven; the current fallback is Account logout plus local cleanup and bounded expiry, not proof of complete logout.

Account Service is the sole writer of account authority-generation advances and all canonical `session:auth:generation:*` projections, including `session:auth:generation:account:<accountId>`. Account commits every applicable canonical tuple field, cutoff, `issuanceFence`, and monotonic outbox event together; the generation projection is an asynchronous outbox output, not an atomically committed part of that durable generation/event transaction. Game Session and other downstream services consume Account-owned generation events and projections; they must not advance canonical authority or write canonical projections directly, and they fail closed while projection or freshness/source evidence is missing, stale, malformed, regressed, or ambiguous. Game Session's only generation projection write is its derived `session:game:auth:issuer-generation:v1:<issuerId>` consumer-local record under the ADR 0022 schema.

For account security events, Account alone advances the durable authority tuple, applicable cutoff, and `issuanceFence` and emits the corresponding committed outbox event in the same Account transaction; an asynchronous projection consumer later applies each canonical generation set-if-greater. Game Session consumes that event and projection idempotently, applies the separate derived issuer projection set-if-greater, and revokes only its owned gameplay bindings through the bounded issuer, account, tenant, membership, private-realm, and character-uniqueness indexes plus their ordered repair/CAS protocol; it must not scan Redis, advance Account authority, write canonical projections, or infer authorization from a missing or stale projection.

## Replacement-State Continuity

[ADR 0122](./decisions/adr-0122-stable-playable-state-namespaces-for-runtime-replacement.md) adds a stable `playableStateNamespaceId` to the session's resolved gameplay context. Target controller uniqueness, admission, takeover, and resume use `{tenantId, playableStateNamespaceId, characterId}`. A binding still carries `playableStateScope`, realm-routing identity, region placement, and runtime fences as separate context, but those fields do not create a second controller slot. The bound `gameInstanceId` must be the active fenced instance for that namespace; a stale instance binding is never durable character identity. The current implementation remains keyed by `{tenantId, gameInstanceId, characterId}` and does not prove the namespace-qualified uniqueness CAS. [ADR 0123](./decisions/adr-0123-database-authoritative-temporal-coordinated-world-lifecycle.md) keeps lifecycle row/epoch and cleanup completion in the owning database; a Temporal workflow or Redis session record cannot independently authorize replacement or termination. Existing implementation and proof gaps remain.

### Namespace-scoped controller transfer (SESSION-02)

The one-controller invariant is exactly one active gameplay controller for `{tenantId, playableStateNamespaceId, characterId}`. A successful authorized `PLAY` for an occupied key performs one atomic compare-and-set transfer that installs the new binding and advances a strictly monotonic `bindingGeneration`; delete-then-create sequences that expose an unowned or dual-owned interval are not valid implementations. `gameInstanceId`, realm scope, region, and transport identity remain binding evidence and routing context, not uniqueness keys.

At the transfer linearization point, the old binding becomes non-admitting for new input. Input arriving from the displaced transport after that point is rejected, while work durably admitted before it retains its existing command/effect identity and follows its ordinary durable execution and reconciliation contract. Takeover does not recreate admitted work from client input, blindly cancel it, reset character-owned ticks/timers/state, or require close-frame delivery to make the transfer authoritative. Closing the displaced transport and emitting `session_replaced` are best-effort consequences after the CAS; failure to deliver them never restores old authority.

## Multi-Client Behavior and Session Takeover

Each gameplay identity can only be controlled by one session at a time. The target uniqueness and CAS owner key is `{tenantId, playableStateNamespaceId, characterId}`; `playableStateScope` and `gameInstanceId` are carried as binding/routing evidence, not as additional controller keys.

If a new login is received for the same active uniqueness key:

- Game Session first fences source command admission and all affected region bindings, reconciles every already-admitted command, completes the applicable repair and lease checks, and performs the final admissible `bindingGeneration` CAS.
- Only after that CAS succeeds is the existing source session terminated and its Redis binding rebound to the new socket; a failed, incomplete, or ambiguous fence, reconciliation, repair, lease check, or CAS leaves the source session and binding usable while the target waits or fails closed.
- Tick state, command queues, and timers are preserved.

This enables:

- Clean device handoff.
- Forced logins (for example "kick and take over").
- Session continuity with at-most-once edge delivery semantics. In-flight command loss at disconnect boundaries remains possible.

During replacement, a fresh `PLAY` or reconnect for the same `{tenantId, playableStateNamespaceId, characterId}` may take over on the target only through the atomic binding-generation CAS described above. Game Session fences new source input, retains the source identity for already-admitted work, and performs the applicable reconciliation and lease/index checks before the transfer can commit; target commands are admitted only after the CAS succeeds. Other source-session identities may continue under the ordinary bounded source-drain deadline. Missing or ambiguous reconciliation, an incomplete region acknowledgement, an unresolved repair, a failed lease check, or a failed CAS leaves the target waiting or fails it closed. This reuses the session binding fence and does not introduce a replacement lease or shorten the general source-drain policy.

Game Session uses Redis locks only to serialize session rebind and takeover operations; they never authorize a replacement or select the active runtime. Replacement-runtime cutover requires the owner-database admission-pointer expected-version CAS, authoritative lifecycle row/epoch, cutover hold, and fresh namespace-bound active-instance authorization under [ADR 0122](./decisions/adr-0122-stable-playable-state-namespaces-for-runtime-replacement.md) and [ADR 0123](./decisions/adr-0123-database-authoritative-temporal-coordinated-world-lifecycle.md). Same-runtime takeover instead requires the `{tenantId, playableStateNamespaceId, characterId}` `bindingGeneration` CAS plus fresh namespace-bound active-instance authorization and performs no pointer swap. See [Redis Architecture](./system-architecture-redis.md#session-keys-and-gameplay-binding) for the serialization boundary.

## Mid-Session Role Updates

If roles change during an active session (for example, a player is promoted to admin):

1. The Game Session Service detects or requests a role refresh.
2. It contacts the Account Service to obtain a new JWT.
3. Updated token context is used for Game Session's subsequent calls to auth/control-plane services; gameplay-domain gRPC calls use typed `PlayerExecutionContext` derived from current authoritative session state rather than forwarding per-player JWT claims downstream.

The Game Session Service exposes `/sessions/{sessionId}/refresh-roles` for manual refreshes. Implementations must ensure the effective claims injected into subsequent backend calls reflect the latest role assignments without requiring players to re-login.

This process is invisible to the client; no re-login is needed.

This is backend role-context maintenance only. It does not prompt for another gameplay factor, reauthenticate the active gameplay session, or turn global account/control-plane roles into gameplay authority.

Membership changes that affect tenant access follow a stricter target contract than ordinary role refresh:

1. The Account Service emits a membership-change event containing `accountId`, `tenantId`, `membershipLifecycleState`, `membershipVersion`, complete applicable `authorityTuple`, positive `issuanceFence`, `outboxStreamKey`, `outboxSequence`, the complete stream-key-ordered `outboxCheckpoints`, `changedRoleSet` as the complete post-change role snapshot represented by a sorted array of unique ASCII role identifiers under the canonical bytewise comparator, whether gameplay admission remains allowed, the Account-committed boolean `callerBoundAuthorityInvalidated`, and `eventDigest` from that same authoritative snapshot/checkpoint.
2. Game Session compares the event against active gameplay bindings for `{accountId, tenantId}`.
3. Losing tenant membership or losing gameplay-admission authority (for example removal of `player` or a required private-realm grant) immediately revokes the affected gameplay sessions. Planned realm or playtest closure uses the owning close-and-drain workflow before grants are revoked; grant revocation itself is not a graceful-drain mechanism.
4. For caller-bound tenant control-plane access, the Account Service must also advance the `{accountId, tenantId}` membership authority generation when membership or tenant-role changes invalidate previously issued tenant authority for that caller.
5. Non-gameplay role changes may be handled by in-session token refresh for gameplay state, but reconnect/resume must compare the unchanged stored `membershipBaseline` against the current Account-owned baseline before restoring gameplay. Its `membershipLifecycleState`, exact one-tenant `membershipVersion` map, and `membershipAuthorityGeneration` are independent members of one same-snapshot object; missing, unavailable, or unequal current values fail closed, and no member substitutes for another.
   The corresponding Account-owned projection is `session:auth:generation:membership:<accountId>:<tenantId>` and is applied set-if-greater; missing, unavailable, or stale evidence fails closed.
6. `PLAY` and reconnect/resume must obtain the complete `membershipBaseline` from one authoritative membership read rather than inferring its lifecycle, map, or generation members from JWT claims or local caches; a process may extract the map value only after validating the complete carrier.

Target membership-change event delivery semantics are required, not best-effort folklore:

- Every event must include `schemaVersion`, a stable `eventId`, `eventType`, exact `outboxStreamKey`, `outboxSequence`, `sourceScope`, `occurredAt`, `eventDigest`, and the complete payload tuple `{accountId, tenantId, membershipLifecycleState, membershipVersion, authorityTuple, issuanceFence, changedRoleSet, gameplayAdmissionAllowed, callerBoundAuthorityInvalidated, outboxCheckpoints}`; `outboxCheckpoints` is the complete stream-key-ordered checkpoint set from the same Account snapshot, not a latest-only or aggregate value.
- A role identifier is an ASCII string matching `[A-Za-z][A-Za-z0-9_-]*`; its bytes are used exactly as supplied, so case variants are distinct and whitespace, non-ASCII characters, Unicode escapes that decode to non-ASCII, and other spellings are invalid. `compareRoleIdentifierBytes(a, b)` is the one canonical comparator: compare the unsigned identifier bytes lexicographically, with the shorter identifier first when one is a prefix. Producers validate every identifier, reject bytewise duplicates, and sort `changedRoleSet` with this comparator without Unicode normalization, locale collation, case folding, or other transformation. Consumers apply the same validation and comparator and reject an unsorted, duplicated, malformed, or differently normalized array; `[]` is the only empty representation.
- `eventDigest` has one canonical meaning: it is `sha256:` followed by 64 lowercase hexadecimal characters for SHA-256 over UTF-8 RFC 8785 JSON Canonicalization Scheme bytes of the complete membership-event envelope and payload, excluding only the `eventDigest` field itself. The canonical schema field set is exactly `schemaVersion`, `eventId`, `eventType`, `outboxStreamKey`, `outboxSequence`, `sourceScope`, `accountId`, `tenantId`, `membershipLifecycleState`, `membershipVersion`, `authorityTuple`, `issuanceFence`, `changedRoleSet`, `gameplayAdmissionAllowed`, `callerBoundAuthorityInvalidated`, `outboxCheckpoints`, and `occurredAt`. Every field in that emitted envelope, including `eventDigest`, is required and non-null; `changedRoleSet` is the complete post-change role snapshot as a sorted array of unique role identifiers and uses `[]` when empty, not an added/removed delta or an unordered set. `outboxCheckpoints` is complete, canonicalized in stream-key order, and comes from the same authoritative snapshot as the payload tuple. Any optional members nested inside `authorityTuple` use the canonical authority-tuple presence rules rather than a new event-specific encoding. An absent optional nested member is represented by omission, never by JSON `null`, an empty string, or a sentinel. `outboxSequence` is a canonical unsigned base-10 JSON string. `membershipVersion` uses the canonical exact one-tenant map `{tenantId: version}`; its sole value uses that same unsigned-string grammar. This preserves values beyond IEEE-754 exact-integer range and the shared carrier shape across implementations. RFC 8785 preserves string data as supplied; producers perform no Unicode normalization before canonicalization. No envelope field may be omitted, added, or serialized through an alternate grammar. Account computes the digest and consumers recompute and compare it before applying or acknowledging the event.
- The sole value in the validated exact one-tenant `membershipVersion` map must be monotonic per `{accountId, tenantId}` and must advance on any role or membership change that can affect gameplay or tenant-safe control-plane authority. A consumer may extract that value only as a process-local arbitrary-precision integer after validating the complete map and exact tenant key; the event, digest, projection, and binding retain the map. `membershipAuthorityGeneration` is a separate authority fence that advances only when `callerBoundAuthorityInvalidated=true`, meaning the change invalidates previously issued caller-bound tenant authority. A non-revoking change must carry `callerBoundAuthorityInvalidated=false`, the current unchanged opaque generation, and complete same-snapshot `authorityTuple`/`issuanceFence`/checkpoint evidence proving that no prior caller-bound authority was invalidated. Missing or mismatched proof fails closed. Consumers must not substitute `membershipVersion` for the generation or use either field as the other's proof.
- Consumers maintain two independent high-water marks per `{accountId, tenantId}`. `membershipVersion` orders membership projection state, and the membership projection payload, including the complete `changedRoleSet` snapshot, changes only when the event's version is newer than the stored membership version. `membershipAuthorityGeneration` is an independent set-if-greater revocation fence. An event with a newer authority generation and an equal or older membership version advances only that separate authority fence and triggers authoritative membership reconciliation; it must not apply its role set, `changedRoleSet`, `gameplayAdmissionAllowed`, or other membership payload over the newer projection and must not downgrade projection state. An event with a newer membership version updates membership state from that event's complete post-change role snapshot even when the authority generation is unchanged, subject to the complete Account evidence check. Only an event that is not newer on either dimension is a duplicate/no-op.
- Consumers maintain `lastAppliedSourceOutboxSequence` per exact `outboxStreamKey` plus bounded retained duplicate evidence using the canonical separate schema `{outboxStreamKey, outboxSequence, eventId, eventDigest, authorityTuple, issuanceFence, membershipBaseline, outboxCheckpoints}` when membership applies. For sequence `0`, permitted only when the Account-owned stream has no committed event, `lastAppliedSourceEventId` and `lastAppliedSourceEventDigest` are omitted from the projection, and there is no duplicate-evidence entry; JSON `null`, an empty string, a zero digest, or another sentinel is invalid. For every positive sequence, `lastAppliedSourceEventId`, `lastAppliedSourceEventDigest`, and every applicable duplicate-evidence field are required non-null values in their canonical formats. An event at or below `lastAppliedSourceOutboxSequence` is a no-op only when the complete retained evidence matches or an authoritative Account lookup for the exact `(outboxStreamKey, outboxSequence)` proves the same event identity, complete payload including `membershipLifecycleState` where applicable, `authorityTuple`, `issuanceFence`, `membershipBaseline` where applicable, complete `outboxCheckpoints`, and `eventDigest`; a watermark or event ID/digest pair alone is never duplicate proof. For a new event above the watermark, the next sequence must be contiguous; a higher sequence is a gap only within that same stream, and an unrelated issuer, account, tenant, membership, or grant stream never creates a gap. If older evidence has aged out, the lookup is unavailable, or the same sequence has different authoritative evidence or digest, the consumer quarantines the stream and stops affected admission/reconnect until exact Account reconciliation succeeds. A same-key gap or same-sequence mismatch, including any invalid absent/null representation, stops affected admission/reconnect and requires Account reconciliation of the exact checkpoint before processing resumes; it must never be accepted as an idempotent duplicate.
- An event whose `membershipAuthorityGeneration` is lower than the current consumer or Account value must not apply its payload, even when its `membershipVersion` is newer. The consumer rejects that payload, quarantines the affected stream/scope, and reconciles one complete Account snapshot containing the authority generation, membership map, full `outboxCheckpoints`, and same-snapshot event evidence before resuming; it must not choose the newer membership version or silently preserve the lower-generation event.
- If Game Session detects a version gap or has no prior version for an active binding, it must reconcile immediately via the authoritative internal membership API before deciding whether the session remains valid.
- Account Service owns the version increment rules; other services must not synthesize membership versions locally.
- The two high-waters have independent meanings and must be stored independently per `{accountId, tenantId}`: `membershipVersionHighWater` orders the Account membership projection, while `membershipAuthorityGenerationHighWater` is the set-if-greater revocation fence for previously issued caller-bound authority. `lastAppliedSourceOutboxSequence` is a separate exact-stream delivery watermark and is never replaced by either membership high-water. A newer generation with an equal or older membership version is valid ordering, advances the separate revocation fence without applying or downgrading the membership projection payload, and requires authoritative membership reconciliation before affected gameplay is retained or admitted. A newer membership version with an unchanged generation is valid only when the Account snapshot proves that the change did not invalidate previously issued tenant authority; it updates membership state but does not imply revocation. A membership-version advance that removes gameplay authority without the corresponding Account generation evidence, a generation value that regresses relative to the Account snapshot, or any pair assembled from different checkpoints is inconsistent.
- On an inconsistent pair, Game Session stops new admission and reconnect/resume for the affected scope and does not choose the larger value, reset either high-water, or substitute one field for the other. It requests one authoritative Account membership snapshot containing both values, `gameplayAdmissionAllowed`, `evaluatedAt`, the applicable authority tuple, and its outbox checkpoint. Only after that atomic snapshot reconciles both high-waters and the membership state may validation resume; unavailable reconciliation remains `AUTH_UNAVAILABLE`, while reachable contradictory or revoked evidence remains denied/revoked. It must retain a newer authority fence even when the membership version was already seen, but must not apply that event's older membership payload or treat a membership-version advance alone as proof of revocation.
- Focused proof must show that Account emits the event's `membershipAuthorityGeneration` from the same committed snapshot: advanced when `callerBoundAuthorityInvalidated=true`, or unchanged when that flag is false. Game Session rejects missing or mismatched generation evidence rather than substituting `membershipVersion`.

Target transaction and consumer contract: once implemented, Account commits each security, membership, grant, or billing authority change, the corresponding durable Account-owned authority-generation or grant-version advance, every applicable cutoff and `issuanceFence`, and its monotonic outbox event in one database transaction or composite CAS/fence. Redis and other downstream projections then idempotently reflect the committed authority state. The cutoff workflow does not report enforcement complete until the required projection and consumer convergence succeeds. Game Session consumes the durable events through an idempotent consumer and maintains the canonical bounded active-binding indexes listed below; correctness must not depend on wildcard Redis scans.
The downstream generation projection uses set-if-greater semantics and may not move authority backward. For a membership or authority-generation event, the Account authority-generation commit atomically includes the exact one-tenant `membershipVersion` map, complete applicable `authorityTuple`, `issuanceFence`, full stream-key-ordered `outboxCheckpoints`, and the event payload/digest from that same durable snapshot; a consumer must reject any event assembled from different snapshots.

For every registry, lease or lease-fence, binding or binding-index, token-identity fence, non-entitlement Account evidence, lease commit, token issuance dependency, outbox/checkpoint delivery, issuer-generation projection, or required Account reconciliation dependency, an unavailable or timed-out dependency returns retryable `AUTH_UNAVAILABLE`. The distinct ADR 0028 entitlement-only path returns `ENTITLEMENT_UNAVAILABLE` when entitlement evaluation alone is unavailable and no eligible same-binding LKG entitlement value supplies that input; it never covers a failed lease, binding, token-identity fence, non-entitlement authority read, lease commit, token issuance dependency, outbox/checkpoint delivery, projection, or reconciliation dependency. Separately, ADR 0037 bounded active-binding continuity may keep an already-admitted connected binding operating only under its prior-positive, unexpired authority-freshness lease and live coordination-health predicate. That continuity does not authorize new admission, reconnect/resume/rebind, scope expansion, lease renewal, token issuance/refresh, or extension or recreation of the lease. A reachable missing, malformed, stale, regressed, expired, or mismatched value is invalid/revoked. No cache, empty projection, Redis presence/absence, or local binding may override that classification.

When the ADR 0028 same-binding entitlement fallback applies, its canonical deadline is `entitlementFallbackDeadline = min(effectiveContinuityDeadline, fallbackAt + 5 minutes, fallbackAt + session_expiration_ms)`, with `effectiveContinuityDeadline = min(continuityBindingExpiresAt, resumeDeadline)` for a disconnected binding or `min(continuityBindingExpiresAt, connectedSessionDeadline)` for an eligible connected binding, and `session_expiration_ms = min(FIREMUD_AUTH_SESSION_EXPIRATION_MS, 300000)`. The fallback expires at that deadline and cannot be replaced by an implementation-local timer, a refreshed Redis TTL, or active-binding continuity.

The LKG entitlement evidence used for that fallback must satisfy `evaluatedAt <= localNow + maxClockSkew` and `localNow - evaluatedAt + maxClockSkew` strictly below the applicable freshness bound. A future timestamp beyond `maxClockSkew` fails closed; a timestamp within the bound never widens the bound, and the exact freshness boundary is expired.

An accepted, delivered authority event is the immediate revocation path: Game Session targets the affected bindings, closes their active sockets, and removes their admission state without waiting for the reconciliation interval. The `<=60-second` bound applies only when an event is missed, delayed, or cannot be consumed; batched authority-generation/version reconciliation must then discover the stale authority and terminate the affected bindings within that bound. If the reconciliation lease cannot be renewed, new admission, reconnect/resume/rebind, and token issuance/refresh fail closed; active bindings whose authority cannot be re-established are terminated at the bound, and no local retry extends or recreates the stored lease deadline. This is periodic per-authority reconciliation, not an Account or Redis lookup on each gameplay command.

## Session and Identity Management

FireMUD deliberately distinguishes between several types of sessions so that identity, gameplay continuity, and auth token lifetimes can evolve independently:

- **Auth token sessions (target state)** – Represented by one versioned, Account-owned `session:auth:token:<tokenHash>` issued-token registry record per revocable JWT in Coordination Redis, backing meta/control and admission APIs. The current runtime still uses the legacy Account session key and does not yet provide this registry proof.
- **Gameplay-connect issuance/replay records** – Dedicated short-lived records for one-use edge credentials, separate from the ordinary `session:auth:token:<tokenHash>` registry/session; Gateway's consume marker is part of this edge replay boundary and does not authorize gameplay.
- **Bootstrap transport session contexts** – Current Game Session implementations store pre-auth socket context under the `sessionctx:*` key family. These records may exist before `LOGIN`, may have no account or membership authority, and are used only for bootstrap scope, locale, and reconnect lookup plumbing.
- **Gameplay sessions** – Tenant-scoped bindings between a connected socket (or reconnect token) and a character in a specific tenant, backed by gameplay Redis keys.
- **Control-plane UI sessions** – Browser or desktop admin/creator sessions that hold short-lived JWTs client-side and rely on auth token sessions on the server.

The Game Session Service is responsible for:

- Authenticating sockets and binding identity context.
- Managing gameplay Redis session state such as `characterId`, `tenantId`, and tick region.
- Obtaining Account-issued JWTs for backend interactions. Game Session never mints JWTs; Account is the sole JWT issuer.

### Session Types and Lifetimes

FireMUD uses distinct lifetimes and invariants for each session type:

- **Issued-token registry records**
  - Key: `session:auth:token:<tokenHash>` on Coordination Redis, where `<tokenHash>` is a fixed-length SHA-256 digest of the complete compact JWT.
  - Purpose: one versioned Account-owned issuance and immediate per-token revocation record for each revocable `control-ui`, `player-bootstrap`, or receiver-specific private player-delegation JWT. Signed claims plus Account-owned revocation/version state govern tenant/global authority without additional per-scope token keys.
  - Lifetime: `registry_ttl_ms = max(0, token_exp_ms - now_ms) + FIREMUD_AUTH_SESSION_SAFETY_MARGIN_MS`, so the normal cleanup lifetime retains each record through that token's actual JWT `exp` plus the cleanup margin. Records are not extended by client activity. Per-token logout may delete a record earlier only after Account durably commits the exact-token `PENDING_LOGOUT`/revocation fence or equivalent tombstone intent; deletion is cleanup, not proof of revocation. A reachable missing record always denies protected use and requires fresh authentication, while an unavailable registry returns `AUTH_UNAVAILABLE`. Coordination Redis resets that drop registry records and authority projections likewise force re-authentication rather than reconstructing authority from the JWT.

- **Gameplay session bindings**
  - Keys: tenant-scoped session keys described in [Redis Architecture](./system-architecture-redis.md#session-keys-and-gameplay-binding), storing `accountId`, `tenantId`, `characterId`, and tick-region context.
  - Purpose: bind a connected socket or reconnect token to a character in a specific tenant, enforce one session per character, and support reconnect flows.
  - Lifetime: on successful gameplay admission at `admissionAt`, Game Session stores the immutable continuity anchor `continuityBindingExpiresAt = admissionAt + session_expiration_ms`. Passing it does not itself end a continuously connected, currently authorized session, but the old binding cannot resume after a later transport loss. The authoritative active binding and its current revocation/fencing state are distinct from the expiring reconnect/transcript cache; cache refresh cannot extend active or resume authority, and cache loss cannot authorize a new binding. The Redis TTL is physical cleanup metadata and may refresh while active without moving the anchor. Each connected-to-disconnected transition starts an immutable episode at `disconnectAt`, with `resumeDeadline = min(continuityBindingExpiresAt, disconnectAt + effective firemud.reconnection.policy.resume-window-ms)`. Failed reconnects cannot extend that pair. Successful resume consumes the episode; a later transport loss starts a new episode bounded by the same continuity anchor. An `auth-revoked` result received while connected must first terminate the active binding and create this disconnection episode before any fresh re-admission. Redis key presence and transcript retention are not sufficient authority to resume.

- **Bootstrap/pre-auth session contexts**
  - Keys: current implementation-local `sessionctx:*` entries described in the Game Session runtime docs.
  - Purpose: remember transport-level bootstrap context before gameplay authentication completes.
  - Lifetime: bounded by the same session-expiration family for cleanup, but these entries are not logically resumable gameplay sessions until `LOGIN` and `PLAY` have established authenticated gameplay scope.

Game Session must also maintain bounded authoritative secondary indexes for gameplay bindings so takeover, reconnect, and revocation do not require scans. There are six physical index families in total. The character family is a tenant-scoped uniqueness index; the other five are bounded cutoff/revocation families. Four families are tenant-scoped and share the shard-local session CAS, while the account family is one untagged account-wide key and the issuer family is a finite set of global-per-issuer partitions; both spanning families use the separate repair protocol below:

- `session:game:index:character:{tenantGameplayTag}:<playableStateNamespaceId>:<characterId>` -> `{sessionId, gameInstanceId, bindingGeneration}`; `playableStateScope` remains binding evidence but is not part of the controller-uniqueness key.
- `session:game:index:account:<accountId>` -> generation-safe active tenant-qualified `accountIndexMember` set across all tenants for the account
- `session:game:index:account-tenant:{tenantGameplayTag}:<accountId>` -> active `sessionId` set
- `session:game:index:tenant:{tenantGameplayTag}` -> active `sessionId` set
- `session:game:index:realm-grant:{tenantGameplayTag}:<worldSlug>:<realmSlug>:<accountId>` -> active `sessionId` set for grant-gated realms
- `session:game:index:issuer:{issuerIndexLayoutTag}:<issuerId>:<partitionId>` -> a bounded Redis hash whose field is the canonical `bindingRef` for one active or provisional binding and whose value is `{schemaVersion: 1, issuerId, accountId, tenantId, gameInstanceId, sessionId, bindingGeneration, issuerAuthGeneration, issuerIndexLayoutVersion}`. `bindingRef` and `partitionId` use the exact [canonical issuer partition mapping](./system-architecture-redis.md#canonical-issuer-partition-mapping): the fixed `bindingRef/v1` UTF-8 length-prefixed bytes, SHA-256, unsigned big-endian normalization, and modulo the positive count pinned by the immutable `issuerIndexLayoutVersion`. Every writer, cutoff, recovery, capacity repair, and migration reuses that mapping and the published vectors; `{issuerIndexLayoutTag}` is the opaque Redis hash tag derived from `(issuerIndexLayoutVersion, issuerId, partitionId)`. The issuer family therefore has a finite, known key set for each issuer and layout and distributes partitions without using wildcard scans.

Index contract requirements:

- Game Session is the sole writer for all six index families; Account authority and realm-grant state remain the authorization source, not the indexes.
- The shard-local CAS/update flow contains exactly the gameplay session record plus the four tenant-scoped indexes: character, account-tenant, tenant, and realm-grant. All of those keys share `{tenantGameplayTag}`. This is the atomic boundary for takeover, resume, and tenant/grant-binding decisions inside Redis Cluster, and its admission predicate includes the Account-owned exact-binding admission lease identity, monotonic lease fence, and applicable authority cutoff checkpoint.
- The cross-tenant `session:game:index:account:<accountId>` and issuer-partition indexes are explicitly excluded from that shard-local CAS because they span tenant hash slots or issuer partitions. The untagged account key is also excluded from every tenant-local Lua invocation. Before the tenant-scoped CAS publishes a new binding, Game Session durably commits deterministic account-index and issuer-index repair obligations keyed to that binding transition. The account obligation contains the expected prior generation, candidate `bindingGeneration`, unique transition identity, desired add/remove, and `accountIndexFence`; the issuer obligation also carries its exact reservation identity. The shard-local CAS may publish only a provisional binding with each applicable `accountIndexState=REPAIR_REQUIRED` and `issuerIndexState=REPAIR_REQUIRED`; it is not admissible for gameplay, resume, or takeover. Game Session then performs each separate idempotent single-key index/capacity compare-and-set, reads back the exact generation/fence-qualified member and reservation state, durably acknowledges the matching obligation, and uses a follow-up shard-local CAS to set the applicable state to `ACKNOWLEDGED` and admit the binding. This ordered protocol closes the cross-slot crash windows without claiming a cross-store transaction.
- An issuer-index write or removal compares the complete expected `bindingRef`, `bindingGeneration`, `issuerAuthGeneration`, and active `issuerIndexLayoutVersion` before changing the hash field; the same operation also compares the exact reservation owner, transition, partition/layout, lifecycle, fence, and revision. An identical already-applied value is an idempotent success, while a newer or conflicting value is a repair conflict. At the start of an issuer cutoff or recovery, Game Session captures the active layout pointer's version, partition count, and capacity while establishing the operation and coverage fences, then reads exactly that pinned finite partition range and maps every binding through the canonical mapping helper; it does not reread the pointer and mix layouts during the operation. If the pointer no longer matches before acknowledgement, the current operation fails closed or enters the explicit layout-transition workflow, which accounts for the complete pinned old layout and separately built new layout before cutover; neither workflow evaluates a mixed partition set. The operation validates every returned value and reservation, then fences or terminates the referenced bindings through their ordinary binding CAS. Missing Redis responses, unreadable partitions, unresolved reservations or repair obligations, or conflicting field values are unavailable or ambiguous coverage, never an empty result. Recovery rebuilds each partition from the complete durable active-binding and reservation inventory using the same expected-value compare-and-set, canonical mapping, and capacity rules and clears the repair obligation only after every required partition, reservation, and binding acknowledgement is proven.
- An issuer-partition acknowledgement is a durable evidence object, not an aggregate flag. For preserved region/tenant recovery it must carry the child-owned `issuerCoverageOperationId` and child lifecycle, the child `issuerCoverageOperationFence`, distinct issuer-wide `coverageFence`, `coverageGeneration`, issuer-wide `inventorySnapshotRevision`, pinned `issuerIndexLayoutVersion`, pinned partition count and capacity, `partitionId`, the exact `issuer/<issuerId>` cutoff checkpoint (`issuerAuthGeneration`, `issuanceFence`, and complete applicable `outboxCheckpoints`), every reservation identity with its owner, transition, lifecycle, fence, and inventory revision, and the capacity tuple `{partitionId, reservationCount, partitionCapacity, aggregateReservationCount, aggregateCapacity}`. The independent parent edge and the parent's consumption record carry the exact linked `parentRecoveryOperationId`, both current lifecycles, parent `operationFence`, distinct `parentCoverageFence`, resolved issuer/scope, and link revision; the child request/digest, transition, partition and reservation readback, acknowledgement, and immutable child result are parent-independent. `coverageGeneration=NOT_YET_ISSUED` remains the pre-coverage value and becomes concrete only after complete finite coverage is proven. For a standalone issuer-wide operation, the operation identity is its own issuer coverage operation identity and still carries its own maintenance fence and coverage fence; all parent fields and account-wide fields are the exact `NOT_APPLICABLE` marker plus `NO_ACTIVE_ACCOUNT_WIDE_FLOW`. The acknowledgement is valid only when all of that evidence comes from the same complete issuer-wide snapshot and operation attempt, with exact readback of the partition and reservation state. Cross-snapshot, cross-attempt, narrow-scope, stale-layout, changed-cutoff, mixed-partition, missing-reservation, or partial-capacity evidence is rejected; no acknowledgement may be assembled from separately read responses or used to authorize a different operation or layout.
- Every post-fence transition, readback, acknowledgement, and exact retry proof must persist and exact-compare all four fields `operationFence`, `coverageFence`, `coverageGeneration`, and `inventorySnapshotRevision` from the same durable snapshot and operation attempt. `operationFence` plus `coverageGeneration` is insufficient, and no local or parent fence, later generation, or partial snapshot may substitute for either missing field.
- Region-local gameplay binding is intentionally outside that atomic boundary and follows the separate session-to-region bridge contract in the Redis architecture docs.
- Normal termination, revocation, takeover, and expiry remove or expire all applicable index entries idempotently. Reconciliation verifies indexed session records, removes stale entries, and recreates missing entries from active authoritative bindings without wildcard keyspace scans. An issuer cutoff reads all and only the finite issuer partitions, so its lookup and termination work remain bounded by the configured issuer capacity.
- Account-wide cutoff and logout-all processing reads both the account index and outstanding durable repair obligations. It must not report complete while an active or provisional binding is omitted, an obligation is unresolved, or index coverage is unavailable or ambiguous. The fail-closed fallback in ADR 0030 fences the affected account scope, terminates locally owned bindings, and keeps any unaccounted binding blocked until reconciliation proves coverage.
- A provisional binding whose account- or issuer-index acknowledgement does not complete within the active-revocation deadline is terminated and recorded as failed closed; reconciliation does not extend the deadline or convert tenant-local presence into complete cross-tenant coverage.
- Billing- and membership-driven revocation flows must use these bounded indexes and obligations rather than wildcard key scans.
- During preserved region- or tenant-scoped recovery, the narrow parent may repair binding-local and tenant-scoped state plus only individually fenced affected `accountIndexMember` entries in the untagged account key. It may not drop or rebuild the untagged global account key, publish account-wide coverage, map the issuer layout, perform issuer Redis or reservation-capacity repair, or publish an issuer-partition acknowledgement from its narrow snapshot. The canonical account-wide child alone owns complete account inventory, any drop/rebuild of the untagged account key, and account-wide coverage; the parent remains subordinate to that child and consumes only its complete proven result. The linked issuer-wide child alone performs issuer mapping/repair and publishes the complete finite partition acknowledgement set; the parent validates `parentRecoveryOperationId`, `issuerCoverageOperationId`, both operation fences, the distinct `parentCoverageFence`, the child `coverageFence` and later `coverageGeneration`, and consumes only that complete proven child result. Tenant-local presence is never global coverage.

### Global Account Active-Binding Index

`session:game:index:account:<accountId>` is the retained untagged global exception because account-wide logout, security revocation, and repair must enumerate active gameplay bindings across every tenant. It is not an authorization source: Account owns the durable authority and cutoffs, while Game Session owns the gameplay binding, this index, its repair obligations, and the termination/reconciliation workflow.

The current physical layout is one Redis set key per account, placed on the shard selected by the full untagged key hash. It is one logical account-wide partition, not a tenant-sharded index. Every member is a versioned, generation-safe `accountIndexMember` containing the complete tenant-qualified `bindingRef`, its positive `bindingGeneration`, and the `accountIndexFence` ordered by that generation. A bare `sessionId`, tenant-only member, member without generation/fence evidence, or Redis-derived tenant association is invalid. Any future split or partitioning must use a new versioned layout and preserve this complete identity contract; reset/reconciliation must not infer a partition scheme from key absence.

The tenant-qualified repair protocol is mandatory and the untagged account key is never included in tenant-local Lua or session-only CAS. Before the tenant-local session CAS can publish an active or provisional binding, Game Session commits a PostgreSQL repair obligation containing the expected prior generation, candidate `bindingGeneration`, unique transition identity, desired account-index add/remove, and `accountIndexFence`. The shard-local CAS may publish the candidate only when the expected prior generation and current session owner/fence still match; it records `accountIndexState=REPAIR_REQUIRED`, so the candidate is provisional and non-admissible. The separate account-key operation carries the same transition identity and fence, adds or retains the generation-qualified candidate before removing an old member, and refuses a removal when the authoritative binding or durable obligation has a newer generation/fence. A stale add may remain as an extra projection for repair, but a stale remove must never hide a newer binding. Game Session acknowledges only an exact `accountIndexAcknowledgement` matching the schema below and the fenced add/remove outcome, then uses a follow-up tenant-local CAS to set `accountIndexState=ACKNOWLEDGED` only when the same candidate generation/fence and the acknowledgement's operation/snapshot carrier are still current and matching. A missing, stale, conflicting, cross-tenant, or unavailable member leaves the binding non-admissible and the account scope fenced.

The exact account-index acknowledgement schema is:

```text
accountIndexAcknowledgement = {
  schemaVersion: 2,
  accountCoverageState: "ACTIVE" | "HISTORICAL" | "NO_ACTIVE_ACCOUNT_WIDE_FLOW",
  operationId,
  accountCoverageOperationId,
  accountCoverageLifecycle,
  accountCoverageOperationFence,
  accountAdmissionFence,
  historicalAccountAdmissionFence,
  resolvedScope,
  transitionId,
  bindingRef,
  accountId,
  tenantId,
  bindingGeneration,
  accountIndexFence,
  operationFence,
  coverageFence,
  coverageGeneration,
  inventorySnapshotRevision,
  action: "ADD_OR_RETAIN" | "REMOVE",
  readback:
    { state: "PRESENT", member: accountIndexMember }
    | { state: "ABSENT" }
}
```

The independent linked edge and the parent's exact consumption record carry `parentRecoveryOperationId`, `parentLifecycle`, `parentOperationFence`, and `parentCoverageFence` alongside the child result identity and `linkRevision`; none of those parent-link fields is part of the parent-independent child acknowledgement.

`operationFence`, `coverageFence`, `coverageGeneration`, and `inventorySnapshotRevision` must bind the acknowledgement to the same durable operation and immutable account inventory snapshot; `accountIndexFence` must bind it to the exact binding generation. `accountCoverageState` is the sole versioned discriminator for the account-fence lifecycle: `ACTIVE` requires concrete `accountCoverageOperationId`, `accountCoverageLifecycle`, `accountCoverageOperationFence`, `resolvedScope`, and `accountAdmissionFence`, with `historicalAccountAdmissionFence=NOT_APPLICABLE`; `HISTORICAL` requires the same concrete account-coverage identity and exact released `historicalAccountAdmissionFence`, with `accountAdmissionFence=NOT_APPLICABLE`; and `NO_ACTIVE_ACCOUNT_WIDE_FLOW` requires `accountCoverageOperationId=NOT_APPLICABLE`, `accountCoverageLifecycle=NOT_APPLICABLE`, `accountCoverageOperationFence=NOT_APPLICABLE`, `accountAdmissionFence=NOT_APPLICABLE`, `historicalAccountAdmissionFence=NOT_APPLICABLE`, and `resolvedScope=NOT_APPLICABLE`. The state and its lifecycle-appropriate fence are carried and exact-compared through the child-owned request/digest, transition, member readback, acknowledgement, exact retry, linked edge, and parent-consumption record; a flow that acquired account-wide fencing never enters the no-active arm. The independent edge and parent-consumption record additionally carry the parent tuple and `linkRevision` and exact-compare the historical account fence after release; those edge fields never enter or specialize the reusable child result. A standalone account-wide operation uses its own concrete account coverage fields and the same live-then-historical fence lifecycle and has no parent edge. `coverageGeneration` is `NOT_YET_ISSUED` before coverage is proven and becomes concrete only in the atomic coverage-proven transition that releases the live account admission fence and retains its historical value. `ADD_OR_RETAIN` requires the exact generation-qualified member in `PRESENT` readback, while `REMOVE` requires `ABSENT` readback and omits `member`. No acknowledgement may be assembled from separately read or cross-snapshot evidence.

For account-wide recovery, logout-all, or reconciliation, the canonical account-wide child enumerates the complete durable inventory for the account, including all tenants and unresolved obligations, under an immutable snapshot. Every child-owned post-fence transition, account-index request/digest, exact member readback, acknowledgement, and retry must carry and exact-compare the child tuple `{child operationId, child lifecycle, child operationFence, child coverageFence, coverageGeneration, inventorySnapshotRevision, accountCoverageState}`; the independent parent edge and the parent's consumption CAS additionally carry and exact-compare `{parentRecoveryOperationId, parentLifecycle, parentOperationFence, parentCoverageFence}` plus the child result identity and `linkRevision`. Neither parent fence nor child fence, coverage generation, inventory snapshot revision, account coverage state, or lifecycle-appropriate account fence may be omitted or substituted by a high-water mark. The issuer-partition form uses the separate issuer-wide acknowledgement tuple above, with parent fields held only by its linked edge and parent-consumption record; account-wide and issuer-wide evidence must not be substituted for one another. A region- or tenant-scoped parent may repair only individually fenced affected `accountIndexMember` entries, must leave unrelated global members untouched, and cannot drop or rebuild the untagged global account key or publish account-wide coverage from that narrow snapshot; it remains subordinate to the canonical account-wide child. The canonical account-wide child rebuilds the complete account key before protected admission reopens. The workflow reads back the exact expected generation-qualified member set and fails closed on missing rows, partial coverage, duplicate identities, stale entries, or unresolved obligations; it never uses Redis `SCAN`, key absence, or the global index alone as proof.

Tenant isolation remains mandatory despite the global key: a tenant-scoped caller may operate only on binding references and authority for its exact tenant, every referenced binding is validated against its tenant-qualified session record and current Account evidence, and the global account index cannot authorize cross-tenant gameplay or substitute for tenant/membership/grant checks. Account-wide operations may enumerate all tenants only under the account-wide authority that authorizes that operation.

The canonical durable active-binding inventory is a Game Session-owned PostgreSQL `GameplayBindingInventory` (or an equivalent durable control-store record with the same transaction and snapshot guarantees). It contains one row for every `ACTIVE`, `PROVISIONAL`, or unresolved account/issuer repair binding, keyed by the exact `bindingRef`, and records the tenant/game/session identity, `bindingGeneration`, issuer and layout identity, lifecycle state, index-obligation state, account transition identity and `accountIndexFence`, every matching `IssuerPartitionReservation` identity/owner/transition/lifecycle/fence/revision, and durable inventory revision. A reservation-only pre-binding row is also included until it reaches terminal `RELEASED`. It is the authority for inventory completeness, recovery enumeration, and cutoff capacity coverage; it is not a substitute for Account authority, the `session:game:*` reconnect record, or the region-local `tick:{tenantRegionTag}:session-binding:<entityId>` command-admission record.

Before a tenant-local binding CAS can publish an active or provisional record, Game Session commits the corresponding inventory row, reservation entry, and account/issuer repair obligations in one durable transaction. Every activation, replacement, terminalization, and removal advances the row and reservation through a fenced compare-and-set; ambiguous cleanup leaves both unresolved rather than deleting either. A standalone issuer-wide cutoff/recovery or the linked issuer-wide child establishes its issuer-wide `inventorySnapshotRevision`, operation identity, maintenance fence, distinct `coverageFence`, and pinned active layout before reading all binding and reservation rows and unresolved obligations at or before that revision under a repeatable snapshot. It deterministically maps every returned binding and reservation through the canonical issuer mapping, repairs or removes the exact Redis field and capacity entry with compare-and-set, reads back every expected partition and reservation entry, and records one durable parent-independent per-partition acknowledgement carrying the child or standalone operation identity/fence, `coverageFence`, later `coverageGeneration`, and exact reservation identities and lifecycle/fence/revision evidence. A linked parent's independent edge and consumption CAS add the parent operation and coverage fences without changing that acknowledgement. A region- or tenant-scoped parent establishes only its binding-local snapshot, may repair only individually fenced affected account-index members, and may consume but not replace the complete linked account-wide or issuer-wide child result; it never drops or rebuilds the untagged account key, publishes account-wide coverage, maps the global issuer family, or emits an issuer acknowledgement. Missing rows, an unavailable snapshot, a post-fence transition not represented by the complete same-attempt `{operationFence, coverageFence, coverageGeneration, inventorySnapshotRevision}` tuple, duplicate identities, excess capacity, or any unresolved obligation keeps the scope blocked; Redis `SCAN`, a partial index, or an empty partition cannot establish inventory or capacity coverage.

Each gameplay session binding must store the server-side auth token identity it is operating under:

- `authTokenHash` – the token hash for the private `game-session-account-delegation` JWT that Game Session uses when making backend calls for this session. Clients never see or transmit this token.
- `authTokenIssuedAt` (`iat`) – the issuance time of that JWT.
- `authTokenExpiresAt` (`exp`) – the deadline used to schedule rotation before expiry.
- `tokenGeneration` – the positive per-lineage generation from the current Account-issued token. When persisted, it is replaced in the same binding CAS as the token identity and is refresh-order metadata, not authority by itself.
- `issuanceFence` – the Account-owned composite issuance/token-lineage fence observed during issuance or installation. A pending logout or later fence advance invalidates stale refresh, rebind, installation, or reconciliation work.
- `rebindHandle` – the protected, Account-issued single-use rebind handle retained with the binding so a restart or takeover owner can establish fresh backend-token authority without the previous raw JWT. The handle binds the exact token hash, signed `jti` and `nbf`, token lineage, gameplay binding, complete `authorityTuple`, the unchanged `membershipBaseline`, complete canonical `outboxCheckpoints` set, and exact `issuanceFence` captured for that issuance. The baseline is the exact one-tenant `{membershipLifecycleState, membershipVersion, membershipAuthorityGeneration}` carrier; neither it nor its nested map may be scalarized, reduced to a high-water or aggregate maximum, reconstructed from the other, or taken from a different authority snapshot. The raw handle is never client-visible; Game Session treats it as opaque, Account alone opens and validates it, and the binding replaces it atomically after successful rotation.
- `membershipBaseline` – the single exact `{membershipLifecycleState, membershipVersion, membershipAuthorityGeneration}` carrier from the Account snapshot used when the session was admitted or last refreshed. Its nested `membershipVersion` map is the exact one-tenant `{tenantId: version}` map and is compared independently from other tuple members, but it is never carried separately in an admission operation or operation digest; membership-event digests retain their explicit event-schema `membershipVersion` field from that same snapshot.
- `authorityTuple` – the complete Account-owned tuple containing `issuerAuthGeneration`, `accountAuthorityGeneration`, exact `tenantAuthorityGeneration` and `membershipAuthorityGeneration` maps, exact `privateRealmGrantVersions`, and applicable `accountSecurityCutoff` and `tenantBillingCutoff` values. Explicitly unscoped bindings contain empty maps/lists and no fabricated tenant or realm values.
- `outboxCheckpoints` – the complete canonical set of exact `{outboxStreamKey, outboxSequence}` entries owned by ADR 0030 and ordered by the comparator in [ADR 0022](./decisions/adr-0022-account-authority-and-gameplay-session-ownership.md#canonical-checkpoint-and-source-evidence-binding). Event identity and digest are separate same-snapshot source evidence. The checkpoint set is admission-freshness evidence, not a replacement authority or an aggregate maximum.
- When roles or private delegation are refreshed mid-session, Game Session must atomically update `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, `tokenGeneration`, `issuanceFence`, `rebindHandle`, `authorityTuple`, unchanged `membershipBaseline`, and `outboxCheckpoints` in the gameplay session binding. The nested `membershipVersion` is written only as the matching member of that baseline. The rebind handle, not a token hash, mTLS identity, fence, generation, grant value, checkpoint, or tuple member alone, is the durable restart/takeover authority.

For the exact active registry record, `authTokenIssuedAt == registry.iat`, `authTokenExpiresAt == registry.exp`, and `tokenGeneration == registry.tokenGeneration`. These are exact field-equality checks for the same token identity; Redis TTL, current time, monotonic ordering, or a different registry record cannot satisfy them.

The canonical `schemaVersion=2` gameplay binding persists exactly ten authentication-specific fields: `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, `tokenGeneration`, `issuanceFence`, `rebindHandle`, `continuityBindingExpiresAt`, the complete `membershipBaseline`, the complete `authorityTuple`, and the complete `outboxCheckpoints` set. `membershipBaseline` is the unchanged carrier used to source and exact-compare `membershipLifecycleState`, the exact one-tenant `membershipVersion` map, and `membershipAuthorityGeneration` together; it is persisted as one field and is not independently assembled during the CAS. Any missing, `schemaVersion=1`, unsupported, or incomplete authenticated payload fails closed. `continuityBindingExpiresAt` remains immutable; the other nine fields are validated and replaced together under the binding CAS, with `membershipAuthorityGeneration` retained inside the baseline and canonical tuple rather than split into a standalone field. Both token-rotation CAS stages must compare and preserve the exact baseline and checkpoint set; neither may replace them with a latest value or aggregate maximum.

All rebind attempts, installation candidates, installation acknowledgements, and their retries carry the same unchanged `membershipBaseline` and complete `outboxCheckpoints` set alongside the binding identity, request digest, lease, and authority tuple. The first replacement CAS writes both carriers unchanged, Account validates them in the acknowledgement request and digest, and the second fenced CAS compares the acknowledged carriers before admission; missing or mismatched baseline or checkpoint evidence leaves the candidate non-admissible.

Rebind-handle consumption uses a crash-safe two-party protocol. Before calling Account, Game Session durably records a `PENDING` rebind attempt containing a stable `rebindRequestId`, canonical request digest, gameplay-binding identity, current `rebindHandle` identity, complete `authorityTuple`, the unchanged `membershipBaseline`, exact stream-key-ordered `outboxCheckpoints` set, exact `issuanceFence`, and token-identity fence. The request digest covers those exact carriers and authority fields; the baseline is compared as one object and is never reconstructed from `membershipVersion` or `membershipAuthorityGeneration` reads. Account uses one durable atomic transaction or equivalent compare-and-set to validate that the handle's exact `issuanceFence` still equals the current Account token/authority fence before consuming the handle for a new operation; a fence advance makes the handle stale and rejects the operation without consumption or replacement issuance. Durable operation evidence never stores a raw JWT. After reconciliation proves the matching registry, lease, binding, fence, and Account postconditions, a separate bounded response envelope encrypted under Account-owned application encryption may retain the exact replacement credential, next `rebindHandle`, unchanged `membershipBaseline`, and exact stream-key-ordered `outboxCheckpoints` set for the authorized Game Session workload until installation acknowledgement or expiry. The envelope is readable only by the exact authorized workload and request/binding tuple, never logged, traced, metered, or exported, expires at the bounded acknowledgement/retry deadline, and is deleted after installation acknowledgement, terminal abort, or expiry. Before installation acknowledgement, a matching retry with the same request ID, digest, workload, binding, handle identity, complete baseline, exact checkpoint set, authority evidence, and issuance fence may recover that exact Account result and response envelope only after current-state revalidation, without consuming the handle or minting again. If the fence advanced, the same-operation retry returns stable stale/failure metadata rather than the credential. After acknowledgement, replay returns only stored completed-installation metadata and never the raw token; reuse of the request ID with a different digest, binding, baseline, checkpoint set, or issuance fence always fails closed.

The `PENDING` rebind attempt, response-envelope binding, Account result, and every retry also carry and exact-compare the unchanged `membershipBaseline` and exact stream-key-ordered `outboxCheckpoints` set. The baseline's map must contain exactly the binding tenant key, and both carriers must come from the same Account authority snapshot; a missing, extra, differently keyed, scalarized, stale, regressed, or cross-scope baseline or checkpoint set cannot be repaired from a high-water mark or aggregate maximum. Digest comparisons include both complete carriers and reject any changed ordering, content, or authority snapshot; the baseline's `membershipVersion` never substitutes for its `membershipAuthorityGeneration`.

Game Session does not claim a transaction across its durable attempt store, Coordination Redis binding, and Account. It uses an ordered fenced installation state machine instead. The binding CAS first writes a non-admissible `INSTALLING` candidate containing the replacement token identity and lineage generation, complete `authorityTuple`, unchanged `membershipBaseline`, exact `outboxCheckpoints` set, `issuanceFence`, token-identity and installation-lease fences, next `rebindHandle`, `rebindRequestId`, and request digest. After exact readback, Game Session durably advances the matching attempt from `PENDING` to `BINDING_INSTALLED`; a crash in either direction is reconciled by comparing the attempt and binding identities and retrying the same Account response-envelope result before acknowledgement. Game Session then sends the idempotent installation acknowledgement carrying that complete tuple, unchanged baseline, exact checkpoint set, and `issuanceFence`. Only after Account records that exact installation as committed may a second fenced binding CAS compare the same carriers and mark the candidate `INSTALLED` and admissible for new backend calls. A stale fence, mismatched tuple, baseline, or checkpoint set, expired response envelope or lease, ambiguous acknowledgement, or unrecoverable write leaves the candidate non-admissible and invokes Account's idempotent abort/retire path. A crash before acknowledgement resumes with the same request identity without consuming another handle or minting another replacement. After acknowledgement, a restarted owner that lost the process-local JWT treats replay as metadata-only success and uses the persisted next `rebindHandle` with a new request identity to establish a fresh replacement; it never asks Account to replay the retired raw token. Game Session never durably stores the raw delegation JWT. Expired, unavailable, or ambiguous response-envelope state without a recorded installation acknowledgement fails closed and requires fresh login or a new authorized recovery path; identity fields alone never substitute for the handle.

An admitted binding keeps `coordinationHealthLease` metadata separate from the Account-owned ADR 0030 authority-freshness lease: the former proves the coordination generation and required queue/lock/session/tick health, while the latter proves prior positive token authority and its applicable authority checkpoint. The coordination controller's current health record is authoritative for `coordinationHealthLeaseFence`, and validation requires the presented fence to exactly equal that current record fence; a newer issuance or renewal invalidates an older lease even when it remains unexpired. Account's current authority-freshness lease record is authoritative for `authorityLeaseFence`, and validation requires the presented fence to exactly equal that current record fence; a newer issuance or renewal likewise invalidates an older lease. They have different issuers, fence domains, renewal paths, and absolute expiries; their fences are never compared across domains, and renewal of one never changes, renews, or recreates the other.

Account authority-freshness lease renewal and revocation follow the ordered Account event and durable Game Session checkpoint contract in [ADR 0037](./decisions/adr-0037-fail-closed-token-authority-outages-with-bounded-active-gameplay.md). A newer observed Account lease fence invalidates the cached lease even before its stored deadline; an event or checkpoint gap, conflict, or unavailability fails closed for new admission, reconnect/resume, renewal, and lease replacement. During the bounded token-authority-only outage exception, an already-admitted binding may retain its stored deadline only while coordination health remains live and no conflicting Account change has been observed; no local action may extend or rewrite that deadline.

On reconnect/resume (after the client re-`LOGIN`s and re-`PLAY`s), Game Session must load the gameplay session binding and confirm:

- The newly authenticated caller `accountId` matches the stored gameplay binding subject.
- Current Account authority still permits gameplay admission for the exact subject and target: the stored complete `authorityTuple`, `issuanceFence`, and `membershipBaseline` must equal the current applicable Account evidence, including issuer, account, exact tenant and membership map entries, lifecycle state, private-realm grants, and applicable security/billing cutoffs. The baseline is compared as one object; its `membershipVersion` and `membershipAuthorityGeneration` members remain independent predicates, and neither may be reconstructed from the other or from a different snapshot. An older or newer mismatch, a missing applicable value, an extra fabricated scope, or unavailable authoritative state rejects resume; consumers compare like fields only and never substitute one generation, grant, cutoff, fence, lifecycle, or version for another.
- The gameplay session key remains logically resumable (key present, `continuityBindingExpiresAt` has not passed, the current `resumeDeadline` has not passed, and the uniqueness key is unchanged).
- Current revocation state does not block the account or tenant for gameplay admission.
- Current Account authority evidence is mandatory for every current authority predicate in reconnect/resume. Game Session must obtain fresh Account evidence for the exact binding and target, including lifecycle, security, membership, grant, revocation, authority-tuple, and checkpoint predicates. The committed activation lease and fresh delegation JWT must each be produced from current Account validation; neither may use a continuity fallback. The only exception is the entitlement predicate: if and only if the entitlement read alone is unavailable while Account can still validate the other current authority predicates, commit the exact activation lease, and issue the fresh delegation JWT, the protected positive same-binding bundle may supply only that entitlement input for the bounded five-minute window. An unreachable or timed-out Account dependency for any required non-entitlement evidence, lease commit, or token issuance returns `AUTH_UNAVAILABLE`; reachable missing, negative, stale, regressed, contradictory, or gapped evidence is denied or revoked according to the canonical auth error contract. No continuity record may authorize a binding or replace current Account validation outside that single entitlement exception.

For every new binding or reconnect/resume, Account issues an exact-binding admission lease only after validating current lifecycle, billing, `authorityTuple`, `issuanceFence`, the exact unchanged `membershipBaseline`, the complete `outboxCheckpoints` set, token-identity fence, and security authority; reconnect continuity uses the exact-resume-episode `resumeActivationLease` specialization. Each lease has a unique lease ID, a monotonic fence, the immutable `authorityTuple`, `issuanceFence`, unchanged `membershipBaseline`, complete `outboxCheckpoints` set, and a bounded absolute expiry no longer than the admission SLA; the lease identity and request digest cover every one of those exact carriers, and the lease cannot be renewed to extend an admission attempt. Game Session's binding CAS includes and independently exact-compares the complete tuple, `issuanceFence`, unchanged baseline, complete checkpoint set, lease fence, and cutoff evidence and may publish only a provisional record. For reconnect/resume that record is `RESUME_PENDING`; it is never admissible, resumable, or takeover-eligible until Account durably finalizes the exact lease, binding decision, authority tuple, baseline, checkpoint set, fence, and resume-episode identity as `COMMITTED`. Account finalization, abort, reconciliation, retries, and replay comparisons are idempotent by lease ID and request ID and require the same unchanged baseline and digest; a missing, extra, scalarized, differently keyed, or changed baseline member fails closed rather than replaying or committing. Game Session remains the owner of the binding CAS and indexes. If an issuer, account, tenant, membership, grant, billing, token-identity, or security cutoff fences the lease before finalization, the local CAS or late finalization fails closed and the provisional record is removed or remains blocked. If finalization commits first, the binding was admitted under the then-current authority and a later cutoff follows the bounded active-revocation path. If the binding CAS or response is lost, Account reconciliation emits durable orphan evidence and a cleanup request; Gateway and Game Session perform fenced edge and gameplay-binding/index cleanup, respectively. No service infers admission from local presence, and Account does not physically remove Game Session state. Missing, expired, fenced, ambiguous, or uncommitted lease state never admits a binding. This is an ordered idempotent cross-service protocol, not a cross-store atomic transaction.

The `resumeActivationLease` is a durable activation gate, not a grace authorization. A previously accepted binding-continuity bundle may supply only the entitlement input under the bounded exception below; it cannot replace current Account validation for any other predicate, the committed lease, or the fresh delegation JWT.

Resume validation must not depend on the previous private player-delegation token remaining valid. After a fresh successful `LOGIN`, Game Session must obtain current Account validation, durably commit the exact `resumeActivationLease`, and obtain a fresh `game-session-account-delegation` token issued by Account; Game Session never mints this token and Account is the sole JWT issuer. Only after the exact activation lease is `COMMITTED` may Game Session atomically replace stored `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, `tokenGeneration`, `issuanceFence`, and `rebindHandle`, replace the complete `authorityTuple`, unchanged `membershipBaseline`, and `outboxCheckpoints` set, consume a current disconnection episode that has not been terminalized `auth-revoked`, and transition the binding from `RESUME_PENDING` to admitted. An episode terminalized `auth-revoked` is permanently excluded: it is never restored or consumed, and fresh `LOGIN` plus `PLAY` must establish a new binding. A binding CAS that loses the lease fence or otherwise fails must not leave the replacement token usable; Game Session must invoke Account's idempotent retire/abort path for the orphan token before reporting resume failure. If Account cannot validate the current evidence, commit the activation lease, or issue the fresh delegation JWT, resume returns `AUTH_UNAVAILABLE`; a reachable negative or mismatched result remains a denial/revocation rather than a local fallback. The new token's expiration, complete authority tuple, unchanged baseline, complete checkpoint set, issuance fence, and replacement rebind handle must be persisted before resumed backend calls use the replacement. Resume is rejected for any failed validation above, including subject mismatch, stale or lost gameplay membership or grant, expired or non-resumable gameplay state, an expired resume window, a changed uniqueness key, or revoked issuer, account, tenant, cutoff, or membership authority state. The fresh token's validity remains bounded by its own `exp`; obtaining it does not extend `continuityBindingExpiresAt` or the current episode's `resumeDeadline`.

### Active-Socket Auth Revocation

When an `auth-revoked` result reaches a currently connected gameplay binding, Game Session must fail closed and atomically transition the gameplay binding out of `connected` to an auth-revoked/disconnected state, record the connected-to-disconnected transition at that termination time, and close the active gameplay socket before any re-admission is possible. Authority revocation terminally ends the current disconnection episode and makes it non-resumable; restoration cannot revive or consume that episode. After authority is restored, a fresh `LOGIN` plus `PLAY` may establish a new gameplay binding only after current authoritative account, membership, entitlement, revocation, uniqueness, and continuity checks pass. A fresh `LOGIN` must never restore or consume an episode terminalized `auth-revoked`, including one created by the connected-to-disconnected transition. A connected binding must never be re-admitted by consuming an episode that was never created.

During a preserved-session region reset, recovery records durable session/recovery evidence for every rebind predicate result, including the operation, binding identity, snapshot/coverage evidence, authority result, and failure reason. `REGION_REBIND_REQUIRED` is the terminal status only of an actually attempted gameplay command or admission command after a valid caller identity and command record have been established: that record becomes `TERMINAL`, its `executionOutcome` is `REGION_REBIND_REQUIRED`, and its gameplay result is non-applied. A failed rebind must not synthesize a command record, terminal outcome, or identity from an invalid, missing, or unauthenticated request. It is not a terminal status for the socket or the authenticated gameplay-session record. A session retained by the recorded `--preserve-sessions` policy stays connected but region-blocked, and no later command is admitted until the region bridge succeeds or fresh `LOGIN` / `PLAY` creates a new binding. Socket closure or session invalidation requires the separate auth-revocation, expiry, explicit invalidation, or close transition.

### Active Session Token Refresh (Required)

Long-lived gameplay sessions require periodic rotation of the private `game-session-account-delegation` JWT used for Account calls. Gameplay clients never receive it, and gameplay-domain authorization continues to use the mTLS workload and typed execution-context contract rather than adding token refresh to each gameplay RPC. This backend token rotation is service maintenance, not active-gameplay reauthentication or elevation: the player supplies no additional factor and the gameplay session does not acquire account or control-plane authority. Game Session must:

1. Schedule planned refresh at approximately 50% of the current JWT lifetime with random jitter, but always before `exp` by the configured safety margin. A 60-second minimum interval may throttle repeated attempts only when enough validity remains; it must never postpone the final safe refresh beyond expiry.
2. Single-flight concurrent refresh demand for the same binding. A transient failure while the current token remains valid retries with bounded jittered backoff and does not rewrite gameplay continuity deadlines.
3. Present the current token identity, including exact `authTokenIssuedAt`, `authTokenExpiresAt`, and persisted per-lineage `tokenGeneration`, exact binding identity, complete `authorityTuple`, unchanged `membershipBaseline`, exact `outboxCheckpoints` set, positive `issuanceFence`, Account-owned token-identity fence, and idempotent request ID to the Account-owned refresh surface. Account revalidates every applicable tuple field, baseline member, account-security and tenant-billing cutoff, private-realm grant, account state, both independent membership predicates, exact token issued/expiry/generation equality, and current token fence before issuing a replacement. Refresh and every competing revocation writer use one serializable Account transaction or composite CAS/fence across all applicable fields and predecessor identity; independent per-field checks cannot commit. A pending or committed exact-token logout fence rejects the request rather than allowing refresh to recreate that token. A restart/takeover owner that no longer has the raw token must use the binding's protected Account-issued single-use `rebindHandle`; Account consumes that handle only after validating its binding, lineage, complete authority tuple, unchanged baseline, exact checkpoint set, `issuanceFence`, continuity deadline, and current token fence and returns a fresh token plus replacement handle. Concrete Game Session mTLS identity, binding identifiers, token hash, or `tokenGeneration` alone cannot refresh or rebind.
Refresh must validate the complete canonical `outboxCheckpoints` set and the separate same-snapshot source evidence for each stream key and sequence, including event identity and digest, against the Account authority snapshot that supplied `authorityTuple`, `membershipBaseline`, `issuanceFence`, and the token identity. A latest-only checkpoint, aggregate maximum, checkpoint set from another snapshot, or projection/readback mismatch is a refresh failure; an unavailable outbox, checkpoint, projection, or reconciliation dependency returns `AUTH_UNAVAILABLE`. The refresh request, response, retry digest, and installation acknowledgement carry the exact checkpoint array unchanged and bind the corresponding source evidence without adding it to each checkpoint entry.
4. Treat auth-expired backend failure as an immediate refresh opportunity while the refresh authority remains valid. Auth-revoked failure is non-refreshable and requires authoritative reconciliation; when the binding is connected, Game Session first applies the active-socket auth-revocation transition above. Logout-all, password reset, security lock, membership loss, or another blocking authority-generation advance cannot be crossed by minting a token with a newer `iat`, and revalidation alone cannot resume gameplay actions.
5. On success, atomically replace `authTokenHash`, `authTokenIssuedAt`, `authTokenExpiresAt`, `tokenGeneration`, `issuanceFence`, `rebindHandle`, the complete `authorityTuple`, the unchanged `membershipBaseline`, and the exact `outboxCheckpoints` set in the gameplay binding before new calls use the replacement. The binding CAS and Account installation acknowledgement must carry that complete tuple, unchanged baseline, exact checkpoint set, `issuanceFence`, and the current token-identity fence; a pending or committed exact-token logout fence, a newer lineage fence, or any changed applicable authority rejects stale installation and prevents recreation of the logged-out identity. Game Session keeps the raw delegation JWT process-local and never persists it. Durable operation evidence never stores a raw JWT. The only persistence exception is the separate bounded Account-encrypted response envelope, which may retain the exact response credential for a matching retry only after reconciliation and current-state revalidation; it is not gameplay binding state, operation evidence, or authorization authority. The protected rebind handle is the deliberately durable restart/takeover credential and is single-use. The prior token may overlap only through the shorter of its original expiry or the maximum already-started internal RPC deadline. Game Session then sends Account an idempotent installation/retirement acknowledgement containing the prior token identity, refresh lineage, replacement identity, complete authority tuple, unchanged baseline, exact checkpoint set, `issuanceFence`, token fence, and retirement request ID. Account, as registry owner, immediately completes the matching fenced installation state and returns metadata-only stored success for a replay of the same acknowledgement; it never replays the raw replacement after acknowledgement. Game Session uses only the replacement for new calls. Account retains the predecessor record through `predecessorRetentionUntil = predecessor.exp + FIREMUD_AUTH_SESSION_SAFETY_MARGIN_MS`, but the predecessor is unusable for new calls after `predecessorUsableUntil` even while retained. Account may delete it earlier only after committing a durable exact-token retirement fence or tombstone bound to the predecessor identity, replacement installation, and operation identity that blocks recreation; deletion is cleanup, never revocation or installation proof. An absent record without matching completed-request evidence is not sufficient authority.
6. Never rewrite the immutable `continuityBindingExpiresAt` anchor or the current disconnection episode's `disconnectAt` / `resumeDeadline` pair during token rotation. Successful resume consumes that episode; a later connected-to-disconnected transition creates a new pair still bounded by the original continuity anchor.
7. If refresh cannot establish authority before the current token expires, fail closed for backend-authenticated actions, atomically transition the affected gameplay authentication state to token-expired/disconnected and create its immutable disconnection episode, close the gameplay socket, and require fresh login. Fresh `LOGIN` plus `PLAY` may resume a still-authorized token-expired binding only after that defined disconnection episode exists and only while it has not been terminalized `auth-revoked`; successful re-admission consumes that eligible episode without extending `continuityBindingExpiresAt`. An episode terminalized `auth-revoked` is never restored or consumed, and fresh `LOGIN` plus `PLAY` must create a new binding.

Security- and billing-related events (for example, account bans, password resets, tenant suspension, or subscription state changes) do not all behave identically; they follow subscription-aware rules:

- For **account-level security events** such as account bans or password resets, the Account Service must:
  - Advance the applicable `authorityTuple.accountAuthorityGeneration`, `accountSecurityCutoff`, and `issuanceFence`, then project `session:auth:generation:account:<accountId>` set-if-greater so previously issued tokens become invalid without requiring key scans or timestamp comparisons. Downstream services consume the resulting Account-owned event/projection and must not write the account-generation state themselves.
  - Emit the committed Account-owned security event; Game Session consumes it idempotently and revokes only its own affected gameplay bindings across tenants so active sockets are kicked and must re-login under the new security conditions. Account does not discover, delete, or write Game Session gameplay keys.
- For **tenant-level billing events**, see the subscription-state mapping below and [Subscription Management](./microservices/account-service/subscription-management.md#tenant-availability-and-quota-enforcement) for when revocation is mandatory versus when quotas and warnings apply.
- For **tenant membership changes**, the Account Service is the authoritative source of membership versioning and change events. Each event carries the Account-committed `authorityTuple.membershipAuthorityGeneration` for the exact `{accountId, tenantId}` scope, complete applicable `authorityTuple`, `issuanceFence`, and separate `membershipVersion`; consumers must use the generation as the authority fence, compare both membership fields independently, treat missing or malformed evidence as a contract failure, reconcile same-stream gaps from Account, and revoke gameplay immediately when the caller loses tenant membership or gameplay-admission authority for that tenant.

### Billing State and Revocation Rules

Subscription and billing state drives how aggressively sessions are revoked:

- `trialing`, `active`
  - No automatic revocation based solely on billing state.
  - Quotas and entitlements from the plan apply; gameplay and control-plane access behave normally.
- `past_due`
  - No automatic revocation or gameplay-admission restriction applies solely because of this state. Existing and new gameplay continue under ordinary plan quotas while operator and creator UIs surface strong warnings.
- `grace`
  - Existing connected gameplay sessions and reconnect of the same still-resumable session remain allowed.
  - First-time public join, fresh gameplay bindings, new instances, scale-out, and quota-increasing operations are denied until billing returns to an eligible state.
  - Auth token sessions remain valid unless separately revoked for security or membership reasons, and billing-safe management remains available.
- Scheduled period-end cancellation (`cancel_at_period_end=true` while the authoritative effective subscription state is not `canceled`)
  - Remains in the prior effective paid state and follows that state's rules until the cancellation becomes effective at the Account-owned effective-cancellation boundary.
  - It does not by itself revoke gameplay, shut down tenant hosting, or map an operation to `TENANT_BILLING_BLOCKED`.
- `suspended`, effective `canceled`
  - Tenant-level hosting is disabled for gameplay:
    - Game Session and world-management flows must reject new game instance creations, restarts, or tenant selection for gameplay for the affected `tenantId` based on `GetTenantEntitlementsForRuntime(tenantId, requestId)`.
    - New player logins and tenant-selection attempts for that tenant are rejected with a dedicated billing error code.
  - Existing gameplay authority is revoked. Game Session sends one bounded, non-sensitive game-unavailable notice, stops further gameplay admission, closes connected sockets, and prevents reconnect into that tenant. The notice flush is not a continuation grace period.
  - Instance processes may then use the separate five-minute maximum drain window for internal cleanup; they are not player-admissible during that drain.
  - Tenant-scoped authorization must be bulk-revoked by advancing the Account-owned tenant authority generation and projecting `session:auth:generation:tenant:<tenantId>` set-if-greater. Downstream services must not write Account authority state or the generation key directly. Services must not rely on wildcard token-record scans or deletes in hot paths. The closed `billing_safe_tenant` exception intentionally bypasses the target-tenant generation; it still requires current issuer and account generations, the caller-bound membership authority generation for the exact `{accountId, targetTenantId}`, the exact target tenant named by the route or typed request, and a live `tenantAdmin` membership/role check. It remains reachable only through that live Account-owned authority; no cached JWT role, membership, generation, or prior authorization result may satisfy any predicate, and no other route class inherits this omission. `cross_tenant_support_safe` survives through current Account-owned issuer/account authority, global token scope, and the live global `support` role or explicitly permitted `platformAdmin` role; the `platformAdmin` alternative requires the `privileged_control` window. `cross_tenant_billing_safe` survives through the corresponding Account-owned issuer/account authority, global token scope, and either the live global `billingAdmin` role with a current `privileged_control` window or the explicitly permitted live global `platformAdmin` role with a current `privileged_control` window. None of these routes may use cached authorization.

Entitlement evaluation is not routine gameplay action authorization. Existing uninterrupted sessions continue without per-action Account/cache reads until a hard billing event or another owning revocation rule ends them.

### Gameplay Logout and Resume Transcript

Explicit gameplay `LOGOUT` is terminal for the current binding. It immediately removes continuity/resume authority and makes the binding's private resume transcript non-replayable; physical deletion may complete asynchronously. A later successful `LOGIN` and `PLAY` is fresh admission and must not replay logged-out private context unless a separate explicit product policy authorizes that behavior.

### Control-Plane Logout

Account remains the authority for ordinary token logout, while Gateway owns the edge-only deny marker for a known gameplay-connect `jti`. The same high-entropy `requestId` and immutable request digest bind the Account and Gateway operations. A changed digest, token identity, account, or operation conflicts without mutation.

Per-token logout covers every associated unexpired `gameplay-connect` credential, not only the presented ordinary JWT. The Account `PENDING` logout fence must commit before any Gateway deny processing; Account then enumerates every associated unexpired issuance/replay record and requires an exact committed Gateway deny-marker/clear acknowledgement for each credential's `jti`, or a retained current fence-bound negative proof that enumeration found none. Success is impossible while any credential acknowledgement or negative proof is missing, stale, conflicting, or ambiguous.

For per-token logout, the coordinator first asks Account to commit a durable server-side `PENDING` logout intent keyed by `(accountId, requestId)` and bound to the exact presented token hash, `jti`, profile, and digest. Account returns an opaque `logoutHandle` bound to that exact intent and fence; the handle is lifecycle reconciliation material only and never authenticates a request or restores token authority. This intent, including its monotonic exact-token fence state, must commit before Gateway is asked to record deny markers. If matching gameplay-connect issuance/replay records exist, the client or coordinator presents that exact `requestId`, digest, and each associated connect-token `jti` to Gateway; Gateway atomically records one deny marker and clears the cookie per credential, returning each stored result for a retry rather than creating another marker. Gateway's markers are edge-only and do not mutate the ordinary Account registry.

Account must retain each gameplay-connect issuance/replay record through the maximum of the gameplay-connect lifetime plus configured clock-skew allowance and the applicable logout/reconciliation retention window. When an issuance expires or no matching issuance was created, Account records a durable terminal expiry/no-issuance tombstone, or an equivalent fence-bound negative proof, keyed to the exact ordinary token identity `{accountId, tokenHash, jti, profile}` and the exact committed logout intent tuple `{requestId, digest, token identity, PENDING fence}`, either directly or through a durable Account-resolvable reference to that intent. There is no unknown-tuple exception: if the proof cannot be resolved to every member of that exact tuple, it is not negative proof. Physical expiry, deletion, registry absence, or cookie absence without that retained proof is never evidence that no issuance remains. A reachable missing ordinary token-registry record is therefore a revoked/invalid state that denies protected use and requires fresh authentication; an unavailable registry is `AUTH_UNAVAILABLE`, not evidence of revocation or permission to recreate the record.

Account idempotently finalizes the same intent only after Gateway returns the committed deny-marker/clear result for every matching unexpired gameplay-connect credential, or after Account's own durable dedicated gameplay-connect issuance/replay inventory provides a current fence-bound negative proof that no such issuance remains for the exact committed logout intent tuple `{requestId, digest, token identity, PENDING fence}`. The proof must bind that tuple directly or through a durable Account-resolvable reference; a missing or unknown member is never accepted. The current contract permits later independently authorized connect-token requests, so per-token logout chooses complete enumeration rather than assuming an at-most-one credential invariant: Account enumerates every matching unexpired issuance/replay record, and every credential's exact `jti` and request identity must be covered or the intent remains `PENDING`. The negative proof must be retained for the full applicable reconciliation window and must match the exact committed `PENDING` fence; it cannot be assembled from separately read records. The `PENDING` fence must commit before enumeration so no later connect-token issuance can race into the scope. A missing, expired, stale, conflicting, separately assembled, or ambiguous issuance record or tombstone is not negative proof and leaves the intent `PENDING`; local cookie absence, client assertion, registry absence, and token expiry never substitute. If any applicable issuance record exists, finalization requires the exact Gateway result for that credential; one successful deny-marker/clear result cannot cover another `jti`. An unavailable, timed-out, conflicting, or ambiguous Gateway result leaves the Account intent `PENDING`; it is retried or reconciled with the same request tuple and is never treated as edge revocation success. The durable logout fence must be committed before any early physical deletion of the ordinary token-registry record; deletion is cleanup, not revocation proof. Finalization advances the Account-owned token-identity fence, invalidates the underlying `player-bootstrap` or control-plane token by deleting its `session:auth:token:<tokenHash>` record, and commits the `COMMITTED` tombstone, audit, and outbox evidence before reporting success. `PENDING` or `COMMITTED` fence state blocks racing issuance, refresh, rebind, and installation, and blocks any reconciliation that could recreate the logged-out identity. The only permitted reconciliation is the matching Account operation presented with the opaque `logoutHandle`, exact request ID, digest, token identity, and fence; it may finish or abort the same intent but never creates authorization context or a replacement credential. Account's reconciler may emit durable orphan evidence or cleanup requests for missing edge or gameplay state; Gateway performs fenced edge deny/clear cleanup and Game Session performs fenced gameplay binding/index cleanup.

If either response is lost, the client or Account reconciler retries Gateway and Account with the same `requestId`, digest, token identity, and opaque `logoutHandle`. Gateway returns its committed marker outcome, and Account returns its committed tombstone or resumes the pending intent without another fence advance, registry mutation, audit, or outbox duplicate. The handle is accepted only for this lifecycle-only retry after current-state revalidation; no retry creates authorization context or a usable token. Reusing the request ID, handle, or digest with changed meaning is rejected, and a new logout attempt uses a new request ID.

In this per-token contract, `matching` means every associated unexpired credential in Account's retained gameplay-connect issuance/replay inventory; it is not a single-record, cookie-based, or at-most-one lookup.

For `POST /auth/logout-all`, Account uses the same durable request-id/digest rule and commits the `authorityTuple.accountAuthorityGeneration`, applicable `accountSecurityCutoff`, `issuanceFence`, logout event, audit, and outbox exactly once in one Account transaction or composite CAS/fence. That advance is paired with a dedicated account-scoped Gateway gameplay-connect deny fence/index, distinct from `replayAdmissionFence`; it must not reuse the per-credential replay-admission fence. The dedicated fence denies issuance and use of every outstanding gameplay-connect credential for the affected account. Gateway must acknowledge or reconcile every affected unexpired gameplay-connect credential, and Game Session must acknowledge or reconcile every affected gameplay binding and binding index, before logout-all is complete; an unavailable, missing, stale, or ambiguous credential or binding result remains pending. A retry returns the stored result without another generation advance. Completion requires the durable Account authority evidence, dedicated Gateway fence convergence, and complete downstream gameplay-credential and gameplay-binding reconciliation; local cleanup or token expiry is never sufficient.

See [Redis Architecture](./system-architecture-redis.md#session-keys-and-gameplay-binding) for Redis structure and gameplay rebinding.

`AUTH_UNAVAILABLE` includes unavailable or timed-out outbox delivery, any required checkpoint-set read or same-snapshot validation, issuer/account/membership projection readback, and required Account reconciliation, in addition to registry, authority, lease, binding, and token-issuance dependencies. `ENTITLEMENT_UNAVAILABLE` remains the separate entitlement-only exception and must not absorb any of those dependencies.

### Control-Plane Session UX Expectations

Control-plane UIs must treat certain auth failures as hard logout conditions and others as tenant-level billing issues:

- Meta/control APIs that rely on JWTs return canonical error codes such as:
  - `AUTH_TOKEN_EXPIRED` – The presented JWT is no longer valid because its cryptographic lifetime has ended. Frontends must clear any in-memory token, redirect to login, and display a "Session expired" message.
  - `AUTH_SESSION_REVOKED` – The JWT’s auth token sessions have been revoked due to a security event (for example, password reset, account ban, or "logout all devices"). Frontends must clear in-memory token state, redirect to login, and indicate that the session was ended for security reasons.
  - `AUTH_UNAVAILABLE` – A registry, auth-generation, lease or lease-commit, binding or binding-index, token-identity fence, non-entitlement authority evidence, or token-issuance dependency could not be reached. Frontends keep in-memory auth state, show retriable availability feedback, and use bounded backoff rather than converting the outage into logout. Billing-safe mutations remain blocked until live authority recovers; no cached JWT role, membership, generation, lease, binding, or allowlist result may authorize the failed operation.
  - `ENTITLEMENT_UNAVAILABLE` – Entitlement evaluation alone could not be reached and the bounded same-binding continuity exception cannot supply the entitlement input. Frontends keep in-memory auth state, show tenant-specific retriable entitlement feedback, and deny the affected admission or entitlement-dependent operation without logging out or treating the result as revocation. Cached entitlement data is never used outside that explicitly bounded exception.
  - `TENANT_BILLING_BLOCKED` – The operation is blocked because the tenant’s effective billing state (for example, `suspended` or effective `canceled`) does not allow the requested action. A scheduled period-end cancellation remains in the prior effective paid state until that boundary and does not produce this code. Frontends must keep the user logged in but surface a billing-specific banner or UI state for that tenant and disable gameplay and instance-management actions while still allowing the billing-safe control-plane surface (for example, updating payment details or exporting tenant-scoped data).
  - `ADMISSION_POINTER_UNAVAILABLE` – Gameplay admission pointer state is unavailable or ambiguous. Frontends keep auth state and retry admission with bounded backoff instead of logging out.
  - `REALM_UNAVAILABLE` – The selected realm is explicitly `CLOSED` or in maintenance. Frontends keep auth state, show the realm state, and refresh discovery rather than treating closure as corrupt pointer authority.
- Closing a browser tab or window does not automatically revoke auth token sessions; users must call explicit logout (or an operator must use "logout all devices") to revoke server-side registry records before TTL expiry. On shared devices, UIs must encourage explicit logout from admin and creator sections.
