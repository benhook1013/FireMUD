# FireMUD Scripting & Automation: Rollout and Rollback

This document is the canonical owner for operator-driven promotion, rollback, workflow sequencing, convergence, timeout, and degraded-operations contracts for scripting and plugin control-plane changes. [Scripting & Automation: Control Plane API](./system-architecture-scripting-control-plane-api.md) defines the underlying RPC contracts and mutable state boundaries. [Scripting & Automation: Control Plane Operations](./system-architecture-scripting-control-plane-operations.md) records each service's participation and cleanup APIs, while the [operations cookbook](./system-architecture-scripting-operations-cookbook.md) provides executable operator examples.

For mutating workflow calls, `actor` is the authenticated operator principal and is projected to audit as `requestedBy`. System-owned reconciliation and cleanup records use a separate `executedBy=system:automation`; they must not replace `requestedBy` or overload `actor` with the worker identity.

## Implementation Status

The rollout and rollback state machine below is target-state canonical. The live Game Session handoff still lacks complete per-command Trigger Identity propagation; the detailed current fallback is recorded in [Command Identity and Live Handoff Boundary](#command-identity-and-live-handoff-boundary). `targetEntityIds[]` multi-target fan-out is target-state only because the existing owners do not define persisted deterministic per-target identity, scope validation, and deduplication at the live boundary. Automation currently claims work through `PENDING_EVALUATION` to `EVALUATING`; its implementation lacks the target lease/fencing-generation recovery and separate evaluated descriptor/outbox boundary. The target state mapping and recovery owner are canonical in [Scripting Runtime Execution](./system-architecture-scripting-runtime-execution.md#current-state-mapping-drain-and-rebuild-rules). Current `GetAutomationDrainStatus` counts `EVALUATING` and `HANDOFF_IN_FLIGHT` in `activeExecutionCount`, including unresolved stale `EVALUATING`, while `pendingCancelableWorkItemCount` covers current handoff-capable `PENDING_EVALUATION` rows; this is a current projection gap, not permission to infer a reclaim. Metric schemas come from [Table 4](./system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix); audit and handoff diagnostics come from the [Scripting & Automation Observability Contract](./system-architecture-scripting-observability-contract.md).

## Patch Promotion (Operator-Driven)

1. Validate patch is `READY` in Automation & Scripting for the tenant (`GetScriptPatchStatus`).
2. Ask Automation to prepare/preload the exact candidate artifact while the current Game Session pin remains active. Preparation is non-authoritative and admits no candidate gameplay work; failure leaves the current pin and epoch unchanged.
3. Enter the scoped Automation admission barrier with `SetAutomationAdmissionMode(..., mode=PAUSED_FOR_ROLLBACK, controlPlaneRequestId, actor, reason)` before the serialized authority change. The barrier stops new external and scheduler triggers, while ordinary player commands and ticks continue.
4. Call `SetPinnedScriptPatchVersion` in Game Session with the required `expectedCurrentPin` precondition and its explicit tag. For a first pin, use `EXPECT_UNPINNED`; for a normal repin, use `EXPECT_EPOCH(scriptPinEpoch)` with the currently authoritative epoch. Game Session atomically persists the exact `(scriptPatchVersion, scriptPinEpoch)` tuple, advances the epoch for every selection change, appends rollout history, and emits `ScriptPatchPinChanged`.
5. Automation reconciles schedules and timers for the exact target tuple before resuming script admission. The default interval behavior is cancel-and-recreate; continuity is carried only when both sides explicitly opt in with the stable continuity key and typed cadence/target compatibility defined by [Scripting Scheduler and Timer Lifecycle](./system-architecture-scripting-scheduler-and-timers.md#explicit-continuity-across-script-transitions). Reconciliation creates no firing claim or `scriptEventId`.
6. Cancel and purge displaced work asynchronously as bounded idempotent cleanup. Cleanup improves resource use and operator visibility but is not the correctness barrier; every persistence, handoff, staging, replay, and final effect boundary enforces the exact pin/epoch fence.
7. Wait for the [Pin Convergence Acknowledgment Predicate](#pin-convergence-acknowledgment-predicate) to succeed for the exact resulting epoch and request, then return Automation admission to `NORMAL`. On a failed or ambiguous `SetAutomationAdmissionMode(..., mode=NORMAL)` call, leave the workflow retryable in `RESUMING_AUTOMATION` with new script admission fail-closed; retry the same `controlPlaneRequestId`, and authoritative scoped readback must prove `admissionMode=NORMAL` before `COMPLETED`.
8. If authority is unavailable, new script admission remains fail-closed with `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_PIN_STATE_UNAVAILABLE` and `admissionReason=pin_state_unavailable`; if the requested exact tuple mismatches the observed tuple, it remains fail-closed with `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE` and `admissionReason=pin_state_mismatch_requested_vs_observed`. Ordinary gameplay remains available unless an explicitly declared unfenced effect requires exceptional tick pause.
9. Operators monitor Game Session's authoritative rollout history alongside Automation readiness/convergence projections; projection disagreement is displayed as lag, not resolved by selecting Automation history.

## Patch Rollback (Operator-Driven, Required)

1. Validate the target is previously published, tenant-`READY`, base-compatible, and immutable. Ask Automation to prepare/preload that exact artifact while the current pin remains active; preparation failure leaves the current tuple unchanged.
2. Call `SetAutomationAdmissionMode(..., mode=PAUSED_FOR_ROLLBACK, controlPlaneRequestId, actor, reason)` for the affected `(tenantId, gameInstanceId)`. This scoped barrier stops new script/plugin triggers and scheduler firings but does not pause ordinary player commands or gameplay ticks. On the exceptional branch, call `PauseTicks` for the declared smallest complete scope after this barrier succeeds and before step 3; a failure leaves the workflow retryable in `PAUSING_TICKS` with no pin or rollout-history mutation while Automation admission remains paused.
3. Call `RollbackScriptPatchVersion` (or `SetPinnedScriptPatchVersion`) with the required `expectedCurrentPin=EXPECT_EPOCH(scriptPinEpoch)` precondition and its explicit tag for the currently authoritative epoch, plus `controlPlaneRequestId`, `actor`, and `reason`. Game Session atomically commits the exact `(scriptPatchVersion, scriptPinEpoch)` tuple, advances the epoch even for repin to a previously used version, appends rollout history, and emits `ScriptPatchPinChanged`.
4. Automation performs durable schedule/timer reconciliation while the admission barrier remains active. The default interval transition is cancel-and-recreate. Continuity requires explicit compatible declarations on both sides with the stable key and typed cadence/target checks in [ADR 0110](./decisions/adr-0110-explicit-opt-in-schedule-continuity-across-script-transitions.md); `scheduleSemanticsHash` is diagnostic evidence only. Reconciliation creates no firing claim or `scriptEventId`.
5. Cancel displaced Automation work and purge stale queue entries as bounded, idempotent asynchronous cleanup. Every persistence, handoff, staging, retry/replay, and final effect boundary rejects the displaced pin epoch; cleanup lag does not delay unrelated gameplay.
6. Wait for fresh Game Session and Automation convergence reads that match the exact target version, `scriptPinEpoch`, and `controlPlaneRequestId`. If the target cannot be loaded or reconciled, Automation stays fail-closed for new script work and exposes repair/repin action; Game Session does not silently restore an older pin.
7. After convergence and schedule reconciliation, the ordinary path calls `SetAutomationAdmissionMode(..., mode=NORMAL, controlPlaneRequestId, actor, reason)`. On the ordinary branch, a failed or ambiguous call leaves the workflow retryable in `RESUMING_AUTOMATION` with new script admission fail-closed; retry repeats the same `controlPlaneRequestId`, and authoritative scoped readback must prove `admissionMode=NORMAL` before `COMPLETED`. On the exceptional branch, call `ResumeTicks` for the declared smallest complete scope first, then return Automation admission to `NORMAL`; a failed or ambiguous `ResumeTicks` call leaves the workflow retryable in `RESUMING_TICKS` with Automation admission paused until authoritative scoped readback proves ticks resumed. An ambiguous response does not claim the tick pause remains active because ticks may already have resumed safely. A full `PauseTicks`/`ResumeTicks` pair is required only for an explicitly declared unfenced effect family, migration, or compatibility transition, and that exceptional workflow must identify its smallest complete scope and prove quiescence.

## Pin Compare-and-Set Preconditions

`SetPinnedScriptPatchVersion` and `RollbackScriptPatchVersion` require an explicit tagged `expectedCurrentPin` with exactly one of `UNCONDITIONAL`, `EXPECT_UNPINNED`, or `EXPECT_EPOCH(scriptPinEpoch)`. Missing or unknown tags are invalid and must be rejected before pin, epoch, or outbox mutation. `EXPECT_UNPINNED` is the safe first-pin compare-and-set; normal repin, same-version epoch-only repin, and rollback use `EXPECT_EPOCH(scriptPinEpoch)` for the currently authoritative epoch. `UNCONDITIONAL` remains only a `platformAdmin` break-glass repair operation with a nonblank `reason`, stable `controlPlaneRequestId`, and durable audit; it skips only the current-pin comparison and must still satisfy coherent Game Session owner state, readiness, authorization, and every other validation. It is never inferred from an omitted field. The tag and value participate in the canonical request digest, so an exact idempotent retry returns the stored result while a different tag or epoch under the same request identity conflicts under the existing request/history semantics.

This tagged precondition is target-state: the current proto and runtime do not yet carry or enforce it, and this document does not claim that implementation or proof is complete.

Concrete example:

- `tenantId=11111111-1111-4111-8111-111111111111`, `gameInstanceId=44444444-4444-4444-8444-444444444444`, current pin `P22`, rollback target `P21`, `controlPlaneRequestId=RB-42`.
- Step 1: Automation prepares the exact P21 artifact while the current P22 pin remains active; preparation failure leaves P22 and its epoch unchanged.
- Step 2: `SetAutomationAdmissionMode(tenantId=11111111-1111-4111-8111-111111111111, gameInstanceId=44444444-4444-4444-8444-444444444444, mode=PAUSED_FOR_ROLLBACK, controlPlaneRequestId=RB-42, actor=operator:alice, reason="rollback RB-42")`.
- Step 3: `RollbackScriptPatchVersion(... targetScriptPatchVersion=P21, expectedCurrentPin=EXPECT_EPOCH(N), controlPlaneRequestId=RB-42, actor=operator:alice, reason="rollback RB-42")` commits `(P21, scriptPinEpoch=N+1)` and Game Session history atomically.
- Step 4: Automation reconciles schedules under RB-42; continuity is preserved only with explicit declarations and typed compatibility, otherwise rows are tombstoned and recreated with fresh due state.
- Step 5: stale P22 work is canceled/purged asynchronously and every exact epoch fence remains active at final mutation boundaries.
- Step 6: fresh convergence reads match P21, epoch N+1, and RB-42; Automation then returns to `NORMAL`.

Ordering is intentional: candidate preparation precedes the admission barrier; the barrier precedes repin and remains active through exact-artifact reconciliation and convergence. Ordinary gameplay ticks are not held by routine script rollback. Exceptional tick pause, when required by an unfenced effect, is a separately named and proven workflow.

## Two-Stage Event Deduplication

Rollback and normal event ingress use two deduplication stages:

- Before handler resolution, incoming request dedupe uses the event-scope identity from [Table 1](./system-architecture-scripting-normative-contract-tables.md#table-1-trigger-identity-required-fields), including `isDryRun`. `scriptId` and `bindingId` are unavailable at ingress and must not be invented. A live claim (`isDryRun=false`) and a dry-run/test claim (`isDryRun=true`) are distinct even when every other applicable field matches; they must not share an event-scope claim, ingress audit result, or materialized handler work. Retries must preserve the original mode, and changing it is an identity conflict.
- After binding resolution, each resolved handler dedupes independently by the full applicable Trigger Identity and retains its own handler-scoped audit outcome.
- The local mode consequence is directional: `isDryRun=false` may continue through live persistence and handoff, while `isDryRun=true` remains on the non-committing test branch and must not use live execution metric consequences; the exact metric families and units remain owned by Table 4.

## Command Identity and Live Handoff Boundary

Rollback diagnosis uses the command-identity contract rather than treating a handler-level trigger identity as a command identity:

- **Target state:** Game Session rejects queued commands whose embedded `(scriptPatchVersion, scriptPinEpoch)` does not match the current instance pin, or whose exact `(pluginId, pluginVersionId, bindingId)` is not admitted by Automation & Scripting's authoritative instance-scoped active plugin tuple/runtime lifecycle together with the fresh publication, signer, component-policy, and capability-grant eligibility evidence owned by Game Design and revalidated/used by Automation; when both provenances are present, both independent fences apply. Game Session consumes the resulting applicable exact plugin fence and fresh evidence without becoming an authority for either domain. Complete plugin handoff/execution-fence records and failure evidence retain the captured `pluginActivationGeneration` unchanged; it is fence evidence only and does not redefine Automation-owned generation advancement. It records one per-command handoff result through `ListScriptHandoffEvents` / `commandHandoffDispositions[]`. Each result retains the complete applicable Trigger Identity plus the complete [Command-Handoff Identity](./system-architecture-scripting-normative-contract-tables.md#command-handoff-identity-target-state), whose final discriminator is `(automationDispatchId, commandOrdinal)`; plugin handlers additionally retain `pluginId`, `pluginVersionId`, and `bindingId`, with `bindingId` used only as plugin provenance/correlation/fence evidence and excluded from Command-Handoff child uniqueness, deduplication, and replay selection, while scheduler/timer handlers additionally retain `scheduleDefinitionId`, `triggerMode`, and exactly one due-point field (`dueTickId` or `dueAt`). `outboxWorkItemId` is parent correlation only and is excluded from command identity, uniqueness, and deduplication keys. Per-command durable progress is independent, and any pair shown without its complete Trigger Identity and scope is only a display suffix; retries resume unresolved commands without dropping unattempted commands or replaying accepted or terminally rejected commands.
- **Current live boundary:** `EnqueueAutomationCommandIfAbsent` carries the current narrower scope, dispatch/work-item, script/plugin provenance, target-command, routing, and origin-source fields, but not `scriptPinEpoch`, `commandOrdinal`, or the complete Trigger/Command-Handoff Identity and scheduler metadata. The current Automation executor supports bounded multiple emitted commands with local ordinals and attempts each handoff independently. `command_count_exceeded` is reserved for an actual configured output-count limit; it is not the consequence of the missing wire identity. The live diagnostic/retry fallback remains narrower and does not establish target per-command deduplication, fencing, or independent progress; see [Scripting & Automation: Cross-Service Contracts](./system-architecture-scripting-contracts.md#implementation-status).

Operators must therefore use the current fallback for live rollback diagnosis and must not infer a complete per-command execution disposition from fields the live handoff does not carry. The target per-command view is the contract to converge to; it does not describe current proto coverage.

## Rollback Orchestration State Machine (Required)

Rollback orchestration must expose and persist a state machine so partial failures are recoverable and retries are deterministic.

Ownership and source-of-truth requirements:

- Game Session is the producer-of-record for rollback orchestration state keyed by `controlPlaneRequestId` and is the sole producer of the convergence-timeout signal.
- Logging & Admin may expose convenience orchestration APIs, but these must call the Game Session workflow APIs and read back the same canonical workflow state; they must not persist a competing rollback-state machine.
- Automation & Scripting participates via idempotent step APIs (`SetAutomationAdmissionMode`, cancel/purge hooks, convergence reads) and must not infer orchestration completion from local state alone.

Required states:

- `PREPARING` -> `PAUSING_AUTOMATION` -> `REPINNING` -> `RECONCILING_SCHEDULES` -> `CONVERGING` -> `RESUMING_AUTOMATION` -> `COMPLETED`
- Exceptional branch (only when the workflow records an unfenced effect/migration boundary and proves quiescence): `PREPARING` -> `PAUSING_AUTOMATION` -> `PAUSING_TICKS` -> `REPINNING` -> `RECONCILING_SCHEDULES` -> `CONVERGING` -> `RESUMING_TICKS` -> `RESUMING_AUTOMATION` -> `COMPLETED`.
- Terminal failure state: `ROLLBACK_CONVERGENCE_TIMEOUT`

State rules:

- Each transition must be idempotent and keyed by `controlPlaneRequestId`.
- Re-running a request in the same state must return current state, not restart from scratch.
- For the exceptional branch, `PAUSING_TICKS` is entered only after `PAUSING_AUTOMATION` succeeds and records the declared unfenced boundary and smallest complete scope. Failure to complete `PauseTicks` leaves the same workflow retryable in `PAUSING_TICKS` with no pin or rollout-history mutation while Automation admission remains paused; a retry must not advance to `REPINNING` until tick/effect quiescence is proven.
- `RECONCILING_SCHEDULES` must complete before target-version timer or script admission resumes. Replacement creation and displaced-row retirement must be one atomic durable result or a resumable, idempotent operation keyed by `controlPlaneRequestId`; retries must create or confirm the target schedule before retiring the displaced row. Continuity is allowed only by explicit opt-in declarations and typed compatibility; `scheduleSemanticsHash` cannot grant continuity. Reconciliation must not create firing claims or `scriptEventId`.
- The workflow persists separate cleanup progress, including bounded pending work, last error, and retry timing, rather than representing cleanup as a critical-path state. Cancellation, purge, and drain cleanup may remain pending after `COMPLETED`; the displaced exact `(scriptPatchVersion, scriptPinEpoch)` fence remains authoritative while that asynchronous work retries.
- Cleanup failures do not invalidate the exact epoch fence or pause ordinary ticks; they remain visible as bounded cleanup backlog and retry state. Automation admission stays paused until exact-artifact convergence and schedule reconciliation succeed, never until cleanup reaches zero.
- Operator retries must continue from the last durable state.
- `CONVERGING` transitions to `RESUMING_TICKS` on the exceptional branch, or to `RESUMING_AUTOMATION` on the ordinary branch, only after the Pin Convergence Acknowledgment Predicate and schedule reconciliation requirements succeed. On the exceptional branch, a convergence failure or unsatisfied observation before the deadline leaves both tick and Automation pauses active while the same attempt remains in `CONVERGING`. If the configured deadline is reached while that predicate remains unsatisfied, `CONVERGING` transitions directly and durably to terminal `ROLLBACK_CONVERGENCE_TIMEOUT`; it must not advance to either resume state or `COMPLETED`.
- `ROLLBACK_CONVERGENCE_TIMEOUT` is terminal for the current convergence attempt and remains terminal while no explicit operator recovery occurs; it keeps new Automation admission fail-closed until explicit repair/repin. Ordinary player commands and gameplay ticks continue unless the optional exceptional tick-pause branch was selected.
- Explicit operator recovery of `ROLLBACK_CONVERGENCE_TIMEOUT` starts a fresh convergence attempt on the same Game Session workflow record with the same `controlPlaneRequestId`; it transitions `ROLLBACK_CONVERGENCE_TIMEOUT -> CONVERGING`, not to a new workflow or state machine or an ordinary retryable state. The new attempt persists a fresh absolute `convergenceDeadlineAt` while retaining each prior attempt's deadline and timeout outcome as immutable attempt/history evidence. A repeated recovery call for the same currently active recovery attempt returns its current state and deadline without refreshing that deadline. Recovery must preserve both fences and, for the exceptional branch, keep ticks and Automation paused. If fresh convergence proof remains unavailable, that attempt returns to `ROLLBACK_CONVERGENCE_TIMEOUT` with the current fences still active.
- On the exceptional branch, `RESUMING_TICKS` is entered only after convergence succeeds. A failed or ambiguous `ResumeTicks` call leaves the workflow retryable in `RESUMING_TICKS` with Automation admission still paused; authoritative scoped readback must prove that ticks resumed before it may advance to `RESUMING_AUTOMATION` or `COMPLETED`. An ambiguous response does not claim that the tick pause remains active because ticks may already have resumed safely.
- `GetAutomationDrainStatus` is a diagnostic cleanup-progress read, not a gameplay pause barrier or Automation-resumption predicate. **Target-state mapping:** `activeExecutionCount` is exactly `EXECUTING` pre-DSL triggers plus `HANDOFF_IN_FLIGHT` evaluated descriptors, and `pendingCancelableWorkItemCount` is exactly `PENDING_EVALUATION` pre-DSL triggers plus `PENDING`/`INDEXED` evaluated descriptors. A cached, stale, or earlier-epoch response remains diagnostic and cannot satisfy exact convergence.
- **Current projection mapping:** the live projection counts `EVALUATING`, including unresolved stale rows, and `HANDOFF_IN_FLIGHT` as active, while every handoff-capable `PENDING_EVALUATION` is pending because the separate `PENDING`/`INDEXED` descriptor layer is not yet persisted. These counts expose an implementation gap and do not gate ordinary ticks or target convergence.
- During target-state asynchronous cancellation and cleanup, `PENDING_EVALUATION` transitions durably to terminal `CANCELED` with `finalStage=ADMISSION`, `finalOutcome=canceled`, and the bounded rollback/operator reason without entering the DSL. A target `EXECUTING` trigger is fenced and its descriptor-commit marker is read first: committed descriptors/children are canceled or fenced without resume or redispatch; separate post-evaluation recovery may replay only the stored child ledger without DSL re-entry; explicit cancellation of an uncommitted trigger transitions to terminal `CANCELED` with `finalStage=DSL_EVAL`, `finalOutcome=canceled`, and the bounded cancellation reason and is never replay-eligible; only the distinct expired-stale recovery-owner path transitions an uncommitted trigger to terminal `DEAD_LETTERED` with `finalStage=DSL_EVAL`, `finalOutcome=canceled`, and `finalReason=stale_execution_fenced`. The cancellation API itself does not dead-letter stale displaced rows. Cleanup progress remains separately observable and does not gate Automation resumption or ordinary gameplay ticks.

## Pin Convergence Acknowledgment Predicate

Promotion and rollback pin convergence succeeds only when, before the configured deadline, both fresh owner acknowledgments are present for the same scope and request:

- Game Session reports the requested target `scriptPatchVersion`, resulting `scriptPinEpoch`, and `controlPlaneRequestId` from a fresh authoritative convergence read.
- Automation & Scripting reports the requested target `scriptPatchVersion`, exact observed `scriptPinEpoch`, and `controlPlaneRequestId`, `isProjectionStale=false`, and `projectionLagMs` within the configured `SCRIPT_PIN_PROJECTION_STALE_THRESHOLD_MS` bound from a fresh Automation projection/convergence read.

An acknowledgment is fresh only when it reflects this promotion/rollback operation rather than a stale cache or an earlier request, and it must arrive before the deadline. A missing, stale, mismatched, or out-of-bound acknowledgment from either owner is a non-terminal unsatisfied observation until the configured deadline. Fresh matching acknowledgments from both owners before the deadline satisfy the predicate; one owner's successful acknowledgment never substitutes for the other's.

Convergence timeout semantics (required):

- Game Session owns and reads the canonical target configuration key `firemud.scripting.rollback-convergence-timeout-ms`, whose value must be a positive integer number of milliseconds. On entering `CONVERGING` for the initial attempt or an explicit recovery attempt, Game Session computes and persists one fresh absolute `convergenceDeadlineAt` in the same workflow record and `controlPlaneRequestId`. Each attempt's deadline is immutable: repeated calls for the same active attempt reuse it without refresh, while prior attempt deadlines and timeout outcomes remain immutable attempt/history evidence.
- Before the deadline, missing, stale, mismatched, or out-of-bound acknowledgments leave convergence unsatisfied and the workflow continues authoritative reads; they do not by themselves enter a terminal state.
- If the deadline is reached before the [Pin Convergence Acknowledgment Predicate](#pin-convergence-acknowledgment-predicate) succeeds, including because either owner's acknowledgment remains missing, stale, mismatched, or out-of-bound at the deadline, the rollback enters terminal state `ROLLBACK_CONVERGENCE_TIMEOUT`.
- In `ROLLBACK_CONVERGENCE_TIMEOUT`, new Automation admission remains fail-closed. Ordinary player commands and ticks continue when healthy; if the exceptional branch was selected, both tick and Automation pauses remain until the separately proven resume steps. Game Session alone commits the terminal state and the `ScriptRollbackConvergenceTimedOut` event through one transactional outbox or equivalent atomic commit, with rollback-scoped idempotency keyed by the same workflow record and `controlPlaneRequestId`; repeated calls for the same timed-out attempt may resume publication of its existing record but must not create a second timeout transition or event, while a later explicit recovery attempt records its own immutable deadline/outcome evidence. Automation consumes that state/signal and does not produce a competing timeout signal or metric. Any metric consequence follows [Table 4](./system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix).
- An operator may explicitly recover the same durable workflow idempotently. Recovery starts the next convergence attempt with a fresh persisted absolute deadline as described above; a repeated call for the same active recovery attempt reuses its existing deadline. Before Automation returns to `NORMAL` (and before exceptional `ResumeTicks`, when applicable), it must obtain fresh matching Game Session and Automation acknowledgments for the [Pin Convergence Acknowledgment Predicate](#pin-convergence-acknowledgment-predicate) and complete schedule reconciliation; cleanup progress is not a gate. Otherwise that attempt returns to `ROLLBACK_CONVERGENCE_TIMEOUT` with script admission fail-closed and, on the exceptional branch, ticks still paused.
- While timeout terminal state remains active, pre-handler ingress must return `admitted=false`, `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE`, `admissionReason=rollback_convergence_timeout`, and no `retryAfterMs`; `script_event_ingress_audit` must record the same event-scope admission outcome and reason. `scriptId` and `bindingId` are unavailable for this decision. No handler-scoped `script_event_audit` row may use `finalOutcome=rollback_convergence_timeout`; already-resolved handlers retain their applicable handler-scoped outcome.

## Pin-State Degraded Operations Policy (Required)

`pin_state_unavailable` is fail-closed. There is no operator stale-pin override: a local projection, TTL, audit record, or emergency flag cannot prove the authoritative `(scriptPatchVersion, scriptPinEpoch)` tuple. Recovery restores Game Session reads/projection delivery, repairs the control-plane path, or performs an explicit repin after authority is available. Ordinary non-script gameplay is not paused by this scripting failure. A future availability exception requires a new accepted contract for a short-lived Game Session-issued exact-pin capability with issuance, audience, expiry, replay resistance, revocation, and downstream verification.

Notes:

- **Target-state only:** Even without an immediate purge, Game Session’s version-and-epoch fence prevents execution of commands produced under the displaced pin. Cancellation/purge remains bounded asynchronous cleanup for queue growth and operator clarity, not the cutover correctness barrier. **Current live gap:** the handoff still lacks `scriptPinEpoch`, so same-version old-epoch rejection is not shipped; see [Command Identity and Live Handoff Boundary](#command-identity-and-live-handoff-boundary).
- Rollback does not attempt compensating actions for already-executed tick effects. Operators rely on normal incident response patterns for remediation such as restore, rollback data, or targeted admin operations.
