# FireMUD Scripting & Automation: Rollout and Rollback

This document is the canonical owner for operator-driven promotion, rollback, workflow sequencing, convergence, timeout, and degraded-operations contracts for scripting and plugin control-plane changes. [Scripting & Automation: Control Plane API](./system-architecture-scripting-control-plane-api.md) defines the underlying RPC contracts and mutable state boundaries. [Scripting & Automation: Control Plane Operations](./system-architecture-scripting-control-plane-operations.md) records each service's participation and cleanup APIs, while the [operations cookbook](./system-architecture-scripting-operations-cookbook.md) provides executable operator examples.

For mutating workflow calls, `actor` is the authenticated operator principal and is projected to audit as `requestedBy`. System-owned reconciliation and cleanup records use a separate `executedBy=system:automation`; they must not replace `requestedBy` or overload `actor` with the worker identity.

The script-pin transition state machine below is target-state canonical for both promotion and rollback. In this workflow, authoritative Automation admission-mode readback is [`GetAutomationDrainStatus`](./system-architecture-scripting-control-plane-operations.md#getautomationdrainstatus); target-state exceptional tick readback is Game Session [`GetRegionTickStatus`](./system-architecture-ticks.md#bootstrap-vs-stream-authoritative-timeline-source). Current-live [`GetRuntimeOwnershipStatus`](./microservices/game-session-service/api-contracts.md) plus `ObserveRuntimeTickProgress` proves owner, timeline, and progress only; it does not prove tick/effect quiescence.

Before any promotion or rollback admission barrier, the orchestrator resolves the complete affected scope set from the authoritative durable PostgreSQL/runtime inventory, including every affected `regionId` and any existing empty/unscoped work. It then issues `SetAutomationAdmissionMode` and `GetAutomationDrainStatus` for each exact scope. Omitted or blank `regionId` means only the exact empty/unscoped row; it is never a regional wildcard. Each Set must return and durably persist a successful `APPLIED` or `ALREADY_APPLIED` request-result acknowledgment bound to the normalized request ID, exact scope, explicit target mode, fingerprint, and admission epoch, and each readback must match that acknowledgment. Missing, stale, contradictory, or incomplete enumeration/readback fails closed and cannot be replaced by aggregate counts or an RPC response.

## Implementation Status

Automation currently claims work through `PENDING_EVALUATION` to `EVALUATING`; its implementation lacks the target lease/fencing-generation recovery and separate evaluated descriptor/outbox boundary. The target state mapping and recovery owner are canonical in [Scripting Runtime Execution](./system-architecture-scripting-runtime-execution.md#current-state-mapping-drain-and-rebuild-rules). While `PAUSED_FOR_ROLLBACK`, current `GetAutomationDrainStatus` restricts its counted set to rows whose `workItem.admissionEpoch <= 0` or `workItem.admissionEpoch < current admissionEpoch`, excluding positive current-epoch rows; within that set `activeExecutionCount` counts `EVALUATING` and `HANDOFF_IN_FLIGHT`, including unresolved stale `EVALUATING`, and `pendingCancelableWorkItemCount` counts `PENDING_EVALUATION`. Normal mode counts the corresponding scoped rows without that epoch filter. This is a current projection gap, not permission to infer a reclaim. Metric schemas come from [Table 4](./system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix); audit and handoff diagnostics come from the [Scripting & Automation Observability Contract](./system-architecture-scripting-observability-contract.md).

The current exact-owner boundary is narrower than the target workflow: Game Session's pin owner persists the exact `(scriptPatchVersion, scriptPinEpoch, scriptPinControlPlaneRequestId)` tuple, and Automation work-item plus handoff-audit persistence retains that evidence. `scriptPinControlPlaneRequestId` is the persisted owner-evidence projection of the successful Game Session pin mutation's API `controlPlaneRequestId`; it is not a second request identity. Later convergence and reconciliation operations use their own operation-scoped `controlPlaneRequestId` values and the separate `convergenceAttemptGeneration`, and never overwrite the persisted pin-owner evidence. For local instance-scoped Automation, the live Game Session handoff carries the complete tuple, compares it before admission or duplicate replay, and rechecks it before final gameplay execution. The remaining final-effect gap is remote Automation source/target handoff and tuple binding; those target gates remain separate and must not be inferred from the local path. Current remote handoff diagnosis uses the narrower fallback documented in [Scripting Runtime Execution](./system-architecture-scripting-runtime-execution.md#current-implementation-status).

## Patch Promotion (Operator-Driven)

1. Validate patch is `READY` in Automation & Scripting for the tenant (`GetScriptPatchStatus`).
2. Optionally ask Automation to prepare/preload the exact candidate artifact while the current Game Session pin remains active. When used, Automation persists and returns immutable preparation evidence bound to the exact `(tenantId, gameInstanceId, controlPlaneRequestId, targetScriptPatchVersion)` together with the artifact digest, current tenant-`READY` state and readiness revision, and applicable policy revisions, as defined by [ADR 0103](./decisions/adr-0103-single-authority-script-pins-with-exact-version-execution.md). Preparation is non-authoritative and admits no candidate gameplay work; failure leaves the current pin and epoch unchanged.
3. For every exact scope resolved above, including each affected region and the exact empty/unscoped scope when present, enter the Automation admission barrier with `SetAutomationAdmissionMode(..., mode=PAUSED_FOR_ROLLBACK, controlPlaneRequestId, actor, reason)` before the serialized authority change. The barrier stops new external and scheduler triggers, while ordinary player commands and ticks continue. A failed or ambiguous response leaves the workflow in `PAUSING_AUTOMATION` and is retried with the same `controlPlaneRequestId`; even a successful response does not authorize the next step until that scope satisfies the durable acknowledgment and matching authoritative readback contract above with `admissionMode=PAUSED_FOR_ROLLBACK`. Unavailable, contradictory, or incomplete per-scope acknowledgment/readback leaves script admission fail-closed and makes no pin or rollout-history mutation; the exact RPC contract remains owned by [Control Plane Operations](./system-architecture-scripting-control-plane-operations.md#setautomationadmissionmode).
4. Call `SetPinnedScriptPatchVersion` in Game Session with the required `expectedCurrentPin` precondition and its explicit tag, plus `controlPlaneRequestId`, `actor`, and `reason`, supplying the immutable preparation evidence when that optional path was used. For a first pin, use `EXPECT_UNPINNED`; for a normal repin, use `EXPECT_EPOCH(scriptPinEpoch)` with the currently authoritative epoch. Game Session revalidates the current tenant-`READY` state, artifact digest, readiness revision, and applicable policy revisions at commit and rejects missing, mismatched, or stale preparation evidence; without preparation, it performs the equivalent authoritative commit-time checks. It then atomically persists the exact owner tuple `(scriptPatchVersion, scriptPinEpoch, scriptPinControlPlaneRequestId)`, projecting the mutation's `controlPlaneRequestId` into `scriptPinControlPlaneRequestId`, advances the epoch for every selection change, appends rollout history, and emits `ScriptPatchPinChanged`.
5. Automation reconciles schedules and timers for the exact target owner tuple `(scriptPatchVersion, scriptPinEpoch, scriptPinControlPlaneRequestId)` before resuming script admission. The default interval behavior is cancel-and-recreate; continuity is carried only when both sides explicitly opt in with the stable continuity key and typed cadence/target compatibility defined by [Scripting Scheduler and Timer Lifecycle](./system-architecture-scripting-scheduler-and-timers.md#explicit-continuity-across-script-transitions). Reconciliation creates no firing claim or `scriptEventId`.
6. Cancel and purge displaced work asynchronously as bounded idempotent cleanup. Cleanup improves resource use and operator visibility but is not the correctness barrier. **Target state:** every local instance-scoped Automation persistence, handoff, staging, replay, and final-effect boundary carries and enforces the exact owner tuple, with the `(scriptPatchVersion, scriptPinEpoch)` pair remaining the execution fence and the request ID retaining owner evidence. The local Game Session path is implemented; remote Automation source/target handoff and final-effect enforcement remain the narrowed gap described in Implementation Status.
7. Wait for the [Pin Convergence Acknowledgment Predicate](#pin-convergence-acknowledgment-predicate) to succeed for the exact resulting epoch and request, then call `SetAutomationAdmissionMode(..., mode=NORMAL)` once for every exact scope resolved above, including any exact empty/unscoped scope. A failed call leaves the workflow retryable in `RESUMING_AUTOMATION` with new script admission fail-closed; retry the same `controlPlaneRequestId`. After either a successful or ambiguous call, completion is gated solely by every scope satisfying the durable acknowledgment and matching authoritative readback contract above with `admissionMode=NORMAL`; unavailable, contradictory, or incomplete per-scope acknowledgment/readback leaves the workflow retryable with new script admission fail-closed, and the RPC response never itself permits `COMPLETED`. The exact RPC contract remains owned by [Control Plane Operations](./system-architecture-scripting-control-plane-operations.md#setautomationadmissionmode).
8. If authority is unavailable, new script admission remains fail-closed with `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_PIN_STATE_UNAVAILABLE` and `admissionReason=pin_state_unavailable`; if the requested exact tuple mismatches the observed tuple, it remains fail-closed with `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE` and `admissionReason=pin_state_mismatch_requested_vs_observed`. Ordinary gameplay remains available unless an explicitly declared unfenced effect requires exceptional tick pause.
9. Operators monitor Game Session's authoritative rollout history alongside Automation readiness/convergence projections; projection disagreement is displayed as lag, not resolved by selecting Automation history.

## Patch Rollback (Operator-Driven, Required)

1. Validate the target is previously published, tenant-`READY`, base-compatible, and immutable. Optionally ask Automation to prepare/preload that exact artifact while the current pin remains active; when used, it persists and returns the immutable preparation evidence bound as defined in [ADR 0103](./decisions/adr-0103-single-authority-script-pins-with-exact-version-execution.md). Preparation is non-authoritative and admits no candidate gameplay work; preparation failure leaves the current tuple unchanged.
2. For every exact scope in the authoritative inventory, call `SetAutomationAdmissionMode(..., mode=PAUSED_FOR_ROLLBACK, controlPlaneRequestId, actor, reason)`. These scoped barriers stop new script/plugin triggers and scheduler firings but do not pause ordinary player commands or gameplay ticks. A failed or ambiguous response leaves the workflow retryable in `PAUSING_AUTOMATION`; retry the same normalized tuple and require durable acknowledgment readback for each scope before advancing. On the exceptional branch, call `PauseTicks` for the declared smallest complete scope only after all Automation scope acknowledgments succeed and before step 3; a failed or ambiguous response leaves the workflow retryable in `PAUSING_TICKS` with no pin or rollout-history mutation while Automation admission remains paused. Retry the same `controlPlaneRequestId`; no `PauseTicks` response authorizes pin or rollout-history mutation or `REPINNING` until target-state [`GetRegionTickStatus`](./system-architecture-ticks.md#bootstrap-vs-stream-authoritative-timeline-source) readback for the exact scope shows `status=PAUSED`, matching `regionEpoch` and `executorFence`, and a fresh `lastCommittedTickId`/`updatedAt`, together with separate durable proof of `durable_committed` and `coordination_cleared` from the tick owner contract.
3. Call `RollbackScriptPatchVersion` (or `SetPinnedScriptPatchVersion`) with the required `expectedCurrentPin=EXPECT_EPOCH(scriptPinEpoch)` precondition and its explicit tag for the currently authoritative epoch, plus `controlPlaneRequestId`, `actor`, and `reason`, supplying the immutable preparation evidence when that optional path was used. Game Session revalidates the current tenant-`READY` state, artifact digest, readiness revision, and applicable policy revisions at commit and rejects missing, mismatched, or stale preparation evidence; without preparation, it performs the equivalent authoritative commit-time checks. It then atomically commits the exact owner tuple `(scriptPatchVersion, scriptPinEpoch, scriptPinControlPlaneRequestId)`, projecting the mutation's `controlPlaneRequestId` into `scriptPinControlPlaneRequestId`, advances the epoch even for repin to a previously used version, appends rollout history, and emits `ScriptPatchPinChanged`.
4. Automation performs durable schedule/timer reconciliation while the admission barrier remains active. The default interval transition is cancel-and-recreate. Continuity requires explicit compatible declarations on both sides with the stable key and typed cadence/target checks in [ADR 0110](./decisions/adr-0110-explicit-opt-in-schedule-continuity-across-script-transitions.md); `scheduleSemanticsHash` is diagnostic evidence only. Reconciliation creates no firing claim or `scriptEventId`.
5. Cancel displaced Automation work and purge stale queue entries as bounded, idempotent asynchronous cleanup. **Target state:** every local instance-scoped Automation persistence, handoff, staging, retry/replay, and final-effect boundary rejects the displaced tuple and compares the complete owner evidence; cleanup lag does not delay unrelated gameplay. Local Game Session admission/replay/final execution now enforce that boundary; remote Automation source/target handoff and final-effect enforcement remain the narrower implementation described in Implementation Status.
6. Wait for fresh owner acknowledgments satisfying the canonical [Pin Convergence Acknowledgment Predicate](#pin-convergence-acknowledgment-predicate). If the target cannot be loaded or reconciled, Automation stays fail-closed for new script work and exposes repair/repin action; Game Session does not silently restore an older pin.
7. After convergence and schedule reconciliation, the ordinary path calls `SetAutomationAdmissionMode(..., mode=NORMAL, controlPlaneRequestId, actor, reason)` once for every exact enumerated scope. On the ordinary branch, a failed call leaves the workflow retryable in `RESUMING_AUTOMATION` with new script admission fail-closed; retry repeats the same normalized tuple. Completion requires each scope's durable successful `APPLIED`/`ALREADY_APPLIED` acknowledgment and matching authoritative [`GetAutomationDrainStatus`](./system-architecture-scripting-control-plane-operations.md#getautomationdrainstatus) readback; unavailable or contradictory readback leaves the workflow retryable, and no RPC response itself permits `COMPLETED`. On the exceptional branch, call `ResumeTicks` for the declared smallest complete scope first, then return Automation admission to `NORMAL` for every enumerated scope; a failed `ResumeTicks` call leaves the workflow retryable in `RESUMING_TICKS` with Automation admission paused. After either a successful or ambiguous `ResumeTicks` response, the workflow must read back target-state [`GetRegionTickStatus`](./system-architecture-ticks.md#bootstrap-vs-stream-authoritative-timeline-source) for the exact scope until `status=RUNNING` and fresh committed progress is observed under matching `regionEpoch` and `executorFence`; unavailable or contradictory readback leaves it retryable in `RESUMING_TICKS` with Automation admission paused. An ambiguous response does not claim the tick pause remains active because ticks may already have resumed safely. Only that authoritative readback permits entry to `RESUMING_AUTOMATION`. A full `PauseTicks`/`ResumeTicks` pair is required only for an explicitly declared unfenced effect family, migration, or compatibility transition, and that exceptional workflow must identify its smallest complete scope and prove quiescence.

## Pin Compare-and-Set Preconditions

`SetPinnedScriptPatchVersion` and `RollbackScriptPatchVersion` require an explicit tagged `expectedCurrentPin` with exactly one of `UNCONDITIONAL`, `EXPECT_UNPINNED`, or `EXPECT_EPOCH(scriptPinEpoch)`. Missing or unknown tags are invalid and must be rejected before pin, epoch, or outbox mutation. `EXPECT_UNPINNED` is the safe first-pin compare-and-set; normal repin, same-version epoch-only repin, and rollback use `EXPECT_EPOCH(scriptPinEpoch)` for the currently authoritative epoch. `UNCONDITIONAL` remains only a `platformAdmin` break-glass repair operation with a nonblank `reason`, stable `controlPlaneRequestId`, and durable audit; it skips only the current-pin comparison and must still satisfy coherent Game Session owner state, readiness, authorization, and every other validation. It is never inferred from an omitted field. The tag and value participate in the canonical request digest, so an exact idempotent retry returns the stored result while a different tag or epoch under the same request identity conflicts under the existing request/history semantics.

The tagged `expectedCurrentPin`/`scriptPinEpoch` precondition is an existing Game Session pin-authority prerequisite delivered by the separate Game Session remainder: the proto carries the tag/value, the owner compares it while holding the authoritative instance row lock, the owner populates the pin epoch, and the durable request ledger binds exact retries and conflicts. Local instance-scoped Automation admission/replay and final Game Session execution now enforce the complete owner tuple; this #2682 workflow does not claim that remote Automation source/target handoff or final gameplay-effect binding is complete. Broader workflow/history and remote end-to-end Automation proof remains target-state.

**Target-state rule:** Every committed pin, CAS precondition/readback, schedule or timer reconciliation, convergence acknowledgment, and local runtime fence carries the exact owner tuple `(scriptPatchVersion, scriptPinEpoch, scriptPinControlPlaneRequestId)`; the version/epoch pair remains the execution fence, while `scriptPinControlPlaneRequestId` retains the originating API `controlPlaneRequestId` as owner evidence. Local Game Session admission/replay/final execution now enforce this boundary; remote source/target handoff and final-effect binding remain target-state.

Concrete example:

- `tenantId=11111111-1111-4111-8111-111111111111`, `gameInstanceId=44444444-4444-4444-8444-444444444444`, current pin `P22`, rollback target `P21`, `controlPlaneRequestId=RB-42`.
- The authoritative inventory resolves exactly one affected scope for this example: the empty/unscoped row for this tenant and game instance (omitted `regionId`), with no regional `regionId` rows; the omitted `regionId` in Steps 2 and 7, and the corresponding Step 8 readback, therefore refer to that exact row and never to a wildcard.
- Step 1: Automation optionally prepares the exact P21 artifact while the current P22 pin remains active and, when used, returns immutable preparation evidence `preparationAttestationRef=PA-17` defined by ADR 0103; preparation failure leaves P22 and its epoch unchanged.
- Step 2: `SetAutomationAdmissionMode(tenantId=11111111-1111-4111-8111-111111111111, gameInstanceId=44444444-4444-4444-8444-444444444444, mode=PAUSED_FOR_ROLLBACK, controlPlaneRequestId=RB-42, actor=operator:alice, reason="rollback RB-42")`; before repin, the durable successful `APPLIED` or `ALREADY_APPLIED` acknowledgment and authoritative scoped `GetAutomationDrainStatus` readback must bind the same request ID, exact normalized scope, explicit target mode, request fingerprint, resulting `admissionEpoch`, and fresh `observedAt`. The RPC response alone is not barrier proof.
- Step 3: `RollbackScriptPatchVersion(... targetScriptPatchVersion=P21, expectedCurrentPin=EXPECT_EPOCH(N), preparationAttestationRef=PA-17, controlPlaneRequestId=RB-42, actor=operator:alice, reason="rollback RB-42")` supplies the preparation evidence when used, then commits `(P21, scriptPinEpoch=N+1, controlPlaneRequestId=RB-42)` and Game Session history atomically.
- Step 4: Automation reconciles schedules under RB-42; continuity is preserved only with explicit declarations and typed compatibility, otherwise rows are tombstoned and recreated with fresh due state.
- Step 5: stale P22 work is canceled/purged asynchronously and every exact epoch fence remains active at final mutation boundaries.
- Step 6: fresh convergence acknowledgments satisfy the canonical [Pin Convergence Acknowledgment Predicate](#pin-convergence-acknowledgment-predicate); convergence alone does not authorize resumption.
- Step 7: `SetAutomationAdmissionMode(..., mode=NORMAL, controlPlaneRequestId=RB-42, actor=operator:alice, reason="rollback RB-42")`; the durable successful `APPLIED` or `ALREADY_APPLIED` acknowledgment and subsequent authoritative scoped readback must bind the same request ID, exact normalized scope, explicit target mode, request fingerprint, resulting `admissionEpoch`, and fresh `observedAt`. The RPC response alone is not completion proof.
- Step 8: authoritative scoped `GetAutomationDrainStatus` readback, paired with that durable successful acknowledgment, proves the exact requested scope, `admissionMode=NORMAL`, the current `admissionEpoch`, matching request fingerprint, and fresh `observedAt` before the rollback workflow completes.

Ordering is intentional: when used, candidate preparation precedes the admission barrier; the barrier precedes repin and remains active through exact-artifact reconciliation and convergence. Without preparation, Game Session performs the equivalent authoritative checks at pin commit. Ordinary gameplay ticks are not held by routine script rollback. Exceptional tick pause, when required by an unfenced effect, is a separately named and proven workflow.

## Two-Stage Event Deduplication

Rollback and normal event ingress use two deduplication stages:

- Before handler resolution, incoming request dedupe uses the event-scope identity from [Table 1](./system-architecture-scripting-normative-contract-tables.md#table-1-trigger-identity-required-fields), including `isDryRun`. `scriptId` and `bindingId` are unavailable at ingress and must not be invented. A live claim (`isDryRun=false`) and a dry-run/test claim (`isDryRun=true`) are distinct even when every other applicable field matches; they must not share an event-scope claim, ingress audit result, or materialized handler work. Retries must preserve the original mode, and changing it is an identity conflict.
- After binding resolution, each resolved handler dedupes independently by the full applicable Trigger Identity and retains its own handler-scoped audit outcome.
- The local mode consequence is directional: `isDryRun=false` may continue through live persistence and handoff, while `isDryRun=true` remains on the non-committing test branch and must not use live execution metric consequences; the exact metric families and units remain owned by Table 4.

## Command Identity and Live Handoff Boundary

Rollback diagnosis uses the command-identity contract rather than treating a handler-level trigger identity as a command identity:

- **Target state:** Game Session rejects queued commands whose embedded owner tuple `(scriptPatchVersion, scriptPinEpoch, scriptPinControlPlaneRequestId)` does not match the current instance pin/evidence, or whose exact `(pluginId, pluginVersionId, bindingId)` is not admitted by Automation & Scripting's authoritative instance-scoped active plugin tuple/runtime lifecycle together with the fresh publication, signer, component-policy, and capability-grant eligibility evidence owned by Game Design and revalidated/used by Automation; when both provenances are present, both independent fences apply. Game Session consumes the resulting applicable exact plugin fence and fresh evidence without becoming an authority for either domain. Complete plugin handoff/execution-fence records and failure evidence retain the captured `(pluginActivationEpoch, lifecycleRevision)` pair unchanged; the pair is fence evidence only and does not redefine Automation-owned lifecycle advancement. It records one per-command handoff result through `ListScriptHandoffEvents` / `commandHandoffDispositions[]`. Each result retains the complete applicable Trigger Identity for correlation plus the complete [Command-Handoff Identity](./system-architecture-scripting-normative-contract-tables.md#command-handoff-identity-target-state), whose final discriminator is `(automationDispatchId, commandOrdinal)`; plugin handlers additionally retain `pluginId`, `pluginVersionId`, and `bindingId`, with `bindingId` used only as plugin provenance/correlation/fence evidence and excluded from Command-Handoff child uniqueness, deduplication, and replay selection, while scheduler/timer handlers additionally retain `scheduleDefinitionId`, `triggerMode`, and exactly one due-point field (`dueTickId` or `dueAt`). Neither lifecycle-fence value is a stable handler, command, schedule-row, continuity, or ordering identity. `outboxWorkItemId` and the parent Trigger Identity are correlation-only and excluded from command identity, uniqueness, and replay keys. Per-command durable progress is independent, and any owner tuple shown without its complete source/target runtime scope is only a display suffix; retries resume unresolved commands without dropping unattempted commands or replaying accepted or terminally rejected commands.

Operators must therefore use the narrower current live handoff fallback documented in [Scripting Runtime Execution](./system-architecture-scripting-runtime-execution.md#current-implementation-status) for live rollback diagnosis and must not infer a complete per-command execution disposition from fields the live handoff does not carry. The target per-command view is the contract to converge to; it does not describe current proto coverage.

## Pin Transition Orchestration State Machine (Required)

Every operator-driven patch promotion or rollback must expose and persist one script-pin transition state machine so partial failures are recoverable and retries are deterministic. The workflow record binds the existing immutable rollout `operationKind` (`SET`, `ROLLBACK`, or `REPIN`) from the authoritative history contract, together with the normalized request digest, target tuple, and durable monotonic `convergenceAttemptGeneration`, initialized to `1` atomically with workflow creation. Explicit same-workflow recovery alone allocates the next generation; retries reuse the current generation.

Ownership and source-of-truth requirements:

- Game Session is the producer-of-record for pin-transition orchestration state keyed by `controlPlaneRequestId` and is the sole producer of the convergence-timeout signal.
- `ScriptPinConvergenceTimedOut` may be emitted only by Game Session from complete, internally consistent persisted workflow evidence after the workflow reaches `PIN_CONVERGENCE_TIMEOUT`, and only when the exact persisted tuple `(tenantId, gameInstanceId, targetScriptPatchVersion, targetScriptPinEpoch, operationKind, convergenceAttemptGeneration, controlPlaneRequestId)` matches the event payload. `operationKind` is one of `SET`, `ROLLBACK`, or `REPIN`; incomplete or conflicting evidence prevents the timeout terminal transition and its event. The [Control Plane Events](./system-architecture-scripting-control-plane-events.md#scriptpinconvergencetimedout-game-session---durable-event-flow) document owns the event fields and consumer correlation rule, while the [Control Plane API](./system-architecture-scripting-control-plane-api.md) owns the RPC timeout semantics.
- Logging & Admin may expose convenience orchestration APIs, but these must call the Game Session workflow APIs and read back the same canonical workflow state through [`GetScriptPinTransitionWorkflowStatus`](./system-architecture-scripting-control-plane-api.md#getscriptpintransitionworkflowstatus); they must not persist a competing pin-transition state machine.
- Automation & Scripting participates via idempotent step APIs (`SetAutomationAdmissionMode`, cancel/purge hooks, convergence reads) and must not infer orchestration completion from local state alone.

Required states:

- `PREPARING` -> `PAUSING_AUTOMATION` -> `REPINNING` -> `RECONCILING_SCHEDULES` -> `CONVERGING` -> `RESUMING_AUTOMATION` -> `COMPLETED`
- Exceptional branch (only when the workflow records an unfenced effect/migration boundary and proves quiescence): `PREPARING` -> `PAUSING_AUTOMATION` -> `PAUSING_TICKS` -> `REPINNING` -> `RECONCILING_SCHEDULES` -> `CONVERGING` -> `RESUMING_TICKS` -> `RESUMING_AUTOMATION` -> `COMPLETED`.
- Terminal failure state: `PIN_CONVERGENCE_TIMEOUT`

State rules:

- Each transition must be idempotent and keyed by `controlPlaneRequestId` plus the current `convergenceAttemptGeneration`; changing `operationKind`, target tuple, generation, or any other normalized request field under that identity conflicts before mutation. The target-state `RecoverScriptPinConvergence` mutation is the only operation that allocates a new generation, and it must CAS the expected timed-out generation before doing so; retries of the active attempt reuse its generation.
- Re-running a request in the same state must return current state, not restart from scratch.
- In `PAUSING_AUTOMATION`, a failed or ambiguous `SetAutomationAdmissionMode(..., mode=PAUSED_FOR_ROLLBACK)` response leaves the same workflow retryable in `PAUSING_AUTOMATION`; retries use the same `controlPlaneRequestId`, and no response alone authorizes `REPINNING`. Only authoritative [`GetAutomationDrainStatus`](./system-architecture-scripting-control-plane-operations.md#getautomationdrainstatus) readback matching the requested scope and `admissionMode=PAUSED_FOR_ROLLBACK`, current `admissionEpoch`, and fresh `observedAt` permits the workflow to advance; unavailable or contradictory readback leaves script admission fail-closed with no pin or rollout-history mutation.
- For the exceptional branch, `PAUSING_TICKS` is entered only after `PAUSING_AUTOMATION` succeeds and records the declared unfenced boundary and smallest complete scope. A failed or ambiguous `PauseTicks` response leaves the same workflow retryable in `PAUSING_TICKS` with no pin or rollout-history mutation while Automation admission remains paused; retries use the same `controlPlaneRequestId`, and no `PauseTicks` response authorizes pin or rollout-history mutation or `REPINNING` until target-state [`GetRegionTickStatus`](./system-architecture-ticks.md#bootstrap-vs-stream-authoritative-timeline-source) readback for the exact scope shows `status=PAUSED`, matching `regionEpoch` and `executorFence`, and fresh `lastCommittedTickId`/`updatedAt`, together with separate durable `durable_committed` and `coordination_cleared` proof from the tick owner contract.
- `RECONCILING_SCHEDULES` must complete before target-version timer or script admission resumes. Replacement creation and displaced-row retirement must be one atomic durable result or a resumable, idempotent operation keyed by `controlPlaneRequestId`; retries must create or confirm the target schedule before retiring the displaced row. Continuity is allowed only by explicit opt-in declarations and typed compatibility; `scheduleSemanticsHash` cannot grant continuity. Reconciliation must not create firing claims or `scriptEventId`.
- The workflow persists separate cleanup progress, including bounded pending work, last error, and retry timing, rather than representing cleanup as a critical-path state. Cancellation, purge, and drain cleanup may remain pending after `COMPLETED`; the displaced exact owner tuple `(scriptPatchVersion, scriptPinEpoch, scriptPinControlPlaneRequestId)` remains authoritative while that asynchronous work retries.
- Cleanup failures do not invalidate the exact epoch fence or pause ordinary ticks; they remain visible as bounded cleanup backlog and retry state. Automation admission stays paused until exact-artifact convergence and schedule reconciliation succeed, never until cleanup reaches zero.
- Operator retries must continue from the last durable state.
- `CONVERGING` transitions to `RESUMING_TICKS` on the exceptional branch, or to `RESUMING_AUTOMATION` on the ordinary branch, only after the Pin Convergence Acknowledgment Predicate and schedule reconciliation requirements succeed. On the exceptional branch, a convergence failure or unsatisfied observation before the deadline leaves both tick and Automation pauses active while the same attempt remains in `CONVERGING`. If the configured deadline is reached while that predicate remains unsatisfied, the workflow follows the complete-evidence and atomic event/metric requirements below to transition directly and durably to terminal `PIN_CONVERGENCE_TIMEOUT`; incomplete or conflicting evidence leaves the attempt retryable in `CONVERGING` and cannot produce a terminal timeout. On the exceptional branch, `PIN_CONVERGENCE_TIMEOUT` is reachable only from `CONVERGING` before the current attempt has a fresh exact-scope `GetRegionTickStatus` proof of `status=RUNNING`; the ordinary branch has no tick-status proof dependency. It must not be introduced from `RESUMING_TICKS` or `RESUMING_AUTOMATION`, and it must not advance to either resume state or `COMPLETED`.
- `PIN_CONVERGENCE_TIMEOUT` is terminal for the current convergence attempt and remains terminal while no explicit operator recovery occurs; it keeps new Automation admission fail-closed until explicit repair/repin. Ordinary player commands and gameplay ticks continue unless the optional exceptional tick-pause branch was selected.
- Explicit `RecoverScriptPinConvergence` recovery of `PIN_CONVERGENCE_TIMEOUT` starts a fresh convergence attempt on the same Game Session workflow record with the same `controlPlaneRequestId` and expected timed-out generation, and a new `convergenceAttemptGeneration` incremented exactly once; it transitions `PIN_CONVERGENCE_TIMEOUT -> CONVERGING`, not to a new workflow or state machine or an ordinary retryable state. The new attempt persists a fresh absolute `convergenceDeadlineAt` and generation while retaining each prior attempt's generation, deadline, and timeout outcome as immutable attempt/history evidence. A repeated recovery call with the same normalized recovery input returns its recorded resulting generation/deadline without allocating again; retries of the original promotion/rollback request return that attempt's stored terminal result and do not recover. Recovery must preserve both fences and, for the exceptional branch, keep ticks and Automation paused. If fresh convergence proof remains unavailable, that attempt returns to `PIN_CONVERGENCE_TIMEOUT` with the current fences still active.
- On the exceptional branch, `RESUMING_TICKS` is entered only after convergence succeeds. A failed `ResumeTicks` call leaves the workflow retryable in `RESUMING_TICKS` with Automation admission still paused. After either a successful or ambiguous `ResumeTicks` response, the workflow must obtain target-state [`GetRegionTickStatus`](./system-architecture-ticks.md#bootstrap-vs-stream-authoritative-timeline-source) readback for the exact scope until `status=RUNNING` and fresh committed progress is observed under matching `regionEpoch` and `executorFence`; unavailable or contradictory readback leaves it retryable in `RESUMING_TICKS` with Automation admission still paused. An ambiguous response does not claim that the tick pause remains active because ticks may already have resumed safely. The workflow persists that fresh exact-scope `RUNNING` proof, including the matching scope, `regionEpoch`, `executorFence`, and committed progress, before entering `RESUMING_AUTOMATION`; retries in `RESUMING_AUTOMATION` do not repeat `ResumeTicks`. If the authoritative readback contradicts the expected scope or fence, or external state has changed, the workflow reads back the authoritative tick status again before acting. Only that authoritative readback permits entry to `RESUMING_AUTOMATION`. The workflow then calls `SetAutomationAdmissionMode(..., mode=NORMAL)` with the same `controlPlaneRequestId`; a successful or ambiguous response does not itself permit completion, which is gated solely by authoritative [`GetAutomationDrainStatus`](./system-architecture-scripting-control-plane-operations.md#getautomationdrainstatus) readback matching the requested scope and `admissionMode=NORMAL`, current `admissionEpoch`, and fresh `observedAt`. Unavailable or contradictory readback leaves the workflow retryable in `RESUMING_AUTOMATION` with new script admission fail-closed.
- `GetAutomationDrainStatus` is an authoritative admission-mode pause/resume readback only when paired with the durable successful `APPLIED`/`ALREADY_APPLIED` Set acknowledgment and when its returned request ID, exact normalized scope, explicit target mode, request fingerprint, resulting `admissionEpoch`, admission mode, and fresh `observedAt` all match that requested operation; its execution/drain counts remain diagnostic and do not replace exact pin/convergence gates. **Target-state mapping:** `activeExecutionCount` is exactly `EXECUTING` pre-DSL triggers plus `HANDOFF_IN_FLIGHT` evaluated descriptors, and `pendingCancelableWorkItemCount` is exactly `PENDING_EVALUATION` pre-DSL triggers plus `PENDING`/`INDEXED` evaluated descriptors. A cached, stale, missing, or earlier-epoch response remains diagnostic and cannot satisfy exact convergence.
- **Current projection mapping:** while `PAUSED_FOR_ROLLBACK`, the live projection restricts its counted set to rows whose `workItem.admissionEpoch <= 0` or `workItem.admissionEpoch < current admissionEpoch`, excluding positive current-epoch rows; within that set it counts `EVALUATING`, including unresolved stale rows, and `HANDOFF_IN_FLIGHT` as active and `PENDING_EVALUATION` as pending. Normal mode counts the corresponding scoped rows without that epoch filter. The separate `PENDING`/`INDEXED` descriptor layer is not yet persisted. These counts expose an implementation gap and do not gate ordinary ticks or target convergence.
- During target-state asynchronous cancellation and cleanup, `PENDING_EVALUATION` transitions durably to terminal `CANCELED` with `finalStage=ADMISSION`, `finalOutcome=canceled`, and the bounded rollback/operator reason without entering the DSL. A target `EXECUTING` trigger is fenced and its descriptor-commit marker is read first: committed descriptors/children are canceled or fenced without resume or redispatch; separate post-evaluation recovery may replay only the stored child ledger without DSL re-entry; explicit cancellation of an uncommitted trigger transitions to terminal `CANCELED` with `finalStage=DSL_EVAL`, `finalOutcome=canceled`, and the bounded cancellation reason and is never replay-eligible; only the distinct expired-stale recovery-owner path transitions an uncommitted trigger to terminal `DEAD_LETTERED` with `finalStage=DSL_EVAL`, `finalOutcome=canceled`, and `finalReason=stale_execution_fenced`. The cancellation API itself does not dead-letter stale displaced rows. Cleanup progress remains separately observable and does not gate Automation resumption or ordinary gameplay ticks.

## Pin Convergence Acknowledgment Predicate

Promotion and rollback pin convergence succeeds only when, before the configured deadline, both fresh owner acknowledgments are present for the same scope, current convergence attempt generation, and request:

- Game Session reports the requested target `scriptPatchVersion`, resulting `scriptPinEpoch`, current `convergenceAttemptGeneration`, and `controlPlaneRequestId` from a fresh authoritative convergence read.
- Automation & Scripting reports the requested target `scriptPatchVersion`, exact observed `scriptPinEpoch`, observed `convergenceAttemptGeneration`, and `controlPlaneRequestId`, `isProjectionStale=false`, and `projectionLagMs` within the configured `SCRIPT_PIN_PROJECTION_STALE_THRESHOLD_MS` bound from a fresh Automation projection/convergence read.

An acknowledgment is fresh only when it reflects this promotion/rollback operation rather than a stale cache or an earlier request, and it must arrive before the deadline. A missing, stale, mismatched, or out-of-bound acknowledgment from either owner is a non-terminal unsatisfied observation until the configured deadline. Fresh matching acknowledgments from both owners before the deadline satisfy the predicate; one owner's successful acknowledgment never substitutes for the other's.

Convergence timeout semantics (required):

- Game Session owns and reads the canonical target configuration key `firemud.scripting.pin-convergence-timeout-ms`, whose value must be a positive integer number of milliseconds. On workflow creation, Game Session atomically persists `convergenceAttemptGeneration=1` with the initial workflow state and computes one absolute `convergenceDeadlineAt` when entering `CONVERGING`; `RecoverScriptPinConvergence` alone increments the generation exactly once and computes a fresh deadline for the new attempt. Each attempt's generation and deadline are immutable: repeated calls for the same active attempt reuse both without refresh, while prior attempt generations, deadlines, and timeout outcomes remain immutable attempt/history evidence.
- Before the deadline, missing, stale, mismatched, or out-of-bound acknowledgments leave convergence unsatisfied and the workflow continues authoritative reads; they do not by themselves enter a terminal state.
- If the deadline is reached before the [Pin Convergence Acknowledgment Predicate](#pin-convergence-acknowledgment-predicate) succeeds, including because either owner's acknowledgment remains missing, stale, mismatched, or out-of-bound at the deadline, the promotion or rollback workflow must enter terminal state `PIN_CONVERGENCE_TIMEOUT` atomically with the exactly-once `ScriptPinConvergenceTimedOut` event and `automation_pin_convergence_timeout_total` metric consequence below when the persisted workflow evidence is complete and internally consistent for the exact scope, target tuple, immutable `operationKind`, current `convergenceAttemptGeneration`, and `controlPlaneRequestId`. Incomplete or conflicting persisted evidence leaves the attempt retryable in `CONVERGING` for authoritative repair/reconciliation and cannot produce a terminal timeout or its event/metric consequence.
- In `PIN_CONVERGENCE_TIMEOUT`, new Automation admission remains fail-closed. Ordinary player commands and ticks continue when healthy; if the exceptional branch was selected and this timeout is reached from `CONVERGING`, no current-attempt `RUNNING` proof exists and the tick state remains at its last authoritative paused proof until the separately proven resume steps. Game Session alone atomically commits the terminal state and exactly one `ScriptPinConvergenceTimedOut` event through one transactional outbox or equivalent atomic commit, with workflow-scoped idempotency keyed by the same workflow record, current `convergenceAttemptGeneration`, immutable `operationKind`, and `controlPlaneRequestId`; the corresponding `automation_pin_convergence_timeout_total` metric consequence is tied to that same transition and increments exactly once without adding an attempt label. Repeated calls for the same timed-out attempt may resume publication of its existing record but must not create a second timeout transition, event, or metric consequence, while a later explicit recovery attempt records its own new generation, deadline, and outcome evidence. Automation consumes that state/signal and does not produce a competing timeout signal or metric. See [Table 4](./system-architecture-scripting-normative-contract-tables.md#table-4-metrics-label-matrix) for the metric contract.
- An operator may explicitly recover the same durable workflow idempotently. Recovery starts the next convergence attempt with a fresh persisted generation and absolute deadline as described above; a repeated call for the same active recovery attempt reuses both. Before Automation returns to `NORMAL` (and before exceptional `ResumeTicks`, when applicable), it must obtain fresh matching Game Session and Automation acknowledgments for the [Pin Convergence Acknowledgment Predicate](#pin-convergence-acknowledgment-predicate) and complete schedule reconciliation; cleanup progress is not a gate. Otherwise the active attempt remains fail-closed in `CONVERGING` and, if its deadline expires, transitions to `PIN_CONVERGENCE_TIMEOUT` under the preceding rule. On the exceptional branch that deadline transition occurs before `ResumeTicks` and retains the last authoritative paused proof; no timeout transition is permitted from `RESUMING_TICKS` or `RESUMING_AUTOMATION`.
- While timeout terminal state remains active, pre-handler ingress must return `admitted=false`, `admissionOutcome=TRIGGER_ADMISSION_OUTCOME_VERSION_UNAVAILABLE`, `admissionReason=pin_convergence_timeout`, and no `retryAfterMs`; `script_event_ingress_audit` must record the same event-scope admission outcome and reason. `scriptId` and `bindingId` are unavailable for this decision. No handler-scoped `script_event_audit` row may use `finalOutcome=pin_convergence_timeout`; already-resolved handlers retain their applicable handler-scoped outcome.

## Pin-State Degraded Operations Policy (Required)

`pin_state_unavailable` is fail-closed. There is no operator stale-pin override: a local projection, TTL, audit record, or emergency flag cannot prove the authoritative owner tuple `(scriptPatchVersion, scriptPinEpoch, scriptPinControlPlaneRequestId)`. Recovery restores Game Session reads/projection delivery, repairs the control-plane path, or performs an explicit repin after authority is available. Ordinary non-script gameplay is not paused by this scripting failure. A future availability exception requires a new accepted contract for a short-lived Game Session-issued exact-pin capability with issuance, audience, expiry, replay resistance, revocation, and downstream verification.

Notes:

- Rollback does not attempt compensating actions for already-executed tick effects. Operators rely on normal incident response patterns for remediation such as restore, rollback data, or targeted admin operations.
