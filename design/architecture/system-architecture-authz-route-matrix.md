# FireMUD System Architecture: Authorization Route Matrix

The machine-readable [authorization route matrix](./system-architecture-authz-route-matrix.yaml) is normative for the route entries it contains. It is not yet a complete route inventory: source-stable OpenAPI/protobuf coverage and its comparison validation are incomplete. This document is the human-readable companion and must not define a competing policy.

Every protected route in a validated inventory must be listed here with:

- route identifier (service + method/path),
- classification (`public`, `account_scoped`, `caller_membership_scoped`, `player_bootstrap_tenant`, `pre_tenant_discovery`, `public_production_onboarding`, `gameplay_admission`, `tenant_regular`, `billing_safe_tenant`, `cross_tenant_support_safe`, `cross_tenant_billing_safe`, `cross_tenant_data_bearing`, `internal_workload`, `pending_deletion_scoped`, `security_lock_export_scoped`),
- whether a matching Account issued-token registry record is required,
- required role checks,
- tenant-billing authority-generation applicability,
- caller-bound membership authority-generation applicability where relevant,
- required live authority checks for the route class,
- any response-profile, exact action-family, or mutation-contract requirements needed for CI/security enforcement,
- any role-assurance or bounded privileged-elevation contract required before a global role may authorize the route.

**Canonical incomplete-inventory rule:** Until source-stable OpenAPI/protobuf inventory coverage is complete and validated, the YAML is declaration-only and must not generate runtime or default-deny policy for routes absent from the validated inventory. Runtime must reject unclassified protected routes and leave unclassified external routes unreachable or denied; CI and deployment inventory checks must fail validated candidate routes missing from the YAML.

Target state: once source-stable OpenAPI/protobuf inventory coverage is complete and validated, services will enforce these classifications through shared middleware annotations/interceptors. Until that gate passes, a protected route missing from the current matrix is recorded as authorization drift/gap; the canonical incomplete-inventory rule above governs its runtime and CI/deployment handling rather than forwarding or approximating it.

Operator mutation rows that require an Account-issued authorization reference or this privileged-control window are normative target rows, not current availability claims.

The current tenant-scoped caller-asserted scaffold must not be exposed or advertised; the target global-account route is owned by [Account Runtime and Data](./microservices/account-service/runtime-and-data.md) and remains unavailable until server-verified provider authorization and recent ordinary reauthentication exist.
- The current Account implementation of `ExportTenantData` remains account-targeted while the canonical target is a tenant-wide, tenant-owned export; this is recorded as known drift while the target route remains a distinct `billing_safe_tenant` exception.
- Logging & Admin feature-flag, admission-pointer/version-upgrade, tick, and moderation mutation paths are implemented or declared but remain externally disabled and nonconformant until each family has a published action schema, shared cross-language `mutationDigest/v1` golden vectors, and the Account-issued authorization-reference issuance/redemption flow. Their rows below describe the target authorization boundary, not current external support. Routes that use global-role branches additionally depend on the target-only `privileged_control` issuance path. Live admission-pointer reads/audit/prepared-upgrade proof reads and `EvaluateModerationPolicy` are separate read contracts and remain available.
- The operator mutation support gate is identity-complete even while the route inventory is incomplete: every exact identity in `operator_mutation_support_gate.applies_to` or `live_exceptions` must either match a YAML route entry or have a nested `coverage_drift` record with a reason. The Game Session HTTP create, stop, and restart mutations are `target_not_currently_routable` under this gate even though current owner-local OpenAPI scaffolds still exist. The owner-local workload-authenticated `refresh-roles` route is not authorization-reference-redeeming and remains outside the gate. The validator rejects unclassified gate identities and stale drift records.
- Public report submission (`POST /reports`) is target-only and not currently routable; the target player-bootstrap route must derive `tenantId` and `reporterAccountId` from the authenticated caller and live membership before it becomes routable.
- Game Session still exposes current owner-local `/sessions*` REST scaffolds. Direct owner edge exposure is denied and the canonical target external ingress for operator create, stop, and restart is Logging & Admin with Account authorization-reference forwarding, but Logging & Admin does not yet have a complete source-stable `/sessions*` route family. The workload-authenticated `refresh-roles` owner route is a separate non-redeeming operation. This remains explicit coverage drift; no external route is invented here.
- The static Gateway route catalog and bounded internal/actuator blockers provide partial edge-exposure enforcement.
- The YAML is normative for declared entries, but the current route inventory is incomplete. CI inventory generation, source-stable OpenAPI/protobuf coverage, YAML completeness comparison, matrix-aware shared middleware, strict token-profile enforcement, and exact proof for remaining broad Gateway route families are not implemented. Missing coverage is a recorded drift/gap; the canonical incomplete-inventory rule above remains the immediate runtime and CI/deployment safeguard.

## Token Profile Vocabulary

The current JWT profile names are `control-ui`, `player-bootstrap`, the one-use `gameplay-connect` handshake token, and receiver-specific private player-delegation profiles. `gameplay-connect` uses audience `gameplay-connect` and is consumed by Gateway rather than accepted as gameplay command authorization. Ordinary JWT registry middleware explicitly excludes `gameplay-connect`; this profile uses its dedicated Account issuance/replay record, signed `replayAdmissionFence`, and Gateway `jti` consume marker. The current private delegation profile is `game-session-account-delegation` with audience `account-service`. A generic backend JWT profile and the `internal` audience are forbidden. A privileged-control window is an authorization condition, not a JWT profile.

### Operator Idempotency and Receiving Boundaries

For a forwarded owner mutation, `controlPlaneRequestId` locates the candidate owner record but is not the complete idempotency proof. The owner compares the full idempotency tuple: normalized action family, schema identifier/version, typed scope, target, expected version, mutation, audit reason, every schema-bound presence/absence value, the applicable `authorityTuple`, separate `membershipVersion`, `issuanceFence`, immutable authority evidence, and the exact `mutationDigest` integrity value. `mutationDigest` is the canonical digest of the typed request fields; it is a member of the idempotency tuple and integrity check, not a replacement for that tuple. `membershipVersion` is compared separately and never substitutes for the `membershipAuthorityGeneration` member of `authorityTuple`. Any mismatch returns `IDEMPOTENCY_CONFLICT` without mutation, while an exact tuple replays the stored owner result.

The moderation policy-input/audit path is the sole receiving-boundary exception. `/moderation/actions` and `ApplyModerationAction` have no forwarded domain owner: Logging & Admin validates and redeems the Account authorization reference at its own receiving boundary before persistence. They do not require domain-owner redemption or enforcement; Game Session and Social & Groups separately consume the live `EvaluateModerationPolicy` read at their enforcement boundaries.

## Governance (Required)

- **Owner**: Platform Security + Account Service maintainers jointly own this matrix.
- **Machine-readable source**: `design/architecture/system-architecture-authz-route-matrix.yaml` is the normative source for declared entries; this Markdown file is the human-readable companion. It is not a complete route registry until the inventory gate below passes.
- **CI enforcement**:
  - Once source-stable OpenAPI/protobuf inventories cover the governed surfaces and validate in the same run, CI and deployment policy checks independently fail if a protected route is not present in the YAML matrix.
  - Fail if a route uses an unknown classification value.
  - Fail if a route is marked billing- or support-safe but lacks required redaction/authorization tests.
  - Once the source-stable inventory gate above passes, fail if the same-run generated route inventory (OpenAPI/proto) differs from the YAML matrix for auth/session and billing/subscription domains. Before that gate passes, record the difference as drift without treating the incomplete inventory as an enforceable registry.
- **Governance vocabulary**:
  - `route_status` is optional; when present, it must use one of the closed values declared by the YAML `route_status_vocabulary`: `current_openapi_operator_surface` for a route currently present and supported under its declared policy, including non-operator routes, or `target_not_currently_routable` for target-only coverage and present scaffolds whose supported path remains gated. The historical `current_openapi_operator_surface` value name does not limit current coverage to operator routes. An omitted value does not imply current or target routability.
  - `route_status_override` uses the closed `route_status_override_vocabulary`; `gate_wins_for_applies_to` gives `operator_mutation_support_gate.status` precedence for every matching `applies_to` route identity, so each such route must declare the same `route_status`. This precedence does not classify `live_exceptions` or identities recorded only in `coverage_drift`.
  - Authority-generation applicability uses the explicit `*_authority_generation_applies` fields, including `issuer_authority_generation_applies`, `account_authority_generation_applies`, `tenant_billing_authority_generation_applies`, and `membership_authority_generation_applies`. `pending_deletion_scoped` and `security_lock_export_scoped` routes must set issuer, account, tenant-billing, and membership authority-generation applicability explicitly to `false`; the non-registry-backed gameplay-connect exception explicitly sets issuer and account applicability to `false`.
  - Class-level `required_authority` is metadata describing authority types that may be required or supplied conditionally by a route or token. It is not an exact per-entry `required_live_checks` list. Route-level checks and explicit branch validators remain authoritative; public-production onboarding, account-scoped subject branches, and pending-deletion credentials retain their dedicated route-specific exceptions.
- **Default-deny behavior**:
  - The declared-entry `default_action: deny` is normative only for entries in the YAML; the canonical incomplete-inventory rule above governs routes absent from the validated inventory.
  - Runtime classification and CI/deployment inventory registration are separate gates; both follow the canonical incomplete-inventory rule above.
  - No route may default to `tenant_regular`, billing-safe, support-safe, or another executable class.
- **Change control**:
  - `billing_safe_tenant`, `cross_tenant_support_safe`, and `cross_tenant_billing_safe` changes require explicit security review approval.

### Critical Domains And Inventory Gate

The following domains become full-fail in CI only after source-stable OpenAPI/protobuf inventories cover them and the same run validates the comparison:

- Authentication/session admission routes (`LOGIN`/`PLAY` surfaces and equivalents).
- Billing-safe and support-safe routes.
- Subscription mutation and entitlement routes.

Before that gate passes, protected routes missing from the YAML matrix are recorded as drift/gap, including pre-existing routes; the canonical incomplete-inventory rule above applies until the validated candidate inventory is compared.

CI should generate candidate inventories from OpenAPI/proto definitions and compare them against the YAML matrix so protected-route drift is detected automatically.

Critical-domain inventory artifacts (required):

- CI must persist generated candidate inventories for auth/session and billing/support domains (OpenAPI + proto derived) under version control (for example `design/architecture/authz-inventory/*.json`).
- Full-fail assertions and generated default-deny policy in critical domains are valid only when these generated inventories are present, source-stable, and compared against the YAML matrix in the same run.
- Inventory generation must distinguish tenant-scoped and cross-tenant route variants explicitly; mixed-scope APIs must not be represented as a single ambiguous route key.

## Classification Rules

Strict issued-token-registry and applicable authority-generation middleware applies to protected control-plane operations and JWT-presenting bootstrap/admission operations. It does not blanket the dedicated `gameplay-connect` handshake: Gateway uses its one-use replay fence, quarantine cutoff, deny marker, and atomic exact-`jti` consume instead. Non-JWT in-band `LOGIN`, `PLAY`, fresh admission, reconnect, and resume use their exact bound-session, binding-fence, and current-authority contracts. Routine commands within an already-admitted gameplay binding use the validated bound context and bounded reconciliation instead of repeating registry or generation lookups; the binding remains valid only within its existing bounded lease and invalid or conflicting evidence still invalidates it.

| --- | --- | --- | --- |
| `public` | none | No | No JWT required |
| `account_scoped` | One matching token record for the exact profile declared by the route | No | Account-level control-plane routes with subject binding (`accountId == caller`), plus explicit route-level admin overrides. A `platformAdmin` exception is never inherited; it is present only on an entry that declares `platform_admin_override: platformAdmin_only`. Subject-bound `DeleteAccount` entries declare exactly two mutually exclusive `account_authorization_branches`: `self_service` binds the target to the caller and requires current account authority, while `platformAdmin_override` permits an explicit target account only with the live global role and role-appropriate assurance. The legacy `ExportAccount` surface is current drift and is superseded by the canonical POST export initiation route. |
| `caller_membership_scoped` | One matching token record for the exact profile declared by the route | No tenant authority generation; membership authority generation: Yes | Caller-bound lifecycle operations on the caller's own account-to-tenant membership. Any current membership role may act on itself; the route must perform a live subject-bound membership check and must not accept an arbitrary account target or global-role override |
| `player_bootstrap_tenant` | One matching `player-bootstrap` token record | No tenant authority generation by default; selected-tenant authority is a route-specific exception and must be declared explicitly | Player-bootstrap-authenticated routes targeting a tenant before gameplay socket auth is complete. `IssueConnectToken` consumes the live Account membership/entitlement contracts and the Game Session admission-pointer contract |
| `pre_tenant_discovery` | In-band gameplay commands may use the already-authenticated Game Session context without presenting a JWT; other routes require the exact token profile they declare | No | Authenticated discovery surfaces that run before a single `tenantId` is selected (for example `WORLDS`). A route using `game_session_authenticated_context` therefore declares `accepted_token_profiles: []`; this does not make the command anonymous. |
| `public_production_onboarding` | No JWT for in-band gameplay commands; otherwise the exact route-declared profile (`player-bootstrap` for Account bootstrap writes) | No tenant authority generation before join; membership authority generation applies after join | **Target:** discovery and explicit open-enrollment join for the default public production realm. The route class does not redefine those owner contracts, and a grant never replaces caller-bound membership. |

| `cross_tenant_billing_safe` | One matching token record for the exact profile declared by the route | No tenant or membership generation; Account-owned issuer/account authority and live global role still apply | Billing operations for global roles; the surviving authority is the current Account-owned global `billingAdmin` role and global token scope, plus the required `privileged_control` window for cross-tenant use |
| `cross_tenant_data_bearing` | One matching token record for the exact profile declared by the route | Yes when operation targets tenant-scoped data | Platform-admin-only data-bearing operations |

| `security_lock_export_scoped` | One Account-issued opaque `security-lock-export` credential from verified Account-owned security-lock recovery | None; no issuer, account, tenant, or membership generation applies | Credential-only exact `accountId` + `recoveryCaseId` binding, then exact export-job and route `actionFamily` binding. The route families are exactly `export_initiate`, `export_status`, and `export_content`; the export-operation comparison is action-family-specific: initiation creates and attaches exactly, status exact-matches, and content exact-matches a completed operation. Both `export_initiate` and `export_content` require `required_account_recovery_case_export_job_and_outcome`. Invalid, expired, or revoked credentials and credential/account/recovery binding mismatches map to `AUTH_SESSION_REVOKED`; export-operation/job binding mismatches are non-disclosing `PERMISSION_DENIED`; unavailable recovery/export authority maps to `AUTH_UNAVAILABLE`; changed export input maps to `IDEMPOTENCY_CONFLICT`. No ordinary, pending-deletion, support, login, billing, deletion, or gameplay fallback exists. |

`pending_deletion_scoped` is a separate workflow-credential path, not a JWT exception. A declared route in this class must use the exact Account workflow-registry lookup and reject a missing, expired, revoked, terminal, wrong-account, wrong-workflow, wrong-generation, wrong-action-family, or otherwise malformed credential as `AUTH_SESSION_REVOKED`; an unavailable credential registry or deletion-workflow authority is `AUTH_UNAVAILABLE`. The status, content, and settlement routes each declare their own exact action family and response/side-effect boundary. Login, bootstrap, connect-token issuance, tenant, purchase, and gameplay routes are outside this class. The dedicated public recovery routes may issue only another `pending-deletion-access` credential and must not upgrade it into normal authority; see the [pending-deletion JWT/access contract](./system-architecture-jwt-and-token-contracts.md#pending-deletion-access-credential).

`security_lock_export_scoped` is the separate Account-owned recovery export path for `security_locked` accounts. No reviewed issuance route is currently registered; coverage drift records that only verified recovery may issue the credential. Invalid, expired, or revoked credentials and credential/account/recovery binding mismatches return `AUTH_SESSION_REVOKED`; export-operation/job mismatches return non-disclosing `PERMISSION_DENIED`; action-family mismatches fail closed, and the credential cannot be reused as another authority. An unrelated target-tenant generation advance does not invalidate this no-target-tenant credential; it remains bound to the exact recovery case and export lifecycle.

### Route-Class Branches

The route-class defaults below are branch-specific. `omitted` is intentional: it means that authority is not an input to that branch, not that a caller may use cached or inferred evidence. `required` names the corresponding live generation check; `target_tenant_generation` is the global-role target fence and is not caller membership.

| Classification | Branch | Scope | Role | Issuer/account generation | Tenant generation | Membership generation | `privileged_control` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `account_scoped` | `platformAdmin` global | `account` | `platformAdmin` | required | omitted | omitted | required |
| `tenant_regular` | tenant role | `tenant` | Route-declared tenant role | required | `tenant_generation` required | required | not required |
| `tenant_regular` | `platformAdmin` global | `tenant` | `platformAdmin` | required | `target_tenant_generation` required | omitted | required |
| `cross_tenant_data_bearing` | `platformAdmin` global | `cross_tenant` | `platformAdmin` | required | `target_tenant_generation` required | omitted | required |
| `billing_safe_tenant` | `tenantAdmin` | `tenant` | `tenantAdmin` | required | omitted | required | not required |
| `cross_tenant_support_safe` | `support` global | `cross_tenant` | `support` | required | omitted | omitted | not required |
| `cross_tenant_support_safe` | `platformAdmin` global | `cross_tenant` | `platformAdmin` | required | omitted | omitted | required |
| `cross_tenant_billing_safe` | `billingAdmin` global | `cross_tenant` | `billingAdmin` | required | omitted | omitted | required |
| `cross_tenant_billing_safe` | `platformAdmin` global | `cross_tenant` | `platformAdmin` | required | omitted | omitted | required |

The `tenant_regular` tenant-role row represents the route-declared tenant roles rather than adding a role to every route; its operator variants are the concrete `tenantAdmin`/`moderator` entries in the YAML. `cross_tenant_data_bearing` is a target class with no currently declared executable route. Exact token profile/registry validation supplies the issuer and account authority for tenant-regular routes; the branch table does not authorize a new route or permit a route to omit its declared role checks.

`tenant_regular` branch selection is deterministic and has no tenant-role fallback after a global-role result. The evaluator first obtains fresh, well-formed current global-role evidence. If `platformAdmin_global` is present, only the explicitly route-allowlisted global branch is eligible; a route without that override, or a failed global-branch predicate, is denied even when a tenant role is also present. Only a conclusive `platformAdmin_global`-absent result permits evaluation of the tenant-role branch. Unavailable, stale, malformed, mismatched, or inconclusive global-role evidence denies the request without evaluating either branch.

### Gameplay Admission Applicability

The gameplay transport and the admission reason are separate dimensions. `gameplay-connect` is the one-use edge credential for the first-party WebSocket path; the trusted TCP Proxy bridge is an mTLS transport that does not consume that credential; and `PLAY` is the in-band Game Session admission decision after transport authentication. None of these transports creates membership or converts a selected UI target into authority.

| Admission mode | `gameplay-connect` | Trusted TCP Proxy bridge | `PLAY` and downstream admission |
| --- | --- | --- | --- |
| `public_production_onboarding` | Not applicable before explicit `JOIN`/`Join & Play`; after Account commits membership, the ordinary connect-token checks apply | May carry the post-join gameplay connection on its trusted mTLS listener; it does not authorize `JOIN` or replace Game Session membership checks | Requires the newly committed caller-bound membership, membership generation, `public_production_admission`, entitlements, pointer, routing, and binding checks; it never creates membership |
| `returning_membership` | Applies to an existing caller-bound member after discovery and current membership-generation validation | May carry the same returning-member admission when the trusted listener is used; transport trust does not replace membership or authority checks | Requires the existing caller-bound membership and current authority/entitlement/routing checks; no onboarding join is performed |
| `grant_backed_private_or_playtest` | Applies only after the applicable private/playtest grant, existing caller-bound membership, and current membership authority generation are validated | May carry the same grant-backed admission when the trusted listener is used; transport trust does not replace the required membership, membership-generation, or grant checks | Requires the applicable grant, existing caller-bound membership, current membership authority generation, current authority/entitlement/routing checks, and final binding checks. The grant never substitutes for membership; no grant-backed admission creates membership or uses the public onboarding `JOIN` path |

Route entries and client flows must state which admission mode they support. A route or transport being reachable does not make all three modes applicable, and a `gameplay-connect` token, proxy identity, or `PLAY` command is not by itself proof of the mode-specific membership or grant predicate.

`pending_deletion_scoped` has no target tenant and is therefore declared under `tenant_generation_policy.no_target_tenant_classifications`, not the closed tenant-target exception allowlist. It has a separate validator and rejection contract: Account validates the opaque `pending-deletion-access` credential against its server-side registry, binds the credential's `accountId` and deletion-workflow identity to the route target, and checks live pending-deletion state before allowing the declared action. Invalid, expired, revoked, binding-mismatched, or wrong-state credential/workflow evidence returns the established `AUTH_SESSION_REVOKED` outcome; unavailable credential registry or deletion-workflow authority returns retryable `AUTH_UNAVAILABLE`; neither outcome discloses account state. Cancellation revokes pending access before restoring normal authority generation; export and necessary billing settlement remain restricted to their declared response/action profiles. These routes never fall back to cached JWT, normal session allowlist, or gameplay context.

Any route that accepts more than one token profile must declare an `accepted_token_profile_audiences` YAML map that binds each accepted profile to its exact audience rather than using an implicit shared audience. When the accepted profiles do not share the same registered type and issuer, the route must additionally declare exact `accepted_token_profile_types` and `accepted_token_profile_issuers` maps; scalar predicates or implicit profile inference are not allowed. Each mapping must cover exactly the accepted profiles and must match the token-profile vocabulary.

The `account_generation` and `current_account_generation` live checks are deliberately distinct. `account_generation` is the captured Account authority generation carried in a private delegation tuple and compared by its receiving owner; `current_account_generation` is a live Account reread used while issuing or validating control-plane authority. They must not be consolidated unless those two evaluation points become the same contract. The `platformAdmin_override` branch of account-scoped subject-bound routes also retains the captured `issuer_generation` and `account_generation` fences; role and assurance checks do not replace those fences.

The `tenant_generation` and `target_tenant_generation` live checks are also deliberately distinct. `tenant_generation` is the caller-bound tenant generation captured by a tenant-scoped token or private delegation and compared for that caller's tenant authority. `target_tenant_generation` is the separately redeemed target-tenant freshness fence used by an allowed global-role operator branch that has no target membership. A route with both authorization branches declares the check required by each branch rather than treating the two names as interchangeable.

Internal-service routes must additionally declare their **service caller policy** in the machine-readable matrix:

- whether the route is callable only by specific service identities,
- whether an end-user issued-token record and scope authorization are still evaluated on behalf of a delegated subject, and
- which token profile/audience the caller must present.

Each `caller_policies` entry is one complete alternative. Alternatives are disjunctive, while the `caller` method identity, `mtls_identity` certificate identity, token state/profile, applicable authority generations, delegated context, and live checks inside one entry are conjunctive. A caller name is not sufficient without its exact certificate identity, and an mTLS identity is not sufficient without the method caller policy. When alternatives use different token states, generation-applicability fields belong inside each caller policy rather than at route level. The YAML `caller_policies_schema` makes these two identity fields and their conjunctive relation explicit without introducing a broader policy framework.

Without these fields, a route classification is incomplete for internal-only APIs.

Critical routes may also require explicit machine-readable fields for:

- `applicability` when multiple entries share one transport route or command; predicates must be explicit and mutually exclusive so classification is deterministic. Account export initiation, status, and content use the closed `account_state_vocabulary` (`active`, `security_locked`, `deactivated_pending_delete`) and the exhaustive, non-overlapping `account_export_applicability` rules; an unmatched state is denied.
- `character_operation` uses the closed `character_operation_vocabulary` values `existing_character_discovery` and `character_creation`.
- `selected_character_requirement` uses the closed `none` value for both existing-character discovery and character creation because neither operation requires a selected character.
- `membership_authority_generation_applies`, which may be `true`, `false`, or `conditional_by_operator_role`; the operator conditional form must declare `membership_authority_generation_condition.tenant_role: true` and `membership_authority_generation_condition.platformAdmin_global: false`. Gameplay admission declares its mode-specific membership-generation checks in `admission_mode_selection` rather than using a legacy conditional applicability value.
- `account_authority_generation_applies`, which must be a boolean when declared and is explicitly `false` for `pending_deletion_scoped` and `security_lock_export_scoped` recovery routes
- `tenant_billing_authority_generation_applies`
- `required_live_checks`, whose values must come from the closed YAML `required_live_check_vocabulary`, such as `membership`, `conditional_realm_access_grant`, `public_production_admission`, `membership_generation`, `runtime_entitlements`, `admission_pointer`, `connect_token_single_use_consume`, `replay_protection_available`, `replay_admission_fence_match`, `connect_scope_match`, and `account_state_export_eligible`. Gameplay `admission_mode_selection` uses the same explicit composition: its common `required_live_checks` are combined with only the selected mode branch, so returning-membership and grant-backed branches do not inherit `public_production_admission` or unconditional membership checks.
- `mutation_contract` for payment-instrument flows must require billing-owner authorization, explicit per-subscription binding, replacement-before-detach, and audited billing-ownership transfer; a shared-instrument acknowledgement is not an authorization substitute. The target-only `PaymentInstrumentWalletCrossTenant` entry must additionally bind `target_account_id`, `affected_subscription_ids`, `new_billing_owner_account_id`, replacement instrument bindings, expected subscription row versions, effective boundary, reason, and `control_plane_request_id`, and require issuer/account generation, current global role, privileged assurance, wallet-to-provider-customer mapping, explicit bindings, safe detachment, and a clear audited ownership-transfer state. When the owning payment-instrument route is not yet routable, the entry must mark this as target-only rather than claiming an implemented path
- `canonical_errors` that CI and contract tests must expect for route-specific security rejections
- `realm_grant_authority` and `realm_grant_version` when grant-gated access depends on Account-owned realm authority
- `canonical_target_route` when an entry records one canonical route string alongside known implementation drift; structured `canonical_target` mappings continue to record converged target semantics
- `implementation_status` when the current implementation is known not to satisfy that target

The validator contract separately requires structural parsing for repeated `required_fields` reads to be cached by source identity and field name before consumers use the result. Cache hits must reuse the validated result without re-emitting structural errors, matching the equivalent live-check cache contract; this is validator behavior rather than a route-entry field.

For first-party gameplay, `connection_mode: first_party_web` names the verified public non-proxy `gameplay-connect` path, not a browser-only client class. It covers every currently supported first-party protected-cookie client, including browser/mobile-browser clients and native or other non-browser Account clients using a protected cookie jar. It does not imply support for the target-only public non-browser header carrier. The `/ws/game/**` route declares `operation: websocket_upgrade`, while `POST /ws/game/connect-token/revoke` declares `operation: connect_token_cookie_revoke`; these applicability predicates remain mutually exclusive even though both use that connection mode.

Without these fields where applicable, a route entry is incomplete for governance and CI enforcement.

### Privileged Role Assurance

Global-role possession is not sufficient to enter a privileged control window. `EnterPrivilegedControlWindow` uses the separate `control_ui_plus_recent_reauthentication_and_independent_totp` auth path and its machine-readable `privileged_control: establishes_window` bootstrap exemption, so the route that creates elevation does not require an elevation window that does not yet exist. `platformAdmin` authority always requires the machine-readable `privileged_control` elevation contract; `billingAdmin` requires it when exercising cross-tenant authority. Support-safe `support` access requires a live support global-role check but no `privileged_control` window and is limited to `cross_tenant_support_safe` routes. Account Service creates the bounded server-side role-scoped state only after recent ordinary reauthentication and independent TOTP. The state is bound to the account, current `control-ui` token `jti`, account generation, requested global role, issue time, and expiry, and is invalidated by token revocation, generation change, role loss, or expiry. It is not a JWT profile or gameplay authority.

Route authorization never becomes in-game elevation. If a global-role account passes the ordinary caller-bound join and admission flow, gameplay presence, command, and actor-capability resolution ignore its global roles. Any moderator, administrator, game-master, or equivalent gameplay authority requires an explicit tenant-scoped gameplay grant; no route classification creates a support impersonation or hidden-observer session.

### Operator Delegation

Account Service is the operator-delegation authority. Human issuance enters through the exact allowlisted workload mTLS identity plus the forwarded `control-ui` token, then validates that token's `jti`, account generation, current tenant or global role, tenant/scope, action family, canonical mutation digest, and any role-required `privileged_control` window. Tenant-scoped `tenantAdmin` and `moderator` actions require live membership and role but not a fabricated global elevation. A global `platformAdmin` tenant operation instead binds the current target-tenant generation without inventing membership. Unattended issuance validates exact allowlisted mTLS workload identity plus a current versioned automation policy and the same mutation digest. The resulting opaque reference is bound either to the human token/account/role evidence or to the workload/policy evidence; automation never impersonates a user.

Logging and Admin records the operator intent and actor kind, then forwards the same reference unchanged with the exact typed action-family request, action-family schema identifier/version, same `control_plane_request_id`, canonical `mutationDigest/v1` digest, and every scope, target, expected-version, mutation, and audit-reason field declared by that schema. Only transport credentials and the authorization reference are excluded from the digest. The owner call is `internal_workload`: exact mTLS caller identity plus Account redemption/validation of the exact reference against that action family, schema pair, scope, request identity, and digest, followed by owner recomputation of the digest from every declared input and owner-side domain facts, fencing, and idempotency checks. Logging and Admin role, actor, or automation-policy assertions alone are never authority, and owner-side admission RPCs do not accept an end-user JWT.

The target operator route inventory includes feature-flag toggle, gated moderation action, admission pointer and version-upgrade writes, tick pause/resume, and the adjacent Game Session session lifecycle mutation surfaces. These rows are target authorization contracts; current external availability remains gated by action schemas, shared `mutationDigest/v1` vectors, Account authorization-reference issuance/redemption, and any target-only `privileged_control` window. Missing quota-override and versioned/broader moderation-propagation contracts remain recorded in the machine-readable coverage-drift inventory; no route is invented for either. Current runtime enforcement instead consumes Logging & Admin's synchronous policy evaluation at `GAMEPLAY_ADMISSION` and `CHAT_SEND`.

### Target Public Production Onboarding Example

1. A brand-new account performs public `WORLDS` discovery, then completes `LOGIN` and authenticated discovery.
2. Public `WORLDS` may list the world's default public production realm even though no tenant membership exists yet.
3. `REALMS <world>` returns that default public production realm plus any separately granted additional realms.
4. The player conditionally uses `JOIN <world>` or `Join & Play` when membership is missing or `INACTIVE`; Account atomically creates or restores membership and durable audit/outbox.
5. `CHARS` or allowed character creation is conditional on whether a valid selected character already exists. It requires the current membership generation, realm visibility/grant, entitlement, and admission pointer, but does not create a gameplay binding or perform `PLAY`'s final binding CAS.
6. Character creation, connect-token issuance, and `PLAY` require that membership and never create it implicitly; each consumes the same current catalog/pointer truth, while `PLAY` additionally performs its full gameplay-binding checks.
7. Global roles alone never bypass this flow or grant gameplay admission/connect-token issuance without the same live checks.
