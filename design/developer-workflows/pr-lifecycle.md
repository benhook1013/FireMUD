# Pull Request Lifecycle

Use this guide for pull-request status, review handling, CI, Renovate, merging, or branch/worktree cleanup.

## Review And Status

- CodeRabbit automatically performs the initial review when a qualifying PR opens; automatic incremental reviews are disabled. Use complete PR reviews for every hosted and CLI checkpoint. Request `@coderabbitai full review` for subsequent hosted checkpoints only after all current and outdated findings are resolved and no review is active or rate-limited. Partial coverage requires a concrete tool constraint adjudicated by the Overseer, or the main orchestrator when no Overseer is assigned, with exhaustive coverage preserved through coherent splits or justified partitions. An over-ceiling incremental hosted fallback also requires a trustworthy substantive checkpoint and verification of its selected commit and file range.
- CodeRabbit CLI reviews use a separate local-review quota. Before launching one, fetch the PR's remote base and pass its remote-tracking ref to `--base`; never use an unchecked local base branch, and verify the resulting file count against the live PR. Review the full stable candidate, including local fixes committed safely or captured in an isolated snapshot, with `coderabbit review --agent --committed --base <remote>/<base-ref>`; CLI findings are additional review evidence and do not replace GitHub review-thread, summary, or merge-gate checks. Do not install or invoke autonomous CodeRabbit skills that can consume review quota outside this deliberate workflow.
- Do not start a review against a base that is about to change. Once a hosted or CLI review has started, let it finish and consume any still-valid findings; cancelling it does not recover quota or evidence.
- Do not treat an unchanged HEAD or a previously reviewed range as evidence that another independent full-PR CLI pass would be redundant. Judge continuation by actual finding usefulness, significance, and remaining coverage, not by whether commits changed. Use local or subagent checks for fix-only deltas; an uncommitted-only CodeRabbit pass is not a substitute for a full candidate checkpoint. Publication of unchanged reviewed content does not itself justify another pass. CLI remains supplementary to hosted taper and merge-gate evidence, and is not a mandatory extra gate when further review has no justified value.
- At each checkpoint, select and report only proportionate validation/runtime-proof evidence using [Validation And Runtime Proof](./validation-and-runtime-proof.md); do not duplicate the validation ledger or already reported CI and review results.
- For "check PR", "check review", or merge-readiness, inspect unresolved non-outdated review threads and the latest completed CodeRabbit review summary before CI and mergeability. Paginate the complete `reviewThreads` connection beyond the first 100 lifetime threads before counting current or outdated unresolved threads; a first-page-only query is not a valid merge-readiness result. Verify summary-only duplicate and outside-diff findings even when they have no unresolved thread. Report current and outdated unresolved counts separately; current threads remain authoritative for inline conversation state, not the complete finding inventory.
- Before calling a PR review-complete or merge-ready, run `python3 dev-tools/validation/check-coderabbit-review.py --repo <owner/repo> --pr <number>` and reconcile its live current and outdated thread counts and explicit-review/coverage verdict with the actual changes. If it reports missing final-head explicit review after a direct, verified correction, preserve that limitation in the evidence and manually verify that every post-review commit directly addresses findings, the correction adds no functionality or independently reviewable behavior, and required CI and proof are green; this narrow exception does not waive substantive review for material changes.
- Resolve a CodeRabbit thread only after verifying its exact finding is fixed in `HEAD`. Do not resolve threads to hide open work, request a review while one is active or rate-limited, or request a review solely to self-resolve already-fixed feedback.

## Review Orchestration

- Within a lane or stack, target hosted and CLI review at the same active, next-to-merge PR. Pending hosted review or CI does not justify reviewing a successor. Use CLI only for a useful checkpoint on that target; otherwise continue authorized fixes, preparation, or proof without spending quota on another PR in that stack. Advance the target after merge readiness under existing stack rules, or explicit reprioritization. Let already-running off-target reviews finish and consume their findings before realigning.
- When hosted or CLI CodeRabbit capacity is contested across persistent user-owned lanes, the Overseer designates one priority PR based on which lane most directly advances the user's next usable outcome, using proximity to merge-ready and unblocking value; a foundation or documentation lane may take priority for a concrete dependency or shared blocker. Concentrate that channel's review opportunities on the priority PR until it is merge-ready. Let active reviews finish. Do not reserve unused quota or blanket-pause the other lane: it continues useful authorized work and may use an opportunity the priority lane cannot use. Priority ends at merge-ready, before human merge; reassess only for a real non-review blocker or substantial scope expansion, not after every review round. If no useful authorized work remains, use the existing watcher guidance and do not poll peer tasks for status.
- Run at most one CodeRabbit CLI review at a time, alongside hosted review on the same primary PR when useful. After fixing useful findings, continue with a full candidate CLI pass once edits are stable; this is part of the assignment, not a new permission boundary. Consume completed hosted findings before subsequent checkpoints. The orchestrator can launch CLI directly without a free helper slot. Pause for actual quota exhaustion, an active CLI pass, unstable overlapping edits, or evidenced low utility—not merely unchanged HEAD, pending hosted review, unavailable helpers, or unfinished broader validation. Stop when further CLI review is no longer useful; hosted findings still determine taper.
- Treat CI and hosted review as asynchronous. Continue safe work that will not invalidate the active review; when no such work exists, report the concrete wait or blocker and actual continuation owner and mechanism, then yield rather than repeatedly polling or inventing unrelated work. Use existing watchers or waiters without inventing recurring schedules or guaranteed wakeups. An explicit pause or stop still means finish only the stated in-progress boundary, publish any promised safe checkpoint, and do not begin substitute work; later explicit resumption supersedes an earlier pause or stop for that scope.
- Do not push review-invalidating commits while hosted review is active. Prepare fixes locally, consume the completed hosted output, then publish one combined fix batch.
- After all known findings are fixed and pushed, the main orchestrator may request the next hosted full review when justified by the [Review Completion Criteria](#review-completion-criteria), no review is active, and the rate limit is free. Verify the resulting summary because a request may be skipped, fail internally, or be rate-limited.
- After each review/fix run, report hosted and per-CLI finding counts, their practical significance, whether another review cycle is recommended, and a concise summary of subagent use. This evidence, rather than quota availability alone, determines whether review should continue.
- Full-PR CodeRabbit CLI review/fix checkpoint recording is canonical per run: the owning lane posts one concise PR comment with reviewed SHA, actual base SHA/ref, coverage and file count, raw/accepted/rejected counts, and fix status/ref or local status. Distinguish repeat rounds on one SHA with a timestamp or run label and avoid duplicate comments for one run; a summary may post before all fixes finish. Save raw CLI output only in ignored/private artifacts, with no parallel disposition or hosted ledger and no routine historical backfill. Post exact real Markdown through a body file or stdin.
- PR reporting reads existing hosted summaries/threads and CLI checkpoint comments, orders PRs by intended merge priority, and gives chronological `(R/A) hosted, R/A CLI` counts (`R` raw, `A` accepted), with fix status separate from counts. Preserve significance, limitations, and missing or partial evidence; exclude failed or rate-limited attempts while counting completed zero-finding rounds. Ask the owner only for material missing, ambiguous, or current evidence, not routine transcript reconstruction. Reporting does not authorize reviews, CI mutations, resuming paused tasks, or merges.

## Review Completion Criteria

- Define a coherent capability or correction scope and obtain an initial substantive CodeRabbit review covering feature-bearing work and changed contracts.
- Resolve every known actionable finding, including current and outdated threads and summary-only or outside-diff findings, and verify each fix at the current head. Useful in-scope corrections to correctness, completeness, authority, or alignment remain actionable regardless of line size; do not relabel them optional merely to finish.
- Re-review new functionality, changed contracts, materially broader risk, or fixes that introduce independently reviewable behavior. Direct, verified corrections need not trigger another whole-PR discovery round solely to accumulate clean results.
- Request an additional discovery round only when the main orchestrator identifies a concrete unresolved risk or coverage/proof gap. Repeated serious findings should trigger focused investigation of their shared failure mechanism and appropriate proof rather than an arbitrary number of broad clean rounds. There is no fixed clean-review streak; neither elapsed time nor review quota availability alone justifies closure or another round.
- A PR is ready to present for human merge only after the checker evidence shows zero unresolved current threads and zero unresolved outdated threads, all actionable summary-only and outside-diff findings are addressed, each fix is verified, the checker evidence is reconciled with the actual changes, required CI is green, and required proportionate validation/runtime proof is complete. Zero threads or a GitHub `CLEAN` result alone is insufficient, and the final head must not be described as reviewed when it was not. Report readiness and leave the PR open for the human to merge. AI workers never execute a PR merge and never enable or schedule auto-merge; the human performs merge clicking.

## Change And Merge Policy

- Keep PRs coherent, normally one medium-sized slice of roughly 800-2,000 changed lines including adjacent convergence. Use smaller PRs for isolated fixes; split independent or genuinely hard-to-review work, and split coherent work that exceeds a reviewer ceiling under the following rules.
- Before requesting CodeRabbit, keep the reviewer-selected file count comfortably below the active plan ceiling rather than targeting the exact limit. Review findings define correctness work, not optional scope: accepted useful findings remain implementation obligations in their canonical code, documentation, or proof owner. The ceiling may change branch topology or review boundaries, but never correctness, cleanliness, or which live issues are fixed; do not offset growth by dropping useful scope, packing unrelated helpers or tests into already-counted files, moving authority to a noncanonical owner, or changing runtime or design semantics.
- Treat reviewer ceilings as dynamic topology constraints. Do not target a hardcoded file count or preserve an arbitrary majority merely to stay under a cap. If the correct implementation exceeds the active ceiling, default to a coherent stack that preserves every finding and its proof; consolidate only when independently justified by cohesion and authority. Use a scoped-review or CLI path only as an Overseer-adjudicated fallback when the change genuinely has no clean split or preserving the review boundary requires it. The ceiling changes review topology, never correctness or cleanliness.
- When a finding or proof moves to another PR in a coherent split, update the existing PR body and review disposition with an explicit successor landing reference and check whether downstream already fixes it; do not create a new ledger.
- The human's selection of an active workstream provides standing authorization for coherent PR splits and routine scope-safe topology changes within that workstream, so a clean split needs no fresh approval. Continue those changes without repeated approval while preserving current work and review evidence. Pause the topology decision and ask the Overseer with a concrete cut whenever clean split, ownership, or preservation is materially uncertain, the split introduces new product or architecture ambiguity or a consequential scope or topology decision, or the action falls outside the authorization; independent safe work continues where possible. During an active review, prepare review-invalidating fixes locally and wait for the review to finish before publishing them.
- Treat failing Renovate PRs as maintenance work: inspect CI and push the smallest compatible fix to its branch when possible; otherwise use a replacement branch with required compatibility changes.

## Branch And PR Hygiene

- Open or update a PR autonomously when an implementation branch reaches a coherent review checkpoint. Stacked PRs are acceptable when their base dependencies are explicit and they let independent work continue while CI or review runs. If the next authorized work is unambiguous and can be cleanly based on a merge-ready PR, continue autonomously in a stacked PR; a draft PR may expose in-progress work and should be marked ready at a coherent review checkpoint. After the parent human merge, retarget the child to `develop` before rebasing or pushing. An explicit pause, unresolved human decision, or dependency requiring merged state stops continuation; do not create tiny placeholder PRs without review-worthy content.
- When active work moves to another worktree, report its absolute path and branch so the human's IDE context and delegated-worker paths remain aligned.
- When retargeting a stacked PR after its parent merges, change the base before rebasing or pushing the child. Required workflows listen for GitHub's `edited` event but run replacement gates only when `changes.base.ref` is present; title/body edits use a separate metadata-only concurrency group and neither cancel an active required gate run nor start replacement jobs.
- For recurring branch, worktree, and PR inventory, use `dev-tools/validation/report-worktree-pr-topology.sh` rather than ad hoc status commands.
- After a merge, remove its defunct local worktree and merged local/remote branch only after confirming no open PR or active stacked branch depends on it. Preserve unmerged branches and worktrees.
- Pass PR-body Markdown through a file or stdin with real newlines rather than literal `\\n` strings.
