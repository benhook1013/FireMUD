# Pull Request Lifecycle

Use this guide for pull-request status, review handling, CI, Renovate, merging, or branch/worktree cleanup.

## Review And Status

- CodeRabbit automatically performs the initial review when a qualifying PR opens; automatic incremental reviews are disabled. Use complete PR reviews for every hosted and CLI checkpoint. Request `@coderabbitai full review` for subsequent hosted checkpoints only after all current and outdated findings are resolved and no review is active or rate-limited. Partial coverage requires a concrete tool constraint adjudicated by the Overseer, or the main orchestrator when no Overseer is assigned, with exhaustive coverage preserved through coherent splits or justified partitions. An over-ceiling incremental hosted fallback also requires a trustworthy substantive checkpoint and verification of its selected commit and file range.
- CodeRabbit CLI reviews use a separate local-review quota. Run `./dev-tools/run-coderabbit-review.sh <pr-number> [--repo <owner/name>]` for a full candidate checkpoint. The wrapper reads the recorded PR base and head, validates the published scope against that immutable base snapshot, resolves the latest named base tip, derives and pins the unique candidate/base merge base, verifies that the current committed HEAD is the published head or a descendant containing local fixes, and runs the candidate in an isolated temporary worktree. It invokes `coderabbit review --agent --committed --base <pinned-candidate-base-ref>` without arbitrary passthrough or partial fallback; dirty source edits remain untouched and are excluded until committed. CLI findings are additional review evidence and do not replace GitHub review-thread, summary, or merge-gate checks. Do not install or invoke autonomous CodeRabbit skills that can consume review quota outside this deliberate workflow.
- Do not start a review against a base that is about to change. Once a hosted or CLI review has started, let it finish and consume any still-valid findings; cancelling it does not recover quota or evidence.
- Do not treat an unchanged HEAD or a previously reviewed range as evidence that another independent full-PR CLI pass would be redundant. Judge continuation by actual finding usefulness, significance, and remaining coverage, not by whether commits changed. Use diff inspection and focused tests for fix-only deltas; additional model-based fix review follows [AI delegation and review](./ai-delegation-and-review.md#independent-review-evidence). An uncommitted-only CodeRabbit pass is not a substitute for a full candidate checkpoint. Publication of unchanged reviewed content does not itself justify another pass. Assess taper from the combined sequence of complete Hosted and CLI reviews, considering accepted finding usefulness and significance, trends across rounds, and material changes after review; low counts in one channel do not establish taper while the other keeps exposing material issues.
- At each checkpoint, select and report only proportionate validation/runtime-proof evidence using [Validation And Runtime Proof](./validation-and-runtime-proof.md); do not duplicate the validation ledger or already reported CI and review results.
- For "check PR", "check review", or merge-readiness, inspect unresolved non-outdated review threads and the latest completed CodeRabbit review summary before CI and mergeability. Paginate the complete `reviewThreads` connection beyond the first 100 lifetime threads before counting current or outdated unresolved threads; a first-page-only query is not a valid merge-readiness result. Verify summary-only duplicate and outside-diff findings even when they have no unresolved thread. Report current and outdated unresolved counts separately; current threads remain authoritative for inline conversation state, not the complete finding inventory.
- Before calling a PR review-complete or merge-ready, run `python3 dev-tools/validation/check-coderabbit-review.py --repo <owner/repo> --pr <number>` and reconcile its live current and outdated thread counts and explicit-review/coverage verdict with the actual changes. If it reports missing final-head explicit review after a direct, verified correction, preserve that limitation in the evidence and manually verify that every post-review commit directly addresses findings, the correction adds no functionality or independently reviewable behavior, and required CI and proof are green; this narrow exception does not waive substantive review for material changes.
- Correlate a direct CodeRabbit bot reply with its review request. Use included quota only; never enable billing or paid reviews. An explicit failure or `Review rate limited` response overrides a generic `Full review triggered` acknowledgement, stale pending state, and billing-eligibility boilerplate: that request is not an active review and creates no publication hold. For rate limits, wait until the stated included-quota reset, retry, and verify the actual response. Preserve publication holds for genuinely active reviews.
- Resolve a CodeRabbit thread only after verifying its exact finding is fixed in `HEAD`. Do not resolve threads to hide open work, request a review while one is active or rate-limited, or request a review solely to self-resolve already-fixed feedback.

## Review Orchestration

- Within a lane or stack, target hosted and CLI review at the same active, next-to-merge PR. Pending hosted review or CI does not justify reviewing a successor. Use CLI only for a useful checkpoint on that target; otherwise continue authorized fixes, preparation, or proof without spending quota on another PR in that stack. After useful CLI findings are consumed and a full candidate is stable, another justified full CLI run may start immediately. Do not invent 20-minute spacing, wait on hosted review, or schedule forced reviews after low utility. Advance the target after merge readiness under existing stack rules, or explicit reprioritization. Let already-running off-target reviews finish and consume their findings before realigning.
- When hosted or CLI CodeRabbit capacity is contested across persistent user-owned lanes, the Overseer designates one priority PR based on which lane most directly advances the user's next usable outcome, using proximity to merge-ready and unblocking value; a foundation or documentation lane may take priority for a concrete dependency or shared blocker. Concentrate that channel's review opportunities on the priority PR until it is merge-ready. Let active reviews finish. Do not reserve unused quota or blanket-pause the other lane: it continues useful authorized work and may use an opportunity the priority lane cannot use. Priority ends at merge-ready, before human merge; reassess only for a real non-review blocker or substantial scope expansion, not after every review round. If no useful authorized work remains, use the existing watcher guidance and do not poll peer tasks for status.
- Run at most one CodeRabbit CLI review at a time, alongside hosted review on the same primary PR when useful. The wrapper launches one review immediately after local preflight and rejects a concurrent CLI pass. Pending hosted review or CI does not block the local checkpoint. After fixing useful findings, continue with a full candidate CLI pass once edits are stable; this is part of the assignment, not a new permission boundary. Consume completed hosted findings before subsequent checkpoints. The orchestrator can launch CLI directly without a free helper slot. Pause for actual quota exhaustion, an active CLI pass, unstable overlapping edits, or evidenced low utility—not merely unchanged HEAD, unavailable helpers, or unfinished broader validation. Stop when further review is no longer useful based on the combined Hosted and CLI sequence.
- Treat CI and hosted review as asynchronous. Continue safe work that will not invalidate the active review; when no such work exists, report the concrete wait or blocker and actual continuation owner and mechanism, then yield rather than repeatedly polling or inventing unrelated work. Use existing watchers or waiters without inventing recurring schedules or guaranteed wakeups. An explicit pause or stop still means finish only the stated in-progress boundary, publish any promised safe checkpoint, and do not begin substitute work; later explicit resumption supersedes an earlier pause or stop for that scope.
- Do not push review-invalidating commits while hosted review is active. Prepare fixes locally, consume the completed hosted output, then publish one combined fix batch.
- After all known findings are fixed and pushed, the main orchestrator may request the next hosted full review when justified by the [Review Completion Criteria](#review-completion-criteria), no review is active, and the rate limit is free. Verify the resulting summary because a request may be skipped, fail internally, or be rate-limited.
- After each review/fix run, report hosted and per-CLI finding counts, their practical significance, whether another review cycle is recommended, and a concise summary of subagent use. This evidence, rather than quota availability alone, determines whether review should continue.
- The Overseer inspects saved decisions after roughly 10 newly completed full Hosted+CLI rounds combined and checks remaining new rounds before merge. Focus on rejected or deferred potentially useful findings and sample accepted findings for significance, using reporter/private evidence. The reviewing lane sends one brief nonblocking Overseer wakeup at that threshold, identifying the PR and last-audited/current checkpoints from existing review records; continue work without waiting and do not send per-round updates or repeat reminders for a pending audit. The Overseer records the last inspected checkpoint in existing private notes and returns it with the assessment so the lane can identify the next window. Do not routinely reread transcripts or code, repeat assessed windows, launch audit agents, create another ledger or scheduler, or trigger CodeRabbit reviews solely for this. Owners escalate consequential gaps normally. This is lightweight judgment, not a fixed audit quota or perfect-zero gate.
- Full-PR CodeRabbit CLI and hosted checkpoint recording is canonical per adjudicated run: the owning lane posts exactly one PR comment with a single-line visible checkpoint containing the actual review type, raw and accepted counts, abbreviated reviewed commit, and actual reviewed file count, for example **Hosted: 5 found / 3 accepted** · `2a26006` · 88 files or **CLI: 5 found / 3 accepted** · `2a26006` · 88 files. GitHub comment timestamps distinguish separate comments; do not add an explicit timestamp or visible run label. Hosted bot summaries are raw evidence; the owner comment supplies the accepted count. A wrapper-backed CLI checkpoint must add `<!-- firemud-cli-run: run.NAME -->` on the following line, copied from the wrapper's `checkpoint_marker` output, to link the comment to its private local capture; direct Hosted capture uses the actual completed GitHub review ID independently of an owner checkpoint, while a Hosted checkpoint may add `<!-- firemud-hosted-review: REVIEW_ID -->` as an association. The Hosted review ID and saved raw review are authoritative, and a missing marker remains explicit missing linkage without an invented capture. The comment records review results once and contains no later fix or publication status. Do not batch rounds or wait for fix publication or a consolidated push, and hosted code-publication restrictions do not block the comment. Post exact real Markdown through a body file or stdin.
- Keep raw CLI output in ignored/private run artifacts. Future `decisions.tsv` rows use `finding ID<TAB>accepted|rejected<TAB>reason`; CLI IDs are 1-based finding ordinals and Hosted IDs are actual inline comment IDs. Accepted reasons may be empty; rejected decisions require one concrete sentence. Existing `rejections.tsv` rows remain supported only when no decisions file exists: three-column ordinal rows join exactly, while legacy two-column `path:line<TAB>reason` rows are displayed separately and never joined by inference. Missing decisions are reported as unknown, not accepted or rejected; these are saved adjudication records, not a separate ledger or report. Do not add routine historical backfill or per-round Overseer notifications.
- PR reporting reads existing hosted summaries/threads, hosted adjudication comments, and CLI checkpoint comments, orders PRs by intended merge priority, and gives chronological `(R/A) hosted, R/A CLI` counts (`R` raw, `A` accepted), with fix status separate from counts. Use `python3 dev-tools/validation/report-pr-review-checkpoints.py --repo <owner/repo> --pr <number>` to retrieve all paginated checkpoint comments before selecting the recent history; use `--json` when a report needs structured values. The overview includes comment IDs and warns when CLI checkpoints lack linkage markers. Use `--details <comment-id>` to validate linked local CLI or Hosted evidence; `--hosted [<review-id>]` fetches the actual completed CodeRabbit review by its numeric GitHub review ID and retains raw summary plus main inline findings, with summary-only items not normalized. Use `--rounds N --source cli|hosted --disposition all|accepted|rejected` for the latest source rounds, selecting rounds before filtering so missing or invalid evidence remains visible; `--rejections N` is rejected-only CLI shorthand. Missing linkage is explicit no-linked-data evidence, and unknown decisions or legacy rejection references remain separate from findings. Hosted and CLI records may share a SHA but remain distinct reviews. The helper records comment `created_at` as posted time and exposes changed `updated_at` separately; these timestamps do not establish review completion. Use Pacific/Auckland dates and NZST/NZDT for human-facing review times; distinguish actual review time from late posting when relevant, and never invent times. Preserve significance, limitations, and missing or partial evidence; exclude failed or rate-limited attempts while counting completed zero-finding rounds. Ask the owner only for material missing, ambiguous, or current evidence, not routine transcript reconstruction. Reporting does not authorize reviews, CI mutations, resuming paused tasks, or merges.

## Review Completion Criteria

- Define a coherent capability or correction scope and obtain an initial substantive CodeRabbit review covering feature-bearing work and changed contracts.
- Resolve every known actionable finding, including current and outdated threads and summary-only or outside-diff findings, and verify each fix at the current head. Useful in-scope corrections to correctness, completeness, authority, alignment, maintainability, consolidation, or clarity remain actionable regardless of line size; judge worthwhile suggestions by their actual benefit against implementation cost and risk, including when they address neither a bug nor an existing design requirement, and do not relabel them optional merely to finish.
- Re-review new functionality, changed contracts, materially broader risk, or fixes that introduce independently reviewable behavior. Direct, verified corrections need not trigger another whole-PR discovery round solely to accumulate clean results.
- Request an additional discovery round only when the main orchestrator identifies a concrete unresolved risk or coverage/proof gap. Repeated serious findings should trigger focused investigation of their shared failure mechanism and appropriate proof rather than an arbitrary number of broad clean rounds. Assess taper from the combined sequence of complete Hosted and CLI reviews, considering accepted finding usefulness and significance, trends across rounds, and material changes after review. There is no fixed zero-finding streak; neither low counts in one channel, elapsed time, nor review quota availability alone justifies closure or another round.
- A PR is ready to present for human merge only after the checker evidence shows zero unresolved current threads and zero unresolved outdated threads, all actionable summary-only and outside-diff findings are addressed, each fix is verified, the checker evidence is reconciled with the actual changes, required CI is green, and required proportionate validation/runtime proof is complete. Before that merge-readiness handoff, refresh stale PR title/body content so the title and body describe the final implemented scope and behavior, current stack/base/dependencies, and relevant validation/limitations; this is a handoff check, not a requirement on every push. At initial PR publication, insert the generated marked LOC section into the PR body; during the final merge-readiness handoff, refresh that section. Do not regenerate it for every fix round or push. Generate and write it with `python3 dev-tools/maintenance/cloc-report.py pr <number> [--repo owner/name] --update-pr`; the command replaces only its marked body section after guarding against revision drift. The section is informational and is not a size gate or a reason to reject useful changes. If `gh` or `cloc` is unavailable, record that limitation instead of inventing counts. Zero threads or a GitHub `CLEAN` result alone is insufficient, and the final head must not be described as reviewed when it was not. Report readiness and leave the PR open for the human to merge. AI workers never execute a PR merge and never enable or schedule auto-merge; the human performs merge clicking.

## Change And Merge Policy

- Keep PRs coherent, normally one medium-sized slice of roughly 800-2,000 changed lines including adjacent convergence. Use smaller PRs for isolated fixes; split independent or genuinely hard-to-review work, and split coherent work that exceeds a reviewer ceiling under the following rules.
- Before requesting CodeRabbit, keep the reviewer-selected file count comfortably below the active plan ceiling rather than targeting the exact limit. Useful review findings define required improvements, not optional scope: accepted useful findings remain implementation obligations in their canonical code, documentation, or proof owner. The ceiling may change branch topology or review boundaries, but never correctness, cleanliness, or which live issues are fixed; do not offset growth by dropping useful scope, packing unrelated helpers or tests into already-counted files, moving authority to a noncanonical owner, or changing runtime or design semantics.
- Treat reviewer ceilings as dynamic topology constraints. Prefer the fewest coherent, independently sound reviewable PRs that preserve every accepted finding and canonical placement under the cap; additional PRs add separate review, taper, and reconciliation costs, so narrowness or neat separation alone is insufficient. If the correct implementation exceeds the active ceiling, default to a coherent stack that preserves every finding and its proof; consolidate only when independently justified by cohesion and authority, without forcing unrelated work together. Do not target a hardcoded file count or preserve an arbitrary majority merely to stay under a cap. Use a scoped-review or CLI path only as an Overseer-adjudicated fallback when the change genuinely has no clean split or preserving the review boundary requires it. The ceiling changes review topology, never correctness or cleanliness.
- When a finding or proof moves to another PR, update its existing PR body and review disposition with the successor reference and check whether downstream already fixes it. After a split or reconstruction materially changes a reused PR's review scope, post one short comment such as **Review scope changed:** validator cleanup moved to #2731. Earlier counts cover the previous scope. Add `<!-- firemud-review-scope-change -->` below it so the checkpoint report can place the timestamped event in its timeline; earlier evidence remains relevant to the previous patch boundary, and still-applicable findings remain obligations, while the event does not by itself require a fresh review streak or imply increased risk. An ordinary post-merge retarget with equivalent scope needs no reset comment. Do not create a new ledger.
- With an explicit Overseer arrangement, local isolated preparation of a concrete topology proposal may proceed, but publishing a split, new prerequisite or successor PR, or retargeting an existing PR requires Overseer approval, including routine cap cases. An approved proposal covers its planned routine retargets and publication without repeated approval and does not add a separate human approval requirement. Without an explicit Overseer arrangement, the human's selection of an active workstream provides standing authorization for routine, straightforward, scope-safe topology changes within that workstream, including cap splits, so those changes need no fresh approval. Continue them without repeated approval while preserving current work and review evidence. If proposing a materially more fragmented topology than a straightforward split (such as extra review stages), bring the Overseer a concise comparison of proposed scopes/dependencies and base-relative file counts, why the simpler topology does not work, and the benefit versus extra review cost; the Overseer adjudicates that consequential choice while safe independent work continues. Pause the topology decision and ask the Overseer with a concrete cut whenever clean split, ownership, or preservation is materially uncertain, the split introduces new product or architecture ambiguity or a consequential scope or topology decision, or the action falls outside the authorization; independent safe work continues where possible. During an active review, prepare review-invalidating fixes locally and wait for the review to finish before publishing them.
- Treat failing Renovate PRs as maintenance work: inspect CI and push the smallest compatible fix to its branch when possible; otherwise use a replacement branch with required compatibility changes.

## Branch And PR Hygiene

- Open or update a PR autonomously when an implementation branch reaches a coherent review checkpoint, subject to the topology and approval rules in [Change And Merge Policy](#change-and-merge-policy). Stacked PRs are acceptable when their base dependencies are explicit and they let independent work continue while CI or review runs. If the next authorized work is unambiguous and can be cleanly based on a merge-ready PR, continue autonomously in a stacked PR subject to those rules; a draft PR may expose in-progress work and should be marked ready at a coherent review checkpoint. After the parent human merge, retarget the child to `develop` subject to those rules before rebasing or pushing. An explicit pause, unresolved human decision, or dependency requiring merged state stops continuation; do not create tiny placeholder PRs without review-worthy content.
- When active work moves to another worktree, report its absolute path and branch so the human's IDE context and delegated-worker paths remain aligned.
- When retargeting a stacked PR after its parent merges, change the base before rebasing or pushing the child. Required workflows listen for GitHub's `edited` event but run replacement gates only when `changes.base.ref` is present; title/body edits use a separate metadata-only concurrency group and neither cancel an active required gate run nor start replacement jobs.
- For recurring branch, worktree, and PR inventory, use `dev-tools/validation/report-worktree-pr-topology.sh` rather than ad hoc status commands.
- After a merge, remove its defunct local worktree and merged local/remote branch only after confirming no open PR or active stacked branch depends on it. Preserve unmerged branches and worktrees.
- Pass PR-body Markdown through a file or stdin with real newlines rather than literal `\\n` strings.
