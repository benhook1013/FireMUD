# Pull Request Lifecycle

Use this guide for pull-request status, review handling, CI, Renovate, merging, or branch/worktree cleanup.

## Review And Status

**Review policy:** Follow the configured queue. Hosted and CLI advance independently, with at most one active request per channel. Count completed, attributable results per PR and channel across heads: one zero-useful Hosted result or three consecutive zero-useful CLI results complete normal taper. An accepted finding owned by that PR breaks its channel's streak and must be fixed; a routed finding does neither. Explicit human stops and min/max extra-review decisions govern their own PR and channel. Head, parent, and patch identity describe a review and may protect a new request; they never reset taper or invalidate a human stop. Use eligible Hosted windows promptly. Merge readiness still requires accepted fixes, clear threads, and required CI.

- CodeRabbit automatic reviews are disabled. The sole operator interface is `dev-tools/pr-review`: configure the one repository review stack with `stack set <ordered PR numbers...>`, inspect it with `stack show`, inspect live state with `status [--pr <number>]`, and inspect historical/private evidence with `evidence [<number>]`. Before explicit SQLite cutover, the locked, atomically replaced, versioned JSON state lives at `<git-common-dir>/firemud/pr-review-stack.json`; after cutover, its sibling `pr-review-stack.sqlite3` is authoritative. The state persists only stack configuration, exact policy overrides, explicit judgments (including summary-only finding dispositions), reconciliation decisions, legacy evidence transitions, and review allocations. Heads, bases, merge state, cooldowns, threads, checks, and evidence are derived live.
- Live shared JSON-to-SQLite cutover waits until the merged, version-matched `dev-tools/pr-review` is installed and selected; verify its `--version` before proceeding. The explicit migration atomically exchanges the JSON path for a marked SQLite cutover directory and retains the source JSON, fencing old JSON readers and writers. Existing controller-era routes remain readable through `routes` and `status`; the review-record schema exposes provider and subagent attempts, findings, decisions, routes, and archived provider evidence. History and route queries read SQLite. After both this state-directory cutover and review-record schema bootstrap or migration are complete, new CLI and Hosted attempts record automatically; scheduled `records sync-hosted` completes posted Hosted attempts without requesting a review. CLI SQLite adjudication uses `records cli-decision` and `records source finalize` after those prerequisites. Before then, retain each new CLI capture's `decisions.tsv` and open routed observations with `decide route open`. Historical captures use the exceptional exact-checkpoint repair path and retain explicit missing-evidence labels. Source records never change Hosted/CLI taper, which remains governed by the public attributable checkpoints and explicit policy decisions. Backup/restore runs separately from review commands. See [PR-review SQLite operations](../../dev-tools/pr_review/README.md); this guidance does not mean live schema promotion or historical comparison has occurred.
- Run complete reviews only through `dev-tools/pr-review run hosted|cli [--expect-pr <number>] [--force [--reason "<optional context>"]]`. The controller derives the permitted target; `--expect-pr` is an assertion that fails before quota or review mutation if it differs. `--force` acknowledges a known candidate-quality warning such as parent movement or stale reconciliation identity, and records the warning with the attempt; `--reason` adds optional context. Forced review anchors bind the actual provider base, head, merge base, and patch identity; the configured queue parent remains separate context. The command still requires an open, identifiable PR and exact committed candidate, rechecks identity during admission, and enforces provider file ceilings and quota, active-request exclusion, channel caps, and accepted-finding obligations. It cannot reopen a completed or stopped channel. A completed provider result counts normally for that PR and channel regardless of force or reviewed head. Failures, rate limits, and incomplete provider results do not count. Each channel targets the earliest eligible PR whose policy is incomplete, skipping a PR with completed channel taper, a verified legacy handoff, or an explicit human stop recorded for that channel. A Hosted rate limit never advances Hosted.
- If a human has already posted a full Hosted command outside the controller, do not post a duplicate. After its public CodeRabbit result completes, use `decide trigger-adopt-manual --pr <number> --trigger-id <GitHub comment ID> --head <reviewed SHA>` with the version-matched entrypoint. The command verifies the unique public trigger/result and exact reviewed identity before recording attribution; for an off-queue PR, its live base branch and matching remote base/head tips provide the parent identity, and adoption leaves the configured queue unchanged. It neither requests a review nor invents a checkpoint. Adjudicate findings and publish the ordinary checkpoint afterward. Separately, already attributable completed evidence counts for its PR and channel across heads; that historical credit does not relax the command's exact identity checks, and ambiguous or incomplete evidence remains non-counting.
- Hosted taper is one completed, attributable zero-useful result for that PR; CLI taper is three consecutive such results for that PR. Results count across reviewed heads without a lineage, patch-equivalence, or current-head requirement. Once reached, taper is durable: later commits, bases, patches, fixes, or reconciliation do not erase it or automatically reopen the channel. An explicit human `reopen` judgment or `allocation grant|renew --fresh-taper` starts a fresh per-PR/channel streak at its decision boundary; earlier dry results remain visible but cannot satisfy the new streak. An ordinary bounded allocation does not reset completed taper by itself. An accepted allocated result breaks the active streak; later taper is evaluated after that result. Accepted findings and fixes remain mandatory holds. Identity checks may guard a new request but never queue advancement past a PR whose channel is complete or human-stopped. Invalid, duplicate, already-fixed-only, and other completed zero-useful results count; a literal `0/0` is unnecessary. Policy overrides remain explicit and are never inferred automatically.
- Future Hosted and CLI checkpoints report `found / accepted / routed`. `found` is the provider's raw count, `accepted` is a valid fix owned by the reviewed PR, and `routed` is an observation assigned to another owner without adjudicating it for that owner. Only accepted findings extend source taper or require an in-PR fix before its next review. A route is informational on its source PR and creates no source warning, taper hold, review-selection hold, or merge hold; the destination owner judges it independently. Existing public counts and captures remain unchanged, and old checkpoints have an unknown routed count rather than an inferred zero or retroactive reclassification.
- For each PR, the controller derives the expected effective parent as the nearest preceding unmerged configured PR, or the repository default base after all predecessors merge. The request records the PR number, child head, expected parent identity and exact parent head, merge-base SHA, and unique patch identity. Without `--force`, admission requires the live base and parent tip to match that identity, the parent to be an ancestor of the candidate, and every earlier adjacent link to be coherent; `PARENT_MOVED` and `UNRECONCILED` remain holds even when a merge base exists. `--force` may acknowledge a known topology or merge-readiness warning only while the PR and committed candidate remain exact, and admission rechecks for identity movement. When the provider's actual diff base/ref differs from the expected parent, retain the provider-observed base/ref with the forced attempt; do not describe the expected queue parent as the diff that was reviewed. The warning remains relevant to merge readiness.
- Reconciliation or an unproven candidate may block a new request only while that channel's policy remains incomplete; `--force` can acknowledge a known reconciliation warning when PR and committed candidate identity are certain, but cannot override candidate uncertainty or undo completed taper or an explicit human stop. A Hosted/CLI head mismatch alone does not require another review or judgment. Further review after completion or a stop requires an explicit human `reopen` decision or fresh-taper allocation.
- When a coherent rebase or retarget leaves historical evidence anchored to the old parent, record the exact transition with `dev-tools/pr-review decide reconcile --pr <number> --channel hosted|cli --checkpoint <id> --prior-head <SHA> --reason "<reason>"`. This records the ancestry transition without erasing completed taper or granting new review credit. The controller verifies the old attributable anchor and current branch, parent, ancestry, merge-base, and patch identities for that transition; the decision becomes invalid after any bound identity changes.
- When historical evidence is readable but lacks the modern linked anchor required by `decide reconcile`, use `dev-tools/pr-review decide transition --pr <number> --head <exact live SHA> --reason "<reason>"` to record the observed legacy records without inventing new checkpoints or spending review quota. The exact observations captured by that transition become non-counting policy history and cannot satisfy taper, even if a legacy record appears completed and attributable; newer independently attributable results remain counting. Active Hosted reservations and unresolved findings remain separate request or merge obligations.
- If that exact legacy transition is followed by a fresh review and a later coherent fix head, reauthorize only the same immutable fingerprints with `dev-tools/pr-review decide transition --reauthorize --pr <number> --head <exact live SHA> --reason "<reason>"`. The controller requires a prior transition, verifies every carried record again, and requires every other observation to be normal completed attributable anchored evidence; newer evidence remains counting and subject to ordinary reconciliation and judgment. A changed head without this explicit reauthorization remains blocked, and the command never creates a checkpoint or consumes review quota.
- A single previously audited Hosted fingerprint that is absent from the complete current history may be retired only with `--reauthorize --retire-missing-hosted-fingerprint <exact fingerprint>`. This requires the exact prior fingerprint, coherent current topology, complete available Hosted trigger records and paginated GitHub review/comment history, terminal and uniquely attributable responses, no active or unresolved reservation, and no unresolved actionable findings; any missing or ambiguous proof remains held. The fingerprint stays in the transition audit and remains non-counting if it later reappears. This decision never reconstructs evidence or creates a checkpoint and does not grant review, taper, finding-count, or merge-readiness credit.
- Record an explicit channel judgment with `dev-tools/pr-review decide judgment retain|reopen --pr <number> --channel hosted|cli --head <exact live SHA> --checkpoint <id> --reason "<reason>"`. Retain confirms the verified equivalent patch for request and queue safety; reopen explicitly requires fresh review without deleting historical completed taper and resets the taper streak at the bound checkpoint. For CLI, a reopen may bind the latest complete modern checkpoint to a proven descendant live head, but carries no new review credit until later completed results arrive. A narrow channel policy override uses `dev-tools/pr-review decide policy --pr <number> --head <exact live SHA> --checkpoint <id> --hosted-zero-useful <count> --reason "<reason>"` or `--cli-zero-useful <count>` (exactly one channel); it sets that channel's zero-useful completion count for the exact checkpoint.
- Extend the existing allocation with `dev-tools/pr-review decide allocation grant --pr <number> --channel hosted|cli --head <exact live SHA> [--checkpoint <completed checkpoint>] [--min-additional-completed <N>] [--max-additional-completed <N>] [--exact-additional-completed <N>] [--fresh-taper] --reason "<human judgment>"`. Both bounds count completed, attributable results for that PR and channel beginning at the decision; the optional checkpoint records the observed identity but does not move that count's start. With neither bound, the existing one-result promise remains (`min=1`, `max=1`). A minimum-only allocation has no maximum; a maximum-only allocation has no extra minimum (`min=0`). `--exact-additional-completed N` is mutually exclusive with the separate bounds and `--fresh-taper`, and records `min=max=N`, so ordinary taper cannot stop discovery before all `N` results and the cap stops discovery immediately afterward. It preserves the existing taper rather than starting a fresh streak. Use `allocation renew --exact-additional-completed N` to replace an existing allocation or audited human stop explicitly. A verifiable request already admitted at the exact-allocation decision remains in flight and counts only when it completes attributably; ambiguous or unsupported active evidence is refused. Without `--fresh-taper`, an allocation after completed taper affects queue eligibility and its additional-result count while preserving the existing historical taper display. Its zero-useful results continue the normal streak. An accepted allocated result resets the active streak at that result, while all earlier checkpoints remain visible with their original counts; after fixes, later zero-useful results can satisfy taper. `--fresh-taper` starts the active streak at the allocation decision immediately; earlier dry results remain visible historical evidence but cannot satisfy it. When both bounds are set, reject `min > max`; the minimum requires that many additional results even after fresh taper, while taper may stop earlier than the maximum once the minimum is met. Rate limits, connection failures, duplicates, partial or ambiguous responses, provisional captures, and other non-counting observations do not consume the count. Hosted and CLI allocations remain independent; request-time identity checks apply only when posting a new review.
- Normal taper can finish before a maximum once the minimum is met. After any additional result with accepted findings, no next request is allowed until those findings, current/outdated threads, actionable summary findings, and fix publication/validation obligations are clear, even if capacity remains. Once the maximum is used, no further request is allowed for that PR/channel; a maximum stop is not taper and does not waive accepted findings or fixes. `status` and `evidence` expose the minimum, maximum, completed count, baseline identity, in-flight results, taper state, and controlling reason. When the maximum is exhausted, the controller derives an audited human-cap stop and advances that channel through its normal selector without a separate `decide stop`, subject to the active-review safety described below. Pending obligations remain source-owned and visible as `cap exhausted; findings pending`; this stop is not taper, current-head review, CI/Smoke proof, or merge readiness. A bounded allocation can be replaced explicitly with `allocation renew` and new bounds; `allocation cancel` removes it. Ordinary fixes never reset its completed count.
- When the Overseer deliberately allocates one further completed review before deciding whether to continue, record it before the review with `dev-tools/pr-review decide allocation grant --pr <number> --channel hosted|cli --head <exact live SHA> --reason "<reason>"`. Completed-result counts belong to the PR and channel and survive later identity changes; rate limits, partial, duplicate, and unattributable results do not consume the allocation. Record a human decision to make no further requests with `dev-tools/pr-review decide stop --pr <number> --channel hosted|cli --reason "<human judgment>"`. This audited PR/channel override bypasses the taper gate only for queue advancement; it is not taper completion or proof of review coverage, and it persists across head and parent changes. It requires no completed checkpoint, clean findings, idle provider, or coherent review topology. An already admitted CLI or Hosted run continues with its reservation, capture, attribution, and eventual findings intact; finishing that run does not clear the override. Stop recording and new-request admission share only the short state mutation boundary, while each provider keeps its execution exclusion. Optional `--head` and `--checkpoint` pins must match the observed identities; unavailable optional Git proof is recorded as absent, never fabricated. Existing ambiguity-retention and over-ceiling acknowledgment options record their specific evidence without granting review credit. Discovery can advance only when the same channel has no active provider run. Accepted fixes, pending captures and adjudication, attributable evidence, current and outdated threads, actionable summaries, required CI, runtime proof, ancestry, and merge safety remain independent obligations. A stop overrides taper only and does not manufacture a reviewed head or merge readiness.
- For a channel that still needs review, targeting stops at the first held, unstable, unreconciled, over-ceiling, or judgment-blocked PR; it skips PRs whose channel has completed taper or an audited human stop. The narrow exception is a verified terminal, non-counting Hosted response: keep that PR incomplete and visible, but use the next coherent PR's Hosted window if one exists. Do not post another request on the ambiguous PR or grant it taper or merge credit; revisit its evidence or obtain an audited human stop before its merge handoff. Request-time identity and active-review checks still apply before any new request for an incomplete channel. A file-ceiling rejection requires a coherent topology decision; there is no normal incremental-review fallback.
- Do not start a review against a base that is about to change. Let an active review finish and consume still-valid findings; cancellation does not recover quota or evidence. Do not publish review-invalidating commits while Hosted review is active.
- For status or merge readiness, begin with `dev-tools/pr-review status --pr <number>`. Inspect all paginated current and outdated unresolved threads and the latest completed summary before CI and mergeability, and verify summary-only duplicate and outside-diff findings. Missing, malformed, unattributed, or incomplete evidence fails closed; an older-head completed result attributable to the same PR still counts toward taper.
- Record a summary-only disposition with `dev-tools/pr-review decide summary-disposition rejected|accepted-unfixed|accepted-fixed|routed --pr <number> --head <exact reviewed SHA> --source review|comment --summary-id <id> --kind outside_diff|duplicate --count <N> --reason "<reason>"`. `accepted-fixed` also requires `--corrected-head <exact live SHA>` after the head advances. A `routed` disposition requires one `--route-finding <stable-ref> --route-observation "<finding>"` pair per summarized finding, may include `--target-pr <number>`, and atomically links every individual observation to its own structured open route before clearing the exact summary bucket. Each decision binds the whole kind/count bucket to its immutable summary identity and never changes raw counts. Only exact `rejected` or `routed` dispositions clear that current-head summary hold; `accepted-unfixed` remains a hold, and `accepted-fixed` is historical audit evidence only. These decisions do not resolve review threads, which remain separate obligations.
- Always open controller-owned routes for Hosted, summary-only, and legacy findings with `dev-tools/pr-review decide route open --source-pr <number> --channel hosted|cli --review <immutable review or run ID> --finding <stable finding reference> --observation "<short description>" [--target-pr <number>]`. Routed CLI findings also use this controller route until both the shared state-directory SQLite cutover and review-record schema bootstrap or migration are complete. Once both are ready, new CLI routed findings use `records cli-decision`, which creates their SQLite route atomically; do not also invoke `decide route open` for those findings. Route IDs remain stable by source PR, channel, review, and finding, and repeated legacy observations append to the same route. `dev-tools/pr-review routes --target-pr <number>` lists open incoming routes, and `dev-tools/pr-review routes --unassigned` lists routes without a named PR, including routes from merged source PRs. Checking the destination with `dev-tools/pr-review status --pr <number>` shows its open incoming routes. Receiving owners manage new SQLite routes with `records route decide`, `records route resolve`, or `records route retarget`; legacy controller routes remain owned by `decide route accepted-fixed`, `rejected`, or `retargeted`. Retargeting keeps the route open for the new destination. These target decisions do not revise the source checkpoint counts. The source status shows routes as historical trace only.
- Resolve a review thread only after verifying its exact finding is fixed at the current head. Do not resolve threads to conceal work, request review while the target is active or rate-limited, or enable paid review capacity.

## Review Orchestration

- Configure merge order once with `dev-tools/pr-review stack set`; the controller owns automatic Hosted and CLI targeting across the configured coherent merge train, and each channel advances independently. A cooldown, failure, or CI hold in one lane does not idle the other lane or safe later work. Keep request-time gates and the Hosted publication boundary intact, allow at most one active Hosted request and one CLI process repository-wide, and re-run `status` after head, parent, base, or merge changes to expose `PARENT_MOVED` descendants. Reconcile before an ordinary request, or use `--force` only for a known warning with exact candidate identity and admission-time rechecks.
- Exhausting an authorized maximum review allocation closes discovery for that PR and channel and advances that channel independently, even when accepted source fixes remain pending. Status retains `cap exhausted; findings pending` as source obligation information, with an audited human-cap stop rather than a discovery selection hold. Do not request another review on the capped source. An already admitted active review remains intact and prevents overlapping execution; its late findings remain source obligations. Minimum/maximum accounting, finding counts and resolutions remain unchanged. Cap closure is neither taper completion nor merge proof: accepted fixes, review threads, required CI and all merge-readiness requirements remain mandatory on the source PR.
- Keep the train moving when one PR or channel is blocked: work on the next safe review or fix up the configured chain, including dependency-safe preparation ahead of the front. Do not stop at a blocked request, red CI, provider cooldown, or human merge wait while useful safe work remains. Report the concrete blocker and the work continuing elsewhere; stop only when no safe useful work remains or the human explicitly pauses the lane.
- Request Hosted promptly when the controller selects an eligible PR; do not delay for CLI, CI, or a possible cleaner head. Prepare fixes while Hosted runs and publish at its safe boundary. If the controller refuses a request, report and address its specific reason rather than inventing an additional wait. CLI may wait for a useful fix batch when its faster cycle makes that sensible, but it does not gate independently eligible Hosted review.
- Hosted and CLI capacity remain explicit shared resources. When capacity is contested across lanes, the Overseer selects the stack and priority; already-running work finishes, and other workers continue non-review implementation.
- Treat CI and Hosted review as asynchronous. Continue safe work that does not invalidate the active review. After posting Hosted, keep an owned bounded wait on its exact trigger with `dev-tools/pr-review wait hosted --pr <number> --trigger-id <comment ID>` (default 30-second poll, 90-minute maximum; both configurable). Keep the process handle and read its result promptly; do not fire and forget or rely on a delegated sentinel's unverified handoff. The wait reuses the controller's complete-history attribution, never posts, counts, or retires a review, and exits separately for completion, another terminal outcome, or an expired wait. Then sync and adjudicate terminal evidence. Only the controller owner triggers or retries, and duplicate polling is prohibited.
- Hosted attribution binds the immutable trigger comment, captured PR/head, and terminal response; rate-limit, no-op, failure, ambiguity, and timeout remain distinct. An exact CodeRabbit `Full review finished.` reply with complete paginated bot comment, review, and inline-thread history containing no other finding or result output in that trigger window is a zero-finding completion even if CodeRabbit omits its separate summary. An edited standing zero-summary may be ignored as corroborating background, but its edit time alone never attributes it to a new trigger. The reply still needs the ordinary linked public checkpoint to count toward taper. Contradictory or incomplete evidence remains non-counting and must be surfaced when history is reread. Elapsed time alone never retires a trigger. An unresolved timed-out trigger cannot be retired at the same head; same-head recovery is refused because a delayed response cannot safely be distinguished from a replacement review. When deterministic live evidence permits retirement, use `dev-tools/pr-review decide trigger-retire --pr <number> --trigger-id <id> --head <exact SHA> --reason "<reason>"`; never edit private records manually. If a verified posted trigger remains active or awaiting after the PR advances, and its bounded wait has expired, use `dev-tools/pr-review decide trigger-retire-stuck --pr <number> --trigger-id <id> --head <exact CURRENT SHA> --reason "<reason>" --confirmed-wait-expired`. This checks the recorded trigger identity, exact live PR head, and complete response history under the per-PR Hosted lock before retiring the stale trigger; any late response is non-counting. New pre-POST reservations must durably record the original attempt identity and immutable comment-ID floor before POST; adoption and recovery require both. A pre-POST reservation may be recovered only when the operator can affirm that POST was never issued: use `dev-tools/pr-review decide trigger-recover-prepost --pr <number> --head <reservation's exact captured SHA> --reason "<reason>" --confirmed-not-posted`. The command fetches complete paginated comments under the per-PR Hosted request lock, requires the stored original actor/time identity, requires `--head` to match the reservation's captured head, and validates and audits the live head as a valid SHA even if it has advanced; it rejects any matching or potentially ambiguous command, then moves the reservation into a private audit file without posting. Legacy reservations without a trusted attempt identity or comment-ID floor remain held. Use included quota only.
- A durable `posted_boundary_changed` trigger is never counted as review evidence. After its exact captured head has advanced, the same confirmed-wait-expired `trigger-retire-stuck` operation may retire it only when the locked check verifies the trigger identity and complete response history as active, awaiting, completed, rate-limited, no-op, or failed, or the exact later/concurrent full-review-trigger ambiguity reason (`a later or concurrent full-review trigger prevents attribution`). No other ambiguous state is retirable; same-head recovery remains refused even for that narrow exception, and late responses remain non-counting.
- A CLI run verifies the published file list, PR identity, exact published child head, and isolated committed candidate before invoking the review process. Without `--force`, it also requires the selected parent tip, ancestry, and merge base to be coherent; force may acknowledge a known warning but does not admit an uncertain candidate or identity movement detected at admission. Dirty source edits are excluded: untracked, staged, and other uncommitted files are outside a committed-candidate review. After the shared SQLite state directory is cut over and the review-record schema is bootstrapped or migrated, its attempt, JSON events, outcome, timing, and force acknowledgment are stored in the private SQLite review records. Before then, keep the legacy capture files as recoverable evidence until historical migration is checked.
- For a new CLI result, record each raw finding through `dev-tools/pr-review records cli-decision --run-id <run ID> --finding <1-based index> --decision accepted|routed|rejected --actor <operator> --reason "<outcome>" [--target-pr <number>]`, then finalize the run through `records source finalize --run-id <run ID>`, only after both the shared state-directory SQLite cutover and review-record schema bootstrap or migration are complete. Until both are complete, retain the captured `decisions.tsv` as raw-positive evidence and open routed findings with `dev-tools/pr-review decide route open`. Accepted decisions are source-owned fixes only; routed decisions name a target without judging it and, once both prerequisites are complete, create the SQLite route atomically. Receiving owners manage that route with `records route decide|resolve|retarget`; do not open a duplicate through `decide route open`. `records cli-correct` appends an audited correction if a decision was wrong. Legacy runs may still require their captured `decisions.tsv` for exact historical repair. Adjudicate every finding before the public checkpoint and leave provider events immutable. Once adjudicated, promptly persist the found/accepted/routed counts in the ordinary public checkpoint; fixes and their proof may follow. This records the completed review and does not gate independently eligible work in the other channel.
- Record each adjudicated completed review once using the canonical single-line checkpoint: `Hosted|CLI: R found / A accepted / T routed · <sha> · N files · <duration>`, followed by the controller-provided hidden linkage and duration markers. `R` must equal accepted plus routed plus rejected/duplicate findings; route disposition is not counted as accepted. Show durations below one minute as `Ns`, otherwise as `Mm SSs` (for example, `8m 07s`) or `Hh MMm SSs` (for example, `1h 08m 07s`). Keep the hidden duration marker and stored duration in integer seconds; visible and hidden values must represent exactly the same elapsed seconds. The parser continues to accept historical two-count checkpoints and visible `Ns` durations. The matching private trigger or capture binds the complete stack anchor. Hosted duration spans accepted trigger to attributable terminal result; CLI duration spans only the review process. Cooldown, preflight, sentinel wait, and delayed posting are excluded. Historical duration-less checkpoints and legacy private trigger/capture records remain readable, while evidence without the modern complete anchor cannot satisfy current taper.
- Finding decisions record accepted, routed, or rejected disposition and a concrete outcome or reason. Accepted work is fixed only when a verified correction is published or is already implemented with useful proof. Routed work names its destination without asserting that owner's acceptance or fix. Target-route disposition never changes the source PR's counts. Reporting never authorizes review, CI mutation, thread resolution, merge, or task resumption.
- When taking up a PR, its owner checks the controller's open routes for that target PR and records each route's disposition and resolution in the controller. When routing a finding, leave a concise target-PR comment with the controller route ID, a short issue description, a link to the source checkpoint, and a request for target-owner adjudication. The comment is a notification only; the controller remains the route record. Keep it focused and do not post another comment for every route state change.
- After each review/fix run, report raw/useful counts, significance, dispositions, current channel target, and whether another review is justified. Use proportionate validation/runtime proof from [Validation And Runtime Proof](./validation-and-runtime-proof.md), without duplicating existing evidence.
- Under an explicit Overseer arrangement, the Overseer periodically samples accumulated decisions and receives meaningful milestones rather than per-round noise. Preserve the existing private per-PR review note required by [AI delegation and review](./ai-delegation-and-review.md#independent-review-evidence) when a separate model-review programme is explicitly assigned.

## Review Completion Criteria

- For each candidate, verify its live head and base, effective parent and unique patch, current and outdated unresolved threads, latest review summary, PR title/body and generated LOC metadata, required exact-head CI, and mergeability. Report recent findings and their significance, each channel's decision, proof limits, and the next action. Reconcile parent movement without losing the child's owned patch or rewriting historical review counts.
- Define a coherent capability or correction scope and obtain an initial substantive review through the controller covering feature-bearing work and changed contracts.
- Resolve every known actionable finding, including current and outdated threads and summary-only or outside-diff findings, and verify each fix at the current head. Useful in-scope corrections to correctness, completeness, authority, alignment, maintainability, consolidation, or clarity remain actionable regardless of line size; judge worthwhile suggestions by their actual benefit against implementation cost and risk, including when they address neither a bug nor an existing design requirement, and do not relabel them optional merely to finish.
- Re-review new functionality, changed contracts, materially broader risk, or fixes that introduce independently reviewable behavior. Direct, verified corrections need not trigger another whole-PR discovery round solely to accumulate clean results.
- The channel defaults above are the controller's normal completion policy, not a quota target. Request work beyond a completed policy only for a concrete unresolved risk, coverage gap, or explicit human override. Repeated serious findings trigger focused investigation of their shared failure mechanism and appropriate proof rather than arbitrary clean-round accumulation.
- Under an explicit Overseer arrangement, present the Hosted/CLI trend and a nonblocking recommendation when marginal utility is uncertain. The Overseer—not the implementing lane or controller—decides whether an additional deliberate round is justified and whether merge-readiness handoff is reached.
- A PR is ready for an Overseer merge decision only after controller evidence shows zero unresolved current and outdated threads, all actionable summary-only and outside-diff findings are addressed, every open incoming route is dispositioned by the target owner, each fix is verified, every required channel has completed its policy through attributable provider results, required CI is green, and proportionate validation/runtime proof is complete. Open routes from this PR to other owners do not hold its merge readiness. An explicit human stop advances only that channel's discovery queue; it remains a visible review limitation, not taper or merge-readiness proof. Before handoff, refresh stale title/body content and the generated marked LOC section with `python3 dev-tools/maintenance/cloc-report.py pr <number> [--repo owner/name] --update-pr`. The section is informational, not a size gate. If tooling is unavailable, record the limitation instead of inventing counts. Zero threads or GitHub `CLEAN` alone is insufficient, and the final head must not be described as reviewed when it was not. The implementing worker reports readiness without taking merge action; the designated Overseer may merge or enable auto-merge under the project owner's standing authorization after verifying the evidence.

## Change And Merge Policy

- Keep PRs coherent, including adjacent convergence. Use smaller PRs for isolated fixes; split independent or genuinely hard-to-review work, and split coherent work that exceeds a reviewer ceiling under the following rules.
- Hosted CodeRabbit reviews have a verified hard limit of 100 changed files; the controller refuses a Hosted request above that count and records a current provider skip as a Hosted limitation. The CLI review path has completed successfully with 111 changed files, but its upper limit is not established. Do not infer a CLI cap from the Hosted limit or from the plan page; verify any higher CLI boundary before documenting it.
- Before starting a canonical `dev-tools/pr-review` run, keep the Hosted reviewer-selected file count comfortably below 100 rather than targeting the exact limit. The CLI path may proceed above 100 when its own request-time checks pass. Useful review findings define required improvements, not optional scope: accepted useful findings remain implementation obligations in their canonical code, documentation, or proof owner. A provider limit may change branch topology or review boundaries, but never correctness, cleanliness, or which live issues are fixed; do not offset growth by dropping useful scope, packing unrelated helpers or tests into already-counted files, moving authority to a noncanonical owner, or changing runtime or design semantics.
- Treat reviewer ceilings as dynamic topology constraints. Prefer the fewest coherent, independently sound reviewable PRs that preserve every accepted finding and canonical placement under the cap; additional PRs add separate review, taper, and reconciliation costs, so narrowness or neat separation alone is insufficient. If the correct implementation exceeds the active ceiling, default to a coherent stack that preserves every finding and its proof; consolidate only when independently justified by cohesion and authority, without forcing unrelated work together. Do not target a hardcoded file count or preserve an arbitrary majority merely to stay under a cap. Use a scoped-review or CLI path only as an Overseer-adjudicated fallback when the change genuinely has no clean split or preserving the review boundary requires it. The ceiling changes review topology, never correctness or cleanliness.
- When a finding or proof moves to another PR, update its existing PR body and review disposition with the successor reference and check whether downstream already fixes it. After a split or reconstruction materially changes a reused PR's review scope, post one short comment such as **Review scope changed:** validator cleanup moved to #2731. Earlier counts cover the previous scope. Add `<!-- firemud-review-scope-change -->` below it; `dev-tools/pr-review` consumes that evidence and places the timestamped marker in its checkpoint timeline. Earlier evidence remains relevant to the previous patch boundary, and still-applicable findings remain obligations, while the event does not by itself require a fresh review streak or imply increased risk. An ordinary post-merge retarget with equivalent scope needs no reset comment. Do not create a new ledger.
- The project owner grants the configured merge-train operator standing authorization for a coherent split when accepted findings or an owned invariant would cross the provider ceiling, or when a natural owner/proof boundary makes one PR materially hard to review. No fresh routine approval is needed. Preserve every finding and the published parent patch and review history; keep the parent fail closed if a child supplies required behavior. Open the smallest coherent stacked child on the verified parent, identify moved observations and their owner in both PRs, prove each unique patch, reconcile descendants at a Hosted-safe point, then update and read back the controller queue. Route a source thread to a named target without claiming the target fix; resolve an in-boundary accepted thread only after its correction is published and validated. A split does not grant taper or merge readiness. Do not create artificial extraction PRs, drop findings, or publish review-invalidating changes during active Hosted.
- Outside that standing merge-train authorization, an explicit Overseer arrangement permits isolated preparation of a concrete topology proposal, but publishing a split, prerequisite, or successor, or retargeting an existing PR, requires Overseer approval. An approved proposal covers its planned routine retargets and publication without repeated approval. Without an explicit Overseer arrangement, the human's selection of an active workstream authorizes routine scope-safe topology changes. Bring a materially more fragmented topology to the Overseer with scope, dependency, and review-cost comparisons. Escalate when no coherent split preserves the invariant, ownership is materially uncertain, or the change introduces consequential product, architecture, or activation choices; continue independent safe work meanwhile.
- Treat failing Renovate PRs as maintenance work: inspect CI and push the smallest compatible fix to its branch when possible; otherwise use a replacement branch with required compatibility changes.

## Branch And PR Hygiene

- Open or update a PR autonomously when an implementation branch reaches a coherent review checkpoint, subject to the topology and approval rules in [Change And Merge Policy](#change-and-merge-policy). Stacked PRs are acceptable when their base dependencies are explicit and they let independent work continue while CI or review runs. If the next authorized work is unambiguous and can be cleanly based on a merge-ready PR, continue autonomously in a stacked PR subject to those rules; a draft PR may expose in-progress work and should be marked ready at a coherent review checkpoint. After the parent merges, retarget the child to `develop` subject to those rules before rebasing or pushing. An explicit pause, unresolved human decision, or dependency requiring merged state stops continuation; do not create tiny placeholder PRs without review-worthy content.
- When active work moves to another worktree, report its absolute path and branch so the human's IDE context and delegated-worker paths remain aligned.
- When retargeting a stacked PR after its parent merges, change the base before rebasing or pushing the child. Required workflows listen for GitHub's `edited` event but run replacement validation only when `changes.base.ref` is present. The Validation, Security, and Smoke workflows use a separate per-run metadata-only concurrency group for title/body edits; those edits neither cancel an active substantive run nor repeat its tests. Their required gate jobs retain the exact branch-protection names and succeed on a metadata edit only after the shared preservation action verifies prior success for the same base/head tuple. The action allows a longer bounded wait only when it verifies an active substantive run or pending gate for that tuple; an absent, failed, stale, ambiguous, or spoofed predecessor remains fail closed. Gate preservation accepts a prior run with no GitHub PR association only when its canonical run title exactly binds the workflow, PR number, base SHA, and head SHA; older runs without that title remain fail closed.
- For recurring branch, worktree, and PR inventory, use `dev-tools/validation/report-worktree-pr-topology.sh` rather than ad hoc status commands. Renovate PRs are omitted from the selected inventory by default; the report records them in `omitted_renovate`, and `--include-renovate` opts them back in. Pass `--pr <number>` for a bounded direct base/dependent stack and `--json` for machine-readable evidence; selected reports correlate only exact branch/SHA identities and fail closed on ambiguous matches, while reporting local worktree dirtiness and unpublished or stale local heads.
- After a merge, remove its defunct local worktree and merged local/remote branch only after confirming no open PR or active stacked branch depends on it. Preserve unmerged branches and worktrees.
- Pass PR-body Markdown through a file or stdin with real newlines rather than literal `\\n` strings.
