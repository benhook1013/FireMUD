# Pull Request Lifecycle

Use this guide for pull-request status, review handling, CI, Renovate, merging, or branch/worktree cleanup.

## Review And Status

- CodeRabbit automatic reviews are disabled. The sole operator interface is `dev-tools/pr-review`: configure the one repository review stack with `stack set <ordered PR numbers...>`, inspect it with `stack show`, inspect live state with `status [--pr <number>]`, and inspect historical/private evidence with `evidence [<number>]`. The locked, atomically replaced, versioned configuration lives at `<git-common-dir>/firemud/pr-review-stack.json`; it persists only stack configuration, exact policy overrides, explicit judgments (including summary-only finding dispositions), reconciliation decisions, legacy evidence transitions, and review allocations. Heads, bases, merge state, cooldowns, threads, checks, and evidence are derived live.
- Live shared JSON-to-SQLite cutover waits until the merged, version-matched `dev-tools/pr-review` is installed and selected; verify its `--version` before proceeding. The explicit migration atomically exchanges the JSON path for a marked SQLite cutover directory and retains the source JSON, fencing old JSON readers and writers. Existing controller-era routes remain readable through `routes` and `status`; separately bootstrapped SQLite records expose provider checkpoints and curated manual/subagent runs, findings, and routes. History and route queries are read-only. Full provider captures remain separate audit evidence outside SQLite, and provider imports or independent records do not change Hosted/CLI CodeRabbit taper. Backup/restore is a separate one-shot operation. See [PR-review SQLite operations](../../dev-tools/pr_review/README.md); this guidance does not mean live cutover or migration proof has occurred.
- Run complete reviews only through `dev-tools/pr-review run hosted|cli [--expect-pr <number>]`. The controller derives the permitted target; `--expect-pr` is an assertion that fails before quota or review mutation if it differs. Each channel targets the earliest eligible PR whose policy is incomplete, skipping only a verified legacy handoff or an explicit human stop recorded for that channel. A Hosted rate limit never advances Hosted.
- Hosted taper is one corrected-state zero-useful completed, attributable result, where corrected-state describes the immutable review-time anchor rather than a dynamic latest-head match. CLI taper is three consecutive zero-useful completed, attributable results. CLI rounds may span reviewed heads within one coherent PR lineage, and completion persists on a proven descendant live head. Once reached, taper is durable historical evidence: later heads, bases, patch identities, useful results, fixes, or parent-only reconciliation never erase it or automatically reopen the channel. An explicit human `reopen` judgment or `allocation grant|renew --fresh-taper` starts a fresh per-PR/channel streak at its exact decision boundary; earlier dry results remain visible historical evidence and cannot satisfy that fresh streak. An ordinary bounded allocation does not reset completed taper by itself, and its zero-useful results continue the normal streak. An accepted allocated result breaks the active streak; later taper is evaluated after that accepted result while every prior checkpoint remains visible with its original count. Accepted findings and their fixes remain independent mandatory holds. Head, ancestry, patch, and topology checks still gate new requests and queue advancement; status must show completed historical taper separately from any active streak or safety hold. Do not auto-reopen because a Hosted fix or corrected descendant commit appeared; a concrete material risk or extra review demand requires an explicit human decision. Invalid, duplicate, already-fixed-only, and other completed zero-useful results count; a literal `0/0` is unnecessary. Exact-bound policy overrides remain explicit and are never inferred automatically.
- Future Hosted and CLI checkpoints report `found / accepted / routed`. `found` is the provider's raw count, `accepted` is a valid fix owned by the reviewed PR, and `routed` is an observation assigned to another owner without adjudicating it for that owner. Only accepted findings extend source taper or require an in-PR fix before its next review. A route is informational on its source PR and creates no source warning, taper hold, review-selection hold, or merge hold; the destination owner judges it independently. Existing public counts and captures remain unchanged, and old checkpoints have an unknown routed count rather than an inferred zero or retroactive reclassification.
- For each PR, the controller derives the effective parent as the nearest preceding unmerged configured PR, or the repository default base after all predecessors merge. Normal review requires the live base branch to match that parent, the exact parent branch tip to match its current head, that parent head to be an ancestor of the candidate, and every earlier adjacent link to be coherent.
- Every new review is anchored to its PR number, child head, effective parent identity and exact parent head, merge-base SHA, and unique patch identity. If an ancestor moves, affected descendants are `PARENT_MOVED` and normal review is refused until reconciliation. An unreconciled child remains refused even when a merge base exists.
- After reconciliation, equivalent history, changed topology, or an unproven candidate may require an exact-head/checkpoint judgment before a new request or queue advancement. That identity hold does not revoke previously completed taper. A head mismatch between channels remains `JUDGMENT_REQUIRED` unless the controller proves that completed CLI taper remains on the coherent descendant current candidate. Use an explicit `reopen` judgment only when fresh review is actually required; there is no generic force option.
- When a coherent rebase or retarget leaves historical evidence anchored to the old parent, record the exact transition with `dev-tools/pr-review decide reconcile --pr <number> --channel hosted|cli --checkpoint <id> --prior-head <SHA> --reason "<reason>"`. The controller verifies the old attributable anchor and every current branch, parent, ancestry, merge-base, and patch identity before permitting a new request. This records the ancestry transition; it neither erases completed taper nor grants new review credit. The decision becomes invalid after any bound identity changes.
- When historical evidence is readable but lacks the modern linked anchor required by `decide reconcile`, record `dev-tools/pr-review decide transition --pr <number> --head <exact live SHA> --reason "<reason>"` only after the controller verifies the coherent current parent, ancestry, merge-base, and patch identity. It records immutable fingerprints of the observed legacy records, keeps them visible but non-counting, and reopens both channels for fresh exact-head review; it never creates a checkpoint or consumes review quota. Active Hosted reservations, unresolved findings, ambiguous or stale records, and later identity changes remain fail-closed.
- If that exact legacy transition is followed by a fresh review and a later coherent fix head, reauthorize only the same immutable fingerprints with `dev-tools/pr-review decide transition --reauthorize --pr <number> --head <exact live SHA> --reason "<reason>"`. The controller requires a prior transition, verifies every carried record again, and requires every other observation to be normal completed attributable anchored evidence; newer evidence remains counting and subject to ordinary reconciliation and judgment. A changed head without this explicit reauthorization remains blocked, and the command never creates a checkpoint or consumes review quota.
- A single previously audited Hosted fingerprint that is absent from the complete current history may be retired only with `--reauthorize --retire-missing-hosted-fingerprint <exact fingerprint>`. This requires the exact prior fingerprint, coherent current topology, complete available Hosted trigger records and paginated GitHub review/comment history, terminal and uniquely attributable responses, no active or unresolved reservation, and no unresolved actionable findings; any missing or ambiguous proof remains held. The fingerprint stays in the transition audit and remains non-counting if it later reappears. This decision never reconstructs evidence or creates a checkpoint and does not grant review, taper, finding-count, or merge-readiness credit.
- Record an explicit channel judgment with `dev-tools/pr-review decide judgment retain|reopen --pr <number> --channel hosted|cli --head <exact live SHA> --checkpoint <id> --reason "<reason>"`. Retain confirms the verified equivalent patch for request and queue safety; reopen explicitly requires fresh review without deleting historical completed taper and resets the taper streak at the bound checkpoint. For CLI, a reopen may bind the latest complete modern checkpoint to a proven descendant live head, but carries no new review credit until later completed results arrive. A narrow channel policy override uses `dev-tools/pr-review decide policy --pr <number> --head <exact live SHA> --checkpoint <id> --hosted-zero-useful <count> --reason "<reason>"` or `--cli-zero-useful <count>` (exactly one channel); it sets that channel's zero-useful completion count for the exact checkpoint.
- Extend the existing allocation with `dev-tools/pr-review decide allocation grant --pr <number> --channel hosted|cli --head <exact live SHA> [--checkpoint <completed checkpoint>] [--min-additional-completed <N>] [--max-additional-completed <N>] [--fresh-taper] --reason "<human judgment>"`. Both bounds count completed, attributable, anchored results beginning at the decision; the optional checkpoint pins an observed identity but does not move that count's start. With neither bound, the existing one-result promise remains (`min=1`, `max=1`). A minimum-only allocation has no maximum; a maximum-only allocation has no extra minimum (`min=0`). Without `--fresh-taper`, an allocation after completed taper affects queue eligibility and its additional-result count while preserving the existing historical taper display. Its zero-useful results continue the normal streak. An accepted allocated result resets the active streak at that result, while all earlier checkpoints remain visible with their original counts; after fixes, later zero-useful results can satisfy taper. `--fresh-taper` starts the active streak at the allocation decision immediately; earlier dry results remain visible historical evidence but cannot satisfy it. When both bounds are set, reject `min > max`; the minimum requires that many additional results even after fresh taper, while taper may stop earlier than the maximum once the minimum is met. Rate limits, connection failures, duplicates, partial or ambiguous responses, provisional captures, and other non-counting observations do not consume the count. Hosted and CLI allocations remain independent and require the current coherent request-time identity.
- Normal taper can finish before a maximum once the minimum is met. After any additional result with accepted findings, no next request is allowed until those findings, current/outdated threads, actionable summary findings, and fix publication/validation obligations are clear, even if capacity remains. Once the maximum is used, no further request is allowed for that PR/channel; a maximum stop is not taper and does not waive accepted findings or fixes. `status` and `evidence` expose the minimum, maximum, completed count, baseline identity, in-flight results, taper state, and controlling reason. If the maximum is exhausted while obligations remain, status says `cap exhausted; findings pending` and the channel stays on that PR without another request. When those obligations clear, the controller derives the audited human-cap stop through its normal selector and advances to the next coherent PR without a separate `decide stop`; this stop is not taper, current-head review, CI/Smoke proof, or merge readiness. A bounded allocation can be replaced explicitly with `allocation renew` and new bounds; `allocation cancel` removes it. Ordinary fixes never reset its completed count.
- When the Overseer deliberately allocates one further completed review before deciding whether to continue, record it *before* the review with `dev-tools/pr-review decide allocation grant --pr <number> --channel hosted|cli --head <exact live SHA> --reason "<reason>"`. The promise binds the current parent, merge base, patch, and pre-existing checkpoints. A rate limit, partial, duplicate, stale, or unanchored result does not consume it. Keep `renew` for an unconsumed promise whose pre-review identity changed, and `cancel` to remove a promise; both require the PR/channel/current head and a reason. After adjudicating completed results, publishing accepted fixes, and clearing current/outdated threads and actionable summary findings, record the Overseer's decision with `dev-tools/pr-review decide stop --pr <number> --channel hosted|cli --reason "<human judgment>"`. The controller records whether the stop consumes an allocation or reflects a direct human decision, refreshes both channels' complete evidence, binds the stop to the exact live head and stack identity, and records the latest attributable checkpoint separately from that final head. A direct-human Hosted stop preserves older unanchored checkpoint/response records as non-counting history without reauthorizing them; this applies only when they are proven historical to the live head. Allocated stops and CLI stops retain their full historical audit requirements. Active reviews, current-head or otherwise ambiguous live results, unresolved current/outdated threads, actionable summary findings, and unpublished accepted fixes still block a direct-human Hosted stop. Each terminal ambiguous response may be retained only by repeating `--retain-ambiguous-fingerprint <exact immutable fingerprint>` for every response, together with `--ambiguity-reason <reason>`; retained responses remain non-counting and never count as dry results. Optional `--head` and `--checkpoint` arguments pin the observed identities. A direct human may explicitly acknowledge only current-head CodeRabbit over-ceiling skip evidence with `--acknowledge-over-ceiling --head <exact live SHA>` and a stop reason; the acknowledgment is stored with the exact-head stop and never counts as taper. It does not clear review threads or other blockers, and allocated stops cannot use it. The stop skips that PR for the selected channel and satisfies only review-discovery capacity; it does not manufacture taper, CI, runtime proof, or merge readiness. Required CI, Smoke/runtime, ancestry, thread, summary-finding, and merge-readiness evidence remain independent. The next PR retains all normal parent, ancestry, and active-review gates.
- `dev-tools/pr-review run cli --allow-unreconciled --reason "<reason>"` permits one exact child/parent-pinned provisional discovery pass when reconciliation cost is disproportionate. Its evidence is provisional, cannot satisfy taper or merge readiness, cannot advance either channel, and cannot be repeated for that identity. Hosted remains refused until reconciliation; if equivalent history remains afterward, it stays refused until an explicit exact-head/checkpoint judgment resolves it.
- Review targeting stops at the first held, unstable, unreconciled, over-ceiling, or judgment-blocked PR. A file-ceiling rejection requires a coherent topology decision; there is no normal incremental-review fallback.
- Do not start a review against a base that is about to change. Let an active review finish and consume still-valid findings; cancellation does not recover quota or evidence. Do not publish review-invalidating commits while Hosted review is active.
- For status or merge readiness, begin with `dev-tools/pr-review status --pr <number>`. Inspect all paginated current and outdated unresolved threads and the latest completed summary before CI and mergeability, and verify summary-only duplicate and outside-diff findings. Missing, malformed, unattributed, provisional, or wrong-head evidence fails closed.
- Record a summary-only disposition with `dev-tools/pr-review decide summary-disposition rejected|accepted-unfixed|accepted-fixed|routed --pr <number> --head <exact reviewed SHA> --source review|comment --summary-id <id> --kind outside_diff|duplicate --count <N> --reason "<reason>"`. `accepted-fixed` also requires `--corrected-head <exact live SHA>` after the head advances. A `routed` disposition requires one `--route-finding <stable-ref> --route-observation "<finding>"` pair per summarized finding, may include `--target-pr <number>`, and atomically links every individual observation to its own structured open route before clearing the exact summary bucket. Each decision binds the whole kind/count bucket to its immutable summary identity and never changes raw counts. Only exact `rejected` or `routed` dispositions clear that current-head summary hold; `accepted-unfixed` remains a hold, and `accepted-fixed` is historical audit evidence only. These decisions do not resolve review threads, which remain separate obligations.
- Record each routed finding in the locked controller state with `dev-tools/pr-review decide route open --source-pr <number> --channel hosted|cli --review <immutable review or run ID> --finding <stable finding reference> --observation "<short description>" [--target-pr <number>]`. Its stable route ID is derived from the source PR, channel, review, and finding. Repeated observations with that identity append to the same route. `dev-tools/pr-review routes --target-pr <number>` lists open incoming routes, and `dev-tools/pr-review routes --unassigned` lists routes without a named PR, including routes from merged source PRs. Checking the destination with `dev-tools/pr-review status --pr <number>` shows its open incoming routes and keeps it from merge-ready until its owner records `decide route accepted-fixed --route-id <id> --proof "<fix evidence>"`, `rejected --route-id <id> --reason "<reason>"`, or `retargeted --route-id <id> --target-pr <number> --reason "<reason>"`. Retargeting keeps the route open for the new destination. These target decisions do not revise the source checkpoint counts. The source status shows routes as historical trace only.
- Resolve a review thread only after verifying its exact finding is fixed at the current head. Do not resolve threads to conceal work, request review while the target is active or rate-limited, or enable paid review capacity.

## Review Orchestration

- Configure merge order once with `dev-tools/pr-review stack set`; the controller owns automatic Hosted and CLI targeting across the configured coherent merge train, and each channel advances independently. A cooldown, failure, or CI hold in one lane does not idle the other lane or safe later work. Keep request-time gates and the Hosted publication boundary intact, allow at most one active Hosted request and one CLI process repository-wide, and re-run `status` after head, parent, base, or merge changes to reconcile `PARENT_MOVED` descendants before normal review.
- Use an eligible Hosted window promptly on the controller-selected coherent published head. Do not defer Hosted solely because CLI, CI, or local fixes elsewhere might yield a cleaner candidate later; prepare fixes while Hosted runs and publish at its safe boundary. An active request, an unresolved accepted finding on that PR, a known unpublished parent change that would invalidate its ancestry, or an explicit controller identity or reconciliation fence is a reason to wait and report the next action. CLI may wait for a useful fix batch when its faster cycle makes that sensible, but it does not gate independently eligible Hosted review.
- Hosted and CLI capacity remain explicit shared resources. When capacity is contested across lanes, the Overseer selects the stack and priority; already-running work finishes, and other workers continue non-review implementation.
- Treat CI and Hosted review as asynchronous. Continue safe work that does not invalidate the active review. A delegated sentinel may watch an established active/cooldown transition, but only the controller owner triggers or retries, and duplicate polling is prohibited.
- Hosted attribution binds the immutable trigger comment, exact head, and terminal response; rate-limit, no-op, failure, ambiguity, and timeout remain distinct. Elapsed time alone never retires a trigger. An unresolved timed-out trigger cannot be retired at the same head; same-head recovery is refused because a delayed response cannot safely be distinguished from a replacement review. When deterministic live evidence permits retirement, use `dev-tools/pr-review decide trigger-retire --pr <number> --trigger-id <id> --head <exact SHA> --reason "<reason>"`; never edit private records manually. If a verified posted trigger remains active or awaiting after the PR advances, and its bounded wait has expired, use `dev-tools/pr-review decide trigger-retire-stuck --pr <number> --trigger-id <id> --head <exact CURRENT SHA> --reason "<reason>" --confirmed-wait-expired`. This checks the recorded trigger identity, exact live PR head, and complete response history under the per-PR Hosted lock before retiring the stale trigger; any late response is non-counting. New pre-POST reservations must durably record the original attempt identity and immutable comment-ID floor before POST; adoption and recovery require both. A pre-POST reservation may be recovered only when the operator can affirm that POST was never issued: use `dev-tools/pr-review decide trigger-recover-prepost --pr <number> --head <reservation's exact captured SHA> --reason "<reason>" --confirmed-not-posted`. The command fetches complete paginated comments under the per-PR Hosted request lock, requires the stored original actor/time identity, requires `--head` to match the reservation's captured head, and validates and audits the live head as a valid SHA even if it has advanced; it rejects any matching or potentially ambiguous command, then moves the reservation into a private audit file without posting. Legacy reservations without a trusted attempt identity or comment-ID floor remain held. Use included quota only.
- A durable `posted_boundary_changed` trigger is never counted as review evidence. After its exact captured head has advanced, the same confirmed-wait-expired `trigger-retire-stuck` operation may retire it only when the locked check verifies the trigger identity and complete response history as active, awaiting, completed, rate-limited, no-op, or failed, or the exact later/concurrent full-review-trigger ambiguity reason (`a later or concurrent full-review trigger prevents attribution`). No other ambiguous state is retirable; same-head recovery remains refused even for that narrow exception, and late responses remain non-counting.
- A CLI run validates the published file list, exact child and parent heads, ancestry, merge base, and isolated committed candidate before invoking the review process. Dirty source edits are excluded. Raw output and finding decisions remain private under the shared Git common directory.
- There is no `dev-tools/pr-review decide` writer for raw CLI finding decisions. After a CLI run, use the emitted `capture_dir` and write decisions to `<capture_dir>/decisions.tsv`; do not change captured `stdout` or metadata. Add one tab-separated row for every raw finding, in finding-event order, with three columns: the 1-based finding event index, `accepted`, `routed`, or `rejected`, and a concrete outcome, route reference/owner, or rejection rationale. Accepted decisions are source-owned fixes only. Record each route in the locked controller state with the corresponding stable finding reference. Adjudicate every finding before recording the checkpoint; leave captured output and metadata immutable.
- Record each adjudicated completed review once using the canonical single-line checkpoint: `Hosted|CLI: R found / A accepted / T routed · <sha> · N files · <duration>`, followed by the controller-provided hidden linkage and duration markers. `R` must equal accepted plus routed plus rejected/duplicate findings; route disposition is not counted as accepted. Show durations below one minute as `Ns`, otherwise as `Mm SSs` (for example, `8m 07s`) or `Hh MMm SSs` (for example, `1h 08m 07s`). Keep the hidden duration marker and stored duration in integer seconds; visible and hidden values must represent exactly the same elapsed seconds. The parser continues to accept historical two-count checkpoints and visible `Ns` durations. The matching private trigger or capture binds the complete stack anchor. Hosted duration spans accepted trigger to attributable terminal result; CLI duration spans only the review process. Cooldown, preflight, sentinel wait, and delayed posting are excluded. Historical duration-less checkpoints and legacy private trigger/capture records remain readable, while evidence without the modern complete anchor cannot satisfy current taper.
- Finding decisions record accepted, routed, or rejected disposition and a concrete outcome or reason. Accepted work is fixed only when a verified correction is published or is already implemented with useful proof. Routed work names its destination without asserting that owner's acceptance or fix. Target-route disposition never changes the source PR's counts. Reporting never authorizes review, CI mutation, thread resolution, merge, or task resumption.
- After each review/fix run, report raw/useful counts, significance, dispositions, current channel target, and whether another review is justified. Use proportionate validation/runtime proof from [Validation And Runtime Proof](./validation-and-runtime-proof.md), without duplicating existing evidence.
- Under an explicit Overseer arrangement, the Overseer periodically samples accumulated decisions and receives meaningful milestones rather than per-round noise. Preserve the existing private per-PR review note required by [AI delegation and review](./ai-delegation-and-review.md#independent-review-evidence) when a separate model-review programme is explicitly assigned.

## Review Completion Criteria

- Define a coherent capability or correction scope and obtain an initial substantive review through the controller covering feature-bearing work and changed contracts.
- Resolve every known actionable finding, including current and outdated threads and summary-only or outside-diff findings, and verify each fix at the current head. Useful in-scope corrections to correctness, completeness, authority, alignment, maintainability, consolidation, or clarity remain actionable regardless of line size; judge worthwhile suggestions by their actual benefit against implementation cost and risk, including when they address neither a bug nor an existing design requirement, and do not relabel them optional merely to finish.
- Re-review new functionality, changed contracts, materially broader risk, or fixes that introduce independently reviewable behavior. Direct, verified corrections need not trigger another whole-PR discovery round solely to accumulate clean results.
- The channel defaults above are the controller's normal completion policy, not a quota target. Request work beyond a completed policy only for a concrete unresolved risk, coverage gap, or explicit human override. Repeated serious findings trigger focused investigation of their shared failure mechanism and appropriate proof rather than arbitrary clean-round accumulation.
- Under an explicit Overseer arrangement, present the Hosted/CLI trend and a nonblocking recommendation when marginal utility is uncertain. The Overseer—not the implementing lane or controller—decides whether an additional deliberate round is justified and whether merge-readiness handoff is reached.
- A PR is ready for an Overseer merge decision only after controller evidence shows zero unresolved current and outdated threads, all actionable summary-only and outside-diff findings are addressed, every open incoming route is dispositioned by the target owner, each fix is verified, every required channel has completed its review policy without provisional evidence, required CI is green, and proportionate validation/runtime proof is complete. Open routes from this PR to other owners do not hold its merge readiness. An explicit human stop advances only that channel's discovery queue; it remains a visible review limitation, not taper or merge-readiness proof. Before handoff, refresh stale title/body content and the generated marked LOC section with `python3 dev-tools/maintenance/cloc-report.py pr <number> [--repo owner/name] --update-pr`. The section is informational, not a size gate. If tooling is unavailable, record the limitation instead of inventing counts. Zero threads or GitHub `CLEAN` alone is insufficient, and the final head must not be described as reviewed when it was not. The implementing worker reports readiness without taking merge action; the designated Overseer may merge or enable auto-merge under the project owner's standing authorization after verifying the evidence.

## Change And Merge Policy

- Keep PRs coherent, including adjacent convergence. Use smaller PRs for isolated fixes; split independent or genuinely hard-to-review work, and split coherent work that exceeds a reviewer ceiling under the following rules.
- Hosted CodeRabbit reviews have a verified hard limit of 100 changed files; the controller refuses a Hosted request above that count and records a current provider skip as a Hosted limitation. The CLI review path has completed successfully with 111 changed files, but its upper limit is not established. Do not infer a CLI cap from the Hosted limit or from the plan page; verify any higher CLI boundary before documenting it.
- Before starting a canonical `dev-tools/pr-review` run, keep the Hosted reviewer-selected file count comfortably below 100 rather than targeting the exact limit. The CLI path may proceed above 100 when its own request-time checks pass. Useful review findings define required improvements, not optional scope: accepted useful findings remain implementation obligations in their canonical code, documentation, or proof owner. A provider limit may change branch topology or review boundaries, but never correctness, cleanliness, or which live issues are fixed; do not offset growth by dropping useful scope, packing unrelated helpers or tests into already-counted files, moving authority to a noncanonical owner, or changing runtime or design semantics.
- Treat reviewer ceilings as dynamic topology constraints. Prefer the fewest coherent, independently sound reviewable PRs that preserve every accepted finding and canonical placement under the cap; additional PRs add separate review, taper, and reconciliation costs, so narrowness or neat separation alone is insufficient. If the correct implementation exceeds the active ceiling, default to a coherent stack that preserves every finding and its proof; consolidate only when independently justified by cohesion and authority, without forcing unrelated work together. Do not target a hardcoded file count or preserve an arbitrary majority merely to stay under a cap. Use a scoped-review or CLI path only as an Overseer-adjudicated fallback when the change genuinely has no clean split or preserving the review boundary requires it. The ceiling changes review topology, never correctness or cleanliness.
- When a finding or proof moves to another PR, update its existing PR body and review disposition with the successor reference and check whether downstream already fixes it. After a split or reconstruction materially changes a reused PR's review scope, post one short comment such as **Review scope changed:** validator cleanup moved to #2731. Earlier counts cover the previous scope. Add `<!-- firemud-review-scope-change -->` below it; `dev-tools/pr-review` consumes that evidence and places the timestamped marker in its checkpoint timeline. Earlier evidence remains relevant to the previous patch boundary, and still-applicable findings remain obligations, while the event does not by itself require a fresh review streak or imply increased risk. An ordinary post-merge retarget with equivalent scope needs no reset comment. Do not create a new ledger.
- With an explicit Overseer arrangement, local isolated preparation of a concrete topology proposal may proceed, but publishing a split, new prerequisite or successor PR, or retargeting an existing PR requires Overseer approval, including routine cap cases. An approved proposal covers its planned routine retargets and publication without repeated approval and does not add a separate human approval requirement. Without an explicit Overseer arrangement, the human's selection of an active workstream provides standing authorization for routine, straightforward, scope-safe topology changes within that workstream, including cap splits, so those changes need no fresh approval. Continue them without repeated approval while preserving current work and review evidence. If proposing a materially more fragmented topology than a straightforward split (such as extra review stages), bring the Overseer a concise comparison of proposed scopes/dependencies and base-relative file counts, why the simpler topology does not work, and the benefit versus extra review cost; the Overseer adjudicates that consequential choice while safe independent work continues. Pause the topology decision and ask the Overseer with a concrete cut whenever clean split, ownership, or preservation is materially uncertain, the split introduces new product or architecture ambiguity or a consequential scope or topology decision, or the action falls outside the authorization; independent safe work continues where possible. During an active review, prepare review-invalidating fixes locally and wait for the review to finish before publishing them.
- Treat failing Renovate PRs as maintenance work: inspect CI and push the smallest compatible fix to its branch when possible; otherwise use a replacement branch with required compatibility changes.

## Branch And PR Hygiene

- Open or update a PR autonomously when an implementation branch reaches a coherent review checkpoint, subject to the topology and approval rules in [Change And Merge Policy](#change-and-merge-policy). Stacked PRs are acceptable when their base dependencies are explicit and they let independent work continue while CI or review runs. If the next authorized work is unambiguous and can be cleanly based on a merge-ready PR, continue autonomously in a stacked PR subject to those rules; a draft PR may expose in-progress work and should be marked ready at a coherent review checkpoint. After the parent merges, retarget the child to `develop` subject to those rules before rebasing or pushing. An explicit pause, unresolved human decision, or dependency requiring merged state stops continuation; do not create tiny placeholder PRs without review-worthy content.
- When active work moves to another worktree, report its absolute path and branch so the human's IDE context and delegated-worker paths remain aligned.
- When retargeting a stacked PR after its parent merges, change the base before rebasing or pushing the child. Required workflows listen for GitHub's `edited` event but run replacement validation only when `changes.base.ref` is present. The Validation, Security, and Smoke workflows use a separate per-run metadata-only concurrency group for title/body edits; those edits neither cancel an active substantive run nor repeat its tests. Their required gate jobs retain the exact branch-protection names and succeed on a metadata edit only after the shared preservation action verifies prior success for the same base/head tuple. The action allows a longer bounded wait only when it verifies an active substantive run or pending gate for that tuple; an absent, failed, stale, ambiguous, or spoofed predecessor remains fail closed. Gate preservation accepts a prior run with no GitHub PR association only when its canonical run title exactly binds the workflow, PR number, base SHA, and head SHA; older runs without that title remain fail closed.
- For recurring branch, worktree, and PR inventory, use `dev-tools/validation/report-worktree-pr-topology.sh` rather than ad hoc status commands. Renovate PRs are omitted from the selected inventory by default; the report records them in `omitted_renovate`, and `--include-renovate` opts them back in. Pass `--pr <number>` for a bounded direct base/dependent stack and `--json` for machine-readable evidence; selected reports correlate only exact branch/SHA identities and fail closed on ambiguous matches, while reporting local worktree dirtiness and unpublished or stale local heads.
- After a merge, remove its defunct local worktree and merged local/remote branch only after confirming no open PR or active stacked branch depends on it. Preserve unmerged branches and worktrees.
- Pass PR-body Markdown through a file or stdin with real newlines rather than literal `\\n` strings.
