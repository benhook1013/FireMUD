# Preview trust bootstrap

This is a prerequisite for the private Gateway–TCP Proxy bridge in #2713. It must be safe on `develop` with `previewStack.certificateIdentity.mode: standalone`: installing the issuance boundary does not activate the hosted identity controller or require public Telnet changes. The canonical hosted identity contract remains in [deployment environments](../../design/architecture/infrastructure/deployment-environments.md#hosted-identity-lifecycle); this page is the preview operator sequence and evidence checklist. It is not a production-CA procedure or a production-readiness claim.

## Required order

1. Apply the fixed `k8s/hosted-identity-controller/namespace.yaml` prerequisite, then install the scoped deployment, standalone certificate-writer, recovery, and admission resources from `k8s/trust-bootstrap` in this reviewed default-branch revision. Keep the existing controller inactive. Do not install `firemud-ca-issuer` or either `firemud-grpc-ca` Secret yet.
2. Replace the legacy `kube-system/preview-deployer` kubeconfig in trusted jobs with the five scoped credentials. For the initial proof namespace, run `bind-runtime-roles.sh` once with the explicit `system:masters` context because the proof namespace's exact runtime RoleBindings do not exist yet. After the manager credential has been provisioned and verified, run the same helper under the namespace-manager identity for later namespace bindings. Run `provision-scoped-kubeconfigs.py --context <system-masters-context> --apply --confirm --proof-namespace <pr-N> --runner-api-server https://host:port` under an explicit `system:masters` context to create, authenticate, RBAC-check, and publish fresh kubeconfigs as `TRUSTED_HOSTED_PREVIEW_NAMESPACE_MANAGER_KUBECONFIG`, `TRUSTED_HOSTED_PREVIEW_RUNTIME_KUBECONFIG`, `TRUSTED_HOSTED_STANDALONE_CERTIFICATE_KUBECONFIG`, `TRUSTED_HOSTED_IDENTITY_REQUESTER_KUBECONFIG`, and recovery-only `TRUSTED_PREVIEW_CA_RECOVERY_KUBECONFIG`. Interpret this URL from the trusted job's self-hosted runner network: loopback is valid only when that runner shares the Kubernetes API host or network namespace; it is not inferred from the operator's kubeconfig. Supply the actual endpoint reachable by the trusted hosted runners; the helper rejects unspecified addresses, malformed hosts, URLs with credentials, and URLs with a path, query, or fragment. It keeps the selected context's embedded CA for normal TLS verification. Its operator-side `whoami` and RBAC probes do not establish connectivity from the hosted runner, so activation also requires the secret-consuming workflow's access check to pass on that runner. This staging operation leaves the legacy credential intact so a publication failure cannot remove the only working deployment path. If `gh secret set` may have accepted a value but the helper reports failure, it retains the token Secret and prints the fixed credential and Secret name. Retry only that credential with `--context <system-masters-context> --apply --confirm --proof-namespace <pr-N> --runner-api-server https://host:port --credential <fixed-service-account> --reuse-token-secret <reported-token-secret>`; the helper verifies the current ServiceAccount UID, exact token Secret identity and ownership metadata, embedded CA, authenticated identity, and RBAC probes before republishing. It refuses a mismatched or incomplete Secret and never silently creates a replacement during this retry. The successful publication proof is required before token rotation or finalization. After the reviewed workflow split is on `develop`, run its separately confirmed `--finalize` operation with the same explicit `system:masters` context and runner endpoint: it stages and verifies all five credentials, rotates prior provisioner tokens, deletes only the exact legacy ClusterRoleBinding, ServiceAccount and token Secrets, removes the repository-scoped `PREVIEW_KUBECONFIG`, and proves the old identity cannot read a Secret, create a CertificateRequest, or change an Issuer. A manifest change or secret-name check alone is not rotation proof.
3. With the live issuer still absent, prove the `Deny` bindings are active and the cluster's actual RBAC/admission response rejects direct `CertificateRequest` creation and approval/status mutation, malformed or unauthorized `Certificate` creation, and issuer aliases/rewrites. Include omitted `issuerRef.group` and kind variants. Prove that the fixed standalone writer's canonical Certificate shape is admitted, while a changed SAN, usage, issuer, namespace, or name is denied. Record commands, caller identity, target namespace, response, and cleanup without logging a CSR private key or Secret data. Use server-side dry-run for negative cases where possible.
4. Prepare the separate recovery-only GitHub Environment `trusted-preview-ca-recovery`. It is restricted to `develop` and is never selected by a PR-controlled or routine deployment job. Provision its dedicated recovery kubeconfig, `FIREMUD_PREVIEW_CA_RECOVERY_BUNDLE` secret, and non-secret fingerprint/context variables. Test the recovery script's bundle validation, exact two-Secret reconstruction, refusal on a missing admission binding or surviving legacy credential, and the trusted `verify` workflow. Before the canonical CA exists, use disposable test material for this procedure; no test key may be installed as `firemud-grpc-ca` in the shared cluster.
5. Only after steps 1–4 have live evidence, generate a new preview-only RSA-4096 CA in a private, ephemeral operator directory. Use an unencrypted PKCS8 private key, critical `BasicConstraints CA:TRUE,pathlen:0`, critical `KeyUsage keyCertSign`, SHA-256, and 730-day validity. Do not use a cert-manager self-signed issuer to create the root. Compute the lowercase SHA-256 fingerprint of the DER certificate. Pipe `recover-firemud-ca.py pack` directly to `gh secret set FIREMUD_PREVIEW_CA_RECOVERY_BUNDLE -e trusted-preview-ca-recovery` without printing or retaining the bundle; set the fingerprint as a protected Environment variable. The GitHub Environment secret is the encrypted out-of-cluster recovery copy. Verify that copy through the trusted workflow before removing the ephemeral operator files. Do not put the key, bundle, or kubeconfig in a PR, Actions artifact, log, issue, chat, user PC, or password manager.
6. Run the reviewed recovery workflow's `restore` operation on `develop`. It accepts only the dedicated recovery ServiceAccount, the explicitly selected Kubernetes context, all eight live fail-closed admission bindings, and a revoked legacy ServiceAccount/ClusterRoleBinding. It writes only `firemud-system/firemud-grpc-ca` (`Opaque`, `ca.crt`/`ca.key`) and `cert-manager/firemud-grpc-ca` (`kubernetes.io/tls`, `tls.crt`/`tls.key`), then compares exact bytes through private readback. The copy is never printed. Install the fixed `firemud-ca-issuer` only after this recovery and readback pass.
7. With the controller still inactive, request the fixed standalone internal Gateway and TCP Proxy Certificates through the scoped writer, then request the eight standalone per-workload gRPC Certificates (five publication workloads, Account, Game Session, and Social Groups) for `dev` and a disposable `pr-N` namespace through that same writer. Observe `Ready`, key-complete output Secrets, and served transport identities/chains. The runtime workflow consumes only the projected leaf keys and public `ca.crt`; after validating every gRPC leaf it deletes the legacy runtime `firemud-grpc-ca` signing-key Secret and old static leaf-source Secrets. The admission exception supports this cleanup and namespace-controller garbage collection of legacy runtime copies, but its authorization result alone does not prove the workflow validated every leaf or that garbage collection met the Namespace UID fence. Keep those proofs with the owning runtime and lifecycle evidence. Repeat unauthorized direct CertificateRequest and Certificate tests after the issuer becomes Ready; an admission-only dry-run before issuance is not proof that unauthorized signing cannot occur. Retain only non-secret evidence. Controller bootstrap and the #2713 private-bridge rollout are later gates. The standalone preview/dev-demo gRPC paths fail closed until this issuer bootstrap and live denial proof are complete.

## Isolated namespace cleanup proof

This proof validates only the namespace-manager credential and one disposable runtime-namespace deletion. It does not complete the trust bootstrap, activate ordinary deployment workflows, retire `preview-deployer`, or authorize CA or issuer installation. The existing `deployment-rbac.yaml` and `deployment-admission.yaml` contain the 11-resource manager-stage subset; there is no separate Kustomize target. Keep the controller inactive and leave the remaining trust-bootstrap resources unapplied for this proof.

Before publishing the manager credential, disable the ordinary manager consumers using GitHub's reversible workflow controls: `preview-janitor.yml`, `preview-reconciler.yml`, `dev-demo-reconciler.yml`, `dev-demo.yml`, and `hosted-identity-request.yml`. Disabling prevents new triggers but does not stop executions already queued, pending, waiting for Environment approval, or running. Drain or cancel every nonterminal execution of all five workflows, then immediately before publication verify that none remains, including queued, pending, and Environment-waiting runs or jobs. Leave all five disabled after the proof until a separately approved activation. The isolated `preview-cleanup-proof.yml` workflow is the only manager consumer during this stage. Do not run the janitor or reconciler as a targeted proof; both process broader lifecycle state.

Under the explicit `system:masters` context, apply only `k8s/trust-bootstrap/deployment-rbac.yaml` and `k8s/trust-bootstrap/deployment-admission.yaml`. Select a real same-repository closed PR with an unused `pr-N` namespace. Create a fresh empty namespace named `pr-N` with `firemud.dev/preview: "true"`, `firemud.dev/pr-number: "N"`, and annotation `firemud.dev/cleanup-proof: "true"`. Capture its Namespace UID. Run `dev-tools/hosted/trust-bootstrap/bind-runtime-roles.sh pr-N` under that same operator context; the helper creates or validates only the exact runtime and standalone-certificate-writer RoleBindings. Do not add workloads or other namespace resources.

Provision only the namespace-manager credential under the explicit operator context, using the proof namespace and an operator-verified runner-reachable TLS endpoint: `python3 dev-tools/hosted/trust-bootstrap/provision-scoped-kubeconfigs.py --context <system-masters-context> --apply --confirm --proof-namespace pr-N --runner-api-server https://host:port --credential firemud-preview-namespace-manager`. The endpoint is interpreted from the self-hosted preview runner's network and keeps the selected context's CA for normal TLS validation. The provisioner verifies the exact manager identity, `get namespaces=yes`, `delete namespaces=yes`, and `get secrets in pr-N=no`; it publishes only `TRUSTED_HOSTED_PREVIEW_NAMESPACE_MANAGER_KUBECONFIG` to `trusted-hosted-cluster`. GitHub's Environment branch restriction must admit only `develop`; the provisioner verifies that exact policy for the configured protected environments. The Kubernetes service-account-token Secret has no configured expiry, so it remains an active grant until it is rotated or explicitly revoked.

Dispatch `Preview Runtime Cleanup Proof` from `develop` with the closed PR number, its exact current head SHA, and the captured Namespace UID. The workflow uses the self-hosted preview runner, verifies the exact namespace-manager username, `get namespaces=yes`, `delete namespaces=yes`, and `get secrets in pr-N=no`, then rechecks that the PR is closed and both head and base belong to this repository. Immediately before deletion it requires the namespace name, UID, canonical preview labels, and cleanup-proof annotation to match the supplied inputs. It passes the captured UID through the existing `prune-stale-preview-namespaces.sh --delete-runtime` path; the shared deletion helper refuses a changed UID and uses the captured value as the Kubernetes DELETE precondition. It requires a subsequent Namespace `NotFound`. It does not retire hosted identity, read Secret data, touch `dev`, or delete another namespace.

The [runtime and retained identity lifecycle boundary](../../design/architecture/infrastructure/deployment-environments.md#hosted-identity-lifecycle) keeps garbage collection subject to the fixed caller, namespace, and object predicates. DELETE admission checks use `oldObject.metadata.name`: Kubernetes collection deletion supplies each stored object while omitting the request name. CEL type-checking and an accepted Namespace DELETE do not establish successful content garbage collection or Namespace `NotFound`; the isolated proof must observe that final result with the policies still installed. This also applies to the reserved CA Secret and dormant hosted identity admission policies; correcting their source does not authorize installing them during the 11-resource manager stage.

Afterward, keep ordinary manager consumers suspended. To abandon the stage, first revoke the manager Environment secret and its exact provisioner-owned token Secret; only then may an operator remove the staged policy and RBAC resources. If `gh secret set` may have accepted the value before reporting failure, retain the token and recover by rerunning only the manager credential with `--credential firemud-preview-namespace-manager --reuse-token-secret <reported-token-secret>` and the same proof namespace and endpoint. Do not mint a replacement or remove the admission boundary while a published token may still be active. Preserve the legacy credential throughout; this proof is not `--finalize` and does not establish permission to migrate or activate any ordinary workflow.

## Recovery copy and rotation

`FIREMUD_PREVIEW_CA_RECOVERY_BUNDLE` is a versioned JSON envelope with base64 PEM certificate and private key plus the public SHA-256 fingerprint. It is stored only as a GitHub Environment secret; the expected fingerprint is a separate Environment variable and must also match the deployed controller trust anchor. `preview-ca-recovery.yml` checks out only `develop`, selects only the recovery Environment, and accepts `verify` or `restore`. The script refuses malformed, mismatched, expired, non-RSA-4096, non-CA, or non-self-signed material. A fresh cluster first installs the same reviewed admission/RBAC boundary and reissues a scoped recovery kubeconfig; it must not reuse a token from the lost cluster. The recovery copy is independently usable without the original operator machine or password manager.

The preview root is valid for 730 days. Schedule expiry alerts at 180, 90, and 30 days and an operator-led replacement before expiry. Reissue every dependent leaf, update the protected recovery bundle and fingerprint, prove the new copy's verify/restore path, and only then change the controller trust anchor. Do not rotate one Secret copy independently. A separate future production environment must use a separate CA, protected GitHub Environment, scoped kubeconfig, recovery bundle, fingerprint, and live proof; reusing this procedure is not evidence that production is ready.

Scoped deployment kubeconfigs use dedicated ServiceAccount token Secrets labeled and annotated by the provisioning helper. Rotate them by staging a new verified token and Environment secret first; only after publication and RBAC proof does the helper remove older helper-owned tokens for that identity. Never overwrite or hand-edit a kubeconfig value, reuse the removed `preview-deployer` token, or delete a token before its replacement is verified.
